Local URLs, routing and HTTPS

Fix CORS errors between app.localhost and api.localhost

Two names that end in .localhost are two origins. The browser enforces that even though both live on your laptop.

A page on http://app.shop.localhost calling http://api.shop.localhost is a cross-origin request, because an origin is scheme plus host plus port and the hosts differ. The browser blocks the response unless the API sends Access-Control-Allow-Origin with the page's exact origin. Fix it on the API, not in the frontend, and handle the preflight OPTIONS request too.

What the browser actually checks

The request usually reaches your API and your API usually answers. The browser then refuses to give the response to your JavaScript, and logs a CORS error. That is why the API log looks fine while the page fails. Three rules matter:

  • Origin match. http://localhost:3000, http://localhost:4000 and http://app.shop.localhost are three different origins. Changing the port changes the origin.
  • Preflight. For a request with a JSON Content-Type, an Authorization header, or a method other than GET, HEAD and POST with simple content types, the browser first sends OPTIONS. The API must answer it with 2xx and the allow headers, before any auth check.
  • Credentials. If the fetch uses credentials: "include", the API must answer with the exact origin (not *) and Access-Control-Allow-Credentials: true.

A local-dev CORS setup

With Express and the cors package:

import cors from "cors";

const allowed = [
  "http://localhost:3000",
  "http://app.shop.localhost",
];

app.use(cors({
  origin: (origin, cb) => cb(null, !origin || allowed.includes(origin)),
  credentials: true,
}));

Requests with no Origin header (curl, server to server) pass. Browser requests pass only from the allowed list. If you change the ingress port, the origin changes too, so http://app.shop.localhost:8080 must be listed if that is what you use. Read the allowed list from an environment variable so each developer can change it without a code edit.

Avoid origin: "*" together with credentials: browsers reject that combination. Avoid reflecting any origin with credentials on in a service that could ever leave your laptop.

The Flisk way

In the Docker path, the frontend runs on app.<project>.localhost and each backend on api.<project>.localhost/api/<name>, so every call from the page to the API is cross-origin. Flisk's troubleshooting guide says what to expect:

  • A backend scaffolded by flisk resource already allows browser origins on *.localhost subdomains. The rule is in the generated source.
  • A backend of your own (bring-your-own, or brought in with flisk import) must allow http://app.<project>.localhost itself.
  • When Traefik is not on port 80, the port is part of the origin. Add it.

The frontend gets the API address from a generated variable, VITE_API_URL (NEXT_PUBLIC_API_URL for Next.js), so you do not type the URL in your code. If a call fails, read that value in the browser first. flisk networks lists the URLs that should answer, and flisk doctor warns when a frontend calls localhost:<backend port>, because the Docker stack does not publish backend ports on your machine.

For a project of local processes, with no gateway, the frontend runs on http://localhost:3000 and the API on http://localhost:4000. Allow the frontend's origin in the API's CORS and give the frontend the API URL through env in its service.json.

How to debug it

  1. Open devtools, Network, and click the failed request. Is there an OPTIONS request before it? What status did it get?
  2. Compare the request's Origin header with the allowed list, character by character, including port and trailing slash (an allowed origin has no trailing slash).
  3. Run the preflight by hand: curl -i -X OPTIONS http://api.shop.localhost/api/orders -H "Origin: http://app.shop.localhost" -H "Access-Control-Request-Method: POST". You should see the allow headers in the answer.
  4. Check that an error page from the proxy (404, 502) is not the thing missing the headers. A proxy error has no CORS headers, and the browser reports it as a CORS failure.

When to avoid CORS entirely

If the frontend and API sit behind one origin, there is nothing to configure. Use a dev-server proxy or a path-routing reverse proxy for the browser calls.

If the browser errors point to cookies rather than headers, see secure cookies on localhost. To compare the layouts, read path prefix or subdomain routing, and for the whole frontend and API setup, how to run a frontend and an API together locally.

Questions people ask

Why does the API log show success but the browser shows a CORS error?

The API answered, but without the Access-Control-Allow-Origin header for the page's origin, so the browser hides the response from your code.

Are two *.localhost names the same origin?

No. An origin is scheme, host and port, so app.shop.localhost and api.shop.localhost are different origins and need CORS.

Why does a 502 from the proxy look like a CORS error?

Error pages generated by a proxy carry no CORS headers, so the browser reports the missing header. Check the status code in the Network tab first.
