Where to store a shopping cart: Redis or Postgres?

A cart is temporary data with a short life and a few awkward rules. Both stores work. Here is how to choose and what each one costs you.

Store the cart in Postgres if you already run it and carts are small: it gives you one transaction boundary with orders and nothing extra to operate. Store it in Redis if you want automatic expiry and very fast reads for anonymous visitors. Either choice works; what matters more is deciding the cart rules up front: when it expires, how guest and user carts merge, and whether prices are copied.

What a cart actually needs

A cart is a list of (variant, quantity) pairs owned by a customer or by an anonymous browser. Four rules decide most of the design:

  • Lifetime. Guest carts should disappear after days or weeks. User carts can live longer.
  • Identity. A guest has only a cookie. The cart key is a random ID in that cookie, not a database row number.
  • Merge. When a guest signs in and already has a saved cart, you must combine the two.
  • Prices. A cart should store quantities and variant IDs, and read the current price when you show it. Copy the price into the order line only at checkout.

Cart in Postgres

CREATE TABLE carts (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id bigint,
  updated_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE cart_items (
  cart_id    uuid   NOT NULL REFERENCES carts(id) ON DELETE CASCADE,
  variant_id bigint NOT NULL,
  qty        int    NOT NULL CHECK (qty BETWEEN 1 AND 99),
  PRIMARY KEY (cart_id, variant_id)
);

Adding an item is one upsert: INSERT ... ON CONFLICT (cart_id, variant_id) DO UPDATE SET qty = LEAST(cart_items.qty + EXCLUDED.qty, 99). You can join to products to validate that the variant still exists, and checkout reads the cart in the same transaction that creates the order. The cost is cleanup: nothing expires on its own, so a scheduled job must delete carts whose updated_at is older than your limit.

Cart in Redis

A hash per cart is the natural shape. The field is the variant ID and the value is the quantity:

HINCRBY cart:7f3a variant:42 1
EXPIRE  cart:7f3a 1209600     # 14 days, refreshed on every change
HGETALL cart:7f3a

Expiry is free, reads are fast and abandoned guest carts clean themselves up. The costs are real, though. Redis is not where your other data lives, so you cannot join to products or validate stock in the same query. If Redis restarts without persistence you lose every cart. And your analytics on abandoned carts need a second path, because expired keys are gone.

Merging a guest cart on login

The rule most shops want is: add quantities, cap at a maximum, and delete the guest cart. Do it in one place, once, right after the login succeeds. In Redis, read both hashes, sum the fields in your code and write the result to the user's key. In Postgres, run it in a transaction: insert the guest items into the user cart with the same upsert, then delete the guest cart. Test the case where both carts contain the same variant, and the case where the user cart is empty.

Running Redis next to your API with Flisk

If you choose Redis, Flisk can start it with the rest of the stack:

flisk resource cache --type database --framework redis --stack shop --yes

This writes a service.json for a redis:7.4-alpine container with a redis-cli ping health check, a cache-data volume, and a provides entry of REDIS_URL: redis://cache:6379. A service that lists cache in dependsOn receives that REDIS_URL, so your cart code reads one environment variable:

"appName": "cart-api",
"dependsOn": ["cache"]

Two things to know. Redis is not published on your host, so inspect it with docker exec into the container, not with a redis-cli on your laptop. And flisk down --purge deletes volumes, which empties every cart. Details are in running Redis for local development.

How to choose

QuestionPostgresRedis
Automatic expiryNo, needs a jobYes, with EXPIRE
Same transaction as the orderYesNo
Survives a restartYesOnly with persistence on
Extra service to runNoYes
Abandoned-cart analysisEasyNeeds an export

For a first version, Postgres is usually the better default: fewer moving parts, and the cart is in the same place as everything you need to join. Add Redis when read traffic on anonymous carts is a measured problem, not before.

Whichever store you pick, the cart ends when checkout begins. The next step is turning it into an order without selling stock twice; see stopping overselling at checkout.

Questions people ask

Should the cart store prices?

Store the variant ID and quantity, and read the current price when you display the cart. Copy the price into the order line at checkout so later price changes do not alter past orders.

How long should a guest cart live?

Common choices are 7 to 30 days. Refresh the expiry on every change so active carts stay alive.

Can I keep the cart in a cookie or localStorage?

For a very small shop, yes. You lose server-side merging, stock checks and abandoned-cart analysis, and the client can edit it, so the server must re-validate everything at checkout.
