RAG and vector databases locally

How to generate embeddings locally with Ollama, no API key

A local embedding model costs nothing per call, works offline and keeps your documents on your machine. Setting it up takes one container and one pull.

Run Ollama, pull an embedding model with ollama pull nomic-embed-text, then POST your text to /api/embed. You get back one vector per input string. No API key and no network access to a paid service is needed, and the model stays on your disk. Embeddings are small enough to compute on a CPU.

Pick a model and note its dimension

The model fixes the vector length, and your vector database must be created with that exact size. Common local choices:

  • nomic-embed-text: 768 dimensions, a good general default for English text.
  • mxbai-embed-large: 1024 dimensions, larger and usually a little better, a little slower.
  • all-minilm: 384 dimensions, very small and fast, weaker on hard retrieval.

Check the model page for its dimension and its recommended prefixes. Some models, including nomic-embed-text, are trained with a task prefix such as search_document: for stored chunks and search_query: for questions. Using them consistently often improves retrieval, and mixing them up quietly hurts it.

Run Ollama and call the API

docker run -d --name ollama -p 11434:11434 \
  -v ollama-models:/root/.ollama ollama/ollama

docker exec ollama ollama pull nomic-embed-text

curl http://localhost:11434/api/embed \
  -d '{"model": "nomic-embed-text", "input": ["search_document: Refunds take 5 days."]}'

The response has an embeddings array with one vector for each string in input. Send many chunks in one request, for example 32 at a time, instead of one request per chunk. Ollama also serves an OpenAI-compatible /v1/embeddings route, which lets code written for the OpenAI SDK point at http://localhost:11434/v1.

The named volume on /root/.ollama matters. Without it the pulled model is deleted with the container, and the next start has to download it again.

The Flisk way

Flisk has an inference resource type for exactly this container:

flisk resource embed --type inference --stack rag --yes

It writes a bring-your-own service.json with the image ollama/ollama, port 11434 and /v1/models as the health path. Other services in the stack reach it at http://embed:11434, the resource name being its host name on the Docker network. The preset mounts no volume, so add one yourself, as in the Docker command above:

{
  "schemaVersion": 1,
  "appName": "embed",
  "appType": "bring-your-own",
  "stack": "rag",
  "port": 11434,
  "healthCheckPath": "/v1/models",
  "image": "ollama/ollama",
  "exposeViaProxy": false,
  "volumes": [{ "source": "ollama-models", "target": "/root/.ollama" }]
}

Start the stack with flisk up rag, then pull the model inside the running container with Flisk's one-off command runner:

flisk run embed -- ollama pull nomic-embed-text

With the volume in place, flisk down keeps the model, so you pull once. Without it, you pull again after every flisk up.

Check that the vectors are sane

Before you embed a whole corpus, embed three sentences and look at the result. The array length must equal the dimension you gave your vector database. Two paraphrases should be closer to each other than to an unrelated sentence, which you can check with a cosine similarity in a few lines. If similar sentences do not score higher than unrelated ones, something is wrong: a missing prefix, the wrong model name, or a text that was cut off by the input limit. A thirty-second check here saves an hour of confusing retrieval results later.

Also time one batch. A batch of 32 short chunks tells you roughly how long a full corpus will take, and lets you decide whether to run Ollama on the host instead of in a container.

Pitfalls

  • No GPU in a Mac container. Docker on macOS cannot use the GPU. Embedding small batches on a CPU is fine, but a large corpus is faster if you run Ollama directly on the host and point your code at http://host.docker.internal:11434 or run your services as local processes.
  • Never mix models in one index. Vectors from two models are not comparable, even when the sizes match. See re-embedding after a model change.
  • Model not pulled yet. A request for a model that is missing returns an error, so make your ingestion script fail loudly, or check /api/tags first.
  • Input length. Each model has a context limit. Text beyond it is cut off, so chunk first, as described in chunking documents for RAG.

Next step

With vectors coming out of Ollama, store them in a database, such as Qdrant. For a local chat model on the same server, see how an agent can call it in running an AI agent locally with tools.

Questions people ask

Which Ollama model should I use for embeddings?

nomic-embed-text (768 dimensions) is a good default. mxbai-embed-large is larger and often a bit better, and all-minilm is tiny and fast.

Do I need a GPU to compute embeddings?

No. Embedding models are small and work on a CPU. A GPU only matters when you embed a very large corpus.

Can I use the OpenAI SDK with Ollama embeddings?

Yes. Ollama exposes an OpenAI-compatible /v1/embeddings route, so you can set the SDK base URL to your Ollama server and pass the model name.
