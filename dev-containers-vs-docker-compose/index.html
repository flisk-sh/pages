Dev Containers vs Docker Compose: what each one is for

They are often compared, but one standardizes the developer's toolbox and the other runs the app's parts.

A dev container is the environment you work in: the compiler, the CLI tools, the editor extensions. Docker Compose runs the services your app talks to: the API, the database, the queue. They answer different questions, so the usual setup is both, with the dev container pointing at a Compose file. Choose one alone only when your project is small enough to need just that half.

What a dev container does

The Dev Containers specification describes a .devcontainer/devcontainer.json file. Editors that support it (VS Code, JetBrains products, GitHub Codespaces and the devcontainer CLI) read the file, build or pull an image, start a container and attach your editor to it. You get the same Node, Python or Go version, the same linters and the same extensions as everyone else, without installing them on the host. Useful fields include image or build, features (reusable install steps), forwardPorts, postCreateCommand and customizations.

{
  "name": "shop",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:22",
  "forwardPorts": [3000, 4000],
  "postCreateCommand": "npm install"
}

On its own this gives you a toolbox. It does not start your database or your other services.

What Compose does

Compose starts and wires containers from a compose.yaml: images, networks, volumes, environment, health checks and startup order. It has no idea which editor you use and no opinion about your toolchain. See Compose depends_on and healthchecks for the ordering part.

Using them together

The spec lets a dev container use a Compose file through dockerComposeFile, service and workspaceFolder. Your editor attaches to one Compose service (the workspace), and the other services start beside it.

{
  "name": "shop",
  "dockerComposeFile": "../compose.yaml",
  "service": "workspace",
  "workspaceFolder": "/workspaces/shop"
}

Inside the workspace container, the other services are reachable by their Compose service names, for example db:5432. That is the main practical gain: no host port juggling for tool-to-service traffic.

How to decide

SituationChoose
Your pain is "works on my machine" for tool versionsDev container
Your pain is starting five services in the right orderCompose, or another orchestrator
New hires lose a day installing things, and the app also has a databaseBoth
You use an editor that does not support dev containersCompose plus a documented tool list
Docker Desktop licensing or RAM is a concernWeigh the cost: a dev container is another container on top of your services

Where Flisk fits

Flisk does not install your toolchain, and it does not provide an editor environment. It starts the app's services. That makes it a companion to a dev container rather than an alternative to one. Flisk's own docs describe running it inside a dev container: the container brings Node, Go or Python, and flisk up brings the stack. Inside a container, flisk doctor reports where it runs (local, wsl2, devcontainer, codespaces and others) and whether a container runtime is reachable.

The detail to plan for: Flisk's container path needs Docker reachable from where you run it. In a dev container that usually means adding the Docker-outside-of-Docker or Docker-in-Docker feature. If your services run as plain local processes (each service.json has a command), that requirement disappears, which keeps a dev container light. See run local services without Docker.

Pitfalls

  • Bind-mount speed. On macOS and Windows, file access across the VM boundary can be slow for large node_modules trees. Use a named volume or clone the repo into the container's filesystem.
  • Docker inside a container. Mounting the host Docker socket gives the container control of the host daemon. Know that trade-off before you enable it.
  • Rebuild habits. Changes to devcontainer.json need a container rebuild. Put one-time setup in postCreateCommand, not in your head.
  • Forwarded ports. A port listed in forwardPorts is forwarded by the editor, not published by Docker. Scripts outside the editor may not see it.

If the remote side matters more than the container, read Codespaces vs local development next.

Questions people ask

Do I need Docker Compose with a dev container?

Only if your app needs other services such as a database. A single-service project can use just devcontainer.json.

Can a dev container start my database?

Yes, by pointing dockerComposeFile at a Compose file that defines it. The dev container spec supports Compose services as the workspace.

Do dev containers replace local installs?

For the toolchain, yes. They do not replace the tools that start and connect your services, which is the job of Compose or a similar orchestrator.
