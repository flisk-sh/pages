Databases in local development

How to reset a local database: drop, recreate, restore

Resetting a local database is routine, but the commands differ in how much they destroy. Pick the smallest one that fixes your problem.

Reset at the smallest level that fixes the problem. Drop and recreate one database if only its data is bad, delete the whole volume if Postgres itself is in a bad state, and restore a saved dump if you want a known-good starting point. Nothing here is safe against a shared or production database.

Level 1: reset one database

Postgres will not let you drop a database while someone is connected to it, and your API probably is. From version 13, WITH (FORCE) disconnects them first. Connect to a different database, such as postgres, and run:

docker exec my_shop_postgres psql -U my_shop -d postgres \
  -c "DROP DATABASE my_shop_store WITH (FORCE)"
docker exec my_shop_postgres createdb -U my_shop -O my_shop my_shop_store

That is a Flisk-shaped example: project my-shop, stack store, container my_shop_postgres. Use docker ps to find your container and \l inside psql to confirm the database name. The database is now empty, with no tables. Run your migrations again, then the seed. With the Prisma scaffold that means flisk restart orders-api-migrator. Restart the API afterwards so it drops its old connections.

Prisma has its own shortcut, prisma migrate reset, which drops the database, applies every migration and, in older versions, runs the seed. Drizzle has no reset command, so use the SQL above.

Level 2: delete the volume

When the whole Postgres is in a strange state, or you want every stack back to zero, remove the data volume. In plain Docker that is docker rm -f NAME followed by docker volume rm VOLUME. With Flisk:

flisk down --dry-run
flisk down --purge
flisk up

--dry-run shows what would be removed first, which is worth running once. flisk down alone stops the stack and keeps the volumes. --purge deletes the volumes, networks and images, so every database in the project is gone, not just one. After flisk up Postgres starts on an empty volume and your migrator and seed run from the beginning.

One thing to know before you purge: the Postgres password is read from DB_PASSWORD in the project .env and is generated once. It is not rotated. A purge creates a new database with the same password, so your connection strings stay valid. If you ever change DB_PASSWORD without purging, the existing volume keeps the old one and logins fail. flisk doctor warns about the mismatch.

Old projects leave volumes behind when you delete their folder. flisk projects --stale lists them, and adding --prune cleans them up. Run it without --prune first and read the list.

Level 3: restore a snapshot

If a clean reset takes ten minutes of migrating and seeding, save a good state once and restore it in seconds. Dump in the compressed custom format:

docker exec my_shop_postgres pg_dump -U my_shop -Fc my_shop_store > good.dump

Restore it over a database with the right name:

docker exec -i my_shop_postgres pg_restore -U my_shop -d my_shop_store \
  --clean --if-exists --no-owner < good.dump

--clean --if-exists drops each object before it recreates it, so the restore works on a database that already has tables. --no-owner avoids errors if the dump came from a different user. Keep dumps out of git unless they contain only fake data. If you take the dump from someone else's environment, check it for real personal data first.

Before you reset

Ask what you are fixing. A failed migration usually needs only Level 1. A pile of junk rows from testing needs Level 1 and a seed. A corrupted container, a forgotten password, or a project you want to wipe completely needs Level 2. If you reset often, take the dump from Level 3 once, right after a good seed, and restore it each time. The restore is faster than replaying every migration, and it gives your whole team the same starting point.

Pitfalls

  • Dropping the database you are connected to. The command fails. Connect to postgres as shown above.
  • Forgetting the app's connections. Connection pools keep their old sessions. Restart the services that use the database.
  • Migration history out of sync. If you reset the schema but not the migration table, your tool believes the work is done. Reset both together, which dropping the whole database does.
  • Purge is wider than you think. It removes every volume in the project, including Redis data. See keep volumes between runs for how to protect the ones you care about.

After a reset, bring the data back with seed a local database. If the migrator will not run after a reset, see service will not start.

Questions people ask

What is the difference between flisk down and flisk down --purge?

flisk down stops the stack and keeps volumes, so your data survives. --purge also deletes volumes, networks and images, which empties every database in the project.

How do I reset only one database in Flisk's shared Postgres?

Connect to the postgres database, run DROP DATABASE name WITH (FORCE), then createdb it again and re-run your migrations. Other stacks' databases are untouched.

Is there a flisk db reset command?

No. Use the SQL steps above, your ORM's reset command, or flisk down --purge.
