Coding agents in practice

What to do when a coding agent is stuck in a loop

Spot the signs of a coding agent going in circles, then break out by resetting context, narrowing the task, adding a failing test or switching approach.

When an agent repeats the same failed fix, stop it. More turns rarely help. Read what it is actually seeing, shrink the problem, give it a failing test or a new fact, and if that fails, restart in a fresh session with a better brief.

Signs of a loop

  • The same command fails three times with the same error.
  • It undoes and redoes the same edit.
  • It "fixes" a test by changing the test, then breaks another one.
  • It claims success while the command output says otherwise.
  • It starts guessing at library options or file paths.

Stop at the second repeat. Every extra attempt adds noise to the context and cost to the bill.

Step 1: read the evidence

Find the first real error, not the last. Often the root cause is above a long stack trace. Reproduce the failure yourself. Many loops come from a fact the agent lacks: a missing environment variable, a service that is not running, a version mismatch, or a file in a different place.

Step 2: change the problem

Options, from cheapest to most drastic:

  1. Give the missing fact in one sentence: "the database is not running, start it with docker compose up -d db first".
  2. Narrow the task: "ignore the other failures, make only this test pass".
  3. Ask for diagnosis only: "do not edit any files, explain what you think is wrong and what you would check".
  4. Write the failing test yourself and ask the agent to make it pass.
  5. Try a different approach: "do not patch this function, replace it with the library call in the docs".

Step 3: reset

A long, confused conversation hurts the model. Save what you learned, discard the failed changes with git restore . or git stash, and start a fresh session with a brief that includes the lessons: what you tried, what failed, and why. Many agents can also compact or clear the conversation. See context limits in long sessions.

git stash push -u -m "agent attempt 1"
# new session, new brief, includes: "do not use approach X, it failed because Y"

Prevent the next one

Set a rule: after two failed attempts, the agent must stop and report. Put it in your project instructions file. Make environment setup a single documented command. And keep tasks small, because big tasks produce the longest loops. When the model keeps failing at one kind of work, do it by hand, or use a different tool for that part.

Know when to stop using the agent

Some tasks are poor fits: obscure hardware, a bug that only appears in production, work that depends on knowledge only in people's heads. If you have spent more than a few attempts, do the hard part yourself and give the agent the mechanical rest. That is a sensible split, not a failure.

Questions people ask

Is switching to a stronger model the answer?

Sometimes, but first check for missing facts and an unclear goal. A better model with the same bad brief often fails the same way.

Should I let it run longer to see if it recovers?

Rarely. If the same error appears twice, intervene.
