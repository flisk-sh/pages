pnpm workspace: how to run several services at once

A pnpm workspace gives you one install and one lockfile. It does not decide which services start, in what order, or where their logs go. Here is how to cover that.

To run several services from one pnpm workspace, list the folders in pnpm-workspace.yaml, give every service a dev script, and start them with pnpm -r --parallel run dev. Use --filter when you want only some of them. That works well for two or three services; past that, start order and mixed logs become the problem.

Set up the workspace

A pnpm workspace is a folder with a pnpm-workspace.yaml at the root. It lists which folders hold packages:

packages:
  - "apps/*"
  - "packages/*"

With that file, one pnpm install at the root installs every package, writes one pnpm-lock.yaml, and links workspace packages to each other. A typical layout:

shop/
  pnpm-workspace.yaml
  package.json
  apps/
    api/        (package.json with a "dev" script)
    web/
    worker/
  packages/
    shared/

Each app is a normal package with its own package.json and its own dev script, such as tsx watch src/index.ts for an API or vite for a website.

Start everything or a part

From the root, -r (recursive) runs a script in every package that defines it:

pnpm -r --parallel run dev

--parallel matters. Without it pnpm runs the scripts one after another in dependency order and waits for each to finish, and a dev server never finishes. With it, every dev script starts at once and pnpm ignores topological order.

To start only some packages, filter by name or by folder:

pnpm --filter @shop/api dev
pnpm --filter "./apps/*" --parallel run dev
pnpm --filter @shop/web... --parallel run dev

The trailing ... adds the package's dependencies, so @shop/web... includes packages/shared if the website imports it. You can wrap the common cases in root scripts such as "dev": "pnpm -r --parallel run dev".

What pnpm does not do

  • No start order. With --parallel the website may start before the API is listening. Most frontends tolerate that; a worker that connects to the API at boot may crash and need a restart.
  • No health waits. pnpm knows a process started, not that it is ready.
  • Interleaved logs. pnpm prefixes lines with the package name, but several watchers writing at once are hard to read.
  • No supervision. If one process dies, the others keep running and you find out later.

If you need caching or task graphs, that is a job for a task runner on top of pnpm. See the Turborepo dev task article.

Where Flisk fits

Flisk can start each workspace package as a local process, in dependsOn order, and wait for health checks. Each service gets a small service.json next to its package.json. For apps/api:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "pnpm dev",
  "port": 4000,
  "healthCheckPath": "/health"
}

And for apps/web, which should wait for the API:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "pnpm dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4000" }
}

The command runs from the service folder, so pnpm dev runs that package's script. Flisk passes the port as the PORT environment variable, so make your dev script read it. Then run:

npm install -g @flisk-sh/flisk
flisk up

Flisk starts api, waits until /health answers, starts web, prefixes every log line with the service name, and restarts a process that exits. flisk up --only web starts web and what it depends on. flisk down stops everything.

The default discovery.paths in .flisk/project.json is services/*/*. When you scaffold a service under apps/, the CLI warns that it is outside that pattern. Add "apps/*" to discovery.paths and run flisk config regenerate.

Pitfalls

  • Run pnpm install once at the root before flisk up. Flisk does not install dependencies for local processes.
  • Flisk and pnpm both need to find pnpm on the PATH. flisk doctor reports a command whose program is missing.
  • Do not mix local-process services with container-built services in one run. Flisk stops with a MIXED_RUNTIME error. A database from a ready-made image is the exception.

For a repo where the real problem is deciding what to run on a given day, read how to run only the changed services, or see the broader monorepo local dev setup.

Questions people ask

Why does pnpm -r run dev only start one package?

Without --parallel pnpm runs scripts in topological order and waits for each to exit. A dev server never exits, so the next package never starts. Add --parallel.

How do I run one app and the packages it depends on?

Use a filter with three dots, for example pnpm --filter @shop/web... --parallel run dev. The trailing dots include the package's workspace dependencies.

Does Flisk replace pnpm workspaces?

No. pnpm still installs and links packages. Flisk only starts the services, in order, and watches their health.
