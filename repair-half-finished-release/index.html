What to Do When a Release Only Half Finished

The package is on npm but the GitHub release is missing, or the tag exists but publishing failed. List what is done, repair forward with idempotent steps and avoid republishing.

First list which channels already have the version: tag, registry, GitHub release, binaries, container image, docs. Then finish only the missing ones, forward, with steps that are safe to repeat. Do not delete the tag or republish a version that is already live.

Take inventory

Write a small table and fill it from real checks, not memory.

git ls-remote --tags origin v1.5.0
npm view your-package@1.5.0 version
gh release view v1.5.0
docker manifest inspect ghcr.io/OWNER/IMAGE:1.5.0

Each command returns an error when the thing is missing. The pattern of what exists tells you where the workflow stopped and why. See verify a release after publishing for the checks.

Find why it stopped

Open the failed run and use the methods from Debugging CI Failures. Common reasons: a registry timeout after the upload succeeded, a lookup that ran before the registry showed the new version, a token that expired between jobs, a permission missing for the release step, or a job that needed approval and timed out. Knowing the cause tells you whether a plain re-run is safe.

Repair forward with idempotent steps

Re-run only the failed jobs, if each step can run twice without harm. Write steps that way from the start: check before you create.

if npm view your-package@"$VERSION" version >/dev/null 2>&1; then
  echo 'already published, skipping'
else
  npm publish --provenance
fi

gh release view "$TAG" >/dev/null 2>&1 || gh release create "$TAG" --generate-notes

With this pattern a re-run of a half finished release fills the gaps and leaves finished parts alone.

What not to do

  • Do not move or delete a tag that people may have fetched. Add a new patch version instead.
  • Do not publish the same version again with different content. The registry will refuse, and for other artifacts such as container tags it silently replaces content, which is worse.
  • Do not bump the version just to get a green run when the old version is still unpublished somewhere. You will leave a gap that confuses users.

If the published part is bad, use the rollback steps instead of repairing.

A repair checklist

  1. List which channels have the version.
  2. Read the failed run and name the cause.
  3. Fix the cause (token, permission, timeout, approval).
  4. Re-run only the failed jobs, or run the missing steps by hand.
  5. Run the verification again for every channel.
  6. Write a two line note in the release issue.

Keep this list next to the release checklist so the person on call does not improvise.

Prevent the next one

Order steps so the least reversible one comes last, and make everything before it checkable. Retry network lookups with a bound. Add a final job that verifies all channels and fails loudly. Track release workflow runs like any other pipeline: a failed release run on the default branch should be on the red list. Cilytics (cilytics.flisk.si) is a public CI health dashboard that lists red workflows per repo, from an hourly snapshot of default-branch runs, so it can serve as a quick reminder, though not a live alert.

Questions people ask

Can I just re-run the whole release workflow?

Only if every step is idempotent. Otherwise a re-run may fail on the already published version or create duplicates. Re-run only the failed jobs or add existence checks.

Should I delete the tag and start over?

Not if anyone may have fetched it. Move forward with a new patch version instead of rewriting a published tag.
