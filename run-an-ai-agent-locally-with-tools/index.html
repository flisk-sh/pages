Running AI agents locally

How to run an AI agent locally with MCP tools and a mock model

An agent with tools is three processes and two URLs. Here is how to run all of them on your machine, test the loop offline, and switch to a real model later.

To run an AI agent locally with tools, start three small processes: the agent loop, a tool server that speaks MCP, and a model endpoint. Point the agent at the model with a base URL and at the tools with another URL. While you build the loop, a local mock model lets you run it offline with no API key, then you switch the base URL to the real API.

What an agent with tools is made of

Every agent framework wraps the same loop. You send the model a question and a list of tools. The model either answers or asks to call a tool. You run the tool, append the result to the conversation, and ask again. You stop when the model answers in plain text. That is all a tool-using agent is, and it is easier to debug when you can see each piece running on its own port.

Locally that means three pieces:

  • The agent, an HTTP service with the loop in it.
  • The tool server, which lists tools (tools/list) and runs them (tools/call). MCP, the Model Context Protocol, is the common format, so the same server also works with coding assistants.
  • The model, which is a hosted API in real use, but can be a fake during development.

The plain way, without any orchestrator

You can do this with three terminals. Start the tool server on one port, start the agent on another with TOOLS_URL=http://localhost:4501, and set your SDK's base URL to the model. The official Anthropic and OpenAI SDKs both let you override the base URL, usually through an environment variable. A mock that returns scripted tool calls and then a final answer is enough to test the loop without spending tokens.

It works, but you now manage ordering (the tool server must be up before the agent calls it), restarts, and three sets of logs by hand. See service startup order for the general problem.

The Flisk way: the tool-loop starter

Flisk ships a starter called tool-loop that is exactly this setup. It uses the Anthropic SDK's tool runner as the loop, an MCP tool server with a lookup tool over a tiny offline knowledge base, and a local mock of the Messages API. Everything runs as plain local processes, so Docker is not needed. Install Flisk first with npm install -g @flisk-sh/flisk, then:

flisk project tool-loop --path tool-loop-demo --yes
cd tool-loop-demo
flisk up
curl -X POST localhost:4500/ask -H 'content-type: application/json' \
  -d '{"question":"what is mcp and flisk"}'
flisk mcp check tools --call --no-icon

The last command connects to the tool server as an MCP client, checks the protocol, and with --call calls the tools. The project has four services, each with its own service.json. This is the agent's:

{
  "schemaVersion": 1,
  "appName": "agent",
  "appType": "backend",
  "command": "node server.mjs",
  "port": 4500,
  "healthCheckPath": "/health",
  "env": {
    "TOOLS_URL": "http://localhost:4501",
    "ANTHROPIC_BASE_URL": "http://localhost:4502",
    "ANTHROPIC_API_KEY": "mock-model-no-key-needed"
  },
  "dependsOn": ["setup", "tools", "model"]
}

A command field makes the service a local process. dependsOn sets the start order: setup is a one-shot job that runs npm install for the SDK and must exit 0 first, then the tool server and the mock model start, then the agent.

Switching to a real model

The mock in model/ follows one fixed strategy: look up each topic, then answer from the results. It is not a model and will not reason about anything else. To use Claude, delete the ANTHROPIC_BASE_URL and ANTHROPIC_API_KEY lines from agent/service.json, put your key in .env as ANTHROPIC_API_KEY=..., and run flisk up again. Keep the key out of service.json and out of git. If you would rather use an open model on your own machine, Flisk has an inference resource type that runs an OpenAI-compatible server (Ollama by default), described in its bring-your-own docs.

Pitfalls

  • Tools are the dangerous part. A model decides when to call them. Start with read-only tools, validate every argument on the tool server, and keep any write behind an explicit step you control.
  • Retry on the right layer. The starter's SDK client retries failed connections (maxRetries: 4) and the agent retries tool server calls with backoff, so a service that is restarting is waited for. Do not retry a tool that has side effects without an idempotency key.
  • The mock hides real failures. A real model returns malformed arguments, calls tools you did not expect, and loops. Test against the real API before you trust the loop.
  • No session memory here. This starter answers one question at a time. If a conversation must survive a restart, you need checkpoints, which is the next topic.

When this is not the right shape

If you already use a framework with its own graph and state, keep it and run it next to the same tool server. The framework owns the loop; Flisk only starts and wires the processes. For conversations that must resume after a restart, read durable agent sessions and checkpoints. To expose the same tool server to a coding assistant, see building an MCP server locally.

Questions people ask

Can I run an AI agent without an API key?

Yes, for the loop itself. Point the SDK's base URL at a local mock that returns scripted tool calls and a final answer. That tests your tool wiring, but it is not a model, so test against a real model before you ship.

Does the tool-loop starter need Docker?

No. Every service declares a command, so flisk up starts them as local processes. Docker is only needed for container resources such as the agent resource type.

How do I check that my tool server speaks MCP?

Run flisk mcp check <resource> to check initialize, tools and error handling, and add --call to also call the tools.
