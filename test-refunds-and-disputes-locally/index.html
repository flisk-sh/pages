How to test refunds and chargebacks in Stripe test mode

Money going back out is where order, ledger and email logic disagree. Stripe test mode can produce every one of these events on demand.

In Stripe test mode you can create a refund with the API, trigger a dispute by paying with card 4000 0000 0000 0259, and then submit test evidence that makes the dispute win or lose. Each step sends the same kind of event a live account would, so you can check that your order status, stock and emails respond correctly before any real money is involved.

Refunds

A refund is a request to return money for a charge, created from your server. Full and partial refunds use the same call:

// full refund
await stripe.refunds.create({ payment_intent: "pi_123" },
  { idempotencyKey: "refund-order-42" });

// partial refund of 5.00
await stripe.refunds.create({ payment_intent: "pi_123", amount: 500 },
  { idempotencyKey: "refund-order-42-part-1" });

Give every refund an idempotency key derived from your own record, as in idempotency keys for payment requests. A double-clicked "Refund" button should return money once. Stripe also refuses to refund more than the remaining amount, so a test for the second partial refund that exceeds the balance should expect an error.

What to check after a refund:

  • You receive charge.refunded. Stripe also has refund-specific events. Check the current event list in its documentation for the ones you want.
  • A partial refund leaves the order in a state that still says "paid, partly refunded", not "refunded".
  • Stock is returned once, even if the event arrives twice.
  • The customer email goes out once.

Disputes

A dispute, also called a chargeback, starts when a cardholder challenges a payment with their bank. Pay with the test card 4000 0000 0000 0259. The payment succeeds, then a dispute is opened and your endpoint receives charge.dispute.created. You can also send the event alone with the CLI:

stripe trigger charge.dispute.created

As with every triggered event, the object IDs are made up, so use the card when you need your own records to match.

To test the outcome, submit evidence through the API with special text. According to Stripe's testing documentation, an uncategorized_text of winning_evidence makes the dispute resolve in your favour and losing_evidence makes it resolve against you:

await stripe.disputes.update(disputeId, {
  evidence: { uncategorized_text: "winning_evidence" },
  submit: true
});

Then watch for the closing event, charge.dispute.closed, whose status tells you whether you won or lost. Funds movement events such as charge.dispute.funds_withdrawn and charge.dispute.funds_reinstated follow the same path. Confirm the names against the Stripe event reference, since the list grows.

Your handler should do three things on a new dispute: mark the order as disputed so it does not ship, put a task in front of a human with the deadline for evidence, and avoid refunding it, since refunding a disputed payment does not always cancel the dispute.

Running it with Flisk

The events reach your laptop through stripe listen --forward-to localhost:4000/webhooks/stripe, as in testing Stripe payments locally. Flisk runs the API and its database as a stack with flisk up. Two commands help during this work. flisk logs --service api --since 10m shows how your handler treated each event in time order, and flisk run starts a scenario script with the service's own environment:

flisk run api -- node scripts/dispute-scenario.js

The script pays with the dispute card, waits for the event, submits losing evidence and asserts the order's final state. It exits with a non-zero code when an assertion fails, which flisk run passes along. The same command works in a CI job. Install Flisk with npm install -g @flisk-sh/flisk. Flisk does not simulate disputes. Stripe does, and Flisk keeps your side of the test in one place.

Pitfalls

  • Refund and event race. The refund API call returns before your webhook arrives. If your code updates the order on both, make the update the same guarded, repeatable one so the second does nothing.
  • Currency units. Amounts are in the smallest unit, so 500 means 5.00 in a two-decimal currency. Zero-decimal currencies differ.
  • Assuming a dispute means fraud. Customers also dispute because they do not recognise the descriptor. Your handling should collect evidence, not auto-block the account.
  • Test-only outcomes. The special evidence text works in test mode. Live disputes are decided by the bank, over weeks.
  • Not testing the lost case. A won dispute needs little. A lost one removes money and may need accounting entries, so test it first.

For the broader set of failure cards that come before this stage, see Stripe test cards for declines and 3D Secure.

Questions people ask

How do I create a dispute in Stripe test mode?

Pay with the test card 4000 0000 0000 0259. The payment succeeds and then a dispute is created, which sends a charge.dispute.created event to your webhook endpoint.

How do I make a test dispute win or lose?

Submit evidence with uncategorized_text set to winning_evidence or losing_evidence, as Stripe's testing documentation describes, and the dispute resolves accordingly.

Can I refund part of a payment in test mode?

Yes. Pass an amount smaller than the payment to the refunds API. You can refund again until the total reaches the original amount.
