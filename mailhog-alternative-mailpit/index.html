MailHog is unmaintained: what to use instead in local dev

If your Compose file or tutorial still says mailhog/mailhog, it works, but nobody is fixing it. Here is what to move to and what changes.

Use Mailpit as the replacement for MailHog. It uses the same two ports (1025 for SMTP, 8025 for the web UI), so most setups change by one line: the image name. MailHog's repository has had no release for years, while Mailpit is actively developed and adds search, a REST API for tests and optional persistent storage.

Why people are moving away from MailHog

MailHog was the default answer to "how do I see my app's email locally" for a long time, and it still runs. The problems are small but they add up: no new releases, no fixes for newer SMTP clients and extensions, and an image that is built for older platforms. On Apple silicon you may see an architecture warning or run it under emulation. None of this breaks a simple demo, but a tool you depend on every day should have someone looking after it.

The framework "log it to the console" backends are fine for a first check and bad as your only test, because the code path that opens an SMTP connection never runs. Pair them with a real catcher.

Switch from MailHog to Mailpit

In Compose, the change is usually just the image:

services:
  mail:
    image: axllent/mailpit   # was: mailhog/mailhog
    ports:
      - "127.0.0.1:1025:1025"
      - "127.0.0.1:8025:8025"

Your application settings stay the same: host, port 1025, no auth, no TLS. Two differences to check:

  • Persistence. MailHog keeps mail in memory by default. Mailpit does too until you set MP_DATABASE=/data/mailpit.db and mount a volume.
  • Test code that calls the API. If your tests fetch /api/v2/messages from MailHog, rewrite them for Mailpit's API, which lives under /api/v1/ (for example GET /api/v1/messages, GET /api/v1/message/{id}, GET /api/v1/search?query=... and DELETE /api/v1/messages to empty the inbox). The JSON field names differ, so run one test and print the response before you adjust the parsing.

The Flisk way

Flisk does not have its own mail catcher and does not care which one you pick. It runs whichever image you name as a bring-your-own resource. For Mailpit that is one resource with the image, a TCP health check on 1025, and the inbox port published on 127.0.0.1. The full service.json is in the Mailpit setup article. If you have an existing docker-compose.yml with a mailhog service, flisk import --dry-run shows what it would turn into, and you can then change the image line in the generated service.json. There is a longer walk-through in importing a Compose file.

A short migration checklist

  1. Search the repository for mailhog, 8025 and 1025. Compose files, Makefiles, CI workflows and README files all tend to mention it.
  2. Replace the image and keep the ports. Pin a version tag instead of latest, so a surprise update does not change your inbox in the middle of a sprint.
  3. Add a volume if you want messages to survive a restart, and set a message cap so the file stays small.
  4. Send one message from your app and one from a script with a different SMTP library. If both arrive, the swap is done.
  5. Update the README line that tells new developers where to find the inbox. Stale setup instructions cost more than the tool does.

When to keep what you have

If MailHog works for you and nothing in your stack touches it beyond port 1025, you are not forced to move today. Move when you hit a bug, when you need to search a busy inbox, or when you start writing tests that read mail. Doing it before a new hire sets the project up on a new machine saves you a confusing evening.

Next, use the inbox API in an end-to-end test so you stop checking mail by eye.

Questions people ask

Is MailHog dead?

It still runs, but the project has had no release for years, so new problems will not be fixed. Mailpit is the actively developed replacement with the same ports.

Can Mailpit replace MailHog without changing my app?

Usually yes for the app itself, since both accept plain SMTP on port 1025. Only tests or scripts that call MailHog's HTTP API need changes.

Is MailCatcher still a good choice?

It works and is simple if you already use Ruby, but it has fewer features than Mailpit and uses a different web port, 1080.
