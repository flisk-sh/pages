Running AI agents locally

How to run a Mastra agent locally next to a database and tools

Mastra serves agents with one command. Putting that command next to Postgres and other services is where a project file saves time. This is the container route, with its traps.

A Mastra agent runs locally with mastra dev, which serves your agents over HTTP on port 4111 by default. To run it next to a database and other services, put it in a container (or a plain local process) and let a project file handle ports, health checks and start order. Flisk has no Mastra scaffold of its own, so this article uses its bring-your-own resource type, which wraps any Dockerfile.

What you are running

Mastra is a TypeScript framework for agents, tools, workflows and memory. Its dev server bundles your project and serves it, which takes a while on a cold start (the Flisk team measured about 45 seconds in its own check, so expect a slow first boot). Out of the box the agent has no stack around it: no Postgres, no queue, no other service to call. Anything beyond a single script needs those pieces to come up in a known order, which is where a project file helps.

The plain approach

Run npm create mastra@latest, then npm run dev, and open the playground at http://localhost:4111. For one agent that is all you need. Once the agent talks to other services you also run those yourself, export their URLs as environment variables and remember which terminal each lives in. A Compose file works too; see alternatives to Compose for local development.

Wrapping a Mastra project with Flisk

Flisk's repository includes a checked example, examples/byo/create-mastra, that runs a real create-mastra project in a container. Its Dockerfile shows the shape. The part worth copying is the end: the dev server listens beyond loopback, reads PORT, and a health check probes the port.

FROM node:22-alpine
WORKDIR /work/app
COPY . .
RUN npm ci
USER node
EXPOSE 4111
CMD ["npm", "run", "dev"]

That is a sketch built from the example, not a copy of it: the example scaffolds the project during docker build, while here you copy your own source. Put the Mastra project in the resource folder, then register it:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource mastra-agent --type bring-your-own --stack agents --port 4111 --yes
# replace services/agents/mastra-agent/Dockerfile with your own and add your source
flisk up agents

flisk resource writes a placeholder Nginx Dockerfile and a service.json like this one. You keep the manifest and replace the Dockerfile:

{
  "appName": "mastra-agent",
  "appType": "bring-your-own",
  "stack": "agents",
  "port": 4111,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile"
}

The Flisk example is checked against /health on a Mastra dev server. If your Mastra version answers elsewhere, change healthCheckPath to a path that returns 2xx.

What only a real run shows

Flisk's bring-your-own notes list traps found by running examples through a full flisk up. Three matter for agents:

  • The route is a path prefix. A routed resource is served at http://api.<project>.localhost/api/mastra-agent and Flisk strips the prefix before the request reaches the container. An API under that prefix works. The Mastra playground is a web UI that serves assets from /, so set "webUi": true in service.json to give it its own host name instead.
  • A Postgres DATABASE_URL is injected into every bring-your-own container, even when the app does not use a database. If a Mastra storage setting reads DATABASE_URL and you meant something else, set your own variable with a different name.
  • The Host header is api.<project>.localhost. A dev server with a host allow list can refuse it. Allow that host, or the request fails with a message about blocked hosts.

Keep Mastra's memory across restarts

If Mastra's storage is a file inside the container, it disappears when the container is recreated. Either point storage at Postgres (see running Postgres locally) or mount a named volume on the folder that holds the file. A bring-your-own service.json takes a volumes list of source and target pairs, the same way Flisk's NATS resource keeps its data:

"volumes": [{ "source": "mastra-data", "target": "/work/app/.data" }]

Check where your Mastra storage config writes before choosing the target path.

When not to use this

If your agent is a single process with no neighbours, npm run dev is simpler and faster to iterate on. Use the wrapper when the agent needs other services started with it. For the session and checkpoint side, read durable agent sessions and checkpoints, which applies to any framework.

Questions people ask

Does Flisk have a Mastra template?

No. There is no Mastra scaffold. Flisk includes a checked bring-your-own example that runs a real create-mastra project in a container, and you can wrap your own Mastra project the same way.

Which port does the Mastra dev server use?

4111 by default. The Flisk example also sets PORT, which the dev server reads, so the project file and the process agree.

Why is the first start of the Mastra container slow?

The dev server bundles the project on start. The Flisk example took about 45 seconds in its own check, so give the first health check a long wait.
