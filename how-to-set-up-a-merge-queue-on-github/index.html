How to Set Up a GitHub Merge Queue for Agent PRs

A merge queue tests each pull request against the latest main plus the ones ahead of it. Here is how to enable it and the workflow change it needs.

Enable the merge queue in your branch protection or ruleset, then add the merge_group trigger to the workflows that run your required checks. Without that trigger the queue waits for checks that never start.

Why a queue helps with many PRs

Two pull requests can each pass CI alone and still break main when combined. With many agents opening changes, that happens often. A merge queue builds a temporary branch with your pull request on top of the queue ahead of it, runs the required checks, and merges only if they pass.

Turn it on

In the branch protection rule or ruleset for your default branch, enable "Require merge queue". Set the merge method, how many pull requests can build at once, and how long to wait for checks. Merge queues are available for repositories on supported plans, so check GitHub's documentation for your account type.

Add the merge_group trigger

This is the step people forget. Checks must run on the queue's temporary branch, which GitHub signals with the merge_group event.

on:
  pull_request:
  merge_group:
    types: [checks_requested]

Keep the job names identical between both triggers so the required check names match.

Tune for speed and cost

  • Run the cheap checks on the pull request and the full set in the queue.
  • Keep the queue's build concurrency modest. Higher concurrency finishes faster but wastes more runs when one fails.
  • Make sure the suite is not flaky. A random failure ejects a pull request and rebuilds everything behind it.

For making the checks themselves quicker, see faster GitHub Actions.

What to do when a PR is ejected

The queue removes a pull request whose checks fail. Let the agent read the failing log, fix it and re-enqueue, but limit the retries to two or three so it does not loop. Pair this with the work-in-progress limit in handling a flood of agent PRs.

Checking that it works

Test the setup before you depend on it. Open two small pull requests that touch the same file in different places, enqueue both, and watch the queue build them one on top of the other. Then open a third that you know will fail a check and confirm it is ejected without blocking the rest.

gh pr merge 101 --auto --squash
gh pr view 101 --json mergeStateStatus,autoMergeRequest

Read the queue's timing. If a pull request waits too long, either the checks are slow or the queue's settings are too conservative. Look at the time from entering the queue to merge for a week and set a target, for example under 15 minutes.

Finally, document the process for contributors and agents in the repo: how to enqueue, what happens on failure and how many retries are allowed. Without this the first ejected pull request becomes a support question.

Questions people ask

Do I need a merge queue for a small team?

Not always. It pays off when many pull requests land daily and main breaks from combined changes. With a few PRs a day, up-to-date branches are enough.

Why do my queued PRs never merge?

Usually the workflows lack the merge_group trigger, so required checks never run on the queue branch.
