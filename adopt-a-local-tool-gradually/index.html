Team dev environments and onboarding

How to adopt a local dev tool gradually without a big switch

A tool earns its place when two people can use it while everyone else keeps the old way, and nobody has to rewrite anything on day one.

Adopt a local dev tool in steps: try it on a branch, check what it changes in the repository, commit only the config files that belong in version control, and keep the old setup working until the team has chosen. In an existing repository, flisk project --yes adds files and leaves your package.json, Dockerfile and docker-compose.yml alone, so the trial is cheap to undo.

Why a gradual rollout is the safe default

Local setups break in ways that code review does not catch: a port that is taken on one laptop, a Docker version, a script that assumed a folder. A switch for the whole team on one Monday means many people hit those problems at once. A pilot with one or two volunteers surfaces them while the rest of the team stays productive.

It also keeps the decision honest. If your app has two or three services and Compose already works, the right outcome of a pilot may be to stay where you are. That is a valid result, not a failed one.

Step 1: try it on a branch

Create a branch and run, from the repository root:

git switch -c try-flisk
flisk project --yes
git status

I ran this on a repository that already had a package.json, a Tiltfile, a .tiltignore, a docker-compose.yml and a Dockerfile. All five were byte-for-byte unchanged afterwards. What changed:

  • Lines were appended to .gitignore: .env, .flisk/.flisk-out/, .flisk/.project-id, .flisk/smoke/, plus a block of root files.
  • New untracked files appeared: .flisk/project.json, services/platform/database-management/docker-compose.yml and a shared-platform-engineering/docker-templates/ folder.

Read the diff before you commit anything. It is the whole footprint of the tool.

Step 2: describe one service, not all of them

You do not have to model the whole system. Add a service.json for one service, run it, and see whether the day-to-day experience is better. For a repository that already has a Compose file, flisk import --dry-run shows what an import would do without writing anything. Use the dry run first, then decide whether to import or to write the manifests by hand. The details of a manifest are in service.json as a team contract.

Step 3: commit the right files

Commit .flisk/project.json and each service.json. Do not commit .env or anything under .flisk/.flisk-out/; both are git-ignored for a reason, since one holds secrets and the other is rebuilt from the sources. A new colleague then needs only the repository and the install step. If something fails, flisk doctor tells them what to fix, as described in check your machine before starting.

Step 4: add the guardrails

Once two people use it, add the CI job from checking config drift in CI. Set pinnedFliskVersion in .flisk/project.json if you want everyone on the same version. A pin is an exact match and prints the exact npm install -g @flisk-sh/flisk@x.y.z command when someone is off. A minFliskVersion is a softer floor.

Pitfalls

  • Running both stacks at once. I did not test Flisk next to the old Compose stack at the same time. Stop one before starting the other, and if you must run both, override ports with FLISK_HTTP_PORT, FLISK_HTTPS_PORT and FLISK_POSTGRES_PORT.
  • Mixing modes in one project. A project cannot yet mix services that run as local processes with services that run as containers. Pick one per project.
  • No Flisk-free mode. There is currently no way to use the tool without Flisk files in the repository. If you cannot add any config files at all, it is not the right choice for that repository.
  • Corporate proxy or private registry. This is not documented as supported. Check it in your pilot before promising the team anything.

When not to adopt it

Skip the pilot if Compose already works for two or three services and nobody complains. Skip it if you need Kubernetes manifests; that is out of scope for the tool. And skip it if your team will not accept one more config file. Whatever you choose, know the exit before you enter: leaving a tool without lock-in covers what you keep and what you lose.

Next step: pick one volunteer and one service, run the branch trial this week, and write down what was better and what was worse. Those notes are your adoption decision.

Questions people ask

Will flisk project change my existing files?

In the repository I tested, package.json, Tiltfile, .tiltignore, docker-compose.yml and Dockerfile were unchanged. It appended to .gitignore and added new files.

Can half the team use it and half not?

Yes, because the old files stay. Only the new config files are committed, and each person chooses which setup to run.

Can I preview an import first?

Yes. flisk import --dry-run shows what would happen without writing files.
