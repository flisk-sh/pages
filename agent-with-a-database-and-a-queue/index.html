Running AI agents locally

How to give an AI agent a database and a job queue locally

An agent that answers inside the request breaks the first time a model call takes a minute. Put the state in a database and the slow work behind a queue.

Give an agent a database for what it must remember and a queue for work that takes too long to do inside a request. In Flisk that is three commands: an agent with --durability postgres, a queue resource that runs NATS with JetStream, and a worker that reads the queue. The agent stores conversations in Postgres, hands slow jobs to NATS, and answers the caller right away.

Why an agent wants both

Most useful agent work is slow. A turn may call a model several times, run a tool that takes a minute, or wait on an external API. If the HTTP request waits for all of that, you meet timeouts, dropped connections and double submissions. The usual fix has two parts.

  • A database keeps state that must survive a restart: the conversation, the status of each job, the result. Postgres is the common answer, and any other store works the same way.
  • A queue separates "accept the work" from "do the work". The agent writes a message and returns. A worker takes the message, does the job and writes the result to the database. The caller polls, or gets a callback.

A queue also gives you retries and a place to put a limit on how many model calls run at once. NATS JetStream stores messages on disk and redelivers a message when a consumer does not acknowledge it, which is the behaviour you want when a worker crashes in the middle of a job. Redis, RabbitMQ or a table with SELECT ... FOR UPDATE SKIP LOCKED would also do the job. NATS is what Flisk scaffolds.

Create the three parts

Start from a project with a stack called shop. The agent needs Docker, because it is a container resource:

flisk resource assistant --type agent --stack shop --durability postgres --yes
flisk resource jobs --type queue --stack shop --yes

The agent's service.json contains "appType": "agent" and "agent": { "runtime": "custom", "durability": "postgres" }. Its source reads DATABASE_URL, which Flisk injects, and keeps one row per session in a table called flisk_agent_sessions. When you create a project, Flisk enables a shared Postgres for it, and flisk config verify says so ("Postgres will start because database-management is enabled"). If you do not want that, use --no-database when you create the project.

The queue resource writes this into services/shop/jobs/service.json:

{
  "appName": "jobs",
  "appType": "bring-your-own",
  "framework": "nats",
  "port": 4222,
  "image": "nats:2.11.8-alpine",
  "container": { "command": ["-js", "-sd", "/data", "-m", "8222"] },
  "volumes": [{ "source": "jobs-data", "target": "/data" }],
  "provides": { "NATS_URL": "nats://jobs:4222" }
}

It is plain NATS with JetStream turned on, storing data in the jobs-data volume, so queued messages survive a restart of the queue. The provides entry is the important part. The CLI says that any service that lists jobs in dependsOn gets NATS_URL=nats://jobs:4222. Add it to your agent's manifest:

"dependsOn": ["jobs"]

Run flisk config verify to confirm the generated files are in sync, then flisk up shop. For more on running NATS by itself, see NATS for local development, and for the database side running Postgres locally.

What you write yourself

Be clear about the boundary. The generated agent talks to Postgres for its checkpoints. It does not talk to NATS. You add the publishing code and the worker. A sketch with the nats package for Node and Bun, which you should check against the version you install:

import { connect } from "nats";

const nc = await connect({ servers: process.env.NATS_URL });
const jsm = await nc.jetstreamManager();
await jsm.streams.add({ name: "TASKS", subjects: ["tasks.*"] });

// in the agent, after saving the user message:
const js = nc.jetstream();
await js.publish("tasks.run", JSON.stringify({ sessionId, input }));

The worker is another resource, with its own service.json and "dependsOn": ["jobs"]. It creates a durable consumer on the TASKS stream, does the work, writes the result to Postgres and only then acknowledges the message. Acknowledging last is what makes a crash safe: the message comes back and the job runs again.

Pitfalls

  • Make jobs idempotent. Redelivery means a job can run twice. Key results by job ID and use an upsert.
  • Do not share the agent's table. Keep flisk_agent_sessions for the agent. Put job results in your own table, created by a migrator resource, not by the start script.
  • Set a retry limit. An infinite redelivery loop with a paid model is expensive. Limit attempts on the consumer.
  • Keep the volume in mind. The jobs-data volume survives flisk down. flisk down --purge removes the project's Docker volumes, including the queue's messages.

When not to add a queue

If a turn finishes in a second or two, a queue is extra moving parts. Start with the database alone, and add the queue when requests start to time out. If the work is a fixed set of steps with retries, a framework with built-in checkpoints may fit better, see a LangGraph agent stack.

Questions people ask

Does the generated agent publish to the queue by itself?

No. It stores checkpoints in Postgres when you choose --durability postgres, and a queue resource provides NATS_URL to services that list it in dependsOn. The publishing code and the worker are yours to write.

Where do queued messages live?

In the jobs-data volume mounted at /data in the NATS container, so they survive a restart. flisk down --purge removes the project's Docker volumes.

Can I use Redis instead of NATS?

Yes, the pattern is the same. The queue resource Flisk scaffolds is NATS with JetStream, so another broker means a bring-your-own resource of your own.
