Build your own MCP server

MCP stdio server will not connect: stop printing to stdout

On stdio, standard output belongs to the protocol. One stray print statement is enough to break the connection.

If a stdio MCP server connects, then fails with a JSON parse error or "connection closed", the usual cause is that something wrote text to standard output that is not an MCP message. On stdio, standard output is the protocol channel. Send every log line, print statement and library warning to standard error instead.

Why stdout is special

A stdio server and its client talk over two pipes. The client writes JSON-RPC messages to the server's standard input, and the server writes its replies to standard output, one message per line. The client reads that stream and parses each line as JSON. A line such as Server started on port 3000 is not JSON. Depending on the client, you see an error like "Unexpected token S in JSON", the connection drops, or the server is marked as failed without a clear reason.

Standard error is the opposite: the specification lets a stdio server write logs there, and clients capture it or show it in a log view. Use it for everything human-readable.

Find the stray output

Run the server by hand and look at what it prints before you send any input:

node build/index.js < /dev/null

A correct stdio server prints nothing on startup, then waits. Anything on screen from that command that is not an MCP message is a problem, but remember that your terminal shows both streams. To see only standard output, discard standard error:

node build/index.js < /dev/null 2>/dev/null

If that prints anything, you have found a leak. Then search for the usual suspects.

The usual suspects

  • TypeScript or JavaScript: console.log writes to standard output. Use console.error. Check dependencies too, because some libraries print banners or deprecation notices with console.log.
  • Python: print() writes to standard output. Use print(..., file=sys.stderr) or the logging module, whose default handler writes to standard error. Also check for third-party code that prints progress bars.
  • Go: fmt.Println writes to standard output. Use fmt.Fprintln(os.Stderr, ...) or log with its default output, which is standard error.
  • Wrapper scripts: a shell script that runs npm install, echos a message, or activates a virtual environment before starting your server can print to standard output. Make the script silent, or call the interpreter directly.
  • npx and package managers: the first run of npx some-server may print install progress. Pin the version and pass flags that silence it, or install the package first.

In Python, a safe pattern is to configure logging once at the top and never call print:

import logging, sys
logging.basicConfig(stream=sys.stderr, level=logging.INFO)
log = logging.getLogger("notes")
log.info("server starting")

In TypeScript, a small helper makes the rule hard to break:

const log = (...args: unknown[]) => console.error('[notes]', ...args);

Other reasons a stdio server will not connect

Once stdout is clean, check these before you blame the protocol:

  • The command is not found. A client starts the program with its own environment, which may have a different PATH than your shell. Use an absolute path to the interpreter, or the full path to a script.
  • Environment variables are missing. The client passes only what its configuration lists, plus a small default set. Put required variables in the configuration's env section.
  • The working directory is not what you expect. Use absolute paths for files the server reads.
  • The server exits right away. A crash at import time looks like a connection failure. Run the exact command by hand.

The MCP Inspector can launch a stdio server for you and shows its standard error output, which makes these problems quicker to find. Debugging with the MCP Inspector shows how.

When this does not apply

An HTTP server has no such restriction: it can print anything to standard output, because the protocol travels over the network. That is one reason to move a hard-to-debug stdio server to HTTP while you develop it. Flisk runs services that listen on a port and collects their output with flisk logs, so it fits the HTTP kind. A stdio server has no port for Flisk to supervise, and its client starts it, so the fix for this problem lives in your own code and in the client configuration.

If a stdio server keeps costing you time, the transport comparison explains when to switch to HTTP.

Questions people ask

Where should an MCP stdio server write logs?

To standard error. The specification allows stdio servers to log there, and clients capture it. Standard output must contain only MCP messages.

Why does my MCP server work in a terminal but not in the client?

The client starts it with a different PATH, environment and working directory, and any text on standard output breaks parsing. Run the exact command by hand with stderr discarded.
