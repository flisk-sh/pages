Required Status Checks for Agent-Written Pull Requests

Which checks to make mandatory, how to set them in branch protection or rulesets, and the one trap that makes required checks useless.

Make typecheck, lint, unit tests and a build required status checks on your default branch, and require branches to be up to date before merging. Required checks turn "CI is green" from a courtesy into a rule an agent cannot skip.

The baseline set

Start with checks that are fast and rarely wrong.

  • Typecheck or compile.
  • Lint and format check.
  • Unit tests.
  • Build of the main artifact.
  • Secret scan.

Add integration tests once they are stable. A flaky required check blocks everyone and trains people to hit re-run, so fix or remove flaky ones before requiring them; see flaky tests and CI.

Turn them on

In the repository settings, use a branch protection rule or a ruleset on the default branch. Enable:

  • Require status checks to pass before merging, and pick the check names.
  • Require branches to be up to date before merging.
  • Require a pull request, and at least one approval for medium and high risk paths.
  • Do not allow bypassing for administrators if you can afford it.

You can also read the current rules from the command line to audit them.

gh api repos/OWNER/REPO/branches/main/protection

The path-filter trap

If a required workflow uses path filters and does not run for a docs-only change, the check never reports and the pull request waits forever. Either make required checks always run, or add a small always-run job that passes when the filtered job was skipped. Test this on a throwaway pull request before you rely on it.

Name checks so they are stable

Branch protection matches on the check name. If you rename a job or change a matrix, the old name stops reporting and merging breaks. Use one stable aggregate job, often called ci-ok, that depends on the others, and require only that.

jobs:
  ci-ok:
    if: always()
    needs: [lint, test, build]
    runs-on: ubuntu-latest
    steps:
      - run: test "${{ contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled') }}" = false

Combine with a queue

Required checks tell you a branch was green on its own. A merge queue tells you it is green when combined with everything ahead of it. Read how to set up a merge queue next.

Choosing what not to require

Be selective. Every required check is something that can block a merge for reasons unrelated to the change, so require only checks you trust. Leave out experimental scanners, slow end-to-end suites with a history of flakes and anything that depends on a third-party service you do not control. Run those as non-required checks and review their trend instead.

Review the list every quarter. Add a check when a class of bug keeps reaching main, and remove one that blocks merges without ever catching a real problem. A quick audit: look at the last 50 failures of each required check and count how many were real. If under half were, the check is hurting you more than it helps.

Finally, require the same checks for agents and people. Separate, weaker rules for humans breed resentment and bugs; separate stricter rules for agents are fine, and are best added as extra labelled checks.

Questions people ask

Why is my required check stuck on waiting?

The workflow probably did not run, often because of path filters or a branch filter. Make the check always run or add a fallback job.

Should agents be allowed to merge their own PRs?

Only for low-risk paths with full required checks. Keep human approval for anything touching auth, money, data or CI.
