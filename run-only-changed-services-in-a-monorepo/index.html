How to run only the changed services in a monorepo

Running every test and every server for every change wastes time. Git-aware filters pick the packages a change touches, and the packages that depend on them.

Each major monorepo tool can select packages by what changed in git: pnpm --filter "...[origin/main]", turbo run test --filter="...[origin/main]" and nx affected -t test. They compare your branch to a base, find changed packages, and add the packages that depend on them. For local servers, start a subset by name instead.

What "affected" means

If packages/shared changes, everything that imports it is affected, but a change in apps/admin affects only itself. A good filter follows the dependency graph, not only the file list. If you test only the folder you edited, you miss breakage in its consumers.

The commands

pnpm. The three dots before the bracket mean "changed packages and their dependents":

pnpm --filter "...[origin/main]" run test

Without the dots, --filter "[origin/main]" selects only the changed packages themselves.

Turborepo. The same filter syntax works with turbo run:

turbo run test build --filter="...[origin/main]"

Nx. The command is built in and has a base option:

nx affected -t test build --base=origin/main
nx show projects --affected --base=origin/main

In all three the base must exist in the checkout. In CI, a shallow clone often has no origin/main, so fetch enough history or the filter selects everything or fails. Use fetch-depth: 0 on GitHub Actions, or fetch the base branch explicitly.

Servers are not tests

Affected filters answer "what should I verify?", which is a build and test question. They do not answer "what should I run to try this change?". For that you choose by hand: the service you edited plus the services it calls. A good habit is to give each service a short name and start exactly those.

With a plain pnpm workspace, that is pnpm --filter @shop/web... --parallel run dev. The trailing dots add dependencies, which for a website usually includes the API package it talks to.

Starting a subset with Flisk

Flisk has this built in. flisk up --only api web starts those services plus what they depend on through dependsOn. For container services it also starts the shared infrastructure the Tiltfile enables for them. With local processes, flisk up --only web starts web and the services it depends on, in order, and leaves the rest off.

flisk up --only api web
flisk up shop               # one stack
flisk up --profile admin    # also start services tagged "admin"

Use profiles in service.json for heavy parts you rarely need, such as an admin app or a reporting job:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "admin",
  "appType": "frontend",
  "command": "pnpm dev",
  "port": 3001,
  "profiles": ["admin"]
}

Without --profile admin that service is left out; with --only admin it starts anyway. Flisk does not compute affected packages from git. If you want that, run your tool's affected command and pass the resulting names to --only yourself. See also starting only the services you need.

A CI example

On GitHub Actions the usual failure is a checkout that is too shallow for the comparison. Fetch the history, then run the filter:

- uses: actions/checkout@v4
  with:
    fetch-depth: 0
- run: pnpm install --frozen-lockfile
- run: pnpm --filter "...[origin/main]" run test

On a pull request, origin/main is the base you want. On a push to main itself, comparing to origin/main selects nothing, so compare to the previous commit (HEAD~1) or run everything on that branch.

Pitfalls

  • Missing base branch. In a shallow clone the base commit is absent. Fetch it.
  • Changed root files. A change to the lockfile, turbo.json or a root config can affect every package. Tools treat some root files as global inputs; check yours, or the filter hides real breakage.
  • Dependents only through runtime calls. The graph sees imports, not HTTP calls. If service A calls service B over HTTP, a change in B does not mark A affected. Add contract tests for those links.
  • Do not skip a full run before release. Run everything on the main branch.

On the CI side, see running a multi-service stack in GitHub Actions. For layout questions, see monorepo or separate repos.

Questions people ask

What do the three dots in a pnpm or turbo filter mean?

A leading ... includes the dependents of the selected packages, and a trailing ... includes their dependencies. ...[origin/main] means changed packages and everything that depends on them.

Why does nx affected select everything in CI?

Usually the base commit is missing from a shallow clone, or a global input such as the lockfile changed. Fetch full history and set --base.

Does flisk up compute affected services?

No. It starts a named subset with --only, a stack, or profiles. Feed it names from your tool's affected command if you want that.
