Larger Runners vs Self-Hosted Runners: When Is Each Worth It?

Compare GitHub-hosted, larger hosted and self-hosted runners on speed, cost, security and upkeep, with a plain rule for when to leave the default runner.

Stay on the standard GitHub-hosted runner until measurement shows your jobs are limited by CPU or memory. Then try a larger hosted runner first, and move to self-hosted only if you need special hardware, a private network or a fixed cost at high volume.

First check it is the runner

Many slow pipelines are slow because of work, not hardware: no caching, serial jobs, huge test suites. Buying a bigger machine for that is the most expensive way to avoid fixing it. Look at CPU use during the slow step. If the job sits at 100 percent CPU on all cores, more cores help. If it waits on the network or a single thread, they do not.

Larger hosted runners

GitHub offers larger runner sizes with more cores and memory on some plans. You select them with a label in runs-on.

runs-on: my-large-runner   # label you set up in org settings

Pros: no maintenance, same clean machine per job. Cons: billed per minute at a higher rate, and availability depends on your plan. Check GitHub's current docs and pricing page, since they change. A faster machine can be cheaper per run if it finishes much sooner, so compare cost per run, not per minute.

Self-hosted runners

You run the runner agent on your own machines.

  • Good for: GPUs, special hardware, access to a private network, very high volume where fixed hardware is cheaper, large persistent caches.
  • Costs: you patch, scale and monitor them, and you pay for idle time.

The security warning matters most. GitHub advises against using self-hosted runners with public repositories, since a pull request from a fork can run code on your machine. Prefer ephemeral runners that are destroyed after one job, and never put long-lived secrets on a persistent runner shared by untrusted code. See GitHub Actions security.

A decision table

SituationPick
Default jobs finish fastStandard hosted
Build is CPU bound, no special needsLarger hosted
Needs GPU or private networkSelf-hosted, ephemeral
Open source with fork pull requestsHosted only

A cost per run example

Say a build takes 20 minutes on a 2-core machine and 6 minutes on a machine with four times the cores that costs more per minute. If the per-minute price is under 3.3 times higher, the larger machine is cheaper per run and gives faster feedback. If the price is higher than that, it is only faster, not cheaper. The numbers are examples, so look up your own rates. The point is to compare cost per finished run, and to include how much developer waiting time you save.

Prove the gain

Run the same workflow on both for a week and compare median and p90 run time and cost per run. A proper before and after measurement prevents an expensive upgrade that changes little.

Questions people ask

Are self-hosted runners cheaper?

Only at sustained high volume, and only if you count the maintenance time and idle hardware. For small teams hosted runners are usually simpler.

Can I use self-hosted runners for public repos?

GitHub recommends against it, because fork pull requests can run arbitrary code on the machine. Use hosted runners for public repos.

Measure before you tune

See which workflows are slow before you change anything.

Cilytics is a public CI health dashboard for GitHub. It shows median and p90 run time per workflow, for an org or any public repo. It reads default-branch runs only, from an hourly snapshot.
