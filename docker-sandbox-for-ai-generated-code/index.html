AI sandboxes for agents

How to run AI-generated code in a Docker sandbox

A copy-paste docker run command that cuts off network, memory, processes and write access, plus a small Python wrapper to run agent code safely.

Run the code in a throwaway container with --network none, a memory limit, a read-only filesystem, a non-root user and all capabilities dropped. Mount only the files the code needs. This is not perfect isolation, but it stops the common accidents and most casual attacks.

The hardened command

docker run --rm \
  --network none \
  --memory 256m --memory-swap 256m \
  --cpus 0.5 \
  --pids-limit 64 \
  --read-only --tmpfs /tmp:rw,size=64m \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --user 65534:65534 \
  -v "$PWD/job:/job:ro" \
  -w /job \
  python:3.12-slim python main.py

Each flag closes one door. --network none removes the network. --pids-limit stops fork bombs. --read-only with a small --tmpfs gives the code one place to write. --user 65534 runs as the unprivileged nobody user.

Never mount the Docker socket

Do not pass /var/run/docker.sock into the container, and do not use --privileged. Either one hands the code control of the host. Also avoid mounting your home directory or the project root as writable.

Add a wall-clock timeout

Docker has no built-in run time limit, so enforce it yourself. This wrapper starts the container with a name and kills it if it runs too long.

import subprocess, uuid

def run_sandboxed(job_dir: str, timeout_s: int = 10):
    name = "sbx-" + uuid.uuid4().hex[:8]
    cmd = [
        "docker", "run", "--rm", "--name", name,
        "--network", "none", "--memory", "256m",
        "--pids-limit", "64", "--read-only",
        "--tmpfs", "/tmp:rw,size=64m",
        "--cap-drop", "ALL", "--user", "65534:65534",
        "-v", f"{job_dir}:/job:ro", "-w", "/job",
        "python:3.12-slim", "python", "main.py",
    ]
    try:
        p = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout_s)
        return p.returncode, p.stdout[-4000:], p.stderr[-4000:]
    except subprocess.TimeoutExpired:
        subprocess.run(["docker", "kill", name], capture_output=True)
        return 124, "", "timed out"

Truncating output matters: a loop that prints forever will otherwise fill your memory.

Dependencies without network

With no network the code cannot pip install. Build an image with the packages you allow, and run from that image. If the agent really must install packages, run that step in a separate container with network access and a package mirror, then run the code step offline.

Where Docker stops being enough

All containers share the host kernel. A kernel bug can let hostile code escape. For code from strangers, or agents reading untrusted web content, move to a stronger runtime: see Docker vs gVisor vs Firecracker. To run a whole local stack of services and agents with Docker, the open-source Flisk CLI can start them from one service.json per service, but it is a development tool, not a security boundary.

Test that the walls hold

Do not assume the flags work. Write a few hostile test scripts and run them in the sandbox: one that tries to reach the internet, one that writes outside /tmp, one that allocates memory forever and one that forks in a loop. Each should fail fast with a clear error. Keep these as a regression test, and run them again whenever you change the image or the Docker version.

Questions people ask

Does --network none break everything?

It blocks all network access, including DNS. That is the point for untrusted code. Allow specific access later through a proxy if the job needs it.

Can I run this on a Mac?

Yes, Docker Desktop and Colima both run Linux containers in a VM, which adds one more layer of isolation from your Mac.
