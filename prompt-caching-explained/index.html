Prompt caching explained: how to get cache hits

What prompt caching is, why only an identical prefix is cached, how to order a prompt so you get hits, and how to check that the cache is working.

Prompt caching lets a provider reuse the work it did on the start of your prompt, so a repeated prefix is billed at a lower rate and often starts faster. To get hits, put everything that stays the same at the top of the prompt and everything that changes at the bottom.

How a prefix cache works

The cache matches your prompt from the first token onward. As soon as one token differs, everything after that point is a miss. That is why the order of your prompt matters more than almost anything else.

Some providers cache automatically once a prompt is long enough. Others make you mark the cache point yourself, for example with a cache_control marker on a content block. Details such as minimum length, how long entries live and the discount differ by provider and change over time, so check the current docs.

Order the prompt: stable first, changing last

  1. System instructions and rules.
  2. Tool definitions.
  3. Reference documents or few-shot examples.
  4. Conversation history.
  5. The new user message.

Never put a timestamp, a request id or the user name at the top. A single changing line in the first paragraph makes every call a miss.

Mark a cache point (Anthropic-style example)

{
  "system": [
    { "type": "text",
      "text": "...long stable instructions...",
      "cache_control": { "type": "ephemeral" } }
  ],
  "messages": [ { "role": "user", "content": "the changing question" } ]
}

With automatic caching you send the same shape without the marker. The rule is the same: keep the prefix byte for byte identical.

Check that it works

The response usage block reports how many input tokens were read from the cache and how many were written. Log those two numbers. If cache reads stay at zero on repeated calls, something at the top of the prompt is changing, or the prompt is shorter than the provider's minimum.

When caching does not help

  • Short prompts, below the minimum cacheable size.
  • Traffic so sparse that entries expire between calls.
  • Prompts that are different on every call, such as a fresh document each time.

For repeated whole questions, a response cache is a different tool. See semantic cache vs exact cache.

A worked example

Say a support bot sends a 6,000 token system prompt plus a 200 token question. Without caching, you pay full input price for 6,200 tokens on every call. With the long prompt cached, the repeated 6,000 tokens are billed at the provider's cached rate and only the new 200 are billed normally. The saving grows with the size of the stable prefix and the number of calls inside the cache lifetime. Look up the current cached-read price on your provider's pricing page and put your own numbers into the formula in the cost estimate guide.

Questions people ask

Does prompt caching change the answer?

No. It reuses computation on the prompt prefix. The model output is generated as usual.

Why do I get no cache hits?

Usually a changing token near the top of the prompt, a prompt below the minimum size, or calls spaced further apart than the cache lifetime.
