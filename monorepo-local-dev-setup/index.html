Run microservices on your laptop

Local development setup for a monorepo with several services

A monorepo makes it easy to see every service. It does not make it easy to start them together unless the layout and the manifests agree.

For a monorepo, put one manifest in every service folder, give each service its own port, and run one command from the repository root. The tool then discovers the services, starts them in dependency order and shows you what is running. The layout matters more than the tool: if a service cannot be started from its own folder, no runner can fix that from outside.

What a good monorepo layout looks like

A layout that works with almost any runner:

shop/
  api/
    server.js
    service.json
  worker/
    worker.js
    service.json
  web/
    package.json
    service.json
  packages/
    shared/

Rules that save time later:

  • Every service can start from its own folder with one command.
  • Every service has its own port, written in one place.
  • Shared code lives in a package folder that is imported, not started.
  • Each service has its own dependency file, so the runtime picks up the right versions.

Workspace tools such as npm workspaces, pnpm, Nx or Turborepo handle installing and building shared packages. They are not a replacement for a service runner, and the two work together fine.

The plain approach

Many teams start with a root script: npm run dev that runs concurrently over each service, or a Makefile with a target per service. It works for three services. It starts to hurt when you need start order, readiness checks, per-service logs and a list of ports. You end up rewriting those in the script. Compose handles it for containers; see alternatives to Compose for local dev for the trade-offs.

The Flisk way: local processes

For local processes, Flisk scans the project for service.json files at any depth, so the folder names above need no special rules. Each service describes itself:

{
  "schemaVersion": 1,
  "appName": "worker",
  "appType": "worker",
  "command": "node worker.js",
  "dependsOn": ["api"]
}

Run flisk up --dry-run from the root to see what was discovered and in which order, then flisk up. A heavy part can sit behind a profile, and one service plus its dependencies starts with flisk up --only worker. See start only the services you need.

The Flisk way: containers

In a container project, discovery is stricter. Services are expected under the paths in discovery.paths, which default to services/*/*, which is a stack folder and then a service folder. Create services with the CLI, which puts them in the right place:

flisk project
flisk resource api --type backend --stack shop
flisk resource web --type frontend --stack shop

If you add a service by hand outside the scan path, flisk resource warns that it is outside discovery.paths. After you change the paths, run flisk config regenerate and then flisk config verify to check that the generated files match. Do not edit the generated .flisk/ files.

When the services live in several repositories

The hard case is not the monorepo, it is a company with one repository per service. A service.json outside the project root is not supported, so one Flisk project cannot reach into a sibling checkout. You have two options:

  • One project per repository. Each repo starts its own services. This is simple and works when the services are mostly independent.
  • A platform repository. It holds the project, and describes the other services as bring-your-own resources that build from a Dockerfile or run an image. flisk repos clone clones the repositories listed in .flisk/project.json that are missing.

Either way, agree on ports and URLs in writing. Two repositories that both want port 3000 will fight, whatever the tool.

Pitfalls

  • Port clashes. flisk doctor reports two services that share a port.
  • Hidden shared state. Services that read the same local file or database without saying so break in a different order on each machine. Write the dependency down.
  • Starting everything by default. A monorepo of twenty services will not run well on a laptop. Group them and start groups.

Naming helps in a large repository. Use the same pattern for every service folder, and keep the appName equal to the folder name, so a name in the logs maps to a path without a lookup. Keep the ports in a short table in the README as well, even though the manifests are the source of truth, because people read the table first. Decide who owns each service folder, so a broken manifest has a clear person to ask, and review manifest changes the way you review code.

Questions people ask

Where do service.json files go in a monorepo?

Put one service.json in each service folder. For local processes, Flisk finds them at any depth under the project. For container projects, services are expected under the discovery paths, which default to services/*/*.

Can one Flisk project span several repositories?

A service.json outside the project root is not supported. Either keep one project per repository, or use a platform repository that brings the other services in as bring-your-own resources. Flisk can clone repositories listed in .flisk/project.json with flisk repos clone.

Do I need a workspace tool like Nx or Turborepo?

Not to start services. Those tools build and cache packages. Starting the services, in order, with ports and health checks is a separate job that a process runner or Flisk handles.
