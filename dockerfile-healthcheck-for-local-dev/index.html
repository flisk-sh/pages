How to write a Dockerfile HEALTHCHECK that works in dev

Slim images often lack curl, so a copied HEALTHCHECK fails forever. Write one that matches what is in your image.

A HEALTHCHECK instruction tells Docker how to test whether the app inside a container really works, not just whether the process is running. The test is a command that exits 0 for healthy and 1 for unhealthy. The usual mistake is copying a curl command into an image that has no curl, which marks a perfectly good container unhealthy forever.

The instruction

HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1
  • --interval: how often to run the test (default 30 seconds).
  • --timeout: how long one run may take before it counts as a failure.
  • --start-period: a grace time after start when failures are not counted, for apps that boot slowly.
  • --retries: how many failures in a row make the container unhealthy.

The status moves from starting to healthy or unhealthy. Read it with:

docker inspect --format '{{.State.Health.Status}}' mycontainer
docker ps --format 'table {{.Names}}\t{{.Status}}'

Plain Docker does not restart an unhealthy container; the state is a signal. Compose uses it for depends_on with condition: service_healthy, see depends_on and healthchecks.

Pick a command your image has

The test runs inside the container, so it can only use what is installed there.

  • Alpine: BusyBox wget is present: wget -qO- http://localhost:3000/health. Add curl with apk add --no-cache curl only if you prefer it.
  • Debian slim: neither curl nor wget is guaranteed. Install one in the Dockerfile, or use the language runtime.
  • Node 18 or later: use the built-in fetch:
HEALTHCHECK CMD node -e "const u='http://localhost:3000/health';fetch(u).then(r =&gt; process.exit(r.ok ? 0 : 1)).catch(() =&gt; process.exit(1))"
  • Python:
HEALTHCHECK CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/health', timeout=2)"

The Python call raises on a connection error or an error status, which makes the interpreter exit non-zero. Always test against localhost and the port the app listens on inside the container, and make sure the app binds 0.0.0.0 or at least loopback.

What the endpoint should check

Keep it cheap and honest. A health route that returns 200 as soon as the server accepts requests is a liveness check. If you also want "ready for traffic", have a second route that checks that the database connection works. Do not make the health route call slow downstream services: a flaky dependency then takes your container down with it. The health versus readiness article draws this line for agents, and it applies to any service.

How Flisk treats it

For a bring-your-own resource, healthCheckPath in service.json is the path Flisk's router probes. In the generated Compose service, Flisk does not add its own container health check for such a resource, because it cannot assume your image has curl. A HEALTHCHECK in your Dockerfile therefore stays in effect, while the router's probe works separately.

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health"
}

Three related cases are verified in the generator. A resource with no healthCheckPath gets no HTTP probe, and Flisk disables the container health check so an image HEALTHCHECK aimed at a port nothing serves cannot mark it unhealthy. A healthCheck object can replace the probe with a command that runs inside the container, or a TCP port check, for services that do not speak HTTP. And healthCheck: false turns both the container check and the router probe off:

"healthCheck": {
  "command": ["pg_isready"],
  "startPeriod": 30
}

Use flisk status to see the result, and read the logs if a container stays unhealthy.

Pitfalls

  • A check that works on your host but not in the container. Run it with docker exec &lt;container&gt; sh -c '...' and read the exit code.
  • Using the container's published port. Inside the container the app listens on its own port, not the one mapped on your host.
  • A start period that is too short. A JVM or a framework with a cold build may need a minute, and retries run out before the app is up.
  • Health checks on one-shot jobs. A migration or seed container exits on purpose and should not have one.
  • Restart loops. If the container keeps exiting rather than turning unhealthy, see why a container keeps restarting.

Next step

Once health reporting is accurate, anything that depends on the service can wait for it. See how to control startup order for the Flisk side of that.

Questions people ask

Why is my container unhealthy when the app works?

The HEALTHCHECK command probably needs a tool the image lacks, usually curl, or it tests the wrong port. Run the command with docker exec and read its exit code.

Does Docker restart an unhealthy container?

Not by itself in plain Docker. The status is informational, though Compose and orchestrators can act on it, for example by waiting for service_healthy.

Does Flisk use the HEALTHCHECK from my Dockerfile?

For a bring-your-own resource with a healthCheckPath, Flisk adds no container health check of its own, so the Dockerfile one stays in effect, and the router probes the path separately.
