How to Run Agent PRs Safely in GitHub Actions

Pull requests from agents and forks run untrusted code in your CI. Use the right trigger, minimal token permissions and no secrets.

Run agent pull requests on the pull_request trigger with a read-only token and no secrets, and never check out and run their code under pull_request_target. An agent's branch is untrusted code until a human has read it.

Treat the branch as untrusted

An agent may be tricked by text in an issue, a web page or a dependency into writing something hostile, and a workflow that runs that code with your secrets hands them over. So the rule is the same as for fork pull requests: assume the code is hostile.

Pick the safe trigger

The pull_request event runs the workflow from the pull request's merge commit, and for forks it withholds secrets and gives a read-only token. The pull_request_target event runs in the context of the base branch with secrets and write access, which is dangerous if it checks out the pull request's code.

on:
  pull_request:

permissions:
  contents: read

Limit the token and secrets

  • Set permissions at the top of every workflow to the least you need, usually contents: read.
  • Keep deploy keys and cloud credentials out of any job that runs pull request code.
  • Use environments with required reviewers for jobs that need real secrets.
  • Pin third-party actions to a full commit SHA.

These are covered in depth in GitHub Actions security.

Never put untrusted text in a script

Titles, branch names and comments are attacker-controlled. Interpolating them straight into a shell step allows command injection. Pass them through an environment variable instead.

- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "$TITLE"

Audit workflows that call AI agents

If a workflow runs an AI agent on pull request content, check who can trigger it, what tools and tokens it holds, and whether attacker text reaches its prompt. This is a newer risk area, so review such workflows more carefully than ordinary ones. Pair it with the review rules in handling a flood of agent PRs.

A safe default workflow

Put the safe pieces together once and reuse them. A workflow that runs tests on agent pull requests should trigger on pull_request, declare read-only permissions, avoid secrets, pin actions by commit SHA and set a timeout so a hostile or runaway job cannot burn minutes.

on:
  pull_request:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
      - run: npm ci --ignore-scripts
      - run: npm test

The persist-credentials: false option stops the checkout step from leaving a token in the git config where later steps could read it. Installing with --ignore-scripts blocks install-time scripts from new dependencies; run the build steps you need explicitly afterwards. If you must use secrets, put that job behind an environment with required reviewers.

Questions people ask

Is pull_request_target always unsafe?

No. It is fine for tasks like labelling that do not run the pull request's code. It becomes dangerous when combined with checking out and executing that code.

Do agent PRs from the same repo get secrets?

Branches in the same repository run with the repository's secrets under pull_request, so scope secrets with environments and approvals.
