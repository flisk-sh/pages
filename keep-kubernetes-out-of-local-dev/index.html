Test the real stack, then hand it off

Why you can keep Kubernetes out of local development

Production may be a cluster. That does not mean every laptop needs one.

You can keep Kubernetes out of daily development by running your services with Compose or as plain local processes, building the same container image you ship, and using a cluster only for what truly depends on one. Application logic, API behaviour and migrations do not need a cluster to test. Charts, operators, network policies and RBAC do.

What a local cluster costs

Tools such as kind, minikube and k3d run a real cluster on your machine, and they are the right choice for some jobs. As the loop for everyday code changes they have a price. You need a container runtime plus the cluster, a registry or an image-loading step, manifests or a chart for every service, an ingress for URLs, and storage classes for databases. A small change goes through build, load, apply and rollout before you see it. People then skip the loop and test in a shared cluster, which is slower still.

A split that works

What you are testingWhere to run it
Code, API behaviour, queriesLocal processes or Compose, with live reload
Service-to-service wiring, migrations, browser flowsThe local stack in a script or CI job
The production image itselfThe same image run once as a container locally
Helm chart, CRDs, operators, probes, network policy, RBACkind or minikube, or a preview cluster
Capacity and failure behaviourA staging cluster

Most changes land in the first three rows, so most of your time never touches a cluster.

The Flisk way

Flisk is scoped to the local loop. Services that declare a command run as local processes with no Docker. Container stacks run on Docker and Tilt, with live reload and URLs on *.localhost hostnames. It does not emit Kubernetes manifests, and service.json is a description of local services, not a values.yaml. The flisk deploy command is an alias of flisk up and does nothing to a cluster. The project documentation states this boundary plainly, and leaves cluster deployment policy to your Helm, Kustomize, Flux or Argo setup.

What Flisk does export are files for other targets, written without deploying anything: render.yaml, wrangler.toml and a standalone Compose file. See from local to Render for the first. If you want the longer argument for skipping a cluster during development, read local dev without Kubernetes.

Keeping local and production close

The fear is that "works locally" will not mean "works in the cluster". Reduce the gap with habits, not with a local cluster:

  1. Run the shipped image. Build the production Dockerfile and run it once locally as a container. With Flisk this is a bring-your-own resource with --dockerfile or --image. Check bring your own Dockerfile. A scaffolded Dockerfile is a starting point, not a reviewed production build, so inspect it first.
  2. Use the same variable names. The chart's values should set the same names the local manifest lists. See env var names, not values.
  3. Respect health checks. The path a probe hits should be the path your local health check hits. A missing /health is a common cause of a pod stuck in a restart loop.
  4. Test in a cluster before release. Run the real chart in kind in CI, or in a preview namespace, with a smoke test. It catches wrong ports, missing config and permissions that local runs cannot.
  5. Run the integration suite on the local stack. See integration tests against the real stack.

When you should run Kubernetes locally

  • You write an operator, a controller or a CRD. There is no way to test them without an API server.
  • You maintain the Helm chart or Kustomize base itself, not just the application.
  • Your bug depends on cluster behaviour: DNS between pods, network policy, service accounts, init containers, sidecar injection or resource limits.
  • You use cluster-only features such as a service mesh, and the code branches on them.

In those cases use kind or minikube for that work, and keep your daily loop separate. Not having a cluster on every laptop is a choice about the loop. It is not a claim that the cluster is unimportant.

Pitfalls

  • Do not let the two descriptions drift. Two sources of truth (local manifest and chart) need a review habit or a check. Name the same ports, paths and variables in both.
  • Architecture matches matter. An image built on Apple silicon is arm64 and a cluster may be amd64. Build multi-architecture images, or build the release image in CI.
  • "Production-like" is not "production". A single-node local cluster still has none of the scale, latency or failure modes of the real one.

If your target is a single server rather than a cluster, the simpler path is deploy a standalone Compose file to a VPS.

Questions people ask

Does Flisk generate Helm charts or Kubernetes manifests?

No. It is a local development tool. It does not emit Kubernetes manifests, and a service.json file is not a values.yaml. The exporters it does have write render.yaml, wrangler.toml and a standalone Compose file. Deployment to a cluster stays with your own Kubernetes workflow.

When do I actually need kind or minikube?

When what you are testing is Kubernetes itself: a Helm chart, an operator or CRD, network policies, RBAC, probes and resource limits as the cluster applies them. For application code, a local stack is faster.

Is it risky that local and production differ?

Some risk is real. Reduce it by running the same container image locally that you deploy, using the same environment variable names, and running a smoke test in a real cluster before release.
