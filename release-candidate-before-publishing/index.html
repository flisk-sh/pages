How to Run a Release Candidate Before Publishing

Dry runs, pre-release tags and a test install give you a rehearsal of the real release, so mistakes happen where they are cheap to fix.

Rehearse the release with the same workflow, but stop before the irreversible step. Build the package, inspect its contents with npm pack --dry-run, publish a pre-release under a non-default tag such as next, install it in a clean directory and run it. Only then promote it.

Why a rehearsal helps

Publishing is the one step you cannot undo cleanly. Most release bugs are not in the code but in the packaging: a missing file, a wrong entry point, a binary without execute permission, a dependency that should have been a runtime one. A release candidate catches these because it runs the full path from tag to installable package.

Step 1: dry run

Show what would be published without publishing:

npm pack --dry-run
npm publish --dry-run

Read the file list. Check that the entry points in main, exports and bin exist in it, that test files and .env are absent, and that the size is what you expect. Add this as a CI job on every pull request, not only at release time.

Step 2: publish a pre-release under a tag

Give the version a pre-release suffix and publish it under a dist-tag other than latest. Users who run a plain install do not get it.

npm version 1.5.0-rc.1 --no-git-tag-version
npm publish --tag next --access public

Pre-release versions are consumed explicitly, for example with npm install your-package@next or the exact version. For other registries, look for the equivalent: pre-release versions in PyPI and crates are not picked by default either, but check your registry's rules.

Step 3: test the install like a user

Install from the registry into an empty directory and run the real entry points.

mkdir /tmp/rc-test && cd /tmp/rc-test
npm init -y
npm install your-package@1.5.0-rc.1
npx your-package --version

Do this on a clean machine or in a container, so your global tools do not hide a missing dependency. If your project has several platforms, test each one. Automate this as a smoke test job so the rehearsal is also the final check. See verify a release after publishing.

What a candidate catches

Typical finds are a missing files entry so the compiled folder is not included, a binary that lost its execute bit, a dependency listed under dev dependencies that the code needs at runtime, and an entry point that works in your repo but not from the package. Each of these passes every unit test, because tests run against source. Only installing the built package tells you the truth, which is why the rehearsal is worth the extra twenty minutes.

Step 4: promote or discard

If the candidate is good, publish the final version, for example 1.5.0, from the same commit or a commit that only changes the version. Do not republish the candidate under the final number. If it is bad, fix and publish rc.2. Candidates are cheap. The workflow that publishes them should be the same as the final one, only with a different tag, as in publishing an npm package from Actions.

Questions people ask

What is an npm dist-tag?

A named pointer to a version. The default install uses the latest tag, so publishing with --tag next keeps a pre-release away from normal users.

Is a dry run enough?

A dry run shows the file list but does not test installation. Install the candidate in a clean directory and run it for real confidence.
