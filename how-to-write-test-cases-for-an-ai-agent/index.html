Testing and evaluating AI agents

How to write test cases for an AI agent

Turn a vague goal like 'the agent should be helpful' into concrete test cases with inputs, expected behaviour and a pass rule you can run on every change.

A test case for an agent has three parts: a fixed input, a description of what a good outcome looks like, and a rule that decides pass or fail without a human. Start with 20 cases drawn from real tasks, run them on every change, and grow the set each time the agent fails in the wild.

Start from real tasks, not imagined ones

Open your logs, support tickets or your own chat history and copy 20 real requests. Imagined test cases tend to be tidy. Real ones have typos, missing details and odd goals, which is where agents break.

Cover a spread: common tasks, edge cases, tasks the agent should refuse, and tasks where it should ask a question. A set made of only easy cases will always look green.

Describe the outcome, not the exact words

Agent output varies from run to run, so do not compare full strings. State what must be true of the result. Prefer facts you can check by code: a file exists, a record was created, a tool was called with certain arguments, the answer contains a specific number.

{
  "id": "refund-01",
  "input": "Refund order 4821, the item arrived broken.",
  "must": [
    {"tool_called": "refund_order", "args": {"order_id": "4821"}},
    {"final_answer_mentions": ["refund", "4821"]}
  ],
  "must_not": [{"tool_called": "delete_customer"}]
}

Add a pass rule for each case

Decide how a case passes before you run it. Options, from strongest to weakest: an exact check on state (database, files), a check on tool calls, a pattern check on text, and finally a model-based grader for things like tone. Use the strongest check that works. Read deterministic graders and LLM-as-judge pitfalls before you reach for the weak end.

Keep cases small and independent

  • One behaviour per case, so a failure points at one thing.
  • Each case sets up its own state. No case depends on another having run first.
  • Use fixed fake data, not live systems, so results do not change with the world.

A runner can be a short script:

import json
cases = [json.loads(l) for l in open("cases.jsonl")]
failed = []
for c in cases:
    result = run_agent(c["input"])      # your agent
    if not check(result, c):            # your grader
        failed.append(c["id"])
print(f"{len(cases)-len(failed)}/{len(cases)} passed", failed)

Grow the set from failures

Every time the agent does something wrong in real use, turn that input into a new case before you fix it. Then the fix is proven, and the failure cannot return unseen. See building a golden dataset from logs for a process that scales. For a wider view of the practice, the hub page Testing and evaluating AI agents lists the full set of guides.

Questions people ask

How many test cases do I need?

Start with 20 to 30 real ones. That is enough to catch large regressions. Add cases whenever a real failure shows up.

Should test cases include the expected final text?

Rarely. Check facts and actions instead of exact wording, since a correct answer can be phrased many ways.
