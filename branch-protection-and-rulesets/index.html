Branch Protection and Rulesets for the Default Branch

Which rules to set on main: required checks, reviews, no force pushes, and how rulesets differ from classic branch protection. Includes the traps with required status checks.

Protect your default branch by requiring a pull request, requiring your CI check to pass, and blocking force pushes and deletion. Set it up as a ruleset or classic branch protection, and make sure the required check name matches a job that always runs.

The rules worth setting

  • Require a pull request before merging, so nothing lands without a diff.
  • Require status checks, naming the exact CI jobs that must pass.
  • Block force pushes and branch deletion, so history cannot be rewritten.
  • Require at least one approval if you have a team. For a solo maintainer, 0 approvals but required checks is still useful.
  • Require branches to be up to date if you want the checks to run on the merged result, at the price of more reruns.
  • Require linear history if you prefer squash or rebase merges.

Rulesets versus classic protection

Classic branch protection is configured per branch pattern in a repository. Rulesets are the newer system: you can layer several, target branches and tags by pattern, apply them across repositories at the organisation level, and run them in an evaluate mode that reports what would have been blocked without enforcing it. Use rulesets for new setups if your plan supports them. Check GitHub's documentation for the current feature list and plan limits.

The required check trap

A required status check is matched by name. If the job is skipped, the check never reports, and the merge sits waiting forever. This is common with path filters: a workflow that only runs when docs/** is untouched never reports on a docs-only change.

The standard fix is a single always-running summary job that depends on the others and is the only required check.

jobs:
  tests: { ... }
  lint: { ... }
  ci-ok:
    if: always()
    needs: [tests, lint]
    runs-on: ubuntu-latest
    steps:
      - run: test "${{ contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled') }}" = false

The same idea is used in monorepo CI, where many jobs are conditional.

Protect tags and workflows too

Release tags deserve a rule that blocks deletion and updates, because users and package tooling trust them. Use CODEOWNERS to require review from the right people for sensitive paths, such as .github/workflows/, where a change can alter what code runs with your secrets.

# .github/CODEOWNERS
/.github/workflows/ @owner/maintainers
/SECURITY.md        @owner/maintainers

Pitfalls

  • Admins can bypass by default in some setups. Decide on purpose whether that is allowed.
  • Do not require a check that is flaky. People learn to click re-run or bypass, and the rule loses meaning. Fix flakiness first, see flaky tests and CI.
  • A merge queue changes which events trigger CI. Make sure your workflows listen for the merge group event.

Test the rules with a throwaway pull request. Push a branch that fails a check and confirm the merge button is blocked, then try a direct push to the default branch and confirm it is rejected. If you use evaluate mode on a ruleset, read the insights for a week before turning on enforcement, so you see who would have been blocked and why. A rule that surprises your own team on day one will be worked around.

Questions people ask

Should a solo maintainer protect main?

Yes. Requiring a pull request and a passing check protects you from your own mistakes and makes CI a real gate. You can approve your own pull request or set approvals to zero.

Why is my pull request stuck on 'Expected - Waiting for status to be reported'?

A required check never ran, often because a path filter or condition skipped the workflow. Use an always-running summary job as the only required check.
