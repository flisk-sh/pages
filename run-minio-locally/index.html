How to run MinIO locally as S3-compatible storage for dev

Your code talks to S3 in production. Locally you can point the same code at a MinIO container and keep everything on your machine.

To run MinIO locally, start one container that serves /data, publish the S3 port 9000 and the console port 9001 on 127.0.0.1, and mount a named volume so objects survive a restart. Your code then uses the same S3 client as in production with a different endpoint. With Flisk, one flisk resource command writes that container definition and gives every service that depends on it the S3 settings as environment variables.

Why a local S3 stand-in at all

Code that uploads files to S3 is hard to test with mocks alone. A mock confirms that you called PutObject. It does not tell you that the key is right, that the content type survived, or that a second service can read the object back. A small server that speaks the S3 API gives you those answers on your laptop, with no AWS account, no network and no bill.

MinIO is the usual choice because it is one binary, it speaks the S3 API, and it has a web console. Other servers work too (Garage, SeaweedFS, LocalStack for several AWS services). The steps below stay the same: pick an image, set a data directory, publish a port, point the SDK at it.

The plain Docker way

One caveat first: MinIO stopped publishing its own images (minio/minio and quay.io/minio/minio), according to the Flisk docs. The Flisk preset uses pgsty/minio, a community build of the last open-source release with the same command line and S3 API. Check where an image comes from before you rely on it.

docker run -d --name dev-minio \
  -p 127.0.0.1:9000:9000 -p 127.0.0.1:9001:9001 \
  -e MINIO_ROOT_USER=minioadmin \
  -e MINIO_ROOT_PASSWORD=minioadmin \
  -v dev_minio_data:/data \
  pgsty/minio:RELEASE.2026-08-04T00-00-00Z \
  server /data --console-address ":9001"

Port 9000 is the S3 API and 9001 is the console. Open http://127.0.0.1:9001 and log in with minioadmin / minioadmin to create a bucket by hand. The 127.0.0.1 prefix keeps both ports off your network, which matters because the login is a well-known development default.

The Flisk way

Install the CLI with npm install -g @flisk-sh/flisk. In a project, with the 1.4.57 release I tested, MinIO is a framework of the database resource type:

flisk resource store --type database --framework minio --stack shop --yes

Newer source on the main branch moves MinIO to its own storage type, so run flisk resource --help to see which one your version lists. Either way the result is a plain bring-your-own service.json. This is what 1.4.57 wrote to services/shop/store/service.json:

{
  "appName": "store",
  "appType": "bring-your-own",
  "framework": "minio",
  "stack": "shop",
  "port": 9000,
  "image": "pgsty/minio:RELEASE.2026-08-04T00-00-00Z",
  "exposeViaProxy": false,
  "healthCheck": { "port": 9000 },
  "container": { "command": ["server", "/data", "--console-address", ":9001"] },
  "extraPorts": [{ "port": 9001 }],
  "volumes": [{ "source": "store-data", "target": "/data" }],
  "params": { "MINIO_ROOT_USER": "minioadmin", "MINIO_ROOT_PASSWORD": "minioadmin" },
  "provides": {
    "MINIO_ENDPOINT": "http://store:9000",
    "AWS_ENDPOINT_URL_S3": "http://store:9000",
    "AWS_ACCESS_KEY_ID": "minioadmin",
    "AWS_SECRET_ACCESS_KEY": "minioadmin"
  }
}

Three parts matter. extraPorts publishes the console on 127.0.0.1:9001 only. volumes keeps your objects in a named volume, and flisk down leaves it alone. provides lists the settings that every service naming store in its dependsOn receives in its environment. The AWS SDKs read AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY already, so a service only has to say it depends on the store:

"appName": "api",
"dependsOn": ["store"]

Start it with flisk up shop. Inside the stack, containers reach MinIO by name at http://store:9000. Flisk does not route it through Traefik.

The S3 port is not published to your machine by default, only the console is. A script or test that runs on your host cannot reach store:9000. Add { "port": 9000 } to extraPorts by hand and use http://127.0.0.1:9000 from the host.

Create buckets yourself

MinIO does not create buckets on its own, and Flisk does not either. Create one in the console, or have your app create it on startup if it is missing. The next article, pointing the AWS SDK at a local S3 endpoint, shows that code in Node and Python.

Pitfalls

  • Development credentials. minioadmin is public knowledge. Keep the ports on 127.0.0.1 and never reuse the pair anywhere real. provides is for plain, non-secret values only.
  • Two addresses. store:9000 works inside the stack and 127.0.0.1:9000 works from your host. Mixing them up is the common cause of "connection refused" and of broken presigned URLs.
  • Data survives flisk down. To start empty, use flisk down --purge, which deletes all of the project's Docker volumes, the database included. See keep volumes between runs, or reset them.
  • Pin the image. A moving tag can change the on-disk format under your data.

When not to use it

If your code only writes a few files and reads them back in the same process, a temporary directory is simpler. If production uses S3 features MinIO does not implement, such as some lifecycle or event rules, test those against a real bucket in a throwaway AWS account.

Next, connect your code to it with the SDK endpoint settings, then build browser uploads with presigned URLs.

Questions people ask

Is MinIO the same as S3?

No. MinIO implements the S3 API, so the same SDK calls work, but it is a different server. Features such as some lifecycle rules, event notifications and IAM details can differ, so test those against real S3.

Why can my script on my laptop not reach store:9000?

That name only exists on the Docker network. The Flisk preset publishes only the console on 127.0.0.1:9001. Add the S3 port to extraPorts and use http://127.0.0.1:9000 from the host.

Does flisk down delete my uploaded files?

No. The data lives in a named volume that flisk down keeps. flisk down --purge deletes the project's Docker volumes.
