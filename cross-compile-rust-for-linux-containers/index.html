How to cross-compile a Rust service for a Linux container

Rust needs a linker for the target, so unlike Go it is not two environment variables. There are three honest routes, and one is a plain Docker build.

The simplest reliable way to get a Linux binary from a Mac is to build inside a Linux container, with a multi-stage Dockerfile. If you want a native cross build on your machine, add a target with rustup and use cargo-zigbuild as the linker, or cross, which runs the build in a container for you. Pick one route per project and keep it in the repo, so that a teammate gets the same binary.

Why Rust is harder than Go

rustc can emit code for another target, but the final link step needs a linker and C libraries for that target. Go bundles its own linker and standard library, so two variables are enough. In Rust you choose among targets such as:

  • x86_64-unknown-linux-gnu and aarch64-unknown-linux-gnu: dynamic, link against glibc.
  • x86_64-unknown-linux-musl and aarch64-unknown-linux-musl: static, link against musl, so the binary runs on any Linux image, including scratch.

musl is convenient for tiny images, but two things bite. The default memory allocator in musl is slower under heavy allocation than glibc's, and crates that wrap C libraries (OpenSSL is the usual one) may not build. Choose rustls in place of OpenSSL for HTTP clients and databases, and you avoid most trouble.

Route 1: build in a container

This needs no local cross toolchain, and it is the same on every machine.

FROM rust:1-slim-bookworm AS build
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    --mount=type=cache,target=/app/target \
    cargo build --release && cp target/release/app /out-app

FROM debian:bookworm-slim
COPY --from=build /out-app /usr/local/bin/app
USER 10001
ENTRYPOINT ["app"]

The binary is copied out of the cache-mounted target folder in the same step, because a cache mount is not part of the image. On an Apple Silicon Mac this produces a linux/arm64 image; add --platform linux/amd64 to build for x86-64 under emulation, which is slow for Rust but works. For multi-platform pushes use docker buildx build --platform linux/amd64,linux/arm64.

Route 2: cargo-zigbuild

This uses the Zig compiler as the linker, so you can target Linux from macOS without Docker.

rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl
brew install zig
cargo install cargo-zigbuild --locked
cargo zigbuild --release --target x86_64-unknown-linux-musl
ls target/x86_64-unknown-linux-musl/release/

Copy the binary into a scratch or distroless image. For glibc targets, cargo zigbuild accepts a glibc version suffix on the target, such as x86_64-unknown-linux-gnu.2.28, to keep the binary compatible with older distributions.

Route 3: cross

cross is a drop-in for cargo that runs the build in a prepared container image.

cargo install cross --locked
cross build --release --target aarch64-unknown-linux-gnu

It needs a working Docker or Podman, and it is the least setup if you already run containers. It is slower than a native build, and crates with a build script that needs host tools can need extra configuration.

What Flisk does here

For a Rust resource made by flisk resource billing --language rust, Flisk writes a Cargo.toml whose binary is named app (the comment in the file says the image copies the release binary by that name), and it generates the image: a rust:1-slim-bookworm build stage with BuildKit cache mounts, a test stage running cargo test, and a debian:bookworm-slim production stage with a health check. It builds for the host architecture and does not cross-compile. If you keep a Dockerfile like Route 1 with an explicit platform or a musl target, register it as a bring-your-own resource, as shown in run an existing Dockerfile in a local dev stack:

flisk resource billing --type bring-your-own --stack app --dockerfile ./Dockerfile --yes

Keep the binary name app if you reuse the generated layout, and make the container listen on 0.0.0.0 and on PORT. The local-process scaffold binds localhost, which works for a process and not for a container.

Pitfalls

  • Linker not found. The error mentions cc or x86_64-linux-gnu-gcc. You added a target but no linker. Use one of the routes above.
  • OpenSSL on musl. Prefer rustls features of your HTTP and database crates.
  • Everything rebuilds. A different target gets its own folder under target, so the first cross build is cold. Cache it in CI.
  • Huge images. Do not ship the build stage. Copy only the binary into the last stage.

Questions people ask

Should I use musl or glibc for a Rust container?

Use musl for a static binary that runs in scratch or distroless images, and glibc when a dependency needs it or allocation speed matters. Test the choice with your own workload.

Can I cross-compile Rust from a Mac to Linux without Docker?

Yes. Add a Linux target with rustup and use cargo-zigbuild, which uses Zig as the linker.

Does Flisk build Rust for other platforms?

No. The generated image builds for the host architecture. Use your own Dockerfile as a bring-your-own resource when you need another target.
