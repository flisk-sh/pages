Durable AI agent sessions: save checkpoints that survive restarts

An agent that forgets everything when its process restarts is hard to develop against. Save a checkpoint per session before every reply and the problem goes away.

A durable agent session saves the conversation state after every turn, in a place that outlives the process, so a restart continues where it stopped instead of starting over. The usual way is one checkpoint per session id, written atomically (write a temp file, then rename it) or committed in a database transaction, before the reply is sent.

What a checkpoint has to contain

A checkpoint is whatever the next turn needs to behave as if nothing happened. At minimum that is the message history. For an agent with tools it may also hold tool results, a plan, a step counter or a scratchpad. Two rules keep it honest:

  • Save before you answer. If you reply first and crash before saving, the caller believes a turn happened that the agent has forgotten.
  • Make a turn a function of the checkpoint plus the new input. If the agent also keeps state in memory, that state is lost on every restart and the replay differs from the original.

Frameworks such as LangGraph and Mastra define their own checkpoint formats and replay logic. This is where you pick a store for them, not a replacement for them.

Where to store it locally

There are two sensible local choices. Files on a volume are the simplest: one JSON file per session, nothing extra to run. A Postgres row per session is better when several processes touch the same state, when you want to query sessions with SQL, or when you want local behaviour close to a production database. A container's own filesystem is not a choice, because it disappears when the container is recreated.

The Flisk agent resource

Flisk has an agent resource type that scaffolds a small Bun HTTP service with this contract already in place. It runs in Docker, so you need Docker and Tilt installed. Create a project, add the agent and start the stack:

flisk project --yes
flisk resource bot --type agent --stack shop --yes
flisk up shop

The generated service.json has the durability choice in an agent block:

{
  "appName": "bot",
  "appType": "agent",
  "stack": "shop",
  "port": 4000,
  "healthCheckPath": "/health",
  "agent": {
    "runtime": "custom",
    "durability": "files"
  }
}

With files (the default), checkpoints are written to /var/lib/flisk-agent/<sessionId>.json inside the container, on a named Docker volume called <project>-<stack>-autogenerated_<resource>-agent-state. A named volume survives flisk down and container recreation. Each write goes to a temporary file and is renamed into place, so a kill in the middle of a write leaves the previous checkpoint intact.

With --durability postgres (or "durability": "postgres") the agent reads DATABASE_URL, creates a flisk_agent_sessions table if it is missing, and upserts one row per session. Either way you only edit runTurn(checkpoint, input) in src/index.ts. The default body just echoes the input, so replace it with your model call and tools.

Try it: a turn, a restart, the same session

Get the agent's URL from flisk status (it has the form http://api.<project>.localhost/api/bot; the port can differ) and send two turns for one session id:

BOT=http://api.myproject.localhost:8080/api/bot   # use the URL flisk status prints
curl -s -X POST "$BOT/turn" -H 'content-type: application/json' \
  -H 'x-session-id: demo' -d '{"input":"hello"}'
flisk restart bot
curl -s -X POST "$BOT/turn" -H 'content-type: application/json' \
  -H 'x-session-id: demo' -d '{"input":"still there?"}'

The second reply reports turn 2 in the default scaffold, because the checkpoint with the first exchange was loaded from the volume. A request without a non-empty string input gets a 400 and writes nothing. A body over 1 MiB gets a 413 (change the limit with AGENT_MAX_TURN_BODY_BYTES).

Cleanup and limits

  • Old sessions are swept. A timer drops sessions idle for longer than SESSION_IDLE_TIMEOUT_MS (default 24 hours), checked every SESSION_CLEANUP_INTERVAL_MS (default 1 hour). A session with a turn in flight is never swept. Set either variable on the resource to change it.
  • Delete one session. DELETE on /session with the x-session-id header drops it, or answers 409 while a turn is running.
  • Delete all of them. Remove the volume yourself with docker volume rm and the volume name above. flisk down --purge also deletes the project's Docker volumes.
  • Concurrency is limited. The scaffold queues turns per session, but Flisk's own docs list known races in its counters, which affect the active or idle label in the session list and the drain timing. Use Postgres durability and your own locking if many callers share a session.
  • Model memory is yours. A checkpoint of messages does not replay a half-finished tool call with side effects. Make tools idempotent.

Questions people ask

Where does Flisk store agent checkpoints?

With files durability, in /var/lib/flisk-agent/<sessionId>.json on a named Docker volume that survives flisk down. With postgres durability, in a flisk_agent_sessions table.

Does flisk down delete my agent's sessions?

No. The named volume stays. flisk down --purge deletes the project's Docker volumes, and docker volume rm removes just the agent's volume.

Can I use LangGraph or Mastra checkpoints instead?

Yes. The custom runtime is a plain HTTP service with no model or framework dependency, so you can call a framework inside runTurn and use its own checkpointer.
