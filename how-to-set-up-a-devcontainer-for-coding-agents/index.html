How to Set Up a Dev Container for Coding Agents

A dev container gives an agent a clean, repeatable environment with the right tools installed, and limits the damage a bad command can do.

Add a .devcontainer/devcontainer.json that names an image, installs your tools and runs the install step, and an agent can start from a known-good environment every time. It also keeps agent commands away from your host machine, which is the safer default.

What a dev container gives you

The dev container spec is supported by VS Code, GitHub Codespaces and several other tools. You describe the environment once in the repo, and anyone, human or agent, gets the same Node or Python version, the same system packages and the same setup steps.

A minimal configuration

{
  "name": "app",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:20",
  "postCreateCommand": "npm ci",
  "forwardPorts": [3000]
}

Pick an image that matches your production runtime. Run the install in postCreateCommand so the agent never starts in a half-built state.

Limit what the container can reach

  • Mount only the project folder, not your home directory.
  • Do not pass cloud credentials or personal tokens into the container. Give the agent a narrow, short-lived token if it needs one.
  • Think about network access: an agent with open internet and a secret can leak the secret. If you can, restrict outbound traffic to the hosts it needs.

A container is a boundary, not a guarantee. For stronger isolation of untrusted code, look at sandbox options such as gVisor or Firecracker microVMs.

Bring up the services too

Most apps need a database or queue next to the code. You can add them with Docker Compose in the dev container, or run them with a local tool. The open-source Flisk CLI starts services, databases and queues from a service.json per service with flisk up, and services that declare a command run as plain local processes without Docker. It is for local development only. For the wider picture of local stacks, see microservices local dev.

Keep it honest with CI

Build the dev container in CI occasionally, or use the same base image in your workflow, so the file does not rot. A dev container that no longer builds is a trap for the next agent session.

Common problems

Slow first start is the usual complaint. Build the image once in CI and publish it to a registry, then reference it with image instead of building from a Dockerfile on every machine. Cache package downloads in a named volume so a rebuild does not fetch everything again.

Permission errors on mounted files are another. Containers often run as a different user than the host, so files the agent creates end up owned by root on the host. Set remoteUser to a non-root user and match the user id where your platform needs it. On macOS and Windows, file sharing between host and container can be slow for large dependency folders; keep node_modules in a container volume rather than the host mount.

Last, remember that the container needs the same environment variables your app expects. Provide safe defaults through .env.example and the remoteEnv setting, never real credentials.

Questions people ask

Do agents need a dev container?

No, but it makes runs repeatable and limits what a bad command can touch. It is most useful when several people or agents work on the same repo.

Is a dev container a security sandbox?

It adds isolation but is not a full sandbox. Treat it as a convenience boundary and avoid giving it real credentials.

Try it

Give your agent a repo it can run on the first try.

Flisk is an open-source CLI that starts a project's services, databases and queues locally from one service.json per service, so an agent gets one command to bring the stack up.
