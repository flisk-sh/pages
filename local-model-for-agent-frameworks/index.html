Agent frameworks on your laptop

How to point an agent framework at a local model with Ollama

Most agent frameworks can talk to any server that speaks the OpenAI API. That means a model on your laptop can replace the paid API while you build.

Ollama serves an OpenAI-compatible API at http://localhost:11434/v1. Any framework that lets you set a base URL for its OpenAI client can use it: set the base URL, set a dummy API key, and use a model name you have pulled. That is enough to develop an agent with no paid API calls, with one important limit: small local models handle tool calls much worse than hosted ones.

The three settings

Switching an agent to a local model is the same change everywhere:

  • Base URL: http://localhost:11434/v1 when the agent runs on your machine, or the model container's address when it runs inside a Docker network.
  • API key: the client library insists on one, and Ollama ignores it. Any non-empty string works.
  • Model name: exactly what ollama list shows, for example one you fetched with ollama pull.

The OpenAI Python and JavaScript clients read OPENAI_BASE_URL and OPENAI_API_KEY from the environment, so many frameworks need no code change at all:

export OPENAI_BASE_URL=http://localhost:11434/v1
export OPENAI_API_KEY=ollama

Frameworks that wrap provider classes take the same values as arguments. A few shapes, to be checked against the docs of your version:

# CrewAI
from crewai import LLM
llm = LLM(model="ollama/YOUR_MODEL", base_url="http://localhost:11434")

# OpenAI Agents SDK
from openai import AsyncOpenAI
from agents import OpenAIChatCompletionsModel
client = AsyncOpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
model = OpenAIChatCompletionsModel(model="YOUR_MODEL", openai_client=client)

// Vercel AI SDK (package @ai-sdk/openai-compatible)
const ollama = createOpenAICompatible({ name: 'ollama', baseURL: 'http://localhost:11434/v1' });
const model = ollama('YOUR_MODEL');

Replace YOUR_MODEL with a name from ollama list. Notice that CrewAI's ollama/ form uses the server root, while the OpenAI-style clients use the /v1 path.

Option 1: the model on your host, the agent as a local process

If you installed Ollama on your machine, it is already listening on port 11434. On a Mac this is also the only way to use the Apple GPU, because a container cannot reach it; Flisk's docs say the same and suggest running the model server on the host there. Run your agent as a Flisk local process and give it the URL in service.json:

{
  "schemaVersion": 1,
  "appName": "agent",
  "appType": "backend",
  "command": "uvicorn main:app --app-dir src --host localhost --port ${PORT:-4000}",
  "port": 4000,
  "healthCheckPath": "/health",
  "env": {
    "OPENAI_BASE_URL": "http://localhost:11434/v1",
    "OPENAI_API_KEY": "ollama"
  }
}

The dummy key is not a secret, so it can sit in the file. A real key must not; see keeping LLM API keys out of git.

Option 2: the model as a resource in the stack

When the agent runs in containers, Flisk has a preset for a model server:

flisk resource brain --type inference --stack kitchen

It writes a service.json with image ollama/ollama, port 11434 and the health path /v1/models. Ollama is only the default. You can pass --image to use vLLM, a llama.cpp server or another image, as long as it answers GET /v1/models. Other containers in the stack reach it at http://brain:11434/v1. Two cautions from Flisk's own notes:

  • The preset mounts no volume, so pulled models are lost when flisk down removes the container. Pull again after each flisk up, or bake the model into your own image.
  • A container on a Mac has no GPU access, so it is slow. Use option 1 there.

Pulling a model into the container is done with Ollama's own command through Docker Compose; Flisk's docs show docker compose exec brain ollama pull <model>.

What changes when the model is small

  • Tool calls. Not every local model supports tool calling, and small ones often produce bad arguments or skip the tool. If your agent depends on tools, check the model's tool support before blaming the framework.
  • Latency. A turn that takes two seconds on a hosted model can take much longer on a laptop CPU. Raise the timeouts in your client and in any step limits that count seconds.
  • Behaviour is not the same. A prompt that works on a local model may fail on the hosted one and the other way round. Treat the local model as a development stand-in and run the final checks against the model you ship with.

To test agent code with no model at all, replace the model with a scripted one, as in testing a Pydantic AI agent without a real model.

Questions people ask

Why does the client need an API key for a local model?

The OpenAI client libraries refuse to build a client without one. Ollama does not check it, so any non-empty string such as ollama works.

Does the Flisk inference preset keep pulled models?

No. The preset mounts no volume, so models pulled into the container are removed with it when the stack goes down. Pull again, or build an image that contains the model.

Can a container use the GPU on a Mac?

No, Docker on macOS cannot reach the Apple GPU. Run the model server on the host and point the agent at it.
