How to handle secrets and .env files for a stack in CI

Let the stack generate its own values, add only the real secrets a test needs, and keep them away from forks and logs.

A stack in CI usually needs no real secrets. Run flisk project --yes and it writes a git-ignored .env with generated values for the database password, the database URL and the JWT secret. Only pass real secrets, as GitHub repository secrets, for third-party services your tests truly call, and never to pull requests from forks.

Let the stack generate its own

On a fresh clone there is no .env, because Flisk's generated .gitignore excludes .env, .env.* (except .env.example), .flisk/.flisk-out/ and .flisk/smoke/. One command creates it, with no Docker or Tilt:

- run: flisk project --yes

The file contains TILT_ENV, DB_PASSWORD, DATABASE_URL and JWT_SECRET. The secrets are generated for this project, so a CI run holds throwaway values that protect nothing but a database that is deleted at the end of the job. This is the best default: nothing to rotate, nothing to leak from repository settings.

Use your own env file with --env-file

flisk up --env-file <path> uses that file instead of .env for the run. The rules are strict:

  • The file must be inside the project and must exist.
  • It must contain TILT_ENV, DB_PASSWORD and JWT_SECRET. Flisk does not fill in missing ones, and it never prints the values.

So an extra file for CI is best built from the generated one. Create .env first, copy it, and append what is special to CI:

- run: flisk project --yes
- name: Build CI env file
  run: |
    cp .env .env.ci
    echo "STRIPE_TEST_KEY=${{ secrets.STRIPE_TEST_KEY }}" >> .env.ci
- run: flisk up --wait --env-file .env.ci

.env.ci matches the .env.* ignore rule, so it cannot be committed by accident. Delete it in a final if: always() step on a self-hosted runner.

Declare which secrets a service needs

In a service.json, secrets.required lists names the service cannot start without. They become ${NAME:?...} in the generated Compose file, so the stack refuses to start and names the missing one. Names in secrets.optional become ${NAME:-} and default to empty. This turns a vague runtime failure, such as a 401 from a third party twenty seconds later, into a clear message at start-up. Only names are written to files, never values.

For a stack run as local processes, the env block of a service can reference ${VAR}, resolved from the shell first. That means a GitHub secret exposed with env: on the step reaches the process directly, with no file at all.

Rules for real secrets in GitHub Actions

  1. Scope them. Put a secret in the step's env: where it is needed, not at the top of the workflow.
  2. Know the fork rule. Workflows from forked pull requests do not receive repository secrets. A test that needs one will fail for outside contributors, so use a stub or skip that test when the variable is empty.
  3. Avoid pull_request_target with a checkout of the PR code. It runs with secrets while executing untrusted code. That combination is a known way to leak credentials.
  4. Mask derived values. GitHub masks the secrets it knows. A value you compute, such as a token built from a secret, needs echo "::add-mask::$VALUE" first.
  5. Use test keys. A CI run against a payment provider should use its test mode. A live key in CI turns a bug into a real charge.

Check that nothing leaks

Flisk masks values from .env in the output of flisk logs and in smoke records. That helps, but your own code can still print a secret in a different form, so do not log request headers or full configuration objects. Before you upload logs as an artifact, read how to get useful logs when a CI run fails for what to keep out.

Pitfalls

  • Committed .env. If one exists in history, rotate every value in it, because deleting the file does not remove it from history.
  • An --env-file missing a key. The run fails on TILT_ENV, DB_PASSWORD or JWT_SECRET. Start from the generated file.
  • Shell values winning. For process services, a variable set in the shell overrides the same name in .env. A stray CI-level variable can change a service silently.
  • Secrets in image layers. Do not copy an env file into an image. Pass values at run time.

When not to automate this

If your tests only need the generated defaults, do not create repository secrets at all. Each real secret is a thing to rotate and a way for a fork or a log to expose it. Add one only when a test cannot run without the real service, and give it the smallest permissions.

The last piece is the data in the database. See how to run migrations and seed data in CI before tests.

Questions people ask

Does the generated .env contain real secrets?

No. flisk project --yes generates values for this project, such as the database password and JWT secret. In CI they only protect a database deleted at the end of the job.

What must a file passed to --env-file contain?

It must exist inside the project and contain TILT_ENV, DB_PASSWORD and JWT_SECRET. Flisk does not complete it and never prints the values.

Why do tests that need a secret fail on pull requests from forks?

GitHub does not give repository secrets to workflows run for forked pull requests. Use a stub or skip the test when the variable is empty.
