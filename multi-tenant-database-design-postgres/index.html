How to design a multi-tenant database in Postgres

Almost every SaaS app has customers whose data must never mix. The choice you make on day one decides how hard migrations, backups and bugs are later.

For most SaaS apps, start with one database and shared tables that carry a tenant_id column on every row. It is the cheapest model to migrate and to run, and with a few rules about keys and indexes it keeps tenants apart reliably. Move to a schema or a database per tenant only when a concrete requirement forces you to.

The three models

ModelIsolationMigrationsGood fit
Shared tables, tenant_id columnLogical, enforced by your queries or row level securityOne run for everyoneMany small and medium tenants
Schema per tenantSeparate namespaces in one databaseRun once per schemaDozens to a few hundred tenants, per-tenant restore
Database per tenantStrongest, separate connections and backupsRun once per databaseFew large tenants, contractual isolation, data residency

The cost of the last two is operational. Every migration has to be applied to every schema or database, and one that fails halfway leaves tenants on different versions. Connection counts grow with tenants, and cross-tenant reporting needs extra plumbing. You pay that bill from the first day, even if you have three tenants.

Rules for the shared-table model

The shared model works when every table follows the same rules:

  • Every tenant-owned table has tenant_id uuid not null. No exceptions for "small" tables, they become big tables.
  • Uniqueness is per tenant. A project slug is unique within a tenant, not across the whole table.
  • Foreign keys include the tenant. A plain foreign key from tasks.project_id to projects.id lets a task in tenant A point at a project in tenant B. A composite key prevents it.
  • Indexes lead with tenant_id. Almost every query filters by tenant, so (tenant_id, created_at) serves far more queries than (created_at).
create table tenants (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  name text not null,
  created_at timestamptz not null default now()
);

create table projects (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants(id),
  slug text not null,
  name text not null,
  created_at timestamptz not null default now(),
  unique (tenant_id, slug),
  unique (tenant_id, id)
);

create table tasks (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null,
  project_id uuid not null,
  title text not null,
  foreign key (tenant_id, project_id) references projects (tenant_id, id)
);

create index tasks_tenant_project on tasks (tenant_id, project_id);

The extra unique (tenant_id, id) on projects exists only so the composite foreign key has something to point at. gen_random_uuid() is built into Postgres 13 and newer.

Where the tenant comes from

Do not read the tenant from a request body. Derive it once per request from something you trust, such as the session, the API key or the host name, and pass it down explicitly. Put one function at the edge of your data layer that takes the tenant and returns a scoped repository, so a forgotten where tenant_id = ... is hard to write. For a stronger safety net, add database-enforced filtering, covered in Postgres row level security for tenants.

Running it locally with Flisk

You need a real Postgres to test constraints, and a plain container is enough. If your services run as local processes, Flisk can start Postgres from an image next to them. Docker must be running for that database, and the local services need nothing else:

{
  "schemaVersion": 1,
  "appName": "postgres",
  "appType": "bring-your-own",
  "image": "postgres:17-alpine",
  "port": 5432,
  "env": {
    "POSTGRES_USER": "${POSTGRES_USER}",
    "POSTGRES_PASSWORD": "${POSTGRES_PASSWORD}",
    "POSTGRES_DB": "app"
  },
  "healthCheck": { "command": ["pg_isready", "-U", "${POSTGRES_USER}"] },
  "volumes": [{ "source": "postgres", "target": "/var/lib/postgresql/data", "name": "saas_postgres" }]
}

The API lists "dependsOn": ["postgres"] and connects to localhost:5432. Set POSTGRES_USER and POSTGRES_PASSWORD in the project .env. The mount path is for Postgres 17 and older, from 18 it must be /var/lib/postgresql. Run flisk config verify after editing. For the container route, see how to run Postgres locally, and for the per-service question see one database per service.

Pitfalls

  • Tests with one tenant. Seed at least two tenants with overlapping slugs and ids of the same shape, and assert that tenant A can never read tenant B. Most leaks show up only with two.
  • Global tables. Plans, countries and feature definitions are shared on purpose. List them somewhere so a reviewer knows a missing tenant_id is intentional.
  • The noisy tenant. One huge tenant slows shared indexes for everyone. Partitioning by tenant_id or moving that tenant to its own database is the later escape hatch, which is a reason to keep the tenant explicit in every query now.
  • Do not shard early. If you will never have contractual isolation or tenants with terabytes, a schema per tenant is cost without benefit.

Next, add the safety net: enable row level security so the database itself refuses cross-tenant reads, then use seed data with two tenants to prove it.

Questions people ask

Should I use a schema per tenant in Postgres?

Only if you need per-tenant restore or strong namespace separation and you have a manageable number of tenants. Each migration must run once per schema, which grows slow and error-prone with hundreds of tenants.

Do I need a tenant_id on every table?

Yes for every table that holds tenant-owned data, including join tables. Shared reference data such as plan definitions is the exception, and you should document it as such.

How do I stop a row pointing at another tenant's row?

Use a composite foreign key on (tenant_id, parent_id) that references a unique (tenant_id, id) on the parent table.
