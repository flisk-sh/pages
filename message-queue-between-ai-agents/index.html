How to connect AI agents with a message queue

A queue lets agents work at their own pace, survive restarts and retry failed tasks. Here is a simple design with a database table you already have.

Put tasks in a queue and let each worker agent pull one at a time. The queue gives you retries, back-pressure and a record of what was done, and it removes the need for agents to call each other directly. You can start with a plain database table.

Why a queue instead of direct calls

Agent calls are slow and sometimes fail. If agent A calls agent B over HTTP and B is busy or restarting, A is stuck. With a queue, A writes a task and moves on. B picks it up when ready. If B crashes halfway, the task goes back in the queue.

Queues also let you scale by running more workers on the same queue, and they cap load: a burst of 500 tasks waits its turn instead of hitting your model rate limit at once.

A queue in one SQL table

For a small system, Postgres is enough. Use FOR UPDATE SKIP LOCKED so two workers never claim the same row.

CREATE TABLE tasks (
  id         bigserial PRIMARY KEY,
  kind       text NOT NULL,
  payload    jsonb NOT NULL,
  status     text NOT NULL DEFAULT 'queued',
  attempts   int  NOT NULL DEFAULT 0,
  result     jsonb,
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- claim one task
UPDATE tasks SET status = 'running', attempts = attempts + 1, updated_at = now()
WHERE id = (
  SELECT id FROM tasks WHERE status = 'queued' AND kind = 'summarize'
  ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
RETURNING *;

Make tasks safe to retry

Queues deliver a task at least once, so a worker may run it twice. Design for that. Give each task an id, write results keyed by that id, and make side effects idempotent: check whether the output already exists before sending the email or opening the pull request.

  • Cap attempts, for example at 3, then mark the task dead for a person to look at.
  • Reset tasks stuck in running longer than a timeout back to queued.
  • Store the model error with the failed attempt. It is the first thing you will want to read.

When to use a real broker

A table is fine for dozens of tasks per second. When you need fan-out to many consumers, delays, priorities or higher throughput, use a broker such as Redis, RabbitMQ or a cloud queue. The agent code barely changes: it still claims a task, works, then reports a result. The older guide on workers and queues covers the options.

Pairing it with an orchestrator

The orchestrator writes one row per subtask and polls for results, or the workers write results to a second table. This is the same orchestrator-worker layout from the first guide, with the queue as the transport. The Flisk Agent Stack starter scaffolds a multi-agent layout with tools, a database and messaging that you can use as a reference.

Questions people ask

Do I need Kafka or RabbitMQ for agents?

Not to start. A database table with SKIP LOCKED handles small workloads. Move to a broker when you outgrow it.

How do I avoid running a task twice?

You cannot fully avoid it, so make the task idempotent: key results by task id and check for existing output before side effects.
