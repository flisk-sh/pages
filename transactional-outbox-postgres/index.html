How to use the transactional outbox pattern with Postgres

Saving data and publishing an event are two writes to two systems, and one of them can fail. An outbox table turns them into one.

The transactional outbox pattern means your service inserts the business row and an "event to send" row in the same database transaction, and a separate relay process reads the unsent rows and publishes them to the broker. Either both rows commit or neither does, so you never save an order without its event or send an event for an order that rolled back.

The dual-write problem

Take a request handler that creates an order and then publishes order.created. Whatever order you do it in, there is a window where one write succeeds and the other does not:

  • Insert, then publish: the process crashes between the two, and the order exists but nobody hears about it.
  • Publish, then insert: the insert fails, and consumers react to an order that does not exist.
  • Publish inside the transaction, before commit: the commit fails, same result as above.

Retrying does not fix this, because the crash can take the retry logic with it. You need the two facts to be stored together, and a database transaction is the one tool that does that.

The outbox table

Add a table next to your business tables, in the same database:

CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  event_id     uuid NOT NULL DEFAULT gen_random_uuid(),
  type         text NOT NULL,
  payload      jsonb NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz
);

CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;

The partial index keeps the relay query fast even after millions of published rows. gen_random_uuid() is built into Postgres 13 and later. The event_id is the identity of the event and travels to every consumer; it is what makes deduplication possible later.

In the handler, write both rows in one transaction:

await client.query("BEGIN");
const { rows } = await client.query(
  "INSERT INTO orders (customer_id, total) VALUES ($1, $2) RETURNING id",
  [customerId, total]
);
await client.query(
  "INSERT INTO outbox (type, payload) VALUES ($1, $2)",
  ["order.created", JSON.stringify({ orderId: rows[0].id, total })]
);
await client.query("COMMIT");

The relay

The relay is a small loop. It locks a batch of unsent rows, publishes each one, marks them sent and commits. FOR UPDATE SKIP LOCKED means a second relay copy would skip the rows the first one holds instead of waiting.

import pg from "pg";
import { connect, StringCodec } from "nats";

const sc = StringCodec();
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 2 });
const nc = await connect({ servers: process.env.NATS_URL });
const js = nc.jetstream();

async function drainOnce() {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(
      `SELECT id, event_id, type, payload FROM outbox
       WHERE published_at IS NULL ORDER BY id LIMIT 50
       FOR UPDATE SKIP LOCKED`
    );
    for (const r of rows) {
      const body = { id: r.event_id, type: r.type, data: r.payload };
      await js.publish(`events.${r.type}`, sc.encode(JSON.stringify(body)), {
        msgID: r.event_id,
      });
    }
    if (rows.length) {
      await client.query(
        "UPDATE outbox SET published_at = now() WHERE id = ANY($1)",
        [rows.map((r) => r.id)]
      );
    }
    await client.query("COMMIT");
    return rows.length;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

while (true) {
  const n = await drainOnce();
  if (n === 0) await new Promise((r) => setTimeout(r, 500));
}

This assumes a JetStream stream that covers events.> already exists; see NATS for local development. The msgID option sets the message ID header, which JetStream uses to drop duplicates published within its duplicate window (two minutes by default). That is a bonus, not a guarantee.

The outbox gives you at-least-once delivery. If the relay publishes and then crashes before the commit, the row is sent again on restart. Consumers must tolerate duplicates, see making a consumer idempotent.

The Flisk way

A stack for this has four pieces: the API, the relay, Postgres and a queue. Create them from the CLI:

flisk resource shop-db --type database --stack shop --yes
flisk resource bus --type queue --stack shop --yes
flisk resource orders-api --stack shop --yes
flisk resource outbox-relay --type worker --stack shop --yes

Then add dependencies in the two service files, so each gets the connection strings it needs:

"dependsOn": ["shop-db"]            // orders-api
"dependsOn": ["shop-db", "bus"]     // outbox-relay

Per the Flisk docs, a service that depends on a database resource receives DATABASE_URL, and the queue resource provides NATS_URL to its dependents. Run flisk config verify to check the files, and flisk up shop to start. The CREATE TABLE belongs in your migrations, not in a service start script; see database migrations in local dev. If the relay does not see events, flisk run outbox-relay -- printenv DATABASE_URL shows which database it uses.

Pitfalls

  • Run one relay. With several relays, rows are claimed in parallel and the order of publishing is no longer the order of id. If order matters, keep a single relay or read keeping events in order per entity.
  • Clean up. Delete published rows older than a day or two with a scheduled job, or the table grows without bound.
  • Publish failures block the batch. A poison message that always throws will stop the relay on that row. Log the event id and decide whether to skip it.
  • Polling delay. A 500 ms sleep adds up to half a second of latency. Postgres can wake the relay immediately, see LISTEN/NOTIFY as an event bus.

You may not need an outbox when losing an event is harmless, or when the broker publish is the only write. For everything else, the next step is the receiving end: a consumer that survives the duplicates this pattern creates.

Questions people ask

Does the outbox pattern guarantee exactly-once delivery?

No. It guarantees that an event is never lost once the transaction commits, which is at-least-once delivery. A relay crash after publishing but before marking the row sent causes a second publish, so consumers must deduplicate.

Can I use the outbox pattern with a database other than Postgres?

Yes. Any database with transactions works. The relay query uses FOR UPDATE SKIP LOCKED, which Postgres, MySQL 8 and Oracle support, so on other databases you may need another way to claim rows.

Should I use change data capture instead of a polling relay?

Change data capture tools such as Debezium read the database log and remove the polling loop. They add another service to run. For a local setup and modest volume, a polling relay is simpler to understand and debug.
