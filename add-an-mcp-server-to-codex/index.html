MCP servers and coding assistants

How to add an MCP server to Codex (config.toml and CLI)

Codex keeps MCP servers in TOML. Add one from the command line or by hand, and know when a project file is loaded.

To add an MCP server to Codex, run codex mcp add <name> -- <command> for a stdio server, or add a [mcp_servers.<name>] table to ~/.codex/config.toml or, for a trusted project, .codex/config.toml. Then run codex mcp list in a terminal or /mcp inside Codex to confirm the server is connected.

Global file versus project file

Codex reads configuration from ~/.codex/config.toml, and a project can add its own .codex/config.toml. Codex loads project-scoped MCP settings only for projects you have marked as trusted, and only when you run it inside that project. That is a sensible default: opening a stranger's repository should not start programs on your machine.

Use the project file for servers tied to one repository, and the global file for tools you want everywhere. If the same name appears in both, be careful: some options set globally can leak into the project entry.

A stdio server

From a terminal, the quickest form is:

codex mcp add flisk -- flisk mcp

Or write it yourself:

[mcp_servers.flisk]
command = "flisk"
args = ["mcp"]

This is the exact entry that Flisk's own repository uses. Optional fields such as env and cwd exist for a server that needs variables or a starting directory; see the Codex MCP guide for the full list.

A server on a URL

A Streamable HTTP server, such as one you built and run on localhost, is configured with a URL instead of a command:

[mcp_servers.docs-mcp]
url = "http://localhost:4000/mcp"

Before you add it, make sure the endpoint answers. curl it as shown in building an MCP server locally, so that a failure in Codex has only one place to come from. For a server run by Flisk, copy the address from flisk networks.

The Flisk shortcut

flisk connect codex --dry-run
flisk connect codex

This writes a flisk entry to .codex/config.toml and the Flisk skills to .agents/skills/. The new entry has no cwd or any other path that exists only on your machine. An existing different flisk entry is kept unless you pass --force, so read the whole file before you commit it. --global writes the entry to ~/.codex/config.toml and skips the skills. Codex reads the AGENTS.md and the skills in .agents/skills/ that Flisk writes, so a new project needs nothing else.

The working-directory trap

A project-aware server needs to start in the project. With a project entry, Codex starts the server in the folder where you run it, so no cwd is needed. With the global file, there is no single project: set cwd to the absolute path of the folder you want, or start Codex in that folder. Two further notes from Flisk's setup guide:

  • Some older Codex app versions start a stdio server in / when the entry has no cwd. If the tools then report that they are not in a Flisk project, update Codex or pass the projectPath argument.
  • If your global entry sets cwd, Codex can apply it to a project entry of the same name too. Remove it there when you use a project entry.

Do not commit an absolute cwd to a shared file. It will not exist on a teammate's machine.

Check it

  1. codex mcp list shows the configured servers.
  2. Start codex in the project, trust the folder if asked, and run /mcp.
  3. Ask for one thing by name: "Run Flisk doctor and tell me what would block startup." For your own server, name one of its tools.
  4. Watch the server's log to see the call arrive.

Pitfalls

  • The project entry is silently ignored. The usual cause is an untrusted project. Trust it, or put the entry in the global file.
  • Environment. A server that needs an API key should get it from env or from your shell, never from a value typed into a committed file.
  • Tool sprawl. Keep the list of servers short. Each one adds descriptions the model has to read.

With the connection working, teach Codex how to behave in this repository. Codex loads AGENTS.md directly, so continue with writing an AGENTS.md file.

If the stack behind the server will not start, work through checking your machine before starting first.

One more habit helps: write down which servers the project expects, in a README or AGENTS.md, so a new teammate can add the same entries in a minute. Commit the project file only when it has no absolute paths and no secrets, and keep personal servers, the ones with your own tokens, in the global file.

Questions people ask

Where does Codex read MCP servers from?

From ~/.codex/config.toml for all projects, and from a project .codex/config.toml, which is loaded only for trusted projects when you run Codex inside that project.

How do I check that Codex connected to my MCP server?

Run codex mcp list in a terminal, or /mcp inside Codex. Then ask it to call one tool by name.

Do I need cwd in the Codex MCP entry?

Not for a project entry, because Codex starts the server in the project folder. In the global file, set cwd to the project's absolute path or start Codex in that folder. Do not commit an absolute path.
