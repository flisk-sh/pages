How to call a gRPC service from a browser: gRPC-Web and Connect

A browser cannot open a raw gRPC connection. You need a protocol it can speak: gRPC-Web through a proxy, or a server that understands Connect.

A browser cannot call a gRPC server directly, because web APIs give JavaScript no control over HTTP/2 framing and trailers. The two practical fixes are gRPC-Web, usually with a translating proxy such as Envoy in front of the server, and the Connect protocol, where the server handles browser-friendly requests itself. Either way, you also configure CORS for local development.

The three protocols

  • gRPC: HTTP/2 with trailers. Works between servers, not from page JavaScript.
  • gRPC-Web: a variant that fits in what browsers can send. It needs either a proxy that converts it to gRPC or a server with built-in support.
  • Connect: a protocol from the Connect RPC project (connectrpc.com). A Connect server answers three kinds of requests on the same port: Connect, gRPC-Web and gRPC. Unary calls can be sent as plain JSON over HTTP POST, so even curl works.

Option 1: gRPC-Web with a proxy

Keep your existing gRPC server and add a proxy that translates. Envoy has a grpc_web HTTP filter for this, and the gRPC-Web project documents a ready Envoy config. The proxy listens on its own port (for example 8080), receives gRPC-Web from the browser and forwards gRPC to the server on 50051. You then generate a gRPC-Web client (with the protoc-gen-grpc-web plugin or Buf) and point it at 8080.

It works, but it adds a moving part to every developer's machine. Use it when you cannot change the server.

Option 2: serve Connect from the server

If you control the server, a Connect library removes the proxy. connect-go, connect-node and connect-es let one handler speak all three protocols. Generate the client with protoc-gen-es (see generating Protobuf code with buf) and call it from the browser:

import { createClient } from '@connectrpc/connect'
import { createConnectTransport } from '@connectrpc/connect-web'
import { Orders } from './gen/shop/v1/orders_pb'

const transport = createConnectTransport({ baseUrl: 'http://localhost:8080' })
const orders = createClient(Orders, transport)

const res = await orders.getOrder({ id: '42' })

Use createGrpcWebTransport from the same package when you want the browser to speak gRPC-Web instead. Check Connect from a terminal with plain curl:

curl -s http://localhost:8080/shop.v1.Orders/GetOrder \
  -H 'content-type: application/json' \
  -d '{"id": "42"}'

Native gRPC clients (other services, grpcurl) still work against the same port. In Go, serving gRPC over plain HTTP/2 without TLS requires h2c support from golang.org/x/net/http2/h2c; connect-go's documentation shows the wiring.

CORS for local development

The browser sends a preflight OPTIONS request, because the content type is not a simple one. The server must answer it. For Connect and gRPC-Web, allow the request headers Content-Type, Connect-Protocol-Version, Connect-Timeout-Ms, X-Grpc-Web, X-User-Agent and Grpc-Timeout, plus your auth header, and expose the response headers Grpc-Status, Grpc-Message and Grpc-Status-Details-Bin so the client can read errors. The Connect project publishes the exact lists for each protocol; use them rather than copying from a blog post. Allow only your dev origin (for example http://localhost:3000), not *, especially if you send credentials. The GraphQL CORS article explains how to read preflight failures in the browser network tab, which applies here too.

Running it as part of a stack

The browser app, the Connect or gRPC server and an optional proxy are separate processes. With Flisk you can describe each with a command, a port and dependsOn, and flisk up starts them in order with prefixed logs. Install with npm install -g @flisk-sh/flisk. I have not verified how Flisk's Traefik gateway treats plain HTTP/2 gRPC traffic, so for gRPC keep the service off the gateway: use local processes and call http://localhost:<port> directly, as in running a frontend and an API together. A TCP healthCheck on the port is enough to order the start (see gRPC health checks).

Which option to pick

SituationChoice
You own the server and it is newConnect handlers, no proxy
Existing gRPC server you cannot changegRPC-Web plus a proxy such as Envoy
Only server-to-server callsPlain gRPC, no browser support needed
You mostly want a JSON API for the webA REST or GraphQL layer in front

The last row is a fair answer. Many teams use gRPC between services and expose GraphQL or REST to the browser, which keeps browser concerns out of the service contract.

Pitfalls

  • Using a gRPC-only server from the browser. The request fails with a protocol or CORS error. Add a proxy or Connect.
  • Streaming limits. Browsers support server streaming in gRPC-Web and Connect, but not client or bidirectional streaming.
  • Proxies that buffer. Some dev proxies buffer responses, which breaks streaming. Test the stream with the proxy removed first.

Questions people ask

Why can't browsers call gRPC directly?

Browser JavaScript APIs do not give access to HTTP/2 framing and trailers that gRPC needs, so a browser-friendly protocol is required.

Do I need Envoy for gRPC-Web?

Only if your server does not speak gRPC-Web itself. With Connect or a server library with built-in gRPC-Web support you can skip the proxy.

Can a browser use client streaming or bidirectional streaming?

No. gRPC-Web and Connect in browsers support unary and server-streaming calls only.
