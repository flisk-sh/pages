Database schema for product variants: sizes, colours and SKUs

A t-shirt in three sizes and four colours is twelve things to stock, not one. Model the product, its variants and the stock separately.

Use three layers: a products row for the thing customers browse, a variants row for each buyable combination (size, colour) with its own unique SKU, and an inventory row per variant. Cart lines, order lines and stock all point at the variant, never at the product. That one rule prevents most catalogue bugs.

Product, variant, stock

The product holds what is shared: name, description, brand. The variant holds what you can put in a cart: SKU, price and the option values that make it different:

CREATE TABLE products (
  id          bigserial PRIMARY KEY,
  slug        text NOT NULL UNIQUE,
  name        text NOT NULL,
  description text NOT NULL DEFAULT '',
  active      boolean NOT NULL DEFAULT true
);

CREATE TABLE variants (
  id          bigserial PRIMARY KEY,
  product_id  bigint NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  sku         text   NOT NULL UNIQUE,
  price_minor bigint NOT NULL CHECK (price_minor >= 0),
  currency    char(3) NOT NULL DEFAULT 'USD',
  options     jsonb  NOT NULL DEFAULT '{}'::jsonb,
  active      boolean NOT NULL DEFAULT true,
  UNIQUE (product_id, options)
);

CREATE TABLE inventory (
  variant_id bigint PRIMARY KEY REFERENCES variants(id) ON DELETE CASCADE,
  on_hand    int NOT NULL DEFAULT 0 CHECK (on_hand >= 0)
);

Prices as minor units are explained in storing prices as integers. Stock lives in its own table because it changes far more often than the catalogue, and because the guarded updates in stopping overselling lock that row and not your product data.

Options: JSONB or tables?

A variant such as {"size": "M", "colour": "blue"} fits well in a jsonb column. The UNIQUE (product_id, options) line stops you creating two "M, blue" variants for the same product. For filtering ("show blue items") add a GIN index:

CREATE INDEX variants_options_gin ON variants USING gin (options jsonb_path_ops);
-- find blue variants
SELECT id, sku FROM variants WHERE options @> '{"colour": "blue"}';

The alternative is normalised tables: option_types, option_values and a join table. It enforces that "size" can only be S, M or L, and it is the better choice if merchants edit options in an admin UI. For a small shop or a prototype, JSONB is quicker, and you can validate the allowed keys in application code. Do not use JSONB for the fields you always filter or sort by on the product page, such as price or brand: those deserve real columns.

SKUs

A SKU is the string your warehouse and your accounting tool use. Make it unique and stable: once an order references it, never reuse it. Generate it from the product and options if you must (TEE-BLU-M), but store it, do not recompute it, because a renamed colour would silently change history. Keep products with no variants out of the model by giving every product at least one variant, even when there is only one size. Then the cart and order code has one path instead of two.

Apply it to your local Flisk database

Start with a project that has the shared Postgres and an API, as set up in running a small shop on one laptop. The shared Postgres container is named after the project, so for a project called my-shop and a stack called shop, the container is my_shop_postgres, the user is my_shop and the database is my_shop_shop. Confirm yours with docker ps, then apply a SQL file for a first try:

docker exec -i my_shop_postgres psql -U my_shop -d my_shop_shop -v ON_ERROR_STOP=1 < schema.sql

For anything you keep, move the same SQL into your migration tool so the migrator creates it on every flisk up; database migrations in local dev shows the setup. Then load a few rows with the approach in seeding a local database.

Pitfalls

  • Pointing orders at the product. The customer bought a size and colour. If the order line points at the product, you cannot say which one to ship.
  • Deleting variants. Old orders reference them. Set active = false instead of deleting.
  • Price on the product only. Larger sizes or special editions often cost more. A price per variant costs nothing extra and saves a migration later.
  • Stock as a column on variants. It works for tiny shops. Once you need reservations or several warehouses, a separate table is much easier to extend.

For a bigger catalogue you will also want realistic rows to test search and pages. Generating realistic shop data shows how.

Questions people ask

Should every product have at least one variant?

Yes. It keeps cart and order code on a single path, because they always reference a variant.

Can I use JSONB for all product attributes?

Use JSONB for optional, varying attributes. Keep fields you filter and sort by, such as price and brand, as normal columns.

Where do I store product images?

Store the file in object storage and keep its URL or key in a product_images table that references the product, and optionally a variant.
