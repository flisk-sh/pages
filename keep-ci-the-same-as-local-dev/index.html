How to keep CI the same as local development

One definition of the stack, used in both places. Pin the versions and write down what legitimately differs.

CI stays close to local development when both start the stack with the same command, the same tool versions and the same committed files, and when every difference is on a short list you can name. If the workflow has its own start-up script that no developer runs, CI is testing something other than what people use.

Why CI and local drift apart

It starts small. A developer fixes a start-up problem with a local flag. CI gets a shell script that sets three variables and a sleep. Six months later, tests pass on laptops and fail in CI, or the other way round, and nobody can say which setup is right. Each drift has the same fix: one definition of the stack, used in both places.

Step 1: one entry command

Decide on the command that starts the stack and use it everywhere. With Flisk it is flisk up locally and flisk up --wait in CI, which runs the stack in the background and exits when it is healthy, so the next step can start. Everything else, such as which services exist, their ports and their dependencies, lives in the service.json files in the repository. The workflow then contains no service list of its own to go stale.

- run: flisk project --yes
- run: flisk up --wait --wait-timeout 600
- run: npm test

If you wrap this in a make ci or an npm script, let developers run the same wrapper. A command only CI runs is a command nobody notices when it breaks.

Step 2: pin the versions

The usual cause of "works on my machine" in CI is a different tool version. Pin what you can:

  • Node. Commit an .nvmrc and point actions/setup-node at it with node-version-file: .nvmrc. Flisk needs Node 22.12 or newer.
  • The Flisk CLI. Install an exact version in CI with npm install -g @flisk-sh/flisk@<version> instead of the latest. Then upgrading is a commit you can review and revert.
  • A floor for everyone. Add "minFliskVersion": "1.4.57" (use your own number) to .flisk/project.json. flisk up and flisk doctor then fail with a clear message on an older CLI, locally and in CI. It is a minimum, not an exact match, so it stops stale installs but does not stop someone being newer.
  • Images and services. Use specific tags for databases and base images, not latest.

Step 3: check that generated files match the source

Flisk generates files from your service.json and package.json files. If someone changes a source and forgets to regenerate, or edits a generated file by hand, local and CI can disagree. Run flisk config verify as a fast job before the stack starts. It exits 1 on drift. This has its own walkthrough in checking config drift in CI, so here the point is only to make it the first job. On a fresh clone, run flisk project --yes first, because the .env and generated output are not committed.

Step 4: write down what legitimately differs

Some differences are fine, as long as you know them:

AreaLocalCI
SecretsGenerated .envGenerated .env, plus repository secrets only for real third parties
DataPersistent volumesFresh every run
HardwareYour laptopA small shared runner, so give waits more time
CacheWarmCold unless you configure it

Keep this table in your contributing guide. When a CI-only failure appears, you check the table first. A difference that is not on it is probably a bug.

Where Flisk fits, and where it does not

Flisk is a local development tool. It does not emit Kubernetes manifests and does not replace the way you deploy. Keeping CI close to local means CI is close to the local loop, not that it equals production. If you also want a Compose file that runs without Flisk, for CI or a colleague, see exporting a standalone Compose file.

Pitfalls

  • CI-only environment variables. A variable set only in the workflow makes a test pass there and fail on a laptop. Prefer values in committed config or the generated .env.
  • Skipped tests in CI. A test tagged to run only locally, or only in CI, makes the two diverge. Avoid environment checks in tests.
  • Different start order. A sleep in the workflow hides a missing dependsOn that a developer will hit locally.

When not to chase parity

Do not push CI to match a developer's laptop in everything. CI should match the shared definition of the stack. Personal settings, editor tools and local overrides are not part of it. Where production differs from both, test that in a staging environment, not in CI.

Questions people ask

What does minFliskVersion do?

It is a minimum version in .flisk/project.json. flisk up and flisk doctor fail with a clear message when the installed CLI is older. It does not require an exact match.

How do I install a specific Flisk version in CI?

Run npm install -g @flisk-sh/flisk@<version> with the exact version you want. flisk upgrade takes no version argument.

Does matching local mean matching production?

No. It makes CI match the local loop. Production differences belong to your deploy pipeline and a staging environment.
