How to check generated config drift in CI

A drift check takes seconds, needs no running containers, and stops the classic bug where a source file changed and the generated one did not.

To check config drift in CI, install the tool, regenerate the project output on the runner, run the tool's verify command, and let a non-zero exit code fail the job. With Flisk that is flisk project --yes, then flisk doctor --no-ping, then flisk config verify. The job needs no running containers and finishes quickly.

What drift is and why it bites

Drift is a mismatch between a source file and something generated from it. In a Flisk project the sources are each service.json and .flisk/project.json. The generated files (the Tiltfile, Compose fragments, routing, .autogenerated/ folders) live in .flisk/.flisk-out/ and next to the services, and they are git-ignored. Someone edits a source, or edits a generated file by hand, and the two no longer agree. Locally this shows up as a service that ignores your change. The same pattern exists in any generator-based setup: a lockfile that does not match the manifest, a client generated from an old schema.

A CI check catches it on the pull request instead of on a colleague's laptop two days later. For the local symptom and its fix, see generated config out of date.

What the commands check

  • flisk config verify compares the generated files with what the sources would produce, and also validates dependsOn. It exits with code 1 on either problem. A typical drift line reads Out of sync: .flisk/.flisk-out/Tiltfile (run 'flisk config regenerate'). With --json it prints an object with valid, errors and diffs, which is easy to parse.
  • flisk doctor --no-ping checks the environment and the services: unique appName, dependsOn names that exist, a supported schemaVersion, the toolchain on PATH, and minFliskVersion. --no-ping skips network checks, which suits a runner. Add --strict if you want warnings to fail the job.
  • flisk project --yes is idempotent. It writes the git-ignored .env and the generated output.

Keep the two diagnostics separate in your head. doctor asks whether this machine and these services are healthy. config verify asks whether the generated project matches its sources.

A workflow you can paste

This GitHub Actions job runs both checks. It is based on the project's own CI docs.

name: flisk-verify
on: [pull_request]
env:
  FLISK_VERSION: 1.4.61
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm install --global @flisk-sh/flisk@$FLISK_VERSION
      - run: flisk project --yes
      - run: flisk doctor --no-ping
      - run: flisk config verify

Three details matter. First, a fresh clone has neither the git-ignored .env nor .flisk/.flisk-out/, so flisk project --yes must run before the checks. Second, the job pins the Flisk version through an environment variable, so a new release cannot change the result of an old pull request. Pick the version your team uses locally, and bump it in one place. Third, Tilt is only needed when the project uses Docker containers; the docs add an install step for it in that case, and a project made of local processes can skip it.

The pitfalls

  • The check passes because nothing was generated. If you skip flisk project --yes, you verify an empty folder. Keep the order.
  • Hand edits get discarded. flisk config regenerate overwrites generated files, including any you edited. A user-owned file such as an existing .tiltignore is reported as not generated by Flisk and left alone. Put your changes in the sources.
  • Version mismatch. You can also set minFliskVersion (a floor, with a hint to run flisk upgrade) or pinnedFliskVersion (an exact match) in .flisk/project.json. Both use MAJOR.MINOR.PATCH. The pin turns a quiet version difference into a clear message with the install command.
  • Ignoring drift at the wrong time. flisk up --ignore-drift exists for a local emergency. Do not put it in CI.

What this does not cover

A verify job proves the files are consistent, not that the stack boots. The project docs describe a second, heavier job that runs flisk up and waits for health, but their authors did not run it on GitHub, so treat it as an idea to test, not a recipe. For running a full stack in Actions with a database, read run the stack in GitHub Actions.

When the check is in place, make it a required status check on your main branch. Then read service.json as a team contract to decide what reviewers should look for in those files.

Questions people ask

Does config verify need Docker?

No. It compares files and validates dependsOn, so it runs on a plain runner. Docker and Tilt matter only if you also boot the stack.

Why does the job fail on a fresh clone?

The .env file and .flisk/.flisk-out/ are git-ignored and absent after checkout. Run flisk project --yes before flisk config verify.

How do I fix a drift failure?

Run flisk config regenerate locally, review the diff in your sources, and commit the source change. Generated files themselves are not committed.

Can I parse the result in a script?

Yes. flisk config verify --json prints an object with valid, errors and diffs, and the exit code is 1 when something is wrong.
