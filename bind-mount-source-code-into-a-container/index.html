How to bind mount source code into a container for development

The image has your code baked in, so every edit needs a rebuild. A bind mount replaces the baked-in copy with your live folder.

A bind mount makes a folder on your computer appear at a path inside the container, so the container sees your edits immediately. Mount only the source folders you change, leave dependency folders such as node_modules inside the image, and use a watcher in the container (nodemon, Vite, air, uvicorn --reload) to restart or reload when files change.

The basic mount

docker run --rm -p 3000:3000 \
  -v "$PWD/src:/app/src" \
  myapp:dev

The same in Compose:

services:
  web:
    build:
      context: .
      target: dev
    ports:
      - "3000:3000"
    volumes:
      - ./src:/app/src

Whatever the image had at /app/src is hidden while the mount is active, and your host folder shows instead. Edit a file in your editor and the container reads the new version at once. Nothing is rebuilt, which is the whole point.

The node_modules trap

The most common mistake is mounting the whole project: -v "$PWD:/app". That hides the node_modules the image installed under /app and replaces it with whatever is on your host. If your host folder has none, the app crashes with "cannot find module". If it has modules built for macOS, native packages fail on Linux.

Prefer mounting only source folders, as above. If you do need to mount the whole folder, mask the dependency folder with an anonymous volume so the image's copy stays visible:

    volumes:
      - ./:/app
      - /app/node_modules

Python virtual environments and Go module caches have the same problem. Keep them in the image, or in a named volume, never on the host mount.

Make the running app notice changes

A bind mount only changes the files. The process still has to reload. Use the dev command of your framework in the dev stage (vite, next dev, nodemon, uvicorn --reload, air for Go). Two common reasons it does not react:

  • File events do not cross the mount. On some setups, especially macOS and Windows with older file sharing, change events are missing. Switch the watcher to polling (for example CHOKIDAR_USEPOLLING=true for Chokidar based tools).
  • The editor saves by renaming. Some editors write a temporary file and rename it, which a few watchers miss. Check the tool's documentation for a flag.

More causes and fixes are in hot reload not working in Docker or locally.

Bind mount or named volume

Use a bind mount for files you edit (source, config) and a named volume for data the container owns (a database directory, a cache). A named volume is managed by Docker, is not tied to a host path and is often faster on macOS and Windows. Add :ro to a bind mount (./config:/etc/app:ro) when the container should only read it.

In a Flisk stack

A bring-your-own resource takes a volumes list in service.json. A source that starts with ./ or ../ is a bind mount relative to the service folder, and a plain name is a named volume:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile.dev",
  "volumes": [
    { "source": "./src", "target": "/app/src" },
    { "source": "./config", "target": "/app/config", "readOnly": true },
    { "source": "web-cache", "target": "/app/.cache" }
  ]
}

A bind path must stay inside the project; flisk up and flisk doctor refuse one that climbs above the project root. A named volume is kept by flisk down. Be clear about what this does not give you: Flisk does not add a live reload to a bring-your-own container. The mount shows your edits inside it, and the process in your Dockerfile.dev must restart itself, for example with nodemon. For services Flisk generates for you, hot reload is built in and you do not write mounts.

Pitfalls

  • Mount paths must be absolute inside the container. target is a full path such as /app/src.
  • Files created by the container are owned by its user. See running as a non-root user for matching ids on Linux.
  • Slow file access on macOS can make a large mounted tree sluggish. Mount fewer folders and keep dependencies out of the mount.
  • Do not mount over the folder holding your build output unless you want your host's copy to win.

Next step

If edits still do not appear, check each link in the chain: mount path, watcher, restart. And if you would rather not keep a dev Dockerfile at all, running services without Docker removes the mount layer entirely.

Questions people ask

Why does my container crash with cannot find module after I mount my project?

Mounting the whole project hides the node_modules installed in the image. Mount only the source folders, or add an anonymous volume at /app/node_modules to keep the image's copy.

Do bind mounts reload my app automatically?

No. They only make your edits visible inside the container. A watcher or dev server in the container, such as nodemon or Vite, has to restart or reload the process.

How do I bind mount a folder in Flisk?

Add an entry to the volumes list in service.json of a bring-your-own resource, with a source starting with ./ or ../ (relative to the service folder) and an absolute target path.
