How to run model training as a one-shot job in a local stack

Training is not a server. It runs, writes a result and stops. Treating it as a job keeps it from restarting forever and lets the API wait for the model.

A training run is a one-shot job: a container that does its work and exits with code 0. Give it a restart policy of no, otherwise Docker starts it again every time it finishes. Make the model API depend on the job, so the API starts only after training succeeded and the model exists. If the job fails, nothing downstream starts, and the failure is visible instead of hidden.

Why the restart policy matters

Containers are designed for servers. With a restart policy such as unless-stopped, a container that exits cleanly is started again, so a training script would retrain in a loop and fill your tracking server with runs. The fix is a policy of no. In plain Compose, that is restart: "no" on the service, and depends_on with condition: service_completed_successfully on whatever needs the result.

The job itself

Keep the training code in its own folder with a Dockerfile:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY train.py .
CMD ["python", "train.py"]

Pin mlflow to the tracking server's version in requirements.txt, and pin scikit-learn. The script logs to the server named in MLFLOW_TRACKING_URI and registers the model under a name with an alias, so the API asks for "the champion" and never for a file path:

import mlflow
import mlflow.sklearn
from mlflow import MlflowClient
from sklearn.datasets import load_iris
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import train_test_split

X, y = load_iris(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, random_state=0)

mlflow.set_experiment("iris")
with mlflow.start_run():
    model = LogisticRegression(max_iter=200).fit(X_tr, y_tr)
    mlflow.log_param("max_iter", 200)
    mlflow.log_metric("accuracy", model.score(X_te, y_te))
    mlflow.sklearn.log_model(model, name="model", registered_model_name="iris")

client = MlflowClient()
newest = max(int(v.version) for v in client.search_model_versions("name='iris'"))
client.set_registered_model_alias("iris", "champion", str(newest))

The API then loads mlflow.sklearn.load_model("models:/iris@champion") at startup, which needs the mlflow package in the API image too.

The Flisk way

You need a tracking server and the job. Create both in one stack:

flisk resource tracking --type database --framework mlflow --stack ml --yes
flisk resource train --type bring-your-own --stack ml --dockerfile ./Dockerfile --restart no --yes

Put the Dockerfile and train.py in services/ml/train. The CLI writes "restart": "no" into service.json. Edit that file so the job waits for the tracking server and has no public route:

{
  "appName": "train",
  "appType": "bring-your-own",
  "stack": "ml",
  "port": 4002,
  "dockerfile": "./Dockerfile",
  "restart": "no",
  "exposeViaProxy": false,
  "dependsOn": ["tracking"]
}

Because tracking declares MLFLOW_TRACKING_URI in its provides, the job gets the variable and train.py needs no address. Now make the model API wait for the job, and for the tracking server it will read from:

"dependsOn": ["tracking", "train"]

In Flisk, a service that lists a restart: "no" job in dependsOn starts only after the job exited with 0. If the job fails, the services after it are not started. Check it:

flisk config verify
flisk up ml
flisk status
flisk logs --service train --tail 100

In flisk status the job should show as exited, not running. The run is in the MLflow UI at http://127.0.0.1:5000. This is the same pattern Flisk uses for database migrations, see running migrations with a migrator.

Iterate without a rebuild

While you change the model, a container rebuild per experiment is slow. Run the script on your host against the published server and use the job for the clean, repeatable run:

export MLFLOW_TRACKING_URI=http://127.0.0.1:5000
python train.py

To rerun the containerised job from scratch, stop the stack with flisk down and start it again. The tracking data is on a volume, so earlier runs stay.

Pitfalls

  • A job that never exits. If the script waits on something, dependents wait forever. Add timeouts and exit non-zero on failure.
  • Data on the container filesystem. Anything the job writes outside a volume or the tracking server is gone when the container is removed.
  • Retrain on every start. This setup retrains each time you bring the stack up. For a long training, skip it when a model with the alias already exists, or keep training out of the default stack and start it on demand with flisk up on a stack that has it.
  • Reproducibility. Set random seeds and pin library versions, or two runs of the same code give different metrics.

Questions people ask

Why does my training container keep restarting?

The default restart policy restarts a container that exits cleanly. Set the restart policy to no for a one-shot job.

How do I make the API wait for training to finish?

Make the API depend on the job with a completed-successfully condition. In Flisk, listing a restart-no job in dependsOn makes the service start only after the job exits with 0.

Should training run in the same container as the API?

Usually not. Training needs different dependencies and runs to completion, while the API runs continuously. Separate containers keep both simple.
