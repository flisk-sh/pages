Build your own MCP server

How to protect a local MCP HTTP server with a bearer token

A port on localhost is open to every program and browser tab on your machine. Three small checks close most of the gap.

Bind the server to 127.0.0.1, reject requests whose Origin header is not one you expect, and require an Authorization: Bearer token that you compare in constant time. Generate the token once, keep it in an environment variable, and give the same value to your client through its header setting. That is enough for a local or personal server. A server that other people use needs proper OAuth, which this article does not try to replace.

Why a localhost server needs any protection

A port on localhost is open to every program you run. It is also reachable from web pages open in your browser, because a page can send requests to http://localhost:PORT, and with a DNS rebinding trick can make them look same-origin. An MCP server often can read files, query a database or call internal APIs, so a stranger's page that reaches it can do the same. The MCP specification for Streamable HTTP tells servers to validate the Origin header on every connection to stop that, to bind to localhost rather than all interfaces when running locally, and to implement authentication.

A stdio server avoids this because it has no port. That is a good reason to prefer it for a private tool, as the transport comparison explains.

Three layers

  1. Bind narrowly. Listen on 127.0.0.1, not 0.0.0.0. Inside a container you do have to bind to all interfaces, so then publish the port only to localhost, or put the server behind a proxy.
  2. Check Origin. Native clients such as coding assistants do not send an Origin header. Browsers always do. So allow a request with no Origin, and reject one whose Origin is not on your list.
  3. Require a token. Compare the bearer token before you parse the body.

A minimal check in Node

import { timingSafeEqual } from 'node:crypto';
import type { IncomingMessage, ServerResponse } from 'node:http';

const TOKEN = process.env.MCP_TOKEN;
if (!TOKEN) throw new Error('MCP_TOKEN is not set');
const ALLOWED_ORIGINS = new Set(['http://localhost:6274']); // the Inspector, if you use it

function guard(req: IncomingMessage, res: ServerResponse): boolean {
  const origin = req.headers.origin;
  if (origin && !ALLOWED_ORIGINS.has(origin)) {
    res.statusCode = 403;
    res.end('forbidden origin');
    return false;
  }
  const header = String(req.headers.authorization ?? '');
  const given = Buffer.from(header.startsWith('Bearer ') ? header.slice(7) : '');
  const want = Buffer.from(TOKEN!);
  if (given.length !== want.length || !timingSafeEqual(given, want)) {
    res.statusCode = 401;
    res.setHeader('www-authenticate', 'Bearer');
    res.end('unauthorized');
    return false;
  }
  return true;
}

Call guard(req, res) at the top of the /mcp branch and return when it is false. Leave /health open if a supervisor needs it, and make sure it reveals nothing. Refuse to start without a token, as the first lines do, so a missing variable never turns into an open server. The length check comes first because timingSafeEqual throws on buffers of different sizes.

In Python, the SDK has token-verification hooks for FastMCP, and the details vary by version, so read its authorization documentation. A plain ASGI middleware that checks the same two headers also works.

Make and keep the token

Generate a long random value, not a word you chose:

openssl rand -hex 32

Keep it out of git. In a Flisk project that runs local processes, secrets.generate in service.json makes one for you. On flisk up it appends any missing name to the project .env once, with random bytes, and leaves existing values alone. The service reads it through env:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "notes-mcp",
  "appType": "mcp",
  "command": "node server.js",
  "port": 4000,
  "secrets": { "generate": { "MCP_TOKEN": "hex:32" } },
  "env": { "MCP_TOKEN": "${MCP_TOKEN}" }
}

The Flisk scaffold from flisk resource --type mcp has no authentication of its own, and the Flisk docs say it is meant for *.localhost. If you add the check above to its src/index.ts, remember that flisk mcp check sends no Authorization header, so it will report failures against a guarded endpoint. Check the protocol on a dev instance without the token, and test the guard with curl:

curl -i -X POST http://localhost:4000/mcp -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
# expect 401

curl -i -X POST http://localhost:4000/mcp -H "authorization: Bearer $MCP_TOKEN" \
  -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
# expect 200

For keeping secrets out of committed config in general, see env var names, not values.

Give the token to the client

Most clients let you set a header for an HTTP server. In Claude Code, for example, the claude mcp add command accepts --transport http and a --header option. Use your client's documentation for the exact syntax, and avoid pasting the token into a file you commit. Testing an MCP server with Claude Code covers the connection steps.

Pitfalls and limits

  • A shared static token is weak. Anyone with it has full access, and you cannot revoke one person. For a server used by several people, implement the OAuth flow described in the MCP authorization specification, or put an authenticating gateway in front.
  • Plain http over a network. A bearer token sent over http can be read by anyone on the path. Use https for anything that leaves your machine.
  • Logging. Do not log request headers. A token in a log file is a leaked token.
  • Tool-level limits still matter. Authentication says who may call. Validate inputs and limit what each tool can touch, as in validating tool arguments.

Authentication is the last piece of a server others can rely on. Go back to the testing guide and add a test that an unauthenticated call gets a 401.

Questions people ask

Does an MCP server on localhost need authentication?

Yes, if it listens on a port. Other programs and browser pages can reach localhost. The specification tells servers to validate Origin, bind to localhost and implement authentication.

Is a static bearer token enough for an MCP server?

For a personal or local server it is a reasonable minimum. For a server used by several people, use the OAuth-based authorization in the MCP specification or an authenticating gateway.
