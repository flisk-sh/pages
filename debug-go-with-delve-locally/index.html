How to debug a Go service with Delve while it runs locally

A print statement gets you far, but a breakpoint in a handler is quicker once the bug depends on state. Delve is the Go debugger, and it needs a binary that still has its debug data.

Run your service under Delve in headless mode, then connect your editor to its port. That gives you breakpoints and variable inspection in a program that is running with the real configuration. The one thing to get right is the build: Delve needs the debug information and, ideally, no inlining or optimisation, so a binary built with -ldflags="-s -w" will not work.

Install Delve and start the service under it

go install github.com/go-delve/delve/cmd/dlv@latest
cd services/app/orders
dlv debug --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient

dlv debug compiles the package in the current folder with optimisations and inlining switched off, then starts it and waits for a client. --accept-multiclient lets you disconnect and reconnect without killing the program. Without the --continue flag the program does not start running until a client connects and continues it. Add --continue when you want the service to start at once and attach later.

Bind to 127.0.0.1. A headless Delve server lets any client run code in your process, so it should not listen on a network interface.

Connect from VS Code or GoLand

In VS Code with the Go extension, add a remote attach configuration to .vscode/launch.json:

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Attach to dlv",
      "type": "go",
      "request": "attach",
      "mode": "remote",
      "host": "127.0.0.1",
      "port": 2345
    }
  ]
}

GoLand has the same thing under Run, Edit Configurations, Go Remote. Set a breakpoint in a handler, send a request with curl, and the editor stops on the line.

If you only need to debug a test, skip the server: dlv test ./..., or use the Debug test link that your editor shows over a test function.

Attach to a binary you already built

To debug a binary that is already running, build it with optimisation off and attach by process id:

go build -gcflags="all=-N -l" -o tmp/app .
./tmp/app &
dlv attach $(pgrep -f tmp/app) --headless --listen=127.0.0.1:2345 --api-version=2

On Linux, attaching to a process you did not start may be blocked by the ptrace_scope setting. On macOS, the first use can ask for permission under Developer Tools. If a debugger session ends right after it connects, check those two before anything else.

Run it under Flisk

With a Go service that has a command, Flisk starts it as a local process, so the command can be Delve:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "stack": "app",
  "language": "go",
  "command": "dlv debug --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient --continue",
  "port": 4003,
  "healthCheckPath": "/health"
}

Create the service first with flisk resource orders --language go --local --stack app --yes, which writes go run . as the command, and replace it. Flisk starts the command from the service directory, passes PORT, waits for the health path, and restarts the process if it exits. Because dlv debug compiles before it starts, the first start takes longer than go run, and Flisk waits up to 60 seconds for a service to become ready, so run go build ./... once beforehand if the cold build is slow. Use flisk logs --service orders to see the build errors and Delve's output.

The Flisk Docker route has a live reload watcher for Go. According to the Flisk docs it builds with -ldflags='-s -w', and Delve cannot attach to that binary. To debug in a container, build the development target yourself without the flag.

Debugging inside a container

The mechanics are the same, with three additions. Build the image with a debuggable binary (-gcflags="all=-N -l", no -s -w). Run dlv exec as the container command and publish port 2345 to 127.0.0.1 only. And if Delve reports "operation not permitted", add the SYS_PTRACE capability to the container, since some runtimes block ptrace by default. In a Flisk bring-your-own resource the container.capAdd field in service.json sets that capability. Keep this image for debugging only: it is large, and an open debug port is a hole.

Pitfalls

  • Breakpoints that never hit. The binary was built without -N -l, or the source path differs between the build and the editor. Use dlv debug locally so both match.
  • Timeouts in a paused handler. While you sit on a breakpoint the HTTP client, the health check and any upstream timeout keep running. Flisk may report the service as not ready while it is paused.
  • Port conflicts. Two debug sessions on 2345 collide. Give each service its own debug port.

Questions people ask

Why can't Delve attach to my Go binary?

Usually the binary was built with -ldflags="-s -w", which strips debug data, or with optimisation on. Build with -gcflags="all=-N -l" and no -s -w.

What does dlv --headless do?

It starts a debug server with no terminal interface and waits for a client, such as VS Code or GoLand, to connect on the port you give it.

Can I debug the Go service that Flisk runs in Docker?

The built-in live reload watcher builds a stripped binary that Delve cannot attach to. Build the development target without the flag yourself, or debug the service as a local process.
