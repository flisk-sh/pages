Env vars and secrets in local dev

How to share dev secrets with your team without pasting in Slack

Chat messages are searchable, forwarded and kept for years. Pick a channel built for secrets, and give people as few of them as you can.

Share development secrets through a tool that controls access and keeps an audit trail: a team password vault, an encrypted file in the repository, or a secrets manager that injects values at run time. A pasted .env in chat works once and then lives forever in search history, so use it only for non-secret settings. Better still, give each developer their own credentials, or generate local ones, so there is less to share.

First, share less

Most of what ends up in a shared .env does not need to be shared:

  • Local secrets such as a JWT signing key or a session secret should be generated per machine. See generating random local secrets.
  • Database passwords for a container on your laptop are not secrets worth guarding.
  • Third-party keys should be sandbox keys, ideally one per developer, so that a leak reveals one person's test account and revoking it affects no one else.

What remains is a short list of values that really are shared, such as a team sandbox key for a paid API or a read-only token. That list is what you need a real channel for.

Options, compared

ApproachGood forCost
Shared vault in a team password manager (1Password, Bitwarden)A handful of secrets, small team, access control and an audit logManual copy into .env unless you use the vendor's command line tool
Encrypted file in git (for example SOPS with age keys)Secrets that change with the code, a team comfortable with gitKey management: each person needs a key, and offboarding means re-encrypting
Secrets manager (Infisical, Doppler, a cloud provider's store)Many services, rotation, per-environment values, larger teamsAnother service to run or pay for, and a login in the setup path

For a team of two to ten, a vault plus per-developer sandbox keys is usually enough. Do not adopt a secrets manager just because the list got long. First check whether the list can get shorter.

Whichever you choose, apply the same habits: give access per person, remove it when someone leaves, rotate a shared secret when a person with access leaves, and never reuse a production secret for development.

Make onboarding fail clearly

The worst experience is a new developer running the app and getting a vague error three layers deep. With Flisk the names a service needs are declared in its service.json, and a missing required one stops flisk up before anything starts:

{
  "secrets": {
    "required": ["STRIPE_KEY"],
    "optional": ["SENTRY_DSN"]
  }
}

If STRIPE_KEY has no value in the env file of the run or in the environment, the check names the file and the secret and prints a fix: add NAME=value to .env (it is gitignored), export it in the environment, or move it to optional. A required name that is also listed under secrets.generate counts as satisfied, since Flisk writes it.

That gives you a simple onboarding step: clone, copy the values from the vault into .env, run flisk up. The error message is the checklist. The README should say where the vault is, as in onboarding a developer on day one.

Because "exported in the environment" also satisfies the check, a vault's command line tool that injects variables into a command can feed the stack. 1Password's op run, for instance, runs a command with secrets resolved from references. I did not test that combination end to end, so try it on one secret before you depend on it.

Flisk can also leave secrets to Infisical. With FLISK_SECRET_PROVIDER=infisical set in the environment, nothing is injected from .env and the required-secret check is skipped, because Infisical supplies the names. Flisk's own security notes say its Infisical path has not been audited, so review that setup yourself before relying on it for anything sensitive.

Pitfalls

  • Screenshots and ticket comments leak secrets just like chat. Share variable names when asking for help.
  • A secret in a pull request description is in the repository host's database even after you edit it.
  • Stale copies. When a shared secret rotates, everyone's .env is wrong. Announce it in one place and make the vault the source of truth.
  • Skipping the offboarding step. Removing someone from the vault does not remove the value from their laptop. Rotate what they could read.

Questions people ask

Is it okay to send a .env file over Slack?

Only for non-secret settings. Chat is searchable and long-lived, so use a password vault or secrets manager for real secrets and give each developer their own sandbox keys where you can.

How do I tell a new developer which secrets they need?

Declare the names in service.json under secrets. With Flisk, flisk up stops before starting anything when a required name has no value and says which service and secret is missing.

Does Flisk work with Infisical?

Setting FLISK_SECRET_PROVIDER=infisical leaves secrets to Infisical and injects nothing from .env. Flisk's security documentation says that provider path was not audited, so test it before relying on it.
