Run Python and Node services in one repo

Two languages mean two toolchains, two dependency managers and two ways to start. Here is how to keep one command anyway.

To run a Python service and a Node service from one repository, give each its own folder, dependency manager and start command, then use one tool to start them in the right order. A Procfile, a Makefile or Docker Compose all work. Flisk does it with one service.json per service, where the Python one runs uvicorn and the Node one runs npm run dev, started by a single flisk up.

What goes wrong in a polyglot repo

Each language brings its own tools. Python wants a virtual environment and a lock file. Node wants node_modules and a specific major version. If you run both from the repo root, you tend to hit the same problems: the wrong Python or Node version on one machine, a service started before the one it calls, and logs from two processes mixed in two terminals. The fix is not to unify the toolchains. It is to keep them separate and put one start command above them.

Common ways to do it without Flisk

  • A Procfile with a runner (foreman, overmind or honcho): one line per process, prefixed logs, no ordering.
  • A Makefile target that starts both with &: short, but stopping it cleanly is on you.
  • Docker Compose with one image per language: strong isolation and a clear depends_on, at the cost of Dockerfiles and a slower edit loop.
  • A version manager such as mise or asdf with a .tool-versions file, so everyone gets the same Python and Node.

Any of these is reasonable. Pick Compose when you need containers anyway, and a Procfile when you want the least machinery.

The Flisk way: one manifest per service

Flisk runs a service as a plain process when its manifest has a command. There is no Docker, no Tilt and no generated file for such services. Put each service in its own folder with its own service.json, for example services/app/api/service.json and services/app/web/service.json.

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "toolchain": "python@3.12",
  "command": "uvicorn main:app --reload --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "toolchain": "node@22",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4000" }
}

The manifests passed flisk config verify when this was tried. Run the stack:

npm install -g @flisk-sh/flisk
flisk up

What Flisk does, per the manifest:

  • It runs each command from the service's own directory, so Python commands find main.py and Node commands find package.json.
  • It passes PORT to each process, so your code should read the port from the environment.
  • It starts services in dependsOn order and waits up to 60 seconds for each to answer its healthCheckPath before it starts the next.
  • It prefixes every log line with the service name and writes each service's log to .flisk/native/logs/<service>.log.
  • It restarts a crashed process with a growing delay of 1, 2, 4 and 8 seconds.

The optional toolchain says which runtime the command needs. flisk doctor and flisk up compare it with the program on your PATH and stop with TOOLCHAIN_MISMATCH if the version differs. Flisk installs nothing, so use pyenv, nvm, mise or similar to switch. Without toolchain, a .python-version or .nvmrc in the service folder is only a hint that produces a warning.

Env vars and daily commands

The env block supports ${VAR} and ${VAR:-default}, so a service can read a value from your shell and fall back to a default. Useful commands:

flisk up --only api
flisk up --dry-run
flisk logs --service api --tail 50
flisk doctor
flisk down

--only starts one service and what it needs, --dry-run prints the plan, and flisk logs prints the last lines of one service. Edit Python code and uvicorn --reload restarts the API. Edit Node code and your dev server (Vite, node --watch, or whatever npm run dev runs) reloads. The live reload belongs to the tools, not to Flisk.

Pitfalls and limits

  • A project is either local processes or containers. You cannot mix command services with services built from a Dockerfile. Flisk stops with MIXED_RUNTIME. Ready-made images such as Postgres are the exception: they can sit next to command services, and they need Docker running.
  • Dependencies are yours to install. Run pip install and npm install before the first start. Flisk does not create a virtualenv.
  • Origins differ in native mode. The frontend runs on http://localhost:3000. If the browser calls the Python API directly, add that origin to the API's CORS settings or use a dev proxy.
  • Windows and shell syntax. A command is run by a shell. Keep it plain, and test it on every platform your team uses.

Questions people ask

Can Flisk run Python and Node services together?

Yes. Give each service its own service.json with a command, for example uvicorn for Python and npm run dev for Node. flisk up starts both as local processes in dependsOn order, with no Docker.

Does Flisk install Python or Node for me?

No. The toolchain field only declares the version a command needs, and flisk up stops with TOOLCHAIN_MISMATCH if the program on PATH differs. Use a version manager to switch versions.

Can I mix local processes and Docker containers in one project?

Not for services built from a Dockerfile. A project cannot mix command services with Dockerfile-built services. Ready-made image services such as Postgres can run next to command services if Docker is running.
