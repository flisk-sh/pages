Flaky tests in CI: find them, quarantine them, fix them

A flaky test trains your team to ignore red builds. Here is how to detect flakes, move them out of the blocking path, and fix the usual causes.

Find flaky tests by re-running failures and recording which ones pass on retry, move them to a non-blocking quarantine job with an owner and a deadline, then fix the cause. Do not just add retries to everything.

Detect them with data

You cannot fix what you cannot name. Run the suite several times on the same commit and list tests whose result differs. With pytest you can repeat a test to expose a flake:

pip install pytest-repeat
pytest tests/test_orders.py --count 30 -x

Many frameworks have a similar option or a retry plugin. In CI, log every test that failed and then passed on retry. That list is your backlog.

Quarantine, do not ignore

Move the flaky test out of the required job but keep running it so it stays visible:

# pytest
@pytest.mark.flaky_quarantine
def test_checkout_timeout(): ...

# required job
pytest -m "not flaky_quarantine"

# non-blocking job
pytest -m flaky_quarantine

Give every quarantined test an owner and a date. A quarantine without a deadline is a graveyard. See required checks for making only the right job blocking.

The usual causes

  • Time. Tests that depend on the clock, time zones or sleep. Inject a fake clock.
  • Order and shared state. One test leaves data behind. Isolate databases per test or per worker.
  • Races. Waiting a fixed time for async work. Wait for a condition with a timeout instead.
  • Network. Real calls to third parties. Stub them or use a recorded fixture.
  • Ports and files. Two tests bind the same port. Use ephemeral ports and temporary directories.

Retries: a short, honest rule

One retry for end-to-end tests that touch a browser is a reasonable trade-off. Retries on unit tests hide real bugs. Whenever a test passes on retry, report it; a silent retry is a flake you will never see. Set a ratchet on the count of retried tests so the number only goes down (see ratchet checks).

AI-written tests and flakiness

A flake is a bug in the test or in the code under test, and sometimes the second is the real finding: a race condition in production code shows up first as a test that fails one run in fifty. Check before you blame the test. Tests produced by a coding agent are often flaky, because they pass once on the author's machine and assume timing. Ask for deterministic tests explicitly, run new tests several times before merging, and read the waiting and cleanup code. For working with agents in general see coding agents in practice.

Questions people ask

Is deleting a flaky test acceptable?

Yes, if it tests nothing important or duplicates other coverage. A deleted test is better than one everyone ignores, but write down why.

How many reruns should CI do?

At most one automatic retry for slow end-to-end tests, none for unit tests, and always report that a retry happened.
