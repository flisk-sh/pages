Docker Compose for local development

Export a standalone docker-compose.yml from service.json

You can leave Flisk with a Compose file that runs on plain Docker. This article shows what the export includes and what you must verify.

Run flisk export compose in your project. It writes .autogenerated/docker-compose.yml, a plain Compose file built from your bring-your-own service.json files. Start it with docker compose --env-file .env -f .autogenerated/docker-compose.yml up -d. It runs without Flisk, and it never starts a container or calls any API while it generates the file.

Why you would want a plain Compose file

A tool you cannot leave is a risk. A standalone Compose file lets a teammate run the stack with Docker only, lets CI start services without installing Flisk, and gives you something to copy to a server. It is also a way to check what a manifest means in Compose terms.

It is a generated file, not a source file. Treat it like build output: commit it if you want others to run it, but change service.json and regenerate instead of editing it by hand.

Run the export

The export is a separate package, flisk-export, pinned by the CLI (version 0.10.0 at the time of writing) and run through npx, so you need Node and npx. It is opt-in and writes files only.

flisk export compose
flisk export compose ./my-project --out ./deploy
flisk export compose --force
flisk export compose --check
  • The directory argument defaults to the current project.
  • --out <dir> chooses where the file goes.
  • --force overwrites an existing file.
  • --check exits with code 1 when the file on disk is out of date. Put it in CI to catch a service.json change that nobody exported.

Then run it from the project root:

docker compose --env-file .env -f .autogenerated/docker-compose.yml up -d

What gets exported

Only bring-your-own services are exported: the ones with an image or a dockerfile. Services built from Flisk's own templates, and services that run as local processes with a command, are not part of the file. If your project is mostly generated services, this export is not the right tool.

These service.json fields are carried over: image or dockerfile, env, secrets.required, envFile, profiles, models, volumes, extraPorts, dependsOn, healthCheck, sidecarOf and container.

The file has no external networks, no FLISK_* variables and no generated secrets. Names such as ${VAR} and everything in secrets.required are written as variable references, never values, so Compose reads them from your .env at start. You must supply those values yourself.

Details that keep your data and order

  • Volume names are kept. A volume with a name keeps that exact Docker name, and the Compose project name comes from the stack. For projects made by flisk import the original Compose project name is used, so the existing data is found.
  • Ordering is translated. A dependsOn becomes service_healthy when the service it waits for has a healthcheck written. If only healthCheckPath is set, it becomes service_started. A job with restart: "no" becomes service_completed_successfully.
  • Restart. A service with no restart setting gets none in the output.

Ordering rules are the same ones described in Compose depends_on and healthchecks.

Check the result before you rely on it

Read the file. Flisk's own guide on leaving the tool notes that the export was not run as part of that guide, so look at the output yourself and run docker compose -f .autogenerated/docker-compose.yml config to let Compose validate it. Things to look at:

  • Every variable you expect is present in .env.
  • Published ports are what you want. In a Flisk project, extraPorts bind to 127.0.0.1 unless you set bind: "0.0.0.0", so confirm the exported file keeps the exposure you intend.
  • Services you rely on are not missing because they were not bring-your-own.

Two related commands exist. flisk export render writes render.yaml and flisk export wrangler writes wrangler.toml, both files only, with variable names and never values. flisk eject is different: it writes an EJECTED.md note and does not produce a Compose file. Kubernetes manifests are not something Flisk exports.

When not to use it

Do not export if you only want to stop using Flisk for a project made of generated services. The file will not contain them. Rebuild those as ordinary Dockerfile services first. Do not treat the output as a production definition either: it is a local-style Compose file with your local env names, with no secrets management and no scaling.

To put the file on a server, follow deploying a standalone Compose file to a VPS. To go the other way, read importing a docker-compose.yml.

Questions people ask

Does flisk export compose start any containers?

No. It writes files only. It never starts a container, never deploys and never calls a cloud API.

Are my secrets written into the exported file?

No. Variable names and secrets.required names are written as references that Compose reads from your .env. The values are never written.

Why are some of my services missing from the export?

Only bring-your-own services are exported. Services built from Flisk templates and services that run as local processes with a command are not included.
