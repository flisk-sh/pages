How to test S3 uploads in integration tests with a real bucket

A mock tells you that you called PutObject. A local bucket tells you what actually arrived.

To test S3 uploads against a real bucket, run a local S3-compatible server (MinIO), create one bucket at test startup, give every test its own key prefix, and delete that prefix afterward. Assert on what is actually stored: the key, the size, the content type and the bytes. A mock cannot catch a wrong content type, a key with a bad character or an object another service cannot read.

What a mock misses

Mocking the S3 client is fine for unit tests of logic around the upload. It tells you nothing about bugs that live between your code and the storage: keys built with a leading slash, a content type that was never set, a multipart upload that fails on files over 5 MB, an object stored with the wrong name after a rename, or an endpoint setting that works with the mock and fails with a real client. These show up in production because nothing exercised the real protocol. One small integration test file against a real bucket covers them.

A test setup

Assuming a local S3 on the endpoint and credentials from the environment (see pointing the AWS SDK at a local S3 endpoint):

import { describe, it, expect, beforeAll, afterEach } from "vitest";
import { randomUUID } from "node:crypto";
import {
  S3Client, CreateBucketCommand, HeadObjectCommand, GetObjectCommand,
  ListObjectsV2Command, DeleteObjectsCommand,
} from "@aws-sdk/client-s3";
import { saveAvatar } from "../src/avatars.js";   // the code under test

const s3 = new S3Client({
  region: "us-east-1",
  endpoint: process.env.AWS_ENDPOINT_URL_S3,
  forcePathStyle: true,
});
const Bucket = "test-uploads";
let prefix;

beforeAll(async () => {
  try { await s3.send(new CreateBucketCommand({ Bucket })); }
  catch (e) { if (e.name !== "BucketAlreadyOwnedByYou") throw e; }
});

afterEach(async () => {
  const list = await s3.send(new ListObjectsV2Command({ Bucket, Prefix: prefix }));
  if (list.Contents?.length) {
    await s3.send(new DeleteObjectsCommand({
      Bucket, Delete: { Objects: list.Contents.map(o => ({ Key: o.Key })) },
    }));
  }
});

describe("saveAvatar", () => {
  it("stores the image with the right key and content type", async () => {
    prefix = `t-${randomUUID()}/`;
    const bytes = Buffer.from("fake-png-bytes");
    const key = await saveAvatar({ bucket: Bucket, prefix, userId: "u1", bytes, type: "image/png" });

    const head = await s3.send(new HeadObjectCommand({ Bucket, Key: key }));
    expect(key).toBe(`${prefix}avatars/u1.png`);
    expect(head.ContentType).toBe("image/png");
    expect(head.ContentLength).toBe(bytes.length);

    const body = await s3.send(new GetObjectCommand({ Bucket, Key: key }));
    expect(Buffer.from(await body.Body.transformToByteArray())).toEqual(bytes);
  });
});

The design that makes this reliable is the prefix. Each test writes under a random prefix, so tests do not see each other's objects and they can run in parallel. Cleanup deletes only that prefix, which leaves your own development data in other buckets alone. Your code needs a way to receive the prefix, either as a parameter as above or through a configuration value.

The Flisk way

Tests need the storage running, and they need the endpoint reachable from wherever the test process runs. With Flisk's MinIO resource (see how to run MinIO locally), the S3 port is not published to your machine by default, only the console is. If your tests run on the host, add the S3 port to extraPorts in the store's service.json, then start the stack and point the tests at it:

"extraPorts": [{ "port": 9001 }, { "port": 9000 }]
flisk up shop --wait
AWS_ENDPOINT_URL_S3=http://127.0.0.1:9000 AWS_ACCESS_KEY_ID=minioadmin AWS_SECRET_ACCESS_KEY=minioadmin npx vitest run

--wait makes flisk up return once the services are healthy, so the tests do not start against a server that is still booting. The credentials shown are the development defaults of the Flisk preset. If your tests run inside a container in the stack instead, the endpoint is http://store:9000 and the variables are already set by dependsOn. The broader pattern is in integration tests against the real stack. In CI, bring the stack up with the same command so local and CI runs match.

Things worth asserting

  • Key shape. Exactly the key you expect, with no leading slash and no double slash.
  • Content type and length. From a HeadObject call. This catches the missing ContentType that makes browsers download instead of display.
  • The bytes. Read the object back and compare. A truncated stream shows up here.
  • A large file. One test with a file above the multipart threshold, for example 6 MB of generated bytes, exercises the multipart path.
  • Failure behavior. What your code does when the bucket does not exist or the key is rejected.

Pitfalls

  • Shared bucket, no prefix. Tests that list a whole bucket will fail when run in parallel or after a failed run left objects behind.
  • Cleanup in the test body. If an assertion throws first, cleanup never runs. Use afterEach.
  • Leftover state. Use a dedicated test bucket, not the one you use for manual work. To reset everything, flisk down --purge removes the project's volumes, including the database, so it is a heavy reset.
  • MinIO is not S3. Passing here shows your code speaks the S3 API. It does not prove IAM policies or bucket policies work in AWS.

When not to use this

If your code just wraps one SDK call with no logic, a unit test with a stub is enough. Keep the real-bucket tests for code with key construction, metadata, streaming or multipart behavior.

Questions people ask

Why a prefix per test instead of a bucket per test?

Prefixes are cheap to create and delete and need no bucket-level setup. A fresh bucket per test is slower and runs into bucket naming rules.

Should integration tests run against real AWS S3?

A local S3-compatible server covers the protocol and your code's behavior. Use a real throwaway bucket for the few checks that depend on AWS itself, such as IAM and bucket policies.

How do I make sure the storage is ready before the tests run?

With Flisk, use flisk up with the --wait flag so it returns after services are healthy. Without it, poll a simple call such as listing buckets before the first test.
