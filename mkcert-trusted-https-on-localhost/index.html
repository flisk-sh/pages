How to get trusted HTTPS on localhost with mkcert

A self-signed certificate gives you a browser warning. A certificate from your own local authority gives you a padlock.

To get trusted HTTPS on localhost, install mkcert, run mkcert -install once to add a local certificate authority to your system trust store, then run mkcert with the host names you use. You get a certificate and a key file that browsers accept without a warning, and you load them into your dev server or reverse proxy.

Why a plain self-signed certificate is not enough

A certificate made with openssl req -x509 is signed by nobody your machine trusts. Browsers show a full-page warning, curl refuses to connect, and Node throws self-signed certificate errors. You can click through the warning or disable verification, but then you are testing a different setup from production, and some features (service workers on a non-localhost name, secure cookies in Safari, HTTP/2 in some clients) behave differently.

mkcert fixes the trust part. It creates a private certificate authority (CA) on your machine and registers it in the system store, and in Firefox when certutil is available. Certificates it issues are then valid for every tool that reads that store.

Install and issue a certificate

On macOS with Homebrew, on Linux with your package manager or the release binary, and on Windows with Chocolatey or Scoop:

brew install mkcert
mkcert -install
mkcert localhost 127.0.0.1 ::1 app.shop.localhost api.shop.localhost

The last command writes two files into the current folder. mkcert names them after the first host and the number of extra names, for example localhost+4.pem and localhost+4-key.pem. Use -cert-file and -key-file if you want fixed names. List every host name you need: a certificate only covers the names inside it. Add the names explicitly rather than counting on a wildcard such as *.localhost, and test the result in the browsers you use.

Use the certificate

Node's built-in server:

import https from "node:https";
import fs from "node:fs";

https.createServer({
  cert: fs.readFileSync("localhost+4.pem"),
  key: fs.readFileSync("localhost+4-key.pem"),
}, (req, res) => res.end("ok")).listen(8443);

Vite takes the same two files in server.https ({ cert, key }), and nginx takes them in ssl_certificate and ssl_certificate_key. Often it is simpler to terminate TLS in one reverse proxy and keep your services on plain HTTP behind it. The Caddy article in this space shows that setup.

Node does not read the system store by default. When a Node script calls your HTTPS service, point it at the mkcert root:

export NODE_EXTRA_CA_CERTS="$(mkcert -CAROOT)/rootCA.pem"

Where Flisk fits

Be clear about what Flisk does here. Its gateway is Traefik, and the URLs Flisk prints are http://. Flisk plans a host port for HTTPS (443, or a port from 8443 to 8543 when 443 is not usable), but its docs describe no certificate setup, so you should not count on Flisk to terminate TLS for you. The practical route is to let Flisk run the services and put your own TLS proxy in front. Run flisk networks to see the HTTP URL of every frontend and API service, and proxy to that.

If every service in your project declares a command, Flisk runs them as local processes without Docker and prints http://localhost:<port>. That is the easiest case: your proxy forwards to those ports.

Pitfalls

  • Do not share the CA. The file rootCA-key.pem in mkcert -CAROOT can mint a certificate for any site on machines that trust it. Never commit it, never copy it to other computers, and never put a mkcert certificate in a shared repository as if it were a team asset. Each developer runs mkcert on their own machine.
  • Containers do not trust it. A service inside a container calling https://app.shop.localhost sees its own image's trust store. Mount the root certificate and set the right variable, or call the service over the internal HTTP network instead.
  • Mixed content. An HTTPS page that calls an http:// API may be blocked by the browser. Change the API URL your frontend uses, or put both behind the same HTTPS proxy.
  • Expiry. Certificates last a little over two years. If the padlock breaks one day, issue the certificate again.

Next, decide where TLS ends. For one proxy in front of several services, read how to run Caddy as a local HTTPS reverse proxy. If cookies are the reason you want HTTPS, check secure cookies on localhost first, because you may not need it.

Questions people ask

Is mkcert safe to use?

Yes for development on your own machine. It is not for production, and its root key must stay private because anyone holding it can issue certificates your machine trusts.

Does Flisk set up HTTPS for me?

No. Flisk prints http:// URLs and its documentation describes no certificate setup. Put a TLS proxy such as Caddy or nginx in front of the URLs Flisk prints.

Why does Node still reject my mkcert certificate?

Node uses its own bundled certificate list. Set NODE_EXTRA_CA_CERTS to the rootCA.pem file in the folder printed by mkcert -CAROOT.
