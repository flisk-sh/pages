How to write a good brief for a coding agent

A short template for task briefs that coding agents can finish: goal, context, constraints, done criteria and what to leave alone, with a before and after example.

A good brief states the goal, points at the relevant files, lists constraints, and says how to check the work. Four to ten lines is usually enough. Most bad agent output comes from a vague goal and no way for the agent to tell whether it succeeded.

The five parts

  1. Goal: the outcome, in one sentence, not the steps.
  2. Context: where to look. Name files, functions or an example to copy.
  3. Constraints: what must not change, libraries to use or avoid, style rules.
  4. Done criteria: a command that must pass, or behaviour you can observe.
  5. Out of scope: things the agent should not touch.

Before and after

Weak brief:

Add rate limiting to the API.

Better brief:

Goal: limit each API key to 60 requests per minute on POST /v1/jobs.
Context: middleware lives in src/server/middleware/. Follow the pattern in auth.ts.
Constraints: use the existing Redis client in src/lib/redis.ts. No new dependencies.
Return 429 with a Retry-After header.
Done when: npm test passes and the new tests in tests/rate-limit.test.ts cover
the limit, the reset, and two keys not affecting each other.
Out of scope: the admin routes, and any change to the auth middleware.

The second version removes the guesses the agent would otherwise make.

Give it a way to check itself

The strongest line in any brief is a command the agent can run. A failing test, a type check, a lint rule or a script that prints OK. Agents that can run a check will iterate until it passes. Agents without one will stop when the code looks plausible. If no test exists, ask for one first: "write a failing test that shows the bug, then fix it". See tests as a feedback loop.

Size the task

A task that fits in one reviewable diff, roughly a few files and a few hundred lines at most, works best. For something bigger, ask for a plan first, read it, correct it, and then run it in steps. Splitting early costs minutes. Reviewing a thousand-line surprise costs hours.

Put repeated parts in a file

If you write "use pnpm, run tests with vitest, never edit generated files" in every brief, move it to a project instructions file. See CLAUDE.md and AGENTS.md. Keep the brief for what is specific to this task.

Common mistakes

Watch for briefs that say "improve" or "clean up" with no measure, briefs that mix three tasks, and briefs that assume the agent knows a convention you never wrote down. Another trap is pasting a long chat history as the brief. Rewrite it as five lines instead. If the agent comes back with questions, treat that as a sign the brief was missing a part, and add it.

Questions people ask

Should briefs be long?

No. Be specific, not long. A few precise lines with a done criterion beat a page of background the agent does not need.

Should I tell the agent how to implement it?

Only when you have a strong preference. Otherwise state the outcome and constraints, and let it propose an approach you can review.
