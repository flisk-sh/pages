Debugging CI Failures

How to Enable Debug Logging in GitHub Actions

Turn on step and runner debug logs with a re-run checkbox or two repository variables, and add your own debug output without leaking secrets.

To get more log detail from GitHub Actions, re-run the failed job and tick Enable debug logging. For every run, set the repository secret or variable ACTIONS_STEP_DEBUG to true. Runner level diagnostics use ACTIONS_RUNNER_DEBUG in the same way.

The quick way: re-run with debug logging

On a failed run, choose Re-run jobs, then Re-run failed jobs or Re-run all jobs. The dialog has a checkbox called Enable debug logging. Tick it and run. This affects only that run, which is what you want while investigating.

With the GitHub CLI you can do the same:

gh run rerun RUN_ID --failed --debug

Debug logging for every run

Add a repository secret or variable named ACTIONS_STEP_DEBUG with the value true. Actions then print extra lines starting with ::debug::, which many actions write but hide by default. ACTIONS_RUNNER_DEBUG set to true adds diagnostic logs from the runner itself and makes them available for download with the run logs.

Do not leave these on permanently. Logs get long and slow to read, and debug output can include values you did not expect. Remove them when you finish.

Write your own debug output

Print the facts you need: working directory, file listing, environment variable names (not values), tool versions, network reachability.

- name: Debug context
  if: failure()
  run: |
    pwd
    ls -la
    env | cut -d= -f1 | sort
    df -h
    free -m || true

if: failure() runs the step only after an earlier step failed. Printing names only with cut -d= -f1 avoids dumping secret values into the log. GitHub masks registered secrets, but a transformed secret (for example a base64 version) is not masked, so be careful.

Keep artifacts of the failure

Logs are not enough when a failure leaves files behind: screenshots, core dumps, test reports, a database dump. Upload them only on failure so you can download and inspect them.

- uses: actions/upload-artifact@v4
  if: failure()
  with:
    name: failure-files
    path: |
      test-results/
      screenshots/
    retention-days: 7

Keep retention short and do not upload anything that contains secrets.

A debugging session in practice

Say a deploy step fails with an unclear 403. Re-run with debug logging, find the request line that shows which API call was made, then compare the token permissions with what that call needs. Add the missing permission, re-run once more without debug and confirm it is green. Then delete the extra debug step you added. The whole loop is three runs. Without debug output the same problem often takes a dozen guesses, each costing a full pipeline run.

If your runs are slow, make the debug step run first and fail fast, so each attempt is short.

What debug logs cannot tell you

Debug logging shows what the runner and actions did. It does not explain a flaky test or a slow dependency. For those, compare runs over time: read the failing log carefully, then reproduce it locally. Enabling debug is a way to gather evidence, not a fix.

Questions people ask

Does debug logging expose my secrets?

GitHub masks registered secret values in logs, but derived values and extra debug output may still show sensitive data. Review the log and turn debug logging off when you finish.

Where do I set ACTIONS_STEP_DEBUG?

In the repository settings under Secrets and variables, for Actions. Create a secret or variable with that name and the value true.
