Use *.localhost URLs instead of port numbers in local dev

Remembering which service is on which port gets old fast. A name per service is easier to read, bookmark and put in config.

To use names instead of ports, put a reverse proxy in front of your services and give each one a hostname under .localhost. Your browser sends app.shop.localhost to the proxy, and the proxy forwards it to the right service. You stop remembering that the billing API is on 4172, and your frontend config gets stable URLs that do not depend on which port was free today.

Why names beat ports

  • Config stays readable: http://api.shop.localhost says more than http://localhost:4172.
  • Several projects can run at once, each under its own name, without port arguments.
  • Cookies and CORS rules are easier to set up on named origins.
  • A port clash changes a number in one place instead of every file that mentions it.

The special name localhost and its subdomains point to your own machine. Current browsers resolve *.localhost to loopback by themselves on macOS and Linux. Other tools, such as curl on some systems, may need the name to be in a hosts file, so test it.

The general approach

You can run Traefik, nginx or Caddy yourself, with a route per service. In Docker, a common setup is Traefik reading labels on each container. It works, but you now maintain a gateway config next to your services, and keep it in sync as services come and go.

The Flisk way

In the container path, Flisk starts a Traefik gateway and writes the routes from your service.json files. The URLs follow two shapes:

http://app.<project>.localhost/<frontend name>
http://api.<project>.localhost/api/<backend name without -api>

List them any time:

flisk networks
flisk networks --stack shop
flisk networks --raw

--raw prints only the URLs, which suits scripts. --json prints a versioned JSON object. Backend ports are not published on your machine, so localhost:<backend port> does not reach a backend in this path. A frontend that calls such an address is flagged by flisk doctor, which suggests the gateway URL.

The gateway removes the route prefix before the request reaches your service. A request to /api/orders/items arrives at the orders service as /items, so the service does not need to know its public prefix.

A bring-your-own service that serves pages from / can set "webUi": true to be routed on <name>.<project>.localhost with no path prefix instead of /api/<name>.

The local-process path uses ports

The plain process path has no gateway. A service with a command listens on the port you gave it, so you open http://localhost:4000. If you want names there, run your own proxy, or switch the project to the container path. Mixing a gateway and bare ports across two services in one project is confusing, so pick one style.

When port 80 is taken

Flisk asks for ports 80 and 443 first, so URLs carry no port. If they are busy, or on Linux and WSL2 where a non-root user cannot check them, it picks the next free ports from a range: ingress 8080 to 8180, HTTPS 8443 to 8543. Then the URLs include the port, such as http://app.shop.localhost:8080/web, and flisk networks shows the real ones. To choose a port yourself:

FLISK_HTTP_PORT=18080 flisk up shop

If you change the port after the stack was started, restart the frontend, because the generated API URL is read when the container starts.

Pitfalls

  • Windows name resolution. If *.localhost does not resolve, Flisk's doctor warns and points to the 127.0.0.1 URLs from flisk networks, or you can edit the hosts file.
  • CORS. A backend you wrote yourself must allow the frontend origin, for example http://app.shop.localhost. Backends scaffolded by Flisk allow *.localhost origins.
  • Another process on port 80. Stop it or move Flisk with the environment variable.
  • Hardcoded ports in code. Read the base URL from an environment variable.

To check a route from the terminal, call it with curl -i and read the status code. A 404 from the gateway means no route matched, so compare your URL with the line from flisk networks. A 502 or 503 means the route exists but the service behind it is not healthy yet, so look at flisk status and flisk logs. Once the names are stable, put them in your frontend env file. They are the same on every teammate's machine that uses the same project name.

If the browser cannot find a name, read localhost subdomain does not resolve. For the browser-to-API link itself, see run a frontend and an API together.

Questions people ask

Do *.localhost names need a hosts file entry?

On macOS and Linux, browsers resolve *.localhost to 127.0.0.1 without any setup. On Windows, resolution can fail. If it does, edit hosts or use the 127.0.0.1 URLs that flisk networks prints.

Why can I not reach a backend on localhost with its port?

In the container path, backend ports are not published to your machine. Use the gateway URL from flisk networks instead.

What if port 80 is taken?

Flisk picks a free port from 8080 to 8180 and puts it in the printed URLs. Set FLISK_HTTP_PORT to choose one yourself.
