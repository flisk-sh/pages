How to split slow end-to-end tests across parallel CI jobs

Each runner boots its own stack and runs a slice of the tests, then one job merges the reports.

Split a slow end-to-end suite by giving each parallel CI job its own copy of the stack and a slice of the tests. In GitHub Actions that means a matrix of shard numbers, flisk up --wait in every job, and --shard=N/M on the test runner. Each runner boots its own stack, so shards never share a database or a port.

Why a shared stack does not work

It is tempting to boot the stack once and run several test jobs against it. GitHub jobs run on separate machines, so they cannot reach each other's localhost. You would have to expose the stack publicly, which is slow and unsafe. The workable pattern is one stack per job. The price is that start-up time repeats in each job, so sharding pays off only when the tests take much longer than the boot.

Step 1: a matrix of shards

jobs:
  e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm install -g @flisk-sh/flisk
      - run: flisk project --yes
      - run: flisk up --wait --wait-timeout 600
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --shard=${{ matrix.shard }}/4 --reporter=blob
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: blob-report-${{ matrix.shard }}
          path: blob-report
          retention-days: 7

fail-fast: false lets the other shards finish when one fails, so you see every failure in one run. The shard count is written twice, in the matrix and in --shard. Keep them equal, or some tests will never run. Jest and Vitest support the same idea with their own --shard flag.

Step 2: merge the reports

Four blob reports are not useful to read. Add a job that downloads them and merges them into one HTML report:

  report:
    needs: e2e
    if: always()
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - uses: actions/download-artifact@v4
        with:
          path: all-blob-reports
          pattern: blob-report-*
          merge-multiple: true
      - run: npx playwright merge-reports --reporter html ./all-blob-reports

The merge job does not need the stack, only the report files. For how the tests themselves should be written against the stack, see Playwright against a local stack.

Where Flisk helps with parallel jobs

Each job runs the same two commands, flisk project --yes and flisk up --wait, so the matrix stays short and the stack definition lives in your repository, not in the workflow. If your project has several stacks, flisk up <stack-name> starts one stack, so you can give each job a different stack instead of a slice of one suite. That works well when the stacks are independent, for example a storefront stack and an admin stack. When you only need part of one stack, flisk up --only starts the named services and what they depend on. Ordinary Flisk start-up applies in every job, so the boot cost is the same each time. Measure it on your own project before you pick a shard count.

Choosing the number of shards

  1. Time one full run and note the boot time (the flisk up --wait step) separately.
  2. With N shards, the run takes roughly boot time plus test time divided by N, assuming the tests are evenly sized.
  3. Stop adding shards when boot time dominates, or when you hit your concurrent job limit.

Uneven tests make uneven shards. If one shard is always the last to finish, the runner is splitting by file, so one very large file is the cause. Split the file.

Pitfalls

  • Tests that share state. Shards run in any order and on separate databases. Tests that rely on data another test created will fail in some shards only.
  • Ports on self-hosted runners. Two jobs on one machine fight for the same ports. Use one job per runner, or give each a different stack.
  • Artifact name clashes. Upload each shard under a unique name, as above, or the upload fails.
  • Cost. Four shards use four runners' minutes of boot time. Parallel does not mean cheaper.

When not to shard

If the suite takes under ten minutes, a single job is simpler and often fast enough. First check whether the time goes to the tests or to the waiting. Slow waits are fixed by better health checks, covered in waiting for every service to be healthy, not by more jobs.

Once your shards run in parallel, make sure a failure in one of them leaves enough evidence, as described in getting useful logs when a CI run fails.

Questions people ask

Can several jobs share one running stack?

Not on GitHub-hosted runners. Jobs run on separate machines and cannot reach each other's localhost, so each job starts its own stack.

How many shards should I use?

Time the stack boot and the tests separately. Add shards until boot time is the larger part of each job or you reach your concurrency limit.

Why use fail-fast: false?

With the default, one failing shard cancels the others, so you only see part of the failures. Turning it off shows every failure in one run.
