How to handle secrets in an AI agent sandbox

Keep API keys out of reach of model-written code: proxies that add credentials, short-lived tokens, scoped permissions and what never to put in environment variables.

Do not put long-lived secrets inside a sandbox where model-written code runs. Keep the key outside, and let a trusted proxy or tool add it to requests, or hand the sandbox a short-lived, narrowly scoped token. Anything the code can read, a prompt injection can steal.

Assume the code will read its environment

Code running in the sandbox can print its environment variables, read mounted files and call any host you allow. If a key is there, treat it as exposed. That includes keys in .env files, build arguments and shell history.

Pattern 1: the tool holds the key

Instead of letting the sandboxed code call a paid API, expose a function that the agent can call. The function runs outside the sandbox, holds the key and returns only the result.

async def send_email_tool(to: str, subject: str, body: str):
    # runs in your service, not in the sandbox
    if not to.endswith("@yourcompany.com"):
        return "refused: recipient not allowed"
    await mail_api.send(api_key=os.environ["MAIL_KEY"], to=to, subject=subject, body=body)
    return "sent"

The same function also gives you a place to validate arguments, rate limit and log.

Pattern 2: a credential-adding proxy

If the code must call an HTTP API directly, route it through your egress proxy. The code sends a request with no key, and the proxy adds the Authorization header for allowed hosts only. The sandbox never sees the secret. It builds on the network setup in limiting sandbox network access.

Pattern 3: short-lived scoped tokens

When a token must enter the sandbox, make it small and temporary: read-only, one repository or one bucket, valid for minutes. Many services let you mint such tokens through an API. Revoke them when the run ends. A leaked token with a ten-minute life and read-only scope is an incident you can live with.

Habits that prevent leaks

  • Never bake secrets into images or commit them to the workspace repo.
  • Use separate keys for the agent, with spending limits set at the provider.
  • Scrub tool output before you show it back to the model: search for known key prefixes and mask them.
  • Log which key was used by which run, so you can rotate precisely.
  • Rotate any key the agent has ever been given in a real environment after a suspected injection.

For more on this, see environment and secrets for local development and the AI security hub.

Test for leaks

Run a canary check. Put a fake key with a recognisable prefix where a real one would be, ask an agent to do a normal task, and search the logs, outputs and any outbound requests for the fake value. If it appears anywhere, your setup leaks. Do the same after changes to the sandbox image or the tool layer.

Questions people ask

Is it safe to pass a key as an environment variable?

It is safe only if the code inside cannot be hostile. For model-written code, assume it can read every variable, and use a proxy or a short-lived token.

What if the agent needs git push access?

Give it a token scoped to one repository, or let it push to a branch through a tool you control, and require a pull request before merge.
