Cursor vs offset pagination: which one to build

Pagination is easy to add and hard to change once clients depend on it, so choose with the data in mind.

Use offset pagination (?page=3&limit=20) for small, slow-changing lists where users jump to a page number. Use cursor pagination (?after=abc&limit=20) for feeds, large tables and anything that changes while people read it. Cursors stay fast on deep pages and never skip or repeat rows when data is inserted.

How offset pagination breaks

Offset pagination translates to LIMIT 20 OFFSET 40. It has two problems.

Unstable pages. You load page 1 (rows 1 to 20). Someone adds a new row at the top. Page 2 now starts with what used to be row 20, so the user sees it twice. Delete a row and the opposite happens: one is skipped without any error.

Cost that grows with depth. The database must read and throw away all the skipped rows. OFFSET 100000 reads 100000 rows to return 20. Whether this matters depends on your table size, so measure with realistic data (seeding a local database helps).

Offset has real strengths: it is trivial to implement, works with any sort order, supports "jump to page 7" and can return a total count for page numbers. For an admin table of a few thousand rows that is often the right trade.

How cursor pagination works

A cursor says "continue after this row". In SQL that is a keyset query, comparing against the last row's sort key rather than counting rows. In Postgres, with a stable sort on (created_at, id):

SELECT id, created_at, status
FROM orders
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 21;

The row-value comparison (created_at, id) < ($1, $2) is valid in Postgres. An index on (created_at, id) lets it jump straight to the right place, so page 5000 costs about the same as page 1. Fetch limit + 1 rows: if you get 21, there is a next page, and you return 20 plus a cursor built from the 20th row. The id is the tiebreaker; without it, rows with the same timestamp can be skipped.

Design the response

GET /orders?limit=20&after=eyJjIjoiMjAyNi0xMS0xNFQxMDowMDowMFoiLCJpIjo5MX0

{
  "data": [ ... 20 orders ... ],
  "next_cursor": "eyJjIjoiMjAyNi0xMS0xM1QwOTozMDowMFoiLCJpIjo3MX0",
  "has_more": true
}
  • Make the cursor opaque: base64url of a small JSON object is typical. Clients must not parse it, so you can change the internals later.
  • When has_more is false, return next_cursor: null.
  • Cap limit on the server (for example 100) and give it a default. Return a clear error for a value outside the range, using problem details.
  • Document the sort order. A cursor is only valid for the sort it was made with, so reject a cursor combined with a different sort.
  • Optionally add a Link header with rel="next" (RFC 8288) for clients that follow links.

What you give up

No random access: a client cannot jump to page 7, only walk forward (and backward if you build a before cursor). A total count is a separate query, SELECT count(*), which can be slow on large tables. Either skip it, return an approximate figure, or put it behind an opt-in parameter. Sorting by a non-unique or nullable column needs care: always append a unique column to the sort, and decide where nulls sort.

Test pagination before clients depend on it

Pagination bugs hide in small data sets. Test with these cases:

  1. More rows than one page, and exactly one page, and zero rows.
  2. Many rows with the same sort value, to prove the tiebreaker works.
  3. Insert a row between page 1 and page 2, and check nothing repeats or disappears.
  4. Walk every page and assert the full list equals the expected set with no duplicates.
  5. A tampered or expired cursor returns a 400 and not a 500.

Run them against a real database, not a mock, since the bugs live in the query. A seeded local Postgres with a few thousand rows is enough to catch ordering mistakes, and EXPLAIN on the keyset query will show whether your index is used.

Pitfalls

  • Switching later is a breaking change. Clients that send page=2 will break when you remove it. Decide early, or support both for a while and deprecate one (deprecation headers).
  • Leaking the schema in the cursor. Do not put a raw SQL fragment or a table name in it, and sign or encrypt it if tampering matters.
  • Soft deletes and filters. Apply filters in the same query as the cursor condition so the page size stays correct.

Questions people ask

Is cursor pagination always faster than offset?

On deep pages of large tables, yes, when an index supports the sort. For small tables the difference is not noticeable, and offset is simpler.

Can I get a total count with cursor pagination?

Not for free. A count is a separate query that may be slow on big tables. Offer it as an opt-in parameter or return an estimate.

Why do I need an id in the sort for a cursor?

Many rows can share a timestamp. A unique tiebreaker such as the id keeps the order total, so no rows are skipped or repeated across pages.
