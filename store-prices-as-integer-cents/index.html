How to store prices in a shop database: integers, not floats

Floating point cannot represent 0.10 exactly, so totals drift. Store the smallest unit as an integer and decide in advance where rounding happens.

Store money as an integer count of the smallest unit (cents for USD and EUR) together with a three-letter currency code. Do arithmetic on the integers, and round exactly once, at a place you chose on purpose. Never store prices in float or double precision columns: 0.1 + 0.2 is 0.30000000000000004 in most languages, and the error shows up as a total that is off by a cent.

The two safe options

Postgres gives you two reasonable column types for money:

  • bigint minor units. 1999 means 19.99 USD. Fast, no rounding surprises on addition, and it maps to integers in every language. This is the default recommendation.
  • numeric(12,2). Exact decimals in the database. Fine too, but your driver may hand it to you as a string, and a careless cast to a JavaScript number brings the float problem back.

The money type is tied to a locale setting and a fixed number of decimals, so most teams avoid it. Whatever you pick, put the currency next to the amount:

CREATE TABLE order_lines (
  id               bigserial PRIMARY KEY,
  order_id         bigint NOT NULL,
  variant_id       bigint NOT NULL,
  qty              int    NOT NULL CHECK (qty > 0),
  unit_price_minor bigint NOT NULL CHECK (unit_price_minor >= 0),
  currency         char(3) NOT NULL
);

Not every currency has two decimals

The exponent comes from ISO 4217. USD, EUR and GBP use 2. JPY has 0, so 500 yen is stored as 500. KWD and BHD use 3. If you hard-code "divide by 100" in the formatting code, a yen price shows as 5.00. Keep a small table or map of exponents, and format using it. A browser or Node Intl.NumberFormat with a currency code applies the right number of digits when you pass the amount in major units, so convert with the exponent first.

const EXP: Record<string, number> = { USD: 2, EUR: 2, JPY: 0, KWD: 3 };
export const toMajor = (minor: number, cur: string) => minor / 10 ** (EXP[cur] ?? 2);

This division is only for display. Do not feed the result back into any calculation.

Snapshot the price on the order

The catalogue price changes; an order must not. Copy the unit price, currency and any tax rate onto the order line when the order is created, as in the table above. Joining back to the product table later gives you today's price, not what the customer paid, which breaks refunds and reports.

Round once, and split the remainder

Percentages and tax produce fractions of a cent. Choose where to round and write it down. Two common rules are rounding each line and summing, or summing first and rounding the total. Either is fine; mixing them gives totals that disagree with the line items on the invoice. Use integer arithmetic: Math.round(subtotal * 15 / 100) for 15 percent, with the rounding rule you picked (half up is the usual one).

A fixed discount spread over several lines needs a remainder rule, or the pieces will not add up. Allocate by proportion, then give the leftover cents to the largest lines:

function allocate(total: number, weights: number[]): number[] {
  const sum = weights.reduce((a, b) => a + b, 0);
  const parts = weights.map((w) => Math.floor((total * w) / sum));
  let left = total - parts.reduce((a, b) => a + b, 0);
  for (let i = 0; left > 0; i = (i + 1) % parts.length, left--) parts[i]++;
  return parts;
}
// allocate(100, [1, 1, 1]) gives [34, 33, 33], and the parts sum to 100

A test like that last comment is worth writing: for any total and weights, the parts must sum to the total.

Pitfalls

  • JSON numbers. A price of 19.99 in an API body becomes a float in the client. Send minor units as integers, or amounts as strings.
  • Integer overflow. A JavaScript number is safe up to 2^53 minor units, which is plenty for a shop. Reports that multiply by large factors should use BigInt or do the math in SQL.
  • Mixed currencies in one sum. Adding USD to EUR minor units is a bug the type system will not catch. Group by currency, or refuse mixed carts.
  • Percentages stored as floats. Store a tax rate as basis points (2000 for 20 percent) or as numeric.

With prices settled, the next structure to get right is the catalogue itself: a schema for products, variants and SKUs.

Questions people ask

Is numeric or bigint better for money in Postgres?

Both are exact. bigint minor units are simpler in application code and cannot turn into floats by accident. numeric(12,2) reads better in raw SQL.

How do I store a price with three decimals, like fuel?

Use a larger exponent for that field, for example thousandths, and keep the exponent in the schema or a currency table so that formatting reads it.

Where should I round tax?

Pick one rule, per line or per order, apply it in a single function, and use it everywhere, including the invoice.
