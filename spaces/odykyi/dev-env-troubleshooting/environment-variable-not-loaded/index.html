When the local stack breaks

Environment variable not loaded in a local service: how to debug

Four questions solve almost every case: where is it set, which source wins, did the process restart, and is it read at build time or run time.

A variable that is "not loaded" is almost always set in one place and read in another. Print the value inside the running process, not in your shell, then check which source wins and whether the process was restarted after you changed it.

Four questions, in order

  1. What does the process see? Look inside it. In a container: docker exec <container> printenv DATABASE_URL. A variable set in your shell is not in the container unless something passes it in.
  2. Which source wins? Most tools have several: the shell, an .env file, a service-level env file and values written in the config. When two define the same name, one silently wins. Docker Compose documents its own order, and it is easy to get wrong, so print before you reason.
  3. Did the process restart? Environment is read when a process starts. Saving a file does not re-read it. A hot reload may restart the code without changing its environment.
  4. Is it read at build time? Frontend tools such as Vite and Next.js copy variables with a public prefix (VITE_, NEXT_PUBLIC_) into the built code. Changing them later has no effect until the next build or dev server start.

File format traps

  • Spaces around = or a quote that is not closed can produce an empty value.
  • An inline comment after a value may be kept as part of the value, depending on the parser.
  • A $ in a value can be read as a variable reference. In a Compose file it must be written as $$.
  • An .env file in the wrong folder is simply not read. Many tools look in the current directory, not the file's neighbour.
  • A variable that is set but empty is different from one that is missing. Some code treats them the same, some does not.

Where Flisk reads variables from

A Flisk project has three places that matter:

PlacePurpose
Project .envGit-ignored. Holds TILT_ENV, DB_PASSWORD, DATABASE_URL and JWT_SECRET. flisk up adds missing keys and never changes existing values.
params in service.jsonWritten to the generated .env.backend.autogenerated of that service. A $ is written as $$ for you.
secrets in service.jsonNames the service needs. required must have a value, optional may be empty, and generate creates a random value once.

Do not edit the generated .env.*.autogenerated files. Change service.json and regenerate, as in generated config is out of date.

See what a service really gets with flisk run, which runs one command with that service's environment:

flisk run orders-api -- printenv DATABASE_URL

Precedence for container services: a value in the compose environment: entry beats the service env file, and for the keys it defines, the file passed with --env-file beats the shell. For local-process services, ${VAR} in env is resolved in this order: the shell, the project .env, the service's own .env, then the default you wrote.

Declare a secret and let Flisk generate it

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "secrets": {
    "required": ["STRIPE_KEY"],
    "optional": ["SENTRY_DSN"],
    "generate": { "SESSION_SECRET": "hex:32" }
  }
}

A required name with no value is reported by flisk doctor and blocks the run. In the generated Compose file a required name becomes ${NAME:?...} and an optional one ${NAME:-}. The generate format accepts hex:N or base64:N.

Switch values for one run

flisk down
flisk up --env-file .env.staging-like

--env-file replaces the project .env for that run. The file must be inside the project and carry TILT_ENV, DB_PASSWORD and JWT_SECRET. A running stack refuses it, which is why flisk down comes first.

Messages you will see

  • Missing required env variables and Invalid env variables: X is set but empty come from flisk doctor.
  • JWT_SECRET is not set. Run flisk up ... means the key has not been generated yet.
  • Doctor warns when a NEXT_PUBLIC_* or VITE_* value looks like a secret, because public variables end up in the browser bundle.
  • Doctor also warns when an env value points outside the local stack. Add the host to allowedHosts if that is intended.

Frontends get VITE_API_URL and a VITE_<NAME>_API_URL per backend from a generated file. After a change, run flisk restart <frontend>.

Pitfalls

  • Never put real credentials in a variable with a public prefix.
  • Do not commit .env. Commit an example file with names and no values.
  • Running a command by hand outside Flisk uses your shell, so it can behave differently from the stack. Use flisk run to compare.

For database variables in particular, see DATABASE_URL and env vars locally. If a missing value makes a service die at boot, why a container keeps restarting covers the loop.

Questions people ask

Why does my VITE_ or NEXT_PUBLIC_ variable stay old after I change it?

These variables are inlined into the frontend code when it is built or started. The page keeps the old value until the frontend restarts or rebuilds.

Does flisk up overwrite values in my .env?

No. It adds missing keys and never changes existing values.

What does --env-file do?

It replaces the project .env for that run. The file must be inside the project and contain TILT_ENV, DB_PASSWORD and JWT_SECRET. Run flisk down first if a stack is already up.
