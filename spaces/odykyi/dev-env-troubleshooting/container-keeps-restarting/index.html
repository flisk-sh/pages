When the local stack breaks

Why a Docker container keeps restarting, and how to find out

A restart policy turns a crash into a loop. The loop is a symptom: the exit code and the first log lines before it tell you the cause.

A container that keeps restarting is crashing and being started again by its restart policy. To find out why, read the exit code and the logs of the last run, not the status column. docker inspect gives you the exit code, whether the kernel killed it for memory, and how many restarts happened.

See the loop for what it is

docker ps shows a status such as Restarting (1) 12 seconds ago. The number in brackets is the last exit code. Start from these two commands:

docker ps -a --filter "status=restarting"
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}' <container>
docker logs --tail 100 <container>

Then read the exit code:

Exit codeUsual meaning
1The application raised an error. The reason is in the log.
126The command exists but cannot be executed (permissions, wrong architecture).
127The command was not found in the image.
137Killed with SIGKILL. Check oom=true above: the container hit its memory limit.
139Segmentation fault.
143Stopped with SIGTERM. Often a normal stop, not a crash.

The usual causes in a dev stack

  • Missing configuration. A required variable is empty and the app exits during start. See why an environment variable is not loaded.
  • The database is not ready. The app tries to connect once, fails and exits. Wait for readiness, or retry inside the app.
  • A migration runs inside the start command. Every restart runs it again, and if it fails the container exits, which restarts it. Run migrations once, as a separate job.
  • Out of memory. A watcher, a compiler or a JVM takes more than the container or the Docker VM allows. This is exit 137 with oom=true.
  • The wrong command. An entrypoint that finishes immediately, such as a shell script that starts a server in the background and then exits, ends the container.
  • A one-shot job with a restart policy. A job that is supposed to finish is restarted every time it does.

What Flisk does and shows

For container services, a bring-your-own resource uses the Compose restart policy unless-stopped unless you set restart in its service.json to no, on-failure or always. So a crash does loop by default. Use no or on-failure for a one-shot job.

{
  "schemaVersion": 1,
  "appName": "seed-data",
  "appType": "bring-your-own",
  "dockerfile": "Dockerfile",
  "healthCheck": false,
  "restart": "no"
}

Start with what Flisk knows:

flisk status --unhealthy
flisk logs --service orders-api --since 5m
flisk doctor

flisk doctor has two checks aimed at this problem. One reports N migration command(s) run from a backend or worker's own start-up. The fix it gives is to move the migration into a migrator resource that the service depends on. The other warns about a container pinned near its memory limit while burning CPU, which it describes as likely stuck in a boot-time retry or fetch loop. Its cause is not always known: the message is a hint, so confirm with docker logs before acting on it.

Once you have changed the cause, restart just that service:

flisk restart orders-api

Services without Docker

A local-process service that exits is started again after 1 second, then 2, 4 and 8. After five quick exits in a row Flisk stops restarting it and says so. That is a safety stop, not a fix: read the log, change the cause, then run flisk up again. Set "restart": "no" to turn the automatic restart off for a one-shot command.

Read the loop in order: first the exit code, then the last 100 log lines, then the configuration the container was given. Most loops are explained by the first two. If both look normal, compare the variables inside the container with what you expected, because an empty value fails quietly in many frameworks.

Pitfalls

  • Do not set the policy to no to hide a crash. You lose the loop and keep the bug.
  • If docker logs is empty, the process probably died before writing anything. Run the image's command by hand with docker run --rm -it --entrypoint sh <image> and start it yourself.
  • A container that is unhealthy but not restarting has a different problem. Its probe command may not exist in the image: see the health check section in a service that will not start.
  • If memory is the cause, raise the Docker VM memory (Docker Desktop settings, or your Colima VM settings) before you tune the app. The choice of Docker runtime is compared in Docker Desktop, Colima and Podman.

For the log-reading part of this routine in more detail, see how to read logs from every service.

Questions people ask

Does Docker restart a container that is unhealthy?

No. A failing health check only changes the reported status to unhealthy. A restart policy reacts to the process exiting, not to the health status.

What does exit code 137 mean?

The process was killed with SIGKILL. In a container that is often the out-of-memory killer, which you can confirm with docker inspect and the OOMKilled field.

How do I stop a one-shot job such as a migration from restarting?

Set the restart policy to no or on-failure. In a Flisk service.json that is the restart field, and migrations belong in their own migrator resource.
