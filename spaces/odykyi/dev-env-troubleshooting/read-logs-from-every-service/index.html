When the local stack breaks

How to read logs from every service in a local stack

One terminal per service does not scale past three services. Pick one place that merges output, prefixes each line with a name and lets you filter.

To read logs from every service at once, use one command that merges them: docker compose logs for Compose, flisk logs for a Flisk project, or the foreground output of a process runner. Each line should carry the service name and a timestamp, and you should be able to narrow the output by service and by age. Opening one terminal per service stops working at about three services.

What you want from a log view

Before picking a tool, know what you need to do with logs while debugging a stack:

  • See all services in time order, so you can follow a request across them.
  • Filter to one or two services when you already know where to look.
  • Look only at the last few minutes, not the whole history.
  • See only what is failing, without the healthy majority.

Plain Docker and Compose

Compose already merges service output and prefixes each line with the service name:

docker compose logs --tail=100 --timestamps
docker compose logs -f api worker
docker compose logs --since 5m

-f follows live output, --since limits the window. With bare docker you read one container at a time with docker logs --tail 100 <container>. If you start processes by hand, a runner such as foreman, overmind or concurrently gives you the same prefixed stream.

The Flisk way

Flisk has one command for both of its runtimes:

flisk logs --tail 50
flisk logs --service orders-api --since 5m
flisk logs --unhealthy
flisk logs --unhealthy --json

The options, as in flisk logs --help:

  • -s, --service <names...> limits output to the services you name, using the names from flisk resources.
  • --tail <n> sets the number of recent lines, 200 by default.
  • --since <duration> accepts values such as 30s, 5m or 1h.
  • --unhealthy shows only services that are failing or still starting.
  • --port <n> points at the Tilt UI port for a Docker stack.
  • --json prints one JSON object.

The command prints a snapshot. It has no follow flag. That is deliberate: a bounded answer is what scripts and coding assistants need, and the live view lives elsewhere.

Local processes (no Docker)

When every service declares a command, flisk up stays in the foreground. Each line is prefixed with the service name and the live stream is that terminal. Lines are also written, with a timestamp, to .flisk/native/logs/<service>.log, and flisk logs reads those files and merges them in time order. You can also open the file directly:

tail -f .flisk/native/logs/api.log

Docker and Tilt stacks

For containers, the live view is the Tilt UI. flisk up prints its address, normally http://localhost:10350. If another project's Tilt already holds that port, Flisk picks the next free one and says so, so read the port from the output. Each resource has its own log there, including the image build, which is where a failing install or compile shows up first.

flisk logs asks that same Tilt. If the stack is not running you get Could not reach Tilt on port 10350. The stack is not running, or Tilt is on another port. Start the stack, or pass --port with the port that flisk up printed.

When you need the container's own output, outside Tilt, Docker still works as usual:

docker ps --format '{{.Names}}'
docker logs --tail 100 -f <container>

If you run without Docker, running services without Docker explains the local-process mode that writes those log files.

A short debugging routine

  1. flisk status --unhealthy to see which services are failing.
  2. flisk logs --unhealthy --tail 100 to read their last lines.
  3. Find the first error, not the last. Later errors are often side effects: a worker that cannot reach the API prints ten lines because the API died on line one.
  4. flisk logs --service api --since 2m to read the failing service in its own timeline.
  5. Reproduce the request and read the same window again.

Pitfalls

  • Logs from a service that restarted may be missing the start of the earlier crash. Read the window right after the first failure.
  • A 200-line tail can cut off a long stack trace. Raise --tail or narrow with --service instead of reading everything.
  • Logs can contain tokens and personal data. Check them before pasting them into an issue or a chat.
  • Application logs written to a file inside a container, not to stdout, are not part of any of these views. Write to stdout and stderr.

If the logs show a service that keeps dying and coming back, continue with why a container keeps restarting. If nothing starts at all, begin with a service that will not start.

Questions people ask

Does flisk logs follow output like tail -f?

No. It prints a bounded snapshot (200 lines by default). To follow live output, keep the terminal where flisk up runs open for local processes, or use the Tilt UI or docker compose logs -f for containers.

Where does flisk logs read from?

For local-process services it reads the files in .flisk/native/logs. For Docker and Tilt stacks it asks Tilt, which listens on port 10350 unless that port was taken.

How do I give logs to a coding assistant?

Use flisk logs --json, or the logs tool of the Flisk MCP server. Both return a bounded snapshot, so the output stays small.
