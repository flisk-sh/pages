When the local stack breaks

Generated config out of date: fix config drift step by step

Drift means a generated file no longer matches the file it comes from. The fix is to change the source and regenerate, not to patch the output.

Config drift means a generated file no longer matches what it is generated from. You find it by running flisk config verify, and fix it by changing the source file and running flisk config regenerate. Editing the generated output by hand only works until the next regeneration.

Why drift happens

Many tools write files for you: a Compose file from a template, a TypeScript config from a schema, a client from an API spec. That is fine as long as everybody agrees on which file is the source. Drift appears in three ways:

  • Someone edits the generated file to fix something quickly and forgets the source.
  • Someone edits the source and forgets to regenerate.
  • Two people regenerate with different tool versions, so the output differs.

The general cure is the same for any generator: commit both the source and the output, add a command that checks they agree, and run it in CI. The check needs no network and no running services.

The Flisk way: verify, explain, regenerate

Flisk separates files into two kinds. You own service.json and .flisk/project.json. Flisk owns files marked as generated, such as *.autogenerated.* and the ones under .autogenerated/ and .flisk/.flisk-out/. Start with verify:

flisk config verify

If every file matches, it reports that the project is in sync. If not, it exits with status 1 and prints which file is out of sync, along with a diff, for example:

Out of sync: .flisk/.flisk-out/TILT_TECH_STACK.star (run 'flisk config regenerate')

Ask who owns a file before you touch it:

flisk config explain .flisk/.flisk-out/TILT_TECH_STACK.star

The answer includes a line such as Ownership: generated and tells you whether editing the file blocks flisk up. Then regenerate:

flisk config regenerate

Regeneration rewrites the generated files from your service.json files. If your change is in a generated file, move it to service.json first (for example a variable goes under params), or it disappears. After regenerating a running stack, run flisk down and then flisk up so the new files take effect.

What blocks flisk up

Hand edits to a service's .autogenerated/ files block flisk up, and the message names the file. Flisk keeps snapshots in .autogenerated/.flisk-contract/ to detect this. The bypass is flisk up --ignore-drift. It exists for an emergency, not for daily work: the edit you keep is lost the next time someone regenerates.

The root .tiltignore

A root .tiltignore that starts with the header "SYSTEM-GENERATED BY Flisk CLI" is regenerated. Remove the header and Flisk treats the file as yours and never overwrites it. Use that on purpose, if you need your own ignore rules.

One more case: a file you generated on a branch and a file generated on main can both be correct for their own source and still conflict when merged. After a merge that touches service.json, regenerate once and commit the result, so the generated files describe the merged source and not either side. This takes seconds and avoids a failing verify on the first pull request after the merge.

A workflow that avoids the problem

  1. Change service.json (or run a flisk resource or flisk config edit command).
  2. Run flisk config regenerate.
  3. Run flisk config verify and look at the diff in git.
  4. Commit the source and the generated files together.
  5. Let CI run flisk config verify on every pull request.

A CI job needs nothing but the CLI:

npm install -g @flisk-sh/flisk
flisk config verify

The full job, with the doctor check as well, is in check config drift in CI. For what lives in a service file, read why an environment variable is not loaded, which shows where values come from.

Pitfalls

  • Do not resolve a merge conflict in a generated file by hand. Resolve the conflict in service.json, then regenerate.
  • Ignoring generated files in git makes verify useless in CI, because there is nothing to compare. The exception is .env, which holds secrets and stays ignored.
  • Different Flisk versions can produce different output. Pin the version with minFliskVersion, as in works on my machine.
  • Let coding assistants know which files are generated. An assistant that edits them creates drift in the same way a person does.

When verify is clean and the stack still misbehaves, return to check your machine before starting the stack to rule out the machine itself.

Questions people ask

Should I commit generated files?

Yes. Flisk generated files are meant to be committed, so a reviewer sees what the stack will run and flisk config verify can check them in CI.

Can I skip the drift check?

flisk up --ignore-drift bypasses it, but this is not recommended. The file you edited by hand will be overwritten the next time it is regenerated.

Do I need to restart after regenerating?

For a stack that is running, yes: run flisk down and then flisk up so the new files are used.
