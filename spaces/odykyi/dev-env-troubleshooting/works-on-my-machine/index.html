When the local stack breaks

Works on my machine: find why a local stack differs

The goal is to turn a feeling into a diff. Collect the same facts from both machines, compare them, and pin the ones that matter.

A stack that works for you and fails for a teammate differs in something you have not looked at yet. Do not argue from memory. Collect the same facts from both machines (tool versions, free ports, environment values, Docker state and leftover data), put them side by side, and the difference is usually on the first screen.

The usual suspects

  • Runtime versions. Node, Python, Go or Bun at different versions. A language feature or a lockfile format that one machine does not know.
  • Docker and Compose versions. Some features need a recent Engine or Compose plugin. Older ones may ignore a setting rather than fail.
  • Ports. Something on the other machine already holds a port you assumed was free.
  • Environment. A value in one person's shell or .env that the other does not have.
  • Leftover state. A volume from an older version of the schema, or an image cache that hides a broken build.
  • Operating system. Case-sensitive file names, line endings, file sharing and file watcher behaviour differ across macOS, Linux and Windows.
  • Resources. A Docker VM with little memory kills processes that a bigger VM runs fine.

Make the difference visible

Run the same small set of commands on both machines and compare the text. This works with any setup:

node --version; docker version --format '{{.Server.Version}}'
docker compose version
git rev-parse HEAD
lsof -nP -iTCP -sTCP:LISTEN | head -30

Add git status to catch uncommitted edits, and check that the lockfile is committed and used (npm ci instead of npm install). A fresh clone in a new folder, run once, is the cleanest test: if it fails there, the repository is missing something that your machine supplies by accident.

With Flisk

Flisk gives you three things to compare and two things to pin.

Compare. flisk doctor --json prints the machine and project checks as JSON, so you can save the output from each machine and diff it. It reports the Docker daemon, the Engine and Compose versions, free disk, ports, missing variables and more. flisk networks --json lists the real URLs. The ports can legitimately differ: Flisk picks a free port from a range when the preferred one is busy, so two machines can show different ports for the same project.

flisk doctor --json > doctor-mine.json
flisk networks --json > urls-mine.json

Doctor expects Docker Engine 25 or newer and Compose 2.20 or newer for the generated health checks, Tilt 0.25.0 or newer and Bun 1.2.0 or newer. It prints the versions it found, so an old install shows up as a line to read, not a mystery.

Pin. Two settings stop version drift before it starts:

  • minFliskVersion in .flisk/project.json makes flisk up refuse to run on an older CLI and print Run: flisk upgrade. --ignore-version skips the check.
  • toolchain in a local-process service's service.json, for example "toolchain": "node@24". If the program on PATH is another version, flisk up stops with TOOLCHAIN_MISMATCH before starting anything. Supported forms include bun@1.3, python@3.12, go@1.23, deno@2 and ruby@3.3. Without it, files such as .nvmrc or .python-version only cause a warning in doctor.
{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch server.js",
  "port": 4000,
  "toolchain": "node@24"
}

Gate it in CI. Run flisk doctor --no-ping and flisk config verify on every pull request, so a change that only works with your local files fails before it reaches a teammate. See check config drift in CI.

Stale data

If the code is the same and the database behaves differently, suspect old data. flisk down --purge deletes the project's volumes, networks and images, and the next flisk up starts from nothing. It also deletes local data you may want, so use flisk down --dry-run first.

What Flisk does not solve

  • Operating system differences. File sharing, line endings and file watcher behaviour are still yours.
  • Docker VM size. Memory and disk limits are set in Docker Desktop or your Colima settings.
  • Credentials. A teammate still needs their own values for the secrets in secrets.required.

Pitfalls

  • Do not compare screenshots of a terminal. Compare text files.
  • Do not fix a difference on one machine only. Put the fix in the repository, as a pin, a check or a line in the setup docs.
  • Check generated files too. If one of you edited a generated file, the other sees different behaviour. See generated config is out of date.

To stop collecting these facts by hand every time, put them behind one command, as described in check your machine before starting the stack.

Questions people ask

Can Flisk guarantee identical machines?

No. It can pin the Flisk version, check runtime versions for local-process services and report tool versions, but operating system differences and VM resources stay yours to manage.

What should I send a teammate who asks for help?

The output of flisk doctor --json, the output of flisk networks, and the last lines of the failing service's log.

Is a different port a bug?

Usually not. Flisk picks a free port from a range when the preferred one is taken, so the same project can use different ports on two machines. Use flisk networks to see the real URLs.
