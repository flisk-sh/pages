When the local stack breaks

Hot reload not working in Docker or locally: causes and fixes

Hot reload has three links: your editor saves the file, something copies it to the process, and the process restarts. Find the broken link.

If changes do not appear after you save, the chain that carries the change is broken somewhere: the file never reaches the running process, or the process does not restart when it does. Find out which half, by checking whether the file inside the container or process changed, and whether the runtime watches for changes at all.

The three links in the chain

  1. Your editor writes the file. Some editors write a temporary file and rename it. A few watchers miss that.
  2. The file gets to the process. Locally this is automatic. In a container it needs a bind mount or a sync tool.
  3. The process notices and restarts. The runtime needs a watch mode, or a tool such as nodemon or air must do it.

Test link 2 directly. Edit a file, then read it from inside the container with docker exec <container> cat /app/src/index.js. If the old content shows, the sync is the problem. If the new content shows and the app is unchanged, the restart is the problem.

Common causes without any specific tool

  • No watcher. node server.js never reloads. Use node --watch server.js, bun --watch, uvicorn main:app --reload or a frontend dev server.
  • File events do not cross the mount. On some setups, bind mounts do not deliver change events. Switch the watcher to polling: CHOKIDAR_USEPOLLING=true for chokidar tools, --poll for some others. Polling uses more CPU.
  • The project is on a slow or foreign filesystem. Under WSL2, a project in /mnt/c is the usual cause. Move it to the Linux home folder.
  • The change is outside the watched folders. A watcher on src will not see config/.
  • The change needs a rebuild. New dependencies, a changed Dockerfile or a changed native module are not hot-reloadable.
  • The browser cache. Do a hard refresh before you conclude the server is stale.

What Flisk does for each language

For container services, Flisk uses Tilt live_update. Tilt copies changed files into the running container and the language's own mechanism restarts it. The copied folders come from syncs in service.json, and default to src and prisma for backends and src and public for frontends. What happens after the copy depends on the language:

ServiceReload behaviour
Bun backend, worker, agent, MCPReloads by default when the dev script runs bun --watch or --hot. Set dev.liveReload to false to opt out.
NodeUses node --watch. Editing package.json rebuilds the container.
PythonRelies on its own reload command, such as uvicorn --reload.
GoNo live update by default. You opt in, see below.
Bring your ownNo live reload. Rebuild after a change.

Go is the case most people trip over. Set liveReload to true in the service:

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "language": "go",
  "dev": { "liveReload": true }
}

Then Flisk builds a watcher called flisk-go-watch into the container. It compiles on change and swaps the binary. If the compile fails, the last good build keeps running and the log says it is waiting for a change to rebuild. A change to go.mod or go.sum rebuilds the image.

Look at the service's output right after you save:

flisk logs --service orders-api --tail 30

A line saying the build failed means the reload worked and your code did not compile.

Windows and WSL2

If the project is under /mnt/c, flisk doctor warns that hot reload may be broken, and --strict turns that warning into a failure. Move the project into your WSL home folder, for example ~/projects, and open it from there. See local development on Windows.

Without Docker

For services that run as local processes, there is no sync step. Flisk starts your command as it is, so reload depends only on that command. Put the watcher in it:

"command": "node --watch server.js"

Other examples: bun --watch server.ts and uvicorn main:app --reload. For several services reloading together, see hot reload across services.

Pitfalls

  • Changing an environment variable needs a restart, not a reload. See why an environment variable is not loaded.
  • If you set dev.liveReload on a language that does not support it, Flisk ignores it and prints a warning.
  • A frontend that reads a generated API address must be restarted with flisk restart <frontend> after that address changes.
  • Reload hides state. A worker that restarts on every save may drop jobs. Do not judge queue behaviour while it is reloading.

If a service reloads but then fails to start, go back to a service that will not start.

Questions people ask

Does every Flisk language reload on save?

No. Bun and Node backends reload by default, Python uses its own reload command, Go needs dev.liveReload set to true, and bring-your-own resources have no live reload.

Why does a package.json change rebuild the container?

Installed dependencies are part of the image, so a dependency change cannot be copied into a running container. It needs a rebuild.

Why is reload slow or broken under WSL2?

Files on a Windows drive under /mnt/c do not send file events reliably to Linux. Keep the project in the WSL home folder.
