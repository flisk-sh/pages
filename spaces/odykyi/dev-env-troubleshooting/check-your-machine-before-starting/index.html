When the local stack breaks

Check your machine before starting a local stack: a checklist

Five minutes of failed builds cost more than a five-second check. Run the preflight first, in a script or with one command.

Check five things before you start a local stack: Docker answers, there is enough disk space, the ports you need are free, your tool versions are recent enough, and your configuration files are in sync. You can script this in a few lines, or run flisk doctor, which does the same and more.

The five checks and why they matter

  1. Docker is running. docker info fails fast when the daemon is down. Starting a build against a stopped daemon wastes the wait.
  2. Disk space. Image builds fail halfway when the disk fills. Look at the host and, with Colima or Docker Desktop, at the VM.
  3. Ports. A stack that needs 80, 443 or 5432 cannot start when another process holds one.
  4. Versions. Compose, Docker and your language runtimes must support what the project uses.
  5. Files in sync. Generated files must match their source. Otherwise the stack runs a different config than the one in review.

A plain script

Nothing here needs special tools. A shell script that fails on the first problem is enough for a small project:

set -u
docker info >/dev/null 2>&1 || { echo "Docker is not running"; exit 1; }
free_gb=$(df -g . | awk 'NR==2 {print $4}')
[ "$free_gb" -ge 5 ] || { echo "Less than 5 GB free"; exit 1; }
for p in 80 443 5432; do
  lsof -nP -iTCP:$p -sTCP:LISTEN >/dev/null && echo "Port $p is in use"
done
docker compose version

The df -g flag is macOS. On Linux use df -BG .. The limits here are examples, not recommendations: set them for your own images. This kind of script grows by one line per incident, which is fair. The cost is that every project ends up with its own slightly different copy.

With flisk doctor

Install Flisk with npm install -g @flisk-sh/flisk and run:

flisk doctor

It checks the Docker daemon, the Engine and Compose versions, the Tilt version, free disk space, the ports Flisk wants (HTTP, HTTPS and Postgres), the project's service files, environment values and secrets, and whether generated files exist. A trimmed run looks like this:

✓ HTTP 8081, HTTPS 8444, Postgres 15434
✓ Docker daemon is running
⚠ 12.6 GiB free on this machine: image builds may fail below 5 GiB

A warning shows the commands that would fix it. A failure makes the command exit with status 1, so scripts and CI can stop on it. Useful options:

  • --all shows every check, including the passing ones.
  • --json prints machine-readable output.
  • --strict turns warnings into failures.
  • --no-ping, --no-gateway and --no-database skip the checks that reach services.
  • --fix repairs what it can. Add --dry-run to see the changes first, and --scope project or --scope machine to limit them. --yes skips the prompts.

Doctor and flisk config verify are different on purpose. Doctor checks the environment and the services. config verify checks that the generated files are consistent with your service.json files. Run both.

See the ports before you start

flisk up --dry-run starts nothing, and prints the URLs and the host ports it would use:

flisk up --dry-run

When port 80 is busy it says so, for example HTTP: wanted 80, using 8081 (selected from fallback range 8080-8180). It also tells you how to force a port: FLISK_HTTP_PORT=80 flisk up. Postgres uses a range starting at 15432 in the same way.

Built-in gates in flisk up

You do not have to remember any of this, because flisk up runs its own checks before it starts. If Docker is not running it stops with Cold start blocked and tells you to start Docker Desktop, OrbStack or Colima. If Tilt is missing it says so. Disk space below 5 GiB stops the run with DISK_SPACE_LOW, and between 5 and 15 GiB it warns.

Where to use it

  • First day on a project. Run flisk doctor before your first flisk up.
  • When something breaks. It is the first command in a service that will not start.
  • In CI. Add flisk doctor --no-ping and flisk config verify as a job, as described in check config drift in CI.

Pitfalls

  • A warning is not an error. A disk with 12 GiB free passes, but one large build can use that.
  • Do not run --fix without --dry-run the first time. Some repairs change machine settings.
  • Doctor cannot know your VM limits are too low for your workload. It reports what it can measure.

When the report is clean and your teammate still sees something different, compare both machines as shown in works on my machine.

Questions people ask

Does flisk doctor change anything on my machine?

Not by default. It reports. The --fix option can repair some problems, and --dry-run shows what it would do first.

Can I run flisk doctor in CI?

Yes. Use flisk doctor --no-ping in a job so it does not try to reach services, and combine it with flisk config verify.

Does flisk up check anything itself?

Yes. It checks the disk, ports and Docker before starting. flisk up --dry-run prints the ports it would use without starting anything.
