When the local stack breaks

Why a *.localhost subdomain does not resolve, and the fix

A browser error, a curl error and a 404 from the proxy look alike but mean different things. Tell them apart first, then fix the right layer.

Any name ending in .localhost, such as api.myapp.localhost, is meant to point to your own machine with no hosts file entry. When it does not work, first read the symptom: a DNS error means the name did not resolve, while a 404 or 502 means it resolved and the proxy answered. They have different fixes.

Three symptoms, three causes

What you seeWhat it means
"Could not resolve host" or "server not found"Your resolver does not map .localhost to 127.0.0.1.
"Connection refused"The name resolved, but nothing listens on that port.
404 from the proxyThe proxy is up, but no route matches this host name or the service is not started.
502, 503 or 504The proxy found the route, but the container behind it is not answering.

Check the resolver without any tool

RFC 6761 reserves .localhost for loopback, so most systems resolve it themselves. Test it in two steps:

ping -c 1 anything.localhost
curl -sS -o /dev/null -w "%{http_code}
" http://127.0.0.1:8081/

If the ping fails, the resolver is the problem. If the second command gets a response but the host name does not, the problem is the name. Two ways around a resolver that will not cooperate:

  • Send the host name yourself: curl --resolve api.myapp.localhost:8081:127.0.0.1 http://api.myapp.localhost:8081/ or curl -H "Host: api.myapp.localhost" http://127.0.0.1:8081/.
  • Add a line to your hosts file for the exact names you use. A hosts file cannot hold a wildcard, so each name needs its own line.

With Flisk

In Docker mode, Flisk puts a Traefik gateway in front of your services and serves each one at a name built from the service and the project, for example http://api.<project>.localhost:8081/api/orders. Do not build the name by hand. Print it:

flisk networks
flisk networks --json

The command shows every URL, with the port Flisk chose. That matters because the gateway does not always get port 80. It tries 80 and 443 first, then 8080 to 8180 and 8443 to 8543. To see the choice before starting, use flisk up --dry-run, which prints something like HTTP: wanted 80, using 8081 (selected from fallback range 8080-8180). To force a port, set FLISK_HTTP_PORT=80 flisk up. A value you set is used as given and fails if the port is busy.

The usual reasons a .localhost URL fails in a Flisk project:

  • The port is missing. http://api.myapp.localhost/ goes to port 80. If Flisk chose 8081, you need :8081 in the URL.
  • The project name differs from what you typed. The host is built from the project folder name. Rename the folder and the host changes. Copy the URL from flisk networks.
  • A 404 from Traefik. No running container is registered for that URL. Either it is still building or it has not started, or it never turns healthy. See a service that will not start.
  • A 502, 503 or 504. The route exists and the container does not answer. Read its logs with flisk logs --service <name>.
  • The ports are held by something else. flisk doctor reports when another container already owns the gateway ports. See how to fix "port already in use".

Windows

On Windows, flisk doctor warns when the system does not resolve *.flisk.localhost to 127.0.0.1. The suggested way out is to use the 127.0.0.1 URLs that flisk networks prints. Windows setup is covered in local development on Windows.

macOS with Colima

If the port is correct and the connection is refused or hangs, the port forwarder of the VM may be stuck. Check who listens with lsof -nP -iTCP:80 -sTCP:LISTEN (use the port Flisk chose), and restart the VM with colima restart if it shows nothing. More in local development on Mac with Colima.

No Docker, no gateway

Services that run as local processes have no Traefik and no .localhost names. Open http://localhost:<port> with the port from the service's service.json.

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000
}

This one is at http://localhost:4000/.

Pitfalls

  • A browser may remember a failed lookup or redirect to HTTPS. Test with curl before you blame the stack.
  • A VPN or a DNS filter can intercept names. If ping anything.localhost fails only on that network, the cause is the network, not the project.
  • Do not hard-code a port or host in the frontend. Take it from the generated configuration, as explained in local URLs instead of ports.

If the URL works for you but not for a teammate, the next step is why it works on my machine.

Questions people ask

Do I need to edit /etc/hosts for *.localhost?

Normally not. Names ending in .localhost are reserved for the local machine, and browsers and most system resolvers send them to 127.0.0.1. If yours does not, call the service on a URL with an explicit Host header, or use the 127.0.0.1 address.

Why do I get 404 instead of a connection error?

A 404 means the name resolved and the proxy answered, but it has no route for that host. Check the project name in the host and whether the service started.

Do local-process services use *.localhost?

No. Without Docker there is no Traefik gateway. Use http://localhost:<port> with the port from service.json.
