When the local stack breaks

How to debug a service that will not start locally

Most start-up failures come from five things: a taken port, a missing program, a missing variable, a wrong health path or a dependency that is not ready.

When a service will not start, find out which of three things happened: the process exited, the process is running but never became healthy, or something refused to launch it at all. Read the last lines of its log, then check the port, the command, the environment and the health route, in that order. Most failures end at one of those four.

Decide which kind of failure you have

Do not guess. The first minute is about sorting the failure into one bucket, because each bucket has a different fix.

  • Refused to launch. The tool stops before your code runs. Typical messages: a program is not installed, a port is taken, a required variable has no value, a runtime version is wrong.
  • Starts, then exits. Your code runs and crashes. The reason is in the service's own output: a stack trace, a missing module, a database that refused the connection.
  • Runs, never healthy. The process is alive, but the check that decides "ready" fails. The usual causes are a health route that does not exist, a server bound to 127.0.0.1 inside a container, or a health command missing from the image.

The checks that work with any tool

These work with Compose, foreman, make targets or plain terminals.

  1. Run the command by hand. Go to the service folder and run exactly what the tool runs. If it fails alone, stop looking at the orchestration.
  2. Check the port. Find out who holds it: 
    lsof -nP -iTCP:4000 -sTCP:LISTEN
    If a process is listed, stop it or move your service. A longer walkthrough is in how to fix "port already in use".
  3. Check the variables. Print what the process really receives, not what you think you set. An empty DATABASE_URL is the most common reason for a crash on boot.
  4. Check the bind address. Inside a container the server must listen on 0.0.0.0. A server on 127.0.0.1 is invisible to the container's health check and to the proxy in front of it.
  5. Check the health path. Call it yourself and look at the status code. A 404 here means the orchestrator will wait forever.
  6. Check the order. If the API needs the database, make sure the tool waits for the database to be ready, not only started.

What Flisk adds

Flisk stops early for several of these and prints the reason. Start with the readiness check, which reads the project and the machine:

flisk doctor
flisk status --unhealthy
flisk logs --unhealthy

flisk status --unhealthy and flisk logs --unhealthy show only services that are failing or still starting, so you do not scroll through the healthy ones.

Flisk can run a service in two ways, and the failures differ.

Services that declare a command (no Docker)

A service with a command in its service.json runs as a local process. Before it starts anything, flisk up refuses to run when a command's program is not installed, a port is already in use (it names the process that holds it), two services share a port, or a dependsOn name is not a service with a command. A service with a toolchain such as node@24 is also refused when the program on your PATH is another version.

After launch, a service counts as ready when its health URL answers, and Flisk waits up to 60 seconds for each one. A process that exits is started again after 1 second, then 2, 4 and 8. After five quick exits in a row Flisk stops and says so. Use "restart": "no" for a one-shot job.

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

Output is prefixed with the service name and also written to .flisk/native/logs/<service>.log.

Container services (Docker and Tilt)

Here the failure often shows up in flisk doctor before anything starts. Messages worth recognising:

  • Backends without a health route: the container never turns healthy and Traefik answers 404. Add a /health route, or set healthCheckPath in the service's service.json to the path you use.
  • secret SECRET_KEY has no value: a name listed under secrets.required has no value in .env or the environment. Add it, or list it under secrets.optional.
  • resource outside discovery.paths: the service folder is not where Flisk looks, so flisk up will not start it. Services live in services/<stack>/<name> by default.
  • container is running, but its health check is failing: read the probe's own result with Docker.
docker inspect --format '{{range .State.Health.Log}}[{{.ExitCode}}] {{.Output}}{{end}}' <container>

Exit 127 with curl: not found means the image has no curl. Flisk proceeds with a warning in that case, because the app may well be fine, but the check is still broken. Use a tool the image has, or set healthCheck in the service.

Pitfalls

  • A 404 from Traefik right after startup does not prove the service is broken. Images may still be building. Re-run flisk doctor after a minute.
  • Two services on one port may not produce a warning in a container stack. Give each its own port.
  • Do not fix a crash by raising timeouts. If the log shows a stack trace, the wait was never the problem.
  • If the process exits immediately and the log is empty, the program may be failing before it can write anything, such as a missing interpreter. Run it by hand.

Once the service runs, learn how to read every service's output in one place in how to read logs from every service, and see why a container keeps restarting if it starts and then falls over.

Questions people ask

How long does Flisk wait for a local-process service to become ready?

Up to 60 seconds per service. Ready means the health URL answers below 400, or without healthCheckPath that the port accepts connections, or without a port that the process is still running after a second.

Why does a container run but flisk up still fails?

Flisk waits on Docker's health status. If the health command does not work inside the image, or the health route does not exist, the container never turns healthy even though the app may be serving.

Can I skip the checks to see the error myself?

Run the service's command by hand in its folder. If it fails there, the problem is the service, not the tooling around it.
