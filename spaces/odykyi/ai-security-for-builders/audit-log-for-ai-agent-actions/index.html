How to build an audit log for AI agent actions

When an agent does something wrong you need to know who asked, what it saw and what it did. Log tool calls and decisions in an append-only record.

Write one append-only record for every tool call an agent makes: who triggered it, which tool, which arguments, what came back, and whether a person approved it. With that record you can answer what happened after an incident, and you can spot abuse as it starts.

What to record

  • Who: the user or system that started the run, and the agent identity.
  • When: a timestamp, plus a run id and a sequence number.
  • What: tool name and arguments, and the result or error.
  • Why: the model name and a reference to the prompt version. Keep the full prompt in a separate store.
  • Approval: who approved, when, and the exact arguments approved.

A table that only grows

CREATE TABLE agent_audit (
  id          bigserial PRIMARY KEY,
  at          timestamptz NOT NULL DEFAULT now(),
  run_id      text NOT NULL,
  seq         int  NOT NULL,
  actor       text NOT NULL,
  tool        text NOT NULL,
  args        jsonb NOT NULL,
  outcome     text NOT NULL,   -- ok | error | denied
  approved_by text
);

REVOKE UPDATE, DELETE ON agent_audit FROM app_user;

Revoking update and delete from the application role makes the table append-only for the app, so a compromised agent path cannot rewrite history. Ship the same events to a second place you control for extra safety.

Write the audit row in the same code path that runs the tool, not inside the model loop, so a missing log line cannot happen because the model skipped a step. If the audit insert fails, fail the tool call. An action with no record is worse than an action that did not happen.

Redact before you store

Audit logs live a long time and many people read them. Remove secrets, tokens and sensitive personal data from arguments and results before writing. Store a hash or an id in place of a full document. Set a retention period and apply access control to the log itself. See keeping secrets away from agents.

Alert on patterns

A log nobody reads is only useful after the fact. Add a few simple alerts:

  • A burst of denied calls or validation failures from one run.
  • A tool called far more often than normal.
  • A write or send action right after a run read untrusted content.
  • Calls to a host that is not on the allowlist.

These checks are plain queries on the table above and need no model.

Use it to improve

Each incident is a lesson. Add the missing check, narrow the tool or add an approval step, then write a test that replays the failing case. The same events feed the traces in multi-agent system patterns and tracing and your evaluations in agent testing.

Questions people ask

Is an application log enough as an audit log?

Usually not. An audit log should be structured, append-only, redacted and access-controlled, so it can be trusted after an incident.

How long should I keep agent audit logs?

Set a retention period that fits your legal and business needs, and delete or anonymize after it. Do not keep sensitive data forever.

Run it in a sandbox

Test risky agent code away from your real machine.
