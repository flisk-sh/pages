How to safely run code that an LLM wrote

Model-written code can delete files, read secrets and call the network. Run it in a throwaway container or microVM with no secrets and limited network.

Run model-written code in an isolated sandbox: a container with a read-only root, no secrets, no network or an allowlist, and CPU, memory and time limits, thrown away after each run. Never run it in your own shell or on your main machine with your credentials.

What can go wrong

Code from a model might be buggy, or it might be the result of an injection. Either way it runs with the permissions of the process that starts it. On your laptop that means your files, your SSH keys, your cloud credentials and your network. A single bad line such as a recursive delete or an upload of ~/.aws is enough.

A locked-down container

Docker is a reasonable first layer. Drop what the code does not need.

docker run --rm \
  --network none \
  --read-only --tmpfs /tmp:rw,size=64m \
  --memory 512m --cpus 1 --pids-limit 128 \
  --cap-drop ALL --security-opt no-new-privileges \
  --user 1000:1000 \
  -v "$PWD/job:/job:ro" \
  python:3.12-slim timeout 30 python /job/script.py

No network, a read-only filesystem, no extra capabilities, a non-root user, a memory cap and a 30 second timeout. Mount the code read-only and copy results out through a separate writable folder if you need them.

Containers share the host kernel

A container is not a strong security boundary on its own, since it shares the host kernel. For code from untrusted sources or from agents that run unattended, add a stronger layer: a user-space kernel such as gVisor, or a microVM such as Firecracker. These cost some startup time and compatibility, and in return a kernel bug in the guest does not hand over the host. The hub on AI sandboxes for agents compares the options.

What to leave out

  • No real credentials. If the code needs an API, give it a narrow, short-lived token for that one purpose.
  • No access to the Docker socket or to your home directory.
  • No outbound network by default. If it needs packages, install them in the image beforehand.
  • No persistence between runs. Start fresh each time so one run cannot poison the next.

Test the sandbox itself. Run a script inside it that tries to read your home directory, call an outside host and write to the root filesystem, and confirm each attempt fails. Keep that script as a regression test, so a change in a base image or a flag cannot quietly weaken the isolation.

Managed sandboxes

If you would rather not run the isolation yourself, hosted sandboxes exist. Fleet offers agent sandboxes from several providers behind one API key and one balance; it is early and in beta. Whatever you choose, check what the sandbox can reach and what happens to the data afterwards. Combine it with the egress controls from the injection guide.

Questions people ask

Is Docker enough to sandbox untrusted code?

It is a good first layer but shares the host kernel. For truly untrusted code, add gVisor or use a microVM such as Firecracker.

Should the sandbox have internet access?

Not by default. Allow only specific hosts the task needs, and install dependencies in the image beforehand.
