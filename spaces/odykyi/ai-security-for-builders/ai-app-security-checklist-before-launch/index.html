AI app security checklist before you launch

A short checklist covering secrets, permissions, untrusted input, output handling, sandboxing, approvals, logging and automated checks in CI.

Before you launch an app that gives a model real capabilities, check eight things: secrets, tool permissions, untrusted input, output handling, sandboxing, approvals, logging, and automated tests for all of these. Each item below links to a guide with the detail.

The checklist

  1. Secrets. No keys in prompts, files the agent reads or tool output. Keys are scoped and revocable. See keeping keys away from agents.
  2. Permissions. Each agent has the smallest toolset. Tools are narrow and credentials scoped. See least privilege.
  3. Untrusted input. You know which content an outsider can write, and no agent combines that with private data and an exit. See indirect injection.
  4. Output handling. Model output is parsed, schema-checked, rule-checked and escaped for its destination. See output validation.

The checklist, continued

  1. Sandboxing. Model-written code runs in an isolated, disposable environment. See sandboxing LLM code.
  2. Approvals. Hard-to-undo actions need a human or a deterministic policy. See human approval.
  3. Logging. Tool calls are logged append-only with redaction and alerts. See the audit log.
  4. Limits. Rate limits, spending caps, step budgets and timeouts exist and are enforced in code.

Run a threat walk-through

Take 30 minutes with your team and walk through one question per input: "if an attacker controls this text, what is the worst thing the agent can do?" List each source of text: user messages, web pages, files, emails, tool results, third-party tool descriptions. For each, trace which tools could be triggered and what data could leave. Write down the worst case and the control that limits it. Gaps appear fast.

Keep the output of the walk-through next to the code, in a short file in the repository, so it is reviewed in pull requests like any other change. When a pull request adds a tool or a data source, the reviewer asks which row of the file changes.

Automate what you can

A checklist rots unless something enforces it. Turn items into tests and CI checks:

  • A secret scanner on every push.
  • A test that fails if a tool's schema loses a validation rule.
  • An injection test set: a few poisoned pages and documents with a check that no write or send tool is called.
  • A dependency audit for packages and MCP servers you use.

Flisk's GEL (Guard, Eval, Loop) describes an approach to CI guards and evals where a model proposes and a deterministic score decides, which fits this kind of check. See also CI guards and AI code review.

Be honest about residual risk

You will not reach zero risk. Write down what you accept: for example, that the support bot can be talked into rude replies, but cannot see other customers' data or issue refunds above a limit. Share that list with whoever owns the product. Revisit it when you add a tool, since every new capability changes the risk. Start from what prompt injection is if you need to explain it to the team.

Questions people ask

What is the single most important security control for an AI agent?

Least privilege. If the agent can only do small, reversible things, a successful attack stays small.

How often should I review AI app security?

Whenever you add a tool, a data source or a third-party server, and on a regular schedule such as quarterly.

Run it in a sandbox

Test risky agent code away from your real machine.

Run untrusted agent code in a disposable sandbox with no secrets and limited network. Fleet offers agent sandboxes behind one API key; it is in beta.
