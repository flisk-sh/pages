How to give an AI agent least-privilege tool permissions

Decide what the agent may do before it runs, not after it surprises you. Narrow tools, scoped credentials and allowlists keep a confused agent from doing damage.

Give an agent the smallest set of tools that does the job, and make each tool narrow: read-only where possible, limited to one folder, one table or one repository, with fixed parameters. Then a confused or manipulated agent can only do small things.

Prefer narrow tools over general ones

A general tool such as run_shell(command) or run_sql(query) hands the model everything the process can do. A narrow tool such as get_order(order_id) hands it one thing.

BroadNarrow
run_sql(query)get_order(order_id), list_orders(customer_id)
write_file(path, text)save_note(topic, text) into a fixed folder
http_get(url)fetch_docs(page) for one known host

Narrow tools take more code, and the code is where your rules live.

Write the tool contract as a table before you write code: tool name, what it reads, what it writes, who may call it, and what limits apply. The table is short, reviewable by a teammate, and becomes the checklist you test against. If a row says "anything" in the writes column, that tool needs to be split.

Scope the credentials too

The tool code uses a credential, and that credential should be as small as the tool. For a database, create a role that can only select from the tables the tool needs.

CREATE ROLE agent_reader LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE app TO agent_reader;
GRANT USAGE ON SCHEMA public TO agent_reader;
GRANT SELECT ON orders, products TO agent_reader;

If the model is tricked into a bad query, the database refuses anything beyond select on two tables. Do not reuse your admin connection string.

Constrain arguments in code

Even a narrow tool needs argument checks, since the model can pass anything.

from pathlib import Path

ROOT = Path("/srv/agent-notes").resolve()

def read_note(name: str) -> str:
    p = (ROOT / name).resolve()
    if ROOT not in p.parents:
        raise PermissionError("outside notes folder")
    return p.read_text()

Resolve the path before checking, so ../ tricks fail. The same thinking applies to URLs, ids and amounts: check type, range and ownership.

Separate read tools from write tools

Split tools by risk and attach them to different agents or modes. A research agent gets read tools. Only an agent in a step you control gets write tools. Mark destructive tools clearly and gate them with approval, see human approval for risky actions.

Review the tool list regularly

Tool lists grow quietly. Once a quarter, list every tool each agent can call and ask whether it still needs it. Remove what it does not. Fewer tools also make the model pick the right one more often. Pair this guide with validating model output, since permission checks and output checks work together.

Questions people ask

Is read-only access always safe?

Not entirely. A read-only agent can still leak what it reads if it can send data out. Combine read-only tools with limits on outbound access.

Should I let the model write its own SQL?

Only with a read-only role limited to specific tables, plus query limits and a timeout. For anything else, use narrow tools with fixed queries.
