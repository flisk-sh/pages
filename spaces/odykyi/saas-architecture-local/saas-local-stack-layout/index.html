Build a SaaS app locally

What to run locally for a SaaS app: web, API, worker, database

A SaaS app is rarely one process. Decide which parts you run, in what order they start and which route fits, before the folders multiply.

A typical SaaS app runs five things locally: a web front end, an API, a background worker, a database and a cache. A sixth, a one-shot migration job, runs before the API. Start them in dependency order with one command, and keep every service's port, environment and start order in a file that is committed with the code.

The parts and why each exists

PartWhat it doesStarts after
Database (Postgres)Tenants, users, plans, audit eventsnothing
MigratorApplies schema changes and exitsdatabase
Cache (Redis)Rate limit counters, sessions, short-lived datanothing
APIBusiness rules, tenant resolution, authenticationmigrator, cache
WorkerEmails, exports, purges, webhooks to customersmigrator, cache
WebThe user interfaceAPI

You can fold parts together early. A monolith with a worker thread is a fine start. The reason to run the worker as its own process is that slow jobs then cannot slow web requests, and you can restart one without the other. Plan for the split even if you start joined.

Two routes with Flisk

Flisk has two ways to run a project, and one project uses one of them, not both.

  • Local processes, no Docker. Each service has a command in its service.json and runs on your machine. Postgres or Redis can still run from an image next to them if Docker is available. Start-up order follows dependsOn. This is the quicker route for a web app, an API and a worker.
  • Docker and Tilt. Services are built into containers, routed through a gateway on *.localhost names, and live-updated on code changes. The shared Postgres is on by default, and a Prisma API gets a migrator.

A project cannot mix both yet: a service built from a Dockerfile next to command services stops flisk up with a mixed-runtime error. The practical rule is: choose local processes for speed, choose containers when you need gateway routing or the same image you deploy.

Scaffold the container route

Install with npm install -g @flisk-sh/flisk. In an empty folder:

flisk project --yes
flisk resource api --stack saas --feature prisma --yes
flisk resource web --type frontend --stack saas --yes
flisk resource jobs --type worker --stack saas --yes
flisk resource cache --type database --framework redis --stack saas --yes
flisk config verify
flisk up saas

The --feature prisma flag creates two folders, api and api-migrator, where the migrator waits for Postgres and the API waits for the migrator. The scaffolded web lists api in its dependsOn. The Redis resource is the redis:7.4-alpine image with a redis-cli ping health check. After flisk up, flisk status shows state and flisk networks prints the URL of each web and API service. Check what your backend sees with flisk run api -- printenv DATABASE_URL.

Prefer a ready-made start? flisk create myapp --starter next-postgres scaffolds a Next.js site, an Express API and Postgres with a migrator, and needs Docker. For the migration pattern, read migrations in local dev with a migrator.

Scaffold the local-process route

flisk project --yes
flisk resource api --local --stack saas --yes
flisk resource web --type frontend --local --stack saas --yes

Each of these writes a service.json with "command": "npm run dev" and a port. Add a Postgres service as an image, as shown in multi-tenant database design, list it in the API's dependsOn, and run flisk up. The output prints a http://localhost:<port> link for each service. Background on this route: run local services without Docker. Run flisk up --dry-run first to see the services, commands and order without starting anything.

Settings that belong in the manifests

  • Ports and health paths, so dependents wait for ready services.
  • Environment variable names and local defaults. Real secrets stay in an uncommitted .env, and dev-only keys can be generated, as in customer API keys.
  • Start order through dependsOn, not through sleep commands in scripts.

To work on one part only, flisk up --only web starts web plus what it depends on, and start only the services you need explains more.

What not to run yet

Do not add a message broker, a search engine or a second database until a feature needs it. Every extra process costs RAM and a place for startup to fail. A Postgres table with a status column can serve as a small job queue long before you need a broker. Likewise, skip an API gateway of your own while the one process does the job.

Once this stack starts with one command, new teammates can use it on day one: see a one-command dev environment for the next step.

Questions people ask

What services does a SaaS app need locally?

Usually a database, a migration job, a cache, an API, a background worker and a web front end. Start with what you need and add more only when a feature requires it.

Can Flisk run some services as local processes and others in containers?

Not in one project yet. A project runs either as local processes or on Docker and Tilt, although local processes can start a database from an image.

How do I see what will start before running it?

Run flisk up --dry-run to list the services, their commands and the start order without starting anything.
