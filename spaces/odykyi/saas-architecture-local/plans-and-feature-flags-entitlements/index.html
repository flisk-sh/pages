How to model SaaS plans and entitlements in your database

Plan names change, pricing experiments run, and one customer gets a custom deal. Code that asks about features instead of plans survives all of it.

Do not write if (plan === "pro") in your code. Store what each plan includes as data, compute a tenant's entitlements from the plan plus any overrides, and ask a single function, can(tenant, "exports") or limit(tenant, "seats"). Then adding a plan, running a price test or giving one customer a custom limit is a data change.

Why plan names in code fail

A check on plan names spreads through the code base. When you rename "Pro" to "Team", add an annual variant, or grandfather old customers on a retired plan, you hunt through every file. A custom deal for one large customer has no plan name at all. The fix is one level of indirection: code asks about a feature, the data says which tenants have it.

A schema that works

create table plans (
  id text primary key,            -- 'free', 'team', 'business'
  name text not null,
  active boolean not null default true
);

create table plan_entitlements (
  plan_id text not null references plans(id),
  key text not null,              -- 'seats', 'exports', 'api_calls_per_day'
  int_value integer,              -- a limit, null when not numeric
  bool_value boolean,             -- a switch, null when not boolean
  primary key (plan_id, key)
);

create table subscriptions (
  tenant_id uuid primary key references tenants(id),
  plan_id text not null references plans(id),
  status text not null,           -- 'trialing', 'active', 'past_due', 'canceled'
  current_period_end timestamptz
);

create table entitlement_overrides (
  tenant_id uuid not null references tenants(id),
  key text not null,
  int_value integer,
  bool_value boolean,
  expires_at timestamptz,
  primary key (tenant_id, key)
);

Resolution is simple: the override wins when it exists and has not expired, otherwise the plan value applies, otherwise the default is "not allowed". Make the missing case deny, so a typo in a key fails closed.

export async function entitlement(tenantId, key) {
  const row = await db.one(`
    select coalesce(o.int_value, e.int_value) as int_value,
           coalesce(o.bool_value, e.bool_value) as bool_value
    from subscriptions s
    left join plan_entitlements e on e.plan_id = s.plan_id and e.key = $2
    left join entitlement_overrides o
      on o.tenant_id = s.tenant_id and o.key = $2
     and (o.expires_at is null or o.expires_at > now())
    where s.tenant_id = $1`, [tenantId, key]);
  return row ?? { int_value: null, bool_value: null };
}

Limits versus switches

A switch is a boolean: exports are on or off. A limit needs a count, and enforcing it needs a second query, such as the number of seats in use. Do the check in the same transaction as the write when it matters, or two simultaneous invites can both pass a limit of one remaining seat. For hard limits on a hot path, lock the tenant row or use a counter column with a constraint.

Subscription status is separate from the plan

A tenant on the Team plan with status past_due is still on Team. Decide what each status allows, for example read-only after cancellation, and keep that policy in one place. The status usually comes from your payment provider, and the plan sync should be idempotent so a repeated event does nothing.

Testing plans locally

Seed every plan, and create one tenant per plan, plus one with an override. A small script that moves a tenant between plans lets you click through the upgrade and downgrade screens without a payment provider. With a service named api in a Flisk stack, run it inside that service's environment:

flisk run api -- npm run seed:plans
flisk run api -- npm run set-plan -- acme team

The second command passes acme team through to your script. Put a -- before any command that has flags of its own. Your scripts, not Flisk, define what seed:plans does, and general seeding advice is in how to seed a local database.

Pitfalls

  • Caching. A per-request lookup is fine until it is not. If you cache entitlements, invalidate on plan change, and keep the cache time short enough that an upgrade feels instant.
  • Frontend checks are for display only. Hiding a button is a courtesy. Enforce on the server.
  • Do not store usage in the entitlements table. Limits are configuration, counters are state. Keep them apart, for example in Redis, as in per-tenant rate limits.
  • Too many flags. Every entitlement key is a code path you must test. Add one only when a plan really differs.

With entitlements in place, the next piece is protecting shared capacity: limit how fast one tenant can call your API.

Questions people ask

Should I store plan limits in code or in the database?

In the database, keyed by plan and feature. Code then asks about features and limits, and pricing changes become data changes without a deploy.

How do I give one customer a custom limit?

Add an override row for that tenant and key, optionally with an expiry. Resolution checks overrides first and falls back to the plan.

What should happen when a feature key is missing?

Deny by default. A missing key should fail closed so a typo never grants access.
