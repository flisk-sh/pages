How to rate limit each tenant of your API with Redis

One tenant running a runaway script should not slow everyone else. A counter in Redis per tenant and window is the smallest thing that works.

Count each tenant's requests in Redis under a key that includes the tenant and the current time window. Use INCR, set an expiry the first time, and answer with 429 and a Retry-After header when the count passes the limit. This fixed-window version is a dozen lines and good enough for most SaaS APIs.

Rate limit or quota

These are different controls and are often confused. A rate limit protects capacity: at most 100 requests a minute, so one tenant cannot starve others. A quota is a product rule: 10,000 calls a month on the Team plan. Rate limits reset in seconds or minutes and are cheap to be approximate about. Quotas affect billing and need exact counts, usually in your database. The size of each limit can come from the tenant's entitlements.

A fixed-window limiter

import { createClient } from "redis";
const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

export async function hit(tenantId, limit, windowSec = 60) {
  const window = Math.floor(Date.now() / 1000 / windowSec);
  const key = `rl:${tenantId}:${window}`;
  const [count] = await redis
    .multi()
    .incr(key)
    .expire(key, windowSec, "NX")
    .exec();
  const retryAfter = windowSec - (Math.floor(Date.now() / 1000) % windowSec);
  return { allowed: count <= limit, count, retryAfter };
}

The NX option on EXPIRE sets the expiry only when none exists yet, and needs Redis 7.0 or newer. Putting INCR and EXPIRE in one transaction avoids the classic bug where the process dies between them and leaves a key that never expires.

In your handler:

const r = await hit(tenant.id, tenant.limitPerMinute);
if (!r.allowed) {
  res.set("Retry-After", String(r.retryAfter));
  return res.status(429).json({ error: "rate_limited" });
}

Know the weakness of fixed windows

A client can send the full limit at the end of one window and again at the start of the next, so twice the limit passes in a short burst. For most APIs that is acceptable. If it is not, use a sliding window with a sorted set, or a token bucket, which is usually written as a small Lua script so the read and write happen atomically. Choose the simple version first and measure.

Details that matter

  • Which key? Limit by tenant for fairness between customers, and optionally by API key or user inside the tenant. Do both if you need to stop one user from using the whole tenant allowance.
  • Fail open or closed? If Redis is down, decide on purpose. Failing open keeps the product up and lets traffic through. Most teams fail open for rate limits and closed for billing quotas.
  • Return useful headers. Retry-After is standard. Many APIs also send the limit and remaining count in custom headers, which clients can use to back off.
  • Do not count what you rejected. Counting rejected calls is fine for a rate limit, and it punishes retry loops, which is often the point.

Run a real Redis locally

A mocked Redis will not tell you that EXPIRE ... NX needs a recent version. Run the real thing. For local-process projects, Flisk can start Redis from an image next to your code, with Docker running:

{
  "schemaVersion": 1,
  "appName": "redis",
  "appType": "bring-your-own",
  "image": "redis:7.4-alpine",
  "port": 6379,
  "healthCheck": { "command": ["redis-cli", "ping"] }
}

Your API lists "dependsOn": ["redis"] and reads REDIS_URL from its env, set to redis://localhost:6379. On the container route, flisk resource cache --type database --framework redis scaffolds a Redis resource from the same image. See how to run Redis for local development for both. This manifest keeps no volume, so counters vanish with the container, which is what you want for rate limits.

Choosing the numbers

Start from observed traffic, not guesses. Pick a limit comfortably above what a healthy client sends, and send the same value to your docs so customers can plan around it. Bursty clients such as importers deserve a higher limit on that route only, so key the counter by route group as well as tenant, for example rl:tenant:imports:window. Keep per-plan values in data, as described above, and not in constants.

Test it

Test with a tiny limit, say 3 per 60 seconds, and a loop of five requests. Assert that the fourth returns 429 with a Retry-After between 1 and 60. Also test two tenants at once to prove one does not consume the other's allowance. To test the window rollover without sleeping, make the clock injectable.

Rate limits protect capacity, but customers also need a way to call your API in the first place. The next article covers customer API keys.

Questions people ask

What is the difference between a rate limit and a quota?

A rate limit protects capacity over short windows, such as 100 requests a minute. A quota is a product rule over a billing period, such as 10,000 calls a month, and needs exact counts.

Why use EXPIRE with NX?

NX sets the expiry only if the key has none, so the window is fixed from the first request. It requires Redis 7.0 or newer.

What should my API return when the limit is hit?

Status 429 with a Retry-After header giving the seconds until the window resets.
