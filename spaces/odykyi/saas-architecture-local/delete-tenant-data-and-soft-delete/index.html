Soft delete or hard delete: removing a tenant's data in SaaS

Deleting a record is a flag. Deleting a customer means rows, files, search indexes and a billing account. They need different designs.

Use soft delete (a deleted_at column) for records users may want back, such as a project in a trash view, and hard delete for everything else. Deleting a whole tenant is a different job: mark it, wait out a grace period, then purge its data in batches from a background worker, including files and external services.

Soft delete: what it costs

A flag looks free, but it touches every query. Each read must add deleted_at is null, and one forgotten filter shows deleted data again. Foreign keys, counts and reports all need the same care. Reserve it for cases with a user-facing restore. For audit needs alone, an audit log is a better answer than keeping dead rows.

If you do use it, make filtering hard to forget. A view such as projects_active, or a default scope in your data layer, beats repeating the condition. With row level security you can put the condition in the policy itself, so deleted rows are hidden from the app role and visible only to a maintenance role.

The unique index trap

With soft delete, a plain unique (tenant_id, slug) blocks a user from creating a new project with the slug of one in the trash. Use a partial unique index that ignores deleted rows:

alter table projects add column deleted_at timestamptz;

create unique index projects_tenant_slug_active
  on projects (tenant_id, slug)
  where deleted_at is null;

Decide separately whether restoring can conflict. If a live project took the slug, restore needs a rename or a refusal.

Deleting a tenant

Cancelling an account or a data deletion request should not be a single delete from tenants. A safe sequence:

  1. Mark and lock. Set tenants.deleted_at, revoke sessions and API keys, stop billing. The customer can no longer use the product.
  2. Offer an export before the grace period ends, if you promise one.
  3. Wait. A grace period of days or weeks lets support undo a mistake. Say the length in your terms.
  4. Purge in a worker. Delete child tables first, in batches, then the tenant row. Record each step so a crash resumes instead of starting over.
  5. Reach beyond Postgres. Delete uploaded files, search index documents, cache keys and the customer record at your payment provider, or anonymize what the provider must keep.
  6. Keep a tombstone. A row stating that tenant X was deleted on date Y, with no personal data, helps with support questions and legal proof.
-- one purge step, safe to repeat
delete from tasks
 where id in (
   select id from tasks where tenant_id = $1 limit 5000
 );

Batches keep locks short and the write-ahead log manageable. Loop until the statement deletes zero rows. on delete cascade is convenient for small tables, and dangerous on huge ones, because one statement cascades into millions of rows in a single transaction.

Backups and the right to erasure

Deleted data stays in backups until they expire. Regulations such as the GDPR do not demand instant removal from backups, but they expect you to have a documented retention period, and to not restore deleted personal data into production. Write down your backup retention, and make restore procedures re-apply recent deletions. Ask a lawyer for what applies to you, this is engineering advice, not legal advice.

Practice it locally with Flisk

The purge job is the part worth rehearsing, because it only matters at scale and fails in unexpected ways. Seed a large tenant and a small one, run the purge and check that the small one is untouched and the large one is gone. If the purge is a script in your API service:

flisk run api -- npm run purge-tenant -- acme

The command runs in the service's environment, with the database URL it would have at runtime. After a bad run, reset your data: how to reset a local database covers dropping and recreating it. In a stack where the purge runs as its own worker, scaffold it with flisk resource tenant-purge --type worker, which writes a worker service.json and a bun run worker dev command.

Pitfalls

  • Hidden copies. Analytics tables, logs and exports can hold tenant data. Inventory them before you promise deletion.
  • Per-tenant databases. If you chose a database per tenant, deletion is drop database after the grace period. That is one benefit of that model, see multi-tenant database design.
  • Restore tests. If you offer undelete, test it on data with children, not just a single row.

Questions people ask

Why does soft delete break unique constraints?

A plain unique index still counts the deleted rows, so the value cannot be reused. Use a partial unique index with where deleted_at is null.

Should I use on delete cascade to remove a tenant?

For small tables it is fine. For large ones, delete child rows in batches from a worker, because one cascading statement can lock and log millions of rows.

How long should a deleted account's data be kept?

Choose a grace period that lets support undo mistakes, state it in your terms, and document how long backups are retained. Check legal requirements for your situation.
