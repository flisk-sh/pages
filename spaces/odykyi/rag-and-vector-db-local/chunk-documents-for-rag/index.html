How to chunk documents for RAG: size, overlap and splitters

Chunking decides what the retriever can find. Most weak RAG answers come from chunks that cut an idea in half or bury it in unrelated text.

Start with chunks of roughly 200 to 500 tokens, split on headings and paragraph breaks before falling back to sentences, with an overlap of about 10 to 15 percent. Keep the source, the heading path and the position with every chunk. Then test the setting against real questions, because no universal best size exists.

Why chunking matters

An embedding turns a piece of text into one vector. If the text covers three topics, the vector is a blurry average, and a question about one topic matches it poorly. If the text is a single sentence with no context, such as "It expires after 30 days", the vector has nothing to anchor it. The goal is a chunk that is one self-contained idea with enough context to be understood alone.

There is a second limit. Every embedding model has a maximum input length, and text beyond it is dropped. Chunks must fit under it with room to spare.

A good default

  1. Split on structure first. For Markdown, split on headings. For other documents, split on blank lines between paragraphs. A section is a natural unit of meaning.
  2. Merge small pieces. Combine consecutive short paragraphs until you reach the target size, so you do not store thousands of fragments.
  3. Split large pieces on sentences. If a section is longer than your maximum, cut it at sentence boundaries, never in the middle of a word or a code block.
  4. Add overlap. Repeat the last sentence or two of one chunk at the start of the next. This protects answers that straddle a boundary. Too much overlap wastes space and returns near-duplicate results.

A small splitter in TypeScript shows the shape. It splits on blank lines, then packs paragraphs up to a character budget:

export function chunk(text: string, max = 1200, overlap = 150): string[] {
  const paras = text.split(/\n\s*\n/).map((p) => p.trim()).filter(Boolean);
  const out: string[] = [];
  let cur = "";
  for (const p of paras) {
    if (cur && cur.length + p.length > max) {
      out.push(cur);
      cur = cur.slice(-overlap) + "\n\n" + p;
    } else {
      cur = cur ? cur + "\n\n" + p : p;
    }
  }
  if (cur) out.push(cur);
  return out;
}

Characters are a rough stand-in for tokens, about four characters per English token. This version does not break a single paragraph that is longer than the limit, so add a sentence splitter for that case. Libraries such as LangChain and LlamaIndex ship tested splitters if you prefer not to maintain your own.

Keep metadata with every chunk

Store, next to each vector: the source file or URL, the heading path (for example "Billing > Refunds"), the chunk number, and a content hash. The source and heading let you cite answers, the hash lets an ingestion job skip unchanged chunks on a re-run, and all of them let you filter, for example to one product version. Consider prepending the heading path to the text you embed, so a chunk about "30 days" knows it is about refunds.

Special content

  • Code. Split on functions or classes, not on a character count, and keep the file path in the metadata.
  • Tables. Keep a table in one chunk, or repeat the header row in each chunk, otherwise the numbers lose their meaning.
  • Chat logs and tickets. Group by thread, not by message.

Check it, do not guess

Pick a few settings, for example 300 and 600 tokens, index the same documents twice, and run the same list of questions against both. Count how often the right chunk appears in the top three. The method is in testing retrieval quality with a small eval set. Changing your chunking means re-indexing, so keep the ingestion repeatable, as in ingesting documents into a vector database.

Questions people ask

What chunk size is best for RAG?

There is no single best. A range of 200 to 500 tokens works for many documents. Test two or three sizes on your own questions and keep the one that retrieves the right chunk most often.

How much overlap should chunks have?

About 10 to 15 percent is a common start. More overlap adds duplicate results without much gain.

Do I need to re-embed when I change chunking?

Yes. Chunks are the unit you embed, so a new strategy means a new index. Keep ingestion repeatable so this is a command, not a project.
