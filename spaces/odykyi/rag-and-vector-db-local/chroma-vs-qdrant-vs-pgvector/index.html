Chroma vs Qdrant vs pgvector for a local RAG prototype

All three store vectors and return nearest neighbours. They differ in what else they give you, and in how much of your prototype you must rewrite when you move on.

For a local RAG prototype, pick pgvector if you already use Postgres, Qdrant if you want a dedicated server with good filtering and a dashboard, and Chroma if you want the shortest path from zero to a working demo in a Python notebook. All three are free to run on a laptop, and for a few thousand chunks all three return good results quickly.

What you are really choosing

At prototype size the search speed is not the deciding factor. An exact scan over tens of thousands of vectors takes milliseconds on any of them. The real differences are operational: how you run it, how you filter, where the data lives, and what the code looks like. Those decide how annoying the next six months are.

pgvector

pgvector is an extension to Postgres. Your chunks are rows, your embeddings are a column, and you query with SQL. That is the main benefit: you can join chunks to users, documents and permissions in one query, apply ordinary WHERE filters, use transactions, and back it up with the tools you already have. The costs are that you must run a Postgres image that includes the extension, you manage the index yourself, and tuning a very large index is on you. Setup is covered in running pgvector locally.

Qdrant

Qdrant is a standalone server with a REST and gRPC API, a dashboard and first-class payload filtering. You create a collection, upsert points with a JSON payload, and query with a filter. It is a good fit when vectors are the main workload, when you want to inspect data in a UI, or when you expect to scale the vector store separately from your relational data. The cost is another service to run and keep in sync with your main database, which is why a small project with an existing Postgres may not need it. See running Qdrant locally.

Chroma

Chroma is aimed at getting started quickly. In Python you can create a client, add documents and query them in a few lines, and it can run embedded in your process or as a server. It handles simple metadata filtering. It is popular in tutorials for that reason. Be careful with the embedded mode in a multi-service setup, because the data directory is then owned by one process. For anything shared between services, run it as a server and treat its data directory as state you persist.

Scale, honestly

For a laptop prototype you will not hit the limits of any of these. For a production system the questions change: how many vectors, how many queries per second, how often data changes, and whether you need replication. Do not pick based on a benchmark from someone else's hardware and data. If you are unsure, start with the option that adds the fewest moving parts to your current setup, measure on your own chunks, and revisit when a real number, not a guess, shows a problem.

Keep the choice reversible

Whatever you pick, hide it behind a small interface with two functions: add chunks and search by text. Keep the embedding step outside the store, so you can re-index into another engine from the same chunks. Store the original text, the source and the chunk number next to every vector, never only the vector. With that, switching costs an evening of re-ingesting, not a rewrite.

If you run these with Flisk, Qdrant has a preset (flisk resource vectors --type database --framework qdrant), and pgvector or Chroma run as bring-your-own containers with an image. Both are covered in the linked articles. To measure which one gives better answers for your data, use the method in testing retrieval quality, not a benchmark from someone else's data.

Questions people ask

Which vector database is easiest to start with locally?

Chroma is usually the quickest for a Python prototype. pgvector is the easiest if you already run Postgres, and Qdrant is one container with a dashboard.

Can I switch vector databases later?

Yes, if you keep the chunk text, source and metadata outside the vector store and keep the embedding step separate. Then you re-ingest the same chunks into the new engine.

Do I need a dedicated vector database at all?

Not for a prototype. For thousands of chunks, pgvector in your existing Postgres is often enough, and an exact scan needs no index.
