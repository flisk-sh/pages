RAG and vector databases locally

How to test RAG retrieval quality with a small eval set

You do not need a benchmark suite. Thirty real questions with known answers will tell you whether a change helped.

Test retrieval separately from generation. Write 20 to 50 questions, mark which source chunk or document should answer each, run each question against your index, and compute hit rate at k (is the right source in the top k results) and mean reciprocal rank. The result is two numbers you can compare before and after every change to chunking, the embedding model or the index.

Why test retrieval on its own

A RAG answer can be wrong for two different reasons: the retriever did not bring the right text, or the model misused text that was there. Judging only the final answer hides which one broke. Retrieval is cheap and deterministic to test: no model call, no judging, just ids. Fix retrieval first, because the model cannot use text it never sees.

Build the eval set

Keep it as a plain file in your repository, for example eval/questions.json:

[
  {"q": "How long do refunds take?", "source": "billing.md"},
  {"q": "Which ports does the gateway use?", "source": "networking.md"}
]

Rules that make it useful:

  • Use real questions. Take them from support tickets, chat logs or teammates. Questions written by the person who wrote the documents tend to reuse the document's exact words, which flatters the retriever.
  • Vary the wording. Include paraphrases and questions with no keyword overlap with the answer.
  • Mark the source, not the exact chunk, unless you want to test chunk boundaries too. Source-level labels survive a change in chunking.
  • Include a few unanswerable questions and check what the top score looks like for them. This helps you pick a similarity threshold later.

Compute the metrics

For each question, embed it, query the top k chunks, and look at the sources in rank order.

  • Hit rate at k: the share of questions where the right source appears anywhere in the top k. Use k of 3 or 5, matching how many chunks you will give the model.
  • Mean reciprocal rank (MRR): for each question, 1 divided by the rank of the first correct result (0 if absent), averaged. It rewards putting the right chunk first.
const ranks = results.map(({ sources, expected }) => {
  const i = sources.indexOf(expected);
  return i === -1 ? 0 : 1 / (i + 1);
});
const mrr = ranks.reduce((a, b) => a + b, 0) / ranks.length;
const hit5 = results.filter(({ sources, expected }) => sources.slice(0, 5).includes(expected)).length / results.length;
console.log({ hit5, mrr });

Run it as part of your test command, and print the failed questions with what was returned. Reading ten failures teaches you more than the averages do.

Compare changes fairly

Change one thing at a time: chunk size, overlap, embedding model, with or without a title prefix, exact scan or an HNSW index. Re-index into a new collection or table with a different name, run the same eval, and compare. With only 30 questions a difference of one or two questions is noise, so treat small gaps as ties and prefer the simpler setup. If you also change the model, remember vectors from different models must never share an index, see re-embedding after a model change.

Where Flisk fits

An eval like this needs a running vector store and embedding server, and a reset between runs. In a Flisk stack you can start them with flisk up and run the eval script against them, in CI too, the pattern shown in integration tests against the real stack. Nothing about the eval itself depends on Flisk, and a script pointed at any vector store works.

Pitfalls

  • Overfitting to the set. Do not tune until all 30 pass. Keep a second set you only look at occasionally.
  • Testing with the index you built the questions from. If you copy a sentence from a chunk into a question, you are testing string matching.
  • Ignoring filters. If production queries use metadata filters, apply them in the eval too.

When the retrieval numbers are good, move on to how the model uses the chunks, which is a separate test with its own questions.

Questions people ask

How many questions do I need to evaluate RAG retrieval?

Twenty to fifty real questions is enough to catch big regressions. With so few, treat a difference of one or two questions as noise.

What is hit rate at k?

The share of questions for which a correct source appears in the top k retrieved results. Choose k equal to the number of chunks you pass to the model.

Should I evaluate the final answer or only retrieval?

Both, but separately. Retrieval first, because it is cheap and deterministic, and the model cannot use text it never receives.
