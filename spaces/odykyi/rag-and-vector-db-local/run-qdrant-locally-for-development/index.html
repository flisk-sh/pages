RAG and vector databases locally

How to run Qdrant locally for development and RAG tests

Qdrant is a single container with a REST API and a web dashboard. Five curl commands are enough to know it works, and one volume keeps your data.

Run Qdrant locally with one container: docker run -p 6333:6333 -v qdrant-data:/qdrant/storage qdrant/qdrant. It serves a REST API and a dashboard on port 6333. Create a collection with the vector size of your embedding model, insert points, and query by vector. The named volume keeps your collections when the container is removed.

Start it and check that it is up

docker run -d --name qdrant \
  -p 6333:6333 \
  -v qdrant-data:/qdrant/storage \
  qdrant/qdrant:v1.12.5

curl http://localhost:6333/collections

An empty list in the response means the server is running. Open http://localhost:6333/dashboard in a browser to browse collections and run queries by hand. Port 6334 is the gRPC port, which you only need if your client library uses gRPC. Pin the image tag, as above, so a later pull does not change the storage format under you.

Create a collection, insert points and search

A collection needs a vector size and a distance metric. The size must equal the dimension your embedding model produces, for example 768 for nomic-embed-text.

curl -X PUT http://localhost:6333/collections/docs \
  -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Cosine"}}'

curl -X PUT 'http://localhost:6333/collections/docs/points?wait=true' \
  -H 'Content-Type: application/json' \
  -d '{"points": [
    {"id": 1, "vector": [0.9, 0.1, 0.0, 0.0], "payload": {"source": "a.md"}},
    {"id": 2, "vector": [0.0, 0.8, 0.2, 0.0], "payload": {"source": "b.md"}}
  ]}'

curl -X POST http://localhost:6333/collections/docs/points/query \
  -H 'Content-Type: application/json' \
  -d '{"query": [0.85, 0.15, 0.0, 0.0], "limit": 1, "with_payload": true}'

The example uses four dimensions so you can read it. The query should return point 1 with its payload. Use integer or UUID ids, and put anything you want to filter or cite later, such as the file name and chunk number, in the payload. The wait=true flag makes the write return after it is applied, which keeps scripts and tests deterministic.

The Flisk way

Flisk has a Qdrant preset. Inside a Flisk project:

flisk resource vectors --type database --framework qdrant --stack rag --yes

This writes a service.json that runs qdrant/qdrant:v1.12.5 with a TCP health check on 6333, a named data volume mounted at /qdrant/storage, and the dashboard published on 127.0.0.1:6333. Any service in the stack that lists vectors in dependsOn gets QDRANT_URL=http://vectors:6333 in its environment, so your code does not hard-code an address:

{
  "appName": "api",
  "appType": "backend",
  "stack": "rag",
  "dependsOn": ["vectors"]
}

Start the stack with flisk up rag. If something already uses host port 6333, change hostPort in the extraPorts entry of the Qdrant service.json. This preset needs Docker, because Qdrant runs as a container.

Filtering and payload indexes

Most real RAG queries are not pure similarity. You want chunks from one product, one language or one document set. Qdrant lets you add a filter to the query that conditions on payload fields:

curl -X POST http://localhost:6333/collections/docs/points/query \
  -H 'Content-Type: application/json' \
  -d '{"query": [0.85, 0.15, 0.0, 0.0], "limit": 3, "with_payload": true,
       "filter": {"must": [{"key": "source", "match": {"value": "a.md"}}]}}'

For a small development collection this works without further setup. When a collection grows, create a payload index on the fields you filter by, so filtering does not scan every point. Test filters early, because a filter that matches nothing returns an empty result, which looks like a retrieval bug.

Pitfalls

  • Wrong vector size. Qdrant refuses a point whose length differs from the collection. Create the collection from the same constant your embedding code uses.
  • Recreating collections in tests. Delete and recreate a collection at the start of a test run instead of deleting the volume, it is much faster.
  • Memory. Qdrant is light for development data, but a large import can need more RAM than a small container limit allows. Raise the container memory if it gets killed.
  • Dashboard exposure. Keep it bound to localhost. The development setup has no API key.

Questions people ask

What port does Qdrant use?

6333 for the REST API and the web dashboard, and 6334 for gRPC.

How do I keep Qdrant data after the container is removed?

Mount a named volume on /qdrant/storage. Removing the container keeps the volume, removing the volume deletes the data.

Does Qdrant need an API key locally?

Not by default. For development on localhost it is open, so keep the port bound to your machine and never expose it to a network.
