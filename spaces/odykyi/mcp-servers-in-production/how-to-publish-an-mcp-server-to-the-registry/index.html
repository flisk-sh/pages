MCP servers in production

How to publish your MCP server so people can find and install it

Package the server, write a README that clients and people can use, add a manifest and list it in the MCP Registry and other directories.

Publish the server as a package (npm or PyPI for local servers) or as a public HTTPS URL (for remote servers), write a README with a copy-paste install snippet, and then list it in the official MCP Registry and the directories your users browse. The registry's schema and CLI change over time, so follow its current documentation for the exact steps.

Choose how users get the server

  • Local, stdio: publish to npm so a client can start it with npx, or to PyPI for uvx. Users need no clone or build.
  • Remote, HTTP: give a stable HTTPS URL and document the auth method.
  • Container: publish an image if the server needs system dependencies.

A remote server is easier for users to adopt, since there is nothing to install, but you carry the hosting and security work. See stdio vs Streamable HTTP.

Write the README people actually need

People and agents read the README to decide whether to install. Include, in this order: one sentence on what the server does, the list of tools with one line each, the install snippet, required environment variables, and a safety note about what the server can change.

{
  "mcpServers": {
    "invoices": {
      "command": "npx",
      "args": ["-y", "my-invoices-mcp"],
      "env": { "INVOICES_API_KEY": "your-key-here" }
    }
  }
}

Most desktop clients accept this shape of config, but the file location differs per client, so link to each client's own docs. You can check your README with README Score, a free checker that gives a score out of 100 and lists what is missing.

List it in the registry and directories

The MCP project runs an official registry where servers publish a metadata file that names the package or remote URL, and a namespace you can prove you own, such as through a GitHub account. Read the registry's publishing guide for the current manifest format and command line tool, since it is still evolving.

Beyond the registry, look at community directories and the marketplaces of the clients you care about. Each has its own review rules. Keep the same name, description and icon everywhere.

Version and announce releases

Use semantic versions, tag releases in git, and keep a changelog that says what changed in tools, not only in code. Users care when a tool name or argument changes, so follow the process in versioning MCP tools.

Make it easy to trust

Publish the source, state what data the server sends where, and list the permissions it needs. Add a security contact. A server with open source, a clear README and a short changelog gets installed. One with none of those usually does not.

Questions people ask

Do I need to be in the registry for clients to use my server?

No. Anyone can add a server by config. The registry and directories only make it easier to discover and install.

Should I publish a remote or a local server?

Publish remote if you can host it safely, because users install nothing. Publish local if the tool needs the user's files or machine.

Try it

Run an MCP server locally before you put it in front of users.

Flisk can scaffold an mcp service next to your database and agents, so you test the whole stack on your own machine first. It is a local development tool, not a production orchestrator.

flisk resource my-tools --type mcp
