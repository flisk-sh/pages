Versioning MCP tools without breaking existing clients

Change tool names, schemas and behaviour safely: additive changes, deprecation windows, protocol version negotiation and how clients learn that the tool list changed.

Treat your tool names and input schemas as a public API. Add optional fields freely, never change the meaning of an existing field, and ship breaking changes as a new tool name while the old one keeps working during a deprecation window. Clients and cached model behaviour depend on what you published yesterday.

Know what counts as a breaking change

Safe changes are additive. Breaking changes are anything an existing caller could trip over.

  • Safe: a new optional argument, a new tool, a new field in the result, a longer description.
  • Breaking: renaming a tool, removing or renaming an argument, making an optional argument required, changing a field type, changing what a value means.

Changing a description is mostly safe but can shift model behaviour. Test it like a code change, using the approach in testing and evaluating AI agents.

Ship a breaking change as a new tool

Keep search_invoices as it is and add search_invoices_v2, or better, a clearer name for the new behaviour. Mark the old one in its description.

"description": "DEPRECATED, removal planned after the next major release. Use find_invoices instead. Finds invoices by email."

Models read this and will usually prefer the new tool. Log every call to the old tool, so you know when it is safe to remove.

Understand protocol version negotiation

MCP versions the protocol separately from your server. During initialize, the client sends the protocol version it supports, and the server answers with the version it will use. Your SDK normally handles this. Your job is to pin the SDK version, read its changelog before upgrading, and run your tests against each client you support.

Report your own server version in the serverInfo block, and use semantic versioning for it. That field is for humans and logs, not for the protocol.

Tell clients when the tool list changes

If your server's tools change at runtime, for example per user permissions, declare the tools.listChanged capability and send a notifications/tools/list_changed message. Clients that support it will call tools/list again. Clients that do not will keep the old list until they reconnect, so do not rely on it for correctness.

For a hosted server, a rolling deploy means old and new instances serve traffic at once. Keep both versions of a tool compatible during that window.

Run a deprecation checklist

  1. Add the new tool and keep the old one.
  2. Mark the old description as deprecated and name the replacement.
  3. Log calls to the old tool by client name.
  4. Announce the removal date in your changelog.
  5. Remove the old tool only when its call count is near zero.

Monitoring from logging and monitoring is what makes step 3 possible.

Questions people ask

Can I put a version in the tool name?

You can, such as search_invoices_v2, but a clearer new name is better for the model. Whatever you pick, keep the old tool working until usage drops.

How do I know which clients still call an old tool?

Log the client name from the initialize request with each tool call, then count calls per tool and client.

Run an MCP server locally before you put it in front of users.
