MCP server rate limits, timeouts and retries

Stop one runaway agent from taking your server down: per-client limits, tool timeouts, idempotency keys and safe retry rules.

Agents call tools in loops, sometimes hundreds of times a minute, so an MCP server needs a per-client rate limit, a hard timeout on every tool, and idempotency for anything that writes. Add these before you publish the URL, not after the first incident.

Limit by client, not only by IP

A single user behind a shared network address can look like many. Identify callers by token or user ID, and count requests per identity. A token bucket is easy to reason about: each client gets a bucket of N calls that refills at a steady rate.

const buckets = new Map();
function allow(id, cap = 30, refillPerSec = 0.5) {
  const now = Date.now() / 1000;
  const b = buckets.get(id) ?? { tokens: cap, t: now };
  b.tokens = Math.min(cap, b.tokens + (now - b.t) * refillPerSec);
  b.t = now;
  if (b.tokens < 1) { buckets.set(id, b); return false; }
  b.tokens -= 1; buckets.set(id, b); return true;
}

This in-memory version works for one instance. With several instances, keep counters in Redis or another shared store.

Say clearly when you limit

Return HTTP 429 with a Retry-After header for the transport, and a plain-language tool error for the model: "Rate limit reached. Wait 20 seconds before calling this tool again." A model can obey a sentence. It cannot obey a bare connection error.

Put a timeout on every tool

A tool that hangs holds a connection, a database handle and a model turn. Set a deadline on each call and return an error when it passes. Choose the number from your slowest legitimate call plus a margin, not from guesswork.

async function withTimeout(promise, ms) {
  let timer;
  const timeout = new Promise((_, rej) =>
    { timer = setTimeout(() => rej(new Error("tool timed out")), ms); });
  try { return await Promise.race([promise, timeout]); }
  finally { clearTimeout(timer); }
}

For long jobs, do not make the model wait. Start the work, return a job ID, and offer a check_job tool. See workers and queues for the pattern.

Make write tools idempotent

Clients and networks retry. If create_invoice runs twice, you have two invoices. Accept an optional idempotency_key argument, store it with the result, and return the stored result on a repeat.

Prefer operations that are naturally idempotent, such as "set status to paid" over "advance status".

Know who retries what

Retry reads freely with exponential backoff and a cap. Retry writes only when you have an idempotency key. Do not retry on validation errors, since the same input will fail again. Cap total attempts so a retry loop cannot become an outage. For transport choices that affect connection behaviour, see stdio vs Streamable HTTP.

Questions people ask

What rate limit should I start with?

Pick a number well above normal human use, such as a few calls per second per client, then watch your logs and adjust. Tighten limits for expensive or write tools.

Should the model see rate limit errors?

Yes. Return a clear message with the wait time so the agent can pause instead of retrying immediately.
