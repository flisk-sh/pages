Logging and monitoring an MCP server in production

Which fields to log for every tool call, which metrics and alerts matter, and how to keep logs useful without leaking user data or secrets.

On this page
  1. Log one line per tool call
  2. Track four numbers per tool
  3. Alert on symptoms
  4. Protect user data
  5. Trace a bad conversation

Log one structured line per tool call with the tool name, client, duration, outcome and a request ID, then chart call counts, error rate and latency per tool. That is enough to answer most production questions. Leave out secrets and raw user content unless you have a clear reason and a retention policy.

Log one line per tool call

Structured JSON lines are easy to search and aggregate. Write them to stdout for an HTTP server (for a stdio server, use stderr, since stdout carries the protocol).

{
  "ts": "2026-11-16T10:21:07Z",
  "request_id": "9f2c1a",
  "client": "claude-desktop",
  "tool": "search_invoices",
  "ms": 184,
  "ok": true,
  "result_bytes": 2310
}

Add error_kind on failures: validation, upstream, timeout, auth, rate_limit. Those categories point to different owners and different fixes.

Track four numbers per tool

  • Call count: shows which tools matter and which are dead weight.
  • Error rate: split by error_kind. A rise in validation errors often means a confusing schema.
  • Latency: the median and the 95th percentile.
  • Result size: large results cost your users tokens.

Any metrics system can hold these. If you have none yet, grepping JSON logs with jq works for a first version.

jq -r 'select(.ok==false) | .tool' server.log | sort | uniq -c | sort -rn

Alert on symptoms

Alert on things a user would feel, and give each alert an owner and a first step to try. An alert with no action attached gets muted within a week. Good candidates are an error rate above a threshold for five minutes, the 95th percentile latency doubling, or zero calls where you normally see traffic. Do not alert on every single failure. Agents will send bad input all day and that is normal.

Protect user data

Tool arguments may contain names, emails or document text. Log argument keys and sizes by default, not values. If you need values for debugging, sample a small share, redact obvious secrets, and delete after a short period. Never log the Authorization header, as covered in authentication.

Trace a bad conversation

When a user says "it called the wrong tool", you need the sequence of calls. Log a session or conversation ID if the client provides one, or issue your own and return it in the initialize response. With that, you can replay the order of calls and see where the model went wrong. For wider tooling ideas, see observability for local development, which applies the same ideas on your own machine.

Questions people ask

Should I log tool results?

Log the size and status by default. Store full results only for debugging, with sampling, redaction and a short retention period.

What is the first alert to set up?

Error rate per tool over five minutes, and a check that the server is reachable at all. Add latency alerts after you know your normal numbers.

Try it

Run an MCP server locally before you put it in front of users.

Flisk can scaffold an mcp service next to your database and agents, so you test the whole stack on your own machine first. It is a local development tool, not a production orchestrator.

flisk resource my-tools --type mcp
