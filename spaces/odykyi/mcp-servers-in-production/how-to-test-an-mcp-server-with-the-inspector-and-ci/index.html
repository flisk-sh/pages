MCP servers in production

How to test an MCP server with the Inspector and in CI

Check your server by hand with the MCP Inspector, then automate protocol checks and tool tests in CI so a refactor cannot silently break clients.

Run npx @modelcontextprotocol/inspector to open the MCP Inspector, connect it to your server, and call each tool by hand. Then write automated tests that start the server, list the tools, and call them with known input. Manual checks find design problems. Automated checks keep them from coming back.

Try the server in the Inspector

The Inspector is a developer tool from the MCP project. Point it at a local stdio server by giving it your start command:

npx @modelcontextprotocol/inspector node build/index.js

It opens a local web page where you can see the tool list, fill in arguments, run a call and read the raw JSON. For an HTTP server, choose the HTTP transport in the interface and enter the URL. Check the project's README for current options.

Look for three things: descriptions that read well, schemas that reject bad input, and errors that tell you how to fix the call.

Write protocol-level tests

Use the official client SDK to talk to your own server in a test. This checks the real protocol path, not only your functions.

import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const client = new Client({ name: "test", version: "1.0.0" });
await client.connect(new StdioClientTransport({
  command: "node", args: ["build/index.js"] }));

const { tools } = await client.listTools();
console.assert(tools.some(t => t.name === "search_invoices"));

const res = await client.callTool({
  name: "search_invoices", arguments: { email: "a@example.com" } });
console.assert(!res.isError);

Use your normal test runner for the assertions. Import paths can change between SDK releases, so check the SDK docs.

Snapshot the tool list

Save the output of listTools to a file in your repo and compare it in CI. A failing diff means a tool name, description or schema changed. That is how you catch an accidental breaking change. Update the snapshot on purpose, in the same pull request as the change.

Test with fakes for upstream services

Your tools call databases and APIs. In CI, replace them with a fake or a local container, so tests are fast and do not need real credentials. Run the test database as part of your local stack; the Flisk CLI can start an mcp service beside a database with flisk resource <name> --type mcp and flisk up, which is handy for local runs. It is a development tool and does not replace your CI setup.

Run it in CI

name: mcp-tests
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm run build
      - run: npm test

For agent behaviour tests that use a real model, see testing and evaluating AI agents. Keep those separate from your fast protocol tests.

Questions people ask

Do I need a real model to test an MCP server?

No. Protocol and tool tests call the server directly with a client SDK. Use a model only for a smaller set of end-to-end behaviour checks.

Can the Inspector test a remote server?

Yes, it can connect over HTTP transports. Add the needed authorization header in the connection settings if the server requires it.

Try it

Run an MCP server locally before you put it in front of users.

Flisk can scaffold an mcp service next to your database and agents, so you test the whole stack on your own machine first. It is a local development tool, not a production orchestrator.

flisk resource my-tools --type mcp
