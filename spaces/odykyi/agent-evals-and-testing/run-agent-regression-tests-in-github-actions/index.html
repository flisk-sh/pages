How to run agent regression tests in GitHub Actions

Run a fast eval suite on every pull request, cache what you can, keep API costs bounded, and fail the build when the score drops below your baseline.

Add a workflow that runs your eval script on pull requests, writes a score to a JSON file, and exits non-zero if the score is below the stored baseline. Keep the PR suite small and cheap, and run the larger suite on a schedule. Treat a score drop like a failing unit test.

Split fast and slow suites

Two suites cover most needs. The PR suite has 20 to 50 cases, mostly deterministic checks, and finishes in a few minutes. The nightly suite has the full set, real model calls and repeated runs. Running everything on every push is slow and costs money for little extra signal.

A minimal workflow

name: agent-evals
on:
  pull_request:
  schedule:
    - cron: "0 3 * * *"
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: python evals/run.py --suite pr --out score.json
        env:
          MODEL_API_KEY: ${{ secrets.MODEL_API_KEY }}
      - run: python evals/gate.py score.json evals/baseline.json
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: eval-report, path: score.json }

Upload the report even on failure, so a reviewer can read what broke. Secrets are not passed to workflows from forks by default, so fork PRs need a mock model path or a manual run.

The gate script

Keep the pass rule in code, not in the workflow YAML.

import json, sys
score = json.load(open(sys.argv[1]))["pass_rate"]
base = json.load(open(sys.argv[2]))["pass_rate"]
TOLERANCE = 0.02   # allow small noise
if score < base - TOLERANCE:
    print(f"FAIL: {score:.3f} below baseline {base:.3f}")
    sys.exit(1)
print(f"OK: {score:.3f} (baseline {base:.3f})")

The tolerance matters because agents are not perfectly repeatable. See why agent evals are flaky for how to set it from data.

Keep cost and secrets under control

  • Set a hard cap on cases and tokens per run, and fail loudly when it is hit.
  • Use a small, cheap model for graders where it passes your human check.
  • Use a separate API key with a spend limit for CI.
  • Cache model responses for unchanged inputs where the test is about your code, not the model.

See results over time

A single pass or fail hides trends. Store each run's score and chart it. Flisk's GEL project describes a pattern where a model proposes changes and a deterministic score decides whether to keep them, and its docs at gel.flisk.si are a useful reference for CI guards and nightly loops. Questions people ask

Should evals block merges?

Block on the cheap deterministic suite once it is stable. Keep noisier, model-graded suites as warnings or nightly reports until you trust them.

How do I stop CI evals from costing too much?

Keep the PR suite small, use cheaper models for grading where checked, cap tokens per run and use a dedicated key with a spend limit.
