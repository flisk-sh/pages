Testing and evaluating AI agents

How to monitor AI agent quality in production

Offline evals miss real-world drift. Track task success, tool errors, retries, cost and user signals, and feed failures back into your test set.

Offline evals tell you whether a change is safe. Production monitoring tells you whether the agent is working for real users today. Track task success signals, tool error rates, steps per task, cost and latency, sample conversations for review, and turn every confirmed failure into a new test case.

Pick signals that need no grader

Start with numbers you can compute without judging text.

  • Tool error rate per tool.
  • Steps per task and how often the step limit is hit.
  • Retry and give-up rate: users who rephrase the same request or abandon the session.
  • Escalation rate to a human, where you have one.
  • Cost and latency per task, with percentiles.

A sudden change in any of these after a deploy or a model update is a strong hint that something moved.

Log structured events

One event per agent run, with enough to rebuild the story.

{
  "run_id": "r_8731", "agent_version": "2026-11-12", "model": "pinned-name",
  "steps": 6, "tools": ["find_order","refund_order"], "tool_errors": 0,
  "tokens_in": 5120, "tokens_out": 480, "ms": 9400,
  "outcome": "completed", "user_feedback": null
}

Version the prompt and tool set, so you can compare before and after. Redact personal data as described in the golden dataset guide.

Collect user feedback cheaply

A thumbs up or down, a "this fixed my problem" button, or the next message ("that is wrong") all carry signal. Feedback is sparse and biased toward unhappy users, so use it to find failures, not to compute a quality percentage.

Set alerts you will act on

Pick two or three alerts: tool error rate above a threshold, step-limit hits doubling, and cost per task jumping. Route them to someone who can act. Too many alerts and the team stops reading them. Review the thresholds after a month, using the real spread you have seen.

Sample and read

Every week, read 20 runs: some random, some with errors, some with negative feedback. Reading is the cheapest way to discover failure types you did not think to test. Write down each problem in a sentence and group them. The groups tell you what to fix first.

Close the loop

For each confirmed failure, add a test case before fixing, then run the suite and ratchet the baseline as in baselines and ratchets. If you serve a model yourself, the Flisk Inference beta at inference.flisk.si offers a free model API with a daily request limit, which is a cheap way to run grader and replay experiments, though a beta service is not something to rely on for production checks. For cost signals, see cutting LLM cost and latency. Start with writing test cases if your set is empty.

Questions people ask

Do I need a monitoring product for this?

No. Structured logs and a few queries or charts are enough to start. Add a dedicated tool when volume or team size grows.

Can I grade production runs with a model?

You can, on a sample, using a checked rubric. Treat the results as a signal for review, not as ground truth.
