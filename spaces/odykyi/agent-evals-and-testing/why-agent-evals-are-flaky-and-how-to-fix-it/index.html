Why agent evals are flaky and how to fix it

The same agent passes a case today and fails tomorrow. Find the sources of noise, repeat runs, set a tolerance from data and stop chasing random failures.

Agent evals are flaky because models sample their output, tools return changing data, and graders can disagree with themselves. Reduce the noise at each source, run each case several times, and compare pass rates with a tolerance learned from your own repeated runs. Do not treat a single failed run as a regression.

Find where the noise comes from

  • Sampling: temperature above 0 gives different outputs each run. Some providers do not guarantee identical outputs even at 0.
  • Tools and data: live APIs, the clock, random IDs and search results change.
  • The grader: a model judge may rate the same answer differently twice.
  • Model updates: a hosted model alias can point to a new version without notice.

Fix the ones you control first. That is usually data and tools.

Remove avoidable randomness

Use fixed fake data, a frozen clock, and seeded random IDs. Pin the model to a specific version where the provider lets you. Set temperature low for evals, even if production uses more. Prefer deterministic graders, which cannot add noise.

FIXED_NOW = "2026-11-16T09:00:00Z"
def fake_now(): return FIXED_NOW

Run each case several times

Run every case N times, such as 5, and record how many pass. A case that passes 5 of 5 is solid, 0 of 5 is broken, and 3 of 5 is unreliable and worth a look. Two common summary numbers:

  • pass@k: at least one of k tries passes. Good when the user can retry.
  • All-k pass rate: all k tries pass. Better for tasks that must work every time, such as payments.

Choose the one that matches how your users experience failure.

Measure the noise, then set a tolerance

Run the unchanged agent 10 times against the same suite and note the lowest and highest score. The spread is your noise. Set the CI tolerance a bit above it. If the spread is 5 points, a 2 point tolerance will fail constantly and teach everyone to ignore red builds.

python evals/run.py --suite pr --runs 10 --out noise.json
python -c "import json;s=json.load(open('noise.json'))['scores'];print(min(s),max(s))"

Quarantine flaky cases

If one case flips often, move it to a separate quarantine list that reports but does not gate. Then fix its cause: a vague rule, a data dependency or a weak grader. Do not delete it silently. Use the tolerance in your gate, as in the GitHub Actions workflow, and keep the history so you can tell noise from drift.

Questions people ask

Does temperature 0 make evals deterministic?

Not always. It reduces variation, but providers can still return slightly different outputs, and tools and graders add their own noise.

How many repeats are enough?

Three to five per case is a practical start. Use more for borderline cases or when measuring the noise level of the suite.
