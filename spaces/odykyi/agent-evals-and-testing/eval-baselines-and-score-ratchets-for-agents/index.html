Testing and evaluating AI agents

Eval baselines and score ratchets for AI agents

Store a baseline score, fail the build when it drops, and raise the bar when it improves. A ratchet keeps agent quality from slowly getting worse.

A baseline is the score your agent got on a fixed suite at a known good commit. A ratchet is a rule that the score may go up but not down: when a change improves the score, the baseline is raised, and when it lowers the score beyond a tolerance, the build fails. This stops quality from decaying one small change at a time.

Why a single threshold is not enough

A fixed bar such as "pass rate above 80 percent" has two flaws. If you are at 95 percent, a drop to 81 still passes. If you are at 78 percent, everything fails until you fix it. A ratchet follows your real level: it protects what you have already earned.

Store the baseline in the repo

Keep the baseline as a small file, reviewed like code, so a change to it shows up in the pull request.

{
  "suite": "golden-v3",
  "model": "pinned-model-name",
  "pass_rate": 0.86,
  "by_tag": { "billing": 0.9, "refunds": 0.8 },
  "commit": "a1b2c3d",
  "date": "2026-11-10"
}

Record the suite version and the model, because a score is only comparable to scores from the same suite. When you change the suite, as in the golden dataset guide, set a new baseline and say so in the commit.

Add the ratchet rule

import json, sys
cur = json.load(open("score.json"))
base = json.load(open("evals/baseline.json"))
TOL = 0.02

if cur["pass_rate"] < base["pass_rate"] - TOL:
    sys.exit(f"regression: {cur['pass_rate']} vs {base['pass_rate']}")
for tag, b in base["by_tag"].items():
    if cur["by_tag"].get(tag, 0) < b - 2 * TOL:
        sys.exit(f"tag regression in {tag}")
if cur["pass_rate"] > base["pass_rate"] + TOL:
    print("improved: update evals/baseline.json in this PR")

Checking per tag matters, since an overall score can hide one area getting much worse while another improves.

Raise the bar on purpose

Do not auto-commit new baselines from CI, or noise will ratchet the bar up and cause false failures. Let a person raise the baseline in a pull request after a real improvement, with the run report attached. Set the tolerance from measured noise, as in why agent evals are flaky.

Pair it with a model-proposes loop

Ratchets work well with automated improvement. Flisk's GEL approach lets a model propose a change, such as a prompt edit, and a deterministic score decide whether to keep it, so the model never grades its own work. Read about it at gel.flisk.si or in the repo, and treat it as one example of the idea, not the only way. Your first version can be the 15-line script above.

Questions people ask

Should the baseline update automatically?

No. Let a person raise it in a reviewed pull request, so noise cannot push the bar above what the agent can reliably reach.

What if I change the model version?

Run the suite with the new model, compare to the baseline, and record a new baseline with the model name if you accept the result.
