Testing and evaluating AI agents

Build a golden dataset for agent evals from your logs

Collect real agent conversations, remove personal data, label the outcome and freeze a versioned test set that you can run on every change.

A golden dataset is a fixed set of real inputs with a known good outcome. Build it by sampling production logs, scrubbing personal data, labelling each case pass or fail with a reason, and storing the result as a versioned file in your repo. A small, well-labelled set of 50 beats a large, messy one.

Sample from real traffic

Pull conversations from your logs. Do not take only the first or most recent ones. Mix three groups: a random sample for typical use, cases users rated badly or retried, and cases where a tool errored. The last two groups are the most valuable, since they are where the agent struggles.

jq -c 'select(.rating == "down" or .tool_error == true)' logs.jsonl   | head -200 > candidates.jsonl

If you do not log conversations yet, start now, with consent and a retention limit, and in the meantime write cases by hand as in writing test cases.

Scrub personal data first

Before anything enters the repo, remove names, emails, phone numbers, addresses, keys and tokens. Replace them with stable fake values so the structure survives: the same person is always user_1. Run an automated pass and then read a sample by eye. Tools miss things. Never commit raw production data to a repository.

Label with a reason

For each case record the intended outcome and why, in a sentence. The reason is what lets you tell later whether a failure is a real regression or a bad label.

{"id":"cancel-07","input":"how do i stop being charged",
 "expected":"explains cancel path in Settings > Billing",
 "reason":"user wants cancellation steps, not a retention offer",
 "tags":["billing","from-logs"],"added":"2026-11-02"}

Have a second person label a subset. If you two disagree often, the task is ambiguous and the case needs a clearer rule.

Split and freeze

Keep a small development set you look at often, and a held-out set you rarely look at. Tune the agent against the first and confirm on the second. If you tune on everything, the score stops meaning anything. Store each version as a file such as evals/golden-v3.jsonl and never edit an old version. A change in cases is a new version.

Keep it alive

  • Add every new real failure as a case, tagged with its source.
  • Remove cases that no longer reflect the product, and say why in the commit.
  • Track the pass rate per tag, so you see which area got worse.

A set that is never updated drifts away from real use. A set that changes without a version number cannot be compared over time. Both are covered in baselines and ratchets.

Questions people ask

How big should a golden dataset be?

Start with 30 to 100 carefully labelled cases. Quality of labels matters more than size, and you can grow it as failures appear.

Can I generate test cases with a model?

Yes, as a source of candidates, but review each one by hand. Generated cases tend to be easier and more uniform than real traffic.
