How to Make Tests Fast Enough for Coding Agents

A slow test suite makes an agent either skip tests or wait. Learn to run only affected tests, split unit from integration and cut repeated setup cost.

Coding agents run tests far more often than people do, so a suite that takes ten minutes becomes the bottleneck of the whole loop. Aim for a focused test run under 30 seconds by selecting affected tests, running in parallel and removing repeated setup.

Measure before changing anything

Find where the time goes. Most test runners can print the slowest tests.

pytest --durations=15
npx vitest run --reporter=verbose
go test ./... -json | head

Usually a handful of tests, often ones that start a server or touch a real database, account for most of the time.

Run only the tests that matter

Give the agent a way to run a single file or a single test by name, and document it in AGENTS.md. Many runners can also select tests related to changed files, such as vitest --changed or jest --onlyChanged. Use these for the inner loop and keep the full suite for CI.

Split unit from integration

Mark tests that need a database, network or browser, and let the default command skip them. In pytest that is a marker; in Go it can be a build tag or a short flag.

pytest -m 'not integration'
go test -short ./...

The agent runs the quick set after every edit and the full set once at the end.

Cut repeated setup

  • Share one database container across tests and reset it with a transaction rollback or truncate, instead of rebuilding it per test.
  • Use an in-memory fake for services you do not own.
  • Run test files in parallel, and fix the tests that break when you do. Hidden shared state is the usual cause.
  • Cache dependency installs so a fresh environment does not download everything each time.

Do not trade speed for trust

A fast suite that is flaky teaches agents to retry and ignore failures. If a test fails sometimes, fix or quarantine it; see flaky tests and CI. Pair this article with one fast check command so the quick tests are the default.

A worked example

Suppose a service has 1,200 tests that take nine minutes. Profiling shows 40 tests starting a real database and taking six of those minutes. Mark those 40 as integration tests, reset one shared database between them instead of rebuilding it, and run the other 1,160 by default. The inner loop drops to about 90 seconds. Run tests in parallel across CPU cores and it may drop below 40 seconds.

The agent's loop is then: edit, run the related test file in a few seconds, repeat, and run the fast set before finishing. CI still runs everything. You gave up nothing, because the slow tests were already guarding the same code in CI. What you gained is that the agent now actually runs tests after each change instead of one big run at the end that fails in a dozen places at once. Write the two commands, quick and full, in AGENTS.md next to the reason for the split.

Questions people ask

What is a good target time for the inner-loop test run?

Under 30 seconds is a comfortable goal and under a minute is acceptable. Beyond that agents and people both start skipping the run.

Is it safe to skip integration tests locally?

Yes for the inner loop, as long as CI runs them before merge. State that split clearly in your instructions.
