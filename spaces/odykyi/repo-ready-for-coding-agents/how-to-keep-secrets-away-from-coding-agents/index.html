How to Keep Secrets Away From Coding Agents

Agents read files and run commands, so anything in the working folder is in reach. Here is how to keep credentials out of it.

Assume a coding agent can read every file in the folder it works in and every environment variable in its shell. So keep real credentials out of both: use example env files, scoped test keys and a secret store the agent has no access to.

Know what the agent can see

An agent that can run shell commands can run cat .env or env. It may also paste output into a prompt, a log or a commit message. The question is not whether the agent is trustworthy; it is whether a secret in reach can end up somewhere public.

Commit an example, never the real file

Commit .env.example with variable names and harmless placeholder values, and make sure the real file is ignored.

# .gitignore
.env
.env.*
!.env.example

The example file doubles as documentation: it tells the agent which variables the app needs without revealing any values. See env and secrets for local dev for fuller patterns.

Give the agent test credentials only

  • Use sandbox or test-mode keys from payment and email providers for local work.
  • Create a separate database user with access to a throwaway database.
  • Prefer short-lived tokens with the smallest scope you can set.
  • Never give an agent a production key to "just check something".

Block secrets from reaching git

Add a secret scanner as a pre-commit hook and again in CI, so a leaked key fails the check even if the agent did not notice. Gitleaks and similar scanners are widely used.

gitleaks detect --source . --no-banner

If a key does leak, rotate it first, then clean the history. Deleting the commit is not enough once it has been pushed. For the broader threat picture, see AI security for builders.

Tell the agent in plain words

Add a rule to AGENTS.md: never print, copy or commit values from .env or the environment. It is not a security control, since a rule can be ignored, but it prevents the casual mistake. The real controls are the ones above: no secrets in reach, scanners in the path.

What to do when you must give access

Sometimes an agent really needs to call an authenticated service, for example to test an integration. Do it with the narrowest credential you can issue. Create a dedicated test account, scope the token to one repository or one API, set a short expiry and record who holds it. Pass it as an environment variable for the single session rather than writing it to a file in the project.

Log the agent's network access where you can, and review the log after the session. If your tooling supports it, run the agent in a container with no access to your home directory, so dotfiles with cloud credentials are out of reach. After the task, revoke the token. This is more work than leaving a long-lived key in your shell profile, but a long-lived key in a profile is exactly what a confused or manipulated agent can read and leak. Rotating a short-lived token costs seconds; rotating a production key costs a bad day.

Questions people ask

Is putting secrets in an ignored file safe enough?

It keeps them out of git, but an agent in the same folder can still read them. Use test keys locally so there is nothing valuable to read.

What if an agent commits a secret?

Rotate the secret immediately, then remove it from history. Treat it as exposed from the moment it was pushed.
