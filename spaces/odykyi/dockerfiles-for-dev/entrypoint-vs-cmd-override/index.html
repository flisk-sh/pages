Docker ENTRYPOINT vs CMD: how to override them in dev

One line in a Dockerfile decides whether docker run image bash gives you a shell or passes the word bash to your app.

ENTRYPOINT sets the program a container always runs, and CMD sets its default arguments, or its whole command if there is no entrypoint. Arguments after the image name in docker run replace CMD. To replace the entrypoint you need --entrypoint. Use the exec (JSON array) form for both, so the app is process 1 and receives stop signals.

How the two combine

Dockerfiledocker run imagedocker run image extra
CMD ["node","server.js"]node server.jsextra (CMD replaced)
ENTRYPOINT ["node"] + CMD ["server.js"]node server.jsnode extra
ENTRYPOINT ["./start.sh"]./start.sh./start.sh extra

A good habit: use ENTRYPOINT for a fixed wrapper (a script that prepares the environment) and CMD for the part you might change. That makes docker run myimage node --inspect server.js or docker run myimage sh do what you expect.

Exec form and shell form

CMD ["node", "server.js"] is exec form: Docker starts node directly. CMD node server.js is shell form: Docker starts /bin/sh -c "node server.js", so the shell is process 1 and your app is its child. Two consequences:

  • Signals. docker stop sends SIGTERM to process 1. A shell may not pass it on, so your app is killed after the timeout, not stopped cleanly. Exec form avoids this.
  • Variables. Exec form does no variable expansion. CMD ["echo", "$HOME"] prints the text $HOME. If you need expansion, start a shell yourself: CMD ["sh", "-c", "echo $HOME"].

A wrapper script that does not swallow signals

#!/bin/sh
set -e
# prepare something, then hand over to the real command
cp -n .env.example .env 2&gt;/dev/null || true
exec "$@"
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["node", "server.js"]

The exec "$@" at the end replaces the script with the command, so the app becomes process 1. Without exec, the script stays as process 1 and your app never sees SIGTERM.

Overriding in Docker and Compose

docker run --rm -it --entrypoint sh myimage
docker run --rm myimage node --version
services:
  web:
    image: myimage
    entrypoint: ["/bin/sh"]
    command: ["-c", "echo hello"]

Compose has the same two keys. One trap: setting entrypoint in Compose also clears the image's default CMD, so set command too if the app needs arguments.

Overriding in a Flisk stack

For a bring-your-own resource, the container block in service.json maps to those Compose keys:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile",
  "container": {
    "entrypoint": ["docker-entrypoint.sh"],
    "command": ["node", "--inspect=0.0.0.0:9229", "server.js"]
  }
}

Both are lists of non-empty strings in exec form, so there is no shell unless you write ["sh", "-c", "..."]. Compose reads $ itself, so write $$VAR for a variable the container should expand when it starts. An empty list, "entrypoint": [], removes the image's ENTRYPOINT and keeps its CMD. Do not confuse this container.command with the top-level command field of service.json: that one runs a local process on your machine with no container. Flisk also starts containers with init enabled by default, which helps with zombie processes, but it does not replace the exec habit above.

To run a one-off command in an already running service instead, see how to run a one-off command inside a running service.

A worked example: a debug run

Say your image runs node server.js through CMD and you want an inspector for one session. You do not need to edit the Dockerfile. Run docker run --rm -p 9229:9229 myimage node --inspect=0.0.0.0:9229 server.js: the trailing words replace CMD completely, so you must repeat the program name. If the image uses an entrypoint script instead, the same trailing words become the arguments handed to exec "$@", and the script still runs first. That is the main reason to keep setup in ENTRYPOINT and the app command in CMD: you can change the second without losing the first.

To look around inside an image whose entrypoint insists on starting the app, run docker run --rm -it --entrypoint sh myimage. On a distroless or scratch image there is no shell to start, so build a debug stage that has one.

Pitfalls

  • A shell script as entrypoint without exec. Ctrl+C and docker stop take ten seconds and then kill the app.
  • Windows line endings. A script saved with CRLF fails with "no such file or directory" because the shebang line has a hidden carriage return. Save it with LF.
  • Missing execute bit. Use COPY --chmod=755 or RUN chmod +x.
  • Alpine has no bash. Use #!/bin/sh, or install bash.

Next step

Questions people ask

What is the difference between ENTRYPOINT and CMD?

ENTRYPOINT is the program the container always runs. CMD supplies default arguments, or the whole command when there is no entrypoint. Arguments to docker run replace CMD; docker run --entrypoint replaces ENTRYPOINT.

Why does docker stop take ten seconds?

Process 1 did not handle SIGTERM, often because a shell or a script without exec sits in front of the app. Use exec form and exec the final command in scripts.

How do I override the command of a Flisk bring-your-own service?

Use the container block in service.json: entrypoint and command take lists of strings in exec form. Set command too when you set entrypoint, since Compose drops the image CMD.
