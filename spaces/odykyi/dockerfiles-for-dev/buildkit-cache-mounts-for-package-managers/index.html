Docker BuildKit cache mounts for npm, pip and Go modules

Add one package and the whole install layer reruns from scratch. A cache mount keeps the downloads so only the new package is fetched.

A BuildKit cache mount is a folder that survives between builds but is not part of the image. Mount your package manager's download cache there with RUN --mount=type=cache,target=... and a change to the lockfile only downloads the new packages instead of everything. It complements layer caching: layers help when nothing changed, cache mounts help when something small did.

The gap that layer caching leaves

If you order your Dockerfile well, npm ci reruns only when package-lock.json changes. But when it does change, even by one package, that layer is invalid and the install starts from an empty cache: every package is downloaded again. On a slow connection or a large dependency tree this is the slowest part of the day. A cache mount fixes exactly this case.

Node

# syntax=docker/dockerfile:1
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
CMD ["node", "server.js"]

npm keeps its download cache in /root/.npm when you run as root. The mounted folder is not written into the layer, so the image does not grow by the size of the cache. The packages themselves still end up in node_modules, which is part of the layer.

Python

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
COPY . .

Do not pass --no-cache-dir here: it would turn off the very cache you are mounting. With uv, mount /root/.cache/uv instead.

Go

FROM golang:1.23
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/api ./cmd/api

The second mount, the Go build cache, is the bigger win: it holds compiled packages, so a rebuild recompiles only what changed.

apt packages

Debian-based images delete downloaded packages after each install by default. To use a mount you have to turn that off and make the mounts lock so parallel builds do not collide:

FROM debian:bookworm-slim
RUN rm -f /etc/apt/apt.conf.d/docker-clean
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update &amp;&amp; apt-get install -y --no-install-recommends git

Here the code block is written with the ampersands escaped for HTML, you type plain &amp;&amp; in your file.

Where Flisk fits

Flisk uses the same mechanism for the shared base images it builds for generated services: the dependency install step mounts a cache folder for Bun, so repeated installs reuse downloaded packages. For a Dockerfile you bring yourself, use the mounts above; Flisk builds it as written, and does not need any service.json setting for this.

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile"
}

The build cache is kept by Docker for the whole machine, not per project. If you prune it to free disk (docker builder prune), cache mounts go with it and the next build downloads everything once.

Checking that the cache is used

Build twice with plain progress output: docker build --progress=plain .. Change one line in your lockfile, build again, and watch the install step. With a working mount you will see packages come from the cache instead of the network, and the step finishes in a fraction of the first time. If every build is as slow as the first, check that the target path matches where your tool really stores its cache, and that the build runs as the user you expect. Run npm config get cache, pip cache dir or go env GOMODCACHE GOCACHE in a throwaway container to confirm the path for your image.

You can also give a mount an id so two different steps share one cache, for example --mount=type=cache,id=npm,target=/root/.npm in both a dev stage and a build stage. Without an id, the target path is the cache key.

Limits and pitfalls

  • BuildKit is required. It is the default builder in current Docker releases. Check that docker buildx version works.
  • The cache is local. Cache mount contents are not exported by the usual remote cache options, so a clean CI runner starts empty. Use a persistent runner cache folder or accept the cold start in CI.
  • Match the user. If the build step runs as a non-root user, the target folder must belong to that user. The mount accepts uid and gid options, and the target path moves to that user's home.
  • Do not rely on the cache being there. It can be evicted at any time. The build must still work with an empty cache.
  • Do not mount the output you ship. Anything that only exists inside a cache mount is not in the image. Install into node_modules, not into the mount.

Next step

If builds are still slow, look at what is in the build context: what to put in .dockerignore. And if the cache is the thing filling your disk, free the space without losing data.

Questions people ask

Does a cache mount make my image bigger?

No. The mounted folder is not part of any layer, so the downloaded packages in the cache do not count toward image size. Installed packages in node_modules still do.

Why is my cache mount empty in CI?

The cache lives in the local builder's storage and is not exported with the usual remote cache options. A fresh runner starts with an empty cache unless you persist the builder state.

Do I need to configure Flisk to use cache mounts?

No. Flisk builds a bring-your-own Dockerfile as written, so put the RUN --mount lines in the Dockerfile itself.
