Alpine or Debian slim for a development Docker image

Smaller is not always faster. For many Python and Node projects, a slim Debian image builds sooner and fails less.

Choose Alpine when your app is a static binary (Go, Rust) or pure JavaScript with no native modules, and choose Debian slim (-slim tags) when you depend on Python packages with compiled parts or Node modules with native addons. Alpine is smaller, but it uses musl instead of glibc, and the difference shows up as slow builds and odd crashes more often than as a saving that matters on a laptop.

What actually differs

Exact sizes change with every release, so check docker images for your own tags instead of trusting a table.

Where Alpine hurts

  • Python wheels. Many packages ship prebuilt wheels for glibc ("manylinux"). On Alpine, pip may find no matching wheel and compile from source, which needs a compiler and headers and can turn a thirty second install into several minutes. Support for musl wheels has improved, but it is still package by package.
  • Node native addons. Packages with native code (image processing, password hashing, database drivers) often have prebuilt binaries for glibc and a separate set for musl, or none. A build that works on your Mac and on Debian may fail on Alpine.
  • Behaviour differences. musl's DNS resolver and some locale and threading details differ from glibc. They are rare, but they are exactly the kind of bug that eats an afternoon.
  • Debugging tools. No bash, and curl, ps and friends are minimal or absent until you add them.

Where Alpine is fine

  • Go and Rust services built as static binaries, ideally in a multi-stage build where the final image only holds the binary.
  • Node apps whose dependencies are pure JavaScript.
  • Small infrastructure images such as nginx, where the official -alpine tag is the common choice.

A practical rule for development

  1. Start with the -slim Debian variant of your language image.
  2. Switch to Alpine only if size really matters and your dependency list builds cleanly there.
  3. Use the same family in dev and production. If production is Debian, test on Debian. A mismatch is where "works in my container" bugs come from. The multi-stage article shows how to share one base.

Note that size matters less on a laptop than people think. The layers of a base image are pulled once and shared by every image that uses it, so the base's size is paid one time. What you feel every day is build time and how often a native module breaks.

Where Flisk fits

Flisk's own shared base images for generated services are Alpine based (the lowest layer is Alpine with Bun, and the Node variant uses a Node 22 Alpine image), and they are built and cached by Flisk, so you do not choose a base for those. For a service you bring, the base is whatever your Dockerfile says, or you can skip building altogether and point at an existing image:

flisk resource api --type bring-your-own --stack app --image python:3.12-slim --port 4000 --yes

That writes a service.json with an image instead of a dockerfile. You will normally still want your own Dockerfile, because a bare language image has no application code. If you use Alpine, remember it has no curl by default: Flisk routes to your service and probes healthCheckPath itself, but a HEALTHCHECK in your own Dockerfile still needs a tool that exists. See writing a HEALTHCHECK that works.

Pitfalls

  • Do not mix. Copying a binary compiled on glibc into an Alpine image fails with "not found", because the dynamic loader is missing. Build and run on the same family, or build a static binary.
  • Do not use latest. Pin a version tag so the base does not move under you. A digest pins it exactly.
  • Image size is not the same as attack surface. A smaller image has fewer packages, but patching and scanning habits matter more than the base.
  • Distroless images are good for production but have no shell, which makes them awkward for a dev stage.

Next step

Whichever base you choose, make it fast to rebuild: layer caching and cache mounts matter more than the base image size.

Questions people ask

Is Alpine faster than Debian slim?

Not necessarily. Alpine images are smaller to pull, but builds can be slower when packages must compile because no musl binary exists. For Python and native Node modules, Debian slim is often faster to build.

Why does pip compile packages on Alpine?

Many Python wheels target glibc. On musl, pip may find no prebuilt wheel and builds from source, which needs a compiler and takes longer.

Can Flisk run an image directly without a Dockerfile?

Yes, a bring-your-own resource can take an image name with the image option instead of a dockerfile, for example python:3.12-slim, although an app normally needs its own Dockerfile to include its code.
