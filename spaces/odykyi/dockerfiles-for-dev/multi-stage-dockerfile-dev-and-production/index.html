Dockerfiles for development

Multi-stage Dockerfile with separate dev and production stages

Production images should not carry compilers or test tools, and dev images should not run a minified build. Stages let one file serve both.

A multi-stage Dockerfile has several FROM lines, each starting a named stage. You can build up to any stage with docker build --target &lt;name&gt;, so one file can produce a development image with watchers and dev tools, and a small production image that only contains what runs. Without --target, Docker builds the last stage.

The shape of the file

Share the common work in a base stage, then branch:

# syntax=docker/dockerfile:1
FROM node:22-alpine AS base
WORKDIR /app
COPY package.json package-lock.json ./

FROM base AS dev
RUN npm ci
COPY . .
CMD ["npm", "run", "dev"]

FROM base AS build
RUN npm ci
COPY . .
RUN npm run build

FROM base AS production
ENV NODE_ENV=production
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]

The build stage has the compiler and dev dependencies. The production stage copies only the compiled output out of it with COPY --from=build, so the final image has no TypeScript, no test runner and no source. Because production is last, a plain docker build . produces it.

Build the stage you want

docker build --target dev -t myapp:dev .
docker build -t myapp:prod .

In Docker Compose, pick the stage in the service's build block:

services:
  web:
    build:
      context: .
      target: dev
    volumes:
      - ./src:/app/src

Stages that nothing depends on are skipped by BuildKit, so building dev does not run the build stage at all. The older classic builder ran stages in order, which is one reason to keep BuildKit on (it is the default in current Docker releases).

Where Flisk fits

For a service you bring yourself, Flisk builds your Dockerfile and passes no build target, so Docker builds the last stage. service.json has no field to choose a stage. That leaves two honest options.

  • Put the stage you want locally last. If the file is only used for local work, end it with the dev stage.
  • Keep two files. Name the dev one Dockerfile.dev and point to it, leaving Dockerfile for production and CI:
{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile.dev"
}

If your Dockerfile lives higher in the repo, set buildContext to a path relative to the service folder. dockerfile is then relative to that context, as it is in Compose. If you let Flisk generate a service instead, it writes its own layered Dockerfile and you do not maintain stages at all. A Bun backend whose dev script uses --watch gets a development image so edits restart the app.

A compiled-language example

Stages matter most for compiled languages, where the build tools are large and the output is a single file. A Go service can build in one stage and run in a tiny one:

FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12 AS production
COPY --from=build /out/api /api
USER nonroot
ENTRYPOINT ["/api"]

The Go toolchain stays in the build stage and never reaches the final image. For development you would add a separate stage with a file watcher on top of golang, since a distroless image has no shell to debug in. The principle is the same as with Node: a stage for each job, and a last stage that holds only what must run.

Pitfalls

  • Stage names are case-insensitive and must be unique. A typo in --target fails with "target stage could not be found".
  • Do not install dev dependencies in the final stage. It is the most common reason a production image is hundreds of megabytes larger than it needs to be.
  • Keep the dev stage close to production. Same base image and same OS packages, otherwise a bug that only appears in production is hard to reproduce. The Alpine or Debian slim choice is one place this drifts.
  • Do not put secrets in an early stage and assume they vanish. A stage you copy from can still be inspected in the build cache and, if you push it, in the registry.
  • Layer order still matters inside each stage. See layer caching.

Next step

A dev stage is only useful if edits reach the container without a rebuild. Bind mounting your source is how the dev stage above picks up changes.

Questions people ask

What happens if I run docker build without --target?

Docker builds the last stage in the Dockerfile. Order the stages so the one you want by default is last, usually production.

Can Flisk select a build stage for my own Dockerfile?

No. service.json has no target field for a bring-your-own resource, and Flisk passes no target, so the last stage is built. Use a separate dockerfile path for a dev variant.

Does the dev stage need to be a separate file?

No. Stages in one file are fine for Docker and Compose. A separate file is only needed when a tool, such as a Flisk bring-your-own resource, cannot choose a stage.
