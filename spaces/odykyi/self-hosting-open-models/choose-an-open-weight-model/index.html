Open models and self-hosted inference

How to choose an open-weight model for your project

Size, task fit, context length, licence and tooling support: a practical way to shortlist open models and avoid benchmark traps.

Pick an open model by your task, your hardware and its licence, not by leaderboard rank. Shortlist two or three that fit in memory, test them on your own prompts, and read the licence before you ship anything built on them.

Start from the constraints

  1. Hardware. What fits? See VRAM.
  2. Task. Chat, coding, extraction, embeddings, vision?
  3. Context length. How long are your inputs?
  4. Licence. Can you use it commercially?
  5. Tool support. Does your server run it, and with the right chat template?

Write these five answers down before you browse model lists. Without them, a leaderboard will pull you toward the biggest model, which is rarely what a small project needs.

Read the licence

"Open weights" does not always mean open source. Some licences are permissive (such as Apache 2.0 or MIT). Others add conditions: usage limits, acceptable-use rules, attribution, or restrictions for very large companies. Read the licence file on the model's page. If your use is commercial or you redistribute the model, check it carefully, and ask a lawyer if the stakes are high.

Keep a copy of the licence text with your project, along with the model name and the date you downloaded it. If terms change later, you will know which ones applied to what you shipped.

Treat benchmarks with care

Public benchmarks measure public tasks. Models can be tuned toward them, and the tasks may not look like yours. Use them to build a shortlist, not to pick the winner. Your own set of 30 to 100 real prompts with expected results tells you more.

Match model type to task

  • Instruct or chat variants for assistants. Base models are for further training.
  • Coding models for code completion and review.
  • Small models for classification and extraction, where speed and cost matter more than depth.
  • Embedding models for search. See RAG and vector databases locally.

Pilot before committing

Try the shortlist through Ollama or a hosted endpoint first, since downloading many large files is slow. Then follow test an open model before you switch. For more on local options, see local LLM models.

Plan for replacing the model. New open models appear often, and a project that hard-codes one name and one prompt format is stuck. Keep the model name in configuration and keep your test set, so a swap takes an afternoon.

To try an open model with no download at all, Flisk Inference offers a free open-beta API with Flisk Wolf, a coding-focused open model. You sign in with GitHub and there is a daily request limit, so it suits trials, not production load.

Questions people ask

Is a bigger model always better?

Usually more capable, but slower and more expensive. For narrow tasks a small model, well prompted, is often enough.

Can I use any open-weight model commercially?

Not automatically. Each has its own licence. Read it for commercial use, redistribution and usage restrictions before you build on it.
