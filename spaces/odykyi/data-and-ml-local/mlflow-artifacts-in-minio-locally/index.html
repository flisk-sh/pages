How to store MLflow artifacts in MinIO on your laptop

By default, MLflow artifacts sit in the same volume as its database. Moving them to an S3-compatible store looks like production and keeps the tracking volume small.

To keep MLflow artifacts in MinIO, run MinIO as an S3-compatible server, create a bucket, give the MLflow server the S3 endpoint and credentials through environment variables, and start it with an artifacts destination such as s3://mlflow. Clients that log runs only talk to the tracking server, which stores the files in the bucket for them. The common failure is a missing endpoint variable, so the server quietly looks for real AWS.

Why bother with an S3 store locally

Run metadata (parameters, metrics) is small. Artifacts are not: model weights, plots, datasets. Keeping them in the tracking volume works, but it hides one thing you will meet in production: code that reads and writes S3 URIs, with an endpoint, a key and a bucket. Running that locally against MinIO catches the configuration mistakes early, at no cost.

The plain way

You need three things. MinIO with a bucket, environment variables for the S3 client library (boto3), and the server flags:

export MLFLOW_S3_ENDPOINT_URL=http://127.0.0.1:9000
export AWS_ACCESS_KEY_ID=minioadmin
export AWS_SECRET_ACCESS_KEY=minioadmin

mlflow server --host 127.0.0.1 --port 5000 \
  --backend-store-uri sqlite:///mlflow.db \
  --artifacts-destination s3://mlflow \
  --serve-artifacts

The bucket must exist first: MinIO does not create buckets on demand. pip install boto3 is required in the server's environment, because MLflow uses it for s3:// paths. With --serve-artifacts the client never needs S3 credentials. Only the tracking server does.

The Flisk way

Flisk has presets for both pieces. Create them in one stack:

flisk resource store --type database --framework minio --stack ml --yes
flisk resource tracking --type database --framework mlflow --stack ml --yes

Then tell the tracking server to depend on the store. Open tracking/service.json and add:

"dependsOn": ["store"]

That is the whole configuration. The MinIO resource declares provides with MINIO_ENDPOINT, AWS_ENDPOINT_URL_S3 (both http://store:9000), AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY. A service that lists it in dependsOn receives them, and the MLflow preset's start script checks for AWS_ENDPOINT_URL_S3:

  • if it is set, the script installs boto3 (about 4 seconds on every start), waits until MinIO answers, creates the bucket mlflow if it is missing, and starts the server with --artifacts-destination s3://mlflow;
  • if it is not set, artifacts stay in the data volume at /data/artifacts.

So the dependency is the switch. Remove store from dependsOn and you are back to local files.

flisk config verify
flisk up ml
flisk status

The MinIO console is published on 127.0.0.1:9001 only, with the development login minioadmin / minioadmin. These values are for local use: the S3 port is reachable on the stack's Docker network, not from outside.

Check that artifacts really land in the bucket

Log a small file from a script on your host, with the tracking URI set to the published port:

import mlflow

mlflow.set_tracking_uri("http://127.0.0.1:5000")
mlflow.set_experiment("s3-check")
with mlflow.start_run():
    with open("hello.txt", "w") as f:
        f.write("hello")
    mlflow.log_artifact("hello.txt")

Open the MinIO console, go to the mlflow bucket and look for an object under the run. If the bucket is empty and the artifact is in the tracking volume instead, the dependency is missing or the tracking server started before it was added: run flisk restart tracking.

Pitfalls

  • Missing endpoint. Without the endpoint variable, boto3 talks to AWS and fails on credentials. Always set MLFLOW_S3_ENDPOINT_URL (plain MLflow) or depend on the MinIO resource (Flisk).
  • Old artifacts do not move. Runs logged before the change keep their original artifact location. Switching the destination affects new runs.
  • The MinIO image. The upstream minio/minio image is no longer published, so the Flisk preset uses a community fork pinned to a release, with the same S3 API. Pass --image to use another build.
  • Do not reuse these credentials. They are fixed development values. Never copy them to a shared environment.

For the first part of the setup, see running an MLflow tracking server locally. If you want the stored model to be served as an API, continue with serving a scikit-learn model with FastAPI.

Questions people ask

Does the training script need S3 credentials?

Not when the tracking server is started with serve-artifacts. The client uploads artifacts to the server over HTTP, and the server writes to the bucket with its own credentials.

Does MinIO create the bucket for MLflow?

No. MinIO does not create buckets automatically. You create the bucket first, or use a start script that creates it, as the Flisk MLflow preset does.

Do old runs move to the new artifact store?

No. Each run keeps the artifact location it was created with. Only new runs use the new destination.
