DuckDB and Parquet: local analytics without a server

For files on your disk, an embedded database beats a server. DuckDB reads Parquet directly, runs in your Python process and costs no setup.

DuckDB is an embedded analytical database: install a package, open a file or an in-memory database, and run SQL over CSV and Parquet files directly. There is no server, no port and no container. For a dataset that fits on your laptop, up to tens of gigabytes of files, it is often faster to set up and to run than a database service.

Query files where they are

pip install duckdb
import duckdb

duckdb.sql('''
    SELECT user_id, count(*) AS events, sum(amount) AS total
    FROM read_csv('events.csv')
    GROUP BY user_id
    ORDER BY total DESC
    LIMIT 10
''').show()

The same works from the command line client, or in a notebook, and read_parquet('data/*.parquet') accepts a glob over many files. DuckDB reads only the columns the query uses and, for Parquet, can skip row groups using the file's statistics, so selecting two columns out of fifty reads a fraction of the bytes.

Convert CSV to Parquet once

CSV is text: every query parses it again, and it has no types. Convert once and query the result:

COPY (SELECT * FROM read_csv('events.csv'))
TO 'events.parquet' (FORMAT parquet, COMPRESSION zstd);

Check the inferred types before you rely on them: DESCRIBE SELECT * FROM read_csv('events.csv') shows each column. If a column of IDs becomes a number and loses leading zeros, force it with read_csv('events.csv', types={'zip': 'VARCHAR'}). For data that grows, write it partitioned by a column you filter on:

COPY events TO 'lake/events' (FORMAT parquet, PARTITION_BY (day));

That creates one folder per day, so a query with WHERE day = '2026-11-01' opens one folder.

Join files with your running database

DuckDB can attach a Postgres database and join it with files, without copying data first:

INSTALL postgres; LOAD postgres;
ATTACH 'host=127.0.0.1 port=5432 dbname=app user=app password=secret' AS pg (TYPE postgres, READ_ONLY);

SELECT o.id, e.total
FROM pg.public.orders o
JOIN read_parquet('events.parquet') e ON e.order_id = o.id;

Use the published port of your local database for this, see connecting to a local database from your machine. Attach it as READ_ONLY so an exploratory query cannot change anything.

Where this fits in a Flisk project

DuckDB is a library, so there is nothing for Flisk to run. It lives in the notebook, script or dashboard that uses it, and those can be services in your stack. A Python service using it only needs duckdb in its dependencies and the data folder mounted. If you want a shared, always-on analytics store that several services query, that is a server, and ClickHouse is the next step.

Use it from a script or a test

Because DuckDB runs in your process, it is also handy in tests and one-off scripts. A test can create an in-memory database, load a small fixture file and assert on the result of a query, with nothing to start and nothing to clean up:

import duckdb

con = duckdb.connect()  # in memory
con.execute("CREATE TABLE t AS SELECT * FROM read_parquet('tests/fixtures/events.parquet')")
assert con.execute("SELECT count(*) FROM t").fetchone()[0] == 1000
df = con.execute("SELECT name, count(*) c FROM t GROUP BY name").df()

The .df() call returns a pandas DataFrame, so you can move between SQL and Python in one cell. To keep results between runs, open a file instead: duckdb.connect('analysis.duckdb'). That file is a build artifact like any other. Add it to .gitignore and rebuild it from the source files when you need it.

Pitfalls and limits

  • One writer. A DuckDB database file allows one process to write at a time. Several processes can read a file only when none of them writes. For shared access use Parquet files plus in-memory connections, or a server database.
  • Memory limit. Large sorts and joins spill to disk, but set SET memory_limit='4GB' if it competes with other containers.
  • Parquet is not editable. You write new files rather than update rows. Treat a Parquet folder as an append-only log.
  • Not a transactional store. Use Postgres for application data and DuckDB for analysis of copies of it.
  • Big files in Git. Keep data files out of the repository. A small sample is fine, anything large is not.

To explore these queries interactively, use a notebook, and keep it readable in diffs with keeping Jupyter notebooks clean in Git. For a notebook next to your database, see JupyterLab next to your local database.

Questions people ask

Do I need to install a server to use DuckDB?

No. DuckDB runs inside your process. Install the package and open a file or an in-memory database.

Why convert CSV to Parquet?

Parquet stores typed columns in compressed form, so queries read less data and skip parsing. A converted file is usually much smaller and faster to query.

Can two processes write to one DuckDB file?

No. One process can write at a time. Use Parquet files or a server database when several writers are needed.
