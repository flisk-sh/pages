How to run JupyterLab next to your app's local database

Notebooks are the quickest way to look at your own data. The setup mistakes are an open server, lost notebooks and a database address that only works from your host.

Run JupyterLab as one more service in your local stack: a container from the Jupyter Docker Stacks image, a bind mount so notebooks live in your repository, a token you choose, and the database address passed in as an environment variable. Then the notebook reaches the same Postgres your API uses, by its container name, and nothing is exposed beyond your own machine.

Why not just run jupyter on the host

You can: pip install jupyterlab and jupyter lab start a server on 127.0.0.1:8888 and print a URL with a token. For a quick look at a CSV that is the right answer. It gets awkward when the data is in a database that runs in a container. You then need the published port, a connection string that differs from the one your services use, and a Python environment that matches the project. A notebook in the stack shares the services' network and environment, so DATABASE_URL means the same thing everywhere.

The plain Docker way

The Jupyter Docker Stacks publish images such as quay.io/jupyter/scipy-notebook. A minimal run:

docker run --rm -p 127.0.0.1:8888:8888 \
  -e JUPYTER_TOKEN=change-me \
  -v "$PWD/notebooks:/home/jovyan/work" \
  quay.io/jupyter/scipy-notebook:latest

Three details matter. Publish on 127.0.0.1, not on all interfaces, because a notebook server runs arbitrary code. Set the token yourself, so the URL does not change on every start. And mount a folder at /home/jovyan/work, because everything else in the container is thrown away when it is recreated. Pin a dated tag from the image's tag list instead of latest once it works, so a rebuild next month does not change your Python.

The Flisk way

Create a bring-your-own resource for the image, then edit its service.json:

flisk resource lab --type bring-your-own --image quay.io/jupyter/scipy-notebook:latest --stack ml --yes
{
  "appName": "lab",
  "appType": "bring-your-own",
  "stack": "ml",
  "port": 8888,
  "image": "quay.io/jupyter/scipy-notebook:latest",
  "webUi": true,
  "healthCheckPath": "/api",
  "dependsOn": ["postgres"],
  "secrets": { "required": ["JUPYTER_TOKEN"] },
  "volumes": [
    { "source": "./notebooks", "target": "/home/jovyan/work" }
  ]
}

What each field does:

  • port is the port the container listens on. The CLI flag --port only accepts 4000 to 5999 for this type, so set 8888 in the file.
  • webUi: true routes the app on its own host name, lab.<project>.localhost, with no path prefix. Without it a bring-your-own resource is an API under /api/<name>, and JupyterLab, which serves pages from /, would not work under that prefix. flisk status prints the real URL.
  • healthCheckPath is /api, which Jupyter answers without a login and which the official images use for their own health check.
  • dependsOn: ["postgres"] gives the container DATABASE_URL. Flisk adds it only when dependsOn names postgres or a database resource, so a plain container does not get a database address by accident.
  • secrets.required reads JUPYTER_TOKEN from the project's git-ignored .env. Put JUPYTER_TOKEN=some-long-random-value there and never in service.json.
  • volumes with a ./ path is a bind mount relative to the service folder, so notebooks are plain files in your repository.
flisk config verify
flisk up ml
flisk status

Open the printed URL and log in with the token. This resource is a container, so the project needs Docker. If you only need a notebook against a database on your host, plain jupyter lab is simpler.

Read data from the database

In a notebook cell, take the address from the environment, as your services do:

import os
import pandas as pd
from sqlalchemy import create_engine

engine = create_engine(os.environ["DATABASE_URL"])
df = pd.read_sql("select id, created_at from orders limit 100", engine)
df.head()

The image may not include the Postgres driver. Install it in a small Dockerfile based on the image (RUN pip install psycopg[binary]) and use dockerfile in service.json instead of image. A pip install typed into a notebook works, but it is lost when the container is recreated. For a read-only look, create a database role that can only select, so a mistaken cell cannot change your data. See connecting to a local database from your machine for the host side.

Pitfalls

  • Files owned by another user. The image runs as user jovyan (uid 1000). On Linux, a notebooks folder owned by a different uid can be read-only inside the container. Change the folder's owner or permissions.
  • Outputs in Git. A notebook stores its outputs, so a data preview can end up in a commit. Read keeping Jupyter notebooks clean in Git before you commit the first one.
  • Do not share the port. A notebook is a remote shell with a login. Leave it on loopback.

When an experiment in a notebook is worth keeping, log it to a tracking server, see running MLflow locally.

Questions people ask

Why can't my notebook container connect to localhost:5432?

Inside a container, localhost is the container itself. Use the database service name on the Docker network, which is what a DATABASE_URL passed to the container contains.

Where are my notebooks saved in Docker?

Only in the folders you mount from the host. Mount a host folder at the image's work directory, otherwise the files are deleted when the container is recreated.

How do I stop the token changing on every start?

Set the JUPYTER_TOKEN environment variable yourself instead of letting Jupyter generate a random one.
