An AI engineer portfolio that gets interviews: what to show

Hiring managers want evidence you can ship. Here is what to put in three projects, how to write them up, and how to put them on a public link.

A good AI engineering portfolio is three small projects, each with a public repo, a clear README, a live link or a recorded run, and numbers showing it works. Show the problem, your decisions, the measurements and the failures.

What reviewers look for

They have minutes. They want to see that you can scope a problem, build something that runs, test it, and explain trade-offs. A repo that clones and runs in one command beats a clever idea that does not start. Evidence matters more than complexity: an eval score, a before and after cost, a list of failure cases you found.

Three projects, three different skills

  1. A retrieval or data project with an eval. See learn RAG by building.
  2. An agent with tools and sensible permissions. See your first agent.
  3. An end-to-end product with a real user, even if it is one friend, deployed at a public address.

Write the README like a case study

Use this outline:

  • One sentence: who it is for and what it does.
  • How to run it, in copyable commands.
  • What you built and why: the two or three decisions that mattered.
  • How you tested it, with the numbers.
  • What went wrong and what you would do next.

Honest failure notes build more trust than polish. You can check the structure of a README with README Score, which gives a score out of 100 and a fix for each missing section, with no AI involved.

Put it online

A live link lets a reviewer try it in seconds. For a static page or a Markdown write-up, Pages publishes a file to a free public link, so do not put anything private in it:

npx -y @flisk-sh/pages publish page.html --wait

For small apps with a server, see publishing and hosting small apps. Record a two-minute screen capture as a fallback.

Show real work too

Open pull requests to open-source tools you use, even small ones: a docs fix, a failing test, a clearer error message. Maintainers merge these, and a merged PR is a verified signal. Open jobs boards where any agent or person can claim a task, such as jobs.flisk.si, are another place to get a first piece of real work; payment there is not live, so see it as practice. Keep your project list current, and link each project from one index page so a reviewer finds all three in one click.

Finally, put the date and the model name you used in each README. AI projects age fast, and a reviewer reads a note like "built with a small open model, evaluated on 25 cases" as a sign of care, not as a weakness.

Questions people ask

How many projects do I need?

Three finished, well-explained projects are enough. More unfinished ones hurt.

Should I include a model I trained?

Only if the training is the point of the project. Most AI engineering roles value shipping features on existing models.
