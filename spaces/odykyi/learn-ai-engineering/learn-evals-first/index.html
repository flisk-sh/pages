Learn evals first: how to know if your AI feature got better

Evals are tests for AI behaviour. Learn to write ten cases, a grader and a baseline before you tune anything, and you will improve faster than people who guess.

An eval is a list of inputs with a way to score the output. Write ten to thirty cases that reflect real use, run them against your current prompt and model, record the score, and only then change anything. Without that baseline, every change is a guess.

Start with ten real cases

Take real inputs from your own use, or from users. Write the expected result next to each, or a rule it must satisfy. Include hard cases and a few that should be refused. Keep them in a plain file in the repo:

{"id": "c1", "input": "Refund order 1042", "expect": {"intent": "refund", "order_id": "1042"}}
{"id": "c2", "input": "hi", "expect": {"intent": "other", "order_id": null}}

Grade with code when you can

Exact match, JSON schema checks, regex and field comparisons are cheap, repeatable and free of opinion. Use them first.

def grade(case, out):
    return out.get("intent") == case["expect"]["intent"] and \
           out.get("order_id") == case["expect"]["order_id"]

results = [grade(c, run(c["input"])) for c in cases]
print(f"{sum(results)}/{len(results)} passed")

When you need a model as grader

For free-text answers, a second model can judge against a rubric. Use it carefully: it favours long answers, its own style and confident wording, and it can be wrong. Write the rubric as yes or no questions, such as "does the answer name the correct file", because scores from one to ten drift between runs. Keep the rubric short and specific, use a different model from the one being tested, check its verdicts by hand on a sample, and never let it be the only signal. The rule "a model proposes, a score decides" works only if the score is trustworthy. See testing and evaluating AI agents for the full treatment.

Use the numbers

Run the eval before and after every change to the prompt, the model or the retrieval. Keep a table: version, score, date, cost. Change one thing at a time. If a change raises the score on your cases but you suspect overfitting, add new cases you have not tuned on. Put the eval in CI so a regression fails a pull request, as described in CI guards and AI code review.

Common beginner mistakes

  • Cases that are too easy, so everything passes.
  • Testing with the same examples you put in the prompt.
  • Only measuring accuracy and ignoring cost and latency.
  • Trusting one run. Models vary, so run several times for noisy tasks and report the spread.
  • Changing the cases to make the score go up. Version the case file and review changes to it like code.

Next, apply this to something you built, such as the RAG app.

Questions people ask

How many eval cases are enough to start?

Ten to thirty real cases is enough to catch big regressions. Add a new case every time you find a bug.

Can I use a model to write the cases?

It can draft them, but review each one by hand, since generated cases tend to be too easy and too similar.
