How to host a static site on GitHub Pages

Publish a built static site from a GitHub repository using a Pages workflow, with the settings, the base-path trap and how to see a failed deploy.

In the repository settings, open Pages and set the source to GitHub Actions, then add a workflow that uploads your site folder as a Pages artifact and deploys it. Your site appears at https://USER.github.io/REPO/ after the workflow finishes.

Set the source

In the repository go to Settings, then Pages, and choose GitHub Actions as the source. Without this the workflow below will build but never publish.

The workflow

Create .github/workflows/pages.yml. This version publishes the site folder as is. Replace the folder if you have a build step.

name: pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
concurrency:
  group: pages
  cancel-in-progress: true
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site
      - id: deployment
        uses: actions/deploy-pages@v4

Check the Marketplace for the latest major versions of these actions when you copy this.

If your site has a build step

Add steps before the upload that install and build, then point path at the output folder, such as dist.

      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci && npm run build

The base path trap

A project site lives under /REPO/, not at the domain root. A link to /style.css then points at the wrong place and the page loads unstyled. Fix it with relative links, or set your framework's base option, for example base: "/REPO/" in Vite. A user site (a repo named USER.github.io) or a custom domain does not have this problem.

Check it from the command line

After the workflow finishes, confirm the site responds and returns the content you expect, rather than trusting a green tick.

curl -sI https://USER.github.io/REPO/ | head -n 5
curl -s https://USER.github.io/REPO/ | grep -i "<title>"

A 404 means the artifact path or the Pages source setting is wrong. A 200 with old content usually means a cache, so try again in a minute or add a query string such as ?v=2 to bypass it while testing.

Keep the workflow file small and pinned to action versions you have tested. When an action releases a new major version, bump it in a pull request and check that the deploy still works before merging.

Debugging a failed deploy

  • Open the Actions tab and read the failed step. Most failures are a wrong path or missing permissions.
  • If the job is green but the site is a 404, confirm the source is set to GitHub Actions and that index.html is at the root of the artifact.
  • Changes can take a minute to appear. Hard refresh before assuming it failed.

Questions people ask

Is GitHub Pages free for private repositories?

Pages from private repositories needs a paid GitHub plan. Public repositories can use it on the free plan. Check GitHub's current plan page.

Can GitHub Pages run a backend?

No. It serves static files only. For an API use a Worker or another service and call it from your page.

Try it

Put one page online in a minute.

Pages publishes an HTML or Markdown file to a free public link. It is public, so do not use it for anything private.

npx -y @flisk-sh/pages publish page.html --wait
