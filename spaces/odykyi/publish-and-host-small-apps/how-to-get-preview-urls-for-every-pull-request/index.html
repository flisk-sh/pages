How to get preview URLs for every pull request

Give each pull request its own live URL so reviewers can click instead of checkout. Covers Cloudflare Pages previews and a manual Actions approach.

Connect your repository to a host that builds previews, such as Cloudflare Pages or Netlify, and every pull request gets its own URL automatically. GitHub Pages has no built-in previews, so there you deploy to a per-branch folder yourself.

The easy way: use a host with previews

In Cloudflare Pages, connect the repo, set the build command and output folder, and save. Each branch and pull request is built and given a URL of the form BRANCH.my-site.pages.dev. The host usually comments on the pull request with the link. Netlify and Vercel behave the same way.

Previews from the CLI

If you build in your own CI, deploy from the workflow and pass the branch name. A non-production branch becomes a preview.

name: preview
on: pull_request
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci && npm run build
      - run: npx wrangler pages deploy dist --project-name my-site --branch ${{ github.head_ref }}
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}

Create the API token with only the permission to edit Pages, and store both values as repository secrets.

Pull requests from forks

Workflows triggered by forks do not receive your secrets, which is a deliberate protection. Do not work around it by switching to pull_request_target and checking out the fork's code with secrets available. That is a well-known way to leak credentials. Let maintainers deploy previews for forks on request.

Keep previews out of search results

Preview sites are public. Add a header so crawlers skip them, and never put real data in them.

# _headers
https://*.my-site.pages.dev/*
  X-Robots-Tag: noindex

Check the host's docs for how its preview domain interacts with this rule.

What reviewers should check on a preview

A preview is only useful if reviewers know what to look for. Add a line to your pull request template: open the preview, check the changed page on a phone width, and click the links you touched. Link the preview in the description. Teach the team that a preview shows the built output, so a bug that only appears in the production build, like a wrong base path, will show up there and not in local dev. That is the main reason previews are worth setting up.

Clean up

Hosts keep old deployments. Delete stale previews if they contain anything you later realise you should not have published. See what not to publish.

Questions people ask

Does GitHub Pages support pull request previews?

Not built in. You can deploy each branch to a subfolder with a workflow, or use a host that provides previews.

Are preview URLs private?

Usually not. Treat them as public unless the host offers access control and you have enabled it.

Try it

Put one page online in a minute.

Pages publishes an HTML or Markdown file to a free public link. It is public, so do not use it for anything private.

npx -y @flisk-sh/pages publish page.html --wait
