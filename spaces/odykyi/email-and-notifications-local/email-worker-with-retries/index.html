How to send email from a background worker with retries

Sending mail inside a web request makes pages slow and loses messages when SMTP hiccups. A small outbox and a worker fix both problems.

Send email from a background worker, not inside the web request. Write an outbox row in the same database transaction as the change that needs the email, let a worker read pending rows and send them, and retry temporary failures with a growing delay. The request stays fast, a slow SMTP server does not break signups, and a message is not lost when the process restarts.

Why not send in the request

SMTP is a network call to a system you do not control. If you call it inside the request, then a slow server makes the page slow, a failure either shows an error to a user whose account was already created, or is swallowed and the email silently never goes out. If you send first and the database commit then fails, the user gets an email about something that did not happen.

The outbox pattern

The fix is to separate "decide to send" from "send":

  1. In the same transaction that creates the user, insert a row into an outbox table: recipient, template, data, status pending, attempts 0, next_attempt_at now.
  2. A worker loop selects pending rows that are due, sends each, and marks it sent.
  3. On a temporary failure, it increments attempts, sets next_attempt_at further out, and leaves the row pending.
  4. After a maximum number of attempts, it marks the row failed and logs it, so a person can look.

If several workers can run, claim rows with SELECT ... FOR UPDATE SKIP LOCKED in Postgres so two workers never send the same row. Give the message a stable ID too, so a provider that supports idempotency keys can drop a duplicate if a send succeeds but the acknowledgement is lost.

Which errors to retry

SMTP replies tell you what to do. A reply starting with 4 is temporary ("try again later"), so retry. A reply starting with 5 is permanent (bad address, rejected content), so do not retry; mark it failed. A network error such as a refused connection or a timeout is temporary. Here is the core of the loop with Nodemailer, where errors carry responseCode when the server answered:

function isPermanent(err: any): boolean {
  return typeof err.responseCode === "number" && err.responseCode >= 500;
}

async function handle(row: OutboxRow) {
  try {
    await transport.sendMail(render(row));
    await markSent(row.id);
  } catch (err: any) {
    const attempts = row.attempts + 1;
    if (isPermanent(err) || attempts >= 6) {
      await markFailed(row.id, String(err.message));
      return;
    }
    const delaySeconds = Math.min(2 ** attempts * 10, 3600);   // 20s, 40s, 80s...
    await reschedule(row.id, attempts, delaySeconds);
  }
}

Add some random jitter to the delay if many messages can fail together, so they do not all retry at the same second.

Run it locally with Flisk

Create the worker next to your API, and add the Mailpit resource from the Mailpit article:

flisk resource mailer --type worker --stack main --yes

In services/main/mailer/service.json, list what it needs to start: "dependsOn": ["mail"], plus whatever supplies your outbox table. The Postgres that comes with a Flisk project can hold the outbox; see sharing one database between a worker and an API. Then follow the worker with flisk logs --service mailer, and watch the inbox at http://127.0.0.1:8025. General worker setup is covered in running a background worker locally.

Test the failure path on purpose

A retry path that you never run is a retry path that is broken. Start a tiny fake SMTP server that always answers with a temporary error, and point the worker at it:

pip install aiosmtpd
python - <<'EOF'
from aiosmtpd.controller import Controller
import time

class Busy:
    async def handle_DATA(self, server, session, envelope):
        return "451 4.3.0 Try again later"

Controller(Busy(), hostname="0.0.0.0", port=2525).start()
time.sleep(3600)
EOF

Set the worker's SMTP_HOST and SMTP_PORT to that server (port 2525), create a signup, and read the worker's logs. You should see attempt 1, 2, 3 with growing delays, then success once you switch back to Mailpit. Change the reply to a 550 and confirm the row goes straight to failed. More on testing consumers this way is in queue consumer retries and dead letters.

Pitfalls

  • Retrying forever. Cap attempts and keep failed rows visible.
  • Duplicate sends. Rows in sending state after a crash need a timeout that returns them to pending, which means a message can occasionally go out twice. Use idempotency keys where your provider offers them.
  • When not to bother. A prototype with one email a day does not need an outbox. Add it when losing a message would cost you something.

Questions people ask

Why should email be sent from a worker?

So a slow or failing SMTP server cannot slow down or break the request, and so a message survives a process restart because it is stored before it is sent.

Which SMTP errors should be retried?

Reply codes starting with 4 and network errors such as timeouts are temporary and worth retrying with a delay. Codes starting with 5 are permanent and should not be retried.

How do I avoid sending the same email twice?

Claim rows safely, for example with FOR UPDATE SKIP LOCKED in Postgres, and give each message a stable ID that your provider can use as an idempotency key.
