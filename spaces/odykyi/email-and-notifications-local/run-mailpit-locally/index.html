Email and notifications in local dev

How to catch outgoing email locally with Mailpit

Mailpit accepts any message your app sends over SMTP and shows it in a web inbox. Nothing leaves your machine, and you do not need an account anywhere.

To catch outgoing email in local development, run Mailpit and point your app's SMTP settings at it. Mailpit listens for SMTP on port 1025, keeps every message it receives, and shows them in a web inbox on port 8025. Your app sends mail exactly as it would in production, but the only place it arrives is your own screen.

What a local mail catcher does

Almost every app sends email: a welcome message, a password reset, an invoice. In development you want to see those messages, click the links in them and check the layout, without sending anything to a real person. A mail catcher is a small SMTP server that accepts all mail and never forwards it. You get an inbox for every address your tests invent.

Mailpit is one such tool. It is a single Go binary, also published as a Docker image, with a web UI, a search box and a REST API. It is the maintained successor to MailHog, which many tutorials still mention (see the MailHog comparison).

Run it without Flisk

The quickest way is Docker:

docker run -d --name mailpit \
  -p 127.0.0.1:1025:1025 \
  -p 127.0.0.1:8025:8025 \
  axllent/mailpit

Open http://localhost:8025 for the inbox. Point your app at localhost, port 1025, no username, no password, no TLS. With Compose the same thing is a service with two published ports. If you do not want Docker, Mailpit also ships as a plain binary and a Homebrew package, and you start it by running mailpit.

Three settings are worth knowing, all environment variables:

  • MP_DATABASE=/data/mailpit.db stores messages in a file instead of memory, so they survive a restart. Mount a volume at /data.
  • MP_MAX_MESSAGES caps how many messages are kept (the default is 500), so the inbox does not grow forever.
  • MP_SMTP_AUTH_ACCEPT_ANY=1 with MP_SMTP_AUTH_ALLOW_INSECURE=1 lets clients that insist on a username and password send anything without errors.

Run it next to your services with Flisk

If your app already runs as containers under Flisk, Mailpit is one more resource. Flisk can run any image as a bring-your-own resource. Create it:

flisk resource mail --type bring-your-own \
  --image axllent/mailpit:v1.33.1 --no-proxy --stack main --yes

That writes services/main/mail/service.json. Edit it so it looks like this (the image tag is the one the Flisk docs pin; pick a newer tag if you like):

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "mail",
  "appType": "bring-your-own",
  "stack": "main",
  "port": 8025,
  "image": "axllent/mailpit:v1.33.1",
  "exposeViaProxy": false,
  "healthCheck": { "port": 1025 },
  "extraPorts": [{ "port": 8025 }],
  "volumes": [{ "source": "mail-data", "target": "/data" }],
  "params": { "MP_DATABASE": "/data/mailpit.db" },
  "provides": {
    "SMTP_HOST": "mail",
    "SMTP_PORT": "1025",
    "MAILPIT_API_URL": "http://mail:8025"
  }
}

What each field does:

  • port is 8025, the HTTP port of the inbox. SMTP is checked separately by healthCheck, a TCP probe on 1025, because Mailpit does not serve Flisk's default /health route.
  • extraPorts publishes the inbox on 127.0.0.1:8025 only, so nothing else on your network can read your test mail. If another program already uses 8025, add a hostPort to that entry.
  • volumes and params keep the inbox in a named volume that flisk down leaves in place.
  • provides lists settings that every service naming mail in its dependsOn receives as environment variables. Keep secrets out of it; these values are not secret.

Then in the service that sends mail, add the dependency:

"dependsOn": ["mail"]

Run flisk up main. Inside the Docker network your app reaches the catcher at mail:1025, by the resource name. From your browser, the inbox is at http://127.0.0.1:8025. Read your app's mail settings from SMTP_HOST and SMTP_PORT so the same code works in production with different values.

Flisk runs a project either as containers or as plain local processes, and does not mix the two yet. If your services run with a command and no Docker, start Mailpit yourself (the Docker command above, or the binary) and use localhost:1025.

Pitfalls

  • Wrong host from inside a container. localhost in a container is the container itself. Use the resource name (mail) there, and localhost only from programs on your host.
  • TLS settings copied from production. If your code sets secure: true or requires STARTTLS, the connection to a plain Mailpit fails. Drive these from environment variables.
  • Mailpit proves delivery to Mailpit, not to a mailbox. It does not tell you whether Gmail would mark the message as spam, or whether SPF and DKIM pass. Test those with your real provider on a staging domain.
  • Port 8025 already taken by another catcher from an old project. Stop it or change the host port.

Questions people ask

What port does Mailpit use?

Port 1025 for SMTP, where your app sends mail, and port 8025 for the web inbox and the REST API. Both can be changed with environment variables or flags.

Does Mailpit send email to real addresses?

No. It stores what it receives and never delivers it. It has an optional release feature that can forward a chosen message to a real SMTP server, but only if you configure one.

Do I need Docker to run Mailpit?

No. Mailpit is a single binary and is also available through package managers such as Homebrew. Docker is just a convenient way to run it.
