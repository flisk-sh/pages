Semantic cache vs exact cache for LLM responses

Cache whole model answers to skip paid calls. Compare an exact-match cache with an embedding-based one, and see when each is safe.

An exact cache returns a stored answer when the request is identical, and it is safe and simple. A semantic cache returns a stored answer for a similar question using embeddings, which saves more calls but can return a wrong answer. Start with exact, add semantic only for low-risk questions.

Exact cache: hash the full request

Build a key from everything that affects the output: model, system prompt, messages, temperature and tool list. Hash it and store the answer.

import hashlib, json

def key(req):
    return hashlib.sha256(json.dumps(req, sort_keys=True).encode()).hexdigest()

hit = cache.get(key(req))
if hit: return hit
out = call_model(req)
cache.set(key(req), out, ttl=86400)

Use Redis, SQLite or any key-value store. This works well for repeated FAQ-style prompts and for tests that replay the same inputs.

Semantic cache: match by meaning

Embed the incoming question, search your stored questions for the nearest one, and reuse its answer if the similarity is above a threshold.

q = embed(question)
nearest, score = index.search(q)
if score > 0.95:
    return answers[nearest]

The threshold is something you tune on real data. Too low and you return answers to a different question. Too high and you rarely hit.

Where semantic caching goes wrong

  • Two questions that look alike but differ in one fact, such as a date, a name or a number.
  • Answers that depend on the user or on data that changed since the answer was stored.
  • Personal or private content leaking between users. Scope the cache per tenant or never cache it.

Cache versus prompt caching

A response cache skips the model call entirely. Prompt caching only makes a call cheaper. They stack. Read prompt caching explained for the second one, and set a time to live so stale answers expire.

Invalidate on purpose

A cache with no invalidation will serve stale facts. Give every entry a time to live that matches how fast the underlying facts change, and add a version number to the key. When you change the prompt, the model or the source documents, bump the version and the old entries stop matching. Log hit rate and sample hits for manual review each week. A rising hit rate with falling user ratings is a sign the threshold is too loose.

Start small: cache one low-risk endpoint, watch hit rate and complaints for two weeks, and only then widen it. A cache you can switch off with one flag is a cache you will be willing to try.

Questions people ask

What similarity threshold should I use?

There is no universal value. Collect real question pairs, label which should share an answer, and pick the threshold that avoids wrong matches.

Should I cache with temperature above zero?

You can, but a cached answer freezes one sample. Include temperature in the key and accept that users will see the same wording.
