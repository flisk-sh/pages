Model routing: when to use a cheap model vs a strong one

Send easy requests to a small model and hard ones to a large one. How to pick the rule, test it, and add a fallback so quality does not drop.

Model routing means choosing the model per request: a small, cheap model for routine work, a stronger model for hard cases. Start with a simple rule based on the task type, measure it on a test set, and add escalation only when the cheap answer fails a check.

Start with routing by task

The simplest router is a lookup table. You know which feature a request belongs to, so you pick the model by feature.

const MODEL = {
  classify: 'small-model',
  extract:  'small-model',
  draft:    'mid-model',
  plan:     'large-model',
};
const model = MODEL[task];

Use real model names from your provider. This needs no extra model call and adds no latency.

Escalate on failure, not on a guess

A better pattern: try the cheap model first, run a deterministic check on the result, and call the strong model only if the check fails. Good checks are cheap and objective: does the JSON parse, does it match the schema, do the tests pass, is the cited id real.

let out = await call('small-model', prompt);
if (!valid(out)) out = await call('large-model', prompt);

Avoid asking the cheap model whether it is confident. Self-reported confidence is unreliable.

Use a classifier only if you must

When the task type is not known in advance, a small model can classify the request as easy or hard. This adds a call and some latency, so it pays off only when the savings on the strong model exceed that overhead. Measure it.

Test the router

Keep 50 to 200 real requests with known good outputs. Report quality, cost and median latency for three setups: always small, always large, and routed. Ship the router only if routed quality is close to always-large at a lower cost. Log the chosen model on every call so you can audit it later.

Use free capacity for development

While building the router and its tests, a free beta endpoint such as Flisk Inference (open beta, daily request limit) can serve as the cheap tier in development. It is not a drop-in proof of production quality, so rerun your test set on the models you will actually pay for. Related reading: how to reduce LLM API costs.

Pitfalls

  • Routing on prompt length alone. A short prompt can still be a hard question.
  • Changing the router and the prompts at the same time, so you cannot tell what changed the score.
  • Forgetting that two calls on escalation cost more than one strong call. If the cheap model fails often, the router loses money.
  • No fallback when the cheap provider is down. Decide in advance which model takes over.

Questions people ask

Is a router worth it for a small app?

Often a fixed table by task is enough. Add checks and escalation only when you see real spend on a strong model for easy requests.

Can the model route itself?

It can, but it adds a call and is not always accurate. Prefer rules and deterministic checks first.
