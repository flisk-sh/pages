Batch API vs real-time LLM requests: which to use

Batch interfaces trade speed for a lower price. Learn which jobs fit a batch, how a typical batch flow works and where it falls short.

Use a batch interface for work nobody is waiting on, such as nightly summaries, bulk tagging or evaluation runs, and use real-time requests for anything a user watches. Major providers offer batch processing at a lower price in exchange for results that arrive later.

What a batch job looks like

You submit many requests in one file or call. The provider processes them asynchronously and returns the results within a time window, not instantly. Each request carries an id you choose so you can match answers back to inputs.

{"custom_id":"doc-001","body":{"model":"your-model","messages":[{"role":"user","content":"Summarise: ..."}]}}
{"custom_id":"doc-002","body":{"model":"your-model","messages":[{"role":"user","content":"Summarise: ..."}]}}

The exact file format, endpoint names, size limits and time window are provider specific. Read the current batch docs before you build.

Good fits

  • Backfilling summaries or tags for an existing database.
  • Running an evaluation suite over hundreds of cases.
  • Generating embeddings or descriptions overnight.
  • Any pipeline where a few hours of delay changes nothing.

Bad fits

  • Chat or anything with a user waiting.
  • Agent loops, where each step depends on the previous answer.
  • Jobs where a failure must be noticed in seconds.

Build the flow so it survives failures

  1. Write inputs and their ids to your database first.
  2. Submit the batch and store the batch id.
  3. Poll on a schedule, or check from a worker.
  4. When finished, write results by id. Retry only the failed items.

Make step four idempotent. Running it twice must not double-write. A background worker plus a queue is a natural home for this, see workers and queues.

To try the submit, poll and collect loop on your own machine, you can run the worker and its queue locally with the open-source Flisk CLI (local development only, not a production orchestrator).

Combine with other savings

Batch pricing and prompt caching can sometimes stack, but check your provider's rules. Whether or not they do, shorter prompts help in both modes. See how to reduce LLM API costs for the full list.

A small decision rule

Ask one question: will anyone notice if this result arrives in six hours instead of six seconds? If not, use a batch. If a person or another service is waiting, use a real-time call. For work in the middle, such as a report a user asked for that can take a minute, a real-time call run by a background worker is usually the right answer, with a status page for the user.

Keep the same prompt and the same output checks in both modes, so a batch result and a live result are interchangeable.

Also plan for partial failure. In a large batch a few items will fail, for example a malformed input or a refused request. Store the error per item, retry only those, and alert if the failure rate passes a threshold you chose in advance.

Questions people ask

How much cheaper is a batch API?

Providers publish a discount for batch jobs. It varies by provider and can change, so read the current pricing page.

How long does a batch take?

Providers give a maximum completion window, often many hours. Many batches finish sooner, but do not depend on it.
