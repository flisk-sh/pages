GitHub Actions Security

GitHub Actions Supply Chain Attacks and How to Defend

How a compromised third-party action reaches your secrets, what the 2025 tj-actions incident showed, and a short defence list you can apply in an afternoon.

A third-party action runs inside your job with whatever secrets and token that job holds, so a compromised action is a compromised pipeline. Defend by pinning to commit SHAs, giving jobs minimal permissions and secrets, and keeping secrets out of any job that runs code you did not review.

The attack path

Attackers do not break into your repository. They break into something your repository already trusts: an action's source repository, a maintainer account, or a dependency that the action installs. They then change the code behind a tag you reference. On your next run the new code executes with your job's environment. The usual goals are reading secrets from process memory or environment, and modifying build outputs.

A real example

In March 2025, the widely used tj-actions/changed-files action was compromised, and tags were repointed to code that printed secrets from the runner's memory into workflow logs. Public repositories with readable logs exposed secrets to anyone. It was tracked as CVE-2025-30066. Repositories that pinned to a full commit SHA from before the compromise kept running the old code. For the exact timeline and indicators, read the project's advisory and GitHub's notice rather than a summary.

Defence list

  1. Pin third-party actions to full SHAs, see how to pin.
  2. Set minimal permissions, see least privilege.
  3. Pass a secret only to the step that needs it, see secrets best practices.
  4. Use OIDC so no long-lived cloud key exists to steal.
  5. Restrict which actions are allowed in organisation settings to your own and a reviewed allow-list.
  6. Replace small, trivial actions with a few lines of shell. Fewer dependencies mean a smaller target.

Review updates, do not auto-merge blindly

Dependabot bumps for actions are good, but read the diff of the action between old and new SHA before merging, especially for actions that touch secrets or publish artifacts. Look for new network calls, obfuscated code and changes to the action's own dependencies.

git clone https://github.com/some-org/some-action /tmp/a
cd /tmp/a && git diff <old-sha> <new-sha> --stat

Plan for the bad day

Decide in advance how you will respond: a list of which secrets each workflow can read, a way to rotate them within an hour, and a habit of checking provider audit logs. If a compromised action ran in your repository, rotate every secret that job could see, then search logs for unexpected output. Do not wait to confirm exposure before rotating.

A one afternoon plan

In one afternoon you can do the most valuable steps: pin every third-party action, add the Dependabot config for actions, set read-only default permissions in the organisation, and add the two linters to CI. After that, schedule the rotation drill. Pick one low-risk secret, rotate it end to end and time it. If it takes a day, you now know that a real incident will be slow, and you can fix the process while nothing is on fire.

Questions people ask

Does pinning to a SHA make me immune?

No. It stops silent tag changes, but you can still pin a malicious commit, and an action can download code at runtime. Pinning is one layer among several.

Should I stop using third-party actions?

Not necessarily. Use well-maintained ones, pin them, and replace trivial ones with shell. Each remaining action is a trust decision, so make it consciously.
