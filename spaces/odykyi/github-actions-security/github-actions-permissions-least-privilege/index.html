GITHUB_TOKEN Permissions: Set Least Privilege

How the GITHUB_TOKEN works, why to set permissions explicitly at the top of every workflow, and which scopes each common job needs.

Add a top-level permissions: block to every workflow and grant only contents: read, then raise individual jobs when they need more. The GITHUB_TOKEN is created for each run, and its default scope depends on repository settings that may be broader than you want.

What the token is

Each workflow run gets a short-lived token that lets steps call the GitHub API as the Actions bot. It expires when the job ends. The risk is not its lifetime but its scope: a compromised step that holds a write-capable token can push code, edit releases or open pull requests during the run.

Set a safe default first

In repository or organisation settings under Actions, set the default workflow permissions to read-only. Then declare permissions in the file anyway, so the workflow is correct no matter where it is copied.

name: ci
on: [pull_request]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

Once you declare any permission, every scope you do not list is set to none.

Raise permissions per job

Put extra scopes on the one job that needs them, not at the top.

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo test
  release:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: write
      id-token: write
    steps:
      - run: echo publish

Common needs: pull-requests: write to comment on a pull request, packages: write to push to GitHub Packages, id-token: write for OIDC to a cloud, contents: write to create a release or push a tag.

Check what a run actually got

Open any job log and expand 'Set up job', then 'GITHUB_TOKEN Permissions'. It lists every scope the token received. Make this part of reviewing a new workflow. Note that for pull requests from forks the token is read-only no matter what you declare, which is covered in pull_request_target vs pull_request.

Pitfalls

  • permissions: write-all is a red flag in review. Replace it with the named scopes.
  • A token with contents: write can push to unprotected branches. Branch protection and rulesets are your second layer.
  • Do not store a personal access token in a secret just to get around a permission error. A PAT usually has far more reach than the scoped token, and it does not expire at the end of the run.
  • Reusable workflows can only keep or reduce the permissions of the caller, never raise them.

A review routine that scales

Add one line to your pull request template: 'Does this workflow declare permissions?'. When a workflow needs a new scope, ask why in the review and write the reason in a YAML comment next to the line. Over time the comments become a map of who can do what. For organisations, search every repository for workflows that lack a permissions: key and fix those first, since they inherit whatever the default is. A failing job with a clear error is a cheap price for knowing exactly what each job is allowed to touch.

Questions people ask

What happens if I do not set permissions at all?

The token gets the repository or organisation default, which can be read-write on older repositories. Declaring permissions in the file makes the result independent of that setting.

Why does my job fail with 'Resource not accessible by integration'?

The token lacks a scope for the API call. Add the specific scope to that job, for example pull-requests: write, rather than switching to write-all.
