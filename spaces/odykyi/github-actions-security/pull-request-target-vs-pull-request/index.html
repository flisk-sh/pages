pull_request_target vs pull_request: Which to Use

The two triggers look alike but run in very different security contexts. Learn what each can access and the one pattern that makes pull_request_target dangerous.

Use pull_request for building and testing code from a pull request. Use pull_request_target only for tasks that need write access or secrets and never check out or run the pull request's code in that job.

What each trigger does

pull_request runs the workflow file from the merge commit of the pull request. For pull requests from forks, it gets a read-only token and no repository secrets. That makes it safe to run untrusted code, because the code has nothing to steal.

pull_request_target runs the workflow file from the base branch, in the context of the base repository. It gets a token that can have write permissions and it can read secrets, even when the pull request comes from a fork. It exists so you can do things like label or comment on fork pull requests.

The dangerous pattern

The mistake is to check out the head of the pull request inside a pull_request_target workflow and then run something from it:

on: pull_request_target
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
      - run: npm ci && npm test   # runs attacker code with secrets

Now an outsider's package.json script, test file or build step executes with your secrets and a write token. Installing dependencies counts as running their code, because install scripts run.

Safe uses of pull_request_target

Keep the job to metadata. Labelling by changed file paths, greeting first-time contributors and checking the pull request title format are fine, because they read the event payload and call the API without executing the contributed files. Even then, treat the title and body as untrusted text, as explained in script injection.

Run tests, then comment: the two-workflow pattern

When you need to test fork code and then post results, split it in two. The first workflow uses pull_request, runs the tests with no secrets and uploads the results as an artifact. A second workflow uses workflow_run, which runs in the base repository context, downloads the artifact and posts the comment.

on:
  workflow_run:
    workflows: ['ci']
    types: [completed]
permissions:
  pull-requests: write
  actions: read

Treat the artifact as untrusted data: parse it, never execute it, and never put its contents into a shell command.

Defence in depth

  • Require approval before workflows run for first-time contributors, in the repository's Actions settings.
  • Give the job the smallest permissions: block. See least privilege.
  • Keep secrets out of jobs that touch contributed files, and scope them to an environment with required reviewers.
  • Search your repositories for pull_request_target and review each hit by hand.

A quick test you can run

Open a pull request from a fork with a harmless change that prints whoami and the names of environment variables, never their values. In a pull_request workflow you should see no secrets and a read-only token. If your pull_request_target workflow checks out the head and runs that same step, you will see secrets exposed, which proves the hole exists. Do this on a throwaway repository, not on your real one, and delete it afterwards. It turns an abstract warning into something your team has seen with its own eyes.

Questions people ask

Is pull_request_target always unsafe?

No. It is safe when the job never executes code from the pull request and treats event text as untrusted. The danger is checking out and running the contributor's code with its elevated context.

Do secrets work with pull_request from forks?

No. Secrets are not passed to workflows triggered by pull requests from forks, apart from the read-only token. Pull requests from branches in the same repository do get secrets.
