GitHub Actions OIDC: Deploy to Cloud Without Secrets

Replace long-lived cloud keys in repository secrets with short-lived tokens issued through OpenID Connect, with a trust policy that limits which repo and branch can deploy.

With OIDC, the workflow asks GitHub for a signed identity token, and your cloud provider exchanges it for temporary credentials. You store no access key, and the cloud side decides which repository, branch or environment may assume the role.

How it works

When a job has id-token: write permission, it can request a JSON Web Token from GitHub. The token carries claims such as the repository, the ref, the workflow and the environment, in a field called sub (subject). Your cloud provider is configured to trust GitHub's token issuer and to accept only tokens whose claims match a rule you wrote. If they match, it returns credentials that expire in minutes to hours.

A minimal workflow

Here is the shape for AWS, using the official action. The same idea works for Google Cloud and Azure with their own login actions.

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@<pinned-sha>
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: eu-west-1
      - run: aws sts get-caller-identity

No secret appears anywhere. The ARN is an identifier, not a credential. Pin the action as described in pinning to a SHA.

The trust policy is the security

The most common mistake is a trust rule that is too loose, such as accepting any repository in your organisation, or any branch. Restrict the sub claim as tightly as the job allows. Typical subject formats are:

  • repo:my-org/my-repo:ref:refs/heads/main for runs on one branch
  • repo:my-org/my-repo:environment:production for jobs that use a protected environment
  • repo:my-org/my-repo:pull_request for pull request runs

Prefer the environment form for production, because you can then require reviewers on that environment. Also check the audience claim your provider documents.

Separate roles by risk

Use one read-only role for pull request jobs and a separate deploy role that only the main branch or production environment can assume. A compromised pull request job then cannot reach production permissions at all.

Pitfalls

  • Jobs without id-token: write cannot request a token. Setting it at top level gives it to every job, so set it per job.
  • Fork pull requests do not receive OIDC tokens by default, so test deployments need another route.
  • Debug a failing trust with the exact sub value. Many providers show the claim they rejected in their audit log.
  • Check your provider's docs for current setup steps, since console flows change.

Test the trust policy from both sides

After setup, run the workflow from the allowed branch and confirm it can assume the role. Then run it from a throwaway branch or a pull request and confirm the cloud provider refuses it. The second test matters more, because it shows the trust rule is tight. Write both results in the pull request. Repeat the check when you rename a repository, move it to another organisation or rename an environment, since the subject claim changes with those names and old rules silently stop matching.

Questions people ask

Is OIDC only for AWS?

No. Google Cloud, Azure, HashiCorp Vault and many other providers accept GitHub's OIDC tokens. Each has its own setup for the trust rule, so follow that provider's documentation.

Does OIDC protect me if a workflow is compromised?

It limits the damage: credentials are short-lived and scoped by your trust rule. A compromised job that is allowed to assume the role can still use it during the run.
