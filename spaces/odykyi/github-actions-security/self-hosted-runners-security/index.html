Self-Hosted Runner Security: What Can Go Wrong

Why self-hosted runners and public repositories are a risky pair, how persistence turns one bad job into a lasting breach, and how to isolate runners properly.

Do not attach self-hosted runners to public repositories, and run them as ephemeral machines wherever you can. A self-hosted runner executes workflow code on hardware you own, so anyone who can get a workflow to run on it can attack your network.

Why they are different

GitHub-hosted runners are fresh virtual machines that are discarded after each job. A self-hosted runner is your machine. It may hold cached credentials, network access to internal services, and files left by the previous job. The runner process runs whatever the workflow tells it to.

The public repository problem

On a public repository, a fork pull request can propose a workflow change or code that a workflow runs. If your settings let those runs reach a self-hosted runner, a stranger executes code inside your network. GitHub's own guidance is to avoid self-hosted runners for public repositories. If you must, require approval for all outside contributors and restrict the runner to specific, trusted workflows through runner groups.

Make runners ephemeral

A persistent runner can be poisoned by one job: a malicious step can plant a binary in a cached directory, change a config or steal a token that the next job then uses. An ephemeral runner takes one job and is then destroyed.

./config.sh --url https://github.com/my-org/my-repo \
  --token <registration-token> --ephemeral
./run.sh

Pair --ephemeral with something that starts a clean container or virtual machine for each registration. Kubernetes based controllers and cloud autoscaling setups exist for this, so check the current GitHub docs for the supported options.

Isolation checklist

  • Run the runner as an unprivileged user, never as root.
  • Put runners on a network segment with no route to production or to internal admin tools.
  • Do not mount the Docker socket into job containers, since that is root on the host.
  • Give the machine no cloud instance role beyond what jobs need.
  • Use runner groups to limit which repositories and workflows can pick up a runner.
  • Patch the runner software and the OS on a schedule.

When self-hosted is worth it

It is justified for special hardware, large builds that need local caches, or private network access. Weigh that against the security work. If the motive is only speed, check faster GitHub Actions first, since caching and larger hosted runners may be enough.

Monitor and log runners

Log what each runner does. Keep the runner service logs, record which repository and workflow used it, and alert on odd network connections from the runner subnet. A runner that suddenly talks to an unfamiliar host is a strong signal. Review the list of registered runners monthly in the settings page and remove any that nobody owns. Old, forgotten runners are common entry points because they are rarely patched.

Questions people ask

Is a self-hosted runner in Docker safe enough?

A container helps only if each job gets a fresh one and the container has no privileged access. Mounting the Docker socket or running privileged mode removes most of the isolation.

Can I use self-hosted runners on a private repository?

Yes, that is the normal use. The risk is lower because only people with repository access can trigger jobs, but ephemeral runners and network isolation still apply.
