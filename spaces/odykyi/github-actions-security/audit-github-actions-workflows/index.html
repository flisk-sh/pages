How to Audit GitHub Actions Workflows (actionlint, zizmor)

A repeatable audit of every workflow file: what to grep for, which linters to run in CI, and how to see the state of many repositories at once.

Run actionlint for correctness and zizmor for security findings on every pull request that touches .github/workflows, then do a short manual review of triggers, permissions and third-party actions. Linters find the patterns, and a human decides what is acceptable.

Step 1: inventory

List every workflow, its triggers and every external action it uses.

ls .github/workflows
grep -rhn '^on:\|^  [a-z_]*:$' .github/workflows | head -40
grep -rhoE 'uses: [^ ]+' .github/workflows | sort | uniq -c | sort -rn

The last command shows which actions you depend on and which are not pinned to a SHA. Also check for reusable workflows and local composite actions under .github/actions.

Step 2: run the linters

actionlint checks syntax, expression types and shell script problems via shellcheck. zizmor is a static analyser aimed at security issues in workflows, such as template injection and excessive permissions. Run both locally first.

actionlint
zizmor .github/workflows

Then run them in CI so new workflows are checked automatically. Follow each tool's install instructions in its own documentation, as installation methods differ by platform.

Step 3: the manual checklist

  • Triggers: any pull_request_target or workflow_run? Review each, see this comparison.
  • Permissions: is there a top-level permissions: block? See least privilege.
  • Untrusted text in run: scripts, see script injection.
  • Third-party actions pinned to a SHA.
  • actions/checkout with persist-credentials: false where later steps do not need to push.
  • Self-hosted runners used on public repositories.
  • Secrets exposed at job level instead of step level.

Step 4: repository settings

Workflow files are only half of it. Check: default workflow permissions set to read, approval required for workflows from first-time or outside contributors, branch protection or rulesets on the default branch, and which actions are allowed. The OpenSSF Scorecard project also scores many of these settings and can run as an Action on your repo.

Step 5: see many repositories at once

One repo is easy. For an organisation, you want a list. Cilytics is a public CI health dashboard that reads the GitHub API and shows red workflows, pass rate and an open-source hygiene score for an org, or for any public repo with ?repo=owner/name. It is a health overview, not a security scanner, so keep running the linters above. Its data is an hourly snapshot of default-branch runs.

Schedule a recurring review. A quarterly audit with a short written result catches drift that one-off cleanups miss.

Write down the result

An audit that lives only in someone's head is lost by the next quarter. Record each finding with the file, the risk, the fix and an owner, and keep the list in the repository, for example in a SECURITY-NOTES.md file or an issue. Close findings by pull request. Share a short summary with the team so people learn which patterns to avoid, and repeat the linters in CI so fixed issues stay fixed.

Questions people ask

How often should I audit workflows?

Lint on every pull request that changes a workflow, and do a manual review of triggers, permissions and third-party actions every quarter or after any security incident in a dependency.

Are linters enough?

No. They catch known patterns, but they cannot judge whether a trigger or a secret is appropriate for your project. Use them as a floor, not a verdict.
