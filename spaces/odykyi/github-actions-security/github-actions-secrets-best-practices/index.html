GitHub Actions Secrets: Store and Scope Them Safely

Where to define secrets, how to scope them to environments, what log masking does not protect, and how to rotate quickly when one leaks.

Store secrets at the narrowest level that works: environment secrets for deployments, repository secrets for shared CI, and organisation secrets only when many repositories truly need the same value. Give each job only the secrets it uses, and prefer short-lived credentials over stored ones.

Three levels, pick the smallest

Repository secrets are available to any workflow in that repository. Organisation secrets can be shared with chosen repositories. Environment secrets only reach jobs that declare environment: production, and that environment can require a human reviewer and restrict which branches may deploy.

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: ./deploy.sh
        env:
          API_TOKEN: ${{ secrets.PROD_API_TOKEN }}

Expose a secret to one step, not the whole job

Set env: on the single step that needs the value. A secret set at job or workflow level is visible to every step and every action in that scope, including third-party ones.

Masking is not protection

GitHub hides exact secret values in logs, but the mask only matches the literal string. A step that base64-encodes, splits or reverses a secret prints it unmasked. Anyone who can change a workflow that has the secret can read it, so secrets are only as safe as your write access and branch protection. Never print secrets to debug, and never pass them as command-line arguments where process listings can show them.

Structured secrets and multiline values

Avoid putting a whole JSON blob in one secret, because masking is unreliable for pieces of it. Store each credential separately. For multiline values such as private keys, write them to a file with restrictive permissions in a temp directory and delete the file at the end of the job.

- run: |
    umask 077
    printf '%s' "$KEY" > "$RUNNER_TEMP/key.pem"
  env:
    KEY: ${{ secrets.DEPLOY_KEY }}

Prefer no stored secret at all

For cloud access use OpenID Connect so there is nothing long-lived to steal. See OIDC for cloud authentication. For local work, env and secrets in local development covers keeping values out of git.

When one leaks

  1. Rotate it at the provider first. Deleting the GitHub secret does not revoke it.
  2. Check the provider's audit log for use since the leak.
  3. Find how it leaked: a printed log, a malicious action, an artifact. Workflow logs and artifacts can be read by anyone with repository read access on a public repository.
  4. Turn on secret scanning and push protection in the repository's security settings so the next one is caught at push time.

A short secrets audit.

List every secret name in the repository and in each environment. For each one write down which workflow uses it, who created it and when it was last rotated. Delete any secret nobody can explain. Add a rotation date to your calendar for the ones that stay, and prefer credentials that expire on their own. A twenty minute audit twice a year removes forgotten tokens, which are the ones attackers find first because nobody is watching them.

Questions people ask

Are secrets available to pull requests from forks?

No. GitHub does not pass repository secrets to workflows triggered by fork pull requests, apart from the read-only token. This is deliberate and should not be worked around.

Should I use a personal access token in CI?

Avoid it. Use the GITHUB_TOKEN with scoped permissions, or a GitHub App token when you need cross-repository access, since both are narrower and short-lived.
