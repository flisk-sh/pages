How to Pin GitHub Actions to a Commit SHA

Why a version tag is not a stable reference, how to pin every third-party action to a full commit SHA, and how to keep those pins updated without doing it by hand.

Pin every third-party action to a full 40-character commit SHA, not to a tag like v4. Tags are mutable: whoever controls the action's repository can move a tag to different code, and your next run will execute it with your secrets in reach.

Why tags are not safe

A line like uses: some-org/some-action@v3 means 'run whatever v3 points to right now'. The maintainer can move that tag on purpose, or an attacker who steals the maintainer's credentials can move it for them. Your workflow changes behaviour without a single commit in your repo.

A commit SHA is a content hash. Git will not let a different commit hide behind the same SHA, so a pinned action runs exactly the code you looked at.

How to pin

Find the commit the tag points to, then use that SHA and keep the tag in a comment so humans can read it.

git ls-remote https://github.com/actions/checkout refs/tags/v4

# then in the workflow
- uses: actions/checkout@<full-40-char-sha> # v4

Use the full SHA. Short SHAs are not accepted for actions. For annotated tags, git ls-remote may show a second line ending in ^{}: the SHA on that line is the commit you want.

Check the SHA belongs to the real repository

A fork can contain a commit that does not exist in the upstream repository, and GitHub resolves such a SHA through the fork network. Before you pin, open the commit page on the official repository and confirm the SHA appears there, or confirm it is reachable from a release tag in the upstream repo.

Keep pins fresh with Dependabot

Pinned actions stop getting fixes unless something updates them. Dependabot understands workflow files and will open pull requests that bump the SHA and the comment together.

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    groups:
      actions:
        patterns: ['*']

The group puts all action bumps into one pull request, so you review one diff a week instead of ten. See Dependency Updates Without Chaos for the wider setup.

Trade-offs and what to pin first

Pinning costs readability and a little maintenance. It is worth the cost for any action that is not owned by your own organisation and that runs in a job with secrets or write permissions. Actions published by GitHub itself are lower risk, but pinning them is still cheap once Dependabot is in place.

Pinning an action does not pin what that action downloads at runtime. A composite or JavaScript action that fetches a script from a URL is still only as safe as that URL. Read the action's source for curl calls and unpinned installs. Also pin your own reusable workflows with uses: org/repo/.github/workflows/x.yml@<sha>.

A quick verification habit

After you pin, run the workflow once on a branch and read the job log. The 'Set up job' step prints each action with the exact SHA it downloaded, so you can confirm the pin took effect. Add a CI check that fails when a uses: line for a third-party action does not match a 40-character hex string. A short grep is enough to start, and a linter such as zizmor can report unpinned references too. Make the check part of the same pull request that introduces the pin, so the rule is enforced from day one and new contributors learn it from a failing check, not from a lecture.

Questions people ask

Do I need to pin actions from the actions/ organisation?

It is lower risk, since GitHub owns them, but pinning is cheap with Dependabot and removes a whole class of tag-moving risk. Pin third-party actions first.

Can I enforce pinning across the organisation?

GitHub offers a policy setting that can require actions to be pinned to a full commit SHA. Check your organisation's Actions settings, since availability depends on your plan.
