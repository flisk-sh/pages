Search, files and object storage locally

How to run Qdrant locally for vector search in development

A vector database for local work is one container and a few REST calls. Here is the setup and the first query.

To run Qdrant locally, start the qdrant/qdrant image with port 6333 published on 127.0.0.1 and a volume at /qdrant/storage. Then create a collection that declares the vector size and distance metric, upsert points, and search with a query vector. There is a web dashboard at /dashboard. With Flisk, one command scaffolds the same container as a resource.

The plain Docker way

docker run -d --name dev-qdrant \
  -p 127.0.0.1:6333:6333 \
  -v dev_qdrant_data:/qdrant/storage \
  qdrant/qdrant:v1.12.5

Open http://127.0.0.1:6333/dashboard to browse collections. The REST API is on the same port. Port 6334 is gRPC, which you only need if your client library uses it. Qdrant clients default to REST in most languages.

Create a collection and search

A collection fixes the vector size at creation. It must match your embedding model's output exactly, for example 384 for a small sentence model or 1536 for a large one. This example uses 4 so you can read it:

curl -X PUT http://127.0.0.1:6333/collections/notes \
  -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Cosine"}}'

curl -X PUT 'http://127.0.0.1:6333/collections/notes/points?wait=true' \
  -H 'Content-Type: application/json' \
  -d '{"points": [
    {"id": 1, "vector": [0.9, 0.1, 0.0, 0.0], "payload": {"text": "cats"}},
    {"id": 2, "vector": [0.1, 0.9, 0.0, 0.0], "payload": {"text": "invoices"}}
  ]}'

curl -X POST http://127.0.0.1:6333/collections/notes/points/search \
  -H 'Content-Type: application/json' \
  -d '{"vector": [0.8, 0.2, 0.0, 0.0], "limit": 3, "with_payload": true}'

Point ids are unsigned integers or UUIDs. The payload is any JSON you want to store with the vector and filter on later. ?wait=true makes the call return after the write is applied, which avoids searching before the point exists. Choose the distance (Cosine, Dot, Euclid) to match how your embedding model was trained. Most text models use cosine.

In real code you replace the toy vectors with embeddings from your model. Qdrant does not create embeddings, it stores and searches them.

The Flisk way

Flisk has a Qdrant preset under the database type:

flisk resource vectors --type database --framework qdrant --stack shop --yes

That writes a bring-your-own service.json with the image qdrant/qdrant:v1.12.5, port 6333, a health check on that port, a named volume vectors-data mounted at /qdrant/storage, the dashboard published on 127.0.0.1:6333, and this in provides:

"provides": { "QDRANT_URL": "http://vectors:6333" }

Any service that lists vectors in dependsOn gets QDRANT_URL in its environment:

import { QdrantClient } from "@qdrant/js-client-rest";
const qdrant = new QdrantClient({ url: process.env.QDRANT_URL });

Run flisk up shop to start it. The data volume survives flisk down. flisk down --purge removes the project's volumes, which wipes your vectors along with the rest, so keep a way to rebuild them. See keep volumes between runs.

Pitfalls

  • Vector size mismatch. Upserting a vector of the wrong length returns an error. If you change embedding models, create a new collection and re-embed.
  • Two addresses. From a service in the stack use http://vectors:6333. From your laptop use http://127.0.0.1:6333.
  • No authentication by default. Fine on 127.0.0.1. Add an API key before exposing it anywhere else.
  • Treat vectors as derived data. The source of truth is your documents. Keep a script that rebuilds the collection from them, because a changed chunking rule or embedding model means a full rebuild.
  • Filtering needs payload indexes at scale. Small local sets work without them. For larger sets, create payload indexes on the fields you filter on.

When not to use it

If you only have a few thousand vectors and already use Postgres, the pgvector extension may be enough and removes a service. If your search is by keyword, not meaning, use a text index instead, as in Postgres full-text search.

Next, keep vectors current with a rebuildable sync job, and see Redis for local development if you want a cache next to it.

Questions people ask

What vector size should I use?

Exactly the output size of your embedding model. The collection rejects vectors of any other length.

Does Qdrant create embeddings?

No. You compute embeddings with a model of your choice and send the vectors. Qdrant stores them and searches by similarity.

How do I reach the Qdrant dashboard?

Open http://127.0.0.1:6333/dashboard once the container runs and the port is published on your machine.
