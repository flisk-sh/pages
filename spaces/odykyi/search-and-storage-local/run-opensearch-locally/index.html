How to run OpenSearch locally for development (single node)

OpenSearch is heavy by default. A single node with a fixed heap and security switched off is enough to develop against.

To run OpenSearch locally, start one container in single-node mode, give the JVM a fixed heap (512 MB is enough for development), turn off the security plugin for local use only, and publish port 9200 on 127.0.0.1. The most common startup failures are a heap that is too large for the container, a too-low vm.max_map_count on Linux, and cluster discovery waiting for nodes that never arrive.

The plain Docker way

docker run -d --name dev-opensearch \
  -p 127.0.0.1:9200:9200 \
  -e "discovery.type=single-node" \
  -e "DISABLE_SECURITY_PLUGIN=true" \
  -e "DISABLE_INSTALL_DEMO_CONFIG=true" \
  -e "OPENSEARCH_JAVA_OPTS=-Xms512m -Xmx512m" \
  --ulimit nofile=65536:65536 --ulimit memlock=-1:-1 \
  -v dev_os_data:/usr/share/opensearch/data \
  opensearchproject/opensearch:2.17.1

curl http://127.0.0.1:9200/_cluster/health?pretty

Each setting solves a specific problem:

  • discovery.type=single-node skips the cluster bootstrap checks. Without it the node waits to find other nodes and exits with an error about bootstrap checks.
  • DISABLE_SECURITY_PLUGIN=true turns off TLS and passwords, so plain http works. This is only acceptable because the port is bound to 127.0.0.1. Never copy it to a shared server.
  • DISABLE_INSTALL_DEMO_CONFIG=true stops the image from installing demo certificates and users.
  • OPENSEARCH_JAVA_OPTS sets the heap. Set minimum and maximum to the same value. The default picks a size from the machine's memory, which can starve everything else on your laptop.
  • The nofile and memlock limits satisfy the node's file descriptor and memory-lock checks.

A health response with "status":"green" or "yellow" means it works. Yellow is normal on one node, because replica shards have nowhere to go. If you create an index with number_of_replicas: 0, it turns green.

The Linux setting that breaks startup

On a Linux host (and in some Docker setups on Linux), OpenSearch needs vm.max_map_count of at least 262144. If it is lower you will see a bootstrap check failure that names it. Fix it on the host:

sudo sysctl -w vm.max_map_count=262144

That lasts until reboot. To keep it, put vm.max_map_count=262144 in a file under /etc/sysctl.d/. Docker Desktop on macOS runs a Linux VM that usually has a sufficient value already.

The Flisk way

OpenSearch is not a built-in Flisk framework, so use a bring-your-own resource:

flisk resource os --type bring-your-own --image opensearchproject/opensearch:2.17.1 --no-proxy --stack shop --yes

Edit services/shop/os/service.json. The file below passed flisk config verify on the 1.4.57 release:

{
  "appName": "os",
  "appType": "bring-your-own",
  "stack": "shop",
  "port": 9200,
  "image": "opensearchproject/opensearch:2.17.1",
  "exposeViaProxy": false,
  "healthCheck": {
    "command": ["curl", "-sf", "http://localhost:9200/_cluster/health"],
    "startPeriod": 60
  },
  "extraPorts": [{ "port": 9200 }],
  "volumes": [{ "source": "os-data", "target": "/usr/share/opensearch/data" }],
  "env": {
    "DISABLE_SECURITY_PLUGIN": "true",
    "DISABLE_INSTALL_DEMO_CONFIG": "true",
    "OPENSEARCH_JAVA_OPTS": "-Xms512m -Xmx512m"
  },
  "container": {
    "ulimits": { "nofile": { "soft": 65536, "hard": 65536 }, "memlock": -1 },
    "memory": "2g",
    "command": ["opensearch", "-Ediscovery.type=single-node"]
  },
  "provides": { "OPENSEARCH_URL": "http://os:9200" }
}

A few notes on the choices. Env keys in service.json must be letters, digits or underscore, so discovery.type cannot go in env. It is passed as a -E argument in container.command instead. I did not run this container, so check that your image version accepts this command form, and read flisk logs --service os if it does not start. The health check is a command probe rather than a port check, because OpenSearch listens before the cluster is ready, and startPeriod gives it 60 seconds before failures count. Bring-your-own containers have no memory cap in Flisk unless you set container.memory, so the 2g value keeps a runaway node from taking the whole machine. Keep it above the heap by a good margin.

Services that list os in dependsOn receive OPENSEARCH_URL. Start with flisk up shop and check with flisk status --json.

Pitfalls

  • Memory. A 2 GB container plus a 512 MB heap is a lot next to your other services. If your laptop is short on memory, see many services on one laptop.
  • Restart loops. If the container exits and comes back, the log shows the real error. See a container that keeps restarting.
  • Disk watermarks. When your disk is nearly full, OpenSearch marks indices read-only. Free space, then clear the block with a settings update.
  • Elasticsearch images. The same ideas apply to Elasticsearch, but its security setting names differ, and recent versions need extra steps to run without TLS.
  • Version pinning. Use the same major version locally as in production, because client libraries check it.

When not to use it

If you only need typo-tolerant search over a few collections, a lighter engine such as Meilisearch starts in seconds and uses far less memory. Reach for OpenSearch when production runs it and you need its query DSL or aggregations to behave the same way.

Questions people ask

Why does OpenSearch exit right after starting?

Usually a bootstrap check. Set discovery.type to single-node, give the JVM a fixed heap, and on Linux raise vm.max_map_count to 262144. The container log names the failed check.

Is it safe to disable the security plugin?

Only for local use with the port bound to 127.0.0.1. Never run a node without security on a shared or public network.

Why is my local cluster yellow?

Replica shards cannot be placed on the same node as their primary, so a single node stays yellow. Set number_of_replicas to 0 on your development indices if you want green.
