Postgres full-text search: try it before adding a search engine

For many apps, search is one SQL query and one index. Find out where that stops before you add a second service.

Postgres can search text without another service: store a tsvector column, index it with GIN, and query it with websearch_to_tsquery and ts_rank. That handles word matching, stemming, phrases and ranking for a catalog or help center of modest size. It does not give you typo tolerance by default, faceting at scale or instant as-you-type results, and those are the usual reasons to add a search engine.

A working example

Say you have an articles table. Add a generated column that holds the search vector, then index it:

ALTER TABLE articles
  ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(body, '')),  'B')
  ) STORED;

CREATE INDEX articles_search_idx ON articles USING GIN (search);

A generated column is recomputed by Postgres whenever the row changes, so there is no trigger to maintain and no sync job to write. The weights make a title match count more than a body match.

Query it:

SELECT id, title, ts_rank(search, q) AS rank
FROM articles, websearch_to_tsquery('english', 'local storage "docker volume"') AS q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 20;

websearch_to_tsquery accepts the kind of input people type into a search box: plain words, quoted phrases, or and a leading minus for exclusion. Unlike to_tsquery it does not raise a syntax error on odd input, so it is safe to feed user text into it. Words are stemmed, so "volumes" matches "volume".

Add typo tolerance with trigrams

Full-text search needs the exact stem. For typos and partial words, the pg_trgm extension compares three-letter fragments:

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX articles_title_trgm ON articles USING GIN (title gin_trgm_ops);

SELECT title, similarity(title, 'postgress') AS sim
FROM articles
WHERE title % 'postgress'
ORDER BY sim DESC
LIMIT 10;

This is good for names and short titles. On long text it is less useful. Combine the two: try full-text first, and fall back to trigram similarity when it returns nothing.

Where it fits with Flisk

If your local database is the Postgres that Flisk provides, nothing extra runs. Declare a database resource and let services receive DATABASE_URL, as described in DATABASE_URL and env vars locally. Put the ALTER TABLE and CREATE INDEX statements in your migration, which belongs in an explicit migrator resource rather than in an API start script. Add the extension line to the same migration. The point of this article for a Flisk project is the negative one: before you add a search service to your stack, which costs memory and another service.json, check whether this query meets the need.

Test it with real data. Load a realistic volume with the approach in seed a local database and look at the query plan:

EXPLAIN ANALYZE SELECT id FROM articles WHERE search @@ websearch_to_tsquery('english', 'storage');

You want to see a Bitmap Index Scan on the GIN index. A sequential scan means the index is not used.

Pitfalls

  • The language configuration matters. 'english' removes stop words and stems English. For mixed or non-English content, use the matching configuration or 'simple' for no stemming. Use the same configuration at index and query time.
  • Ranking is basic. ts_rank counts term frequency. It has no notion of popularity, recency or learned relevance. If you need that, add your own factors to the ORDER BY or move to an engine.
  • Write cost. GIN indexes are slower to update than B-trees. Heavy write loads may need fastupdate tuning.
  • Prefix search. Search as you type needs to_tsquery('english', 'stor:*') syntax, which websearch_to_tsquery does not offer. Build the prefix query yourself and escape the user input.
  • Do not guess at scale. Measure on realistic data. A table that is fast with a thousand rows can behave differently with ten million.

When to move to a search engine

Move when you need typo tolerance across large text, faceted counts on many filters at once, as-you-type latency under load, synonyms and relevance tuning without writing SQL, or search over data that does not live in Postgres. At that point see Meilisearch or Typesense.

If you do add one, plan how the index stays correct: keep a search index in sync with the database.

Questions people ask

Is Postgres full-text search good enough for production?

For many catalogs, help centers and internal tools, yes. Check it against your data size and the features you need. Typo tolerance, large-scale faceting and relevance tuning are where it falls short.

Why use websearch_to_tsquery instead of to_tsquery?

It parses text the way a search box does and does not throw syntax errors on unusual input, so it is safe to use with raw user queries.

Do I need a trigger to keep the tsvector up to date?

Not with a generated column. Postgres recomputes it whenever the row changes.
