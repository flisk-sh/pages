How to expire unpaid orders and release the reserved stock

An abandoned checkout keeps stock locked. A small sweep job fixes that, as long as the query is safe when two copies run at once.

Give every order that waits for payment an expires_at time, and run a sweep that moves expired orders to expired and returns their reserved stock, all in one transaction. Make the sweep safe to run twice at once with FOR UPDATE SKIP LOCKED. To test it, set expires_at to the past instead of waiting for the clock.

Why you need it

When a customer starts checkout, you hold stock for them (see stopping overselling). If they close the tab, nothing tells you. Without a sweep the last three units of a popular item stay held for ever, and the shop looks sold out while nobody is buying. A fifteen to sixty minute hold is a common choice; the exact number is a business rule, so keep it in configuration.

Set the deadline when you create the order

ALTER TABLE orders ADD COLUMN expires_at timestamptz;
CREATE INDEX orders_expiry_idx ON orders (expires_at) WHERE status = 'pending_payment';

The partial index keeps the sweep fast, because it only covers orders that can still expire. When the order is created, set expires_at = now() + interval '30 minutes'. When payment is confirmed, the status changes and the order drops out of the index. If the customer opens the payment page again, you may extend the deadline once; decide that rule now, not during an incident.

The sweep query

Do the whole expiry in a single transaction, so an order is never marked expired without its stock coming back:

WITH due AS (
  SELECT id FROM orders
  WHERE status = 'pending_payment' AND expires_at < now()
  ORDER BY expires_at
  LIMIT 100
  FOR UPDATE SKIP LOCKED
), expired AS (
  UPDATE orders o SET status = 'expired', updated_at = now()
  FROM due WHERE o.id = due.id
  RETURNING o.id
)
UPDATE reservations r SET released_at = now()
FROM expired WHERE r.order_id = expired.id AND r.released_at IS NULL
RETURNING r.sku, r.qty;

SKIP LOCKED means that if a second sweep starts while the first is running, it skips rows the first one holds, so nothing is processed twice. LIMIT 100 keeps each transaction short; loop until the query returns no rows. Writing a row to order_events for each expired order, as in the state machine article, gives you a history. If you track stock with a reserved counter instead of a reservations table, decrement it in the same statement chain.

The race that matters: a payment confirmation arriving just as the sweep expires the order. The guarded status update decides the winner. If the payment loses, your handler sees "zero rows updated" and must refund or re-open the order. Plan that path, do not ignore it.

Where to run the sweep

Three honest options, in order of effort. Run it from a timer inside the API process (simple, but every API replica runs one, which is why you need SKIP LOCKED). Run it as a small worker with its own schedule. Or call it from an external scheduler in production. For local work, the best choice is a plain script you can run on demand, plus the timer if you want the full behaviour. Cron jobs in local development compares the options and covers time zones and overlapping runs.

Test it without waiting

Do not wait thirty minutes. Make the clock a parameter, or just edit the data. With Flisk, run the script inside the service so it uses the stack's DATABASE_URL:

flisk run orders-api -- bun run sweep

A good test sequence: create an order, check stock went down by its quantity, set expires_at to now() - interval '1 minute' in psql, run the sweep, and check that the order is expired and the stock is back. Then run the sweep again and check that nothing changes, which proves it is idempotent. The one-off command form is explained in running a one-off command in a service.

Pitfalls

  • Releasing stock twice. Guard on released_at IS NULL, as above, so a repeated run cannot add the stock back again.
  • Clock differences. Use now() from the database, not the application clock, so several API instances agree.
  • A stopped stack does not sweep. After a weekend with the laptop off, many orders expire at the first run. Your loop should handle a large backlog, which is what the batch limit is for.
  • Silent failures. Log how many orders each sweep expired. Zero for days on a busy shop means the job is not running.

Questions people ask

How long should an unpaid order be held?

Fifteen to sixty minutes is common. Shorter holds free stock sooner; longer holds are kinder to slow payers. Make it a setting.

What if payment succeeds after the order expired?

Treat it as a conflict. Either re-open the order if stock is still free, or refund the payment. The guarded status update tells you which case you are in.

Do I need a queue for the expiry job?

No. A periodic query is enough for most shops. A queue helps only if you want delayed messages per order.
