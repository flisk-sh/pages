E-commerce backends locally

How to run a storefront, orders API and database on one laptop

A shop backend is a few ordinary parts. Here is the shortest verified path to a running storefront, API and database, with the commands to check each one.

A small shop needs three things running together: a storefront the customer sees, an orders API, and a database. With Flisk you create each part with one command, start the stack with flisk up shop, and read the real URLs from flisk networks. This article uses a dry run first, so you can see what would start before anything does.

What you need

Flisk's container route needs Docker and Tilt on your machine, because it runs a database and a gateway. Install the CLI with npm install -g @flisk-sh/flisk and check your machine:

flisk doctor

If you want to try the tool before building anything, npx @flisk-sh/flisk demo starts a sample app. Without a stack of your own in mind, the plain alternative is a Compose file with three services; the trade-offs are covered in Docker Compose alternatives for local development.

Create the parts

In an empty folder:

flisk project --yes
flisk resource storefront --type frontend --stack shop --yes
flisk resource orders-api --type backend --stack shop --feature drizzle --yes
flisk resource shop-db --type database --stack shop --yes

This creates a Flisk project and three folders under services/shop/, each with its own service.json. The storefront is a Vite frontend (React by default). The orders API is a Bun and Hono backend, and --feature drizzle adds a database client in src/db.ts that reads DATABASE_URL, a drizzle.config.ts and an empty src/schema.ts for your tables. The shop-db resource does not start a container of its own: it declares the shared Postgres that Flisk runs for the project. Its output reminds you to add the database to dependsOn:

"appName": "orders-api",
"dependsOn": ["shop-db"]

Edit services/shop/orders-api/service.json and add that line. The generated backend also has /health, /health/live, /health/ready and /health/db routes, which is what makes the checks below possible.

Prefer another backend? Run flisk resource orders-api --type backend --frameworks to list the real choices (Hono, Express, Fastify, NestJS, Koa, h3 and Elysia on Bun), and --language python, go, rust or node for other runtimes. Pass --feature prisma instead of Drizzle and Flisk also writes a separate migrator resource that runs prisma migrate deploy before the API starts.

See the plan, then start

flisk config verify
flisk up shop --dry-run
flisk up shop

config verify checks that the generated files match your service.json files. The dry run lists the services it would start, the URL of each API and the host ports it chose (Flisk falls back to a free port if 80, 443 or 5432 are taken). flisk up shop then starts the stack and stays in the foreground, so use a second terminal for the next commands.

Check each part

flisk status
flisk networks --stack shop

flisk networks prints the routed URLs. The API URL has the shape http://api.<project>.localhost:<port>/api/orders-api, so the health route is .../api/orders-api/health and the database check is .../api/orders-api/health/db:

curl -s "$(flisk networks --stack shop --raw | head -n 1)"

Use the URLs the command prints and not the ones in this text, because the project name and port are yours. If one fails, flisk logs --service orders-api shows the service's output; the general method is in debugging a service that will not start. Stop everything with flisk down. Your database data stays, and only flisk down --purge deletes it.

What to add next

Write the tables in src/schema.ts and keep real schema changes in migrations, not in the start script; migrations in local dev shows how. Then add the pieces a shop needs, one at a time:

  • A cart in Redis: flisk resource cache --type database --framework redis --stack shop --yes, as in choosing where to store the cart.
  • Stock that cannot go negative: stopping overselling.
  • Believable test data: generating shop data.

When this is not the right fit

If your shop is already a Compose project, import it instead of rewriting it; see importing a docker-compose.yml. If you build on a hosted platform such as Shopify, you do not run a backend yourself. And Flisk is a local tool: it does not deploy your shop, so production hosting stays a separate decision.

Questions people ask

Do I need Docker to run this stack?

The database and gateway run in containers, so yes. A project of plain local processes needs no Docker, but it has no database resource.

Where does the storefront find the API?

The frontend scaffold can use a generated API client, and the API is reachable through the URL that flisk networks prints.

Does flisk down delete my data?

No. The Postgres volume is kept. Only flisk down --purge removes volumes.
