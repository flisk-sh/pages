How to paginate order history without OFFSET in Postgres

OFFSET gets slower on every page and skips rows when new orders arrive. Keyset pagination reads a fixed amount each time and does not lose its place.

Paginate with a cursor made of the last row's sort keys, not with OFFSET. For an order list sorted newest first, ask for rows where (created_at, id) is less than the cursor, ordered the same way, with a composite index that matches. Each page costs about the same however deep you go, and new orders arriving do not shift the pages.

What is wrong with OFFSET

A query such as ORDER BY created_at DESC LIMIT 20 OFFSET 10000 makes Postgres produce and discard 10,000 rows before returning 20. The cost grows with the page number. It also drifts: if a new order arrives while the customer is on page 2, every row moves one place and page 3 repeats the last row of page 2. For a customer with 30 orders none of this matters. For an admin screen over millions of orders, or an API someone scripts against, it does.

Keyset pagination in SQL

Sort by a column that is unique when combined with the id, because many orders can share one timestamp. Use both in the sort and in the cursor:

-- first page
SELECT id, created_at, status, total_minor
FROM orders
WHERE customer_id = $1
ORDER BY created_at DESC, id DESC
LIMIT 21;

-- next page: $2 and $3 come from the last row of the previous page
SELECT id, created_at, status, total_minor
FROM orders
WHERE customer_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 21;

The pair comparison (created_at, id) < ($2, $3) compares the first value, and the second only on a tie. That is exactly the order of the sort, so no row is missed or repeated. Ask for one more row than the page size (21 for 20). If you get 21, there is a next page, and you return only 20 of them.

The index must match the sort so Postgres can walk it directly:

CREATE INDEX orders_customer_created_idx
  ON orders (customer_id, created_at DESC, id DESC);

The cursor in your API

Do not expose raw column values as the contract. Encode them into one opaque string, so you can change the sort later:

const encode = (c: { t: string; id: number }) =>
  Buffer.from(JSON.stringify(c)).toString("base64url");
const decode = (s: string) => JSON.parse(Buffer.from(s, "base64url").toString());

// response: { items: [...], next: encode({ t: last.created_at, id: last.id }) }
// request:  GET /orders?limit=20&after=<cursor>

Validate the cursor on input: reject anything that does not decode to the expected shape, and cap limit (for example at 100). Pass the timestamp back as it came from the database, with its full microsecond precision, or you will skip rows that share a rounded timestamp.

Check the plan, not the guess

Run EXPLAIN (ANALYZE, BUFFERS) on both queries against a large table. With the index above you should see an index scan that stops after 21 rows. With OFFSET you will see it read far more. The difference only shows on lots of rows, so load a big seed first; generating realistic shop data shows how to create 100,000 orders in seconds. If your local Postgres runs in Flisk, open a psql session with docker exec -it my_shop_postgres psql -U my_shop -d my_shop_shop (the names follow the project and stack, see connecting to a local database), and paste the queries there.

Trade-offs

  • No "jump to page 50". Cursors only go forward and back. If the admin UI needs page numbers, OFFSET is acceptable for small, filtered sets.
  • Changing the sort. Each sort order needs its own index and cursor shape. Sorting by total value needs (total_minor, id).
  • Total counts. COUNT(*) on a big table is slow. Show "more than 1,000" or an estimate, or cache the count.
  • Mixed sort directions. A row comparison needs the same direction on every column. If you need created_at DESC, id ASC, write the condition as an explicit OR expression.

For the order list to be useful, orders must also have clean statuses; see modelling order statuses.

Questions people ask

Is OFFSET ever fine?

Yes, for small tables or admin screens with filters that keep the result set small. The problems appear with deep pages on large tables.

Why include id in the sort?

Many rows can share one created_at value. Without the id as a tie-breaker, pages can repeat or skip rows.

Can I paginate backwards?

Yes. Flip the comparison and the sort, fetch the rows, then reverse them in code.
