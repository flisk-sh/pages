How to model order statuses as a state machine in Postgres

Most order bugs are a status that moved when it should not. Write the allowed moves down, enforce them in one place and keep a log of every change.

Model order status as a small state machine: a fixed list of states, a table of allowed moves, and one function that performs every change with a guarded UPDATE. The guard (WHERE status = 'expected_current_state') means two competing requests cannot both win. Add an events table and you get a full history for free.

Keep the list of states short

A typical shop needs fewer states than people expect. A workable set:

  • pending_payment: the order exists and stock is held.
  • paid: money is confirmed.
  • fulfilling: the warehouse or your code is packing it.
  • shipped and delivered.
  • cancelled and expired: terminal, stock released.
  • refunded: terminal, after paid or later.

Resist adding a state for every screen in the admin. A flag such as gift_wrap is not a state. If you find yourself writing status = 'paid_but_waiting_for_address', that is a second field.

Write the allowed moves as data

Put the transitions in one place, as a map your code reads and your tests iterate over:

export const NEXT: Record<string, string[]> = {
  pending_payment: ["paid", "cancelled", "expired"],
  paid: ["fulfilling", "refunded", "cancelled"],
  fulfilling: ["shipped", "cancelled"],
  shipped: ["delivered", "refunded"],
  delivered: ["refunded"],
  cancelled: [],
  expired: [],
  refunded: [],
};

Terminal states have an empty list. That one line prevents a whole family of bugs, such as a late "payment succeeded" message reviving an order you already cancelled and released.

Change status with a guarded UPDATE

The only way status should change is through one function. It checks the map, then updates with the current state in the WHERE clause, in the same transaction as the history row:

BEGIN;
UPDATE orders
SET status = 'paid', updated_at = now()
WHERE id = $1 AND status = 'pending_payment';
-- affected rows = 0 means someone else moved it first: stop here
INSERT INTO order_events (order_id, from_status, to_status, actor, created_at)
VALUES ($1, 'pending_payment', 'paid', $2, now());
COMMIT;

If the update touches zero rows, do not insert the event and do not treat it as a crash. Return a clear "already changed" result. The caller decides whether that is fine (a duplicate message) or a conflict (two admins clicking at once). The same guard makes retries safe: sending "mark as paid" twice moves the order once.

Add the table that records the history:

CREATE TABLE order_events (
  id          bigserial PRIMARY KEY,
  order_id    bigint NOT NULL REFERENCES orders(id),
  from_status text NOT NULL,
  to_status   text NOT NULL,
  actor       text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON order_events (order_id, id);

Later, when a customer asks why an order was cancelled, the answer is one query.

Use a CHECK or an enum for the values

Constrain the column so a typo cannot become a state. A CHECK (status IN (...)) is easier to change than a Postgres enum, because adding a value to a CHECK is a normal migration, while enum changes have extra rules. Postgres cannot easily express "only these transitions" in a constraint; a trigger can, but most teams keep the transition rule in application code and the allowed values in the schema.

Test every move, with and without the database

Two kinds of test pay off. First, a pure test over the map: for each state and each target, assert that the function accepts the listed moves and rejects the rest. It runs in milliseconds and needs no database. Second, a test against real Postgres for the guard: call "mark as paid" twice in parallel and assert exactly one event row.

For the second test with Flisk, create the API and the shared database as in stopping overselling, keep the DDL above in a migration, and put the test in a script you run inside the service:

flisk run orders-api -- bun test

That runs the command with the service's environment, including its DATABASE_URL, so the test hits the same Postgres your API uses. Use a separate database or schema for tests if the data matters, and see integration tests against the real stack for the options.

Pitfalls

  • Status set in several places. Webhook handlers, admin screens and jobs each running UPDATE orders SET status = ... is how invalid states appear. Search your code for it.
  • Timestamps instead of states. paid_at and shipped_at columns are useful, but derive them from the events, or set them in the same function.
  • Cancelling a shipped order. Decide the rule now. In the map above a shipped order can only be refunded, which forces a return flow.
  • One giant state for everything. Keep payment, fulfilment and shipping as separate fields on bigger systems, so they can move on their own.

Once statuses are safe, the next common failure is an order that sits in pending_payment forever and holds stock. Expiring unpaid orders covers it.

Questions people ask

Should I use a Postgres enum for order status?

A CHECK constraint on a text column is simpler to change. Enums work, but adding or removing values needs more care in migrations.

Do I need an event table if I have updated_at?

Yes, if you ever need to answer who changed the status and when. updated_at only keeps the last change.

Can a database trigger enforce the transitions?

It can, and it is a good safety net. Most teams keep the rule in application code where it is easier to test, and add a trigger only for critical paths.
