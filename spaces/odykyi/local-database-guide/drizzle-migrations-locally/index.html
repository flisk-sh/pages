Drizzle migrations in local development with Postgres

Drizzle splits schema changes into generate, migrate and push. Here is which to use locally, and how to run the migration step before your API starts.

With Drizzle, edit your schema file, run drizzle-kit generate to write a SQL migration, and run drizzle-kit migrate to apply it. Use drizzle-kit push only for quick prototypes, because it changes the database without leaving a migration file behind.

The commands that matter locally

CommandWhat it doesUse it for
drizzle-kit generateCompares your schema with the previous snapshot and writes a SQL file into the out folderEvery schema change you keep
drizzle-kit migrateApplies the SQL files that the database has not seen yetLocal runs, CI, a migration job
drizzle-kit pushSyncs the database to the schema directly, with no migration fileThrowaway prototypes
drizzle-kit studioOpens a browser UI over your dataLooking at rows

There is no built-in reset command. To start over you drop and recreate the database, then run migrate again. That is covered in how to reset a local database.

A minimal drizzle.config.ts for Postgres reads the URL from the environment:

import { defineConfig } from "drizzle-kit";

export default defineConfig({
  dialect: "postgresql",
  schema: "./src/schema.ts",
  out: "./drizzle",
  dbCredentials: { url: process.env.DATABASE_URL as string },
});

Commit the drizzle folder. It holds the SQL files and the snapshots that generate diffs against.

The Flisk way

Add Drizzle to a service with the feature flag:

flisk resource orders-api --type backend --stack shop --feature drizzle --yes

That writes a drizzle.config.ts like the one above, a src/db.ts that builds a pg pool and wraps it with drizzle-orm/node-postgres, and an empty src/schema.ts. It also adds drizzle-orm and drizzle-kit to the dependencies.

What it does not do is create a migrator. Unlike the Prisma feature, the Drizzle feature does not add a one-shot migration resource and does not add Postgres to dependsOn for you. Two things follow:

  • You must make sure the service can reach a database. List a database resource in dependsOn, for example one created with flisk resource shop-db --type database --stack shop, and the service receives DATABASE_URL.
  • You must run migrations yourself, either from your terminal or from a job you register.

From your terminal, the shared Postgres is on 127.0.0.1:15432 by default, so with the stack up you can run:

DATABASE_URL="postgresql://USER:PASSWORD@127.0.0.1:15432/DBNAME?sslmode=disable" \
  npx drizzle-kit migrate

Fill in the user, password and database name from your project. Connecting from your machine shows where each value lives.

Run migrations as a job before the API

To make flisk up apply migrations without you, use a bring-your-own one-shot job. The Flisk repository ships a working example in examples/byo-jobs/drizzle. Its container command is:

node ensure-db.js && npx drizzle-kit migrate

The first step exists because Flisk does not create a database for a bring-your-own job. ensure-db.js creates the database if it is missing, removes a trailing ?schema=public from the URL if there is one, and appends ?sslmode=disable. Register the job so it never restarts after finishing:

flisk resource drizzle-migrate --type bring-your-own --stack shop \
  --dockerfile ./Dockerfile --restart no --register-existing --yes

Without "restart": "no" in its service.json, Docker starts the finished job again and again. Then add drizzle-migrate to the API's dependsOn, so the API waits for it. The reasoning behind a separate job is in database migrations in local dev.

A normal day

Edit src/schema.ts, run generate, open the new SQL file and read it, then run migrate. Reading the SQL is the habit that pays off: Drizzle may turn a rename into a drop and an add, which loses the column's data, and the file shows you that before it runs. Commit the schema change and the SQL together in one commit so teammates apply both at once.

Pitfalls

  • Using push, then switching to migrate. A database built with push has no migration history. When you later run migrate, it tries to create tables that already exist. Pick one approach per database, and reset the database when you switch.
  • Forgetting to generate. Changing schema.ts does nothing to the database until you run generate and then migrate.
  • SSL errors. The local Postgres has no SSL, and some drivers try it by default. Add ?sslmode=disable to the URL.
  • Editing generated SQL after it ran. Treat applied migration files as read-only and write a new one.
  • Seeds. Drizzle has no seed command. Write a script, or use plain SQL as in seed a local database.

If you are choosing between the two ORMs, Prisma migrations locally shows the other flow side by side. If a worker shares the same database, see worker and API sharing a database.

Questions people ask

Should I use drizzle-kit push or migrate locally?

Use migrate for anything you want to keep, because it leaves SQL files in version control. push is fine for a prototype you will throw away, but a database built with push has no migration history.

Does Flisk create a migrator for Drizzle?

No. The drizzle feature writes the config, a db module and a schema file, but no migration resource. Run migrations from your terminal or register a bring-your-own one-shot job.

Why does my Drizzle job fail on SSL?

The local Postgres has no SSL. Add ?sslmode=disable to the connection URL.
