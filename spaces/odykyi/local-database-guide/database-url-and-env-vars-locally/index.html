DATABASE_URL and env vars in local development

Keep the values in one place, read them in code, and never copy a URL between environments. Here is how that looks with and without Flisk.

Keep local settings in one gitignored file, read them in your code through process.env (or your language's equivalent), and commit only an example file with fake values. For DATABASE_URL, let your tooling inject it into each service so nobody pastes it by hand.

The general approach

A reliable layout has three layers:

  1. .env.example, committed, with names and harmless placeholder values.
  2. .env, gitignored, with your real local values.
  3. The process environment, which wins over both when you set a variable on the command line.

In Compose, env_file: loads the second layer into a container. In a plain Node project, a loader such as dotenv or the --env-file flag does it. Whatever you pick, read the variable in one module, check that it exists at startup and fail with a clear message if not. A missing DATABASE_URL that surfaces as "cannot read properties of undefined" three layers deep wastes an hour.

Two rules save most grief. First, never hard-code a host in code: the host differs between your laptop (127.0.0.1) and a container (the service name). Second, treat a local password as non-secret and a production password as secret, and never let them share a file.

The Flisk way

Flisk has a project-level .env with a few generated keys: TILT_ENV, DB_PASSWORD, DATABASE_URL and JWT_SECRET. It is created for you and meant to stay on your machine. The parser accepts the common Compose-style syntax, but does no interpolation, so write plain KEY=value lines.

Services then get their variables from their service.json, in a few forms:

  • Injected URLs. A service that lists postgres, a database resource or a migrator that waits on it in dependsOn receives DATABASE_URL pointing at the shared Postgres. A bring-your-own container gets one only if its dependsOn names a database, or it sets databaseName. Anything under the service's own env wins over the injected value, so setting DATABASE_URL there overrides it.
  • params are non-secret strings written to a generated env file. A literal $ is doubled to $$ in that file, so values with a dollar sign survive. The older envVars field is deprecated.
  • secrets hold names only. The value stays in the project .env, so service.json can be committed without leaking anything.
  • Local-process env maps accept ${VAR} and ${VAR:-default}, for services that run as plain processes through command.
{
  "appName": "orders-api",
  "appType": "backend",
  "stack": "shop",
  "dependsOn": ["shop-db", "cache"],
  "params": { "LOG_LEVEL": "debug" },
  "secrets": ["JWT_SECRET"]
}

With that manifest, orders-api receives DATABASE_URL from the database resource, REDIS_URL from the cache, a plain LOG_LEVEL, and a JWT_SECRET whose value comes from .env. Create the database resource with flisk resource shop-db --type database --stack shop. Declaring one starts Postgres even when you pass --no-database.

Run against a different set of values

To run an integration pass with other settings, point flisk up at another file:

flisk up --env-file .env.integration

The file replaces the project .env for that run. It must sit inside the project and contain TILT_ENV, DB_PASSWORD and JWT_SECRET. Flisk refuses it while the stack is already running, so run flisk down first or add --force. Note that a different DB_PASSWORD does not change an existing database volume, so the new password only works on a fresh one. Pair it with integration tests against the real stack.

Reading the value in code

Read each variable once, in a small config module, and import that module everywhere else. Validate it right there: check that DATABASE_URL exists and starts with postgresql:// or postgres://, and throw a message that names the variable. Do not log the whole URL, because it contains the password. If you must log it, print the host and database name only.

Pitfalls

  • Variable not reaching the service. Edit the manifest, then run flisk config regenerate and flisk config verify, and restart the resource with flisk restart orders-api. Generated files are output, so change the source service.json instead of them. If it still is missing, read environment variable not loaded.
  • Password mismatch. If the password inside DATABASE_URL differs from DB_PASSWORD, logins fail. flisk doctor reports it.
  • Secrets in params or provides. Both land in plain-text generated files. Use secrets for anything sensitive.
  • Prisma suffix. A ?schema=public ending breaks non-Prisma tools. See connecting from your machine.
  • Committing .env. Check git status before every commit.

To give each service its own database inside this arrangement, continue to one database per service.

Questions people ask

How does a service get DATABASE_URL in Flisk?

List postgres, a database resource or a migrator that depends on it in dependsOn. Flisk then injects DATABASE_URL. A value in the service's own env overrides the injected one.

Where do secrets go?

Put the names in the secrets array of service.json and the values in the project .env, which stays out of git.

Can I use a different env file for one run?

Yes: flisk up --env-file .env.integration. The file must be inside the project and contain TILT_ENV, DB_PASSWORD and JWT_SECRET.
