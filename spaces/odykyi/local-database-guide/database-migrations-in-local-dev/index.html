Databases in local development

Run database migrations in local dev with a migrator

Migrations belong in their own step. Here is why, how to wire the order by hand, and how a Flisk migrator resource does it for you.

Run migrations as a separate one-shot job that applies the pending changes and exits, and make your API start only after that job succeeds. Do not put the migration command in the API's start script. In Flisk that job is a resource with appType set to migrator, and the API lists it in dependsOn.

Why not migrate from the API start script

The shortcut is "start": "prisma migrate deploy && node server.js". It works on day one and causes trouble later:

  • Every restart of the API runs the migration again, including restarts caused by a hot reload.
  • If you run two copies of the API, both try to migrate at once. Most tools take a lock, but a failed lock shows up as a crashing API.
  • A failing migration looks like a crashing API, so you read the wrong logs first.
  • The API image needs the migration tooling and its permissions, which production often does not want.

A separate job has one purpose, one exit code and one log. It runs, it finishes with 0 or fails loudly, and the API either starts or does not.

The general pattern without Flisk

In Docker Compose you express this with a one-shot service and a dependency condition:

services:
  migrate:
    build: ./api
    command: npx prisma migrate deploy
    restart: "no"
    depends_on:
      db:
        condition: service_healthy
  api:
    build: ./api
    depends_on:
      migrate:
        condition: service_completed_successfully

The two details that people miss are restart: "no", because the default restart policy would start a finished job again and again, and service_completed_successfully, because service_started only waits for the container to exist.

The Flisk way

Flisk scaffolds this pair when you enable the Prisma feature:

flisk resource orders-api --type backend --stack shop --feature prisma --yes

That creates two folders under services/shop/: orders-api and orders-api-migrator. The migrator manifest waits for Postgres:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-api-migrator",
  "appType": "migrator",
  "stack": "shop",
  "featuresEnabled": ["prisma"],
  "dependsOn": ["postgres"]
}

and the API waits for the migrator:

"appName": "orders-api",
"appType": "backend",
"dependsOn": ["orders-api-migrator"]

Read it from the bottom up: the API needs the migrator, the migrator needs Postgres, so the order is Postgres, migrator, API. The migrator's start script is prisma migrate deploy. Flisk gives a migrator a one-shot container with restart: "no", no port, no health check and no route. It is ready when it exits 0, and any other exit code counts as a failure. When it fails, the services after it are not started. Tilt shows an orders-api-migrator-done resource for the wait.

Run flisk config verify after editing the manifests. It catches a dependsOn name that matches no service.

Other migration tools

The Prisma scaffold is the only one that writes a migrator for you. For Drizzle, Atlas, dbmate or anything else, register your own job as a bring-your-own resource with a restart policy of no:

flisk resource migrate --type bring-your-own --stack shop \
  --dockerfile ./Dockerfile --restart no --register-existing --yes

A service that lists migrate in dependsOn then waits for it to exit 0. The Flisk repository has runnable job examples for dbmate, Atlas, Drizzle and MikroORM under examples/byo-jobs/. A bring-your-own job has no database created for it, so your job must create the database if it is missing and wait for Postgres to accept connections. The examples do both.

Pitfalls

  • Re-running after a fix. After a migration fails and you fix it, restart the migrator resource (flisk restart orders-api-migrator or the button in Tilt). Restarting only the API will not run the migrator again.
  • Destructive migrations. A migrator that drops a column runs on every flisk up that starts it. Keep local data disposable, and read how to reset a local database before you need it.
  • Two sources of schema. The Prisma scaffold writes a prisma/schema.prisma in both the API and the migrator folder. Pick one place to edit and keep the other identical, or the client and the applied migrations drift apart.
  • Not yet verified by Flisk's own docs. The docs state that Tilt holds the API until the migrator exits, but mark that as not checked against a live stack. Watch the first run of your own project.

For the tool-specific steps, continue with Prisma migrations locally or Drizzle migrations locally. For ordering beyond databases, see service startup order.

Questions people ask

Why not run migrations when the API starts?

Each API restart would re-run them, parallel instances would race, and a migration failure would look like an API crash. A one-shot job has one purpose and one exit code.

What does appType migrator do in Flisk?

It creates a one-shot container with restart no, no port and no route. It counts as ready when it exits 0, and services that depend on it start only after that.

Can I use a migration tool other than Prisma?

Yes. Register your own job as a bring-your-own resource with --restart no and list it in dependsOn. The repository has examples for dbmate, Atlas, Drizzle and MikroORM.
