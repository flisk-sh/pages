Databases in local development

Connect to a local Postgres database from your machine

Four values and one address rule are enough to connect from any tool. The address rule is the part people get wrong.

To connect from your own machine you need five values: host, port, user, password and database name. If Postgres runs in Docker with a published port, the host is 127.0.0.1 and the port is the one on the left of the -p mapping. With Flisk's shared Postgres, the port is 15432 unless that was busy.

The connection string

Every client accepts the same URL form:

postgresql://USER:PASSWORD@HOST:PORT/DATABASE

With psql, pass it directly: psql "postgresql://app:secret@127.0.0.1:5432/myapp". GUI tools such as TablePlus, DBeaver or the database panel of an IDE ask for the same five fields in a form. If the password has characters such as @ or /, percent-encode them in the URL, or type the fields separately.

The local server has no SSL, and some clients try it first. If you see an SSL error, add ?sslmode=disable to the URL or switch the SSL option off in the GUI.

Two addresses for the same database

This is the rule that explains most "connection refused" reports. The database has two addresses and each one only works from one place.

Where the client runsHostPort
Your laptop (psql, GUI, host-side scripts)127.0.0.1The published port, for example 15432
Another container on the same Docker networkThe container or service name, for example postgres5432, the port inside the container

Inside a container, 127.0.0.1 is that container itself. On your laptop, the name postgres does not resolve. Services get the right form for them in DATABASE_URL. Copying that same URL into a GUI on your laptop will not work.

The Flisk way: finding each value

Flisk runs one Postgres container per project, and every value has a known place.

  • Host and port. It is published on 127.0.0.1 at port 15432 by default. If that port is taken, Flisk picks the next free one in the range 15432 to 15532. Check the real mapping with docker ps, where the PORTS column shows 127.0.0.1:15432->5432/tcp. You can pin a port with the FLISK_POSTGRES_PORT variable. The bind address defaults to loopback, so nothing on your network can reach it.
  • User. The superuser is named after your project, with dashes replaced by underscores. Project my-shop gives my_shop.
  • Password. It is DB_PASSWORD in the .env file at the project root. Flisk generates it once and does not rotate it. Open the file yourself and read the value there. The file is for your machine only, so keep it out of version control and chat.
  • Database name. Each stack gets its own database. For project my-shop and stack store the documented name is my_shop_store. The service manifest reference gives the default as FLISK_{stack}, so do not trust either from memory. List what exists:
docker exec my_shop_postgres psql -U my_shop -d postgres -c "\l"

The container is named <project>_postgres with underscores, which is the name used in the commands above. Once you know the values:

psql "postgresql://my_shop:PASSWORD@127.0.0.1:15432/my_shop_store?sslmode=disable"

Replace PASSWORD with the value from .env. If you do not want a password in your shell history, use docker exec -it my_shop_postgres psql -U my_shop -d my_shop_store, which needs no password from inside the container and no published port at all.

If the connection fails, run flisk doctor. It warns when the DATABASE_URL password differs from DB_PASSWORD.

Pitfalls

  • The URL suffix ?schema=public. Flisk's DATABASE_URL can carry it for Prisma. psql and many GUIs reject it as an unknown parameter. Remove it.
  • Port conflicts. If a native Postgres is on 5432, do not assume you reached the container. Check the port in docker ps. For a clash, see how to fix "port already in use".
  • Stack not running. The port is published only while the container runs. flisk up first.
  • Running without Docker. Services that run as plain local processes have no Flisk database. Start Postgres yourself and pass its URL in the service's env.
  • Wrong password after a change. The password in an existing volume is the one from first start. See how to reset a local database.

When not to expose it

If you only need to run a query now and then, docker exec is enough and exposes nothing. Keep the loopback binding. Binding to every interface with FLISK_BIND_ADDRESS is for a deliberate case such as a second device on a trusted network, because the development password is easy to guess.

Questions people ask

Which port does Flisk's Postgres use on my machine?

15432 by default, bound to 127.0.0.1. If it is busy, Flisk picks the next free port up to 15532. Confirm with docker ps.

Where is the Postgres password?

DB_PASSWORD in the project .env file. Flisk generates it once and does not rotate it.

Why can't I use postgres as the host from my laptop?

That name resolves only inside the Docker network. From your laptop use 127.0.0.1 and the published port.

Why does psql reject my DATABASE_URL?

It may end in ?schema=public, a Prisma parameter. Remove it and add ?sslmode=disable.
