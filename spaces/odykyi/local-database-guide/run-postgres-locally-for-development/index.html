Databases in local development

How to run Postgres locally for development

You need a real Postgres that starts fast, keeps its data and does not fight with other projects. Here is how to get one, with and without Flisk.

The quickest way to run Postgres for development is one Docker command that publishes port 5432 and mounts a named volume, so the data survives a restart. A native install (Homebrew, apt) also works and needs no Docker. Pick one, set a password, and write down the connection string your app will use.

Option 1: a native install

On macOS, brew install postgresql@16 followed by brew services start postgresql@16 gives you a server on port 5432. On Debian or Ubuntu, sudo apt install postgresql does the same. The upside is that nothing sits between you and the database. The downside is that every project on the machine shares one server and one version, and upgrading the major version means migrating the data directory.

Option 2: one Docker command

For a throwaway or per-project server, run the official image:

docker run -d --name myapp-pg \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=dev-only-password \
  -e POSTGRES_DB=myapp \
  -p 127.0.0.1:5432:5432 \
  -v myapp_pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

Three details matter. First, 127.0.0.1:5432:5432 publishes the port on your machine only. Plain 5432:5432 listens on every interface, which is rarely what you want on a laptop on shared Wi-Fi. Second, the named volume is what keeps your data when you remove the container. Without -v, deleting the container deletes the database. Third, pin the major version (16), so a later docker pull does not hand you a data directory your server cannot read.

Check that it is ready with docker exec myapp-pg pg_isready -U app -d myapp. Your connection string is postgresql://app:dev-only-password@127.0.0.1:5432/myapp.

The Flisk way: one shared Postgres per project

If your project already runs several services, you do not want to start Postgres by hand and copy its URL into each service. Flisk runs one Postgres container for the whole project and gives each service a DATABASE_URL that points at it. Install it with npm install -g @flisk-sh/flisk, then create a service that needs a database:

flisk resource orders-api --type backend --stack shop --feature prisma --yes
flisk up shop

The scaffold writes a migrator next to the API, and the migrator lists postgres in dependsOn, which is what tells Flisk to start the database. You can also declare it explicitly with flisk resource shop-db --type database --stack shop. That resource gets no container of its own: it names the shared Postgres.

What you get, read from the generated Compose file and the Flisk docs:

  • The image is postgres:16-alpine, with a health check based on pg_isready.
  • The host port is 15432 by default, bound to 127.0.0.1. Flisk does not use 5432, so a Postgres you installed natively does not collide with it. Set FLISK_POSTGRES_PORT to pin another port.
  • The superuser is named after the project, and the password is DB_PASSWORD in the project .env, generated once per project.
  • Data lives in a named volume, and flisk down keeps it. Only flisk down --purge deletes it.
  • SSL is off, so clients that insist on it need ?sslmode=disable on the URL.

Each stack gets its own database inside that one server, so two stacks do not see each other's tables. See one database per service for how to split further.

Pitfalls

  • Port already in use. If something else holds 5432 (or 15432), the container fails to start. Find the owner with lsof -i :5432, or pick another host port. The general fix is in how to fix "port already in use".
  • Changing the password later does nothing. The POSTGRES_PASSWORD variable is read only when the data directory is empty. If you change it after the first start, the old password stays in the volume. Flisk behaves the same way: a different DB_PASSWORD does not change an existing database, and flisk doctor warns when DATABASE_URL and DB_PASSWORD disagree.
  • Version drift. Run the same major version locally as in production. Postgres 16 and 17 differ in small ways that show up as a failing migration on deploy day.
  • Passwords in the repo. A development password is not a secret, but do not commit it next to a production one. Keep the project .env out of version control.

When this is not the right fit

If you have a single script and a single table, a SQLite file is simpler than any server. If your app uses managed Postgres features (extensions that only exist on one cloud, for example), run the closest image you can find rather than the stock one. And if you run Flisk without Docker, with plain command services, there is no database at all: that mode is for apps that do not need one, so start Postgres yourself and pass its URL in env.

Check that it works

Before you point an app at the server, prove it accepts queries. Run docker exec -it myapp-pg psql -U app -d myapp -c "select version();" and read the version line. If it prints, the server, user, password and database name are all correct, and any later failure is in your app's configuration. Do this once per new project, because it separates a database problem from an app problem in about ten seconds.

Questions people ask

Which port does Postgres use locally?

Postgres listens on 5432 by default. Flisk publishes its shared Postgres on 15432 instead, so it does not clash with an installed server. Set FLISK_POSTGRES_PORT to choose another.

Does the data survive when I stop the container?

Only if you mounted a named volume at /var/lib/postgresql/data. With Flisk, flisk down keeps the volume and flisk down --purge deletes it.

Should I use Docker or a native install?

Docker is easier when you work on several projects or need to match a production major version. A native install is fine for one project and avoids Docker overhead.
