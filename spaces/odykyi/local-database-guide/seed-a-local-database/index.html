How to seed a local database with test data

A good seed can run twice without breaking anything. Here is how to write one, and three ways to run it against a local database.

Write the seed as a script that is safe to run more than once, then run it after your migrations. Plain SQL with ON CONFLICT DO NOTHING is the simplest form. Flisk has no flisk db seed command, so you run the script with docker exec or as a one-shot job.

Write a seed you can run twice

The mistake that costs the most time is a seed that inserts rows blindly. The second run fails on a unique key, or worse, doubles your data. Give every seeded row a fixed key and skip rows that exist:

-- seed.sql
INSERT INTO customers (id, email, name) VALUES
  (1, 'ada@example.test', 'Ada'),
  (2, 'grace@example.test', 'Grace')
ON CONFLICT (id) DO NOTHING;

INSERT INTO products (id, sku, price_cents) VALUES
  (1, 'MUG-01', 1200),
  (2, 'TEE-01', 2500)
ON CONFLICT (id) DO NOTHING;

Use fake addresses on a domain such as example.test so no test email can ever reach a real person. Keep the seed small. Ten well-chosen rows that cover the awkward cases (an empty order, a long name, a refunded payment) find more bugs than ten thousand random ones.

If your ORM owns the schema, you can seed through it. Prisma runs prisma db seed, which executes the command you set under prisma.seed in package.json. In Prisma 7 the seed no longer runs automatically after migrate dev or migrate reset, so call it yourself. Use upsert in the script so it stays repeatable. Drizzle has no seed command, so a small script that calls db.insert(...).onConflictDoNothing() does the same job.

Run it by hand

With Postgres in a container, pipe the file in:

docker exec -i my_shop_postgres \
  psql -U my_shop -d my_shop_store -v ON_ERROR_STOP=1 < seed.sql

The -i flag lets the container read your file from standard input. ON_ERROR_STOP=1 makes psql exit non-zero on the first error, instead of printing it and carrying on. That flag is what lets a script or CI notice a failed seed.

The Flisk way

The names in the command above follow the Flisk convention: for a project called my-shop with a stack called store, the container is my_shop_postgres, the superuser is my_shop and the database is my_shop_store. Confirm yours with docker ps and, inside psql, with \l. The stack stays up, so nothing needs a restart.

To make the seed part of flisk up, turn it into a one-shot job. Create a folder with the SQL, a script and a Dockerfile that has psql in it:

services/store/seed/
  seed.sql
  seed.sh
  Dockerfile        # FROM alpine, apk add postgresql-client
  service.json

The service.json makes it run once, after Postgres:

{
  "appName": "seed",
  "appType": "bring-your-own",
  "stack": "store",
  "restart": "no",
  "dependsOn": ["postgres"]
}

In seed.sh, call psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f seed.sql. A bring-your-own container receives DATABASE_URL because it depends on postgres. Register it with flisk resource seed --type bring-your-own --stack store --dockerfile ./Dockerfile --restart no --register-existing --yes.

Two cautions, both from the Flisk docs. First, the order of the seed job relative to the migrator and the API is not guaranteed, so the seed has to cope with a table that does not exist yet. The simplest fix is to list the migrator in the seed's dependsOn too. Second, the documented example was checked in pieces and not end to end through flisk up, so run it once and read flisk logs --service seed before you rely on it. If DATABASE_URL ends in ?schema=public, strip that suffix, because psql rejects it.

Pitfalls

  • Seeding production by accident. Gate the seed on an environment check, or keep it in a folder that only the local stack registers.
  • Hard-coded IDs and sequences. If you insert rows with fixed ids, the serial counter does not move. The next normal insert then collides. Follow the inserts with SELECT setval(pg_get_serial_sequence('customers','id'), (SELECT max(id) FROM customers));.
  • Real data. Do not copy production rows into a laptop. Generate fake data, or anonymise before it leaves the server.
  • Seeding before migrating. The tables must exist. See database migrations in local dev.

When the seed is wrong and you want a clean slate, how to reset a local database shows how to drop everything and start again. For integration tests that need the same data, see integration tests against the real stack.

Questions people ask

Is there a flisk db seed command?

No. Seed with docker exec and psql, with your ORM's seed command, or with a one-shot bring-your-own job that runs after Postgres.

How do I make a seed safe to run twice?

Give each row a fixed key and use ON CONFLICT DO NOTHING in SQL, or upsert in your ORM.

Does prisma migrate reset run the seed?

Not in Prisma 7. Run prisma db seed explicitly after a reset.
