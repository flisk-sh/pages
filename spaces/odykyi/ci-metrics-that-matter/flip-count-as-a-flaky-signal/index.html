Flip Count: A Simple Metric for Flaky CI Workflows

Count how often a workflow switches between pass and fail on the default branch to spot flakiness without reading test reports. Definition, script and limits.

A flip is a change of result between two consecutive runs, pass to fail or fail to pass. Count flips per workflow over the last 100 default-branch runs. Many flips with few code changes mean the workflow is flaky.

Why flips and not failures

A workflow that fails 10 times in a row has one flip: it is broken, and that is a different problem. A workflow that alternates fail, pass, fail, pass has many flips: it is unstable. Pass rate cannot tell those two apart, but flip count can.

A script

gh run list --workflow ci.yml --branch main --limit 100 \
  --json conclusion,createdAt > runs.json

node -e '
const r=require("./runs.json")
  .filter(x=>x.conclusion==="success"||x.conclusion==="failure")
  .sort((a,b)=>a.createdAt<b.createdAt?-1:1);
let f=0;
for(let i=1;i<r.length;i++) if(r[i].conclusion!==r[i-1].conclusion) f++;
console.log("runs",r.length,"flips",f);
'

Skip cancelled and skipped runs, since they carry no pass or fail information.

Pick a threshold

Cilytics uses a simple rule: a workflow is listed as flaky when it flipped between pass and fail at least 3 times in the last 100 runs. That is a reasonable starting point for your own script too. Tune it to your volume. A repo with 5 runs a week needs a longer window than one with 200.

Limits of the metric

  • Real alternation can come from real changes: a bug lands, then a fix lands. That is two flips and not flakiness.
  • To tell them apart, check whether the commit changed. Two results on the same headSha are a stronger signal.
  • Workflow-level flips do not say which test is flaky. Use test reports for that, as in finding flaky tests in CI.

Same-commit flips

There is a stricter variant. Group runs by headSha. A commit that has both a success and a failure is a confirmed flake, because the code did not change. This needs reruns on the same commit, so it only catches flakes that were noticed and retried. Run both counts: the sequence flip count finds unstable workflows broadly, the same-commit count gives you proof for the issue you write. Together they take about twenty lines of script.

Use it in practice

Review the top three workflows by flip count weekly. Open an issue for each, assign an owner and set a deadline, as in the team policy. You can see flaky workflows for any public repo at cilytics.flisk.si with ?repo=owner/name, using default-branch runs and an hourly snapshot.

Keep a baseline. Record the flip count for each workflow once a week. A workflow whose count rises from 1 to 6 over a month is getting worse, even if its pass rate still looks fine. A workflow whose count drops after a fix gives you evidence that the fix worked, which is useful when you explain the effort to the team.

Questions people ask

Is a flip always a flake?

No. A real regression followed by a fix also produces flips. Same-commit differences are the clearest evidence of a flake.

How many runs do I need?

At least 30 to 50 for a rough signal. 100 is better, since rare flakes need enough runs to show up.
