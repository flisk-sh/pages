Mean Time to Green: How Fast Do You Fix a Broken Main Branch?

Measure how long the default branch stays red after a failure, compute it from run history, and cut it with ownership, alerts and a revert-first rule.

Mean time to green is the average time between the first failed run on the default branch and the next successful run. It measures how fast a team repairs CI. A broken main blocks everyone, so shorter is better, and the median is often more honest than the mean.

Define the interval

Sort completed default-branch runs by time. Find each failure that follows a success. That is the start of a red period. The period ends at the next success. The duration is the end time minus the start time. Skip cancelled runs.

Compute it

gh run list --workflow ci.yml --branch main --limit 100 \
  --json conclusion,createdAt > runs.json

node -e '
const r=require("./runs.json")
  .filter(x=>x.conclusion==="success"||x.conclusion==="failure")
  .sort((a,b)=>a.createdAt<b.createdAt?-1:1);
const d=[];let start=null;
for(const x of r){
  if(x.conclusion==="failure"&&!start) start=new Date(x.createdAt);
  if(x.conclusion==="success"&&start){d.push((new Date(x.createdAt)-start)/3600000);start=null;}
}
d.sort((a,b)=>a-b);
console.log("red periods",d.length,"median hours",d[Math.floor(d.length/2)]);
'

Beware flaky red periods

If a flaky test causes a failure and the next run passes with no change, the red period is short, but nothing was repaired. A cluster of very short red periods is a sign of flakes, not of fast fixes. Pair this metric with flip count.

How to shorten it

  • Revert first. If a merge broke main, revert it and fix forward on a branch.
  • Alert someone. A failed default-branch run should notify the author of the commit, or a team channel, within minutes.
  • Name an owner. A rotation for who watches main prevents everyone assuming someone else will.
  • Use a merge queue. It tests the combined change before it lands, so main breaks less often.

What the number hides

The metric treats a failure on a Friday evening the same as one on Tuesday morning, so weekends inflate it. Consider measuring in working hours, or report the median next to the mean. It also says nothing about how many people were blocked. A red main on a busy team costs more than the same red on a quiet repo. Use it as a prompt to ask why the repair took as long as it did, and note the cause for each long red period.

See red workflows now

To see which workflows are red right now, Cilytics lists red workflows, defined as those where the newest default-branch run failed, for a whole org or a public repo. Since it is an hourly snapshot, it is not an alerting tool. Use GitHub notifications for real-time alerts and read how to alert on a red default branch.

For teams that use pull requests with required checks, main should rarely go red, so there may be only a few red periods in 100 runs. In that case widen the window to 90 days and read each red period by hand. Small numbers are fine here: the goal is to learn why each one lasted as long as it did, and to find the pattern, such as no owner, slow review of the revert, or a flaky rerun hiding the failure.

Questions people ask

Median or mean time to green?

Report both. One weekend-long red period can pull the mean up, while the median shows the typical repair.

What is a good target?

Pick one from your baseline. Many teams aim for a repair or revert within the same working day, and under an hour for critical pipelines.
