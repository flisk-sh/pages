How to Alert When Your Default Branch Goes Red

Send a notification when a default-branch workflow fails, using a workflow_run trigger or the built-in GitHub notifications, and avoid alert fatigue from flaky runs.

Use a second workflow with the workflow_run trigger that fires when your CI workflow completes on the default branch and the result is a failure, then post to a channel or open an issue. Keep the alert rare and specific, or people will mute it.

A workflow_run alert

name: Alert on red main
on:
  workflow_run:
    workflows: ['CI']
    types: [completed]
    branches: [main]

permissions:
  issues: write

jobs:
  alert:
    if: ${{ github.event.workflow_run.conclusion == 'failure' }}
    runs-on: ubuntu-latest
    steps:
      - env:
          GH_TOKEN: ${{ github.token }}
          URL: ${{ github.event.workflow_run.html_url }}
        run: |
          gh issue create --repo "$GITHUB_REPOSITORY" \
            --title "CI is red on main" \
            --body "Failed run: $URL"

The workflows value must match the name of the workflow you watch. The workflow_run trigger runs from the default branch's copy of the workflow file.

Avoid duplicates

Without care, ten failures open ten issues. Search for an open issue first and comment on it instead.

gh issue list --repo "$GITHUB_REPOSITORY" --state open \
  --search 'CI is red on main in:title' --json number --jq '.[0].number'

If a number comes back, add a comment with gh issue comment. If not, create the issue. Close it when the next run is green.

Send to chat

For a chat message, post to a webhook URL stored as a repository secret.

- run: |
    curl -sS -X POST -H 'Content-Type: application/json' \
      -d "{\"text\":\"CI red on main: $URL\"}" "$WEBHOOK_URL"
  env:
    WEBHOOK_URL: ${{ secrets.CHAT_WEBHOOK }}
    URL: ${{ github.event.workflow_run.html_url }}

Pass the run URL through an environment variable, as above, and not directly into the script text. Values like branch names and titles can be controlled by others. See GitHub Actions security.

Cut the noise

  • Alert only on the default branch, not on pull requests.
  • Skip cancelled runs.
  • If a failure is likely a flake, wait for one automatic rerun before alerting.
  • Alert on repeated failure, such as two in a row, for known-flaky workflows while you fix them.

Then track mean time to green to see if alerts lead to faster fixes.

Test the alert

Do not wait for a real failure to find a typo. Create a branch with a deliberately failing test, merge it into a throwaway copy of the repo or use a test repository, and watch the alert fire. Check that the issue or message contains a link to the run and the commit, and that a second failure comments instead of creating a duplicate. Then check that a green run closes or updates the alert. A short test now saves a missed outage later.

A snapshot view as backup

An alert tells you when it breaks. A dashboard tells you what is red now. Cilytics lists red workflows, where the newest default-branch run failed, for an org or one public repo. It refreshes hourly, so treat it as an overview and not as the alert itself.

Questions people ask

Does workflow_run work for forks?

It runs in the context of the base repository. Be careful with code from fork pull requests, and keep this alert workflow limited to the default branch.

Why did my alert workflow not run?

The workflows name must exactly match the watched workflow, and the alert workflow file must exist on the default branch.
