How to Get GitHub Actions Run Data with the gh CLI

Export workflow runs as JSON with gh run list and gh api, with the fields you need for pass rate and run time, and handle pagination and rate limits.

Run gh run list --json with the fields you need and a limit, and you get workflow run history as JSON you can process with jq or Node. For more than that, call the REST API with gh api and --paginate.

gh run list

gh auth login

gh run list --workflow ci.yml --branch main --limit 100 \
  --json databaseId,workflowName,status,conclusion,createdAt,startedAt,updatedAt,headSha,attempt,event \
  > runs.json

Useful fields: conclusion (success, failure, cancelled and others), status (completed or still running), startedAt and updatedAt for duration, headSha to group by commit and attempt for retries. Run gh run list --help to see the full field list for your version.

Filter with jq

jq '[.[] | select(.status=="completed")] | length' runs.json

jq '[.[] | select(.conclusion=="failure")] | length' runs.json

Always filter to completed runs before computing anything. Runs in progress have no final conclusion, and skewing the sample is an easy mistake. Treat cancelled runs separately, since they are usually caused by newer pushes and not by failures.

More than 100 runs with the API

gh api --paginate \
  'repos/OWNER/REPO/actions/runs?branch=main&status=completed&per_page=100' \
  --jq '.workflow_runs[] | {id, name, conclusion, run_started_at, updated_at, head_sha}' \
  > runs.ndjson

Each line is one JSON object. The REST endpoint is GET /repos/{owner}/{repo}/actions/runs. It lists runs for the repo, with filters such as branch, event and status.

Rate limits and tokens

Authenticated requests have a much higher hourly limit than anonymous ones. Check yours with gh api rate_limit. In a workflow, pass the built-in token as GH_TOKEN:

- run: gh run list --limit 100 --json conclusion > runs.json
  env:
    GH_TOKEN: ${{ github.token }}

Keep the token read-only by setting permissions: actions: read on the job.

Handle reruns and attempts

A rerun keeps the same run id and raises the attempt counter. The list shows the latest attempt, so a run that failed first and passed on retry looks green. To see the failed first attempt, query the attempts endpoint for that run, for example gh api repos/OWNER/REPO/actions/runs/RUN_ID/attempts/1. If you care about first-attempt pass rate, fetch attempt 1 for runs whose attempt is above 1. For most dashboards, counting how many runs needed a retry is already a useful number.

Next steps

With the JSON in hand, compute pass rate and median and p90 run time. If you only want to look at a public repo without scripting, Cilytics can do it: https://cilytics.flisk.si/?repo=owner/name.

Store the exports with a date in the file name so you can rebuild a trend later even after GitHub has expired old runs. A folder of small JSON files in a separate repository or a bucket is enough. Keep the fields you use, not the full payload, to keep files small.

Questions people ask

How far back does run history go?

GitHub keeps run records for a limited time that depends on retention settings. Export what you need regularly if you want a long history.

Can I get job and step timing too?

Yes. The jobs endpoint for a run lists each job with start and end times, and steps within it.
