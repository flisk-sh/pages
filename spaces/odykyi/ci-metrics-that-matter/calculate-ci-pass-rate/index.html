How to Calculate CI Pass Rate (and the Traps That Skew It)

A pass rate is successful runs divided by finished runs, but cancelled runs, retries and pull request noise change the answer. Here is a defensible definition and a script.

CI pass rate is the number of successful runs divided by the number of completed runs, over a window, for one workflow on the default branch. Decide up front how to treat cancelled, skipped and retried runs, or the number will not mean much.

A clear definition

Use this: pass rate = success / (success + failure), for runs on the default branch, excluding cancelled and skipped runs, over the last N runs. Write the definition on the dashboard. Without it, two people compute different numbers and argue about them.

Script it

gh run list --workflow ci.yml --branch main --limit 100 \
  --json conclusion > runs.json

node -e '
const r=require("./runs.json");
const ok=r.filter(x=>x.conclusion==="success").length;
const bad=r.filter(x=>x.conclusion==="failure").length;
console.log(ok+" of "+(ok+bad)+" = "+(100*ok/(ok+bad)).toFixed(1)+"%");
'

Trap 1: cancelled runs

If you use cancel-in-progress, many runs end as cancelled because a newer push replaced them. Counting those as failures makes the rate look worse for a good practice. Counting them as successes looks better than the truth. Leave them out and report how many there were.

Trap 2: retries hide failures

If someone reruns a failed job and it passes, the run shows green with a second attempt. The final pass rate looks high, but the first attempt failed. Track the first-attempt pass rate too. It is the honest measure of how often a push goes green with no help, and the gap between the two tells you how much retries are covering for flakes.

Show the sample

Print the denominator every time. A line such as 92.0% (92 of 100) is more honest than 92%. If the sample is under about 30 runs, say so and avoid drawing conclusions. When a repo is quiet, widen the window by days instead of run count, for example the last 30 days. Whichever window you pick, keep it fixed so week-to-week comparisons mean something.

Trap 3: mixing branches and sizes

Pull request runs include work in progress, so their failure rate is naturally higher. Do not merge them with default-branch runs. Also compute the rate per workflow: a 95 percent average can be one workflow at 100 and one at 70. A public view of per-repo pass rate and a pass-rate trend is on Cilytics; it looks at default-branch runs, so it matches this definition for the default branch. For a deeper cut, see flip count.

If you want a first-attempt rate, count a run as a pass only when it succeeded on attempt 1. Compare it with the final rate. A gap of a few points is normal. A gap of ten points or more means retries are doing a lot of quiet work, and that is the best place to start fixing. Put both numbers on the same chart so the gap is visible.

Questions people ask

What is a good CI pass rate?

On the default branch, close to 100 percent is normal. A sustained rate well below that usually means flaky tests or a broken main that nobody fixes quickly.

Should skipped runs count?

No. A skipped run did no work, so it says nothing about quality. Exclude it from both sides of the ratio.
