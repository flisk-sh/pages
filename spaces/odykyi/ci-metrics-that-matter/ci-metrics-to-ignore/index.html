CI Metrics to Ignore: Vanity Numbers That Mislead

Total runs, average duration, test count, coverage percent in isolation and billable minutes without context: why these mislead, and what to look at instead.

Ignore CI numbers that go up when work happens, not when things improve: total runs, total minutes, test counts and a single average. They reflect activity. Prefer ratios and tails that show health: pass rate, median and p90, flips, and time to green.

Total runs and total minutes

More runs usually means more commits, or more retries, or a bigger matrix. None of that is good or bad by itself. Total minutes matter for the bill, but they do not tell you whether CI is helping. If you track cost, track it per merged pull request, so growth in the team does not hide waste.

Average duration

The average mixes cache hits, cache misses and hangs into one number that no run matches. Use median and p90 instead.

Number of tests

A growing test count is a proxy for effort. A suite of 5,000 tests with a lot of overlap is not safer than 800 good ones, and it is slower. What matters is whether the tests catch regressions and whether they are stable.

Coverage percent alone

Coverage says which lines ran, not whether anything was asserted. Teams that chase a target write tests that execute code without checking results. Use coverage as a map of untested areas, and look at changes in coverage on new code rather than a global target.

Green badge on the README

A badge shows only the latest run. A repo can show green while flipping every other day. Always pair status with history: pass rate over the last 100 runs and the number of flips. A public view such as Cilytics gives that history for an org or a repo, with the limits that it uses default-branch runs and an hourly snapshot.

A test for any metric

Ask: if this number moved 20 percent next month, what would we do? If nobody can answer, stop tracking it. A good metric has a threshold, an owner and an action attached. For the short list that passes this test, see which CI metrics to track.

Two more to treat carefully. Lines of YAML or number of workflows says nothing about quality, and more workflows often means more overlap. Time spent in CI per developer sounds attractive, but it rewards skipping checks. If you want one summary number, use the share of pushes that go green on the first attempt in under ten minutes. It combines trust and speed, and it is hard to game without actually making CI better.

Also be careful with comparisons between teams. Two repos with different languages, test types and risk levels cannot be ranked on one scale. Compare each repo with its own past instead, and use the same window each time. A repo that improves its own median by 30 percent has done more than one that merely started with a fast suite.

Questions people ask

Is cost a bad metric?

No, but total cost is easy to misread. Track cost per merged change or per run so team growth does not look like waste.

Should I remove coverage checks?

Not necessarily. Keep a check on coverage of changed lines, and avoid treating one global percentage as a goal.
