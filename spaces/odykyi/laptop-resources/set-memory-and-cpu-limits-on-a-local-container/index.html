Keep your laptop fast while developing

How to set memory and CPU limits on a local Docker container

A container with no limit can take the whole Docker VM. A limit turns a slow leak into a clear, local failure.

Set a memory limit with docker run --memory 512m --cpus 1, or with deploy.resources.limits in a Compose file. When a container goes over its memory limit the kernel kills it and Docker reports exit code 137; that is a sign to raise the limit or fix a leak, not a random crash.

Why limit local containers at all

On a laptop all containers share one virtual machine (on Mac and Windows) or your whole host (on Linux). One container with a memory leak, or a model server that loads everything it can, pushes the others into swap and slows your editor too. A limit gives each container a ceiling. It does not make the service use less; it makes the failure small and visible. Limits also catch a service that will not fit in production's memory budget long before it gets there.

With plain Docker

docker run --rm --memory 512m --cpus 1 -p 8080:80 nginx
  • --memory (-m) is a hard limit. Use m or g as the unit.
  • --cpus is a share of CPU time. 1.5 means one and a half cores' worth, spread over any cores.
  • --memory-reservation is a soft limit that applies only when the host is short of memory.

Inspect what is applied:

docker stats --no-stream
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' <container>

Memory is shown in bytes and CPUs in billionths of a core in the inspect output.

With Compose

services:
  worker:
    image: myapp-worker
    deploy:
      resources:
        limits:
          cpus: "1"
          memory: 512M

Current Docker Compose applies deploy.resources.limits on a plain docker compose up. Older guides say this only works in Swarm; that was true of the first Compose file format, not today's Compose specification. The short forms mem_limit and cpus directly under the service also work.

Recognise an out of memory kill

A container that reaches its limit is killed by the kernel with no application error. The signs:

  • Exit code 137 (128 plus signal 9) in docker ps -a.
  • docker inspect -f '{{.State.OOMKilled}}' <container> prints true.
  • Logs that simply stop mid-line.

Raise the limit, or find the leak. Runtimes with their own heap limit add a second ceiling: a Node process stops at its heap limit before the container limit, with a different error. The article on containers that keep restarting shows how to tell the causes apart.

In Flisk

On the Docker and Tilt path, Flisk limits a container it builds from its own Dockerfile to 0.5 CPU and 512M of memory. A bring-your-own container (an image or your own Dockerfile) has no limit unless you set one in the container block of its service.json, and only the limit you set is written:

{
  "schemaVersion": 1,
  "appName": "cache",
  "appType": "bring-your-own",
  "stack": "dev",
  "image": "redis:7",
  "port": 6379,
  "container": { "memory": "256m", "cpus": "0.5" },
  "healthCheck": { "command": ["redis-cli", "ping"] }
}

memory is a size string such as 8g or 512mb. cpus is a whole number or a string such as "2.5"; a bare decimal number like 0.5 is rejected by flisk config verify, so quote it. Run flisk config verify after editing to catch that. flisk export compose writes the same limits into a standalone Compose file.

The container fields that apply to the simpler mixed run (local processes plus an image started with docker run) are listed separately in the Flisk docs, and memory and cpus are not among them, so check there before relying on them in that mode. Local processes started from a command are not containers and have no such limit; use the tool's own settings, such as a heap flag, for them.

When a container does hit the memory ceiling, flisk doctor can flag containers pinned near their memory limit while using CPU, which points to a boot-time retry loop, and it explains exit 137 as usually out of memory, with the advice to raise the container's limit.

Pitfalls

  • Limits that are too tight look like flaky crashes. Size them from docker stats readings under real load, then add headroom.
  • A CPU limit throttles instead of killing. A service that is slow only in a container may be throttled; raise cpus before you hunt for a bug.
  • Databases use memory for cache by design. Give them a limit large enough for their working set, or tune the server as in tuning Postgres for a laptop.
  • The total of all limits must fit in the VM. Check the VM size too.

Limits cap a single container. To see how everything adds up across the machine, start with finding what uses your RAM.

Questions people ask

What does Docker exit code 137 mean?

The process was killed with signal 9, most often by the kernel because the container went over its memory limit. docker inspect shows OOMKilled true in that case.

Does Docker Compose honor deploy.resources.limits outside Swarm?

Yes, current Docker Compose applies deploy.resources.limits on a normal docker compose up.

What is the default limit Flisk gives a container?

A container Flisk builds from its own Dockerfile gets 0.5 CPU and 512M. A bring-your-own container has no limit unless you set container.memory or container.cpus.
