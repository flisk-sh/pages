Keep your laptop fast while developing

Why VS Code and the TypeScript server use so much memory

Your editor is often the largest process on a developer laptop. Most of its memory comes from the files you tell it to watch and index.

VS Code and its language servers use memory in proportion to how many files they watch, index and type-check. In a large repo the fix is to tell the editor what to ignore (node_modules, build output, generated code), to cap the TypeScript server, and to avoid opening the same repo in several windows.

See what the editor is actually running

VS Code is several processes: the main window, one or more extension hosts, a file watcher, a search process and a TypeScript server per workspace. Run the command Developer: Open Process Explorer from the command palette. It lists each process with CPU and memory, so you can see whether the cost is the TypeScript server, a single extension or the watcher.

The TypeScript server process is named tsserver and appears as a Node process. In a monorepo it can hold a type graph for the whole workspace. Typical growth comes from large generated files, many node_modules type packages and projects that include far more than they need.

Exclude what you never read

Three settings do most of the work. Put them in .vscode/settings.json in the repo so the whole team gets them.

{
  "files.watcherExclude": {
    "**/node_modules/**": true,
    "**/dist/**": true,
    "**/.next/**": true,
    "**/target/**": true
  },
  "search.exclude": {
    "**/node_modules": true,
    "**/dist": true,
    "**/.next": true
  },
  "typescript.tsserver.maxTsServerMemory": 4096
}
  • files.watcherExclude stops the editor from watching these folders for changes. Fewer watches means less memory and less CPU. The defaults already cover some paths such as .git objects and node_modules in the common layout, but custom build folders are not covered.
  • search.exclude keeps them out of search results and the search index.
  • typescript.tsserver.maxTsServerMemory is the memory limit in MB for the TypeScript server. When it hits the limit, VS Code restarts it instead of letting it grow, which is better than a slow swap spiral. Raise it if you see repeated restarts in a very large project.

Make the TypeScript project smaller

The server type-checks every file that a tsconfig.json includes. Narrow it:

  • Set include to your source folders and put dist, test fixtures and generated output in exclude.
  • Turn on skipLibCheck so declaration files in dependencies are not re-checked.
  • In a monorepo with several packages, use project references so each package has its own smaller program instead of one huge one.

The shared config pattern is described in the monorepo articles; the point here is that smaller programs cost less memory in the editor and in tsc.

Windows, extensions and folders

  • Open the repo folder you work in, not a parent folder that holds ten repos. The editor indexes everything under the root.
  • Do not open the same repo in two windows. Each window starts its own servers.
  • Disable extensions per workspace that you do not need for this project. Language extensions for stacks you are not touching still start servers on matching files.
  • Use the Extension Bisect feature from the command palette if one extension is responsible for a slowdown and you cannot tell which.

Where Flisk fits

Flisk does not change how your editor works. It only affects which of your own processes are running next to it. Services that have a command in service.json run as local processes, and flisk up --only web starts web and what it depends on instead of every service, so the editor shares the machine with fewer Node processes. Note that Flisk generates files under .flisk/; add that folder to files.watcherExclude if you see the watcher react to log files there. Generated files are not meant to be edited by hand, which also makes them safe to exclude from search.

Pitfalls

  • Raising maxTsServerMemory hides a bloated project instead of fixing it. Narrow tsconfig first.
  • Excluding a folder from search also hides it from "Find in files", which can confuse teammates. Say so in the README.
  • If everything is slow only after a long session, restart the TypeScript server with TypeScript: Restart TS Server before you change settings.

If memory is still short after this, measure the whole machine with the RAM checklist. For Node processes that crash on heap size, see Node heap out of memory.

Questions people ask

How much memory should the TypeScript server use?

It depends on project size. Small projects stay under a few hundred MB. Large monorepos can reach gigabytes. Narrow tsconfig include and exclude before raising any limit.

What is Developer: Open Process Explorer?

A VS Code command that lists the editor's processes with CPU and memory so you can see whether the TypeScript server, an extension or the file watcher is the cost.

Should I exclude node_modules from the file watcher?

Yes. Watching it costs memory and CPU for no benefit, and you rarely edit files in it.
