Keep your laptop fast while developing

How to tune a local Postgres container for a laptop

Postgres defaults suit a small server. For local work a handful of settings change memory use and test speed. Most do not matter.

For a development Postgres, three settings matter: shared_buffers and max_connections set how much memory the server holds, and fsync=off (with synchronous_commit=off) makes writes much faster by skipping the wait for the disk. Pass them with -c name=value after the image name. Use the durability switches only for data you can recreate.

What each setting does

SettingDefaultEffect on a laptop
shared_buffers128MBPostgres's own page cache. The operating system caches files too, so a small value is fine for local data sets. Lower it to 64MB to save memory; raise it only if a big local data set needs it.
max_connections100Each connection is a process that takes memory when active. Several services with pools of 10 add up. Lower it to 30 or 50 if your pools are small, and fix pools that are too large.
work_mem4MBMemory per sort or hash step per query, per connection. Raise it for one slow query with a session setting, not globally.
fsynconOff skips flushing to disk. Much faster writes, but a crash or power loss can corrupt the whole cluster.
synchronous_commitonOff lets a commit return before its WAL is flushed. A crash can lose the last few transactions but does not corrupt data. Safer than turning fsync off.

The values above are the stock ones in current Postgres releases; check SHOW shared_buffers; in your version. Do not copy "production tuning" advice such as setting shared_buffers to a quarter of RAM. That is for a server that does only database work.

Pass settings to the container

Anything after the image name goes to the postgres command, so settings are flags:

docker run -d --name pg \
  -e POSTGRES_PASSWORD=postgres \
  -v pgdata:/var/lib/postgresql/data \
  -p 127.0.0.1:5432:5432 \
  postgres:17 \
  -c shared_buffers=64MB \
  -c max_connections=50 \
  -c synchronous_commit=off

Check that they took effect:

docker exec pg psql -U postgres -c "SHOW shared_buffers;" -c "SHOW max_connections;"

In Compose the same flags go in the command list of the service. A mounted postgresql.conf also works but is easy to get wrong because it replaces the defaults file the image generates; flags are simpler for a few settings.

The same settings in Flisk

For a Postgres you run yourself as a bring-your-own service, container.command in service.json carries the flags, and container.shmSize raises the shared memory of the container:

{
  "schemaVersion": 1,
  "appName": "pg",
  "appType": "bring-your-own",
  "stack": "dev",
  "image": "postgres:17",
  "port": 5432,
  "env": { "POSTGRES_PASSWORD": "${POSTGRES_PASSWORD}" },
  "healthCheck": { "command": ["pg_isready", "-U", "postgres"] },
  "volumes": [{ "source": "pg", "target": "/var/lib/postgresql/data", "name": "myapp_pg" }],
  "container": {
    "command": ["postgres", "-c", "shared_buffers=64MB", "-c", "max_connections=50", "-c", "synchronous_commit=off"],
    "shmSize": "256mb"
  }
}

Run flisk config verify to check the file. The command list is passed as given, without a shell, so spell out postgres as the first element. The container block can also carry memory to cap the container, as described in memory and CPU limits. Flisk's own shared Postgres, which runs when you use --type database or postgres in dependsOn, is a platform service; the docs do not describe a way to pass server flags to it, so if you need custom settings, run your own bring-your-own Postgres instead.

Speed up tests, safely

  • Use fsync=off only on a throwaway container whose data you can rebuild with migrations and a seed script. Never on a database that holds work you cannot recreate.
  • For a test database that is rebuilt on each run, a RAM backed data directory (--tmpfs /var/lib/postgresql/data) removes disk cost altogether. Data is gone when the container stops.
  • Run migrations once and reuse a template database for each test, with CREATE DATABASE test_x TEMPLATE base, instead of migrating every time.
  • Log slow queries with -c log_min_duration_statement=200 to find the query that matters before you tune anything else.

Pitfalls

  • Settings are read at start. Changing a flag means recreating or restarting the container; a docker restart keeps the flags and the volume.
  • With a very small max_connections, a pool that is too big gets "too many clients" errors. Size the pools first.
  • Docker gives containers 64MB of shared memory by default. Parallel queries can fail with a shared memory error if it is too small; raise --shm-size (or shmSize in Flisk).
  • Do not carry fsync=off into a staging or shared environment because "it was in the dev config".

Questions people ask

Is it safe to set fsync=off in development?

Only for data you can rebuild. A crash or power loss can corrupt the whole cluster. synchronous_commit=off is a safer way to speed up writes.

How do I pass Postgres settings to the Docker image?

Add -c name=value flags after the image name, for example postgres:17 -c max_connections=50, or put the same strings in the command list of a Compose service.

How do I check that a setting was applied?

Run SHOW shared_buffers; or SHOW max_connections; inside psql against the running container.
