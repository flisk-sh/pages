Why your dev server sits at 100% CPU and how to find the cause

A dev server that burns a core while you are not touching it is almost always in a loop. The job is to find which loop.

A dev server stuck at 100% CPU is nearly always running a loop you did not intend: a watcher that rebuilds because its own output changed, a file watcher in polling mode, a crash and restart cycle, or a real hot code path. Find the process with top, then profile it to see which of the four it is.

Find the process first

Sort by CPU and let it settle for a few seconds, because the first sample is always noisy.

# macOS
top -o cpu -stats pid,command,cpu

# Linux
top -o %CPU
ps aux --sort=-%cpu | head

Note the PID and the command. If the command is node, python or java you still do not know which service it is. On macOS and Linux ps -o pid,command -p <pid> shows the full command line, and lsof -p <pid> | grep cwd shows the folder it was started from.

If the busy process is com.docker.virtualization, qemu or a similar VM process, the load comes from inside a container instead. docker stats --no-stream names the container.

Check the four usual loops

1. The build writes into a watched folder

A bundler or compiler that watches the project root, and also writes its output there, triggers itself. Typical culprits are dist, .next, build, a generated *.d.ts file or a log file. The sign is an endless "File changed, rebuilding" line with nothing edited. Fix it by ignoring the output folder in the watcher configuration, or by writing output outside the watched tree.

2. The watcher polls

Polling watchers check every file on a timer instead of waiting for operating system events. Options such as usePolling in Vite and chokidar, watchOptions.poll in webpack and the CHOKIDAR_USEPOLLING variable turn it on. People enable polling to make reload work inside containers, then forget it. A large node_modules makes polling expensive. Turn it off where events work, and where you must keep it, raise the interval to 1000 ms or more and ignore node_modules.

3. A crash loop

A service that exits at once and gets restarted by its supervisor keeps a core busy on startup work. The log shows the same startup lines again and again. Read the first error, not the last. The article on debugging a service that will not start walks through this.

4. Real work in your code

A render loop, a tight retry without a delay, a regex with catastrophic backtracking, or a query run on every request. These need a profile.

Profile instead of guessing

For Node, start the process with the built-in profiler and open the result in Chrome DevTools or any .cpuprofile viewer:

node --cpu-prof server.js

Stop the process normally and a CPU.*.cpuprofile file appears in the working directory. For Python, py-spy top --pid <pid> attaches to a running interpreter without a restart. On macOS, sample <pid> 5 records five seconds of stacks for any native process. On Linux perf top -p <pid> does a similar job.

Whichever tool you use, look for one function that dominates. If it is file system code in a watcher, you are in case 1 or 2. If it is your own handler, you are in case 4.

How Flisk behaves here

If a service has a command in its service.json, flisk up runs it as a local process, so the PID in top is the real process and not a hidden container. Flisk restarts a process that exits after 1 second, then 2, 4 and 8, and after five quick exits in a row it stops restarting it and says so. A crash loop therefore cannot keep your CPU busy forever. To see what a service printed before it died:

flisk status
flisk logs --service api --since 5m

flisk status marks each service as ready, restarting or not running. A service that you only need for a one-shot job can set "restart": "no" in its service.json so it is not started again after it exits.

Pitfalls

  • High CPU right after npm install or a branch switch can be indexing by your editor, antivirus or Spotlight. Wait two minutes before you debug.
  • Do not lower the watcher interval to make reload feel faster. That is how the loop starts.
  • If the CPU only spikes when you save a file, that is a rebuild and normal. Constant load at idle is the symptom to chase.

When the cause is the editor rather than the server, see VS Code and TypeScript server memory in big repos. If the watcher fails instead of spinning, too many open files and watcher limits is the next read.

Questions people ask

Why is my dev server using CPU when I am not editing anything?

Common causes are a watcher that rebuilds because its own output changed, polling mode, a crash and restart loop or a busy loop in your code. Profile the process to see which.

How do I profile a Node dev server?

Start it with node --cpu-prof, stop it normally, and open the generated .cpuprofile file in Chrome DevTools.

Does turning off polling break hot reload?

Usually not on the host machine, where file events work. Inside containers on some setups events do not arrive, so you may need polling there with a longer interval.
