Keep your laptop fast while developing

Run one Postgres server for several local services to save RAM

Each Postgres container carries its own processes and caches. One server with several databases costs much less on a small laptop.

You can run one Postgres server and give each service its own database and user inside it. That keeps the data separated while paying the fixed memory cost of a Postgres server once instead of once per service. The cost is that all services share one version, one set of settings and one point of failure.

What you save and what you give up

A running Postgres server has a postmaster, background writers, a WAL writer, autovacuum and a shared buffer cache. An idle server is not free. In Flisk's published idle memory measurement of its restaurant demo (six services on one Mac, Docker VM with 7.7 GiB), Postgres was 107 MiB of the 134 MiB of infrastructure. That is one machine and one run, not a guarantee, but it shows the size of the fixed cost: five separate Postgres containers can use a few hundred MB before they hold any data.

What you give up:

  • One major version for everyone. If two services need different versions, they need separate servers.
  • Shared max_connections and a shared cache. A noisy service can starve the others.
  • A restart or crash affects every service at once.
  • It is easier to write a cross-database shortcut by mistake. Postgres does not allow cross-database queries in one statement, which helps, but a shared superuser account lets code reach another service's database. Give each service its own role.

If you want strict isolation, read one database per service first; it is about separate databases, and this article is about putting them on one server.

Create the databases with an init script

The official postgres image runs files in /docker-entrypoint-initdb.d the first time it starts with an empty data directory. A shell script there can create a role and a database for each service:

#!/bin/bash
set -e
for svc in orders billing search; do
  psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname postgres <<SQL
CREATE ROLE ${svc} LOGIN PASSWORD '${svc}_dev';
CREATE DATABASE ${svc} OWNER ${svc};
SQL
done

Mount it read-only and keep the data in a named volume:

docker run -d --name pg \
  -e POSTGRES_PASSWORD=postgres \
  -v pgdata:/var/lib/postgresql/data \
  -v "$PWD/init.sh":/docker-entrypoint-initdb.d/init.sh:ro \
  -p 127.0.0.1:5432:5432 postgres:17

Each service then connects with its own URL, such as postgres://orders:orders_dev@localhost:5432/orders. These are local development passwords; never reuse them elsewhere. For Postgres 18 and later the volume mount path is /var/lib/postgresql instead; check the image notes for the version you run.

The init scripts run only once. If you add a service later, either run the CREATE statements by hand with docker exec or reset the volume, which deletes the data.

How Flisk's shared Postgres works

Flisk's Docker and Tilt path already works this way. It runs one shared PostgreSQL for the project, and each stack gets its own database inside it, named FLISK_{stack} by default (databaseName in a service overrides that). Services receive DATABASE_URL without you writing it. You can declare the database as a resource so services can wait for it by name:

flisk resource shop-db --type database --stack shop

That writes a service.json with "appType": "database" and "framework": "postgres". It gets no container of its own; it is the project's shared Postgres. A service lists "dependsOn": ["shop-db"] to start after it. Note that the unit is the stack, so two services in the same stack share one database unless you set databaseName on one of them.

If you do not need the shared Postgres at all, flisk up --no-database turns it off and saves capabilities.database=false in .flisk/project.json. For a project made only of bring-your-own resources, the shared Postgres starts only when some resource asks for it through dependsOn or a database resource.

Pitfalls

  • Migrations: run each service's migrations against its own database and role. A migration run as superuser can create objects the service role cannot touch. See migrations in local dev.
  • Resetting: dropping the volume resets every service at once. Drop one database with DROP DATABASE to reset only one.
  • Do not point a service at a database it does not own just because the credentials work.
  • If a service needs an extension such as pgvector, the image must contain it for all services.

Once the server is shared, its settings matter more. Tune Postgres for a laptop shows the few that count, and running Postgres locally covers the basics.

Questions people ask

Can several services share one Postgres container safely?

Yes for local development, if each service has its own database and role. They share the version, connection limit and restarts, so use separate servers when you need real isolation.

Why did my init script not create a new database?

Scripts in /docker-entrypoint-initdb.d run only when the data directory is empty. Create the new database by hand or reset the volume.

Does Flisk start one Postgres per service?

On the Docker and Tilt path Flisk runs one shared Postgres per project and gives each stack its own database inside it.
