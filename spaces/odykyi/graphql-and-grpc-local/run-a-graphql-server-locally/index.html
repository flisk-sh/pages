GraphQL and gRPC in local dev

How to run a GraphQL server locally and query it with curl

A GraphQL API is one HTTP endpoint. Once you can hit it with curl, every other tool (a frontend, a codegen step, a test) is easy to wire up.

To run a GraphQL server locally, install a server library such as GraphQL Yoga, define a schema with resolvers, listen on a port, and send queries as a JSON POST to /graphql. You can check it from the command line with curl before any frontend exists. This article builds the smallest useful server and shows how to start it with the rest of your app.

A minimal server

GraphQL Yoga is a server that runs on plain Node.js, Bun and Deno. Apollo Server, Mercurius (Fastify) and Strawberry (Python) are good alternatives and work the same way for what follows: a schema, resolvers and one HTTP endpoint.

mkdir shop-graphql && cd shop-graphql
npm init -y
npm install graphql graphql-yoga

Create server.mjs (set "type": "module" in package.json, or keep the .mjs extension):

import { createServer } from 'node:http'
import { createSchema, createYoga } from 'graphql-yoga'

const products = [
  { id: '1', name: 'Espresso beans', priceCents: 1200 },
  { id: '2', name: 'Milk jug', priceCents: 800 },
]

const yoga = createYoga({
  schema: createSchema({
    typeDefs: /* GraphQL */ `
      type Product { id: ID!, name: String!, priceCents: Int! }
      type Query {
        products: [Product!]!
        product(id: ID!): Product
      }
    `,
    resolvers: {
      Query: {
        products: () => products,
        product: (_, { id }) => products.find((p) => p.id === id) ?? null,
      },
    },
  }),
})

const port = Number(process.env.PORT ?? 4000)
createServer(yoga).listen(port, () => {
  console.log(`GraphQL on http://localhost:${port}/graphql`)
})

Reading the port from PORT matters later: many process runners pass the port that way, and it avoids a hard-coded number in two places.

Query it with curl

A GraphQL request is a POST with a JSON body that has a query field. The response is always JSON with data and, when something went wrong, errors.

node server.mjs

curl -s http://localhost:4000/graphql \
  -H 'content-type: application/json' \
  -d '{"query":"{ products { id name priceCents } }"}'

You get {"data":{"products":[...]}}. Two habits save time. First, always send content-type: application/json; several servers answer a request without it with a confusing 400. Second, remember that GraphQL reports many failures with HTTP 200 and an errors array, so look at the body, not only the status code.

To see the schema itself, ask for introspection:

curl -s http://localhost:4000/graphql \
  -H 'content-type: application/json' \
  -d '{"query":"{ __schema { queryType { name } types { name } } }"}'

Open http://localhost:4000/graphql in a browser and Yoga serves GraphiQL, an in-browser editor with autocomplete from that same introspection. Introspection is on by default in development; many teams turn it off in production, so do not rely on it there.

Start it together with your other services

A GraphQL server rarely runs alone. A frontend calls it and often something else (a database, another service) sits behind it. With Flisk you can describe the server as a plain local process: no Docker, no generated files. Install it once:

npm install -g @flisk-sh/flisk

Add a service.json next to server.mjs:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "graphql-api",
  "appType": "backend",
  "command": "node --watch server.mjs",
  "port": 4000
}

Then run flisk up in that folder. Flisk starts the command with PORT=4000, waits until the port accepts connections (there is no healthCheckPath here, so an open port counts as ready), prefixes the logs with the service name and prints http://localhost:4000. node --watch gives you restart on save, because Flisk's local-process mode does not watch files for you; use your runtime's own watch mode. flisk down stops it, and if the process crashes Flisk restarts it with a growing delay and stops after five quick exits in a row.

Add a frontend as a second service with "dependsOn": ["graphql-api"] and an env entry holding the API URL, and it will start after the API is ready. The frontend and API together article walks through that wiring.

Pitfalls

  • Port already in use. A leftover server from yesterday holds 4000. Find the holder with lsof -i :4000; Flisk also refuses to start and names the process. See how to fix port already in use.
  • Binding to the wrong interface. listen(port) on all interfaces is fine for development, but on a shared network it exposes your dev server. Bind to 127.0.0.1 if you do not need other devices to reach it.
  • GET queries. Many servers accept GET /graphql?query=... for queries only. Mutations over GET are refused by design.
  • Schema drift. When the schema changes, clients with generated types need a regeneration step. See GraphQL codegen in watch mode.

Once the endpoint answers curl, the next step is letting a browser app call it: fix CORS and CSRF errors is the usual first wall.

Questions people ask

What URL does a GraphQL server use?

Usually a single endpoint, most often /graphql, that accepts POST requests with a JSON body. The path is a convention of the server library, not part of GraphQL itself.

Why does curl return a 400 error from my GraphQL server?

The most common causes are a missing content-type: application/json header or a body that is not valid JSON. Check the quoting of the JSON string in your shell.

Do I need Docker to run a GraphQL server locally?

No. A GraphQL server is an ordinary process. Docker is only needed for things like databases that you prefer to run in a container.
