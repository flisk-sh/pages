How to test a gRPC service locally with grpcurl

curl cannot speak gRPC, but grpcurl can. With server reflection on, you can explore and call a local service in a minute.

Use grpcurl to test a gRPC service from the terminal: grpcurl -plaintext localhost:50051 list shows the services, describe shows their messages, and -d '{...}' with a full method name calls one. It needs the server to expose reflection, or you pass the .proto files yourself. This is the gRPC equivalent of curl and works against any language.

Why curl is not enough

gRPC runs over HTTP/2, sends Protocol Buffers instead of JSON, and uses trailers for the status. You cannot reproduce that with a plain curl call. grpcurl takes JSON you type, converts it to Protobuf using the service definition, calls the server and prints the reply as JSON. Alternatives with the same idea are buf curl, grpcui (a browser UI built on the same library) and GUI clients such as Postman and Bruno. Install grpcurl with brew install grpcurl or download a release from its GitHub page.

Turn on reflection in the server

grpcurl needs to learn the schema. The easy way is gRPC server reflection, a standard service the server registers. In Go:

import "google.golang.org/grpc/reflection"

s := grpc.NewServer()
pb.RegisterOrdersServer(s, &ordersServer{})
reflection.Register(s)

Node has the @grpc/reflection package and Python has grpcio-reflection. Reflection exposes your whole API shape, so enable it for development only, for example behind an environment variable.

List, describe, call

A local development server normally has no TLS, so every command needs -plaintext. Without it grpcurl tries TLS and fails with a handshake error.

# which services exist
grpcurl -plaintext localhost:50051 list

# methods of one service
grpcurl -plaintext localhost:50051 list shop.v1.Orders

# the request and response messages
grpcurl -plaintext localhost:50051 describe shop.v1.Orders.GetOrder
grpcurl -plaintext localhost:50051 describe shop.v1.GetOrderRequest

# call a method: full service name, a slash, the method
grpcurl -plaintext -d '{"id": "42"}' localhost:50051 shop.v1.Orders/GetOrder

Field names in the JSON use the proto names (order_id) or the lowerCamelCase form (orderId); both are accepted. Metadata such as an auth token goes in with -H 'authorization: Bearer dev-token'. For a server-streaming method grpcurl prints each message as it arrives. For a client-streaming method, give -d @ and feed several JSON objects on standard input.

Without reflection

Point grpcurl at the proto files:

grpcurl -plaintext \
  -import-path ./proto -proto shop/v1/orders.proto \
  -d '{"id": "42"}' localhost:50051 shop.v1.Orders/GetOrder

Imports resolve against -import-path. If your project uses Buf, buf build -o image.binpb produces a descriptor file that grpcurl reads with -protoset image.binpb, which also covers imports of third-party protos.

Check the standard health service

If the server registers the standard gRPC health service, you can ask it directly. An empty service name means the whole server:

grpcurl -plaintext -d '{"service": ""}' localhost:50051 grpc.health.v1.Health/Check

A healthy reply is {"status": "SERVING"}. The same service is what a readiness check for a local stack uses.

Run the server first, with Flisk if you like

You need the server running and its port known. If the gRPC server is one of several services, a service.json with a command and a port lets flisk up start it as a local process and print where it listens (localhost:50051 here, not an HTTP link, so read the port rather than clicking). Install with npm install -g @flisk-sh/flisk. Flisk does not wrap grpcurl or know about Protobuf; it only keeps the server running.

Use it in a repeatable script

Once a call works, save it. A shell script with three or four grpcurl lines (health, one read, one write) becomes a smoke test you can run after every change and in CI. Print only the reply with -format json, which is the default, and pipe it to jq to assert on one field:

grpcurl -plaintext -d '{"id": "42"}' localhost:50051 shop.v1.Orders/GetOrder | jq -e '.status == "PAID"'

A failing call prints the gRPC status code, such as NotFound or InvalidArgument, and exits non-zero, so the script stops on the first failure. Add -max-time 5 so a hung call cannot block the script.

Pitfalls

  • Handshake or "first record does not look like a TLS handshake". You are mixing plaintext and TLS. Add -plaintext for a dev server without TLS.
  • "Server does not support the reflection API". Register reflection, or use -proto or -protoset.
  • Connection refused on localhost. Some servers listen on IPv4 only and localhost can resolve to IPv6. Try 127.0.0.1:50051.
  • Behind a gateway. A proxy that only understands HTTP/1.1 breaks gRPC. Call the service port directly while developing.

Questions people ask

Why does grpcurl say 'first record does not look like a TLS handshake'?

grpcurl uses TLS by default. A local server without TLS needs the -plaintext flag.

Can I use curl for gRPC?

Not in a practical way. gRPC needs HTTP/2 with Protobuf framing and trailers. Use grpcurl or buf curl. Servers that also speak the Connect protocol can be called with plain curl and JSON.

Is grpcurl reflection safe to leave on?

Reflection reveals your full API definition, so keep it on for development and turn it off in production unless you have a reason.
