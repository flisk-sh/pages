How to let gRPC services find each other in local development

gRPC clients dial host:port, nothing more. Locally, the whole problem is choosing ports, passing addresses and starting servers before their callers.

gRPC clients connect to a host:port target, so local service discovery is just three decisions: a fixed port for every gRPC server, an environment variable that carries that address to each caller, and a start order that brings servers up first. Keep the address out of the code, and every developer's machine and your CI use the same code with different values.

A target is an address, not a URL

A gRPC target is written localhost:50051, with no http://. Clients in each language take it as a string, and a dev server without TLS needs insecure credentials explicitly:

// Go
conn, err := grpc.NewClient(os.Getenv("INVENTORY_ADDR"),
    grpc.WithTransportCredentials(insecure.NewCredentials()))

// Node, @grpc/grpc-js
const client = new InventoryClient(process.env.INVENTORY_ADDR,
    grpc.credentials.createInsecure())

# Python
channel = grpc.insecure_channel(os.environ["INVENTORY_ADDR"])

Connections are lazy in modern clients: NewClient returns without dialing, so a wrong address only shows up as Unavailable on the first call. Treat code = Unavailable as "no server at that address, or it is not ready" and check the address and start order before the code.

Pick ports on purpose

Do not let each service choose a random free port; callers cannot guess it. Write a small table in your README and keep it in the service config. A convention that avoids clashes with HTTP ports: 4xxx for HTTP APIs, 50051 and up for gRPC. Use 127.0.0.1 instead of localhost if a server binds only IPv4 and your resolver prefers IPv6; the symptom is "connection refused" on a port that is plainly open.

Describe the topology in service.json

With Flisk's local-process mode, each service has a command, a port and an env map. The orders service calls inventory, so it depends on it and receives its address:

// inventory/service.json
{
  "schemaVersion": 1,
  "appName": "inventory",
  "appType": "backend",
  "command": "go run ./cmd/inventory",
  "port": 50051,
  "healthCheck": { "port": 50051 }
}

// orders/service.json
{
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "command": "go run ./cmd/orders",
  "port": 50052,
  "healthCheck": { "port": 50052 },
  "dependsOn": ["inventory"],
  "env": { "INVENTORY_ADDR": "localhost:50051" }
}

Install with npm install -g @flisk-sh/flisk, then flisk up. It starts inventory, waits until port 50051 accepts connections, then starts orders and passes INVENTORY_ADDR. Before starting, it refuses to run if two services share a port or a port is already taken, and says which process holds it. flisk up --dry-run prints the order; flisk logs --service orders --tail 50 reads one service's output. Add a language toolchain constraint with "toolchain": "go@1.23" if you want a version mismatch to stop the start. The values in env can read from your shell or a .env file with ${VAR:-default}, so a developer can point INVENTORY_ADDR at a shared environment without editing the file.

The wait is only as good as the probe. A port probe says the port is open; if the server needs its database first, use the gRPC health protocol (gRPC health checks for a local stack). General ordering rules are in how to control service startup order.

When one service runs in Docker

Mixing is common: a database or a legacy gRPC service in a container, your code as local processes. Flisk can run a ready-made image next to local processes; the container's port is published on 127.0.0.1 at the same number, and a local process reaches it at localhost, not by service name, because those containers share no Docker network. If everything runs in containers on the Docker path, containers reach each other by service name on the Docker network instead, so the address in env changes to the name. Keep the address in an environment variable and this is a one-line change per mode. A project cannot mix a Dockerfile-built service with local processes, so check flisk up --dry-run if it refuses to start.

Pitfalls

  • Circular calls. If A calls B and B calls A at startup, dependsOn cannot order them. Make one call lazy, or retry.
  • Calls at startup. A server that dials a dependency in main and exits on failure turns an ordering bug into a restart loop. Connect lazily and let the first request fail with a retry.
  • Retries and deadlines. Set a deadline on every call. A call without one waits forever on a dead address. gRPC can retry on its own with a service config; enable it deliberately.
  • Testing one service. You do not need the whole graph. Start just one with its dependencies using flisk up --only orders.

Questions people ask

How do gRPC services find each other locally?

Give each server a fixed port, pass the host:port address to callers through an environment variable, and start servers before their callers.

Why do I get Unavailable when calling a local gRPC service?

Nothing is listening at that address yet, the address is wrong, or you mix TLS and plaintext. Check the port, the start order and the credentials.

Is there a scheme like http:// in a gRPC address?

No. A target is host:port, for example localhost:50051. In Go the target can optionally carry a resolver scheme such as dns:///.
