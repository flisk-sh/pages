GraphQL CORS and CSRF errors from a local frontend: how to fix

The query works in curl but the browser refuses it. That is almost always CORS or CSRF prevention, and both are fixed on the server or with a dev proxy.

If a GraphQL query works in curl but fails in the browser with "blocked by CORS policy", the server did not answer the preflight request or did not allow your page's origin. If Apollo Server answers with a message about a potential Cross-Site Request Forgery, the request lacked a header the server requires. You fix the first by configuring CORS for your dev origin, or avoid it altogether with a dev-server proxy, and the second by sending a JSON content type.

Why curl works and the browser does not

CORS is enforced by the browser. A page on http://localhost:3000 calling http://localhost:4000/graphql is a cross-origin request, because the port is part of the origin. A GraphQL POST with content-type: application/json is not a "simple" request, so the browser first sends an OPTIONS preflight asking whether it may. If the server does not reply with the right Access-Control-Allow-* headers, the browser blocks the real request. The server never sees a problem, which is why logs look clean.

Open the Network tab and look for the OPTIONS request. If it is missing, the error is something else. If it returns 404 or 405, the server has no CORS handling. If it returns 204 without Access-Control-Allow-Origin, the origin is not allowed.

Fix 1: allow your dev origin on the server

With GraphQL Yoga:

const yoga = createYoga({
  schema,
  cors: {
    origin: 'http://localhost:3000',
    credentials: true,
    methods: ['GET', 'POST', 'OPTIONS'],
    allowedHeaders: ['content-type', 'authorization'],
  },
})

With Apollo Server 4 and Express, add the cors middleware in front of expressMiddleware:

app.use('/graphql',
  cors({ origin: 'http://localhost:3000', credentials: true }),
  express.json(),
  expressMiddleware(server))

Use an exact origin, not *, when you send cookies: browsers reject a wildcard with credentials. Remember that http://localhost:3000 and http://127.0.0.1:3000 are different origins. Read the origin from an environment variable so each developer or port setup works.

Fix 2: let the dev server proxy

If the browser only talks to the frontend's own origin, there is no CORS at all. Vite can forward a path to the API:

// vite.config.ts
export default defineConfig({
  server: {
    proxy: { '/graphql': 'http://localhost:4000' },
  },
})

Then the client uses the relative URL /graphql. This also matches production if you serve both behind one host. For WebSocket subscriptions add ws: true to the proxy entry; GraphQL subscriptions locally shows the detail. The trade-off: dev now differs from a setup where the browser calls a separate API host, so test CORS once before shipping if that is how production works.

The CSRF prevention error

Apollo Server 4 has CSRF prevention on by default. It rejects requests that a plain HTML form could send, to protect cookie-based sessions. A normal client sending content-type: application/json passes. You hit the error when you send a GET query without a header, or a POST with text/plain or form encoding. The error text names the fix: set a non-simple content-type, or send a non-empty apollo-require-preflight or x-apollo-operation-name header. Apollo Client and most tools do this already. Do not switch the protection off to make a dev error go away; fix the request.

Wire the URLs without hard-coding them

Put the API address in one place. With Flisk's local-process mode, the frontend's service.json carries it in env and starts after the API:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npx vite --port 3000",
  "port": 3000,
  "dependsOn": ["graphql-api"],
  "env": { "VITE_API_URL": "http://localhost:4000/graphql", "CORS_ORIGIN": "http://localhost:3000" }
}

Vite exposes variables that start with VITE_ to the browser code. Install Flisk with npm install -g @flisk-sh/flisk and run flisk up. For the full recipe see Express API and Vite frontend in one dev command. Flisk has no GraphQL-specific CORS handling; the server settings above are yours.

A quick debugging routine

  1. Reproduce with curl, including the header the browser sends: curl -i -X OPTIONS http://localhost:4000/graphql -H 'origin: http://localhost:3000' -H 'access-control-request-method: POST' -H 'access-control-request-headers: content-type'.
  2. Look at the status and at access-control-allow-origin in the answer. No such header means the server is not doing CORS for that route.
  3. Check that the allowed origin equals the page origin exactly, including scheme and port.
  4. Only then look at the request itself: content type, auth header, method.

This takes the browser out of the loop and shows what the server really sends, which is usually clearer than the console message.

Pitfalls

  • Credentials and wildcard. * plus cookies is rejected; use an exact origin.
  • Auth header not allowed. A custom header must be listed in Access-Control-Allow-Headers.
  • Error looks like a network failure. A blocked request shows as "Failed to fetch" in the code. The console message says CORS.
  • Mixed content. An https page cannot call an http API. Keep dev on http or use a local certificate; see local URLs instead of ports.

Questions people ask

Why does my GraphQL query work in curl but fail in the browser?

CORS and CSRF checks are enforced by browsers and some servers, not by curl. A cross-origin JSON POST triggers a preflight request that the server must answer.

How do I fix the Apollo Server CSRF prevention error?

Send a content-type such as application/json, or add a non-empty apollo-require-preflight header. Keep CSRF prevention on.

Is a dev proxy better than enabling CORS?

A proxy avoids CORS in development, but it hides a CORS problem you may have in production if the browser calls a separate API host. Test it once.
