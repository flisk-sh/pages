How to run GraphQL federation locally: subgraphs and a router

Federation splits one GraphQL schema across services. Locally that means several processes, one composed schema file and a router, all started in the right order.

To run GraphQL federation locally you start each subgraph as its own server, compose their schemas into a supergraph file with Rover, and start a router that reads that file and sends queries to the subgraphs. Three things must agree: the subgraph URLs, the composed supergraph and the router's listen address. Most local problems are one of those drifting out of sync.

What runs where

In Apollo Federation (version 2) each team owns a subgraph, an ordinary GraphQL server that also describes how its types connect to other subgraphs, for example with @key. Clients never talk to subgraphs. They talk to a router, which plans a query across them. Apollo Router is a standalone binary; Apollo Gateway is the older Node library. Other routers exist (WunderGraph Cosmo, Hive Gateway, GraphQL Mesh) and the local steps below are similar for them.

A typical local layout:

  • products subgraph on port 4001
  • reviews subgraph on port 4002
  • the router on port 4000, which is the only URL the frontend knows

Compose the supergraph

Rover is Apollo's CLI. Describe the subgraphs in supergraph.yaml:

federation_version: =2.9.0
subgraphs:
  products:
    routing_url: http://localhost:4001/graphql
    schema:
      subgraph_url: http://localhost:4001/graphql
  reviews:
    routing_url: http://localhost:4002/graphql
    schema:
      subgraph_url: http://localhost:4002/graphql

With subgraph_url, Rover introspects the running subgraph, so the subgraphs must be up first. If you would rather not depend on a running server, point schema at a file with file: ./products/schema.graphql instead. Then compose:

rover supergraph compose --config supergraph.yaml > supergraph.graphql

The first run may ask you to accept the Elastic License v2 for the composition code; set APOLLO_ELV2_LICENSE=accept in non-interactive scripts. Composition fails loudly when two subgraphs define the same field incompatibly. That error is the point of doing it locally: you see it before a pipeline does.

Start the router

Download the router binary from Apollo's install script or releases page, then run it against the file:

./router --supergraph supergraph.graphql --config router.yaml --dev

A minimal router.yaml sets the listen address:

supergraph:
  listen: 127.0.0.1:4000

The --dev flag turns on development defaults such as the Apollo Sandbox page and introspection. The router also has a hot-reload option for the supergraph file; check ./router --help for the exact flag in your version, because it has changed over releases.

Start everything with Flisk

Each subgraph and the router are plain commands, so each gets a service.json with a command and a dependsOn list. Flisk starts them in dependency order as local processes, with no Docker. Subgraph products/service.json:

{
  "schemaVersion": 1,
  "appName": "products",
  "appType": "backend",
  "command": "node --watch server.mjs",
  "port": 4001
}

The router service waits for both subgraphs and runs the compose step first, so the supergraph is never stale:

{
  "schemaVersion": 1,
  "appName": "router",
  "appType": "backend",
  "command": "rover supergraph compose --config supergraph.yaml > supergraph.graphql && ./router --supergraph supergraph.graphql --config router.yaml --dev",
  "port": 4000,
  "env": { "APOLLO_ELV2_LICENSE": "accept" },
  "dependsOn": ["products", "reviews"]
}

The command is a shell command, so && works. Flisk passes PORT but the router ignores it; keep port equal to the address in router.yaml so the readiness check and the printed URL are right. Run flisk up --dry-run to see the start order before you start anything, and flisk logs --service router to read one service's output.

Test the graph with curl

Query the router, not a subgraph, and ask for fields that live in different subgraphs in one request:

curl -s http://localhost:4000/ \
  -H 'content-type: application/json' \
  -d '{"query":"{ products { name reviews { body } } }"}'

The router path is / by default, not /graphql; it can be changed in router.yaml. If one subgraph is down, the router returns an error for the fields it owns and still serves the rest where the schema allows it. Call each subgraph directly on its own port to tell a subgraph bug from a planning bug. Many routers can also print the query plan in dev mode, which shows which subgraph each field came from.

Pitfalls

  • Stale supergraph. Changing a subgraph schema does nothing until you compose again. Restarting the router service in the setup above re-composes.
  • Wrong routing URL. The routing_url is what the router calls. If it says localhost and the router runs in a container, that is the container itself. Run the router as a local process, or use the host address your runtime provides.
  • Do you need federation at all? One team and one service means one schema. Federation adds a router, a composition step and a deploy contract. Start with a single server such as the one in run a GraphQL server locally and split when team boundaries demand it.

When the router answers, point your frontend at port 4000 only and handle browser access with CORS settings on the router.

Questions people ask

Do I need a router for GraphQL federation?

Yes. A router (Apollo Router, Apollo Gateway or an alternative) receives client queries and splits them across subgraphs. Subgraphs alone cannot answer a query that spans several of them.

Can I run federation without Docker?

Yes. Subgraphs are normal servers, Rover is a CLI and the Apollo Router is a single binary, so all of them can run as local processes.

Why does rover supergraph compose fail?

Composition checks that the subgraph schemas fit together. The error message names the type or field that conflicts, such as a field defined with different types in two subgraphs.
