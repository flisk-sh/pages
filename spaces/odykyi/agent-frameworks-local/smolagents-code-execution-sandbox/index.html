Agent frameworks on your laptop

How to run a code-writing agent (smolagents) in a sandbox

An agent that writes and runs code is the one agent you should not run directly in your home directory. Contain it before you try it.

A code-writing agent such as smolagents' CodeAgent asks a model for Python and then executes it. Whatever the model writes runs with your permissions, so treat every run as running untrusted code. Use the framework's isolated executor options where they exist, and run the whole service in a container with a read-only filesystem, no extra Linux capabilities and a memory limit. That reduces the damage; it does not make it zero.

What the risk is

With a normal tool-calling agent, the model chooses between functions you wrote. A code agent writes arbitrary statements, which makes it flexible and also makes mistakes and prompt injection far more consequential. A web page the agent reads can contain text that steers it to delete files, read your ~/.ssh folder or send data out. The model does not need to be malicious; a confused one is enough.

smolagents' default local executor restricts imports and some operations, and its own documentation is clear that this is a safeguard, not a security boundary. It lets you widen the allowed imports with additional_authorized_imports. Each import you add widens what the generated code can do, so add only what the task needs. For code you do not control, the framework offers other executors, such as Docker, E2B or Modal sandboxes, chosen with an executor_type argument; check the documentation of your version for the exact options.

from smolagents import CodeAgent

agent = CodeAgent(
    tools=[],
    model=model,                      # any model class you configured
    additional_authorized_imports=["json", "math"],
)

Contain the whole service with Flisk

Even with a restricted executor, run the agent service itself with limited rights. Flisk's bring-your-own resource type wraps your own Dockerfile and lets you set container options in service.json. Create it:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource code-agent --type bring-your-own --stack agents --port 4600 --yes

Flisk writes a placeholder Dockerfile; replace it with one for your agent (a Python base image, your dependencies, your server). Then edit service.json. The container block maps to the Compose options of the same meaning:

{
  "appName": "code-agent",
  "appType": "bring-your-own",
  "stack": "agents",
  "port": 4600,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile",
  "container": {
    "readOnly": true,
    "capDrop": ["ALL"],
    "securityOpt": ["no-new-privileges:true"],
    "user": "10001:10001",
    "tmpfs": ["/tmp:nosuid,nodev,size=100m"],
    "cpus": 1,
    "memory": "1g"
  },
  "volumes": [{ "source": "code-agent-work", "target": "/work" }]
}

What each setting does:

  • readOnly makes the container's root filesystem read-only, so generated code cannot modify installed packages or your service code.
  • capDrop: ["ALL"] removes Linux capabilities the process does not need, and no-new-privileges stops it from gaining more.
  • user runs it as a fixed non-root user. Make sure the user can write to the volume path.
  • tmpfs gives an in-memory /tmp for scratch files that disappears with the container.
  • cpus and memory cap resources. A bring-your-own container has no limit unless you set these, so an infinite loop in generated code can otherwise take the machine.
  • The named volume is the only writable place that survives a restart. Mount nothing from your home directory.

Set the Python process to use writable locations, for example HOME=/tmp, because many libraries write caches on startup and fail on a read-only root. Run flisk config verify to catch a malformed container block, then start the stack with flisk up agents.

What this does not do

  • It does not block the network. I found no Flisk setting that turns outbound network access off for a container. Generated code can still make requests, and a prompt injection can still send data out. If that matters, run the agent on a host or network without access to what you care about.
  • The API key is inside. The agent process needs the model key, so code it runs can read it from the environment. Use a key with a spending cap, as covered in keeping LLM API keys out of git.
  • Containers are not virtual machines. A shared kernel is a weaker wall than a separate sandbox service. For hostile inputs, use a dedicated sandbox executor rather than relying on a laptop container alone.

When to skip this

If your agent calls a fixed set of tools and never executes model-written code, none of this is needed; the ordinary service setup is enough. Code agents are for tasks where flexibility is worth the exposure, such as data wrangling in a throwaway folder. To keep the model itself off a paid API while you experiment, see pointing a framework at a local model, and for wrapping any existing Dockerfile, running an existing Dockerfile in a local dev stack.

Questions people ask

Is smolagents' local executor safe for untrusted prompts?

Its own documentation treats it as a safeguard, not a security boundary. For untrusted input use an isolated executor such as a Docker, E2B or Modal sandbox and keep the permitted imports short.

Does a read-only container stop a code agent from sending data out?

No. It protects the filesystem. Network access is a separate matter, and Flisk has no documented switch to turn it off for a container, so limit what the agent can reach in other ways.

Why set memory and CPU limits?

A bring-your-own container has no limit unless container.cpus or container.memory is set, so generated code that loops or allocates without bound can starve the rest of your machine.
