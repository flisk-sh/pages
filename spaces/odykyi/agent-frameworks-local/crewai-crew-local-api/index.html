How to run a CrewAI crew locally behind an HTTP endpoint

A crew run takes minutes, so an HTTP endpoint that waits for it will time out. Start the run, return an id, and let callers poll.

To call a CrewAI crew from a frontend or another service, put it behind a small web API that starts the run in a background thread, returns a run id at once, and lets the caller poll for the result. crew.kickoff() is a blocking call that makes several model requests, so waiting for it inside one HTTP request is fragile. This article builds that wrapper with FastAPI and runs it as a local process.

Why a crew does not fit a plain request and response

A crew is a group of agents that work through tasks one after another (or with a manager). Each task is one or more model calls, and an agent may loop through tool calls before it finishes. A run of a few minutes is normal. Browsers, proxies and test clients give up long before that, and a dropped connection does not stop the crew: it keeps running and spending tokens with nobody listening.

The usual answer is the one job systems use. POST /runs accepts the inputs and returns 202 with an id. GET /runs/{id} returns running, done or failed, plus the output when it is ready.

Start from the CrewAI project

CrewAI ships a generator. Install it as the CrewAI docs describe, then create a crew:

crewai create crew research_crew
cd research_crew
crewai run

That gives you src/research_crew/ with crew.py, config/agents.yaml and config/tasks.yaml. Get crewai run working first with your model key set in the environment, so any failure later is about the wrapper and not the crew. Check the Python versions your CrewAI release supports before you pick an interpreter.

The wrapper

Copy the research_crew package next to the API file so both are importable. The run table below is a plain dict. That is enough for local work and is the first thing to replace if you need runs to survive a restart.

import threading
import uuid

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

from research_crew.crew import ResearchCrew

app = FastAPI(title="crew-api")
runs: dict[str, dict] = {}


class RunIn(BaseModel):
    topic: str


def execute(run_id: str, topic: str) -> None:
    try:
        result = ResearchCrew().crew().kickoff(inputs={"topic": topic})
        runs[run_id] = {"status": "done", "output": str(result.raw)}
    except Exception as exc:  # report any crew failure to the caller
        runs[run_id] = {"status": "failed", "error": str(exc)}


@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}


@app.post("/runs", status_code=202)
def start(body: RunIn) -> dict[str, str]:
    run_id = uuid.uuid4().hex
    runs[run_id] = {"status": "running"}
    threading.Thread(target=execute, args=(run_id, body.topic), daemon=True).start()
    return {"id": run_id}


@app.get("/runs/{run_id}")
def get_run(run_id: str) -> dict:
    if run_id not in runs:
        raise HTTPException(status_code=404, detail="unknown run")
    return runs[run_id]

The inputs (topic here) must match the placeholders your tasks.yaml uses, such as {topic}. A mismatch usually shows up as a literal placeholder in the model's output.

Run it with Flisk as a local process

Flisk can scaffold the FastAPI service for you and start it without Docker. Install it with npm install -g @flisk-sh/flisk, then in a project folder:

flisk project --yes
flisk resource crew-api --type backend --language python --local --stack agents --yes

The scaffold writes services/agents/crew-api/ with a pyproject.toml, a FastAPI src/main.py and a service.json whose command is a uvicorn line. Replace src/main.py with the wrapper above, add crewai to the dependencies in pyproject.toml, and install them into your active virtual environment. The scaffold pins its own versions, so if pip reports a conflict with CrewAI's requirements, loosen the pins. Flisk will refuse to start a command whose program is not installed.

Pass the model key through env in service.json. In a local-process service, ${VAR} is read from your shell, the project .env or the service's own .env:

"env": { "OPENAI_API_KEY": "${OPENAI_API_KEY}" }

Then start it and try a run:

flisk up
curl -X POST localhost:4003/runs -H 'content-type: application/json' -d '{"topic":"local dev tools"}'
curl localhost:4003/runs/<id>

Use the port that flisk up prints for your service. The scaffold chose 4003 in a fresh project, but the next free port depends on what the project already has.

Pitfalls

  • Reload drops runs. The scaffold's uvicorn command includes --reload --reload-dir src. Saving any file in src restarts the process, and the in-memory run table is gone with it. While you test a long run, do not edit files, or remove --reload from the command.
  • Threads and shared state. A crew object keeps state while it runs. Build a new one per run, as the wrapper does, instead of sharing one instance between requests.
  • Cost control. A crew that cannot finish keeps calling the model. Set iteration limits on its agents; see how to stop an agent from looping forever.
  • Keys. Never write the key into service.json. See keeping LLM API keys out of git.

When this is more than you need

If you only run the crew from your terminal, crewai run is the right tool and a wrapper adds nothing. Build the API when something else has to call the crew, for example a React frontend, a webhook handler or a test suite. The same pattern for any Python framework is covered in putting a Python agent behind a FastAPI endpoint. For a different framework with durable runs, read running a LangGraph agent locally.

Questions people ask

Does Flisk have a CrewAI template?

No. Flisk has no CrewAI-specific scaffold. You can scaffold a plain Python FastAPI service with flisk resource --language python --local and put your crew behind it.

Can I use kickoff_async instead of a thread?

CrewAI offers async kickoff methods, and they work if your wrapper is async. A thread around the blocking kickoff is the simplest version and behaves the same for the caller.

Where do I keep run results so they survive a restart?

Replace the in-memory dict with a database table or a file per run. The wrapper only needs to write a status and an output for each run id.
