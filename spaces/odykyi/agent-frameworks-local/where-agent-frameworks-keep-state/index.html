Agent frameworks on your laptop

Where agent frameworks keep state: LangGraph, CrewAI and others

Two different things get called state: the conversation so far, and the progress of a run in flight. Frameworks cover them very differently.

Most agent frameworks keep nothing between runs unless you configure it. Some store the conversation only when you pass a session or storage object, a few can resume a run that was cut in half, and some leave all storage to your own code. Before you pick a framework for an agent that must survive a restart, decide which kind of state you need.

Two kinds of state

Conversation state is the history: what the user said and what the agent answered. Losing it means the agent forgets you. Run state is where a multi-step run had got to: which nodes finished, which tool results exist. Losing it means a half-finished job starts over, or finishes twice.

Most chat apps need only the first. Long jobs that call tools with side effects need the second. Frameworks that look equivalent in a demo often cover only one.

The comparison

This is a summary of each framework's documented model. Names and defaults change between releases, so confirm against the version you install.

Read the table as a map of where to look, not as a ranking. The two stateless SDKs are not worse; they give you a thin function and trust you to store messages, which is exactly what you want in a web app that already has a database.

What goes wrong in practice

  • The default saver is in memory. Tutorials use the memory option because it needs no setup. The agent seems to remember until the first restart, which in development is every file save.
  • A file inside a container disappears. If storage is a SQLite file in the container's own filesystem, recreating the container deletes it. Mount a named volume on the folder, or use a database server.
  • Resumed work runs twice. Resuming from a checkpoint repeats the step that was running when the process died. Make tools that charge cards or send email idempotent, whatever the framework.
  • History grows without limit. Every stored message is re-sent to the model. Plan to trim or summarise.

Where Flisk fits

Flisk does not replace any framework's state handling, and it does not know which one you use. What it offers is a framework-neutral layer for the conversation kind of state. The agent resource (flisk resource bot --type agent) is an HTTP service that keeps one checkpoint per session id, written atomically, on a named volume or in Postgres (--durability files|postgres). Your framework runs inside its runTurn function, so a stateless SDK gets durable sessions without extra code, as shown in using the Vercel AI SDK inside runTurn.

For frameworks that bring their own storage, Flisk's job is the stack around it: start the database before the agent, keep a volume across restarts, and restart the process when it crashes. See restarting an agent without losing state and durable agent sessions and checkpoints.

A quick way to choose

If the agent is a long job with side effects, pick something with run checkpoints and test the crash path on purpose: kill the process mid-run and see what happens. If it is a chat, any framework works, and the decision is where messages live. Whatever you choose, write the restart test first; the next article on step limits covers the other failure that costs money, a run that never ends.

Questions people ask

Which framework survives a restart by default?

None of the ones compared here persist anything by default. Each needs a file or database-backed store, or your own message storage, to survive a restart.

Is conversation memory the same as a checkpoint?

No. Memory holds what was said. A checkpoint holds where a run was, so it can continue after a crash. Some frameworks offer one, some both.

Do I need Flisk's agent resource if my framework has storage?

No. It is useful mainly for stateless libraries or when you want one session API across several agents. A framework with its own saver works with Flisk as an ordinary service.
