How to build webhook delivery with signatures and retries

Receiving webhooks gets all the attention. If your product sends them, the hard parts are the retries you control and the signature your customers will verify.

To send webhooks reliably, write each event to a table first, deliver from a separate worker that signs the body with an HMAC and a timestamp, treat any 2xx response as success, and retry everything else with exponential backoff and jitter until a limit. Storing the event before sending is what lets you retry, replay and audit later.

The moving parts

A webhook sender is smaller than it looks, and it has the same shape in every product:

  • An events table. One row per thing that happened, with a stable ID, a type and the JSON payload, written in the same database transaction as the change itself.
  • A deliveries table. One row per event and endpoint, with an attempt count, the next attempt time and the last response code.
  • A worker. It picks deliveries that are due, sends them and records the result.
  • Endpoints with secrets. Each customer endpoint has its own signing secret.

Writing the event in the same transaction as the change avoids two bad outcomes: an event for a change that rolled back, and a committed change with no event. A separate worker keeps a slow customer server from slowing your API.

Signing the request

Customers must be able to check that a request came from you and was not altered. Send the event ID, a timestamp and a signature in headers. The Standard Webhooks specification uses webhook-id, webhook-timestamp and webhook-signature, with an HMAC-SHA256 over the ID, the timestamp and the body joined with dots, base64 encoded. Following a published format means customers can use existing libraries. If you design your own, keep these properties:

  • The signature covers the timestamp, so a captured request cannot be replayed forever. Tell customers to reject old timestamps.
  • The signature covers the exact body bytes, which is why receivers need the raw body. Serialize once, sign those bytes and send those bytes.
  • The event ID stays the same on every retry, so receivers can ignore duplicates.
import { createHmac } from "node:crypto";

function sign(secret, id, ts, body) {
  return "v1," + createHmac("sha256", secret)
    .update(id + "." + ts + "." + body).digest("base64");
}

async function deliver(d) {
  const body = JSON.stringify(d.payload);     // serialize once
  const ts = Math.floor(Date.now() / 1000);
  const res = await fetch(d.url, {
    method: "POST",
    headers: {
      "content-type": "application/json",
      "webhook-id": d.event_id,
      "webhook-timestamp": String(ts),
      "webhook-signature": sign(d.secret, d.event_id, ts, body)
    },
    body,
    signal: AbortSignal.timeout(10000)
  });
  return res.status;
}

Retries that do not hurt anyone

Treat any 2xx as delivered and everything else, including a timeout, as a failure to retry. Space the attempts out with exponential backoff and add random jitter, so a customer server that comes back after an outage is not hit by every queued event in the same second:

function nextDelaySeconds(attempt) {
  const base = Math.min(30 * 2 ** attempt, 6 * 3600);   // cap at 6 hours
  return base / 2 + Math.random() * base / 2;
}

Decide the stopping rule up front. Stripe retries live-mode events for up to three days. Whatever you pick, mark the delivery as failed after the last attempt, keep it visible in a dashboard, and let the customer replay it. Consider disabling an endpoint that has failed for days and telling its owner. Set a short timeout. A customer endpoint that takes a minute to answer holds a worker for a minute.

Testing it locally with Flisk

You need a receiver that misbehaves on purpose. A few lines are enough: a service that returns 500 for the first N requests and then 200, and logs each attempt with its headers.

// receiver/server.js
let seen = 0;
const failFirst = Number(process.env.FAIL_FIRST || 2);
require("http").createServer((req, res) => {
  if (req.url === "/health") return res.end("ok");
  let raw = "";
  req.on("data", c => raw += c);
  req.on("end", () => {
    seen += 1;
    console.log("attempt", seen, req.headers["webhook-id"]);
    res.statusCode = seen <= failFirst ? 500 : 200;
    res.end();
  });
}).listen(process.env.PORT);

Run the receiver and the sender as two local processes. Install with npm install -g @flisk-sh/flisk, then give each a service.json:

{ "schemaVersion": 1, "appName": "receiver", "appType": "backend",
  "command": "node server.js", "port": 4100, "healthCheckPath": "/health",
  "env": { "FAIL_FIRST": "2" } }

{ "schemaVersion": 1, "appName": "sender", "appType": "worker",
  "command": "node worker.js", "dependsOn": ["receiver"],
  "env": { "TARGET_URL": "http://localhost:4100/hook" } }

flisk up starts the receiver, waits for it to be healthy and then starts the sender. Watch the attempts across both services in time order with flisk logs --since 5m. You should see two 500 responses, then a success, with the same webhook-id each time and growing gaps between them. For a fast test, use a short backoff base through an environment variable instead of waiting minutes. Flisk does not provide webhook delivery or retries. It runs the pieces so you can see them work.

Pitfalls

  • Sending inside the request. An API call that waits for a customer's server inherits that server's slowness and failures.
  • One secret for everyone. A leaked shared secret breaks every customer. Use one per endpoint, and support rotation by accepting two secrets for a while.
  • Following redirects blindly. A customer URL that redirects to an internal address is a request forgery risk. Block private address ranges and do not follow redirects without a check.
  • No replay. The first time a customer says "we missed events from Tuesday", you need a button and not a database script.
  • Ordering promises. Retries reorder events. Say so in your docs, and see handling out-of-order events for what receivers should do.

The retry loop is a queue consumer at heart. Testing queue consumer retries locally covers the dead-letter side in more depth.

Questions people ask

What status codes should a webhook sender treat as success?

Any 2xx. Treat other codes and timeouts as failures to retry, with exponential backoff and jitter, up to a limit you document.

How do I sign outgoing webhooks?

Compute an HMAC-SHA256 with a per-endpoint secret over the event ID, a timestamp and the exact body, and send it in a header. The Standard Webhooks format is a good published choice.

Should the API call send the webhook directly?

No. Store the event in the same transaction as the change and let a separate worker deliver it, so a slow receiver cannot slow your API and failed sends can be retried.
