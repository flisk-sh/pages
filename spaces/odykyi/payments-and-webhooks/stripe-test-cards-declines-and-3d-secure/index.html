Stripe test cards for declines, 3D Secure and insufficient funds

A payment flow that only ever sees 4242 4242 4242 4242 is untested. These are the cards that make Stripe fail on purpose, and what your code should do with each.

Stripe test mode accepts special card numbers that force a specific result. Use 4242 4242 4242 4242 for success, 4000 0000 0000 0002 for a generic decline, 4000 0000 0000 9995 for insufficient funds and 4000 0025 0000 3155 for a payment that needs 3D Secure authentication. Any future expiry date, any three-digit CVC and any postal code work with all of them.

The cards worth keeping in a test file

Card numberWhat happensWhat your code should do
4242 4242 4242 4242The payment succeedsMark the order paid after the webhook
4000 0000 0000 0002Declined with card_declinedShow a retry message, keep the order unpaid
4000 0000 0000 9995Declined with insufficient_fundsAsk for another card, do not say "card number invalid"
4000 0025 0000 3155Requires 3D Secure authenticationComplete the challenge, handle the customer abandoning it
4000 0000 0000 0341Attaching to a customer works, later charges failHandle a failed renewal on a saved card
4000 0000 0000 0259Succeeds, then a dispute is openedHandle a chargeback event

The full list is in Stripe's testing documentation, and it changes over time, so treat the table as a starting set and check the page when a number stops behaving as described.

Why each case matters

The decline. Most checkout bugs live here. The order was created before the payment, so a decline leaves a row in "pending". Your test should assert that the order is still unpaid, that no confirmation email went out and that the customer can try again with the same order.

Insufficient funds. It is a decline with a different decline_code. If your error mapper shows one message for every failure, this case shows you whether you read the code or just the type.

3D Secure. The payment does not finish in one request. Stripe returns a status that says further action is needed, the browser shows an authentication step, and the final result arrives later by webhook. The common mistakes are treating the first response as success and never handling the case where the customer closes the challenge. In test mode the challenge page has buttons to complete or fail the authentication, so you can walk both paths by hand.

The failing saved card. It is the cheap way to reach the "payment failed on renewal" branch without waiting for a billing cycle. See testing renewals with test clocks for the time side of that.

Using them from code

For a server-side test you often do not type a number at all. Stripe provides test payment method IDs, such as pm_card_visa, that you can pass directly:

const intent = await stripe.paymentIntents.create({
  amount: 2000,
  currency: "usd",
  payment_method: "pm_card_visa",
  confirm: true,
  automatic_payment_methods: { enabled: true, allow_redirects: "never" }
});
console.log(intent.status);   // "succeeded"

A declined card throws an error with a code field, which is what you assert on:

try {
  await stripe.paymentIntents.create({ /* ... same, with a declining method ... */ });
} catch (err) {
  console.log(err.type, err.code);   // StripeCardError card_declined
}

Use the card numbers in a browser test (Playwright or Cypress against the hosted Checkout page or Stripe Elements) and the payment method IDs in API-level tests. Mixing them up wastes time: Elements fields live in an iframe that is awkward to automate, so keep the browser tests few and let the API tests cover the many branches.

Where Flisk fits

Flisk does not change which card does what, since that is Stripe's behaviour. What it gives you is a repeatable place to run the checks: your API, the database and the worker as one stack started with flisk up, so a test that pays with a declined card can then read the order row and the worker's log. Running integration tests against the real stack covers that setup.

Pitfalls

  • Real card numbers. Test mode rejects a real card, and typing one into a test page is a habit you do not want.
  • Live mode has different rules. A test-only number fails in live mode, and live issuers decline for reasons you cannot reproduce here. Treat test cards as coverage of your code paths, not of the card networks.
  • Assert on codes, not on message text. The human message can change. card_declined and insufficient_funds are stable.
  • Do not assert on webhook arrival order. The failed and the later events may arrive in any order.

After the failure paths pass, move on to the follow-up side: testing refunds and chargebacks reuses the dispute card from the table.

Questions people ask

Which Stripe test card always declines?

4000 0000 0000 0002 produces a generic card_declined error. Use 4000 0000 0000 9995 when you want the insufficient_funds decline code.

How do I test 3D Secure in Stripe test mode?

Pay with 4000 0025 0000 3155. Stripe shows a test authentication page where you can complete or fail the challenge, and the final result is sent by webhook.

Do the test card details matter beyond the number?

No. Any future expiry date, any three-digit CVC and any postal code work with the test numbers.
