How to test subscription renewals with Stripe test clocks

Billing code runs on the calendar. A test clock gives it a calendar you control, and Stripe sends the same webhooks it would in a month.

Stripe test clocks let you move a simulated clock forward in test mode, attach customers to it, and watch Stripe run its billing, trial end and renewal logic at the new time. You create a clock, create a customer and a subscription on that clock, advance the clock, and your webhook endpoint receives the real events, so the month-long path runs in a few minutes.

The problem with time

Subscription code has branches you rarely reach: the trial ends, the first invoice is paid, the second invoice fails, the account is retried, and after the last retry the subscription is cancelled. Waiting for real days is not an option, and changing your own machine's clock does nothing, because Stripe's clock is on its servers. Faking time inside your code only tests your code against your assumptions about Stripe. A test clock changes Stripe's time, so Stripe itself produces the invoices and events.

How a test clock works

  1. You create a test clock with a starting frozen_time, a Unix timestamp.
  2. You create a customer with test_clock set to that clock. Anything the customer owns, subscriptions and invoices included, follows the clock.
  3. You advance the clock to a later time. Stripe processes everything that would have happened up to then and sends the matching events.

Test clocks exist in test mode only. A clock moves forward, never back, so to repeat a scenario you create a new clock and new customers. Stripe limits how far one advance can go and how many customers a clock can hold, so advance in stages and check the current limits in its documentation.

A scenario in code

const now = Math.floor(Date.now() / 1000);

const clock = await stripe.testHelpers.testClocks.create({
  frozen_time: now,
  name: "trial-then-renewal"
});

const customer = await stripe.customers.create({
  email: "test@example.com",
  test_clock: clock.id,
  payment_method: "pm_card_visa",
  invoice_settings: { default_payment_method: "pm_card_visa" }
});

await stripe.subscriptions.create({
  customer: customer.id,
  items: [{ price: process.env.PRICE_ID }],
  trial_period_days: 7
});

// Move 8 days ahead: the trial ends and the first invoice is created
await stripe.testHelpers.testClocks.advance(clock.id, {
  frozen_time: now + 8 * 24 * 3600
});

Advancing is asynchronous. The clock reports a status of advancing and then ready. Poll stripe.testHelpers.testClocks.retrieve(clock.id) until it is ready before you assert anything, or you will check state that Stripe has not finished creating.

What to assert after each advance

  • After the trial. You receive an invoice event and a payment event, and your database shows the subscription as active, not trialing.
  • After one renewal period. A new invoice is paid. Check that you extended access by one period, not two. Duplicate delivery is the usual cause of a double extension.
  • After a failing card. Attach the card 4000 0000 0000 0341, which attaches but fails on charge, advance to the renewal date and confirm your code marks the account past due and does not cut access instantly. Stripe test cards for declines lists that number with the others.
  • After the last retry. The subscription is cancelled and your system revokes access.

Running it next to your stack

The events reach your laptop through stripe listen --forward-to localhost:4000/webhooks/stripe as described in testing Stripe payments locally. Real time does not move: events from an advance arrive within seconds. With Flisk, run the API as a local process (flisk up), keep the scenario script as a one-shot command, and read what the API did with:

flisk run api -- node scripts/renewal-scenario.js
flisk logs --service api --since 5m

flisk run starts the script with the environment the api service has, which includes the test key from .env, and returns the script's exit code, so the same command works in CI. Flisk adds nothing to Stripe's clock. It only keeps the API, its database and the script in one place.

Pitfalls

  • Customers not on the clock. A customer created without test_clock lives in real time and never advances.
  • Cleanup. Deleting a clock deletes its customers and their data. Do it when a scenario ends so the test account stays readable.
  • Your own timers. If your app also computes "days left" from your machine's clock, the two will disagree. Drive access decisions from Stripe's events and fields, not from local time.
  • Skipping the wait for ready. The most common cause of a flaky renewal test.
  • Treating it as the real world. A test clock does not reproduce issuer behaviour, bank holidays or live retry timing. It tests your handling, not Stripe's schedule.

For the related question of money going back, see testing refunds and chargebacks.

Questions people ask

Can I move a Stripe test clock backwards?

No. A test clock only moves forward. To rerun a scenario, create a new clock and new customers attached to it.

Do Stripe test clocks work in live mode?

No. They exist only in test mode, so they are safe to use on a development account.

Why are my renewal events missing right after I advance the clock?

Advancing is asynchronous. Wait until the clock status is ready, then check for events. Also make sure stripe listen or a webhook endpoint is receiving events.
