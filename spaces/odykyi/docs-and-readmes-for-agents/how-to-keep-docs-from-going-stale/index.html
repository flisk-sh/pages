How to keep README and docs from going stale: test them in CI

Stale docs mislead people and agents. Use CI to run the commands in your docs, check links and fail the build when a documented step no longer works.

Treat commands and links in your docs as code and test them in CI. A docs page whose commands are run on every pull request cannot silently rot, and that matters more now that agents run what the docs say without questioning it.

Why docs go stale

Code changes in a pull request and the docs do not. Nobody notices until a new user or an agent follows a command that no longer exists. The fix is not discipline but a check that fails.

Run the quick start in CI

Put the quick start steps in a script and run that script in CI. If the README says three commands, the job runs those three commands.

name: docs
on: [pull_request]
jobs:
  quickstart:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: bash scripts/quickstart.sh

To avoid keeping the script and the README apart, extract the code block from the README in the script, or have the README link to the script. One source is the goal.

Check links

Broken links are the cheapest staleness to find. A link checker such as lychee runs fine in CI. Check its own docs for current flags.

lychee --no-progress README.md docs/

Run it on pull requests that touch docs and on a weekly schedule, because external pages die even when you change nothing.

Check that documented paths and scripts exist

A small script can catch most drift. Search the docs for npm script names and file paths, and verify each exists.

grep -o 'npm run [a-z:-]*' README.md AGENTS.md | sort -u |
while read -r _ _ name; do
  grep -q "\"$name\"" package.json || echo "missing script: $name"
done

It is crude, but it catches a renamed script in seconds. Make the job exit non-zero when it prints anything.

Test code samples, not just commands

Code samples in docs rot faster than shell commands, because a changed function signature breaks them without any visible failure. Keep samples as real files in an examples folder, run them in CI, and include them in the docs from there. If a sample must live inline, extract fenced blocks with a small script and run them.

node examples/basic.js
python examples/basic.py

Pin the versions your samples use in the example itself. A sample that says "latest" is a sample that will break on a day you did not choose.

Make staleness a review item

  • Add a pull request checklist line: "Docs updated if behaviour changed".
  • Put the rule in AGENTS.md so agents update the docs with the code.
  • Fail CI if the README score or required sections regress, using a fixed checker such as README Score.

For the idea behind deterministic gates, see CI guards and AI code review. For the instruction file itself, see What is AGENTS.md.

Questions people ask

Can an AI update my docs automatically?

It can draft changes, but have CI run the commands and a person review the result. A model can write a confident, wrong command.

How often should link checks run?

On every pull request that touches docs, plus a weekly scheduled run to catch external links that died.

Check your README

Find out which sections your README is missing.

README Score gives a GitHub README a score out of 100 with the sections found and missing. It uses fixed rules and no AI, so the same README gets the same score. Free to try.
