README structure that scores well: a section checklist

The sections a good README has, in a sensible order, with a short template. Use it to find gaps before a reader or an agent does.

A strong README answers six questions in order: what is this, why would I use it, how do I install it, how do I use it, how do I contribute and what is the license. Missing any one of them is the usual reason a README feels incomplete.

The checklist

  1. Title and one-sentence description.
  2. Why it exists, or what problem it solves, in two or three lines.
  3. Install or quick start, with commands that run.
  4. Usage: one realistic example, then links to more.
  5. Configuration: options and environment variables.
  6. Contributing: how to run tests and open a pull request.
  7. License, named and linked to the file.

Optional but useful: requirements, supported platforms, a link to the changelog, and where to get help.

A template you can copy

# project-name

One sentence: what it does and for whom.

## Why
Two or three lines on the problem and how this differs from the usual option.

## Install
npm install project-name

## Usage
A short, complete example that runs as written.

## Configuration
| Option | Default | Meaning |

## Contributing
npm install && npm test, then open a pull request.

## License
MIT. See LICENSE.

Order matters

People and agents read from the top and stop when they have enough. Put install and usage before history, philosophy or a long feature list. Badges are fine, but a row of ten pushes the first useful line off the screen.

Use headings that say what is under them. "Install" and "Usage" are searched for by readers and by tools. "Getting going" and "Fun stuff" are not.

Write for the skimmer

Most visitors decide in ten seconds. Use short paragraphs, code blocks for anything typed, and tables for options. Put a screenshot or terminal output near the top if the project has a visible result, with alt text that says what it shows, since agents and screen readers cannot see the image itself.

Link to deeper docs instead of growing the README. A README over about 400 lines usually hides its own best parts.

Check it with a score

You can run a checklist like this by hand, or let a tool do it. README Score takes a GitHub repository or pasted text and returns a score out of 100, the sections it found and missed, and a suggested fix for each. It uses fixed rules, with no AI, so the same README always gets the same score. That makes it good for catching missing sections and unsuitable for judging clarity. Read your README aloud once as well.

Common gaps

  • No license, which blocks many companies from using the project.
  • An install section that assumes tools the reader may not have.
  • A usage example that is a fragment and does not run.
  • No contributing section, so outside pull requests arrive without tests.

Fix the gaps in that order. For the commands themselves, see How to document commands so agents run them correctly.

Questions people ask

Does a high README score mean a good project?

No. It means the expected sections are present. It says nothing about code quality or whether the project is maintained.

Should the README include an API reference?

Only for small projects. Otherwise link to a separate reference and keep the README as the front door.
