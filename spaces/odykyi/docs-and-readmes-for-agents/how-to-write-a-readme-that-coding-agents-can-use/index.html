How to write a README that coding agents can use

A README that works for people and for coding agents: what to put first, which commands to list, and which habits make an agent guess wrong.

Put the exact commands to install, run and test the project near the top, and say what the project is in one sentence. A coding agent reads your README the same way a new hire does: it takes the first screen as the truth and runs what it finds there.

Start with one sentence and one command

The first line should say what the project is and who it is for. Then show the shortest path to a working result. Agents stop reading early when they find something that looks runnable.

# acme-queue

A small job queue for Node services, backed by Postgres.

## Quick start

npm install
npm run dev

If the quick start needs a database or a key, say so on the next line. A missing prerequisite is the most common reason an agent loops on a failing command.

List install, run, test and lint separately

Four short blocks beat one paragraph. Agents look for a command to verify their own work, so the test and lint commands matter more than the install line.

## Commands

npm install        # install dependencies
npm run dev        # start on http://localhost:3000
npm test           # unit tests, about 20 seconds
npm run lint       # must pass before a pull request

Add the expected time or output when it helps. "About 20 seconds" tells an agent not to kill the process early.

State versions and prerequisites

Name the runtime version, the package manager and any system tool. "Node 20, pnpm, Docker" is enough. Do not write "recent Node". If you pin a version in a file such as .nvmrc or .python-version, mention that file.

  • Runtime and package manager, with versions.
  • Services that must be running, such as Postgres or Redis.
  • Environment variables, listed by name in a .env.example, never with real values.

Say where things live

A short map of the repository saves an agent a lot of searching. Three to eight lines is plenty.

src/        application code
src/api/    HTTP handlers
tests/      unit and integration tests
scripts/    maintenance scripts, not run in production

Keep it to what is stable. A map that lists every file goes stale in a week. For rules aimed only at agents, such as "do not edit generated files", use a separate file, covered in What is AGENTS.md.

Pitfalls that make agents guess

  • Commands in screenshots or images. Agents cannot copy them.
  • Commands that only work after an undocumented step.
  • Prompts like $ npm test mixed into copy-paste blocks. Leave the dollar sign out.
  • Marketing text before the first command. Move it below.

Questions people ask

How long should a README be?

Long enough to get a new reader to a running project and no longer. Put detail in a docs folder and link to it.

Should I write a separate README for agents?

Usually not. Keep one README for everyone and add an AGENTS.md for rules that only matter to coding agents.

Do agents read the whole README?

Often they read the top and search for the rest. Put the commands and prerequisites first.
