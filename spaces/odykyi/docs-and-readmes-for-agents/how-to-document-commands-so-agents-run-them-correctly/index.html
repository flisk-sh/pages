How to document commands so agents run them correctly

Write install, build and test commands that an agent can copy, run and verify. Covers working directory, exit codes, prerequisites and long-running processes.

  1. One command per line, no prompt characters
  2. State the working directory
  3. Say what success looks like
  4. Mark long-running and destructive commands
  5. Make one command do the whole check

Write each command as a copy-paste line in a code block, say which directory to run it from, and say what success looks like. An agent cannot ask you what you meant, so every missing assumption turns into a failed run or a wrong guess.

One command per line, no prompt characters

Leave out the leading dollar sign and any shell prompt text. Put one command per line, and put comments on their own line or after the command.

npm install
npm test -- --run
npm run build

If a step has several parts, number them. Do not describe commands in prose, such as "install the dependencies and then run the tests". Show the lines.

State the working directory

In a monorepo, the same command means different things in different folders. Say where to run it, or write it so it works from the root.

# from the repository root
npm --prefix cli test
make test-python

Using a flag like --prefix or a Makefile target removes the "which folder am I in" problem completely.

Say what success looks like

An agent needs a signal to decide it is done. Tell it:

  • Exit code: the command exits with 0 on success.
  • Output: a line such as "42 passed" or a URL that should respond.
  • Time: "takes about two minutes" so the agent does not give up early.
npm run dev
# ready when http://localhost:3000/health returns 200
curl -fsS http://localhost:3000/health

The -f flag makes curl exit non-zero on an HTTP error, which is what a script or agent needs.

Mark long-running and destructive commands

A dev server never exits. Say so, and say how to run it in the background or in a second terminal. An agent that runs it in the foreground will hang.

Mark anything destructive plainly, for example a command that drops a database or wipes a volume. Put it under a heading that says "Reset" and state what is lost. Agents follow headings.

Make one command do the whole check

A single entry point such as make test or npm run verify that runs lint, types and tests gives an agent one thing to run before it says it is done. For a multi-service project, a local runner helps too. The Flisk CLI starts services from service.json files with flisk up and reports state with flisk status --json, a machine-readable form that is easy to document. It is a local development tool, not a production orchestrator. For the README side of all this, see How to write a README that coding agents can use.

Questions people ask

Should commands include the dollar sign?

No. Omit it so a reader or agent can copy the line without editing it.

How do I document a command that needs a secret?

Name the environment variable and point to a .env.example file. Never print a real value in the docs.
