How to store secrets in a Cloudflare Worker

Keep API keys out of your code and repo: wrangler secret put for production, .dev.vars for local, and what not to put in plain vars.

Run npx wrangler secret put API_KEY, paste the value, and read it as env.API_KEY. For local runs, put the same names in a .dev.vars file that is never committed.

Secrets versus vars

Plain variables in wrangler.toml are visible in your repo and dashboard. Use them for non-sensitive settings only.

[vars]
APP_NAME = "notes"
LOG_LEVEL = "info"

Anything that grants access, such as tokens, passwords, webhook signing keys and private keys, must be a secret.

Set a production secret

npx wrangler secret put API_KEY
npx wrangler secret list
npx wrangler secret delete API_KEY

The value is stored encrypted and cannot be read back through Wrangler. Keep your own copy in a password manager. To set one non-interactively in CI, pipe it in.

printf '%s' "$API_KEY" | npx wrangler secret put API_KEY

Local development

# .dev.vars  (add to .gitignore)
API_KEY=local-test-value
echo ".dev.vars" >> .gitignore
echo ".wrangler" >> .gitignore

Use test values locally, not production keys. See env and secrets for local development for habits that carry across projects.

Use them safely in code

  • Never log a secret or return it in a response, including in error messages.
  • Send it in an Authorization header, not in a URL.
  • Give each token the smallest scope. A key that can only read is safer than one that can delete.
  • Rotate keys on a schedule and immediately after any suspected leak.

Separate staging from production

Use a different Worker, and different keys, for staging. Wrangler supports named environments in the config, and secrets are set per environment.

npx wrangler secret put API_KEY --env staging
npx wrangler deploy --env staging

A staging key that leaks should never open production data. Give staging its own database too, and never copy real customer data into it.

Finally, scan your repository for old keys. Check the Git history, not just the current files, using a scanner such as gitleaks. If an old commit contains a real key, rotate it, since removing the file does not undo the exposure.

Never in the browser

A secret used only in the Worker stays server side. If your frontend needs the result of a secret-backed call, have the browser call your Worker and let the Worker call the third party. A key embedded in client code is public. More in AI security for builders.

Questions people ask

Can I read a secret back after setting it?

No. Wrangler can list secret names but not values. Keep the source of truth in a password manager.

Is Workers secret storage the same as a vault?

It is encrypted storage for your Worker's configuration. For org-wide controls such as rotation policies, use a dedicated secrets manager.
