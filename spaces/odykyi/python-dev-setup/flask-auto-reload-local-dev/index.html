How to run Flask with auto-reload in local development

Flask has a reloader built in. The trick is knowing which command turns it on, what it watches, and why you must never leave it on outside your laptop.

Start Flask with flask --app app run --debug. The --debug flag turns on both the reloader, which restarts the server when your Python files change, and the interactive debugger, which shows a traceback page in the browser. Use --port to choose the port. Never enable debug mode on a server that anyone else can reach.

The commands that work

With a file named app.py that defines app = Flask(__name__):

flask --app app run --debug --port 5000

--app names the module, or module:object if your variable has another name. Without --app, Flask looks for app.py or wsgi.py by itself. You can also set the environment variable FLASK_DEBUG=1 instead of passing the flag.

Older tutorials end the file with app.run(debug=True) and start it with python app.py. That still works. The flask run form is preferred now because it uses the same app discovery everywhere, including the shell command flask shell and CLI commands you add yourself.

What the reloader watches

The reloader restarts the process when an imported Python module changes. If watchdog is installed, Flask uses it, which is more efficient. Without it, the reloader polls file times. Things it does not watch by default are non-Python files that your app reads at start, such as a JSON config or a translation file. Add them explicitly:

flask --app app run --debug --extra-files config.json:translations/messages.po

The separator is the OS path separator, a colon on macOS and Linux. Jinja templates are a special case. In debug mode Flask reloads templates when they change without restarting the process, so you do not need to list them.

If your reloader restarts constantly, something in the watched tree is changing on its own, for example a log file or a .venv folder. The newer versions of Flask let you filter with --exclude-patterns. Another fix is to keep the virtual environment outside the project folder.

Why the debugger is dangerous

The Werkzeug debugger lets anyone who can open the error page run Python code on your machine. It is protected by a PIN printed to your terminal, which is a guard against accidents and not a security boundary. Keep two rules:

  • Bind to 127.0.0.1, which is Flask's default. Do not use --host 0.0.0.0 on a shared network just to test from a phone.
  • Do not set FLASK_DEBUG=1 in any image or environment you deploy. Production should use a real server such as gunicorn.

Run it next to other services with Flisk

Flask is just a command to Flisk. Put it in a service.json and give it a health route:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "toolchain": "python@3.12",
  "command": "flask --app app run --debug --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}
@app.get("/health")
def health():
    return {"status": "ok"}

Flisk passes PORT to the process and runs the command through a shell from the service folder, so $PORT expands. Flisk waits for /health to answer before it starts services that depend on this one,. The reload still comes from Flask, not from Flisk. Read the output with flisk logs --service api --tail 50 and stop everything with flisk down. Flisk does not create a virtualenv, so activate yours first or call .venv/bin/flask in the command. This setup is described in running services without Docker.

Flisk scaffolds FastAPI, not Flask, for its Python backend template. A Flask service is a service you write yourself and register with a service.json, which is the example above. If you want the container route for it, you would write your own Dockerfile and use the bring your own Dockerfile path.

Pitfalls

  • Port 5000 is taken on macOS. AirPlay Receiver can listen there, so a default Flask start fails or answers with something else. Pick another port, which is what $PORT under a manager gives you.
  • Reloader runs your startup code twice. It starts a parent and a child process. Code at import time, like creating a background thread, runs in both. Keep side effects inside functions.
  • Environment changes need a restart. Flask does not re-read .env on reload unless your code loads it at startup.
  • Docker bind mounts. File events may not arrive from a mounted folder. See hot reload not working.

Next step

Reload is only half of the loop. To stop at a line and look at variables, read debugging with debugpy. If you use uvicorn instead, the equivalent problems are in uvicorn reload not working.

Questions people ask

What is the difference between flask run --debug and app.run(debug=True)?

Both enable the reloader and the debugger. flask run --debug is the current way and works with Flask's app discovery and CLI commands.

Why does my Flask app start twice with the reloader?

The reloader launches a parent process that watches files and a child that serves requests, so import-time code runs in both.

Does Flisk have a Flask template?

No. Flisk's Python backend scaffold uses FastAPI. A Flask app runs as any other service with a command in its service.json.
