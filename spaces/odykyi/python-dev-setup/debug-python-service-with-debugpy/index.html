How to debug a Python service with debugpy and VS Code

Print statements get you far. When they stop being enough, attach a real debugger to the running service. It is a small amount of setup and it works the same for a service you start by hand or through a tool.

Install debugpy, start your service with python -m debugpy --listen 5678 -m uvicorn main:app, and add an "attach" configuration to VS Code that connects to port 5678. Then set breakpoints in the editor and send a request. Turn off auto-reload while you debug, because the reloader runs your code in a child process, which complicates attaching.

Two ways to debug in VS Code

Launch means VS Code starts your program under the debugger. It is the easiest when you have one service. Attach means the program is already running and the debugger connects to it. Attach is what you want when something else starts the service, such as a process manager or a container, or when you only want to debug one of several services.

Launch configuration for a single service

In .vscode/launch.json:

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "API (launch)",
      "type": "debugpy",
      "request": "launch",
      "module": "uvicorn",
      "args": ["main:app", "--port", "8000"],
      "cwd": "${workspaceFolder}/api",
      "envFile": "${workspaceFolder}/.env"
    }
  ]
}

This needs the Python Debugger extension, and VS Code must have the right interpreter selected, ideally your project's .venv. Notice there is no --reload. The debugger works with the process it started, and a reloader replaces that process on every save.

Attach to a service that is already running

Install the package in the same environment as the service:

python -m pip install debugpy

Start the service so that it listens for a debugger:

python -m debugpy --listen 127.0.0.1:5678 -m uvicorn main:app --port 8000

The program runs normally and debugpy waits in the background for a client. Add --wait-for-client only if you need to debug code that runs at startup. Otherwise a service that blocks until you attach will never answer its health check.

Then the attach configuration:

{
  "name": "API (attach)",
  "type": "debugpy",
  "request": "attach",
  "connect": { "host": "localhost", "port": 5678 },
  "pathMappings": [
    { "localRoot": "${workspaceFolder}/api", "remoteRoot": "${workspaceFolder}/api" }
  ]
}

When the service runs on the same machine, the local and remote roots are the same folder. They only differ when the program runs inside a container, where the code is mounted at another path, for example /app. Then remoteRoot must be that container path or breakpoints will show up as unbound.

Debug one service in a Flisk stack

A service Flisk starts from a command is an ordinary process on your machine, so a debugger can attach to it. Put the debugpy command in its manifest while you debug:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "python -m debugpy --listen 127.0.0.1:5678 -m uvicorn main:app --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}

Run flisk up, attach VS Code to port 5678, and the other services keep running as usual. Flisk's own readiness checks still apply, so keep --wait-for-client out of this command. Change the command back (or keep a second manifest value in a branch) when you finish, so the team does not inherit a debug port. Container services behave differently: they need the debug port published and the path mappings above.

For breakpoints in a one-off script, a test or a management command, use flisk run, which passes stdin and stdout through, so an interactive debugger prompt works:

flisk run api -- python -m pytest --pdb

That runs pytest on the host from the service folder with the service's environment, and drops into pdb on the first failure. Details are in running a one-off command.

Pitfalls

  • Breakpoints that never hit. Wrong interpreter, wrong path mapping, or the code path never ran. Add a log line to confirm the request reaches that function.
  • Debugging with --reload on. The reloader runs your app in a child process and replaces it on change. Debug without reload, then turn it back on.
  • Exposing the debug port. debugpy gives whoever connects full control of the process. Listen on 127.0.0.1, not 0.0.0.0, unless you also control the network.
  • Timeouts. Stopped at a breakpoint, requests wait. A client with a short timeout will give up, and a health check that depends on the paused thread can fail, so a supervisor may restart the service while you are looking at it.
  • Async code. Stepping across an await is supported, but the call stack shows the event loop. Use the "Call stack" panel to follow coroutines.

Next step

If the thing you are chasing is a reload that does not happen, see uvicorn reload not working. For a failing import rather than a failing request, start with ModuleNotFoundError in a local service.

Questions people ask

Why does my VS Code breakpoint show as unbound?

Usually the path mapping is wrong, the debugger is attached to a different process or interpreter, or the code was never imported. For code in a container, set remoteRoot to the container path.

Can I debug with uvicorn --reload?

It is awkward, because the reloader serves requests from a child process that it replaces on each change. Turn reload off while debugging.

What is the difference between debugpy launch and attach?

Launch starts your program under the debugger. Attach connects to a program that is already running and listening, which suits services started by another tool.
