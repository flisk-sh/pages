How to run Django locally with Postgres in Docker

Django reloads fast on the host, and Postgres is easiest in a container. Splitting them this way is a common setup. Here is how to wire it so migrations run first and data survives restarts.

Run Django with python manage.py runserver on your machine, run Postgres from the official image in Docker, and point Django at it with a DATABASE_URL. Apply migrations as a separate step before the server starts. This keeps Django's reload and debugger working normally and keeps a real Postgres version instead of SQLite.

Why not SQLite in development

SQLite is fine for a first tutorial. It differs from Postgres in ways that matter later: stricter column types in Postgres, different locking, no JSONField lookups on some SQLite builds, and no way to test things like ArrayField or full text search. If production uses Postgres, development should too. A container is the cheapest way to get one without installing it system-wide.

Wire Django to Postgres

Install a driver and a URL parser:

python -m pip install "psycopg[binary]" dj-database-url

In settings.py, read the connection from the environment so no password lives in code:

import dj_database_url

DATABASES = {
    "default": dj_database_url.config(default="sqlite:///db.sqlite3"),
}

With DATABASE_URL=postgres://app:app@localhost:5432/app in the environment, Django talks to Postgres. Without it, it falls back to SQLite, which is a deliberate default so a fresh clone still runs. The username and password above are throwaway values for a database that only listens on your own machine. Do not reuse them anywhere real. More patterns are in DATABASE_URL and env vars locally.

Without Flisk

docker run --name pg -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app \
  -e POSTGRES_DB=app -p 127.0.0.1:5432:5432 \
  -v pgdata:/var/lib/postgresql/data -d postgres:17-alpine
export DATABASE_URL=postgres://app:app@localhost:5432/app
python manage.py migrate
python manage.py runserver

Binding the port to 127.0.0.1 keeps the database off your network. The named volume pgdata keeps the data when the container is removed. For Postgres 18 and later the mount point changes to /var/lib/postgresql, so check the image documentation when you move up. You have to remember the order every time, and wait for Postgres to accept connections before migrate, which is where the first-run errors come from. See running Postgres locally for the container details.

The Flisk way: three services in order

Flisk can run Django and the migration as local processes and Postgres as a container, started by one flisk up. It needs Docker running for the Postgres image, and nothing else in the project may be built from a Dockerfile. Each service has its own service.json. The database:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "postgres",
  "appType": "bring-your-own",
  "stack": "app",
  "image": "postgres:17-alpine",
  "port": 5432,
  "exposeViaProxy": false,
  "env": {
    "POSTGRES_USER": "app",
    "POSTGRES_PASSWORD": "app",
    "POSTGRES_DB": "app"
  },
  "healthCheck": { "command": ["pg_isready", "-U", "app"] },
  "volumes": [{ "source": "postgres", "target": "/var/lib/postgresql/data" }]
}

The migration, as a one-shot job that runs once and must exit with code 0:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "migrate",
  "appType": "migrator",
  "stack": "app",
  "command": "python manage.py migrate",
  "dependsOn": ["postgres"],
  "env": { "DATABASE_URL": "postgres://app:app@localhost:5432/app" }
}

And Django:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "backend",
  "stack": "app",
  "toolchain": "python@3.12",
  "command": "python manage.py runserver localhost:$PORT",
  "port": 8000,
  "healthCheckPath": "/health/",
  "dependsOn": ["migrate"],
  "env": { "DATABASE_URL": "postgres://app:app@localhost:5432/app" }
}

The three manifests passed flisk config verify when I tried them. A few details are worth knowing. The healthCheck.command runs inside the container and Flisk waits for it to exit 0, which matters because Docker accepts connections on the published port before Postgres is ready. A migrator is ready when it exits 0 and is never restarted, so Django starts only after the migrations succeed. Django needs a /health/ route for the health path, or you can leave healthCheckPath out and Flisk falls back to checking that the port accepts connections. The container is published on 127.0.0.1, and flisk down stops it but keeps the named volume.

flisk up --dry-run
flisk up

For one-off commands that need the same environment, use flisk run:

flisk run web -- python manage.py createsuperuser

It runs on the host, from the service folder, with the environment that service has. More on that in running a one-off command in a service.

Pitfalls

  • Docker must be running. The Postgres image needs it. If you want no Docker at all, use SQLite for development and accept the differences.
  • A leftover volume with an old password. Postgres reads the password only when it first initialises the volume. Changing it in the manifest later does nothing until you reset the data.
  • ALLOWED_HOSTS. With DEBUG = True, Django allows localhost and 127.0.0.1 by default. Behind another hostname you have to list it.
  • Not for production parity. This runs Django's development server. Test your real WSGI or ASGI server before you ship.

Questions people ask

Do I need Docker to run Django with Postgres locally?

You need Docker only for the Postgres container. You can install Postgres directly on your machine instead, or use SQLite in development.

Where should Django migrations run in local development?

As a separate step before the server starts, not inside the web process. In Flisk that is a migrator service that web depends on, so the server starts only after migrate exits successfully.

Why does Django ignore my new Postgres password?

Postgres sets the password when it first creates the data volume. A later change in the environment does not apply to an existing volume until you recreate it.
