uvicorn --reload not working: causes and fixes

When uvicorn stops picking up your edits, the cause is nearly always one of five things. Each is quick to check once you know what the reloader watches.

If uvicorn --reload ignores your edits, check these in order: the app is passed as an import string, you are editing a file the reloader watches, the file pattern matches, and, if you use Docker or WSL, file events actually reach the process. If it reloads endlessly instead, it is watching a folder that changes on its own, usually .venv or a log directory.

How the reloader decides

With --reload, uvicorn runs a supervisor process that watches files and restarts a worker process when something changes. By default it watches the current working directory. If the watchfiles package is installed (it comes with uvicorn[standard]), it uses that. Otherwise it falls back to polling file modification times. By default only *.py files count as changes. Knowing that default explains most surprises.

The checklist

1. Reload needs an import string

This works:

uvicorn main:app --reload

This does not, and uvicorn says so in the log:

uvicorn.run(app, reload=True)   # app object, not an import string

Use uvicorn.run("main:app", reload=True) when you start it from Python. The supervisor has to import your app again in a fresh process, so it needs a name to import.

2. You edited a file that is not watched

Changing an .html template, a .env file or a YAML config does not trigger a reload, because only Python files are included. Add patterns:

uvicorn main:app --reload --reload-include "*.html" --reload-include "*.yaml"

Environment variables are read when the process starts. Even if you reload, a changed .env is only picked up if your code loads it at startup.

3. The edited file is outside the watched directory

--reload-dir src limits watching to src. A helper package in a sibling folder will not trigger anything. Pass the option once for each folder:

uvicorn main:app --app-dir src --reload --reload-dir src --reload-dir ../shared

4. It reloads in a loop

A restart that triggers another restart means something under the watched path is being written constantly. The usual culprits are a .venv inside the project, a SQLite database file, or a log file. Narrow the watch with --reload-dir, or exclude the noisy pattern with --reload-exclude. Limiting the watch to your source folder is the most robust fix.

5. File events never arrive

Inside Docker on macOS or Windows, bind mounts do not always deliver the change notifications Linux programs rely on. The same happens for projects stored under /mnt/c in WSL 2. If saving does nothing and the paths above are right, this is likely it. Either run the service on the host, keep the project in the Linux file system, or switch to polling. The general causes are covered in hot reload not working.

What Flisk does here

Flisk does not add its own reloader to a Python service. For a service started as a local process, the reload is whatever you put in command:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "uvicorn main:app --app-dir src --reload --reload-dir src --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}

That is the same shape that flisk resource api --type backend --language python --local scaffolds: its command is a uvicorn line with --reload and --reload-dir src. Running on the host avoids the bind mount problem in step 5 entirely. For the container route, the generated Python image starts uvicorn with the same flags, and Flisk syncs your changed files into the running container and relies on uvicorn's reload to pick them up. If you watch the output with flisk logs --service api --tail 50, you should see the reload message after each save. If you do not, work through the checklist above.

Pitfalls

  • Reload in production. --reload is for development. It starts a supervisor, watches files and restarts workers. Leave it out of production commands.
  • Combining --reload with --workers. Reload is a single-process development mode, so run one process while you develop.
  • Import errors on reload. A syntax error stops the worker, and the supervisor waits for the next save. The log shows the traceback.

Next step

When reload works but you still cannot see why a request misbehaves, attach a debugger: debugging a Python service with debugpy. For Flask, which has its own reloader, see Flask auto-reload.

Questions people ask

Why does uvicorn --reload not detect changes to my templates?

By default only .py files are watched. Add --reload-include with a pattern such as *.html to include other file types.

Why does uvicorn reload again and again?

Something inside the watched directory changes on its own, often a .venv folder, a SQLite file or a log file. Limit watching with --reload-dir or use --reload-exclude.

Can I use --reload with multiple workers?

No. Reload is a development feature and is not compatible with --workers. Use a single process while developing.
