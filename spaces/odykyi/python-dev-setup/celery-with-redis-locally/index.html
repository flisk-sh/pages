How to run Celery with Redis for local development

A Celery setup has three moving parts: something that enqueues, a broker that holds the jobs, and a worker that runs them. Locally you can run all three with a couple of small files.

Start Redis, define a Celery app that uses it as broker and result backend, run a worker with celery -A tasks worker --loglevel=info, and enqueue work from your web service with .delay(). For tests, set task_always_eager so tasks run inline with no broker at all. Three processes are enough: the web app, the worker and Redis.

The pieces

The producer, for example a FastAPI endpoint, puts a message on a queue. The broker holds it. The worker pulls it and runs the function. Celery can also store the result in a backend so the producer can ask for it later. Redis can play both the broker and the backend roles, which is why it is the usual local choice. Redis itself is covered in running Redis for development.

The Celery app

Install the packages and write tasks.py:

python -m pip install celery redis
import os
from celery import Celery

REDIS_URL = os.environ.get("REDIS_URL", "redis://localhost:6379/0")

app = Celery("tasks", broker=REDIS_URL, backend=REDIS_URL)

@app.task(name="tasks.add")
def add(x, y):
    return x + y

The producer imports the task and sends it:

from tasks import add

result = add.delay(15, 30)        # returns immediately
print(result.id)
print(result.get(timeout=10))     # 45, waits for the worker

In a web endpoint, return the id with a 202 response and let clients poll a status route, instead of calling .get() inside the request. Waiting inside a request ties up a web worker for the length of the job.

Run the worker

docker run --name redis -p 127.0.0.1:6379:6379 -d redis:7-alpine
celery -A tasks worker --loglevel=info

On Windows, Celery's default pool does not work. Add --pool=solo (one task at a time) for local development. Celery 5 removed the old --autoreload option, so the worker does not restart when you edit a task. A common workaround is the watchfiles command line tool, which restarts a command when files change:

python -m pip install watchfiles
watchfiles "celery -A tasks worker --loglevel=info" .

Restart the worker whenever you change task code. A worker keeps the old version of a function in memory, and "my fix did nothing" is very often just an old worker still running.

The Flisk way

Flisk can run the worker and the web app as local processes with Redis in a container, in one command. This is the same shape as the repository's own recipe for FastAPI, Celery and Redis (docs/recipes/fastapi-celery-redis.md), which also has an end-to-end test. A shortened version of the manifests, each in its own folder with a service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "redis",
  "appType": "bring-your-own",
  "stack": "app",
  "image": "redis:7-alpine",
  "port": 6379,
  "exposeViaProxy": false
}
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "worker",
  "appType": "worker",
  "stack": "app",
  "command": "celery -A tasks worker --loglevel=info",
  "dependsOn": ["redis"],
  "env": { "REDIS_URL": "redis://localhost:6379/0" }
}
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "stack": "app",
  "command": "uvicorn main:app --reload --port $PORT",
  "port": 8000,
  "healthCheckPath": "/health",
  "dependsOn": ["redis"],
  "env": { "REDIS_URL": "redis://localhost:6379/0" }
}

Points to know:

  • Flisk starts Redis first with docker run, so Docker must be running. It publishes the port on 127.0.0.1.
  • Local processes reach the container at localhost, not by service name, because the containers share no Docker network with them.
  • A service with no port counts as ready once its process is still running after about a second, which is how the worker is treated. It is not a proof that Celery connected to Redis, so read its log.
  • If the worker crashes, Flisk restarts it after 1, 2, 4 and 8 seconds, and gives up after five quick exits. Look at it with flisk logs --service worker --tail 50.
  • Restart only the worker after changing a task, with flisk restart worker, instead of the whole stack.

Python buffers output when it is not writing to a terminal. If a worker looks silent, set PYTHONUNBUFFERED=1 in its env block. Celery's own log handler is usually unaffected, but your print calls are not.

Testing tasks

For unit tests, you rarely want a broker. Set eager mode and tasks run in the calling process:

app.conf.task_always_eager = True
app.conf.task_eager_propagates = True

The second line makes exceptions in a task raise in your test instead of being stored in the result. Use real Redis and a real worker only for the few tests that check wiring. See debugging a stuck job for what to check when a task never finishes.

Pitfalls

  • Different Redis databases. A producer on /0 and a worker on /1 never meet. Share one URL through the environment.
  • Task names. Autogenerated names include the module path, so importing a task as src.tasks in one place and tasks in another yields two names. Set name= explicitly.
  • Passing big objects. Pass IDs, not model instances or files.
  • Losing jobs on restart. Without persistence, Redis forgets queued jobs when the container is removed.

Questions people ask

Do I need Redis to try Celery locally?

You need some broker. Redis is the easiest to run in a container. For unit tests you can skip the broker with task_always_eager.

Why does my Celery worker not pick up code changes?

The worker keeps the imported code in memory. Restart it after editing a task, or run it under a file watcher such as the watchfiles command.

Does Flisk run Celery workers?

Flisk runs any command as a local process, so a Celery worker is a service with a command in service.json. Redis can run beside it as a container image.
