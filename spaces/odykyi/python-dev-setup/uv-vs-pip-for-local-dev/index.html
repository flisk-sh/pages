uv vs pip for a local Python project: which to use

pip is everywhere and does one job. uv replaces pip, venv and a few other tools with one program. Here is how to choose without a migration project.

Use pip when your project is a plain requirements.txt and nobody on the team has a reason to change. Use uv when you want a lock file, one command that creates the environment and installs into it, and the ability to install Python itself. Both install from PyPI, and a project can move from one to the other in minutes because both read pyproject.toml and requirements files.

What each tool does

pip installs packages into the environment you are running in. It does not create environments (that is venv), it does not manage Python versions, and it has no lock file of its own. That is a small, stable surface, and it ships with Python.

uv is a separate program from Astral. It covers more ground:

  • uv venv creates an environment, and uv pip install -r requirements.txt is a drop-in for the pip workflow.
  • uv add fastapi edits pyproject.toml and a uv.lock file, and uv sync makes the environment match the lock file.
  • uv run uvicorn main:app --reload makes sure the environment is in sync, then runs the command inside it, with no activation step.
  • uv python install 3.12 and uv python pin 3.12 fetch an interpreter and write a .python-version file.

uv is usually noticeably quicker on installs, mostly because it caches and resolves aggressively. I am not going to put a number on it, because it depends on your packages and your network. Time your own project if the difference matters to you.

A side-by-side workflow

The same task, adding a dependency and running tests, in both tools:

# pip
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install httpx
python -m pip freeze > requirements.txt
python -m pytest

# uv
uv add httpx
uv run pytest

The uv version is shorter because it handles the environment for you. The pip version has more steps, and each one is something you can see and debug with ordinary tools.

How to choose

SituationLean toward
Tiny script or one service, requirements.txt already workspip
You want reproducible installs across a teamuv, for the lock file
People on the team have different Python versionsuv, or pyenv or mise with either
CI image is minimal and you cannot add toolspip
A Dockerfile that must work on any base imagepip, unless you copy uv into the image

Poetry and PDM are also good, and have their own lock files. If your team already uses one of them, the case for switching to uv is weaker than the case for finishing what you started.

Running either under Flisk

Flisk does not care which installer you use, because it only runs the command in your service.json. With pip, activate the environment before flisk up, or name the interpreter in the command. With uv, let uv do it:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "uv run uvicorn main:app --reload --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}

Flisk checks before it starts that the program in the command is installed, so uv must be on your PATH. One thing to watch: the optional toolchain field is compared with the python3 or python found on your PATH, not with the interpreter uv picks for the project. If uv manages the interpreter, leave toolchain out and pin the version with uv python pin instead.

The container route is different. A service scaffolded with flisk resource api --type backend --language python gets a pyproject.toml, and its generated Dockerfile builds wheels from that file with pip. It does not use uv, and you should not expect it to read a uv.lock.

Pitfalls

  • Mixing tools in one environment. Installing with uv pip and then pip works, but two lock sources drift. Choose one source of truth.
  • Forgetting to commit uv.lock. The lock file only helps if everyone shares it.
  • Assuming uv replaces your deploy process. Production images still need an install step, and you need to decide how it will read your lock file.

Next step

Questions people ask

Is uv a replacement for pip?

For most local workflows, yes: uv pip install works like pip, and uv add, uv sync and uv run cover environments and locking. pip remains the default that ships with Python.

Does uv work with requirements.txt?

Yes. uv pip install -r requirements.txt installs from it, and a project can keep using requirements files while you try uv.

Does Flisk require a particular Python package manager?

No. Flisk runs the command in service.json as a local process, so any installer works as long as the program in the command is on your PATH.
