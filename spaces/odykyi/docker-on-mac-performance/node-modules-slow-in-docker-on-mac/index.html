Docker on Mac: speed and resources

Why node_modules is slow in Docker on Mac and the fix

A dependency folder can hold tens of thousands of files. Sharing it between macOS and a Linux VM is the most common reason for a slow Node container on a Mac.

Do not share node_modules between your Mac and a container. Install dependencies inside the image, or keep them in a named volume, and mount only your source code. The folder holds tens of thousands of small files, each of which crosses the macOS to VM boundary on a bind mount, and it contains binaries that only work on one operating system.

The two problems with a shared node_modules

Speed. An install writes many small files, and a bind mount makes each write slow. The reasons are in why bind mounts are slow on Mac.

Wrong binaries. Packages with native code (image libraries, password hashing, database drivers) install a binary for the current operating system. An install on macOS puts darwin binaries in node_modules. Mounted into a Linux container, they fail with errors such as "invalid ELF header" or "exec format error", and the reverse also happens. Even an install inside the container on a shared mount leaves Linux binaries in the folder your Mac editor and tools see.

Fix 1: install in the image

The simplest pattern is to copy only the manifest files first, install, and copy the source afterwards. The dependencies then live in an image layer on the VM's own disk and are cached until a manifest changes:

FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["npm", "run", "dev"]

Add a .dockerignore file with node_modules so the host copy never enters the build. In development you then mount only the source, as in the next fix.

Fix 2: a named volume over node_modules

If you must bind mount the project root for live editing, put an anonymous or named volume on top of node_modules. The volume hides the host folder inside the container:

services:
  web:
    build: .
    volumes:
      - ./:/app
      - web_node_modules:/app/node_modules
volumes:
  web_node_modules:

The catch is staleness. A named volume is populated from the image the first time it is created and is not refreshed when you rebuild with new dependencies. After you change package.json, remove the old volume so it is filled again:

docker compose down
docker volume rm <project>_web_node_modules
docker compose up --build

Check the exact volume name with docker volume ls, and take care with docker compose down -v, which removes every volume of the project, including a database.

Fix 3: mount only the source

Better than hiding a folder is never mounting it. Mount ./src and your config files, and leave the project root alone. Nothing outside those paths crosses the boundary, and node_modules stays in the image.

How Flisk handles it

For a service Flisk builds, dependencies are installed in the image by a dependency layer that copies only the manifest files, package.json and the package manager configuration, and runs the install. Changing only application code leaves that layer cached, and Flisk's own documentation describes the install layer being reused when you edit src/index.ts. A change to package.json re-runs the install, and a lockfile change alone does not, by design. To force a reinstall after changing only the lockfile, the docs describe a CACHE_BUSTER build argument. Source changes then reach the running container through live_update, which copies the folders in syncs: src and prisma for a backend, src and public for a frontend. That is the pattern of Fix 1 and Fix 3, set up for you.

flisk resource orders-api --type backend --stack shop
flisk logs --service orders-api --tail 30

If a dependency does not build for Linux on arm64, you see the error in the image build, not at run time. The install log shows which package failed, for example a prebuilt binary download that returns a 404 for linux arm64.

Pitfalls

  • Editor tooling. If node_modules exists only in the container, your editor on the Mac has no types or autocomplete. Install on the host as well, for the editor only, and keep that folder out of the build with .dockerignore.
  • Different lockfiles. Use npm ci in the image so it installs exactly what the lockfile says.
  • Monorepos. Hoisted dependencies live at the repository root. Mount the services' source, not the root.
  • A slow install in the image. That is a build cache problem, covered in why Docker builds are slow on Mac.

Related checks for reload problems after the move are in hot reload not working. If a Node service still feels slow, ask whether it needs a container at all: run natively or in Docker on a Mac.

Questions people ask

Should node_modules be in a Docker volume?

Either install it inside the image or keep it in a named volume. Do not share the macOS copy with the container, because it is slow and holds binaries for the wrong operating system.

Why does my named volume keep old packages?

A named volume is filled from the image only when it is first created. After a dependency change, remove the volume with docker volume rm and start again.

Why do I get invalid ELF header from a package?

The package has a native binary built for macOS and the container is Linux. Install the dependencies inside the image instead of mounting the host node_modules.
