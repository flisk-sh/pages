Docker on Mac: speed and resources

Why Docker bind mounts are slow on Mac and how to speed them up

A project that runs in a second on Linux can crawl on a Mac. The cause is the file sharing layer, and you can usually avoid most of its cost.

Bind mounts are slow on a Mac because Docker does not run natively on macOS. Containers live in a Linux VM, and every file you share from your Mac folder has to cross from macOS into that VM. Large numbers of small reads, such as node_modules or a PHP vendor folder, pay that cost again and again. The fix is to use the fastest file sharing mode, and to keep heavy folders out of the shared path.

What is actually slow

Reading one big file through a bind mount is fine. The slow case is thousands of tiny file operations: a dependency install, a test run that scans a tree, a framework that stats every file on each request. Each operation is a round trip between two operating systems. On Linux the same mount is just a directory, so none of this exists there.

A quick way to see it is to time the same command inside and outside the mount:

docker run --rm -v "$PWD":/app -w /app alpine sh -c 'time find . -type f | wc -l'
docker run --rm -v "$PWD":/app -w /app alpine sh -c 'cp -r /app /tmp/copy && cd /tmp/copy && time find . -type f | wc -l'

The second command runs on the container's own filesystem, so the difference between the two timings is the mount overhead for your project. Do not trust a general benchmark from the internet, because it depends on your tree and your Docker version.

Use the fastest file sharing mode

Docker Desktop has had several file sharing implementations over the years (osxfs, gRPC FUSE and VirtioFS). In recent versions VirtioFS is the default for new installs and is the quickest. Check Settings, then General, then the file sharing implementation, and pick VirtioFS if it is not already selected. The old :cached and :delegated flags on a volume line are accepted but have no real effect with current implementations, so you can drop them from Compose files.

With Colima the choice is made when the VM is created:

colima start --vm-type vz --mount-type virtiofs

This needs a recent macOS. If the instance already exists with another type, stop it and delete it first, because the mount type is fixed at creation. Deleting a Colima instance removes its images and volumes, so dump any database you care about first. More about Colima settings is in the Colima settings article.

Keep heavy folders off the mount

Even with VirtioFS, a bind mount is slower than the container's own disk. Three habits help more than any setting:

  • Mount only source code. Mount ./src, not the whole project root with dependencies, build output and .git.
  • Put dependencies in a named volume. A named volume lives inside the VM, so it is not crossing the boundary. See node_modules slow in Docker on Mac.
  • Write build output and caches to a volume or tmpfs. Compilers and bundlers write many files. Send them to a place that is not shared with the host.
services:
  web:
    build: .
    volumes:
      - ./src:/app/src
      - web_modules:/app/node_modules
      - web_cache:/app/.cache
volumes:
  web_modules:
  web_cache:

The Flisk way: sync instead of mount

For services that Flisk builds from its own Dockerfile, it does not bind mount your source folder at all. It builds an image and uses Tilt live_update to copy changed files into the running container. The folders that are copied come from the syncs field in service.json. They default to src and prisma for a backend and src and public for a frontend, so dependencies are never part of the sync.

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "stack": "shop",
  "syncs": ["src", "prisma"]
}

The restart after a copy is done by the language's own mechanism, as covered in hot reload not working. If a Docker file mount is the part you cannot get working at all, run flisk doctor. It has a Docker File Sharing check that starts a small container with a bind mount of your project folder. If the mount fails, the message tells you what to share: Docker Desktop's file sharing list, or colima start --mount <folder> for Colima.

Pitfalls

  • Projects outside your home folder. Docker only shares folders it has been told about. Temporary folders under /private/tmp are a common failure with Colima. Keep projects under your home directory.
  • Symlinks that point outside the mount do not resolve inside the container.
  • File watchers. Some watchers need polling over a mount, which costs CPU. See Docker high CPU on Mac.
  • Case sensitivity. macOS folders are usually case insensitive and the container's filesystem is not. A wrongly cased import works on your Mac and fails in the container.

If the mount is still too slow after these changes, the remaining option is to avoid containers for that service. Running it as a plain process removes the boundary entirely, and the last article of this set shows how to decide which services should be native.

Questions people ask

Is VirtioFS faster than gRPC FUSE?

In current Docker Desktop versions VirtioFS is the default and generally the fastest of the options. Time your own project before and after, because results depend on the file layout.

Do :cached and :delegated still help?

Not with current file sharing implementations. Docker accepts the flags for compatibility, but you can remove them without losing speed.

Why is npm install slow in a mounted folder?

An install writes many thousands of small files, and each one crosses the Mac to VM boundary. Keep node_modules in a named volume or inside the image.
