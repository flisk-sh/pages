Fix "exec format error" in Docker on Apple Silicon

The container starts and dies at once with a message that says nothing useful. It is almost always an architecture mismatch.

exec format error means the container tried to run a binary built for a different CPU architecture. On an Apple Silicon Mac the host is arm64, so an image built for amd64 (Intel) can fail to run, and an arm64 image fails on an Intel server. Check which architecture the image has, then rebuild it for the right one or ask Docker for the matching platform.

Confirm the mismatch

Three commands show the facts. First, your host and the Docker engine:

uname -m
docker info --format '{{.Architecture}}'

On Apple Silicon both usually print arm64 or aarch64. Then look at the image:

docker image inspect --format '{{.Os}}/{{.Architecture}}' myimage:latest

If it prints linux/amd64 on an arm64 engine, that is your mismatch. Docker often warns about this when you pull or run: "The requested image's platform (linux/amd64) does not match the detected host platform (linux/arm64/v8)". When it does not warn, the failure is the bare exec format error in the container log. You can also look at a registry image without pulling it:

docker buildx imagetools inspect nginx:stable

That lists every platform the tag supports. If linux/arm64 is there, Docker picks it automatically. If it is missing, the publisher never built it.

Four causes, four fixes

CauseFix
You pulled or built an amd64 image earlier and it is cached under the same tagRemove it and pull again: docker rmi myimage:latest then docker pull --platform linux/arm64 myimage:latest
The Dockerfile has FROM --platform=linux/amd64 or a Compose file has platform: linux/amd64Remove the pin, or keep it on purpose and accept emulation (see the next article)
The image is published only for amd64Run it under emulation with --platform linux/amd64, or find or build an arm64 version
A script inside the image has a wrong shebang or Windows line endings (CRLF)Fix the first line of the script and convert line endings to LF. The error text can look the same.

The last row surprises people. A shell script saved with CRLF endings fails with exec format error or no such file or directory on any architecture, so check it if the platform is already correct. file entrypoint.sh reports CRLF line terminators when they are there.

Binaries copied into the image

A second common source is a binary built on the host and copied in. A Go or Rust program compiled on your Mac with a plain go build is a macOS binary, and it cannot run in a Linux container at all. Build for the target:

GOOS=linux GOARCH=arm64 go build -o app .
docker build --platform linux/arm64 -t myapp .

The cleaner approach is to compile inside a multi stage build, so the build runs on the same architecture as the final image. Native modules in Node projects have the same trap: a node_modules folder installed on macOS contains macOS binaries. Install inside the image, not on the host, and keep the host folder out of the build with a .dockerignore entry.

Build for more than one platform

If the image has to run on both your Mac and an amd64 server, build both architectures into one tag:

docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/myapp:1.0 --push .

Multi platform builds need a builder that can emit more than one platform and a registry to push to, because the local image store holds one platform at a time in many setups. Running the foreign architecture has a speed cost, which slow amd64 images on Apple Silicon covers.

Pitfalls

  • A global default. DOCKER_DEFAULT_PLATFORM=linux/amd64 in your shell profile silently makes every pull and build amd64. Unset it unless you want it.
  • Tags move. The latest tag may gain arm64 support later, but your local copy stays as it was until you pull again.
  • A fix that hides the real problem. Forcing amd64 makes the error go away and the service slow. Prefer a native arm64 image when one exists.

If the container starts but then exits for another reason, go to why a container keeps restarting. If you must keep an amd64 image, the next question is how to make it tolerable, and the Rosetta settings in the Colima settings article answer that.

Questions people ask

What does exec format error mean in Docker?

The kernel could not run the file as a program for this CPU. Usually the image or a binary inside it was built for another architecture, such as amd64 on an arm64 Mac.

How do I check an image's architecture?

Run docker image inspect --format '{{.Os}}/{{.Architecture}}' <image> for a local image, or docker buildx imagetools inspect <image> for a registry image.

Can a script cause exec format error?

Yes. A script with CRLF line endings or a wrong shebang line can fail in the same way, even when the architecture is correct.
