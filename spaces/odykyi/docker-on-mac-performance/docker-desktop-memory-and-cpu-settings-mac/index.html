Docker on Mac: speed and resources

How much memory and CPU to give Docker on a Mac

Too little and containers get killed with no clear error. Too much and your editor and browser swap. Here is how to pick numbers from measurements.

Give the Docker VM enough memory for the containers you run at the same time, plus a margin, and leave the rest of the machine to macOS. There is no universal number. Measure your own stack with docker stats, add 25 to 30 percent headroom, and set that in the Docker settings. Then limit single containers so one runaway service cannot take the whole budget.

Where the limits live

On a Mac, Docker runs containers in one Linux VM. The VM has a CPU count, a memory size and a disk size. Every container shares that budget. In Docker Desktop these are under Settings, then Resources. In Colima you set them when you start the VM:

colima start --cpu 4 --memory 8 --disk 60

Changing them needs a restart of the VM, which stops your containers. OrbStack and Podman have their own settings, with the same idea.

How to measure instead of guess

Start the services you really use together, let them settle for a few minutes, and read the numbers:

docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}"

Add up the memory column. That is your working set. A JVM service, a database under load or a machine learning model can use many times more than a small Node API, so do not borrow a figure from someone else's project. Peaks matter too. A build or a test run can double memory for a minute, so measure while you do the heavy thing, not just at idle.

A practical sizing rule:

  1. Sum the container memory at peak.
  2. Add 25 to 30 percent for the Docker VM's own cache and for spikes.
  3. Check that the machine still has room: your editor, browser and other tools need memory outside the VM.
  4. For CPUs, give the VM about half of your cores if you do other work at the same time. More CPUs do not speed up a container that is single threaded.

Recognise a memory kill

When a container exceeds its limit or the VM runs out of memory, the kernel kills a process and Docker shows exit code 137. There is often no error in the application log, because it was killed from outside. Check:

docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' <container>

true 137 means it was killed for memory. The fix is a bigger VM, a bigger per container limit, or a smaller service. This is also one cause of containers that keep restarting; why a container keeps restarting covers the others.

Per container limits in Flisk

Flisk applies limits for you, and they differ by kind of resource. According to its bring-your-own documentation, a container that Flisk builds from its own Dockerfile is limited to 0.5 CPU and 512M of memory, while a bring-your-own container has no limit unless you set one. In the generated Compose file, a Next.js frontend gets a 1G and 1.0 CPU limit, and other frontends get 64M and 0.15 CPU. If a service you scaffolded dies under load, check these first.

For a bring-your-own container, set container.cpus and container.memory in its service.json:

{
  "schemaVersion": 1,
  "appName": "search",
  "appType": "bring-your-own",
  "stack": "shop",
  "image": "getmeili/meilisearch:v1",
  "port": 7700,
  "container": {
    "cpus": 2,
    "memory": "1g"
  }
}

These values replace Flisk's limits and become deploy.resources.limits in the generated Compose file. A reservation never exceeds the limit. Limits only help if the VM is big enough to hold the sum of them, so add them up the same way as above.

Flisk also has a Container Resource Health check in flisk doctor. It samples the project's running containers and flags a container that uses 90 percent or more of its memory limit while also using 80 percent or more of a CPU. That pattern usually means a boot loop, such as something downloading a package on every start, not honest work.

Pitfalls

  • Limits above the VM size. A container limit of 4g in a VM with 3 GB does nothing useful. The VM runs out first.
  • Swap hides the problem. Swap inside the VM keeps things alive and slow. Treat heavy swapping as a sign to raise memory.
  • Memory that macOS shows. Activity Monitor shows the VM as one large process. The figure is the VM, not each container. See why Docker uses so much memory.
  • Running more than you need. Starting fewer services is the cheapest saving. flisk up --only api starts a service and what it depends on, and start only the services you need explains how.

Once the numbers are right, write them down in the repo's README so the next developer does not guess. Then look at what else the VM is spending: the next article to read is about high CPU when nothing is running.

Questions people ask

What does exit code 137 mean in Docker?

The process was killed with SIGKILL. On a Mac it is most often the out of memory killer, either from a container limit or because the Docker VM ran out of memory. docker inspect shows OOMKilled.

How much memory should I give Docker Desktop?

Measure the memory of the containers you run together with docker stats at peak, then add 25 to 30 percent. Leave enough for macOS, your editor and your browser.

Does Flisk set container memory limits?

For containers it builds from its own Dockerfile it applies a default limit, and for bring-your-own containers you set container.cpus and container.memory in service.json.
