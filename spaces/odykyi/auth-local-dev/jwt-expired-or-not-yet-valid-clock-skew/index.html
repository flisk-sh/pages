Authentication in local development

JWT expired or not yet valid in local dev: check clock skew

The token was issued a second ago and the verifier calls it expired. The signature is fine; the clocks are not.

If a token you just issued is rejected as "expired", "not active" or "issued in the future", compare the clocks of the issuer and the verifier. A container or virtual machine whose clock fell behind, usually after your laptop slept, is the most common cause in local development. Fix the clock first, and add a small tolerance second.

What the checks compare

A JWT carries timestamps in seconds since 1970 (not milliseconds): iat is when it was issued, nbf is the earliest time it is valid, and exp is when it expires. The verifier compares them with its own clock. If the issuer's clock is ahead of the verifier's, a new token looks like it comes from the future. If the verifier's clock is ahead, a token looks expired early. The error names differ by library:

jsonwebtoken (Node)jwt expiredjwt not active
jose (Node)"exp" claim timestamp check failed"nbf" claim timestamp check failed
PyJWTExpiredSignatureErrorImmatureSignatureError
golang-jwttoken is expiredtoken is not valid yet

Measure the gap

Decode your token's payload (a JWT is three base64url parts separated by dots, and the middle one is JSON) and read iat and exp. Then ask each machine for the time:

# on the host
date -u +%s

# inside a container
docker run --rm alpine date -u +%s

# the payload of a token in $TOKEN (needs jq)
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null | jq '{iat, nbf, exp}'

The middle part is base64url without padding, so base64 -d can fail on some tokens; if it does, paste the token into your language's JWT debugger or decode it with a short script. If the container's time differs from the host's by more than a few seconds, you found it.

Why a virtual machine drifts

On macOS and Windows, containers run inside a Linux VM that keeps its own clock. When the laptop sleeps or hibernates, the VM's clock can stop and resume late, and until it resyncs every container is minutes or hours behind. This is a known behaviour of Docker Desktop, Colima and WSL2. The remedies:

  • Restart the VM. Restarting Docker Desktop, or colima restart, resets the clock. The Colima setup article covers the VM itself.
  • WSL2. Run sudo hwclock -s inside the distro to resync it from the Windows clock, or wsl --shutdown and start again.
  • Linux. Containers share the host kernel clock, so drift between host and container cannot happen. Look at the issuer's code instead.

Add a small tolerance anyway

Production systems allow a few seconds of skew between machines. Do the same in verification:

// jsonwebtoken (seconds)
jwt.verify(token, secret, { algorithms: ["HS256"], clockTolerance: 5 });

// jose
await jwtVerify(token, key, { clockTolerance: "5s" });

# PyJWT
jwt.decode(token, key, algorithms=["HS256"], leeway=5)

Keep the tolerance to seconds. A tolerance of an hour hides a real problem and makes a short-lived token pointless. Never solve a drift problem by issuing tokens with a one-year exp.

Bugs that look like drift

  • Milliseconds instead of seconds. Date.now() returns milliseconds. An exp of Date.now() + 3600 expires in 3.6 seconds, and Date.now() / 1000 is not an integer. Use Math.floor(Date.now() / 1000).
  • Time zones. Epoch seconds have no time zone. If you build exp from a local date string, you have introduced one. Build it from the epoch.
  • A very short lifetime in tests. A 30 second exp plus a debugger breakpoint gives you an expired token. Raise it in development.
  • Cached tokens. A test that reuses a token saved in a fixture will expire on the day the fixture ages out. Mint tokens inside the test.

Where Flisk fits

Flisk runs your services but does not manage their clocks. It does give you one command to compare them: flisk run <service> -- date -u +%s runs the command with that service's environment, inside its container when the service is a container, or on the host when it is a local process. Compare the output between the issuer and the verifier. In a Docker stack, if the container's time is far from the host's, restart the VM as above, then flisk down and flisk up. A local-process stack uses the host clock, so all of its services agree by construction. If the clocks agree and verification still fails, the cause is the secret, not the time. Questions people ask

Why is my JWT expired the moment I create it?

The verifier's clock is ahead of the issuer's, or exp was built in milliseconds instead of seconds. Compare both clocks and the exp value.

How much clock tolerance should I allow?

A few seconds, for example 5. A larger value hides real problems and weakens short-lived tokens.

Can Docker containers have a different time than my Mac?

Yes. Containers use the clock of the Linux VM, which can fall behind after the laptop sleeps. Restarting the VM resyncs it.
