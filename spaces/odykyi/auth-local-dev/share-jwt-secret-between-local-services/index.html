Authentication in local development

How to share a JWT secret between local services safely

A token signed by the auth service must verify in every other service. The easy way to break that is two different secrets.

Generate one random secret for the project, store it outside git, and inject the same value into every service that signs or verifies tokens as an environment variable. Pin the algorithm in the verify call. If a token says "invalid signature" in only one service, that service has a different secret.

Symmetric or asymmetric

With HS256 the same secret signs and verifies, so every service that can verify a token can also forge one. That is acceptable on a laptop and in a small system. When more services or other teams verify tokens, prefer RS256 or ES256: only the auth service holds the private key, and the others fetch the public key from a JWKS URL. The rest of this article is about the shared-secret case, because that is where local setups go wrong.

  • Use at least 32 random bytes for HS256. A short word such as secret or changeme makes tokens easy to guess offline.
  • Pass the allowed algorithms to the verifier, for example jwt.verify(token, secret, { algorithms: ["HS256"] }) in jsonwebtoken. Never accept whatever algorithm the token header names.
  • Set exp and check it. See the clock skew article for what goes wrong when machines disagree on the time.

Generate and store it once

openssl rand -hex 32

That prints 64 hex characters. Put the value in an ignored .env file, add a placeholder to .env.example, and read it in code in one place:

const secret = process.env.JWT_SECRET;
if (!secret || secret.length < 32) {
  throw new Error("JWT_SECRET is missing or shorter than 32 characters");
}

Fail at startup. A service that silently falls back to a default secret verifies nothing useful, and a hard-coded fallback ends up in every checkout. The articles on generating random local secrets and gitignoring env files cover the surrounding habits.

The Flisk way: Docker and Tilt

In a Docker stack, a scaffolded backend defaults to AUTH_MODE=local-jwt. Flisk keeps one JWT_SECRET in the project .env, generated per project (64 hex characters) and never shared between projects. flisk up adds it to an older .env that lacks one, and never changes a value already there. Compose injects the same value into every service of the stack, so a token signed by one backend verifies in the others without any extra work. If the key is missing, Compose stops with a message that says so.

Two rules from Flisk's own docs:

  • A jwtSecret field in service.json is ignored, and flisk doctor warns about it. A secret must not be committed, so set JWT_SECRET in .env.
  • A service that depends on an identity resource, or sets "authMode": "identity-service", runs in identity-service mode instead: it gets IDENTITY_RESOURCE_URL and no JWT_SECRET. Set identityServiceUrl to the real address, because the default guess is http://identity-service:3000.

For a run with different settings, flisk up --env-file .env.integration replaces the project .env for that run, and the file must still contain TILT_ENV, DB_PASSWORD and JWT_SECRET.

The Flisk way: local processes

For services that run through a command, declare the key under secrets.generate. On flisk up, each name missing from the project .env is appended once with random bytes, and never changed afterwards, so the value is stable across restarts. Then map it into each service with ${NAME}:

{
  "schemaVersion": 1,
  "appName": "auth",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "secrets": { "generate": { "SHARED_JWT_KEY": "hex:32" } },
  "env": { "JWT_SECRET": "${SHARED_JWT_KEY}" }
}

Every other service that verifies tokens repeats the env line, with the same ${SHARED_JWT_KEY}, and has no generate block of its own; the first service creates the value, and all of them read it from the project .env. Use a generated name that differs from the variable the code reads: flisk config verify rejects a manifest whose env sets a variable that secrets.generate also creates, because the fixed value would replace the generated one. Flisk prints the names it generated, never the values, and keeps .env out of git. Back that file up if tokens must outlive a deleted checkout; a deleted .env gets a new key.

Pitfalls

  • Different secrets in different shells. For a local-process ${NAME}, your shell is checked first and the project .env second, so an old exported variable can hide the file. When verification fails in one service, print a short hash of the secret in each service at startup and compare the hashes. Never print the secret.
  • Whitespace. A trailing newline copied into .env changes the secret. Check for it first when two services "have the same secret" but disagree.
  • Rotating. Changing the secret invalidates every token. In development that is fine; clear the cookie or log in again.
  • Encoding. Some libraries treat the secret as a string, others as base64. Use the same library on both sides, or confirm how each decodes it.
  • Do not reuse a production secret. A local secret should be worthless anywhere else.

Once tokens verify everywhere, the next failure is time: a token that is already expired the moment it is issued. That is the next article.

Questions people ask

How long should a local JWT secret be?

At least 32 random bytes for HS256, for example 64 hex characters from openssl rand -hex 32.

Can every service use a different JWT secret?

Only the service that verifies a token needs the secret that signed it. If several services verify the same token, they need the same secret or the public key.

Should I put the JWT secret in service.json?

No. Flisk ignores a jwtSecret field and warns about it. Keep the value in the ignored .env file.
