Authentication in local development

How to set up a GitHub OAuth app for local development

One OAuth app has one callback URL. The clean answer for local work is a second app that only ever points at your machine.

Create a second GitHub OAuth app that exists only for development. Set its homepage URL and callback URL to your local address, copy the client ID into your config, and keep the client secret in a gitignored .env file. Do not reuse the production app: an OAuth app accepts one callback URL, so sharing it means changing the setting every time you switch.

Create the app

  1. On GitHub open Settings, Developer settings, OAuth Apps, then New OAuth App. For an organisation, use the organisation's settings so the app does not belong to one person's account.
  2. Name it so nobody mistakes it for the real one, for example myapp (local dev).
  3. Homepage URL: http://localhost:3000. It is informational, but fill it in.
  4. Authorization callback URL: the exact path your library handles, for example http://localhost:3000/api/auth/callback/github for Auth.js.
  5. Register the application, then use Generate a new client secret. GitHub shows the secret once. Copy it straight into your local env file.

GitHub's rule is that the host and port of the redirect_uri your app sends must match the registered callback URL, and its path must be inside the registered path. Port 3000 registered and port 5173 sent fails. If it does, the article on redirect_uri_mismatch on localhost shows how to compare the two.

Keep the credentials out of git

The client ID is not secret and can sit in an example file. The client secret is. Put it in .env, make sure .env is ignored (see gitignoring env files safely), and commit a .env.example with placeholders:

# .env.example
GITHUB_CLIENT_ID=your-dev-app-client-id
GITHUB_CLIENT_SECRET=paste-it-here

If you ever paste the secret into a commit by accident, treat it as leaked: generate a new one in the app settings and delete the old one. The checklist for a committed secret applies here too.

Ask for the scopes you need

By default an OAuth app reads public profile information. To get the user's primary email address, which many apps use as the account key, request the user:email scope. A user can also hide their email, so handle a missing address instead of assuming one. Request read:user only when you need the full profile. Fewer scopes mean fewer consent screens while you test.

Exchange the code on the server

The flow is the plain authorization code flow. Your app sends the browser to https://github.com/login/oauth/authorize with client_id, redirect_uri, scope and a random state. GitHub redirects back with code and the same state. Your server checks the state, then posts the code and the client secret to https://github.com/login/oauth/access_token and gets a token. The secret must only ever be used on the server. Never read it from a variable that a frontend bundler would inline, such as one starting with VITE_ or NEXT_PUBLIC_.

Wire it into a Flisk project

With services that run as local processes, the env map in service.json can read values from the project .env or your shell with ${NAME}, so the manifest holds names and the secret stays in the ignored file:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 3000,
  "env": {
    "GITHUB_CLIENT_ID": "${GITHUB_CLIENT_ID}",
    "GITHUB_CLIENT_SECRET": "${GITHUB_CLIENT_SECRET}",
    "APP_BASE_URL": "http://localhost:3000"
  }
}

Run flisk config verify to check the manifest. If a variable is not set in .env or the shell, flisk up warns that an unset variable expanded to an empty value, which is the first thing to look at when the GitHub page says the client is invalid. In a Docker stack, list the names under secrets instead; Flisk injects them from the project .env, and Docker Compose refuses to start a service whose required secret is missing. See DATABASE_URL and env vars in local development for the three kinds of variable.

Pitfalls

  • Changing the callback to test something. Do not edit the production app's callback. A second app removes the temptation.
  • Teammates. Each developer can share one dev app, since every developer's callback is localhost:3000, or create their own. Share the client ID freely; share the secret through your normal secret channel, not chat history.
  • A different local port. If your team uses several ports, pin each service's port so the callback never changes.
  • Using a GitHub App instead. GitHub Apps are a different product from OAuth apps and let you list more than one callback URL. They also use different settings, so pick one model and follow its documentation.

The same dev-app idea carries to Google, with more settings to get right. That is the next article.

Questions people ask

Can one GitHub OAuth app serve localhost and production?

An OAuth app has one callback URL, so you would have to edit it each time. A separate development app is simpler and safer.

Is the GitHub client ID a secret?

No, it appears in the authorize URL. The client secret is private and belongs in an ignored env file.

Why does GitHub return a bad_verification_code error?

A code can be used once and expires quickly. Retrying the same callback URL or reusing an old code produces it; start the login again.
