Authentication in local development

Why two apps on localhost log each other out (shared cookies)

You log in to one project, open another on a different port, and the first one forgets you. Nothing is wrong with either app.

Browsers scope cookies by host, not by port. http://localhost:3000 and http://localhost:4000 read and write the same cookies, so two apps that both name their session cookie session overwrite each other. Give every app a unique cookie name, or serve each app from its own host name.

What is happening

The cookie standard (RFC 6265) defines a cookie's scope by domain and path. It says nothing about ports, and browsers follow that. App A on port 3000 sets session=abc. App B on port 4000 sets session=xyz for the same host, which replaces it. A moment later app A sends xyz, fails to find that session in its store, and shows the login page. You did nothing wrong, and no log line explains it.

Typical triggers are older projects that are still running in another terminal, a second checkout of the same repo on another port, or a tutorial app and your real app that both use a framework default such as connect.sid, session or next-auth.session-token.

Confirm it in five minutes

  1. Open devtools, Application tab (Storage in Firefox), Cookies, and pick the localhost entry.
  2. Log in to app A and note the cookie names, values and expiry.
  3. Open app B on another port and log in. Look at the same list.
  4. If a cookie with the same name changed its value or expiry, you have a collision. If two apps show the same name on one row, that is the proof.

Also look at the number and size of cookies. Every cookie for the host travels with every request to every port. A stack of old session cookies can push the header past the server's limit, and you get "400 Request Header Or Cookie Too Large". Clearing the cookies for localhost fixes that for the moment, but only unique names stop it from returning.

Fixes, from simplest

  • Unique cookie name per app. Most session libraries take a name option: name in express-session, SESSION_COOKIE_NAME in Flask, SESSION_COOKIE_NAME in Django. Use the project name, for example shop_session. Read it from an environment variable so a second copy of the same app can set another one.
  • Different host names. localhost and 127.0.0.1 are different hosts, so they have separate jars. Any name that ends in .localhost works in current Chrome, Firefox and curl without a hosts file, and app.shop.localhost and app.crm.localhost do not share cookies.
  • One origin per project behind a proxy, as described in path prefix or subdomain routing. Each project has its own host name, so projects stay separate, and inside one project the app and API can share a first-party cookie.

Avoid the idea that a Path or the __Host- prefix fixes this. Path only narrows by URL path, and apps usually live at /. The __Host- prefix requires Secure, Path=/ and no Domain, and it still ignores the port.

A related surprise: same-site is not same-origin

Because ports do not count for site matching, a request from localhost:3000 to localhost:4000 is cross-origin but same-site. A SameSite=Lax cookie does travel on it. You still need credentials: "include" on the fetch and a CORS response with the exact origin and Access-Control-Allow-Credentials: true; the CORS article linked from the subdomain CORS fix covers it. The reverse also bites: a cookie your API sets for localhost reaches every other app on localhost, including one you would rather it did not.

Where Flisk fits

Flisk does not manage cookies, but its two run modes change which problem you have.

  • Local processes. Every service answers on http://localhost:<port>, so every service shares one cookie jar, and so does anything else running on your machine. Set a distinct name per service in env and read it in code:
{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "env": { "SESSION_COOKIE_NAME": "shop_session" }
}
  • Docker and Tilt. Frontends are on app.<project>.localhost and backends on api.<project>.localhost, so two Flisk projects get different hosts and different cookie jars. Within one project the app and the API are different hosts, so a cookie the API sets is not sent to the app host unless you set it up on purpose.

In local-process mode Flisk also refuses to start a service whose port is already in use and names the process that holds it, which helps you find a forgotten old copy of an app that is still setting cookies.

Pitfalls

  • Clearing "all cookies" in the browser logs you out of real sites. Clear only the localhost entries from devtools.
  • A cookie name change logs everyone out once. That is fine in development, and a deliberate rollout step in production.
  • Remember the collision when a bug report says "random logouts". Ask which other localhost ports are running before reading any auth code.

If the cookie is set but never sent, the cause is likely CORS credentials or SameSite instead. The Secure cookies article is the next place to look.

Questions people ask

Do cookies include the port number?

No. Cookies are scoped by host and path. Two apps on different ports of the same host share cookies.

Do localhost and 127.0.0.1 share cookies?

No. They are different hosts, so each has its own cookie jar.

Is localhost:3000 same-site with localhost:4000?

Yes. Site matching ignores the port, so a SameSite=Lax cookie is sent, but the request is still cross-origin for CORS.
