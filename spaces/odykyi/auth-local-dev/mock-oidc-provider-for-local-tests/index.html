Authentication in local development

How to use a mock OIDC provider for local tests and CI

A throwaway identity provider that hands out valid tokens for any user name you type, so tests stop depending on a real one.

Run mock-oauth2-server, a small container that behaves like an OpenID Connect provider and signs tokens with its own keys. Your app uses its issuer URL, http://localhost:8080/default, exactly like a real one. The login page accepts any username, and you choose the claims in the token. No account, no network, nothing to clean up.

Start it

The project is published as ghcr.io/navikt/mock-oauth2-server. Pick a release tag from its GitHub releases page rather than latest, so a test run next month uses the same server as today. The tag below is an example; check that it exists before you rely on it:

docker run --rm -p 127.0.0.1:8080:8080 \
  ghcr.io/navikt/mock-oauth2-server:2.1.10

The server creates an issuer on demand for the first path segment of any request. So default is not special: /default, /staging and /anything are three separate issuers with their own keys. Open the discovery document to see the endpoints:

curl http://localhost:8080/default/.well-known/openid-configuration

The issuer field is http://localhost:8080/default. Its authorization_endpoint, token_endpoint and jwks_uri are under the same path.

Point your app at it

Any OIDC client library needs three values: the issuer (or its discovery URL), a client id, and a client secret if the client is confidential. This server does not check the client id or secret, so any value works. Register this redirect in your app, and nothing in the mock server needs to match it first:

OIDC_ISSUER=http://localhost:8080/default
OIDC_CLIENT_ID=local-app
OIDC_CLIENT_SECRET=anything
OIDC_REDIRECT_URI=http://localhost:3000/auth/callback

Start the sign-in flow in the browser. The server shows a form: type any username, and in the claims box a JSON object such as {"email":"alice@example.test","groups":["admin"]}. Submit, and the browser returns to your callback with a code. Your app exchanges it at the token endpoint for an ID token and an access token. The sub claim is the username you typed.

Run it with Flisk

Put the image in a service.json without a command, and flisk up starts it with docker run next to your local processes. Docker has to be running for this one service.

{
  "schemaVersion": 1,
  "appName": "oidc",
  "appType": "bring-your-own",
  "stack": "auth",
  "image": "ghcr.io/navikt/mock-oauth2-server:2.1.10",
  "port": 8080
}

Make the app depend on it and pass the issuer through env:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "stack": "auth",
  "command": "npm run dev -- --port 3000",
  "port": 3000,
  "dependsOn": ["oidc"],
  "env": { "OIDC_ISSUER": "http://localhost:8080/default" }
}

Check the files with flisk config verify, and see the start order with flisk up --dry-run. The image's own port is published on 127.0.0.1 at the same number, which is why the issuer is localhost:8080 for your browser and for your local processes.

Use it in automated tests

  • Keep the issuer stable. Tokens contain iss, and your API compares it with its configured issuer string. One typo in the scheme, port or trailing path is enough to reject every token.
  • Test the failures too. Request a token for a user without the expected group and check that your API answers 403. A mock that always succeeds only proves the happy path.
  • Do not reuse it for production. It trusts everyone by design.
  • Short expiry for expiry tests. The server can be configured with a JSON file for token lifetime and claims; see its README for the exact setting, and the clock skew article for what your API should do on exp.

Common failures

  • Issuer differs by one character. http://localhost:8080/default/ with a trailing slash is not the same string as http://localhost:8080/default. Copy the issuer value from the discovery document instead of typing it.
  • The API runs in a container. From inside another container, localhost is that container itself, so it cannot fetch the keys. If the API is a local process this does not apply; otherwise the issuer your API reaches must also be the issuer that ends up in the token, and that is hard to arrange for two different host names.
  • Keys change on restart. The server generates its signing keys when it starts. An API that cached the key set from the previous run rejects new tokens until it fetches the keys again, so restart both together or let the API refresh on an unknown key id.
  • Browser blocks the redirect. If the callback never loads, check that your app is actually listening on the port in the redirect URI. The redirect URI article covers the usual mistakes.

For a login flow with real users, roles and a console, use Keycloak. For tests, the mock is faster to start and has nothing to seed.

Questions people ask

What is a mock OIDC server?

A small server that implements the OpenID Connect endpoints and signs tokens with its own keys, so an app can run a full sign-in flow in tests without a real identity provider.

What issuer URL does mock-oauth2-server use?

http://localhost:8080/<name>, where the first path segment is the issuer name. The server creates that issuer on the first request.

Does the mock server check client id and secret?

No. Any client id and secret work, so do not use it to test client authentication.
