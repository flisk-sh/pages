Authentication in local development

Auth.js on localhost: AUTH_SECRET, AUTH_URL and the callback

Most Auth.js problems on localhost come down to three values: a secret, the app's own URL, and the exact callback path.

Auth.js (the library formerly called NextAuth.js) needs three things to work on localhost: a secret that signs its session cookie, the URL your app is served from, and a provider callback registered as /api/auth/callback/<provider>. Get those three consistent and most local sign-in errors disappear.

Version note: Auth.js v5 reads variables prefixed with AUTH_. NextAuth v4 reads NEXTAUTH_SECRET and NEXTAUTH_URL. Check which one your package.json installs and use the matching names; mixing them is a common reason a value seems ignored.

1. The secret

AUTH_SECRET is a random string used to sign and encrypt the session token. If it is missing, Auth.js throws a configuration error instead of starting a session. Generate one and keep it in an untracked .env.local file:

openssl rand -base64 32
# .env.local  (not committed)
AUTH_SECRET=paste-the-generated-value-here

Use a different secret for each environment. If you change it, every existing session cookie becomes unreadable and users are signed out, which is harmless on a laptop. Do not commit it; the gitignore article shows how to keep the file out of git.

2. The URL

Set AUTH_URL=http://localhost:3000 when your app is on port 3000. On a plain next dev Auth.js can often work out the host from the request, so the variable matters most when something sits in front of the app: a proxy, a custom domain, or a different port from the one the browser shows. In that case also set AUTH_TRUST_HOST=true, which tells Auth.js to believe the host header the proxy forwards. Never set that on a server that is directly open to the internet without a proxy you control. The forwarded headers article explains why those headers are trusted only from your own proxy.

The URL must match the one in the browser's address bar exactly: scheme, host and port. http://127.0.0.1:3000 and http://localhost:3000 are different origins, so a session cookie set on one is not sent to the other. Pick one name and use it everywhere. See why apps on localhost share cookies for the port detail.

3. The callback path

When you register your app with a provider, the redirect URI is your URL plus /api/auth/callback/ and the provider id. For GitHub on port 3000 that is:

http://localhost:3000/api/auth/callback/github

For Google, replace the last segment with google. A mismatch shows up as redirect_uri_mismatch at the provider; the redirect URI article has a step-by-step comparison, and the GitHub OAuth app article covers the registration side. If your app mounts Auth.js under another base path, the callback follows that path.

Check it works

Open /api/auth/providers in the browser. It lists the configured providers and their callback URLs as JSON, so you can copy the exact callback string into the provider's settings instead of typing it. Then sign in once, open the browser's storage panel, and confirm a session cookie exists for localhost. If the providers page itself returns an error, the problem is the route or the secret, not the provider.

Run it with Flisk

Flisk can generate the secret and pass it to a Next.js process. Declare a generated name under secrets.generate and map it to AUTH_SECRET in env. The two names must differ, because flisk config verify rejects an env variable that secrets.generate also creates:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "stack": "auth",
  "command": "npx next dev -p 3000",
  "port": 3000,
  "secrets": { "generate": { "AUTH_SESSION_KEY": "base64:32" } },
  "env": {
    "AUTH_SECRET": "${AUTH_SESSION_KEY}",
    "AUTH_URL": "http://localhost:3000",
    "AUTH_GITHUB_ID": "${AUTH_GITHUB_ID}",
    "AUTH_GITHUB_SECRET": "${AUTH_GITHUB_SECRET}"
  }
}

On flisk up, a missing AUTH_SESSION_KEY is appended once to the project .env and never changed afterwards, so sessions survive restarts. Put the GitHub client id and secret in that same .env by hand; a bare ${NAME} is read from your shell, then the project .env, and flisk up warns when one is unset. Run flisk config verify before starting. flisk up prints http://localhost:3000, and flisk logs --service web shows the Auth.js errors.

Common errors

  • MissingSecret. AUTH_SECRET is unset in the process that serves the route. A value in a shell you opened earlier is not seen by a service Flisk starts; define it in the manifest or in the project .env.
  • Sign-in loops back to the login page. The session cookie is not accepted. Check that you use one host name, and that no secure flag is forced over plain HTTP; see secure cookies on localhost.
  • UntrustedHost. The request came with a host Auth.js does not trust. Set AUTH_TRUST_HOST=true behind your own proxy.
  • Callback shows "not found". The route handler is not mounted at /api/auth/[...nextauth].

Questions people ask

What is the Auth.js callback URL on localhost?

Your app URL plus /api/auth/callback/<provider>, for example http://localhost:3000/api/auth/callback/github.

Do I need AUTH_URL in local development?

Often not on a plain next dev, since Auth.js can read the host from the request. Set it when a proxy, a custom domain or another port sits in front of the app.

What is the difference between AUTH_SECRET and NEXTAUTH_SECRET?

AUTH_SECRET is the Auth.js v5 name. NextAuth v4 uses NEXTAUTH_SECRET. Use the one your installed version reads.
