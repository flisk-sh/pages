Vibe coding without the mess

How to vibe code in small steps with git checkpoints

Commit after every working slice so a bad prompt costs you one command, not an afternoon. A simple loop with the exact git commands.

Commit after every change that works, keep each prompt to one small task, and use git diff to see what the agent touched before you accept it. When a prompt goes wrong, git restore . brings you back to the last good state.

The loop

  1. Start from a clean working tree: git status shows nothing.
  2. Give the agent one small task.
  3. Run the app or the tests.
  4. Read git diff --stat and skim the diff.
  5. If it is good, commit. If not, restore.

The point is that every step ends in a state you can return to.

Write the loop on a sticky note if you need to. The habit that matters most is step one: never start a prompt with uncommitted changes, because you then cannot tell which edits came from the agent and which were yours.

The commands you need

git init
git add -A && git commit -m "checkpoint: empty app runs"

# after the agent works
git diff --stat          # which files changed, how much
git diff                 # the actual changes
git add -A && git commit -m "add checkin endpoint"

# a bad result
git restore .            # drop edits to tracked files
git clean -fd            # remove new untracked files (check first with -n)

Run git clean -nfd before the real one. It lists what would be deleted.

What counts as small

A good task fits in one sentence and touches a few files: "add a delete button to each habit", "validate the email field". A bad task is "make it production ready". If the diff is more than a few hundred lines, the step was too big. Restore and split it.

A useful rule of thumb: if you cannot describe the change in a commit message of one line, the step was two steps. Also commit before you ask for a refactor, so that the "before" state is one command away.

Use branches for risky experiments

For a larger idea, such as swapping the database, make a branch: git switch -c try-postgres. If it goes badly, switch back and delete the branch. Branches cost nothing and keep the main line working.

If you run several agents or sessions at once, give each its own worktree with git worktree add ../app-feature feature-branch so they do not overwrite each other's files.

Pitfalls

  • Committing secrets. Add .env to .gitignore before the first commit. See env and secrets for local development.
  • Giant "fix everything" prompts. They produce diffs nobody reviews.
  • Skipping the run step. A commit that does not start is a bad checkpoint.

Pair this with tests (next article) and each checkpoint becomes trustworthy.

Questions people ask

Should the agent commit for me?

It can, but read the diff first. Many people let the agent commit on a scratch branch and squash later, which keeps the main branch clean.

How often should I commit?

After every working slice, usually every few minutes of agent time. Commits are cheap and you can squash them before sharing.
