Vibe coding without the mess

When should you read the code an AI wrote?

You do not have to read every line, but some parts deserve a careful look every time. A checklist of what to read, what to skim and what to ignore.

Reading time
4 min
Updated

On this page
  1. Read line by line
  2. Skim
  3. Mostly ignore
  4. Questions to ask while reading
  5. Ask the agent to help you read

Read the code that handles authentication, permissions, money, data deletion, database schema and anything that runs shell commands or reaches the network. Skim the rest, and rely on tests and the running app for UI details.

Read line by line

  • Authentication and sessions. How passwords or tokens are checked and stored.
  • Authorisation. Every place a record is fetched by id: does it check the owner?
  • Payments and quotas. Anything that changes a balance.
  • Deletes and migrations. Anything that cannot be undone.
  • Shell, file and network calls. Where user input becomes a command, a path or a URL.

Why these areas? Because a mistake in them is silent and costly. A layout bug is visible in seconds. A missing owner check can sit unnoticed until someone else finds it. Read where you cannot see the failure by clicking around.

Skim

Business logic that has tests, route wiring, and glue code. Look at the shape: are there obvious duplicates, huge functions, or new dependencies you did not ask for? Run git diff --stat and notice files that changed for no reason.

A practical trick is to read the diff, not the whole file. git diff shows what changed in this step, which is a much smaller thing to understand than the entire project, and you can do it every commit in a minute or two.

Mostly ignore

Styling details, boilerplate config, and generated lock files. If the page looks right and the tests pass, do not spend attention here.

If a large generated file looks fine in the browser and its tests pass, move on. Perfectionism about code you did not write and rarely touch is a poor use of your time.

Questions to ask while reading

  1. What happens with empty, huge or malicious input?
  2. What happens when this call fails or times out?
  3. Is there a hard-coded secret, URL or user id?
  4. Could two requests at once corrupt this?
  5. Is this dependency real and maintained?

That last one matters: agents sometimes import packages that do not exist or are not what you expect. Check the name on the package registry before installing.

Ask the agent to help you read

You can say: "Explain this file as if I will maintain it. List every place that touches the database and every place that trusts user input." Treat the answer as a map, then verify the key lines yourself. A model explaining its own code can be confidently wrong.

For a pre-launch pass, use the security checklist.

Keep a short list in your repo of the places you review every time. After a few weeks you will know which files the agent edits carelessly, and you can aim your attention there first.

Questions people ask

Is it fine to never read the code for a personal tool?

Yes, if a bug only affects you and you would notice it. Read it as soon as the tool handles credentials or other people's data.

What if I cannot read the language?

Ask the agent for a plain-language summary of the risky parts, then get a developer to review those parts before real users arrive.
