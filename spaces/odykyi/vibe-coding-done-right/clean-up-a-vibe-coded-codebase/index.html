Vibe coding without the mess

How to clean up a vibe-coded codebase step by step

You have a working app that nobody dares to touch. Add tests, remove dead code, document it and refactor in small steps, without breaking what works.

To clean up a vibe-coded codebase, freeze its current behaviour with tests first, then delete dead code, remove duplicates and document how to run it, committing after every step. Do not refactor and add features in the same change.

Step 1: make it run from a clean checkout

Clone the repo into a new folder and follow your own instructions. Fix whatever breaks. Write the commands in the README: install, configure, run, test. If a stranger cannot start the app in a few minutes, nothing else is worth doing yet. The free README Score gives a README a score out of 100, lists the missing sections, and shows a fix for each. It is rule based, so the same README always gets the same score.

Tick the boring boxes too: a pinned runtime version, a lock file, a sample environment file with variable names and no values. They remove most of the "works on my machine" trouble.

Step 2: pin behaviour with tests

Before changing anything, write tests for what the app does today, including its quirks. These are characterization tests: they describe reality, not the ideal. Ask the agent to write them and tell it not to change application code. See how to add tests.

Step 3: remove what is unused

git grep -n "functionName"        # is it called anywhere?
npx knip                            # JS/TS: unused files and exports
vulture src/                        # Python: unused code

Run the tests, delete one batch, run the tests again, commit. Unused dependencies go too; fewer packages means fewer security issues.

Step 4: merge duplicates

Agents often write the same helper in several places. Find the repeats, pick the best one, and point everything at it. One change per commit, tests green each time. This is where small checkpoints pay off.

Step 5: write the rules down

Add a short AGENTS.md or similar with the stack, the folder layout, the test command, and what not to do. Future sessions will follow it instead of inventing new structure. Keep it under a page.

What not to do

  • Do not ask the agent to "clean up everything". The diff will be unreadable.
  • Do not rename and restructure files while fixing bugs.
  • Do not upgrade major dependencies and refactor at the same time.

When the code is stable, run the security checklist once more.

When all of this is done, run the whole test suite from a clean clone one more time. That final check is the proof that you improved the project and did not only move things around.

Budget time for this in the plan. Clean-up feels like no progress, but it is what makes the next ten features cheap instead of risky.

Questions people ask

How long does a clean-up take?

For a small app, a day or two of focused work. The first two steps, a clean start and tests, give most of the benefit.

Should I use an AI to refactor?

Yes, with tests in place and small scoped requests. Without tests, you cannot tell whether a refactor changed behaviour.
