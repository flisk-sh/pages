Vibe coding without the mess

How to write prompts that make AI coding agents build what you meant

Vague prompts get vague code. A practical pattern for coding prompts: context, task, constraints, and how to verify, with before and after examples.

A good coding prompt names the task, the files it may touch, the constraints, and how to verify the result. Keep it to one task, say what not to change, and tell the agent which command proves it worked.

The four parts

  1. Task. One sentence, one outcome.
  2. Scope. Which files or folders it may change.
  3. Constraints. Libraries, style, what to leave alone.
  4. Check. The command or behaviour that proves it works.

You will not need all four every time. A tiny change needs only a task and a check. The longer prompts are for work where the agent could reasonably go several ways, and you want it to pick yours.

Before and after

Before:

make the signup better

After:

In src/routes/signup.js, reject emails that are not valid and passwords
shorter than 12 characters, returning 400 with a JSON error message.
Do not change the database code or add dependencies.
Add tests in tests/signup.test.js. Run `npm test` and show the result.

The second prompt can be checked. The first can only be argued about.

Give examples, not adjectives

"Clean" and "modern" mean little. Point at an existing file: "Follow the pattern in src/routes/habits.js." For UI, describe layout and content: "a table with columns name, created, and a delete button". An example in the repo beats a paragraph of description.

Screenshots, error messages and sample data are examples too. Paste the real error text instead of describing it, including the line numbers and the command that produced it. Specifics let the agent find the problem in one try instead of three.

Ask for a plan on bigger tasks

For anything over a few files, say: "First list the files you will change and why. Wait for my OK." Reading a plan takes a minute and catches wrong assumptions before they become code. Then implement in steps (see git checkpoints).

Review the plan for what is missing as well as what is wrong. If it never mentions tests, error handling or the file you expected, say so before any code is written.

Pitfalls

  • Several tasks in one prompt. The agent does some of them well and drops others.
  • No success check. The agent says done because it ran out of ideas.
  • Saying only what you want. Also say what not to touch.

Reusable rules go in a project file, covered in why AI-built apps keep breaking. For prompts inside your app, see prompts and structured outputs.

When a result is wrong, resist the urge to scold. Say what is wrong, what it should do instead, and restate the check. Three precise sentences work better than a long correction, and a long argument fills the context with noise that later hurts quality.

Questions people ask

Should prompts be long?

As long as they need to be and no longer. A short prompt with a clear scope and a check beats a long one full of preferences.

Do I need different prompts for different agents?

The pattern works across tools. Details such as the project instruction file name differ, so check your tool's documentation.
