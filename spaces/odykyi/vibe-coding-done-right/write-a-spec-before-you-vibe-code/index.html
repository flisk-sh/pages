Vibe coding without the mess

How to write a spec before you ask an AI to build your app

A one-page spec gives the agent the constraints it would otherwise guess. Here is a short template, a worked example, and the parts that matter most.

Write a one-page spec before the first prompt: what the app does, who uses it, the data it stores, what it must not do, and how you will know it works. Then paste it into the agent and ask it to implement only the first slice.

Why a spec beats a longer prompt

A prompt is a request. A spec is a contract you can check the result against. When the agent drifts, you can point at a line and say "this violates item 4" instead of rewording your wish.

It also survives the session. Save it in the repo as SPEC.md and every new session starts from the same facts.

A template that fits on one page

# SPEC: Habit tracker

## Goal
One sentence on what this app does and for whom.

## Users and flows
1. User signs in with email.
2. User adds a habit.
3. User ticks it done for today.

## Data
habit(id, user_id, name, created_at)
checkin(id, habit_id, day)  -- unique per habit and day

## Out of scope
No teams, no notifications, no mobile app.

## Constraints
SQLite, one process, no external services.

## Done means
- A user can only see their own habits.
- Ticking twice on one day does not create two rows.
- `npm test` passes.

Keep the headings, change the content. The "Data" section is the one people skip and regret: if you do not name the tables and the unique rules, the agent will invent them, and a wrong data model is the most expensive thing to change later.

Write the out of scope list first

Agents love adding features. Every extra feature is more code to be wrong. A short "out of scope" list is the cheapest control you have. Be blunt: no admin panel, no analytics, no new dependencies without asking.

Turn "done means" into checks

Each line under "Done means" should be something a test or a command can confirm. "Fast" is not checkable. "The list page returns in under one second with 1,000 rows" is. If you cannot phrase a line that way, leave it out or mark it as a goal.

These lines become your first tests. See how to add tests to a vibe-coded app.

Hand it over in slices

Do not say "build the whole spec". Say: "Read SPEC.md. Implement only flow 1 and its data. Stop and show me how to run it." Then continue slice by slice, committing between them (small steps with git checkpoints).

Update the spec when you change your mind. A spec that disagrees with the code is worse than none.

A good first slice is the thinnest path through the whole app: one screen, one endpoint, one table. It proves the pieces connect. Adding features to a working skeleton is much easier than debugging a large first draft that was never run.

If you only have a rough idea, Build Me an App turns a plain description into the Flisk commands to run it on your own computer. It is a way to get a skeleton to react to, not a replacement for the spec.

Questions people ask

How long should a spec be?

One page is enough for a small app. If it runs past two pages, split the project into parts and write one spec per part.

Should I let the AI write the spec?

Yes for a first draft, but read and cut it. Remove anything you did not ask for, then add the constraints only you know.

Try it

Run the app you just built, with its database, on your own machine.
