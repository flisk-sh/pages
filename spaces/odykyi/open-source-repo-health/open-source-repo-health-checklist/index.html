Open-Source Repo Health Checklist: 12 Things to Fix

A short checklist of the files, settings and habits that make a public repository easy to trust, use and contribute to, in the order that gives the most return.

A healthy open-source repository has a license, a README that shows how to run it, a contributing guide, a security policy, working CI on the default branch, and a maintainer who answers issues. Fix them in that order, because each one removes a reason for a visitor to leave.

The twelve items

  1. A LICENSE file with a standard license text.
  2. A README with what it is, install, a first example and where to get help.
  3. CONTRIBUTING.md with how to set up, test and submit a change.
  4. SECURITY.md saying how to report a vulnerability.
  5. CODE_OF_CONDUCT.md for projects that accept outside contributors.
  6. Issue and pull request templates.
  7. A passing CI workflow on the default branch.
  8. Branch protection or rulesets on the default branch.
  9. A short repository description and topics.
  10. Tagged releases and a changelog.
  11. Automated dependency updates.
  12. Labels such as good first issue and an owner for triage.

Each has its own article in this hub. Start with the first four, they take an hour.

Use GitHub's own checklist

Every repository has a Community Standards page, under Insights, that lists which of these files are present and links to create the missing ones. It checks the README, code of conduct, contributing guide, license, security policy and templates. It is a good first pass, though it only checks that files exist, not that they are any good.

Measure it, do not guess

A one-off cleanup fades. Measure the same few signals regularly. Cilytics is a public CI health dashboard for GitHub that needs no account. Point it at any public repo with a query like the one below and it shows pass rate, median run time, red workflows, flaky and slow workflows, and an open-source hygiene score out of 100.

https://cilytics.flisk.si/?repo=owner/name

Know its limits: it looks at default-branch runs only, at the last 100 runs, from an hourly snapshot rather than live data, and it leaves out repos inactive for 90 days. Use it as a signal, not as a verdict. See CI metrics that matter for how to read those numbers.

Do the cheap things first

License, README and a security policy cost almost nothing and change how a stranger sees the project. A red badge on the default branch costs the most trust. If CI is failing for weeks, fix or delete the broken workflow before polishing anything else, because a visitor reads a red build as an abandoned project. For help with that, see flaky tests and CI.

What not to do

  • Do not copy a long governance document you will not follow. A short honest file beats a grand unused one.
  • Do not add every badge you can find. Two or three that mean something are enough.
  • Do not promise response times you cannot keep. Say 'best effort' if that is the truth.
  • Do not leave template placeholders like 'Your Name Here' in published files.

Put the list into your own repository as an issue, check items off, and review it every quarter. Health is a habit, not a state.

Questions people ask

Which file matters most?

The license. Without one, the default is that nobody may legally use, copy or modify your code, so many companies will not touch the project. Add the README next.

Where do community files go?

In the repository root, in a docs folder or in a .github folder. GitHub recognises all three locations, and an organisation-level .github repository can supply defaults for all its repositories.
