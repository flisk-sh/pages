GitHub Issue and Pull Request Templates That Work

Write templates that get reproducible bug reports and reviewable pull requests, including YAML issue forms, a config file and a short pull request checklist.

Put issue templates in .github/ISSUE_TEMPLATE/ and a pull request template at .github/pull_request_template.md. Keep each template to the few fields that save you a back-and-forth, and ask for versions, steps to reproduce and expected behaviour.

Bug report issue form

GitHub supports YAML issue forms that render as real fields and can mark some as required.

# .github/ISSUE_TEMPLATE/bug.yml
name: Bug report
description: Something does not work
labels: [bug]
body:
  - type: input
    id: version
    attributes:
      label: Version
    validations:
      required: true
  - type: textarea
    id: steps
    attributes:
      label: Steps to reproduce
      description: Commands, input and what you saw
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: Expected behaviour

Required fields stop empty reports. Keep optional fields few, since a long form discourages people.

Send questions elsewhere

A config.yml in the same folder controls the template chooser. Use it to send usage questions to Discussions and security issues to the private route, so the issue tracker stays for bugs and features.

# .github/ISSUE_TEMPLATE/config.yml
blank_issues_enabled: false
contact_links:
  - name: Questions
    url: https://github.com/owner/repo/discussions
    about: Ask usage questions here
  - name: Security
    url: https://github.com/owner/repo/security/advisories/new
    about: Report a vulnerability privately

## Checklist
- [ ] Tests added or updated
- [ ] Docs updated if behaviour changed
- [ ] CI is green
- [ ] Linked issue: #

The template is not paperwork if every line corresponds to a check a reviewer would otherwise ask for. Delete lines nobody reads. Where you can, enforce the checklist with CI rather than hoping people tick boxes, see CI for agent-written pull requests.

Labels and triage

Templates can add labels automatically, as the labels key above does. Keep a small label set: bug, enhancement, question, good first issue, help wanted. A short list is used, a long one is ignored. Decide who triages and how often. Even a weekly sweep that closes duplicates and tags the easy issues keeps the tracker useful. Link to this process from CONTRIBUTING.md.

Pitfalls

  • Too many required fields cause people to type 'n/a' or leave.
  • Templates in a fork or a wrong folder name are silently ignored, so open a test issue after you add them.
  • An organisation-wide .github repository can provide default templates, but a repo's own templates override them.
  • Update templates when your project changes, for example when you add a new platform that needs a field.

Review the templates with real data after a month. Look at ten recent issues and ask which fields were filled usefully and which were ignored. Remove the ignored fields and add a field for any question you asked in comments more than twice. Templates are a living part of the project, and the best ones are short because someone kept cutting them. If you accept pull requests from coding agents, the same checklist gives them an explicit target, which cuts review noise.

Questions people ask

Markdown template or YAML form?

YAML forms give structured, required fields and are best for bug reports. Markdown templates are simpler and fine for pull requests, which do not support YAML forms.

Can I have multiple templates?

Yes. Put several files in the ISSUE_TEMPLATE folder and GitHub shows a chooser, for example bug report, feature request and question.
