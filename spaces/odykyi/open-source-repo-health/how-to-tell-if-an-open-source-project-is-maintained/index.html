How to Tell If an Open-Source Project Is Still Maintained

Signals to check before you depend on a library: recent releases, open issue handling, CI status, bus factor and a quick way to look at its health in a few minutes.

Check five things before you depend on a project: a release or commit in the last few months, issues and pull requests that get replies, a passing build on the default branch, more than one active maintainer, and a license plus security policy. No single signal decides it, but together they tell you quickly.

Signals in the repository

  • Commits and releases: look at the dates. Stable libraries may change rarely, so compare with the issue activity.
  • Issues and pull requests: are recent ones answered? A pile of untouched pull requests older than a year is a bad sign.
  • Maintainers: check the contributors graph. One person doing everything is a single point of failure.
  • Releases and tags: are releases tagged, with a changelog?
  • Dependencies: do automated update pull requests get merged, or do they sit?

Signals from CI

A permanently red default branch says nobody is looking. Open the Actions tab and check the latest runs on the default branch, then how often it fails and whether failures are fixed. Cilytics shows this for any public repository without an account, using a query like the one below. It lists red workflows, pass rate, median run time, flaky workflows and an open-source hygiene score out of 100.

https://cilytics.flisk.si/?repo=owner/name

It reads default-branch runs from the last 100, as an hourly snapshot, and skips repos inactive for 90 days, so a missing project may simply be quiet. Treat it as one input.

Use the API for a quick look

You can do a rough check from the terminal with the GitHub CLI.

gh repo view owner/name --json pushedAt,updatedAt,isArchived
gh release list -R owner/name -L 3
gh run list -R owner/name -b main -L 10

Check isArchived. An archived repository is read-only and its maintainers have said it is finished.

Judge the response, not only the activity

Read three recent issues and see how the maintainers respond: polite, specific, fast enough for your needs? Look at how they handled a security report or a breaking change, if you can find one in the release notes. A slow project can be fine for a stable parser and unacceptable for a web framework. Match the bar to the role the dependency plays in your system.

Decide and plan

If a dependency passes, still protect yourself: pin versions, enable automated updates and keep a note of the alternatives. If it fails, you can fork, vendor a small piece, or replace it. Do the same honest check on your own repo, using the health checklist, since your users will make the same judgement about you.

Write down your result in the pull request or design note where you add the dependency, with the date. A short line such as 'last release March, two active maintainers, CI green, issues answered within days' lets the next person re-check the same signals later. Dependencies change owners and fall quiet, so a dated note makes the review repeatable instead of a vague memory that the library seemed fine.

Questions people ask

Is no recent commit a dealbreaker?

Not always. Small, finished libraries can be stable for years. Look for unanswered issues, a broken build or unpatched security reports, which matter more than the date.

What does an archived repository mean?

The owner has made it read-only, usually because it is finished or abandoned. Do not start new work on it unless you plan to fork and maintain it yourself.
