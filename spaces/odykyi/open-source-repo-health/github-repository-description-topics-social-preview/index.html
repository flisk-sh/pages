GitHub Repo Description, Topics and Social Preview Image

Small repository settings that decide whether people and search engines find and click your project: description, topics, website link, social preview and pinned repos.

Write a one-line description that says what the project does, add five to ten relevant topics, set the website link, and upload a social preview image. These fields appear in GitHub search, in link previews on chat apps and in search engines, and cost five minutes.

Description

The description sits under the repository name and is shown in search results and in link cards. Write it as a plain sentence a stranger can understand: what it is, and for whom. 'CLI that runs microservices locally from one JSON file per service' beats 'My awesome project'. Keep it short enough to fit a link preview, and include the words people would search for.

Topics

Topics are tags that make your repository show up on GitHub topic pages and in search filters. Use specific, widely used ones: the language, the framework, the problem area and the tool category, such as cli, docker, github-actions. You can set them in the sidebar by clicking the gear icon, or with the CLI:

gh repo edit owner/name --add-topic cli --add-topic docker \
  --description 'One-sentence description' \
  --homepage https://example.com

Do not stuff every topic you can think of. Irrelevant topics look like spam, and GitHub limits how many you can add.

Website link

The homepage field accepts a URL. Point it at your docs or landing page. If you have no site, link the documentation folder or a published README. A simple way to get a free public link for a page is Pages, which publishes a page or Markdown file with npx -y @flisk-sh/pages publish page.html --wait. Note that the result is public, so do not publish anything private.

Social preview image

Under Settings, you can upload an image that appears when the repository link is shared on social networks and chat apps. GitHub documents the recommended size, at the time of writing around 1280 by 640 pixels, so check the current guidance. Use the project name in large text, a one-line tagline and your logo, with plenty of contrast. A plain generated card still beats the default, which just shows your avatar and the description.

Pin and tidy

  • Pin your best repositories on your profile or organisation page, so visitors see them first.
  • Archive repositories you will not maintain, so people are not misled.
  • Make sure the README title matches the repository name and description.
  • Run through the repo health checklist once the basics are in place, and write a README that follows this structure.

Check the result the way a stranger would. Paste the repository link into a chat app and a social post draft, and look at the preview card. Search GitHub for your main topic and see where the project appears. If the card shows an unreadable image or a vague sentence, change it. Repeat the check after major renames, since the preview is cached and can show old text for a while. These checks take two minutes and catch the most visible mistakes.

Questions people ask

How many topics should I add?

Five to ten specific ones is a good range. GitHub caps the number, so pick the ones people actually search for.

Does the description affect search engines?

It is shown on the repository page and in many link previews, so a clear sentence helps people and crawlers understand the project. Treat it as a headline.
