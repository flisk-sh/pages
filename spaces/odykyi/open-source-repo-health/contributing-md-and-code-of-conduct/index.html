CONTRIBUTING.md and Code of Conduct: What to Write

What a contributing guide must contain, how to set expectations for review time, when a code of conduct is worth adding and how DCO sign-off works.

A CONTRIBUTING.md should tell a newcomer how to set up the project, run the tests, follow your style, and submit a pull request, in under a page if possible. Add a CODE_OF_CONDUCT.md when you invite outside contributors, so people know how disagreements are handled.

What goes in CONTRIBUTING.md

  • Setup: the exact commands to clone, install and run.
  • Tests: the one command that must pass before a pull request.
  • Style: the linter or formatter, and how to run it.
  • Workflow: branch naming, commit message format, one change per pull request.
  • Review: who reviews, and a realistic time to expect an answer.
  • Big changes: ask people to open an issue first, so no one wastes a weekend on a change you will decline.

GitHub links to this file when someone opens an issue or pull request, so it is read at the right moment.

A short example

# Contributing

## Setup
    git clone https://github.com/owner/repo
    cd repo && npm ci

## Before you open a pull request
    npm run lint && npm test

## Pull requests
- One change per pull request.
- Add or update a test for behaviour changes.
- Sign off your commits: git commit -s

We aim to review within a week. Large changes: open an issue first.

Make the claims real. If you write 'within a week' and take a month, say 'best effort' instead.

DCO sign-off

The Developer Certificate of Origin is a lightweight way for contributors to state they have the right to submit their work. It uses a Signed-off-by line in each commit, added by git commit -s. It is lighter than a contributor license agreement, which requires signing a document. You can check sign-offs in CI so missing ones fail early. Pair this with your license choice.

Code of conduct

A code of conduct states what behaviour is expected and where to report problems. The Contributor Covenant is a widely used ready-made text, and you can adopt it as is. The part that matters is the contact: name a real address or a private channel that someone actually reads, and say what happens after a report. A code with no working contact is decoration. For a solo project with no outside contributors yet, you can add it when the first contributors arrive.

Reduce the load on yourself

Most reviewer time is spent on avoidable things: failing CI, missing tests, unclear titles. Put them in the guide, and let automation say no for you. Use a pull request template and checks, see issue and pull request templates. When contributors are a mix of humans and coding agents, the same rules help both, and CI is the fair referee. In an organisation, a shared .github repository can hold default community files for every repo.

Link both files from the README and the pull request template so they are found. Review them once a year, and after any incident, to see whether the instructions still match how the project runs. Dead commands in a contributing guide are as bad as dead commands in a README, because they are the first thing a new contributor tries and the first thing that fails.

Questions people ask

Do I need a code of conduct for a small project?

Not strictly. Add one when you start accepting outside contributions or building a community, because it gives you a basis for acting when someone behaves badly.

Is DCO or CLA better?

DCO is lighter and needs only a sign-off line. A CLA is a signed agreement and can allow relicensing. Most small open-source projects choose DCO.
