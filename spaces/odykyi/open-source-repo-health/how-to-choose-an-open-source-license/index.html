How to Choose an Open-Source License for Your Project

A plain guide to picking between MIT, Apache 2.0 and the GPL family, what each lets others do, and how to add the license file correctly.

If you want maximum adoption with minimal fuss, choose MIT. If you want the same freedom plus an explicit patent grant, choose Apache 2.0. If you want improvements to stay open, choose a copyleft license such as the GPL. Whatever you pick, add the full text as a LICENSE file in the repository root.

Why you need one

Code published without a license is still protected by copyright, which means other people have no permission to use, change or share it. Users and companies see a missing license as a hard stop. Adding one is the single biggest step a public repository can take. This article is general information, not legal advice. For a company project or any doubt, ask a lawyer.

The three common choices

LicenseTypeIn short
MITPermissiveUse, modify and sell it. Keep the copyright notice. No patent language.
Apache 2.0PermissiveLike MIT, plus an explicit patent grant and a notice of changes requirement.
GPL familyCopyleftDerived works that are distributed must be released under the same terms.

Permissive licenses let others build closed products on your code. Copyleft requires them to share modifications when they distribute. The AGPL extends that to software offered over a network, which matters for hosted services.

A simple decision path

  • Want everyone, including companies, to use it freely: MIT.
  • Want that, and care about patents or expect corporate contributors: Apache 2.0.
  • Want to prevent closed forks of your work: GPL or AGPL.
  • Building a library that others link into their programs: weigh the copyleft effect carefully, because it can limit who adopts it. The LGPL exists for this case.

The site choosealicense.com summarises these and more in plain language, and is a good place to check before you commit.

Add the license correctly

Copy the official text, fill in the year and holder name, and save it as LICENSE. When you create the file through GitHub's 'Add file' flow, it offers license templates. Then declare it in your package metadata using an SPDX identifier so tools can read it.

{
  "name": "my-lib",
  "license": "MIT"
}

Use the exact identifier, such as MIT or Apache-2.0. GitHub detects standard license files and shows the license in the repository sidebar. Edit the text and detection can fail.

Pitfalls

  • Do not invent your own license text. Custom terms confuse users and block adoption.
  • Check that your dependencies' licenses are compatible with the one you pick.
  • If many people contribute, make sure contributors agree to your license. Many projects use a Developer Certificate of Origin sign-off, covered in the contributing guide article.
  • Changing a license later is hard once there are outside contributors, because each one holds copyright on their part.

Record the decision. Add a short note to the README stating the license, and if you chose copyleft, add one sentence on why, so users understand the intent. If you later add code from other projects, keep their notices intact and list them in a third-party notices file. Good license hygiene is mostly bookkeeping, and doing it early is far cheaper than untangling it when a company asks for a compliance review.

Questions people ask

Can I change my license later?

You can for your own code, but with outside contributions you generally need every contributor to agree, or a contributor agreement that allows relicensing. Decide early.

MIT or Apache 2.0?

Both are permissive. Apache 2.0 adds an explicit patent grant and is longer. MIT is shorter and more common in small libraries. Pick Apache 2.0 if patents matter to your users.
