How to Write a GitHub README That Gets Used

The sections a README needs, in order, with a template you can copy, plus how to check yours against a score so you know what is still missing.

A good README answers four questions in the first screen: what is this, why would I use it, how do I run it, and where do I get help. Put a working install command and a tiny example near the top, and move everything else below it.

The order that works

  1. Name and a one-sentence description that says what it does.
  2. A short 'why' with who it is for and when not to use it.
  3. Install or quick start with copy-paste commands.
  4. A minimal usage example with its output.
  5. Configuration or links to full docs.
  6. How to contribute and how to report problems.
  7. License.

Readers decide in seconds. A screenshot or a short code sample next to the install line does more than three paragraphs of motivation.

A starter template

# project-name

One sentence: what it does and for whom.

## Quick start

    npm install project-name
    npx project-name init

## Example

    import { run } from 'project-name'
    console.log(run('hello'))   // prints: HELLO

## Docs

Full guide: https://example.com/docs

## Contributing

See CONTRIBUTING.md.

## License

MIT

Test every command in a clean directory or container before you publish it. Broken quick starts are the top reason people give up.

Check it with a score

It is easy to forget a section. README Score gives a GitHub README a score out of 100, lists the sections it found and the ones missing, and gives a fix for each. The same README always gets the same score, because it is rule-based and uses no AI. It also has an MCP server at https://readme.flisk.si/mcp if you want a coding agent to run it. Treat the score as a checklist, not as a measure of how good your writing is.

Keep it honest and current

  • State what the project cannot do. Honest limits build trust and cut support questions.
  • Pin versions in examples or say which version you tested.
  • Use relative links for files in the repo, so they work on forks.
  • Keep badges to a few that show real state, such as CI status and the latest release.
  • Put long reference material in a docs folder and link to it.

Maintenance habit

When you change a command, option or default, change the README in the same pull request. Add a line to your pull request template asking whether docs changed. Run the quick start from scratch before each release. See the wider repo health checklist for what else belongs around the README. If agents will read your repo too, a short AGENTS.md beside the README helps, which is covered in making your repo ready for coding agents.

Ask someone who has never seen the project to follow your quick start while you watch, without helping. Every question they ask is a missing line in the README. Fix those lines, then repeat with another person. This is the cheapest test of documentation there is, and it finds problems that no checklist or score can see, such as a step that only works on your machine.

Questions people ask

How long should a README be?

Long enough to get a stranger from zero to a working example, and no longer. Most good READMEs fit a few screens, with detail linked to separate docs.

Should the README include a table of contents?

For long READMEs, yes. GitHub also generates an outline from the headings, so a manual table is only needed when you want it visible on other sites.
