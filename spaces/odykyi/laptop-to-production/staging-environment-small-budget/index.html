From laptop to production

How to set up a staging environment on a small budget

You do not need a copy of production. You need a place where the deploy can fail without anyone noticing.

A cheap staging environment runs the same images and the same configuration shape as production, on smaller plans, with its own database, its own secrets and test-mode keys for third parties. Its job is to catch deploy problems such as missing variables, failed migrations and broken routing, so it needs to be close in structure, not in size.

What staging is for

Staging answers one question: will this release work on a real host? It does not need production traffic or production data. It does need the same moving parts: the same Dockerfile, the same start command, the same kind of database, the same environment variable names and the same deploy path. Most surprises in a first deploy come from the differences between a laptop and a host, and staging is a host.

What must be separate

  • The database. Never point staging at production data. A bug or a migration test must not touch real users.
  • Secrets. Generate new ones. If staging leaks, production should not.
  • Third-party accounts. Use test modes and sandbox keys, for example a payment provider's test keys. See testing Stripe payments locally for the idea.
  • Outgoing email and notifications. Route them to a sink or an allow-listed address. See stopping dev from emailing real users.
  • The domain. A subdomain such as staging.example.com, with OAuth redirect URIs and webhooks registered for it.

What can be smaller

  • The plan size: one small instance per service, no autoscaling, a small database.
  • The data: a seed set or an anonymised sample. Never copy raw production data into staging, because it carries personal data into a less protected place. See how to seed a database.
  • The uptime: some hosts let free or low plans sleep, which is fine for a place that only you and your team use.
  • The lifetime: tear it down at night or on weekends if your host bills by time.

Three budget shapes

  1. A second environment on your platform. Same Blueprint or project, different names, smaller plans, separate database. This is the closest to production, and often the simplest, because the deploy path is identical.
  2. One small VPS with Compose. A single server running the stack from a Compose file with its own .env. Cheap, and you control it fully, but you also own backups, updates and HTTPS. See deploy a standalone Compose file to a VPS.
  3. Preview environments per pull request, if your platform supports them. Useful for UI review, but each needs its own data and costs add up. Most small teams are better off with one shared staging.

Use the same config for both

Staging only helps when production is built the same way. The trick is one set of config files and different values. With Flisk, the service.json files hold the names of the variables each service needs, and the exporters write them without values, so the same exported file works for both environments and each environment supplies its own values.

flisk export render --dry-run            # review the Render Blueprint
flisk export render --resource api       # export only one service
flisk export compose                     # standalone Compose file for a VPS

--resource and --out are real options of the Render exporter, --dry-run prints without writing, and every exporter needs Node.js 22.12 or later because it runs through npx. The exporters write files only: no deploy, no DNS record and no cloud calls. For Render, each variable is written as a name that Render asks for when you create the Blueprint, so staging and production values stay out of git. Create the staging Blueprint with its own values and the same file. Check the generated file is current in CI with a config drift check. The step-by-step version is in from a local stack to a Render Blueprint.

Make staging earn its keep

  1. Deploy every merge to main to staging automatically.
  2. Run the smoke test against it and block the production deploy on a pass.
  3. Run migrations on staging first, against a database that has realistic volume if the table is big.
  4. Promote the same image to production. Do not rebuild it, because a rebuild is a different artifact.

When you can skip it

For a hobby project with one service and an easy rollback, the production-image test on your laptop plus a good smoke test may be enough. Add staging when a bad deploy costs you real money or users, when more than one person deploys, or when you have a migration you cannot undo.

Whichever shape you pick, start from the checklist in the first deploy checklist and run through it on staging first.

Questions people ask

Can staging share the production database?

No. A staging bug or a migration test could change real user data. Use a separate database, even a small one.

How close should staging be to production?

Close in structure: same images, config names, database engine and deploy path. It can be smaller in size, data volume and uptime.

Is a preview environment per pull request worth it?

For UI-heavy teams it can be. For small teams one shared staging is cheaper and easier to keep in order.
