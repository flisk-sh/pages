How to back up and restore Postgres before you launch

A backup you have never restored is a hope, not a backup. Do the restore once, before launch day.

Back up Postgres with pg_dump in custom format, restore it into an empty scratch database with pg_restore, and check that the tables and row counts match. Do that once before launch, then schedule it. If your provider offers managed backups or point-in-time recovery, turn those on as well, and still try a restore.

Two kinds of backup

A logical backup such as pg_dump writes the schema and data as a file. It is portable, works across Postgres versions with care, and is easy to try on a laptop. A physical backup or snapshot copies the database files, usually with continuous archiving for point-in-time recovery. Managed Postgres providers offer this as a feature, and it is the better tool for restoring to a precise minute. Read your provider's documentation for what is on by default, how long copies are kept, and how to restore, because the answers differ and some plans have no automatic backups at all.

For a new app, run both ideas: the provider's snapshots for the quick recovery, and your own dump files stored somewhere else for the day the whole account has a problem.

Take a dump

pg_dump --format=custom --no-owner --file=app-$(date +%F).dump "$DATABASE_URL"
  • --format=custom produces a compressed archive that pg_restore can restore selectively and in parallel.
  • --no-owner skips ownership statements, which avoids errors when the target has different role names.
  • Use a pg_dump that is the same major version as the server, or newer. An older client refuses to dump a newer server.
  • The dump is consistent: it is taken from a single snapshot, so you can run it against a live database.

The file contains all your data, including personal data. Store it encrypted, restrict access, and delete old copies on a schedule.

Restore into a scratch database

This is the step people skip. Create an empty database, restore into it, and look:

createdb -h localhost -U postgres restore_test
pg_restore --no-owner --dbname "postgresql://postgres:password@localhost/restore_test" app-2026-11-14.dump
psql "postgresql://postgres:password@localhost/restore_test" -c "select count(*) from users;"

Compare the count with production. Open the app against the scratch database if you can. You are checking three things: the restore finishes without errors, the data is current, and you know how long it takes. A one-hour restore changes how you plan a risky migration. If you run Postgres locally in a container, running Postgres locally for development shows how to get a scratch server in a minute, and how to reset a local database covers dropping and recreating it.

When you restore over an existing database, pg_restore --clean --if-exists drops objects first. Point it at the right database, because it will delete things.

Schedule it

A manual dump before launch is a start. After launch you need a schedule and an offsite copy:

  1. Run the dump daily from a cron job or a scheduled job on your host. Do not run it inside the app container that serves traffic.
  2. Upload the file to object storage in a different account or region from the database.
  3. Keep a retention rule, for example daily files for two weeks. Set a lifecycle rule on the bucket so old files expire.
  4. Alert when a run fails or when the newest file is older than expected. A silent failure is the common way backups die.
  5. Repeat the restore test on a schedule, say monthly.

Where Flisk fits

It does not manage production databases. The exporters write services and environment names, and flisk export render leaves the database for you to define on the host. Your backup practice lives with the database provider or your own scripts. Locally, Flisk can run a Postgres container for development, but treat it as disposable data and never as the thing you back up from.

Pitfalls

  • Dumping the wrong database. Check the host and database name in the connection string before you run a restore with --clean.
  • Missing extensions and roles. A dump references extensions such as pgcrypto or vector. They must be available on the target. Roles are not part of a single-database dump.
  • Large objects and other databases. pg_dump covers one database. Use pg_dumpall for roles, or your provider's export, when you need cluster-wide data.
  • Backups that live next to the data. A copy on the same disk does not survive the disk.

With a tested backup in hand, a risky migration stops being scary. Continue with running migrations on deploy safely.

Questions people ask

How often should I back up Postgres?

Daily is a common minimum for small apps. Decide how much data you can afford to lose and back up at least that often. Point-in-time recovery from your provider narrows the gap.

Does pg_dump lock my database?

It reads from a consistent snapshot and does not block normal reads and writes, though it adds load and can conflict with some schema changes while it runs.

Is a provider snapshot enough?

It is good for quick recovery, but keep an independent copy elsewhere and test restoring both, because snapshots are tied to one account and region.
