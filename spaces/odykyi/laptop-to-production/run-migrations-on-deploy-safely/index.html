From laptop to production

How to run database migrations on deploy safely

On your laptop you run the migration by hand. In production, someone has to run it exactly once, at the right moment.

Run migrations as a separate step that finishes before the new version takes traffic, once per release, not from every app instance as it starts. Keep each migration compatible with both the old and the new code, so a slow rollout or a rollback does not hit a schema one of them cannot read.

Why starting the app is the wrong place

The easy way is putting migrate at the front of the start command. It works with one instance and breaks as soon as you have two. Both instances run the migration at once, and some tools lock against that while others fail or apply a change twice. A restart loop then re-runs it on every crash. A failing migration also takes the app down with it, when the old version could have kept serving.

The better order is: build the image, run the migration in a one-shot job, and only if it succeeds, start the new version. Most platforms have a slot for this, often called a release command or pre-deploy command. Check your host's documentation for the exact name. With Compose you use a separate service that runs to completion, and make the app depend on it with condition: service_completed_successfully.

Production commands, not dev commands

Dev and production commands differ, and mixing them is a common first-deploy bug:

  • Prisma: prisma migrate deploy applies pending migrations in production. prisma migrate dev is for your laptop and can reset data. Never run it against a live database.
  • Drizzle: drizzle-kit migrate applies the generated SQL files. drizzle-kit push syncs a schema directly and is meant for prototyping.
  • Plain SQL tools such as Flyway, dbmate or Atlas apply versioned files the same way.

See Prisma migrations locally and Drizzle migrations locally for the local side.

Keep every migration backward compatible

During a deploy there is a window where old code runs against the new schema, or the other way round. Rolling back has the same problem. The standard pattern is expand, then contract, over two releases:

  1. Expand. Add the new column as nullable, or add the new table. Old code ignores it. Deploy code that writes to both the old and new places.
  2. Backfill. Copy existing data in batches.
  3. Switch reads to the new column in a later release.
  4. Contract. Only after nothing reads the old column, drop it in its own migration.

Renaming a column in one step breaks the old code instantly. Adding a NOT NULL column without a default fails on a table with rows, and on large tables it can lock for a long time, depending on your Postgres version and the change. Test on a copy of production-sized data when a table is big.

The Flisk way

Flisk's own convention is to run migrations in an explicit one-shot resource, with appType: "migrator", and not from the API's start script. Locally that gives you the same order as production: database healthy, migration finished, then the API. The setup is described in run database migrations in local dev with a migrator.

When you move to a host, remember what the exporter covers. flisk export render writes services and their environment names, and it does not write the database, secret values or the migration step. You add the migration as a pre-deploy command or job on the host yourself. flisk export compose works differently for bring-your-own resources: a dependency declared with restart: "no" becomes service_completed_successfully, so a migration job finishes before the API starts. To run a single command against a running local service, such as a manual migration check, use flisk run <service> -- <command>.

Before you run one on production

  • Take a backup first. See back up Postgres before launch.
  • Read the generated SQL. An ORM may drop and recreate a column when you only meant to rename it.
  • Keep migrations small. One logical change per migration is easier to reason about and to revert.
  • Do not edit applied migrations. Add a new one. Tools compare checksums and will refuse or drift.
  • Set a lock timeout for risky changes, so a migration fails fast instead of blocking every query behind it.

When a separate job is overkill

A single-instance hobby app with a tolerance for a short outage can run the migration on start and be fine. Accept that choice knowingly, and move it out the day you add a second instance.

Next, make the rollback side safe too. Rolling back code is easy, rolling back a schema is not, which is the focus of how to roll back a bad deploy.

Questions people ask

Should migrations run automatically on every deploy?

Yes for most apps, as a separate step before the new version starts. Automatic is fine as long as it runs once, fails the deploy on error, and the migration is backward compatible.

Can I roll back a migration?

Down migrations exist in some tools but are risky on data. Prefer forward-only changes that stay compatible with the previous code, and restore from a backup only as a last resort.

What if two instances start at the same time?

They may both try to migrate. Run the migration in a single job instead, or use a tool that takes a database lock before applying changes.
