How to roll back a bad deploy quickly and safely

The deploy is live, the error rate is climbing, and you have a few minutes. This is what to do, and what to prepare so those minutes are enough.

To roll back a bad deploy, redeploy the last known good version of the code, which is the previous image tag or the previous release in your platform. Do it first and investigate afterwards. The code is the easy part. The hard part is the database: a migration that already ran may not be compatible with the old code, so you plan for that before the deploy, not during the incident.

Decide quickly

Set a rule in advance, for example: if a smoke test fails or the error rate stays above a threshold for five minutes after a deploy, roll back. Do not debug in production while users are failing. Reverting buys time, and the broken version is still in git for a calm investigation. A fix forward is reasonable only when the fix is a one-line change that you can ship in less time than a rollback.

Make rolling back cheap

  • Tag images by commit. Build once, tag as myapp:3f9c2b1, and deploy that exact image. Never deploy latest, because you cannot say what it was an hour ago. The same image you tested is the one you ship.
  • Keep the last few images in the registry. A cleanup rule that deletes everything but latest removes your way back.
  • Use the platform's history. Many hosts keep earlier deploys and let you redeploy one from the dashboard or a command. Learn where that button is before you need it.
  • Keep configuration in the same history. A rollback of code with today's environment variables may still be broken. Note which variables changed in a release.

On a self-managed server with Compose, rolling back is a tag change and a restart of one service:

# in .env or the compose file: IMAGE_TAG=3f9c2b1
docker compose pull api
docker compose up -d api
docker compose ps

A standalone Compose file that points at pinned image tags, as produced by flisk export compose from services that declare an image, makes this a one-line change. The exporter needs the images to exist, so pin a version in the registry. See deploy a standalone Compose file to a VPS.

The database is the catch

Code rolls back instantly. Data does not. Three cases:

  1. No schema change in the release. Roll back the code and you are done.
  2. Additive schema change (a new nullable column or table). The old code ignores it, so rolling back the code is safe and the extra column can stay.
  3. Destructive or incompatible change (a dropped or renamed column, a changed type). The old code now fails. This is why you split such changes across releases. See run migrations on deploy safely.

A down migration can undo a schema change, but it cannot bring back data a migration already dropped. Restoring from a backup loses everything written since the backup. Keep that as the last resort, and make sure you have tried one, as in back up Postgres before launch.

Reduce the blast radius

  • Feature flags. Ship risky behaviour behind a flag that defaults to off, then turn it on for a few users. Turning off a flag is faster than any rollback and needs no deploy.
  • Gradual rollouts. If your platform supports a canary or a percentage of traffic, send a small share to the new version first. Otherwise deploy at a quiet hour.
  • Automated checks. A smoke test after every deploy tells you within a minute that you need to roll back.

Write the plan down

Keep three lines in your README or runbook: how to see which version is live, the exact command or button to redeploy the previous one, and who can decide. Try it once on a quiet day. A rollback you have never practised often fails on a detail, such as a registry login that expired or an image that was cleaned up.

If you use Flisk locally, flisk config verify and the same service.json files describe what the services need, which makes it easier to compare what changed between two releases. It does not roll anything back on a host, since the exporters write files and never deploy.

After the rollback

  • Confirm recovery with the smoke test and your error dashboard, not only a green status.
  • Write down what happened while it is fresh: the trigger, the time to detect, the time to recover.
  • Reproduce the failure locally or in staging before you ship the fix. See a staging environment on a small budget.

The best next step is to rehearse: deploy a harmless change, roll it back, and time it.

Questions people ask

Should I roll back or fix forward?

Roll back by default, because it is fast and predictable. Fix forward only when the fix is tiny, tested, and quicker than a rollback.

Can I roll back a database migration?

Only if you wrote a down migration and no data was lost by the change. The safer approach is additive migrations that old and new code both work with, with a backup as the last resort.

Why not deploy the latest tag?

Because latest points to a different image over time, so you cannot redeploy what ran yesterday. Tag every image with a commit SHA or version.
