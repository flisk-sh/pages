Uploaded files disappear after a deploy: ephemeral disks

It worked for days, then a deploy ran and every uploaded image was gone. The disk was never yours to keep.

Files vanish after a deploy because most container hosts give each release a fresh filesystem. Whatever your app wrote to local disk lives only as long as that container. Store uploads and generated data in object storage or a database, or attach a real persistent volume if your host offers one.

What "ephemeral" means

A container starts from an image. Files the app writes go into a thin layer on top of that image. When the container is replaced, because of a deploy, a crash, a scale event or a move to another machine, the layer is discarded and the next container starts from the clean image. Platforms such as Render, Fly.io, Heroku-style hosts and Cloud Run document this behaviour for their default storage, so check your own host's page on disk persistence.

On your laptop you never see this. You run the same container for weeks, or you mount a project folder into it, and the files seem permanent. The first deploy is where the assumption breaks. A second symptom comes from running more than one instance: a file uploaded through instance A does not exist on instance B, so downloads fail randomly.

Your options

OptionGood forWatch out for
Object storage (S3, Cloudflare R2, MinIO, GCS)User uploads, images, exports, backupsNeeds credentials, a bucket policy and a public or signed URL plan
The databaseSmall blobs, settings, anything relationalLarge files bloat the database and its backups
A persistent volume or disk from the hostA single instance that needs a real filesystem, such as SQLite or a search indexOften limited to one instance, tied to one region, may cost extra, and still needs backups
A named Docker volume on a plain VPSSelf-managed serversLives on that one server. Back it up, and know it disappears if the server does

For most web apps the answer is object storage. It survives deploys, works with any number of instances, and lets the browser upload directly with a signed URL so the file never touches your server.

Develop against the same shape locally

The trick is to use object storage locally too, so you meet the problem on your laptop and not in production. MinIO runs an S3-compatible server in one container, and the AWS SDK talks to it when you point the endpoint at it. Read how to run MinIO locally and how to point the AWS SDK at local S3. Read the endpoint, bucket and keys from environment variables, as in:

const s3 = new S3Client({
  region: process.env.S3_REGION ?? "auto",
  endpoint: process.env.S3_ENDPOINT,      // local MinIO URL, or the provider's endpoint
  forcePathStyle: process.env.S3_PATH_STYLE === "true",
  credentials: {
    accessKeyId: process.env.S3_ACCESS_KEY_ID,
    secretAccessKey: process.env.S3_SECRET_ACCESS_KEY,
  },
});

In production you change the values, not the code. Keep the keys out of git. Only the names belong in your config files.

Find what writes to disk

Before you deploy, look for writes to the local filesystem. They hide in upload handlers, report generators, image resizers, caches and logs. A quick way is to run the production image with a read-only root filesystem and a small writable temp area:

docker run --rm --read-only --tmpfs /tmp -p 8080:8080 myapp:test

Anything that writes elsewhere fails with a permission error, which tells you exactly which code paths need a new home. Temporary files in /tmp are fine as long as nothing depends on them after the request ends.

Pitfalls

  • SQLite in a container. It is a file. Without a persistent volume it resets on each deploy. It also does not suit several instances.
  • Logs in files. Write to stdout and stderr so the platform keeps them. See limiting container log size for the local side.
  • Public buckets by accident. Make uploads private and hand out short-lived signed URLs unless the files are truly public.
  • Forgetting the backup. Object storage durability is not a backup against deletion by your own code. Turn on versioning or keep a copy where your provider supports it.

Data that matters needs a way back. Pair this change with a database backup and restore test, so both the files and the rows are covered.

Questions people ask

Can I use a Docker volume on a managed platform?

Not in the Compose sense. Managed platforms usually offer their own persistent disk product, often tied to one instance. Check your host's documentation and pricing, or use object storage.

Do cache files matter?

Not if you can rebuild them. A cache on local disk is fine, as long as the app works when it is empty after a deploy.

Why do my uploads work in staging but not production?

Check how many instances run. With two or more, a file saved by one instance is not on the other. Move uploads to shared storage.
