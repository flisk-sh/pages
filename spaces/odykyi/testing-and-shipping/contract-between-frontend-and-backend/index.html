Test the real stack, then hand it off

How to keep a frontend and backend API contract in sync

The frontend works on your machine, then the backend renames a field. A contract is how you find out before your users do.

To keep a frontend and a backend in sync, give the API one written contract (usually an OpenAPI schema or shared TypeScript types), generate the client types from it so a change shows up as a compile error, and add at least one automated check that runs the real backend against that contract. Hoping both sides remember to update together does not scale past one person.

What "the contract" actually is

A contract is the part of the API a consumer depends on: paths, methods, status codes, field names and types, which fields are optional, error shapes, auth headers. Two kinds of drift cause nearly all incidents. The backend changes something the frontend relied on (rename, removed field, new required field). Or the frontend sends something the backend never accepted and the gap went unnoticed because both sides were tested only against their own mocks.

Four ways to enforce it

  1. Shared types in a monorepo. Put request and response types in a package both sides import. A rename breaks the compile on both sides in the same pull request. It is the cheapest option and only works when both ends are TypeScript in one repository.
  2. A schema as the source of truth. The backend produces an OpenAPI document (from code annotations or by hand). The frontend generates types and a client from it, for example with openapi-typescript. CI regenerates the types and fails if the committed output differs, and a diff tool such as oasdiff can flag breaking changes between two versions of the schema.
  3. Consumer-driven contract tests. The frontend records the requests it makes and the responses it needs, and the backend verifies those recordings in its own build (Pact is the best-known tool). It shines with many consumers, such as mobile apps you cannot update instantly.
  4. Tests against the running provider. Start the real backend and check it against its schema. A tool such as Schemathesis reads an OpenAPI document and generates requests, reporting responses that violate the schema or crash the server.

The options stack. A reasonable small-team setup is option 2 plus a smoke version of option 4 in CI.

What Flisk contributes

It helps with the address, not the payload. For a frontend, Flisk's generator can write env.ts, api-client.ts and api-index.ts into the service's .autogenerated/ folder. The documented purpose is a preconfigured client and an API URL built from the same hostnames the gateway routes, so the frontend never holds a copy-pasted address that can go stale. Flisk also keeps dependsOn so the API starts before the site that calls it, and flisk config verify reports when a generated file no longer matches its manifest.

It does not read your request and response types, generate an OpenAPI schema, or run contract tests. Do not infer a payload contract from the existence of a generated client: the file is about where to call, not what to send.

Run the contract check against the real stack

Option 4 needs a running backend, which is what a local stack gives you. Expose the schema from the API (most frameworks can serve /openapi.json), start the stack and point the tool at it:

flisk up --wait --wait-timeout 900
schemathesis run http://api.my-shop.localhost/api/orders/openapi.json
flisk down

Use the URL that flisk networks --raw prints for your API; the path above is only an example. Adjust the checks and add auth headers as the tool's documentation describes. Run it against a stack seeded with test data, never against shared or production data: these tools send unusual input on purpose.

For the frontend side, generate types in a script and make CI verify they are current:

npx openapi-typescript http://api.my-shop.localhost/api/orders/openapi.json -o src/api-types.ts
git diff --exit-code src/api-types.ts

If the backend renamed a field, the diff fails in CI, and the compile fails wherever the old field was used.

Pitfalls

  • A schema nobody enforces is documentation. It must be generated from the code, or checked against it, otherwise it rots.
  • Error responses are part of the contract. Describe 400, 401, 404 and 409 shapes, not just 200.
  • Additive changes are safe, removals are not. Add fields, deprecate before removing, and version the API when a break is unavoidable.
  • Mocks drift. If the frontend tests use a mock server, generate its responses from the schema rather than writing them by hand. See mock or run the real service.
  • Do not over-test. You do not need contract tests for an internal admin page with one author. They pay off when two teams or a deploy delay sit between the sides.

To exercise the contract end to end through the UI as well, continue with Playwright against a local stack.

Questions people ask

Does Flisk check that my frontend and backend agree on request and response shapes?

No. Flisk generates the address the frontend uses (an API URL and a small client built from the same hostnames the gateway routes), and flisk config verify checks that generated files match the manifests. It does not read your payload types or run contract tests. Use a schema or a contract test tool for that.

Is OpenAPI or Pact better?

They answer different questions. A schema such as OpenAPI says what the provider offers, and generators and validators can check both sides against it. Consumer-driven contracts such as Pact record what each consumer actually uses, which makes it safe to change what nobody uses. Small teams usually start with a schema.

Where does the contract live in a monorepo?

Next to the backend that owns it, as a generated schema file committed to the repository or published as an artifact, with the frontend generating its types from it. One owner, one source of truth.
