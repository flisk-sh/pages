Test the real stack, then hand it off

Mock or run the real service in tests? A practical rule

Mocks are fast and lie. Real services are honest and slow. The useful question is which dependencies deserve which.

Run the real service for anything you own and anything cheap to run (your database, your queue, your own APIs). Mock or fake the things you do not control, cannot run locally, or that cost money or send real messages (payment providers, email delivery, SMS, third-party SaaS). Everything else is a judgment call, and the judgment gets easier once you list what each choice costs you.

What each choice costs

DependencyMock it whenRun it for real when
Your databaseThe code under test only needs a value from a repository interfaceThe test touches queries, constraints, transactions or migrations
Your queue or cacheYou test pure business logicYou test ordering, retries, expiry or serialization
Your other servicesThe boundary is covered by a contract testThe test crosses the boundary on purpose
Payment, email, SMSAlmost always: use a fake or the vendor test modeA scheduled smoke test against the vendor sandbox
A slow or flaky external APIAlways in the main suiteIn a separate, non-blocking job

The failure of each extreme

Mock everything and your suite is green while production breaks: the mock returns what you assumed, not what the service does. Run everything for real and the suite becomes slow, needs credentials, and fails when a vendor has a bad afternoon. People then stop trusting it, which is worse than having fewer tests.

A good split: real for your own infrastructure, a fake server for third parties, and a small contract or smoke layer that checks the fake still resembles the real thing. The contract side is covered in contract between frontend and backend.

Fakes beat in-code mocks for HTTP dependencies

An in-code mock (patching fetch or an SDK method) tests that you called the SDK the way you wrote it. A fake HTTP server tests the full path: serialization, headers, timeouts, retries, and error handling when the response is a 500. Because a fake is a separate process, the same fake also serves your manual testing and your browser tests.

Many third-party tools ship a ready-made local fake or catcher. Mailpit, for example, accepts SMTP on port 1025 and shows the messages in a web UI on port 8025, so you can test email without sending any. For a payment provider, use its test mode, or write a 50-line server that returns the responses you need, including the failures.

Run a fake next to your services with Flisk

With Flisk a fake is a bring-your-own resource: an image, a port and a health path. This creates one for Mailpit:

flisk resource mail --type bring-your-own --stack shop \
  --image axllent/mailpit --health-path /livez --yes

flisk resource assigns a port in the 4000 to 5999 range and writes services/shop/mail/service.json. Mailpit listens on 8025 for its UI and API, so edit the manifest to match, and publish the SMTP port with extraPorts:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "mail",
  "appType": "bring-your-own",
  "stack": "shop",
  "port": 8025,
  "healthCheckPath": "/livez",
  "image": "axllent/mailpit",
  "extraPorts": [{ "port": 1025 }]
}

Run flisk config verify afterwards; it checks the manifest and that the generated files are in sync. An extraPorts entry is published on 127.0.0.1 only unless you set "bind": "0.0.0.0", which is what you want for a test fake. Your API then uses mail as the SMTP host and 1025 as the port, taken from environment variables so the same code runs in production with the real host. Add "dependsOn": ["mail"] to the services that need it so they start after it.

The healthCheckPath must be a plain path without characters such as underscores: flisk config verify rejected /__admin/health when we tried it. If your fake only has a path like that, use a different readiness signal or put a tiny proxy in front.

Pitfalls

  • Fakes drift. A fake that nobody checks becomes fiction. Re-record responses from the real service now and then, or run a nightly test against the vendor sandbox.
  • Do not hard-code fake URLs. Read base URLs from environment variables, so production and tests differ only in configuration. See env var names, not values.
  • A shared fake keeps state. Reset it between tests, or give each test its own tenant or inbox.
  • Not every service runs locally. A managed cloud database with a vendor-specific feature may have no faithful local twin. Say so in the test name and keep that test separate.

Next, wire the choice into a full run: integration tests against the real stack shows the start, wait, test and stop script.

Questions people ask

Should I mock my own database in tests?

For tests that check queries, constraints or migrations, no. Run the real database engine you use in production, in a container. An in-memory fake or an ORM mock cannot catch a missing index, a type mismatch or a constraint violation. Mocking is fine for a pure unit test of code that only needs a value from a repository.

How do I test code that calls Stripe, an email provider or another paid API?

Use the provider's own test mode where it exists, or put a fake server you control in front of it and point the base URL at the fake through an environment variable. Keep a small number of tests that hit the real sandbox, run on a schedule, so you notice when the provider changes.

Can Flisk run a fake service next to my real ones?

Yes. A fake is just another container. Add it as a bring-your-own resource with an image, give it a port, and let your services call it by its name. Flisk does not generate the fake for you.
