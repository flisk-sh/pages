Test the real stack, then hand it off

How to run Playwright tests against a local multi-service stack

Browser tests are only as stable as the stack under them. Start the whole thing first, give Playwright one base URL, and keep the data predictable.

To run Playwright against a local stack, start all services and wait for their health checks, read the frontend URL from your stack tool instead of hard-coding it, pass it to Playwright as baseURL, and make the test data deterministic before the first test starts. Playwright itself is the easy part. The stack under it decides whether the suite is stable.

Start the stack outside Playwright

Playwright has a webServer option that starts a command and waits for a URL. It fits one dev server that keeps running. A multi-service stack is different: the command that starts it often exits once everything is up. Using flisk up --wait or docker compose up --wait as the webServer command would look like a server that died, so start the stack in a script and run Playwright after it:

#!/usr/bin/env bash
set -euo pipefail
trap 'flisk down || true' EXIT

flisk up --wait --wait-timeout 900
export WEB_URL="http://app.my-shop.localhost/shop-web"
npx playwright test

With Compose, replace the first command with docker compose up -d --wait and the trap with docker compose down -v. The principle is the same: block until healthy, then test, then clean up whatever happens.

Give Playwright one base URL

Read the URL from an environment variable so the same config works on your laptop, in CI and against a shared environment:

// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL: process.env.WEB_URL ?? 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
});

When the stack runs under Flisk with the gateway, each service has a hostname such as app.my-shop.localhost. Ask Flisk for the real URLs with flisk networks --raw, because the gateway moves to another port when port 80 is taken. If the stack is only local processes (a service with a command in its service.json), the URL is http://localhost:<port> as printed by flisk up. Chromium resolves *.localhost names to your machine without an /etc/hosts entry; check other browsers before relying on it.

Careful with relative paths: a baseURL that includes a path prefix, such as /shop-web, changes how page.goto('/login') resolves. Put the full path in the goto calls, or make the frontend serve from / on its own hostname.

Make the data predictable

Browser tests that depend on whatever is in the database are the number one source of flaky suites. Pick one of these and stick to it:

  • Seed before the suite. Run a seed command once in globalSetup or in the script. With Flisk: flisk run orders-api -- bun run seed.
  • Create what you need through the API in a fixture, with unique values, and delete it afterwards.
  • Log in once and reuse the session. Use Playwright's storageState so only one test pays for the login flow.

More on resetting data in reset a local database.

Things that break browser tests on a multi-service stack

  • CORS. The frontend on app.my-shop.localhost calls an API on a different hostname, so the API must allow that origin. Add an explicit rule for the frontend origin in your API.
  • Cookies. A cookie set for one host is not sent to another. Test the login flow once end to end, and check SameSite and Secure attributes if the session is lost between pages.
  • Readiness. The frontend can be healthy while the API is still running migrations. Wait on the API too; with --wait every service must be healthy before the command returns.
  • Slow first load. A dev server may compile on the first request. Either test the production build or add one warm-up request before the suite.
  • Browsers in CI. Install them with npx playwright install --with-deps chromium on the runner.

Collect evidence when it fails

A browser failure message rarely names the real cause. Keep the Playwright trace, and also the server side: flisk logs --service orders-api --since 5m prints recent logs for one service. In CI, upload both as artifacts. The workflow in run the stack in GitHub Actions has a diagnostics step you can copy.

When not to use real browser tests

Do not test every validation rule through a browser. Cover logic with unit and API tests, and use Playwright for the handful of journeys that matter: sign in, the main purchase or save flow, and one failure path. They are the slowest layer, so keep that layer thin.

If the stack does not start reliably in CI yet, fix that first with integration tests against the real stack, then add the browser layer on top.

Questions people ask

Should I use Playwright's webServer option to start the stack?

It is built for one long-running dev server. A multi-service stack is easier to start in a separate step, because a command like flisk up --wait or docker compose up --wait exits when the stack is ready, which does not fit a process that webServer expects to keep running. Start the stack in your script or CI step, then run npx playwright test.

Why do my browser tests fail with CORS errors on a local stack?

When the frontend and API run on different origins, the browser enforces CORS even on localhost. The API must allow the frontend origin. Check the response headers in the trace or network log before debugging the test.

Does Flisk generate a Playwright config?

There is an optional playwright feature that writes a generated configuration, but the project documentation lists Playwright configuration among the features that need a license key. You do not need it: a normal playwright.config.ts with a baseURL from an environment variable works with any stack.
