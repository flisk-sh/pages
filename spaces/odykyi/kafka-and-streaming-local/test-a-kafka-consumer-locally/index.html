Kafka and streaming locally

How to test a Kafka consumer on your machine

Keep the handler separate, point the consumer at a broker on your machine, and feed it messages from the terminal.

Keep the message handling in a plain function, run the consumer against a local broker, and send it test messages from the broker container's own console producer. You see the effect in seconds and you never touch a shared cluster.

Split the handler from the consumer

Most consumer bugs are logic bugs, not Kafka bugs. If the logic lives inside the eachMessage callback, the only way to test it is with a broker. Put it in its own file so a unit test can call it directly:

// handler.js
export async function handleOrder(order, { save }) {
  if (order.id === undefined) throw new Error("order without id");
  await save({ id: order.id, total: order.total ?? 0 });
}

The consumer file only wires Kafka to that function. This one uses kafkajs:

// consumer.js
import { Kafka } from "kafkajs";
import { handleOrder } from "./handler.js";

const kafka = new Kafka({
  clientId: "orders-consumer",
  brokers: (process.env.KAFKA_BROKERS || "localhost:29092").split(","),
});
const consumer = kafka.consumer({ groupId: "orders-consumer" });

await consumer.connect();
await consumer.subscribe({ topic: process.env.KAFKA_TOPIC || "orders", fromBeginning: true });
await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    const order = JSON.parse(message.value.toString());
    await handleOrder(order, { save: async (o) => console.log("saved", o) });
    console.log(`handled ${topic}[${partition}]@${message.offset}`);
  },
});

fromBeginning: true only matters the first time a group id is seen. After that the group resumes from its committed offset, which is the usual surprise when a new test message "does not arrive". See replaying messages by resetting offsets.

Which address does the consumer use

This depends on where the consumer runs, and it is the same listener question as in the advertised listeners article:

  • On your machine (a plain node consumer.js): use the external listener, localhost:29092 in the broker from the KRaft article.
  • In a container on the same network: use broker:9092.

Reading the address from an environment variable lets the same code run in both places.

Send it test messages

The broker image already contains a console producer, so you need nothing extra installed. Without Flisk, ask Docker to run it in the broker's container. With Flisk, flisk run runs a command inside a service:

echo '{"id":"o-1","total":42}' | flisk run broker -- \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders

Inside the broker container the broker is reachable at localhost:9092, because that is the internal listener. A producer with --property parse.key=true --property key.separator=: reads lines like o-1:{"id":"o-1"} and sends the part before the colon as the key. If your terminal does not forward standard input through flisk run, wrap the command in sh -c and use a here-string inside it. I checked that the command exists in CLI 1.4.57 but did not pipe data through it on a running stack.

Run the consumer with Flisk

A consumer is a normal backend with no port that anyone calls. Two ways to run it:

  1. As a local process. Give the resource a command and Flisk runs it on your machine with your toolchain, with live reload. Set KAFKA_BROKERS=localhost:29092 and turn the health check off, because a consumer serves no HTTP. See run services without Docker.
  2. As a container. Build it like any other service and set KAFKA_BROKERS=broker:9092. Add "dependsOn": ["topics"] so it starts after the topics job.
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "consumer",
  "appType": "worker",
  "stack": "streaming",
  "port": 4002,
  "command": "node --watch consumer.js",
  "toolchain": "node@22",
  "healthCheck": false,
  "env": { "KAFKA_BROKERS": "localhost:29092", "KAFKA_TOPIC": "orders" }
}

Edit and save consumer.js, the process restarts, and the group rejoins. Check the field names against flisk config verify in your project, since I validated the other manifests in this series but not this exact combination against a running broker.

Watch it work

flisk logs --service consumer

Open the Kafka UI and look at the consumer group. Lag of 0 means the consumer has read everything. A lag that grows means it is stuck or slower than the producer.

Pitfalls

  • A rebalance on every restart. Each restart of a live-reloading process leaves and rejoins the group. The broker waits for the session to time out before it reassigns partitions, so the first message after a restart can be slow. A short session.timeout.ms in development helps.
  • Poison messages. A handler that throws on one message stalls that partition when it retries forever. Decide what happens: skip it, or publish it to a dead-letter topic such as orders.dlq.
  • Offsets committed too early. If you commit before the work is done, a crash loses the message. kafkajs commits after eachMessage resolves by default, which is the safe order.

To prove the same code in CI without sharing a broker between tests, read integration tests against a local Kafka broker.

Questions people ask

Why does my consumer not see a message I just sent?

The group has a committed offset from an earlier run, and fromBeginning only applies to a new group id. Reset the offsets or use a new group id.

Which broker address should a local consumer use?

Use the external listener, for example localhost:29092, when the consumer runs on your machine. Use the internal address, for example broker:9092, when it runs in a container on the same network.

How do I send a test message without installing anything?

Run the console producer that ships in the broker image, in the broker container. flisk run broker -- runs a command inside the service.
