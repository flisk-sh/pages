Kafka and streaming locally

How to create Kafka topics automatically on startup

Auto-created topics have one partition and no settings. A short init job creates the real ones before any service connects.

Add a one-shot container that runs kafka-topics.sh --create --if-not-exists after the broker is healthy, and make your services wait for it. Then every developer and every CI run gets the same topics with the same partition counts, and nobody has to remember a manual step.

Why not rely on auto-creation

A Kafka broker creates a topic the first time a client produces to it or subscribes to it, unless auto.create.topics.enable is false. The default is true. That is convenient and wrong for development in three ways:

  • You get the broker's default partition count (1), so ordering and parallelism bugs hide until production, where the topic has more partitions.
  • A typo in a topic name silently creates a new empty topic. The consumer then waits for messages that were sent somewhere else.
  • Per-topic settings such as retention and compaction cannot be set at creation time this way.

Production clusters often turn auto-creation off, so creating topics explicitly locally also matches how they run.

The plain command

/opt/kafka/bin/kafka-topics.sh --bootstrap-server broker:9092 \
  --create --if-not-exists --topic orders \
  --partitions 3 --replication-factor 1

--if-not-exists makes the command safe to run again: it exits 0 when the topic exists. Replication factor is 1 because there is one broker. Configuration goes in repeated --config flags, for example --config retention.ms=604800000 for seven days. Partitions can be increased later with --alter but never decreased, and increasing them changes which partition a given key lands on (see keys, partitions and message order).

Put the topics in a script

Keep the list in a file in the repository so reviewers see topic changes. Save this as services/streaming/topics/create-topics.sh:

set -e
KT="/opt/kafka/bin/kafka-topics.sh --bootstrap-server broker:9092"

$KT --create --if-not-exists --topic orders      --partitions 3 --replication-factor 1
$KT --create --if-not-exists --topic orders.dlq  --partitions 1 --replication-factor 1 \
    --config retention.ms=604800000
$KT --list

A file avoids a quoting problem: Compose reads a lone $ in a manifest, so inline commands need $$, while a script mounted as a file keeps its variables as written.

Run it as a Flisk one-shot job

Add a second bring-your-own resource using the same image as the broker, so the Kafka scripts are already inside it. The key setting is "restart": "no". A container is restarted by default, and a job that exits cleanly would otherwise start again forever. You can create the file with the CLI:

flisk resource topics --type bring-your-own --image apache/kafka:4.2.2 \
  --stack streaming --restart no --no-proxy --yes

Then edit services/streaming/topics/service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "topics",
  "appType": "bring-your-own",
  "stack": "streaming",
  "port": 4001,
  "exposeViaProxy": false,
  "image": "apache/kafka:4.2.2",
  "restart": "no",
  "dependsOn": [{ "name": "broker", "condition": "service_healthy" }],
  "volumes": [{ "source": "./create-topics.sh", "target": "/create-topics.sh", "readOnly": true }],
  "container": {
    "entrypoint": ["sh", "-c"],
    "command": ["sh /create-topics.sh"]
  }
}

Here container.entrypoint replaces the image's entrypoint and container.command is the argument list, so the container runs sh -c "sh /create-topics.sh". The bind mount path starts with ./, so it is relative to the folder that holds this service.json. The broker side is in the KRaft article.

Any service that should not start before the topics exist lists the job:

"dependsOn": ["topics"]

The Flisk docs say a service that lists a one-shot job in dependsOn starts only after the job exited 0, and that when the job fails the services after it are not started. The same file also runs through flisk config verify, which accepted both manifests in CLI 1.4.57. I did not start the stack, so run flisk logs --service topics after flisk up streaming to see the job's output.

Pitfalls

  • Healthy is not the same as started. Use the service_healthy condition, with the broker's health check, so the job does not run before the broker accepts connections. See Compose depends_on and healthchecks.
  • Edits do not reshape existing topics. --if-not-exists skips a topic that already exists, so changing the partition count in the script changes nothing on a broker whose volume remembers the old topic. Use --alter --partitions or reset the volume.
  • Do not put topic creation in the app's start script. It is the same mistake as running database migrations from the API's entrypoint. A separate job runs once, and restarting the app does not repeat it.
  • The job shows as exited. That is normal for a one-shot container.

Topics exist now, so you can look at what lands in them. Kafka UI for local development adds a browser view, and testing a Kafka consumer locally puts a consumer on them.

Questions people ask

Is it safe to run the topic creation job on every start?

Yes, if you use --if-not-exists. The command exits 0 when the topic exists and changes nothing.

Why not let Kafka auto-create topics?

You get the default partition count of 1 and no settings, and a mistyped topic name silently creates an empty topic. Explicit creation also matches production clusters that disable auto-creation.

How do I change the partition count of an existing topic?

Run kafka-topics.sh --alter --topic NAME --partitions N with a larger N. You cannot reduce partitions, and more partitions change which partition each key maps to.
