Kafka and streaming locally

Kafka keys, partitions and message order, tested locally

Order is per partition and the key picks the partition. Three short experiments on a local topic make that concrete.

Kafka keeps order only inside one partition, and the key decides the partition. Messages with the same key go to the same partition and are read in the order they were written. Messages with different keys, or no key, can be read in any order relative to each other. You can see this in a minute on a local broker with a topic of three partitions.

The two rules

  1. Order is per partition. A topic with one partition is totally ordered. A topic with six partitions is six ordered logs that a consumer reads in parallel.
  2. The key picks the partition. The producer hashes the key and takes it modulo the partition count. Same key, same partition. With no key, the producer spreads messages across partitions, so there is no ordering to rely on.

The practical rule: use the id of the thing whose events must stay in order, such as the order id or the user id, as the key.

Set up a topic with three partitions

Create it explicitly. An auto-created topic has one partition and hides everything below. The topics job line is:

kafka-topics.sh --bootstrap-server broker:9092 --create --if-not-exists \
  --topic orders --partitions 3 --replication-factor 1

Experiment 1: keyed messages

Send six messages with two keys, using the console producer with a key separator:

printf 'a:1\nb:1\na:2\nb:2\na:3\nb:3\n' | flisk run broker -- \
  /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic orders --property parse.key=true --property key.separator=:

Read them back with the partition and offset shown, as in reading Kafka messages from the command line:

flisk run broker -- /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic orders --from-beginning --timeout-ms 5000 \
  --property print.key=true --property print.partition=true --property print.offset=true

Expect every a message on one partition with offsets 0, 1, 2, and every b message on one partition too. The two keys may or may not share a partition, because hashing two keys into three partitions can collide. The lines from different partitions can be interleaved in the output, because the console consumer reads all partitions at once. Within one partition the values are in the order you sent them.

Experiment 2: no key

Send the same six values without a key. The producer now spreads them over the partitions (the exact pattern depends on the client version, since recent clients batch to one partition for a while before switching). Read them back and you will see partitions, each in order, but the sequence 1 to 6 is no longer preserved across them. Code that assumes the second message is processed after the first breaks here, and only under load, which is why it survives local testing with a single partition.

Experiment 3: change the partition count

Add partitions to the topic:

flisk run broker -- /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 6

Now send keyed messages again. The hash is taken modulo 6, so a key that used to land on partition 1 may land elsewhere. New messages for key a can end up on a different partition from the old ones, and a consumer can read the new one before it has finished the old one. Partitions can only grow, never shrink, so choose the count early. See replaying messages if you need to rebuild after such a change.

Consumers and partitions

Within one consumer group, each partition is read by one member at a time. Three partitions means up to three useful consumers. A fourth sits idle. If you run the consumer from the local consumer article twice with the same group id, the broker splits the partitions between them. This is the cheapest way to see a rebalance happen, and a UI shows which member holds which partition.

Pitfalls

  • One partition hides bugs. A dev topic with one partition always looks ordered. Create the same partition count as production.
  • Hot keys. One key with most of the traffic puts everything on one partition. Pick a key that spreads.
  • Null keys on compacted topics. Compaction needs keys. Messages without one cannot be compacted.
  • Cross-topic order. Nothing orders messages between topics. If a handler needs "created" before "paid", put them in one topic with one key.

I ran none of these commands against a live broker while writing this page. The behaviour described is Kafka's documented partitioning, and the exact partition numbers you see will differ.

Questions people ask

Does Kafka guarantee message order?

Only within one partition. Messages with the same key go to the same partition and stay in order. Across partitions or topics there is no order guarantee.

What happens if I add partitions to a topic?

New messages hash to a different partition than before, because the key hash is taken modulo the new count. Old messages stay where they are. You cannot reduce the count.

Why does my local topic always look ordered?

It probably has one partition, which is the default for an auto-created topic. Create the topic with the same partition count as production.
