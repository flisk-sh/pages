Redpanda or Kafka for local development: which one to run

Both speak the Kafka protocol. The practical question is which one matches production and fits in your laptop's memory.

Run the one your production system uses. If you deploy on Apache Kafka, Amazon MSK or Confluent, use apache/kafka locally, because the closest match hides the fewest surprises. If you have no fixed target, or your laptop is short on memory, Redpanda is a reasonable choice: it speaks the Kafka protocol, starts as one binary and has no JVM.

Compatibility is the part to be careful about. Producers, consumers, consumer groups and transactions work through the standard client libraries on both. Edge cases can differ: specific broker settings, Kafka Connect plugins, tools that read broker internals or JMX metrics. If your code depends on one of those, test it against the broker you deploy.

Run Kafka

The Kafka setup, with two listeners so that containers and your laptop both connect, is in How to run Kafka locally without ZooKeeper. It is a bring-your-own container: Flisk's built-in queue frameworks are NATS and RabbitMQ, not Kafka.

Run Redpanda the same way

Create the resource, then replace the generated file. flisk resource --help lists --image as the flag that skips the Dockerfile for bring-your-own resources:

flisk resource broker --type bring-your-own \
  --image docker.redpanda.com/redpandadata/redpanda:v25.3.18 \
  --stack streaming --no-proxy --yes

Then set services/streaming/broker/service.json to this. The image tag is an example, pick a current one from the Redpanda registry:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "broker",
  "appType": "bring-your-own",
  "stack": "streaming",
  "port": 9092,
  "exposeViaProxy": false,
  "image": "docker.redpanda.com/redpandadata/redpanda:v25.3.18",
  "container": {
    "command": ["redpanda", "start", "--mode", "dev-container", "--smp", "1", "--memory", "1G",
      "--kafka-addr", "internal://0.0.0.0:9092,external://0.0.0.0:19092",
      "--advertise-kafka-addr", "internal://broker:9092,external://127.0.0.1:19092"]
  },
  "healthCheck": { "command": ["rpk", "cluster", "health", "--exit-when-healthy"], "startPeriod": 20 },
  "extraPorts": [{ "port": 19092 }],
  "volumes": [{ "source": "broker-data", "target": "/var/lib/redpanda/data" }],
  "provides": { "KAFKA_BROKERS": "broker:9092" }
}

The pattern is the same as for Kafka. container.command replaces the image's default command, so it carries the flags. There are two named Kafka listeners: internal is for other containers at broker:9092 and external is for your machine at 127.0.0.1:19092. extraPorts publishes the external port on loopback only. Services that depend on broker get KAFKA_BROKERS.

flisk config verify
flisk up streaming
flisk run broker -- rpk cluster info

flisk config verify accepted this manifest in CLI 1.4.57. I did not start the container, so if Redpanda rejects a flag for your image version, flisk logs --service broker prints its message. Redpanda's own docs describe the flags, and they change between releases more than Kafka's.

What the client code sees

Nothing, if you did the wiring right. Your service reads KAFKA_BROKERS, which Flisk fills from provides, and connects. It does not know whether broker is Kafka or Redpanda. That is the real benefit of keeping the choice in one committed manifest: swapping the image and the listener flags is a diff in one file, and you can run the same integration tests against both before you decide. If you see differences, they are worth knowing about before production does it for you.

A schema registry is the one place where the choice shows up in your code. Redpanda serves a registry from the same process, on its own port. With Kafka you add a separate registry container. Either way you can still add it later as one more bring-your-own resource, so do not let it decide the broker today.

Picking in practice

  • Same as production wins. A different broker locally is a source of bugs that only appear in staging.
  • Memory. Redpanda lets you cap memory explicitly. Kafka's heap can be cut with KAFKA_HEAP_OPTS. Both run in about a gigabyte, so measure on your machine instead of trusting a rule of thumb. Running many services on one laptop covers how.
  • Tooling. If your team uses kafka-*.sh scripts in runbooks, stay with Kafka. If you like rpk, use Redpanda.
  • Do not mix without reason. Switching brokers between developers produces "works on my machine" reports. Put one choice in the committed service.json.

Both brokers need the same two-listener layout to be reachable from a container and from your laptop. Kafka advertised listeners: fix connection refused explains why.

Questions people ask

Is Redpanda a drop-in replacement for Kafka?

For standard producers, consumers and consumer groups, yes: clients use the Kafka API. Check anything beyond that, such as Connect plugins, broker-specific settings or JMX metrics, against the broker you deploy.

Does Redpanda need ZooKeeper?

No. Redpanda is a single binary with its own Raft-based metadata, so there is nothing to start before it.

Can I use Kafka CLI tools against Redpanda?

Often yes, because they speak the Kafka protocol, but rpk is the supported tool and is already in the Redpanda image.
