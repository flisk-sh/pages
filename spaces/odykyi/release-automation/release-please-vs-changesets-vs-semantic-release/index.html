Release Automation

release-please vs Changesets vs semantic-release

Three ways to automate versions and changelogs, how each decides the next version, and which fits a single package, a monorepo or a team that wants a human gate.

All three tools automate version bumps and changelogs but differ in who decides. semantic-release publishes automatically from commit messages. release-please also reads commit messages but opens a release pull request that a human merges. Changesets asks contributors to add small files that describe the change and its bump, which suits monorepos.

semantic-release

It reads conventional commit messages on the main branch, works out the next version, generates notes, tags and publishes, all in one CI run. There is no review step: merging to main is the release. That is fast and consistent, and it only works when commit messages are reliable, which usually means squash merges with checked titles. It has a plugin system for registries and notes. Choose it when you want zero manual steps and trust your commit discipline.

release-please

It also reads conventional commits, but instead of releasing at once it opens and updates a pull request that contains the version bump and changelog. When someone merges that PR, the tag and release are created. You get a human gate and a visible preview of the next release, which makes it a good middle path. It supports several languages and monorepo setups with its own configuration. The release PR is a place to fix wording before it ships.

Changesets

Contributors run a command that creates a small Markdown file in a .changeset directory saying which packages change and whether the bump is patch, minor or major, plus a note for the changelog.

npx changeset
npx changeset version
npx changeset publish

The bump decision is explicit and made by the author, not inferred from a commit prefix. It handles packages in a monorepo that depend on each other, and bumps dependents when needed. The cost is one extra file per change.

Migration and exit costs

Switching later is possible but not free. Moving from commit-driven tools to Changesets means teaching contributors a new habit. Moving the other way means enforcing commit message format. Keep your release notes and tags in plain git history, and the tool you pick stays replaceable. Try the tool on a test repository first, with a real merge sequence, before you point it at the main project.

How to choose

One package, disciplined commits, no gate wanted: semantic-release. One or a few packages and you want to review the release: release-please. A monorepo with linked packages, or contributors who do not write conventional commits: Changesets. Or skip all three and run a small hand-written workflow, as in publishing from a tag, when you release rarely. Whatever you pick, the versioning rules in semantic versioning still apply, and you should keep a person responsible for reading what is about to ship.

Questions people ask

Which tool needs conventional commits?

semantic-release and release-please read them to decide the version. Changesets does not, because authors write change files instead.

Do I need any of these tools?

No. For a small project that releases rarely, a tag-triggered workflow and generated release notes are enough.
