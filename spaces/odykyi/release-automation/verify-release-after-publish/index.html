How to Verify a Release After You Publish It

Check that the registry serves the new version, that it installs and runs on a clean machine, and retry around registry lag so a good release is not reported as failed.

After publishing, look the version up in the registry, install it in an empty directory and run a basic command. Retry the lookup for a short time, because registries can take seconds to minutes to show a new version. A release that is published but never verified is only a hope.

Check the registry

Ask the registry what it now serves:

npm view your-package version
npm view your-package dist-tags
npm view your-package@1.5.0 dist.tarball

The first shows the latest version, the second shows tags such as latest and next, and the third confirms that this exact version exists. Compare the result to the version you intended, not to a number you typed from memory.

Retry around registry lag

A lookup right after publish can return the old version or a not-found error, because of caches and replication. Do not fail the release on the first try. Poll a bounded number of times:

VERSION=1.5.0
for i in $(seq 1 10); do
  got=$(npm view your-package@"$VERSION" version 2>/dev/null || true)
  [ "$got" = "$VERSION" ] && echo ok && exit 0
  sleep 15
done
echo 'version not visible' >&2
exit 1

Keep the loop bounded, so a real failure still ends the job. Without retries, a correct release can turn the pipeline red and tempt someone to publish twice.

Install and run on a clean machine

The registry listing says nothing about whether the package works. Install it in an empty directory and run a command that touches the real entry point:

cd "$(mktemp -d)"
npm init -y
npm install your-package@"$VERSION"
node -e "require('your-package')"
npx your-package --version

Make the smoke test fail if the printed version differs from the release. Run it on each operating system you support, using a matrix in the workflow.

Verify every channel

Many projects publish to more than one place: a registry, a GitHub release, a container image, a binary download, documentation. Check each channel, not only the first. List the channels in the release checklist and give each a one-line check: a command or a URL that must return the new version. A half finished release is the usual result of verifying only one of them, see repair a half finished release.

Make the check part of the workflow

Add the verification as a final job that depends on the publish job, so a green run means the release is installable and not only uploaded. Give it its own timeout. If it fails, the run should be red and notify someone, because the situation needs a decision: wait, roll back or repair. Treat a failed verification as an incident, not as noise.

Report the result

End the workflow with a clear summary: version, channels checked, links. A job summary or a message to the team channel is enough. A short, public release page helps users too, see generating the changelog. If verification fails after publishing, do not delete the release in a hurry. Decide with the rollback options.

Questions people ask

Why does npm view not show my new version right away?

Registry metadata is cached and replicated, so a new version can take a short time to appear. Retry for a bounded period before treating it as a failure.

What is the smallest useful smoke test?

Install the exact version into an empty directory and run the package's main command with --version or import it. Check that the output matches the release.

Share the release notes

Publish a release report to a public link in one command.

Pages turns an HTML or Markdown file into a free public link. It is public, so do not publish anything private.

npx -y @flisk-sh/pages publish page.html --wait
