Semantic Versioning: How to Choose the Next Version Number

Decide between patch, minor and major from what changed for the people who use your package, and handle pre-releases and 0.x versions without surprises.

Under semantic versioning, a version is MAJOR.MINOR.PATCH. Raise PATCH for bug fixes that change no behaviour users rely on, MINOR for new backward compatible features, and MAJOR when something that worked before can break. Decide from the point of view of the person who depends on you, not from the size of the diff.

The three numbers

  • PATCH (1.4.2 to 1.4.3): a bug fix. Same public behaviour, fewer defects.
  • MINOR (1.4.3 to 1.5.0): new functionality that does not break existing use. New option, new command, new export.
  • MAJOR (1.5.0 to 2.0.0): a change that can break existing users. Removed or renamed API, changed default, dropped runtime version.

When a release has several kinds of change, the highest one wins. One breaking change makes the whole release a major.

What counts as the public API

Write down what you promise. For a library it is the exported functions and types. For a CLI it is commands, flags, exit codes and output that scripts parse. For a service it is endpoints and payloads. Anything you did not promise (internal modules, log wording) can change in a patch. If people depend on it anyway, either document it as supported or accept that changing it will hurt them.

Common breaking changes that people miss: raising the minimum Node or Python version, changing a default value, changing an error type, and tightening validation.

Versions before 1.0.0 and pre-releases

Semver says that anything may change at any time while the major version is 0. Many projects still use minor bumps for breaking changes in 0.x and patch bumps for the rest. Say so in the README so users can pin correctly. Do not stay at 0.x forever, because users cannot tell what is stable.

Pre-releases add a suffix: 2.0.0-rc.1, 2.0.0-beta.3. They sort before the final version. On npm, publish them under a separate tag so they are not installed by default, as described in run a release candidate before publishing.

Let commit messages carry the signal

Conventional Commits ties the message to the bump: fix: is a patch, feat: is a minor, and a ! after the type or a BREAKING CHANGE: footer is a major.

fix: handle empty config file
feat: add --json flag to status
feat!: drop support for Node 16

Tools can read these and propose the next version, see release-please vs changesets vs semantic-release. The convention only works if people follow it, so check it in CI.

A quick decision list

Ask four questions before you choose. Could any existing user's code or script stop working? Then major. Did you add something new that old users can ignore? Then minor. Did you only fix behaviour that was clearly a bug? Then patch. Did you change something only inside the package? Patch or no release at all. If the answer is not clear, choose the higher bump. Users forgive an unneeded minor much more than a surprise break in a patch.

Pitfalls

A version is permanent on most registries. You cannot republish the same number with different content, so a wrong bump costs a new version, not an edit. Do not use the version to signal marketing size. Do not skip numbers to look important. And remember that your users' ranges (for example ^1.4.0) trust you: a breaking change in a minor release breaks their builds on the next install. See Dependency Updates Without Chaos for that side of the relationship.

Questions people ask

Is changing a default value a breaking change?

Usually yes, because existing users get different behaviour without changing their code. Treat it as a major change or make it opt in first.

Should I release 1.0.0 early?

Release 1.0.0 when you are ready to keep the public API stable. Staying on 0.x for years makes it hard for users to judge the risk of upgrades.
