How to Publish an npm Package from GitHub Actions

Set up setup-node with the npm registry, authenticate safely, publish with provenance and avoid the common failures on first publish and scoped packages.

Use actions/setup-node with registry-url, pass an npm token as NODE_AUTH_TOKEN, and run npm publish. Add --provenance with the id-token: write permission to let npm record where the package was built. Scoped packages need --access public on the first publish.

A working publish job

name: Publish
on:
  push:
    tags: ['v*']

permissions:
  contents: read
  id-token: write

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: 'https://registry.npmjs.org'
      - run: npm ci
      - run: npm test
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

setup-node writes an .npmrc that reads the token from NODE_AUTH_TOKEN. The token itself lives in repository or environment secrets, never in the repo.

Use the right kind of token

Create a granular access token on npmjs.com limited to the one package and to publish rights, with an expiry. Avoid a classic token with full account access. If your account requires two-factor authentication for publishing, an automation or granular token set up for CI is needed, since a CI job cannot type a one-time code. npm also supports trusted publishing from CI through OpenID Connect, which removes the long-lived token. It has requirements on workflow setup, so check the current npm documentation before relying on it.

Provenance

With --provenance, npm records a signed statement linking the published package to the repository, commit and workflow run that built it. Users can see that on the package page. It needs a supported CI provider, the id-token: write permission and a public repository for the public display. It proves where the package came from, not that the code is safe.

Common failures

  • 403 on first publish of a scoped package. Scoped packages are private by default, so add --access public or set publishConfig.access in package.json.
  • You cannot publish over an existing version. Bump the version. Registry versions are immutable.
  • 404 or 401 on publish. The token is missing, expired, or lacks rights on that package or scope.
  • Wrong files published. The files field and .npmignore decide the content. Check before you publish.

A pre-publish checklist

  • Version in package.json is new and matches the tag.
  • npm pack --dry-run lists only the files you intend.
  • The token is scoped and not expired.
  • Tests and build passed in the same workflow.
  • publishConfig.access is set for scoped packages.

Put this list in the release checklist of the repository, and turn each line you can into an automatic check.

Check the package before it goes out

Run npm pack --dry-run to list the files that would be included, and look for secrets, test fixtures and build leftovers. Combine this with a prerelease flow, see run a release candidate before publishing, and verify the result afterwards with a post-publish check. Keep publish rights narrow, as described in secure a release workflow.

Questions people ask

Why does npm publish fail with 403 for a scoped package?

Scoped packages default to private, which needs a paid plan. Publish with --access public, or set publishConfig.access to public.

Can I publish without a long-lived token?

npm supports trusted publishing through OIDC for CI. Check the current npm documentation for the setup and requirements.
