How to Roll Back a Bad npm Release

You cannot edit a published version. Move the latest tag back, deprecate the bad version, ship a fixed patch and know when unpublish is allowed.

If a published npm version is broken, point the latest tag back to the last good version with npm dist-tag add, mark the bad one with npm deprecate, and publish a fixed patch. Do not rely on npm unpublish: it is restricted and it breaks people who already depend on that version.

Step 1: stop new users getting the bad version

New installs use the version that the latest tag points to. Move it back:

npm dist-tag add your-package@1.4.3 latest
npm view your-package dist-tags

This takes effect quickly and affects only unpinned installs. Users who already installed or pinned the bad version keep it.

Step 2: deprecate the bad version

Deprecation prints a warning on install and keeps the version available, so no build breaks.

npm deprecate your-package@1.5.0 'Broken CLI entry point, use 1.5.1 or later'

Write what is wrong and what to use instead. Deprecation can be undone by running the command with an empty message. It is the normal, polite way to retire a version.

Step 3: ship the fix as a new version

Registry versions are immutable, so fix the code, bump the patch (1.5.1) and publish it through the usual workflow, preferably after a rehearsal, see release candidates. Then move latest to the new version if the publish did not do it. Write the problem into the changelog so users know whether they were affected.

When unpublish is an option

npm limits unpublishing: it is allowed in a short window after publishing and when no other packages depend on the version, and it has other restrictions. Check the current npm unpublish policy before you plan on it. Unpublishing a version that people use breaks their installs, and the version number can never be reused. Use it only for a mistake such as a leaked secret in the package, and in that case rotate the secret first, because anyone may already have downloaded it.

Tell your users

A rollback that nobody knows about helps few people. Add a short note to the GitHub release and the changelog, saying which version is bad, what the symptom is and which version to use. If the issue affects security, publish an advisory. Post in the places your users read: the repository discussions, the issue tracker or your announcement channel. Keep the tone factual and keep the message short.

Roll back the other channels

The same release may exist as a GitHub release, a container tag or a binary download. Mark the GitHub release as a pre-release or edit its notes with a warning, repoint movable tags (such as a container latest) to the last good build and keep immutable tags as they are. Write one short incident note: what broke, which versions, what to do. Then add the check that would have caught it to the pipeline, as in verifying a release.

Questions people ask

Can I overwrite a published npm version?

No. Versions are immutable. Publish a new version and deprecate the bad one.

What if I published a secret by mistake?

Treat the secret as leaked and rotate it immediately. Removing the package version does not remove copies that others downloaded.
