How to Generate a Changelog from Commits and Pull Requests

Write changelogs that humans read: from conventional commits, from pull request titles or from GitHub generated notes, and edit them before they ship.

The quickest way to a changelog is to let GitHub generate release notes from merged pull requests with gh release create --generate-notes, then edit the result. If you want grouped sections by type, use conventional commit messages and a tool that reads them. In both cases, a person should read the text before it is published.

Option 1: GitHub generated release notes

GitHub can build notes from the pull requests merged since the previous release and list contributors. You can call it from the CLI:

gh release create v1.5.0 --generate-notes --title v1.5.0

You can group entries by label with a .github/release.yml file, so that pull requests labelled for example breaking or bug land under their own headings. The notes are only as good as your pull request titles, so write titles for readers, not for yourself.

Option 2: conventional commits

If every commit or squashed PR title starts with feat:, fix:, docs: and so on, a tool can group them into Features, Fixes and the rest, and decide the version bump. Squash merging makes this practical: the PR title becomes the single commit message, so you only need to check titles. A small CI job can reject titles that do not match the format.

Option 3: a hand-kept CHANGELOG.md

The Keep a Changelog layout is simple and readable: an Unreleased section at the top, then one section per version with Added, Changed, Deprecated, Removed, Fixed and Security. Each contributor adds a line in their pull request. It costs a little discipline and gives the best text, because the author describes the change in user terms.

## [1.5.0] - 2026-11-10
### Added
- `status --json` prints machine readable output.
### Fixed
- Empty config file no longer crashes startup.

Write entries for the user

A commit says what the code did. A changelog entry says what is different for the reader. Compare 'refactor config loader' with 'Config files may now include comments'. Put breaking changes first and say what to do: the old name, the new name, one line on how to migrate. Link to the pull request or issue for details. Leave out internal changes that nobody outside your team would notice.

A release.yml for grouped notes

To group generated notes by label, add this file and label pull requests accordingly:

changelog:
  categories:
    - title: Breaking changes
      labels: [breaking]
    - title: Features
      labels: [enhancement]
    - title: Fixes
      labels: [bug]
    - title: Other
      labels: ['*']

Check the GitHub documentation for the exact keys, since the format can gain options over time.

Automate the draft, review the final

Generate the draft in CI when a release is prepared, then let a person edit it before it is published. The release workflow itself is covered in publishing a GitHub release from a tag. If you want a shareable page for a big release, you can publish the notes as a Markdown file with Pages (pages.flisk.si): npx -y @flisk-sh/pages publish notes.md --wait. The link is public, so only use it for notes you want public.

Questions people ask

Do I need conventional commits to get a changelog?

No. GitHub generated notes work from pull request titles and labels. Conventional commits add grouping and automatic version bumps.

Where should the changelog live?

A CHANGELOG.md in the repository and the GitHub release page both work. Pick one as the source of truth and link to it from the other.

Share the release notes

Publish a release report to a public link in one command.

Pages turns an HTML or Markdown file into a free public link. It is public, so do not publish anything private.
