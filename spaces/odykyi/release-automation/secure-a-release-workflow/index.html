How to Secure a GitHub Actions Release Workflow

A release job holds the keys to your users' machines. Limit who can trigger it, require approval, pin actions, scope tokens and add provenance.

A release workflow can publish code that thousands of machines will run, so give it stricter rules than your test jobs. Use a protected environment with required reviewers for the publish step, minimal permissions, actions pinned by commit SHA, short-lived or narrowly scoped credentials and protected tags.

Gate the publish step with an environment

Environments hold secrets and rules. Put the registry token in an environment, for example release, and require reviewers or a wait before jobs that use it run.

jobs:
  publish:
    runs-on: ubuntu-latest
    environment: release
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm publish --provenance
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

Secrets in that environment are not available to other jobs, so a compromised test job cannot read them. You can also limit which branches or tags may deploy to the environment.

Control who can release

Protect release tags with tag protection or a ruleset so only maintainers can create v* tags. Protect the main branch: required reviews, required status checks, no force pushes. Limit who can edit workflow files, because a changed workflow is a changed release process. A CODEOWNERS entry for .github/workflows/ makes workflow changes require a specific reviewer.

Pin and minimise

Tags on third-party actions can be moved by their owner. Pin actions that run in the release job by full commit SHA, with a comment for the version, and let a dependency updater propose bumps (see keeping Actions up to date). Set permissions explicitly at the top of every workflow. Avoid running arbitrary scripts from the pull request that triggered the run, and never build releases from pull_request_target with untrusted code.

- uses: actions/checkout@SHA_OF_THE_COMMIT # v4.x.y

Credentials

Prefer short-lived credentials from OIDC over stored long-lived tokens, where the registry supports it. Otherwise use a token that is scoped to one package, publish-only and with an expiry. Rotate it on a schedule and when anyone with access leaves. Never echo secrets, and be aware that logs mask only exact secret values.

A short audit you can do today

Open your release workflow and check: are permissions declared, are third-party actions pinned, does the publish job use an environment, who can push tags, who can edit the workflow, and when was the registry token last rotated? Each 'no' is a task. Fix the cheapest first, which is usually permissions and environment approval, then plan the rest. An hour spent here is worth more than most features.

Make the release auditable

Publish with provenance where supported so users can trace a package to a commit and a run (how to do it for npm). Keep release logs. Announce releases in one place so unexpected ones are noticed. For the full picture of workflow hardening, read GitHub Actions Security. Security reduces risk, it does not remove it: assume someday a credential leaks, and make sure you can revoke it and see what it did.

Questions people ask

What does an environment with required reviewers do?

A job that targets the environment waits until a listed reviewer approves it, and only then gets the environment's secrets.

Is pinning actions by SHA worth the effort?

For jobs that hold publish rights, yes. A moved tag on a third-party action could run attacker code with your credentials. Use an update bot to keep SHAs current.
