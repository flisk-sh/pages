How to Find Flaky Workflows Across Many Repositories

Count how often a workflow flips between pass and fail on the default branch and rank the worst, with a script you can run today.

A flaky workflow flips between pass and fail without a code fix in between. Count the flips in each workflow's recent default-branch runs, and any workflow with three or more flips in its last 100 runs is a good first candidate.

Why count flips

A simple failure rate cannot tell a broken workflow from a flaky one. A workflow that has failed ten times in a row is broken. One that passes, fails, passes, fails is flaky. Counting transitions between pass and fail, in time order, separates them.

The script

gh run list -R your-org/your-repo --branch main --limit 100 \
  --json workflowName,conclusion,createdAt \
  | jq -r '
    map(select(.conclusion=="success" or .conclusion=="failure"))
    | group_by(.workflowName)[]
    | sort_by(.createdAt)
    | {w: .[0].workflowName, c: map(.conclusion)}
    | .flips = ([range(1; .c|length) | select(.c[.] != .c[.-1])] | length)
    | select(.flips >= 3)
    | "\(.w)\t\(.flips)"'

The threshold of three flips in 100 runs is a reasonable starting point. Lower it if your repos run rarely.

Confirm with reruns

A flip can be a real fix followed by a real new bug. To confirm flakiness, look for the same commit with different outcomes. If a run failed and a rerun of the same commit passed, that is flaky by definition.

gh run list -R your-org/your-repo --json headSha,conclusion,workflowName,attempt \
  --limit 100

Group by headSha and workflow and look for mixed results.

Rank by cost

Fix first the flaky workflows that run most often and block the most people. A flaky check on every pull request outranks a flaky nightly job. Quarantine a flaky test with a tag so it stops blocking while someone fixes it, and give the quarantine an owner and a deadline. The causes and fixes are in flaky tests and CI.

Or use a dashboard

Cilytics flags a workflow as flaky when it flipped between pass and fail at least 3 times in the last 100 default-branch runs, and lists them for the whole org or a public repo via ?repo=owner/name. As with any hourly snapshot of 100 runs, rarely run workflows may not show enough history to be flagged.

Acting on the list

Take the top three and assign each to an owner with a date. For each, read the failing logs from three failed runs and look for the common cause. The usual suspects are timing assumptions, tests that depend on order, shared state between tests, external network calls, and runners that run out of memory or disk.

Fixes fall into a few buckets. Remove the dependency on time or network by using fakes. Isolate state so tests can run in any order. Add a retry only at the level of a known-unreliable operation, never around the whole job, because blanket retries hide real regressions and make runs slower. If you cannot fix it quickly, quarantine the test: move it to a non-required job that still runs and reports.

After the fix, watch the flip count for a week. The number should go to zero. If it does not, you fixed a symptom. Keep a short log of what you found, because the same causes tend to repeat across repos, and the log becomes your checklist.

Questions people ask

How many runs do I need?

At least a few dozen. With too few runs a normal fix looks like a flip and a flaky workflow looks stable.

Does rerun count as a flip?

A pass after a rerun of the same commit is the clearest sign of flakiness, and it also appears as a transition when you order results by time.
