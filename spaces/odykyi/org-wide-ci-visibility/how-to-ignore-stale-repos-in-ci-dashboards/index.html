How to Ignore Stale Repos in a CI Dashboard

Archived and inactive repositories add noise to CI numbers. Filter them by last push date and archive status with one command and report what you left out.

Exclude archived repositories and ones with no push in the last 90 days before you compute any CI metric. Stale repos have old red workflows that nobody will fix, and they hide the signal from active ones.

Why filter at all

A dead repo's last run might have failed a year ago. It will show red forever and drag your pass rate down, though nothing is wrong with how you work today. A dashboard full of such noise teaches people to ignore it.

Filter with the CLI

CUTOFF=$(date -u -v-90d +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -d '90 days ago' +%Y-%m-%dT%H:%M:%SZ)
gh repo list your-org --limit 300 --no-archived --json name,pushedAt \
  --jq ".[] | select(.pushedAt > \"$CUTOFF\") | .name"

The first line handles both macOS and Linux date syntax. The result is your list of active repos to scan.

Pick the cutoff on purpose

Ninety days is a common choice and the one Cilytics uses, leaving out repos inactive for that long. A quarterly-release project may need a longer window. Note that pushedAt counts pushes to any branch, so a bot that pushes weekly keeps a dead repo looking alive. Exclude known bot-only activity if it matters to you.

Do not hide, resolve

A stale repo is a decision waiting to happen. List them in the weekly review and choose: archive, transfer or revive. Archiving also stops scheduled workflows from running, which saves cost. See running a weekly CI review.

Keep a note of what you left out

Print the count of excluded repos on the dashboard, such as "37 repos skipped: archived or inactive 90 days". Readers trust a report that says what it hides. For overall repository upkeep see open-source repo health.

Scheduled workflows and cost

Stale repositories can cost money and attention. A workflow with a schedule trigger keeps running on the default branch of an active repo, and failures in it generate email nobody reads. GitHub disables scheduled workflows in public repositories after a long period without repository activity, but private repositories are not treated the same, so check your own.

List repositories whose only recent activity is scheduled runs. They look active in CI data but have no human changes. Candidates for archiving show up quickly when you compare the date of the last push with the date of the last non-scheduled run.

gh run list -R your-org/your-repo --limit 20 --json event,createdAt --jq '[.[]|select(.event!="schedule")]|length'

If the result is zero, nothing but the clock has touched the repository for a while. Archive it or give it an owner. Removing dead scheduled jobs also cuts your Actions minutes bill and reduces failure noise.

Questions people ask

Does archiving a repo delete its workflows?

No, but an archived repository is read-only and scheduled workflows stop running. You can unarchive it later.

Should forks be included?

Usually not, unless you actively maintain them. Add a fork filter with gh repo list --source.
