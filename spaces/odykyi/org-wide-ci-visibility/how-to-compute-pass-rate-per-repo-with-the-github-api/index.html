How to Compute CI Pass Rate Per Repo With the GitHub API

What counts as a pass, which runs to exclude and a script that gives each repository a pass rate over its last 100 runs.

Pass rate is successful runs divided by runs that finished with success or failure, counted on the default branch. Exclude cancelled and skipped runs, or the number will lie.

Define the numerator and denominator

Count a run as a pass when its conclusion is success and a fail when it is failure. Leave out cancelled, skipped and runs still in progress. A workflow that cancels older runs when a new commit arrives would otherwise look unhealthy for doing its job.

One repository

gh run list -R your-org/your-repo --branch main --limit 100 \
  --json conclusion \
  | jq '[.[] | select(.conclusion=="success" or .conclusion=="failure")]
    | {pass: (map(select(.conclusion=="success"))|length), total: length}
    | "\(.pass)/\(.total) = \((.pass*100/(if .total==0 then 1 else .total end))|floor)%"'

Use the same window, such as the last 100 runs, for every repo so they compare fairly.

All repos, sorted

Wrap the command in a loop over gh repo list and write one line per repo, then sort ascending so the worst appear first. Skip repos with fewer than about ten runs, since a percentage from three runs says nothing. See ignoring stale repos for filtering.

Read it with care

  • A repo with a very high rate may simply run few checks.
  • A low rate on a repo with pull request runs included reflects normal iteration, which is why default-branch only is better.
  • One broken workflow among ten drags the repo average down, so look at per-workflow rates before blaming the repo.

The trend matters more than any single number; see CI metrics that matter.

Mind the API limits

Authenticated requests have an hourly rate limit, and one list call per repo adds up in a big org. Run the script on a schedule, not on demand, and cache the output. Reading once an hour, as some dashboards do, keeps you well inside the limits.

Per-workflow rates and trends

Once the repo-level number works, compute it per workflow, since that is where the action is. Group runs by workflow name inside each repository and calculate the same ratio. A repo at 80 percent might be one workflow at 20 percent and nine at 100, which is a different problem from ten workflows at 80.

For a trend, compute the pass rate over rolling weeks instead of one window. Group runs by the ISO week of createdAt and compute the ratio for each. A line that falls over a month is more useful than a single low value, because it shows when something broke.

jq 'group_by(.createdAt[0:7])[] | {month: .[0].createdAt[0:7], runs: length}'

Store each run's output as a dated file or in a small table so you can build history beyond the last 100 runs, which the API returns by default. Keep the raw numbers, not only the percentages, so you can recompute with a different definition later.

Questions people ask

Should I include pull request runs?

For a measure of main's health, no. Include them separately if you want to measure developer experience.

Why 100 runs?

It is the maximum one page returns by default and gives a recent window. Larger windows need pagination.
