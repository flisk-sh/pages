How to Find Slow GitHub Actions Workflows (Median and p90)

Compute median and p90 run time per workflow from the GitHub API, rank by total wait, and learn why p90 matters more than the average for developers.

Measure each workflow's median and p90 duration from recent successful runs, then sort by the p90 multiplied by how often it runs. The median shows the typical wait; the p90 shows the pain people complain about.

Why median and p90, not average

Averages are dragged up by rare outliers such as a stuck runner. The median is the typical run. The p90 is the time that nine out of ten runs beat, so it shows how bad a slow day feels. Reporting both tells you whether a workflow is steadily slow or occasionally terrible.

Compute durations

A run's duration is the time between startedAt and updatedAt. Use successful runs only so that fast failures do not drag the number down.

gh run list -R your-org/your-repo --branch main --limit 100 \
  --json workflowName,conclusion,startedAt,updatedAt \
  | jq -r '
    map(select(.conclusion=="success")
      | {w: .workflowName,
         s: ((.updatedAt|fromdateiso8601) - (.startedAt|fromdateiso8601))})
    | group_by(.w)[]
    | {w: .[0].w, d: (map(.s)|sort)}
    | "\(.w)\tmedian=\(.d[(.d|length)/2|floor])s\tp90=\(.d[((.d|length)*0.9)|floor])s"'

The result is in seconds. The time includes queueing for a runner, which is useful, because people wait for that too.

Rank by total cost

A 20-minute workflow that runs twice a week matters less than a 6-minute one that runs on every push. Multiply p90 by the run count over the period to get the total wait, and start at the top of that list. Then look inside the top workflow for the slowest job or step; the run page shows timing per step.

Common causes

  • No dependency cache, so installs run in full each time.
  • Tests run serially that could be split across a matrix.
  • Every workflow runs on every change, with no path filters.
  • Waiting for a busy runner pool.

Fixes are covered in faster GitHub Actions.

A ready-made view

Cilytics lists slow workflows with their median and p90 and per-repo median run time, from default-branch runs, for an org or a public repo via ?repo=owner/name. It is an hourly snapshot, so use it to find targets, then measure your own fix with the script above.

Measuring a fix

Before you change anything, save the median and p90 of the target workflow. After the change, wait for at least 20 runs and compute the numbers again over the same kind of runs. A single fast run proves nothing, because runner speed and queue time vary.

Look at queue time separately from run time. The difference between createdAt and startedAt shows how long a run waited for a runner. If queue time is large, the cure is more runner capacity or fewer concurrent runs, not faster jobs.

gh run view RUN_ID --json jobs --jq '.jobs[] | {name, started: .startedAt, done: .completedAt}'

That shows the timing of each job inside a run, so you can see which one dominates. Often one job, such as a full end-to-end suite, sets the pace for the whole workflow, and splitting or caching it brings the p90 down more than anything else you could do.

Questions people ask

Why only successful runs?

Failed runs often stop early and make a workflow look faster than it is. Use successful runs for duration, and track failures separately.

What is a good p90?

It depends on the workflow, but many teams aim for pull request checks under ten minutes. Compare against what your developers will actually wait for.
