How to See CI Health Across All Repos in a GitHub Org

Three ways to get one view of every repository's CI: scripts with the GitHub CLI, a scheduled report, or a ready-made dashboard.

The fastest way is a script that lists your repositories and reads recent workflow runs for each, then prints pass rate and failures. For something ready-made, a public dashboard such as Cilytics shows the same picture without any setup.

What you want to see

Start with a short list of questions. Which workflows are red right now? Which repos fail most often? Which workflows are slow? Which flip between pass and fail? These four views answer most of what a platform team needs, and each maps to a later article in this series.

Option 1: a script with the GitHub CLI

List active repos, then read the latest default-branch runs.

ORG=your-org
gh repo list $ORG --limit 200 --no-archived --json name,pushedAt \
  --jq '.[].name' | while read r; do
  gh run list -R $ORG/$r --branch main --limit 20 \
    --json conclusion --jq "[.[]|.conclusion] | map(select(.==\"failure\")) | length" \
    | sed "s/^/$r failures: /"
done

Adjust the branch name per repo, since not everything uses main. Mind the API rate limit on large orgs.

Option 2: a scheduled report

Run the script from a scheduled workflow, write the result to a Markdown or JSON file and publish it. A nightly cron is enough since CI health changes slowly. We cover this in building a CI dashboard with GitHub Actions.

Option 3: use Cilytics

Cilytics is a public CI health dashboard for GitHub that needs no account. It reads the GitHub API once an hour and shows an org-wide view: a pass-rate trend, red workflows, per-repo pass rate and median run time, flaky workflows, slow workflows, an open-source hygiene score and an AI-readiness view. Use ?repo=owner/name to scan one public repository.

Know the limits of any of these

  • Default-branch runs only, so pull request failures are invisible.
  • The last 100 runs per workflow, which is a recent window, not history.
  • Hourly snapshots, so it is not a live alert system.
  • Repos inactive for 90 days are left out of Cilytics.

For alerting, use your CI's own notifications. For the metrics themselves, see CI metrics that matter.

Which route to pick

Choose by how much you need to customise. If you want a quick picture of public repositories today, open a ready-made dashboard and spend your time on the findings instead of the tooling. If you need private repositories, alerts or your own definitions, write the script and schedule it. Many teams start with the dashboard, learn which views they use, and only then decide what to build.

Whichever route you take, write down the definitions: what counts as red, what counts as flaky, what window you look at, which repos are excluded. A dashboard without definitions starts arguments; one with them ends arguments. Keep the definitions next to the data, as a short note at the top of the page.

Finally, decide who reads it and when. A dashboard nobody opens is decoration. Attach it to a weekly habit, covered in running a weekly CI review.

Questions people ask

Do I need admin rights on the org?

For public repos no. For private repos your token needs read access to Actions for each repository you want to include.

Why use the default branch only?

Pull request runs include many expected failures while people iterate. Default-branch runs show what is actually broken.
