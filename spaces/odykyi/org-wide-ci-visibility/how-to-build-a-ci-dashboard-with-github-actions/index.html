How to Build a CI Dashboard With GitHub Actions and a Static Page

Run a scheduled workflow that collects run data, writes a JSON file and publishes a small page your whole team can open.

Use a scheduled workflow to collect run data with the GitHub CLI, write it to a JSON file and a simple HTML page, and publish the result. It needs no server, and a nightly or hourly schedule is enough.

The pieces

  • A collector script using gh and jq.
  • A scheduled workflow that runs it.
  • A static page that reads the JSON and draws tables.
  • A place to publish it.

The scripts from listing red workflows and finding slow workflows are the building blocks.

The scheduled workflow

name: ci-report
on:
  schedule:
    - cron: '17 * * * *'
  workflow_dispatch:
permissions:
  contents: read
jobs:
  collect:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - env:
          GH_TOKEN: ${{ secrets.ORG_READ_TOKEN }}
        run: bash scripts/collect.sh > report.json
      - uses: actions/upload-artifact@v4
        with:
          name: report
          path: report.json

The default workflow token only sees its own repository, so you need a token with read access to Actions across the org. Store it as a secret and give it the minimum scope.

Publish the page

GitHub Pages can serve the output from the same repository. For a quick public link to a generated HTML or Markdown report, you can also use Pages from Flisk, which publishes a page to a free public link with npx -y @flisk-sh/pages publish page.html --wait. Pages are public, so do not publish private repository names or data that way.

Keep the page honest

  • Show the time of the last update at the top.
  • State the window, such as the last 100 default-branch runs.
  • List what was excluded, like archived or inactive repos.
  • Link each red workflow to its latest run.

These four lines prevent most arguments about whether a number is right.

When not to build it

If a public view of public repositories is enough, a ready-made dashboard saves the maintenance. If you need private repos, custom metrics or alerts, building your own is justified. See Cilytics vs building your own.

Storing history

The API only gives you the most recent runs, so a dashboard built on it forgets older data. If you want to see a trend over months, store each snapshot. The simplest way is to commit the JSON to a data branch on every run, with the date in the file name. A branch of small JSON files is cheap and easy to diff.

git config user.name ci-report
git config user.email ci-report@users.noreply.github.com
git add data/$(date -u +%F).json
git commit -m 'ci snapshot' && git push origin HEAD:data

The page can then read the last 30 snapshots and draw the pass-rate trend. Keep the format stable and add a version field so old files stay readable when you add columns.

Give the job a concurrency group so two overlapping runs do not both push, and handle the case where there is nothing new to commit. Both are easy to forget and easy to fix, but both will page you at the worst time if you do not.

Questions people ask

How often should the workflow run?

Hourly is plenty for trends. Scheduled workflows can be delayed by GitHub under load, so do not depend on exact times.

Can the default GITHUB_TOKEN read other repos?

Not private ones. Use a fine-grained token or app installation with read access to Actions on the repositories you need.
