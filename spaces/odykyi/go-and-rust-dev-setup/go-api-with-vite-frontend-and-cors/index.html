Go API and Vite frontend locally: proxy instead of CORS

The browser calls the API from one origin and the API answers on another. A dev proxy makes the two look like one, so you can leave CORS rules for the day you deploy.

Put a proxy in the Vite dev server so the browser calls /api/... on its own origin, and Vite forwards the request to the Go API. The browser then sees one origin and does not apply CORS at all. If you prefer direct calls, the other fix is an allowed-origin rule in the Go server, and it has to include the exact origin Vite uses.

Why the browser blocks the call

A page at http://localhost:3004 that calls http://localhost:4003 makes a cross-origin request, because the port differs. The browser sends the request, and then it hides the response unless the API replies with an Access-Control-Allow-Origin header that matches. A request with a JSON body or custom headers triggers a preflight OPTIONS request first, and the API has to answer that as well. The error in the console says "blocked by CORS policy", and the request still shows in the network tab, which is why it is confusing: the server did get it.

Fix 1: a Vite proxy (usually the better one)

Configure the dev server to forward a path prefix to the API:

// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    host: 'localhost',
    port: Number(process.env.PORT ?? 3004),
    strictPort: true,
    proxy: {
      '/api': {
        target: process.env.API_URL ?? 'http://localhost:4003',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
});

In the app, call fetch('/api/health'). Vite receives it and forwards /health to the Go server. Cookies and auth headers also work as on a single site, because the browser thinks there is one. This proxy exists only in vite dev. A production build needs a real reverse proxy or a CORS policy, so it is worth keeping the API prefix the same in both.

Fix 2: allow the origin in Go

If the frontend must call the API directly, answer the preflight and set the header for known origins. Here is a small middleware with an explicit list:

func withCORS(next http.Handler, allowed map[string]bool) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		origin := r.Header.Get("Origin")
		if allowed[origin] {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Vary", "Origin")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type, Authorization")
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE, OPTIONS")
		}
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
		next.ServeHTTP(w, r)
	})
}

Never answer with * if you send cookies, since browsers refuse the combination. List the origins instead, and echo the matching one.

Running both with Flisk

Create both services as local processes:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource api --language go --local --stack app --yes
flisk resource web --type frontend --local --stack app --yes
cd services/app/web && npm install && cd ../../..

Then edit the frontend's service.json to start after the API and to receive its address:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "stack": "app",
  "framework": "react",
  "command": "npm run dev",
  "port": 3004,
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4003" }
}

Use the ports your scaffold picked, since Flisk assigns the next free one. flisk up starts api, waits until its /health answers, then starts web, and prints a http://localhost:<port> link for each. The Vite config above reads API_URL from that env block, which keeps the target out of the code.

The Go and Rust scaffolds include a CORS rule, but it only allows origins of the form name.localhost, which matches the Docker route (app.<project>.localhost). In the local-process route the frontend is http://localhost:3004, which that pattern does not match, so a direct call is blocked. Use the Vite proxy, or widen the pattern in main.go.

The Vite config written by flisk resource --local is a plain one with strictPort on, so if the port is taken Vite fails instead of moving, which keeps it on the port Flisk checks. More on running a frontend and API together is in run a frontend and an API together.

Pitfalls

  • Proxy path mismatch. If the Go routes do not live under /api, the rewrite must strip the prefix, or the Go side must register it.
  • localhost against 127.0.0.1. These are different origins. Use one name everywhere.
  • WebSockets. Add ws: true to the proxy entry if the API upgrades connections.
  • Preflight that returns 404. A router that only registers GET /x will reject OPTIONS /x. Handle OPTIONS in middleware before routing.

Questions people ask

Why does CORS fail when both run on localhost?

Different ports are different origins. The browser blocks the response unless the API sends an Access-Control-Allow-Origin header that matches the page's origin.

Is a Vite proxy a production fix?

No. It only exists in the dev server. In production use a reverse proxy that serves both under one origin, or configure CORS on the API.

Why does the Flisk Go scaffold block my local frontend?

Its CORS pattern allows origins like app.project.localhost, which fits the Docker route. A frontend on http://localhost:3004 does not match, so use a Vite proxy or widen the pattern.
