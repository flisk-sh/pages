Air vs reflex vs watchexec: reload a Go app on save

Go has no built-in watcher. Three small tools fill the gap, and they differ in one detail that decides whether your API is down while it compiles.

Use Air if you want a Go-specific tool with a config file, and use watchexec or reflex if you want one small binary that restarts any command when files change. All three do the same core job: watch your files, stop the running program, and start it again. The difference that matters is the order. Some tools stop the old process before they compile, so your API is unreachable for the length of the build.

What a Go reload tool has to do

go run . compiles and runs once, then you stop it by hand. A watcher repeats that loop for you. It needs to ignore the files it generates (a tmp folder, test files), wait a moment so that a burst of saves causes one rebuild, and kill the old process cleanly, including any child it started. That last part is where simple setups go wrong: go run compiles a binary and starts it as a child, and if the parent is killed hard the child can keep the port open. Building a binary yourself and running that file avoids the problem.

Air

Air is written for Go and reads a .air.toml file.

go install github.com/air-verse/air@latest
air init   # writes .air.toml
air

The part of the config you will touch is the build section:

[build]
  cmd = "go build -o ./tmp/main ."
  bin = "./tmp/main"
  exclude_dir = ["tmp", "vendor"]
  exclude_regex = ["_test.go"]
  # poll = true   # needed when files change on a network or bind-mounted drive

Air stops the running binary as soon as it sees a change and then compiles, so there is a gap with no server. For a small service that gap is a fraction of a second. For a large one, a request in that window fails.

Since Go 1.24 you can pin the tool in go.mod instead of installing it globally: go get -tool github.com/air-verse/air@latest, then run go tool air. Every developer then gets the same version.

reflex and watchexec

Both are generic. They know nothing about Go, so you tell them what to watch and what to run.

# reflex: -s treats the command as a long-running service and restarts it
reflex -r '\.go$' -s -- go run .

# watchexec: -r restarts the command, -e picks extensions
watchexec -r -e go -- go run .

watchexec honours .gitignore by default, which keeps a git-ignored tmp folder out of the loop. Use -e go,mod,sum if you also want changes to go.mod and go.sum to restart the program. Neither tool needs a config file, which is the reason to choose them when you also work in Rust or Node and want one habit for all of them.

Running the watcher under Flisk

With Flisk, a service that declares a command runs as a local process with no Docker. The command can be your watcher, because Flisk only starts it, reads its port, and restarts it if it exits. The Go scaffold gives you the service, and you change one field.

npm install -g @flisk-sh/flisk
flisk resource orders --language go --local --stack app --yes

The scaffold writes go run . as the command, which does not reload. Edit service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "stack": "app",
  "language": "go",
  "command": "air",
  "toolchain": "go@1.23",
  "port": 4003,
  "healthCheckPath": "/health"
}

Flisk passes PORT to the process, and the scaffolded program listens on it. toolchain makes flisk up refuse to start if the Go on your PATH does not match, and Flisk also refuses to start when the program in command (here air) is not installed. Keep your port from the scaffold, since it picks the next free one.

If you run the Docker route instead, Flisk has its own watcher behind "dev": { "liveReload": true }. It compiles into a staging binary while the old one keeps serving, and swaps only when the build succeeds. The Flisk docs say that Air, tried first, stopped the app before compiling, which is the gap described above. The Docker path is covered in Go API local dev.

Pitfalls

  • A reload loop that never stops. If the program writes a file inside the watched tree (logs, a SQLite file), the watcher sees it and restarts. Exclude that folder.
  • Port still in use after a restart. Usually a leftover child from go run. See how to fix port already in use.
  • Nothing reloads in a container. File events do not always cross a bind mount. Turn on polling in Air, or see hot reload not working.
  • Dependency changes. A watcher reloads on code changes. After go get, restart it so it picks up the new module graph.

Questions people ask

Does Go have built-in hot reload?

No. go run compiles and runs once. You need a watcher such as Air, reflex or watchexec to restart the program on each save.

Is Air still maintained?

The project moved to the air-verse organisation on GitHub, and that is the module path to install. Check its repository for recent releases before you adopt it.

Can I use these tools with Flisk?

Yes for local processes. Put the watcher in the command field of service.json, and Flisk starts it, passes PORT and restarts it if it exits.
