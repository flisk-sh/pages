How to debug a Rust service with LLDB and VS Code

The Rust compiler catches a lot before you run anything. For the bugs that remain, a debugger and good logs cover most of what you need.

In VS Code, install the CodeLLDB extension and the rust-analyzer extension, then click the Debug link rust-analyzer shows above main or above a test. From a terminal, run rust-lldb target/debug/app. Both work on the default dev build, which already contains debug information. For async code, such as an axum handler, breakpoints are only half the answer: set up structured logs too, because a task can hop between threads.

Check that the build has debug information

cargo build uses the dev profile, which includes debug data. Two common settings remove it. A release build does not have full debug data by default, and a dev profile with debug = "line-tables-only" keeps backtraces but drops variable inspection. If your Cargo.toml has that setting for faster builds (see speed up Cargo builds), turn it back to the default while you debug:

[profile.dev]
debug = true

Debug from VS Code

With CodeLLDB installed, a .vscode/launch.json entry builds and starts your binary under the debugger:

{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "lldb",
      "request": "launch",
      "name": "Debug billing",
      "cargo": { "args": ["build", "--bin=app"] },
      "cwd": "${workspaceFolder}/services/app/billing",
      "env": { "PORT": "4004", "RUST_BACKTRACE": "1" }
    }
  ]
}

The cargo block lets the extension find the binary, and the env block is how you give it the settings that a runner would normally pass. Put a breakpoint on a line inside a handler, call the route with curl, and execution stops there. To debug one test, use the rust-analyzer Debug link over the #[test] function, or run cargo test --no-run and start the test binary under rust-lldb.

Debug from the terminal

cargo build
PORT=4004 rust-lldb target/debug/app
(lldb) b main.rs:30
(lldb) run

rust-lldb is a wrapper that ships with the Rust toolchain and loads pretty-printers, so String, Vec and Option values are readable. To attach to a process that is already running, use lldb -p <pid>. On macOS this needs permission for the terminal under Developer Tools, and it can be refused for a binary that was not built locally.

Async code: logs beat breakpoints

A tokio task can resume on a different thread after each .await, and stepping over an await can jump somewhere unexpected. Use breakpoints for straight-line logic, and use the tracing crate with RUST_LOG for flow:

RUST_LOG=billing=debug,tower_http=debug cargo run

Also set RUST_BACKTRACE=1 to get a stack trace on a panic, and RUST_BACKTRACE=full when the short form is not enough. If you suspect a task that never finishes or a lock that is held, tokio-console shows live task states, and it needs the console-subscriber crate and the tokio_unstable cfg flag.

Run it under Flisk

With a Rust service created by flisk resource billing --language rust --local --stack app --yes, Flisk runs cargo run as a local process. Pass the debugging environment through the env field of its service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "billing",
  "appType": "backend",
  "stack": "app",
  "language": "rust",
  "command": "cargo run",
  "port": 4004,
  "healthCheckPath": "/health",
  "env": { "RUST_BACKTRACE": "1", "RUST_LOG": "billing=debug" }
}

Read the output with flisk logs --service billing --tail 50. To run the tests with the same environment the service has, use flisk run billing -- cargo test; for a local process Flisk runs the command on the host, and the -- keeps cargo's own flags apart from Flisk's.

When you debug from the editor, the binary you start takes the port. Stop the Flisk-managed copy first with flisk down, or start the other services alone with flisk up --only, remembering that --only also starts what a service lists in dependsOn. Flisk refuses to start a service whose port is already in use and names the process that holds it, which tells you quickly when the two copies collide.

Pitfalls

  • Breakpoints that look grey or never hit. The code in that line was optimised away, or you are debugging a release binary. Debug the dev build.
  • Source mismatch after a rebuild. The debugger is stopped on an old binary. Restart the session after each build.
  • Paused service reported as down. While you stand on a breakpoint the health path does not answer.
  • Docker. Debugging inside a container needs ptrace permission and a debug-friendly image. It is usually quicker to debug the process on the host and keep only the database in Docker.

Questions people ask

What is the difference between rust-lldb and plain lldb?

rust-lldb is a wrapper from the Rust toolchain that loads pretty-printers so standard types such as String and Vec are shown in readable form.

Why does my Rust breakpoint not hit?

Usually the build has no debug information, the line was optimised away in a release build, or the binary is older than the source. Rebuild the dev profile and restart the session.

How do I run tests with the service's environment in Flisk?

Use flisk run <service> -- cargo test. For a local process it runs the command on the host with the environment that the service has.
