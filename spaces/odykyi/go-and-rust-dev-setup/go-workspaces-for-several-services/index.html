Go workspaces (go.work) for a repo with several services

One module per service keeps builds small. A workspace file lets those modules see each other's local code while you edit, with nothing to undo before you commit.

Create a go.work file at the repo root with go work init, list your module folders in it, and Go will resolve imports between those modules to your local copies. You do not need a replace directive in each go.mod. The catch is that the workspace only exists on your machine and in any build that uses the repo root, so a Docker build of one service folder will not see it.

The problem it solves

Say you have two services and a shared package, each its own module:

repo/
  go.work
  libs/shared/go.mod        # module example.com/repo/shared
  services/app/api/go.mod   # module example.com/repo/api
  services/app/worker/go.mod

Without a workspace, api imports example.com/repo/shared from the module proxy at a tagged version. To test an edit to shared you either tag and push, or add replace example.com/repo/shared => ../../../libs/shared to the go.mod and remember to remove it. A workspace removes both chores.

Set it up

cd repo
go work init ./libs/shared ./services/app/api ./services/app/worker
cat go.work
go 1.23

use (
	./libs/shared
	./services/app/api
	./services/app/worker
)

Add a module later with go work use ./services/app/newsvc. go work sync pushes the workspace's dependency versions back into each module's go.mod, and Go writes a go.work.sum next to the file. Check what is in the workspace with go list -m.

Go finds go.work by looking in the current folder and then in each parent, so running go run . or go test ./... inside services/app/api uses the workspace without extra flags. To prove a module builds without it, which is what a published build sees, run GOWORK=off go build ./....

Test every module

go test ./... covers the packages of one module. To run all modules in the workspace:

for d in $(go list -f '{{.Dir}}' -m); do (cd "$d" && go test ./...); done

Run this once with GOWORK=off in CI as well. It catches the case where a module only builds because the workspace supplies a change that was never released.

Should go.work be committed?

Both choices are used. If every module lives in this repo and the team always develops them together, committing go.work saves each person one command. If developers keep personal paths in it, or you publish modules that others import, keep it out of git (add go.work and go.work.sum to .gitignore) and document go work init in the README. Whatever you pick, make CI check the build with GOWORK=off.

Running the services with Flisk

Create each service as a local process:

flisk resource api --language go --local --stack app --yes
flisk resource worker --language go --local --stack app --yes
flisk up

For a local process Flisk starts the command from the service directory, and the Go tool searches upward from there, so it finds go.work at the repo root. That follows from how Go and Flisk each work, and I did not run it end to end. Setting "toolchain": "go@1.23" in each service.json makes flisk up check that the Go on your PATH matches.

The Docker route is where workspaces break. The Flisk docs say that only the service folder is copied into the generated image, so a replace to a folder outside it fails at go mod download, and that a go.work workspace was not tried.

If a service must build in a container and needs the shared module, use your own Dockerfile and set the build context to a folder that contains everything. Flisk's bring-your-own resources accept a buildContext in service.json, a path relative to the resource directory, and the Dockerfile path is then relative to that context. A Dockerfile for the layout above:

FROM golang:1.23-bookworm AS build
WORKDIR /src
COPY go.work go.work.sum* ./
COPY libs/shared libs/shared
COPY services/app/api services/app/api
RUN cd services/app/api && CGO_ENABLED=0 go build -o /out/app .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]

That Dockerfile copies go.work, so the build resolves the shared module the same way your editor does. It also copies the modules the workspace lists but this service does not need, unless you trim the use list in a CI copy. Note that a container built this way loses the live reload that the generated Go image offers, as explained in run an existing Dockerfile in a local dev stack.

Pitfalls

  • Works here, fails in CI. The workspace hid a missing release or a missing require. Build with GOWORK=off.
  • Editor shows errors. gopls needs to be opened at the repo root, or at a folder inside it, to find go.work. Opening one service folder in a separate window usually still works, since the lookup goes upward.
  • Different Go versions per module. The workspace's go line must be at least the highest module version.
  • Vendoring. go work vendor exists, and it is a different workflow from the one above.

Questions people ask

Do I still need replace directives with go.work?

No for local development. The workspace resolves imports between listed modules to your local folders. Test with GOWORK=off to be sure the released modules also work.

Should I commit go.work?

Commit it if every module is in the repo and the team always works on them together. Keep it out of git if it holds personal paths or you publish modules to others.

Does go.work work in the Flisk Docker route?

The Flisk docs say only the service folder is copied into the generated image and that go.work was not tried. Use a bring-your-own Dockerfile with a wider build context.
