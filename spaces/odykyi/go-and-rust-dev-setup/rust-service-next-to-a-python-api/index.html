How to run a Rust service next to a Python API locally

Python is quick to change and Rust is quick to run. Putting a hot path in Rust and keeping the rest in Python works, once the two processes find each other.

Run both as plain processes with fixed ports, give the Python app the Rust service's URL through an environment variable, and start Rust first so Python can call it from its first request. The shortest working setup is two commands under a process manager. Flisk can be that manager, and the same layout also works with a Procfile runner or two terminal tabs.

When this split makes sense

Keep the product logic, the routes and the glue in Python. Move one narrow, CPU-heavy or latency-sensitive piece to Rust, such as a parser, a pricing calculation or a validator, and expose it over HTTP. The boundary should be a clear request and response, so each side can be tested alone. If you only need a function from Python, a PyO3 extension module (built with maturin) is a different and often simpler route, since it avoids a network call. Choose a separate service when the Rust part needs its own lifecycle, its own deploy, or a long-lived state such as a cache.

The two services

With Flisk, create both as local processes in one stack:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource billing --language rust --local --stack app --yes
flisk resource api --language python --local --stack app --yes

The Rust scaffold is axum on tokio with a /health route, and its command is cargo run. The Python scaffold is a FastAPI app, and its command runs uvicorn with --reload on src, so edits to the Python code restart the app by themselves. Both read PORT from the environment. Check the generated ports in each service.json; the examples below use 4004 and 4005.

Wire them together

Edit the Python service's service.json so that it starts after Rust and knows where it is:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "stack": "app",
  "language": "python",
  "command": "uvicorn main:app --app-dir src --host localhost --port ${PORT:-4000} --reload --reload-dir src",
  "port": 4005,
  "healthCheckPath": "/health",
  "toolchain": "python@3.12",
  "dependsOn": ["billing"],
  "env": { "BILLING_URL": "http://localhost:4004" }
}

In Python, read the address once and call it with a client that has a timeout:

import os
import httpx

BILLING_URL = os.environ["BILLING_URL"]

async def price_for(order: dict) -> dict:
    async with httpx.AsyncClient(base_url=BILLING_URL, timeout=2.0) as client:
        r = await client.post("/price", json=order)
        r.raise_for_status()
        return r.json()

Then run flisk up. Flisk starts billing first, waits for its /health to answer, starts api, and prints a link for each service. flisk logs --service billing shows one service's output, and flisk down stops both. This is the same pattern as a Python worker next to a Node API, with Rust on the other end.

The first-build trap

The first cargo run compiles every dependency, and with axum and tokio that can take longer than a minute. Flisk waits up to 60 seconds for a service to become ready, so on a cold machine billing can be late and api never gets its turn. Compile once before the first flisk up:

cd services/app/billing && cargo build

Later runs reuse that build, and only your own crate is recompiled. The Rust command does not reload on save by default; to get that, change its command to cargo watch -x run, as in Rust API local dev.

Without Flisk

The same layout works with two terminals, or with a Procfile and a runner such as overmind or honcho. The parts you must supply yourself are the start order, a wait for the Rust port to open, and a restart when a process dies. Docker Compose gives you ordering with depends_on and a healthcheck, at the cost of building a container for each service.

Pitfalls

  • Bind address. The Rust scaffold binds localhost, and a URL with 127.0.0.1 may not match if localhost resolves to IPv6 on your machine. Use localhost on both sides, or bind explicitly.
  • No timeout on the client. A hung Rust service then hangs every Python request. Set a timeout and handle it.
  • Mixed runtimes. A project cannot mix services that run as local processes with services that Flisk builds into containers, and flisk up stops with MIXED_RUNTIME. A ready-made image such as Postgres can sit next to local processes.
  • Two Pythons. The python that uvicorn uses is whichever one is on PATH. Activate the virtual environment before flisk up, or Flisk's toolchain check will report a mismatch.

Questions people ask

Should I call Rust from Python over HTTP or use PyO3?

Use PyO3 with maturin when you only need a fast function inside the Python process. Use a separate HTTP service when Rust needs its own lifecycle, state or deploy.

Why does the Python service start before Rust is ready?

Without a dependency it does. Add the Rust service to dependsOn in service.json, and Flisk starts Python only once the Rust health path answers.

Can Flisk start a Rust and a Python service without Docker?

Yes, when both services declare a command. Flisk runs them as local processes in dependsOn order. It needs cargo and python on your PATH.
