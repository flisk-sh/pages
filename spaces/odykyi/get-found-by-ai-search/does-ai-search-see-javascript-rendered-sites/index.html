Can AI crawlers read JavaScript-rendered sites?

Many AI crawlers fetch HTML and do not run your scripts. How to test what they see, and how to fix a single-page app with server rendering or prerendering.

Assume AI crawlers see only the HTML your server returns, because many do not execute JavaScript. If your page text appears only after a script runs, it may be invisible to them. Fix it by rendering on the server or prerendering the pages that matter.

Test what a bot receives

Fetch the raw HTML and look for your real content.

curl -s https://example.com/pricing | grep -i 'per month'

If the text is missing and you only see an empty <div id="root"></div> plus script tags, a crawler that does not run scripts sees an empty page. Browser view-source shows the same thing, unlike the live inspector, which shows the page after scripts ran.

Why it matters

Search products differ. Some crawlers do render pages, others do not, and assistants that fetch a page on demand often use a simple fetch. You cannot count on rendering, so design so that you do not need it.

Fix 1: Server-side rendering

Frameworks such as Next.js, Nuxt, SvelteKit and Astro can render HTML on the server, so the first response already holds the text. Prefer this for content pages: docs, blog posts, pricing, product pages. Keep client-only rendering for the logged-in app, which crawlers do not need.

Fix 2: Static generation or prerendering

If content changes rarely, build the pages to static HTML at deploy time. Static files are fast, cheap to host and easy for any bot to read. For an existing single-page app, a prerender step can produce HTML for the public routes only.

Other things that hide content

  • Text inside images or canvas. Add real text.
  • Content behind tabs or accordions that load on click. Put it in the HTML.
  • Infinite scroll with no paginated URLs. Provide real links to each page.
  • Cookie walls or login gates in front of public content.

After the fix, run Citable to confirm the pages can be read, and see sitemaps and meta tags for the supporting basics.

A quick decision guide

  • Marketing, docs, blog: render on the server or build static HTML.
  • Logged-in dashboard: client rendering is fine, since bots should not see it anyway.
  • Mixed site: split it. Public routes get HTML, the app routes stay client side.

Whatever you choose, keep the curl check from the first section in your release checklist, because a framework upgrade can silently switch a page from server to client rendering.

If a full rewrite is not possible this quarter, start with the five pages that matter most, such as the home page, pricing and the main docs entry, and prerender only those.

Questions people ask

Does Googlebot render JavaScript?

Googlebot can render JavaScript, but it adds delay and can fail. Other AI crawlers may not render at all, so server HTML is safer.

Is a single-page app a bad choice?

Not for an app behind a login. For public content you want found, serve HTML from the server or build static pages.
