Debugging CI Failures

How to Reproduce a GitHub Actions Failure Locally

Match the runner's OS, tool versions and environment variables, run the same commands in a clean checkout and you can reproduce most CI failures on your own machine.

To reproduce a CI failure, check out the exact commit in a clean directory, install tools at the versions the workflow uses, and run the same commands in the same order with the same environment variables. Most failures reproduce this way without any special tool.

Check out the exact commit in a clean directory

Your working directory has untracked files, a populated node_modules, a build cache and local env files. CI has none of that. Start from a fresh clone of the failing commit.

git clone https://github.com/OWNER/REPO.git /tmp/repro
cd /tmp/repro
git checkout FAILING_SHA

For a pull request, CI usually tests a merge of the PR into the base branch, not the PR head. Fetch the merge ref with git fetch origin pull/123/merge and check out FETCH_HEAD.

Match versions and environment

Open the workflow file and the setup steps in the log. Note the runner OS (ubuntu-latest is Linux), the language version, and the env block. Then match them locally. For Node, use a version manager. For Python, use a virtual environment with the same minor version.

Use the install command CI uses, not the one you use. For npm that is usually npm ci, which installs exactly from the lockfile and fails if the lockfile is out of date. npm install can quietly change the lockfile and hide the problem.

Run in a Linux container if you are on a Mac or Windows

Path case, line endings, file permissions and missing system libraries differ between macOS or Windows and the Linux runner. A container removes that difference.

docker run --rm -it -v "$PWD":/work -w /work node:20 bash
npm ci && npm test

Pick the image that matches your version. A plain Linux image does not have everything a GitHub-hosted runner has installed, so a missing tool in the container is not always the cause. Treat the container as a close approximation, not a copy.

Use a tool that runs workflows, with care

The open-source act project runs workflow files in Docker. It is handy for quick checks of shell steps and simple jobs. Its images are not the same as GitHub's runner images, and some features (some contexts, services, caches, OIDC) behave differently. If a failure does not reproduce under act, that tells you little. Check the project's docs for what it supports.

A short checklist

  • Fresh clone of the exact commit or merge ref.
  • Same language and tool versions as the log shows.
  • Same install command, from the lockfile.
  • Same environment variables, with test values for secrets.
  • Same working directory and the same command order as the workflow.

Write the working reproduction down as a script in the repository, for example scripts/ci.sh, and call it from the workflow. Then the local run and the CI run are the same code, and the gap between them shrinks for good.

When the failure does not reproduce

If the same commands pass locally, the difference is in the environment: a secret, a service container, a timezone, CPU count, parallelism or a network call. Work through the list in tests pass locally but fail in CI.

If your repo has several services, a local stack that mirrors the CI setup helps. The Flisk CLI (open source, MIT) runs services, databases and queues locally from one service.json each, and flisk doctor checks your environment: flisk.sh/docs. It is a local development tool, not a replacement for the CI runner.

Questions people ask

Why does CI test a merge commit for a pull request?

By default GitHub checks out a temporary merge of the PR into the base branch, so CI tests what the result would look like after merging.

Is act a faithful copy of GitHub runners?

No. It runs workflows in Docker with different images and some features differ. Use it as a quick check, not as proof.
