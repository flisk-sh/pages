Next.js, Express and Postgres on one laptop

A web app, an API, a database and a migration step make four things that must start in the right order. Here is a starter that wires them and the reasoning behind it.

To run Next.js, Express and Postgres together, you need four things in order: the database, a one-shot migration, the API, then the web app. With Flisk, flisk create myapp --starter next-postgres followed by flisk up builds exactly that stack in Docker. The same shape works without Flisk, and the reasoning below applies to any tool.

Why the order matters

A Next.js page that fetches from an API on first render fails if the API is not up. The API fails on its first query if the table does not exist. The table does not exist until the migration has run, and the migration needs a database that accepts connections. That chain is the whole problem.

A common shortcut is to run prisma migrate deploy in the API start script. It works with one API instance and breaks as soon as there are two replicas, a worker that shares the database, or a failed migration that makes the API crash in a loop with a confusing error. The cleaner pattern is a separate step that runs once, exits, and is a hard dependency of the services that need the schema.

The same thing in plain Docker Compose

Compose can express the chain with depends_on conditions:

services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
  migrate:
    build: ./api
    command: npx prisma migrate deploy
    depends_on:
      db: { condition: service_healthy }
  api:
    build: ./api
    depends_on:
      migrate: { condition: service_completed_successfully }
  web:
    build: ./web
    depends_on: [api]

That is a fair setup and many teams keep it. You maintain the Dockerfiles, the health checks, the port mapping and the hostnames yourself.

The Flisk way: the next-postgres starter

Flisk ships this stack as a starter. You need Docker running.

npm install -g @flisk-sh/flisk
flisk create myapp --starter next-postgres
cd myapp
flisk up

You can also write flisk project next-postgres --path myapp. The starter has four resources:

  • db: a database resource with the postgres framework, the shared Flisk Postgres.
  • api-migrator: an appType: migrator resource that uses Prisma and depends on postgres. It runs prisma migrate deploy against the migrations in prisma/migrations and then exits.
  • api: an Express API that depends on api-migrator. It serves GET and POST on /items and PATCH and DELETE on /items/:id, reads DATABASE_URL, and its /health/ready route runs SELECT 1.
  • web: a Next.js app with backendName: api that depends on api.

The dependency is written in each service.json and, for the dependencies that need a condition, it can also be an object:

"dependsOn": [
  { "name": "api-migrator", "condition": "service_completed_successfully" }
]

The accepted conditions are service_started, service_healthy and service_completed_successfully, the same words Compose uses. A plain string in dependsOn is the short form.

Find the URLs

Ports are not published on your host. Ask Flisk instead of guessing:

flisk networks
flisk open
flisk status

The API is reachable at http://api.<project>.localhost/api/<name> and the web app at http://app.<project>.localhost/web. If the host port is not 80, the port is appended. The Next.js resource runs next dev, so edits to a page reload in the browser, and its health check is at /web/health because Next.js is served under the /web base path.

Change the table

Add a new folder with a migration.sql file under api-migrator/prisma/migrations, then restart only the migrator:

flisk restart api-migrator

The migrator runs again, applies the new migration and exits. The API keeps running. After editing dependsOn, backendName or apiPath of the web app, run flisk restart web, because those values are read when the frontend starts. To confirm that generated files match the manifests, run flisk config verify. For the Prisma side in more detail, see Prisma migrations locally.

Pitfalls

  • Next.js needs a recent Flisk. The Next.js provider needs Flisk 1.4.3 or newer.
  • Do not hand-edit generated files. Files under .autogenerated/ and .flisk/ are rewritten. Change service.json instead.
  • Server code calling the API. Browser code uses the public API URL. Server-side code in a container uses the Docker network, so check which one your fetch runs in before you hard-code a URL.
  • No Docker, no this stack. The Postgres container and the Prisma migrator need Docker. For a database-free app, see the local-process route in Express and Vite.

Questions people ask

Where should Prisma migrations run in local development?

In a separate one-shot step that runs before the API starts, not in the API start script. That avoids races between several instances and keeps a failed migration from crash-looping the API.

Does the next-postgres starter need Docker?

Yes. It runs Postgres, a Prisma migrator, an Express API and a Next.js app as containers, so Docker must be running before flisk up.

How do I add a column after the stack is running?

Add a new migration folder with a migration.sql file under api-migrator/prisma/migrations, then run flisk restart api-migrator. The migrator applies it and exits.
