Vue or Svelte frontend with a local API

A Vite frontend only needs to know where the API is. The hard parts are the variable name, the origin and the start order.

A Vue or Svelte app built with Vite finds its API through an environment variable that starts with VITE_, such as VITE_API_URL, read as import.meta.env.VITE_API_URL. In development you either proxy API calls through the Vite dev server or allow the frontend origin on the API with CORS. Flisk generates the variable for you when it runs the frontend in Docker, and you set it yourself when you run the frontend as a local process.

How a Vite frontend finds its API

Vite exposes only variables whose names begin with VITE_ to browser code, and it bakes them in when the dev server starts. That is why changing VITE_API_URL needs a restart of the dev server. The usual client code is the same in Vue and Svelte:

const API_URL = import.meta.env.VITE_API_URL ?? '';
const res = await fetch(API_URL + '/health');

An empty fallback means relative URLs, which works when a Vite proxy forwards them. Without a proxy the browser calls the API origin directly, and the API must answer the CORS preflight for the frontend origin.

The plain approach

Put the address in .env.development and start both servers:

# web/.env.development
VITE_API_URL=http://localhost:4000

Or use the proxy and keep the variable empty:

// vite.config.ts
export default defineConfig({
  plugins: [vue()],   // or svelte()
  server: { proxy: { '/api': 'http://localhost:4000' } },
});

The proxy avoids CORS in development and still needs a real CORS rule or a reverse proxy in production.

The Flisk way in Docker

Flisk has providers for these frontend frameworks: react (the default), vue, svelte, preact, lit, solid, qwik, vanilla and tanstack-router. All are Vite single page apps. Create the API and the frontend, and name the API in backendName:

npm install -g @flisk-sh/flisk
flisk resource api --stack app --yes
flisk resource web --framework vue --stack app --yes
flisk up

Use --framework svelte for Svelte. The scaffolded service.json of the frontend has dependsOn: ["api"], backendName: "api" and the features api-client, env-config and api-index. Flisk writes the API address into .autogenerated/.env.frontend.autogenerated as VITE_API_URL and generates a typed env.ts and api-client.ts next to it. The scaffolded App.vue reads import.meta.env.VITE_API_URL and calls /health.

The scaffolded page shows three states for the API call, checking, ok and unreachable, and that is a good habit to copy: a frontend that starts before its API should say so on screen, not show a blank page. Wrap your own calls in the same way, with a visible loading state and a visible error.

The frontend is served at http://app.<project>.localhost/web for a resource named web. The backend scaffold already allows *.localhost origins in CORS. After you change dependsOn, backendName or apiPath, run flisk restart web so the frontend picks up the new address.

The frontend's dev script uses a Vite config under .autogenerated/, which Flisk writes when flisk up loads the resource. Running npm run dev by hand before the first flisk up stops with an error that says exactly this.

The Flisk way without Docker

Any Vite app can run as a plain process. Write the manifest with the variable by hand:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "VITE_API_URL": "http://localhost:4000" }
}

In this mode the frontend origin is http://localhost:3000, so the API's CORS rule must allow it, or you add the Vite proxy. Make Vite listen on PORT (server.port: Number(process.env.PORT) with strictPort: true) so Flisk's port and the dev server agree.

Frameworks Flisk does not scaffold

Nuxt, SvelteKit, Astro, Angular, Remix and TanStack Start are server frameworks or use their own toolchain, so they are not Vite providers. Use --type bring-your-own for them, with a Dockerfile, as described in bring your own Dockerfile. Next.js is a special case with its own provider, covered in Next.js, Express and Postgres.

Pitfalls

  • A variable without the VITE_ prefix. It is silently undefined in the browser.
  • A bring-your-own backend. If the API is not a Flisk scaffold, it must allow http://app.<project>.localhost itself.
  • A stale value. Vite reads variables at start. Restart the frontend after any change.
  • Trailing slashes. A frontend served under /web builds links with that base path, so do not hard-code absolute paths that skip it.

Questions people ask

Why is import.meta.env.VITE_API_URL undefined?

Vite only exposes variables that start with VITE_ and reads them when the dev server starts. Check the name, put the value in .env.development or the service env, and restart the dev server.

Does Flisk support Vue and Svelte?

Yes, as Vite single page apps with --framework vue or --framework svelte. SvelteKit and Nuxt are not covered by these providers and use the bring-your-own type.

Do I need CORS if I use a Vite proxy?

Not in development, because the browser only talks to the Vite origin. You still need it when the frontend calls the API origin directly or when the two are deployed on different hosts.
