Run a FastAPI backend and React frontend locally

Two dev servers, two ports and one browser rule called CORS. Here is how to wire a FastAPI backend and a React frontend so one command starts both.

To run FastAPI and React together locally, start uvicorn with --reload for the API and npm run dev for the Vite frontend, then let the browser reach the API through a Vite proxy or through CORS. You can do this with two terminals. Flisk replaces the two terminals with one command, flisk up, and starts the API first.

Why two dev servers need wiring

FastAPI (through uvicorn) listens on one port, for example 8000. Vite serves your React app on another, usually 5173. A page loaded from http://localhost:5173 that calls http://localhost:8000 is a cross-origin request, and the browser blocks the response unless the API sends the right CORS headers. There are two honest fixes.

  • Proxy through Vite. The frontend calls relative URLs such as /api/items, and the Vite dev server forwards them to the API. The browser sees one origin, so there is no CORS problem in development.
  • Allow the origin in FastAPI. Add CORSMiddleware and list the frontend origin. This is also what you need in production if the two apps live on different hosts.

The proxy is simpler for development. CORS is needed anyway once the frontend and API are deployed separately, so it is worth setting up once.

The plain version without Flisk

This is the setup most tutorials use, and it works fine for a two-service project.

# terminal 1
cd api
uvicorn main:app --reload --port 8000

# terminal 2
cd web
npm run dev

In vite.config.ts, add the proxy:

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      '/api': { target: 'http://localhost:8000', changeOrigin: true },
    },
  },
});

And in FastAPI, allow the origin if you call the API directly:

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)

The cost of this setup is that you remember two commands, two ports and the start order. A new teammate has to read a README to run it.

The Flisk way: both services as local processes

Flisk can run a service as a plain process when its service.json has a command. No Docker, no Tilt and no generated files are involved. Install it and scaffold inside a Flisk project:

npm install -g @flisk-sh/flisk
flisk resource api --language python --local --stack app --yes
flisk resource web --local --stack app --yes

The first command writes a FastAPI service (pyproject.toml, src/main.py, a health test) whose command is a uvicorn line with --reload. The second writes a React frontend with a plain Vite config and command: npm run dev. That Vite config proxies /health and /api to the API's local port, which Flisk fills in when it scaffolds, so the frontend works without CORS.

A hand-written pair of manifests looks like this. The optional toolchain field states which runtime version the command needs. flisk up and flisk doctor compare it with the program on your PATH and stop with TOOLCHAIN_MISMATCH if it differs. Flisk installs nothing, so switch versions with your own version manager.

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "toolchain": "python@3.12",
  "command": "uvicorn main:app --app-dir src --reload --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "toolchain": "node@22",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "VITE_API_URL": "http://localhost:4000" }
}

Flisk passes PORT to each service, starts api before web because of dependsOn, waits for the health check, and prefixes every log line with the service name. Then run:

flisk up

Edit a Python file and uvicorn reloads. Edit a React file and Vite hot-reloads. Flisk does not add its own reloader here, the live reload comes from the tools you already use. Logs are also written to .flisk/native/logs/<service>.log, and flisk logs --service api --tail 50 prints the last lines of one service.

The CORS detail in native mode

In native mode the frontend runs on http://localhost:<port>, not on a Flisk subdomain. If your React code calls VITE_API_URL directly instead of going through the Vite proxy, your FastAPI app must allow that exact origin, for example http://localhost:3000 from the manifest above. The scaffolded API allows *.localhost origins, which is meant for the Docker route, so use the proxy or add your origin when you stay native.

Pitfalls and when not to use this

  • A port that is already taken. The scaffolded Vite config uses strictPort, so it fails instead of moving to another port. That is deliberate: Flisk checks and opens the exact port. Free the port or pick another.
  • A missing Python environment. Flisk runs your command, it does not create a virtualenv for you. Install the dependencies (pip install -e . or your usual tool) before the first start.
  • A database next to the API. A Postgres container needs Docker. Flisk allows ready-made image services such as Postgres next to command services, but not a service that builds its own Dockerfile.
  • One service only. If you only have a React app and an API and never forget the two commands, a Makefile or concurrently is enough. The value shows up when the setup grows past two services or a new person joins.

Questions people ask

Do I need CORS if I use the Vite proxy?

No. The browser only talks to the Vite origin, and Vite forwards the request. You still need CORS for any direct call to the API origin and for production setups where the two apps are on different hosts.

Does uvicorn --reload work under Flisk?

Yes. Flisk runs your command as a normal process, so the reload comes from uvicorn. Edit a file under the watched directory and the server restarts itself.

Can I run FastAPI and React with Flisk without Docker?

Yes. A service with a command in service.json runs as a local process with no Docker and no Tilt. Docker is only needed for services that use an image or a Dockerfile, such as a Postgres container.
