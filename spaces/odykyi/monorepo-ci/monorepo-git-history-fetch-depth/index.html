Git History in CI: fetch-depth and Finding the Merge Base

Why changed-file detection fails on a shallow clone, how to fetch just enough history in GitHub Actions and how to diff a pull request against the right base.

actions/checkout fetches a single commit by default, so any step that needs a diff against the base branch fails or sees the wrong files. Set fetch-depth: 0 for full history, or fetch the base branch explicitly and diff against the merge base.

What goes wrong on a shallow clone

With depth 1, the checkout contains one commit and no ancestors. Commands like git diff origin/main...HEAD either error with 'no merge base' or compare the wrong things. The symptom in CI is a changed-files step that reports every file, or no files, regardless of the real change.

Option 1: full history

- uses: actions/checkout@v4
  with:
    fetch-depth: 0

It is simple and correct. On huge repositories, the clone takes longer and uses more disk, so measure it.

Option 2: fetch only the base

Keep a shallow checkout and add what you need. For a pull request, fetch the base branch with enough depth to include the merge base.

- uses: actions/checkout@v4
  with:
    fetch-depth: 50
- name: Fetch base
  run: git fetch --no-tags --depth=200 origin ${{ github.base_ref }}

If a pull request is very old, 200 commits may not reach the merge base. Either deepen the fetch or fall back to running everything when no merge base is found. Failing safe, by running more, is better than silently running less.

Three dots or two dots

Use the merge base to see only what the branch changed.

git diff --name-only origin/main...HEAD

With three dots, git compares HEAD to the common ancestor with origin/main, which excludes changes that landed on main after you branched. Two dots compare against the current tip of main and show other people's changes as if they were yours. On a pull_request event, the checkout is a merge commit of the pull request into the base, so the diff of that merge commit against its first parent also works.

Push events and the default branch

On pushes, the base is the previous commit, available as github.event.before. For a first push of a new branch it is all zeros, so handle that case by comparing to the default branch. Test your detection script on three cases: a pull request, a push to main and a new branch. See the dynamic matrix article for a plan script that uses this, and debugging CI failures for general reading of such logs.

Add a guard to your planning script: if it cannot find a merge base, print a clear warning and run everything. This one rule turns a whole class of silent failures into harmless extra work. Log the base commit and the number of changed files at the top of the job, so a confusing result can be explained from the log alone.

Questions people ask

Is fetch-depth 0 slow?

It is slower on repositories with long history, but usually a few seconds to a minute. Measure it, then decide whether a targeted fetch is worth the extra complexity.

Why does my diff include files I did not touch?

You probably used two dots against a moving base branch. Use three dots, or the merge base explicitly, to see only your branch's changes.
