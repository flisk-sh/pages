Path Filters and Required Checks: Fix Stuck Pull Requests

Why a pull request waits forever on a required check when a workflow is skipped by a path filter, and the two reliable ways to fix it for good.

If a workflow is skipped because of paths or paths-ignore, its required status check never reports, and the pull request shows 'Expected: waiting for status'. Fix it by making one always-running summary job the only required check.

The problem

Branch protection waits for the named checks to report success. A workflow that never starts reports nothing, so the check stays pending. For example, a workflow filtered to src/** never runs on a README-only change, and if it is required, the merge is blocked even though nothing needed testing.

Note the difference: if a job inside a running workflow is skipped by if:, GitHub reports the check as success. If the whole workflow is skipped by a path filter, nothing is reported.

Fix 1: a summary job that always runs

Remove the path filter from the trigger, compute changes inside the workflow, and add a final job that depends on all others. Make only that job required.

jobs:
  changes: { ... }
  test-api:
    needs: changes
    if: needs.changes.outputs.api == 'true'
    runs-on: ubuntu-latest
    steps: [ ... ]
  ci-ok:
    if: always()
    needs: [changes, test-api]
    runs-on: ubuntu-latest
    steps:
      - name: Fail if any needed job failed
        env:
          RESULTS: ${{ join(needs.*.result, ' ') }}
        run: |
          case "$RESULTS" in *failure*|*cancelled*) exit 1;; esac

The if: always() is essential: without it the summary job is itself skipped when a dependency fails or is skipped.

Fix 2: duplicate no-op workflow

GitHub's documentation describes a second approach: create a second workflow with the same name and job names, triggered by the opposite path filter, that just reports success. It works, but it is easy to let the two drift apart, so prefer the summary job.

Rename carefully

When you change which job is required, branch protection still lists the old names until you remove them. Add the new check as required first, merge a test pull request, then remove the old requirements. Required checks are matched by name, so renaming a job breaks the gate silently.

Related traps

  • Matrix jobs create one check per combination. Requiring each by name is brittle, so require the summary job instead.
  • With a merge queue, workflows must also trigger on the merge_group event, or checks never report there.
  • A flaky required check teaches people to bypass the rule. Fix that first, see flaky tests and CI.
  • Back to the overview in running only what changed.

After the change, test the three cases on a scratch branch: a docs-only change, a code change that passes and a code change that fails. The first should merge with the summary check green, the second should run the real jobs, and the third should block. If the failing case still merges, your summary job is probably missing the if: always() line or a dependency in needs.

Questions people ask

Why is a skipped job treated as success but a skipped workflow is not?

A skipped job still belongs to a workflow run that reports a result. A workflow that never starts creates no run, so there is nothing to report to the required check.

Do I need the summary job if I have one workflow with no filters?

No. If every required job always runs, you can require them directly. The summary job helps when jobs are conditional or when matrix names change.
