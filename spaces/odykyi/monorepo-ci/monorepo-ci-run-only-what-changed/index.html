Monorepo CI: How to Run Only What Changed

Three ways to skip work for unchanged packages in GitHub Actions, from simple path filters to build-graph tools, with the trade-offs of each so you pick the right one.

Start with path filters on the workflow trigger, move to a changed-files job when one workflow covers many packages, and use a build tool's affected graph when packages depend on each other. Each step costs more setup and catches more cases.

Why run everything is the default and why it hurts

A monorepo with twenty packages that runs every test on every pull request wastes minutes on every change and trains people to ignore CI. The goal is not to skip checks. The goal is to run the checks that could have changed, and to be sure you did not miss one.

Option 1: path filters per workflow

The simplest approach is one workflow per area, each triggered only when its paths change.

on:
  pull_request:
    paths:
      - 'services/api/**'
      - 'libs/shared/**'
      - '.github/workflows/api.yml'

Include shared libraries and the workflow file itself in the list, or changes there silently skip the check. This works well when packages are independent. The trap with required checks is covered in this article on skipped required checks.

Option 2: one workflow, a changed-files job

A first job computes which areas changed, and later jobs run conditionally. This keeps one workflow file and lets you add one always-running summary job for branch protection.

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      api: ${{ steps.f.outputs.api }}
    steps:
      - uses: actions/checkout@v4
      - id: f
        uses: dorny/paths-filter@<pinned-sha>
        with:
          filters: |
            api:
              - 'services/api/**'
              - 'libs/**'
  api:
    needs: changes
    if: needs.changes.outputs.api == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo test api

Pin third-party actions, see GitHub Actions security.

Option 3: the affected graph

Tools such as Nx and Turborepo know the dependency graph between packages. If libs/shared changes, they also rebuild everything that imports it, which a hand-written path list often misses. See affected commands with Nx and Turborepo. The cost is adopting the tool and keeping its configuration accurate.

Which to pick, and the safety net

  • Fewer than five independent packages: path filters.
  • Many packages, one workflow, no build tool: changed-files job.
  • Packages that import each other: an affected graph.

Whatever you choose, run the full suite on the default branch after every merge and on a nightly schedule. A skipped test is a bet that your filter is right, and the full run is how you find out when it is not.

Prove the filter works before you trust it. Open three test pull requests: one that touches only a docs file, one that touches a single package and one that touches a shared library. Confirm that the first runs almost nothing, the second runs only that package and its dependents, and the third runs everything that imports the library. Write the results in the pull request that introduces the filter, so the next person can repeat the test when the structure of the repo changes.

Questions people ask

Will path filters miss tests when shared code changes?

Only if the shared paths are not in the filter. List shared libraries and the workflow file in every filter, or use a dependency-aware tool that finds affected packages for you.

Should the default branch run everything?

Yes. Running the full suite after merge catches filter mistakes and cross-package breakage that pull request runs skipped.
