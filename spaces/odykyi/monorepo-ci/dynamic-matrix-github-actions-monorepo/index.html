Dynamic Matrix in GitHub Actions for a Monorepo

Build the job matrix at run time from the packages that changed, so one workflow tests exactly the right set. Includes a working script and the empty matrix trap.

Compute a JSON list of changed packages in a first job, expose it as an output, and feed it to strategy.matrix with fromJSON. One workflow then fans out one job per changed package, with no hand-edited list.

The shape

jobs:
  plan:
    runs-on: ubuntu-latest
    outputs:
      packages: ${{ steps.p.outputs.packages }}
      any: ${{ steps.p.outputs.any }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: p
        run: ./scripts/changed-packages.sh origin/${{ github.base_ref }}

  test:
    needs: plan
    if: needs.plan.outputs.any == 'true'
    strategy:
      fail-fast: false
      matrix:
        package: ${{ fromJSON(needs.plan.outputs.packages) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cd packages/${{ matrix.package }} && npm ci && npm test

Note that ${{ github.base_ref }} is a branch name chosen by the repository, but treat any ref text carefully, see script injection.

The planning script

A small shell script turns changed paths into package names. This one assumes packages live in packages/<name>.

#!/usr/bin/env bash
set -euo pipefail
base=$(git merge-base HEAD "$1")
pkgs=$(git diff --name-only "$base" HEAD \
  | grep '^packages/' | cut -d/ -f2 | sort -u \
  | jq -R . | jq -sc .)
echo "packages=${pkgs:-[]}" >> "$GITHUB_OUTPUT"
if [ "$pkgs" = '[]' ] || [ -z "$pkgs" ]; then
  echo 'any=false' >> "$GITHUB_OUTPUT"
else
  echo 'any=true' >> "$GITHUB_OUTPUT"
fi

Add logic for shared directories: if libs/ or the lockfile changed, output all packages.

The empty matrix trap

A matrix with an empty list makes the workflow fail with an error that the matrix must define at least one vector. That is why the example has an any flag and an if: on the test job. When the test job is skipped, pair it with a summary job so branch protection still works, see path filters and required checks.

Limits and tips

  • A matrix can have at most 256 jobs per workflow run. For large repos, group packages into batches.
  • Use fail-fast: false so one failing package does not hide results from the others.
  • Include richer objects in the matrix, for example {"name":"api","node":"20"}, and read matrix.package.name.
  • Print the plan in the job summary so reviewers see why a package ran.

When not to do this

If packages depend on each other, a path-based plan is wrong: it will skip a dependent when its dependency changes. Use a dependency-aware tool instead, see Nx and Turborepo affected runs. Dynamic matrices also make cache keys and job names harder to read, so keep them for cases where static jobs would be unmanageable.

Log the plan so it is visible. Write the list of selected packages to the job summary with echo 'Packages: ...' >> "$GITHUB_STEP_SUMMARY", and a short reason for each. When a developer asks why their package did not run, the answer is one click away instead of a code reading session. Unit test the planning script with a few fake diffs, because a bug there silently skips tests.

Questions people ask

Can a job output hold large JSON?

Job outputs have a size limit, around one megabyte per job, so keep the matrix small. Pass only package names and let each job look up the details.

Why does fromJSON fail?

Usually the output is empty or not valid JSON. Print it in the plan job and make sure an empty result is the string [] and not nothing.
