Test a Multi-Service Monorepo Locally the Way CI Does

Run the same service stack on a laptop and in CI so integration tests behave the same, using Docker Compose or the Flisk CLI, and keep one command for both.

Define the stack once, start it with a single command locally and in CI, wait for health checks, then run integration tests against it. When developers and CI use the same command, 'works on my machine' failures shrink.

The problem

A monorepo with an API, a worker, a database and a queue is tested in CI by one set of scripts and run locally with another. They drift, and integration failures appear only in CI. The fix is one source of truth for how services start, and one script for tests that does not care where it runs.

Option 1: Docker Compose

Compose is the common baseline. Put health checks on services so tests can wait for them.

docker compose up -d --wait
npm run test:integration
docker compose down -v

The --wait flag makes up block until services with health checks report healthy. In CI, dump logs on failure with docker compose logs so a red run is debuggable, see debugging CI failures.

Option 2: the Flisk CLI

Flisk is an open-source (MIT) CLI that runs services, databases, queues and agents locally from one service.json per service, which suits a monorepo where each package already has a folder. Create a service with flisk resource <name> --type backend, start everything with flisk up, and read the state with flisk status --json. Services that declare a command run as local processes, and container stacks use Docker and Tilt. Run flisk doctor to check the environment. It is a local development tool, not a production orchestrator, so keep your production deployment story separate. Try npx @flisk-sh/flisk demo to see it, and read the docs at flisk.sh/docs. More background is in microservices local dev and CI for multi-service apps.

A CI job that mirrors local use

jobs:
  integration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose up -d --wait
      - run: npm ci && npm run test:integration
      - if: failure()
        run: docker compose logs --no-color | tail -300
      - if: always()
        run: docker compose down -v

The same two commands work on a laptop, so a failure can be reproduced exactly.

Keep it fast and deterministic

  • Start only the services a test needs, not the whole stack. Group tests by the services they require.
  • Seed data from files in the repo, never from a shared database.
  • Use random free ports or fixed ones documented in one place, see dev environment troubleshooting.
  • Run the integration job only when affected services change, using the approach in run only what changed, and run the full set nightly.

Finally, document the one command in the README and the contributing guide, and keep CI calling the same script. If a developer must remember three commands and a flag, they will skip the integration tests locally and discover failures in CI an hour later. One command, one result, the same everywhere.

Questions people ask

Docker Compose or Flisk?

Compose is universal and fine for container-only stacks. Flisk is worth a look when you want services as local processes with live reload plus containers for data stores, from one service.json per service.

Should integration tests run on every pull request?

Run them for affected services on pull requests, and the full integration suite after merge and nightly. This keeps feedback fast while still catching cross-service breakage.

Try it locally

Run the same multi-service stack on your laptop that CI tests.
