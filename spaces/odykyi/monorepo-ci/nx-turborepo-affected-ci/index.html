Nx and Turborepo in CI: Run Only Affected Tasks

How to use the affected and filter commands of Nx and Turborepo in GitHub Actions, why they need git history, and when a build tool is overkill for your repo.

Both Nx and Turborepo read the dependency graph between your packages, so they can run tasks only for packages that changed or depend on something that changed. In CI you give them a base commit to compare against, and you must fetch enough git history for that comparison to work.

Nx affected

Nx runs a target for every project touched by the diff, plus projects that depend on them.

npx nx affected -t lint test build --base=origin/main --head=HEAD

The -t flag lists the targets to run. Nx also provides a GitHub Action to set the base and head SHAs correctly for pull requests and pushes, so check its documentation for the current setup. The flags above are stable, but verify them against the Nx version you use.

Turborepo filter

Turborepo filters packages by git ranges.

npx turbo run test build --filter='...[origin/main]'

The three dots before the bracket mean 'packages changed since origin/main, plus their dependents'. Without the leading dots you get only the changed packages and miss the ones that depend on them, which is rarely what you want in CI.

Give the tool the history it needs

actions/checkout fetches only one commit by default, so there is no base to compare against. Fetch more:

- uses: actions/checkout@v4
  with:
    fetch-depth: 0

Full history is the safest option, but it is slower for huge repositories. A shallow depth that still includes the merge base also works, and is covered in the git history article.

Add a task cache

Both tools can replay results of unchanged tasks from a cache. In CI that cache disappears with the runner unless you persist it or use the tool's remote cache. With a remote cache, a task that ran on one machine is a cache hit on every other. Choose a remote cache provider you trust, since cached outputs flow into your builds, and read the tool's docs for authentication, which should use short-lived or scoped tokens, see secrets best practices.

When not to adopt a build tool

If your repo has a handful of independent packages, path filters are simpler and have no new config to maintain. A build tool earns its place when packages import each other, builds are slow and the graph is large. Its config must also stay true: a wrong dependency declaration means a wrongly skipped test. Keep a nightly full run, as advised in running only what changed.

Keep the tool versions pinned in the lockfile and read the release notes before upgrading, since filter syntax and cache behaviour can change between major versions. Add a job that runs the full task graph without the affected filter on a schedule, so a mistake in package dependencies shows up as a failing nightly build instead of a production bug.

Questions people ask

Do I still need path filters with Nx or Turborepo?

Usually not for tasks, since the tool decides what is affected. You may keep a filter for workflows that do not use the tool, such as docs deployment.

Why does affected run nothing on my branch?

The base is probably wrong or the history is shallow, so the tool sees no diff. Fetch full history and check that the base ref exists in the runner's clone.
