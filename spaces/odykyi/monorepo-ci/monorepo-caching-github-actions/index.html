Caching Dependencies in a Monorepo with GitHub Actions

Key the cache by lockfile, share it across packages, avoid cache thrash from too many matrix entries and know which caches are worth restoring at all.

Cache the package manager's download store, keyed by the lockfile hash, and let all jobs share one key per lockfile. Do not cache node_modules blindly, and measure whether restoring the cache is actually faster than installing.

The simple, reliable version

Most setup actions can cache the package manager store for you. For Node:

- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm
    cache-dependency-path: '**/package-lock.json'

The cache-dependency-path matters in a monorepo: by default the action looks only at the root lockfile. Python (setup-python with cache: pip) and others have similar options. This caches downloaded packages, and you still run the install, which is quick when everything is local.

A manual cache key

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      npm-${{ runner.os }}-

The restore-keys fallback gives a partial hit from the nearest older cache when the lockfile changes, so you download only the difference.

Pitfalls specific to monorepos

  • Cache scope: a pull request can read caches from its base branch but not from sibling branches. Make sure the default branch populates the cache by running the same workflow there.
  • Size limit: a repository has a total cache quota and old entries are evicted. Check GitHub's current limit in its docs. A giant monorepo with a different key for every package fills it fast and evicts everything.
  • Cache thrash: if every matrix job saves its own key, you store many near-identical entries. Share one key per lockfile instead.
  • Saving on failure: by default a cache is saved only when the job succeeds.

Build caches

For compiled output, tools such as Turborepo and Nx keep a task cache keyed by the inputs of each task. Persist that directory in CI, or use the tool's remote cache, so unchanged packages replay from cache. Check the tool's own documentation for the current setup, since remote cache options differ. The details of those tools are in the affected article. Docker layer caching needs its own setup in the Buildx cache options.

Measure it

Open a job log and compare the time of the restore step plus install against a cold install. If restoring a large node_modules cache takes longer than npm ci with a warm download store, drop it. Keep a before-and-after record, as described in faster GitHub Actions. Do not cache secrets or tokens, since caches can be read by other workflows on the same branch scope.

Review cache use monthly. In the repository settings, look at the cache list: which keys exist, how large they are and when they were last used. Delete entries that are never hit, and fix the key patterns that produce one entry per run. A tidy cache list is a quick check on whether your keys are doing what you think.

Questions people ask

Should I cache node_modules?

Usually cache the package manager's download store instead. Restoring node_modules can be slower than reinstalling from a warm store, and it can hide dependency problems.

Why is my cache never hit on pull requests?

Pull requests can only restore caches from their own branch and the base branch. If the default branch never saves that key, nothing exists to restore.
