Multi-agent system patterns

How to hand off work between AI agents without losing context

A handoff is a message from one agent to another. Make it a typed contract with the goal, the facts, the constraints and the expected result.

A good handoff is a structured message, not a chat transcript: it states the goal, the facts the next agent needs, the constraints, and the format of the answer you expect. Dumping the full history into the next agent wastes tokens and buries the important parts.

What a handoff must carry

The receiving agent starts with an empty head. Everything it needs has to be in the message.

  • Goal: what done looks like, in one or two sentences.
  • Inputs: the data, file paths or ids to work on.
  • Decisions already made: so the next agent does not reopen them.
  • Constraints: time, budget, forbidden actions.
  • Output schema: the exact shape you will parse.

Think of the handoff as an API between two teammates who cannot ask follow-up questions. If a human colleague could not do the job from your message alone, neither can the model. Read your handoff once as if you had never seen the project, and add whatever you would have to guess.

Write it as a typed contract

Define the handoff as a schema and validate it on both sides. A missing field then fails loudly instead of causing a vague wrong answer later.

from pydantic import BaseModel

class Handoff(BaseModel):
    task_id: str
    goal: str
    inputs: dict
    decisions: list[str] = []
    constraints: list[str] = []
    reply_schema: dict

class Reply(BaseModel):
    task_id: str
    status: str  # "ok" or "failed"
    output: dict
    notes: str = ""

The sender builds a Handoff, the receiver returns a Reply. Reject anything that does not parse.

Summarize, do not forward

If earlier work matters, summarize it into the decisions list. Pass pointers to big artifacts, such as a file path or a database row id, instead of pasting them. The receiver can read the artifact if it needs to.

A useful rule: a handoff message should fit on one screen. If it does not, the task is probably too large for one worker.

Handoff pitfalls

Lost constraints. A rule given to agent A, like "never delete files", must be repeated in the handoff to agent B. Do not assume it is inherited.

Ping-pong. Two agents handing a task back and forth forever. Add a hop counter to the message and stop at a limit. See limits on loops and cost.

Silent partial results. Always include a status field so a failure is data the sender can act on.

Log every handoff

Write each handoff and reply, with the task id, to a log or database. When a final answer is wrong, you can follow the task id back through each hop and find where the information changed. More on this in tracing and debugging multi-agent runs.

Questions people ask

Should I pass the whole conversation to the next agent?

Usually not. Pass a short summary and the facts it needs. Full history costs tokens and distracts the model.

How do I stop agents handing work back and forth?

Put a hop counter in each handoff and refuse to continue past a fixed limit, then escalate to a person or fail the task.
