How to run parallel coding agents with git worktrees

Give each agent its own working directory and branch so they never edit the same files. A few git commands set it up and tear it down.

Create one git worktree per agent, each on its own branch, and run each agent inside its directory. They share one repository but have separate working files, so parallel edits cannot collide, and you merge the branches when they finish.

Why worktrees

Two agents in one checkout will overwrite each other, switch each other's branches and fight over the index. Cloning the repo several times works but wastes disk and duplicates history. A git worktree is a second working directory attached to the same repository, so it is cheap and fast.

Create and remove them

# from the main checkout
git worktree add ../agent-a -b agent/a main
git worktree add ../agent-b -b agent/b main

git worktree list

# when an agent is done and merged
git worktree remove ../agent-a
git branch -d agent/a

A branch can be checked out in only one worktree at a time. That constraint is useful here: it stops two agents from sharing a branch by accident. Remove only the worktrees you created. Other tools and people may have their own.

Start one agent per worktree

Run each agent with its working directory set to its worktree. With a CLI coding agent that is as simple as opening a terminal in ../agent-a and starting the agent there. Give each a separate, scoped task so the diffs touch different files where possible.

  • Split by area: one agent on the API, one on the docs, one on tests.
  • Tell each agent which files are off limits.
  • Keep a task file per agent so you can see what each was asked.

Write the task into a short file in each worktree, for example TASK.md, with the goal, the files in scope and the command that proves it works. The agent reads it at the start, and you can read it later to check whether the result matches what was asked.

Merging and conflicts

Merge the branches one at a time, running tests after each. Conflicts show up exactly where two agents touched the same lines, which tells you the split was not clean.

git checkout main
git merge --no-ff agent/a && npm test
git merge --no-ff agent/b && npm test

Review every diff before merging. Parallel agents multiply the amount of code to read, which is the real limit on how many you can run. Work on coding agents in practice covers review habits.

Pitfalls

Worktrees share the repository but not installed dependencies or running servers. Each needs its own node_modules or virtualenv, and servers must use different ports. Shared resources such as one local database can still collide, so give each agent its own database name. FliskOS is a desktop app for running coding agents such as Claude Code and Codex side by side if you prefer not to manage terminals by hand.

Questions people ask

Is a worktree the same as a clone?

No. A worktree shares one repository and history with the main checkout, so it uses less disk and branches are visible to both.

How many parallel agents should I run?

As many as you can review. The limit is usually your ability to read the diffs, not the machine.
