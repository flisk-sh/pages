Multi-agent system patterns

Why multi-agent systems fail, and how to plan for it

The common failures are loops, lost context, conflicting writes and runaway cost. Know them early and design guards for each.

Multi-agent systems fail in a few repeatable ways: endless loops, information lost at handoffs, two agents overwriting each other, silent wrong answers passed on as fact, and cost that grows faster than value. Each has a cheap guard you can add before launch.

Loops and ping-pong

Agent A asks B to fix something, B asks A to review, and it repeats. Nothing crashes, but the bill grows. Guard: a hop count and a total step budget in every message, and a hard stop that escalates to a person.

A simple version is a counter in the task record: increment it on each handoff, and when it passes a fixed number such as 8, mark the task failed with the reason "hop limit" and notify a person.

Lost or distorted context

Each handoff is a summary, and summaries drop details. By the third hop a constraint such as "do not touch production data" may be gone. Guard: carry constraints as a separate field in every handoff, and re-check them on the receiving side. See the handoff guide.

Errors that compound

If one agent returns a confident wrong fact, the next treats it as true. With five hops, small error rates add up. Guard: validate outputs between steps with code where you can, such as schema checks, tests, or a lookup against the source. Use a second model as a checker only when no deterministic check exists.

Conflicting writes and duplicate work

Two workers claim the same task, or two agents edit the same file. Guard: claim tasks atomically from a queue, one owner per record, and version checks on writes. See shared state.

Cost and rate-limit blowups

Ten parallel workers can hit a provider rate limit in seconds, and retries then multiply the problem. Guard: a concurrency cap, exponential backoff with jitter on retries, and a per-run token budget that stops the run when exceeded.

import asyncio
sem = asyncio.Semaphore(4)  # at most 4 model calls at once

async def call(task):
    async with sem:
        return await run_worker(task)

Test these guards on purpose. Force a worker to return nonsense, make a tool time out, and feed in a task that causes a loop, then confirm each guard fires. A guard you have never triggered is a guess, and the first real failure will be the first time it runs.

Make failure visible

The worst failure is the quiet one: the run finishes and returns a plausible answer built on a failed step. Mark every task result as ok or failed, and make the final step refuse to answer, or say what is missing, when a required task failed. Then keep traces so you can see what happened, as described in tracing and debugging multi-agent runs.

Questions people ask

What is the most common multi-agent failure?

Runaway loops and lost context at handoffs. Both are cheap to guard against with step budgets and typed handoff messages.

Should a second model check the first model's work?

Only when you cannot check deterministically. Prefer schema validation, tests and source lookups, which do not share the first model's blind spots.
