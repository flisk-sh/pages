Multi-agent system patterns

How to build the orchestrator-worker pattern for AI agents

One agent splits a job into tasks, several workers do them, and the orchestrator merges the results. Here is the shape, the code and the traps.

The orchestrator-worker pattern uses one agent to break a job into small tasks and hand each to a worker agent with a narrow job and its own context. The orchestrator then collects the results and decides what happens next. It is the most common multi-agent design because it keeps control in one place.

The shape of the pattern

There are three parts. The orchestrator reads the user goal and writes a plan. Workers take one task each, run with only the context they need, and return a result. A merge step turns the results into the final answer or into the next plan.

Workers never talk to each other. All traffic goes through the orchestrator. That makes the system easy to reason about and easy to log, because every message has one sender and one receiver.

A minimal orchestrator loop

Keep the plan as data, not prose. Ask the orchestrator for a JSON list of tasks, validate it, then run the tasks.

import asyncio, json

async def orchestrate(goal, llm, run_worker):
    plan = json.loads(await llm(f"Split into independent tasks as a JSON list of {{id, instruction}}: {goal}"))
    results = await asyncio.gather(*(run_worker(t) for t in plan))
    return await llm(f"Goal: {goal}\nResults: {json.dumps(results)}\nWrite the final answer.")

The llm and run_worker functions are yours: any model client and any worker that returns a JSON-serializable result. Parse failures on the plan are common, so wrap the json.loads in a retry that feeds the error back to the model once.

Give each worker a narrow brief

A worker should get the task, the few facts it needs, the tools it may use and the output format. Not the whole conversation. Small contexts are cheaper, faster and less likely to drift.

  • One task per worker call. If a worker needs to plan, it is an orchestrator in disguise.
  • Define the result schema up front, for example {"id": ..., "status": "ok|failed", "output": ...}.
  • Give workers only the tools their task needs. A summarizer does not need shell access.

Pitfalls

The orchestrator is a single point of failure and a bottleneck. If it writes a bad plan, every worker does bad work in parallel. Check the plan before running it: task count within a limit, no duplicate ids, no task that asks for more than the worker can do.

Workers also fail on their own. Decide in advance what a failed task means: retry once, skip and note it, or stop the run. Passing the failure to the orchestrator as data lets it replan.

Finally, watch cost. Ten workers each carrying a long context is ten times the tokens. See how to put limits on agent loops and cost.

When not to use it

If the task is a straight line of steps that each depend on the last, one agent with tools does the job with less overhead. The pattern pays off when tasks are independent and can run in parallel, or when different tasks need different tools or models. The next guide, single agent or multi-agent, covers that choice.

Questions people ask

How many workers should an orchestrator run at once?

Start with 3 to 5 and measure. The limit is usually your model rate limit and your token budget, not the code.

Can the orchestrator and workers use different models?

Yes, and it is common. Use a stronger model to plan and a smaller, cheaper model for routine worker tasks.
