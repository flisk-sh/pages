Single agent vs multi-agent: when you actually need more than one

Most tasks run fine with one agent and good tools. Here is a short test for when splitting into several agents earns its cost and complexity.

Use one agent with tools until you hit a concrete problem it cannot solve: tasks that can run in parallel, contexts that overflow, or roles that need different permissions. Multi-agent systems add latency, tokens and failure modes, so the default should be a single agent.

Start with one agent

A single agent with a handful of tools is easy to debug. There is one conversation to read and one place where a decision was made. Many systems described as multi-agent are really one agent with a long prompt and three tools. That is fine and often the right design.

Before you split, try these first: a better system prompt, clearer tool descriptions, fewer tools, and a summary step that shrinks old context.

Four good reasons to split

  1. Parallel work. Independent subtasks, such as reviewing ten files, finish faster when run side by side.
  2. Context size. A long job fills one context window. Workers with fresh contexts return short summaries instead.
  3. Different permissions. An agent that reads the web should not also hold the deploy key. Separate agents let you give each the smallest set of tools.
  4. Different models. A cheap model for classification and a stronger one for reasoning can cut cost without hurting quality.

A practical middle path is a single agent that can call a sub-agent as a tool. The main agent stays in charge and keeps one transcript, while the sub-agent handles one bounded job, such as searching a large codebase, and returns a short answer. You get context savings without a full multi-agent design.

Costs of splitting

Every handoff is a place where information is lost. The worker only knows what you told it. Every extra agent also adds a model call, so latency and tokens go up. You now need to trace requests across agents, retry partial failures and handle two agents disagreeing.

A quick test

Ask three questions. Can the subtasks run without seeing each other's output? Does one task need tools or permissions another must not have? Does the work overflow one context window? Two yeses means a split is likely worth it. Zero means keep one agent.

If you do split, begin with the simplest layout, an orchestrator and workers, described in the orchestrator-worker guide.

Measure before and after

Keep a small set of real tasks and run both designs on them. Compare success rate, total tokens and wall-clock time. If the multi-agent version is not clearly better on at least one of these, go back to one agent. For how to build that task set, see testing and evaluating AI agents.

Questions people ask

Is multi-agent always more accurate?

No. It can be worse, because each handoff drops context and errors compound. Measure on your own tasks.

Does one agent calling several tools count as multi-agent?

No. Tool calling is one agent. Multi-agent means several model-driven loops with their own context that pass work between them.
