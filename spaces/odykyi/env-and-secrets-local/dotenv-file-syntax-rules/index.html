Why your .env file is not parsed: quotes, comments and $ signs

Two tools can read the same .env file and disagree about it. Learn the rules that most often differ, and how to check what a process really received.

When a value in a .env file comes out empty, cut short or full of strange characters, the cause is nearly always one of five syntax rules: spaces around =, an unclosed quote, a # that starts a comment, a $ that is read as a variable, or a multiline value. The file has no formal standard, so each tool decides for itself, and the same line can mean different things to your shell, to Docker Compose and to a Node.js loader.

The rules that differ between tools

A .env file looks like shell, but it is not shell. Nothing runs it, and each loader implements a subset. These are the places where subsets disagree:

  • Spaces. NAME = value is not a valid shell assignment, and some loaders reject it or keep the space in the key. Write NAME=value with nothing around the equals sign.
  • Quotes. Double quotes usually allow escapes such as \n. Single quotes usually keep everything literally. An unclosed quote can swallow the rest of the file, or just the rest of the line, depending on the parser.
  • Comments. A full line starting with # is a comment everywhere. A # in the middle of a value is where parsers split: some strip it only after whitespace, some strip it always, some never. A password such as ab#cd is a classic casualty.
  • Dollar signs. Docker Compose expands $NAME and ${NAME} in .env files and in Compose files. A password pa$word silently loses $word. In a Compose file you escape it as $$. Single-quoted values in Compose's own .env reading stay literal.
  • Multiline values. Private keys and certificates span lines. Some parsers accept a double-quoted value with real newlines, some want \n escapes, some cannot do it at all.
  • export prefix. export NAME=value is accepted by most loaders so the file can also be sourced by a shell, but not all.

The safe subset is small: one KEY=value per line, no spaces around the equals sign, comments on their own lines, and quotes around anything with a space, a # or a $. When a value is long or binary, such as a certificate, store it as a base64 string and decode it in code.

Check what the process received

Do not reason about the file, look at the result. Print the variable from inside the running process, and print its length rather than the whole value if it is a secret. In Node.js:

node -e "console.log(JSON.stringify(process.env.DB_PASSWORD), (process.env.DB_PASSWORD || '').length)"

JSON.stringify makes invisible problems visible: a trailing space, a leftover quote character, a \r from a Windows line ending. A \r at the end of every value is the usual sign that the file was saved with CRLF line endings. Convert it to LF.

What Flisk's .env parser does

Flisk reads the project .env with a deliberately small Compose-compatible parser. From its documentation:

  • export NAME=value works.
  • An unquoted inline comment is stripped only when the # is preceded by whitespace, so ab#cd keeps its #.
  • A quoted value ends at its matching quote and ignores the rest of the line.
  • Double-quoted values decode \n, \r, \t, \", \\ and \$. Single-quoted values stay literal, and \' is accepted for an embedded quote.
  • Variable interpolation, colon separators and multiline values are not implemented. NAME="" and NAME='' count as empty.

Container interpolation is still done by Compose afterwards, so a $ in a value you put in .env is a risk there. Prefer single quotes, or avoid $ in passwords you choose yourself. The values Flisk generates are hex strings, so they are safe.

For non-secret settings in service.json, the params field handles quoting for you. A plain value stays bare. A value with a space, #, $, a quote, a backslash, a newline, or an empty value is double-quoted with those characters escaped, and $ becomes $$:

{ "params": { "PLAIN": "ok", "GREETING": "hello world", "NOTE": "a # b", "PRICE": "$5" } }

That is written to the generated env file as PLAIN=ok, GREETING="hello world", NOTE="a # b" and PRICE="$$5". In the container, PRICE arrives as $5. Never edit that generated file by hand. Change params and regenerate, as described in generated config out of date.

To see what a stack service really received, run a command with its environment:

flisk run orders-api -- printenv GREETING

Pitfalls

  • Do not trust an editor's syntax highlighting. It colours a line the way it guesses, not the way your loader reads it.
  • If a value works in your shell but not in the file, the shell removed the quotes before the program saw them.
  • Changing the file does not change a running process. Restart the service. Environment variable not loaded walks through the other causes.
  • A file with two definitions of the same name uses the last one in most loaders, but not in all of them. Delete the duplicate instead of relying on it.

Once the syntax is right, the next question is which file wins when several define the same name. That is covered in which .env file wins.

Questions people ask

Why does my password lose characters after a dollar sign?

Docker Compose expands $NAME and ${NAME} in .env files and Compose files, so pa$word becomes pa. Escape the dollar as $$ in a Compose file, or single-quote the value in the .env file.

Can a .env value contain a # character?

Usually yes, if you quote it. Parsers differ on unquoted values: Flisk's parser strips a comment only when the # follows whitespace, others strip from any #. Quote the value to be safe.

Does Flisk support multiline values in .env?

No. Its project .env parser does not implement multiline values or interpolation. Store a certificate as one base64 line and decode it in your code.
