Env vars and secrets in local dev

How to stop a local service from calling production by accident

The scary bugs here are quiet: the app works, and the data lands in someone else's system.

Make every value that points at a service resolve to something on your machine by default, use test or sandbox credentials for anything external, and run a check that lists env values naming a remote host. The usual cause is a .env copied from staging or production "just to get it running", after which a local test run deletes real rows or sends real emails.

How it goes wrong

  • A teammate shares their .env in chat, and it contains DATABASE_URL for the shared staging database.
  • A seed or reset script runs against it. Nothing in the script knows the difference.
  • A webhook URL or EMAIL_HOST is a real one, so tests send real messages.
  • A payment key is live. Even a "test" purchase is real money.

The symptoms are subtle: data you did not create shows up in your local app, unexplained 401 errors because a token was issued by another environment, or a colleague asking why their staging data vanished.

Defaults that prevent it

  1. Local defaults for everything. The example file and the manifest should point at local services: localhost, a container name, or *.localhost.
  2. Sandbox credentials for third parties. Use the test mode or sandbox of each provider, with keys that cannot touch production. Keep them separate from production keys, in a different secret file.
  3. Fail on suspicious hosts. A short startup check that refuses to run destructive commands (reset, seed, migrate down) when DATABASE_URL does not point at localhost saves real data.
  4. Least privilege. If someone must read from a shared environment, give them a read-only role instead of the application's owner role.

A simple guard for a seed script:

const host = new URL(process.env.DATABASE_URL).hostname;
if (!["localhost", "127.0.0.1", "db", "postgres"].includes(host)) {
  throw new Error(`Refusing to seed ${host}: not a local database`);
}

Adapt the allowed list to your container names.

Let Flisk list the remote hosts

flisk doctor has a check for exactly this. It looks at the project .env, each service's env and params in service.json, and the .env, .env.local, .env.development and .env.development.local files in each service folder. It looks for URLs and for values of names ending in _HOST, _HOSTNAME or _DOMAIN, and warns about any whose host is not local. The output names the service, the variable, the host and the file, never the value:

⚠ 2 values point outside the local stack:
    orders-api DATABASE_URL -> db.shared.example.com (services/shop/orders-api/.env.local)
    (project) AUTH_ISSUER -> auth.dev.example.com (.env)

What counts as local: localhost, *.localhost, *.local, *.internal, loopback and private IP addresses, one-word names such as Compose service names, and the names of the project's services and stacks. It is a warning by default. Run flisk doctor --strict to make it fail, for example in CI or a pre-push hook.

Some hosts are meant to be remote, like a payment sandbox or a model API. List them once in .flisk/project.json so the warning stays meaningful:

{
  "allowedHosts": ["api.stripe.com", "*.openai.com"]
}

A leading *. matches every subdomain. Keep the list short, and think twice before adding a host that could hold real customer data. Edit .flisk/project.json directly, then run flisk config regenerate as the documentation advises after changing it. flisk doctor may need Docker for its other checks, so run it where your stack runs.

Limits of the check

  • It reads configuration files. A host that your code builds at runtime, or a hardcoded URL in the source, will not be found.
  • It does not read values you export in your shell, so a leftover export DATABASE_URL=... from last week is invisible to it. Check with flisk run orders-api -- printenv DATABASE_URL when something looks wrong.
  • It says nothing about credentials. A local host with a production password is still a bad idea.

If real data may already have been touched, pause, tell the owner of that system, and fix the config first. For a related mystery where a value will not take effect, see environment variable not loaded. And when a shared database is genuinely needed, DATABASE_URL and env vars locally shows how to keep the local one as the default.

Questions people ask

How can I tell if my local app is using a remote database?

Print the variable the process sees, for example flisk run orders-api -- printenv DATABASE_URL, and look at the host. flisk doctor also warns about env values that point outside the local stack.

What does allowedHosts do in Flisk?

It lists hosts that env values may point at on purpose, such as api.stripe.com. Hosts on the list stop triggering the remote-host warning from flisk doctor.

Does flisk doctor read my shell environment?

No. The remote-host check reads the project .env, service env and params, and the .env files in each service folder, not variables exported in your shell.
