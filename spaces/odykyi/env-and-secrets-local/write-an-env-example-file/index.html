Env vars and secrets in local dev

How to write a .env.example file that stays up to date

A new developer should know what to fill in without reading the code. An example file only works if it cannot rot.

A .env.example is a committed copy of your .env with the names kept and the secrets replaced by placeholders. It tells a new developer what to set, and it stays accurate only if something fails when it is out of date. Without that check, it is a README that nobody updates.

What goes in the file

For every variable the app reads, include four things: the name, a safe example value, a one-line comment saying what it is for, and whether it is required. Group related names and leave secrets obviously fake.

# Postgres connection, required. Local default works with the Compose database.
DATABASE_URL=postgres://app:app@localhost:5432/app

# Required. Generate with: openssl rand -hex 32
SESSION_SECRET=

# Optional. Leave empty to disable error reporting.
SENTRY_DSN=

# Optional. Defaults to info.
LOG_LEVEL=info

Some conventions that help:

  • Empty means "you must fill this". Use a real harmless default only when the app works with it. Never put a value that looks real, such as a live-looking API key.
  • Say how to get it. A comment with the command or the dashboard URL saves a question in chat.
  • Name the file consistently. .env.example is the most recognised name. Some projects use .env.sample or .env.template. Pick one.
  • Keep it flat. Do not rely on interpolation inside the file, because loaders disagree about it. See the syntax rules.

Stop it from drifting

Three small checks make the file trustworthy:

  1. Validate at startup. Read variables in one config module and throw a message naming the missing one. The code is the source of truth, and the example file is documentation of it.
  2. Compare the names in CI. A short script that extracts the keys from the example and the keys your code reads, and fails on a difference, is enough:
#!/usr/bin/env bash
# fail when code reads a variable the example does not list
used=$(grep -rhoE 'process\.env\.[A-Z_][A-Z0-9_]*' src | sed 's/process\.env\.//' | sort -u)
listed=$(grep -oE '^[A-Z_][A-Z0-9_]*' .env.example | sort -u)
missing=$(comm -23 <(echo "$used") <(echo "$listed"))
if [ -n "$missing" ]; then echo "Not in .env.example:"; echo "$missing"; exit 1; fi
  1. Test the first run. The most honest check is a fresh clone: copy the example to .env, follow the README, and see if the app starts. Do it when you onboard someone, and fix whatever they hit. Onboarding a developer on day one describes that routine.

The grep above is for Node-style code. Adapt the pattern for os.environ in Python or os.Getenv in Go.

How this looks with Flisk

Flisk does not write a .env.example for you, but it keeps one safe. The .gitignore that flisk project writes contains .env, .env.* and !.env.example, so the example file is the one variant that stays committable.

The list of names also lives in service.json, which is committed and checkable:

{
  "secrets": {
    "required": ["STRIPE_KEY"],
    "optional": ["SENTRY_DSN"]
  }
}

A required name with no value in the env file of the run or in the environment makes flisk up stop before anything starts, naming the service and the secret, and printing the fix: add NAME=value to .env, export it, or move it to optional. That is the startup validation from step one, done for every service at once. Listing the same names in the example file keeps it useful for people who read it before they install anything. Using service.json as a team contract covers the wider idea.

Pitfalls

  • A real credential pasted into the example "just for now" is a leak. Review the file in every pull request that touches it.
  • Do not use the example as a deploy template. Production values come from your platform.
  • If your example has fifty variables, most of them probably deserve defaults in code, so new developers have fewer lines to fill in.

Names you commit are safe. Values are the part to protect, which is the subject of gitignoring env files safely.

Questions people ask

Should .env.example be committed?

Yes. It holds names and harmless placeholders, no real values, so it is safe in git and helps new developers.

Does Flisk generate a .env.example?

No. It generates a project .env with working defaults and a gitignore that keeps .env.example committable. The names a service needs go under secrets in service.json.

How do I keep .env.example in sync with the code?

Validate variables at startup and add a CI script that compares the names the code reads with the names in the file.
