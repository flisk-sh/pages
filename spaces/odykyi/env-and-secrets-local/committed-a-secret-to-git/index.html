Env vars and secrets in local dev

I committed a secret to git: what to do, in order

Deleting the file in a new commit does nothing for the secret. Treat it as public from the moment it was pushed.

Rotate the secret before you do anything else. Once a credential has been pushed, assume someone or something has copied it, because bots scan public repositories within minutes. Cleaning the history is worth doing, but it is the second step, and it never makes a leaked secret safe again.

Step 1: revoke and replace

Go to the service that issued the secret and create a new one, then revoke the old one. Update wherever the new value is used. Order of work depends on the secret:

  • API keys and tokens: revoke in the provider's dashboard, create a new key, update your secret store.
  • Database passwords: change the password in the database (ALTER ROLE app PASSWORD '...' in Postgres), then update the services.
  • Signing keys (JWT, sessions): issue a new key. Existing tokens signed with the old one stop being valid, which is the point.
  • Cloud credentials: deactivate the key and check the account for new resources you did not create.

If the value was only a local development password that never worked anywhere else, the risk is small, but still replace it so the habit stays the same.

Step 2: find out if it was used

Look at the provider's access or audit log for the time since the commit. Unfamiliar IP addresses, new API usage, new resources or unexpected billing are signs of misuse. Also check whether the secret appears elsewhere: other branches, tags, forks, open pull requests, CI logs and issue comments.

# every commit in any branch that touched the file
git log --all --oneline -- .env

# search all history for a distinctive prefix of the value, not the whole value
git log --all --oneline -S'sk_live_'

Use a prefix or a pattern. Typing the full secret on the command line puts it in your shell history.

Step 3: remove it from the current code

Stop tracking the file and add the ignore rule, as in gitignoring env files safely:

git rm --cached .env
echo ".env" >> .gitignore
git commit -m "Stop tracking .env"

Read the secret from the environment in code, never from a literal.

Step 4: rewrite the history if it matters

A new commit hides the value but the old commit still contains it. To remove it from every commit, use git filter-repo, which replaced the older filter-branch and the BFG for most uses:

# drop a whole file from all history
git filter-repo --invert-paths --path .env

# or replace strings listed in a file, one rule per line: literal==>REMOVED
git filter-repo --replace-text ../replacements.txt

Run it on a fresh clone, and keep the replacements file outside the repository, because it contains the secret. Then force-push all branches and tags:

git push --force --all
git push --force --tags

Tell everyone who has a clone to re-clone or reset hard, otherwise they will push the old commits back. On GitHub, pull request refs and forks may keep the old objects. Contact GitHub support to purge cached views if the repository is public and the secret is serious. This is also why rotation comes first: you cannot recall every copy.

If the repository is private, small and the secret is already rotated, many teams stop after step 3. That is a reasonable call, as long as it is a decision and not an oversight.

Step 5: make it harder next time

  • Turn on secret scanning and push protection if your host offers them. GitHub does for many known token formats.
  • Add a pre-commit scanner such as gitleaks or detect-secrets, and run it in CI as well.
  • Keep real values in an untracked file and commit only names. Keeping env var names, not values, in committed config shows the pattern.
  • Prefer secrets that are generated per machine, so a leaked local value is worth nothing elsewhere. See generating random local secrets.

A short note on Flisk: the DB_PASSWORD and JWT_SECRET that flisk project writes to the project .env are generated per project, so a committed one exposes only that project's local stack, and a new DB_PASSWORD will not change an existing Postgres volume until you reset it.

Common mistakes

  • Deleting the file and calling it done. The history still has it.
  • Force-pushing a cleaned history without rotating. The secret is still out there.
  • Rotating in one place but not in CI variables, staging or a teammate's machine.
  • Posting the secret in a ticket while asking for help. Share the variable name and the commit hash.

Prevention is cheaper than this checklist, so set up the ignore rules and the scanner today.

Questions people ask

Is deleting the file in a new commit enough?

No. The secret stays in the earlier commits and in every clone. Rotate it, then rewrite history if you need it gone.

How do I remove a secret from git history?

Use git filter-repo on a fresh clone, for example git filter-repo --invert-paths --path .env, then force-push all branches and tags and ask everyone to re-clone.

Do I need to rewrite history in a private repository?

Not always. Once the secret is rotated, a private repository with few collaborators may not need it, but make that a deliberate decision.
