Env vars and secrets in local dev

How to gitignore .env files and still commit .env.example

Two lines of .gitignore protect your secrets, but only if the order is right and the file was never tracked.

Add .env and .env.* to .gitignore, then a negation line !.env.example after them so the example stays committable. Order matters because git uses the last matching pattern. And a .gitignore entry does nothing for a file that git already tracks, which is the case people miss.

The lines to use

.env
.env.*
!.env.example

A pattern with no slash, such as .env, matches at any depth, so it also covers services/api/.env in a monorepo. .env.* covers .env.local, .env.production and .env.integration. The negation has to come after them. If !.env.example is written first, .env.* matches it again and wins.

If your team wants to commit shared, non-secret defaults such as .env.development, add another negation for that file, and keep real secrets in .env.local or .env only. Do this on purpose. Most leaks happen because an example or a defaults file slowly gains a real value.

Ignoring does not untrack

If .env was committed once, git keeps tracking it and shows changes to it no matter what .gitignore says. Stop tracking it without deleting your local copy:

git rm --cached .env
git commit -m "Stop tracking .env"

That only fixes the future. The old content is still in history, and anyone who cloned has it. If the file held a real secret, treat the secret as leaked and follow what to do after committing a secret.

Check before you commit

# which rule ignores this file, or no output if none does
git check-ignore -v .env services/api/.env.local

# the example must NOT be ignored: expect no output and exit code 1
git check-ignore -v .env.example

# list any env file git already tracks
git ls-files | grep -E '(^|/)\.env'

The last command should show only .env.example files. Run it in CI as a guard: fail the build when it prints anything else.

if git ls-files | grep -E '(^|/)\.env($|\.)' | grep -v '\.env\.example$'; then
  echo "Tracked env file found"; exit 1
fi

Two more layers help. A global ignore file (git config --global core.excludesFile ~/.gitignore_global) protects you in repositories that forgot the rule. A pre-commit hook or a secret scanner such as gitleaks catches values that are in a file you did not think about. GitHub's push protection also blocks many known credential formats on push.

What Flisk writes for you

When you run flisk project, it appends this block to the project .gitignore (I ran it in an empty git repository to confirm):

# Flisk (generated files and secrets)
.env
.env.*
!.env.example
.flisk/.flisk-out/
.flisk/.project-id
.flisk/smoke/
node_modules/

It puts !.env.example right after .env.*, so the order is already correct, and it is only added when missing. The smoke records under .flisk/smoke/ are ignored because they store response bodies, with the values from your .env masked.

One consequence to know: flisk up --env-file .env.integration reads a file that matches .env.*, so it is ignored by default. That is what you want, because such a file is usually a copy of .env and carries DB_PASSWORD and JWT_SECRET. Flisk also refuses to complete a file you pass, since "a file you name may well be committed" and writing a generated credential into it would leak one.

The generated files themselves, such as .flisk/.flisk-out/ and the root package.json block, are a separate matter. Flisk generates the files under services/**/.autogenerated/ without secrets in them and checks them with flisk config verify. See checking config drift in CI for the CI side.

Pitfalls

  • A .gitignore inside a subfolder with its own !.env line can re-include the file. Search for !.env across the repository.
  • Editors and tools sometimes create .env.bak or .env~. The .env.* pattern catches the first, not the second. Add *~ if that applies to you.
  • Docker build contexts need their own .dockerignore with .env*, otherwise COPY . . bakes your .env into an image.
  • Do not rely on ignoring alone for anything that would be a disaster to publish. Rotate, scan and use push protection.

With the ignore rules sorted, the next question is how teammates get the values they need. That is the subject of sharing dev secrets with a team.

Questions people ask

Why is my .env still showing in git status after I added it to .gitignore?

The file was already tracked. Run git rm --cached .env to stop tracking it, commit, and the ignore rule takes effect. The old content stays in history.

How do I ignore .env files but keep .env.example?

Use .env, .env.* and then !.env.example, in that order. Git uses the last matching pattern, so the negation must come last.

Does Flisk add .env to .gitignore?

Yes. flisk project appends .env, .env.* and !.env.example, plus its generated-file paths, when they are missing.
