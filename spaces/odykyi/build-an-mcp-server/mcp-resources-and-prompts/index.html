MCP resources and prompts: when to use them instead of tools

Tools get all the attention, but MCP has two more primitives. Each one has a different owner, and that decides which to use.

Use a tool when the model should decide to run an action or query. Use a resource when you want to expose data the application or user can attach as context, such as a file or a record at a stable URI. Use a prompt for a reusable instruction template that a user picks on purpose. The specification calls these model-controlled, application-controlled and user-controlled, and that difference is the quickest way to choose.

The three primitives

PrimitiveWho triggers itGood for
ToolThe modelActions and parameterized queries: search, create, update
ResourceThe application or userRead-only content with a URI: a config file, a schema, a document
PromptThe userNamed workflows with arguments: "review this diff", "summarize this ticket"

Most servers only ship tools, because tools work in every client. Resources and prompts are optional features, and clients vary in how well they present them. Check your target client before you depend on either. A server that has only tools is a perfectly good server.

Add a resource

A resource has a URI, a name and content. In the TypeScript SDK:

server.registerResource(
  'schema',
  'db://schema',
  { title: 'Database schema', description: 'The SQL schema of the orders database', mimeType: 'text/plain' },
  async (uri) => ({
    contents: [{ uri: uri.href, text: await loadSchemaSql() }],
  })
);

In Python, FastMCP derives it from a decorator. A URI with a placeholder defines a template, and the function argument fills it:

@mcp.resource("db://schema")
def schema() -> str:
    """The SQL schema of the orders database."""
    return load_schema_sql()

@mcp.resource("orders://{order_id}")
def order(order_id: str) -> str:
    """One order as JSON."""
    return json.dumps(db.get_order(order_id))

Resources suit content the user might want to attach once and then ask several questions about. If the model needs to look something up while it works, make it a tool instead. When you are unsure, expose the same data both ways: a resource for attaching and a tool for searching.

Add a prompt

A prompt returns messages. The user fills in the arguments, and the client puts the result into the conversation. The Flisk MCP scaffold registers a similar one, echo_message. Here is the shape:

server.registerPrompt(
  'review_order',
  {
    title: 'Review an order',
    description: 'Ask the assistant to check an order for problems',
    argsSchema: { order_id: z.string() },
  },
  ({ order_id }) => ({
    messages: [
      { role: 'user', content: { type: 'text', text: 'Use get_order to load order ' + order_id + ' and list anything unusual.' } },
    ],
  })
);

In Python:

@mcp.prompt()
def review_order(order_id: str) -> str:
    """Ask the assistant to check an order for problems."""
    return f"Use get_order to load order {order_id} and list anything unusual."

A good prompt names the tools it expects the model to use. That ties the three primitives together: the prompt starts the workflow, tools do the work and resources supply background. In clients that support prompts, they usually appear as something a user can pick, such as a slash command. Claude Code lists server prompts as slash commands, for example.

Check them

List and read them by hand in the Inspector (see the debugging guide), or send resources/list and prompts/list with the request format from the Streamable HTTP guide. If the server runs as a Flisk resource, flisk mcp check goes through prompts/list and calls prompts/get once for every prompt, with the string example for each required argument. It does not exercise resources, so test those yourself. The check also requires the server to declare a tools capability at initialize, so a server with resources and prompts but no tools fails that first check.

Pitfalls

  • Capabilities must match. A server declares what it supports at initialize. The SDKs fill this in when you register at least one of each kind, so register before you connect.
  • Do not hide actions in resources. Reading a resource should have no side effects. Anything that changes data belongs in a tool.
  • Large resources cost context. If a resource is a big file, split it or offer a tool that returns a part.
  • Do not assume a client lists them. Some clients show only tools. Keep tools as the main path for anything essential.

With the shape of the server settled, think about who can reach it. Protecting an MCP HTTP server with a token is the next article, and tool design covers the tools half in more detail.

Questions people ask

What is the difference between an MCP resource and a tool?

A tool is called by the model to act or query. A resource is read-only content with a URI that the application or user can attach as context.

Do all MCP clients support resources and prompts?

No. Tools are supported nearly everywhere, but clients differ in how they show resources and prompts, so check your target client.
