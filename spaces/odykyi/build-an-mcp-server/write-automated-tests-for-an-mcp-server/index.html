Build your own MCP server

How to write automated tests for an MCP server

A server that only works when an assistant happens to call it is hard to trust. Three kinds of tests keep it honest.

Test an MCP server at three levels. Unit-test the tool logic as plain functions. Test the protocol in memory by connecting the official SDK client to your server object with no network. Then run a few checks against the real running server over HTTP. The first two are fast enough to run on every save, and the last confirms that the process you ship actually answers.

Level 1: the tool logic

Keep the work a tool does in a normal function, and keep the MCP registration thin. Then ordinary unit tests cover the logic, with no protocol involved. In FastMCP, the @mcp.tool() decorator returns your original function, so you can import and call it directly:

# test_tools.py
from server import add_note, find_notes, NOTES

def test_find_notes_respects_limit():
    NOTES.clear()
    for i in range(10):
        add_note(f"note {i}", "shopping")
    assert len(find_notes("shopping", limit=3)) == 3

This level cannot catch a wrong schema or a missing registration, so you need the next one too.

Level 2: the protocol, in memory

The TypeScript SDK includes an in-memory transport that links a client and a server inside one process. You get the real tools/list and tools/call path, including schema validation, with no port and no child process. With Vitest:

import { describe, expect, it } from 'vitest';
import { Client } from '@modelcontextprotocol/sdk/client/index.js';
import { InMemoryTransport } from '@modelcontextprotocol/sdk/inMemory.js';
import { buildServer } from '../src/index';

async function connect() {
  const [clientTransport, serverTransport] = InMemoryTransport.createLinkedPair();
  const server = buildServer();
  const client = new Client({ name: 'test', version: '1.0.0' });
  await Promise.all([server.connect(serverTransport), client.connect(clientTransport)]);
  return client;
}

describe('echo tool', () => {
  it('is listed with its schema', async () => {
    const client = await connect();
    const { tools } = await client.listTools();
    expect(tools.map((t) => t.name)).toContain('echo');
  });

  it('returns the message', async () => {
    const client = await connect();
    const res = await client.callTool({ name: 'echo', arguments: { message: 'hi' } });
    expect(res.content).toEqual([{ type: 'text', text: 'hi' }]);
  });

  it('rejects a missing argument', async () => {
    const client = await connect();
    const outcome = await client.callTool({ name: 'echo', arguments: {} }).then(
      (r) => r.isError === true,
      () => true
    );
    expect(outcome).toBe(true);
  });
});

The helper imports buildServer, so export it from your module (the Flisk scaffold declares it without export, so add one). The last test accepts either a protocol error or an isError result, because SDK versions differ in how they report invalid arguments (see returning errors from a tool). Once you know what your version does, assert on that exact behavior.

For Python, the SDK client (ClientSession with stdio_client) can start your server as a child process and call it. That needs the server to run on stdio, so give it a small switch, such as an environment variable that selects the transport in mcp.run().

Level 3: the running server over HTTP

Start the server on a free port and send real HTTP requests. The Flisk MCP scaffold does this: its generated test file imports the HTTP server, listens on port 0, and sends JSON-RPC requests with fetch, checking initialize, the tool list with its annotations and the prompt. You can copy the idea to any HTTP server. Two details matter. Send Accept: application/json, text/event-stream, and when the reply is an event stream, read the JSON from the line that starts with data:.

With a stack running, flisk mcp check covers the same ground without code. It is read-only unless you add --call, and it exits with 1 on a failed check, so it works as a gate in a script:

flisk mcp check notes-mcp --json

Its JSON report lists each check with a pass flag and a detail line. For running a whole stack in GitHub Actions, see that guide. Keep in mind that the check does not send credentials, and that it treats a tool without readOnlyHint: true as a failure.

What to cover

  • Every tool, with one valid call and one invalid call.
  • The tool list itself: names, required fields and descriptions are your public interface, so a snapshot test catches accidental renames.
  • Failure paths: not found, permission denied, upstream timeout. Return errors a model can act on.
  • Side effects, against a test database. For ideas on isolating state, see integration tests against the real stack.

Pitfalls

  • Shared state between tests. A module-level variable in the server leaks from one test to the next. Reset it, or build a new server per test as the helper above does.
  • Calling real external services. Stub the HTTP client or database layer in tests that run on every commit.
  • Testing only through a chat client. That checks the model more than your server. Use it as a last step.

When tests pass, hand the server to an assistant. Testing an MCP server with Claude Code is the next step.

Questions people ask

How do I test an MCP server without an AI model?

Use the official SDK client. In TypeScript, an in-memory transport links a Client to your server object in one process, so you can call listTools and callTool directly in a test.

Can I run MCP server tests in CI?

Yes. Unit and in-memory tests need nothing but your test runner. For the running server, start it in the job and send HTTP requests, or use a read-only protocol check that exits non-zero on failure.
