How to return errors from an MCP tool (isError explained)

A failed tool call should teach the model what to do next. That depends on choosing the right kind of error.

MCP has two kinds of failure. A tool that runs and fails should return a normal result with isError: true and a message the model can read. A request that is broken at the protocol level, such as an unknown tool or a malformed message, produces a JSON-RPC error. Use the first for anything the model can fix by trying again differently, because the model never sees a protocol error as conversation text.

The two kinds of error

Protocol errors are JSON-RPC error responses with a numeric code, for example -32601 for an unknown method or -32602 for invalid parameters. They mean the request itself was wrong. Clients generally treat them as a failure of the connection or of the call, not as content for the model to reason about.

Tool execution errors are successful JSON-RPC responses whose result has isError: true and the explanation in content. The specification describes this form for failures inside a tool, such as an API returning 404 or a business rule being violated. Clients pass this content to the model, which can then retry with different arguments or explain the problem to the user.

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "isError": true,
    "content": [
      { "type": "text", "text": "No order with id 8812. Order ids look like ORD-1234. Use search_orders to find one." }
    ]
  }
}

Write the message for the model

A good error text states what went wrong, what a valid input looks like, and what to try next. Compare "Error" with the message above. The second one lets the model fix its own mistake in the next call without bothering the user. Keep it short, and leave out stack traces, file paths, SQL and secrets.

In TypeScript

Return the error result yourself for failures you expect. If the handler throws, the SDK catches the exception and reports it as a tool error rather than crashing, but the text it sends is the exception message, so do not rely on that for anything you care about wording.

server.registerTool(
  'get_order',
  { description: 'Get one order by id', inputSchema: { id: z.string() } },
  async ({ id }) => {
    const order = await db.getOrder(id);
    if (!order) {
      return {
        isError: true,
        content: [{ type: 'text', text: `No order with id ${id}. Use search_orders to find ids.` }],
      };
    }
    return { content: [{ type: 'text', text: JSON.stringify(order) }] };
  }
);

In Python

In FastMCP, raising an exception inside a tool function produces an error result for the client. The exception message becomes the text, so raise with a message written for the model.

@mcp.tool()
def get_order(id: str) -> dict:
    """Get one order by id."""
    order = db.get_order(id)
    if order is None:
        raise ValueError(f"No order with id {id}. Use search_orders to find ids.")
    return order

Lower-level server code in the Python SDK can build the result itself, but check your SDK version's documentation for the exact shape. The pattern is the same: failure goes in the result, marked as an error.

Check how your server fails

Do not assume. Call the tool with an input that should fail, and read the raw result. With the HTTP transport you can do it with curl, as in the Streamable HTTP endpoint guide. If the server is a Flisk resource, flisk mcp check <resource> --call does a simpler version of this for you. It calls every tool once with generated sample arguments and marks a tool as failed when the call returns isError: true, has no content, or gets a protocol error. Its sample arguments are valid ones, so it tests the happy path only: you still need your own bad-input checks. The same command also confirms that an unknown method returns -32601 and that a body that is not JSON gets HTTP 400.

Pitfalls

  • Returning success with an error message in the text. The model sees "Error: not found" and may treat it as data. Set isError so the client knows.
  • Retry loops. If an error message always suggests the same failing call, a model can repeat it. Say what to change.
  • Leaking internals. An exception message from a database driver can include table names or credentials. Catch it and write your own text.
  • Using errors for empty results. A search with no matches is a successful call with an empty list, not an error.

With errors handled, you can test failure paths automatically. Writing automated tests for an MCP server shows an in-memory client that makes this cheap.

Questions people ask

What does isError true mean in an MCP tool result?

It marks the result as a tool failure while the JSON-RPC call itself succeeded. The content is passed to the model, which can read the message and try again.

When should an MCP server return a JSON-RPC error instead?

When the request is wrong at the protocol level, such as an unknown tool or method, or a malformed message. Failures inside a tool belong in an isError result.
