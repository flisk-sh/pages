Build your own MCP server

How to design MCP tools an AI model can call correctly

A model chooses tools by reading text. The name, description and schema are the entire interface, so design them with the same care as a public API.

Give each tool one clear job, a short verb-first name, a description that says when to use it and when not to, and a small set of arguments with their own descriptions. The model never sees your code. It sees the name, the description and the input schema, and nothing else, so those three things are the whole interface.

What the model actually receives

When a client connects, it calls tools/list and gets, for each tool, a name, an optional title, a description, a JSON Schema for the input, and optional annotations. The client passes that text to the model with the conversation. The model picks a tool by reading it, so vague text leads to wrong calls, and too many overlapping tools lead to indecision.

Names

  • Use verb and object: search_issues, create_invoice, get_order_status. A name like handle or query says nothing.
  • Stay within a safe character set. Many clients and model APIs accept letters, digits, underscores and hyphens, up to 64 characters. A name with spaces or dots can be rejected, or silently renamed.
  • Be consistent. If one tool is list_orders, do not name the next fetchCustomers. Pick one style.
  • Avoid near-duplicates. search_orders and find_orders force the model to guess. Merge them, or make the difference obvious in the names.

Descriptions

A good description answers three questions in one or two sentences: what the tool does, when to call it, and what it returns. Add a line about what it does not do when another tool is easy to confuse with it.

// Weak
description: 'Gets orders'

// Better
description: 'List a customer\'s orders, newest first. Use this to answer questions about ' +
  'order history. Returns id, status and total for up to 20 orders. ' +
  'To see the items in one order, use get_order instead.'

Put constraints the model cannot guess into the text: date formats, units, allowed values, limits. Do not paste a long manual. Large descriptions cost context on every conversation, for every tool, whether or not it is used.

Arguments

Keep the number of arguments low and make most of them optional with defaults. Describe each one, because the schema's field descriptions are also shown to the model. Prefer an enum to free text when the choices are fixed, and a flat structure to deep nesting. Use names a person would recognize, such as customer_email, not cid. Do not ask the model to supply values that your server can find itself, such as the current user.

inputSchema: {
  status: z.enum(['open', 'shipped', 'cancelled']).default('open')
    .describe('Order status to filter by'),
  limit: z.number().int().min(1).max(50).default(20)
    .describe('Maximum number of orders to return'),
}

Size and number of tools

Every tool you expose adds to the text the model reads before it does anything. A server with five well-chosen tools usually works better than one with fifty thin wrappers over every API endpoint. Design around tasks the user wants done, not around your database tables. If one task needs three API calls in a fixed order, make it one tool that makes them. Return what the model needs: a trimmed, readable result, not a raw dump that spends thousands of tokens.

Annotations

The specification lets a tool carry hints: readOnlyHint, destructiveHint, idempotentHint and openWorldHint. Clients may use them to decide whether to ask the user before running a tool. They are hints, not enforcement, and a client should not trust them from an unknown server. Set them honestly anyway. The tool scaffolded by flisk resource ... --type mcp sets all four on its sample echo tool, and flisk mcp check reports a failure for any tool without readOnlyHint: true. That rule suits a read-only server, such as one published to a directory. If your server has tools that write, that particular check will fail by design, and you can read it as a list of the tools that change something.

Pitfalls

  • Leaking secrets in results. Whatever a tool returns goes into the model's context. Strip tokens, passwords and internal URLs.
  • Changing a name after release. Clients and saved prompts refer to tools by name. Treat renames like API changes.
  • Not testing with a model. Read your own tool list as if you had never seen the code, then try a few real requests in an assistant and see which tool it picks.

Once the shape is right, make the inputs strict. Validating MCP tool arguments shows how, and returning useful errors covers what happens when a call still goes wrong.

Questions people ask

How many tools should an MCP server expose?

As few as the tasks need. Every tool adds text the model reads in each conversation, so a handful of task-shaped tools usually works better than one tool per API endpoint.

What characters are safe in an MCP tool name?

Letters, digits, underscores and hyphens, up to 64 characters, are accepted by common clients and model APIs. Avoid spaces and dots.
