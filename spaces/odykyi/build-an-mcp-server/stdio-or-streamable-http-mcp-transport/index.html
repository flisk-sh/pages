Build your own MCP server

MCP stdio or Streamable HTTP: which transport to choose

The transport decides how a client reaches your server. Pick it before you write much code, because it changes logging, testing and security.

Use stdio when one assistant on your machine will start the server as a child process and nobody else needs it. Use Streamable HTTP when the server should run on its own, be shared by several clients, sit next to other services, or live on another machine. The MCP specification defines these two transports, and a server can offer both.

How the two transports differ

With stdio, the client launches your program, writes JSON-RPC messages to its standard input and reads replies from its standard output. There is no port, no URL and no network. When the client exits, the server exits with it. Configuration in a client looks like a command line: a program name, arguments and environment variables.

With Streamable HTTP, your server is a web service with one endpoint, usually /mcp. The client sends each JSON-RPC message as an HTTP POST. The server may answer with plain JSON or open a server-sent event stream for that request. Configuration in a client is a URL, plus optional headers for authentication. This transport replaced the older HTTP plus SSE transport in the 2025-03-26 revision of the protocol, so new work should not use the old one.

A practical rule

Start with stdio if the server is a small tool for your own use, such as a script that reads files on your laptop. It is the least setup and nothing can reach it from the network. Move to HTTP when any of these becomes true:

  • A second client needs the same server, for example Claude Code and Cursor, or a test script.
  • The server holds state that should not be rebuilt for every client, such as a warm cache or a database connection pool.
  • It depends on other services (a database, a queue) that you already run as part of a stack, and you want to start and stop it with them.
  • You want to debug it with curl, a browser tool or an automated test over HTTP.
  • It will be used by people who cannot install your code.

The cost of HTTP is that you now run a network service. A port on localhost can be reached by every program on your machine, and by web pages in your browser if the server does not check the Origin header. The specification tells servers to validate that header and bind to localhost when running locally. Protecting an MCP HTTP server with a token covers it.

Adding both

You can keep one set of tool definitions and pick the transport at startup. In the Python SDK the choice is an argument to mcp.run(). In the TypeScript SDK you connect the same McpServer to a StdioServerTransport or to a StreamableHTTPServerTransport:

import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';

const server = buildServer(); // registers your tools
if (process.argv.includes('--stdio')) {
  await server.connect(new StdioServerTransport());
} else {
  startHttp(server); // your own HTTP listener, as in the local build guide
}

One caveat for HTTP: the simplest pattern builds a fresh McpServer for each request, which keeps the endpoint stateless. Stateful servers use session IDs and need a place to keep them. If you do not need server-initiated messages, stateless is easier to restart and to scale.

Where Flisk fits

Flisk supervises processes that listen on a port, so it fits the HTTP kind. flisk resource docs-mcp --type mcp scaffolds a stateless Streamable HTTP server in TypeScript on Bun, and flisk up starts it with the rest of the stack. Building an MCP server locally walks through that scaffold. A stdio server has no port and no URL, so there is nothing for Flisk to route to or health-check, and the client's own configuration is the right place to start it.

Pitfalls

  • Do not mix output with the protocol. On stdio, any stray text on standard output corrupts the stream. See why logs break a stdio server.
  • Clients differ in what they support. Check your client's documentation for HTTP and for authentication headers before you choose.
  • A remote HTTP server is a public service. Treat it like an API: authentication, rate limits and input checks.

Next, if you chose stdio and the client says it cannot connect, read the stdout article. If you chose HTTP, the Streamable HTTP endpoint guide shows the exact requests.

Questions people ask

Is the SSE transport for MCP deprecated?

The HTTP plus SSE transport was replaced by Streamable HTTP in the 2025-03-26 protocol revision. Servers can still stream events inside Streamable HTTP, but new servers should implement the newer transport.

Can one MCP server support both stdio and HTTP?

Yes. Keep your tool definitions in one place and connect them to a stdio transport or an HTTP transport at startup, chosen by a flag or environment variable.
