Vite HMR WebSocket fails behind a reverse proxy: how to fix it

Hot reload needs a WebSocket back to the dev server. When something sits between the browser and Vite, that socket often fails. Here is how to find which layer broke it.

Vite's hot module replacement uses a WebSocket from the browser to the dev server. When a reverse proxy sits in between and does not forward the Upgrade headers, or when the browser connects to the wrong host or port, the console prints [vite] failed to connect to websocket and the page stops updating on save. Fix it by forwarding the upgrade at the proxy and telling Vite the address the browser actually uses.

How the socket is chosen

By default the Vite client connects back to the same host and port that served the page, using ws for http pages and wss for https pages. That works when you open http://localhost:5173 directly. It breaks when the page is served on a different address than the one Vite listens on: a proxy on port 80 or 443, a container with a published port, or a tunnel. The browser asks the public address for a socket, and either nothing forwards the upgrade or the address is wrong.

Layer 1: the proxy must pass the upgrade

For nginx, a location that serves Vite needs HTTP/1.1 and the two upgrade headers:

location / {
  proxy_pass http://127.0.0.1:5173;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_set_header Host $host;
}

Caddy and Traefik forward WebSocket upgrades without extra options. If the console error shows a 400 or 426 for the socket request, the upgrade was stripped. If it shows nothing for a long time and then fails, a firewall or a timeout is the likelier cause.

Layer 2: tell Vite the public address

When the browser must use another host or port for the socket, set it in vite.config.ts:

export default defineConfig({
  server: {
    host: true,
    hmr: {
      protocol: 'wss',
      host: 'dev.example.test',
      clientPort: 443,
    },
  },
});

clientPort is the port the browser connects to, and port is where Vite opens the socket server. Set clientPort when a proxy changes the port. Use wss when the page is served over HTTPS, because browsers block a plain ws socket from a secure page.

Layer 3: the host check

Newer Vite versions refuse requests whose Host header is not allowed, with the message Blocked request. This host is not allowed. localhost, *.localhost and IP addresses are allowed by default. A custom domain through a proxy or a tunnel is not. Add it with server.allowedHosts. If you do this to reach the dev server from another machine, remember that the dev server then answers requests from anyone who can reach it.

Layer 4: file changes never reach Vite

If the socket connects but a save changes nothing, the problem is the file watcher, not the socket. That happens with bind mounts from a virtual machine, where file events may not arrive. See hot reload not working in Docker or locally.

What Flisk does here

The simplest fix is to leave nothing in the middle. A frontend scaffolded with --local runs Vite as a plain process with server.host set to localhost and strictPort: true, so you open the page on the very port Vite listens on and the default socket address is right:

flisk resource web --type frontend --local --stack app --yes
flisk up

In Docker mode the engine writes the Vite config itself. It listens on 0.0.0.0, sets an hmr port, and puts Traefik in front under app.<project>.localhost. Flisk's own documentation for the frontend suite says it checks that the route and the built assets are served, and that it does not cover hot reload. So if the socket fails in that mode, treat it as something to verify, not something that is promised: read the browser console, then flisk logs --service <frontend> --tail 100, and compare the address in the socket error with the one in flisk networks. A hand-edited generated Vite config would be overwritten, so change the settings in the source files, not in the .autogenerated folder.

Pitfalls

  • Two Vite servers. A second dev server on the same machine silently takes the next port, and the page you have open talks to the wrong one. Pin the port with strictPort, as in why a changed Vite port breaks CORS.
  • Proxying the API with ws. The ws: true option on server.proxy is for your backend's sockets. It is not what makes HMR work.
  • Cached service workers. An old service worker can serve a stale page that never connects. Unregister it in the browser while you debug.

Questions people ask

What does 'failed to connect to websocket' mean in Vite?

The browser could not open the HMR socket. The usual causes are a proxy that drops the Upgrade headers, the wrong host or port for the socket, or a blocked host name.

Which Vite option sets the HMR port the browser uses?

server.hmr.clientPort. Use it when a proxy or a container maps the dev server to a different public port.

Why does Vite say 'This host is not allowed'?

Newer Vite checks the Host header. Localhost, *.localhost and IP addresses pass by default. Add other names to server.allowedHosts.
