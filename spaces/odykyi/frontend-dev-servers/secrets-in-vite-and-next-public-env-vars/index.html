Why secrets must never go in VITE_ or NEXT_PUBLIC_ variables

The prefix is not a label for 'frontend config'. It is the switch that publishes the value to every visitor. Here is how to tell what is safe and what to do with the rest.

A variable that starts with VITE_ in Vite, or NEXT_PUBLIC_ in Next.js, is copied into the JavaScript that is sent to the browser. Anyone who opens the page can read it in the bundle or the network tab. So a secret never belongs there. Keep it in a server-side variable that only your API or server code reads, and let the frontend call that code.

What the prefix does

Both tools use the prefix as a filter. Vite exposes only VITE_* variables to client code through import.meta.env. Next.js inlines only NEXT_PUBLIC_* variables into the browser bundle. Variables without the prefix stay on the server. The rule exists to protect you: if the prefix were not required, every value in the file would be published.

The value is substituted at build time. That has two consequences. Changing it needs a rebuild or a dev server restart, and deleting it from the file later does not remove it from a bundle you already deployed.

What is safe in a public variable

  • The API's base URL.
  • Feature flags that are fine for everyone to see.
  • Publishable keys, made to be public: a Stripe pk_... key, an analytics site id, a map tile token that is restricted by domain.

A useful test is this: could a stranger who has the value do damage with it? If yes, it is a secret.

What is not

  • Stripe sk_ and rk_ keys, OpenAI and Anthropic keys, database URLs with a password, signing secrets, webhook secrets, cloud access keys, GitHub tokens.
  • A key that is "only for development". It is often the same account, and a leaked value in a bundle gets copied into a repository or a screenshot.

Where a secret goes instead

Put it in a variable without the prefix and read it only in server code: your API, a Next.js route handler, a server action or a server component. The frontend calls an endpoint, the server adds the key and calls the third party, and the browser only gets the result.

// Next.js route handler: app/api/chat/route.ts
const PROVIDER_URL = 'https://api.example.com/v1/chat';

export async function POST(req: Request) {
  const body = await req.json();
  const r = await fetch(PROVIDER_URL, {
    method: 'POST',
    headers: { Authorization: `Bearer ${process.env.CHAT_API_KEY}` },
    body: JSON.stringify(body),
  });
  return new Response(r.body, { status: r.status });
}

With a Vite single-page app there is no server of its own, so the key lives in your backend, and a dev proxy lets the frontend reach it without knowing anything else. Keep .env out of git, and commit an example file with empty values.

If one already leaked

Treat the key as public. Revoke it at the provider and create a new one, and only then clean the code. Removing the line from the repository does not help, because the value is in git history and in every deployed bundle.

What Flisk does here

flisk doctor has a check for exactly this. It reads the project's env files and warns when a NEXT_PUBLIC_* or VITE_* variable holds a value that looks like a secret. It recognises provider formats such as Stripe secret keys, OpenAI and Anthropic keys, AWS access key ids, GitHub tokens, Slack tokens and Google API keys, and it skips the values that are public by design, such as pk_live_ and pk_test_ keys and obvious placeholders. The warning names the variable and the file, and its fix text tells you to move the value to a server-side variable or an API route. In the JSON output it is a warning and the command still exits 0, so run flisk doctor yourself, and do not rely on a failing exit code to catch it. It looks at values with a known shape, so a custom token with no recognisable format may pass: the check helps, it does not replace review.

For secrets your services need during development, Flisk can generate them rather than have you paste a real one. Declare them in a service's service.json:

{ "secrets": { "generate": { "AUTH_SECRET": "hex:32" } } }

On flisk up, a name missing from the project .env is appended once with a random value, an existing value is never changed, and Flisk prints the names it generated, not the values. This is for development keys that only your own stack uses. It does not create a key for a third-party service, and it should not be used to put a value into a VITE_ variable.

Pitfalls

  • The prefix added "to make it work". A variable that is undefined in the browser is the prefix doing its job. The answer is a server endpoint, not a rename.
  • Source maps. Shipping source maps does not make a key safer, and it does not make it less exposed.
  • Server code in the client bundle. In Next.js, a file with 'use client' that imports a module reading process.env.SECRET gets undefined at best. Keep secret-reading code in server-only modules.

Questions people ask

Are VITE_ variables secret?

No. Vite copies every VITE_ variable into the client bundle, so anyone who loads the page can read it. Keep secrets in server-side variables.

Is NEXT_PUBLIC_ safe for a Stripe publishable key?

Yes. Publishable keys such as pk_live_ and pk_test_ are meant to be public. Secret keys starting with sk_ or rk_ are not.

Does flisk doctor fail when it finds a secret in a public variable?

It reports a warning that names the variable and the file, and the command still exits 0. Read the warning and move the value to the server.
