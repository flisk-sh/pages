Why cookies are not sent from your frontend to a local API

The login works, the cookie is set, and the next request still arrives without it. Here is the checklist, in the order that finds the cause fastest.

When a cookie does not reach your local API, the cause is almost always one of four things: the request did not use credentials: 'include', the API did not send Access-Control-Allow-Credentials: true with a named origin, the cookie was stored for a different host, or a Secure or SameSite attribute made the browser drop it. Open the network tab and the Application tab and check them in that order.

First, is it the same origin?

If the page and the API share an origin, for example because a dev server proxy forwards /api, cookies behave normally and none of the CORS options below apply. This is the simplest local setup, and a Vite proxy or a Next.js rewrite gives it to you. If the API has its own origin, keep reading.

Cross-origin: the two sides must agree

For a cross-origin request the browser sends and accepts cookies only when both sides opt in.

  1. The request opts in. With fetch, add credentials: 'include'. With axios, withCredentials: true. Without it the browser neither sends the stored cookie nor saves a Set-Cookie from the response.
  2. The response opts in. The API must send Access-Control-Allow-Credentials: true, and Access-Control-Allow-Origin must be the exact origin of the page. The wildcard * is rejected when credentials are on. The preflight response needs the same headers.
// frontend
const api = 'http://localhost:4000';
await fetch(`${api}/api/me`, { credentials: 'include' });

// Express API
app.use(cors({ origin: 'http://localhost:5173', credentials: true }));

The cookie itself

  • Host, not port. A cookie is scoped to a host name. It is not isolated by port, so localhost:5173 and localhost:4000 share cookies. That helps this setup, and it also means two projects that both use localhost and a cookie named session overwrite each other. Use a distinct cookie name per project.
  • Different host names. A cookie set by api.demo.localhost belongs to that host. Do not set a Domain attribute you do not need. Whether two *.localhost names count as the same site is a browser decision, so test with the Application panel instead of assuming.
  • SameSite. Lax is the default in current browsers. It blocks cookies on cross-site requests made by fetch. Ports do not make two localhost origins cross-site, but different host names might. SameSite=None requires Secure, which needs HTTPS or a browser exception for localhost.
  • Secure. Chrome and Firefox treat http://localhost as a secure context and accept a Secure cookie there. Other browsers may not, so do not set Secure only in development builds by accident: make it depend on the environment.

In Chrome the Application tab, Cookies section, shows the stored cookie and, in a filter, whether a blocked one was rejected. The network tab marks a response cookie with a warning icon and the reason.

What Flisk adds, and what it does not

A backend scaffolded with flisk resource has a CORS rule for local frontends: it echoes back an origin that matches a *.localhost host, with any port, and nothing else. In the scaffolds I read, that rule sets the origin, methods and headers but no credentials option, so a cookie flow needs one more change. For Express, add Access-Control-Allow-Credentials: true next to the existing header, or switch the middleware to cors({ origin: ..., credentials: true }). The generated file carries a comment explaining the rule, so you can find the place.

The simpler route with Flisk is the same-origin one. A frontend scaffolded with --local proxies /api through Vite to the API's port, so the cookie lives on the frontend's origin and no credentials header is needed:

flisk resource api --framework express --local --stack app --yes
flisk resource web --type frontend --local --stack app --yes

In Docker mode the frontend is on app.<project>.localhost and the API on api.<project>.localhost, so calls are cross-origin and you need both sides of the agreement above. Run flisk networks to see the two origins.

Pitfalls

  • 127.0.0.1 versus localhost. A cookie set for one is not sent to the other. Pick one name and use it in the browser, the CORS allow list and the API URL.
  • Server-side requests. A Next.js server component that calls the API does not have the browser's cookies unless you forward the header yourself.
  • Old cookies. After you change an attribute, delete the cookie in the browser. A stale one with a different path or domain can shadow the new one.

Next step

Questions people ask

Why is my cookie missing on cross-origin fetch requests?

Usually the request lacks credentials: 'include', or the API does not send Access-Control-Allow-Credentials: true with an exact origin. Both are required.

Are cookies shared between localhost ports?

Yes. Cookies are scoped to the host name, not the port, so localhost:3000 and localhost:4000 see the same cookies. Use a distinct cookie name per project to avoid collisions.

Can I use Access-Control-Allow-Origin: * with cookies?

No. With credentials the browser rejects the wildcard. The API must return the exact origin of the page.
