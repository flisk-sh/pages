Frontend dev servers and APIs

How to make the frontend dev server wait for the API to be ready

You start both with one command, and the page loads before the API listens. Here are three ways to order the start, and why readiness beats a fixed sleep.

To make a frontend wait for its API, start the API first, then poll a health URL until it answers, and only then start the dev server. You can do that with wait-on in an npm script, with a Compose healthcheck and depends_on, or with dependsOn and healthCheckPath in a Flisk service.json. A fixed sleep is the version that fails on the slowest day.

Why the race exists

Starting two processes from one command does not order their readiness. The API may need a second to connect to its database or compile TypeScript. A Vite dev server starts in well under that, so the browser tab opens, the first request fails with ECONNREFUSED or a 502 from a proxy, and the developer reloads. It is not a bug in either app. It is a missing rule that says which one is ready first.

Readiness is different from started. A process that has begun is not necessarily accepting requests. Wait for something that proves the API can answer: a TCP connection at minimum, an HTTP 200 on a health path better.

Option 1: wait-on in a script

npm install -D wait-on concurrently

# package.json
"scripts": {
  "dev:api": "npm --prefix api run dev",
  "dev:web": "wait-on -t 60000 http-get://localhost:4000/health && npm --prefix web run dev",
  "dev": "concurrently -n api,web \"npm run dev:api\" \"npm run dev:web\""
}

wait-on accepts tcp:4000 and http-get://host:port/path resources, and -t sets a timeout in milliseconds so a broken API fails the command instead of hanging. This is a good answer for two services in one repo. It does not restart anything that crashes.

Option 2: Compose

In Compose, give the API a healthcheck and make the frontend depend on it with the long form:

services:
  api:
    build: ./api
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:4000/health"]
      interval: 2s
      timeout: 2s
      retries: 30
  web:
    build: ./web
    depends_on:
      api:
        condition: service_healthy

The test command runs inside the API container, so the image needs wget or curl. Without condition: service_healthy, depends_on only waits for the container to start.

Option 3: Flisk

With local processes, the order and the wait are fields in the manifests. The API says how to check it is up:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "npm run dev",
  "port": 4000,
  "healthCheckPath": "/health"
}

and the frontend names it in dependsOn:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"]
}

flisk up starts the services in dependsOn order. A service starts once everything it depends on is ready. Ready means the health URL answers with a status below 400. Without healthCheckPath it means the port accepts connections, and without a port it means the process is still running after a second. Flisk waits up to 60 seconds per service. A process that exits is started again after 1, 2, 4 and 8 seconds, and after five quick exits in a row Flisk stops restarting it and says so. Flisk also refuses to start when a program is not installed, a port is taken (it names the process that holds it), two services share a port, or a dependsOn name is not a service with a command.

Two commands help while you work. flisk up --only web starts web and what it depends on. flisk status shows each service as ready, restarting or not running. A runnable pair comes from flisk resource api --framework express --local and flisk resource web --type frontend --local: the scaffold already writes healthCheckPath for the API and the dependency for the frontend.

Pitfalls

  • A health route that lies. If /health returns 200 before the database connection exists, the wait ends too early. Make a separate readiness route that checks what the API needs, and point the wait at it.
  • Waiting hides slow starts. A frontend that waits 40 seconds feels broken. Print the reason: Flisk prefixes each log line with the service name, so you can see the API still building.
  • Your code should still retry. The wait protects a cold start. It does not protect you when the API restarts later. Handle a failed request with an error state, not a blank page.

Questions people ask

Is depends_on enough to wait for a service in Compose?

Not by itself. The short form waits only for the container to start. Add a healthcheck and use condition: service_healthy to wait until it reports healthy.

What does Flisk consider ready for a local service?

A health URL answering below 400 when healthCheckPath is set, a port accepting connections when only port is set, or the process still running after a second when neither is set.

How long does Flisk wait for a service?

Up to 60 seconds per service before it reports the failure.
