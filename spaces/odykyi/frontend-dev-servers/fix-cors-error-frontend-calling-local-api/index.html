How to fix a CORS error when your frontend calls a local API

The browser blocked a response your API did send. These are the three headers that decide it, the common mistakes, and the options for local development.

A CORS error means the browser refused to let your page read a response because the API did not say that your page's origin is allowed. To fix it, make the API send Access-Control-Allow-Origin with the exact origin of the frontend, answer the OPTIONS preflight request, or avoid the cross-origin call with a dev server proxy.

What the browser is checking

An origin is scheme, host and port. http://localhost:5173 and http://localhost:3001 are two origins, so a fetch from the first to the second is cross-origin. The request is usually still sent. The API answers. Then the browser looks at the response headers and, if they do not allow the calling origin, it hides the response from your code and prints the error.

Some requests are preceded by a preflight: an OPTIONS request the browser sends first. This happens for methods other than GET, HEAD and POST, for a Content-Type of application/json, and for custom headers such as Authorization. The preflight must return a success status and the right Access-Control-Allow-* headers. A 404 or 401 on OPTIONS is a very common cause of the error.

Read the message first

  • No 'Access-Control-Allow-Origin' header is present: the API sent no CORS headers at all, or the request never reached it. Look in the network tab for the real status code.
  • The value of the header must not be the wildcard '*' when credentials mode is include: you send cookies, so the API has to name the origin and also send Access-Control-Allow-Credentials: true.
  • Response to preflight request doesn't pass access control check: fix the OPTIONS handler, or add the requested method or header to Access-Control-Allow-Methods or Access-Control-Allow-Headers.
  • Origin mismatch: the header exists but names a different origin. localhost and 127.0.0.1 are different hosts, and so are two ports.

Fix it in the API

For Express, allow the origins you use in development and nothing broader:

import cors from 'cors';

const allowed = ['http://localhost:5173'];
app.use(cors({ origin: allowed }));

The same idea applies in every framework: compare the request's Origin header with an allow list, echo it back in Access-Control-Allow-Origin, add Vary: Origin, and answer OPTIONS with 204. Avoid * in anything that is not a public read-only API, and keep the list in an environment variable so production gets its own values.

Or avoid the cross-origin call

If the frontend is served by Vite or Next.js, forward the calls through the dev server and the browser sees one origin. See how to proxy API requests in the Vite dev server. This removes the error in development, but it does not tell you how the deployed pair will behave, so keep a real CORS rule too if the two will live on different hosts.

What Flisk does here

Flisk gives different answers in its two modes, and both are in the source.

Docker mode (the default for a stack with a gateway) serves the frontend on app.<project>.localhost and the API on api.<project>.localhost, so every call is cross-origin. A backend created with flisk resource allows origins that match a *.localhost host, with any port, and nothing else. The generated source carries a comment that says why, so you can read it and change it. A backend you bring yourself (bring-your-own, or one imported with flisk import) has no such rule: it must allow http://app.<project>.localhost itself. flisk networks prints the URLs, so you can see the exact origin to allow.

Local process mode (a command in service.json) has no gateway. The services answer on http://localhost:<port>. The scaffolded frontend proxies /api and /health through Vite, and the scaffolded API's allow rule matches only hosts with a name in front of .localhost, so a direct call from http://localhost:<port> would not match it. Use the proxy, or add your own origin to the allow rule.

Pitfalls

  • Fixing the wrong layer. If a gateway, a CDN or a second proxy adds its own CORS headers, you can end up with two Access-Control-Allow-Origin values, which browsers reject. Set CORS in one place.
  • An error page without headers. A 500 from your API usually skips the CORS middleware, so the browser reports CORS when the real problem is a crash. Read the API logs. With Flisk, flisk logs --service <name> --tail 50 prints them.
  • Do not turn CORS off in the browser. Flags that disable web security hide the problem from you and from your tests.

Next step

If the request works but your session cookie is missing, you have a related problem: cookies not sent from a frontend to a local API. For a NestJS API in particular, see NestJS local development: watch mode and CORS.

Questions people ask

Why do I get a CORS error even though the API returns 200?

The browser checks the response headers, not the status. If Access-Control-Allow-Origin is missing or names another origin, the browser hides the response from your code.

Is localhost:3000 the same origin as localhost:3001?

No. An origin includes the port, so the two are different origins and a request between them is cross-origin.

Can I use Access-Control-Allow-Origin: * in development?

It works for requests without credentials, but it fails when you send cookies, and it hides mistakes you will meet in production. An explicit allow list is safer.
