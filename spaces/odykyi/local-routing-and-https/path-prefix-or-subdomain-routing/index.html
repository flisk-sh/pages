Local URLs, routing and HTTPS

Path prefix or subdomain: how to route local services

Both work. The choice decides whether you fight CORS or fight base paths.

Use path prefixes when you want one origin and no CORS, and use subdomains when a service serves pages and assets from / and cannot live under a prefix. Path routing (/api/orders) keeps cookies and fetch calls same-origin. Subdomain routing (api.shop.localhost) leaves each app untouched but turns every call between them into a cross-origin request.

What each scheme costs

Path prefixSubdomain
Browser originOneOne per service
CORSNot neededNeeded for browser calls
CookiesFirst-party, simpleNeed care with host and SameSite
App changesOften needs a base pathNone
Proxy ruleStrip the prefixMatch the Host header

Where path prefixes hurt

An API can ignore the prefix if the proxy strips it. A web app cannot. If a React or Svelte app is served under /shop but its HTML links to /assets/app.js, the browser requests the wrong URL. You have to set a base path in the build tool (base in Vite, basePath in Next.js) and in the router. Apps you did not write, such as a prebuilt image with a web UI, often have no such setting. Redirects are the other trap: an app that answers Location: /login sends the browser out of the prefix unless it knows the prefix (see the forwarded headers article for X-Forwarded-Prefix).

Where subdomains hurt

Each name has to resolve. In Chrome, Firefox and current curl, names ending in .localhost resolve to your machine with no hosts-file edits; other tools may not, which is a common surprise (the troubleshooting article on subdomains that do not resolve covers it). Custom names such as .test need a hosts entry or a local DNS. And the browser treats app.shop.localhost and api.shop.localhost as different origins, so the API must send CORS headers and credentialed requests need an exact allowed origin.

What Flisk does

In the Docker path, Flisk uses both, by resource type. These shapes are generated for you:

  • A frontend is served at http://app.<project>.localhost/<name>, a path under the app host.
  • A backend, mcp or bring-your-own API is at http://api.<project>.localhost/api/<name>, with the prefix stripped before it reaches the container. The name is appName without a trailing -api, or the apiPath you set.
  • A bring-your-own app that serves its own pages from / can set "webUi": true. It is then routed on its own host, <name>.<project>.localhost, with nothing stripped.
{ "appName": "app", "appType": "bring-your-own", "port": 3000,
  "image": "mauriceboe/trek", "webUi": true, "healthCheckPath": "/api/health" }

So Flisk's own rule matches the table: APIs go under a prefix, and an app that needs / gets a subdomain. Run flisk networks to see which one each service got. When the whole project runs as local processes, there is no gateway: each service answers on http://localhost:<port>.

How to choose

  1. List the services that serve a browser UI from /. Give those a host name.
  2. Put pure APIs under a prefix on the same host as the frontend that calls them, if you can run one proxy. This removes CORS for that pair.
  3. If you cannot control the proxy (you use Flisk's generated one), accept the cross-origin layout and configure CORS and cookies once.
  4. Keep the local layout close to production. If production uses api.example.com, subdomains locally will expose the same CORS and cookie issues earlier, which is often a benefit.

For the nginx configuration of the path-prefix layout, see routing several local services through one nginx. For the other layout's most common failure, read CORS between localhost subdomains.

Questions people ask

Which is better for local development, paths or subdomains?

Paths give one origin and no CORS but need base-path support in web apps. Subdomains leave apps unchanged but need CORS and careful cookies. Use paths for APIs and a host for web UIs.

How does Flisk route a web UI?

A bring-your-own resource with webUi set to true gets its own host, name.project.localhost, with no prefix stripped. A frontend resource is served under /name on the app host.

Do .localhost names need a hosts file entry?

Not in current browsers and curl, which resolve *.localhost to loopback. Other tools may not, and custom domains need a hosts entry or local DNS.
