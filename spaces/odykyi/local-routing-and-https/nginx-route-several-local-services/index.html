Local URLs, routing and HTTPS

How to route several local services through one nginx

One address in the browser, three processes behind it. The details that break are the trailing slash and the Host header.

To route several local services through one nginx, add one server block and one location per service, each with a proxy_pass to that service's port. A trailing slash on both the location and the proxy_pass URL strips the prefix before the request reaches the service. Pass the Host header on, and reload nginx with nginx -s reload.

A working configuration

Say you have a frontend on port 3000, an orders API on 4000 and a billing API on 4100. Save this as dev.conf and include it from nginx.conf, or run nginx with -c:

server {
  listen 8080;
  server_name shop.localhost;

  location /api/orders/ {
    proxy_pass http://127.0.0.1:4000/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
  }

  location /api/billing/ {
    proxy_pass http://127.0.0.1:4100/;
    proxy_set_header Host $host;
  }

  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
  }
}

Now http://shop.localhost:8080/api/orders/health reaches /health on the orders service. Use 127.0.0.1 instead of localhost in proxy_pass: nginx resolves the name once at startup and localhost may resolve to the IPv6 address ::1 while your service listens only on IPv4.

The trailing slash rule

This is where most routing bugs come from.

locationproxy_passrequest /api/orders/42 arrives as
/api/orders/http://127.0.0.1:4000//42 (prefix stripped)
/api/orders/http://127.0.0.1:4000/api/orders/42 (kept)
/api/ordershttp://127.0.0.1:4000///42 (double slash)

Keep the slashes matched. If the service expects to be mounted at /api/orders itself, do not strip.

Other settings worth knowing

  • Timeouts. proxy_read_timeout defaults to 60 seconds. A debugger pause or a slow job returns 504 from nginx, not from your app. Raise it in development.
  • Buffering. For server-sent events or streamed responses, add proxy_buffering off; or the browser sees the stream late.
  • Upload size. client_max_body_size defaults to 1 MB. Set it higher for file uploads.
  • Restart after crash. If an upstream is down, nginx answers 502. That tells you which service is missing.

Run it and check it

Test the file before you load it with nginx -t -c /full/path/dev.conf. It reports a syntax error with a line number. Then start nginx in the foreground with nginx -c /full/path/dev.conf -g "daemon off;" so you see the log in your terminal, or load the file into your installed nginx and run nginx -s reload. On macOS with Homebrew the main config is under /opt/homebrew/etc/nginx/, and you can drop your file into its servers folder.

Use curl -i against each route in turn, and read the status first. A 404 with an nginx footer means no location matched. A 404 with your own app's error body means the route matched but the prefix was not stripped as you expected. A 502 means nginx could not connect to the port, so the service is down or the port is wrong. A 504 means the service accepted the connection and then took longer than the timeout.

Check one more thing when the frontend loads but its API calls fail: the browser calls the address in the page, not the one you typed in curl. Open devtools, Network, and read the real URL the page requested. A hard-coded localhost:4000 in the frontend bypasses nginx completely, and works only on your own machine.

How Flisk relates

You do not need to write this by hand in a Flisk Docker project. Flisk generates Traefik routes from each service.json: a backend named orders-api is reachable at http://api.<project>.localhost/api/orders, and Flisk strips the prefix before the request reaches your container, the same result as the trailing slash rule above. flisk networks lists every routed URL. That is the same job nginx does here, with the route taken from the manifest.

The nginx approach still fits when your services run without Docker and you want one address and path routing. Flisk starts them as local processes and prints http://localhost:<port> for each, and nginx gives you the single origin. Keep nginx's job small: routing only.

When not to use nginx

If your dev server already proxies (Vite's server.proxy, Next.js rewrites), a second proxy adds one more place for bugs. Use nginx when several backends of different stacks need one address, or when you want your local routing to resemble production.

If a service answers with the wrong paths behind your proxy, read path prefix or subdomain routing to choose a scheme. For a ready-made version of this idea with *.localhost names, see local URLs instead of port numbers.

Questions people ask

Why does my API get a path with a double slash?

The location has no trailing slash but proxy_pass does. Make both end in a slash to strip the prefix, or neither to keep it.

Why use 127.0.0.1 instead of localhost in proxy_pass?

nginx resolves the name once at start, and localhost can resolve to ::1 while your service listens only on IPv4, which gives 502 errors.

Does Flisk need nginx?

No. In the Docker path Flisk generates Traefik routes from service.json. You can still put nginx in front of services that run as local processes.
