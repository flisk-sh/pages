Human Review vs Auto-Merge for Agent PRs: How to Choose

A risk-based rule for which agent pull requests can merge on green CI and which need a person, with the trade-offs of each.

Auto-merge agent pull requests only for low-risk paths that have strong automated checks, and require human review for everything else. The right split depends on how good your tests are, not on how good the agent is.

What auto-merge needs

Auto-merge is safe only when a green build really means "safe to ship". That needs trusted, non-flaky checks, a fast revert path and monitoring after deploy. If you lack any of these, keep humans in the loop.

Sort paths into tiers

TierExamplesMerge rule
LowDocs, comments, test-only changes, patch bumpsAuto-merge on green
MediumFeature code with testsOne human approval
HighAuth, billing, migrations, CI configCode-owner review

Encode the tiers with CODEOWNERS and path labels so the rule is enforced, not remembered.

Turn on auto-merge

GitHub's auto-merge lets a pull request merge itself once required checks and reviews pass. Enable it in repository settings, then it can be turned on per pull request.

gh pr merge 123 --auto --squash

Combine it with a merge queue so combined changes are tested too; see the merge queue guide.

Review after the fact

Some teams let low-risk changes land and have a human skim what merged once a day, turning repeated mistakes into lint rules or checks. This trades a little risk for much faster flow. It only works with fast reverts and good checks, so do not copy it without them.

Watch the numbers and adjust

If reverts or hotfixes climb after you loosen a rule, tighten it. Track revert rate and time to merge by tier; see measuring agent PR quality. The aim is the least human attention that keeps quality steady.

Getting started safely

Begin with the smallest auto-merge scope you can defend, such as documentation-only and test-only changes, and run it for a month. Check what merged, look for reverts and read a sample by hand. If all is well, add the next tier, for example patch dependency updates with passing checks.

Make the rules visible. Put the tiers and their merge rules in CONTRIBUTING.md so authors, agents and reviewers all see the same thing, and so a surprised developer can find the reason a change merged without review. Include who to ask when a pull request lands in the wrong tier.

Keep an emergency stop. A repository variable or label that turns auto-merge off lets you pause everything within a minute if something goes wrong, for example a bad dependency or a flaky check that has started to pass anything. Test the stop switch before you need it. The rest of the safeguards are covered in GitHub Actions security.

Questions people ask

Is auto-merge for agent PRs reckless?

Not if limited to low-risk paths with strong, stable checks and quick revert. It is reckless when checks are weak or flaky.

Who approves if the agent opened the PR?

A person or team other than the author. Use CODEOWNERS so approval comes from someone responsible for that code.
