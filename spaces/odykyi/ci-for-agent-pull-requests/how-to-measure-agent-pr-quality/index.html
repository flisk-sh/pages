How to Measure the Quality of Agent-Written Pull Requests

Merge rate, revert rate, time to green and review rounds tell you whether agents help. Here is how to collect them with the GitHub CLI.

Track four numbers for agent pull requests: merge rate, revert rate, time to green and review rounds. They show whether agents are saving time or just producing review work, and you can pull all of them from the GitHub API.

The four numbers

  • Merge rate: merged pull requests divided by opened ones. A low rate means wasted review.
  • Revert rate: merged changes later reverted or hot-fixed. This is the quality signal.
  • Time to green: from open to all required checks passing.
  • Review rounds: how many times a human had to ask for changes.

Compare each with human pull requests in the same repo, not with an ideal.

Pull the data

If agent pull requests carry a label, as in labelling agent PRs, you can list them.

gh pr list --label agent --state all --limit 200 \
  --json number,state,createdAt,mergedAt,closedAt \
  > agent-prs.json
jq '[.[] | select(.state=="MERGED")] | length' agent-prs.json
jq 'length' agent-prs.json

Divide the two numbers for the merge rate. For reverts, search merged pull requests whose title starts with Revert and map them back.

Watch CI health, not only PRs

Agent volume stresses CI. If default-branch pass rate falls or workflows start flipping between pass and fail, quality is slipping even if each pull request looks fine. Cilytics shows pass rate trends, red and flaky workflows for an org or, with ?repo=owner/name, any public repo. It reads default-branch runs from the last 100 runs and refreshes hourly, so use it for trends rather than live alerts.

Let a score decide

For changes where you can define a deterministic score, such as tests passing, a benchmark number or a lint count, let the model propose and the score accept or reject. That approach is what GEL (Guard, Eval, Loop) is about: CI guards, evals and nightly loops where a fixed score decides. See the GEL repository for how it is set up. It is an approach for work you can measure, not a way to judge every change.

Review monthly and act

Look at the numbers once a month. A rising revert rate means tighten checks or reduce auto-merge. A low merge rate means the tasks or instructions are poor. A long time to green points to slow or flaky CI. For more on what to measure, see CI metrics that matter.

Pitfalls in the numbers

Be careful with small samples. Ten pull requests tell you little, and one bad week can swing the revert rate. Look at at least a month and report counts next to percentages, such as "3 of 41 reverted".

Beware of comparing different kinds of work. Agents are often given the easy tasks, so a high merge rate may reflect task choice, not skill. Break results down by tier or by task type before drawing conclusions.

Do not reward volume. A team that celebrates the number of agent pull requests will get more of them, and worse ones. Track merged value instead: changes that shipped and stayed shipped. Finally, make sure the measurement itself cannot be gamed by the thing it measures. If the agent can edit the label or the check, the numbers mean nothing, which is another reason to apply labels from a workflow and protect the CI configuration.

Questions people ask

What is a good merge rate for agent PRs?

There is no standard number. Compare with your own human pull requests and look at the trend; a falling rate is the warning sign.

How do I detect reverts?

Search merged pull requests with titles starting with Revert, or commits created by git revert, and link them to the original change.
