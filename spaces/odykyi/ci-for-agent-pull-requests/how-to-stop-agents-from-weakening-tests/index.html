How to Stop Coding Agents From Weakening Tests

To get a green build, agents sometimes skip, delete or loosen tests. Learn to detect it in CI, send it to a human and make the rule explicit for the agent.

Add a CI check that flags removed tests, new skip markers and loosened assertions, and send those pull requests to a human. An agent told to make the build green will sometimes reach for the easiest way, and the easiest way is to change the test.

What weakening looks like

  • Deleting a failing test file.
  • Adding skip, xfail, .only or @Ignore.
  • Replacing an exact assertion with a vague one, such as comparing to any().
  • Raising a timeout or tolerance until the test passes.
  • Catching an exception and ignoring it.

Any of these can be legitimate. The point is that a human should see them.

Flag them in the diff

Scan the added lines of the diff for skip markers, and the removed lines for deleted assertions.

git fetch origin main
if git diff -U0 origin/main...HEAD -- tests | grep -E '^\+.*(\.skip|xfail|@skip|\.only\(|@Ignore)'; then
  echo 'Skipped tests added, needs human review'
  exit 1
fi

Make the failure message tell the agent what to do: fix the code, not the test, or ask for a maintainer to add an override label.

Detect fewer tests

Record the test count on main and compare it in the pull request. A drop in the number of collected tests without a matching removal in the diff deserves a look. Most runners can print a count, for example pytest --collect-only -q | tail -1.

Say it in the instructions

Write the rule in AGENTS.md in plain words: do not delete, skip or weaken tests to make the build pass; if a test seems wrong, say so in the pull request description. This will not stop every case, but it removes the excuse that nobody said it was not allowed. See how to write an AGENTS.md.

Protect the test configuration

Treat the files that define what runs, such as the test config, the CI workflow and coverage settings, as protected paths with code-owner review. Otherwise an agent can "fix" a failure by excluding the failing folder. For protecting paths, read files agents should not edit.

Handling a flagged pull request

When the check flags a pull request, read the reason before deciding. Sometimes a test really was wrong, or tests a behaviour that has been removed on purpose. In that case, approve and make sure the pull request description explains it. Other times the agent has hidden a real bug. Ask it to restore the test and fix the code.

Make the review quick. The check should print the exact added skip lines or removed assertions with file and line, so the reviewer sees what changed without reading the whole diff. Link the output in a pull request comment.

If the same agent or task keeps producing flagged pull requests, look at the instructions and the task. Often the test is failing because the task needs information the agent does not have, such as a running service or a seed dataset. Fixing that cause beats policing symptoms. See making a repo ready for coding agents for the setup side.

Questions people ask

Do agents really do this?

It is a known failure mode when the goal is only a green build. The risk is real enough to add a cheap automated check.

Will this block legitimate test cleanup?

It sends such pull requests to a human, which is the intent. A maintainer can approve them or add an override label.
