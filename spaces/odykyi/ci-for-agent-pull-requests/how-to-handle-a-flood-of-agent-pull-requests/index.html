How to Handle a Flood of Agent-Written Pull Requests

When coding agents open more pull requests than people can read, you need limits, triage and automation. Here is a workable setup.

Cap the number of open agent pull requests, make CI the first reviewer, and sort the rest by risk so humans read only what needs judgement. Without limits, agents produce review debt faster than any team can pay it.

Why the queue grows

An agent can open a pull request in minutes, but a person still needs minutes to understand one. Open a dozen a day and review becomes the bottleneck, so changes pile up, conflict with each other and go stale. The fix is not to review faster; it is to let fewer, better-prepared pull requests through.

Set a work-in-progress limit

Allow each agent, or the agent fleet as a whole, only a small number of open pull requests at once, for example three. A new one starts only when an old one merges or closes. This keeps changes small, avoids merge conflicts and forces the agent to finish work instead of starting more. You can enforce it with a script that counts open pull requests by label or author.

gh pr list --label agent --state open --json number | jq length

Triage by risk

Not every change deserves the same attention. Sort them.

  • Low risk: docs, tests, formatting, dependency patch bumps. Let CI decide.
  • Medium risk: behaviour changes in well-tested code. One quick human review.
  • High risk: auth, billing, migrations, workflows. Careful review by code owners.

A path-based labeler can apply these tiers automatically; see labelling agent pull requests.

Make CI the first reviewer

Every pull request should arrive with a pass or fail from required checks, so people never read a red one. Failing pull requests go back to the agent automatically or get closed after a few days. See required status checks for agent PRs.

Close stale ones without guilt

An agent pull request that has sat for a week and conflicts with main is cheaper to regenerate than to repair. Close it with a comment and let the agent redo it on a fresh base. Keeping the queue short is a feature.

A simple daily routine

Make the process boring. Each morning, list open agent pull requests sorted by risk and age. Merge the green low-risk ones, send the red ones back or close them, and review the medium ones in a single block of time instead of context-switching all day. Keep high-risk ones for the owning team.

gh pr list --label agent --state open --json number,title,createdAt,statusCheckRollup

Track how many pull requests you closed without merging. A high number means the agent is being given tasks it cannot finish, or the instructions are poor, and that is where to look first. Reducing the volume of bad pull requests is worth more than speeding up review of them. If one task type keeps failing, take it away from the agent until the instructions or checks improve.

Questions people ask

What is a reasonable limit on open agent PRs?

Start small, such as three per agent, and adjust to how fast your reviewers actually work. If the queue still grows, lower it.

Should agents rebase their own PRs?

Yes where possible, but closing and regenerating a stale one is often faster than resolving conflicts.
