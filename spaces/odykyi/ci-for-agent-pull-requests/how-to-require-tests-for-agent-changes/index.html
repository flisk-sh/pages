How to Require Tests for Agent-Written Changes

Check that source changes come with test changes, and that new code is actually covered, without turning CI into a coverage game.

  3. Check that tests can fail

Fail a pull request when it changes source files but touches no tests, and report coverage on the changed lines, not the whole project. Agents often produce plausible code that nothing exercises, and these two checks catch it.

The simple rule: code change needs test change

Compare the changed paths. If anything under src/ changed and nothing under tests/ did, fail with a clear message.

git fetch origin main
FILES=$(git diff --name-only origin/main...HEAD)
echo "$FILES" | grep -q '^src/' && ! echo "$FILES" | grep -qE '^(tests/|.*\.test\.)' \
  && { echo 'Source changed without tests'; exit 1; }
exit 0

Allow a label like no-tests-needed for refactors, docs and config, set only by maintainers.

Measure coverage on the diff

Whole-project coverage moves slowly and hides gaps in new code. Diff coverage tells you what share of the lines in this pull request ran during tests. Tools such as diff-cover for Python read a coverage report and the git diff.

pytest --cov=src --cov-report=xml
diff-cover coverage.xml --compare-branch=origin/main --fail-under=80

Pick a threshold your team can meet. Other languages have similar tools or services.

Check that tests can fail

A test that asserts nothing passes forever. Ask the agent to show the new test failing before the fix and passing after it, and paste both outputs in the pull request. For important modules, mutation testing tools can check whether tests notice changed behaviour, though they are slow and best run nightly.

Avoid the coverage game

Coverage is a floor, not a goal. An agent told to reach 90 percent can write tests that call code and assert nothing. Keep the threshold moderate, review a sample of new tests by hand and watch for patterns like empty assertions. See how to stop agents from weakening tests for the related failure mode.

Where this check fits

Run the test-required check early in the pipeline, because it costs a few seconds and gives immediate feedback. Put the diff-coverage step after the unit tests, since it needs the coverage report. Make both required only once they have been stable for a couple of weeks, and start by commenting the result on the pull request without blocking.

Tell the agent in AGENTS.md what is expected: new behaviour needs a test that would fail without the change, and bug fixes need a regression test. Ask it to name the test in the pull request description. Reviewers then know where to look first.

Finally, remember that tests are code too. Review them for clarity: one behaviour per test, a name that says what is expected, and no logic that mirrors the implementation. Tests that copy the code under test will pass even when the code is wrong.

Questions people ask

What coverage threshold should I set?

Choose a number your current pull requests already meet most of the time, often around 70 to 85 percent on changed lines, then raise it slowly.

Do config and docs changes need tests?

No. Use path rules or a maintainer-only label to exempt them.
