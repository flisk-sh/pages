CI for multi-service apps

How to run integration tests in CI without Docker

No image builds, no pulls. Each service runs as a local process and CI waits until all of them answer.

You can run a multi-service stack in CI with no Docker by running each service as a plain process. In Flisk, a service whose service.json has a command runs as a local process, and flisk up --wait starts them all and exits 0 once they answer. Your tests then run against http://localhost:<port>.

When this path makes sense

Skipping containers removes image builds and pulls, so the job starts faster and needs fewer moving parts. It suits stacks where the services are Node, Python, Go or Bun programs and the only real dependency is a database or cache you can start another way. It does not reproduce your production images, so keep a container run for the checks that need them.

Step 1: declare each service as a process

Each service has a service.json with a command, a port and, ideally, a health check path:

{
  "appName": "orders-api",
  "appType": "backend",
  "command": "bun run start",
  "port": 4001,
  "healthCheckPath": "/health",
  "dependsOn": ["billing-api"]
}

Flisk treats a service as ready when its health URL answers. With no health path it falls back to the port accepting connections. dependsOn controls start order, so the services a service needs start first. The full list of fields is in the service.json reference, and flisk resource <name> --type backend creates the file for you rather than writing it by hand.

Step 2: start the stack and wait

- uses: actions/setup-node@v4
  with:
    node-version: 22
- run: npm install -g @flisk-sh/flisk
- run: flisk project --yes
- run: flisk up --wait --wait-timeout 300
- run: npm test

flisk project --yes writes the git-ignored .env that a fresh clone lacks, and it needs no Docker. flisk up --wait starts the stack in the background and exits 0 when every service is healthy, or 1 on failure or timeout. The processes keep running for the next step. Flisk needs Node 22.12 or newer, so pin a version that satisfies it. Your test step can then call the services directly, for example curl http://localhost:4001/health. There is no gateway in this mode, so no hostnames, only ports. If a test needs the stack's environment for a one-off command, flisk run orders-api -- bun run seed runs it with that service's variables.

What the process runner does for you

  • It waits up to 60 seconds per service for it to become ready.
  • A process that exits is restarted after 1, 2, 4 and 8 seconds. After five quick exits Flisk stops restarting it, so a crash loop surfaces as a failed run instead of hanging.
  • It refuses to start when a port is already in use, which catches two jobs sharing a self-hosted runner.
  • Logs go to .flisk/native/logs/<service>.log, and flisk logs --unhealthy prints them for failing services.

Environment values in env can use ${VAR}, resolved from the shell first, then the project .env, then the service's own .env, then a :-default. This lets CI override a value with a plain environment variable.

The database still needs a home

Most stacks need Postgres or Redis. You have two honest options. Use a GitHub Actions services: container for the database and point DATABASE_URL at localhost, which keeps your own services as processes. Or declare the database as an image service and let Flisk run it in Docker alongside the process services. Mixing is supported for an image service, but a service that has a Dockerfile in the same stack as command services fails with MIXED_RUNTIME. The trade-offs of the first option are in service containers or the whole stack in CI.

Pitfalls

  • Passing here, failing in production. Processes skip the Dockerfile, the base image and the container network. A missing system library only shows up in the image. Keep one container-based run, even if it is nightly.
  • Background processes at job end. On a hosted runner they die with the job. On a self-hosted one, run flisk down in an if: always() step so ports are free for the next job.
  • Health check always green. A /health that returns 200 before the database connects makes --wait report success too early. Make it check what the service really needs. See waiting for every service to be healthy.
  • Windows and macOS runners. Treat them as separate cases and test them before you rely on them.

When not to use it

Do not use this as your only CI if you ship container images, if services depend on Linux packages baked into the image, or if your tests cover network policy, volumes or the gateway. In those cases run the container stack, and use the process run as a quick first job.

Next, make sure the way CI starts the stack matches how developers start it, in how to keep CI the same as local development.

Questions people ask

Can I still use a database without Docker?

Yes. Use a GitHub Actions services container or a hosted test database and set its URL through an environment variable. Flisk can also run an image service in Docker next to process services.

What happens if a service keeps crashing?

Flisk restarts it after 1, 2, 4 and 8 seconds, then stops after five quick exits, so the wait fails instead of hanging.

Does this replace testing the container images?

No. Processes skip the Dockerfile and base image, so keep at least one run that builds and starts the real images.
