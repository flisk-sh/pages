How to wait for every service to be healthy before CI tests

Replace the fixed sleep with a readiness wait that fails fast, names the unhealthy service and prints its last log lines.

Do not start your tests when the containers are merely running. Start them when every service answers a real readiness check, and give that wait a timeout that is shorter than the job timeout. In CI that means a health endpoint per service, one blocking wait command (Compose --wait, a polling script, or flisk up --wait), and a clear failure message when the wait times out.

Why "started" is not "ready"

A container is running as soon as its main process has been forked. A Postgres container accepts TCP connections before it can run a query. An API can listen on its port while it is still running migrations or warming a cache. Tests that start in that gap fail with connection resets, 502 responses or empty tables, and the failure disappears when you re-run the job. That is the most common source of "flaky" integration runs in CI, and the cure is a deliberate wait, not a sleep 30.

A fixed sleep is wrong in both directions. On a fast run it wastes time, and on a slow runner (a cold image cache, a noisy neighbour) it is too short. Wait for a condition instead.

Design the health endpoint first

Whatever tool does the waiting, it needs something to ask. Keep two ideas apart:

  • Liveness: the process is up. A restart is the only cure if it fails.
  • Readiness: the service can do its job now. Its database connection works, its migrations are done, and it can serve a request.

For CI you want readiness. Return a non-2xx status until the service has connected to what it needs. Do not make the check call other services deeply, or one slow neighbour will turn the whole stack red for the wrong reason. The article on health and readiness endpoints for an agent service shows the same split in a concrete service.

Three ways to block until ready

Docker Compose. Give each service a healthcheck, then start with --wait. The command returns once the services are running and healthy, and fails if one cannot reach that state:

docker compose up -d --wait --wait-timeout 300
npm test

A service without a healthcheck counts as ready when it is running, so the flag only helps if you wrote the checks. See Compose depends_on and healthchecks for the check itself.

A polling script. When the services are not in Compose, poll the URLs. With curl, --retry-connrefused is needed because a refused connection is not retried by default, and a 404 is not retried either:

for url in http://localhost:4000/health http://localhost:3000/; do
  curl --fail --silent --show-error \
    --retry 60 --retry-delay 2 --retry-connrefused \
    "$url" > /dev/null
done

Node projects often use the wait-on package for the same job: npx wait-on -t 120000 http://localhost:4000/health.

Flisk. flisk up --wait starts the stack in the background and returns when every service is healthy. It exits 0 on success and 1 on failure or timeout, and the stack keeps running, so the next step can use it. flisk down stops it:

flisk up --wait --wait-timeout 600
npm test --prefix tests/integration
flisk down

The timeout is in seconds, from 1 to 21600, and defaults to 1800. That default is long for CI: pick a value a little below your job's timeout-minutes so the wait fails with a useful message instead of the job being killed with none.

What Flisk waits for

For services started as local processes (a command in service.json), a service is ready once its healthCheckPath answers, or, with no path, once its port accepts connections. A service that declares dependsOn starts only after those are ready. For container services, healthCheckPath sets the container health check. You can set the probe in service.json with the healthCheck field: a path, a TCP port, or a command that must exit 0. A gRPC server or a database proxy is the usual reason to use port or command.

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "stack": "shop",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["postgres"]
}

When the wait fails, flisk up --wait prints which services were unhealthy and the last lines of each one's log (up to 5 per service and 20 in total), which is often the whole diagnosis. With --json it prints one result object instead, with the same log lines under data.failures.

Check the public URL too

A container can be healthy while the route in front of it returns 404. On the Docker and Tilt path you can add a smoke block to service.json. flisk up then sends HTTP requests to the public URL it prints and exits non-zero when a step fails, retrying 404, 502, 503 and 504 for timeoutSeconds (default 60) before it gives up. A step can save a value from one response, such as an id, and use it in the next request. The smoke check is HTTP only, so it does not replace a browser test. The integration tests against the real stack article covers what to assert once the stack is up.

Pitfalls

  • Waiting on a stack that is already running. flisk up --wait on a stack that is already up returns success without checking health. On a fresh CI runner this never happens, but on a self-hosted runner a leftover stack can hide a broken start. End every job with flisk down in an if: always() step.
  • A health endpoint that always returns 200. The wait then proves nothing. Make the endpoint fail until the dependencies are reachable.
  • Deferred services. Services configured with sablier.deferStart are not waited for. They start on their first request, so the first test that hits one will be slower.
  • Mixing up timeouts. Keep three numbers in order: the per-request timeout of the poll, the wait timeout, and the job timeout. Each should be smaller than the next.

When a wait is not the answer

If a test fails because it ran before some background work finished (a queue consumer, an index build), a health check cannot help. Poll for the outcome in the test itself, with a timeout, instead of waiting for the whole stack to be quiet.

Questions people ask

Does docker compose up --wait wait for services without a healthcheck?

It waits until they are running. A service with no healthcheck is treated as ready once it is running, so write a healthcheck for every service you want the wait to cover.

What exit code does flisk up --wait return?

0 when every service is healthy, 1 when the stack fails or the --wait-timeout (default 1800 seconds, at most 21600) passes. The stack keeps running either way, and flisk down stops it.

Why not just sleep for 30 seconds?

A fixed sleep is too long on a fast run and too short on a slow one. Waiting for a health check takes exactly as long as needed and fails with a reason when something never starts.
