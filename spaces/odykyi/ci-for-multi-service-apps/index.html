CI for multi-service apps

Run the whole stack in CI: service containers, health waits, caching, test splits and keeping CI close to local.

  1. How to cache Docker builds in GitHub Actions for many servicesA fresh runner has no layers. Give BuildKit a cache, keep each service's cache separate, and build only what changed.
    4 min
  2. GitHub Actions service containers or the whole stack in CI?Service containers are the fast path for one service and a database. A full stack is for tests that cross service boundaries.
    4 min
  3. How to get useful logs when a multi-service CI run failsThe runner disappears after the job. Collect status and logs before it does, and choose the files you upload.
    4 min
  4. How to keep CI the same as local developmentOne definition of the stack, used in both places. Pin the versions and write down what legitimately differs.
    4 min
  5. How to run migrations and seed data in CI before testsMake migrations a service the stack waits for, so tests never start against a half-built schema.
    4 min
  6. How to run CI only for the services that changed in a monorepoMap changed files to services, run only those jobs, and keep a single gate job so branch protection never hangs.
    3 min
  7. How to run integration tests in CI without DockerNo image builds, no pulls. Each service runs as a local process and CI waits until all of them answer.
    4 min
  8. How to handle secrets and .env files for a stack in CILet the stack generate its own values, add only the real secrets a test needs, and keep them away from forks and logs.
    4 min
  9. How to split slow end-to-end tests across parallel CI jobsEach runner boots its own stack and runs a slice of the tests, then one job merges the reports.
    3 min
  10. How to wait for every service to be healthy before CI testsReplace the fixed sleep with a readiness wait that fails fast, names the unhealthy service and prints its last log lines.
    5 min
Try it on your laptop

One command starts a working multi-service app.
