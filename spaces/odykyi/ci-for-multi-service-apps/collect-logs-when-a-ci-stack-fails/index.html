How to get useful logs when a multi-service CI run fails

The runner disappears after the job. Collect status and logs before it does, and choose the files you upload.

When a multi-service CI run fails, the useful evidence is gone as soon as the runner is discarded. Add a step that runs even on failure, prints which services are unhealthy and their last log lines, and uploads the full logs as an artifact. With Flisk that is flisk status --json plus flisk logs --unhealthy, and you never upload your .env.

Print the failure where people look first

flisk up --wait already helps. When the wait fails, it prints the last log lines of the unhealthy services, up to 5 lines per service and 20 in total. With --json the same lines appear as logs inside data.failures. For many failures that is enough to name the broken service in the job log. For the rest you need more, and that is what the next steps add.

Step 1: a step that always runs

By default a step is skipped once an earlier step has failed. Use if: always() (or if: failure() to run only on failure):

- name: Stack state on failure
  if: failure()
  run: |
    echo "::group::status"
    flisk status --json || true
    echo "::endgroup::"
    echo "::group::unhealthy logs"
    flisk logs --unhealthy --tail 200 || true
    echo "::endgroup::"

The ::group:: lines make each block collapsible in the Actions log. The || true keeps the diagnostic step itself from hiding the real failure. flisk status --json lists each service and whether it is ready. flisk logs also takes --service, --since and --json. Flisk masks secret values it knows from .env in log output, so the lines are safer to read. That is a safeguard, not a guarantee: a secret that your own code prints in another form is not covered.

Step 2: save the full logs as an artifact

A tail is often too short. Write everything to files and upload them:

- name: Save logs
  if: always()
  run: |
    mkdir -p ci-logs
    flisk status --json > ci-logs/status.json || true
    flisk logs --tail 2000 > ci-logs/all.log || true
    flisk doctor --json --no-ping > ci-logs/doctor.json || true
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: stack-logs
    path: ci-logs
    retention-days: 7

flisk doctor --json records the environment checks (Docker, ports, versions). --no-ping skips the network ping, which is useful when the failure might itself be a network problem. When you run services as local processes, their raw logs are also in .flisk/native/logs/<service>.log, and you can upload that directory instead. Upload from ci-logs or a specific log directory, not from the project root.

What never goes in the artifact

  • The .env file. It holds generated passwords and keys. Artifacts can be downloaded by anyone with read access to the repository, and for a public repository that is everyone.
  • Whole directories. Do not upload . or .flisk without checking what is inside. Pick the files you want.
  • Raw output of commands that print the environment. A debug env dump is a leak waiting to happen.

If a log might contain a secret, mask it before it is printed with ::add-mask::, and keep retention short.

Plain Compose, for comparison

If you run a Compose file yourself, the equivalent is docker compose logs --no-color --timestamps, plus docker compose ps -a to see which containers exited and with what code. The timestamps matter: they let you line up a crash in one service with the error that appeared in another a moment earlier. Flisk's own wait output and logs give you the same starting point without writing that yourself, but the approach is the same.

Make the summary readable

Write a short note to $GITHUB_STEP_SUMMARY so the run page shows the answer without opening the log. For example, append the names of the unhealthy services from the status JSON. Keep it to a few lines and link to the artifact by name.

Pitfalls

  • The step is skipped. Without if: always() or failure() it never runs when you need it.
  • A cancelled job. A timeout or manual cancel may leave no time for cleanup steps. Set the wait timeout below the job timeout.
  • Logs from the wrong moment. If you stop the stack before collecting, the logs may be gone. Collect first, then run flisk down.
  • The smoke records. If you use the smoke feature, its records are kept under .flisk/smoke/. They have secret values masked, but check them before you upload.

When not to bother

For a two-service stack that fails rarely, the output of flisk up --wait alone is usually enough. Add the artifact step when failures happen on CI only and you cannot reproduce them, which is when you most need the evidence.

Better logs are one half; the other half is failing less often, so read how to wait for every service to be healthy.

Questions people ask

Why does my cleanup step not run after a failure?

Steps are skipped after a failure unless they have if: always() or if: failure().

Is it safe to upload the whole project directory?

No. The generated .env holds passwords and keys, and artifacts can be read by anyone with repository read access. Upload chosen files from a dedicated folder.

Where are logs for services running as local processes?

In .flisk/native/logs/<service>.log, and flisk logs prints them too.
