How to run migrations and seed data in CI before tests

Make migrations a service the stack waits for, so tests never start against a half-built schema.

In CI, start with an empty database on every run, apply migrations with the non-interactive deploy command, load only the seed data the tests need, and only then run the tests. The cleanest way to guarantee the order is a one-shot migrator service that the API depends on, so that your wait step returns only after migrations have finished.

Start from an empty database every time

A CI database should not survive between runs. A fresh one proves that your migrations build the schema from nothing, which is what a new developer or a new environment does. On a GitHub-hosted runner the database disappears with the job, so you get this for free. On a self-hosted runner, make sure volumes are removed at the end of the job, for example with flisk down --purge, which deletes the stack's volumes, networks and images. Use it only on runners you own, since it deletes the data it names.

Use the deploy command, not the dev command

Migration tools have an interactive mode for development and a strict mode for automation. Use the strict one:

  • Prisma: prisma migrate deploy. Do not use prisma migrate dev in CI. It can prompt, and it can create new migrations or reset the database.
  • Drizzle: drizzle-kit migrate applies the committed migration files. drizzle-kit push is a development shortcut.
  • Other tools have the same split. Look for the command that only applies files already in the repository.

This also makes CI a check: if the committed migrations do not produce the schema the code expects, tests fail here, not in production.

Make the migration a service, so the wait covers it

A common failure is a test that starts before migrations finish, and fails with "relation does not exist". Fix the order in the stack, not with a sleep. Flisk's convention is an explicit migrator resource. Creating a Prisma backend with the CLI shows it:

flisk resource orders-api --type backend --stack shop --feature prisma

This creates orders-api and also orders-api-migrator, whose appType is migrator, whose start script is prisma migrate deploy, and which depends on the database. The API lists the migrator in its dependsOn. A dependsOn condition can be service_started, service_healthy or service_completed_successfully, and the last one is for one-shot jobs like migrators and seeders: the dependent starts only after the job has exited with code 0. If the migration fails, the API never starts and flisk up --wait exits 1, so CI fails at the right step, with the migrator's log lines in the output.

- run: flisk project --yes
- run: flisk up --wait --wait-timeout 600
- run: npm test

By the time --wait returns, migrations are done. The principle is also described, with Compose, in Compose depends_on and healthchecks, and for local development in database migrations in local dev.

Seed the data tests need

Seed after migrations and before tests, and keep the seed small and deterministic. Two ways to do it:

  1. As a one-shot service. A seeder resource with service_completed_successfully in the dependency chain, the same way as the migrator.
  2. As a step. flisk run orders-api -- bun run seed runs one command with that service's environment, so it connects to the same database as the service. Add --json if you want the exit code, stdout and stderr in a form a script can read.
- run: flisk up --wait
- run: flisk run orders-api -- bun run seed
- run: npm test

Replace bun run seed with your own seed command. Prefer the step when only some tests need the data, and the service when everything does.

Keep tests independent of the seed

Seed a base set: reference data, a test user, a few records. Let each test create the rest through the API and use unique values such as a random suffix, so tests do not collide when they run in parallel or when shards share nothing but their own database. A test that depends on row number 1 is a test that fails when the seed changes.

Pitfalls

  • Migrations run from the API's start script. Several replicas race each other, and a slow migration looks like an unhealthy API. Keep them in a separate migrator.
  • A migrator that never exits. If the job is a long-running process, service_completed_successfully waits forever. The migrator must run once and exit.
  • Prompts in CI. A command that waits for input hangs until the job times out. Use the deploy command and non-interactive flags.
  • Production data. Never point CI at a database with real data, and never load a production dump without anonymising it.
  • Seed drift. A seed that is not updated with the schema fails with column errors. Run it on every CI run so it cannot rot.

When not to seed in CI

If your tests create all their own data, skip the seed. Fewer shared fixtures mean fewer surprises. Add a seed for the things you cannot create from a test, such as reference tables that the application expects to exist.

For the start-up wait that this order relies on, see how to wait for every service to be healthy before CI tests.

Questions people ask

Why not run prisma migrate dev in CI?

It is the interactive development command. It can prompt, create migrations or reset the database. Use prisma migrate deploy, which only applies committed migrations.

How do I make sure tests start after migrations?

Put the migration in a one-shot migrator service and make the API depend on it. Then flisk up --wait only returns after the migration finished, and fails if it did not.

How do I run a seed script with the service's environment?

Use flisk run <service> -- <command>, for example flisk run orders-api -- bun run seed. Add --json for the exit code and output.
