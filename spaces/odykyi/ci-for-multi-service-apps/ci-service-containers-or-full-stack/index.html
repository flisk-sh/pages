CI for multi-service apps

GitHub Actions service containers or the whole stack in CI?

Service containers are the fast path for one service and a database. A full stack is for tests that cross service boundaries.

Use GitHub Actions service containers when one service under test needs a few backing images such as Postgres or Redis. Boot the whole stack when the thing you are testing is how services work together. Service containers are simpler and start in parallel with your job, but they only run ready-made images, with no build step and no ordering between them.

What service containers give you

The services: key in a workflow job starts containers next to the job and removes them when the job ends. You can pass a health check in options, and the runner waits for it before your first step runs:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: app
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
        env:
          DATABASE_URL: postgres://postgres:postgres@localhost:5432/app

If the job runs directly on the runner, as above, reach the container on localhost and the port you mapped. If the job itself runs in a container (container:), use the service label (postgres) as the hostname instead. Service containers need a Linux runner.

Where service containers stop

  • Images only. There is no build:. Your own services must run some other way, usually as processes started in a step.
  • No ordering. The containers start together. If one needs another to be ready first, you handle that yourself.
  • No routing. You get published ports, not the host names and paths your frontend uses in development. Anything that depends on a gateway or a hostname behaves differently from your laptop.
  • Different from local. The configuration lives in the workflow file, so it is a second description of your backing services next to the one developers run locally. The two drift.

Many teams use both. Unit and per-service integration tests run on every push with service containers. The whole-stack job runs on pull requests that touch more than one service, or nightly. That keeps the fast feedback loop fast and still gives you one job that proves the wiring.

Use the same service.json for both

With Flisk you can keep one description of your services and choose where the database comes from. A service that has a command in its service.json runs as a local process, and ${VAR} in its env resolves from your shell first, then from the project .env, then from the :-default. So the same manifest works on a laptop and in a job that sets APP_DATABASE_URL to point at a service container (the name differs from DATABASE_URL on purpose, because a project .env can define that one too):

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "env": {
    "DATABASE_URL": "${APP_DATABASE_URL:-postgres://postgres:postgres@localhost:5432/app}"
  }
}

The workflow then installs Flisk, runs flisk up --wait after the Postgres service container is healthy, runs the tests and ends with flisk down. This path needs no Docker for your own code, but it also has no gateway: services are reached at http://localhost:<port>. The article on running integration tests in CI without Docker covers its limits.

If your stack uses Flisk's container path, Flisk provisions its own Postgres, and a service container on port 5432 would clash with it. Pick one source of Postgres per job. The runner image may also have Postgres installed and listening on 5432, which is worth checking in either approach.

Pitfalls

  • Missing health options. Without --health-cmd the runner cannot know when the database is ready, and the first test is the one that finds out.
  • Version drift. Pin the image tag to the major version you run in production, not latest.
  • Wrong host name. localhost works on the runner; the service label works inside a job container. Mixing them gives a connection refused that looks like a flaky service.
  • Passwords in the workflow. Throwaway CI database credentials are fine in the file. Real credentials are not.

When not to use the whole stack

If your tests mock every network boundary, booting everything buys you nothing. Start with service containers, and add a stack job for the specific journeys that cross service boundaries.

If you decide to boot the stack, the next thing to make reliable is the start-up itself: how to wait for every service to be healthy before CI tests.

Questions people ask

Can GitHub Actions service containers build my Dockerfile?

No. The services key runs images that already exist. To run your own services, build and start them in a step, or boot the stack with Compose or another tool.

What host name do I use to reach a service container?

If the job runs on the runner, use localhost and the mapped port. If the job runs inside a container, use the service label, for example postgres.

Do service containers work on macOS or Windows runners?

No. Service containers and job containers need a Linux runner.
