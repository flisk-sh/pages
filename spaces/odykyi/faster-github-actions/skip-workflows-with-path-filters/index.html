GitHub Actions Path Filters: Skip Workflows When Files Did Not Change

Use paths and paths-ignore to avoid running tests on docs-only changes, and avoid the required-checks trap that leaves pull requests waiting forever.

Use paths or paths-ignore under the push and pull_request triggers so a workflow runs only when relevant files change. The catch: a skipped workflow does not report a status, which can block merges if that check is required.

Basic usage

on:
  pull_request:
    paths:
      - 'src/**'
      - 'package.json'
      - 'package-lock.json'
      - '.github/workflows/ci.yml'

# or the opposite
on:
  pull_request:
    paths-ignore:
      - 'docs/**'
      - '**.md'

Always include the workflow file itself in paths, so a change to the pipeline triggers a test of the pipeline.

The required checks trap

If a workflow is skipped by a path filter, its checks stay in a pending state. If that check is marked as required in branch protection, the pull request cannot merge. This is the most common problem with path filters.

Two workable fixes. First, do not put the path filter on the trigger. Instead, run the workflow always, and decide inside it which jobs to run. Second, add a small always-running gate job that is the only required check.

Filter at the job level

The dorny/paths-filter action outputs whether files matched, and jobs can use that in if.

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      src: ${{ steps.f.outputs.src }}
    steps:
      - uses: actions/checkout@v4
      - id: f
        uses: dorny/paths-filter@v3
        with:
          filters: |
            src:
              - 'src/**'
  test:
    needs: changes
    if: needs.changes.outputs.src == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo run tests

Pin third-party actions to a commit SHA if your security policy requires it.

A gate job for required checks

  ci-ok:
    if: always()
    needs: [test, lint]
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo '${{ toJSON(needs.*.result) }}' | grep -Eq 'failure|cancelled' && exit 1 || exit 0

Mark only ci-ok as required. A skipped dependency counts as a pass, a failed or cancelled one fails the gate. This pattern also helps in a monorepo.

Test the filters

Path patterns use glob rules, and mistakes are common. A pattern like src/* matches files directly in src, while src/** matches all nested files. Open a pull request that changes only a docs file and confirm the workflow is skipped. Then change a source file and confirm it runs. Do both before you rely on the filter. Also remember that a filter is evaluated per event, so a pull request that touches many files will run if any file matches.

Be careful what you skip

Skipping is only safe if you are sure what depends on what. A change to a shared config, a lockfile or a script can affect everything. List those paths explicitly. When unsure, run the workflow and use a cache instead, as in caching dependencies.

Questions people ask

Do path filters work for tags?

No. Path filters are ignored when a workflow runs on a tag push, so use branches for filtered triggers.

Why is my pull request stuck waiting for a check?

A required check was skipped by a path filter, so it never reported. Use a gate job as the only required check.
