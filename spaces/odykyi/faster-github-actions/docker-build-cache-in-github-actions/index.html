How to Cache Docker Builds in GitHub Actions with Buildx

Reuse Docker layers between runs with the GitHub cache backend, order your Dockerfile for cache hits, and know when the cache will not help.

Use Docker Buildx with the gha cache backend so layers are saved in the GitHub Actions cache and reused on the next run. Pair that with a Dockerfile that copies dependency files before source code, so most layers stay unchanged.

Workflow setup

- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v6
  with:
    context: .
    push: false
    tags: myapp:ci
    cache-from: type=gha
    cache-to: type=gha,mode=max

mode=max exports all layers, including intermediate ones from multi-stage builds. The default exports only final layers, which misses a lot. Check the action's README for current major versions.

Order the Dockerfile for the cache

Docker reuses a layer only if everything before it is unchanged. Put things that change rarely first.

FROM node:20-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

If you copy all source first, every code change reinstalls all dependencies. Splitting the copy keeps the npm ci layer cached until the lockfile changes.

Use a .dockerignore

Without it, COPY . . sends .git, node_modules and build output as context, which slows the build and changes the layer hash for no reason.

.git
node_modules
dist
*.log

Alternatives: a registry cache

The GitHub cache has size limits and is scoped per branch. An alternative is a registry cache that you push to your own image repository.

cache-from: type=registry,ref=ghcr.io/OWNER/myapp:buildcache
cache-to: type=registry,ref=ghcr.io/OWNER/myapp:buildcache,mode=max

This needs login and package write permissions. It works across branches and from your laptop. It is more setup, so start with gha.

Check that layers are reused

Read the build log. Cached layers are marked CACHED in BuildKit output. Run the workflow twice with no code change and the second run should show most steps as cached. Then change one source file and confirm only the steps after the COPY . . line rebuild. If the dependency install runs again, the layer order or the cache scope needs a fix. Also pin the base image tag, since a moving tag such as latest changes the first layer and invalidates everything after it.

When it will not help

If your image build is under a minute, the overhead of loading and saving cache may cancel the gain. Builds with unpinned downloads, like apt-get update without versions, can produce a changed layer anyway. And if you need a clean build for releases, build without cache on the release workflow. For other ways to speed up a stack with containers, see CI for multi-service apps.

One more habit: use multi-stage builds so the final image does not carry compilers and test tools. The build stage can be cached on its own, and the final stage stays small, which also speeds up pushing and pulling the image. Keep the number of layers reasonable and combine related shell commands in a single RUN so a failed download does not leave half-finished layers cached.

If you build for several platforms, remember each platform has its own cache entry, so the first multi-platform build is slow and emulated platforms are much slower than native ones. Build only the platforms you test in CI, and leave the full set for the release workflow.

Questions people ask

Why does my Docker cache miss on every run?

An early layer changes each build, such as copying the whole source before installing dependencies, or a step that writes a timestamp. Reorder the Dockerfile.

Is type=gha shared across branches?

It follows the same scoping rules as the GitHub Actions cache, so a branch can read the default branch cache but not the reverse.
