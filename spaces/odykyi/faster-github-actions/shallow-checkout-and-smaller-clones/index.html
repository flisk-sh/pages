Faster Checkout in GitHub Actions: Shallow Clones and Sparse Checkout

actions/checkout fetches only one commit by default. Learn when to fetch more, how to use sparse checkout for big repos, and how to skip large files and submodules.

actions/checkout already does a shallow fetch of a single commit by default, which is fast. Slowdowns come from extras you added: fetch-depth: 0, submodules, large files or a huge monorepo. Fetch only what the job needs.

Check what you actually fetch

Look at the checkout step time in a run. If it takes more than a few seconds on a mid-sized repo, something is fetching extra. Search your workflows for the usual suspects.

grep -rn 'fetch-depth\|submodules\|lfs' .github/workflows/

fetch-depth: 0 only when needed

Full history is needed by tools that read git history: changelog generators, version tools based on tags, and some diff-based checks. Most jobs do not need it.

- uses: actions/checkout@v4
  with:
    fetch-depth: 1      # default, the latest commit only

If one job needs history, set fetch-depth: 0 on that job only. For a diff against the base branch, fetch just enough depth, or fetch the base ref explicitly.

Sparse checkout for large repos

In a monorepo, a job for one package does not need every other package.

- uses: actions/checkout@v4
  with:
    sparse-checkout: |
      services/api
      shared
    sparse-checkout-cone-mode: true

This limits the working tree to the listed folders. Make sure you include shared code and config that the build needs, or the job will fail in confusing ways. More on this in monorepo CI.

Submodules and large files

Submodules and Git LFS are off by default. Turn them on only for jobs that use them.

with:
  submodules: false
  lfs: false

If you need LFS only for some paths, fetch those files in a separate step instead of pulling every large file on each run.

Measure the checkout

Add a timing note with a step before and after checkout, or just read the step duration in the run page. On many projects checkout is only a few seconds, in which case you should leave it alone and look elsewhere. Only invest here if the step takes tens of seconds. In that case compare a run with the current settings against one with fetch-depth: 1, no submodules and no LFS, and keep whichever the job can live with. Tools that need more history will tell you with a clear error, so the change is easy to verify.

Keep the repo itself lean

If checkout is slow even when shallow, the repo may hold large binaries or generated files in the latest commit. Move them to artifact storage or LFS, and add build output to .gitignore. Then confirm the gain by measuring run time before and after.

A related trick for monorepos is to run the expensive jobs only for the packages that changed, and to give each of them a sparse checkout. Combine that with a path filter or a changed-files check so a change to one service never downloads or tests the others. Keep a short list of shared folders every job needs, such as build config and the lockfile, in one place so nobody forgets to add them to a new job.

Questions people ask

Why does my release tool say it cannot find tags?

The shallow checkout has no history or tags. Use fetch-depth 0 in that job, or fetch tags explicitly.

Is sparse checkout safe?

It is safe if you list every folder the job needs. Missing shared folders cause build failures that look unrelated.
