How to Measure Whether Your GitHub Actions Got Faster

Compare median and p90 run time before and after a change with gh and a short script, avoid noisy comparisons, and check queue time separately from run time.

To prove a workflow got faster, compare the median and the p90 run time of at least 20 runs before and after the change, on the same branch and trigger. One lucky run proves nothing, since run time varies with load and cache state.

Collect the data

gh run list --workflow ci.yml --branch main --limit 100 \
  --json databaseId,status,conclusion,startedAt,updatedAt,createdAt \
  > runs.json

Use only completed, successful runs for timing. Failed runs stop early and make the average look better than it is.

Compute median and p90

node -e '
const r=require("./runs.json").filter(x=>x.conclusion==="success");
const m=r.map(x=>(new Date(x.updatedAt)-new Date(x.startedAt))/60000).sort((a,b)=>a-b);
const q=p=>m[Math.min(m.length-1,Math.floor(p*m.length))];
console.log("runs",m.length,"median",q(0.5).toFixed(1),"p90",q(0.9).toFixed(1),"min");
'

The median is the typical run. The p90 is the slow run that one in ten people hit. A change that improves the median but not the p90 still leaves people waiting on bad days. More on this in CI metrics that matter.

Compare before and after fairly

  • Take the same number of runs on each side, at least 20.
  • Keep trigger and branch the same. Pull request runs differ from default branch runs.
  • Separate warm cache from cold cache runs. A cache change shows up on the warm runs.
  • Ignore the first run after the change, which often has a cold cache.
  • Watch for unrelated changes in the same window, like a test suite that grew.

Queue time is not run time

Time between createdAt and startedAt is waiting for a runner. Optimizing steps will not change it. If queue time is large, you may be limited by concurrency, in which case cancelling superseded runs or fewer matrix jobs helps more than faster steps. Track both numbers separately.

A simple report

Save the output of the script with the date and the change that was made, for example in a small file in the repo called ci-timings.md. A line per change is enough: date, change, median before, median after, p90 before, p90 after. The file is cheap to keep and answers the question of whether a past optimization is still working when the pipeline slows down again. It also helps new people understand why the workflow looks the way it does.

Keep watching

Pipelines get slower again as code grows. For a public repo you can see median and p90 per workflow in Cilytics with ?repo=owner/name. It uses default-branch runs and an hourly snapshot, so it fits trends, not a precise before and after of one pull request. Use your own script for that, then recheck monthly.

Be honest about noise. Two runs of the same commit on the same day can differ by 20 percent or more because of runner load and network speed. A real improvement is one that holds across many runs. If your sample shows a difference smaller than the usual spread, call it no change and move on to a bigger lever instead of tuning further.

Questions people ask

Why use median instead of average?

A few very slow or very fast runs distort the average. The median shows the typical run and the p90 shows the slow tail.

Does updatedAt minus startedAt equal run time?

It is a close approximation for finished runs, and fine for comparing before and after. For billable minutes use the usage data in your settings.

Measure before you tune

See which workflows are slow before you change anything.

Cilytics is a public CI health dashboard for GitHub. It shows median and p90 run time per workflow, for an org or any public repo. It reads default-branch runs only, from an hourly snapshot.
