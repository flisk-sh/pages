GitHub Actions Matrix Builds and Test Sharding Explained

Run versions and operating systems in parallel with a matrix, split one slow test suite across jobs with shards, and avoid paying setup cost many times over.

A matrix runs the same job several times with different values, in parallel. Use it to test versions and operating systems, and to split a slow suite into shards. It cuts wall-clock time, but it does not cut total compute: every job repeats the setup.

A version and OS matrix

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci && npm test

This creates six jobs. With fail-fast: false, one failure does not cancel the others, which helps you see the pattern. Use the default true if you want to save minutes on a failing build.

Sharding one slow suite

If a single suite takes 20 minutes, split it into parts that run at once. Many runners support this. Playwright has --shard, Jest has --shard, and pytest has plugins such as pytest-split.

strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/4

Four shards give roughly a quarter of the test time if shards are balanced, plus the setup time for each job.

Where matrices cost you

Each matrix job checks out code, installs dependencies and starts services. If setup takes 2 minutes and tests take 4, eight shards will not give 8 times faster. Past a certain count, you add cost for no gain. Try 2, 4, 8 shards and measure the longest shard, because the slowest one decides the finish time.

Trim the matrix

  • Test the full matrix on the default branch and a small one on pull requests.
  • Use include and exclude to drop useless combinations.
  • Use max-parallel if you share a limited number of concurrent runners.
matrix:
  os: [ubuntu-latest]
  node: [20]
  include:
    - os: windows-latest
      node: 20

Balance the shards

Splitting by file count gives uneven shards when test files differ in size. Some tools can split by recorded timing so each shard gets a similar amount of work. If your runner does not support that, shuffle files with a fixed seed, or move the slowest files into their own shard by hand. Look at the duration of each shard after a few runs. If the slowest is twice the fastest, rebalance. The finish time is set by the slowest shard, so an uneven split wastes the extra jobs.

Merge results for required checks

Matrix jobs create many check names. Add one final job that needs the whole matrix and make that the required check, as shown in path filters and the gate job. For splitting work across several dependent jobs, see splitting slow jobs.

Questions people ask

Does a matrix cost more?

Usually yes in total minutes, because each job repeats setup. It saves wall-clock time, not compute time.

Should fail-fast be on?

Leave it on to save minutes when any failure is enough to stop. Turn it off when you want to see every failing combination.
