How to Speed Up GitHub Actions Workflows: A Checklist

Measure first, then apply the changes that usually pay off: caching, cancelling stale runs, path filters, parallel jobs and shallow checkouts. In priority order.

To speed up GitHub Actions, find the slowest job, then apply the cheap fixes in order: cache dependencies, cancel superseded runs, skip work that a change cannot affect, run independent jobs in parallel and fetch less. Measure after each change so you know what helped.

Find where the time goes

Open a recent run and read the time per step, not just per job. Often one step, like installing dependencies or a Docker build, takes half the run. List recent runs with the CLI:

gh run list --workflow ci.yml --limit 20 \
  --json databaseId,startedAt,updatedAt,conclusion

The difference between updatedAt and startedAt is a good enough run time for comparison. Write down the median of ten runs before you change anything.

The checklist, cheapest first

  1. Cache dependencies. Often the biggest single win.
  2. Cancel superseded runs so old pushes stop using runners.
  3. Skip workflows when files did not change.
  4. Run independent jobs in parallel, as in matrix builds and sharding.
  5. Use a shallow checkout.
  6. Cache Docker layers when you build images.

Set timeouts

Speed also means failing fast. A hung step can burn the default job limit, which is long. Set your own.

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15

Pick a limit about twice the normal run time. It saves minutes on stuck jobs and makes hangs obvious.

Do less work per run

Do not run slow checks on every push if they only matter before a merge. Run linting and unit tests on every push, and run the long end-to-end suite on pull requests to the default branch or on a schedule. Put cheap checks first and make slow jobs depend on them with needs, so a lint error stops the pipeline in seconds, not after twenty minutes.

A realistic order of work

On a typical Node project the first pass looks like this: turn on the cache option of the setup action, add the concurrency block, add path filters for docs-only changes, then split lint from tests. Each is a few lines of YAML and each can be reverted on its own. Make one change per pull request. If you change five things at once and the run gets slower, you will not know which one hurt.

Keep a short note of the median before and after each change. After a month you will have a record that shows which habits pay off in your repo.

What not to do

  • Do not remove tests to look faster. Remove duplicated work instead.
  • Do not raise parallelism blindly. Each job repeats setup, and many small jobs can cost more total time.
  • Do not skip required checks in a way that blocks merges. See the path filter pitfall in the next guides.

When you have the numbers, measure the speedup properly, with median and p90.

Questions people ask

What is a good target time for CI?

There is no universal number. Many teams aim for pull request feedback in about ten minutes, because longer waits push people to switch tasks.

Where should I start?

Start with dependency caching and cancelling superseded runs. Both are small changes with large effect on most repos.

Measure before you tune

See which workflows are slow before you change anything.

Cilytics is a public CI health dashboard for GitHub. It shows median and p90 run time per workflow, for an org or any public repo. It reads default-branch runs only, from an hourly snapshot.
