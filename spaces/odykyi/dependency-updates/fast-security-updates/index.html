Dependency Updates Without Chaos

How to Land Dependency Security Fixes Fast

Turn on security alerts and security updates, separate them from routine version bumps, triage by reachability and set a clear time to merge for each severity.

Enable Dependabot alerts and Dependabot security updates in the repository settings, and keep them separate from your weekly version updates so a security pull request never waits in a queue. Then agree a target time to merge by severity and check whether the vulnerable code is actually reachable in your project.

Turn on the three settings

In repository settings, under advisories and code security, enable the dependency graph, Dependabot alerts and Dependabot security updates. Alerts tell you that a dependency has a known advisory. Security updates open a pull request that raises the version to the fixed one, when a fix exists. These work independently of your dependabot.yml schedule, so a security PR can arrive any day. Also review who gets notified, since an alert nobody reads is not a control.

Check locally too

Your package manager can report known issues from the registry's advisory data:

npm audit
npm audit --omit=dev
npm audit fix

npm audit fix applies compatible updates, and it changes your lockfile, so review the diff. Run an audit in CI on the default branch and on a schedule, but do not block every pull request on pre-existing advisories unrelated to the change, or the team will learn to bypass the check.

Triage: is it reachable?

Many advisories concern a function you never call, or a dev-only tool that never runs in production. Read the advisory: which function, which condition, which versions. Ask whether your code reaches it with attacker-controlled input. If yes, treat it as urgent. If no, update on the normal schedule and note why. Do not dismiss alerts without a written reason, and do not panic over every high score, because the score does not know your code.

Set time targets

Agree a simple policy, for example: critical and reachable, same day; high, within a few days; others with the regular update batch. Put it in the contributing or security document so the team shares it. Measure the actual time from alert to merge. If it is long, find the blocker: a failing test suite, no reviewer available, or a major version jump. Faster automerge rules for security patches help, see safe automerge.

Keep an eye on the whole tree

Most vulnerable packages are transitive, so you meet them through a dependency of a dependency. The package manager can explain the path: npm ls vulnerable-package shows who requires it. Often the fix is to update the direct parent. If the parent is unmaintained, that is a sign to replace it. Add the question 'how many transitive packages does this bring?' to your review of new dependencies.

When there is no fixed version

Sometimes the advisory has no patched release. Options: replace the package, pin to a fork you maintain, add a mitigation (input validation, disabling the feature, a network rule), or accept and document the risk with a review date. For transitive dependencies you can force a fixed version with the package manager's override mechanism, for example overrides in npm, and then remove it when the parent catches up. Whatever you choose, leave a record, and see AI Security for Builders for the wider habit.

Questions people ask

Are security updates the same as version updates?

No. Security updates fix a known advisory and can arrive at any time. Version updates follow your schedule and cover all newer releases.

Should CI fail on any npm audit finding?

Usually not for every pull request. Fail on new, reachable high severity findings and run a scheduled audit for the rest, so unrelated advisories do not block unrelated work.
