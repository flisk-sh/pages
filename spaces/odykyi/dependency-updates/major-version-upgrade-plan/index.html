Dependency Updates Without Chaos

How to Plan a Major Dependency Upgrade Without Breaking Everything

Read the migration notes, upgrade in a branch with small steps, let the compiler and tests lead, and ship it behind your normal release checks.

Treat a major upgrade as a small project: read the changelog and migration guide first, upgrade on a branch in the smallest step possible, fix what the compiler and tests report, and merge only when CI is green. If a jump is large, go through intermediate majors one at a time instead of straight to the latest.

Prepare before you touch the code

Read the release notes of every version between yours and the target, and the official migration guide if one exists. Make a list of breaking changes that affect you. Search your code for the removed or renamed APIs. Check that the other dependencies support the new version: peer dependency ranges on plugins and frameworks often block the upgrade. Make sure your test suite is green on the current version first, so any failure afterwards is caused by the upgrade.

npm ls some-package
npm outdated
grep -rn 'removedFunction' src/

Upgrade in small steps

If you are two majors behind, go one at a time. Each step has fewer changes, a clearer error list and a working intermediate state. On a branch, change the version, install, then run the build, the type checker, the linter and the tests, in that order. Fix compile and type errors first, because they point at every usage for you. Commit after each working step so you can bisect later (see Debugging CI Failures).

Use codemods and compatibility shims

Many large projects ship codemods that rewrite your code for a new major. Run them on a clean working tree and review the diff, since they do not understand every pattern. For a gradual move, use compatibility layers or run old and new APIs side by side for a while. Keep such shims in one place with a removal date.

Test beyond the unit tests

Unit tests may miss integration breakage: serialization formats, query behaviour, default settings, performance. Run the integration and end-to-end suites, start the app locally and click the main paths. For services, run the stack against realistic data. If your project has several services, bring them up together locally. The Flisk CLI (open source, MIT) runs services, databases and queues from one service.json each with flisk up, and is a local development tool, not a production orchestrator: flisk.sh/docs. Watch the logs for new deprecation warnings.

A simple plan template

  1. Goal and target version.
  2. Breaking changes that apply to us, with file counts.
  3. Blockers: other packages, runtime versions.
  4. Steps, one per intermediate major.
  5. Test plan beyond unit tests.
  6. Rollback: how to revert, and what data changes, if any.

A half page like this is enough, and it makes the work reviewable.

Ship it carefully and keep the bot informed

Merge the upgrade in its own pull request so it is easy to revert. Release it with the same checks as any release and watch error rates afterwards. If the bot keeps opening a pull request for a major you are not ready for, ignore that major for now with a comment and a review date rather than closing the PR repeatedly, as in reducing dependency PR noise. Never mix a major upgrade with feature work.

Questions people ask

Should I skip major versions to catch up faster?

Only if the migration guide says it is safe. Going through each major in turn gives smaller changes and easier debugging.

What if a plugin does not support the new major yet?

Wait for the plugin, replace it, or pin the main package until support exists. Record the blocker and a review date.
