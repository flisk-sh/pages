Dependency Updates Without Chaos

Too Many Dependency PRs? How to Reduce the Noise

Cut a flood of bot pull requests with grouping, slower schedules, limits, ignores and dropping dependencies you do not need.

Reduce the number of dependency pull requests by grouping related updates, moving from daily to weekly or monthly schedules, capping open PRs and ignoring packages you cannot move yet. Then remove dependencies you do not need, since every dependency is a stream of future updates.

Measure the noise first

Count the dependency PRs opened in the last month and how many were merged, closed or ignored. If most are merged within a few days, the volume is fine and you need only better automation. If many sit open or get closed, you have noise, and each one costs a review and a CI run. List them with the CLI:

gh pr list --author 'app/dependabot' --state all --limit 100
gh pr list --label dependencies --state open

Group, delay and limit

Grouping is the biggest lever: one pull request per week for minor and patch updates instead of one per package, see the Dependabot grouped updates config or Renovate basics. Move from daily to weekly. Cap open PRs. For Renovate you can also wait a few days after a release before proposing it, which cuts churn from releases that are quickly followed by a fix.

Ignore with a reason and a date

Some packages cannot move now: a major that needs a migration, a version that conflicts with a plugin. Tell the bot to skip that update type and write down why.

ignore:
  - dependency-name: 'webpack'
    update-types: ['version-update:semver-major']
    # blocked by loader X, review 2026-Q2

Closing a PR by hand without a rule usually brings it back. Review ignores quarterly, or they become a permanent freeze.

Have fewer dependencies

The cheapest update is the one you never get. Remove packages you no longer use (npx depcheck is one tool for JavaScript projects), replace tiny packages with a few lines of code or a platform feature, and avoid pulling a large library for one function. Look at your tree before adding one. If you want to see the weight of your own tree as a joke that is also true, Gardener (gardener.flisk.si) draws a dependency-tower meme from any GitHub repo.

Agree on a policy

Write down the policy in one paragraph: how often updates come, which ones merge automatically, who reviews the rest and how fast security fixes must land. A shared rule stops the silent drift where each person handles bot pull requests differently or ignores them. Review the policy every quarter and adjust it with the numbers you collected.

Automate the boring ones

Updates that nobody reviews carefully anyway, such as patch updates of dev tools, are candidates for automerge behind required checks. That leaves people with the few updates that need judgement. Pick a regular time for the human part, for example Monday morning, so dependency work is a routine and not an interruption.

Questions people ask

Is it bad to close dependency PRs?

Closing a PR does not stop the bot from reopening the update later. Use an ignore rule with a reason if you want it to stay away.

How often should dependency updates run?

Weekly is a good default for most projects. Daily creates noise, and monthly lets updates pile up into big jumps.
