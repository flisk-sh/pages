npm ci vs npm install: which one to run and when

Both commands fill node_modules. They differ in who wins when package.json and the lockfile disagree.

Use npm ci when you want the exact versions in package-lock.json: in CI, in Docker builds, and on a fresh clone. Use npm install when you add or update a dependency and want the lockfile to change. npm ci never writes the lockfile and fails if it does not match package.json.

What each command does

npm installnpm ci
Source of truthpackage.json, then the lockfileThe lockfile only
Writes the lockfileYes, when versions changeNever
Existing node_modulesReused and updatedDeleted first, then rebuilt
Lockfile missingCreates oneFails
Lockfile disagrees with package.jsonFixes the lockfileFails with an error

The failure of npm ci is the point. If a teammate changes package.json and forgets to commit the lockfile, CI stops instead of installing something nobody tested.

Day-to-day use

# add a dependency and update package-lock.json
npm install zod

# commit both files
git add package.json package-lock.json

# fresh clone, CI, Dockerfile
npm ci

# production image: skip devDependencies
npm ci --omit=dev

Always commit the lockfile for an application. For a library you publish, the lockfile is not shipped to users, but committing it still gives your CI a stable install.

A common surprise is that npm install on a clean machine may change the lockfile slightly, for example by rewriting a field after a different npm version touched it. That produces noisy diffs. Pin the Node and npm versions (see a Node version per project) and use npm ci when you are not changing dependencies.

In a Dockerfile

Copy the manifest files first, install, then copy the code. The install layer is cached until a dependency changes:

FROM node:22-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["node", "src/server.js"]

Add a .dockerignore with node_modules so a host copy never overwrites the one built inside the image. Native modules built on macOS do not run in a Linux container, which is one more reason to install inside the image.

Equivalents in other tools

  • pnpm: pnpm install --frozen-lockfile (it is the default in CI environments)
  • Yarn (current line): yarn install --immutable; Yarn 1: yarn install --frozen-lockfile
  • Bun: bun install --frozen-lockfile

If you are still choosing a tool, see npm, pnpm, Yarn or Bun.

Installing and starting a local stack

Installing packages and starting services are separate steps. Flisk's flisk up runs your service commands, it does not install their dependencies. A reasonable repeatable setup is a script or README line that runs the lockfile install in each service folder, then flisk up. If a service starts and then crashes with "Cannot find module", the install step was skipped or ran in the wrong directory.

Checking what you actually installed

After an install, three commands tell you what is on disk. npm ls prints the dependency tree, and npm ls some-package shows every copy of one package and which parent pulled it in. npm outdated lists packages that have newer versions than the ones installed. npm explain some-package says why a package is there at all. If two teammates see different behaviour, have both run npm ls for the suspect package and compare the output. A difference means one of them did not use npm ci, or the lockfile was not committed.

When you update on purpose, do it in a small, separate commit: run npm update or npm install package@latest, run your tests, and commit the lockfile with a message that names the change. A reviewer can then see exactly which versions moved. Mixing an upgrade into a feature commit hides it.

Pitfalls

  • "npm ci can only install with an existing package-lock.json". Run npm install once and commit the lockfile.
  • "package.json and package-lock.json are not in sync". Run npm install locally, commit the lockfile, and push again.
  • Lifecycle scripts. Both commands run postinstall and similar scripts of your dependencies. Use --ignore-scripts when you install code you do not trust, and then run the needed build step by hand.
  • Slow npm ci in CI. It deletes node_modules every time, so cache the npm download cache (~/.npm), not node_modules.

Questions people ask

Is npm ci faster than npm install?

Often, because it skips dependency resolution and uses the lockfile directly, but it also deletes node_modules first. Measure on your project and cache ~/.npm in CI.

Should I commit package-lock.json?

Yes for applications. It makes installs repeatable for everyone and for CI.

Does flisk up install my npm packages?

No. It starts the commands you declared. Run your install step first.
