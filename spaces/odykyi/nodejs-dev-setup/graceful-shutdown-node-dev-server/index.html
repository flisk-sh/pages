How to shut down a Node.js dev server cleanly on Ctrl+C

A dev server that ignores signals leaves ports busy and connections open. Twenty lines of code fix it.

Listen for SIGINT (Ctrl+C) and SIGTERM (what process managers send), stop accepting new connections with server.close(), end your database pool, and then exit. Add a timer that forces an exit if something hangs, so a stuck shutdown never blocks the next start.

Why it matters in development

Node's default for SIGINT and SIGTERM is to exit at once. That is fine for a plain script. It is wrong for a server that holds open requests, a queue consumer that is halfway through a job, or a database pool with connections the server has to time out. In development the visible symptom is the next start failing with EADDRINUSE because the old process is still shutting down, or a worker that processes the same job twice after a restart. A clean shutdown also makes node --watch restarts quicker, since the old process exits promptly.

A handler you can copy

import http from "node:http";

const server = http.createServer(app);
server.listen(process.env.PORT || 3000);

let closing = false;

async function shutdown(signal) {
  if (closing) return;       // ignore a second signal
  closing = true;
  console.log(`${signal} received, shutting down`);

  // Hard stop if something hangs.
  const timer = setTimeout(() => process.exit(1), 4000);
  timer.unref();

  server.close(async (err) => {
    try {
      await pool.end();      // database pool, queue client, etc.
    } finally {
      process.exit(err ? 1 : 0);
    }
  });
  server.closeIdleConnections();  // keep-alive sockets block close()
}

process.on("SIGINT", () => shutdown("SIGINT"));
process.on("SIGTERM", () => shutdown("SIGTERM"));

Three details matter. server.close() stops new connections but waits for existing ones, and idle keep-alive connections count, so call closeIdleConnections() (available since Node 18.2) right after it. In a dev server you can also call server.closeAllConnections() to cut slow requests. The timer must be shorter than the time your supervisor waits before it kills you. And unref() stops the timer itself from keeping the process alive.

Express, Fastify and Koa all sit on a Node http.Server, so the same pattern works. Fastify also has await app.close(), which does the closing for you.

Make sure the signal reaches your code

The signal goes to the process the supervisor started. If that process is a wrapper, your server may never see it. With npm run dev the chain is npm, then a shell, then Node. Each extra layer is another place where a signal can be swallowed. In a dev script, run node directly (node --watch server.js) when you can, and in a shell command use exec node server.js so Node replaces the shell.

How Flisk stops local services

When you press Ctrl+C in the terminal running flisk up, or run flisk down from another one, Flisk sends SIGTERM to each service's process group, which includes the shell and everything it started. It waits up to 5 seconds for the process to exit, and then sends SIGKILL. Services that depend on each other are stopped dependents first, and they get their grace period at the same time. So a handler that finishes in a second or two is enough, and one that hangs costs a five-second wait and an unclean exit.

flisk status

flisk status afterwards shows each service as not running, and the ports are free again. If a port is still held, flisk up refuses to start and names the process that holds it. Flisk's SIGTERM-then-SIGKILL behaviour applies to services with a command. Container services use Docker's own stop behaviour, which has its own timeout.

Pitfalls

  • A handler that never calls process.exit(). If something keeps the event loop busy (a timer, an open socket), the process stays alive until the supervisor kills it. Exit explicitly or unref your timers.
  • Doing real work in the handler. Keep it short. Stop taking work, finish what is in flight, release resources.
  • Workers. For a queue consumer, stop fetching new jobs first, then wait for the current one. Make jobs safe to run twice anyway, because a hard kill will happen eventually.
  • Windows. Signals behave differently there: SIGTERM is not delivered the same way, and Ctrl+C is the reliable one. Test your shutdown path on a clean terminal.

Questions people ask

How do I handle Ctrl+C in a Node.js server?

Listen for SIGINT and SIGTERM with process.on, call server.close(), end your database pool, then call process.exit. Add a short timer that forces an exit if shutdown hangs.

Why does server.close() never finish?

It waits for open connections, and idle keep-alive sockets count. Call server.closeIdleConnections() or closeAllConnections() after it.

How long does Flisk wait before killing a local service?

It sends SIGTERM to the process group, waits 5 seconds, then sends SIGKILL.
