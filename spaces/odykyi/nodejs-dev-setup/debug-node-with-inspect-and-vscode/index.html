How to debug a Node.js server with --inspect and VS Code

console.log gets you far, but a breakpoint on a running server is faster. Here is the minimum setup that works.

Start the server with node --inspect server.js, then attach a debugger to port 9229: in VS Code with an attach launch configuration, or in Chrome by opening chrome://inspect. The server keeps running normally, and your breakpoints stop it when they are hit.

The flags

  • --inspect opens the inspector on 127.0.0.1:9229 and runs your code at once.
  • --inspect-brk opens it and pauses on the first line. Use it when the bug happens during startup, before you could attach.
  • --inspect=127.0.0.1:9230 picks another port. You need this as soon as two Node processes run at once.
node --inspect --watch src/server.js
Keep the inspector on 127.0.0.1. Anyone who can reach the port can run code in your process. Do not use 0.0.0.0 unless you know why, and never on a shared network.

Attach from VS Code

Add a configuration to .vscode/launch.json:

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Attach to API",
      "type": "node",
      "request": "attach",
      "port": 9229,
      "restart": true,
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}

Run it from the Run and Debug panel and set a breakpoint in your source file. "restart": true matters with watch mode: each restart is a new process, and this setting makes VS Code reattach to it. Without it the debugger disconnects at every save and you have to click attach again.

If you do not want to edit any file, open the Command Palette and choose "Debug: JavaScript Debug Terminal". Anything you start in that terminal, including npm run dev, is attached automatically.

Attach from Chrome DevTools

Open chrome://inspect in Chrome, and your Node process appears under Remote Target. Click "inspect" to get a DevTools window with sources, a console, the memory tab and a profiler. This is also how you take a heap snapshot, which helps with out of memory errors.

Debugging a service started by Flisk

For a Flisk service with a command, add the flag to the command. Flisk runs the command as written, so nothing else changes:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch --inspect=127.0.0.1:9229 src/server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

Run flisk up and attach VS Code to 9229. If a second Node service also needs a debugger, give it --inspect=127.0.0.1:9230. Flisk checks that the port values of services do not collide, but the inspector port is not a service port, so it does not know about it. Two services on 9229 means the second one fails to bind, which shows up in that service's log (flisk logs --service worker).

Containers need a different recipe: you must publish the inspector port, and the inspector inside a container has to listen on all interfaces, which is why that setup is a security trade-off. For the Docker route, prefer running the process you are debugging on the host. A mixed setup, where Postgres is a container and your code runs as a local process, is described in running services without Docker.

Pitfalls

  • Breakpoints show as gray. The source map does not match. For TypeScript, run the code with a runner that emits source maps (tsx does), or enable --enable-source-maps.
  • "Address already in use" on 9229. Another Node process holds the inspector. Use a different port with --inspect=127.0.0.1:PORT.
  • The debugger pauses the whole server. While stopped at a breakpoint, requests wait. A health check from a supervisor may time out and mark the service unhealthy. That is expected while you are paused.
  • Do not ship the flag. Keep --inspect in the dev script, not in start.

Next step

If you start several Node processes together, give each one its own inspector port and read how to run several npm scripts at once for ways to keep their logs readable.

Questions people ask

What port does node --inspect use?

9229 on 127.0.0.1 by default. Change it with --inspect=127.0.0.1:PORT.

How do I keep VS Code attached when node --watch restarts?

Set restart to true in the attach configuration of launch.json, so VS Code reattaches to each new process.

Can I debug a Flisk service?

Yes for a service with a command: add --inspect to the command and attach to that port. Use different inspector ports for different services.
