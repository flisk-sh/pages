Fix "JavaScript heap out of memory" in Node.js

The error means one Node process hit its heap limit. Raising the limit is one fix. Knowing whether you have a leak is the other.

Run the process with a larger limit, for example node --max-old-space-size=4096 build.js (the value is in megabytes), or set NODE_OPTIONS=--max-old-space-size=4096 so tools that start Node for you pick it up. If the process still runs out after you double the limit, you have a leak or an unbounded data load, and a bigger heap only delays the crash.

What the error means

The message looks like FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory. V8, the engine inside Node, caps the old-generation heap, which is where long-lived objects live. The default cap depends on the Node version and on how much memory the machine or container has, so the same code can fail on a small CI runner and work on your laptop. It is a per-process limit and it is separate from the machine's RAM: Node can fail with 8 GB free.

It shows up most often in builds and tools (a TypeScript compile, a bundler, a linter on a large repo, a test runner) and in dev servers that have run for hours. Those are two different problems.

Raise the limit

# one command
node --max-old-space-size=4096 node_modules/.bin/vite build

# every Node process started from this shell
export NODE_OPTIONS="--max-old-space-size=4096"

# one npm script (cross-platform with cross-env)
"build": "cross-env NODE_OPTIONS=--max-old-space-size=4096 tsc -p ."

Pick a value below the memory you really have, and remember that every Node process in the shell gets the setting, including editors' helper processes. 4096 (4 GB) is a common first step on a laptop. Do not set it to the total RAM of the machine.

Decide: big job or leak

Watch the memory of the process over time with process.memoryUsage().heapUsed, or the Activity Monitor or top. A build that climbs to a peak and then exits is a big job: raise the limit or split the work (for example, run tsc per package). A server that grows with each request and never drops back is a leak.

To find the leak, ask Node to write a snapshot before it dies:

node --heapsnapshot-near-heap-limit=1 server.js

Open the resulting .heapsnapshot file in Chrome DevTools, in the Memory tab, and sort by retained size. Or attach with --inspect and take two snapshots a few minutes apart, then use the "comparison" view to see which objects grew. See debugging with --inspect for the attach steps. Typical culprits are a global array or Map used as a cache with no limit, event listeners added on every request, and a request body or query result loaded entirely into memory.

Set it for a Flisk service

A service with a command receives the variables from its env map, so you can set the option there and keep it out of the command line:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch server.js",
  "port": 4000,
  "env": { "NODE_OPTIONS": "--max-old-space-size=2048" }
}

If the service then restarts by itself, check flisk logs --service api --tail 100 for the fatal error text. Flisk restarts an exited process after 1, 2, 4 and 8 seconds and stops after five quick exits, so a service that runs out of memory at startup ends up stopped, and the log tells you why. Flisk does not measure or limit the memory of a local process.

Container kills look different

If the process runs in Docker, there are two limits: V8's heap and the container's memory limit. When the container limit is hit, the kernel kills the process without any JavaScript error, and the exit code is 137. If you see 137 and no "heap out of memory" text, raise the container memory, or lower the heap setting so Node fails with a message before the container does. On a Mac, the Docker VM has its own memory size as well. See many services on one laptop without running out of RAM.

Pitfalls

  • Setting it too high. The machine starts swapping, and everything slows down before Node fails.
  • Setting NODE_OPTIONS in a profile file. It then affects every Node tool on the machine. Set it per command or per service.
  • Treating it as a fix for a leak. The process will fail later, usually in the middle of something important.
  • Buffers and streams. Large files read with readFile use memory outside the old-generation heap as well. Stream them.

Questions people ask

How much should I set --max-old-space-size to?

A value in megabytes below the memory you really have free. 4096 is a common first step. Do not set it to the total RAM, or the machine will swap.

What does exit code 137 mean for a Node container?

The kernel killed the process because the container hit its memory limit. It is not a V8 heap error, so raise the container memory or lower the heap limit.

Where do I set NODE_OPTIONS for a Flisk service?

In the env map of the service.json, for example NODE_OPTIONS set to --max-old-space-size=2048.
