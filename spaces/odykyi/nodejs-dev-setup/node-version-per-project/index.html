How to use a different Node.js version per project

Two projects on one laptop often need two Node versions. Pin the version in the repo so nobody has to remember it.

Write the version you want in a file at the root of the project (.nvmrc for nvm and fnm, or a volta entry in package.json for Volta) and let your version manager read it when you enter the folder. Add an engines field so a wrong version produces a clear message instead of a strange crash later.

Why one global Node version breaks

A project written for Node 20 can fail on Node 24 because a native module has no build for the newer version. A newer project may use node --watch, --env-file or built-in TypeScript support that older versions lack. If you install Node once with a system installer, you have to reinstall it each time you switch project. A version manager keeps several versions side by side and picks one per shell.

Pin the version in the repo

The version file is the contract. Commit it, so a new teammate gets the same Node as CI.

# .nvmrc
22

A major number such as 22 means the newest 22.x you have installed. Use a full version such as 22.11.0 when you need an exact patch. lts/* also works with nvm, but it moves when a new LTS line starts, so it is a poor pin for a team.

With nvm you run nvm use in the folder (it reads .nvmrc) and nvm install when the version is missing. fnm reads the same file and can switch for you when you change directory if you start it with fnm env --use-on-cd in your shell profile. Volta works differently: you run volta pin node@22 once and it writes the version into package.json, and Volta then picks it automatically whenever you run node or npm inside that project.

{
  "name": "orders-api",
  "engines": { "node": ">=22 <23" },
  "volta": { "node": "22.11.0" }
}

Make a wrong version fail loudly

The engines field is advisory by default. npm prints a warning for a mismatch and carries on. To make it an error, put this in a project .npmrc:

engine-strict=true

pnpm reads the same setting. Do this for applications. For a published library, keep it off, because the setting would also block people who install your package on a different Node.

A cheap extra guard is a check at the top of your entry file or in a preinstall script that compares process.versions.node with what you expect. Most teams do not need it once engine-strict is on.

Check which Node a service really uses

The version manager changes PATH for one terminal. Anything you start from that terminal inherits it, and anything started from a different terminal, an editor task or a launcher does not. When a service behaves differently in two places, run this in both:

which node
node -v
node -p "process.execPath"

If you start local services with Flisk, the command in each service.json runs through a shell that inherits your environment, so it uses whichever Node is active in the terminal where you ran flisk up. Switch version first, then start. Flisk also checks that the program a command starts is installed. If it is not on PATH, flisk up stops before starting anything and prints a message like this one:

service "web" runs npm, which is not installed (not found on PATH). Install it, or change "command" in its service.json.

That message appears when a shell has no Node at all, for instance a new terminal where the version manager did not load. It is a quick signal that the problem is your shell setup and not the project. Flisk does not manage Node versions itself, and it does not compare the version with engines.

Pitfalls

  • Different versions in different services. A frontend on Node 22 and an API pinned to Node 20 cannot both come from one shell. Run them from one version if you can. If you cannot, give the older service a command that selects its own Node, for example fnm exec --using=20 node server.js.
  • Global packages. Each Node version has its own global packages. Prefer project scripts and npx to global installs.
  • Docker and CI use another version. Use the same major in the FROM node:22 line, in your CI setup step and in .nvmrc. Some CI setups can read .nvmrc directly, which removes one copy.
  • Native modules. After a version switch, delete node_modules and reinstall. Compiled addons are built for one Node ABI.

Questions people ask

Does .nvmrc work with fnm?

Yes. fnm reads .nvmrc and .node-version files. Start it with fnm env --use-on-cd in your shell profile if you want it to switch when you change directory.

Does package.json engines stop the wrong Node version?

Not by default. npm only warns. Set engine-strict=true in a project .npmrc to make a mismatch an error.

Does Flisk pick the Node version for my services?

No. A service command runs with the Node that is active in the shell where you started flisk up.
