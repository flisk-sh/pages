How to use Postgres LISTEN/NOTIFY as a lightweight event bus

Postgres can push a message to waiting clients when a transaction commits. It is a good wake-up call and a poor message queue.

Postgres LISTEN and NOTIFY let one connection subscribe to a named channel and be woken when another session sends a notification on it. Notifications are delivered only when the sending transaction commits, they are not stored, and the payload is limited to under 8000 bytes. So use them as a signal that says "look at the table now", and keep the data in the table.

The basics

In two psql sessions:

-- session A
LISTEN order_events;

-- session B
NOTIFY order_events, 'order 123 created';
-- or from code or a trigger:
SELECT pg_notify('order_events', 'order 123 created');

Session A receives the message the next time it checks, and psql prints it after its next command. The channel name is an identifier, so keep it lowercase and simple. Notifications sent inside a transaction that rolls back are never delivered, which is why this works well with data changes: the signal exists only if the data does.

What it does not do

  • No storage. If nobody is listening when the notification is sent, it is gone. A service that restarts misses everything sent while it was down.
  • No acknowledgement and no retry. Postgres does not know whether your handler worked.
  • No consumer groups. Every listener gets every message, so two copies of a worker both react.
  • Small payloads. Under 8000 bytes in the default configuration. Send an id, not the record.
  • Identical notifications can merge. Inside one transaction, repeats of the same channel and payload are delivered once.

These limits are why LISTEN/NOTIFY should not replace a queue for work that must happen. They are also why it pairs well with a table.

Table for truth, notify for speed

The robust design: write the work to a table (an outbox, see the outbox article), and send a notification from a trigger so the relay wakes immediately instead of waiting for its next poll:

CREATE FUNCTION notify_outbox() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('outbox', NEW.id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER outbox_notify
AFTER INSERT ON outbox
FOR EACH ROW EXECUTE FUNCTION notify_outbox();

The listener does three things: it listens on a dedicated connection, drains the table when a notification arrives, and also drains on a timer and at startup, so a missed notification costs only a delay:

import pg from "pg";

const listener = new pg.Client({ connectionString: process.env.DATABASE_URL });
await listener.connect();
await listener.query("LISTEN outbox");

let running = false;
async function drain() {
  if (running) return;
  running = true;
  try {
    while ((await drainOnce()) > 0) {}   // drainOnce: your batch query
  } finally {
    running = false;
  }
}

listener.on("notification", () => drain());
setInterval(drain, 5000);   // safety net for missed notifications
await drain();              // catch up on start

The guard flag collapses a burst of notifications into one drain loop. The timer is not optional: it is what makes the design correct, with the notification only making it fast.

The Flisk way

This needs nothing beyond Postgres, which Flisk runs as a database resource:

flisk resource shop-db --type database --stack shop --yes
flisk resource outbox-relay --type worker --stack shop --yes

With "dependsOn": ["shop-db"] in the relay, it receives DATABASE_URL according to the Flisk docs. Create the trigger in a migration, see database migrations in local dev. I did not test notifications through the Flisk-managed Postgres, but the feature is part of Postgres itself, so the quickest check is to insert a row and watch the relay's output with flisk logs --service outbox-relay --since 1m. Use a direct database connection for the listener; see the pitfall below about poolers.

Pitfalls

  • Connection poolers. A listener needs a long-lived session. A pooler in transaction mode, such as PgBouncer, can hand your connection to someone else, and the subscription is lost. Connect the listener directly.
  • Reconnects. After a dropped connection, LISTEN is gone. Re-run it on reconnect and drain the table, because you missed notifications while disconnected.
  • Do not use a pool client. A pooled connection returned to the pool keeps listening or loses its state. Use one dedicated pg.Client.
  • Heavy fan-out. Notifying on every row change of a busy table adds load at commit time. Notify per batch or per entity if you see contention.

For two or three services on a laptop, a trigger and a timer are enough. When you need several competing consumers with retries, move to a real broker, as in NATS for local development.

Questions people ask

Does Postgres NOTIFY guarantee delivery?

No. A notification reaches only sessions that are listening when the transaction commits. Anyone disconnected misses it. Keep the data in a table and use NOTIFY only to wake the reader.

What is the maximum NOTIFY payload size?

Under 8000 bytes in a default Postgres build. Send an id and have the listener read the row.

Can I use LISTEN/NOTIFY through PgBouncer?

Not in transaction pooling mode, because the session that issued LISTEN can be reassigned. Use a direct connection or session pooling for the listener.
