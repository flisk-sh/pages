How to make an event consumer idempotent with a dedupe table

If your consumer sends an email or adds to a balance twice when an event arrives twice, it is not idempotent yet. Here is the smallest fix that works.

An idempotent consumer produces the same result whether it handles an event once or five times. The simplest way to get there is a processed_events table with the event id as primary key: in one transaction, insert the id and do the work, and if the insert finds the id already there, skip the work.

Why duplicates are normal

Most brokers promise at-least-once delivery, not exactly-once. A message is redelivered when a consumer crashes before it acknowledges, when an acknowledgement is lost, when a visibility timeout expires on a slow job, or when a producer retries after a timeout. A transactional outbox adds one more source, see the outbox article. You cannot remove duplicates at the broker. You handle them in the consumer.

Some operations are naturally idempotent: "set the status to shipped" gives the same row however often you run it. Others are not: "add 10 to the balance", "send the welcome email", "insert a row". Those need a guard.

The dedupe table

CREATE TABLE processed_events (
  consumer     text        NOT NULL,
  event_id     uuid        NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, event_id)
);

The consumer column lets several consumers in one database track the same event separately. The event id must come from the producer, never from the consumer: generate it once when the event is created, as the outbox does.

The handler claims the id and does the work in one transaction:

async function handle(event) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const claim = await client.query(
      `INSERT INTO processed_events (consumer, event_id)
       VALUES ($1, $2) ON CONFLICT DO NOTHING`,
      ["billing", event.id]
    );
    if (claim.rowCount === 0) {
      await client.query("ROLLBACK");
      return; // seen before, acknowledge and move on
    }
    await client.query(
      "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
      [event.data.amount, event.data.accountId]
    );
    await client.query("COMMIT");
  } catch (err) {
    await client.query("ROLLBACK");
    throw err; // do not acknowledge, the broker will redeliver
  } finally {
    client.release();
  }
}

The order matters. Because the claim and the balance update commit together, a crash in the middle rolls back both, and the redelivered event is processed from scratch. If you inserted the id first in its own transaction and crashed before the update, the event would be marked done and the work lost.

Acknowledge the message only after handle returns. Acknowledging a duplicate is correct: you have handled it, by doing nothing.

When the side effect is not in your database

The trick only works when the effect and the claim share a transaction. Sending an email or calling a payment API cannot join it. Two options:

  • Pass the event id as an idempotency key to the other system, if it supports one. Many payment APIs do.
  • Write the intent to your own table in the transaction (an emails_to_send row, keyed by event id) and let a separate worker perform it. The worker's own retries then need the same care.

There is always a small window when an external call succeeds and your commit fails. Design the external call so that repeating it is harmless.

The Flisk way

The setup is a database and a queue next to your consumer service:

flisk resource shop-db --type database --stack shop --yes
flisk resource bus --type queue --stack shop --yes
flisk resource billing --type worker --stack shop --yes

Put "dependsOn": ["shop-db", "bus"] in the worker's service.json, and it receives DATABASE_URL and NATS_URL, as described in the Flisk docs. Create processed_events in a migration. To prove the guard works, replay one event on purpose from a script with flisk run billing -- bun run scripts/send-duplicate.ts, where the script publishes the same event id twice, and then check the balance changed once. A test that sends each event twice is the best regression test you can write for this.

Pitfalls

  • Same id, different content. If a producer reuses an id for a changed event, the consumer drops the update. Treat the id as the identity of one fact.
  • Unbounded growth. The table gets a row per event. Delete rows older than your longest redelivery window, a few days is usual, with a scheduled job.
  • Wrong key. A random id generated in the consumer on each delivery never matches, and nothing is deduplicated.
  • Check-then-insert. A SELECT to see if the id exists, then an INSERT, races when two copies run at once. Let the primary key decide.

Deduplication solves repeats, not disorder. If events for the same entity can arrive out of sequence, read keeping events in order per entity next.

Questions people ask

What is the difference between idempotent and exactly-once?

Exactly-once delivery cannot be achieved in general across a network. An idempotent consumer gets exactly-once effects on top of at-least-once delivery, by making repeated handling harmless.

How long should I keep rows in the processed events table?

At least as long as the broker can redeliver the same message, plus a margin. A few days is common. After that a duplicate would be treated as new, so choose a window longer than any retry or replay you expect.

Can I deduplicate in the broker instead?

Partly. Some brokers drop duplicate publishes within a short window, but that does not cover redelivery to a consumer after a crash. Keep the consumer-side guard.
