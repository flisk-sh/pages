How to test eventual consistency without sleep calls

A test that sleeps for two seconds is slow when the system is fast and flaky when it is slow. Poll for the outcome instead.

In an event-driven system, the effect of an action shows up later, so a test must wait for it. Do not call sleep. Write a small eventually helper that runs a check repeatedly until it passes or a timeout expires, and have the test fail with the last observed value so you can see what was missing.

Why sleep is the wrong tool

A fixed sleep has to be longer than the slowest case you ever see, so every test pays the worst-case price, and it still fails on a loaded CI machine. Worse, it hides real problems: a test that passes after a three second sleep may be telling you that a consumer is slow. Polling returns as soon as the condition holds, so the common case is fast, and the timeout only matters when something is broken.

An eventually helper

export async function eventually(check, { timeoutMs = 10000, everyMs = 100 } = {}) {
  const deadline = Date.now() + timeoutMs;
  let last;
  while (Date.now() < deadline) {
    try {
      last = await check();
      if (last) return last;
    } catch (err) {
      last = err;
    }
    await new Promise((r) => setTimeout(r, everyMs));
  }
  throw new Error(`timed out after ${timeoutMs} ms, last result: ${JSON.stringify(last)}`);
}

Use it with a check that returns something truthy when the condition is met:

test("placing an order creates an invoice", async () => {
  const orderId = crypto.randomUUID();
  await fetch(`${API}/orders`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ id: orderId, total: 4200 }),
  });

  const invoice = await eventually(async () => {
    const res = await fetch(`${BILLING}/invoices?orderId=${orderId}`);
    const rows = await res.json();
    return rows.length === 1 ? rows[0] : null;
  });

  expect(invoice.total).toBe(4200);
});

The pieces that make this reliable:

  • A unique id per test. The test creates its own order id and looks only for that one. Parallel tests and leftovers from an earlier run cannot confuse it.
  • Assert the exact count. Checking rows.length === 1, not "at least one", is how a duplicate-processing bug shows up.
  • A clear failure. The error includes the last value. "last result: null" and "last result: two rows" point at different bugs.

Asserting that something did not happen

"No email is sent for a cancelled order" cannot be polled for, because absence has no moment where it becomes true. Two honest options. First, test the cause: assert that the consumer logged or recorded that it skipped the event. Second, publish a marker event after the one you care about, wait until the marker's effect is visible, and then assert the absence. Events on one stream are handled in order by a single consumer, so once the marker is processed, the earlier event has been too. State this assumption in a comment, because it fails with several consumers.

Check the stack is ready first

Many "eventual" failures are really a consumer that has not started yet. Make the test run wait for readiness before the first action. With Flisk, flisk status --strict exits with code 1 when any service is not ready or nothing is running, so it works as a gate in a shell script:

flisk up shop
until flisk status --strict; do sleep 2; done
bun test e2e/

Add a limit to that loop in CI so a broken stack fails instead of hanging. When a test times out, the quickest next look is flisk logs --service billing --since 2m, which prints the last two minutes of that service's output. For the wider setup of tests against a running stack, see integration tests against the real stack and Playwright against a local stack.

Tune the timeout, not the interval

Choose the timeout from what the system promises. If the pipeline normally settles in under a second, ten seconds leaves room for a slow machine, and failing at ten seconds is still quick. A very short interval, under 50 ms, mostly adds load. For tests that need to be repeatable, also make the system deterministic where you can: use a fixed clock, and avoid retry delays in the test environment by setting them to a few milliseconds through configuration.

Pitfalls

  • Shared data. Tests that read "the latest invoice" instead of their own break when run in parallel.
  • Swallowing errors. If check throws a typo error, the helper keeps retrying for ten seconds. The last error in the message tells you which it was, so do read it.
  • Polling an internal table. Prefer asserting through a public API or read model, which is what users depend on. Querying the database directly couples the test to the schema.
  • Unit tests that poll. A pure function does not need waiting. Keep polling for end-to-end tests only.

When a test times out and the log is silent, the question becomes where the event went. Debugging an event that never arrived goes through it in order.

Questions people ask

How long should the timeout be in an eventual consistency test?

Long enough for a slow machine, short enough that a real failure is reported quickly. For a local pipeline that normally settles in well under a second, ten seconds is a common choice.

Can I use a test library's built-in wait function?

Yes. Libraries such as Playwright and Testing Library have retrying assertions, and Awaitility does this on the JVM. The helper in this article is the same idea in a few lines for plain API tests.

How do I test that an event was not processed?

Wait for a later marker event to be processed first, then assert the absence. Or assert on a record the consumer writes when it intentionally skips an event.
