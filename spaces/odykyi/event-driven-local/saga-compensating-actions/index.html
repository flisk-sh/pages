How to implement a saga with compensating actions

You cannot wrap three services in one database transaction. A saga is the next best thing: do each step, and know how to undo it.

A saga is a sequence of local transactions across services, where each step has a compensating action that undoes it. If step three fails, you run the compensations for steps two and one in reverse order. The result is not atomic, because other services can see the in-between state, but it ends in a consistent place.

A concrete example

Placing an order touches three services: inventory reserves stock, payment authorizes a charge, shipping books a courier. The steps and their undo actions:

StepServiceCompensation
Reserve stockinventoryRelease the reservation
Authorize paymentpaymentVoid the authorization
Book couriershippingCancel the booking

If the courier booking fails, the saga voids the payment and releases the stock. Note that a compensation is a new business action, not a database rollback. "Cancel the booking" can itself fail, so compensations must be retryable and idempotent, see the idempotent consumer article.

Choreography or orchestration

  • Choreography: no coordinator. Inventory emits stock.reserved, payment reacts and emits payment.authorized, and so on. Failures emit events that earlier services react to. It has few moving parts, but the process exists only in your head: to answer "what step is order 42 at?" you read the logs of three services.
  • Orchestration: one service owns the process. It sends commands, waits for replies and decides what comes next. The flow is written in one place and its state is queryable. The cost is one more component, and the temptation to put business rules in it.

For two or three steps, choreography is fine. Once there are branches, timeouts or more than three participants, orchestration is easier to debug. Both work locally.

A minimal orchestrator state table

The orchestrator persists where each saga is, so a restart does not lose it:

CREATE TABLE sagas (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id   uuid NOT NULL,
  state      text NOT NULL,          -- reserving, charging, booking, done, compensating, failed
  step_log   jsonb NOT NULL DEFAULT '[]',
  updated_at timestamptz NOT NULL DEFAULT now()
);

On each reply event, the orchestrator loads the row, decides the next move from a small transition table, and updates the row and sends the next command in one transaction (use an outbox for the send). A sketch of the decision logic:

const next = {
  "reserving:stock.reserved":    { state: "charging", send: "payment.authorize" },
  "charging:payment.authorized": { state: "booking",  send: "shipping.book" },
  "booking:shipping.booked":     { state: "done" },
  "booking:shipping.failed":     { state: "compensating", send: "payment.void" },
  "charging:payment.declined":   { state: "compensating", send: "stock.release" },
};

function step(saga, event) {
  const t = next[`${saga.state}:${event.type}`];
  if (!t) return null; // unexpected, log it and keep the state
  return t;
}

A real version would have a longer table and would track which compensations are still pending. The shape stays the same: current state plus incoming event gives the next state and the next command. A plain lookup table is easy to unit test without any broker.

Testing failures on purpose

The compensation path is where the bugs hide, and it never runs on a happy-path demo. Give each participant a way to fail on demand, for example an environment variable such as FAIL_AT=shipping, and write a test per failing step that asserts the final state: stock released, payment voided, order marked failed. Also test a duplicate reply event and a reply that arrives after the saga timed out.

The Flisk way

Each participant is a small service in one stack, with a shared queue for events and a database for each service that owns data:

flisk resource bus --type queue --stack shop --yes
flisk resource orchestrator --stack shop --yes
flisk resource inventory --stack shop --yes
flisk resource payment --stack shop --yes
flisk resource shipping --stack shop --yes

List "bus" in each service's dependsOn so it receives NATS_URL. To run a failure scenario, put FAIL_AT under the service's params (non-secret values), run flisk config regenerate and restart the service with flisk restart shipping. Follow one order through the stack with flisk logs --service orchestrator shipping --since 5m, which prints recent lines from only those services. Putting a shared saga id in every event and every log line makes this readable.

Pitfalls

  • Not every step can be undone. An email already sent cannot be unsent. Put irreversible steps last, and use a "pending" state for steps that need a human.
  • Timeouts. A participant that never answers leaves the saga stuck. Store a deadline in the state row and let the orchestrator fail the saga when it passes.
  • Lost isolation. Between steps, other requests see reserved stock or an authorized charge. Model those states explicitly instead of hiding them.
  • Using a saga for one database. If all the data is in one Postgres, use a normal transaction.

To see the saga's state across time instead of only the latest row, look at storing the events themselves in a minimal event store.

Questions people ask

Is a saga the same as a distributed transaction?

No. A distributed transaction such as two-phase commit locks resources across systems until all agree. A saga commits each step locally and undoes earlier steps with compensating actions if a later one fails, so it is eventually consistent.

What if a compensating action fails?

Retry it until it succeeds, which requires it to be idempotent. If it cannot succeed, move the saga to a failed state that raises an alert, because a person has to resolve it.

Should I use a workflow engine instead of writing an orchestrator?

For long-running or complex processes, engines such as Temporal handle persistence, timers and retries for you. A small state table is enough for a few steps and is easier to run locally.
