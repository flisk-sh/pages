How to rebuild a read model by replaying events

A read model is disposable. If you can rebuild it from the events, you can change its shape whenever the questions change.

To rebuild a read model, create the new table next to the old one, read every event from the start in order, apply each to the new table while saving a checkpoint of the last position handled, and when it has caught up with the live stream, point queries at the new table and drop the old one. The events stay untouched throughout.

What a projection is

A projection (or read model) is a table built from events for one kind of question: "orders per customer", "stock by warehouse", "revenue by day". It is derived data. When you add a column, fix a bug in the handler or want a new view, you do not migrate it, you rebuild it. That only works if the events are complete and your handlers are deterministic: same events in, same table out. Avoid calling other services or reading the clock inside a projection handler.

Store a checkpoint

A projection needs to remember how far it has read, so a restart continues instead of starting over:

CREATE TABLE projection_checkpoints (
  name     text PRIMARY KEY,
  position bigint NOT NULL
);

The loop reads events with a position greater than the checkpoint, applies them, and updates the checkpoint in the same transaction as the read model change. That single transaction is what makes a crash safe: either the table and the checkpoint both moved, or neither did. It also makes the projection idempotent without a dedupe table, as the position acts as the event identity. The events come from a table such as the one in the minimal event store.

async function runBatch(pool, name, apply) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const cp = await client.query(
      "SELECT position FROM projection_checkpoints WHERE name = $1 FOR UPDATE",
      [name]
    );
    const from = cp.rows[0]?.position ?? 0;
    const { rows } = await client.query(
      "SELECT position, type, data FROM events WHERE position > $1 ORDER BY position LIMIT 500",
      [from]
    );
    for (const e of rows) await apply(client, e);
    if (rows.length) {
      await client.query(
        `INSERT INTO projection_checkpoints (name, position) VALUES ($1, $2)
         ON CONFLICT (name) DO UPDATE SET position = $2`,
        [name, rows[rows.length - 1].position]
      );
    }
    await client.query("COMMIT");
    return rows.length;
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}

Note the FOR UPDATE on the checkpoint row, which stops two copies of the projector from running the same batch. If the checkpoint row does not exist yet, create it with position 0 first, or the lock has nothing to hold.

The rebuild procedure

  1. Create the new table, for example order_summary_v2, and a checkpoint named order_summary_v2 at position 0.
  2. Run the projector against the new name until a batch returns zero rows. The old projection keeps serving queries meanwhile.
  3. Leave the new projector running so it stays current. Compare a few rows against the old table, or compare counts.
  4. Switch the query code to read from the new table, deploy, and drop the old table and its checkpoint.

This avoids downtime and gives you a way back: until you drop the old table, you can point reads at it again.

The commit-order trap

If position comes from a bigserial column, positions are assigned when rows are inserted, not when transactions commit. Two writers can get positions 10 and 11, and 11 can commit first. A projector that reads position > 9 in between sees 11 but not 10, saves the checkpoint at 11, and event 10 is skipped for good when it commits later. This is rare locally and real in production under load. Ways to deal with it:

  • Append events from a single writer process, so inserts are serialized.
  • Have the projector stay a short distance behind, ignoring events newer than a few seconds, so slow transactions finish first. It is a heuristic, not a proof.
  • Read only events whose transaction id is older than the oldest running transaction, using pg_snapshot_xmin(pg_current_snapshot()) against an xmin-style column you store. This is the exact fix and takes care to get right.

Whichever you pick, write it down, because it explains a missing row six months later.

The Flisk way

Run the projector as a worker with the database as a dependency, and run rebuilds as one-off commands that use the service's own environment:

flisk resource summary-projector --type worker --stack shop --yes
# in its service.json: "dependsOn": ["shop-db"]

flisk run summary-projector -- bun run scripts/rebuild.ts --name order_summary_v2

The flisk run command runs your command with the environment the service has in the stack, so the script gets the same DATABASE_URL as the live projector. Because the checkpoint lives in the database, you can stop and rerun the rebuild at any point. flisk logs --service summary-projector --since 5m shows its progress lines. To start a rebuild from a clean database, see resetting a local database.

Pitfalls

  • Non-deterministic handlers. Using now() or a random id inside a handler gives a different table on every rebuild. Take time from the event.
  • Old event shapes. A rebuild reads the whole history. Make sure the handler can read every version, see versioning event schemas.
  • Big batches. A single transaction over millions of events holds locks and bloats. Batches of a few hundred are fine.
  • Side effects in handlers. A rebuild must not send emails. Projections write tables only.

Questions people ask

How is a read model different from a cache?

A cache can be dropped and refilled on demand from the source of truth. A read model is built from the event history by a handler, shaped for queries, and kept up to date continuously. It is rebuilt rather than refilled on a miss.

Can I rebuild a read model without downtime?

Yes. Build a new table beside the old one with its own checkpoint, let it catch up, switch reads to it and then drop the old table.

Do I need event sourcing to have read models?

No. You can project from any ordered stream of events, including events published by other services, as long as you can replay them from a known position.
