Event-driven systems locally

How to keep events in order for one entity

You do not need the whole stream in order. You need the events for one order, one account or one user in order, and that is a much easier promise to keep.

You cannot rely on events arriving in the order they were created, but you can make the consumer detect disorder. Give every event a version number that counts up per entity (per order, per account), and have the consumer apply an event only when its version is exactly one more than the last it applied. Older versions are ignored, and gaps are parked until the missing event arrives.

Where disorder comes from

Even a single queue can deliver events out of order. A failed message is redelivered after later ones have already been handled. Two consumer instances take consecutive messages and finish in the opposite order. A producer publishes from two processes. A retry sends an old event after a newer one. Global ordering would need one producer and one consumer handling one message at a time, which removes the reason to use a queue.

The useful guarantee is smaller: events about the same entity are applied in order. Different entities may interleave freely.

Number the events per entity

The producer owns the counter. If you already store entity changes in a table, the version can be a column that increments in the same transaction that changes the entity:

UPDATE orders
SET status = $2, version = version + 1
WHERE id = $1
RETURNING version;

The returned version goes into the event next to the order id. Because the update takes a row lock, two concurrent changes to one order get different versions, in commit order. Put both the entity id and the version in the envelope, see versioning event schemas for the other fields.

The consumer rule

The consumer keeps the last applied version per entity and compares:

  • version = last + 1: apply it and store the new last version.
  • version <= last: it is a duplicate or stale event, skip it and acknowledge.
  • version > last + 1: something is missing. Do not apply it.
async function apply(client, e) {
  const cur = await client.query(
    "SELECT version FROM order_view WHERE id = $1 FOR UPDATE",
    [e.data.orderId]
  );
  const last = cur.rows[0]?.version ?? 0;

  if (e.data.version <= last) return "skip";
  if (e.data.version > last + 1) return "gap";

  await client.query(
    `INSERT INTO order_view (id, status, version) VALUES ($1, $2, $3)
     ON CONFLICT (id) DO UPDATE SET status = $2, version = $3`,
    [e.data.orderId, e.data.status, e.data.version]
  );
  return "applied";
}

The row lock with FOR UPDATE stops two workers from applying versions 3 and 4 of the same order at once. A first event for a new entity finds no row, so last is 0 and version 1 is accepted.

What to do with a gap

You have three honest options, and the right one depends on how a gap can happen in your system:

  1. Reject and let the broker redeliver. Do not acknowledge, or negatively acknowledge with a delay. The missing event is usually just late, and the redelivery will succeed after it arrives. Limit the attempts, or a lost event blocks that entity forever.
  2. Park it. Save the event in a pending_events table keyed by entity and version, and after each successful apply check whether the next version is waiting.
  3. Fetch the truth. Call the producer's API for the current state and overwrite, which makes you self-healing but couples you to the producer.

For local work, option one with a small retry count is the easiest to build and to test, see testing consumer retries locally.

The Flisk way

Flisk does not reorder anything for you: ordering is a property of your events and your consumer. What it gives you is a way to reproduce disorder on your machine. Run a queue and a consumer as usual (flisk resource bus --type queue --stack shop, flisk resource order-view --type worker --stack shop, and "dependsOn": ["bus"] in the consumer), then use a test script that publishes versions 1, 3, 2 and 2 again, started with flisk run order-view -- bun run scripts/out-of-order.ts. Assert that the final view is at version 3 with the right status. Run the script after every change to the consumer.

Pitfalls

  • Per-entity counters that skip numbers. A database sequence can leave gaps after a rollback, so a counter taken from one is unsafe here. Increment a column in the entity row instead.
  • Ordering across entities. Do not depend on "customer created" arriving before "order created". Make the consumer cope, for example by creating a placeholder customer row.
  • One slow entity blocks the rest. If you retry gaps in place, one stuck order holds the queue. Park it and move on.
  • Too much machinery. If the consumer overwrites the whole state from each event, ordering errors only matter for the last event. Compare timestamps or versions and keep the newest.

Questions people ask

Does a message queue guarantee ordering?

Usually only within narrow limits, for example per partition or per single consumer, and redelivery of failed messages can still break it. Design the consumer to detect out-of-order events instead of assuming order.

Is a timestamp good enough to order events?

Rarely. Clocks differ between services, and two events can share a millisecond. A per-entity version number assigned in the same transaction as the change is reliable.

What if I only need the latest state?

Then ordering matters less. Store the version or timestamp with the state and ignore any event older than what you hold, so a late event cannot overwrite newer data.
