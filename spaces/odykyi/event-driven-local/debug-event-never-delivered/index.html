Why your event was never delivered: a debugging checklist

An event vanished somewhere between two services. Do not guess. Follow it hop by hop and stop at the first place it is missing.

When an event never reaches its consumer, walk the path in order and stop at the first hop where the evidence is missing: was it created, was it committed, was it published, does the subject match a stream, is a consumer subscribed with the right filter, did the handler run, and did a deduplication guard swallow it. Each hop has one cheap check.

Start with one event and one id

Pick a single failing case and note its event id (or order id). Everything below searches for that value. If your events have no id and no correlation field in the logs, add them first: debugging without an identifier is guessing. Log the id at every hop: when it is created, when it is published, and when it is received and finished.

Hop 1: did the producer commit the event?

If you use an outbox, look in the table:

SELECT id, event_id, type, created_at, published_at
FROM outbox
WHERE payload->>'orderId' = 'ord_123';
  • No row: the handler never wrote it. The request failed earlier, or the code path skips the insert. Look at the producer's logs.
  • Row with published_at empty: the relay has not sent it. Is the relay running, and is it connected to the same database as the producer? Two services pointed at different database names is a classic.
  • Row with published_at set: the relay believes it sent it. Move on.

Without an outbox, check whether the publish call happened before the commit, and whether its error was swallowed by a missing await.

Hop 2: is it in the broker?

For NATS with JetStream, the nats command line tool shows streams and their message counts: nats stream ls, then nats stream info EVENTS. A publish whose subject matches no stream fails with "no responders", or in core NATS disappears silently because no one listens. Compare the subject you published to, for example events.order.created, with the subjects the stream captures. A stream created for events.* does not match events.order.created, because * matches one token and > matches several.

The server also has an HTTP monitoring port, 8222 in the NATS resource Flisk generates (flisk resource bus --type queue). Publish it through "extraPorts": [{ "port": 8222 }] in the queue's service.json, and curl http://127.0.0.1:8222/jsz returns JetStream totals. I did not start the stack to test this, so confirm the port answers before depending on it. See NATS for local development for the setup. For RabbitMQ, the management UI lists queues and unrouted messages, see RabbitMQ for local development.

Hop 3: is a consumer attached?

  • Is the consumer service running at all? flisk status lists every service, and flisk status --unhealthy shows only the ones failing or still starting.
  • Is it subscribed to the same subject or queue name, with the same broker URL? Print its environment with flisk run billing -- printenv NATS_URL.
  • With a durable consumer, does it have a filter subject that excludes your event, or an acknowledgement backlog? nats consumer info shows pending and unacknowledged counts.
  • With a plain subscription (no durable consumer), it only receives messages published after it subscribed. An event sent while it was restarting is gone.

Hop 4: did the handler run and finish?

Read the consumer's recent output for your id:

flisk logs --service billing --since 10m --tail 500

Three outcomes: you see the id and a success line (the problem is later), you see the id and an error (a normal bug, and the broker may be retrying it, see testing consumer retries), or you see nothing (the message did not arrive, go back to hop 3). Also check for a crash loop: a consumer that dies on start receives nothing. Reading logs from every service covers the log tooling in more detail.

Hop 5: did a guard drop it?

A deduplication table or a version check can swallow an event that is not a duplicate:

SELECT * FROM processed_events WHERE event_id = '6f1c0a6e-8d0a-4f5e-9d1e-2b7a4c1f9a10';

If the row exists but the effect is missing, the claim was committed without the work, which means the claim and the work were not in one transaction, see the idempotent consumer article. A version guard that sees a gap parks the event on purpose, see keeping events in order.

Pitfalls

  • Stale volume. A queue that keeps its data in a named volume still holds old messages and old stream definitions from earlier runs. A stream with different subjects than your code expects explains many silent failures.
  • Two environments. Host tools use 127.0.0.1, services use the service name. A script on your laptop that publishes to the wrong address reports success against a different server.
  • Fixing by restart. Restarting everything can hide the cause. Find the hop first, then fix it.

Once you can find the lost hop quickly, lock it down with a test that fails when it happens, see testing eventual consistency.

Questions people ask

Why does my NATS subscriber not receive messages I published?

Usually the subscriber subscribed after the publish, the subjects do not match (a single token wildcard versus a multi-token one), or it connects to a different server than the publisher. With JetStream, use a durable consumer so it receives messages stored while it was away.

How can I see what is inside a queue without consuming it?

Use the broker's inspection tools. In NATS JetStream, stream and consumer info and the stream get commands read messages without acknowledging them. RabbitMQ's management UI has a Get messages option with requeue.

Should I add logging at every hop?

Yes, with the event id in each line: when created, published, received and finished. It costs little and turns a search through three services into one grep.
