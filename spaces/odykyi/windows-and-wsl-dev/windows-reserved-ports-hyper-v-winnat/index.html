Port blocked on Windows but nothing uses it: winnat fix

Some ports are taken by Windows itself, not by a program. Hyper-V and WSL reserve ranges that look free in every process list.

If a port fails to bind on Windows with "An attempt was made to access a socket in a way forbidden by its access permissions" and netstat shows nothing listening, Windows has probably reserved it for Hyper-V. List the reserved ranges with netsh interface ipv4 show excludedportrange protocol=tcp, then either move your service to another port or reset the reservation by restarting the winnat service as administrator.

What the error looks like

You start a container or a dev server and one of these appears:

  • Ports are not available: exposing port TCP 0.0.0.0:5432 -> 0.0.0.0:0: listen tcp 0.0.0.0:5432: bind: An attempt was made to access a socket in a way forbidden by its access permissions.
  • Error: listen EACCES: permission denied 0.0.0.0:3000 from Node.

This is different from a normal "address already in use" error. Looking for a process with netstat -ano | findstr :5432 finds nothing, because no process owns the port. The usual guide to port already in use covers the case where a program holds it; this page covers the case where Windows does.

Find the reserved ranges

Run this in PowerShell:

netsh interface ipv4 show excludedportrange protocol=tcp

The output is a table of start and end ports. If your port falls inside any row, that is the cause. Windows picks these ranges dynamically when the Hyper-V or Windows NAT components start, which is why the same port can work for weeks and then fail after a reboot or a WSL update. Rows marked with an asterisk are ranges an administrator excluded on purpose.

Fix 1: reset the reservation

In an administrator PowerShell or Command Prompt, stop and start the NAT driver service:

net stop winnat
net start winnat

Run the list command again. The dynamic ranges are usually regenerated somewhere else, which frees your port. Stopping winnat briefly breaks networking for WSL and Docker Desktop, so close them first, or restart them afterwards with wsl --shutdown and a Docker Desktop restart.

Fix 2: keep the port reserved for you

If the same port keeps getting taken, exclude it yourself so Windows cannot hand it to Hyper-V. Do this while the service is stopped, as administrator:

net stop winnat
netsh int ipv4 add excludedportrange protocol=tcp startport=5432 numberofports=1
net start winnat

This adds a persistent administrative exclusion for that one port. Programs can still bind it, because the exclusion only prevents the dynamic range from claiming it.

Fix 3: pick a different port

The least invasive fix on a locked-down company laptop, where you may not have administrator rights, is to move your service. For a Node dev server, set PORT. For Postgres in a container, publish it as 15432:5432 instead of 5432:5432.

What Flisk checks on native Windows

When you run flisk doctor on native Windows, a check called "Windows ports and DNS" runs the same netsh command and looks at ports 80, 443 and 5432. If any is inside a reserved range, it reports that Windows reserved the port for Hyper-V or WSL and offers two fixes: reset the ranges with net stop winnat and net start winnat as administrator, or change Flisk's ports with FLISK_HTTP_PORT, FLISK_HTTPS_PORT and FLISK_POSTGRES_PORT, set in the shell or the project .env. If those ports are in use by a real listener, it tries to name the owner, for example IIS for port 80. Note that on native Windows the doctor run ends with a native Windows finding and a failing exit code by design, so read the "Windows ports and DNS" lines rather than the exit code.

flisk doctor

A few honest limits. This check is part of the native Windows diagnostics, so it does not run inside Ubuntu on WSL2. On WSL2 as a non-root user, Flisk falls back to ports in the 8080 to 8180 range instead of 80, and prints the real URLs with the port, so the reserved-range problem seldom shows up there. If the netsh call fails, the check says it could not inspect the ranges and skips that part.

Pitfalls

  • Not an admin. Both net stop winnat and netsh ... add excludedportrange need elevation. Without it you get "Access is denied".
  • Fast Startup. A Windows with Fast Startup on can keep ranges across what feels like a reboot. A full restart or the winnat reset clears them.
  • VPN clients. Some VPN and security tools also reserve or hold ports. If the ranges look clean and the bind still fails, check the firewall and VPN software.

Questions people ask

Why does netstat show nothing but the port is blocked?

Windows can reserve ports for Hyper-V and WSL without any process owning them. Those reservations do not appear in netstat. Use netsh interface ipv4 show excludedportrange.

Is it safe to run net stop winnat?

It is a common fix, but it briefly drops NAT for WSL and Docker Desktop. Close them first and restart them afterwards.

Which ports does flisk doctor check on Windows?

On native Windows it checks 80, 443 and 5432 for Hyper-V reservations and existing listeners.
