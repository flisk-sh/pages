*.localhost not resolving on Windows: the hosts file fix

Names ending in .localhost should point at your own machine. On some Windows setups they do not, and the hosts file has no wildcard to fix it in one line.

If api.myapp.localhost does not open on Windows, add one line per name to C:\Windows\System32\drivers\etc\hosts pointing at 127.0.0.1, then run ipconfig /flushdns. The hosts file cannot do wildcards, so every hostname needs its own entry. As a shortcut with no edits, send the request to 127.0.0.1 and set the Host header yourself.

Why it happens

The standard says any name under .localhost must resolve to the loopback address. Modern browsers such as Chrome, Edge and Firefox apply that rule themselves, so they usually open these names without help. Other programs ask the operating system's resolver, and the Windows resolver does not always answer for *.localhost. Tools you may notice it in: older curl builds, Python requests, Node scripts, PowerShell's Invoke-WebRequest and test runners. A name that works in the browser but fails in a script is the typical sign. The generic version of this problem, with Linux and Mac causes, is in localhost subdomain does not resolve.

Edit the hosts file

  1. Open Notepad as administrator: search for Notepad, right-click, Run as administrator.
  2. Open C:\Windows\System32\drivers\etc\hosts. Set the file filter to All Files so it shows.
  3. Add a line for each name you use:
127.0.0.1 api.myapp.localhost
127.0.0.1 app.myapp.localhost
  1. Save, then flush the resolver cache in a terminal: ipconfig /flushdns.
  2. Check: ping api.myapp.localhost should reply from 127.0.0.1.

A line such as 127.0.0.1 *.myapp.localhost does nothing, because the hosts file matches names exactly. If you add services often, either keep a short list of names or use the Host header method below.

Skip the hosts file: connect to 127.0.0.1

A reverse proxy that routes by hostname only needs the right Host header, not a working DNS name. Connect to the loopback address and tell the proxy which site you mean:

curl -H "Host: api.myapp.localhost:8080" http://127.0.0.1:8080/health

This works with any client that lets you set headers, and it needs no administrator rights. Flisk's own agent tooling does the same: when a route URL ends in .localhost, it connects to 127.0.0.1 and keeps the route's host in the Host header, because Traefik, the gateway Flisk uses, matches on that header.

What Flisk checks and tells you

On native Windows, flisk doctor includes a "Windows ports and DNS" check that looks up flisk.localhost and example.flisk.localhost. If either does not resolve to 127.0.0.1 or ::1, it fails with the message that browser URLs with hostnames will fail until you fix the hosts file or use the 127.0.0.1 URLs, and prints these two lines to add to the hosts file:

127.0.0.1 flisk.localhost
127.0.0.1 example.flisk.localhost

Those two names are the doctor's probe. For your own project, the real hostnames follow the pattern service.project.localhost, and flisk networks prints the exact URLs, including the port. Copy names from that output into your hosts file if a tool on your machine needs them. Inside Ubuntu on WSL2, name resolution is Linux's, not Windows', and this doctor check does not run there.

flisk networks

If a project runs as local processes, the URLs are plain http://localhost:<port>, so no hostname is involved at all.

Pitfalls

  • Forgetting the port. On WSL2 the gateway often sits on 8080, not 80, so http://api.myapp.localhost reaches nothing. Use the URL with the port from flisk networks.
  • Browser DNS cache or secure DNS. If a browser still fails after the hosts edit, restart it. A browser using DNS over HTTPS may skip the hosts file for some names.
  • Hosts file permissions. Editing without elevation silently fails to save in some editors. Reopen the file and confirm your lines are there.
  • Corporate lockdown. If you cannot edit hosts at all, use the Host header method or plain ports.

Questions people ask

Can I use a wildcard in the Windows hosts file?

No. Each hostname needs its own line because the hosts file matches names exactly.

Why does the name work in Chrome but not in curl?

Browsers resolve .localhost to loopback themselves. Other tools ask the Windows resolver, which does not always do so.

How do I test without editing the hosts file?

Request 127.0.0.1 and set the Host header, for example curl -H "Host: api.myapp.localhost:8080" http://127.0.0.1:8080/health.
