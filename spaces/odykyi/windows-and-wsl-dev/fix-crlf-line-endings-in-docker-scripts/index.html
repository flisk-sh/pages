Fix CRLF line endings that break shell scripts in Docker

A shell script saved with CRLF endings looks fine in an editor and fails inside a Linux container. The fix is one repository file and one git setting.

Windows editors and Git can save text files with CRLF line endings, but Linux expects LF. A shell script with CRLF fails in a container with errors such as /bin/sh^M: bad interpreter, exec ./entrypoint.sh: no such file or directory or exec format error. Fix it by committing a .gitattributes file that forces LF for scripts, setting core.autocrlf input locally, and renormalizing the files once.

Why it fails

The first line of a script is #!/bin/sh. With CRLF the kernel reads the interpreter as /bin/sh followed by a carriage return character, a path that does not exist. The error message is confusing because the file you point at does exist; it is the interpreter named inside it that does not. The same thing breaks .env files (a value ends with a hidden \r), Makefiles and any shell snippet copied into a Dockerfile.

Check a file quickly:

file entrypoint.sh
# entrypoint.sh: Bourne-Again shell script, ASCII text executable, with CRLF line terminators

"with CRLF line terminators" is the problem. You can also list all offenders in a repo:

git ls-files --eol | grep 'w/crlf'

Fix it for the whole team: .gitattributes

A git setting on one laptop does not protect the next person. Put the rule in the repository so every clone follows it:

* text=auto
*.sh text eol=lf
Dockerfile text eol=lf
*.yml text eol=lf
*.json text eol=lf
.env* text eol=lf
*.bat text eol=crlf
*.ps1 text eol=crlf

The wildcard line lets Git decide which files are text. The explicit eol=lf lines pin the ones that run on Linux. Batch and PowerShell files keep CRLF because those are Windows scripts.

Then renormalize what is already in the repository, once, and commit the result:

git add --renormalize .
git commit -m "Normalize line endings"

Teammates who already have CRLF files in their working tree can refresh them after pulling:

git rm --cached -r . 
git reset --hard

Make sure they have committed or stashed their changes first, because reset --hard discards uncommitted work.

The local git setting

Git for Windows often defaults to core.autocrlf true, which converts LF to CRLF on checkout. For a project that runs in Linux containers, set it to input, which leaves files alone on checkout and only converts CRLF to LF on commit:

git config --global core.autocrlf input

Run it in Ubuntu on WSL2, and also in Git for Windows if you use both, because each has its own global config.

Where Flisk helps

On native Windows, flisk doctor reads git config core.autocrlf and warns when it is true, with the message that generated files may get CRLF while Docker Linux containers expect LF, and the fix git config core.autocrlf input. That check lives in Flisk's Windows diagnostics, so it runs on native Windows and not inside Ubuntu. Inside WSL2, rely on .gitattributes and the script snippet below. Flisk's own setup-wsl.ps1 helper sets core.autocrlf input inside Ubuntu as part of its setup.

The .gitattributes file is also what keeps files that Flisk generates from a service definition, such as Compose or Tilt files, from being rewritten with CRLF if you do commit them. Flisk keeps generated output in git-ignored folders by default, so this mostly matters for your own scripts and Dockerfiles.

A guard inside the Dockerfile

If you cannot control every contributor's setup, you can strip carriage returns during the image build. It treats the symptom, not the cause, but it stops builds from breaking:

COPY entrypoint.sh /entrypoint.sh
RUN sed -i 's/\r$//' /entrypoint.sh && chmod +x /entrypoint.sh

Pitfalls

  • Editors. Configure the editor to use LF for the repository. In VS Code the status bar shows CRLF or LF and can switch it; an .editorconfig with end_of_line = lf makes it automatic.
  • Binary files. text=auto detects binaries, but mark known ones with binary if you see corruption.
  • Files already mangled. Renormalizing fixes line endings, not content. If a script was edited in a tool that added a byte order mark, remove that too.

Questions people ask

What does bad interpreter with ^M mean?

The script has Windows CRLF line endings, so the shebang names the interpreter with a trailing carriage return, which is not a real path.

Should I use core.autocrlf true or input?

For projects that run in Linux containers, use input. It keeps LF in your working tree and still converts CRLF to LF when you commit.

Does flisk doctor check autocrlf inside WSL2?

No. The autocrlf warning is part of the Windows diagnostics that run on native Windows. Inside WSL2, use .gitattributes.
