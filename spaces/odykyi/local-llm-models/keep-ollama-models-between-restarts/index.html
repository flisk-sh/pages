How to keep Ollama models when the container restarts

A model is a file of several gigabytes. If it lives in the container's own filesystem, every recreate throws it away. One volume fixes that.

Mount a volume at /root/.ollama in the Ollama container. That directory holds the downloaded model files. Without a volume they live in the container's writable layer and disappear whenever the container is removed and recreated.

Why the models vanish

A restart keeps a container's filesystem. Removing the container does not. docker compose down, docker rm, an image update or a changed configuration that forces a recreate all create a fresh container from the image, and the image contains no models. The symptom is always the same: a request fails with a "model not found" error, and you wait through another multi-gigabyte pull.

Plain Docker and Compose

With plain Docker, add a named volume:

docker run -d --name ollama \
  -v ollama-models:/root/.ollama \
  -p 11434:11434 ollama/ollama

In Compose, declare the volume and mount it:

services:
  ollama:
    image: ollama/ollama
    ports: ["11434:11434"]
    volumes:
      - ollama-models:/root/.ollama
volumes:
  ollama-models:

A named volume survives docker compose down. It is removed only by docker compose down -v or docker volume rm. A bind mount such as ./models:/root/.ollama works too and is easier to inspect, but file permissions can cause trouble on Linux. The general rules are in keep Docker Compose volumes between runs, or reset them.

The Flisk way

The --type inference preset mounts no volume, so pulled models are lost when flisk down removes the container. Add one to the resource's service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "brain",
  "appType": "bring-your-own",
  "stack": "llm",
  "port": 11434,
  "healthCheckPath": "/v1/models",
  "image": "ollama/ollama",
  "volumes": [
    { "source": "ollama-models", "target": "/root/.ollama" }
  ]
}

A name in source is a named Docker volume. Flisk declares it once in the stack's generated Compose file, and flisk down keeps it. Two services that name the same volume share it. Run flisk config regenerate or flisk up llm to apply the change, then pull the model once:

flisk run brain -- ollama pull llama3.2

Stop and start the stack and the model is still there. Check with flisk run brain -- ollama list.

If you already have models in an existing Docker volume, for example one called ollama from an earlier docker run, a volume entry can set "name": "ollama" next to source. Flisk then mounts that Docker volume as it is, with no copy. Without name, the volume gets the generated project's prefix and your old data is not found.

Starting from empty on purpose

To reset, stop the stack with flisk down, find the full volume name with docker volume ls --filter label=com.docker.compose.volume=ollama-models, and remove it with docker volume rm <that name>. That deletes every model in it, so check the size you are about to re-download first.

Pitfalls

  • Disk space. Several models quickly add up to tens of gigabytes inside the Docker VM. If the disk fills up, see Docker disk full.
  • Two Ollama copies. The native app stores models in its own folder under your home directory, not in the container's volume. Models pulled on the host are not visible to the container. Pick one runtime for a project, or accept pulling twice.
  • Baking a model into an image. A custom Dockerfile that runs ollama pull at build time gives a reproducible image, but a very large one. Use it for CI, not for daily work.

How to confirm it worked

Do the test once, on purpose, so you trust it later. Pull a tiny model, list models, remove the container (with Flisk, flisk down, then flisk up llm), and list again. If the model is still listed and the second start did not download anything, the volume is mounted in the right place. If the list is empty, the target path is wrong or the volume was created under a different name than you expect. Run docker volume ls to see which volumes exist, and compare them with the name in your configuration.

Document the pull command in the README, or add it to a small setup script, so a new teammate gets the same models as you with one command. Models are data, not code, so they do not belong in git. A short list of names in a file that the script reads is enough.

With models persisted, the next problem is speed. A GPU makes a large difference, and Docker only gives you one on some hosts, which the GPU guide covers.

Questions people ask

Where does Ollama store models in Docker?

In /root/.ollama inside the container. Mount a volume there to keep them.

Does docker compose down delete my models?

Not if they are in a named volume. Only docker compose down -v or docker volume rm deletes the volume.

Why does my model disappear after flisk down?

The inference preset mounts no volume, so the container is removed with its models. Add a volumes entry for /root/.ollama.
