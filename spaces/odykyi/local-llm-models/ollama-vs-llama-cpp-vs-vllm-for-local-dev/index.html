Ollama vs llama.cpp vs vLLM for local development

They all serve open models over an OpenAI-style API. The differences are in setup effort, hardware and how much control you want.

For daily development on a laptop, start with Ollama: one install, one command to pull a model, an OpenAI-compatible API. Pick llama.cpp's server when you need control over quantization files and flags, or the smallest footprint. Pick vLLM when you have an NVIDIA GPU and care about throughput with many concurrent requests. Your app code can stay the same, because all three can answer OpenAI-style requests.

The short comparison

OllamaDaily dev, quick model switchingCPU, Apple silicon, NVIDIA, some AMDLowest

vLLMThroughput on a GPU server, batchingNVIDIA mostly, a serving setup rather than a laptop toolHigher

This table is a simplification. Hardware support changes quickly, so check each project's documentation for your card.

How to decide

  • You want to try models and get on with your app. Use Ollama. Its model library handles downloads, formats and templates.
  • You need a specific quantized file, or exact flags. Use llama.cpp directly. It also fits when you want to build a small image for CI.
  • You are testing a production-style GPU setup. Use vLLM so your local behavior, such as batching and memory use, resembles the deployment.
  • You are not sure. Use Ollama, and keep the base URL in configuration so you can change your mind.

Swapping the server in Flisk

Because Flisk's --type inference resource is a bring-your-own container that only needs to answer GET /v1/models for its health check, the engine is a few flags. The default is Ollama:

flisk resource brain --type inference --stack llm --yes

For vLLM's OpenAI server image, listening on port 8000:

flisk resource brain --type inference --stack llm \
  --image vllm/vllm-openai --port 8000 --health-path /health --yes

This writes "image": "vllm/vllm-openai", "port": 8000 and "healthCheckPath": "/health". Flisk's own tests cover exactly this combination. For llama.cpp, use the server image from the project's registry and its listening port. Look both up in the llama.cpp documentation, because image tags change, and pass them the same way with --image and --port. The server needs a model file mounted into the container, which is what volumes in service.json is for, and the model path goes in the container's command arguments in its own documentation. If you prefer to build your own image, --dockerfile ./Dockerfile.llm builds from a Dockerfile instead.

The vLLM image needs a GPU and usually shared memory, so add the container block from the GPU guide, with "gpus": "all" and a large shmSize or "ipc": "host". On a Mac, none of the three reach the GPU from a container, so run the engine natively there.

The consumers do not change. They call http://brain:PORT/v1/chat/completions by service name. Keep PORT in an environment variable so a swap is one edit. See switching between local and hosted.

Pitfalls

  • Different model names. Ollama uses names such as llama3.2. vLLM and llama.cpp use the model path or repo name you started them with. Keep the model name in configuration.
  • Different defaults. Context length, chat template and sampling defaults differ per engine. The same prompt can behave differently. Compare outputs when you swap.
  • Different health endpoints. Use the path your engine documents, passed with --health-path, or Flisk will wait on a path that never answers.
  • Feature gaps. Tool calling and structured output differ. Test what you use.

A practical rule for teams

Pick one default engine for the repository, document it in the README, and make everything else an opt-in. A team that mixes engines per developer cannot reproduce a bug that depends on the model's behavior. Record the engine, the model name and the version in the project, for example in the service.json and the .env.example, so a new teammate gets the same setup from a clean clone. Re-evaluate when your production engine changes, since the local one only has to be close enough to catch your own mistakes.

Start with Ollama as in run Ollama locally for app development, and move only when you hit a limit.

Questions people ask

Is vLLM better than Ollama?

They solve different problems. vLLM is built for throughput on GPU servers. Ollama is simpler for one developer on a laptop.

Can I use llama.cpp with the OpenAI SDK?

Yes. Its server exposes OpenAI-style routes, so you change the base URL, as with Ollama.

How do I use vLLM as a Flisk inference resource?

Pass --image vllm/vllm-openai, --port 8000 and --health-path /health to flisk resource --type inference, and give the container a GPU.
