Local LLMs for development

How to mock an LLM API in tests

A model call is a network request with a non-deterministic answer. Treat it like any other flaky dependency and replace it in tests.

Replace the model with a small fake that returns a fixed, valid response. Run it as a local HTTP server that speaks the same API your code calls, and point your client's base URL at it in tests. That keeps the test fast, free and repeatable, and it exercises your real HTTP client code rather than a stub of it.

What a test should and should not check

A unit test for your own code needs to know that you send the right request and that you handle each kind of response. It cannot judge the quality of a model's answer. So write the cases you control: a normal reply, a tool call, an empty reply, a malformed JSON reply, a 429 rate limit, a 500 error and a timeout. A real model almost never produces the last four on demand, and these are the ones that break in production. The general rule for mocks and real services is in mock or run the real service in tests.

Option 1: mock inside the process

Most SDKs let you inject a transport or a fake client. This is the fastest test and fine for pure logic. The weakness is that it skips real serialization, headers, streaming and retries, so a bug in those still ships.

Option 2: a fake server on a port

A tiny server is about twenty lines. This one answers the chat completions route with a fixed reply and lets a test force an error with a header:

import { createServer } from "node:http";

createServer((req, res) => {
  if (req.url === "/health") return res.end("ok");
  if (req.headers["x-fake-error"]) {
    res.writeHead(Number(req.headers["x-fake-error"]), { "content-type": "application/json" });
    return res.end(JSON.stringify({ error: { message: "forced error" } }));
  }
  res.writeHead(200, { "content-type": "application/json" });
  res.end(JSON.stringify({
    id: "chatcmpl-test",
    object: "chat.completion",
    model: "fake",
    choices: [{ index: 0, finish_reason: "stop",
      message: { role: "assistant", content: "fixed answer" } }],
    usage: { prompt_tokens: 1, completion_tokens: 2, total_tokens: 3 },
  }));
}).listen(Number(process.env.PORT || 4010));

Point the client at http://localhost:4010/v1. Add one more branch for streaming that sends data: lines and ends with data: [DONE], because streaming is where hand-written parsers fail. Keep fixtures as files so a reviewer can read them.

Record-and-replay libraries do the same job from captured traffic. They are useful, but a recording goes stale when the API changes, so re-record on a schedule.

The Flisk way

If your test or dev stack runs under Flisk, make the fake one more service. As a local process it needs only a command:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "model",
  "appType": "backend",
  "command": "node server.mjs",
  "port": 4010,
  "healthCheckPath": "/health"
}

The consumer lists it in dependsOn and gets the URL through env, so it starts only after the fake answers its health check:

"dependsOn": ["model"],
"env": { "LLM_BASE_URL": "http://localhost:4010/v1" }

Flisk's tool-loop starter uses this shape. flisk project tool-loop creates an agent, an MCP tool server and a model service that stands in for the Anthropic Messages API, all as local processes with no Docker. The agent's ANTHROPIC_BASE_URL points at the mock, and you delete two lines of env and add a real key to use Claude. The mock follows one fixed strategy and is not a model. It is there so the real SDK loop runs offline. Read the walk-through in run an AI agent locally with MCP tools and a mock model.

In CI, the same service.json files start the fake before the tests, as described in running a stack in GitHub Actions.

Pitfalls

  • A mock that is too kind. If it never fails, your error handling is untested. Make failures one header or one fixture away.
  • Drift from the real API. Run a small number of tests against a real local model, such as Ollama with a 1B model, on a schedule. Mark them slow and keep assertions loose, for example "the reply is non-empty text", never an exact string.
  • Asserting on model wording. Even a seeded local model changes between versions. Assert on structure.
  • Secrets in tests. Use a dummy key. A test that needs a real key will be skipped by half your team.

For the local-model side of testing, see running Ollama for app development.

Questions people ask

Should unit tests call a real LLM?

No. The answer varies, calls cost time and money, and failures are hard to reproduce. Use a fake for unit tests and a few loose checks against a real local model.

How do I mock streaming responses?

Return text/event-stream with lines that start with data: followed by JSON chunks, and finish with data: [DONE].

What is a local alternative to the real API?

A small Ollama model behind the OpenAI-compatible /v1 route gives realistic responses without a key, but it is slower and not deterministic.
