How to call Ollama on the host from a Docker container

Inside a container, localhost means the container itself. That is why your app gets connection refused even though Ollama works from your terminal.

From inside a container, localhost is the container, not your computer. To reach an Ollama server running on the host, use host.docker.internal, for example http://host.docker.internal:11434. On Linux, add the name yourself with --add-host=host.docker.internal:host-gateway, and make Ollama listen on an address the container can reach.

Why this is worth doing

On a Mac, a container cannot use the GPU, as covered in the GPU guide. The native Ollama app uses Metal. So the fast setup is the model on the host and everything else in containers. You pay for it with one networking detail.

Docker Desktop and Colima

Docker Desktop provides the name host.docker.internal on macOS and Windows. Recent Colima versions provide it too. Test it from a throwaway container before changing your app:

docker run --rm curlimages/curl -s http://host.docker.internal:11434/api/tags

If this prints your model list, the path works. Set the app's base URL to http://host.docker.internal:11434/v1 and you are done.

Linux

Docker on Linux does not define the name by default. Add it, mapped to the special value host-gateway:

services:
  app:
    image: my-app
    extra_hosts:
      - "host.docker.internal:host-gateway"
    environment:
      LLM_BASE_URL: http://host.docker.internal:11434/v1

On Linux the request arrives from the Docker bridge, not from loopback. Ollama listens on 127.0.0.1 by default and will refuse it. Set OLLAMA_HOST=0.0.0.0:11434 for the server, for example in the systemd unit's environment, then restart it. Be aware of what that does: anyone who can reach your machine's network address can then use your model. On an untrusted network, bind to the bridge address or add a firewall rule instead.

The Flisk way

In a Flisk project the consumer is a container service, and extraHosts lives in the container block of its service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "chat-api",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 3000,
  "image": "my-chat-api:dev",
  "container": {
    "extraHosts": ["host.docker.internal:host-gateway"]
  },
  "env": {
    "LLM_BASE_URL": "http://host.docker.internal:11434/v1"
  }
}

Flisk writes that as extra_hosts in the generated Compose service. The same mapping works on Docker Desktop, where it is harmless. Do not copy the generated file by hand, run flisk config regenerate after editing, and flisk config verify to check that the generated files match.

If you would rather not touch the host, the alternative is the model server as a stack resource. That is flisk resource brain --type inference, reached as http://brain:11434/v1. It runs on the CPU on a Mac. Choose per project: the host server when speed matters, the stack resource when you want flisk up to be the only step.

Flisk's documentation also describes a third route: a service with a top-level command such as ollama serve runs on the host with no Docker. It applies when your whole project runs as local processes, because a project cannot mix local processes and containers yet. For a pure local-process project, the app and the model are both on the host, and http://localhost:11434 is correct. See run local services without Docker.

Pitfalls

  • Using localhost in the container's env. It is the number one cause. The value must be the host alias or the service name.
  • Port clash. If a containerized Ollama also publishes 11434, only one of them can own the port. Stop one, or publish the second on another host port.
  • Corporate VPNs and firewalls. They can block traffic from the Docker bridge to the host. Test with the curl command above, not with your app.
  • Binding to 0.0.0.0 permanently. Do it only on networks you trust.

A three-step way to find where the break is

  1. On the host, run curl http://localhost:11434/api/tags. If this fails, Ollama is not running, and nothing about Docker matters yet.
  2. From a throwaway container, run the curlimages/curl command above. If this fails, the problem is the alias or the binding address.
  3. From your app's own container, run the same request with flisk run chat-api -- curl -s http://host.docker.internal:11434/api/tags, or with docker exec in plain Compose, if the image has curl. If only this fails, the app's configuration is wrong, usually the environment variable.

Keep the address in one variable and document it in .env.example, so a teammate on Linux and a teammate on a Mac can each set the right value without editing code. The alias works the same way for any other host service, such as a database you run natively, so the habit pays off beyond Ollama.

When the call works, point your client at it as described in pointing the OpenAI SDK at Ollama.

Questions people ask

What address does a container use to reach the host?

host.docker.internal on Docker Desktop and recent Colima. On Linux add it with extra_hosts set to host-gateway.

Why is Ollama refusing connections from Docker on Linux?

It listens on 127.0.0.1 by default, and container traffic arrives from the Docker bridge. Set OLLAMA_HOST to an address the bridge can reach, and mind who else can connect.

How do I set extra_hosts in Flisk?

Add container.extraHosts to the service.json, for example host.docker.internal:host-gateway, then run flisk config regenerate.
