How to generate embeddings locally with Ollama and Qdrant

Embeddings turn text into vectors for search. You can develop the whole pipeline offline with two containers.

Pull an embedding model into Ollama, such as nomic-embed-text, then send text to POST /api/embed and store the returned vectors in a vector database such as Qdrant. Everything runs locally, so you can build and test a search or retrieval pipeline without an API key.

Use an embedding model, not a chat model

Embedding models are small, fast and purpose-built. A chat model can also return vectors, but its output is worse for search and slower. Pull one:

ollama pull nomic-embed-text

Then request vectors. input may be one string or a list of strings:

curl http://localhost:11434/api/embed -d '{
  "model": "nomic-embed-text",
  "input": ["How do I reset my password?", "Billing questions"]
}'

The response contains an embeddings array with one vector per input. The OpenAI-compatible route works as well: POST /v1/embeddings with the same model and input, so an OpenAI client can call client.embeddings.create(...) against the base URL from pointing the SDK at Ollama.

Every model has a fixed vector size. Read it from the first response (len(vector)) and use that number when you create the collection. Do not guess, and do not hard-code the size of a model you may swap later.

Store and search the vectors

Qdrant has a REST API on port 6333. Create a collection with the size you measured, add points, and search:

curl -X PUT http://localhost:6333/collections/docs -H 'content-type: application/json' -d '{
  "vectors": { "size": 768, "distance": "Cosine" }
}'

The 768 above is an example. Replace it with the length you measured. Then upsert points with PUT /collections/docs/points, each with an id, a vector and a payload holding the original text, and search with POST /collections/docs/points/search. Check Qdrant's current API reference for the exact body of each call, since it evolves between versions.

Embed your query with the same model you used for the documents. Mixing models gives meaningless distances. This is the most common retrieval bug. If you change the model, re-embed everything and recreate the collection.

The Flisk way

Both servers are resources in one stack. Inside a Flisk project:

flisk resource embeddings --type inference --stack rag --yes
flisk resource vectors --type database --framework qdrant --stack rag --yes
flisk up rag

The first command makes a bring-your-own Ollama container on port 11434. The second makes a Qdrant resource using qdrant/qdrant:v1.12.5, port 6333, with a named volume vectors-data mounted at /qdrant/storage so the data survives flisk down. Its UI and API are published on 127.0.0.1:6333 only. The Qdrant resource also records QDRANT_URL as http://vectors:6333, which is the address for containers on the stack.

Then pull the model into the embeddings container once:

flisk run embeddings -- ollama pull nomic-embed-text

Remember that the inference preset has no volume, so add the one from keeping Ollama models between restarts. Otherwise you pull the embedding model again after every flisk down. An indexing worker in the same stack calls http://embeddings:11434/api/embed and http://vectors:6333 by service name.

Pitfalls

  • Dimension mismatch. Qdrant rejects vectors whose length differs from the collection. Create the collection from the measured size.
  • Batching. Send lists of inputs rather than one request per chunk. Keep batches moderate so a single request does not time out.
  • Long inputs. A model has a maximum input length. Chunk documents before you embed them, and test with your longest chunk.
  • Local versus production vectors. A hosted embedding model gives different vectors. Treat the local one as a development model and plan to re-index if production uses another.

A quick way to check the pipeline

Before you build the real indexer, check the loop by hand. Embed three short sentences, store them, then search with a fourth that is close in meaning to one of them. If the nearest hit is the sentence you expected, the dimensions, the model and the distance metric are all consistent. If the results look random, the usual cause is a collection created with a different vector size or distance than the model expects, or a query embedded with a different model. Fix that before you add chunking, metadata filters or a reranker, because every later layer assumes this one is right.

With search working locally, you can feed retrieved text into a chat model. See running Ollama for app development for that half.

Questions people ask

Which Ollama model should I use for embeddings?

An embedding model such as nomic-embed-text. It is small and fast, and better for search than a chat model.

What vector size should my Qdrant collection use?

The length of the vectors the model returns. Measure it from a real response and use that number.

Can I mix embedding models in one collection?

No. Documents and queries must be embedded by the same model. If you change the model, re-embed everything.
