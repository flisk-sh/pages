Local LLMs for development

How to point the OpenAI SDK at a local Ollama server

Most LLM code already uses an OpenAI client. You can keep it and change two settings to run against a model on your own machine.

Set the client's base URL to http://localhost:11434/v1, pass any non-empty string as the API key, and use an Ollama model name as the model. Ollama implements the OpenAI chat completions API, so the official Python and Node SDKs work without other changes.

Python and Node

from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

reply = client.chat.completions.create(
    model="llama3.2",
    messages=[{"role": "user", "content": "Name three HTTP status codes."}],
)
print(reply.choices[0].message.content)
import OpenAI from "openai";

const client = new OpenAI({ baseURL: "http://localhost:11434/v1", apiKey: "ollama" });
const reply = await client.chat.completions.create({
  model: "llama3.2",
  messages: [{ role: "user", content: "Name three HTTP status codes." }],
});
console.log(reply.choices[0].message.content);

The API key is required by the client library but ignored by Ollama. The model must already be pulled, otherwise the call fails with a "model not found" error. List what is available with curl http://localhost:11434/v1/models.

Do not hard-code the URL

The point of the OpenAI-compatible route is that the same code can run against a local model in development and a hosted one in production. So read the settings from the environment:

client = OpenAI(
    base_url=os.environ.get("LLM_BASE_URL", "http://localhost:11434/v1"),
    api_key=os.environ.get("LLM_API_KEY", "ollama"),
)
model = os.environ.get("LLM_MODEL", "llama3.2")

Many SDKs also read OPENAI_BASE_URL and OPENAI_API_KEY themselves. Check the version you use, then you may not need code changes at all. The switching pattern, including the production side, is in switch between a local LLM and a hosted API.

What to double-check

Compatible does not mean identical. Test the features your app really uses:

  • Streaming. stream=True works and returns server-sent events like the hosted API.
  • Tool calling. Support depends on the model. A small model may ignore tools or return malformed arguments. Validate arguments in your code regardless.
  • JSON output. response_format support differs. Parse defensively and retry once on a parse failure.
  • Token counts and limits. Context length is a property of the model and the Ollama settings, not of your request. A long prompt can be truncated rather than rejected, so test with realistic input.
  • Newer endpoints. If you use a newer OpenAI API surface than chat completions and embeddings, check the Ollama documentation before relying on it.

From another container in a Flisk stack

If the model server is a resource in a Flisk stack, created with flisk resource brain --type inference, the other services reach it by service name on the Docker network at http://brain:11434/v1/chat/completions. Set the base URL in the consumer's env:

"env": {
  "LLM_BASE_URL": "http://brain:11434/v1",
  "LLM_API_KEY": "ollama"
}

A service that runs as a local process, one with a command, is not on the Docker network. It needs a host URL such as http://localhost:11434/v1, and the model server needs a published port, for instance "extraPorts": [{ "port": 11434 }]. This mismatch between container and host addresses causes most "connection refused" reports. See environment variable not loaded if the value does not arrive.

Pitfalls

  • Wrong path. The base URL ends in /v1, and the SDK appends /chat/completions. A base URL without /v1 returns 404.
  • Model names differ. A hosted model name will not exist locally. Keep the model name in configuration too.
  • Quality differs. A 3B model is a good test of your plumbing and a poor judge of your prompts. Re-check prompt quality against the model you ship.

A smoke test you can keep

Add one small script to the repository that sends a single short request through your configured client and prints the first line of the reply. Run it when you change the base URL, the model or the stack. It answers the question "does the wiring work" in a second, before you debug the larger application. Keep it separate from your test suite, since it needs a live model, and have it exit with a non-zero code on failure so a teammate or a CI job can run it too.

One more habit helps: log the base URL and model name once at startup, never the key. When a call hits the wrong server, the first thing you need is a line that says where the request went.

Once calls work, the next question is what your tests do. They should not need a model at all, which is covered in how to mock an LLM API in tests.

Questions people ask

What is the Ollama base URL for the OpenAI SDK?

http://localhost:11434/v1. From another container in the same Docker network use the service name, such as http://brain:11434/v1.

Do I need a real API key for Ollama?

No. Pass any non-empty string, because the client library requires one and Ollama ignores it.

Does tool calling work with Ollama's OpenAI API?

The endpoint accepts tools, but the result depends on the model. Test with the model you use and validate the arguments.
