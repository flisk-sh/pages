Flaky Tests and Flaky CI

Fix Flaky Tests Caused by Shared State and Test Order

Find tests that only pass in a certain order, isolate databases, files and ports per test, and use random order to expose leaks before CI does.

If a test passes alone but fails in the full suite, or fails only when another test runs first, it shares state with that test. Find the shared thing, then give each test its own copy or reset it after every test.

Prove it is order

Run the suite in random order a few times. Order-dependent tests show up fast.

pip install pytest-randomly
pytest -p randomly

go test -shuffle=on -count=5 ./...

When you have a failing order, shrink it. Run the failing test with one suspected partner. Bisect the list of tests that ran before it until two remain: the one that leaks and the one that suffers.

The usual shared things

  • Database rows. One test inserts a user with a unique email, another inserts the same email.
  • Files and temp dirs. Tests write to a fixed path.
  • Ports. Two tests start a server on the same port.
  • Globals and singletons. A cached config, a patched function that is never restored.
  • Environment variables. Set in one test, never unset.

Isolate by default

Give each test its own resources. Use temp directories and port 0, which makes the OS pick a free port.

import os

def test_writes_report(tmp_path):
    out = tmp_path / 'report.txt'
    write_report(out)
    assert out.exists()

def test_env(monkeypatch):
    monkeypatch.setenv('MODE', 'test')   # restored automatically

The tmp_path and monkeypatch fixtures clean up after the test. Other frameworks have the same idea: temp directory helpers and setup/teardown hooks.

Databases

The common pattern is to wrap each test in a transaction and roll it back. Another is to truncate tables after each test. Generate unique values for anything with a unique constraint.

import uuid

email = f'user-{uuid.uuid4().hex[:8]}@example.test'

If tests run in parallel, use one database per worker, named by worker id. To run a real database locally the same way as CI, see CI for multi-service apps.

A bisect example

Say test_report fails only in the full run. List the tests that ran before it, split the list in half and run each half followed by test_report. The half that still fails contains the leak. Repeat until one test remains. Many runners can print the order they used, which makes this mechanical rather than guesswork. Once you find the leaking test, look for what it creates and does not remove: rows, files, patches, threads or environment variables.

Fix the leak in the test that causes it, and also make the victim test create its own data, so one bad neighbor cannot hurt it again.

Keep order random in CI

Leave random order on permanently. It turns a hidden dependency into a visible failure the first time someone introduces it, with a seed in the log for replay. For the broader picture, see what causes flaky tests.

Questions people ask

Should I run tests in parallel to find these bugs?

Parallel runs expose shared state fast, but they also add noise. Random order on a single worker is the cleaner first step.

What is the cheapest isolation for database tests?

Wrap each test in a transaction and roll back at the end. It is fast and needs no cleanup code.
