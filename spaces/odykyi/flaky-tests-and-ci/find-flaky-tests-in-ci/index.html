How to Find Flaky Tests in CI Using Run History

Use the GitHub API and plain scripts to find tests and workflows that flip between pass and fail, then rank them so you fix the worst first.

To find flaky tests, look for the same commit or the same workflow flipping between pass and fail across runs. You do not need a paid tool: the GitHub CLI gives you run history, and test reports give you per-test results.

Start with workflow runs

Pull the last 100 runs of one workflow on the default branch. A workflow on the default branch should almost always be green, so a mixed history is a signal.

gh run list --workflow ci.yml --branch main --limit 100 \
  --json conclusion,headSha,createdAt \
  > runs.json

Count the flips: how many times did the conclusion change from success to failure or back, when ordered by time?

node -e '
const r=require("./runs.json").filter(x=>x.conclusion==="success"||x.conclusion==="failure")
  .sort((a,b)=>a.createdAt<b.createdAt?-1:1);
let f=0;for(let i=1;i<r.length;i++)if(r[i].conclusion!==r[i-1].conclusion)f++;
console.log("flips:",f,"of",r.length);
'

Same SHA, different result

The strongest proof is two runs on one commit with different outcomes. Group by headSha and look for groups that contain both a success and a failure. That means the code did not change and the result did.

Retried jobs count too. When someone reruns a failed job and it passes, the run has more than one attempt. That run is a flake candidate even if the final status is green.

Go down to the test level

Workflow history tells you which pipeline is noisy. To find the test, make your runner write a machine-readable report and upload it as an artifact.

pytest --junitxml=report.xml

- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: junit-${{ github.run_id }}
    path: report.xml

Download a batch of reports with gh run download and count failing test names across runs. Names that fail in some runs and pass in others are your flaky list.

Use a dashboard for the first look

If you want the workflow-level view without writing a script, Cilytics is a public CI health dashboard for GitHub. Open https://cilytics.flisk.si/?repo=owner/name and it shows flaky workflows, defined as flipping between pass and fail at least 3 times in the last 100 runs. Limits: it reads default-branch runs only, takes an hourly snapshot, and leaves out repos inactive for 90 days. It finds noisy workflows, not individual tests.

What to record

Whatever method you use, keep a small log with the date, the test or workflow name, the commit, the error text and the run link. Patterns appear quickly: the same error on the same step, failures clustered at certain hours when the runner pool is busy, or failures only on one operating system in the matrix. The error text is the most useful field, because identical messages across different commits usually mean one root cause.

Keep the log in an issue or a spreadsheet. The format matters less than the habit of writing every flake down instead of just clicking rerun.

Rank before you fix

Make a table: test or workflow, failures in the last 100 runs, minutes lost per failure. Multiply the last two. Fix the top three first. Then look at reproducing a flaky test locally.

Questions people ask

How many runs do I need to call something flaky?

Look at the last 50 to 100 runs on the default branch. A few flips in that window is enough to investigate.

Do pull request runs count?

They are noisier because code changes. Use default-branch runs or same-commit reruns for a clean signal.
