How to Stabilize Flaky End-to-End Tests With Playwright

Use auto-waiting locators, stable test data, traces on retry and a repeat loop to turn a flaky browser test into a reliable one. Honest limits included.

Stabilize a flaky Playwright test by using locators that wait for the element, asserting on visible outcomes instead of timing, resetting data before each test, and collecting a trace on the first retry so you can see what happened.

Use web-first assertions

Playwright assertions on locators retry until they pass or time out. Reading a value once does not.

// flaky: reads the text once
const text = await page.locator('#status').textContent();
expect(text).toBe('Saved');

// stable: retries until true
await expect(page.locator('#status')).toHaveText('Saved');

Avoid page.waitForTimeout except for debugging. Prefer locators by role or label, such as getByRole('button', { name: 'Save' }), over brittle CSS paths.

Wait for the network, not the clock

If a click triggers a request, wait for that response in the same step.

const [res] = await Promise.all([
  page.waitForResponse(r => r.url().includes('/api/save') && r.ok()),
  page.getByRole('button', { name: 'Save' }).click(),
]);

Start the wait before the click, as above, so you cannot miss a fast response.

Control the data

Most browser flakes are data flakes: a record another test changed, a seed that did not finish. Create the data the test needs through the API in a setup step and use a unique name per test. Do not rely on rows left by earlier tests. Mock third-party calls you do not own, using page.route, so a slow payment sandbox cannot fail your build.

Get a trace from CI

Set a trace to record when a test is retried. The trace shows each action, the DOM and the network.

// playwright.config.ts
export default {
  retries: process.env.CI ? 1 : 0,
  use: { trace: 'on-first-retry' },
};
npx playwright show-trace trace.zip

Upload the test-results folder as an artifact with if: always().

Parallel workers and shared accounts

Playwright runs test files in parallel by default. If every test logs in as the same user and edits the same record, tests collide. Give each worker its own account, or create a fresh user in a fixture. If a test truly needs exclusive access to a shared resource, mark that file to run serially and keep such files few. Also check that the app under test is warm before the run starts, for example by polling its health endpoint in a setup step, so the first test does not fail on a cold start.

Measure the fix and know the limit

Prove it: npx playwright test login.spec.ts --repeat-each=30. Also run with fewer CPUs and one worker. End-to-end tests are the slowest, most fragile layer. If a flow can be checked at the API or unit level, move it down, as covered in reproducing flakes locally, and keep only a few browser tests for the critical journeys.

Questions people ask

How many retries should end-to-end tests have?

One or two on CI, none locally. Use the retry report to find and fix the tests that need it.

Should I run browser tests against production?

Avoid it for blocking checks. A local or preview environment with controlled data fails less for reasons you do not own.
