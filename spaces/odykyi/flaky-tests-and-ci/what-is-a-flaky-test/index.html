What Is a Flaky Test and Why Does It Fail Randomly?

A flaky test passes and fails on the same code. Learn the five usual causes, how to tell flaky from broken, and why ignoring them costs more than fixing them.

A flaky test is a test that gives different results on the same code, with no change to the test or the code under test. It passes on one run and fails on the next. The cause is almost always something the test did not control: time, order, shared state, the network or a race.

Flaky versus broken

A broken test fails every time. You fix the code or the test and it goes green. A flaky test fails sometimes, so you cannot tell from one run whether your change caused it.

The quick check is to rerun the same commit. If a failed job goes green with no change, you have a flaky test or a flaky environment. If it fails again, it is probably real. Keep that rule in mind: one rerun is evidence, not proof.

The five usual causes

  1. Timing. The test sleeps for a fixed time, or asserts before an async job finishes.
  2. Shared state. Two tests use the same database row, file, port or global variable.
  3. Test order. A test only passes because another test ran before it.
  4. External services. The test calls a real network endpoint that is slow or down.
  5. Nondeterminism. Random values, the current date, hash ordering or unseeded generators.

Resource limits on the CI runner add a sixth: a test that is fine on your laptop times out on a busy shared machine.

What a flaky test looks like in the log

Common signs are a timeout with no useful message, an assertion on a list whose order changed, or a port already in use. The error often differs from run to run. That is a hint by itself: real bugs usually fail the same way every time.

FAIL tests/test_jobs.py::test_job_finishes
E   assert job.status == 'done'
E   AssertionError: 'running' != 'done'

This one asserts a status after a fixed wait. On a fast machine the job is done. On a slow runner it is not.

Why not just rerun

Rerunning makes the red go away, so it feels cheap. The cost shows up elsewhere. Every rerun adds minutes to the pipeline, and developers learn to ignore red builds. Then a real failure gets rerun too, and a bug ships. See how to rerun failed tests without hiding them for a safe way to use retries.

A quick example

Imagine a test that creates a user, then lists all users and expects exactly one. On your machine it passes. In CI another test has already created a user in the same database, so the list has two. The test did not change and neither did the code, yet the result did. That is a flake caused by shared state.

Now imagine a test that starts a server and immediately sends a request. On a fast machine the server is ready. On a busy runner it is not. That one is a flake caused by timing. Both look random from the outside and both have a deterministic cause once you find it.

What to do first

Do not start by fixing. Start by counting. Write down which tests failed and passed on the same commit, then rank by how often. A handful of tests usually cause most of the noise. The next article covers how to find flaky tests in CI.

Questions people ask

Can a flaky test be a real bug?

Yes. Race conditions in production code often show up first as flaky tests. If the failure is a genuine race in the code under test, fix the code, not the test.

How many reruns prove a test is flaky?

One green rerun on the same commit is a strong sign. To measure how flaky it is, run it many times in a loop and count failures.
