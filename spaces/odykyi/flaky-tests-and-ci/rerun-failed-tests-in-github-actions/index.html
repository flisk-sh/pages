Retry Failed Tests in GitHub Actions Without Hiding Bugs

Rerun failed jobs and retry single tests safely: gh run rerun, test-runner retries, and how to record every retry so flakes stay visible.

You can rerun only the failed jobs of a run with gh run rerun --failed, or retry single tests inside the test runner. Both are useful as a bridge, but a retry that passes must still be counted as a flake, or the problem grows silently.

Rerun failed jobs

In the GitHub UI, choose "Re-run failed jobs". From a terminal:

gh run rerun 1234567890 --failed
gh run view 1234567890 --json attempt,conclusion

The run keeps one id but gets a higher attempt number. That number is your signal: a green run with attempt 2 is a flake that was forgiven.

Retry inside the test runner

Runners can retry a single failing test, which is cheaper than rerunning a whole job.

# pytest (pip install pytest-rerunfailures)
pytest --reruns 2 --reruns-delay 1

// Playwright config
export default { retries: process.env.CI ? 2 : 0 };

// Jest
jest.retryTimes(2);

Keep retries low, one or two. A test that needs five tries is not flaky, it is broken. Do not set retries locally, so you still see flakes while you develop.

Make retries visible

The danger is a suite that is always green because everything is retried. Playwright marks tests that passed on retry as flaky in its report. For pytest, the rerun plugin lists reruns in the summary. Either way, write the list somewhere people see it.

- name: Report flaky tests
  if: always()
  run: |
    echo '### Retried tests' >> "$GITHUB_STEP_SUMMARY"
    grep -i 'rerun\|flaky' test.log >> "$GITHUB_STEP_SUMMARY" || true

GITHUB_STEP_SUMMARY shows Markdown on the run page.

Do not retry whole workflows blindly

Some teams add a retry action around the test step or a bash loop. That works, but it hides the failure from the run history, so your pass rate looks better than the truth. Prefer the runner-level retry, which logs which test retried.

  • Retry tests, not builds or deploys.
  • Never retry steps that are not idempotent.
  • Set timeout-minutes so a hung retry does not eat the budget.

Count your retries

You can see how often retries save you by listing runs and checking the attempt number. Run gh run list --json databaseId,attempt,conclusion --limit 100 and count runs where attempt is above 1 and the conclusion is success. If that count is more than a few per week on the default branch, your pipeline depends on retries to look healthy.

Put that count next to your pass rate. A pass rate of 99 percent with retries on is a different story from 99 percent without them.

Retries are a bridge

Treat a retry as a ticket: it buys time until the fix lands. Pair it with a quarantine list and a deadline. See also the team policy for who owns each one.

Questions people ask

Does gh run rerun --failed rerun passing jobs?

No. It reruns the failed jobs and the jobs that depend on them, and reuses the results of jobs that passed.

Should CI auto-retry on every failure?

No. Retry single tests with a low limit and record each retry. Auto-retrying everything hides real regressions.
