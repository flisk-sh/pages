Flaky Workflows vs Flaky Tests: How to Tell Them Apart

Some CI failures are not test bugs but runner, network, cache or dependency problems. Learn how to classify a failure and what to fix in each case.

A flaky test fails because of its own logic. A flaky workflow fails because of its environment: a package registry timeout, a full disk, a cache miss or a rate limit. Classify the failure first, because the fixes are different.

Read where it failed

Open the failed step. If the failing step is a test and the assertion is about your code, it is a test flake. If the failing step is checkout, npm ci, docker pull, or a download, it is a workflow flake. The error text usually says it: ETIMEDOUT, 503, rate limit exceeded, no space left on device.

Common environment flakes and fixes

SymptomLikely causeFix
Timeout on installRegistry or network blipCache dependencies, retry the install step
Rate limit on image pullAnonymous registry pullsLog in to the registry, use a mirror
No space left on deviceLarge builds on a small diskClean up, trim images, split jobs
Out of memory, killedParallel workers too highLower worker count
Job cancelledConcurrency or timeout settingCheck concurrency and timeout-minutes

Retry the right things

Network steps are safe to retry because they are idempotent. A plain shell loop is enough.

- name: Install
  run: |
    for i in 1 2 3; do
      npm ci && exit 0
      echo "attempt $i failed"; sleep 5
    done
    exit 1

Do this for installs and downloads only. Never wrap the test step this way, since it would hide real failures, as explained in retry failed tests safely.

Measure at the workflow level

Test reports will not show an install failure. Workflow run history will. Cilytics lists flaky workflows (at least 3 flips between pass and fail in the last 100 default-branch runs) and red workflows, where the newest default-branch run failed, for a whole org or for one public repo with ?repo=owner/name. It is an hourly snapshot, not live, so use gh run list for the latest run.

Disk, memory and concurrency

Two causes get missed because the log message is vague. A job killed for memory often ends with a bare exit code 137 and no stack trace. Lower the worker count or split the heavy step into its own job. Disk problems show as write errors in the middle of a build; check df -h at the start and end of the job and remove what you do not need. Finally, if jobs are cancelled with no error, check whether a newer push triggered a concurrency cancel, which is working as designed.

Pin what you can

Pin action versions and base images so an upstream change does not break you without a commit on your side. Use a lockfile and npm ci, not npm install. For problems inside the runner, see debugging CI failures.

Questions people ask

Can a runner be flaky itself?

Yes. Shared runners vary in load and speed, so timing-sensitive tests that pass elsewhere can fail there. Loosen the timing in the test rather than blaming the runner.

Should I retry the whole job on network errors?

Retry the network step only. Rerunning the whole job wastes minutes and hides the pattern.

Check which of your workflows flip between pass and fail.
