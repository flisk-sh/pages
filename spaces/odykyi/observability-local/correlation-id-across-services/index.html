Correlation IDs across services in Node.js

A shared request ID lets you follow one request through every service that touched it.

Give every incoming request an ID, put that ID in every log line, and send it on in a header whenever your service calls another service. Then one search for that ID shows what each service did for that request. The common header name is x-request-id. You need about thirty lines of code and no tracing backend.

The problem it solves

A checkout request enters web, which calls orders, which calls inventory and payments. Something returns a 500. Each service has its own log with its own timestamps, and under load the lines from many requests interleave. Matching them by time and guessing is slow and wrong half the time. A shared ID turns it into a plain text search.

The rule has three parts: accept an ID if the caller sent one, create one if not, and pass it on. The first service in the chain creates it, and everyone after that reuses it.

Middleware that sets and reads the ID

In Node.js, AsyncLocalStorage keeps a value for the lifetime of one request without passing it through every function:

// request-context.js
const { AsyncLocalStorage } = require("node:async_hooks");
const { randomUUID } = require("node:crypto");

const store = new AsyncLocalStorage();

function requestId(req, res, next) {
  const id = req.get("x-request-id") || randomUUID();
  res.set("x-request-id", id);          // hand it back to the caller too
  store.run({ id }, next);
}

const currentId = () => store.getStore()?.id;

module.exports = { requestId, currentId };

Mount it first in an Express app with app.use(requestId). Now add the ID to every log line. With pino the mixin option runs on each call:

const pino = require("pino");
const { currentId } = require("./request-context");

module.exports = pino({
  mixin: () => ({ requestId: currentId() }),
});

Every log.info(...) in a request now has a requestId field, including logs written deep inside helper functions. See structured JSON logs in Node.js for the logger setup.

Pass it on to the next service

This is the step people forget. Wrap outgoing calls so the header is always set:

const { currentId } = require("./request-context");

function callService(url, init = {}) {
  return fetch(url, {
    ...init,
    headers: { ...init.headers, "x-request-id": currentId() },
  });
}

Python has the same idea in contextvars: set a ContextVar in a middleware, read it in a logging filter, and add the header in your HTTP client wrapper. Go uses context.Context. Whatever the language, the three parts do not change.

Run it and find one request

With Flisk, two services that call each other are two service.json files. The caller gets the callee's address through env, and dependsOn starts the callee first:

{
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["inventory"],
  "env": { "INVENTORY_URL": "http://localhost:4001" }
}

This is the local process form: flisk up starts each command and prefixes every output line with the service name. Send one request with a known ID, then search for it:

curl -H "x-request-id: demo-123" http://localhost:4000/orders/42
flisk logs --since 2m | grep demo-123

You get the lines from orders and inventory together, in time order, each prefixed with its service. That merged, time-ordered view is the part Flisk adds; the ID itself is your code. If you run services as containers, the same flisk logs call reads them through Tilt. See reading logs from every service for the other options.

Pitfalls

  • Trusting a client's ID. At the public edge, anyone can send any x-request-id, including very long strings or text meant to confuse log searches. Limit the length and characters you accept, or always generate a new one at the edge and keep the client's value in a separate field.
  • Background jobs. A job pulled from a queue runs outside any request. Put the ID in the job payload when you enqueue, and restore it when the worker starts the job, otherwise the trail stops at the queue.
  • Logs without the field. Libraries that write their own lines will not carry the ID unless they use your logger. A search for the ID then misses them. Check by grepping a request you know touched them.
  • Not a trace. A correlation ID tells you which lines belong together. It does not tell you the parent and child relationship or how long each step took.

When to move to traces

If you need timing per step and the call tree, use distributed tracing. The W3C traceparent header plays the same role as x-request-id but is understood by tracing libraries, which add the timing for you. The trace ID can also be added to your log lines, so the two approaches work together. The next guide, sending OpenTelemetry traces from Node.js to Jaeger, sets that up on your laptop.

Questions people ask

What is a correlation ID?

A unique value attached to a request when it first enters your system and passed along to every service it calls, so every log line about that request carries the same value.

Why AsyncLocalStorage?

It keeps the ID available anywhere in the request's async call chain without passing it through every function argument.

Is this the same as a trace ID?

It does the same job in a simpler form. OpenTelemetry trace IDs are the standard version and add timing and span structure.
