Structured JSON logs in Node.js with pino

One JSON object per line turns logs from text you scroll into data you can search.

Replace console.log with a logger that writes one JSON object per line. In Node.js that is usually pino. Every line then carries named fields (level, time, message, and your own such as orderId), so you can filter with jq today and send the same lines to a log store later without writing a single regular expression.

Why one JSON object per line

A line like created order 42 for user 7 in 183ms is easy to read and hard to query. To find slow orders you must parse the sentence, and the parser breaks the day someone rewords the message. A JSON line keeps the message and the data apart:

{"level":"info","time":"2026-11-14T10:00:00.000Z","service":"orders-api","msg":"order created","orderId":42,"userId":7,"ms":183}

Now "all orders slower than 500 ms" is a field comparison. The format is also what almost every log tool expects, from jq to Loki, Elasticsearch and cloud log services. The cost is that raw JSON is harder to read by eye, which the section on terminal output below deals with.

Set up pino

npm install pino

Create one logger module and import it everywhere:

// logger.js
const pino = require("pino");

module.exports = pino({
  level: process.env.LOG_LEVEL || "info",
  base: { service: process.env.OTEL_SERVICE_NAME || "orders-api" },
  formatters: {
    // pino logs the level as a number by default; a label is easier to filter
    level: (label) => ({ level: label }),
  },
  timestamp: pino.stdTimeFunctions.isoTime,
});

Then log an event with an object first and a short message second:

const log = require("./logger");

log.info({ orderId: 42, userId: 7, ms: 183 }, "order created");
log.error({ err, orderId: 42 }, "payment failed");

Put the changing data in the object, not in the message string. The message stays a constant phrase you can count and group by. Pass errors under the err key: pino serialises the message and stack for you.

Choose levels you will actually use

Pino has trace, debug, info, warn, error and fatal. A workable rule for a service you run locally:

  • error: a request or job failed and someone should look.
  • warn: something odd that was handled, such as a retry.
  • info: one line per request or job outcome, and startup and shutdown.
  • debug: details you want while building a feature. Off by default, on with LOG_LEVEL=debug.

Reading the level from an environment variable lets you turn on debug for one service without a code change.

Readable output in your terminal

For a human, pipe the stream through pino-pretty only when you run the service by hand:

node server.js | npx pino-pretty

Keep the service itself writing JSON, so the output you debug locally has the same shape as the output you would collect elsewhere. To filter lines, jq is enough:

node server.js | jq -c 'select(.level == "error")'

Where Flisk fits

Flisk does not add a logger, and it does not parse or index your logs. What it does is collect each service's stdout, so structured lines from several services end up in one place. For a stack started with flisk up, flisk logs prints a bounded snapshot of recent lines, merged across services and prefixed with the service name:

flisk logs --service orders-api --since 5m

With --json the output is one object, and each line has time, resource, level, source and text fields. Your own JSON line arrives as the text string, so to filter on your fields, unwrap it with jq:

flisk logs --json --since 5m | jq -r '.data.lines[].text' | jq -R -c 'fromjson? | select(.level == "error")'

The -R and fromjson? parts skip any line that is not JSON, such as a framework banner printed at startup. flisk logs is a snapshot, not a live stream: for a live view of a Docker stack use the log pane of the Tilt dashboard, and for local processes the prefixed output of flisk up itself. The guide on reading logs from every service covers the plain options.

Pitfalls

  • Do not log secrets or whole request bodies. Structured logging makes it easy to dump an object, and easy to leak a token. Log ids and sizes, and see keeping secrets out of logs.
  • Do not use dynamic keys. { ["user_" + id]: true } creates a new field per user and makes the logs unsearchable. Use { userId: id }.
  • Log to stdout. Writing to a file inside a container disappears with the container. Stdout is what Docker, Tilt and Flisk collect.
  • Synchronous logging in hot paths. Pino is fast, but formatting a huge object per request still costs. Keep the object small.

Once each service logs JSON, the next problem is following one request across several of them. A correlation ID solves that with a few lines of middleware.

Questions people ask

Why use JSON logs instead of plain text?

Each line becomes a record with named fields such as level, time and a request ID, so you can filter with jq or a log tool instead of guessing with grep.

Should I use pino-pretty in production?

No. Use it only as a development viewer by piping the output through it. Production should keep raw JSON lines.

Does Flisk parse the JSON?

No. flisk logs shows the lines your services write to stdout. You parse them yourself, for example with jq.
