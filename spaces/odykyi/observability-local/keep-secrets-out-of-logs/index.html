Keep secrets out of local logs

Most leaks come from logging whole objects. Allow-list fields and redact the rest.

Stop secrets at the source: never log whole request objects, headers, config or environment dumps, and add a redaction rule to your logger for the fields that remain risky (authorization headers, cookies, passwords, tokens). Treat any log file as something that will be pasted into a chat, an issue or a bug report, because it will be.

How secrets end up in logs

Almost nobody writes log.info(apiKey). The leaks are indirect:

  • Logging a whole request, response or error object. HTTP clients often attach the full request, including the Authorization header, to the error they throw.
  • Printing the configuration at startup to "see what the service got". That prints database passwords and API keys together.
  • Connection strings in error messages, such as postgres://user:password@host/db.
  • Debug logging left on, which logs request bodies, including login forms.
  • Stack traces from a library that includes its arguments.

Local logs feel harmless, since the keys are development keys. But development logs get shared, and a habit formed on your laptop carries to production. Some "development" keys are also real keys to a real third-party account.

Redact in the logger

Most structured loggers can censor named fields before they are written. In pino:

const pino = require("pino");

module.exports = pino({
  redact: {
    paths: [
      "req.headers.authorization",
      "req.headers.cookie",
      "res.headers['set-cookie']",
      "*.password",
      "*.token",
      "config.databaseUrl",
    ],
    censor: "[redacted]",
  },
});

A path names a field by where it sits in the logged object; * matches one level of any key. This is a safety net, not a substitute for care. It only catches names you listed, so a new field called apiSecret passes straight through. Allow-list instead where you can: log the fields you chose, not the whole object. Structured JSON logs in Node.js shows the logger setup this builds on.

In Python, use a logging.Filter that rewrites records, or a structured logger such as structlog with a processor that drops keys. The shape is the same: a list of names, applied in one place.

Keep the secrets out of the repository, too

Redaction is the second line of defence. The first is that a secret lives in one place, outside git, and reaches the process through the environment. Flisk's service files support that: env values may refer to ${VAR}, which it fills from your shell or the git-ignored project .env, and secrets.required names variables that must exist:

{
  "schemaVersion": 1,
  "appName": "payments",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "env": { "STRIPE_API_KEY": "${STRIPE_API_KEY}" },
  "secrets": { "required": ["STRIPE_API_KEY"] }
}

Only the name is in service.json, so the file is safe to commit. The guide on keeping env var names, not values, in config goes further. A key that is only needed for local development, such as an auth signing secret, can be generated: secrets.generate with a value like "hex:32" makes Flisk append a random value to the project .env the first time you run flisk up, and it prints the names, never the values.

What Flisk does with secrets in log output

Flisk's changelog and assurance notes say flisk logs replaces any value from the project .env that is 8 characters or longer with [REDACTED] before it prints, and that flisk doctor --json and error messages do the same. This is useful when you copy a snapshot into an issue:

flisk logs --service payments --since 10m

Know the limits. The check is an exact match of the value as it appears in .env. A value that your code transforms (base64, URL-encoded, split in two) will not match. Values shorter than 8 characters are not touched. A secret that is in your shell but not in the .env file is not known to it. And it applies to what flisk logs prints: the log files themselves, such as .flisk/native/logs/<service>.log for local processes, and the Docker or Tilt logs are written as your service produced them. Think of it as a safety net for sharing, not for storage.

Check what you already log

Run the service, exercise the login and payment paths, and search the output for the secrets you use:

flisk logs --since 10m | grep -i -E "authorization|bearer|password|token"

Because flisk logs already masks values from .env, a match here means the secret is leaking in a form it did not recognise, or the word appears in a header name only. Read the lines. If you do not use Flisk, run the same grep over your service output. For credentials that were already pasted somewhere, rotate them; deleting the log line does not undo a leak.

Pitfalls

  • Debug logs in shared environments. Keep LOG_LEVEL=debug out of anything that other people can read.
  • Redacting after the fact. Scrubbing a log file later is unreliable. Prevent the write.
  • Trace attributes. If you add OpenTelemetry attributes from request data, the same rules apply: they are stored in the tracing backend.
  • Errors from libraries. Wrap them and log the code and message, not the whole error object, when the library is known to attach its inputs.

For ways to share logs safely with teammates and tools, see reading logs from every service.

Questions people ask

Does flisk logs hide secrets?

It replaces values from the project .env that are 8 characters or longer with [REDACTED]. It matches exact values only.

Is redaction enough?

No. It only catches field names you listed. Avoid logging whole request or config objects.

What if a secret already leaked into a log?

Rotate the credential. Removing the log line does not undo exposure.
