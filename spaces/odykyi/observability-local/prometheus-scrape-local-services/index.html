Scrape local services with Prometheus

The address inside the container is the usual reason a local target stays down.

Run Prometheus in a container with a prometheus.yml that lists each service's /metrics address under static_configs. The one thing that trips people up is the address: a container cannot reach your laptop's services at localhost. Use host.docker.internal:PORT for services running on the host, or the service name when the service is also a container on the same Docker network.

How scraping works

Prometheus pulls. Every scrape_interval it requests the metrics path of each target and stores the numbers with a timestamp. A target that does not answer is marked down, and that state is itself a metric (up), which makes "is my service reachable" the first thing you can see. Your services only need to serve /metrics; see exposing Prometheus metrics from a Node.js service for that side.

The configuration file

# prometheus.yml
global:
  scrape_interval: 5s

scrape_configs:
  - job_name: orders
    metrics_path: /metrics
    static_configs:
      - targets: ["host.docker.internal:4000"]
        labels:
          service: orders

  - job_name: inventory
    static_configs:
      - targets: ["host.docker.internal:4001"]
        labels:
          service: inventory

Five seconds is shorter than a production setting and suits local work, since you want a graph to move soon after you click something. host.docker.internal is a name that Docker Desktop resolves to the host. Check it on your setup: run docker run --rm curlimages/curl -s http://host.docker.internal:4000/health while a service is up. On Linux the name does not exist by default, and you add it with --add-host=host.docker.internal:host-gateway on the container. Colima and Podman have their own behaviour, so test rather than assume.

Run Prometheus with Flisk

Like other images, Prometheus is a bring-your-own resource. Its config is a bind mount and its data is a named volume:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "prometheus",
  "appType": "bring-your-own",
  "stack": "obs",
  "port": 9090,
  "healthCheckPath": "/-/healthy",
  "image": "prom/prometheus:v3.2.1",
  "volumes": [
    { "source": "./prometheus.yml", "target": "/etc/prometheus/prometheus.yml", "readOnly": true },
    { "source": "prometheus-data", "target": "/prometheus" }
  ]
}

Place prometheus.yml next to this service.json. The ./ path is relative to that folder, and Flisk requires it to stay inside the project. /-/healthy is Prometheus's own health endpoint, so services that depend on it wait until it answers. The prometheus-data volume keeps history across flisk down. Pin the image tag to a current one. flisk config verify accepts this file.

With your own services as local processes (a command in their service.json) and Prometheus as an image, Flisk starts them together as a mixed run, as described in its documentation on running without Docker. Prometheus is then at http://localhost:9090. Open http://localhost:9090/targets and check that each target shows UP. Flisk's mixed-run documentation does not list a way to add host entries to the container, so on Linux either run Prometheus yourself with --add-host, or run your services as containers.

When services are containers on the Flisk Docker and Tilt path, they share a Docker network with Prometheus, and the target is the resource name and the port the container listens on, such as orders:4000. No host.docker.internal is needed there. See running microservices locally for how the two modes differ.

Check that metrics arrive

  1. Open http://localhost:9090/targets. A red target shows the error, such as "connection refused" or "context deadline exceeded".
  2. In the Graph tab, run up. A value of 1 per target means the last scrape worked.
  3. Run rate(http_request_duration_seconds_count[1m]) while you click around your app. The number should rise.

After you edit prometheus.yml, restart the container so it re-reads the file. Prometheus can also reload on request, but only when started with --web.enable-lifecycle.

Pitfalls

  • Using localhost in the target. Inside the container that means the container itself. It is the most common cause of a target that stays down.
  • A service that listens on 127.0.0.1 only. Traffic from a container arrives through Docker's network, not loopback. Most Docker setups still reach a host service bound to 127.0.0.1, but if a target is refused while curl from the host works, try binding the service to 0.0.0.0 for local work.
  • Ports that change. Prometheus reads a fixed target list. If your services pick a free port at random, the list is stale. Give each service a fixed port.
  • Disk growth. Retention defaults to 15 days. For a laptop, add --storage.tsdb.retention.time=2d, or remove the volume when you want a clean start. In service.json the arguments go in container.command, which replaces the image's default arguments, so repeat --config.file=/etc/prometheus/prometheus.yml and --storage.tsdb.path=/prometheus in the list too.

Graphs are easier to read in Grafana. The single container with Grafana, Loki, Tempo and Prometheus gives you a ready set of data sources if you would rather not wire them yourself.

Questions people ask

Why is my Prometheus target down?

Usually the target uses localhost, which inside the container means the container itself. Use host.docker.internal or the service name.

Does host.docker.internal work on Linux?

Not by default. Add --add-host=host.docker.internal:host-gateway to the container.

How do I reload prometheus.yml?

Restart the container, or start Prometheus with --web.enable-lifecycle and request a reload.
