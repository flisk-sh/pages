OpenTelemetry traces for Node.js with Jaeger

Add tracing to a Node.js service in one file and read the spans in Jaeger.

Install the OpenTelemetry Node SDK, load a small tracing.js before your app code, point the exporter at http://localhost:4318, and run Jaeger in a container that publishes the OTLP port and the UI on 16686. A request that crosses two services then shows up as one trace with a bar per step. This works on a laptop with no cloud account.

What you are setting up

Three parts talk to each other. Your service creates spans (one per incoming request, outgoing call or database query). The OpenTelemetry SDK batches them and sends them over OTLP, which is plain HTTP on port 4318 or gRPC on 4317. Jaeger receives them, stores them in memory, and shows them in a web UI. Jaeger's current image, jaegertracing/jaeger, accepts OTLP directly, so you do not need a collector between the two for local work. If you want one, read how to run an OpenTelemetry Collector locally.

Add tracing to the service

npm install @opentelemetry/sdk-node \
  @opentelemetry/auto-instrumentations-node \
  @opentelemetry/exporter-trace-otlp-http
// tracing.js
const { NodeSDK } = require("@opentelemetry/sdk-node");
const { getNodeAutoInstrumentations } = require("@opentelemetry/auto-instrumentations-node");
const { OTLPTraceExporter } = require("@opentelemetry/exporter-trace-otlp-http");

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter(),   // reads the endpoint from the environment
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
process.on("SIGTERM", () => sdk.shutdown().finally(() => process.exit(0)));

The file must run before anything else imports http, express or your database driver, because instrumentation works by patching those modules as they load. Start the app with:

node --require ./tracing.js server.js

Configuration comes from the standard OpenTelemetry environment variables, so the code does not change between machines:

OTEL_SERVICE_NAME=orders
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_BSP_SCHEDULE_DELAY=1000

The exporter adds /v1/traces to the endpoint itself. OTEL_BSP_SCHEDULE_DELAY lowers the batch delay from its default of five seconds so spans appear quickly while you experiment.

Run Jaeger with Flisk

Jaeger is an image you start, not code you write, so it is a bring-your-own resource. Create it with the CLI, then set the ports by hand, because the generator picks a port in the 4000 to 5999 range and Jaeger's UI is on 16686:

npm install -g @flisk-sh/flisk
flisk resource jaeger --type bring-your-own --image jaegertracing/jaeger:2.5.0 --stack obs --yes

Edit the generated service.json. Pin a current 2.x tag from Docker Hub rather than trusting the one shown here:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "jaeger",
  "appType": "bring-your-own",
  "stack": "obs",
  "port": 16686,
  "image": "jaegertracing/jaeger:2.5.0",
  "extraPorts": [{ "port": 4317 }, { "port": 4318 }]
}

port is the UI. extraPorts publishes the two OTLP ports on 127.0.0.1 only, so nothing else on your network can send data to it. Then add the environment to your own service and make it wait for Jaeger:

{
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "command": "node --require ./tracing.js server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["jaeger"],
  "env": {
    "OTEL_SERVICE_NAME": "orders",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://localhost:4318",
    "OTEL_BSP_SCHEDULE_DELAY": "1000"
  }
}

Flisk's documentation describes this as a mixed run: your code runs as local processes, the image runs with docker run next to it, and a local process reaches the container at localhost. Docker must be running for it. Start with flisk up, send a few requests, and open http://localhost:16686. To check what the process really received, run flisk run orders -- printenv OTEL_EXPORTER_OTLP_ENDPOINT.

If you run your services as containers on the Docker and Tilt path instead, they are on a Docker network with Jaeger, and the endpoint becomes http://jaeger:4318 (the resource name), not localhost. That is the most common reason for "no traces" after a switch.

Read the trace

In the Jaeger UI pick the orders service and press Find Traces. Open one: each bar is a span, nested by caller, with its duration. When orders calls another traced service over HTTP, the SDK sends a traceparent header and the second service's spans join the same trace. Look for the longest bar first, and for a database query repeated many times in a row, which is the usual sign of an N+1 problem.

Pitfalls

  • No spans at all. Check that tracing.js loads first, that the service name is set, and that port 4318 answers: curl -i http://localhost:4318/v1/traces should return a 405 or similar, not a refused connection.
  • Too many spans. The auto-instrumentation bundle patches many libraries, including the file system. Recent versions let you pick: OTEL_NODE_ENABLED_INSTRUMENTATIONS=http,express,pg.
  • Traces vanish on restart. Jaeger keeps traces in memory by default. That is fine for debugging a request, and wrong for comparing yesterday with today.
  • Watch mode. If you use node --watch, keep --require ./tracing.js in the command so every restart reloads it.
  • Not for production as set up here. The in-memory store, the sampling at 100 percent and the open local ports are for development.

Services written in Python can send to the same Jaeger. Adding OpenTelemetry tracing to a FastAPI service shows the equivalent steps.

Questions people ask

Which port does a Node.js service send OTLP traces to?

OTLP over HTTP uses port 4318 and OTLP over gRPC uses 4317. The Node HTTP exporter normally targets 4318.

Why do I see no traces in Jaeger?

Common causes are a wrong endpoint, tracing.js loaded after the app instead of with --require, or the service exiting before the exporter flushes.

Does Flisk provide tracing?

No. Flisk runs Jaeger as a bring-your-own image resource and starts your service next to it.
