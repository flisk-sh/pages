How to run a frontend and an API together locally

Two processes, two ports, one browser. The usual failures are a wrong API URL and a CORS error. Here is how to avoid both.

To run a frontend and an API together, start the API first, give the frontend the API's base URL through an environment variable, and either allow the frontend's origin in the API's CORS settings or put a proxy in front of both. Most "it works on my machine" failures here come from a hard-coded URL or a missing CORS header.

Why the browser complains

A page served from http://localhost:3000 and an API at http://localhost:4000 are different origins, because the port is part of the origin. The browser sends the request, but it only hands the response to your code if the API answers with an Access-Control-Allow-Origin header that matches. For requests with JSON bodies or custom headers, the browser first sends an OPTIONS preflight request, and the API has to answer that too.

Three ways to connect them

  1. Direct call with CORS. The frontend reads an API base URL from an environment variable (VITE_API_URL in a Vite app) and calls it. The API allows the frontend's origin. This matches production most closely.
  2. Dev-server proxy. The frontend dev server forwards /api to the API, so the browser only talks to one origin. In Vite this is server.proxy in vite.config.ts. It removes CORS locally, but production then needs a real reverse proxy that does the same.
  3. One gateway in front of both. A local reverse proxy routes by host or path. This is what the container setup in Flisk does.

Whichever you pick, do not write the API address into component code. One variable, read in one place, is easy to change.

The Flisk way, without Docker

When both services declare a command, Flisk starts them as local processes. Put the API address in the frontend's env and use dependsOn so the API is ready first:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "VITE_API_URL": "http://localhost:4000" }
}

Flisk does not generate a frontend environment file in this mode. You pass the URL yourself, and you allow http://localhost:3000 in the API's CORS settings. If you scaffold the frontend with flisk resource web --type frontend --path web --local --stack app, you get a plain Vite config and "command": "npm run dev", with no Docker files.

flisk up then prints http://localhost:4000 and http://localhost:3000 once both answer.

The Flisk way, with Docker and Tilt

In the container setup, Flisk puts Traefik in front of everything. The frontend runs at http://app.<project>.localhost/<name> and a backend at http://api.<project>.localhost/api/<name>, where the name is the service name without a trailing -api. Backend ports are not published on your machine, so localhost:4000 will not work from the browser here.

For each frontend, Flisk writes the backend's route into VITE_API_URL (and NEXT_PUBLIC_API_URL for Next.js). It takes the backend from backendName, or from the first backend in dependsOn. A backend scaffolded by flisk resource allows browser origins on *.localhost subdomains. Create the pair like this:

flisk resource api --type backend --stack shop --yes
flisk resource web --type frontend --stack shop --yes
flisk up shop

The scaffolded frontend lists the API in dependsOn and sets backendName. Run flisk networks to see the exact URLs.

What to check when it still fails

  • Open the API URL directly in the browser. A 404, 502 or 503 means the route is not up yet, not that CORS is wrong.
  • Read the browser console. A CORS message names the origin that was refused. Allow exactly that origin.
  • If you changed dependsOn, backendName or the HTTP port, restart the frontend with flisk restart web. The value is baked in when the container starts.
  • If you wrote your own API (a bring-your-own service), it must allow http://app.<project>.localhost itself. Flisk only configures CORS in code it scaffolds.
A dev proxy hides CORS problems that will appear in production. If production serves the frontend and API from different origins, test with a direct call at least once.

A quick way to tell the causes apart is the browser network tab. A request that is blocked with a CORS message means the server did not allow your origin. A request that reaches a server and returns 404 or 502 is a routing or port problem. A request that hangs usually means the backend is down or still starting. Fixing the right layer first saves the hour you would spend changing CORS settings that were never the problem. If the API address in the browser looks old, see environment variable not loaded.

Next, use *.localhost URLs instead of port numbers so the addresses stop changing, or read hot reload across services to make the edit loop fast.

Questions people ask

Why does my frontend get a CORS error from my local API?

The page and the API have different origins (different port or host), so the browser blocks the response unless the API sends an Access-Control-Allow-Origin header that names the page's origin. Allow the frontend's exact origin in the API in development.

Should the frontend call the API directly or through a proxy?

Both work. A dev-server proxy keeps the browser on one origin and removes CORS, but the production setup then differs. Calling the API directly with a configurable base URL matches production more closely.

Can I hard-code localhost:4000 in the frontend?

You can, but it breaks as soon as the port changes or the app runs in a container. Read the API base URL from an environment variable.
