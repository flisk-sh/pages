Run microservices on your laptop

Local development without Kubernetes (minikube, kind, k3d)

A local cluster is a good way to test Kubernetes. It is a heavy way to write an API. Pick the lightest tool that answers your question.

You do not need Kubernetes to develop microservices on your laptop. If your task is writing code, run the services as plain processes or containers and keep a cluster for the days you are changing Kubernetes itself. A local cluster adds memory use, startup time and a layer of YAML between you and your code, so use it when it answers a question nothing lighter can.

What each option is for

ToolGood forCost
minikube, kind, k3dTesting manifests, Helm charts, operators, ingress, probesA cluster to run, images to load into it, YAML to keep in sync
Docker ComposeSeveral containers with a database, on one machineA container build for each change unless you add syncing
Plain processesFast edit and run loops for code you writeYou manage ports, order and logs yourself, or use a runner
FliskProcesses or Compose-style containers with order, health checks and URLsA service.json per service

The three local cluster tools differ in packaging. kind runs cluster nodes as Docker containers and is popular in CI. k3d runs k3s, a small distribution, in Docker. minikube runs a single-node cluster in a VM or container. For this question they behave alike: you get a real Kubernetes API, and you pay for it.

The case for a cluster

Run one when the behavior you care about is only visible there:

  • You write or change Helm charts, Kustomize overlays or raw manifests.
  • You depend on cluster features: operators, custom resources, network policies, RBAC.
  • You need to see how liveness and readiness probes or resource limits behave.
  • Your team ships through Kubernetes and a bug only shows up there.

Even then, you can write the application code outside the cluster and bring it in for the final check.

The case against, for day-to-day work

For everyday changes, a cluster slows the loop. A code change usually means building an image, loading it and rolling a deployment, unless you add a sync tool on top. Memory goes to the control plane. When something fails, you debug the cluster first and your code second. Many teams settle on this split: develop against plain processes or Compose, and run a cluster in CI or on a shared environment for the last mile.

The Flisk way without Kubernetes

Flisk is a local development tool. Its default path runs services as local processes: each service declares a command and a port, and Flisk starts them in order, waits for health and restarts a crashed one with backoff.

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

Run flisk up. No Docker and no cluster are involved. A service that cannot run as a plain process, such as a database, can run from an image with docker run next to the processes. If you want containers for everything, Flisk's container path uses Docker, Tilt and a Traefik gateway, which gives you URLs like api.<project>.localhost.

What Flisk does not do matters here. It has no Kubernetes API, does not emit Kubernetes manifests by default and does not replace Helm, Kustomize, Flux or Argo. It is for the inner loop. For the hand-off, flisk export can write a render.yaml, a wrangler.toml or a standalone docker-compose.yml from your service.json files. Those are files only; nothing is deployed.

Pitfalls

  • Dev and production drift. Running without a cluster means differences in networking, config and limits. Keep a cluster stage in CI so these surface before release.
  • Service discovery. In a cluster, services reach each other by DNS name. Locally they use ports or *.localhost URLs. Read addresses from environment variables, not constants.
  • Secrets. Use development-only values locally, never production ones.
If you are unsure, start with processes. Add a cluster the first time you hit a question that needs one.

There is a middle path worth naming. Some teams keep one shared development cluster for integration checks and let each developer run their own service locally against it, or against local copies of the dependencies. That keeps laptops light, at the cost of needing network access and a rule for who may change the shared cluster. Whether it fits depends on how many services you own and how stable the shared environment is. Start with the simplest setup that lets you run the code you are changing.

For how to keep the cluster out of the local loop on purpose, see keep Kubernetes out of local dev. To set the processes up, start with how to run microservices locally.

Questions people ask

Do I need Kubernetes to develop microservices locally?

No. Most day-to-day work, such as writing endpoints, calling other services and running a database, works with plain processes or Compose. You need a cluster to test things that only exist in Kubernetes, such as manifests, operators or network policies.

Does Flisk replace kind or minikube?

No. Flisk has no Kubernetes API and does not generate Kubernetes manifests. It starts your services locally, as processes or as containers, and leaves cluster deployment to your own workflow.

When should I use a local cluster?

When the thing you are changing is Kubernetes itself: Helm charts, Kustomize overlays, ingress rules, RBAC, controllers or resource limits.
