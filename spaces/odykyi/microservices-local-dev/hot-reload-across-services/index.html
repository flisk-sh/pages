Run microservices on your laptop

How to get hot reload across several services locally

Hot reload for one service is a flag. For five services in two languages it is a decision you make per service.

To get hot reload across several services, choose the reload mechanism per service and let the runner handle only the process. For plain processes, use your runtime's own watch flag in the start command. For containers, sync changed files into the container and run a command that restarts on change. Settings that are read once at start, such as environment variables, always need a restart.

Three layers of reload

People say "hot reload" for three different things:

  • Process restart on save. A watcher restarts the server when a file changes. Examples are node --watch, bun --watch, uvicorn --reload and Go tools such as air.
  • Module replacement in the browser. A dev server like Vite updates the page without a full reload.
  • File sync into a container. Your editor changes a file on the host, and a tool copies it to the running container so the watcher inside sees it.

You need the right layer for each service. A frontend with Vite already has the second layer. An API in a container needs the third and the first.

The general approach

With Compose, you bind-mount the source folder into the container and run the watcher inside. Newer Compose versions add a develop.watch section that syncs or rebuilds on change. Both work, with a catch on macOS and Windows, where bind mounts can be slow and file events may not arrive. The Compose hot reload guide covers this in more depth.

The Flisk way: local processes

No containers means no syncing. The command in each service.json is the watcher:

{ "appName": "api",    "appType": "backend",  "command": "node --watch server.js",           "port": 4000 }
{ "appName": "worker", "appType": "worker",   "command": "uvicorn main:app --reload --port 4100", "port": 4100 }
{ "appName": "web",    "appType": "frontend", "command": "npx vite --port 3000",            "port": 3000, "dependsOn": ["api"] }

Each service reloads by its own rules, and Flisk keeps them running and ordered. If a watcher restarts the process quickly, that is a normal reload. A crash is different: Flisk restarts a crashed process after 1, 2, 4 and 8 seconds, and gives up after five quick exits.

The Flisk way: containers

In the container path, Tilt copies changed files into the running container. The folders to watch come from dev.watch in service.json:

"dev": { "command": "bun run dev", "watch": ["src/**/*"] }

What happens after the copy depends on the language:

  • Bun backends, workers, agents and MCP servers reload by default when the dev script in package.json runs under bun --watch or --hot. Set "dev": { "liveReload": false } to use the compiled build instead.
  • Go services opt in with "dev": { "liveReload": true }, which recompiles inside the container. A compile error shows in the log and the last good build keeps answering.
  • Python and Node rely on their own process reload.
  • Bring-your-own containers get no source sync. Rebuild the image from the Tilt UI or restart the stack after a change.

Edits outside the watched folders do not trigger an update, and a dependency file such as go.mod still rebuilds the image.

Changes that need a restart

Environment variables are read when a process starts. Change one in service.json or .env and nothing happens until you run:

flisk restart api

The same goes for a generated frontend variable such as VITE_API_URL: it ends up in the browser bundle, so restart the frontend after changing the backend it points to.

Pitfalls

  • Two watchers fighting. If the runner and a framework both restart the process, you get double restarts. Use one.
  • A dependency reloads while others are talking to it. Expect a short run of failed requests. Retry in clients.
  • Watching too much. Watching node_modules or build output causes restart loops. Exclude them.

Order matters when several services reload at once. If the API restarts while the web app is polling it, the first requests after the save may fail. That is expected, so make clients retry, and avoid saving files in three services in the same second. For a frontend that calls an API, also check that the browser is not showing a cached response. A hard refresh can look like a reload bug when it is only the cache, and the network tab shows which one it is.

If a save changes nothing, hot reload not working lists the checks. To make the services reachable under stable names, see local URLs instead of ports.

Questions people ask

Does Flisk reload my code when I save a file?

For local processes, reload comes from your command: use your runtime's watch mode such as node --watch or uvicorn --reload. For containers, Flisk syncs changed files into the running container, and the app restarts if its start command watches files.

Why did my change not show up?

Common reasons are that the file is outside the watched folders, the app was not started in watch mode, or the value is an environment variable, which is read only at start. Restart the service after changing env.

Does hot reload work for a bring-your-own Dockerfile service?

No. Flisk does not sync source into a bring-your-own container. Rebuild the image or restart the service after a change.
