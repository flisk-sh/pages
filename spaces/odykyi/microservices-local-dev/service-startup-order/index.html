How to control service startup order in local development

Starting in the right order is half of it. The other half is waiting until the first service is actually ready, not just launched.

To control startup order, declare which service each one needs, and make the tool wait for readiness, not just for the process to launch. A service that has started is not a service that is ready: it may still be opening its port, connecting to a database or running migrations. Order by readiness, and add retries in the client for the cases ordering cannot cover.

Started is not the same as ready

A process can exist for several seconds before it accepts connections. If the web app starts the moment the API process exists, its first request fails. That is why the common pattern has three parts: a dependency list, a readiness check for each service, and a start that waits for the check.

In Docker Compose that is depends_on with condition: service_healthy plus a healthcheck on the dependency. Without the condition, Compose only waits for the container to start. The details are in depends_on and healthchecks.

Order local processes with dependsOn

In Flisk, each service lists what must be ready first:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "node server.js",
  "port": 3000,
  "dependsOn": ["api"]
}

For a local process, "ready" means:

  • the health URL answers with a status below 400, when the service sets healthCheckPath;
  • otherwise, the port accepts connections;
  • otherwise, the process is still running after a second.

Flisk waits up to 60 seconds per service. You can change what "ready" means with the healthCheck field: path, a TCP port, or a command that must exit 0 (for example pg_isready for a database). Setting healthCheck to false counts a service as ready while its process runs.

The graph is checked before anything starts. Two mistakes are reported with a clear message:

circular dependency api -> web -> api
service "api" dependsOn "ghost", which is not a service in this project.

Order containers and one-shot jobs

In the container setup, dependsOn becomes a Tilt dependency, and entries can carry a Compose-style condition:

"dependsOn": [
  { "name": "shop-db", "condition": "service_healthy" },
  { "name": "orders-api-migrator", "condition": "service_completed_successfully" }
]

service_healthy is for long-running services. service_completed_successfully is for one-shot jobs such as migrations. Flisk rejects a mismatch, for example service_healthy on a job that exits. The usual chain is Postgres, then a migrator, then the API. If the migrator fails, the services after it do not start. Keep the migration command in the migrator, not in the API's start command, so restarting the API does not run migrations again. The scaffold flisk resource orders-api --type backend --stack shop --feature prisma creates the API and its migrator as a pair.

What ordering does not give you

This is the part people miss. Ordering applies at startup only. In Flisk, dependsOn does not make a service retry or wait if a dependency stops later. If the API restarts while the web app is running, the web app sees failed requests for a moment. Plan for it:

  • Retry outgoing calls with backoff in the client, at least for startup.
  • Reconnect to the database after a lost connection instead of crashing.
  • Expose a real health endpoint that checks what the service needs, not one that always returns 200.

Also note that a crashed local process is restarted after 1, 2, 4 and 8 seconds. After five quick exits in a row Flisk stops restarting it and says so. A service that exits on purpose (a one-shot job) should set "restart": "no".

Pitfalls

  • A health endpoint that lies. If /health returns 200 before the database connection is up, dependents start too early. Make it check the real dependencies, or use healthCheck.command.
  • Too long a wait. A service that needs more than 60 seconds to become ready is reported as failed. Find out why it is slow first.
  • Cycles. A cycle means two services each need the other first. Break it by moving what they share into a third service.

Look at an order before you rely on it. flisk up --dry-run prints the plan, and a service with dependencies shows them after its command, for example web: node server.js (after api). Read it once after each change to dependsOn. It is much quicker than finding a wrong order through a failing request. If a service is missing from the plan, check whether it sits behind a profile, which keeps it out of a plain flisk up. A cycle or a missing name stops the run before anything starts, so you find those mistakes early.

If a service never becomes ready, service will not start walks through the checks. To start a smaller graph, see start only the services you need.

Questions people ask

Does depends_on wait for a service to be ready?

In Docker Compose, plain depends_on only waits for the container to start. Add a healthcheck and use condition: service_healthy to wait until the service reports healthy.

What happens if a dependency crashes after startup?

Startup ordering does not cover it. In Flisk, dependsOn is only local startup ordering and does not make a service retry or wait if a dependency stops later. Add retries with backoff in the client code.

How do I run database migrations before the API starts?

Run them in a one-shot job that the API depends on, and start the API only after the job exits with code 0. Do not run migrations from the API's start script.
