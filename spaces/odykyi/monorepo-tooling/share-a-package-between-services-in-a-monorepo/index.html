How to share a package between services in a monorepo

A shared package is the main reason to use a monorepo, and the main reason edits seem to have no effect. Here is how the links and the builds work.

Create the shared code as its own package under packages/, depend on it with "@shop/shared": "workspace:*", and decide how consumers read it: either from a built dist folder that a watch process keeps fresh, or straight from the TypeScript source. The second is simpler when your tools can compile TypeScript; the first works everywhere.

Create the package and link it

A shared package is a normal package with a name and an entry point:

packages/shared/package.json
{
  "name": "@shop/shared",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./dist/index.js" },
  "types": "./dist/index.d.ts",
  "scripts": {
    "build": "tsc",
    "dev": "tsc --watch --preserveWatchOutput"
  }
}

In each service that uses it, add the dependency with the workspace protocol:

"dependencies": { "@shop/shared": "workspace:*" }

After pnpm install, pnpm links node_modules/@shop/shared to the folder in your repo. It is a link, not a copy, so an edit is visible immediately. npm and Yarn workspaces behave the same way for packages listed in workspaces, though they use * or the workspace: protocol in different forms.

Option one: build the package and watch it

The consumer imports dist/index.js. That file only exists after a build, and it is stale after an edit until the next one. So the dev script above runs tsc --watch. Run it next to the services:

pnpm --filter @shop/shared dev &
pnpm --filter @shop/api dev

Or let a task runner do it: pnpm -r --parallel run dev starts the watcher and the apps together. The common surprise is that an API running with node --watch or tsx watch restarts only when files it loaded change. If your watcher ignores node_modules, which most do, a rebuilt dist reached through a link may not restart it. Restart the service once to check, and if that is the case, tell the watcher to include the package path.

Option two: export the source

Point the package at TypeScript directly:

"exports": { ".": "./src/index.ts" }

No build step and no stale output. This works when the consumer compiles TypeScript itself: Vite and Next.js (with transpilePackages set for the package), Bun, tsx, and bundlers. It does not work for plain node before native type stripping, and it cannot be published to npm as is. For an internal package that is never published, that is usually fine.

How Flisk fits

Flisk starts services, not packages. A service folder has a service.json with a command and optional dependsOn. Your shared package does not need one if consumers read its source. If they read dist, run the watcher from the service command so it is always on:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "pnpm --filter @shop/shared build && pnpm dev",
  "port": 4000,
  "healthCheckPath": "/health"
}

That builds the package once before the API starts. For continuous rebuilds, keep a watcher in the shell that runs flisk up, or use option two. flisk up restarts a service that exits, and each service reloads with its own watcher, such as tsx watch. Flisk's schema also lists library and sdk as resource types for shared packages; I did not verify what Flisk does with them for a workspace package, so I do not rely on them here.

Pitfalls

  • Stale build output. If an edit has no effect, look at the timestamp of dist. Delete it and rebuild.
  • Two copies of a dependency. If the shared package and a service resolve different versions of the same library (a validation library, say), instanceof checks and types can fail. Keep versions aligned with one lockfile.
  • Circular dependencies. If shared imports from a service, move that code into shared or a third package.
  • Types and runtime drift. Keep a shared tsconfig; see sharing one tsconfig.

If the shared code is an API contract between a frontend and a backend, also read keeping a frontend and backend contract in sync.

Questions people ask

What does workspace:* mean?

It tells pnpm (and Yarn) to resolve the dependency to the package in the same workspace and link it, instead of downloading it from the registry.

Why do my changes in the shared package not show up?

Usually the consumer reads a built dist folder that is out of date, or its file watcher ignores node_modules where the link lives. Run a watch build and restart once to check.

Can I import TypeScript source from another package?

Yes, if the consumer compiles TypeScript itself, such as Vite, Next.js with transpilePackages, Bun or tsx. Plain Node needs a built JavaScript output.
