How to write an AGENTS.md file for your repo

AGENTS.md is a README for the assistant. The best ones are short, concrete and written from the mistakes the assistant actually made.

Write an AGENTS.md as a short list of commands the assistant should run, rules it must not break, and places to look for details. Keep it to what a new colleague could not guess from the code. Codex and Cursor read the file as it is, and Claude Code reads it when the project has no CLAUDE.md, or when your CLAUDE.md includes it with @AGENTS.md.

What the file is for

A README is written for people who will decide whether to use the project. An AGENTS.md is for a reader that will edit it right now, starts with no memory, and follows instructions literally. That reader needs the exact build command, the test command, which folders are off limits, and what "done" means here. It does not need your mission statement.

The file is plain Markdown. There is no required structure, so use headings that you would scan yourself.

What to put in

  • Commands that work from the repository root. Install, run, test, lint, type check. Copy them from a terminal that actually ran them. A command that is slightly wrong costs the assistant several turns.
  • Hard rules, stated as rules. "Do not edit generated files." "Every behaviour change needs a test in the same change." "No secrets in the repository."
  • Where things live. One line per top-level folder is enough.
  • Traps you have already hit. The stale build output, the test that needs a database, the formatter that must be run through the package script. These lines earn their place fastest.
  • How to check the work. Which command proves the change, and what to report back.

What to leave out

  • Anything that is already obvious from package.json or the folder names.
  • Style rules a linter can enforce. Run the linter instead.
  • Long prose. Every line is read on every task, so a 600-line file costs attention, and a rule buried in it gets missed.
  • Secrets, tokens, internal URLs.

When the file grows, split by area: a short root file that links to a deeper file in each package folder, and tell the assistant to read the local one before it changes that folder. Flisk's own repository does this, with a root file and one for each subsystem.

An example

# AGENTS.md

Local dev stack for the shop. Runs with Flisk.

## Commands
- Check the machine: `flisk doctor`
- Start everything: `flisk up main`, then `flisk networks` for URLs
- Logs for one service: `flisk logs -s orders-api`
- Tests: `npm test` in each service folder

## Rules
- Do not edit `.flisk/`, `.flisk/.flisk-out/` or `services/**/.autogenerated/`.
  Change `service.json` instead, then run `flisk up`.
- Database changes go in the `migrator` service, never in an API start script.
- Never commit `.env`.

## When something fails
Read the logs of the failing service before changing code.

That is about fifteen lines, and each line prevents a specific mistake.

What Flisk writes for you

When you run flisk project or flisk connect, Flisk writes an AGENTS.md with its own few rules (add a service with flisk resource, start it with flisk up, debug with flisk doctor and flisk logs, never hand-write Dockerfiles or Compose files, never edit .autogenerated/) and the skills the assistant uses. It never overwrites a file you already have: if AGENTS.md exists it is left as it is. Add your own rules above or below Flisk's lines. flisk project --no-agent-skills skips the skills and the file.

How each tool reads it

  • Codex and Cursor read AGENTS.md.
  • Claude Code reads CLAUDE.md. It reads AGENTS.md only when the project has no CLAUDE.md. If you keep both, put the line @AGENTS.md in CLAUDE.md, so there is one source of truth.

Keep it true

An instruction file that lies is worse than none. Review it when the commands change, and add a line the moment the assistant makes the same mistake twice. Treat it like code: it lives in the repository, changes go through review, and a teammate's assistant benefits from them too. For a team, the same idea applies to service.json as a team contract.

The most useful single rule to start with is about generated files. See stopping AI from editing generated files.

Read the file back as a stranger would. If a line only makes sense to someone who sat in the last planning meeting, rewrite it with the command or the path spelled out.

Questions people ask

Does Claude Code read AGENTS.md?

Only when the project has no CLAUDE.md. If you have a CLAUDE.md, add the line @AGENTS.md to it so the same instructions apply.

How long should an AGENTS.md be?

As short as you can keep it true. Commands, hard rules and known traps usually fit in a few dozen lines. Move per-folder detail to a file in that folder.

Does flisk project overwrite my existing AGENTS.md?

No. If the file exists it is left alone, and Flisk writes its own version only when there is none.
