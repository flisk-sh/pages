MCP servers and coding assistants

How to build an MCP server locally and run it on your laptop

A local MCP server is a small HTTP service with one endpoint. Here is what it needs, how to write one, and how to keep it running while you edit.

To build an MCP server locally, write a small HTTP service that answers JSON-RPC on one path (usually /mcp), register your tools with the official SDK, and run it with a file watcher so edits reload. Then call it with curl before you connect any assistant. With Flisk, flisk resource docs-mcp --type mcp scaffolds all of that.

Pick a transport first

MCP servers talk to clients over one of two transports. A stdio server is a child process: the client starts it and exchanges messages over standard input and output. It needs no port and no network, which makes it the simplest choice for a tool that only your own assistant uses on your own machine.

A Streamable HTTP server is a normal web service. It listens on a port, and clients POST JSON-RPC messages to one URL. Choose this when the server should sit next to your other services, when several clients (Claude Code, Cursor, Codex, a test script) should share one running instance, or when you want to reach it with curl. The rest of this article builds that kind. If you want the protocol details, see the Streamable HTTP endpoint guide.

Write the smallest useful server

With the TypeScript SDK (@modelcontextprotocol/sdk) and zod for argument schemas, a server with one tool is short. This version keeps the endpoint stateless: it builds a fresh server for every request, so there is no session to lose when the process restarts.

import { createServer } from 'node:http';
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StreamableHTTPServerTransport } from '@modelcontextprotocol/sdk/server/streamableHttp.js';
import { z } from 'zod';

function buildServer() {
  const server = new McpServer({ name: 'docs-mcp', version: '1.0.0' });
  server.registerTool(
    'echo',
    { description: 'Echo a message back', inputSchema: { message: z.string() } },
    async ({ message }) => ({ content: [{ type: 'text', text: message }] })
  );
  return server;
}

createServer(async (req, res) => {
  if (req.url === '/health') { res.end('ok'); return; }
  if (req.url === '/mcp' && req.method === 'POST') {
    const chunks = [];
    for await (const c of req) chunks.push(c);
    const body = JSON.parse(Buffer.concat(chunks).toString('utf8'));
    const server = buildServer();
    const transport = new StreamableHTTPServerTransport({ sessionIdGenerator: undefined });
    res.on('close', () => { transport.close(); server.close(); });
    await server.connect(transport);
    await transport.handleRequest(req, res, body);
    return;
  }
  res.statusCode = 404; res.end();
}).listen(Number(process.env.PORT ?? 4000), '0.0.0.0');

Keep a /health route even in a toy server. Anything that supervises the process, from a Compose healthcheck to a reverse proxy, can use it to know when the server is ready. Binding to 0.0.0.0 matters only if the server runs in a container and something outside it needs to connect.

Call it before you connect an assistant

Do not debug a server through a chat window. Send the three requests yourself and read the answers:

curl -s -X POST http://localhost:4000/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

The accept header must list both media types, because the transport can answer as JSON or as a server-sent event stream. The reply comes back in event-stream framing (event: message, then a data: line). A strict client sends initialize first; a quick tools/list like this is usually enough for a stateless server while you develop. When the tool list looks right, the MCP Inspector (npx @modelcontextprotocol/inspector) gives you a UI for calling tools by hand.

The Flisk way

Flisk has a resource type for this. In a project (flisk project creates one), run:

npm install -g @flisk-sh/flisk
flisk resource docs-mcp --type mcp --stack main
flisk up main

The scaffold writes services/main/docs-mcp/ with a service.json, a Bun-based src/index.ts built on the SDK with an echo tool and a prompt, a /health route, a Dockerfile and a test file. The generated service.json looks like this (trimmed):

{
  "appName": "docs-mcp",
  "appType": "mcp",
  "port": 4000,
  "healthCheckPath": "/health",
  "dev": { "command": "bun run dev", "watch": ["src/**/*"] },
  "dependsOn": []
}

The port is picked from the 4000 to 5999 range. bun run dev is bun run --watch src/index.ts, so saving a file restarts the server. Once the stack is up, Traefik routes the server at http://api.<project>.localhost/api/docs-mcp/mcp; flisk networks prints the real address, and the curl call above works against it. To add a tool, edit buildServer() in src/index.ts and register it with registerTool.

Pitfalls

  • Stateless means no memory between calls. If a tool must remember something, store it in a database, not in a variable inside the process.
  • GET /mcp returns 405. That is expected for a stateless server that does not open server-to-client streams. It is not a crash.
  • No authentication. The scaffold is meant for *.localhost. Do not expose it beyond your machine as it is.
  • The scaffold is Bun only. There is no --language option for --type mcp. If you need Python, write the server yourself and register it as a bring-your-own container.
  • Write tools for a model, not a person. Short names, one job each, and a description that says when to use it.

Next, connect the server to an assistant. Testing an MCP server with Claude Code walks through it, and the same URL works in Cursor and Codex.

When the server runs in a stack, the address changes from a bare port to a project host name. Local URLs instead of ports explains how that routing works.

Questions people ask

Do I need Docker to build an MCP server locally?

No. A plain Node or Bun process that listens on a port is enough, and you can test it with curl. Flisk's mcp resource type runs in Docker behind Traefik, which is useful when the server must sit next to other services.

What is the difference between stdio and Streamable HTTP MCP servers?

A stdio server is started by the client as a child process and needs no port. A Streamable HTTP server is a web service that clients reach by URL, so several clients and test scripts can share one running instance.

Why does curl to /mcp need an Accept header with two types?

The transport can reply as plain JSON or as an event stream, so it expects the client to accept both application/json and text/event-stream. Without both, the SDK refuses the request.
