How to test an MCP server with Claude Code

Claude Code is a good test client, but it is a poor debugger. Check the server yourself, then connect Claude Code and ask it to use a tool.

To test an MCP server with Claude Code, run claude mcp add --transport http my-server http://localhost:4000/mcp, start Claude Code, type /mcp to see whether the server is connected, then ask it to call one of the server's tools. Check the server with curl or flisk mcp check first, so a failure in Claude Code means something specific.

Check the server before the client

When a tool does not show up in an assistant, the cause could be the URL, the transport, the protocol, the tool schema or the assistant itself. Remove the assistant from the list of suspects by testing the server directly:

curl -s -X POST http://localhost:4000/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

If that returns your tools, the server works and any remaining problem is on the client side. The official MCP Inspector (npx @modelcontextprotocol/inspector) does the same with a UI and lets you fill in tool arguments.

If your server runs under Flisk, there is a built-in protocol check that takes a resource name:

flisk mcp check docs-mcp

It sends initialize, tools/list, prompts/list and one prompts/get per prompt, then four deliberately malformed requests, to see that the server refuses them the right way: an unknown method must get error code -32601, a body that is not JSON must get HTTP 400, a GET must get 405, and a client that accepts only application/json must not get 406. It also checks that every tool is marked readOnlyHint: true, so a server whose tools write data will report that check as failed, by design. It calls no tool unless you add --call, because a tool call can have side effects or reach the network. --json prints a machine-readable report and the exit code is 1 when any check fails.

Add the server to Claude Code

For a server on a URL, use the HTTP transport:

claude mcp add --transport http docs-mcp http://api.shop.localhost/api/docs-mcp/mcp

Replace the URL with the one flisk networks prints for your resource, or with http://localhost:4000/mcp for a plain process. By default this stores the entry for you in the current project (the local scope). Add --scope project to write it to a .mcp.json file you can commit, which Claude Code asks you to approve before it trusts a project server. The Claude Code MCP guide describes all three scopes.

Start claude in the project and run /mcp. You should see the server listed as connected. claude mcp list shows the same from a terminal.

Make Claude Code call a tool

Name the tool in your request so there is no guessing. With the scaffolded server:

Use the echo tool from docs-mcp to send the message "hello from claude code".

Claude Code asks permission before the first call to a tool. Approve it once, and watch the server's own log at the same time:

flisk logs -s docs-mcp

Seeing the request arrive in the server log is the proof that the call went through your server and not a guess from the model. Then try a request that should not use the tool, and see that Claude Code leaves it alone. Tool descriptions decide that, so this is the quickest way to find a description that is too broad.

When it does not connect

  • Failed status in /mcp. Repeat the curl call with the exact URL you gave Claude Code. A typo, a wrong port or a missing /mcp path are the usual causes.
  • The name *.localhost does not resolve. The Flisk docs record that Node resolved api.<project>.localhost on its own, but they also say that Claude Code, Cursor and the MCP Inspector were not run against it. If your client cannot resolve the name, check flisk networks and try the address it prints.
  • The server changed but the tool list did not. Claude Code reads the tool list when it connects. Reconnect from /mcp or start a new session after you add or rename a tool.
  • Another server with the same name. A project entry and a local entry with one name can shadow each other. Remove the one you do not want with claude mcp remove <name>.

When this is not the right test

Claude Code tests whether a model chooses your tools well. It does not test your server's behaviour under bad input, and a model will not reliably send the malformed requests that a protocol check does. Use a script or an automated test for those, and keep Claude Code for the question of whether the tool names and descriptions make sense to an assistant.

Once the server behaves, point more than one client at it. Adding an MCP server to Cursor and to Codex use the same URL.

If the stack itself will not start, fix that before you blame the server. Check your machine before starting covers the usual causes.

Questions people ask

How do I see if Claude Code connected to my MCP server?

Start claude in the project and run /mcp. The server is listed with its connection status. From a terminal, claude mcp list prints the same information.

Does flisk mcp check call my tools?

No. It only sends initialize, list and get requests plus a few malformed ones, and it calls no tool unless you pass --call, because a tool call can reach the network or change data.

Why does Claude Code not use my tool?

The model chooses tools from their names and descriptions. Name the tool in your request to confirm the connection works, then rewrite the description so it says when the tool should be used.
