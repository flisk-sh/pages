MCP Streamable HTTP endpoint: how it works and how to test it

Streamable HTTP replaced the older two-endpoint SSE transport. It is simpler than it sounds, and most failures come from three small details.

An MCP Streamable HTTP server exposes a single URL, conventionally /mcp. The client sends each JSON-RPC message as an HTTP POST with an Accept header that lists both application/json and text/event-stream. The server answers either with one JSON body or with an event stream. A server can be stateless, or it can issue a session id.

What the transport replaced

The first HTTP transport for MCP used two endpoints: a long-lived server-sent events connection for server-to-client messages, and a separate POST endpoint for requests. It was awkward to run behind load balancers and proxies. The Streamable HTTP transport, introduced in the 2025-03-26 revision of the protocol, puts everything on one endpoint. If a tutorial tells you to expose /sse and /messages, it describes the older design.

The request

A client opens by sending initialize. After that it can list and call tools. Every message is a JSON-RPC 2.0 object in a POST body:

curl -s -X POST http://localhost:4000/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

The answer for a request that has an id carries the same id. With the TypeScript SDK's default settings the reply is framed as an event stream:

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"tools":[...]}}

Notifications (messages without an id) get an HTTP 202 and no body.

The three details that break things

  1. The Accept header. The transport refuses a request that does not accept both media types, usually with 406 Not Acceptable. A client that can only read JSON is a legitimate client, and a server can handle it: the Flisk scaffold adds text/event-stream to such a request and enables the SDK's JSON-response option, so the reply is plain JSON. If you write your own server, decide on purpose what a JSON-only client should get.
  2. GET on the endpoint. The specification lets a server open a stream for server-initiated messages on GET. A server that does not need that must say so with 405 Method Not Allowed and an Allow: POST header. The Flisk scaffold does this. A 405 on GET /mcp is therefore a correct answer, not a bug.
  3. Malformed input. A body that is not JSON should get HTTP 400 with a JSON-RPC parse error (code -32700), and an unknown method should get a JSON-RPC error with code -32601. Throwing an exception inside an async request handler can end the whole process, so catch the parse step.

Stateless or sessions

With sessionIdGenerator: undefined the SDK runs in stateless mode: every request is independent, so you create a server instance per request. This is the easiest mode to run and restart, because there is nothing to lose. If you need server-to-client streaming, resumable streams or per-client state, give the transport a session id generator. The client then echoes an Mcp-Session-Id header on later requests, and your process has to keep that session in memory. That makes restarts and multiple replicas harder. Prefer stateless unless you need what sessions give you, and keep real state in a database.

Test it without a client

You can check all of the above from a terminal. Send a non-JSON body and expect 400, send GET and expect 405, and send an unknown method and expect -32601. If the server runs under Flisk, one command does the whole list:

flisk mcp check docs-mcp
flisk mcp check https://mcp.example.com/mcp --json

It accepts a resource name or an https URL (plain http only for localhost, *.localhost and loopback addresses), checks initialize, tools/list, prompts, the error cases above and the Accept behaviour, and exits with 1 if any check fails. It does not call tools unless you add --call. Because it is a protocol check, you can also point it at a server that Flisk does not run.

In a Flisk project

The mcp resource type scaffolds a stateless Streamable HTTP server with the behaviours above: POST /mcp for JSON-RPC, 405 with Allow: POST on GET, 400 for bad JSON and GET /health for readiness. Traefik routes it at http://api.<project>.localhost/api/<name>/mcp. It has no authentication, so keep it behind *.localhost.

When this is the wrong transport

If only one assistant on your machine will ever use the tool and it needs no network, a stdio server is simpler: no port, no URL, no headers. Streamable HTTP earns its cost when a server must be shared, tested by scripts, or run next to other services.

To build one end to end, read building an MCP server locally.

Inside a stack the endpoint is reached through a project host name, not a port. See local URLs instead of ports for how those names are built.

Questions people ask

Why does my MCP server return 406 Not Acceptable?

The client did not send an Accept header that lists both application/json and text/event-stream. Send both, or make the server handle JSON-only clients on purpose.

Is a 405 response on GET /mcp an error?

Not for a stateless server. The specification lets a server decline to open a server-to-client stream, and a 405 with an Allow: POST header says exactly that.

Should my local MCP server use sessions?

Only if you need server-initiated messages or per-client state. A stateless server restarts without losing anything, and shared state belongs in a database.
