Agent memory and context engineering

Why long-context agents forget instructions and drift

Big windows do not guarantee good attention. Why agents lose rules, repeat work or wander in long sessions, and the fixes that work.

Agents drift in long sessions because the window fills with stale, noisy and contradictory text, and the model pays less reliable attention to the parts that matter. The fix is a smaller, tidier window, not a bigger one.

What the symptoms look like

  • The agent ignores a rule from the system prompt that it followed an hour ago.
  • It repeats a failed approach, or redoes finished work.
  • It mixes up two similar items, such as two files with similar names.
  • Quality slowly drops in a session that started well.

Research and practitioner reports describe models using information in the middle of a very long input less reliably than at the start or end. Treat that as a tendency to design around, and measure it on your own task.

Common causes

Noise. Raw tool output, logs and whole files crowd out the signal.

Contradiction. Early plans and later corrections both sit in history, and the old text still looks authoritative.

Dilution. A rule stated once, 50,000 tokens ago, competes with everything after it.

Fixes that work

  1. Restate the goal and the active rules near the end of the input on each call, in a short "current state" block.
  2. Trim tool results and drop ones that no longer matter.
  3. Replace superseded plans instead of appending corrections. Rewrite the plan, do not stack versions.
  4. Compact on a threshold, as in summarizing history.
  5. Start a fresh session for a new task, carrying over only a short handoff note.

A state block you can reuse

CURRENT STATE (updated each step)
Goal: migrate the users table to the new schema
Done: schema file written, migration script drafted
Next: run migration on a copy, compare row counts
Rules: never touch prod; ask before deleting any column
Open questions: none

Have the agent rewrite this block after each step and place it last in the input. It acts as a short-term memory the model can always find.

How to confirm it is the cause

Take a failing late-session input, cut it to the state block plus the last few turns, and rerun. If the answer is right, drift was the problem. This is a standard check in debugging agent context.

Design for it from the start

Assume every long session will drift and plan a cheap exit. Give each task a clear end state so the agent can say it is done. Cap the number of steps per session and hand over to a fresh one with a note. Log token counts per call so you can see the curve: if quality drops at roughly the same size every time, set your compaction threshold below that point. You are looking for a number that holds for your task, not a rule that holds for all models.

Questions people ask

Will a model with a larger window fix this?

It can help for tasks that truly need more text, but it does not remove drift. Tidier context usually helps more than a larger limit.

Should I restart the session when quality drops?

Often yes. Start a new session with a short handoff note, which is cheaper and more reliable than carrying a very long history.
