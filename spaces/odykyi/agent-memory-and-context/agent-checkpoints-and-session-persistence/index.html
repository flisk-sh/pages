Agent checkpoints and session persistence explained

A checkpoint is the saved state of an agent run, keyed by session ID. What to save, when to write it, and how to resume safely after a crash or restart.

Save the agent's state after each completed step, keyed by a session ID, so a crash or restart can resume from the last good step instead of starting over. The state is small: messages, working notes, and a record of which tool calls already ran.

What a checkpoint holds

  • Session ID and a version number for the state format.
  • Messages (or summary plus recent turns).
  • The plan and a step counter.
  • Tool calls already executed, with their results and an idempotency key.
  • Timestamps, for expiry.

Keep it as plain JSON. If you cannot read it in a text editor, you cannot debug it.

When to write

Write after every step that changed something: a model reply, a tool result. Write before a risky or slow action as well, so you know what was in flight. Use an atomic write (write to a temp file or use a database transaction) so a crash in the middle never leaves half a checkpoint.

A minimal implementation

import json, sqlite3, time

db = sqlite3.connect("agent.db")
db.execute("create table if not exists ckpt (sid text primary key, state text, ts real)")

def save(sid, state):
    with db:
        db.execute("insert or replace into ckpt values (?,?,?)",
                   (sid, json.dumps(state), time.time()))

def load(sid):
    row = db.execute("select state from ckpt where sid=?", (sid,)).fetchone()
    return json.loads(row[0]) if row else None

The HTTP side is simple too: take the session ID from a header such as x-session-id, load the state, run one turn, save, reply.

Resuming without doing things twice

The danger on resume is repeating a side effect: sending the email again, charging twice. Give each tool call an idempotency key such as session:step:tool, record it before the call, and skip calls whose key is already marked done. For tools you cannot make idempotent, ask the user before re-running.

Running it locally with Flisk

For the memory design around it, read short-term vs long-term memory.

Pitfalls

  • Saving only the messages. Without the plan and tool records you cannot resume cleanly.
  • No state version. When you change the shape, old checkpoints break. Store a version and migrate or discard.
  • Unbounded growth. Compact messages before saving, or checkpoints become huge.
  • Concurrent turns on one session. Use a lock or a version check so two requests do not overwrite each other.

Questions people ask

How long should I keep checkpoints?

Keep them as long as a user might resume, such as days or weeks, then expire them. Delete on request if they contain personal data.

Is a checkpoint the same as long-term memory?

No. A checkpoint restores one session. Long-term memory holds facts that apply across sessions.
