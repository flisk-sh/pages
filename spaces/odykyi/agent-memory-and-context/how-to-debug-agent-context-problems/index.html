Agent memory and context engineering

How to debug an AI agent that gets the wrong context

When an agent acts on the wrong facts, the bug is usually in what it was shown. A method: log the exact input, bisect it, and fix the assembly step.

Log the exact input of every model call, then read the failing call as the model saw it. Most "the model got it wrong" bugs turn out to be a missing file, a stale note, an oversized tool result or a truncated message.

Step 1: capture the real input

Write each call's full request to a file or log line with a session ID and step number. Include system text, tools, messages and parameters. Redact secrets before storing.

import json, time

def log_call(sid, step, request):
    with open("calls.jsonl", "a") as f:
        f.write(json.dumps({"sid": sid, "step": step,
                            "ts": time.time(), "req": request}) + "\n")

Without this you are guessing. With it you can replay any call.

Step 2: read it as the model

Open the failing call and ask five things:

  1. Is the fact the answer needs actually present?
  2. Is it present twice with different values?
  3. Is it buried under a large tool result?
  4. Did something get cut off, such as a message ending mid-sentence?
  5. Are the instructions contradictory?

Counting tokens per section here often finds the problem in minutes.

Step 3: bisect

Replay the call with parts removed. Drop old history, then retrieved notes, then tools, until the behaviour changes. The part whose removal fixes (or breaks) the answer is your suspect. Set temperature to 0 for these replays, where the API allows it, so you are not chasing randomness.

To test cheaply and often, you can point your client at a free-tier or local endpoint. For example, Flisk Inference (inference.flisk.si) is an open beta model API with a daily request limit, so it suits replay experiments but not production traffic.

Step 4: fix the assembly, not the symptom

Typical fixes: clip tool output, add a per-section budget, dedupe notes, put the current state last, scope memory by user. Avoid patching with a new line in the system prompt that says "never forget X". It adds more text and does not repair the cause.

Step 5: keep the case

Save the failing input as a test case with the expected behaviour. Run it whenever you change context assembly. A small set of such cases catches regressions that eyeballing misses. Related reading: why long-context agents drift and testing and evaluating AI agents.

A short list of usual suspects

  • A tool returned an error message that the agent treated as data.
  • A memory note from another user or project leaked into the call.
  • The retrieval query was the whole user message, including pleasantries, so the wrong chunks came back.
  • A summary replaced a fact with a paraphrase that changed its meaning.
  • The system prompt and a retrieved document disagree and the document won.

Check these before changing models or prompts.

Questions people ask

Should I log full prompts in production?

Only if your privacy rules allow it. Redact secrets and personal data, set a short retention period, and restrict access to the logs.

What if the context looks right but the answer is still wrong?

Then it is more likely a prompt or model limit. Try a clearer instruction, a worked example or a stronger model, and test the change on saved cases.
