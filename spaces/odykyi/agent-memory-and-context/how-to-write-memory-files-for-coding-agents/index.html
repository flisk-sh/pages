Agent memory and context engineering

How to write CLAUDE.md and AGENTS.md memory files

Coding agents read a markdown file at the start of every session. What belongs in it, what to leave out, and how to keep it short enough to be followed.

Put the commands, conventions and traps that an agent cannot guess in a short AGENTS.md or CLAUDE.md at the repo root. Keep it under about 150 lines, write it as instructions, and delete anything the code already makes obvious.

Why these files work

Coding agents start every session with an empty window. A project memory file is loaded into it each time, so it is the cheapest long-term memory you have. It is also in version control, so the team reviews it like code.

Different tools read different names. Many read AGENTS.md, and Claude Code reads CLAUDE.md. Check your tool's docs, and if you need both, keep one as the source and point the other at it.

What to include

  • Commands: install, build, test, lint, run one test. Exact strings.
  • Layout: where things live, in a few lines.
  • Conventions: naming, error handling, how to add a new endpoint.
  • Traps: things that fail silently, generated files not to edit, flaky steps.
  • Rules of the repo: small PRs, tests required, never commit secrets.

A compact example

# AGENTS.md

## Commands
- Install: npm ci
- Test all: npm test
- Test one file: npx vitest run path/to/file.test.ts
- Lint: npm run lint (run before every commit)

## Layout
- src/api: HTTP handlers. src/core: business logic, no I/O.

## Traps
- src/gen/ is generated. Edit schema/*.json and run npm run gen.
- Tests need Postgres on port 5432; start it with docker compose up -d db.

What to leave out

Do not paste your whole style guide, API docs or architecture essay. Long files get skimmed by the model too, and rules at the bottom are followed less often. Do not state what the code shows: an agent can read package.json. Link to deeper docs and say when to read them: "Read docs/db.md before changing migrations."

Keep it alive

Add a line when an agent makes the same mistake twice. Remove a line when it stops being true. Review the file in pull requests. If a rule matters a lot, back it with a check in CI, because a markdown rule is a request, not a guarantee. For a broader guide, see docs and READMEs for humans and agents and coding agents in practice.

Check the file like any README

A memory file is documentation with a strict reader. If you want a second opinion on structure, the README Score tool at readme.flisk.si gives a GitHub README a score out of 100 with the sections found and missing. It scores READMEs, not agent files, but the same habits apply: commands near the top, clear headings, no filler. Then test the file the practical way: start a fresh agent session and ask it to run the tests. If it cannot do that from the file alone, the file is missing something.

Questions people ask

Should CLAUDE.md and AGENTS.md be identical?

They can be. Keep one as the real file and have the other import or point to it, so the two never drift apart.

How long should the file be?

Short enough that every line earns its place, often 50 to 150 lines. If it keeps growing, move detail into linked docs.
