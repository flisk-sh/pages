Skaffold vs Tilt: which inner-loop tool should you use?

Both tools watch your code and update a running app. They differ in how you configure them and what they assume about your deploys.

Pick Skaffold if you want a declarative skaffold.yaml that the same team can reuse in CI and deploys. Pick Tilt if you want a live dashboard and are happy to script the loop in a Tiltfile. Both build images, deploy to Kubernetes, sync files and stream logs. If your app does not run on Kubernetes at all, neither is required.

What they have in common

The inner loop is the cycle of edit, build, deploy, look. Skaffold and Tilt both watch your source, rebuild only what changed, redeploy to a cluster (a local one such as kind, minikube or Docker Desktop Kubernetes, or a remote one) and forward ports. Both can sync a changed file into a running container so you skip a full image build for interpreted languages.

How Skaffold works

Skaffold is configured with skaffold.yaml. You list the images to build and the manifests to deploy, then run skaffold dev. It builds, deploys with kubectl, Helm or Kustomize, watches files and redeploys on changes, and cleans up when you press Ctrl+C. The same file works with skaffold run for a one-shot deploy, which is why teams reuse it in CI. Profiles let you change settings per environment, and skaffold init can propose a first config from your repo.

apiVersion: skaffold/v4beta11
kind: Config
build:
  artifacts:
    - image: myorg/api
      context: api
manifests:
  rawYaml:
    - k8s/*.yaml

The schema version changes between releases, so take the exact apiVersion from your installed version's docs rather than from a blog post.

How Tilt works

Tilt is configured with a Tiltfile written in Starlark. You call functions such as docker_build, k8s_yaml and k8s_resource. Running tilt up opens a web UI that shows each resource, its build state and its logs. live_update syncs files and runs commands inside a container. Because the Tiltfile is code, you can use loops, conditions and helper functions, and run host commands with local_resource. The price is that you maintain code, not a declaration.

Choosing between them

You care most aboutLean toward
One declarative file reused for local, CI and deploySkaffold
A live UI with status for many servicesTilt
Custom logic, host commands, scripted setupTilt
Buildpacks, Jib or Bazel builders without a DockerfileSkaffold (builders are built in)
Docker Compose as the targetTilt (Skaffold targets Kubernetes)

If you are unsure, try both on one service for an afternoon. The migration cost of a single service is small, and the feel of the loop is personal.

When you need neither

A local Kubernetes cluster costs memory and attention. If Kubernetes is only where the app lands in production, and you do not touch manifests, operators or network policies while coding, a plain Docker or process-based loop is faster. See local development without Kubernetes.

Flisk is on that side of the line. It runs services as local processes or on Docker and Tilt, and it does not talk to a cluster or generate Kubernetes manifests. Keep Skaffold or Tilt for the days you need real cluster behavior. A reasonable split is Flisk for daily feature work, and Skaffold in CI or a shared cluster to check the manifests.

Pitfalls

  • Both tools will happily deploy to whatever your kubectl context points at. Check kubectl config current-context before you run them. Tilt refuses non-local contexts unless you allow them in the Tiltfile.
  • File sync does not rebuild dependencies. If you change a lockfile, expect a full image build.
  • Mixing both in one repo creates two loops to maintain. Pick one for the team.

Questions people ask

Is Skaffold or Tilt better?

Neither wins everywhere. Skaffold suits teams that want one declarative file reused in CI. Tilt suits teams that want a live UI and scriptable logic.

Can Tilt deploy to Kubernetes?

Yes. Tilt uses docker_build, k8s_yaml and k8s_resource for Kubernetes, and it can also drive Docker Compose.

Do I need Kubernetes locally to develop a microservice?

Not always. If you do not work on manifests or cluster features, running services as processes or on Docker is lighter. Use a cluster when you need real cluster behavior.
