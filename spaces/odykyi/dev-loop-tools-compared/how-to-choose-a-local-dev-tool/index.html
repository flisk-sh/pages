Local dev tools compared

How to choose a local dev tool: a decision guide for teams

Most teams choose a dev tool by habit. These questions make the choice from facts about your project instead.

Choose the lightest tool that covers your actual problem. Two services you can start with two commands need a short script, not an orchestrator. Many containers need Compose, and possibly Tilt. A Kubernetes target brings in Skaffold, DevSpace or Garden. Reproducible tools for a team bring in dev containers. Answer the questions below in order and stop at the first row that fits.

Question 1: where does your app run in production?

If it runs on Kubernetes and you work on manifests, operators or network policies, you need a real cluster in your loop. Use Skaffold or Tilt, or DevSpace or Garden. If Kubernetes is only the deployment target and your daily work is application code, you can usually skip the cluster in the inner loop and keep the manifests checked in CI.

Question 2: how many parts, and are they containers?

Your appReasonable tools
One to three processes, no databasenpm scripts, concurrently, a Procfile runner, Make, just or Task
A few services plus a database, already on DockerDocker Compose
Many services, often changing, in containersCompose plus Tilt, or a generator on top
Processes with startup order but no containersprocess-compose, or Flisk's local-process mode

The process-oriented options are compared in concurrently vs mprocs vs process-compose and Foreman vs Overmind vs Honcho. For the container options, see Tilt vs Docker Compose.

Question 3: what takes your team's time today?

Write down what hurts and match it to a tool, instead of the reverse.

  • "Setup takes a day": a one-command start, and a documented tool list, or a dev container.
  • "Different tool versions break things": dev containers or a version manager.
  • "Services start in the wrong order": health-checked ordering, which Compose, Tilt, process-compose and Flisk all offer in different forms.
  • "Port numbers and URLs are confusing": a gateway such as Traefik. Flisk's Docker path includes one and serves *.localhost URLs.
  • "My laptop is too slow": a lighter loop, or a cloud workspace.
  • "I need production data": a cluster bridge.

Question 4: who writes the config?

Compose is YAML anyone can read. A Tiltfile is code that someone must own. Skaffold and DevSpace are YAML tied to Kubernetes concepts. A generator such as Flisk takes a small service.json per service and writes the Dockerfile, Compose and Tilt files itself, which suits teams who do not want to maintain those files, and costs you control over the generated parts. Flisk's own guidance is to avoid it when you have two or three stable services and a working Compose file.

Question 5: how easy is it to leave?

Every tool adds some lock-in. Prefer tools whose output you can read and run without them. Compose, Skaffold and Tilt files are plain files. For Flisk, flisk import . reads an existing docker-compose.yml into service.json files, and flisk eject writes an EJECTED.md describing the generated Tilt files and how to run them with plain Tilt. It copies nothing, so the generated files still depend on Flisk's inputs. See how to check a dev tool for lock-in.

Question 6: what is the smallest trial?

Run the tool against one service for one afternoon, with the person who will maintain it. Measure the things you care about with your own stopwatch: time from clone to running app, time from save to visible change, and number of files you edit to add a service. Do not trust anyone's benchmark, including a vendor's, until you have run yours.

If you want to see Flisk's side of that trial without installing a stack, npx @flisk-sh/flisk demo starts a demo, and without Docker it falls back to a two-service app of local processes. flisk doctor tells you what your machine is missing for your own project.

A short summary

  • Small and simple: scripts and a task runner.
  • Containers and a database: Compose, plus Tilt when you want live update and a dashboard.
  • Kubernetes inner loop: Skaffold, DevSpace, Garden or Tilt.
  • Same toolchain for everyone: dev containers.
  • Too much glue between services: a generator or an orchestrator, chosen from your trial.

When you have picked, adopt it step by step. How to adopt a local dev tool gradually shows how to start with one service.

Questions people ask

What is the simplest local dev setup for microservices?

A Docker Compose file for containers, or a process runner for plain commands. Add tools only when a specific problem such as ordering, routing or reload speed appears.

Should I use Kubernetes for local development?

Only if you work on Kubernetes features such as operators or manifests. If it is just the deploy target, a local loop without a cluster is lighter.

Can I use more than one of these tools?

Yes. Dev containers for the toolchain, Compose or Flisk for the services, and Skaffold or a kind cluster in CI for the manifests is a common split.
