Make vs just vs Task for project dev commands

A command runner gives the team one set of names for build, test and start. The three popular choices differ mostly in syntax and portability.

Use Make if it is already in your repo and your team knows it. Use just if you want Make's idea without Make's tab rules, quirks and file-timestamp logic. Use Task if you prefer YAML and want built-in file watching. For three commands, a scripts/ folder or the scripts block in package.json is enough. The goal is the same either way: one obvious way to run dev, test and lint.

Make

Make is on nearly every Linux and macOS machine. A Makefile is made of targets with commands, and Make's real feature is rebuilding only when file timestamps say so. That is a great fit for compiling C, and less so for "run the dev server", where you mark targets as .PHONY to turn that logic off.

.PHONY: dev test
dev:
	docker compose up -d db
	npm run dev

test:
	npm test

Pitfalls: recipe lines must start with a tab, every line runs in its own shell, and variables use $(VAR) and $$ escaping that surprises newcomers. On Windows you need a Make install and a compatible shell, or WSL.

just

just is a command runner, not a build system. A justfile looks like a Makefile without the timestamp logic. It supports recipe parameters, just --list to print the available recipes with their comments, and set dotenv-load to read a .env file. It runs on Linux, macOS and Windows.

set dotenv-load

# start the database and the dev server
dev:
    docker compose up -d db
    npm run dev

# run tests for one package
test pkg="api":
    npm --prefix {{pkg}} test

Cost: one more binary to install, and teammates need to learn a small syntax.

Task

Task (the task command) uses a Taskfile.yml. Tasks can declare dependencies with deps, run commands, set variables and load dotenv files. It can watch files with --watch, and it runs on all major platforms as a single binary. If your team is comfortable with YAML, the learning curve is gentle.

version: "3"
tasks:
  dev:
    deps: [db]
    cmds:
      - npm run dev
  db:
    cmds:
      - docker compose up -d db

What these tools do not do

A command runner starts commands. It does not wait for the database to accept connections, restart a crashed service, route traffic or show you merged logs. A make dev that runs five things in the background is a script with a good name, not an orchestrator. When the recipe starts to contain sleep 5 and wait-for-it lines, look at a tool built for processes. See concurrently vs mprocs vs process-compose.

Using one with Flisk

They combine well. The runner gives the names, and Flisk does the running. A recipe can be as small as flisk up for dev, flisk down for stop and flisk logs --service api --tail 100 for logs. For one-off tasks inside the stack, flisk run api -- npm run migrate runs a command with that service's environment (put -- before a command that has flags of its own). A make or just target that calls these keeps the habit the same for new teammates. Flisk is optional here, and if you only have two npm scripts, you do not need either.

Pitfalls

  • Do not duplicate logic. If npm test already works, the recipe should call it.
  • Document the runner in the README. See what to put in the README.
  • Avoid shell-specific features in recipes if teammates use different shells.

Questions people ask

Is just a replacement for Make?

For running project commands, yes. just does not rebuild based on file timestamps, so it is not a build system like Make.

Does Task support watching files?

Yes. The task command has a watch mode that reruns a task when its source files change.

Do I need a task runner for a small project?

No. The scripts block in package.json or a scripts folder is enough for a handful of commands.
