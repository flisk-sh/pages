Docker Compose for local development

Keep Docker Compose volumes between runs, or reset them

Your database should be there after a restart, and gone when you ask. Here is what decides which one you get.

Named volumes survive docker compose down. They are removed only by docker compose down -v, by docker volume rm, or by a prune. Data usually disappears for a different reason: the volume was never named, the Compose project name changed, or the mount path was wrong. In Flisk, flisk down keeps volumes and flisk down --purge deletes them.

What stays and what goes in Compose

  • Named volume (pgdata:/var/lib/postgresql/data): kept by down, removed by down -v.
  • Anonymous volume (a path with no name): gets a random name and is easy to lose track of. It is removed with down -v, and a new container creates a new one.
  • Bind mount (./data:/var/lib/postgresql/data): a folder on your disk. Compose never deletes it.
services:
  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

Compose prefixes the volume with the project name, which defaults to the directory name. Rename the folder, or run from a different folder, and Compose creates a new empty <newname>_pgdata volume. Your old data is still there under the old name. That is the most common "my database was wiped" story. Check with docker volume ls before you panic.

The mount path matters too. For Postgres 17 and earlier the data directory is /var/lib/postgresql/data. From Postgres 18 the image expects the volume at /var/lib/postgresql. Mounting the old path on a new image gives you a database that looks fine and loses its data when the container is replaced.

How Flisk handles volumes

For the Postgres that Flisk generates, flisk down runs tilt down, which removes containers but not named volumes. The next flisk up starts Postgres on the same volume. The volume name is built from the project and stack. For a project called my-shop it looks like my-shop-database-management_my_shop_postgres_data, and you can confirm yours with:

docker volume ls | grep postgres_data

flisk down --purge is the deliberate exception. After stopping the stack it deletes this project's Docker volumes (the database data), networks and images. Use it when you are done with a project or want an empty database. Preview first with flisk down --purge --dry-run.

Agent resources keep their state in a volume too, named like <project>-<stack>-autogenerated_<resource>-agent-state, so checkpoints survive restarts. The one preset that mounts no volume is the inference preset, so downloaded models are lost when its container is removed.

Volumes for bring-your-own services

A bring-your-own service declares its volumes in service.json. A source without a path is a named volume, and target is the absolute path in the container. Setting name to the Docker volume's own name, as docker volume ls shows it, mounts that existing volume as it is. Without name, the volume gets the generated project's prefix, so an old Compose volume like myapp_pgdata would not be found:

"volumes": [
  { "source": "pgdata", "target": "/var/lib/postgresql/data", "name": "myapp_pgdata" }
]

A named volume is kept by flisk down, and two services that name the same volume share it. A source starting with ./ or ../ is a bind mount relative to the service folder, and it must stay inside the project. flisk import writes name for you from the Compose file, so docker compose up and flisk up share the same data.

Start empty on purpose

Sometimes you want a clean database. For a bring-your-own volume, stop the stack first, then find and remove the volume by its full name:

flisk down
docker volume ls --filter label=com.docker.compose.volume=pgdata
docker volume rm <full volume name>

For the generated Postgres, flisk down --purge does the job. More ways to reset a database, including re-seeding, are in how to reset a local database.

Pitfalls

  • Do not relabel generated volumes by hand. Docker volume labels are fixed at creation, and Compose recreates a volume whose labels no longer match what it expects. That means your data is gone. Let Flisk create and name its own volumes.
  • Deleting a project folder does not delete its volumes. They sit on the Docker host until you remove them. flisk projects --stale lists what projects whose folders are gone left behind, and --prune removes it after asking.
  • Resource names must be unique across Flisk projects that share one Docker daemon, or two projects can end up fighting over a volume.
  • A full disk can damage Docker's image store, and the repair deletes every volume. Flisk stops flisk up when free space drops under 5 GiB for that reason. See what to do when Docker's disk is full.
  • Back up what matters. A volume is local state, not a backup. Dump a database you care about with pg_dump before any purge.

Questions people ask

Does docker compose down delete my volumes?

No. It removes containers and networks. Named volumes stay unless you add -v or remove them yourself.

Why is my database empty after I renamed the folder?

Compose prefixes volumes with the project name, which defaults to the folder name. A new name creates a new empty volume. The old one is still listed by docker volume ls.

How do I wipe the Flisk database?

Run flisk down --purge. It stops the stack and deletes the project's Docker volumes, networks and images. Add --dry-run to preview.
