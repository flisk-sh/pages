Run local services without Docker

If your services run fine on your laptop, you can skip the containers. Here is how to start them in order, wait for health and see the logs.

Give each service a command and a port in its service.json, then run flisk up. Flisk starts the services as ordinary processes on your machine, in dependsOn order, waits until each one is ready, and prefixes every log line with the service name. There is no Docker, no image build and no Tilt in this mode.

When plain processes are enough

Containers earn their keep when you need the same operating system and libraries as production, or a database image. For a Node, Python or Bun app that runs fine on your laptop, a container adds build time and file-sync trouble. Running the processes directly gives instant reload with the runtime's own watcher, simple debugging, and a machine that does not need Docker at all. That also helps on a laptop without Docker, and Flisk runs this mode on native Windows.

The general recipe works with any tool: a script or a process manager that starts each program, a fixed port for each, and a health URL to wait on. Flisk packages that recipe and checks for the usual mistakes.

A two-service example

Create one folder per service, each with its own service.json. The API:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

A web service that depends on it and gets its address through an environment variable:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "node web.js",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4000" }
}

The env map accepts ${VAR} and ${VAR:-default}, so values can come from your shell or .env. For a one-off secret such as a signing key, secrets.generate can produce a random value (hex:N or base64:N) and append it to .env.

If the repository is a plain Node project with a package.json that has scripts.dev or scripts.start and no service.json, Flisk can infer the service. Inferred state is stored in ~/.flisk/inferred/, not in your repo.

Start, watch and stop

flisk up --dry-run
flisk up
flisk status
flisk logs --service api --tail 50
flisk down

Use --dry-run first to see the plan. flisk up --only web starts one service and what it depends on, and --json gives machine-readable output. Ctrl+C stops everything.

How readiness works: Flisk starts services in dependsOn order and waits up to 60 seconds for each. A service is ready when its health URL answers. With no health path, it is ready when the port accepts connections. With neither, it is ready if the process is still running after one second. Logs also go to .flisk/native/logs/<service>.log.

If a process crashes, Flisk restarts it with a backoff of 1, 2, 4 and 8 seconds. After five quick exits it stops trying and says so. Set "restart": "no" on one-shot tasks.

What it refuses, and why that helps

Flisk checks before it launches anything and stops with a clear message when:

  • the program in command is not installed,
  • a port is already in use, naming the process: Port 4000 for service "api" is already in use by node (pid 48211). Stop it, or change "port" in the service.json.,
  • two services share one port, or
  • a dependsOn name does not exist.

The port message pairs with how to fix "port already in use".

Databases next to local processes

You usually still want Postgres in a container, and Flisk supports that mix. Declare the database as a bring-your-own service with an image, a port, a healthCheck.command and a named volume. The processes run on the host and the database runs in Docker, published on 127.0.0.1. flisk down keeps the named volume.

The restriction: one project cannot mix command services with services built from a Dockerfile. Flisk reports that as MIXED_RUNTIME. A database image is allowed, a Dockerfile build is not. If you do not want Docker at all, use a database that runs as a process or a local file such as SQLite.

Pitfalls

  • No isolation. Processes use your installed Node, Python or Go versions. "Works on my machine" is back, so pin versions in the repo.
  • Reload is the runtime's job. Use node --watch, bun --watch or uvicorn --reload in the command. See Docker Compose hot reload for the container side.
  • No gateway. You use localhost:port URLs, not *.localhost names behind Traefik.
  • Different from production. If production runs in containers, test the image before you ship.

To see this mode without writing anything, run npx @flisk-sh/flisk demo. When Docker is not running, the demo falls back to a two-service app as local processes. For a broader view of running a service set on a laptop, read local development without Kubernetes.

Questions people ask

Can I run a database without Docker in this mode?

Flisk can run a database image in Docker next to local processes, as a bring-your-own service. If you want no Docker at all, use a database that runs as a process or a file, such as SQLite.

Can I mix local processes and Dockerfile builds?

No. A project cannot mix command services with services built from a Dockerfile, and Flisk reports MIXED_RUNTIME. A database image next to local processes is supported.

Does it work on Windows?

Native Windows runs the local process mode. The Docker container path needs WSL2.
