How to use git worktrees to run coding agents in parallel

Give each coding agent its own checkout with git worktree so parallel tasks do not trample each other, then merge, clean up and avoid port and database clashes.

Create one git worktree per task with git worktree add, start one agent in each, and merge the branches when they finish. Each worktree has its own files and branch but shares one repository, so it is faster and lighter than cloning again.

Why not just one checkout

Two agents editing the same folder overwrite each other, and one agent switching branches breaks the other. Separate worktrees remove that. Each agent sees a stable branch, runs its own tests and produces one diff you can review on its own.

Create and use worktrees

# from the main checkout
git worktree add ../app-rate-limit -b agent/rate-limit
git worktree add ../app-fix-login -b agent/fix-login

cd ../app-rate-limit && claude   # or your agent of choice

git worktree list

Each folder is a full working tree on its own branch. You cannot check out the same branch in two worktrees at once, which is a useful guard.

Install and run per worktree

A worktree does not copy ignored files. Dependencies, .env files and build output are missing. Run your install command in each one. Copy a template .env.example and never copy real secrets by habit. A short script for this saves time:

#!/usr/bin/env bash
set -euo pipefail
name="$1"
git worktree add "../$(basename "$PWD")-$name" -b "agent/$name"
cd "../$(basename "$PWD")-$name"
npm ci

Avoid clashes outside git

Git separates files, not ports or databases. Two worktrees starting a dev server on port 3000 will fight. Give each its own port through an environment variable, and use a separate database name or a throwaway container per worktree. Tools that run your services from a manifest can help here: the Flisk CLI starts a local stack from service.json files, and FliskOS is a desktop app to run several coding agents. Both are tools to try, not requirements.

Merge and clean up

Review each branch as a pull request, see reviewing AI-generated PRs, then merge. Remove the worktree and branch:

git worktree remove ../app-rate-limit
git branch -d agent/rate-limit
git worktree prune

Do not delete worktree folders by hand or with wildcards, since another session may be using one. Use git worktree list first. Limit yourself to as many parallel agents as you can review: usually two to four.

Pitfalls

Worktrees share the same git object store, so a hook or a stash in one affects the others. Long-running branches drift from main, so rebase often. Editors can get confused when you open the same project from two folders, so use one window per worktree. And remember disk: each worktree has its own node_modules or virtualenv.

Questions people ask

Is a worktree the same as a clone?

No. A worktree shares the same .git data with the main checkout, so it is quicker to create and uses less disk, but branches and stashes are shared.

What if two agents change the same file?

You will get a merge conflict. Reduce it by giving each agent a different area, and merge the smaller change first.
