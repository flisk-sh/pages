Coding agents in practice

How to review AI-generated pull requests quickly

A review checklist for agent-written changes: read the tests first, check scope, look for fake success, verify behaviour, and know what to skim and what never to skip.

Read the tests before the code, check that the diff only touches what the task needed, and run the change yourself. Agent code usually looks tidy, so the risk is not style. It is wrong assumptions, quietly weakened tests and changes outside the brief.

Start with the description and the tests

Ask the agent for a short summary: what changed, why, and how it was verified. Then read the tests. If the tests describe the behaviour you asked for and would fail without the change, you have a map for the code. If there are no new tests for new behaviour, send it back.

Check scope first

git diff --stat main...HEAD
git diff main...HEAD -- package.json package-lock.json

Look at the list of files before the content. Files you did not expect are the first red flag: config changes, lockfile churn, a reformatted unrelated module, edited generated files. New dependencies need a reason you accept.

Look for these failure patterns

  • Weakened tests: an assertion loosened, a test skipped, a timeout raised, an expected value edited to match the bug.
  • Fake success: a function that returns a hard-coded value, a catch block that swallows errors, a mock that hides the real call.
  • Invented APIs: calls to functions or options that do not exist in your version of a library.
  • Silent scope creep: refactors nobody asked for.
  • Security basics: string-built SQL, unchecked input, secrets in logs, new network calls.

Run it

Check out the branch, run the test suite, then use the feature by hand once. Agents say "all tests pass" when they ran a subset, or ran them before a late edit. Run the full checks yourself, or let CI do it. A guard that fails the build on lint, types and tests saves you from re-checking basics. See CI guards and AI code review.

Review in layers

RiskReview depth
Auth, payments, data deletion, migrationsLine by line, plus a second person
Business logicRead the code and the tests
Docs, renames, test-only changesSkim and run the checks

If a diff is too large to review in one sitting, do not approve it. Ask for smaller changes, as described in writing a brief.

Ask the agent to help you review

Before you read, ask the agent that wrote the change: "list the assumptions you made, the files you were unsure about, and what you did not test". The answers are often honest and point you at the weak spots. It does not replace your review, but it makes the first pass faster and more targeted.

Questions people ask

Can another model review the code instead?

It can catch real issues and is a useful extra pass, but it is not a replacement for tests and a human on risky changes.

How do I stop reviewing the same mistakes?

When you see a repeated problem, turn it into a lint rule, a test or a line in the project instructions file.
