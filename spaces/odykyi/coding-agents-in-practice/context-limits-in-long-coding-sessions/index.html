Coding agents in practice

How to handle context limits in long coding sessions

Why agents get worse as a session grows, and how to manage it: clearing, compacting, notes in files, small tasks and starting fresh without losing the plan.

The longer a session runs, the more the agent has to carry, and quality drops: it forgets earlier decisions, repeats work and mixes up files. Keep tasks small, write the plan and progress to a file, and start a fresh session between tasks instead of stretching one forever.

What goes wrong

Every message, file read and command output takes space in the context window. When it fills, older content is dropped or summarised. Even before that limit, a huge noisy context makes the model less focused. Signs: it re-asks things you already said, edits the wrong file, or undoes an earlier fix.

Use the session controls

Most agents offer a way to clear the conversation and a way to compact it into a summary. In Claude Code these are the /clear and /compact commands. Compact when you are mid-task and want to keep the thread. Clear between unrelated tasks. Compaction keeps a summary, not every detail, so state key constraints again after it.

Keep the plan in a file

A file survives any reset. For a multi-step task, ask the agent to write a plan and keep it updated:

Create PLAN.md with the steps for this migration as a checklist.
Tick each item when it is done and tested. Add a Notes section for
decisions and gotchas. Read PLAN.md at the start of each session.

Now a fresh session can resume from the file. Do not commit the plan file unless you want it in history. See the agent memory and context hub for the general idea.

Keep output small

  • Ask for failing test names only, not entire logs: run tests with a quiet reporter.
  • Point to files and line ranges instead of asking it to read a whole directory.
  • Do not let it paste large generated files or lockfiles into the conversation.
  • Use a project instructions file for stable rules instead of repeating them each time.

Split work at natural seams

One task per session is a good rule: one bug, one feature, one migration step. Commit when a task is done, then clear and start the next. If the next task depends on the first, the commit message and the plan file carry the knowledge. If you get stuck in circles in a long session, see what to do when an agent loops.

Pitfalls

Compaction can lose a constraint you stated early, such as "do not touch the public API". Re-state hard rules after compacting, or keep them in the project instructions file where they are re-read. Another trap is pasting a long log "for context". Paste the first error and a few lines around it instead.

Questions people ask

Is a bigger context window the fix?

It helps with large files, but focus still degrades with clutter. Small, clear contexts usually give better results than one giant one.

What should I re-state after compacting?

The goal, hard constraints, the done criteria and which files are in play.
