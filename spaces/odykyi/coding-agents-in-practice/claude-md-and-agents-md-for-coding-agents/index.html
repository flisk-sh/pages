CLAUDE.md and AGENTS.md: what to put in them

What goes in a project instructions file for coding agents, what to leave out, and how to keep it short enough that the agent actually follows it.

CLAUDE.md is the project instructions file that Claude Code reads, and AGENTS.md is a common, tool-neutral name that other coding agents, such as Codex, read. Put the commands to build and test, the layout of the repo and the rules that are easy to get wrong. Keep it short, because a long file gets skimmed by the model too.

What belongs in it

  • Commands: install, build, test, lint, typecheck. The exact strings.
  • Layout: where code, tests and generated files live, in a few lines.
  • Rules with a reason: "do not edit files under dist/, they are generated by npm run build".
  • Traps: things that failed before, such as a flaky test or a command that needs an environment variable.
  • Definition of done: what must pass before a change is ready.

A compact example

# AGENTS.md

## Commands
- Install: npm ci
- Test: npm test (single file: npm test -- path/to/file.test.ts)
- Lint: npm run lint
- Typecheck: npm run typecheck

## Layout
- src/ application code, tests/ tests, dist/ generated (never edit)

## Rules
- Run lint and typecheck before saying a task is done.
- New behaviour needs a test in the same change.
- Do not add dependencies without asking.

## Traps
- tests/e2e needs Docker running; skip it unless asked.

What to leave out

Do not paste your whole style guide, a project history or the README. Do not include rules a linter already enforces: let the linter say it, and the agent will fix it. Do not include secrets. Avoid vague advice such as "write clean code", which changes nothing.

One file or two

If you use more than one agent, keep one source of truth. Some teams keep AGENTS.md and make CLAUDE.md a one-line file that points to it, or a symlink. Check each tool's documentation for how it finds and merges instruction files, since this changes over time. Nested files in subfolders can hold rules for just that part of a monorepo.

Maintain it like code

When an agent makes the same mistake twice, add one line to the file. When a line stops being true, delete it. Review changes to it in pull requests. Treat a mistake as a missing sentence or a missing check. If it can be a check, such as a lint rule or a test, make it one, because checks cannot be ignored. More on writing for agents in the docs and READMEs hub.

Test the file

Open a fresh session and ask the agent: "how do I run the tests here and what must I not edit?" If the answer is wrong or vague, fix the file. Do this after every large edit. It takes one minute and it is the fastest way to find lines the model ignores or misreads.

Questions people ask

How long should the file be?

Aim for under about a hundred lines. If it grows, split rules into nested files for subfolders, or turn rules into automated checks.

Does the agent always obey it?

No. It is guidance, not enforcement. For rules that must hold, add a hook, a lint rule or a CI check.
