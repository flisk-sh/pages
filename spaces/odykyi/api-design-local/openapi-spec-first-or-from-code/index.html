OpenAPI: write the spec first or generate it from code?

Both approaches work. The mistake is having two sources of truth that drift apart, so pick one and let a check enforce it.

Write the OpenAPI spec first when other teams or clients need to agree on the API before the code exists. Generate it from code when one team owns both sides and the code is the thing you actually change every day. Whichever you choose, commit the spec file and add a check that fails when the file and the running API disagree.

The two approaches

Spec-first (design-first) means you write openapi.yaml by hand, review it like code, and then build the server and clients against it. Frontend and backend can start on the same day, because a mock server can answer from the spec while the real one is still empty. The cost is that the spec is a second place to edit, and a handler that returns a field the spec does not list is easy to miss.

Code-first means the framework builds the spec from your routes and types. FastAPI does this by default: it serves the schema at /openapi.json and a Swagger UI at /docs. In the Node world you add a library, for example @hono/zod-openapi for Hono or swagger-jsdoc with swagger-ui-express for Express. The spec is always as accurate as your annotations, but design review happens after code is written, and a refactor can change the public contract without anyone noticing.

A common middle path: generate the spec from code, commit it, and review its diff in every pull request. You get the accuracy of code-first and the design review of spec-first.

Export the spec from a FastAPI service

You do not need a running server to get the file. FastAPI builds the schema from the app object:

python -c "import json; from main import app; print(json.dumps(app.openapi(), indent=2, sort_keys=True))" > openapi.json

Sorting keys keeps the diff small. Commit openapi.json, and in CI regenerate it and compare:

python -c "import json; from main import app; print(json.dumps(app.openapi(), indent=2, sort_keys=True))" > /tmp/openapi.generated.json
diff openapi.json /tmp/openapi.generated.json

If the diff is not empty, someone changed the API without updating the committed contract. The same idea works in any framework that can print its schema.

See the live docs while you edit

Swagger UI is most useful when it reloads with your code. With Flisk, describe the service as a local process. This service.json runs FastAPI with uvicorn's own reload:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "command": "uvicorn main:app --reload --port ${PORT:-8000}",
  "port": 8000,
  "healthCheckPath": "/health"
}

Run flisk up from the project folder. Flisk starts the process, waits until /health answers, and prints http://localhost:8000. Open /docs there. Without Docker, the reload comes from --reload in the command, not from Flisk. To fetch the spec from the running service instead of importing the app:

curl -s http://localhost:8000/openapi.json -o openapi.json

This is the better route when the spec depends on things the running app builds, such as plugins or routes registered at startup. Your service needs a /health route for healthCheckPath; without one, drop that line and Flisk waits for the port instead.

Spec-first without losing the server

If you write the YAML yourself, make the spec do real work: lint it (see linting with Spectral), run a mock from it (mock server with Prism), and test the real server against it. A tool such as Schemathesis reads the spec and sends generated requests to the running API, reporting responses that break it. The related question of keeping a frontend in sync is covered in keeping a frontend and backend contract in sync.

Pitfalls

  • Do not hand-edit a generated spec. The next export overwrites your change. Fix the annotations or the model instead.
  • Examples matter. Mocks and docs are only as useful as the example values in the schema. Generated specs often lack them, so add them to your models.
  • Internal routes leak. Code-first tools document every route by default. Hide admin and debug endpoints from the public spec with the framework's option for it (in FastAPI, include_in_schema=False).
  • Version the file, not just the API. The info.version field is yours to maintain; generators fill it with a placeholder unless you set it.

Once you have a committed spec, the next useful step is guarding it against accidental breaking changes, which is the subject of detecting breaking API changes.

Questions people ask

Can I use both spec-first and code-first?

Yes. A common setup generates the spec from code, commits it, and reviews its diff in pull requests. CI regenerates the file and fails when it differs from the committed copy.

Where does FastAPI serve the OpenAPI schema?

At /openapi.json by default, with Swagger UI at /docs and ReDoc at /redoc. You can also print it without a server with app.openapi().

Does Flisk generate an OpenAPI spec?

No. Flisk starts and watches your service. The spec comes from your framework or from a file you write.
