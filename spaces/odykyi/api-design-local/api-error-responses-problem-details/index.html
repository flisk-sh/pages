API error responses: use RFC 9457 problem details

Clients write one error handler if every endpoint fails the same way. RFC 9457 gives you that shape without inventing your own.

RFC 9457 "Problem Details for HTTP APIs" defines a JSON error body with the media type application/problem+json and five standard members: type, title, status, detail and instance. Return that shape from every endpoint and clients can write one error handler instead of one per route. It replaces RFC 7807, with the same format.

The problem with ad-hoc errors

Without a convention, one endpoint returns {"error": "not found"}, another {"message": "Invalid", "code": 12}, and a third an HTML page from the framework's default handler. A client then needs a parser per endpoint and still cannot tell a validation error from an outage. A shared shape fixes this, and a standard shape means existing libraries and your own future self already know it.

The shape

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request is not valid",
  "status": 422,
  "detail": "The field quantity must be at least 1.",
  "instance": "/orders",
  "errors": [
    { "pointer": "/quantity", "message": "must be at least 1" }
  ],
  "trace_id": "01HZX3K4..."
}
  • type is a URI that identifies the kind of problem. Clients branch on it, not on the text. It may be a page that documents the problem, and if you omit it the default is about:blank.
  • title is a short, human-readable summary that stays the same for one type.
  • status repeats the HTTP status, useful when the body is logged without headers.
  • detail explains this occurrence. Write it for a developer, not for end users.
  • instance identifies this occurrence, often the request path or an ID.
  • errors and trace_id are extension members. The RFC lets you add your own. Use one for field-level validation errors and one for a request or trace ID that matches your logs.

Implement it once

Do it in a single place, an error-handling middleware, so no route can forget. In Express:

app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  res.status(status).type('application/problem+json').json({
    type: err.type ?? 'about:blank',
    title: status < 500 ? err.title ?? 'Request failed' : 'Internal error',
    status,
    detail: status < 500 ? err.message : undefined,
    instance: req.originalUrl,
    trace_id: req.id,
  });
});

Note what the handler does for a 5xx: it hides the message. A stack trace, an SQL error or an internal hostname must never reach the client. Log the full error on the server with the same trace_id. FastAPI users override the exception handlers for HTTPException and RequestValidationError to return the same shape, since its default 422 body is a different format.

Pick status codes on purpose

  • 400 for a malformed request, 422 for a well-formed one that fails validation. Choose one convention for validation and keep it.
  • 401 when the caller is not authenticated, 403 when they are but may not do this, 404 when the thing does not exist (or you do not want to reveal it does).
  • 409 for a conflict such as a duplicate; 429 with a Retry-After header for rate limits.
  • 5xx only for your faults. A client sending bad input and getting 500 hides a bug in your validation.

Document the error schema once in OpenAPI as a reusable component and reference it from every 4xx and 5xx response. A Spectral rule can enforce that (linting your spec).

Check it on a running service

Start the service and look at a failing call, headers included, because the media type is part of the contract:

flisk up
curl -i -X POST http://localhost:4000/orders -H 'Content-Type: application/json' -d '{"quantity":0}'
flisk logs --service orders-api --tail 50

Use your service name, URL and port. flisk logs --service <name> --tail <n> prints the recent output of one service, so you can match the trace_id in the response to the log line with the real cause. If it is not there, your handler is not logging the original error. For more on reading logs across services, see reading logs from every service.

Pitfalls

  • Do not parse title or detail in clients. They are for humans and can change. Branch on type or your own stable code.
  • Leaking internals. Detail strings that echo a SQL fragment or a file path are a security problem. Review them like you review logs.
  • Proxies and gateways. An HTML 502 from a proxy will not follow your format. Clients still need a fallback for non-JSON bodies.
  • Success shapes too. A consistent error format does not help if success and failure share a 200. Use the status code.

Mock these errors in the frontend with a documented 404 example and a Prefer: code=404 header, as shown in the Prism mock guide.

Questions people ask

What is the difference between RFC 7807 and RFC 9457?

RFC 9457 obsoletes RFC 7807 and keeps the same format, with clarifications and guidance for multiple problems in one response.

What media type do problem details use?

application/problem+json, or application/problem+xml for XML. Send it in the Content-Type header.

Can I add my own fields?

Yes. The RFC allows extension members, such as an errors array for field validation or a trace_id. Clients must ignore ones they do not know.
