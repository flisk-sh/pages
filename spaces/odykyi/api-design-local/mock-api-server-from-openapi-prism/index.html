How to run a mock API server from an OpenAPI file with Prism

A mock built from the spec lets the frontend team work today and keeps requests honest, because Prism rejects calls that break the contract.

Prism, from Stoplight, reads an OpenAPI file and serves a mock API from it. Run npx @stoplight/prism-cli mock openapi.yaml and every path in the spec answers with its documented example response on port 4010. Frontend work can start before the backend does, and the spec stays the single source of truth.

What a spec-driven mock gives you

A hand-written mock (a JSON file behind a tiny server) tends to drift. A mock generated from the spec cannot invent endpoints the spec does not have, and it checks the requests you send. Prism validates the request body, parameters and security headers against the spec. A bad request gets a 422 with the reasons, so you find a wrong field name in the frontend while building it, not at integration time.

The limits are real: a mock has no state. A POST does not make the next GET return the new item. For flows that depend on data you need a real service or a hand-written fake (see mock or run the real service).

Start the mock

Take a small spec:

openapi: 3.0.3
info: { title: Orders, version: 1.0.0 }
paths:
  /orders/{id}:
    get:
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        "200":
          description: One order
          content:
            application/json:
              schema:
                type: object
                properties:
                  id: { type: string }
                  status: { type: string, enum: [pending, paid, shipped] }
                example: { id: "o_1", status: paid }
        "404":
          description: Not found
          content:
            application/json:
              example: { title: Not found, status: 404 }

Then run:

npx @stoplight/prism-cli mock -p 4010 openapi.yaml
curl -i http://127.0.0.1:4010/orders/o_1

You get the 200 example. Prism picks the response from the request:

  • Prefer: code=404 returns the documented 404. This is how you test the error path in a UI without touching a database.
  • Prefer: example=name picks one of several named examples.
  • -d (dynamic mode) generates values from the schema instead of using the static example.
curl -i -H "Prefer: code=404" http://127.0.0.1:4010/orders/o_1

Prism also has a proxy mode that forwards requests to a real upstream and reports where the traffic differs from the spec. That is useful once the backend exists and you want to find drift without writing tests first.

Run it next to the rest of your stack

You want the mock to start with everything else, not in a forgotten terminal tab. With Flisk, give the mock its own folder, put openapi.yaml in it, and add a service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-mock",
  "appType": "backend",
  "command": "npx @stoplight/prism-cli mock -h 127.0.0.1 -p ${PORT:-4010} openapi.yaml",
  "port": 4010
}

The command runs from the service folder, so openapi.yaml resolves there. Prism has no health route, so there is no healthCheckPath: Flisk treats the service as ready when the port accepts connections. Then point the frontend at it:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["orders-mock"],
  "env": { "API_URL": "http://localhost:4010" }
}

flisk up starts the mock first, then the site. When the real API is ready, change one line: the API_URL value. The frontend code does not change, which is the point. How the env var reaches your dev server depends on the tool; for Vite, see the Vite API URL guide.

Check the first start with flisk up --dry-run, which prints each service, its command and the start order without running anything. If the port is taken, Flisk names the process holding it and stops.

Use the mock in tests as well

The same mock can back automated frontend tests, so they do not depend on a database or on another team's service being up. Start it in the test setup, point the app at its URL and use the Prefer header to drive the error cases: a loading state, an empty list, a 404, a 500. Because the answers come from the spec, a test that passes today will still pass tomorrow unless the contract changes, and then the failure points at the spec diff instead of at a flaky network.

Pitfalls

  • Examples decide everything. A spec with no examples gives Prism nothing realistic to return, so it produces generic values. Write examples for the responses the UI depends on.
  • The mock only knows the spec. If the spec is wrong, the mock is wrong in the same way. Check the real service against the spec too.
  • Auth. If the spec declares a security scheme, Prism requires the header to be present, though it does not verify a token. Send any value while testing.
  • Do not use it for load or for stateful flows. It is a contract tool, not a fake database.

Once the spec is good enough to mock, protect it: lint it with Spectral so examples and descriptions stay present.

Questions people ask

What port does Prism use?

4010 by default. Change it with the -p flag, for example prism mock -p 5000 openapi.yaml.

How do I make Prism return an error response?

Send the header Prefer: code=404 (or another documented status) and Prism answers with that response from the spec.

Does Prism keep state between requests?

No. A POST does not change what a later GET returns. Use a real service or a hand-written fake for stateful flows.
