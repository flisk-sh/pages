How to deprecate an API endpoint with a Sunset header

Removing an endpoint is a breaking change. A dated warning in every response gives clients time to move.

To deprecate an endpoint, keep it working, add a Deprecation header to its responses, add a Sunset header with the date it will stop working, link to the replacement with a Link header, tell your consumers outside HTTP too, and remove it only after the date and after traffic has dropped to zero. The headers are standard, so tools and client libraries can read them.

The standard headers

Two RFCs cover this:

  • Deprecation (RFC 9745) says the resource is deprecated, and since when. Its value is a date written as a Structured Fields date, which is a Unix timestamp with an @ prefix.
  • Sunset (RFC 8594) says when the resource is expected to become unavailable. Its value is an ordinary HTTP date.

A response for a deprecated endpoint looks like this:

HTTP/1.1 200 OK
Deprecation: @1767225600
Sunset: Wed, 30 Sep 2026 23:59:59 GMT
Link: <https://api.example.com/v2/orders>; rel="successor-version",
      <https://docs.example.com/migrate-orders>; rel="deprecation"; type="text/html"
Content-Type: application/json

@1767225600 is the timestamp of 1 January 2026 in UTC. The Link relations tell a human or a script where to go next: successor-version for the replacement and deprecation for the migration notes. Sunset must not come before the deprecation date, and you should treat the Sunset date as a promise, not a guess.

Add it in one place

Do not add headers by hand to each handler. Use a middleware that wraps a route or a router:

const deprecated = ({ since, sunset, successor }) => (req, res, next) => {
  res.set('Deprecation', `@${Math.floor(new Date(since).getTime() / 1000)}`);
  res.set('Sunset', new Date(sunset).toUTCString());
  res.append('Link', `<${successor}>; rel="successor-version"`);
  next();
};

app.use('/v1/orders', deprecated({
  since: '2026-01-01T00:00:00Z',
  sunset: '2026-09-30T23:59:59Z',
  successor: 'https://api.example.com/v2/orders',
}), ordersV1);

Also mark the operation in your OpenAPI file with deprecated: true. Docs, generated clients and linters then show the warning, and a Spectral rule can require every deprecated operation to have a description that names the replacement (see linting your spec). Removing the operation later will show up in the spec diff as breaking, which is expected (detecting breaking changes).

A deprecation plan that works

  1. Ship the replacement first. The new endpoint must be live and documented before the old one is marked deprecated. See running two versions side by side.
  2. Announce through more than headers. Most clients never read headers. Email known consumers, add a changelog entry and a banner in the docs.
  3. Pick a period you can defend. For a public API, months, not weeks. For an internal API with a few known callers, a sprint may do. Write the period in your API policy.
  4. Measure usage. Log each call to a deprecated route with the caller's identity (API key, client ID or user agent). Use that to chase the stragglers by name.
  5. Brown out, then remove. A few days before the date, make the endpoint fail for short, announced windows. Clients that ignored all warnings notice, and you find them while rollback is still easy.
  6. After the date, return 410 Gone with a problem-details body that names the replacement (error response format), and keep that answer for a while before deleting the route.

Test the headers

A deprecation header is part of the contract, so assert it. A quick manual check:

curl -sI http://localhost:4000/v1/orders | grep -iE '^(deprecation|sunset|link):'

Replace the URL with your service's. Better, make it a request test that fails when the header goes missing, so a refactor cannot silently drop it.

What to tell consumers

A good deprecation notice is short and answers five questions: what is deprecated, what replaces it, what changes for the caller (a field renamed, a new required header), the date it stops working, and who to contact. Send the same text by email, put it at the top of the endpoint's documentation and link it from the deprecation link relation shown above. If a consumer cannot meet the date, they should be able to tell you before the date, not after the outage. Keep a list of affected consumers and tick them off as their traffic moves, which is much easier when usage is logged by client as suggested in step four.

For internal APIs the same rules apply on a smaller scale. Even if you can read every caller's code, a sunset date in the response and a note in the team channel prevents the case where a service nobody remembers still calls the old route.

Pitfalls

  • Silent deprecation. A header nobody reads is not an announcement. Contact the owners.
  • Moving the date. Extending a Sunset is fine. Shortening it breaks trust and agreements.
  • Header support in clients. Many HTTP libraries ignore these headers. Some API gateways and SDK generators surface them, but do not rely on it.
  • Caches and proxies. Make sure they pass the headers through, and that cached responses do not outlive the removal.

Questions people ask

What is the difference between Deprecation and Sunset?

Deprecation says a resource is deprecated and since when. Sunset says when it will stop working. A resource can be deprecated for a long time before its sunset date.

What status code should a removed endpoint return?

410 Gone is the clearest, ideally with a body pointing to the replacement. 404 also works but says less.

What format does the Deprecation header use?

A Structured Fields date: an @ followed by a Unix timestamp in seconds, for example Deprecation: @1767225600. Sunset uses an ordinary HTTP date.
