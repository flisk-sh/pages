AI sandboxes for agents

How to limit network access for an agent sandbox

Block exfiltration without breaking the job: no network, internal networks, an allowlist proxy, DNS limits and logging of every outbound request.

Start with no network at all and add only what the job needs. If the code must reach the internet, send it through a proxy that allows a short list of hostnames and logs each request, and make the sandbox unable to reach anything else.

Why network is the main risk

Most damage from agent code is data leaving: source code, tokens or customer records sent to a host the attacker controls. Files and CPU limits do not stop that. Network rules do.

Option 1: none

Many jobs need no network: data transforms, tests with vendored dependencies, formatting. Use it:

docker run --rm --network none my-sandbox-image python main.py

Option 2: an internal network and a proxy

Create a Docker network marked internal, which has no route to the outside. Put an allowlist proxy on both that network and a normal one.

docker network create --internal sandbox-net
docker run -d --name egress --network sandbox-net my-proxy-image
docker network connect bridge egress
docker run --rm --network sandbox-net \
  -e HTTPS_PROXY=http://egress:3128 \
  my-sandbox-image python main.py

The sandbox can reach only the proxy. The proxy decides which hostnames to forward. Squid, tinyproxy or a small custom proxy all work. Remember that the proxy variable is only a hint to well-behaved clients: the real enforcement is that the internal network has no other route.

Allowlist by hostname, not by IP

Cloud services change IPs, so allow by hostname at the proxy. Keep the list short, for example your package mirror and one API. Deny everything else, including raw IP addresses and cloud metadata addresses such as 169.254.169.254, which can leak instance credentials when you run on a cloud VM.

Watch DNS and log everything

Data can leave inside DNS lookups to a hostname the attacker controls. If the sandbox has no direct DNS and only talks to the proxy, that path is closed. At the proxy, log the time, the sandbox id, the host and the byte count of every request. Alert on unusual volume. Those logs also help you decide later which hosts to allow permanently.

For the surrounding controls, see sandbox secrets and resource limits.

Test it

From inside the sandbox, try a request to an allowed host, a blocked host, a raw IP address, and the metadata address. Only the first should work. Repeat the test after any change to your proxy or network setup. A rule you never tested is a rule you do not have.

Questions people ask

Can the agent still pip install?

Only through an allowed package mirror or a build step with network that runs before the offline run. Do not give the code step open internet access.

Does --network none block localhost?

Processes inside the container can still talk to each other on loopback. They cannot reach the host or outside.
