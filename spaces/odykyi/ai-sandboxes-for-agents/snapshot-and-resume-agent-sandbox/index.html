How to snapshot and resume an agent sandbox

Keep an agent's working state between steps: volumes, docker commit, image layers and microVM snapshots, with the trade-offs of each approach.

For most agents, keep the workspace on a named volume or in a git repository and rebuild the container each step. Use filesystem-level snapshots when you need exact state, and memory-level microVM snapshots only when startup speed matters enough to justify the complexity.

What state you actually need

Decide first what has to survive. Usually it is files: the repository, generated outputs and installed packages. Running processes and memory rarely matter. If you only need files, you do not need a true snapshot.

Approach 1: a volume or a git checkout

Mount a named volume for the workspace and start fresh containers on it.

docker volume create ws-session-17
docker run --rm -v ws-session-17:/work -w /work my-image python step1.py
docker run --rm -v ws-session-17:/work -w /work my-image python step2.py

To restore an earlier point, commit the workspace to git after each step and check out the commit. That also gives the agent and you a readable history.

Approach 2: docker commit

Keep a container alive, then save its filesystem as an image.

docker commit job42 sandbox-snap:step3
docker run --rm -it sandbox-snap:step3 bash

This captures installed packages and files, but not running processes. Images pile up, so tag them by session and delete old ones with docker image prune. Do not commit images that contain secrets.

Approach 3: microVM snapshots

Firecracker can save the full memory and device state of a microVM and restore it later, so a sandbox resumes with processes still running. This gives fast starts and exact resume, which is why hosted platforms use it. The cost: snapshot files are large, restoring many copies of one snapshot needs care so they do not share secrets or random seeds, and you have to manage the files. Check the Firecracker documentation for the snapshot API before relying on it.

Pick by need

NeedUse
Keep files between stepsVolume or git
Reuse an installed environmentA built image, tagged by dependency hash
Resume a running processMicroVM snapshot, usually via a provider

Whichever you use, set a time to live and delete idle sandboxes, since stored state also costs money. See sandbox cost per run.

Pitfalls

Snapshots can capture things you did not mean to keep: tokens written to disk, shell history, cached credentials. Scrub them before saving, or never put them in the sandbox at all. Also watch for stale state. A restored sandbox may have an old clock, an expired token or a package index from last week, so refresh what matters after a resume.

Questions people ask

Can docker checkpoint save a running container?

Docker has an experimental checkpoint feature based on CRIU. It is not reliable for every workload, so test it on your own images before depending on it.

How long should I keep a sandbox idle?

Minutes to hours for interactive agents, depending on cost. Store durable results outside the sandbox so deleting it loses nothing important.
