Background jobs and queues locally

How to run RabbitMQ for local development with a management UI

RabbitMQ is a good fit when you need routing rules, per-message TTLs or dead-letter exchanges. Here is how to run it locally and look inside it.

The quickest local RabbitMQ is the rabbitmq:4-management image with ports 5672 (clients) and 15672 (the management UI) published to your machine. Flisk writes an equivalent definition for you with flisk resource broker --type queue --framework rabbitmq, so the broker starts with the rest of your stack and its URL reaches the services that depend on it.

RabbitMQ or NATS

Both move messages between services. Pick by the features you need, not by habit.

  • RabbitMQ has exchanges and routing keys, per-queue and per-message TTL, dead-letter exchanges, priorities, and a management UI that shows every queue. It speaks AMQP, and clients exist for every language.
  • NATS with JetStream is smaller and simpler to run, with subjects instead of exchanges. See NATS for local development.

If your production system already uses RabbitMQ, use it locally too. Differences between brokers are where integration bugs hide.

The plain Docker way

docker run --rm --name rabbit \
  -p 127.0.0.1:5672:5672 -p 127.0.0.1:15672:15672 \
  -v rabbit-data:/var/lib/rabbitmq \
  rabbitmq:4-management

Open http://127.0.0.1:15672 and sign in with guest and guest. The guest account is a built-in default meant for local use. RabbitMQ restricts it to loopback connections in a normal install, and the Flisk resource below relaxes that restriction so other containers can connect. Never copy that setting to a server.

The Flisk way

flisk resource broker --type queue --framework rabbitmq --stack shop --yes

The generated service.json (CLI 1.4.57) includes these fields:

{
  "appName": "broker",
  "appType": "bring-your-own",
  "framework": "rabbitmq",
  "port": 5672,
  "image": "rabbitmq:4.1-management-alpine",
  "exposeViaProxy": false,
  "healthCheck": { "command": ["rabbitmq-diagnostics", "-q", "ping"] },
  "extraPorts": [{ "port": 15672 }],
  "volumes": [{ "source": "broker-data", "target": "/var/lib/rabbitmq" }],
  "provides": { "AMQP_URL": "amqp://guest:guest@broker:5672" }
}

It also sets two parameters, a node name and an Erlang argument that lets guest connect from other containers. The management UI is published on http://127.0.0.1:15672, with guest and guest. Flisk binds extra ports to 127.0.0.1, so the UI is not open to your network.

The health check uses rabbitmq-diagnostics -q ping, so services that depend on the broker wait until it answers. Add it to a consumer:

"dependsOn": ["broker"]

That consumer then gets AMQP_URL as an environment variable. Run flisk config verify after editing, and flisk up shop to start. The named volume broker-data keeps queues between runs, so flisk down does not clear them.

Publishing and connecting

Services in the stack read AMQP_URL and use it as is. The host in that URL, broker, is the service name, so it resolves only for other services in the stack. A tool on your own machine needs 127.0.0.1 and a published port 5672. The resource publishes the management port for you, and I did not test publishing 5672 as well, so check that the port answers, or use the plain Docker command above for ad hoc experiments.

When you publish from Node, mark messages persistent, or a broker restart loses them even from a durable queue:

ch.sendToQueue("jobs", Buffer.from(JSON.stringify(job)), { persistent: true });

Both parts are needed: a durable queue keeps the queue definition, and a persistent message keeps the contents.

A queue with a dead-letter exchange

Using the amqplib package in Node, declare the failure path before the main queue, so rejected messages have somewhere to go:

import amqp from "amqplib";

const conn = await amqp.connect(process.env.AMQP_URL);
const ch = await conn.createChannel();

await ch.assertExchange("jobs.dead", "fanout", { durable: true });
await ch.assertQueue("jobs.dead.q", { durable: true });
await ch.bindQueue("jobs.dead.q", "jobs.dead", "");

await ch.assertQueue("jobs", {
  durable: true,
  deadLetterExchange: "jobs.dead",
});

ch.consume("jobs", (msg) => {
  try {
    handle(JSON.parse(msg.content.toString()));
    ch.ack(msg);
  } catch (err) {
    ch.nack(msg, false, false);   // do not requeue: send to the dead exchange
  }
});

The third argument false in nack means "do not requeue", and with a dead-letter exchange set on the queue, RabbitMQ then routes the message to jobs.dead. Open the management UI, find jobs.dead.q, and use "Get messages" to read what failed. That inspection is the main thing the UI adds over a bare client.

To delay a retry, a common pattern is a second queue with messageTtl set and the main exchange as its dead-letter target, so messages wait and then come back. For more on testing the failure paths, see queue consumer retries locally.

Pitfalls

  • Changing a queue's arguments. A queue declared with one set of arguments cannot be redeclared with another. RabbitMQ answers with a "PRECONDITION_FAILED" error. Delete the queue in the UI, or remove the volume, then restart.
  • Unacknowledged messages stay hidden. A message delivered but not acknowledged shows as "unacked" and returns only when the channel closes.
  • Prefetch. Without a prefetch limit, one consumer takes the whole backlog. Set ch.prefetch(1) to see a fair spread.
  • Default credentials. guest and guest are for your laptop only.
  • Too much for the job. If you only need to hand one task to one worker, a database table or NATS is lighter.

The broker is only half of it. Run a background worker locally shows how to run the consumer beside it.

Questions people ask

What is the RabbitMQ management UI address locally?

With the rabbitmq management image and port 15672 published, it is http://127.0.0.1:15672. The default login is guest and guest, which is meant for local use only.

How do I see failed messages in RabbitMQ?

Give the queue a dead-letter exchange, bind a queue to it, and reject failed messages without requeue. Then open that queue in the management UI and use Get messages.

Does flisk down delete my RabbitMQ queues?

No. The queue resource keeps its data in a named volume, and flisk down keeps named volumes. Delete the queue in the UI or remove the volume for a clean start.
