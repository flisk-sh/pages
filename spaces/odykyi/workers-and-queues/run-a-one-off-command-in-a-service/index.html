How to run a one-off command inside a running service

You want to run one script with the same variables the service sees, without copying them into your shell by hand.

To run a one-off command with a service's environment, execute it inside that service instead of in your own shell. With plain Docker that is docker exec or docker compose exec. With Flisk it is flisk run <service> -- <command>, which gives the command the environment the service has in the stack and returns the command's exit code.

Why not just run it in your shell

Run node scripts/backfill.js from your terminal and it fails in small ways. DATABASE_URL is missing. Or the hostname postgres does not resolve outside the Docker network. Or it points at a different database than the one your API uses, and you write test data to the wrong place. A one-off command should see exactly what the running service sees.

With Docker and Compose

Compose gives you two commands, and the difference matters:

  • docker compose exec api node scripts/backfill.js runs inside the container that is already running. It shares that container's files and processes, and it fails if the service is down.
  • docker compose run --rm api node scripts/backfill.js starts a new container from the same image and configuration, runs the command, and removes it. It works when the service is stopped, but it starts dependencies, and it does not share anything with the running copy.

Use exec to look at a live service, and run for a job that should not depend on the live one. For an interactive shell add a shell as the command, such as docker compose exec api sh.

The Flisk way

Flisk wraps this in one command:

flisk run orders-api -- printenv DATABASE_URL
flisk run orders-api -- bun run seed
flisk run orders-api -- sh

These three examples come from the command's own help text. The first line prints the database URL the service really uses, which is the fastest way to answer "which database is this pointed at". The second runs a seed script. The third opens a shell. The words after -- are the command, so its own flags are not read by Flisk.

What happens depends on how the service runs:

  • For a container service, the command runs inside the running container.
  • For a local process (a service with a command in service.json), it runs on your machine from the service folder, with the project .env, the service's own env and its PORT.

The command's exit code comes back as the exit code of flisk run, so it works in scripts and in CI:

flisk run orders-api -- node scripts/check-data.js || echo "check failed"

For tools that read output, add --json. It runs without input and prints one JSON object with the exit code and the captured output. Put the flag before the service name:

flisk run --json orders-api -- node scripts/count-orders.js

Coding assistants can do the same through the resource_run tool of the Flisk MCP server, so an assistant can run a seed without guessing at variables.

Jobs that should run on every start

A command you run by hand is different from a step that is part of startup. If a task must finish before another service starts, such as a migration, make it a resource instead of a command you remember to run. A bring-your-own service with "restart": "no" runs once, and a service that lists it in dependsOn starts after it exits with code 0. Database migrations get their own resource type, covered in database migrations in local dev.

Pitfalls

  • The service must be running. flisk run uses the running stack. Start it first, and check with flisk status.
  • Container paths, not host paths. Inside a container, scripts/seed.js must exist in the image or in a mounted folder. A file that only exists on your laptop is not there.
  • Ready-made image services in a no-Docker run. When a database or queue runs from an image next to local processes, flisk run cannot reach into it. Use docker exec directly for those.
  • Do not run destructive scripts against a database you did not check. Print DATABASE_URL first, as in the first example.
  • One-off is not repeatable. A command you type once and forget will be missing on the next laptop. If the team needs it, put it in a script or a resource.

Questions people ask

What is the difference between docker compose exec and run?

exec runs a command inside a container that is already running. run starts a new container from the service's image and configuration, runs the command and removes it. Use exec to inspect a live service and run for an independent job.

How do I see which environment variables a service really uses?

Run printenv inside the service. With Flisk that is flisk run <service> -- printenv, or add the name of one variable such as DATABASE_URL.

Does flisk run return the exit code of my command?

Yes. The exit code of the command becomes the exit code of flisk run. With --json you get one JSON object that includes the exit code and the output.
