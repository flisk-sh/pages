Background jobs and queues locally

How to run cron jobs in local development

Flisk has no scheduler of its own. That is fine: a scheduled job is a worker plus a clock, and you can test the job without waiting for the clock.

Flisk does not include a scheduler, so you have two honest options: run a small worker that owns the schedule (node-cron, APScheduler or similar), or keep the job as a plain command and trigger it by hand while you develop. Most teams do both: the schedule lives in a worker, and the job body is a function you can also run on demand.

Separate the schedule from the job

The most useful habit is to keep the work in one function and the timing in another. If the job is runCleanup() and the schedule is a single line that calls it, you can test the job by calling it directly. Waiting five minutes to see whether a cron expression fires is the slowest way to find a bug in the job itself.

For local work, there are three places the schedule can live:

  • Inside a worker process. A long-running process holds the timer. This is the closest match to a production setup that uses a scheduler library.
  • The operating system. crontab -e on your laptop works, but it lives outside the repository, so nobody else on the team gets it. It also runs when your stack is stopped.
  • Nowhere. You run the command yourself. For most development this is the right choice.

An in-process scheduler

With Node, the node-cron package takes a standard five-field expression:

import cron from "node-cron";
import { runCleanup } from "./jobs/cleanup.js";

let running = false;

cron.schedule("*/5 * * * *", async () => {
  if (running) return;          // skip if the last run is still going
  running = true;
  try {
    await runCleanup();
  } finally {
    running = false;
  }
}, { timezone: "UTC" });

console.log("scheduler started");

In Python, APScheduler has the same idea, and the overlap guard is built in:

from apscheduler.schedulers.blocking import BlockingScheduler
from jobs.cleanup import run_cleanup

sched = BlockingScheduler(timezone="UTC")
sched.add_job(run_cleanup, "cron", minute="*/5",
              max_instances=1, coalesce=True)
sched.start()

max_instances=1 prevents two overlapping runs, and coalesce=True merges runs that were missed into one.

The Flisk way

Run the scheduler as its own local process, so it has a log and a restart policy like any other service. Create services/shop/scheduler/service.json:

{
  "schemaVersion": 1,
  "appName": "scheduler",
  "appType": "worker",
  "command": "node scheduler.js",
  "dependsOn": ["api"],
  "env": { "TZ": "UTC" }
}

A service with a command runs as a local process on your machine. The scheduler starts after api, its output goes to the same place as every other service's, and if it crashes Flisk restarts it. Read what it did with:

flisk logs --service scheduler --since 10m

To run the job now, without waiting for the clock, use flisk run. It starts a command with the environment the service has in the stack:

flisk run scheduler -- node jobs/run-cleanup.js

For a local process this runs on your machine from the service folder, with the project .env, the service's env and its PORT. For a container service it runs inside the running container. Either way you get the command's exit code back, which is handy in a script. More on this in running a one-off command in a service.

If the job is something that should run once whenever the stack starts, such as a seed or a warm-up, a one-shot resource is a better fit than a scheduler. Set "restart": "no" on it, and services that depend on it start after it exits with code 0.

Pitfalls

  • Time zones. A schedule written as "02:00" means different moments on your laptop and on a server set to UTC. Set the zone explicitly in the scheduler, as the examples do, and keep the machine zone out of it.
  • Missed runs. Nothing fires while the stack is down. If your job depends on every slot running, store a "last run" timestamp and catch up on start.
  • Duplicate runs. If you ever start a second copy of the scheduler, each copy fires the job. Production setups use a lock or a single scheduler process, and your local setup should do the same if the job is not safe to repeat.
  • Hot reload restarts the timer. If your tooling restarts the process on every file save, a job scheduled for the top of the hour can be skipped or run twice during editing.
  • Do not copy the production schedule. A job that sends real email every minute is not something to leave running on a laptop. Run it on demand, or use a long interval.

If the scheduled work is really "process this when something happens", a queue is a better fit than a clock. Running NATS locally shows how to set one up.

Questions people ask

Does Flisk have a built-in cron scheduler?

No. Flisk starts and supervises processes, but it does not schedule them. Put a scheduler library in a worker, or run the job on demand with flisk run.

How do I test a cron job without waiting for it to fire?

Keep the job body in its own function or script and run it directly. With Flisk, flisk run <service> -- <command> runs it with the service's environment and returns the exit code.

Why did my scheduled job run twice locally?

Usually two copies of the scheduler are running, or a file watcher restarted the process. Check which processes are alive and use a lock or max-instances setting if the job is not safe to repeat.
