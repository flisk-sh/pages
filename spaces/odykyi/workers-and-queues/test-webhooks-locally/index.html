Background jobs and queues locally

How to test webhooks locally without a public URL

A tunnel shows you that a webhook arrives. A local test shows you that your handler stays correct when it arrives twice, late or out of order.

To test webhooks locally you have two tools, and they answer different questions. A tunnel (ngrok, cloudflared, or a provider CLI that forwards events) proves a real provider can reach your laptop. A local test with saved payloads proves your handler checks the signature, ignores duplicates and survives a retry, and it needs no internet. Use the tunnel once, and the test every day.

What goes wrong with webhooks

Almost every webhook bug is one of four things:

  • Signature checks on the wrong bytes. The signature is computed over the raw request body. If a JSON parser runs first and you re-serialize, the bytes differ and every check fails.
  • Duplicates. Providers retry when they do not get a fast success response, so your handler will see the same event more than once.
  • Slow handlers. If you do the work inside the request, a slow job makes the provider retry, which produces more duplicates.
  • Lost acknowledgements. You commit your work, but the response never reaches the provider, so it sends the event again.

The standard design is to verify the signature, write the event to an inbox keyed by the provider's event ID, return success quickly, and let a worker do the real work. A duplicate event hits the same key and does nothing.

Reaching your laptop from the internet

When you want a real provider to send a real event, you need a public URL that forwards to your machine. Options that work without Flisk:

  • ngrok http 4000 or cloudflared tunnel --url http://localhost:4000 prints a public URL for a local port.
  • Some providers ship a CLI that forwards events straight to localhost. Stripe's is stripe listen --forward-to localhost:4000/webhooks/stripe, and it prints a signing secret to use for the events it forwards.

If you tunnel to a Flisk stack, point the tunnel at the port your backend listens on. Flisk backends use ports in the 4000 to 4999 range, and flisk networks prints the URLs your stack exposes. If the gateway rejects requests that arrive with the tunnel's hostname, tunnel to the backend port directly. I did not test every tunnel product against the gateway, so check this on your setup.

A local test that needs no tunnel

Flisk does not have a webhook replay command. What it gives you is a stack where the API, the inbox database and the worker all run locally, and that is enough to test the cases that matter. This recipe is the one in the Flisk docs, and it is a pattern you build in your tests, not a Flisk feature.

  1. Pin the payloads. Save a few real events as files in your test folder, as exact bytes. Use a dummy signing key that you commit, never a real one.
  2. Sign them in the test. The test computes the signature the same way the provider does and sends the raw body.
  3. Control the clock. Many providers include a timestamp in the signature and reject old ones. Make the "now" function injectable so a test can move it.
  4. Reset state first. Clear the inbox and the worker's output before each scenario.

The handler that the test exercises looks like this:

import express from "express";
import { createHmac, timingSafeEqual } from "node:crypto";

const app = express();
const KEY = process.env.WEBHOOK_KEY;

app.post("/webhooks/demo", express.raw({ type: "*/*" }), async (req, res) => {
  const given = Buffer.from(req.get("x-signature") ?? "", "hex");
  const want = createHmac("sha256", KEY).update(req.body).digest();

  // timingSafeEqual throws when lengths differ, so compare lengths first
  const valid = given.length === want.length && timingSafeEqual(given, want);
  if (valid === false) {
    return res.status(400).end();
  }

  const event = JSON.parse(req.body.toString("utf8"));
  await db.insertInbox(event.id, event);   // unique on event.id, ignore a repeat
  res.status(200).end();
});

Then write scenarios against the running stack, not against mocks of it:

  • Deliver an event, commit it to the inbox, then drop the response and deliver it again. Assert one effect.
  • Deliver the same event twice at once. Assert one effect.
  • Stop the worker, deliver events, start the worker, and assert it drains the inbox.
  • Change one byte of the body and assert a 400.

The worker is a normal service in your stack that reads from the inbox, as in running a background worker locally. Running these scenarios against the real stack is the subject of integration tests against the real stack.

Pitfalls

  • Do not use a live key for local tests. A dummy key is enough, because you sign the payload yourself.
  • Do not trust the event order. Providers do not promise delivery in the order events happened. Look at the state in the event, not the arrival sequence.
  • A tunnel URL changes. Free tunnel URLs change on restart, so a webhook registered with the provider stops working until you update it.
  • Return fast. Anything slow in the handler belongs in the worker.

Once the inbox is filled and the worker drains it, failures become the next thing to test. Testing consumer retries locally picks up from there.

Questions people ask

Do I need ngrok to test webhooks locally?

Only when a real provider must reach your machine. For checking your own handler, sign saved payloads in a test and send them to localhost. That needs no tunnel and no internet.

Why does my webhook signature check always fail locally?

Most often the body was parsed and re-serialized before verification. Signatures are computed over the raw bytes, so read the raw body, verify it, and parse it afterwards.

How do I handle duplicate webhook events?

Store each event in an inbox keyed by the provider's event ID with a unique constraint. A repeat hits the same key and does nothing, so processing is safe to retry.
