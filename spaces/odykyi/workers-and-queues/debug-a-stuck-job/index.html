Background jobs and queues locally

How to debug a background job that never finishes

A stuck job is silent. Work through the same short list each time and you will find the cause faster than by guessing.

When a job never finishes, check in this order: is the worker alive, is it reading the right queue, did the message arrive, is it being held without acknowledgement, and does the worker see the same environment as the API. Most stuck jobs are one of those five, and each has a quick check.

Find where the job stops

A job passes through stages: the API accepts the request, it publishes a message, the broker stores it, the worker takes it, the worker does the work, and the worker acknowledges. Find the last stage that happened, and the cause is in the gap after it. Add a log line at each stage that includes the job ID, and the search takes minutes instead of hours.

Checklist, in order

  1. Is the worker running? A worker has no HTTP endpoint, so "the stack is up" says nothing about it. Check the process or container directly.
  2. Is it connected to the queue? Look for the connection line at startup, or the error that replaced it.
  3. Is the subject or queue name identical? A typo such as job.email against jobs.email is silent: the publish succeeds and nobody listens.
  4. Did the message get stored? With JetStream, a publish to a subject that no stream covers fails with a no-responders error. With a queue broker, check the queue depth.
  5. Is the message unacknowledged? A message that was delivered but never acknowledged waits for the ack timeout, then comes back. A handler that throws before the acknowledge, or hangs, looks like a stuck job.
  6. Is it a poison message? One message that always fails can block a consumer if the code retries it in place. See queue consumer retries locally.
  7. Is it waiting on something else? A database lock, an HTTP call with no timeout or a full disk makes a handler hang without an error.

With Flisk

Flisk gives you read-only commands for most of the checklist. Start with the stack as a whole:

flisk status
flisk status --unhealthy

Then read the worker's output. flisk logs prints a bounded snapshot, and you can filter it:

flisk logs --service mailer --since 10m
flisk logs --service mailer --tail 100 --json

--unhealthy limits the output to services that are failing or still starting. Remember that a worker has no HTTP health check, so the status mostly tells you whether the process is alive, not whether it is doing work. A process that Flisk restarts again and again shows up as a pattern of start lines in the log,, and for a local process Flisk stops restarting it after five quick exits.

Compare what the API and the worker each see. This catches the case where the worker connects to a queue the API never publishes to:

flisk run mailer -- printenv NATS_URL
flisk run shop-api -- printenv NATS_URL

The two lines should match. A local process that uses localhost and a container that uses the service name bus are both fine, but they must point at the same server. For a worker running as a local process, the logs are also in files under .flisk/native/logs/, one per service.

When the checks above find nothing, run flisk doctor for environment problems and flisk config verify for generated files that are out of date.

Look inside the queue

For NATS, the nats command line tool is the best view. It needs the server port on your host, which you can publish with extraPorts as described in NATS for local development:

nats stream ls
nats stream info JOBS
nats consumer info JOBS mailer

The consumer view shows the number of messages not yet delivered, the number delivered and waiting for acknowledgement, and the number of redeliveries. Pending above zero with no worker activity means the consumer is not pulling. Waiting for acknowledgement above zero means a handler took the message and has not finished. With the -m 8222 flag, the server also serves a monitoring page with the same numbers over HTTP.

For RabbitMQ, the management UI at http://127.0.0.1:15672 shows ready and unacked counts for each queue.

Pitfalls

  • Restarting too early. Restarting the worker clears the evidence. Read the log and the queue state first, then restart with flisk restart mailer if you must.
  • Old state. Queue data persists in a volume between runs, so a job that seems stuck can be an old message from yesterday's code. Check its age.
  • Buffered output. Some languages hold output back when it is not a terminal, which makes a busy worker look silent. Flush your logs.
  • The job succeeded. Sometimes the work is done and the status update failed. Check the side effect itself before blaming the queue.

Once you know the cause, write a test for it. Reading logs from every service covers the logging commands in more depth.

Questions people ask

Why is my queued job never processed?

The usual causes are a worker that is not running, a subject or queue name that does not match, a message that was delivered but never acknowledged, or a worker that points at a different broker or database than the API.

How do I check if a worker is alive in Flisk?

Run flisk status, then flisk logs --service <worker> --since 10m. A worker has no HTTP health check, so the logs are the real signal that it is doing work.

What does unacked mean in a message queue?

It means the message was delivered to a consumer, but the consumer has not acknowledged it yet. If the ack timeout passes or the consumer disconnects, the message is delivered again.
