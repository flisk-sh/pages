How to share one database between a worker and an API

Two processes, one database. The setup is simple. The mistakes are about who owns the schema and who picks up which row.

A worker and an API can share one database if they get the same connection string and only one of them, or better a separate migration step, changes the schema. Give both the same DATABASE_URL, run migrations once before either starts, and make sure the worker claims rows in a way that two copies cannot both take the same job.

What sharing means

Sharing a database does not mean sharing code. The API and the worker are separate processes that happen to read and write the same tables. Three things make that safe:

  • One address. If the API uses postgres://localhost:5432/app and the worker uses a different database name by accident, the worker polls an empty table and nothing ever happens. This is the most common cause of "the job is never processed" in a new setup.
  • One schema owner. If both processes run migrations at start, they race. Put migrations in one step that runs first.
  • Clear claims. When several workers can read the same queue table, you need a way to say "this row is mine".

Without Flisk

In Compose you put the same variable in both services, usually through a shared .env file, and add depends_on with a health check on the database. Remember the two addresses: inside the Compose network the host is the service name (postgres), and from your laptop it is localhost. A worker you run by hand on the host needs the second one.

A table that acts as a job queue is common and works well at small scale. The claim query uses FOR UPDATE SKIP LOCKED, so two workers never block on or take the same row:

WITH next AS (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'running', started_at = now()
FROM next WHERE jobs.id = next.id
RETURNING jobs.*;

Run it as a single statement, and set the status to done or failed afterwards. A job stuck in running after a crash needs a timeout that puts it back, which is something to test deliberately.

The Flisk way

Create the database as a resource, then name it in dependsOn of both services:

flisk resource ordersdb --type database --stack shop --yes

This writes a small service.json with appType: "database" and framework: "postgres", the shared Flisk Postgres. The command prints "Add ordersdb to dependsOn in the services that use the database" as its next step. In the API and in the worker:

"dependsOn": ["ordersdb"]

Per the Flisk docs, services that depend on a database receive DATABASE_URL in their environment, and a stack gets its own database inside the shared Postgres, so every service in the same stack sees the same data. I confirmed the resource and config with flisk config verify, but I did not start the stack, so to see the exact value your worker received, run this once it is up:

flisk run orders-worker -- printenv DATABASE_URL
flisk run orders-api -- printenv DATABASE_URL

If the two lines differ, you found your bug before writing any code. For the general rules on connection strings, see DATABASE_URL and env vars locally.

Keep migrations out of both

The Flisk rule for new services is to run migrations in an explicit migrator resource, not in an API start script or entrypoint. Both the API and the worker then depend on the migrator, and neither one touches the schema at boot. Database migrations in local dev shows the setup. Starting order follows dependsOn, so the database comes up first, the migrator second, and the API and worker last.

Pitfalls

  • Connection limits. Each process opens its own pool. Postgres allows 100 connections by default, so a pool of 20 in each of several services adds up. Keep local pool sizes small.
  • The worker sees uncommitted data as missing. If the API inserts a job and then commits, a worker polling in between finds nothing. That is normal. If you publish a message in the same request, publish after the commit, not before.
  • Two workers, one row. Without SKIP LOCKED or an equivalent claim, a second worker repeats jobs. Test it by starting two copies deliberately.
  • Do not share tables with a service you do not own. If a third service reads your worker's tables directly, schema changes become a coordination problem. Give it its own database, as described in one database per service.
  • When a real queue is better. If jobs need delays, retries with backoff or fan-out, a broker such as NATS fits better than a table.

With the shared database in place, the next question is how the API hands work to the worker. Run a background worker locally covers that wiring.

Questions people ask

Can a worker and an API use the same Postgres database?

Yes. Give both the same connection string, run migrations in one separate step, and make sure the worker claims rows so two copies cannot take the same one.

How do I stop two workers from picking the same job?

Claim the row in one statement with SELECT ... FOR UPDATE SKIP LOCKED inside an UPDATE, then mark it running. Locked rows are skipped, so each worker gets a different job.

Why does my worker never see the jobs my API creates?

Check that both processes use the same database name and host. Print DATABASE_URL in each one. A different database name or a missing commit are the usual causes.
