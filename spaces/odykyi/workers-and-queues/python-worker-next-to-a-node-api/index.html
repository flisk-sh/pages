Background jobs and queues locally

How to run a Python worker next to a Node API locally

Mixed languages are normal: Node takes the requests, Python does the heavy lifting. They only need to agree on a queue and a message format.

Run the Python worker as its own service and let the Node API talk to it through a queue, not through function calls. The two only share a subject name and a JSON message shape. Locally you can start the worker from a small Dockerfile, or as a plain Python process if you do not want a container in the loop.

Agree on the contract first

Before any tooling, write down three things, because they are the only coupling between the services:

  • The subject or queue name, for example jobs.resize.
  • The message shape as JSON, for example {"imageId": "abc", "width": 640}. Use plain types, since Node and Python disagree about big integers and dates.
  • What the worker does on success and failure: acknowledge, retry, or give up.

Keep the message small and put large files in storage, passing only an ID. Then each side is testable alone: the Node side by checking what it publishes, and the Python side by publishing a hand-written message.

The queue

This article uses NATS with JetStream, set up as in running NATS locally. With Flisk:

flisk resource bus --type queue --stack shop --yes

The Python worker with a Dockerfile

Flisk's worker resource type generates a Bun project, and the --language option works only for backends. That is not a limit, because a Python worker is a bring-your-own service: you write the Dockerfile, and Flisk runs it. The files are small. First worker.py, using the nats-py package:

import asyncio, json, os
import nats

async def main():
    nc = await nats.connect(os.environ["NATS_URL"])
    js = nc.jetstream()
    await js.add_stream(name="JOBS", subjects=["jobs.>"])
    sub = await js.pull_subscribe("jobs.resize", durable="resizer")
    while True:
        try:
            msgs = await sub.fetch(1, timeout=5)
        except nats.errors.TimeoutError:
            continue
        for msg in msgs:
            job = json.loads(msg.data)
            print("resizing", job["imageId"], flush=True)
            await msg.ack()

asyncio.run(main())

Then requirements.txt with the line nats-py, and the Dockerfile:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-u", "worker.py"]

The -u flag turns off output buffering, so log lines appear immediately instead of in bursts. Now the service.json in services/shop/resizer/:

{
  "schemaVersion": 1,
  "appName": "resizer",
  "appType": "bring-your-own",
  "stack": "shop",
  "dockerfile": "Dockerfile",
  "exposeViaProxy": false,
  "healthCheck": false,
  "dependsOn": ["bus"]
}

Each field has a reason. exposeViaProxy: false and healthCheck: false say that the service has no HTTP side, so Flisk should not route to it or probe it. dependsOn: ["bus"] starts the queue first and passes NATS_URL to the worker. I checked a file of exactly this shape with flisk config verify. Do not use flisk resource ... --type bring-your-own for this without editing the result, because that command assumes an HTTP service and sets a health check path of /health and a port of 4001.

Bring-your-own services restart with unless-stopped by default, so a crash in the Python code brings the worker back. If you want a crash to stay crashed while you debug, set "restart": "no". More on custom Dockerfiles in bring your own Dockerfile.

The Node side

The API publishes after it has saved its own state. With the nats package, and the same NATS_URL variable from the queue resource:

import { connect, StringCodec } from "nats";

const sc = StringCodec();
const nc = await connect({ servers: process.env.NATS_URL });
const js = nc.jetstream();

app.post("/images/:id/resize", async (req, res) => {
  await js.publish("jobs.resize",
    sc.encode(JSON.stringify({ imageId: req.params.id, width: 640 })));
  res.status(202).json({ queued: true });
});

Reply with 202 Accepted, because the work is not done yet. A client that needs the result checks a status route, or polls.

Without a container

If you do not want to build an image on every change, run the worker as a local process. Give the service a command instead of a Dockerfile:

{
  "schemaVersion": 1,
  "appName": "resizer",
  "appType": "worker",
  "command": "python3 worker.py",
  "dependsOn": ["bus"]
}

This runs on your machine with your own Python and virtual environment, which is faster to iterate on. The cost is that "works on my machine" returns, because the Python version is yours, not the image's. The no-Docker mode is described in run services without Docker.

Pitfalls

  • Buffered output. Without -u or flush=True, a Python worker can look dead while it works. Read its output with flisk logs --service resizer.
  • Message drift. If one side renames a field, the other fails only at runtime. Keep a sample message in the repository and test both sides against it.
  • Slow image builds. Copy requirements.txt and install before copying the code, as above, so the dependency layer is cached.
  • Do not split a tiny app. If the Python code is a ten-line function, a Node library may be less to maintain than a second runtime.

For what happens when the Python code throws, read testing consumer retries locally.

Questions people ask

Can Flisk scaffold a Python worker?

Not directly. The worker resource generates a Bun project, and the language option only applies to backends. A Python worker is a bring-your-own service with your own Dockerfile, or a local process with a command.

How do a Node API and a Python worker communicate?

Through a queue or a database table, using an agreed message shape in JSON. The API publishes a message and returns, and the worker consumes it. They share no code.

Why do I see no output from my Python worker?

Python buffers stdout when it is not a terminal. Run it with python -u or call print with flush=True so lines show up in the logs immediately.
