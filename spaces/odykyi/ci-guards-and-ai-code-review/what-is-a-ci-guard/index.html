What is a CI guard and which checks should you add first

A CI guard is a deterministic check that fails a pull request when a rule is broken. Here is what counts as one, which to add first, and what to leave out.

A CI guard is an automated check in your pipeline that returns pass or fail on a rule you can state in one sentence, such as "no file over 500 lines" or "the generated files match their source". It does not give opinions. It blocks the merge or it does not.

What makes a check a guard

A guard has three properties. It is deterministic: the same commit gives the same result every time. It is fast: a minute or two, not twenty. And it is specific: when it fails, the message says which file and which rule.

A linter, a type checker, a test suite and a secret scanner are all guards. A model that reads your diff and writes comments is not a guard. It is a reviewer, and it belongs after the guards. See AI review bot vs linters for how the two fit together.

The first five guards to add

  1. Formatter and linter. Fails on style, so humans do not argue about it.
  2. Type check. Catches whole classes of bugs for free.
  3. Unit tests. The minimum proof that behaviour did not change.
  4. Secret scan. One leaked key costs more than all the other guards save. See secret scanning in CI.
  5. Generated-file sync. Fails when committed output is stale. See the dist sync check.

Add them in that order. Each one is a few lines of workflow and pays back the first week.

A minimal workflow

One job, one command per guard, so a failure points at one cause:

name: guards
on: [pull_request]
jobs:
  guards:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test

Mark the job as a required check in branch protection, or it is advice, not a guard. See required checks.

Write the rule as a script, not a wiki page

Rules that live in a CONTRIBUTING file get forgotten. Rules that live in a script get enforced. When a review comment repeats a third time, turn it into a guard. A ten-line shell script is often enough:

#!/usr/bin/env bash
set -euo pipefail
big=$(git ls-files '*.ts' | xargs wc -l | awk '$1 > 500 && $2 != "total" {print $2" ("$1")"}')
if [ -n "$big" ]; then
  echo "Files over 500 lines:"; echo "$big"; exit 1
fi

What not to guard

Do not guard things that are subjective, slow or flaky. A guard that fails one run in twenty teaches people to press re-run, and then it protects nothing. Fix or quarantine it. Measure the cost too: count how many times a week someone re-runs a job, because that is real engineering time you are paying for a guard that does not guard. (See flaky tests). Do not add a guard you cannot explain in a sentence to a new contributor.

If you want a worked example of guards, evals and nightly loops used together, the GEL project (Guard, Eval, Loop) at gel.flisk.si describes Flisk's approach, and the code is at github.com/flisk-sh/gel.

Questions people ask

What is the difference between a guard and a test?

A test checks that code behaves correctly. A guard checks any rule about the repo, including tests, style, file size, generated files and secrets. Tests are one kind of guard.

How many guards is too many?

When the full set takes longer than a few minutes or people start ignoring failures. Keep each one fast, and delete guards that never catch anything.
