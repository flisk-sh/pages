CI guards and AI code review

Check that generated files are in sync with their source in CI

If your repo commits build output, lockfiles or generated code, add a CI check that rebuilds and fails on any difference. It takes ten lines and ends stale-artifact bugs.

Rebuild the generated files in CI, then run git diff --exit-code. If anything changed, the committed copy was stale and the job fails. This one guard catches the "I forgot to rebuild" mistake every time.

When you need this

Any repo that commits something derived from other files: compiled JavaScript in a dist/ folder, an OpenAPI client, generated types, a bundled CLI, a lockfile, a schema dump. The source and the output must agree, and nothing but a check will make people remember.

The check

name: generated-in-sync
on: [pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build
      - name: Fail if generated files changed
        run: |
          git add -N .
          git diff --exit-code || { echo 'Run npm run build and commit the result.'; exit 1; }

git add -N marks new untracked files as intent-to-add, so a newly generated file also shows up in the diff.

Make the output deterministic

The check fails randomly if the build is not reproducible. Common causes: timestamps in output, absolute paths of the build machine, unordered keys, a different tool version locally and in CI. Pin the tool version in package.json or a version file, sort keys when you write JSON, and strip timestamps. If you cannot make it deterministic, compare a hash of the meaningful parts instead of the raw bytes.

Tell people how to fix it

A failing check should say the exact command. Better, add a local script and a pre-push hook so the mistake never reaches CI:

npm run build && git add -A dist

Keep the message in the workflow. Nobody reads a doc after a red build, but they do read the log line.

Also decide who may update generated files. If a bot or a release script regenerates them on main, the PR check can stay, but it should compare against the PR's own base, so an unrelated change on main does not turn every open PR red. A rebase fixes that, and the failure message can say so.

Never hand-edit generated files

Say so in your contributor guide, and make the check enforce it: a hand edit gets overwritten by the next build and shows up as a diff. Agents also need this rule written down, since they will happily patch the output file. Put it in your AGENTS.md; see docs and READMEs for agents. For a broader list of first guards, see what is a CI guard.

Questions people ask

Should I commit build output at all?

Often not. Commit it only when users consume the repo directly, for example a GitHub Action or a CLI installed from git. Otherwise build in the release pipeline.

Why does the check pass locally and fail in CI?

Usually a different tool version, line endings, or a non-deterministic build. Pin versions and compare in a clean checkout.
