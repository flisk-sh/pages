How to stop an AI code review bot from posting false positives

Most noisy review bots are noisy because of their instructions and context, not their model. Here are the changes that cut false positives and keep the useful comments.

On this page
  1. Give it a narrow job
  2. Say what it should not say
  3. Require evidence in a fixed format
  4. Measure with resolved comments
  5. Cap the volume

To cut false positives from a review bot, give it a narrow job, feed it only the changed files plus the rules that matter, require it to cite a line and a reason, and drop low-confidence comments before posting. Then measure which comments people resolve, and prune the rest.

Give it a narrow job

"Review this PR" invites twenty style remarks. A narrow instruction gets better results: "Find bugs and security problems in the changed lines. Ignore style, naming and formatting. If you find nothing, say so." Every category you remove is a category of noise gone. Linters already own style.

Say what it should not say

Keep a short list of rules the bot reads from a file in the repo, so the team can edit them in a PR:

# review-rules.md
- Do not comment on formatting. The linter does that.
- Do not suggest renaming unless the name is wrong or misleading.
- Do not flag missing tests for files under docs/ or scripts/.
- Only comment on lines changed in this diff.
- Each comment must name a concrete failing input or scenario.

The last rule is the strongest. A comment that cannot describe how it fails is usually a guess.

Require evidence in a fixed format

Ask for structured output so you can filter before anything is posted. Each finding gets a file, a line, a severity and a reason:

{"findings": [{"file": "src/api.ts", "line": 42, "severity": "high",
  "reason": "user id is concatenated into the SQL string", "fix": "use a parameter"}]}

Then in plain code, drop findings whose line is not in the diff, whose severity is below your bar, or that repeat an earlier finding. A script filter is deterministic, so it is a guard on the model.

Measure with resolved comments

Track for two weeks: how many comments the bot posted, and how many led to a change. If under about one in four did, tighten the rules. If you have no data, you are guessing. Sample ten merged PRs and mark each comment useful, harmless or wrong, then change one thing and compare. See bot vs linters for where the bot fits.

Cap the volume

Limit the bot to a maximum of five comments per PR, highest severity first. A reviewer who sees three good comments reads them. A reviewer who sees thirty stops reading. Also skip draft PRs and very large diffs, where the model loses track of context; ask the author to split the PR instead.

Questions people ask

Is a bigger model the answer to false positives?

Sometimes it helps, but narrower instructions, a diff-only scope and an evidence requirement usually help more and cost less.

Should the bot be able to approve a PR?

No. Let it comment only. Approval should stay with a person.
