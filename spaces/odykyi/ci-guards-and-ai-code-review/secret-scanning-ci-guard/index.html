CI guards and AI code review

Add a secret scanning guard to CI before a key leaks

A leaked API key is the most expensive mistake a repo can make. Add a secret scan to pull requests, know what to do on a hit, and keep agent output from committing keys.

Run a secret scanner on every pull request and on a nightly job over the full history, fail the build on a verified or high-confidence match, and rotate any key that was ever committed. Deleting the file is not enough, because git history keeps it, and so do forks and clones.

Why scan in CI and not only locally

Local pre-commit hooks are optional and easy to skip, and coding agents do not always run them. CI is the one place every change passes through. Also turn on your host's own secret scanning and push protection if it is offered for your plan, which blocks known key formats at push time. A CI scan is the second layer.

A scanner in the workflow

Gitleaks and TruffleHog are widely used open-source scanners. Check each project's README for the current install method and flags. A common pattern with the Gitleaks binary:

jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: Scan
        run: |
          gitleaks detect --source . --redact --exit-code 1

fetch-depth: 0 pulls the whole history so older commits in the PR are scanned too. --redact keeps the secret itself out of the build log.

What to do when it fires

  1. Assume the key is compromised. Revoke and rotate it at the provider first.
  2. Then remove it from the code and load it from the environment. See env and secrets for local development.
  3. Rewrite history only if you must, and only after rotating. Rewriting does not help for a public repo, since copies exist.
  4. Check logs at the provider for use of the key.

Reduce false alarms

Test fixtures, docs examples and random IDs can look like keys. Use an allowlist file for specific, reviewed paths or fingerprints, never a broad pattern like *.md. Keep the allowlist in the repo so changes are reviewed. Run the same scan locally before you push if you can, so a leaked key never even leaves your machine. Use obviously fake values in examples, such as sk-test-not-a-real-key.

Agents and secrets

Coding agents read your .env and sometimes copy values into code, tests or logs. Keep real keys out of the working directory the agent sees, add .env to .gitignore, and let the scan be the backstop. More on this in AI security for builders. For the first set of guards to add alongside this one, see what is a CI guard.

Questions people ask

Is scanning enough without rotation?

No. Once a secret is committed, treat it as exposed and rotate it, even if you removed the commit quickly.

Should the scan run on the whole history every time?

Not on every PR. Scan the PR's commits there, and run a full-history scan on a schedule.
