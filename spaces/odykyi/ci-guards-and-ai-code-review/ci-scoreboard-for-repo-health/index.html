Build a CI scoreboard that tracks repo health with plain numbers

A scoreboard turns guards and ratchets into a short list of numbers people actually look at. Here is how to build one with a script and a CI job.

Build a scoreboard by writing one script that prints a handful of deterministic numbers, such as test count, lint warnings and open ratchets, then run it in CI and fail when a gate drops. Keep the output short enough to read in ten seconds.

What belongs on it

Pick five to ten numbers that mean something to your team and can be computed without a model. Examples: tests passing, lint warnings, type errors, files over the size limit, docs pages without a title, time of the slowest test, dependencies with known advisories.

Each number is either a gate (must be at or above a value) or a ratchet (must not get worse, see ratchet checks). Anything that is neither is trivia and should go.

A scoreboard script

A scoreboard can be a Node or shell script that prints one line per metric and exits non-zero if a gate fails:

// scripts/scores.mjs
import { execSync } from 'node:child_process';
const count = (cmd) => Number(execSync(cmd).toString().trim());
const rows = [
  { name: 'todo comments', value: count("git grep -c TODO | awk -F: '{s+=$2} END {print s+0}'"), max: 120 },
  { name: 'test files', value: count("git ls-files '*.test.*' | wc -l"), min: 40 },
];
let failed = false;
for (const r of rows) {
  const bad = (r.max !== undefined && r.value > r.max) || (r.min !== undefined && r.value < r.min);
  console.log((bad ? 'FAIL ' : 'ok   ') + r.name.padEnd(20) + r.value);
  failed ||= bad;
}
process.exit(failed ? 1 : 0);

Run it in CI and on main

Run the scoreboard on every pull request so a gate drop blocks the merge. Also run it on a schedule against the default branch and keep the output as a build artifact or log. A trend of numbers across weeks tells you more than one run.

on:
  pull_request:
  schedule:
    - cron: '0 6 * * *'

Look across repositories

If you own many repositories, a dashboard of CI results helps. Cilytics at cilytics.flisk.si is an hourly dashboard of CI results across the flisk-sh GitHub organisation, and is a useful picture of what a cross-repo view looks like. For the score of a single README, README Score returns a number out of 100 with no AI involved: same README, same score, which is the property you want from any scoreboard line.

Keep it honest

  • Never let a model compute a number on the board.
  • Print the raw value, not only pass or fail.
  • Delete a metric when nobody has acted on it for a quarter.
  • Do not make a score a personal target. People optimise what you measure, so measure things you want optimised.

Questions people ask

Do I need a dashboard tool?

No. A script that prints numbers in CI logs is enough to start. Add a dashboard when you have many repositories or want a history.

How often should the scoreboard run?

On every pull request for the gates, and once a day on the default branch for the trend.
