GitHub required checks and branch protection, set up correctly

A CI check only guards anything if the merge is blocked when it fails. Here is how required status checks work, the common mistakes, and how to set them up.

Open the repository's branch protection (or ruleset) settings for your default branch, turn on "require status checks to pass before merging", and select the job names of your guards. Until you do that, a red check is only a suggestion.

Why a green workflow is not enough

A workflow that fails shows a red cross on the PR, but GitHub will still let you merge unless a rule says otherwise. The rule is a required status check, set per branch pattern. Without it, the first deadline will see someone merge over a red build, and the guard stops being believed.

Set it up

  1. Repository Settings, then Branches (or Rules, then Rulesets).
  2. Add a rule for your default branch.
  3. Enable "Require status checks to pass before merging".
  4. Search for and select each check by its job name. A check only appears in the list after it has run at least once.
  5. Enable "Require branches to be up to date before merging" if you want the check to run against the latest main.

You can also do it from the command line with the GitHub CLI and the REST API, which is handy for many repos. Check the GitHub REST docs for the current body of the branch protection endpoint before scripting it.

Common mistakes

  • Path filters skip the check. If a workflow has paths: filters and a PR does not match, the required check never reports, and the PR waits forever. Use a job that always runs, or a small "all checks" job that depends on the rest.
  • Renaming a job. The required name is the job name. Rename it and the old required check never arrives.
  • Admins bypass. By default administrators can merge over a failing check. Turn on "include administrators" if you want the rule to apply to everyone.
  • Matrix jobs. Each matrix entry is its own check name. Require an aggregate job instead.

An aggregate job

One stable name that you require, no matter how the workflow changes inside:

  all-green:
    if: always()
    needs: [lint, typecheck, test]
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo '${{ toJSON(needs) }}' | grep -q '"result": "failure"' && exit 1 || exit 0

Require all-green and nothing else. New jobs go into needs, and the protection rule never changes.

Handling emergencies

You will need a hotfix path. Decide it in advance: a small group may bypass, the bypass is logged, and a follow-up PR explains why. An undocumented way around the rules becomes the usual way. For flaky checks that tempt people to bypass, read flaky tests and quarantine.

Questions people ask

Can I require checks from a fork's pull request?

Yes, the required checks apply to pull requests from forks too, but secrets are not available to them by default, so design guards that do not need secrets.

What if a required check never starts?

Usually a path filter or a renamed job. Make a job that always runs and require that one.
