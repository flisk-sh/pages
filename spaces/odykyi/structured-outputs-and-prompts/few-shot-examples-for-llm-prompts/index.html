Few-shot examples: how many, which, and how to format

Examples teach format and edge cases better than rules do. How to pick them, how many you need, and how to avoid copying and bias.

Use three to five examples that cover the typical case and the hard edge cases, in exactly the output format you want, and keep them separate from your test data. Examples show the model what you mean when rules alone leave room for guessing.

When examples beat rules

Rules struggle with style, tone and fine category boundaries. "Short, neutral summary" can mean ten things. Two examples of a good summary show it at once. Use examples for output format, labelling decisions and tricky cases. Use rules for hard constraints.

Choosing examples

  • One plain, typical case.
  • One edge case per common mistake you have seen.
  • One example where the right answer is "unknown" or "other", so the model learns to abstain.
  • Variety in length and wording, so it does not lock onto surface features.

Take them from real inputs, with personal data removed, not made up in the abstract.

Formatting them

Classify the ticket. Reply with JSON only.

Example 1
Ticket: "I was charged twice in March."
Answer: {"category": "billing", "priority": 2}

Example 2
Ticket: "The export button does nothing on Safari."
Answer: {"category": "bug", "priority": 2}

Example 3
Ticket: "Do you have a podcast?"
Answer: {"category": "other", "priority": 1}

Match the real output format exactly, including key order and quotes. Models copy format faithfully, including your typos.

Pitfalls

Label skew. If four of five examples are "bug", the model leans that way. Balance them to reflect reality.

Order effects. The last example can pull hardest. Test a shuffled order.

Leakage. Never use your test cases as examples, or your scores will look better than reality.

Cost. Examples are tokens on every call. Prefer fewer, sharper ones.

Static or retrieved examples

For a stable task, fix the examples in the prompt file. For a wide task, store many labelled examples and pick the few most similar to the current input at call time. Start static. Move to retrieval only if accuracy on varied inputs needs it. Keep the example set in version control beside the prompt. For a compact guide to the rest of the prompt, read how to write a system prompt.

A quick check for bias

After you pick your examples, count the labels and the openings. If every example starts with "Thank you for", or four of five carry the same label, rebalance. Then run your test set with and without the examples. If the score does not move, remove them. If it rises on easy cases but falls on hard ones, your examples may be too similar to each other, so swap one for a harder case.

Questions people ask

How many examples do I need?

Often three to five. Add more only if tests show specific failures that an example would fix.

Do examples still help with strong models?

Yes for format and edge cases, but test it. If zero examples already pass your cases, skip them and save tokens.
