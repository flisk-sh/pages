Prompts and structured outputs

How to write a system prompt that actually works

A good system prompt states the role, the task, the rules, the output format and what to do when unsure. A template and the mistakes that make prompts worse.

State the job, the audience, the hard rules, the output format and what to do when information is missing, in that order, using short plain sentences. Long, emphatic prompts usually perform worse than short, specific ones.

A structure that holds up

  1. Role and goal: one or two sentences about what the assistant does and for whom.
  2. Inputs: what it will receive and how it is formatted.
  3. Rules: the things that must always or never happen.
  4. Output format: exact shape, with an example.
  5. Edge cases: what to do when information is missing or the request is out of scope.

A template

You triage support tickets for a billing product. Readers are agents.

Input: one customer message.

Rules:
- Pick exactly one category: bug, billing, other.
- Never promise refunds or dates.
- If the message is not about the product, use "other".

Output JSON: {"category": string, "priority": 1-3, "summary": string}
Summary: one sentence, under 25 words, no customer names.

If you cannot tell, use category "other" and priority 2.

Say what to do, not only what to avoid

"Do not be verbose" is weak. "Answer in at most three sentences" is testable. Positive, concrete rules are followed more reliably than a list of prohibitions. Explain the reason for a rule when it is not obvious, because a model that knows why can handle cases the rule did not list.

Mistakes that make prompts worse

  • Capital letters and repeated warnings everywhere, so nothing stands out.
  • Contradictions added over time: "be brief" in one paragraph, "be thorough" in another.
  • Pasting a whole policy document when five rules matter.
  • No fallback for unclear input, so the model invents an answer.

Read the prompt once as a stranger would. If two lines can be read in conflicting ways, fix them.

Iterate with evidence

Change one thing at a time and run it against a fixed set of examples, as in testing prompts. Add examples if rules alone leave gaps: see few-shot examples. Keep the file in version control so you can compare versions.

A quick review pass

Before you ship a prompt, read it against this list: Is the job clear in the first two lines? Is every rule testable? Is there at least one example of the output? Does it say what to do when the input is unclear? Is anything in it that the model could not possibly know, such as a variable that was never filled in? Print the final text with all variables substituted and read that, not the template.

Questions people ask

How long should a system prompt be?

As short as it can be while covering the rules that matter. Many good ones are 100 to 400 words. Move reference material to retrieval instead.

Does the role line ("You are an expert...") matter?

A concrete job description helps. Vague flattery adds little. Say what the assistant does and for whom.
