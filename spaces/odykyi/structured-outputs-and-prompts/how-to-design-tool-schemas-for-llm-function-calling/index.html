How to design tool schemas for LLM function calling

Models pick tools by name and description, and fill arguments from your schema. Design names, descriptions, parameters and errors so the right call is the easy one.

Give each tool a clear verb-first name, a one or two sentence description that says when to use it and when not to, a small flat parameter schema with enums where you can, and error messages the model can act on. Fewer, sharper tools beat many overlapping ones.

Names and descriptions do the routing

The model reads the name and description to decide. search_orders beats query. Write the description as guidance: what it does, what it returns, when to use it, and when to use a different tool instead.

{
  "name": "search_orders",
  "description": "Find orders by customer email or order ID. Returns up to 10 orders with status and total. Use get_order for full details of one order.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string"},
      "order_id": {"type": "string"}
    },
    "additionalProperties": false
  }
}

The key name for the schema differs between providers (input_schema, parameters), so check your API docs.

Keep parameters simple

  • Flat objects. Avoid deep nesting.
  • Enums for fixed choices, such as "status": ["open", "closed"].
  • Describe each parameter, with an example value and its format (dates as ISO 8601).
  • Make only truly needed fields required.
  • Prefer IDs the model has already seen over free-text names.

How many tools is too many

Every tool definition costs tokens on every call and adds a chance of picking wrongly. A handful that do clearly different things works well. If you have dozens, group them behind a router step, or load only the tools relevant to the current task. Merge near-duplicates: one search with a type parameter can replace three tools.

Return results and errors the model can use

Return compact, relevant results, not raw database rows. For failures, say what went wrong and how to fix it: "No order with id 123. IDs look like ORD-1234." The model will then retry correctly. A stack trace helps nobody. Return a stable shape, so the model does not have to parse a new format each time.

Validate on your side, always

The model's arguments are untrusted input. Validate them against the schema in code, check permissions for the current user, and apply limits such as a maximum page size. Destructive tools should require confirmation or run in a dry-run mode first. These ideas carry over to servers: see MCP servers in production and AI security for builders.

Test tool selection

Write 20 user requests and the tool you expect for each. Run them and count the picks. Wrong picks tell you which descriptions overlap. This is cheap and catches most schema problems early. See testing prompts.

Questions people ask

Should tool descriptions be long?

Keep them to a few sentences. Say what the tool does, what it returns and when to use it. Move long reference text elsewhere.

Can the model call a tool with wrong arguments?

Yes, even with a schema. Validate arguments in your code and return a helpful error so the model can correct itself.
