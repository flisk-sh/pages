JSON mode vs structured outputs vs function calling

Three ways to get machine-readable output from a model. What each one guarantees, where each fits, and how to choose without reading five API docs.

JSON mode guarantees valid JSON but not your shape. Structured outputs constrain the reply to a JSON Schema you provide. Function calling (tool use) has the model fill in arguments for a named function, which also gives you a schema, and is the right pick when the output triggers an action.

JSON mode

You turn on a setting and the model returns syntactically valid JSON. You still describe the fields in the prompt, and nothing stops it from omitting one or using a different name. Good for quick prototypes. For production you need validation and retries.

Structured outputs

You pass a JSON Schema, and the provider constrains decoding so the reply matches it: required fields present, enums respected, types right. Support and the allowed schema subset vary by provider and model, so read the docs for yours. Open-model servers offer similar features, often through grammar-based decoding.

Use it when the output is the product: extraction, classification, a report object.

Function calling

You declare tools, each with a name, a description and a parameter schema. The model replies with a tool name and arguments, and your code runs the function. Use it when the model chooses between actions, or when you want arguments for something that executes.

You can also force one tool and ignore its execution, which gives you structured output through a different door. Many APIs let you set a tool-choice option for this.

The last column of "depends" is why you validate regardless.

How to choose

  1. Output is data you will store or show: structured outputs.
  2. Output chooses or triggers an action: function calling.
  3. Prototype or provider supports neither: JSON mode plus a validator and retries.

Whatever you pick, validate with a typed model as in validating LLM output with Pydantic or Zod. Details on writing good tool definitions are in designing tool schemas.

Trade-offs to know

Constrained decoding can slightly change quality: the model is forced into a shape even when the honest answer is "I do not know". Always include a way out, such as a nullable field or an "unknown" enum value. First-call latency can rise for new schemas on some providers. Measure both on your own task.

If you run open models, the same ideas apply. Servers such as Ollama and llama.cpp support schema or grammar constraints, and small models benefit from them even more, because they break format more often. For a free model API to try structured output against, Flisk Inference (inference.flisk.si, open beta, with a daily request limit) exposes a coding-focused open model called Flisk Wolf. It is an early service, so treat it as a place to experiment. Background on open models is in local LLM models.

Questions people ask

Do all models support structured outputs?

No. Support differs by provider and model. Check the documentation, and fall back to JSON mode or tool calls plus validation where it is missing.

Is function calling only for agents?

No. It is also a convenient way to get structured arguments out of a model for any pipeline, even if you never run the function.
