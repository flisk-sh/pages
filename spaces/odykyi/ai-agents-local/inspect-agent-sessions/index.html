Running AI agents locally

How to inspect AI agent sessions and checkpoints locally

You cannot debug what an agent remembers if you cannot see it. One command lists every session and prints any checkpoint.

Run flisk agent sessions <resource> to list every conversation a local agent has stored, with its last activity, whether it is active or idle, and the size of its checkpoint. Add --session-id <id> to read one checkpoint, --watch to refresh the table every 2 seconds, or --json for scripts. It works on any resource created with --type agent.

Why you need a way to look inside

An agent's behaviour depends on what it remembers. When an answer is wrong, the question is usually "what did it have in its history at that point". If sessions are only reachable through the model call, you debug by guessing. Whatever stack you use, you want three views: a list of sessions, the full message history of one, and a way to see when each was last touched. With a plain Compose setup you get these by opening a shell in the container or querying the database yourself. That works, but it is different for every project.

The generated Flisk agent standardizes it. It exposes GET /sessions, and the CLI and an MCP tool read from there, so the same command works for every agent in the project.

List sessions

With the stack running (flisk up), name the resource:

flisk agent sessions assistant

The table has four columns: SESSION, LAST ACTIVITY, STATUS and CHECKPOINT (its size in bytes). If nothing has talked to the agent yet, you see "No sessions yet." Send a turn first, as shown in route requests by session ID, and run the command again.

The data comes from GET /sessions on the agent. It returns {"sessions":[...],"total":N}, newest first, with at most 500 rows. Each row has sessionId, lastActivity, checkpointBytes and status. A status of active means a turn is running for that session now, and idle means it is stored and waiting.

Read one checkpoint

flisk agent sessions assistant --session-id alice

This prints the stored conversation for that ID: the number of turns and the messages, user and agent, in order. It is the same data as GET /session with the x-session-id header. Use it when you want to compare what the agent holds with what you think you sent.

Watch while you test

flisk agent sessions assistant --watch

The table refreshes every 2 seconds, so you can send requests from another terminal and see sessions appear and flip between active and idle. --watch cannot be combined with --json; the command stops with a usage error if you try.

The active and idle label can lag by a moment. Flisk's agent notes list known race conditions around that label and around drain timing. They affect what the table shows for a few milliseconds, not what is saved in a checkpoint.

Use the JSON output in scripts

flisk agent sessions assistant --json

The sessions are under data.sessions, and a single checkpoint read with --session-id is under data.session. That makes checks easy in a test, for example failing when the number of stored sessions is not what you expect after a run. A coding assistant can do the same through the agent_sessions MCP tool, which takes an optional sessionId, and agent_list lists the agents in the project.

Errors and what they mean

  • AGENT_NOT_RUNNING. The container is not up. The hint is to run flisk up.
  • NOT_AN_AGENT. The resource exists but is not of type agent.
  • UNKNOWN_RESOURCE. Check the name with flisk status.
  • SESSION_LIST_UNSUPPORTED. The agent was scaffolded by an older Flisk and has no /sessions route. Add the route from a new scaffold, or create a fresh agent and compare the files.
  • NO_PORT, NO_ROUTE, AGENT_REQUEST_FAILED. The CLI could not find or reach the agent. The CLI connects to 127.0.0.1 with the right Host header, because *.localhost names do not resolve everywhere. If requests fail, read the agent's logs, see reading logs from every service.

Limits

  • The list shows at most 500 sessions. For a larger store, query the database directly.
  • Sessions removed by the idle sweep (24 hours by default) are gone from the list. That is expected, not a bug.
  • The command shows what the agent stored, not what the model saw. If your agent trims or summarizes history before each call, the prompt differs from the checkpoint.
  • Checkpoints can contain user data. Treat the output like logs before pasting it into an issue.

Questions people ask

How do I see the messages of one session?

Run flisk agent sessions <resource> --session-id <id>. It prints the stored turns and messages for that session.

Can I use the session list in a script?

Yes. Add --json: the list is under data.sessions and a single checkpoint under data.session. --watch cannot be combined with --json.

Why does the command say SESSION_LIST_UNSUPPORTED?

The agent was created by an older Flisk and has no /sessions route. Create a new agent and copy its route, or recreate the agent.
