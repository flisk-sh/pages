How to route requests by session ID to an AI agent

A session ID is a key, not an address. Treat it that way and any restart, replica or deploy stops being a conversation-ending event.

To route requests by session ID, send an x-session-id header with every call and let the agent use it as the key for that conversation's saved state. In the agent that Flisk generates, POST /turn, GET /session and DELETE /session all require the header, so two clients with two IDs never see each other's messages. That is routing to a session, not to a server, and the difference matters.

Two meanings of "sticky"

People use "route by session" for two different designs, and mixing them up causes bugs.

  • Sticky routing. A load balancer sends every request of one session to the same instance, because that instance holds the conversation in memory. It is simple and fast, and it breaks when the instance restarts or is replaced: the memory is gone.
  • Shared state. Any instance can serve any session, because the conversation lives in a store that every instance reads. The session ID is only a key. Restarts are harmless, and you do not need the balancer to be clever.

For agents the second design is the safer one. Agent conversations are long, an instance can restart in the middle of a task, and a deploy replaces every instance. If the only copy of a conversation is in process memory, each of those events ends it. Sticky routing is then an optimization on top of shared state, not a replacement for it.

How the generated agent uses the header

Create an agent and look at what it requires:

flisk resource assistant --type agent --stack shop --yes

Every session call needs x-session-id. The value must match ^[A-Za-z0-9_-]{1,128}$, which keeps it safe to use as a file name or a database key. Anything else gets a 400. With the agent running, send two turns for one session and one turn for another:

curl -s -X POST http://localhost:4000/turn \
  -H 'x-session-id: alice' -H 'content-type: application/json' \
  -d '{"input":"hello"}'
curl -s -X POST http://localhost:4000/turn \
  -H 'x-session-id: alice' -H 'content-type: application/json' \
  -d '{"input":"again"}'
curl -s -X POST http://localhost:4000/turn \
  -H 'x-session-id: bob' -H 'content-type: application/json' \
  -d '{"input":"hi"}'

Each reply is {"sessionId":"alice","reply":"...","turns":2} and so on. The turn counter for alice reaches 2 while bob stays at 1. Read a whole conversation back with the same header:

curl -s http://localhost:4000/session -H 'x-session-id: alice'

That returns sessionId, turns and the messages list. DELETE /session removes it, or answers 409 turn_in_flight if a turn is still running.

Two behaviours help when several clients are talking to one agent. Turns of the same session are queued, so two requests for alice never race over one checkpoint, while different sessions run independently. And the checkpoint is saved before the reply is sent, so a reply you received is a reply that was stored.

Errors you will meet

  • 400 for a missing or bad header. Clients often forget the header on the first call. Generate the ID on the client, for example a UUID, and keep it for the whole conversation. A UUID fits the allowed characters.
  • 400 input_required or invalid_json. The body must be JSON with a non-empty input string.
  • 413 payload_too_large. A body over 1 MiB is refused. The limit is AGENT_MAX_TURN_BODY_BYTES.
  • 503 while draining. The agent is shutting down. Retry after it is back, see health and readiness endpoints.

What Flisk does and does not do here

Be careful with claims about routing. What the generated agent does is read x-session-id and pick the checkpoint. Do not count on Flisk to pin a session to one replica: Flisk's docs say that running several instances of one service locally is not supported yet, so locally there is one agent instance and nothing to pin. The header selects the conversation. If you later run more than one copy elsewhere, add replica stickiness with your own balancer, and keep the shared store as the source of truth.

The address of a container agent is a local URL of the shape http://api.<project>.localhost/api/<name>, possibly with a port. Use the URL that flisk status prints. Header-based clients do not care which form they use, because headers pass through the router unchanged. If the .localhost name does not resolve on your machine, see local URLs instead of ports.

Pitfalls

  • Do not put the session ID in the model prompt as the only key. Pass it as a header so the store and the logs can use it.
  • Do not use a user's email or name as an ID. It can leak in logs and does not fit the allowed characters.
  • One ID per conversation, not per user, unless you want one endless conversation per user.
  • Old sessions disappear. An idle sweep removes sessions after 24 hours by default (SESSION_IDLE_TIMEOUT_MS).

Questions people ask

Which characters can an x-session-id contain?

Letters, digits, underscore and dash, 1 to 128 characters. Anything else is rejected with 400.

Does Flisk pin a session to one agent replica?

Do not count on it. Locally you run one instance per agent, and the header selects the saved conversation. Running several instances of one service locally is not supported yet.

What happens if two requests for the same session arrive together?

The agent queues turns per session, so they run one after the other and never race over one checkpoint. Different sessions run independently.
