Health vs readiness endpoints for an AI agent service

Liveness tells you the process is up. Readiness tells you it can save a conversation. An agent that mixes them up either restarts for no reason or loses replies.

An agent service should answer two different questions over HTTP. /health says the process is alive, and /ready says it can do real work, which for an agent means its checkpoint store works. Keep them separate: a restart helps when the process is stuck, but it does nothing when the database is down. The agent that flisk resource --type agent generates exposes both.

Liveness and readiness are not the same thing

The two terms come from container orchestration, and they apply on a laptop too.

  • Liveness asks whether the process should be killed and restarted. It must be cheap and must not depend on anything outside the process. If liveness checks your database, a database outage makes every agent restart in a loop, which hides the real problem.
  • Readiness asks whether the service should receive traffic right now. It is the place to check dependencies: the store, a model gateway, a queue.

For an agent the distinction matters more than for a plain API. An agent keeps a conversation per session. If it accepts a turn while its store is unreachable, the reply is produced and then lost, so the user sees an answer that the agent will not remember. Failing readiness before that happens is cheaper than repairing a half-saved session.

In plain Docker Compose you get the same effect with a healthcheck on the container and depends_on with condition: service_healthy. The mechanism is covered in Compose depends_on and healthchecks. What Compose does not give you is the endpoint itself, so you write it.

The two endpoints in the generated agent

Create an agent in a project that already has a stack:

flisk resource assistant --type agent --stack shop --yes

The scaffold is a small Bun HTTP service. Its contract has these two checks:

  • GET /health returns {"status":"ok","service":"assistant","draining":false}. It is liveness only and never touches the store.
  • GET /ready returns {"ready":true,"durability":"files"} with status 200 when the store is writable (the files option) or reachable (the postgres option). It returns 503 when the store is not usable, and also while the agent is draining.

Try them against a running agent. Use the URL that flisk status prints for the resource, or the port from its service.json if you run it as a local process:

curl -i http://localhost:4000/health
curl -i http://localhost:4000/ready

The first call should be 200 whatever the store is doing. The second is the one to watch while you break things. Stop the Postgres your agent depends on, if you chose the postgres option, and /ready turns to 503 while /health stays 200. The agent is alive, but not ready.

How Flisk uses the health path

The generated service.json for an agent sets healthCheckPath to /health:

{
  "appName": "assistant",
  "appType": "agent",
  "port": 4000,
  "healthCheckPath": "/health",
  "agent": { "runtime": "custom", "durability": "files" }
}

Flisk uses healthCheckPath for the Docker health check it generates for the container, and flisk status shows whether each resource is healthy. The readiness endpoint is part of the agent's contract, so use it in your own scripts, your tests and any load balancer in front of the service. A good pattern in a test setup is to poll /ready before the first turn:

until curl -fs http://localhost:4000/ready > /dev/null; do sleep 1; done
echo ready

If you want an overview of unhealthy resources, flisk status --unhealthy lists only those, and flisk status --json gives the same data for scripts.

Draining on shutdown

Both endpoints include the draining state. When the agent receives SIGTERM it stops accepting new turns, lets turns that are in flight finish, and exits with code 0, by default within 10 seconds (DRAIN_TIMEOUT_MS). During that window /health reports "draining":true, /ready returns 503, and POST /turn returns 503. That is what a router needs to stop sending new requests before the process goes away. The checkpoint is saved before each reply is sent, so a turn that completed is never lost by a shutdown.

If you write your own agent

The same contract works for an agent you build with any framework, including one you wrap with a Dockerfile of your own. Keep these rules:

  • Make /health do no I/O. Return a fixed body.
  • Make /ready do one real, small operation on the store, such as writing and deleting a marker, not just opening a connection that may be cached.
  • Use a short timeout in /ready. A check that hangs is worse than one that fails.
  • Flip /ready to 503 as soon as shutdown starts.
  • Do not call the model provider in either check. It costs money, it can be rate limited, and a provider outage should not mark your agent as broken.

Some frameworks only expose one route. In that case point healthCheckPath at it, and add a second route in front of the framework for readiness.

When this is too much

A throwaway script that calls a model once does not need two endpoints. The split pays off when the agent keeps state, runs next to other services that wait for it, or sits behind a router. For the ordering side of that, see service startup order.

Questions people ask

What is the difference between /health and /ready in the Flisk agent?

/health only says the process is alive and never touches the store. /ready returns 200 when the checkpoint store is writable or reachable, and 503 when it is not or while the agent is draining.

Should a readiness check call the model provider?

No. It costs money, can be rate limited, and a provider outage should not mark your own service as broken. Check your own dependencies, such as the store.

What does the agent do on SIGTERM?

It stops taking new turns, lets turns in flight finish and exits with code 0, by default within 10 seconds. While draining, /ready and POST /turn return 503.
