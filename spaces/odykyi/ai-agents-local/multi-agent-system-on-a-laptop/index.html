Running AI agents locally

How to run a multi-agent system on your laptop with retries

A multi-agent system is a queue with opinions. Run the coordinator and the workers as real processes and the failure modes show up while they are still cheap to fix.

You can run a multi-agent system on one laptop as a handful of small processes: one coordinator that owns a queue of tasks, and several workers that claim a task, do it and report back. Each worker needs its own port and name, the coordinator must start first, and a worker that dies must lose its claim so the task is retried. Flisk has two starters, swarm and super-agent, built on this pattern.

The pattern that works locally

Multi-agent demos often hide the plumbing inside one process. Splitting them into services shows the parts that break in practice. A simple, debuggable design is pull-based:

  • A coordinator splits a goal into subtasks and keeps them in a queue.
  • Each worker asks the coordinator for work, which marks the task as claimed. When it finishes it posts the answer. If it fails, it reports the failure.
  • A claim has a timeout. A worker that crashes or hangs never completes the task, so after the timeout it goes back in the queue.
  • A task has a retry limit, so a task that always fails ends the goal instead of looping forever.
  • The coordinator saves its state to disk, so restarting it loses no goals.

Pushing tasks to workers instead is possible, but then you have to track who is alive. Pulling keeps the coordinator ignorant of the workers, which is also how you would put them behind a queue later.

Run the swarm starter

Install Flisk (npm install -g @flisk-sh/flisk) and create the project. It needs no Docker:

flisk project swarm --path swarm-demo --yes
cd swarm-demo
flisk up
curl -X POST localhost:4100/goals -H 'content-type: application/json' \
  -d '{"goal":"Read the docs. Summarize them and list the risks"}'
curl localhost:4100/goals

That starts one coordinator on port 4100 and three workers on ports 4101 to 4103. The coordinator also serves a small page at / where you can submit goals, and GET /goals lists goals and their subtasks. Each worker has a manifest like this:

{
  "schemaVersion": 1,
  "appName": "worker-1",
  "appType": "worker",
  "command": "node ../worker/server.mjs",
  "port": 4101,
  "healthCheckPath": "/health",
  "env": {
    "WORKER_NAME": "worker-1",
    "COORDINATOR_URL": "http://localhost:4100"
  },
  "dependsOn": ["coordinator"]
}

All three workers run the same file, worker/server.mjs, and differ only in name and port. dependsOn makes each wait for the coordinator. To add a fourth worker, copy a worker-N folder and its service.json, change the name and use the next free port. The work function in worker/server.mjs is where you call a model or a tool.

Break it on purpose

A multi-agent system is only trustworthy once you have seen it fail. The starter documents the numbers: a claim expires after CLAIM_MS (15 seconds), a failed subtask is retried up to MAX_ATTEMPTS (3) times, and then the subtask and its goal are marked failed. Try three things:

  1. Set FAIL_RATE=0.5 in one worker's env and submit a goal. Some subtasks fail and are retried, possibly by another worker.
  2. Stop a worker while it holds a task. After the claim timeout, a different worker finishes it.
  3. Kill the coordinator and start it again. Goals come back, because it saves them to coordinator/.data/swarm-state.json.

Adding tools and a reviewer: super-agent

The super-agent starter adds the structure most real agent teams grow into. A planner turns a goal into steps, an MCP tool server provides a lookup tool, and three sub-agents pull steps: a researcher that calls the tool, a writer that composes the answer, and a checker that sends back research that came back empty. The checker may send work back MAX_REVISIONS (2) times. Ports are 4300 for the planner, 4301 for tools and 4302 to 4304 for the sub-agents. Without ANTHROPIC_API_KEY the planner splits the goal with rules, so it works offline, and BAD_RATE=0.5 on the researcher shows the checker working.

flisk project super-agent --path super-agent-demo --yes
cd super-agent-demo
flisk up
curl -X POST localhost:4300/goals -H 'content-type: application/json' \
  -d '{"goal":"Explain flisk and mcp and retries"}'
curl localhost:4300/goals

Pitfalls

  • Pick ports on purpose. Seven or eight agents plus tools is easy to clash with something else on your laptop. A project file gives each service one fixed port. See fixing "port already in use" if one is taken.
  • Memory budget. Every worker is a full process. Start only what you need while developing, as covered in starting only the services you need.
  • Runaway cost. With a real model, a retry loop is a bill. Keep the attempt limit low and log every model call.
  • Several copies of one service. Flisk's own docs say running several instances of one service is not supported yet. The swarm uses separate folders per worker instead.

Questions people ask

Does the swarm starter need Docker?

No. The coordinator and the three workers each declare a command, so flisk up starts them as local processes.

What happens when a worker dies in the middle of a task?

Its claim expires after CLAIM_MS (15 seconds) and the subtask goes back in the queue. A subtask that fails MAX_ATTEMPTS (3) times is marked failed together with its goal.

How do I add more workers to the swarm?

Copy a worker-N folder and its service.json, change appName, WORKER_NAME and the port, and run flisk up again. Each worker runs the same worker/server.mjs file.
