What to put in the README for local development setup

A setup section that lists forty manual steps goes stale in a month. Write the few things a person must know, and let commands print the rest.

A good local-setup section in the README has six parts: prerequisites with versions, the install and start commands, where to open the app, how to reset it, what to do when it breaks, and who owns it. Keep it short, put the commands in code blocks, and let tools print anything that changes often, such as ports and URLs.

Why setup docs go stale

Setup pages rot because they repeat facts that live somewhere else. The port of the API is in the service config and also in the README. The Postgres password is in .env and also in a wiki. When one changes, nobody edits the other. A new developer then follows the page, hits an error, and learns the page cannot be trusted.

The rule that keeps a README honest is simple: do not write down a fact that a command can print. Write the command instead. A README that says run flisk networks to see the URLs never needs an update when a port changes. A README that lists five URLs always will.

The six parts

1. Prerequisites with versions

List what must be on the machine before the first command, with the minimum version. Be exact, because "Docker" is not a prerequisite, "Docker Engine 25 or newer with Compose 2.20.2 or newer" is. For a Flisk project that runs Docker stacks, the setup pages in the Flisk repository list Node.js 22.12 or newer, Docker Engine 25+ with Compose 2.20.2+, and Tilt 0.25+. For a project whose services all declare a command, you only need Flisk and the runtimes of your own services.

2. Install and start

Three commands at most, copy-paste ready:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk up

If you pin a CLI floor with minFliskVersion in .flisk/project.json, say so here. The CLI will print Run: flisk upgrade on an older version, so you do not need to explain the failure.

3. Where to open the app

Do not list URLs. Write: "flisk up prints the URLs. To see them again run flisk networks." Flisk also shows services and ports with flisk resources, and what is healthy with flisk status. If you routinely open one page first, name it ("the storefront") rather than its address.

4. Daily commands

A short table beats prose here:

TaskCommand
Start everythingflisk up
Start part of itflisk up --only orders-api or flisk up shop
Read logsflisk logs, or flisk logs --service orders-api
Restart one serviceflisk restart orders-api
Run a one-off commandflisk run orders-api -- npm test
Stopflisk down

The --only option starts the named services plus what they depend on, so a developer working on one API does not have to run the rest. Replace the example service and stack names with yours.

5. Reset and clean up

Say what survives a restart. In a Docker Flisk stack, flisk down removes containers but keeps named volumes, so Postgres data stays. flisk down --purge also deletes the project's Docker volumes, so say plainly that it deletes local data. Put this next to the command, because it is the one a tired person types by mistake.

6. When it breaks

Start with one line: "Run flisk doctor and read the first failed check." Doctor prints a fix under each failure. Then add the three or four problems your team has actually hit, with the exact error text so a search finds them. Delete an item when the tooling stops producing that error. Our troubleshooting articles, such as check your machine before starting, can fill the generic part.

A template to copy

## Local development

Prerequisites: Node.js 22.12+, Docker Engine 25+ with Compose 2.20.2+, Tilt 0.25+.
Windows: use Ubuntu on WSL2 (see docs/windows.md).

    npm install -g @flisk-sh/flisk
    flisk project --yes
    flisk doctor
    flisk up

URLs: `flisk networks`. Services and ports: `flisk resources`.
Stop: `flisk down`. Wipe local data: `flisk down --purge` (deletes the database).
Stuck: `flisk doctor`, then ask in #dev-help with its output.
Owners of the local setup: @your-org/platform-team

What to leave out

  • Generated passwords or tokens. The project .env is git-ignored and written by flisk project; never paste its values into a README.
  • Port numbers, hostnames and container names. They come from service.json and the project name.
  • Steps the tool already does. If flisk up runs migrations through a one-shot resource, do not tell people to run them by hand.

Check the README like code

Once a quarter, give the section to someone who has never run the project, and watch without helping. Every question they ask is a missing line. You can also test the commands in CI, which is covered in checking config drift in CI. For the full day-one plan around this README, see onboarding a developer on day one.

Questions people ask

Should the README or a docs folder hold the setup steps?

Put the first-run commands in the README so they are the first thing a new person sees, and link to a docs folder for per-OS details such as WSL2 or Colima.

Does flisk down delete my database?

No. In a Docker stack it removes containers and keeps named volumes. flisk down --purge also deletes the project's Docker volumes, including database data.
