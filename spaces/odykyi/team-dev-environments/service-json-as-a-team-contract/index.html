How to use service.json as a team contract for local services

When every service describes itself in one small file, the file becomes the place where teams agree on ports, health checks and dependencies.

A service contract is a small file next to the code that says how the service runs locally: its name, type, port, health path, start command and what it depends on. In Flisk that file is service.json. Commit it with the service, review it like code, and let tooling check it, so the contract cannot disagree with reality.

What a contract must answer

Whatever tool you use, a local service needs a few facts that other people and tools rely on. What is it called? What kind of thing is it (API, website, worker)? Which port does it listen on? How do you know it is healthy? What must start before it? Which environment variables does it need, without their values?

Teams usually keep these facts in four places: a Compose file, a Makefile, a README, and people's heads. A contract file puts them in one place, per service, owned by the team that owns the service. That is why it works well for teams: a change to a port is a diff in the owning team's folder, not a message in a chat.

A real example

This is the smallest useful service.json for a service that runs as a local process, without Docker:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": [],
  "env": { "LOG_LEVEL": "debug" }
}

The fields that matter most:

  • appName: the identifier used in dependsOn, logs and --only. Keep it short and stable, because other files refer to it.
  • appType: backend, frontend, worker, migrator, mcp, agent, bring-your-own and a few more.
  • command: if present, the service runs as a local process started from its own folder, with PORT set. If absent, Flisk builds a container.
  • healthCheckPath: Flisk waits until this path answers before it starts the services that depend on this one.
  • dependsOn: names of services that must start first. An entry can also be an object such as {"name": "db", "condition": "service_healthy"}.
  • schemaVersion: currently 1. An unsupported value is rejected rather than guessed.

The $schema line gives editors completion and inline validation, which catches typos before anyone runs anything.

Secrets: names in the file, values outside

A contract is committed, so it must never hold a secret. Flisk's model is to put non-secret config in params in service.json, and to put only the names of secrets in a secrets list. The values live in the project .env, which is git-ignored and injected by Compose. Review is easier when the rule is that the file contains names only. The same rule applies when you export a standalone Compose file: Flisk writes variable names, never values.

Let tools enforce the contract

A contract nobody checks is a wish. Flisk checks several things for you:

  • flisk doctor fails when a dependsOn names a service that does not exist, when two resources share an appName, and when a schemaVersion is unsupported. It warns when two routed resources declare the same port.
  • flisk config verify exits with code 1 when a dependsOn points at an unknown name. I tried a typo, orders-apii, and it printed the offending service and exited non-zero. In CI this turns a typo into a failed check.
  • flisk up stops when the generated files have drifted from the sources, unless you pass --ignore-drift.

Run the checks in CI as described in checking config drift in CI.

Ownership and review

Because each contract lives in the service's own folder, ownership follows the folder. In a single repository, a CODEOWNERS file maps services/orders/ to the orders team, and the project-wide file .flisk/project.json to the platform team. Enforcement needs branch protection with required code owner review, which is a GitHub feature, not a Flisk one.

What to keep out of the contract

  • Machine-specific values. Absolute paths, your username, a local IP. They break on the next laptop.
  • Generated output. Do not copy anything from .flisk/.flisk-out/ or .autogenerated/ folders into reviews; they are rebuilt from the sources.
  • Business logic switches. Feature flags belong in the application config, not in the process manifest.

Also be honest about the limits. service.json is Flisk-specific, and a service.json outside the project root is not supported: Flisk finds services by scanning the project directory. If you need several repositories, declare them under repos in .flisk/project.json so they are cloned into the project tree.

When the contract is in place, the next question is how to roll it out without forcing everyone at once: adopt a local tool gradually.

Questions people ask

Should service.json be committed?

Yes. Commit each service.json with its service and .flisk/project.json. Do not commit .env or .flisk/.flisk-out/, which Flisk adds to .gitignore.

Can a service.json live in another repository?

Not as a discovered manifest. Flisk finds service.json files by scanning the project directory. Use the repos block in .flisk/project.json to clone other repositories into the project tree.

Where do secrets go?

Only the names go in service.json. The values go in the git-ignored project .env.
