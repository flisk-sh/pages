Logs, traces and metrics locally

Grafana, Loki, Tempo and Prometheus in one container

One development image gives you Grafana with logs, traces and metrics wired together.

Grafana publishes a development image, grafana/otel-lgtm, that bundles Grafana, Loki (logs), Tempo (traces), Prometheus (metrics) and an OpenTelemetry Collector in one container. You start it, point your services' OTLP exporter at port 4318, and open Grafana on port 3000. It is meant for local development and demos, not for production.

Why one container

A real Grafana setup is four or five services, each with a config file: Loki, Tempo and Prometheus for storage, a collector for intake, and Grafana with data sources wired up. That is a good project to learn from and a poor use of an afternoon when you only want to see whether your service emits sensible telemetry. The otel-lgtm image ships the pieces already connected, with Grafana's data sources configured, so a log line, a trace and a metric from the same service can be looked at side by side.

The trade-off is that you see little of how the pieces fit, you cannot tune each one, and the image is large. If you only need traces, Jaeger alone is lighter.

Start it with plain Docker

docker run --rm -p 3000:3000 -p 4317:4317 -p 4318:4318 grafana/otel-lgtm

Open http://localhost:3000. The image's documentation gives the default login as admin with the password admin, which Grafana asks you to change; check the image README for the current value, since defaults can change between versions. Port 4317 takes OTLP over gRPC and 4318 takes OTLP over HTTP. Pin a version tag instead of latest once you rely on it.

Send data from your services

All three signals go to the same endpoint, so the exporter settings are the standard ones:

OTEL_SERVICE_NAME=orders
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf

Traces and metrics work with the SDK settings shown in the Node.js and FastAPI guides. Logs need one more step: the SDK must export logs over OTLP, and your logger must feed it. Many logging libraries have an OpenTelemetry bridge for that. If you do not set that up, your service output still goes to stdout and is not in Loki. That is the case most people hit first: traces and metrics appear and logs do not.

Run it with Flisk

As a bring-your-own resource it needs the image, its web port and the OTLP ports:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "lgtm",
  "appType": "bring-your-own",
  "stack": "obs",
  "port": 3000,
  "healthCheckPath": "/api/health",
  "image": "grafana/otel-lgtm",
  "extraPorts": [{ "port": 4317 }, { "port": 4318 }],
  "volumes": [{ "source": "lgtm-data", "target": "/data" }]
}

Here port is Grafana, and healthCheckPath points at Grafana's own health endpoint, so services that list lgtm in dependsOn wait until it answers. extraPorts publishes the OTLP ports on 127.0.0.1. The named volume lgtm-data is a Docker volume that flisk down keeps, so you keep dashboards and stored data between runs; confirm which directories the image keeps its data in before relying on it, because the layout is the image's business, not Flisk's. To start from empty, stop the stack and remove the volume, as keeping volumes between runs explains. flisk config verify accepts this manifest.

Flisk's documentation notes that a bring-your-own resource whose page lives at / can be given "webUi": true, so it is routed on its own host name instead of a path prefix. Grafana serves its pages and assets from /, so on the Docker and Tilt path that is the setting to use, and flisk up prints the address. In a mixed run (your code as local processes), use http://localhost:3000.

flisk up
flisk status

Find your data in Grafana

  • Traces: open Explore, choose the Tempo data source, and search by service name. Click a trace to see the span tree.
  • Metrics: choose the Prometheus data source, and type a metric name your services export. The default HTTP duration metrics from the SDKs are a good first query.
  • Logs: choose Loki and filter by service_name (the label comes from OTEL_SERVICE_NAME). If a log line carries a trace ID, Grafana can link it to the trace.

Pitfalls

  • Memory. Several databases run inside one container, so expect it to use noticeably more RAM than Jaeger. Check docker stats if your laptop is already busy, and limit the container with your Docker settings.
  • Startup time. Grafana answers before every component inside is ready. If the first requests are lost, wait a little or retry.
  • Port 3000 is popular. Frontend dev servers like it too. If Grafana will not start, see fixing "port already in use".
  • Not a production setup. There is no authentication hardening, retention or high availability here.

Metrics need your services to expose something worth looking at. The next guide, exposing Prometheus metrics from a Node.js service, adds a /metrics endpoint with a few lines.

Questions people ask

Is otel-lgtm for production?

No. It is a development and demo image with no retention, hardening or high availability.

Why do traces show but logs do not?

Logs reach Loki only if your SDK exports them over OTLP. Plain stdout output does not go there.

Which ports do I publish?

3000 for Grafana, 4317 for OTLP over gRPC and 4318 for OTLP over HTTP.
