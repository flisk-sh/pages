Run microservices on your laptop

How to start only the services you need in local development

A full stack on a laptop eats memory and time. Most days you touch one or two services.

To start only the services you need, name the one you work on and let the tool pull in what it depends on, group related services so you can start the group, and mark heavy services as opt-in. Everything else stays off, which saves memory, startup time and noise in the logs.

Three ways to choose a subset

Whatever tool you use, the choices are the same:

  • By name. "Start the orders API and whatever it needs."
  • By group. "Start the checkout services." A group is a stack, a Compose profile or a folder.
  • By opt-in. Some parts (an admin panel, a search cluster, an analytics worker) are off unless you ask for them.

In Docker Compose, docker compose up orders-api starts that service and the services it lists under depends_on. Services with a profiles key are skipped unless you pass --profile. This works well for containers. See Compose profiles compared with stacks for the details.

Start by name with --only

In Flisk, --only starts the services you name and what they declare in dependsOn. Take three services where web and worker both depend on api:

flisk up --dry-run --only web

The dry run shows the plan without starting anything:

Would start 1 requested service plus api as local processes (no Docker, no Tilt)...
  - api: node --watch server.js
  - web: node server.js (after api)
Dry run: not starting services

The worker is not in the list. Drop --dry-run to start the same two. If you work on the API, flisk up --only api starts just that.

Start a group with a stack

Give related services the same stack in their service.json:

{
  "schemaVersion": 1,
  "appName": "orders-api",
  "appType": "backend",
  "stack": "checkout",
  "command": "node server.js",
  "port": 4001
}

Then flisk up checkout starts the services of that stack. When you name a stack together with --only, the names must belong to the stack, but their dependencies may come from other stacks. In a local-process project stack is optional. In a container project it is required, and a bare flisk up starts the stacks enabled in the active phase of .flisk/project.json. Run flisk stacks to list the stacks and their services.

Keep heavy services opt-in with profiles

Add profiles to a service you do not need every day:

{
  "schemaVersion": 1,
  "appName": "worker",
  "appType": "worker",
  "command": "node server.js",
  "dependsOn": ["api"],
  "profiles": ["jobs"]
}

A plain flisk up now leaves it out and says so:

Not starting worker (profile jobs): add --profile <name> to start them
Would start 2 services as local processes (no Docker, no Tilt)...

Run flisk up --profile jobs and all three start. Naming the service with --only worker also starts it. The same field works for containers, which is where it saves the most memory.

Pitfalls

  • A missing dependency. The subset only works if dependsOn is honest. If web calls api but does not list it, --only web will start the web app alone and it will fail on its first request. Fix the manifest, not the command.
  • Calls to services that are off. A running service that calls a service you left out will see connection errors. Decide whether to stub that call in development or start the service.
  • Shared infrastructure. In the container setup, shared parts such as Postgres and the gateway are started for the services that need them. A service that needs a database brings the database up too.
  • Stale habits. Preview with --dry-run before you rely on a subset in a script.
If a feature needs six services to work at all, a subset will not help. Start the full stack for that task and stop it when you are done.

One habit helps. For each kind of task, write down the smallest set of services that makes the feature testable, and keep it in the README as a command such as flisk up --only orders-api. A new person copies the line instead of guessing. Review the list whenever a service gains a call to another service, because a subset that worked last month breaks the day someone adds a dependency and forgets to declare it. The manifest is the contract, and the subset is only as good as that contract.

Subsets rely on a correct dependency graph, which is the topic of how to control service startup order. When you finish for the day, stop and clean up the stack.

Questions people ask

Does starting one service also start its dependencies?

With Flisk, yes: --only starts the named services plus the services they list in dependsOn. With Compose, docker compose up api also starts the services api depends_on, unless you pass --no-deps.

How do I keep a heavy service off by default?

Use an opt-in mechanism. Compose has profiles. Flisk has a profiles list in service.json and a --profile flag, and the service is also started when you name it with --only.

Can I preview what will start?

Yes. flisk up --dry-run prints the services and the start order without starting anything.
