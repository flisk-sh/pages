Run microservices on your laptop

How to run microservices locally on your laptop

You do not need Kubernetes to work on five services. You need each one running on a known port, started in the right order, with logs you can read.

To run microservices on your laptop, start each service as its own process (or container) on a fixed port, start them in dependency order, and give yourself one command that does all of it. A cluster is not required. What you need is a list of services, their start commands, their ports and what each one waits for.

Decide how each service runs

Every service in a local setup is one of two things: a process you start from source, or a container built from an image. Mixing them is normal. Your own code usually runs as a process because that gives the fastest edit loop. A database usually runs as a container because installing Postgres by hand is a chore.

Service kindUsually runs asWhy
Your API, web app, workerA local processYour runtime's watch mode reloads it on save
Postgres, Redis, a message brokerA containerNo local install, easy to reset
A service you do not work on todayA container from a published imageYou do not need its source

The plain approach, and where it gets painful

The simplest setup is a script that starts every service in the background, or a process manager that reads a list of commands (a Procfile runner or concurrently will do). For three services this is fine. It starts to hurt for four reasons:

  • Nothing waits for readiness. The web app starts before the API listens and shows an error page.
  • Two services pick the same port, and the second one fails with a message buried in the log.
  • Logs from every service are mixed in one stream, or hidden in separate files you forget to open.
  • A crashed service stays down until you notice.

Docker Compose solves several of these for containers, with depends_on and health checks. If your services already run well under Compose, keep it. See when Compose is enough and when it is not.

The Flisk way: one service.json per service

Flisk can run services that declare a command as plain local processes, with no Docker and no Tilt. Install it and describe each service in a small file next to its code:

npm install -g @flisk-sh/flisk

Say you have an api and a web folder. api/service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

web/service.json starts after the API and gets its address through an environment variable:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "node server.js",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4000" }
}

Check the plan before you run anything:

flisk up --dry-run

On a project like this one it prints which services it would start and in what order:

Would start 2 services as local processes (no Docker, no Tilt)...
  - api: node --watch server.js
  - web: node server.js (after api)
Dry run: not starting services

Then run flisk up. It stays in the foreground, prefixes every log line with the service name, waits until the API's health URL answers before it starts the web app, restarts a process that exits, and prints a http://localhost:<port> link for each service. Stop everything with Ctrl+C, or run flisk down from another terminal.

Add a database without giving up the fast loop

A service with an image and no command is started with docker run next to your local processes. Docker has to be running for that one, and nothing else changes. The database stays in a container, your code stays a process, and dependsOn orders them. The full example, with a Postgres health check and a named volume, is in the run-without-docker guide. One catch: a local process reaches that container at localhost, not by service name.

Pitfalls

  • Port clashes. Give every service its own port and write it down in its manifest. Flisk refuses to start when a port is in use and names the process that holds it. For the general fix, see how to fix port already in use.
  • Hard-coded URLs. Pass other services' addresses through environment variables, not constants in the code.
  • Mixed runtimes. A project cannot mix services with a command and services built from a Dockerfile. A ready-made image is allowed next to commands, a Dockerfile build is not.
Do not use this approach if you need to test Kubernetes itself (operators, network policies, Helm charts). Use a local cluster for that.

Once the services run, the next thing to fix is order and readiness. How to control service startup order covers it, and one-command dev environment shows how to hand the setup to a teammate.

Questions people ask

Do I need Docker to run microservices locally?

No. If every service starts with one shell command, you can run them all as plain local processes. You need Docker when a service is a database or when you want the same container image you deploy.

How many microservices can a laptop run?

It depends on the services, not on the tool. Plain processes cost what the programs cost. Containers add a base cost each. Measure your own stack with your own services before you decide.

Should every microservice have its own repository for local development?

It does not matter for running them. One repository makes one command easy. Separate repositories need a place that knows where they all live, such as a platform repository.
