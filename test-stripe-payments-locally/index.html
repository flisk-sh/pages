Payments and webhooks locally

How to test Stripe payments locally in test mode

You do not need a public URL or a live account to test a payment end to end. You need test keys, one forwarding command and an endpoint that checks signatures.

To test Stripe payments locally, use the test-mode API keys from your Stripe account, create the payment from your own server, and run stripe listen --forward-to localhost:4000/webhooks/stripe so Stripe's events reach your laptop without a tunnel. The CLI prints a signing secret for the events it forwards, and your webhook route must use that secret, not the one from the Dashboard.

What you need before the first payment

Four pieces have to line up, and most "it does not work locally" reports are one of them being wrong:

  • Test-mode keys. The secret key starts with sk_test_ and the publishable key with pk_test_. A live key (sk_live_) charges real cards, so keep it out of your laptop setup completely.
  • A server route that creates the payment. The browser never holds the secret key. It asks your server, and your server calls Stripe.
  • A webhook route. The redirect after checkout tells you the customer came back. Only the webhook event tells you the payment succeeded, so fulfilment belongs there.
  • The Stripe CLI. Install it, run stripe login once, and use stripe listen as the bridge from Stripe to your machine.

A minimal server

This Express service creates a Checkout Session and receives events. It is the smallest shape that exercises both directions:

import express from "express";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const app = express();

// The webhook route needs the raw body, so it is registered before express.json()
app.post("/webhooks/stripe", express.raw({ type: "application/json" }), (req, res) => {
  let event;
  try {
    event = stripe.webhooks.constructEvent(
      req.body,
      req.get("stripe-signature"),
      process.env.STRIPE_WEBHOOK_SECRET
    );
  } catch (err) {
    return res.status(400).send("invalid signature");
  }
  console.log("event", event.id, event.type);
  res.sendStatus(200);
});

app.use(express.json());

app.post("/checkout", async (req, res) => {
  const session = await stripe.checkout.sessions.create({
    mode: "payment",
    line_items: [{
      price_data: {
        currency: "usd",
        product_data: { name: "Test order" },
        unit_amount: 2000
      },
      quantity: 1
    }],
    success_url: "http://localhost:3000/thanks",
    cancel_url: "http://localhost:3000/cart"
  });
  res.json({ url: session.url });
});

app.get("/health", (req, res) => res.sendStatus(200));
app.listen(process.env.PORT || 4000);

Open the returned url, pay with the card number 4242 4242 4242 4242, any future expiry date, any three-digit CVC and any postal code. Stripe marks the Checkout Session as paid and sends checkout.session.completed.

Forward events with the Stripe CLI

In a second terminal:

stripe listen --forward-to localhost:4000/webhooks/stripe

It prints a line starting with Ready that contains a signing secret beginning with whsec_. Put that value in STRIPE_WEBHOOK_SECRET and restart the server. Every event now appears in the CLI output with the HTTP status your route returned, which makes a wrong secret obvious: you see 400 next to each event.

You can also fire an event without a browser:

stripe trigger payment_intent.succeeded

A triggered event has made-up data, so it proves the route works but not that your fulfilment logic finds the order. For that, pay through the real Checkout page at least once.

Running it with Flisk

If your API is a Node, Python or Go process, Flisk can start it from a service.json without Docker. Install with npm install -g @flisk-sh/flisk, then put this in api/service.json:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "env": {
    "STRIPE_SECRET_KEY": "${STRIPE_SECRET_KEY}",
    "STRIPE_WEBHOOK_SECRET": "${STRIPE_WEBHOOK_SECRET}"
  }
}

The ${NAME} form reads the value from your shell or the project .env, so the file you commit holds names only. Add the two values to .env, make sure it is in .gitignore, and run flisk up. It starts the process with PORT set, waits for /health, restarts it if it crashes and prints http://localhost:4000. The Stripe CLI keeps running in its own terminal. flisk logs --service api --since 10m shows what the webhook route did.

Pitfalls

  • Two signing secrets. An endpoint you register in the Dashboard has its own whsec_ secret. The one printed by stripe listen is different. Use the CLI's secret locally and the Dashboard's in the deployed environment.
  • A restart loses nothing, but the secret may change. If you later run stripe listen with a different login or project, check that the printed secret still matches your .env.
  • Test and live data are separate. A test-mode customer or price does not exist in live mode. Create what you need in the mode you are testing.
  • Do not trust the redirect. A customer can close the tab before the success page loads. If your order only completes on that page, some paid orders stay pending.
  • Keys in a public variable. Never put the secret key in a variable that a frontend bundle reads, such as one starting with NEXT_PUBLIC_ or VITE_. Only the publishable key belongs there.

Once a single payment works, the next question is what happens when the card fails: Stripe test cards for declines and 3D Secure lists the numbers that produce each outcome. For checking signatures and duplicate delivery without Stripe at all, see testing webhooks locally.

Questions people ask

Do I need ngrok to test Stripe webhooks locally?

No. The Stripe CLI command stripe listen forwards test-mode events to a localhost URL, so you do not need a public tunnel for Stripe.

Why does my webhook return 400 with stripe listen running?

Usually the signing secret is the wrong one. Use the whsec_ value that stripe listen prints, not the secret of a Dashboard endpoint, and make sure the route reads the raw request body.

Can I use my live Stripe key for local testing?

Do not. A live key moves real money. Use sk_test_ keys on your laptop and keep live keys only in the deployed environment.
