Compose profiles vs Flisk stacks: start only part of a project

Two ways to run only part of a system: profiles for optional services and stacks for groups. Here is how each works and when to use which.

Use a Compose profile or a Flisk profile to keep optional services out of the default start, such as an admin tool or a debugger. Use a Flisk stack to group services that belong together and start a group with flisk up <stack>. Profiles answer "should this run by default", and stacks answer "which group am I working on".

Compose profiles

A Compose service with a profiles list starts only when you enable one of its profiles. Services without profiles always start.

services:
  api:
    build: ./api
  db:
    image: postgres:17
  pgadmin:
    image: dpage/pgadmin4
    profiles: ["admin"]
docker compose up                      # api and db
docker compose --profile admin up      # api, db and pgadmin
COMPOSE_PROFILES=admin docker compose up

Profiles are a good fit for tools you want sometimes. They are weaker as a way to split a big system into parts, because every service still lives in one file and one project, and a service with a profile that another service depends on can be hard to reason about.

Flisk profiles

Flisk has the same idea in service.json. Add a profiles array with names made of lowercase letters, digits and dashes:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "admin",
  "appType": "backend",
  "command": "node admin.js",
  "port": 4100,
  "profiles": ["admin"]
}

Then choose at start time:

flisk up                      # leaves out services with profiles
flisk up --profile admin      # includes the admin profile
flisk up --only admin         # starts it regardless of profile

Services without profiles always start. flisk up prints which services it skipped, so a missing service is not a mystery. An unknown profile name is refused, and the error lists the profiles in the project. Profiles work for both container services and local-process services, and they were added in Flisk 1.4.24. If you import a Compose file, its profiles are carried over when the names fit that pattern.

Stacks

A stack is a group, set with the stack field in service.json or the --stack flag when you create a resource. It is not a Compose feature. A stack also affects the generated database name, the routes and the generated Compose project name.

flisk resource orders-api --type backend --stack shop
flisk resource shop-web --type frontend --stack shop
flisk stacks
flisk up shop
flisk up shop --dry-run

flisk stacks lists the groups, flisk resources lists services, and flisk stack <name> --resources ... assigns resources to a stack. When you start a stack, the services you name must belong to it, but their dependencies may cross into other stacks. For a service that runs as a local process, stack is optional.

Which one to use

SituationUse
A tool you need once a week (admin UI, mail catcher)Profile
A debug sidecarProfile
Shop services versus billing services in one repoStacks
Work on one service and what it needsflisk up --only <service>, which also starts its dependencies

A worked example: a repo holds a shop and a billing system, and a mail-catcher you only need when you test emails. Put the shop services in a shop stack and the billing services in a billing stack. Give the mail-catcher a mail profile. On a normal day you run flisk up shop and the mail-catcher stays off. On the day you test emails you add --profile mail. The two features answer different questions, so you can use both in one project.

Both approaches have the same weak point: they hide things. A teammate who runs flisk up and does not see the admin service may think it is broken. Write the profile names in your README next to the command that uses them.

Pitfalls

  • Dependencies on a profiled service. If a default service depends on one that has a profile, plan for it. Check flisk up --dry-run to see what will start.
  • Name rules. A Compose profile with capital letters or underscores is not carried over by the import, so rename it.
  • Stacks are not isolation. Services in different stacks share the machine, the gateway and the database host. Two stacks that need the same port still conflict, see fixing port conflicts.
  • Moving a service between stacks changes its generated names. Check the data it uses before you do.

For more on starting only what you need, read start only the services you need. If you are coming from Compose, importing your Compose file keeps the profiles you already have.

Questions people ask

How do I start a Compose profile?

Use docker compose --profile NAME up, or set COMPOSE_PROFILES=NAME. Services without profiles always start.

How do I include a profile in Flisk?

Run flisk up --profile NAME. Services with profiles are left out by default, and flisk up prints which ones it skipped. flisk up --only SERVICE starts a service regardless of its profile.

What is a Flisk stack?

A named group of services set with the stack field in service.json. flisk up NAME starts that group, and its dependencies may come from other stacks.
