Workers KV vs D1: which should you use?

KV is a fast key-value cache with eventual consistency, D1 is a relational SQLite database. Here is how to choose for sessions, config, lists and counters.

Use KV for data you read often by key and can tolerate being slightly stale, such as config, cached results and sessions. Use D1 when you need queries, relations, ordering or consistent writes.

How they differ

KVD1
ModelKey to valueSQL tables
ReadsVery fast, cached at the edgeQuery cost depends on SQL
ConsistencyEventually consistent across locationsConsistent database
QueriesList by prefix onlyJoins, filters, sorting
WritesFine for rare updatesFine for transactional writes

Good fits for KV

  • Feature flags and site configuration.
  • Cached API responses with an expiry.
  • Short-lived tokens and session data.
  • Redirect maps.
await env.CACHE.put("rates", JSON.stringify(data), { expirationTtl: 3600 });
const rates = await env.CACHE.get("rates", "json");

Good fits for D1

  • Users, orders, notes: anything with relations.
  • Lists you filter and sort.
  • Counters and balances that must not lose updates.

See using D1 for setup.

The consistency trap

A value written to KV may not be visible at once in other locations. If your code writes then immediately reads from another request, it may see the old value. Do not use KV for a counter or for anything where two writers could overwrite each other. Use D1, or a Durable Object if you need strict coordination.

A quick decision rule

Ask three questions. Do you ever need to search by anything except the key? Then use D1. Can two requests write the same value at nearly the same time? Then use D1 or a Durable Object. Is the value cached from somewhere else, or rarely changed config? Then KV is fine. If you cannot decide, start with D1. It is easier to add a KV cache in front of a working database than to migrate a data model out of a key-value store later.

Also think about cost shape. Both have free allowances and then usage-based pricing, with different units for reads and writes. Check the current pricing pages with your expected traffic in mind rather than guessing from the model alone.

Using both

A common pattern: D1 is the source of truth, KV caches the hot read. On a miss, read from D1 and write the result to KV with a short TTL. Keep the TTL short enough that staleness does not matter.

let page = await env.CACHE.get(key);
if (!page) {
  const row = await env.DB.prepare("SELECT html FROM pages WHERE slug = ?").bind(slug).first();
  page = row?.html;
  if (page) await env.CACHE.put(key, page, { expirationTtl: 300 });
}

Questions people ask

Can I list all keys in KV?

Yes, with the list operation, which supports prefixes and pagination. It is not a query language, so design keys with prefixes in mind.

Is KV a good primary database?

Usually not. Use it for caching and config, and use D1 or another database for data you cannot lose or need to query.
