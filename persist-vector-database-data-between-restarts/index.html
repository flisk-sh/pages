RAG and vector databases locally

How to keep vector database data between restarts

Re-embedding a large corpus can take hours. Put the vector store on a named volume, and know exactly which command deletes it.

A vector database keeps its data across restarts only if its data directory is on a named Docker volume or a bind mount. Without one, the data lives in the container's writable layer and disappears when the container is removed, which is what docker compose down does. Mount the right path for your engine and the embeddings survive.

Why data disappears

A container's filesystem is created from the image and thrown away with the container. Stopping a container keeps its filesystem, but removing and recreating it, which Compose does on down and up and whenever the image or config changes, starts from the image again. A volume is storage managed outside the container, so it outlives it. The general rules are in keeping Compose volumes between runs.

The path to mount for each engine

EngineMount a volume on
Qdrant/qdrant/storage
pgvector (Postgres 17 and earlier images)/var/lib/postgresql/data
Chroma serverThe directory the image persists to, check the image docs for your version (it is /data in recent images)
Ollama models/root/.ollama

Postgres 18 images changed the data directory layout, so a volume mounted at the old path is not the right shape there. Read the image notes before upgrading the major version.

Verify persistence instead of assuming it. Insert one point, remove the container, start a new one with the same volume and query again. If the point is gone, your mount path is wrong, which usually means the engine writes somewhere you did not mount.

The Flisk way

The Qdrant preset already does this: flisk resource vectors --type database --framework qdrant writes a named volume vectors-data mounted at /qdrant/storage. flisk down stops the stack but keeps named volumes, so your collections are there on the next flisk up. For a bring-your-own container, such as pgvector or Chroma, add the volume yourself in service.json:

"volumes": [{ "source": "pgv-data", "target": "/var/lib/postgresql/data" }]

A bare name is a named Docker volume, declared once in the generated Compose file. A path that starts with ./ is a bind mount relative to the service folder, which is handy when you want to look at the files, but is slower on macOS file sharing.

Deleting data on purpose

Three levels, from smallest to largest:

  1. One collection. Delete it through the database API (DELETE /collections/docs in Qdrant, TRUNCATE chunks in SQL) and re-ingest. This is the right reset for tests and for a changed chunking strategy.
  2. One volume. Stop the stack with flisk down, find the full volume name with docker volume ls --filter label=com.docker.compose.volume=vectors-data, then remove it with docker volume rm <that name>. Flisk prefixes volume names with the generated project name, so do not guess the name.
  3. Everything. flisk down --purge also deletes this project's Docker volumes, networks and images. That includes the project's Postgres data, not only the vectors. Run flisk down --purge --dry-run first to see what it would remove.

Pitfalls

  • Persisted vectors, changed model. If you change the embedding model, old vectors stay in the volume and are now wrong. Re-index, see re-embedding documents.
  • The volume is not a backup. It is local to one machine and one Docker install. If a Docker store gets corrupted, it goes with it. Keep your source documents and ingestion script in git, so the index is always rebuildable.
  • Embedded Chroma in a container. If your app uses Chroma in-process with a local directory, the app container needs that directory on a volume, not the Chroma image.

Next step

Treat the index as a build artifact you can recreate, and write the ingestion as a repeatable job. That is the topic of ingesting documents into a vector database.

Questions people ask

Why did my Qdrant collections disappear after docker compose down?

Most likely the container had no volume on /qdrant/storage, so its data was removed with the container. Mount a named volume there.

Does flisk down delete my vector data?

No. It keeps named volumes. Only flisk down --purge, or removing the volume yourself, deletes them.

Should I back up a vector index?

Better to keep the source documents and the ingestion script in version control and rebuild the index. Snapshots are an option for very large indexes.
