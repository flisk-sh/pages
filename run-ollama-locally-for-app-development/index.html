How to run Ollama locally for app development

A local model server gives your app a chat endpoint with no API key and no per-token bill. Here is the shortest path from nothing to a working call, and how to keep it next to your other services.

Install Ollama, run ollama pull for one small model, and your app can call it at http://localhost:11434. It speaks its own API under /api and an OpenAI-compatible API under /v1, so most SDKs work after changing one base URL.

Install, pull a model, check it answers

On macOS and Windows, use the installer from ollama.com. On Linux, use the install script from the same site or your package manager. Then pull a small model first. A 1B to 3B model downloads quickly and is enough to test your wiring. You can switch to a bigger one later.

ollama pull llama3.2
ollama run llama3.2 "Say hello in five words"
curl http://localhost:11434/api/tags

The last command lists the models on disk as JSON. If it answers, the server is up. The desktop app and ollama serve both listen on 127.0.0.1:11434 by default, so only your own machine can reach it.

Call it from code

The native chat endpoint takes a model name and a list of messages:

curl http://localhost:11434/api/chat -d '{
  "model": "llama3.2",
  "messages": [{"role": "user", "content": "What is a port?"}],
  "stream": false
}'

Without "stream": false the server streams one JSON object per line. That is what you want for a chat UI, and a surprise if you pipe the output straight into JSON.parse.

The OpenAI-compatible route is POST /v1/chat/completions, and GET /v1/models lists the models. If your code already uses an OpenAI client, see how to point the OpenAI SDK at Ollama.

Run it as a service in your dev stack

Running Ollama by hand works for one app. It gets awkward when a frontend, an API and a worker all depend on it, and a new teammate has to remember which terminal to open first. In that case, make the model server one more service in the project.

Flisk has a resource type for this. Inside a Flisk project, run:

flisk resource brain --type inference --stack llm --yes

It writes services/llm/brain/service.json with no Dockerfile:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "brain",
  "appType": "bring-your-own",
  "stack": "llm",
  "port": 11434,
  "healthCheckPath": "/v1/models",
  "image": "ollama/ollama"
}

So an inference resource is a bring-your-own container running the ollama/ollama image on port 11434, health-checked at /v1/models. Ollama is only the default. Anything that answers GET /v1/models can take its place, and the engine comparison shows how.

Start the stack with flisk up llm. Other containers in the stack call the model at http://brain:11434/v1/chat/completions. To reach it from your host as well, publish the port in service.json:

"extraPorts": [{ "port": 11434 }]

Flisk publishes that on 127.0.0.1 only. If Ollama is already running on your host, pick another host port with "hostPort": 11435, or the container will fail to start on the taken port.

Models are not in the image. Pull one into the running container with flisk run brain -- ollama pull llama3.2. A container service must be running for flisk run to work, since it uses docker exec.

Pitfalls

  • Models are lost on recreate. The preset mounts no volume, so pulled models disappear when flisk down removes the container. Add a volume to keep them.
  • No GPU on a Mac container. Docker on macOS cannot use the Apple GPU. For Metal speed, keep the native Ollama app and have containers call it from the host. See calling a host Ollama from a container.
  • The first request is slow. Ollama loads the model into memory on the first call and unloads it after five minutes idle by default. Send a warm-up request when the stack starts, or set OLLAMA_KEEP_ALIVE.
  • Do not pick a model that does not fit. A swapping laptop is slower than a smaller model. Check the memory rule of thumb first.

A short checklist when it does not answer

  1. Run curl http://localhost:11434/api/tags from the same place your app runs. A host terminal and a container are different places.
  2. Check the model name exactly as ollama list prints it, including any tag after the colon.
  3. Watch the server log while you send a request. A model that does not fit in memory shows up there as a load failure, not as an HTTP error from your code.
  4. Try a smaller model. If that works, the wiring is fine and the problem is size.

When the model answers, the next step is deciding how your code will talk to it. The OpenAI SDK route is the least work, and it keeps a way back to a hosted API open.

Questions people ask

What port does Ollama use?

11434 by default, bound to 127.0.0.1. Inside the official container it listens on all interfaces, so you publish the port to reach it from the host.

Does Ollama need an API key?

No. OpenAI-compatible clients still insist on a value, so pass any non-empty string such as ollama.

Do I need Docker to run Ollama?

No. The native app or ollama serve is simpler and can use your GPU on a Mac. Docker is useful when the model server is one service in a stack.
