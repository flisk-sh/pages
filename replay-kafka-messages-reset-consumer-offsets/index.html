How to replay Kafka messages by resetting consumer offsets

The messages are still in the topic. Move the group's bookmark back and the consumer reads them again.

To replay messages, stop the consumer, then run kafka-consumer-groups.sh --reset-offsets against its group with --to-earliest, a timestamp or a shift, first with --dry-run to see what would change and then with --execute. Start the consumer again and it reads from the new position. The messages are still in the topic. Only the group's bookmark moves.

What an offset reset does

Kafka keeps messages for a time (the topic's retention) whether or not anyone read them. Each consumer group stores one committed offset per partition, the position it will read next. Resetting that number does not delete or copy anything, it changes where the group starts. That makes it the right tool for:

  • Re-running a handler after you fixed a bug.
  • Reproducing a customer case from a few minutes ago.
  • Starting a fresh test run without creating a new group.

Look at the group first

The Kafka tools are inside the broker image. Without Flisk, run them with docker exec. With Flisk, use flisk run:

flisk run broker -- /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group orders-consumer

The output has one row per partition. CURRENT-OFFSET is the group's bookmark, LOG-END-OFFSET is the newest message, and LAG is the difference. List all groups with --list.

Stop the consumer

A reset is refused while the group has active members. Kafka answers with a message that the group is not inactive, and nothing changes. Stop the consumer first. If you run it as a Flisk resource, stop that resource or the whole stack, or stop the local process in its terminal. After the last member leaves, Kafka marks the group empty. A consumer that has just left may take a moment to be dropped, so wait a few seconds if the first try is refused.

Reset, dry run first

KCG="flisk run broker -- /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092"

# back to the oldest retained message
$KCG --group orders-consumer --topic orders --reset-offsets --to-earliest --dry-run

# back to a point in time (UTC)
$KCG --group orders-consumer --topic orders --reset-offsets \
     --to-datetime 2026-11-14T09:00:00.000 --dry-run

# back by 100 messages on every partition
$KCG --group orders-consumer --topic orders --reset-offsets --shift-by -100 --dry-run

Without --execute the command only prints the new offsets as a table, and --dry-run makes that explicit. When the numbers look right, repeat the same command with --execute in place of --dry-run. Other targets are --to-latest (skip everything waiting), --to-offset N and --by-duration PT30M. Leaving out --topic and using --all-topics resets every topic the group has read. To reset one partition, write --topic orders:0.

These are the flags of the Kafka 4.x tool. I did not run them on a live broker for this page, so run --dry-run before trusting any of them.

Start the consumer again

When it rejoins, the group fetches from the reset position. Watch it in flisk logs --service consumer, or in the Kafka UI where lag jumps up right after the reset and falls as the consumer catches up. Reading the messages again does not duplicate them in the topic, but it does run your handler a second time. A handler that writes to a database should therefore be idempotent. See testing a consumer locally for the handler layout that makes that easy to check.

Other ways to replay

  • A new group id. With fromBeginning: true (or auto.offset.reset=earliest), a group id the broker has never seen starts at the oldest message. It is the simplest reset, and it leaves the old group and its offsets behind, so the group list grows.
  • Read without a group. To just look at old messages, use the console consumer with --from-beginning and no group, as in reading Kafka messages from the command line. Nothing is committed.
  • Wipe the volume. Removing the broker's data volume deletes every topic, message and offset. It is the heaviest option and takes the topics job with it, so the topics come back empty when the stack starts again.

Pitfalls

  • Retention is the limit. If a message was deleted by retention, --to-earliest starts at the oldest one that is left. The default is 7 days, so a reset cannot bring back last month.
  • Time zones. --to-datetime is read as UTC. A local time typed as if it were UTC replays the wrong window.
  • Auto-commit races. A consumer that restarts quickly can commit new offsets over your reset. Stop it, reset, then start it.
  • Several consumers in a group. The reset applies to the whole group. Stop every instance first.

Questions people ask

Why does the reset say the group is not inactive?

The group still has a live member. Stop every consumer in the group, wait a few seconds for it to leave, then run the reset again.

Does resetting offsets delete or duplicate messages?

No. It only moves the group's bookmark. The handler runs again for the messages you replay, so make it safe to repeat.

Can I replay messages that retention already deleted?

No. A reset to the earliest offset starts at the oldest message that is still there, which is 7 days back by default.
