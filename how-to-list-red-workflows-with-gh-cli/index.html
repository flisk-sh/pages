How to List Failing (Red) Workflows With the gh CLI

A short script that finds every workflow whose latest default-branch run failed, across one repo or a whole organisation.

A workflow is red when its newest run on the default branch failed. List the latest run per workflow with gh run list, keep the failures and you have a red list you can act on.

Define red clearly

Agree on one definition so the list means the same thing each week. A useful one: the newest completed run of the workflow on the default branch has a conclusion of failure. Ignore cancelled and skipped runs, and ignore pull request runs. Write the definition on the page that shows the list.

One repo

gh run list -R your-org/your-repo --branch main --limit 100 \
  --json workflowName,conclusion,createdAt,url \
  | jq -r 'group_by(.workflowName)[]
    | sort_by(.createdAt) | last
    | select(.conclusion=="failure")
    | "\(.workflowName)\t\(.url)"'

This groups runs by workflow, picks the newest of each and prints the failed ones with a link.

The whole org

Loop over the repositories, skipping archived ones and anything inactive.

gh repo list your-org --limit 300 --no-archived --json name --jq '.[].name' \
| while read r; do
  gh run list -R your-org/$r --branch main --limit 100 \
    --json workflowName,conclusion,createdAt,url 2>/dev/null \
  | jq -r --arg r "$r" 'group_by(.workflowName)[]
    | sort_by(.createdAt) | last
    | select(.conclusion=="failure")
    | "\($r)\t\(.workflowName)\t\(.url)"'
done

If a repo's default branch is not main, read it with gh repo view --json defaultBranchRef and use that.

Make the list actionable

  • Add an owner column from CODEOWNERS or a repo topic; see assigning ownership.
  • Add the number of days it has been red. Old reds are the real debt.
  • Post the list to a channel weekly, not every run.

A ready-made red list

If you would rather not maintain a script, Cilytics has a red workflows section built on this definition, newest default-branch run failed, for an org or one public repo via ?repo=owner/name. It is an hourly snapshot built from the GitHub API, so a fix may take up to an hour to show. For debugging each failure, see debugging CI failures.

Edge cases

A few cases surprise people. Workflows triggered only on a schedule may have no recent run, so their newest run can be weeks old; show the age of the run next to the status. Workflows that only run on tags or releases never run on the default branch, so they will not appear at all. Decide whether to include them by listing runs for all branches in a separate report.

Matrix jobs can fail in one cell while the rest pass. The run's conclusion is still failure, which is correct, but the fix may be about one environment. Link to the run so the reader can see which cell failed.

Finally, be careful with reruns. If a run failed and a rerun of the same attempt passed, the run's final conclusion is success. That hides flakiness from the red list, which is why a separate flaky list matters. See finding flaky workflows.

Questions people ask

Why does a workflow show red after I fixed it?

If a dashboard is an hourly snapshot it lags. A script reading the API reflects the fix as soon as a new passing run exists.

Should cancelled runs count as red?

Usually no. Cancellations are often caused by newer commits via concurrency settings, not by a failure.
