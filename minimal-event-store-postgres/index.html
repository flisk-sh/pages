How to build a minimal event store in Postgres

You do not need a special database to try event sourcing. One table and one constraint get you most of the way.

A minimal event store in Postgres is a single append-only table with a primary key on (stream_id, version). Appending an event with the next version fails if someone else appended first, which gives you optimistic concurrency. The current state of an entity is a fold over its events, read in version order.

What event sourcing means here

Instead of storing the current state of an order and overwriting it, you store every fact that happened to it: OrderPlaced, ItemAdded, OrderPaid. The state is computed by replaying those facts. You gain a complete history and the ability to rebuild any view later. You pay in complexity: queries need read models, and past events cannot be edited, only corrected by new events. If you only want an audit trail, an ordinary table plus a history table is simpler. Use event sourcing when the history is the product.

The table

CREATE TABLE events (
  position   bigserial   NOT NULL UNIQUE,
  stream_id  text        NOT NULL,
  version    integer     NOT NULL,
  type       text        NOT NULL,
  data       jsonb       NOT NULL,
  metadata   jsonb       NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (stream_id, version)
);
  • stream_id identifies one entity, for example order-123.
  • version starts at 1 for each stream and goes up by one.
  • position is a global counter, useful for projections that read all events in one pass. It can have gaps and is not strictly commit-ordered, see rebuilding a read model.

Make the table append-only in practice. Do not write UPDATE or DELETE statements against it, and if you want the database to enforce it, revoke those privileges from the application role.

Appending with optimistic concurrency

The caller says which version it expects the stream to be at. The insert uses the next number, and the primary key rejects a conflicting writer:

async function append(client, streamId, expectedVersion, newEvents) {
  let version = expectedVersion;
  try {
    for (const e of newEvents) {
      version += 1;
      await client.query(
        "INSERT INTO events (stream_id, version, type, data) VALUES ($1, $2, $3, $4)",
        [streamId, version, e.type, JSON.stringify(e.data)]
      );
    }
  } catch (err) {
    if (err.code === "23505") {
      throw new Error(`stream ${streamId} changed, reload and retry`);
    }
    throw err;
  }
}

Run this inside a transaction so that a batch of events lands together. The error code 23505 is Postgres's unique violation. The usual response is to reload the stream, run the decision again on the fresh state, and retry a limited number of times.

Reading the state

async function load(client, streamId) {
  const { rows } = await client.query(
    "SELECT version, type, data FROM events WHERE stream_id = $1 ORDER BY version",
    [streamId]
  );
  const state = rows.reduce(evolve, { status: "new", items: [] });
  return { state, version: rows.length ? rows[rows.length - 1].version : 0 };
}

function evolve(s, e) {
  switch (e.type) {
    case "OrderPlaced": return { ...s, status: "placed" };
    case "ItemAdded":   return { ...s, items: [...s.items, e.data.sku] };
    case "OrderPaid":   return { ...s, status: "paid" };
    default:            return s;   // ignore events this code does not know
  }
}

The pattern is: load, decide (a function that checks business rules and returns new events), append with the loaded version. Keep evolve free of side effects and checks, because it must accept every event in history. Long streams get slow to load; add a snapshot table later when you measure a problem, not before.

The Flisk way

The event store is a table in your service's database, so what you need from Flisk is the database and a place to run the migration:

flisk resource shop-db --type database --stack shop --yes
flisk resource orders --stack shop --yes

Add "dependsOn": ["shop-db"] to the service, and per the Flisk docs it receives DATABASE_URL for the stack's database. Put the CREATE TABLE in a migration run by a migrator resource rather than in the service's start script, see database migrations in local dev. To look at the events while you develop, connect with psql as described in connecting to a local Postgres and run SELECT * FROM events WHERE stream_id = 'order-123' ORDER BY version. If you reset the database to start clean, see how to reset a local database.

Pitfalls

  • Fixing history. A wrong event stays. Append a correcting event, such as ItemRemoved, and handle it in evolve.
  • Changing event shapes. Old events never change, so you need to read every version you ever wrote, see versioning event schemas.
  • Publishing events. The store is not a broker. Use an outbox or have a poller read by position to publish, see the outbox article.
  • Personal data. Events are permanent, so deleting a user's data on request is hard. Keep personal fields out of events, or encrypt them per user and delete the key.

With events stored, the payoff is building views from them, which the next article covers.

Questions people ask

Is Postgres a good event store?

For small and medium systems, yes. It gives you transactions, a unique constraint for concurrency control and familiar tooling. Dedicated event stores add features such as subscriptions and built-in projections, which you may want later.

What is the difference between event sourcing and an outbox?

Event sourcing stores events as the source of truth and derives state from them. An outbox is a temporary table of events to publish, next to state that is stored the usual way.

Do I need snapshots?

Not at first. Load time grows with stream length, so add snapshots only when measurements show that rebuilding state from a long stream is too slow.
