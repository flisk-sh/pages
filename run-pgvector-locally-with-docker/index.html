How to run pgvector locally with Docker for vector search

If your app already uses Postgres, pgvector lets you store embeddings next to the rest of your data. Here is the smallest setup that works and keeps its data.

To run pgvector locally, start the pgvector/pgvector image instead of plain postgres, run CREATE EXTENSION vector; once per database, and store embeddings in a vector(N) column, where N is the dimension of your embedding model. Mount a volume on the data directory so the rows survive a container restart.

Why the stock Postgres image is not enough

The official postgres image does not ship the pgvector extension. If you run CREATE EXTENSION vector; against it, you get an error that the extension is not available. The maintainers publish a separate image, pgvector/pgvector, with tags that follow the Postgres major version, for example pg17. It is a normal Postgres with the extension files added, so everything you know about Postgres still applies: the same ports, the same psql, the same backup tools.

The same applies to a database that Flisk or another tool runs for you. The shared Postgres that Flisk starts for a project uses a plain postgres:16-alpine image, so it has no pgvector. For vectors you start a second Postgres of your own, with the pgvector image, next to it.

Start it with plain Docker Compose

A minimal Compose service looks like this:

services:
  pgvector:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_PASSWORD: dev
    ports:
      - "15433:5432"
    volumes:
      - pgvector-data:/var/lib/postgresql/data
volumes:
  pgvector-data:

The host port is 15433 so it does not collide with a Postgres you may already run on 5432. The volume matters: without it, docker compose down followed by up gives you an empty database. For Postgres 18 images the data directory layout changed, so if you move to pg18 read the image notes before reusing a volume.

Create the extension, a table and an index

Connect with psql postgres://postgres:dev@localhost:15433/postgres and run:

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  source text NOT NULL,
  content text NOT NULL,
  embedding vector(768) NOT NULL
);

CREATE INDEX chunks_embedding_idx
  ON chunks USING hnsw (embedding vector_cosine_ops);

The number in vector(768) must match your embedding model exactly, and Postgres rejects a vector of the wrong length. The HNSW index is optional for small tables: with a few thousand rows an exact scan is fast, and it gives perfect recall. Add the index when queries slow down, and match the operator class to the distance you query with (vector_cosine_ops for <=>, vector_l2_ops for <->).

Query the five nearest chunks to a query embedding. The <=> operator is cosine distance, so smaller is closer:

SELECT id, source, embedding <=> '[0.01, 0.02, ...]' AS distance
FROM chunks
ORDER BY embedding <=> '[0.01, 0.02, ...]'
LIMIT 5;

The Flisk way

Flisk has no dedicated pgvector preset, so you describe it as a bring-your-own container. Create the resource, then edit its service.json:

flisk resource pgv --type bring-your-own --image pgvector/pgvector:pg17 --port 5432 --no-proxy --stack rag --yes
{
  "schemaVersion": 1,
  "appName": "pgv",
  "appType": "bring-your-own",
  "stack": "rag",
  "port": 5432,
  "image": "pgvector/pgvector:pg17",
  "exposeViaProxy": false,
  "healthCheck": { "command": ["pg_isready", "-U", "postgres"] },
  "env": { "POSTGRES_PASSWORD": "dev" },
  "volumes": [{ "source": "pgv-data", "target": "/var/lib/postgresql/data" }],
  "extraPorts": [{ "port": 5432, "hostPort": 15433 }],
  "provides": { "PGVECTOR_URL": "postgres://postgres:dev@pgv:5432/postgres" }
}

What each part does: healthCheck.command makes Flisk wait until pg_isready succeeds, volumes creates a named volume that flisk down keeps, extraPorts publishes the database on the host so you can use psql, and provides adds PGVECTOR_URL to the environment of every service that lists pgv in dependsOn. Run flisk config verify to check the file, then flisk up rag. The password is a throwaway development value in a file you commit, so never reuse it anywhere real.

Pitfalls

  • Dimension mismatch. Switching embedding models changes N. Plan a new column or table and a re-index, see re-embedding after a model change.
  • Index limits. The plain vector type can be indexed up to 2000 dimensions. Larger vectors need a different type or a reduced dimension.
  • Not the shared database. Do not point your migrations at the vector instance unless you mean to. Keep one connection string per database, as in one database per service.

When pgvector is the wrong choice

If you only need a vector store and nothing relational, a dedicated engine can be simpler. Compare them in Chroma vs Qdrant vs pgvector. Next, fill the table with real data using a small ingestion script.

Questions people ask

Can I add pgvector to the official postgres image?

You can build your own image that installs the extension package, but the simpler route is the pgvector/pgvector image, which is Postgres with the extension already included.

Do I need an index for pgvector?

Not for small tables. An exact scan over a few thousand rows is fast and returns perfect results. Add an HNSW index when queries get slow, and use the operator class that matches your distance.

Does Flisk's built-in Postgres include pgvector?

No. It runs a plain postgres:16-alpine image, so run a separate pgvector container, for example as a bring-your-own resource.
