Authentication in local development

Fix OAuth redirect_uri_mismatch on localhost

The error page rarely shows the two values it compared. You can read the one your app sent straight from the address bar.

A redirect_uri_mismatch error means the callback URL your app sent to the identity provider is not on the list you registered there. The match is exact: scheme, host, port, path and trailing slash all count. Copy the real value out of the browser address bar, compare it with the registered one, and fix whichever side is wrong.

Read the URL your app actually sent

Do not trust the value you think your app uses. Start the login, and when the browser lands on the provider's error page, look at the address bar of the page just before it, or open devtools, Network, and click the first request to the provider's authorize endpoint. The query string has a redirect_uri parameter. Decode it:

redirect_uri=http%3A%2F%2Flocalhost%3A3000%2Fapi%2Fauth%2Fcallback%2Fgoogle
# decoded:
http://localhost:3000/api/auth/callback/google

Now open the provider's console and compare it to the registered redirect URI, one part at a time. Pasting both into a text editor with a monospace font makes a stray slash or a letter case difference obvious.

The differences that cause it

  • localhost against 127.0.0.1. They are different hosts to an OAuth provider, even though they reach the same machine. Pick one and use it everywhere, including in the URL you type in the browser.
  • The port. http://localhost:3000/cb and http://localhost:5173/cb are different URIs. A dev server that moves to the next free port because 3000 is taken breaks the login without any code change. Pin the port.
  • http against https. A tunnel or proxy can make your app believe it is on http while the browser used https, so the app builds the wrong URI. See why redirects go to http or the wrong port behind a proxy.
  • The trailing slash. /callback and /callback/ do not match at most providers. Frameworks that redirect one to the other make this worse.
  • The path. Library defaults differ: Auth.js uses /api/auth/callback/<provider>, Passport examples often use /auth/<provider>/callback, and Django allauth uses /accounts/<provider>/login/callback/. Read your library's documentation for the exact path.
  • Letter case and invisible characters. The host is case-insensitive in theory, but some providers compare strings. A pasted space at the end of the field is also common.
  • A stale environment value. The app reads BASE_URL or AUTH_URL once at startup, so editing .env without restarting changes nothing.

Make the value deterministic

Most of these problems vanish when the redirect URI is never guessed from the incoming request. Put the public base URL in one environment variable, build the callback from it, and register exactly that value for local development:

# .env (local only)
APP_BASE_URL=http://localhost:3000

// in code
const redirectUri = new URL("/auth/callback", process.env.APP_BASE_URL).toString();

Providers differ in how many URIs they allow. Most let you register several, so keep one local entry next to the staging and production ones. A few, such as GitHub OAuth apps, allow one callback per app, which is why a second "dev" app is the usual answer (the GitHub article in this space covers it).

Where Flisk helps

Flisk does not talk to your provider, but it decides which URL your app lives at, and that URL is what you must register.

  • Local processes. If every service has a command, flisk up prints http://localhost:<port> for each one. The port is the port field of its service.json, so it does not drift. Fix it there and register that origin.
  • Docker and Tilt. A frontend is served at http://app.<project>.localhost/<name> and a backend at http://api.<project>.localhost/api/<name>, and the ingress port is part of the URL when Traefik is not on port 80. Run flisk networks to print the exact URLs, then register the one your callback lives on.
{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "env": { "APP_BASE_URL": "http://localhost:3000" }
}

Two ports to keep apart: with a Docker stack the callback has to use the address in the browser, which is the Traefik one, not the container's internal port.

When the registered value is already right

If the strings match and it still fails, check the client. A provider may hold separate client IDs for development and production, and it is easy to use the production ID with a local secret. Look at the client_id in the same authorize request. Some providers also cache a change for a few minutes, so wait a moment after saving. For cookies that vanish after the callback instead, read do you need HTTPS to test Secure cookies on localhost.

Once the callback works, the next hurdle is usually the identity provider's own setup. The next articles here cover GitHub and Google.

Questions people ask

Is localhost allowed as a redirect URI?

Yes, for development. GitHub and Google accept http://localhost URIs. Google does not accept other custom names such as myapp.test for web clients.

Why does it work on 127.0.0.1 but not on localhost?

The provider compares strings, so the two hosts are different. Register the one you open in the browser.

Can I use a wildcard redirect URI for local ports?

Most providers do not allow wildcards. Pin the port in your dev server instead of registering many ports.
