Agent memory and context engineering

Short-term vs long-term memory for AI agents

Short-term memory is the current window and session. Long-term memory is anything stored outside it and loaded on demand. Learn the split, with simple designs for each.

Short-term memory is what is in the context window for the current session. Long-term memory is anything you store outside the window, such as notes, facts or past results, and load back only when it is relevant. The model itself keeps nothing between calls.

The practical split

Short-termLong-term
Lives inContext window, session storeDatabase, files, vector index
ScopeOne conversation or taskAcross sessions and users
CostTokens on every callTokens only when loaded
FailureOverflow, driftStale or wrong facts

Short-term: keep it small and ordered

Short-term memory is the message list plus the working state of the task: the plan, what is done, what is left. Store it per session ID so a restart can pick it up, as covered in checkpoints and session persistence.

A short "working state" block that the agent rewrites each step is more reliable than hoping it re-reads 40 messages.

Long-term: store facts, not transcripts

Do not save whole conversations and hope retrieval finds the useful sentence. Save small, self-contained notes: "User prefers metric units", "Deploy target is staging by default", "Test command is pytest -q".

  • One fact per record.
  • Add a timestamp and a source (which session, which user).
  • Add a scope: user, project or global.

Deciding what to remember

Write explicit rules. Remember stable preferences, decisions and corrections. Do not remember secrets, one-off values or anything the user did not expect to be kept.

Let a person see and delete memories. An agent that remembers silently will eventually remember something wrong, and nobody can fix it.

Pitfalls

Stale memory is worse than none: an old "the API key is X" or "we use Postgres 12" steers the agent confidently in the wrong direction. Expire or re-verify notes that can change.

For a storage design you can copy, see storing agent memory in SQLite or Postgres.

A quick example

A coding assistant is working on a bug. Its short-term memory holds the failing test output, the file it just edited and the plan for the next step. When the session ends, that goes away or is archived. Its long-term memory holds "tests run with pytest -q" and "do not edit the generated client". Next week, a new session loads those two lines and skips the discovery work. If you build multi-agent setups, the same split applies per agent, with shared notes in a store all of them can read, as in the multi-agent patterns hub.

Questions people ask

Does fine-tuning count as long-term memory?

Not in a practical sense. Fine-tuning changes behaviour and style, but it is a poor way to store facts that change or need to be deleted.

Do I need a vector database for long-term memory?

Not at the start. A table with a few hundred notes can be loaded by scope or searched with plain text matching. Add embeddings when that stops being enough.
