Databases in local development

One database per service in local development

Sharing one database between services is quick and quietly couples them. Separate databases cost one extra command and keep the boundaries honest.

Give each service its own database inside the one Postgres server you already run. You do not need a container per service. Create the databases with createdb, give each service a URL that points at its own, and never let one service query another's tables.

Why separate them

When two services share a database, a column rename in one breaks the other and neither team sees it until runtime. A shared database also hides which service owns which table, and it lets a quick join slip in where an API call belongs. A separate database makes the boundary physical, and it matches how you will likely run in production, so the local setup finds coupling early. If your services really do need the same data, that is a design discussion, not a reason to share: see worker and API sharing a database for the legitimate case of a worker and API that belong to one service.

The general approach

One Postgres server can hold many databases. Create one per service, and for stricter isolation one role per service that may only connect to its own:

createdb -U postgres orders
createdb -U postgres billing
psql -U postgres -c "CREATE ROLE billing_app LOGIN PASSWORD 'dev-only'"
psql -U postgres -c "GRANT CONNECT ON DATABASE billing TO billing_app"
psql -U postgres -c "REVOKE CONNECT ON DATABASE billing FROM PUBLIC"

The last line matters: by default every role may connect to every database, so without it the separate role stops nothing. Each service then gets its own URL, such as postgresql://billing_app:dev-only@db:5432/billing. Migrations run per database, so each service owns its own migration folder. A database per service does mean no cross-service foreign keys. That is the point, but plan for it.

The Flisk way

Flisk already separates databases by stack. It runs one Postgres container per project, and each stack gets its own database inside it. For project my-shop, the stacks store and billing give the databases my_shop_store and my_shop_billing, per the Flisk data guide. Create the stacks and services like this:

flisk resource orders-api --type backend --stack store --feature prisma --yes
flisk resource invoices-api --type backend --stack billing --feature prisma --yes
flisk up

Each service receives a DATABASE_URL for its own stack's database. The migrator for each stack applies migrations only there. Check the result instead of trusting it:

docker exec my_shop_postgres psql -U my_shop -d postgres -c "\l"

Container and user names follow your project name, so adjust them. The service manifest reference gives the default database name as FLISK_{stack}, so the list is the source of truth.

If you need two databases inside one stack, a bring-your-own container can set databaseName in its service.json. The value may contain letters, digits, _ or -, up to 63 characters. A service that sets it receives a DATABASE_URL for that name.

It is not confirmed that Flisk creates a custom-named database for you. After flisk up, run the \l listing above. If the name is missing, create it once with docker exec my_shop_postgres createdb -U my_shop -O my_shop NAME. A job that must work on a fresh volume should create it itself, as the bring-your-own examples in the repository do.

Isolation here is by database, not by role. Every service connects as the project superuser, so a service could still read another database if its code tried. Treat the separation as a convention that keeps code honest, and add roles as above if you need enforcement. Keep that in mind before you describe it as secure.

Pitfalls

  • Shared tables by accident. Two services pointing DATABASE_URL at the same database name are not separated. Check the names with \l.
  • Resetting too much. flisk down --purge removes every database. To reset only one, drop that database as shown in how to reset a local database.
  • Cross-service joins. If you find yourself wanting one, call the other service's API or copy the needed data through a queue.
  • Connection limits. Many services each holding a pool can exceed Postgres's default of 100 connections. Keep pools small locally.
  • Startup order. A service that needs another's data must wait for it. See service startup order.

When not to split

A small app with one deployable and a worker is one service. Do not split a database to look like microservices. Split when two teams, or two release cycles, own the data. For a typical web app plus API, the layout in Next.js, Express and Postgres uses a single database on purpose.

For the values each service needs, go back to DATABASE_URL and env vars locally.

Questions people ask

Do I need a separate Postgres container per service?

No. One Postgres server holds many databases. Create one database per service inside it.

How does Flisk separate databases?

Each stack gets its own database inside the project's single Postgres container. Check the names with \l.

Does Flisk enforce that a service cannot read another database?

No. Services connect as the project superuser, so separation is a convention. Add per-service roles if you need enforcement.
