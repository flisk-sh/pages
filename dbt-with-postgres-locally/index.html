How to run dbt with a local Postgres database

dbt turns SQL files into tables and views and tests them. Against a local Postgres it takes five minutes to set up, and the main trap is where the connection settings come from.

To run dbt against a local Postgres database, install dbt-postgres, create a project with dbt init, and write a profiles.yml that reads host, user, password and database from environment variables. Then dbt debug checks the connection and dbt build runs your models and tests. The same two commands work on your host and in a container.

Set up on the host

python -m venv .venv && . .venv/bin/activate
pip install dbt-postgres
dbt init shop --skip-profile-setup

Put a profiles.yml in the project folder and tell dbt to look there with --profiles-dir .. Keep credentials out of the file. dbt supports the env_var function in profiles:

shop:
  target: dev
  outputs:
    dev:
      type: postgres
      host: "{{ env_var('DBT_HOST', '127.0.0.1') }}"
      port: "{{ env_var('DBT_PORT', '5432') | as_number }}"
      user: "{{ env_var('DBT_USER') }}"
      password: "{{ env_var('DBT_PASSWORD') }}"
      dbname: "{{ env_var('DBT_DB') }}"
      schema: analytics
      threads: 4

Add a model, models/orders_daily.sql:

select date_trunc('day', created_at) as day, count(*) as orders
from {{ source('app', 'orders') }}
group by 1

Declare the source and a couple of tests in models/schema.yml (unique and not_null on a key column), then run:

export DBT_USER=app DBT_PASSWORD=secret DBT_DB=app
dbt debug --profiles-dir .
dbt build --profiles-dir .

build runs models, tests and seeds in dependency order and stops downstream work when a test fails, which is what you want. Models land in the analytics schema, so they never overwrite your application tables. See running Postgres locally for development if you do not have a database yet.

The Flisk way

Flisk gives a container a DATABASE_URL when its dependsOn lists postgres or another database resource. dbt does not read a URL, so a short entrypoint splits it into the variables the profile uses. Create the job:

flisk resource postgres --type database --stack ml --yes
flisk resource transform --type bring-your-own --stack ml --dockerfile ./Dockerfile --restart no --yes

The services/ml/transform folder holds the dbt project, profiles.yml and this Dockerfile:

FROM python:3.12-slim
WORKDIR /app
RUN pip install --no-cache-dir dbt-postgres
COPY . .
RUN chmod +x run.sh
CMD ["./run.sh"]

And run.sh:

#!/bin/sh
set -e
eval "$(python - <<'EOF'
import os
from urllib.parse import urlparse
u = urlparse(os.environ["DATABASE_URL"])
print(f"export DBT_HOST={u.hostname} DBT_PORT={u.port or 5432}")
print(f"export DBT_USER={u.username} DBT_PASSWORD={u.password} DBT_DB={u.path.lstrip('/')}")
EOF
)"
dbt build --profiles-dir .

Check that service.json has "restart": "no", "exposeViaProxy": false and "dependsOn": ["postgres"], which are the fields for a one-shot job:

flisk config verify
flisk up ml
flisk logs --service transform --tail 100

The job runs dbt build once and exits. Services that list transform in their own dependsOn start after it exits with 0, so a failing test stops them. This is the same pattern as running migrations, and the general idea is in running a one-shot job in a local stack. Keep the migrations that create the source tables in their own job, and make the dbt job wait for it.

Seeds, sources and tests worth adding first

Three small habits make a dbt project trustworthy early. First, declare every table you read as a source and never write the table name directly in a model, so dbt knows the lineage and you can add freshness checks later. Second, put unique and not_null tests on the key of each model; they catch duplicated joins within seconds. Third, keep small reference data, such as a list of country codes, in the seeds folder as CSV and load it with dbt seed, which dbt build also does. Run dbt docs generate now and then to see the dependency graph of your models, which often shows a model that nothing uses.

Use dbt build --select orders_daily+ to build one model and everything downstream of it while you iterate. The plus sign after a name means its children. Selecting a single model keeps the feedback loop short, and the full dbt build in the job stays the final check.

Pitfalls

  • Passwords with special characters. The entrypoint reads the URL as plain text. If the password has characters such as @ or /, they arrive percent-encoded. Decode them with urllib.parse.unquote before exporting.
  • Rebuilding the image for every model change. While you edit SQL, run dbt build on your host against the published port and use the container for the clean run.
  • Wrong schema. If tables appear in public, your profile has no schema or a model sets its own. Set it explicitly.
  • Not for huge data. Postgres is fine for development samples. Large analytical work belongs in a column store, see ClickHouse for local analytics.

Questions people ask

Does dbt support a DATABASE_URL?

No. The Postgres adapter takes host, port, user, password and database separately. Split the URL into environment variables and read them with env_var in profiles.yml.

Where does dbt look for profiles.yml?

In the project folder when you pass --profiles-dir ., otherwise in the .dbt folder of your home directory.

What is the difference between dbt run and dbt build?

run builds models only. build runs models, tests, seeds and snapshots in dependency order and stops downstream nodes when a test fails.
