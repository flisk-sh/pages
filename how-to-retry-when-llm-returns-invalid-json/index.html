How to retry when an LLM returns invalid JSON

Retry with the exact validation error, cap the attempts, change one thing between tries and fail safely. A loop you can copy, plus what not to retry.

Catch the parse or validation error, send it back to the model with the failed reply and ask for a corrected one, and stop after two or three attempts. Retrying blindly with the same input mostly repeats the same mistake.

The loop

def get_valid(prompt, parse, call_llm, max_tries=3):
    messages = [{"role": "user", "content": prompt}]
    last_err = None
    for attempt in range(max_tries):
        reply = call_llm(messages)
        try:
            return parse(reply)
        except Exception as e:
            last_err = str(e)
            messages += [
                {"role": "assistant", "content": reply},
                {"role": "user", "content": "That failed validation:\n"
                 + last_err + "\nReply again with corrected JSON only."},
            ]
    raise ValueError("no valid output: " + last_err)

Why feeding back the error works

The error names the field and the rule: "priority: must be between 1 and 3". That is far more useful than "try again". Keep the message short and put the original request in view, so the model fixes the object rather than rewriting the task.

What to change between tries

  • Add the error (always).
  • Lower the temperature on later tries, if your API allows it.
  • On the last try, switch to a stronger model or a simpler schema, if you can afford it.

Prefer enforced structured output to a retry loop where it exists, as described in getting reliable JSON. Retries should be the rare path.

What not to retry

Do not retry network errors, rate limits and timeouts with this loop. They need backoff and a different handler. Do not retry when the input itself is the problem, such as an empty document: validate input before the call. And do not retry actions with side effects. Parsing may be safe to repeat, but a tool call that sends an email is not.

Measure and cap cost

Count how many calls needed a retry. If more than a few percent do, fix the prompt or schema instead of relying on the loop: each retry costs tokens and time. Set a hard cap, log the raw replies of failures, and add the worst of them to your test set. Related: cutting LLM cost and latency.

Log what failed

Store the raw reply, the error and the attempt number for every failure. After a week, group the errors by field. You will often find one field behind most failures, such as a date format or a number returned as text. Fix that with a clearer description, an example or a looser schema, and your retry rate drops without touching the loop.

Questions people ask

How many retries are reasonable?

Two or three. If the third still fails, the problem is usually the prompt, schema or input, not luck.

Should I strip markdown fences and repair the JSON myself?

A small repair step for stray code fences is fine as a fallback. It should not replace enforced output or validation.
