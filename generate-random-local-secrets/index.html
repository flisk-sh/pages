Env vars and secrets in local dev

How to generate random secrets for local development

A hardcoded fallback such as change-me ends up in real deployments. A random value per machine costs one line.

Generate the secret once per machine with a random source, write it to your untracked .env, and let the app fail if it is missing. openssl rand -hex 32 prints 64 hex characters from a secure source, which is enough for a JWT signing key, a session secret or an encryption key in development.

Why not a fixed fallback

A line such as process.env.JWT_SECRET || "dev-secret" is convenient and wrong. The fallback is in the repository, so everyone knows it. When someone deploys without setting the variable, the app starts happily and signs tokens with a public key. A missing secret should be an error, not a default. Generating a random one per developer gives you the convenience without the hole.

One-liners that work everywhere

# 32 random bytes as hex (64 characters)
openssl rand -hex 32

# the same as base64
openssl rand -base64 32

# without openssl
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
python3 -c "import secrets; print(secrets.token_hex(32))"

Append the result to .env only when the name is not there yet, so a rerun does not rotate a value that sessions or encrypted data depend on:

grep -q '^SESSION_SECRET=' .env 2>/dev/null || echo "SESSION_SECRET=$(openssl rand -hex 32)" >> .env

Put that in a make setup or scripts/setup.sh that new developers run once. Create the file with restricted permissions (chmod 600 .env), because on a shared machine other users could otherwise read it.

Sizes: 32 bytes is a sound default for signing and session keys. An encryption key must match what the cipher expects, for example 32 bytes for AES-256, so check the library before choosing the length.

Let Flisk generate them

flisk project already generates DB_PASSWORD and JWT_SECRET in the project .env, per project and never shared. For your own secrets, declare them in service.json under secrets.generate:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "secrets": { "generate": { "SESSION_SECRET": "hex:32", "APP_ENCRYPTION_KEY": "base64:32" } },
  "env": { "SESSION_SECRET": "${SESSION_SECRET}", "ENC_KEY": "${APP_ENCRYPTION_KEY}" }
}

On flisk up, before any service starts, each name missing from the project .env is appended once with a random value from crypto.randomBytes. What the documentation promises:

  • hex:N or base64:N means N random bytes, with N between 8 and 128.
  • A new .env is created with mode 0600. Existing lines are never changed or reordered.
  • A name that already has a value in .env or the shell is kept, so the value is stable across restarts.
  • flisk up prints the names it generated and never the values.
  • With --env-file, the names are appended to that file instead.

flisk config verify refuses a bad spec. I tried hex:2 and it reported that N must be between 8 and 128 bytes. It also refuses a generated name that has a fixed value in the same service's env or params. A name in secrets.required that is also generated counts as satisfied, so a container service that needs the value injected can list it under both. Read the value a service sees with flisk run web -- printenv SESSION_SECRET, bearing in mind that it prints a secret to your terminal.

What can go wrong

  • Deleting .env rotates the secret. Existing sessions stop validating, and anything encrypted with the old key becomes unreadable. Back up .env if the key protects data you cannot recreate. Local development data usually can be recreated.
  • Do not copy the dev value to production. Production gets its own secret from your platform. The point of per-machine generation is that no two environments share one.
  • A different DB_PASSWORD does not change an existing database. A Postgres volume keeps the password it was created with. See how to reset a local database.
  • Short is not secure. Eight bytes is the Flisk minimum, not a recommendation. Use 32.

Questions people ask

How long should a local JWT secret be?

32 random bytes, which is 64 hex characters from openssl rand -hex 32, is a sound default for signing keys. Encryption keys must match the cipher, for example 32 bytes for AES-256.

Does Flisk regenerate a secret on every flisk up?

No. A name already in the project .env, or set in the shell, is kept. It generates a value only for names that are missing, and never prints the value.

Can I reuse the local secret in production?

No. Generate a separate value for each environment and store the production one in your platform's secret store.
