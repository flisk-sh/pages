AI sandboxes for agents

CPU, memory and timeout limits for agent-run code

Set the right limits for CPU, memory, processes, disk and wall-clock time so a runaway script from an agent cannot hurt your machine or your bill.

Set five limits on every sandbox run: wall-clock time, memory, CPU share, process count and disk. Pick small defaults, raise them per job type, and always kill the sandbox from outside when time is up, because code cannot be trusted to stop itself.

The five limits

LimitStopsDocker flag
Wall-clock timeInfinite loops, hung callsYour wrapper plus docker kill
MemoryOut-of-memory on host--memory 512m --memory-swap 512m
CPUStarving neighbours--cpus 1
ProcessesFork bombs--pids-limit 100
DiskFilling the volume--tmpfs /tmp:size=100m, read-only root

Time: enforce it from outside

A timeout inside the sandbox can be defeated by the code itself. Enforce time from the host: start the container with a name, wait, then kill it.

docker run -d --name job42 --network none --memory 256m my-image python main.py
timeout 30 docker wait job42 || docker kill job42
docker logs --tail 200 job42
docker rm -f job42

For a Python host program, subprocess.run(..., timeout=30) followed by docker kill does the same, as shown in the Docker recipe.

Memory: set swap equal to memory

If you set --memory alone, Docker may allow additional swap. Setting --memory-swap to the same value prevents swapping, so a leak ends in a clean out-of-memory kill with exit code 137 instead of a slow machine.

Choosing defaults

Start strict: 10 seconds, 256 MB, half a CPU, 64 processes, 64 MB of scratch space. Log how often each job type hits a limit. If a legitimate job such as a build or a test run keeps hitting memory, create a named profile with higher values instead of raising the global default.

PROFILES = {
    "snippet": {"time": 10, "mem": "256m", "cpus": "0.5"},
    "tests":   {"time": 120, "mem": "1g",   "cpus": "2"},
}

Limits also protect the bill

On a hosted sandbox you pay for time and size. A strict time limit is a cost cap as well as a safety measure. Tie each limit to a per-run budget, which the cost article covers. Also cap the number of runs per agent session so a retry loop cannot launch hundreds of sandboxes.

Report limits back to the agent

When a limit stops a run, return a plain message such as "killed: exceeded 256 MB memory" or "timed out after 10 seconds". The model can then adapt, for example by processing a file in chunks. A bare exit code leaves it guessing, and guessing leads to retry loops. Include the limit in the tool description as well, so most code fits from the start.

Questions people ask

What exit code means out of memory?

Exit code 137 usually means the process was killed by SIGKILL, which is what the kernel does when a container exceeds its memory limit. Check docker inspect for OOMKilled.

Should the agent be told the limits?

Yes. Put the limits in the tool description so the model writes code that fits, and return clear error text when a limit is hit.
