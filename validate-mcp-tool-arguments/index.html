Build your own MCP server

How to validate MCP tool arguments with Zod or Pydantic

A model can send the wrong type, a missing field or a huge limit. Put the rules in the schema and keep the data-dependent checks in the tool.

Declare the input schema with Zod in the TypeScript SDK or with type hints and Pydantic Field in the Python SDK, and put the limits in the schema: types, minimums, maximums, enums and defaults. The SDK turns the schema into JSON Schema for the client and checks incoming arguments against it before your function runs. Keep checks that depend on your data, such as "this order exists", inside the tool.

Why validation matters in MCP

The caller is a language model. It usually sends valid arguments, but it can send a string where you expect a number, invent a field, leave out a required one, or pass an enormous limit. An MCP server also gets calls from scripts and other clients that never read your descriptions. Validate everything at the edge, the same way you would for a public HTTP API.

TypeScript with Zod

With McpServer.registerTool, the inputSchema is an object of Zod types. This is the same pattern the Flisk MCP scaffold uses for its echo tool.

import { z } from 'zod';

server.registerTool(
  'search_orders',
  {
    description: 'Search orders by customer email and status',
    inputSchema: {
      email: z.string().email().describe('Customer email address'),
      status: z.enum(['open', 'shipped', 'cancelled']).default('open'),
      limit: z.number().int().min(1).max(50).default(20),
    },
  },
  async ({ email, status, limit }) => {
    const rows = await db.findOrders(email, status, limit);
    return { content: [{ type: 'text', text: JSON.stringify(rows) }] };
  }
);

The handler receives typed values, with defaults applied. If a call arrives with limit: 500, the schema rejects it and the handler never runs. Use .describe() on fields, because the descriptions travel to the client inside the JSON Schema and the model reads them.

Python with type hints and Pydantic

In FastMCP the function signature is the schema. Use Annotated with Field when you need limits or descriptions.

from typing import Annotated, Literal
from pydantic import Field

@mcp.tool()
def search_orders(
    email: Annotated[str, Field(description="Customer email address")],
    status: Literal["open", "shipped", "cancelled"] = "open",
    limit: Annotated[int, Field(ge=1, le=50)] = 20,
) -> list[dict]:
    """Search orders by customer email and status."""
    return db.find_orders(email, status, limit)

A bad argument fails validation before your code runs. A parameter without a default is required, and one with a default is optional.

What the client sees when validation fails

How a failure is reported depends on the SDK and its version. Some versions return a JSON-RPC error for invalid parameters, and some return a normal tool result with isError: true and a message. Do not guess: send a bad call to your own server and read the reply. The Streamable HTTP guide shows the request format. The Flisk docs state that for the TypeScript scaffold invalid arguments come back as an MCP error result and not as a crash, which is the behaviour you want to preserve if you change the setup.

Check your schemas with Flisk

If the server runs as a Flisk resource, flisk mcp check <resource> --call calls each tool once, building sample arguments from its inputSchema. It fills every required property: it uses a default, an example or the first enum value when there is one, and otherwise a typed sample such as example for a string or 1 for a number, respecting minimum, maximum and format. A tool call that returns isError, or no content, is reported as a failure. This tells you quickly whether a schema is satisfiable and whether the tool survives its own simplest input. Be careful, because a call can have side effects: a tool that writes or sends something will do it. That is why the command makes no calls unless you add --call.

Validation beyond the schema

  • Existence and permission. A schema cannot know that an order ID is missing or that the caller may not see it. Check inside the tool and return a clear error.
  • Cross-field rules. "End date after start date" is easy in code and awkward in a schema. Do it in the handler.
  • Size. Cap lists, string lengths and page sizes, so a single call cannot make the server read or return too much.
  • Injection. Never build SQL, shell commands or file paths by pasting an argument into a string. Use parameterized queries and an allowlist of paths.

When a check inside the tool fails, the message you return is what lets the model correct itself. Returning errors from an MCP tool shows how to write it.

Questions people ask

Does the MCP SDK validate tool arguments for me?

Yes. Both official SDKs convert your schema to JSON Schema and check incoming arguments before running the tool. You still need your own checks for data-dependent rules.

Should I use Zod or JSON Schema directly?

In the TypeScript SDK, Zod is the usual choice and it generates the JSON Schema for you. In Python, type hints and Pydantic do the same job.
