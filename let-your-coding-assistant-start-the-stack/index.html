MCP servers and coding assistants

How to let your coding assistant start and check your local stack

An assistant that can start your stack saves a lot of copy and paste. It also needs rules, because starting is not the same as being healthy.

Let an assistant run the stack through a small set of structured tools, in a fixed order: check the machine, start detached, poll status until ready, read logs when something is red, stop when done. With Flisk, flisk mcp provides those tools as doctor, up, status, logs and down.

Why a shell is not enough

Any coding assistant can type docker compose up in a terminal. Three things go wrong. A foreground command never returns, so the assistant sits blocked on a log stream. The output is a wall of text that a model has to interpret. And "the command returned" gets mistaken for "the stack works". Starting detached, asking a status question and getting a bounded log snapshot fix all three, whether you build that yourself with scripts or use a ready-made server.

The order of calls

Connect the server first (flisk connect claude, cursor or codex, see connecting Claude Code). Then the assistant should follow this loop:

  1. doctor. It checks the container runtime, Tilt, Docker Compose, host and ingress ports, disk space and the project's own configuration. It reports data.ready and data.host.canUp, with a suggested fix for each problem. A passing doctor means the host can start a stack. It does not mean your services are healthy.
  2. up. It starts the stack detached and watches briefly for early failures. It returns as soon as startup has begun, not when the stack is ready. A first build can take minutes.
  3. status. Repeat it until data.tilt.readiness.ready is true. It also reports the services, their ingress URLs and ports.
  4. logs. When something is not ready, read a bounded snapshot (200 lines by default, 10,000 at most), optionally for chosen services or a since window such as 5m. It is a snapshot, not a live stream.
  5. resource_restart or down. Restart the one service that needs it, or stop everything when you are done.

Prompts that follow that order are easy to write:

Run Flisk doctor and tell me what would block startup. If it passes, start only web and its dependencies, poll status until ready, and give me the URLs. If a service is red, read its last 100 log lines before you change anything.

Starting part of the stack

up accepts only, a list of service names. Flisk starts their dependencies and the shared infrastructure with them. For a ten-service project that is the difference between a quick check and a full boot. It also accepts stack, waitSeconds (the window for early failures) and force (replace an existing Tilt process).

What else the assistant can reach

Besides the lifecycle tools, the server has resource_list, network_list for URLs, resource_run for a one-off command with one service's environment (a seed script, printenv), config_verify to check generated files, and agent_sessions if you run agents. resource_run needs the container to be running.

Limits you should set

  • Tools that change files are cautious by default. config_regenerate is a dry run until dryRun is false, and a real run discards hand edits in generated files. project_eject is refused without confirm: true. Still, read what the assistant plans to run, as your assistant's permission prompts allow.
  • It cannot see what is not logged. If a service fails quietly, the assistant sees a red status and an empty log. Make services print their startup errors.
  • It does not fix your machine. If Docker is not running, doctor says so and the assistant should stop and tell you, not try to install things.
  • Parallel agents collide. Two worktrees of the same repository inherit the same project name and fixed ports. Starting both gives container-name conflicts and port errors. Give each worktree its own project.name and port overrides, or run them one at a time.

Without Docker

If every service in service.json declares a command, flisk up runs them as plain local processes, with no Docker or Tilt. The same tools work, which is useful on a laptop where Docker is heavy. See running services without Docker. A project cannot mix local processes and containers yet.

When it is not worth it

For a single process you start with one command, a shell is enough. The loop above pays off once a stack has a gateway, a database and several services, and you want the assistant to answer "what is red and why" from facts. When something does fail, give it the project's rules in an AGENTS.md so it reads logs first and edits second. That is the next step: write an AGENTS.md file.

Questions people ask

Does a successful up mean my stack is ready?

No. up starts the stack detached and returns when startup has begun. Check status until data.tilt.readiness.ready is true, and read logs for any service that stays red.

Can my assistant start only part of the stack?

Yes. Pass the service names in only. Flisk starts their dependencies and the shared infrastructure with them.

Does the assistant need Docker to use flisk mcp?

Not to connect the server or run doctor. Docker and Tilt are needed to start a container stack, but a project whose services all declare a command runs as local processes without them.
