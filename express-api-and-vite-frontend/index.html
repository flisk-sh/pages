Express API and Vite frontend in one dev command

An Express API and a Vite app are two processes that must agree on ports and origins. Here is the plain way, and the one-command way.

The usual way to run an Express API and a Vite frontend together is two processes plus a proxy rule: Vite forwards /api requests to Express, so the browser sees one origin. You can start both with concurrently or an npm script, and Flisk can do the same from a service.json per service, with the API started before the frontend.

The problem: two processes and one browser

Express might listen on port 3001 and Vite on 5173. Each starts on its own, logs to its own terminal, and fails in its own way. Three things usually go wrong: the frontend starts before the API is ready and shows a connection error, the frontend calls a hard-coded URL that differs between machines, or the browser blocks the call because of CORS.

The plain approach

Put the Vite proxy in vite.config.ts and call relative URLs from the frontend code.

import { defineConfig } from 'vite';

export default defineConfig({
  server: {
    proxy: {
      '/api': { target: 'http://localhost:3001', changeOrigin: true },
    },
  },
});

Then run both from the repository root with a single script:

npm install -D concurrently
# package.json
"scripts": {
  "dev": "concurrently -n api,web \"npm --prefix api run dev\" \"npm --prefix web run dev\""
}

This is a good answer for two services. It does not wait for the API to be healthy, and it needs everyone to know the port in two places.

The Flisk way, as local processes

Flisk can scaffold both services so that each one has a command and needs no Docker:

npm install -g @flisk-sh/flisk
flisk resource api --framework express --local --stack app --yes
flisk resource web --local --stack app --yes
flisk up

The Express scaffold gets command: npm run dev, a /health route and a healthCheckPath. The React frontend gets a plain Vite config that proxies /health and /api to the API's local port. Flisk starts the services in dependsOn order, waits up to 60 seconds for each to answer, and restarts a crashed process with a growing delay (1, 2, 4 and 8 seconds).

The frontend manifest names the API in dependsOn, which is what orders the start:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "VITE_API_URL": "http://localhost:4000" }
}
The Express scaffold runs its dev script with Bun (bun run --watch src/index.ts), so Bun must be installed even for the local route. If you do not use Bun, write the command yourself, for example node --watch src/index.js, and keep the same manifest fields.

Only the API, or only the frontend

Because every service is its own entry, you can start part of the stack:

flisk up --only api
flisk up --dry-run

--only starts one service (and what it depends on), and --dry-run prints what would run without starting it. Stop everything with flisk down.

When you want real URLs: the Docker route

The local route gives you http://localhost:<port> URLs. If you prefer names, the Docker route runs the same services in containers behind Traefik. A frontend named web is served at http://app.<project>.localhost/web, and an API named orders-api at http://api.<project>.localhost/api/orders, with the /api/orders prefix removed before the request reaches Express. Browsers resolve *.localhost without any /etc/hosts entry. In that mode the frontend receives the API address in VITE_API_URL from a generated file, so the code does not hard-code it. See local URLs instead of ports for how the routing works.

Pitfalls

  • Two sources for the API port. The Vite proxy target is written when the service is scaffolded. If you change the API's port later, update the proxy target too.
  • The proxy only forwards the prefixes you list. The scaffold forwards /health and /api. Add other prefixes if your routes live elsewhere.
  • Express must bind a reachable host. Local processes are fine on localhost. Inside a container the server must listen on 0.0.0.0.
  • Do not rely on start order for readiness. The frontend waiting for the API hides a race on a cold start, but your code should still handle a failed first request.

Next step

When the API needs a database, move to Next.js, Express and Postgres, where migrations run in their own service instead of the API start script.

Questions people ask

How do I proxy API calls from Vite to Express?

Add server.proxy in vite.config.ts with the path prefix as the key and the Express URL as the target. The frontend then calls relative URLs like /api/items and Vite forwards them.

Do I need CORS when I use the Vite proxy?

Not for requests that go through the proxy, because the browser only talks to the Vite origin. You do need CORS if the frontend calls the API origin directly or the apps are deployed on different hosts.

How does Flisk know to start Express before Vite?

The frontend service lists the API in dependsOn. Flisk starts services in that order and waits for the API health check before it starts the dependent service.
