Docker on Mac: speed and resources

Why docker build is slow on a Mac and how to speed it up

Most slow builds are not about the Mac. They re-run steps that should have been cached. A few Mac specific costs sit on top.

A slow docker build on a Mac is usually caused by a large build context, a Dockerfile that orders layers so the cache is lost on every edit, or downloads that repeat on each build. Add a .dockerignore, copy dependency manifests before source, and use BuildKit cache mounts for package downloads. Then check the build output to see which step is actually slow.

See where the time goes

Run the build with plain progress output, so every step and its duration is visible:

docker build --progress=plain -t myapp .

Look at the first lines. "transferring context" with a large size means the context is the problem. A step marked CACHED was reused. A step that takes a minute and was not cached is the one to fix.

Shrink the build context

Before any step runs, Docker sends the build context, normally the whole folder, to the builder. On a Mac the builder is inside the VM, so every megabyte crosses the VM boundary. A project with node_modules, .git, build output and data folders can send gigabytes. A .dockerignore file in the context root stops that:

node_modules
.git
dist
.next
coverage
*.log
.env

It also stops host files with secrets such as .env from being copied into an image by mistake. Check the effect: the "transferring context" size should drop to a few megabytes.

Order layers by how often they change

Docker reuses a layer only if the step and everything before it are unchanged. Put things that change rarely first:

FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

If you wrote COPY . . before the install, every edit to any file would repeat the install. The same idea applies to pip install -r requirements.txt, go mod download and cargo fetch: copy the manifest, fetch, then copy the source.

Cache package downloads between builds

A layer cache is lost when a manifest changes, and then every package is downloaded again. BuildKit cache mounts keep the download cache across builds:

RUN --mount=type=cache,target=/root/.npm npm ci
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

The cache lives in the builder, not in the image, so it does not make the image larger. If your Docker is old enough not to enable BuildKit by default, use docker buildx build.

Mac specific costs

  • Emulated builds. A build for linux/amd64 on Apple Silicon runs every step under emulation. Build for arm64 while developing and for amd64 in CI. See amd64 images on Apple Silicon.
  • Too little VM. A build that swaps in a small VM is slow. A compile or a bundler step can use more memory than the running service, so check the VM size as in memory and CPU for Docker.
  • Bloated cache. A very large build cache makes lookups and disk use worse. docker system df shows the build cache size, and docker builder prune clears it, at the price of one slow build afterwards.

What Flisk does for its own builds

Flisk's generated Dockerfiles use the layering above: a dependency stage that copies only manifests and installs, with package manager cache mounts such as /cache/bun, then a stage that copies source. Editing application code does not repeat the install. Flisk also keeps the shared Docker build cache from growing without limit: flisk up trims it to 20 GiB by default using docker builder prune -f --keep-storage. You can change the limit with FLISK_BUILD_CACHE_MAX_GIB, and 0 turns the trim off.

FLISK_BUILD_CACHE_MAX_GIB=40 flisk up
flisk down --prune-cache

flisk down --prune-cache prunes build cache older than 24 hours by default. The cache is shared by every project on the machine, not only this one. For a Dockerfile you wrote yourself, run it as a bring-your-own resource with flisk resource <name> --type byo --dockerfile <path>, and apply the advice in this article to it, because Flisk does not rewrite your Dockerfile. More on that is in run an existing Dockerfile in a local dev stack.

Pitfalls

  • Cache busting by accident. ARG values or a timestamp used early in the file invalidate every layer after them.
  • Installing and building in one layer. If they are separate steps, a source change only repeats the build step.
  • Copying a lockfile that changes every time. A generated file in the manifest copy defeats the cache.
  • Pruning too eagerly. Clearing the cache every day makes every first build slow. See Docker disk full for a safe order.

Once builds are cached, the next cost is how long the running stack takes to boot. Run the slow service natively if it does not need an image to be correct: which services to run natively on a Mac.

Questions people ask

Why does docker build re-run npm install every time?

A COPY of the whole source before the install changes the cache key on every edit. Copy package.json and the lockfile first, install, then copy the rest.

What does .dockerignore do?

It lists files and folders that are left out of the build context. That makes the context smaller, so less data is sent to the builder, and it keeps files such as .env out of images.

Do BuildKit cache mounts make the image bigger?

No. The mounted cache stays in the builder and is not part of the image layers.
