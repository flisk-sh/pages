Monorepo CI Is Slow: How to Find the Bottleneck

Measure before you optimise: find your slowest workflows, separate queue time from run time, and fix the biggest cost first, with a script and a public dashboard.

To speed up monorepo CI, rank workflows by median and p90 run time, find the single slowest job in the longest workflow, and attack that. Queue time, setup time and repeated installs are common hidden costs, and they are invisible if you only look at the total.

Collect real numbers

Pull recent runs with the GitHub CLI and compute durations.

gh run list -L 100 --json name,createdAt,updatedAt,conclusion \
  -q '.[] | [.name, .createdAt, .updatedAt, .conclusion] | @tsv'

Run time is roughly updatedAt - createdAt. For per-job and per-step timings, use gh run view <id> --json jobs, which lists each step with start and finish times. Take medians and p90 values, not averages, because a few outliers distort the mean.

A public view

Cilytics shows slow workflows with their median and p90, plus pass rate and flaky workflows, for an organisation or a public repo using ?repo=owner/name. It reads default-branch runs only, from the last 100, as an hourly snapshot, so it will not show a slowdown from an hour ago and it skips repos inactive for 90 days. For private repos or fine detail, use the CLI above. See also CI metrics that matter.

Break down one slow run

Open the longest recent run and write down the time of each phase:

  • Queue: time between the trigger and the first job starting. If this is high, you are short of runners or hitting concurrency limits.
  • Setup: checkout, tool install, cache restore.
  • Install: dependency installation.
  • Build and test: the real work.
  • Upload: artifacts and caches.

Teams often find that setup and install add up to more than the tests.

Typical fixes in order of payoff

  1. Run only what changed, see run only what changed.
  2. Cancel superseded runs with concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }.
  3. Cache dependencies and build outputs, see monorepo caching.
  4. Split the longest job into parallel jobs, or shard the test suite.
  5. Move slow integration tests to run after fast ones, or nightly.
  6. Use a larger runner only when the job is CPU bound and measured to benefit.

Verify the win

Record the median and p90 before the change, make one change, then compare after twenty or so runs. A single run proves nothing, since runner speed varies. Keep a short log of changes and results in the repository. Broader techniques are in faster GitHub Actions. Do not trade away safety for speed: if a faster pipeline starts missing regressions, you have only moved the cost to production.

Set a budget. Pick a target such as 'p90 under ten minutes for pull request runs' and put it somewhere visible. When a change pushes the p90 over the budget, treat it like a failing test. Without a number, pipelines creep up a minute at a time until everybody complains and nobody remembers why.

Questions people ask

Median or average run time?

Use the median for the typical run and the p90 for the slow tail. Averages are pulled up by rare outliers and hide what developers usually wait for.

Is a larger runner worth it?

Only for CPU-bound work, and only after measuring a speedup on your own jobs. Network-bound or install-bound steps rarely get faster with more cores.
