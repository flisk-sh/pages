Docker ARG vs ENV: which one to use at build time and run time

Both set a variable, but one disappears after the build and the other ships with the image. Picking wrong leaks data or breaks the app.

Use ARG for values that only matter while the image is being built, such as a base image version, and use ENV for values the running application reads. An ARG is gone from the container's environment once the build ends. An ENV is baked into the image and appears in every container started from it. Neither is a safe place for a secret.

How they differ

ARGENV
Available during buildYes, from its declaration onYes, from its declaration on
Available in the running containerNoYes
Set at build time--build-arg NAME=valueOnly through an ARG you copy into it
Override at run timeNo effect-e NAME=value or Compose environment
Visible in docker historyYesYes

The last row is the one people miss. Build arguments are recorded in the image's metadata, so anyone who can pull the image can read them.

The FROM trap

An ARG declared before the first FROM can be used in the FROM line, but it is not visible after that line unless you declare it again:

ARG NODE_VERSION=22
FROM node:${NODE_VERSION}-alpine
ARG NODE_VERSION
RUN echo "building on Node ${NODE_VERSION}"

Without the second ARG NODE_VERSION, the RUN line prints an empty value. The same applies to each stage of a multi-stage file: declare what a stage needs inside that stage.

Turning an ARG into a runtime value

If the application needs a build-time value at run time, copy it with ENV:

ARG APP_VERSION=dev
ENV APP_VERSION=$APP_VERSION

That is a good use: a version string or a git commit that identifies the build. Frontend bundlers need this too. Vite replaces import.meta.env.VITE_* values while it builds, so an API URL must be present at build time, not only when the container starts. Changing the container's environment later does not change an already built bundle.

Secrets belong to neither

Do not pass a token with --build-arg and do not write it in ENV. For build-time secrets such as a private registry token, BuildKit has secret mounts that exist only for one RUN step and are not stored in a layer:

RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .

For run-time secrets, pass them when the container starts, not when it is built.

Which one for which job

  • Tool or base image version: ARG. Nothing at run time needs to know it.
  • Build identity (version, commit hash): ARG copied into ENV, so the app can report it.
  • A fixed default such as NODE_ENV=production: ENV, because the app reads it and a sensible default belongs in the image.
  • Anything that differs per machine or per environment (database URL, log level): neither. Leave it out of the image and inject it when the container starts, so the same image runs everywhere.
  • Anything secret: a BuildKit secret mount at build time, and a run-time variable or mounted file at run time.

A useful test: if two developers would need different values, it should not be in the Dockerfile at all.

Where Flisk fits

With a bring-your-own resource, Flisk reads build arguments from a buildArgs object in service.json and passes them to the build. Values may use Compose variables with a default, so the file stays free of machine-specific data:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile",
  "buildArgs": { "NODE_VERSION": "${NODE_VERSION:-22}" },
  "env": { "LOG_LEVEL": "debug" },
  "secrets": { "required": ["DATABASE_PASSWORD"] }
}

buildArgs is for the build (ARG). env is plain run-time configuration, and secrets names variables that Flisk reads from the git-ignored project .env file at run time, so no secret value is committed. buildArgs applies only to a resource built from a Dockerfile, and flisk config verify refuses it next to an image, because nothing is built then. Flisk has no field for BuildKit secret mounts, so build-time secrets stay a plain docker build concern. For the naming convention see env var names, not values, in config.

Pitfalls

  • Changing an ARG invalidates the cache from the point it is first used. Declare it as late as you can. See layer caching.
  • An unset ARG without a default is empty, not an error. Give every ARG a default or check it in a script.
  • ENV values are literal. Docker does not expand $HOME inside a JSON-form CMD, only in shell form or in a shell you start.
  • A variable that is not loading at run time is usually a build versus run confusion. How to debug it walks through the checks.

Next step

Questions people ask

Is ARG available when the container runs?

No. An ARG exists only during the build. To keep a value, copy it into an ENV in the Dockerfile, or pass the value again as an environment variable when the container starts.

Why is my ARG empty after FROM?

An ARG declared before FROM is only in scope for the FROM line. Declare the ARG again after FROM, and again in each stage that needs it.

How do I pass build arguments from Flisk?

Add a buildArgs object to the service.json of a bring-your-own resource that has a dockerfile. Values may use Compose style variables with defaults, such as ${NODE_VERSION:-22}.
