Run microservices on your laptop

How to set up a one-command dev environment for your team

The goal is simple: clone, run one command, open a URL. Everything between those steps should be written down in files, not in someone's head.

A one-command dev environment means a new developer clones the repository, runs a single command, and gets every service running with working URLs. To get there, put the service list, start commands, ports, order and development secrets in files that live in the repository, and add a check that tells the developer what is missing on their machine.

What the command has to do

"Run everything" hides a list of small jobs. If any of them is manual, the setup is not one command:

  1. Check that the right runtimes are installed (Node, Python, Go, Docker if you use it).
  2. Start every service with the right command and port.
  3. Start them in dependency order and wait for readiness.
  4. Provide development secrets and environment variables.
  5. Print the URLs to open.
  6. Offer a way to stop everything again.

A Makefile target or a shell script can do this. The hard part is keeping it correct as services change. A script that starts everything blindly gets stale, and nobody notices until a new hire hits it.

The Flisk way

With Flisk the list lives in one service.json per service, and the command is flisk up. Install it once:

npm install -g @flisk-sh/flisk
git clone <your-repo>
cd <your-repo>
flisk doctor
flisk up

flisk doctor runs first. For a project made of local processes it checks that every service's program is installed, that dependencies and ports are valid, and that no two services share a port. It does not check Docker, because that project does not need it. Pin the runtime a service needs with toolchain:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "toolchain": "node@24",
  "port": 4000
}

If the installed Node is not 24.x, Flisk refuses to start and names the service and both versions. Flisk installs nothing itself, so the message is the whole fix: the developer installs the right version.

You can also point flisk up at a repository: flisk up <git-url> clones it shallowly into a folder named after the repo, then starts it. To see the idea first on any machine, run npx @flisk-sh/flisk demo. It starts a small demo, and falls back to local processes when Docker is not running.

Secrets without a shared password file

Do not commit a .env with real values, and do not put a fixed fallback secret in a manifest. For keys a service needs only in development, ask Flisk to generate them:

{
  "secrets": { "generate": { "AUTH_SECRET": "hex:32", "APP_ENCRYPTION_KEY": "base64:32" } },
  "env": { "SESSION_SECRET": "${AUTH_SECRET}" }
}

On flisk up, each name missing from the project .env is appended once with random bytes. Existing lines are never changed, a new .env is created with mode 0600, and Flisk prints the names, not the values. Back the file up if the key protects data you cannot lose. A deleted .env gets a new key. Other variables use ${VAR} or ${VAR:-default}, resolved from your shell first, then the project .env, then the service's own .env, then the default.

What to commit

  • Every service.json, and .flisk/project.json, which flisk up creates on the first run.
  • A short README section with the install command, flisk doctor and flisk up.
  • Do not commit .env. Flisk adds it to .gitignore.

For scripts and CI, flisk up --wait starts the stack in the background and returns when every service is healthy, with exit code 0, or fails. flisk down stops it.

Pitfalls

  • The one command still needs dependencies installed. If a service needs npm install first, say so in the README or in the service's command.
  • One runtime path per project. A project cannot mix local commands with Dockerfile builds. Pick the path that matches what you need.
  • Different machines. Windows runs the local-process path natively. The container path needs WSL2.

Keep the command honest by running it on a clean checkout now and then, in a fresh clone or in CI with flisk up --wait. A setup that only works on the machine of the person who wrote it is the usual way this goes wrong. When it fails on a clean clone, the missing step is the thing to write down, in the manifest if possible and in the README if not. Treat each manual step you find as a bug in the setup, not as a fact of life, and fix it once for everyone.

Questions people ask

What should a one-command environment contain?

A list of services with start commands and ports, a start order, readiness checks, development-only secrets that are generated rather than shared, and a command that stops everything.

Should I commit the .env file?

No. Commit an example file or generate the values. Flisk can generate missing development secrets into a git-ignored .env on the first run.

How do I check the machine before the first run?

Run flisk doctor. It checks the tools the services need and the service definitions, and reports what to fix.
