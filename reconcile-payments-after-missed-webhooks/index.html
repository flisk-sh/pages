Payments and webhooks locally

How to reconcile payments after missed webhooks

Webhooks are a fast path, not a guarantee. A job that asks the provider what really happened is the safety net, and it is easy to test by turning the receiver off.

To recover from missed webhooks, run a reconciliation job that asks the provider for everything that changed since the last successful run, compares each item with your database, and applies the difference. The webhook is the fast path. The job is the safety net for the hours when your server was down, a deploy dropped events, or a bug returned 200 without saving anything.

Why webhooks are not enough

A provider retries failed deliveries for a while, but not forever. Stripe retries live-mode events for up to three days, and after that the event is not sent again by itself. Several ordinary failures fall outside any retry window or never look like failures to the provider:

  • Your service was down for longer than the retry window.
  • A handler returned 200 before saving, then crashed.
  • A signing secret was rotated and every event was rejected for a day.
  • An endpoint was removed or disabled in the provider's dashboard and nobody noticed.

The result is the same each time: a customer paid, your database says unpaid. A reconciliation job finds those rows without anyone filing a ticket.

The shape of a job

  1. Read a cursor, the time of the last successful run. Subtract a safety margin, such as an hour, so the windows overlap.
  2. List the provider's payments created or updated since the cursor, page by page.
  3. For each one, apply it through the same guarded update your webhook handler uses, so the job and the handler cannot disagree.
  4. Store the new cursor only after the whole run succeeds.
  5. Report the number of corrections. A run that fixes many rows means something upstream is broken.

Reusing the handler's update is the important design choice. If the job has its own rules, you end up with two sources of truth. The rank-based update from handling out-of-order events makes the job safe to run at any time, because it never moves a payment backwards.

A Stripe example

import Stripe from "stripe";
import { applyPaymentState } from "./payments.js";   // the same function the webhook uses

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

export async function reconcile(sinceUnix) {
  let fixed = 0;
  for await (const pi of stripe.paymentIntents.list({
    created: { gte: sinceUnix },
    limit: 100
  })) {
    const changed = await applyPaymentState(pi.id, pi.status);
    if (changed) fixed += 1;
  }
  return fixed;
}

The SDK's list calls paginate automatically when you iterate them, so you do not handle starting_after yourself. Listing payments by creation time finds payments you never heard of. To catch updates to older payments, such as a refund added later, list events instead with stripe.events.list, which Stripe keeps for 30 days, and apply those. Many teams do both: events for recent changes and a slower full comparison once a day.

Testing it locally with Flisk

The test that matters is the outage itself. Run your API as a local process, create test-mode payments while the receiver is stopped, and check that the job repairs the gap. With Flisk installed (npm install -g @flisk-sh/flisk), the steps are:

flisk up                                   # API and database running
flisk down                                 # stop everything, as in an outage
stripe trigger payment_intent.succeeded    # event nobody receives
flisk up
flisk run api -- node scripts/reconcile.js --since 1h

flisk run runs the script with the environment the api service has, so it reads the same test key and database settings, and its exit code is the script's. Then read the log with flisk logs --service api --since 10m and check that the payment row now exists. Use real test-mode payments for this, because a triggered event carries made-up object IDs that do not match anything in your database.

To run it on a schedule while you develop, keep the schedule in a tiny worker with a timer, as described in running cron jobs in local development. Flisk has no built-in scheduler.

Pitfalls

  • Cursor moved too early. Saving the new cursor before the run finishes hides a failure. Save it last, and keep the overlap.
  • Rate limits. A first run over a large history can hit the provider's limits. Page in small windows and back off on a 429.
  • Different rules in the job. If the job can set a status the handler would refuse, the two will fight.
  • Fixing silently. A correction is a symptom. Log each one with the payment ID, and alert when the count is above zero for several days.
  • Test mode and live mode keys mixed. A job that reads live data with a test database writes nonsense. Check the key prefix at start.

When the gap came from a retried request on your side rather than a lost event, the fix is in idempotency keys for payment requests.

Questions people ask

How long does Stripe retry a failed webhook?

In live mode Stripe retries for up to three days with exponential backoff. After that you must fetch the data yourself, which is what a reconciliation job does.

How far back can I list Stripe events?

Stripe's events API returns events from the past 30 days. For older data, list the objects themselves, such as payment intents, by creation time.

Should a reconciliation job use the same code as the webhook handler?

Yes. Share the function that updates a payment so both paths follow the same rules and cannot move a payment backwards.
