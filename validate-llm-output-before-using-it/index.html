How to validate LLM output before your app acts on it

Treat model output like user input: parse it, check it against a schema, then check it against your rules. Never pass it straight to a shell, a query or a browser.

Treat everything a model returns as untrusted input. Parse it into a typed structure, validate the fields against a schema and your business rules, and only then act. Never pass raw model text to a shell, a database query, a file path or an HTML page.

Why model output is untrusted

The model can be manipulated by injected text, can hallucinate fields and can produce text that is valid for the wrong reason. If your code takes a string from the model and builds a command or a query with it, you have recreated classic injection bugs with a new source of strings. Ask the same questions you would ask about a form field from a stranger.

Parse into a schema

Ask for JSON, then validate it. Reject anything that does not match, rather than guessing.

from pydantic import BaseModel, Field, ValidationError

class Refund(BaseModel):
    order_id: str = Field(pattern=r"^ord_[a-z0-9]{8}$")
    amount_cents: int = Field(gt=0, le=50_000)
    reason: str = Field(max_length=200)

try:
    refund = Refund.model_validate_json(model_text)
except ValidationError as e:
    refund = None  # retry once with the error, then fail safe

The limits in the schema, such as the maximum amount, are a cheap safety net. For getting reliable structure in the first place, see prompts and structured outputs.

Check business rules separately

A valid shape is not a valid action. After parsing, check it against your data and your policy: does the order exist, does it belong to this user, is it within the refund window, is the amount at most what was paid? These checks run in your code and use your database, not the model's opinion.

Where possible, let the model choose from a closed set instead of writing free text. An enum of allowed actions, a list of valid ids from your database, or a yes or no decision are all far easier to validate than a paragraph. When the model must pick an id, check that the id was one you offered it.

Escape for the destination

  • SQL: use parameterized queries, never string formatting with model text.
  • Shell: avoid it. If you must, pass arguments as a list and never use shell=True with model text.
  • HTML: escape or sanitize before rendering, since model text can contain script tags.
  • Markdown: remove or restrict images and links that point to unknown hosts, as they can carry data out in the URL.
  • Paths: resolve and check against an allowed folder, as in the permissions guide.

Fail safe

When validation fails, do not fall back to "best effort". Retry once with the validation error in the prompt, and if it still fails, stop and report. A refused action is a smaller problem than a wrong one. Log failed validations: a spike often means a prompt change or an attack attempt, which you can follow up in the audit log.

Questions people ask

If I use structured outputs, do I still need validation?

Yes. A schema guarantees shape, not truth or safety. You still need business rules, ownership checks and escaping for the destination.

Can I ask another model to validate the first one's output?

It can add a signal, but it can be fooled the same way. Use code checks first and a second model only for what code cannot check.
