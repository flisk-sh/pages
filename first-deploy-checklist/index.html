First deploy checklist: what to check before going live

Most first-deploy failures are the same ten small things. Check them on your laptop first, when fixing them is cheap.

Before the first deploy, check that the app reads all its settings from environment variables, listens on the port the host gives it, runs its database migrations as a separate step, keeps no data on local disk, answers a health check, and can be rolled back. Each item takes a few minutes on your laptop and can cost an evening on a live host.

Why a checklist helps

Your laptop is a forgiving place. Ports are free, the database is always up, files stay where you put them, and there is one user. A host is the opposite: containers restart, disks are wiped on every release, the database address is different, and strangers send requests. The checklist below is ordered by how often each item breaks a first deploy. It is deliberately tool-neutral, so it works with Compose, a platform such as Render or Fly.io, or a plain server.

The checklist

  1. Every setting comes from the environment. No hardcoded localhost URLs, no secrets in code. Search the repo for localhost and 127.0.0.1. See why localhost URLs break in production.
  2. The app listens on 0.0.0.0 and reads PORT. A server bound to 127.0.0.1 inside a container is unreachable from outside. See app not reachable after deploy.
  3. Migrations run once, before the new code serves traffic. Not from every instance on start. See run migrations on deploy safely.
  4. Nothing important is written to local disk. Uploads and generated files go to object storage or the database. See files disappear after deploy.
  5. There is a health endpoint that returns 200 only when the app can really serve a request.
  6. Production secrets are new. Do not reuse the values from your laptop. Generate fresh ones in the host's secret store.
  7. A backup exists and a restore has been tried. See back up Postgres before launch.
  8. Logs go to stdout and stderr, where the host collects them, not to a file inside the container.
  9. Images and dependencies are pinned. Use a version tag such as postgres:17 rather than latest, and commit your lockfile.
  10. You know the way back. Keep the previous image tag and read how to roll back a bad deploy before you need it.

Check the config before you deploy it

If your services are described by service.json files, three Flisk commands cover part of the list. They check your project, not your host.

flisk config verify          # generated files still match service.json
flisk doctor                 # machine checks, and pings /health of running services
flisk export render --dry-run   # print the render.yaml it would write, write nothing

flisk config verify catches a generated file that was edited by hand. flisk doctor pings the /health endpoints of services that are running, unless you pass --no-ping. The export command prints the Render Blueprint it would produce so you can read it as a review step. It needs Node.js 22.12 or later, because it runs through npx, and it never deploys anything or calls a cloud API. A project that declares a healthCheckPath per service gives the host the same path to probe that you tested locally.

The exporter writes services, not databases or secret values. You add the database and the secrets yourself, which is what items 3 and 6 of the checklist are about. The full walk through is in from a local stack to a Render Blueprint.

Do a dry run of the deploy itself

Build the production image on your laptop and run it the way the host will. Use the host's environment style: pass settings with -e flags or an env file, publish only the app port, and do not mount your source code.

docker build -t myapp:test .
docker run --rm -p 8080:8080 -e PORT=8080 --env-file .env.production.local myapp:test
curl --fail http://localhost:8080/health

If this works, most of the platform-specific surprises are already gone. If it fails, you found the problem for free.

When a checklist is not enough

  • Anything with payments, personal data or compliance needs more than ten items. Treat this list as the floor.
  • If the app has a single user and no state, skip the backup and staging items. Do not skip the health check or the rollback plan.
  • A checklist does not replace a staging environment. See a staging environment on a small budget for a cheap way to rehearse.

Next, pick the item that scares you most and fix it first. For most apps that is the database, so start with the backup and restore guide, then add a smoke test so every later deploy is checked the same way.

Questions people ask

How long should a first deploy take?

The deploy itself is minutes. The preparation is the real work. Plan a few hours to go through the checklist, build the production image locally and try a restore of a database backup.

Do I need staging before the first deploy?

Not for a hobby project, but you do need some rehearsal. Running the production image locally with production-style environment variables catches most problems.

What breaks most often on a first deploy?

Hardcoded localhost URLs, a server bound to 127.0.0.1, a missing environment variable, and migrations that nobody ran. All four can be checked before you deploy.
