WSL2 using too much memory: limit it with .wslconfig

WSL2 takes up to half your RAM by default and gives little back. A five-line file puts a ceiling on it.

The vmmem or vmmemWSL process in Task Manager is the WSL 2 virtual machine, and Docker Desktop runs inside it too. To cap it, create %UserProfile%\.wslconfig with a [wsl2] section that sets memory, processors and swap, then run wsl --shutdown so the new limits apply on the next start.

Why the VM grows

WSL 2 runs all your distributions in one lightweight VM. By default it may use up to 50 percent of the Windows machine's RAM and all logical processors. Linux uses free memory for the file cache, so after a big build or a few containers the VM looks full and Windows sees it as used. Memory that Linux has cached is not always handed back quickly. On a 16 GB laptop that leaves Windows, your browser and your editor competing for what remains.

Docker Desktop with the WSL 2 backend uses the same VM, so one cap covers both your Ubuntu shell and your containers.

Write the limits

Create the file at C:\Users\<you>\.wslconfig. A reasonable starting point on a 16 GB machine:

[wsl2]
memory=8GB
processors=4
swap=4GB

Pick numbers that leave room for Windows: roughly half the RAM is a common start, and the right value depends on how many containers you run. Then restart the VM from PowerShell:

wsl --shutdown

Wait a few seconds, reopen Ubuntu, and check from inside:

free -h
nproc

The total in free -h should be near your limit. If Docker Desktop was running, restart it too. Note that .wslconfig is read per Windows user and applies to every distribution. Per-distro settings go in /etc/wsl.conf inside the distro instead.

Let the VM give memory back

Recent WSL releases have an experimental option that returns unused cache gradually:

[experimental]
autoMemoryReclaim=gradual

It needs a current WSL (wsl --update) and it is marked experimental, so keep it optional and check the WSL release notes if it is ignored. The fixed memory cap is the dependable part.

Find what is using the memory inside Linux

A cap only helps if your workload fits. Look at what is running:

docker stats --no-stream
ps aux --sort=-%mem | head

Databases, search engines and JVM services are usual suspects. A container killed with exit code 137 is often the out-of-memory killer acting inside the capped VM; see why a container keeps restarting.

Where Flisk helps: start less

The cheapest saving is not starting what you are not working on. Flisk starts a named stack with flisk up <stack> and can start only some services with flisk up --only <services...>. Before a run, flisk up --dry-run lists what would start without starting it, so you can see how big the run is on a small machine:

flisk up --only orders-api --dry-run

Pair that with the memory cap, and a laptop that struggled with the whole system can hold the three services you are editing. The same idea, without WSL specifics, is in many services on one laptop and start only the services you need. Flisk does not change WSL's limits for you; the .wslconfig file is yours to edit.

Pitfalls

  • Setting the cap too low. Builds fail with out-of-memory errors or containers restart. Raise it in steps of 1 or 2 GB.
  • Forgetting to shut down. The file is read at VM start. Editing it without wsl --shutdown does nothing.
  • Zero swap. swap=0 avoids disk use, but a memory spike then kills a process instead of slowing down.
  • Wrong location. The file must be in your Windows user profile folder, named exactly .wslconfig, not in the Linux home.

Next step: if the disk, not the RAM, is what hurts, read how to shrink the WSL2 virtual disk.

Questions people ask

Why is vmmem using so much memory?

It is the WSL 2 virtual machine. Linux caches files in free RAM and may not release it quickly, and Docker Desktop's engine runs in the same VM.

Where does the .wslconfig file go?

In your Windows user profile folder, as %UserProfile%\.wslconfig. Run wsl --shutdown after editing it.

Does Flisk set WSL limits?

No. You edit .wslconfig yourself. Flisk can start fewer services with flisk up --only or a named stack, which lowers use.
