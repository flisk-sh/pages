Databases in local development

How to run Redis for local development

Redis is a single small container. The part worth getting right is the address your code uses, which differs inside and outside Docker.

Run Redis as a container, pin the image version, and give your code a REDIS_URL instead of hard-coding localhost. For one service on your machine, docker run -p 127.0.0.1:6379:6379 redis:7.4-alpine is enough. For several services, run Redis next to them on the same Docker network and use its service name as the host.

The general approach

The simplest start:

docker run -d --name dev-redis \
  -p 127.0.0.1:6379:6379 \
  -v dev_redis_data:/data \
  redis:7.4-alpine

Check it with docker exec dev-redis redis-cli ping, which should print PONG. Your URL is redis://127.0.0.1:6379.

The volume only matters if you want data to outlive the container. Redis writes snapshots to /data, so a mounted volume keeps them. If you use Redis purely as a cache, you can skip the volume and treat an empty Redis as normal. If you use it for a job queue, losing it means losing queued jobs, so keep the volume.

Binding to 127.0.0.1 keeps the port off your network. A default Redis container has no password, so an open port would let anyone who can reach it read and write your keys.

Inside Docker, the host is not localhost

This is the usual source of "connection refused". When your API runs in a container, localhost means that container, not Redis and not your laptop. Containers on the same Compose network reach each other by service name, so the URL becomes redis://cache:6379 when the Redis service is called cache. Read the address from an environment variable and set it differently for each place the code runs.

The Flisk way

Create Redis as a resource in a stack:

flisk resource cache --type database --framework redis --stack shop --yes

The generated service.json describes a bring-your-own container:

{
  "appName": "cache",
  "appType": "bring-your-own",
  "framework": "redis",
  "port": 6379,
  "image": "redis:7.4-alpine",
  "exposeViaProxy": false,
  "healthCheck": { "command": ["redis-cli", "ping"] },
  "provides": { "REDIS_URL": "redis://cache:6379" }
}

It also mounts a cache-data volume at /data. The important line is provides. Any service that lists cache in its dependsOn receives REDIS_URL in its environment, and Flisk starts Redis first and waits for the redis-cli ping health check:

"appName": "orders-api",
"dependsOn": ["cache"]

Your code then reads process.env.REDIS_URL and nothing else. To use a different version, pass --image redis:8-alpine when you create the resource. Run flisk up shop to start the stack.

Redis is not published to your host and has no password. Flisk does not route it through Traefik, and the docs only publish the web interfaces of other database frameworks on 127.0.0.1. So redis-cli on your laptop cannot reach it by default. Use docker exec into the container instead, and never put a secret in provides, because that value lands in plain text in the generated files.

To look inside, run Redis commands in the container. Its name is generated from the project, so list it first with docker ps --filter name=cache, then run docker exec -it NAME redis-cli.

Using Redis from code

Any client library takes the URL as one string, so the connection code is the same locally and elsewhere. With the Node redis package it is createClient({ url: process.env.REDIS_URL }), and with Python it is redis.Redis.from_url(os.environ["REDIS_URL"]). Fail at startup if the variable is missing, and set a short connect timeout so a stopped Redis gives you an error in seconds and not a hung request.

Pitfalls

  • A stale cache after a code change. Old keys outlive your deploy. Flush with redis-cli FLUSHALL when you suspect it, on a local instance only.
  • Running one Redis for two projects. Keys from both mix. Use one instance per project, or separate numbered databases with redis://host:6379/1, and remember that numbered databases are not available in cluster mode.
  • Queues and workers. If a worker and an API share Redis, both need the same REDIS_URL. See worker and API sharing a database for the same idea applied to Postgres.
  • Persistence surprises. flisk down keeps volumes and flisk down --purge removes them, so a purge empties your queue as well. The volume rules are in keep volumes between runs.

When not to use it

If you only need a key-value store for one process, an in-memory map in your code is simpler. If your production Redis is a managed service with TLS and a password, test that path separately, because a plain local Redis will not show those failures.

Questions people ask

What URL does my service use for Redis in Flisk?

Services that list the cache resource in dependsOn receive REDIS_URL, which is redis://cache:6379 by default. Read it from the environment.

Can I reach Flisk's Redis from redis-cli on my laptop?

Not by default. The documented behaviour is that Redis is not published to the host. Run redis-cli inside the container with docker exec.

Does Redis keep data after flisk down?

Yes, the cache-data volume survives flisk down. Only flisk down --purge deletes it.
