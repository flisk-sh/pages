CI for multi-service apps

How to run CI only for the services that changed in a monorepo

Map changed files to services, run only those jobs, and keep a single gate job so branch protection never hangs.

To run CI only for the services that changed, compute the list of changed directories, map them to services, and run only those jobs, while a single gate job keeps your required status check stable. Then start only what the tests need with flisk up --only. Remember that a change to a shared library or a dependency must still trigger the services that use it.

Step 1: find what changed

The simplest tool is a path filter action. dorny/paths-filter outputs one boolean per group of paths:

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      orders: ${{ steps.f.outputs.orders }}
      billing: ${{ steps.f.outputs.billing }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: f
        with:
          filters: |
            orders:
              - 'services/shop/orders-api/**'
              - 'packages/shared/**'
            billing:
              - 'services/shop/billing-api/**'
              - 'packages/shared/**'

Note that packages/shared/** appears in both groups. That is the part people forget: a shared package changes every service that imports it.

Without a helper action, use git. Check out with fetch-depth: 0 and run git diff --name-only origin/main...HEAD. The default shallow checkout has no history to compare, so the diff fails or lists everything.

Step 2: run only the matching jobs

  test-orders:
    needs: changes
    if: needs.changes.outputs.orders == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @flisk-sh/flisk
      - run: flisk project --yes
      - run: flisk up --wait --only orders-api
      - run: npm --prefix services/shop/orders-api test

--only starts the named services plus their dependsOn chain and shared infrastructure, so you do not start the billing service to test orders. It pulls in what a service needs. It does not pull in services that depend on it, so a change to a low-level service does not automatically test its callers. Add those callers to the filter yourself.

Step 3: generate the filter from the service list

Hand-written path lists drift when you add a service. Flisk can list your services with their locations:

flisk resources --json | jq -r --arg root "$PWD" \
  '.data.resources[] | [.name, (.path | sub($root + "/"; "") | sub("/service.json$"; ""))] | @tsv'

Each entry has a name, stack, type, port and an absolute path to its service.json, and the command above turns that into the repository-relative directory, for example orders-api and services/shop/orders-api. Compare those directories with the output of git diff --name-only, and you have the list of changed services without maintaining a second file. You still add shared paths by hand, because a service listing cannot know who imports packages/shared.

Run this listing step in a job that has checked out the repository and installed Flisk, since it reads the service.json files from the checkout. The result can feed a job matrix, so each changed service becomes one parallel job with its own flisk up --wait --only call and its own test command.

Step 4: keep one stable required check

If you set on.pull_request.paths on the workflow, a pull request that changes no matching path never starts it. A required status check that never reports blocks the merge forever. Two ways around it: do not filter at the workflow level and skip jobs with if: instead, then add a final job with needs: [test-orders, test-billing] and if: always() that fails when any needed job failed or was cancelled. Mark only that job as required. A skipped job counts as success for needs, so the gate passes when nothing relevant changed.

Pitfalls

  • Shared code and config. A change to a lockfile, a root package.json, the CI workflow itself or a base Dockerfile should run everything. Put those paths in every group, or add an "all" group.
  • Merge base. A diff against main instead of the merge base reports changes you did not make when main moved on. Use the three-dot form.
  • Squash and push builds. On pushes to main, compare against the previous commit, or just run everything there.
  • Integration gaps. Two services can each pass alone and fail together. Keep a full-stack run on main or nightly.

When not to do this

With a small stack, a full run that takes five minutes is cheaper than the filter logic you have to maintain and the escapes you will miss. Add selective runs when the full run is slow enough that people stop waiting for it. If your slow part is a few long tests rather than many services, splitting them across jobs is the better fix.

For the basic workflow that these jobs build on, see how to run the stack in GitHub Actions.

Questions people ask

Does flisk up --only also start services that depend on the one I name?

No. It starts the named services plus their dependsOn chain and shared infrastructure. Callers of a changed service are not added, so include them in your change filter.

Why does my required check stay pending?

A workflow limited by on.pull_request.paths never starts when no path matches, so the required check never reports. Use if: on jobs and one always-running gate job instead.

Why does git diff list nothing or everything?

The default checkout is shallow. Use fetch-depth: 0 and compare with the three-dot form origin/main...HEAD.
