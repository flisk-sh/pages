Which CI Metrics Should You Track? Five That Matter

Pass rate, median and p90 run time, flip count, mean time to green and red default branch: the short list of CI metrics worth watching, and what each one tells you.

Track five things: pass rate on the default branch, median run time, p90 run time, how often results flip, and how long a red build stays red. Together they say whether CI is trustworthy, fast and well looked after. Everything else is optional.

The five metrics

MetricQuestion it answers
Default-branch pass rateCan we trust a green or red result?
Median run timeHow long does a typical run take?
p90 run timeHow bad is a slow day?
Flip countHow often does the result change without a code change?
Mean time to greenHow fast do we repair a broken build?

Why these and not others

Each one maps to a decision. A falling pass rate means look at quality or flaky tests. A growing p90 means look at queueing or heavy jobs. A long time to green means nobody owns a broken main. If a number does not lead to an action, drop it. See metrics to ignore.

Scope matters

Measure the default branch separately from pull requests. Pull request runs fail for good reasons, since that is what CI is for, so their pass rate mixes real catches with noise. The default branch should be almost always green, and a failure there is a signal. Also measure per workflow, because a single average across all of them hides the one that is broken.

Window and sample size

Use a rolling window, such as the last 100 runs or the last 30 days. Small samples lie: three failures in ten runs is 30 percent, but also just a bad week. Show the count next to the percentage, for example "92 percent of 100 runs", so nobody over-reads a thin sample.

Where to get the data

All five come from workflow run history, which the GitHub API exposes. Learn how to pull it with the gh CLI, or look at a ready-made view like Cilytics, which shows pass rate trend, median and p90 run time and flaky workflows for an org or a public repo. Its limits: default-branch runs only, last 100 runs, hourly snapshot. For a per-test view you still need your own reports.

Set targets last

Measure for a few weeks first. Then pick targets from your own baseline, like "p90 under 15 minutes" or "main red for less than an hour". Targets copied from another company often do not fit your stack. Review them quarterly and change them when they stop driving behavior.

Write the five numbers on one page with the window and the sample size, and review them in the same meeting every week. Ten minutes is enough. The point is the habit: when someone sees pass rate slip from 98 to 91, they ask why while the cause is still fresh in the log. Metrics that nobody reviews turn into wallpaper.

Questions people ask

How many CI metrics are too many?

More than a handful on one page. If nobody can name an action a metric would trigger, remove it.

Should I track pull request metrics too?

Yes, but separately, mainly run time and time to first feedback. Do not mix them into the default-branch pass rate.
