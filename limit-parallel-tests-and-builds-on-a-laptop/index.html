Keep your laptop fast while developing

Limit parallel tests and builds so your laptop stays usable

Test runners and compilers default to one worker per core. That is fast, and it leaves nothing for your editor, browser and database.

Most test runners and build tools start one worker per CPU core, which makes the machine unusable while they run. Cap the worker count to half your cores (Jest --maxWorkers=50%, pytest-xdist -n 2, cargo -j 4), and start the job with nice so the desktop stays responsive.

Why defaults hurt on a laptop

A build server is dedicated, so using every core is correct there. On a laptop the same job competes with your editor, a browser, a database and the other services of your stack. Memory is the bigger risk: each worker is a full process, so 12 Jest workers can hold several gigabytes, and the machine starts swapping. Fewer workers often finish nearly as fast, because tests spend time waiting for the database or disk, and fast cores have fewer slow neighbours.

First find how many cores you have:

# macOS
sysctl -n hw.ncpu
# Linux
nproc

Per tool settings

ToolHow to limit
Jestjest --maxWorkers=50% or -w 2. --runInBand (-i) runs tests in one process, useful when debugging.
pytestWith the pytest-xdist plugin, pytest -n 2 sets two workers. Without the plugin there is no parallelism.
Cargocargo build -j 4, or set CARGO_BUILD_JOBS=4, or build.jobs in .cargo/config.toml.
Gogo build -p 4 and go test -p 4 limit parallel packages. GOMAXPROCS=4 limits threads running Go code.
makemake -j4. Plain make -j with no number starts as many jobs as it can, which is the classic way to freeze a machine.
Vitest, webpack, esbuild and othersEach has a worker or thread option. Check its docs for your version; names changed between major versions.

Put the setting in the project config rather than the command line when the team shares it. Jest has maxWorkers in its config, Cargo has .cargo/config.toml, and pytest has addopts in pytest.ini or pyproject.toml.

Lower the priority instead

If you do not want to change the tool, change how the operating system treats the process. nice makes a job yield to others:

nice -n 10 npm test

A higher number means lower priority. This does not reduce memory use, only CPU competition, so combine it with a worker cap when memory is the issue. On macOS a background quality of service can be requested with taskpolicy -b in front of the command, which also lowers disk priority.

Test runs against a stack

Integration tests that call a running stack add load of their own: the services, the database and the test workers all share your cores. Run the tests with a low worker count, and start only the services the tests need. With Flisk, a one-off command can use the environment a service has in the stack:

flisk run api -- npx jest --maxWorkers=2

flisk run <service> <command...> runs the command with that service's environment (inside its container, or on the host for a local process), and the exit code is the command's, which suits scripts and CI. Put -- before a command that has flags of its own, as above. The full setup is in integration tests against the real stack.

Pitfalls

  • Fewer workers can expose shared state between tests, or hide it. If results change with the worker count, tests share a database row, a port or a file. Fix the tests; do not rely on the number.
  • Do not set workers to 1 permanently to fix flaky tests. It hides the cause and makes the suite slower for everyone.
  • Watch mode runs on every save. Limit workers there first, since it runs the most often.
  • Docker builds have their own parallelism inside the VM. Cap the VM, not just the command.

To see what is left after limiting, check what is using your RAM. If a container is the heavy part, give it a limit as shown in memory and CPU limits on a local container.

Questions people ask

How many Jest workers should I use on a laptop?

Start with half your cores, for example --maxWorkers=50%, and lower it if memory runs short. Tests that wait on a database gain little from more workers.

Is make -j dangerous?

Plain make -j with no number has no limit on parallel jobs and can freeze a machine on a large build. Give it a number such as make -j4.

Does nice reduce memory use?

No. It only lowers CPU priority. Cap the worker count to reduce memory.
