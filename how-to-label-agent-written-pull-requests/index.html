How to Label Agent-Written Pull Requests Automatically

A branch prefix, a commit trailer and an automatic label make agent work visible, filterable and measurable. Here is the setup, with a workflow you can copy.

Mark agent pull requests with a branch prefix, a commit trailer and an automatic label, so you can filter them, apply different rules and measure them later. If you cannot tell which pull requests came from agents, you cannot manage them.

Choose three markers

  • A branch prefix such as agent/ or bot/.
  • A commit trailer such as Co-Authored-By, which many agent tools add already.
  • A pull request label such as agent, applied by automation.

Use more than one marker. A branch prefix can be forgotten; a label applied by a workflow cannot.

Apply the label with a workflow

A small workflow can read the branch name and add the label. Give it only the permission it needs.

name: label-agent-prs
on:
  pull_request_target:
    types: [opened]
permissions:
  pull-requests: write
jobs:
  label:
    if: startsWith(github.head_ref, 'agent/')
    runs-on: ubuntu-latest
    steps:
      - env:
          GH_TOKEN: ${{ github.token }}
        run: gh pr edit ${{ github.event.pull_request.number }} --add-label agent --repo ${{ github.repository }}

This workflow does not check out any code, which is why pull_request_target is safe here.

Use labels to drive rules

Once pull requests carry a label you can act on it.

  • Count open ones to enforce a work-in-progress limit.
  • Require a different review depth for the agent label.
  • Auto-close ones that fail checks for several days.
  • Report merge rate and revert rate by label; see measuring agent PR quality.

Add a PR template

A short template makes the agent state what it did and how it checked it.

## What changed
## How it was verified (commands and output)
## Risk and rollback

The verified section is the most useful. An agent that must paste real test output is less likely to claim a pass it did not see.

Keeping the labels honest

Labels are only useful if they are accurate. Review a sample each month: do all pull requests from agents carry the label, and does any human pull request carry it by mistake? If agents sometimes push from branches without the prefix, add a second rule that checks the commit trailer, and treat a pull request as agent-written when either marker is present.

Create the label in advance with a clear description, such as "Opened by a coding agent", so it shows up consistently and people know what it means. Add a second label for the risk tier if you use tiers, for example risk-low, risk-medium and risk-high, applied by path rules.

Do not use the label to shame the work. The aim is routing and measurement, not a separate caste of pull requests. A good agent change that passes all checks should merge as quickly as a good human one.

Questions people ask

Should agent PRs be marked as drafts?

Opening them as drafts until CI is green can reduce noise, since reviewers skip drafts. Convert to ready once required checks pass.

Can the agent remove its own label?

If it holds a token with label permission it can, so apply the label from a workflow and keep rules based on branch and commit data as well.
