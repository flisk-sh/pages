How to Give a Coding Agent One Fast Check Command

Agents need a single command that says pass or fail in under a minute. Here is how to build one from typecheck, lint and focused tests.

Create one command, usually npm run check or make check, that runs typecheck, lint and the fast tests and exits non-zero on any failure. An agent that can verify its own work in under a minute will fix its own mistakes before you ever see the pull request.

Why one command matters

If checking means remembering four commands and their order, an agent will skip some. A single entry point removes the choice. It also gives you one place to add a new check later, with no change to the instructions.

Build it from cheap checks first

Order matters: put the fastest, most informative checks first so a failure shows up in seconds.

{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "test:fast": "vitest run --changed",
    "check": "npm run typecheck && npm run lint && npm run test:fast"
  }
}

The same idea works in any language: a Makefile target, a just recipe, or a shell script. The tool does not matter; the single exit code does.

Keep the output short

Agents read the output, and long logs cost time and attention. Make failures easy to spot.

  • Print one line per passing step and the full detail only on failure.
  • Turn off progress bars and colors when stdout is not a terminal.
  • Fail with a clear last line such as check failed: lint.

Separate fast from full

Do not put your two-hour integration suite behind check. Keep a second command for the full run, and say in AGENTS.md when to use which: the fast check after every edit, the full suite once before finishing. CI runs the full suite either way, so the fast check only has to catch the common mistakes. For speeding up the tests themselves, see making tests fast enough for agents.

Check that the stack is healthy first

When tests need services such as a database, a failing check can mean the environment is down, not the code. If you use the open-source Flisk CLI to run your services locally, flisk status --json shows what is running and flisk doctor checks the environment, which gives an agent a way to tell the difference. Flisk is a local development tool, not a production orchestrator.

Pitfalls to avoid

The most common failure is a check command that passes locally and fails in CI because it uses different versions or flags. Have CI call the same scripts, or at least the same tool versions, so a pass means the same thing in both places. Pin versions in a lockfile and use the install command that respects it, such as npm ci.

Another trap is a check that silently skips work. A --changed test mode that finds no changed files can pass with zero tests run. Make the command print how many tests it ran, and fail if the number is zero when source files changed. Finally, do not let the check modify files. A formatter that rewrites code during check hides problems and creates a confusing diff. Use a check mode, such as prettier --check, and keep the auto-fix as a separate command named fix.

Questions people ask

What should the check command not include?

Slow end-to-end tests, deploys and anything that needs real credentials. Keep it fast and safe to run on every edit.

Should the same command run in CI?

CI can call the same scripts, but usually runs more on top of them. Sharing the underlying scripts keeps local and CI results consistent.

Try it

Give your agent a repo it can run on the first try.
