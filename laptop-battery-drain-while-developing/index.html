Keep your laptop fast while developing

Why your laptop battery drains while developing and what to stop

A dev stack keeps the CPU awake even when you are reading. A few changes make a workday on battery possible.

Battery drain while developing comes from work that never lets the CPU sleep: a container VM, watchers that poll, language servers, indexers and browser tabs. Find the top energy users in Activity Monitor, stop the stack when you are away from the desk, and replace polling with file events. The biggest win is usually to shut down what you are not using.

Measure before you change things

On a Mac open Activity Monitor and choose the Energy tab. Sort by Energy Impact, or by 12 hr Power for a longer view. Processes that are busy in the background but not in front of you are the targets. From a terminal:

pmset -g batt
pmset -g assertions
sudo powermetrics --samplers tasks --show-process-energy -i 5000 -n 1
  • pmset -g batt shows charge and whether you are on battery.
  • pmset -g assertions lists programs that prevent the Mac from sleeping, so you can see what keeps it awake.
  • powermetrics needs sudo and prints a per process energy estimate for the sampling window.

On Linux, powertop shows wake-ups and estimated power per process, and upower -i /org/freedesktop/UPower/devices/battery_BAT0 shows battery state. The device path can differ by machine.

The usual causes, in order

  1. The container VM. Docker Desktop, Colima and Podman run a Linux VM that uses CPU even with idle containers, and more with many running. Stop containers you do not need, or stop the VM when you leave the desk: colima stop for Colima. Docker Desktop has a Resource Saver mode that pauses the VM when no containers run.
  2. Polling file watchers. A watcher that scans files on a timer wakes the CPU all day. Use native file events and turn polling off (see dev server at 100% CPU).
  3. Dev servers left in the background. A forgotten Vite or Next process and its watcher run until you quit them.
  4. Language servers and indexers. The editor's TypeScript server, a code search indexer or Spotlight right after a big checkout. They settle down after some minutes; if they do not, see VS Code and TypeScript server memory.
  5. Browser tabs. Pages with animation, live reload sockets and video are heavy. The dev page you reload all day is one of them.
  6. Databases and brokers with busy jobs. A cron container or a queue worker that wakes every second adds up.

Plan your day on battery

  • Run only the services you need for the task. A frontend change may need the API but not the worker, the mail catcher and the metrics stack.
  • Prefer plain local processes for code you edit, and keep the container VM stopped when you work on something that does not need a database.
  • Raise polling intervals for anything that must poll, and move scheduled jobs from every second to every minute in development.
  • Lower screen brightness. It often beats any software tuning.
  • Plug in before a long build or test run. A sustained load on battery is slow on many laptops anyway because the system throttles.

With Flisk

Flisk helps with the "run less" part. In a project where every service has a command in its service.json, flisk up starts them as plain local processes with no Docker, no Tilt and no virtual machine. To work on one piece, flisk up --only web starts web and what it depends on. A service with "profiles": ["admin"] is left out until you ask for it with flisk up --profile admin, so a heavy service such as a dashboard or a metrics stack is off by default. When you leave, flisk down stops every service of the project, dependents first, and flisk status afterwards confirms that nothing is still running.

flisk up --only web
# ... work ...
flisk down
flisk status

For the case where Docker is needed only for a database, Flisk can start the database image with docker run next to local processes; the VM is still needed then. See running services without Docker for the exact conditions. Flisk does not manage your laptop's power settings and makes no claim about how much battery it saves: measure your own stack with the tools above.

Pitfalls

  • Do not judge by a single reading. Energy Impact spikes during builds; look at the 12 hr Power column or sample at idle.
  • Killing the Docker app does not always stop the VM. Check pmset -g assertions and the process list after you quit it.
  • caffeinate and some dev tools prevent sleep on purpose. Make sure a leftover one is not keeping the lid-closed Mac awake in your bag.

The other part of keeping a laptop calm is memory. Finding what uses your RAM is the place to continue, and starting only the services you need goes deeper on the "run less" habit.

Questions people ask

Does Docker drain the battery on a Mac?

The Linux VM behind Docker uses CPU even when containers are idle, and more when many run. Stopping containers, or the VM itself, is the most effective change.

How do I see what keeps my Mac awake?

Run pmset -g assertions. It lists the programs that currently prevent sleep.

Can I see energy use per process from the terminal?

On macOS run sudo powermetrics --samplers tasks --show-process-energy -i 5000 -n 1. On Linux use powertop.
