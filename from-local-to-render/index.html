How to go from a local stack to a Render Blueprint

Your local stack already describes ports, health checks and environment names. A generated starting file saves retyping them, as long as you know what it skips.

To move a local stack to Render, write a render.yaml Blueprint at the root of your git repository, push it, and create the Blueprint in the Render dashboard. If your services are described by service.json files, flisk export render generates the first version for you: one web service per resource, with the Docker paths, port, health check and environment variable names filled in. The file is a starting point. You still add the database, the secrets and the migration step.

The general approach

Render reads a Blueprint file called render.yaml from the repository root and creates the services in it. For each service you give it a type, a runtime (Docker or a language runtime), build and start settings, a health check path and environment variables. Writing that by hand for four services is tedious and easy to get slightly wrong, such as a port that does not match what the app listens on. People usually copy a sample and edit it, which works until the local setup and the deploy file drift apart.

The Flisk way

Flisk's exporter reads your service.json files and writes the Blueprint. It writes a file and nothing else: no deploy, no API call, no secret values. Run it from the repository root:

flisk export render --dry-run   # print the file, write nothing
flisk export render             # write render.yaml at the git root

Useful flags are --resource <name> to export a subset, --out to choose the location, and --force to overwrite an existing file. For an API with a Dockerfile, a Postgres URL and a log level, the output looks like this:

services:
  - type: web
    name: "api"
    runtime: docker
    dockerfilePath: "./services/shop/api/Dockerfile"
    dockerContext: "./services/shop/api"
    healthCheckPath: "/health"
    envVars:
      - key: PORT
        value: "4000"
      - key: DATABASE_URL
        sync: false
      - key: LOG_LEVEL
        sync: false

Things to notice:

  • The port becomes a PORT variable with the value from service.json, so the app must read PORT.
  • Names only. Each key under env is written as sync: false. Render then asks for the value when you create the Blueprint, and no value is stored in git. That includes plain values like LOG_LEVEL, so you enter them in the dashboard.
  • Docker or Node. A resource with a Dockerfile becomes a Docker service. One with only a package.json becomes a Node service with npm install && npm run build as the build command and npm start as the start command. A resource with only an image and neither file is refused with an error.
  • Health check. It uses healthCheckPath from service.json, or /health when not set. Make sure the deployed app really answers there.

What you add by hand

  1. The database. The exporter writes services only. Add a databases: block and point DATABASE_URL at it, or create the database in the dashboard and paste its internal URL into the prompt. Check the current Blueprint reference on Render's site for the exact fields.
  2. Secrets. Entries under secrets and params are not exported. If the API needs SESSION_SECRET, add it to envVars as a sync: false entry yourself.
  3. Migrations. Locally you may run them as a separate one-shot resource. On Render, run them as a pre-deploy command or a job rather than from the API start script. See database migrations in local dev for the pattern.
  4. Region, plan and scaling. Choose them in the file or the dashboard. The local manifests do not know about them.

Deploy it

  1. Review the generated file and edit it.
  2. Commit render.yaml at the repository root and push it to GitHub or GitLab.
  3. In Render choose New, then Blueprint, select the repository and fill in every value Render asks for.
  4. Open each service URL and confirm the health check passes.

When you change a manifest later, run flisk export render --force again and review the diff before committing it. Anything you added by hand is overwritten by --force, so keep hand-written additions in a separate file you merge, or re-add them from the diff.

Pitfalls and when not to use it

  • The image has to build there. Render builds from the Dockerfile in a clean environment. Run the same build locally with docker build first, and check the container runs as a non-root user and does not copy .env into the image.
  • Frontends in Docker are not always the best fit. A static site may be cheaper and faster on a static hosting plan. Treat the exported entry as a default, not a recommendation.
  • No state. A container filesystem is not durable. Keep files and data in the database or object storage.
  • Do not paste values into the file. If a secret ends up in git, rotate it.
  • Not your tool? If you deploy with another platform, the same manifests can produce a standalone Compose file instead. See deploy a standalone Compose file to a VPS.

Questions people ask

Does flisk export render deploy anything?

No. It writes a render.yaml file and stops. It does not call the Render API, create services or write secret values. You commit the file and create the Blueprint yourself in the Render dashboard.

Why are my secrets missing from render.yaml?

By design. Only the keys listed under env in service.json are written, each as an entry that Render asks you to fill in. Names under secrets and params are not exported, so add the ones your service needs by hand.

Is the generated Dockerfile ready for production?

Not necessarily. A scaffolded Dockerfile is a starting point for local work. Build the image the way Render will, run it once, and review the base image, the user it runs as and what it copies in before you ship it.
