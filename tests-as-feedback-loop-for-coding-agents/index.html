Coding agents in practice

How to use tests as a feedback loop for coding agents

Write the failing test first, let the agent iterate until it passes, and protect the tests from being weakened. A practical loop for fixing bugs and adding features.

Give the agent a failing test and a command to run it. It will edit, run, read the failure and try again, which is the loop that makes agents useful. The test is the specification, so keep a human in charge of what the test says.

The loop

  1. You or the agent write a test that fails for the right reason.
  2. The agent changes the code and runs the test command.
  3. It reads the output and repeats until the test passes.
  4. It runs the full suite to catch regressions.
  5. You review the diff, with the test first.

Without step 1, there is nothing to converge on, and the agent decides on its own when it is "done".

Bug fix example

A brief that works:

Bug: parsePrice("1,299.50") returns 1.
First write a failing test in tests/parse-price.test.ts that shows it.
Run it with: npm test -- tests/parse-price.test.ts and show me the failure.
Then fix src/parse-price.ts until it passes, and run npm test.
Do not edit existing tests.

Asking to see the failure first proves the test actually tests the bug.

Make the check fast and loud

Agents work best with a feedback command that takes seconds and prints a clear error. Make a single script for the checks you want, and put it in the instructions file:

"scripts": {
  "check": "npm run lint && npm run typecheck && npm test"
}

Slow or flaky suites produce confusing signals, and the agent may chase noise. Fix flaky tests first, or tell the agent which ones to ignore.

Stop test cheating

An agent that wants a green run may edit the test, add a skip, or special-case the input. Counter it:

  • Say "do not modify existing tests" in the brief, and check with git diff --stat.
  • Run tests in CI from the base branch version of the test files for protected areas.
  • Add property-style or extra cases the agent has not seen.
  • Read assertions in review. A test with no assertion always passes.

When tests are not enough

Tests do not cover layout, copy or performance feel. For UI, ask the agent to run the app and describe what it sees, then look yourself. For tests that grade model outputs rather than code, see testing and evaluating AI agents. For the review step, see reviewing AI-generated PRs.

Pitfalls

Beware of tests that pass for the wrong reason, such as a mock that returns what the test expects. Also beware of over-fitting: the agent makes the one given case pass but breaks similar inputs. Ask for a few extra cases, including edge cases like empty input, large input and malformed data, before you call it done.

Questions people ask

Should the agent write the tests too?

It can draft them, but you must read them. A wrong test locks in a wrong behaviour, and the agent will then defend it.

What if the project has no tests?

Start with one smoke test or a type check that runs the main path, and let the agent add tests for each change from there.
