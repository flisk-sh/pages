Docker on Mac: speed and resources

Which services to run natively on a Mac and which in Docker

On a Mac, containers cost memory, file sharing time and emulation. You do not need to pay for them on every service.

Run the code you edit all day as a native process on your Mac, and keep in Docker the things that are awkward to install, need a specific Linux environment or have to match production. A typical split is a Node, Python or Go API and its frontend native, with Postgres or Redis in a container. This avoids the file sharing, memory and emulation costs where they hurt most.

A rule for deciding

QuestionIf yes
Do I edit this code many times an hour?Native. Reload is instant and no files cross the VM boundary.
Is it a database, cache or broker with an official image?Docker. One command, a clean upgrade path, and the data lives in a volume.
Does it need system libraries that are painful to install on macOS?Docker.
Does it need the exact Linux image I deploy?Docker, at least before release.
Does it need the Apple GPU?Native. Containers on macOS cannot use it.
Is it amd64 only?Docker under emulation, or look for another build.

Nothing in this table is a Flisk rule. It follows from how Docker works on a Mac. The Docker VM holds memory, shared files are slower than local ones and foreign architectures are emulated. Reasons and numbers for each are in the other articles of this set, for example bind mounts and memory.

The mixed setup in Flisk

Flisk supports exactly this split. A service with a command runs as a local process, with PORT set to its port. A bring-your-own service with only an image, such as a database, starts with docker run and is published on 127.0.0.1. First the API:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "npm run dev",
  "toolchain": "node@22",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["postgres"],
  "env": { "DATABASE_URL": "postgres://app:${POSTGRES_PASSWORD}@localhost:5432/app" }
}

Then the database, as a ready made image with a named volume and a healthcheck that runs inside the container:

{
  "schemaVersion": 1,
  "appName": "postgres",
  "appType": "bring-your-own",
  "image": "postgres:17",
  "port": 5432,
  "env": { "POSTGRES_USER": "app", "POSTGRES_PASSWORD": "${POSTGRES_PASSWORD}", "POSTGRES_DB": "app" },
  "healthCheck": { "command": ["pg_isready", "-U", "app"] },
  "volumes": [{ "source": "postgres", "target": "/var/lib/postgresql/data", "name": "myapp_postgres" }]
}

toolchain makes flisk doctor and flisk up compare your installed Node with node@22 and refuse to start on a mismatch. Flisk installs nothing for you. Check the plan, then start:

flisk up --dry-run
flisk up
flisk status

flisk down stops the processes and removes the database container, and the named volume is kept. Wait for the database with dependsOn as in Compose depends_on and healthchecks. The full local process mode is explained in run local services without Docker.

Limits you must know

  • No Dockerfile builds in this mode. A project that has services with command cannot also contain services built from a Dockerfile. Flisk stops with a MIXED_RUNTIME error. A ready made image is allowed. If one service must be built from a Dockerfile, use the Docker and Tilt path for the whole project.
  • No gateway. Native services use localhost:port URLs, not *.localhost names through Traefik.
  • Your machine's versions apply. There is no isolation. Pin them with toolchain and in the repo.

Model servers on a Mac

Flisk's documentation states that Docker on macOS cannot reach the Apple GPU (Metal). To use the GPU, run the model server as a native process instead, for example a service whose command is ollama serve, and let the other services call it on its port. A container in a stack reaches it like any other service.

Pitfalls

  • Works natively, fails in production. A different OS and different library versions can hide bugs. Test the production image before release, or in CI.
  • Different data between teammates. If the database is native on one machine and a container on another, results differ. Pick one way and write it in the README.
  • Forgetting the database volume. Name it, so the data survives flisk down and a rebuilt container.

For a first look without writing anything, run npx @flisk-sh/flisk demo. When Docker is not running, it falls back to a two service app as local processes. The sibling article on stopping Flisk projects, stop and clean up a local stack, covers what to do when you are finished.

Questions people ask

Is it better to run Node natively than in Docker on a Mac?

For code you edit constantly, usually yes: reload is immediate and there is no file sharing cost. Keep databases and Linux specific dependencies in containers.

Can Docker use the Mac GPU?

No. Containers on macOS cannot reach the Apple GPU through Metal. Run model servers such as Ollama as native processes to use it.

Can Flisk run some services natively and a database in Docker?

Yes. Services with a command run as local processes, and a service with only an image, such as Postgres, runs with docker run. A service built from a Dockerfile cannot be in the same project.
