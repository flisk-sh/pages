Agent frameworks on your laptop

How to keep LLM API keys out of service.json and git

An agent project has at least one secret that really costs money. Commit the name of the variable and never its value.

Keep an LLM API key in a git-ignored .env file, read it into the process through an environment variable, and commit only the variable's name. A leaked model key is more expensive than most leaked credentials because anyone can spend with it, and scanners find keys pushed to public repositories within minutes. The same rule applies to every framework: the key never appears in code, in a Dockerfile, or in a manifest.

The general rule

  • The value lives in one local file that is in .gitignore from the first commit. Add the ignore line before you create the file; deleting a committed key later does not remove it from history.
  • The code reads an environment variable. Provider libraries already do: the OpenAI client reads OPENAI_API_KEY, and the Anthropic ones read ANTHROPIC_API_KEY. Do not pass the key as a string literal even in a quick test.
  • A template documents the names. Commit a .env.example with the names and empty values so a new developer knows what to set.
  • Limit the damage. Use a separate key for development with a monthly spending cap at the provider, and rotate it when you suspect exposure.

With Flisk: a service that runs as a local process

For a service with a command, service.json has an env map. A value may use ${VAR} or ${VAR:-default}, resolved in this order: your shell, the project .env, the service's own .env next to its service.json, then the default.

{
  "schemaVersion": 1,
  "appName": "agent",
  "appType": "backend",
  "command": "uvicorn main:app --app-dir src --host localhost --port ${PORT:-4000}",
  "port": 4000,
  "env": {
    "OPENAI_API_KEY": "${OPENAI_API_KEY}",
    "MODEL": "${MODEL:-your-default-model}"
  }
}

The file holds the reference. The value sits in .env in the project root:

OPENAI_API_KEY=sk-...your-key...

Flisk adds .env to .gitignore when flisk up or flisk init runs, but do not rely on that for an old repository: check git check-ignore .env yourself. If you use a per-service .env, check that file too.

With Flisk: containers

For resources that run in Docker, list the names under secrets:

"secrets": { "required": ["ANTHROPIC_API_KEY"], "optional": ["SENTRY_DSN"] }

Flisk's documentation describes the behaviour: a required name is injected so that Docker Compose refuses to start the resource and says which name is missing, while an optional name starts the resource with the variable empty. The values come from the project .env, and nothing secret is written to generated files, which is why those files can be committed. The setting FLISK_SECRET_PROVIDER=infisical hands secrets to Infisical instead, in which case nothing is injected from .env.

Two other fields are easy to confuse with this one. params holds plain configuration and is written to a generated file, so never put a key there. And secrets.generate creates random development secrets such as an auth signing key ("hex:32" or "base64:32") on first start. That is for keys you invent locally. A provider key is issued by the provider, so it cannot be generated.

Check before you commit

  • git check-ignore -v .env prints the rule that ignores the file. No output means it is not ignored.
  • grep -rn "sk-" --include=service.json . is a crude search for pasted keys in manifests. Use a proper secret scanner in CI as well.
  • Do not put keys in frontend variables. Vite inlines variables starting with VITE_, and Next.js inlines NEXT_PUBLIC_ ones, into JavaScript every visitor downloads. Flisk's flisk doctor warns when it finds a key-shaped value in such a variable. Call the model from a backend, and give the browser only your own API.

Pitfalls

  • A key in shell history. export OPENAI_API_KEY=... typed into a terminal lands in your history file. Prefer the .env file.
  • Logs. Do not log request headers or the whole environment while debugging an agent. Many frameworks have verbose modes that print configuration.
  • Env files in images. A COPY . . in a Dockerfile copies .env into the image unless .dockerignore excludes it.
  • Different environment, different key. Staging and CI should have their own keys. See keeping env var names, not values, in committed config.

For what to do when a variable does not reach your service at all, read debugging an environment variable that is not loaded. To avoid paid keys while you develop, see using a local model.

Questions people ask

Is it safe to put a dummy key in service.json?

A placeholder such as ollama for a local model server is fine because it is not a credential. A real provider key must never be written there.

What happens if a required secret is missing?

For container resources, Flisk documents that Docker Compose refuses to start the resource and names the missing variable. For a local process, check your command's own error, since the variable would simply be empty.

Can Flisk generate my OpenAI key?

No. secrets.generate makes random values for keys you invent, such as a signing secret. Provider keys come from the provider's dashboard.
