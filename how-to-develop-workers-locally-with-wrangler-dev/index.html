How to develop Workers locally with wrangler dev

Run a Worker and its D1, KV and secrets on your machine, test scheduled handlers, and know which bindings need the remote network.

npx wrangler dev runs your Worker locally on port 8787 with local copies of D1, KV and other bindings, and reloads on every save. Secrets for local runs go in a .dev.vars file.

Start the dev server

npx wrangler dev
# Ready on http://localhost:8787

Edit a file and the Worker reloads. Wrangler stores local bindings state in a .wrangler folder, so add it to .gitignore.

Local secrets and variables

Create .dev.vars next to the config. It is read only by local dev.

API_TOKEN=local-test-value
WEBHOOK_SECRET=another-test-value

Never commit this file. In code you read these as env.API_TOKEN. See storing secrets for production.

Local D1 and KV

By default D1 and KV use local storage that starts empty. Apply migrations to it with the --local flag.

npx wrangler d1 migrations apply app --local
npx wrangler d1 execute app --local --command "SELECT count(*) FROM users"

Local data is separate from production data, which is what you want while testing.

Testing a scheduled handler

Start dev with the scheduled test flag and hit the special route.

npx wrangler dev --test-scheduled
curl "http://localhost:8787/__scheduled?cron=0+*+*+*+*"

More in cron triggers.

Write a test for the handler

Unit test the pure parts of your Worker the same way you would any JavaScript: extract logic into functions, and test them with a regular runner. For the full handler, call it directly with a constructed request.

import worker from "./index.js";

const res = await worker.fetch(
  new Request("http://x/health"), {}, { waitUntil() {} }
);
console.log(res.status, await res.json());

Pass a fake env object with stubs for any bindings the code touches.

Keep one terminal for wrangler dev and one for requests. When something fails, the dev server prints the stack trace in the first terminal, which is usually all you need. Add console.log freely while developing and remove noisy logs before you deploy.

Remote mode and what differs

  • Some bindings, such as Workers AI, run on Cloudflare's network even in local dev, so they need a login and count against your usage.
  • wrangler dev --remote runs your code on the edge, which is closer to production but slower to iterate.
  • Local and production can differ in limits and performance. Always smoke test after deploying.

If your Worker talks to other services you run yourself, a tool like the Flisk CLI can start those services locally from service.json files, alongside wrangler dev.

Questions people ask

Why do I get a different result locally than in production?

Local mode simulates bindings and has no real network edge. Differences in limits, caching and timing are normal, so test after deploying.

Should .wrangler be committed?

No. It holds local state and caches. Add it to .gitignore.
