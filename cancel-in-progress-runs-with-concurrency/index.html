Cancel Old GitHub Actions Runs with Concurrency Groups

Stop wasting runner minutes on superseded pushes. Use a concurrency group with cancel-in-progress, and know when you must not cancel, like deploys and release jobs.

Add a concurrency block with cancel-in-progress: true and a group named by workflow and branch. When you push again, the older run for the same branch is cancelled and only the newest one runs.

The standard block

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

Put it at the top of the workflow file, next to on:. The group name decides which runs compete. This one means: one run at a time per workflow per branch or pull request ref. Different branches do not cancel each other.

Only cancel on pull requests

On the default branch you usually want every commit tested, so you can find which one broke the build. Cancel only for pull requests.

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

With this, pushes to a pull request cancel older runs, while runs on the default branch queue and all complete.

Do not cancel deploys

Cancelling a deploy halfway can leave an environment in a broken state. For deploy or release workflows, serialize instead of cancelling.

concurrency:
  group: deploy-production
  cancel-in-progress: false

With false, a new run waits for the current one. Note that GitHub keeps at most one pending run per group, so if several runs queue up, the older pending ones are replaced by the newest.

Pitfalls

  • A cancelled run shows as cancelled, not failed. If a required check is cancelled and the newest run passes, the merge is fine. Make sure your dashboards do not count cancelled runs as failures.
  • If the group name is too broad, such as a fixed string, unrelated pull requests cancel each other. Always include the ref.
  • Scheduled and manual runs can cancel each other if they share a group. Add the event name when it matters.

Job-level concurrency and a worked example

You can also put concurrency on a single job. That is useful when only one expensive job, such as an end-to-end suite, should be cancelled while quick checks always finish. Give that job its own group name, for example e2e-${{ github.ref }}. A worked case: a developer pushes five commits in ten minutes to a pull request. Without cancellation, five full runs execute. With it, four are stopped within seconds of the next push, and the one that matters is the last. The saving grows with push frequency, and it also clears the queue for other people.

How much does it save

It depends on how often people push. For active pull requests with several quick pushes, a large share of runs is wasted. Check by counting cancelled runs with gh run list --json conclusion after you enable it. Combine this with path filters to skip even more.

Questions people ask

Does cancel-in-progress cancel jobs on other branches?

Not with a group that includes the ref. Only runs in the same group are cancelled.

Can I cancel only some jobs?

Concurrency can be set at job level too, with its own group, so you can cancel one job and let others finish.
