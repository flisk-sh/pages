Docker build context in a monorepo: build one service image

A Dockerfile inside apps/api cannot see packages/shared if the build context is apps/api. The fix is to move the context up, then keep it small.

In a monorepo, run docker build from the repo root and point -f at the service's Dockerfile: docker build -f apps/api/Dockerfile -t shop-api .. The final dot is the build context. If it were apps/api, Docker could not copy packages/shared or the root lockfile, because a build can only read files inside its context.

Why the context is the problem

The context is the set of files Docker sends to the builder. COPY can only reference paths inside it. With the usual one-repo-one-service layout the Dockerfile sits at the root and everything is available. In a monorepo it sits in apps/api/, but the service needs the root pnpm-lock.yaml, pnpm-workspace.yaml and workspace packages next to it. So move the context to the root and keep the Dockerfile where it is:

docker build -f apps/api/Dockerfile -t shop-api .

In Compose the same thing is:

services:
  api:
    build:
      context: .
      dockerfile: apps/api/Dockerfile

A Dockerfile that uses the root context

FROM node:22-alpine AS base
RUN corepack enable
WORKDIR /repo

FROM base AS deps
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY apps/api/package.json apps/api/
COPY packages/shared/package.json packages/shared/
RUN pnpm install --frozen-lockfile --filter @shop/api...

FROM deps AS build
COPY apps/api apps/api
COPY packages/shared packages/shared
RUN pnpm --filter @shop/api... build

FROM base AS run
COPY --from=build /repo /repo
WORKDIR /repo/apps/api
CMD ["node", "dist/index.js"]

The package manifests are copied first so the install layer is cached until a dependency changes. Source comes later. This is the same idea as in any layered Dockerfile, applied to several package.json files.

Keep the context small

Sending the whole repo is slow. Two tools help:

  • A .dockerignore at the context root. Exclude node_modules, .git, .turbo, dist, .env* and the other apps' build output. Without it, a host node_modules can overwrite the container's.
  • turbo prune. turbo prune @shop/api --docker writes an out/ folder with only the packages the API needs: out/json holds the manifests for the install layer, out/full the source, plus a pruned lockfile. Use it when the repo is big enough that copying everything hurts.

Check what Docker receives

Before you tune anything, measure. BuildKit prints the size of the context it transfers at the start of the build, a line such as "transferring context". If that number is hundreds of megabytes for a service with a few thousand lines of code, the .dockerignore is missing or too short. A starting file for a pnpm repo:

**/node_modules
**/dist
**/.turbo
.git
.env*
apps/*/coverage

Remember that the ignore file is read from the context root, not from the folder that holds the Dockerfile. Docker also supports a file named like the Dockerfile with a .dockerignore suffix, for example apps/api/Dockerfile.dockerignore, which takes priority when it exists, so each service can keep its own rules.

The Flisk way

For a service that is already built from a Dockerfile, Flisk's bring-your-own type has a buildContext field: a path, relative to the service folder, to build from elsewhere in the repo. dockerfile is then relative to that context. For apps/api/service.json:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "bring-your-own",
  "stack": "main",
  "port": 4500,
  "healthCheckPath": "/health",
  "buildContext": "../..",
  "dockerfile": "apps/api/Dockerfile"
}

I checked a manifest like this with flisk config verify in a scratch project, and it passes. I did not build the image through Flisk. BYO ports run from 4000 to 5999. This path uses Docker and Tilt, so it cannot share a run with services that have a plain command: Flisk stops with a MIXED_RUNTIME error and lists both groups. Pick one runtime per project for your own services. See running an existing Dockerfile in a dev stack for the wider picture.

Pitfalls

  • Cache busts on every edit. A COPY . . early in the Dockerfile invalidates the install layer whenever any file in the repo changes. Copy manifests first.
  • Secrets in the context. A missing .dockerignore sends .env to the builder and may bake it into a layer.
  • Dev images versus production images. A bind-mounted dev container does not need the build stage at all. For live code, local processes are often simpler; see running services from a pnpm workspace.

When the image is ready, the monorepo versus separate repos question shows up again at deploy time, since each service gets its own pipeline.

Questions people ask

What is the build context in docker build?

It is the folder whose files Docker sends to the builder. COPY can only read files inside it. The last argument of docker build is the context.

How do I use a Dockerfile in a subfolder with a root context?

Run docker build -f apps/api/Dockerfile . from the repo root. The -f flag selects the Dockerfile and the dot sets the context.

What does turbo prune --docker do?

It copies only the packages one app needs into an out folder, split into json files for the install layer and full source, with a pruned lockfile.
