How to build an audit log table for a SaaS app

Customers ask who deleted a project, and your support team asks it twice a week. An audit log answers that, if you design it before you need it.

Write one row per meaningful action into an append-only table, in the same database transaction as the change it describes. Each row records the tenant, who acted, what they did, which object it touched and a request id. Revoke update and delete on the table from your app role, and trim it with a separate retention job.

Audit log, app log or history table

Three things get mixed up. An application log is for engineers and can be dropped or sampled. A history table keeps old versions of one record so you can show or restore them. An audit log is a business record of security-relevant actions: sign-ins, role changes, key creation, exports, deletions. It must be reliable, searchable per tenant and shown to customers in some form. This article is about the third.

The table

create table audit_events (
  id bigint generated always as identity primary key,
  tenant_id uuid not null,
  occurred_at timestamptz not null default now(),
  actor_type text not null,        -- 'user', 'api_key', 'system'
  actor_id text,
  action text not null,            -- 'member.role_changed'
  target_type text,
  target_id text,
  metadata jsonb not null default '{}',
  request_id text,
  ip inet
);

create index audit_tenant_time on audit_events (tenant_id, occurred_at desc);

revoke update, delete on audit_events from app_user;

Use a stable, dotted action vocabulary such as project.deleted or apikey.created, and keep a list in code so names do not drift. A typed constant beats a string typed in twenty places. Record the actor type, because a deletion by a scheduled job and one by a person are different stories.

Write it in the same transaction

await db.transaction(async (tx) => {
  await tx.query("update memberships set role = $1 where id = $2", [role, id]);
  await tx.query(
    `insert into audit_events
       (tenant_id, actor_type, actor_id, action, target_type, target_id, metadata, request_id)
     values ($1,'user',$2,'member.role_changed','membership',$3,$4,$5)`,
    [tenantId, actorId, id, { from: oldRole, to: role }, requestId]);
});

If the change commits, the event does too. A fire-and-forget write after the transaction loses events whenever the process dies in between, which is the exact moment you need them. The cost is a slightly longer transaction, which is fine at audit volumes. Pass the same request id you use in logs, so support can jump from an event to the log lines of that request.

What to put in metadata

  • Changed fields, as before and after values for things like roles and settings.
  • Never secrets, tokens or full request bodies. An audit log that stores a leaked key is a second leak. Record the key id, not the key.
  • Avoid personal data you do not need. Audit rows outlive the records they mention, which matters when you delete a tenant's data.

Immutability and retention

Removing update and delete rights from the app role makes accidental edits impossible, and makes tampering require a different credential. It does not stop a database admin, so for strict compliance you ship events to storage with write-once settings. For most products, the grant is enough. Table size grows forever otherwise, so partition by month with Postgres declarative partitioning and drop old partitions on a schedule, or run a retention job under a separate owner role. Pick the retention period from the plan or the contract, and tell customers.

Trying it locally with Flisk

A retention or export job is a background process, which Flisk calls a worker. On the container route, scaffold one and let it share the stack with the API:

flisk resource audit-retention --type worker --stack saas --yes

That creates a worker resource under services/saas/audit-retention with its own service.json and a bun run worker dev command, ready for your job code. Scheduling patterns are in how to run cron jobs in local development. To test the retention logic quickly, seed events with old timestamps and run the job once by hand with flisk run audit-retention -- bun run worker, which runs in that service's environment while the stack is up.

Pitfalls

  • Logging reads. Recording every GET fills the table. Log changes and sensitive reads, such as exports.
  • Different tenant ids. Use the same tenant column and row level security policy as other tables, so one customer never reads another's audit trail.
  • Time zones. Store timestamptz and format in the viewer's zone.
  • Skipping the UI. A log nobody can see answers nothing. A filterable list per tenant, by actor and action, is the first version.

Deleting records is the action that most needs an audit trail, and it has its own design questions: see soft delete and tenant data removal.

Questions people ask

Should audit events be written in the same transaction as the change?

Yes. That guarantees the event exists if and only if the change committed, which asynchronous logging cannot promise.

What should not go into audit metadata?

Secrets, tokens and full request bodies. Store identifiers and changed fields instead.

How do I make an audit table append-only?

Revoke update and delete on it from the application role, and use a separate role for retention work. For strict compliance also ship events to write-once storage.
