What not to publish on a public page

A checklist of things that should never reach a public static site: secrets, personal data, internal URLs and source maps, with commands to find them before you deploy.

Never publish secrets, personal data, internal addresses or anything you would not put on a billboard. Anything on a public page can be fetched by anyone and copied by crawlers, and deleting it later does not remove the copies.

Secrets

API keys, tokens, passwords, private keys and .env files. A frontend bundle is public, so a key referenced in browser code is published even if it never appears in your repo. If the page needs a secret, call your own backend and keep the key there. See env and secrets.

Personal and customer data

Emails, phone numbers, addresses, screenshots with names, analytics exports and database dumps. Agent-built dashboards often embed sample data copied from a real source. Check it.

Internal details

  • Internal hostnames and IP addresses in code comments or config.
  • Source maps (*.map), which reveal your original source.
  • Git metadata: a .git folder inside the published directory.
  • Draft notes, TODO comments and prompts pasted into HTML.

Scan before you deploy

Publish only the build folder and scan it. These commands are a start, not a guarantee.

grep -rniE "(api[_-]?key|secret|token|password|BEGIN (RSA|PRIVATE))" dist/
find dist -name "*.map" -o -name ".env*" -o -name ".git"
grep -rnoE "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}" dist/

For a more thorough scan use a dedicated secret scanner such as gitleaks or trufflehog on the folder.

Make it a habit with a pre-deploy check

People rarely leak things on purpose. They leak them because the scan was manual and they skipped it. Put the grep commands in a script and run it in CI before the deploy step, failing the build on any match. A small allowlist of expected strings keeps it from crying wolf. For agent-generated pages, add one more rule to your prompt: do not include real names, emails or keys, and use placeholders. Then still run the scan, because prompts are not guarantees.

Finally, remember metadata. Images carry EXIF data that can include location, and PDFs carry author names. Strip them before publishing, for example with exiftool -all= image.jpg.

If you already published something

  1. Rotate any exposed key first. Assume it is compromised.
  2. Remove the content and redeploy.
  3. Remember caches and search engines. Ask the search engine to remove the URL if needed.
  4. Check your Git history, since deleting a file does not remove it from older commits.

Unlisted is not private. A link nobody knows can still be guessed, shared or crawled. For private material use access control, not obscurity.

Questions people ask

Is a page with a random URL private?

No. An unguessable URL only makes it harder to find. Anyone with the link can read it, and links leak. Use real authentication for private content.

Are public API keys for maps or analytics safe?

Some keys are designed to be public but should be restricted by domain in the provider's settings. Read the provider's docs for each key.

Try it

Put one page online in a minute.

Pages publishes an HTML or Markdown file to a free public link. It is public, so do not use it for anything private.

npx -y @flisk-sh/pages publish page.html --wait
