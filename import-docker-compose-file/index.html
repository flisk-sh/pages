How to import a docker-compose.yml into Flisk

flisk import turns a Compose file into service.json files without touching the original. Here is what it reads, what it maps and what you must check by hand.

Run flisk import . --dry-run in the folder that holds your docker-compose.yml. It prints what Flisk would write. When the plan looks right, run flisk import . --yes, check the generated .env, and start the stack with flisk up. Your Compose file and your source code are never changed.

What the import reads and writes

The importer is a separate package, flisk-import, pinned by the CLI to version 0.18.2. Flisk runs it through npx --yes, so you need Node and npx on the machine. It reads one file, <dir>/docker-compose.yml. These are not read: compose.yaml, docker-compose.yaml, override files and Procfiles. If your file is named differently, rename or copy it first. When docker compose is available, include and extends are resolved through docker compose config.

For each Compose service it writes services/<stack>/<service>/service.json, where the stack is the name of the directory you ran it in. It also creates .flisk/project.json if that file does not exist yet.

flisk import . --dry-run
flisk import . --yes
flisk up

The flags are --dry-run (print the plan, write nothing), --yes (skip the question), --force (overwrite existing files) and --json (machine-readable output).

How Compose fields map

Every imported service gets appType: "bring-your-own", which means Flisk runs your image or your Dockerfile as it is and does not generate application code. The importer carries over the parts of a Compose service that have a Flisk equivalent:

Composeservice.json
buildbuildContext and dockerfile
imagekept, including ${VAR:-default} forms
depends_ondependsOn
healthcheckhealthCheck.command and its timing fields
environmentliterals in env; secret-looking values in secrets.required and the git-ignored .env
volumesvolumes, with the volume name kept
portsone published port becomes port; the rest become extraPorts
profilesprofiles, when the name is lowercase letters, digits and dashes
command, entrypointcontainer.command, container.entrypoint

Restart policy, stop_grace_period, network aliases, extra_hosts and ulimits are carried over too. Databases and other well-known non-HTTP ports (22, 25, 3306, 5432, 6379 and similar) are marked private, with exposeViaProxy: false and no gateway route. Other single ports get a Traefik route, so a web service becomes reachable under a *.localhost name.

What is not imported

The plan tells you about each item it skips. The common ones:

  • container_name is dropped.
  • Anonymous volumes and absolute host paths are not mapped.
  • network_mode: host and extends are not mapped by the importer itself.
  • Build contexts outside the project directory are not mapped.
  • Unusual forms of image variables are not mapped.

Read the dry-run output before you accept it. Whatever it skips, you decide by hand.

Check these after the import

  • The .env file. Literal values from Compose are copied. A value written as ${VAR} has to be set by you.
  • Ports and hostnames. Flisk injects PORT and DATABASE_URL, and requests reach services with a Host header like api.<project>.localhost. Some apps reject unknown hosts (Rails host checks are one example), so allow the new name.
  • Data. Volume names are kept, so docker compose up and flisk up can use the same data. Read how to keep volumes between runs before you delete anything.
  • Hot reload. Imported services are bring-your-own containers. Flisk watches the manifest but does not live-sync code into them. Rebuild from the Tilt UI or restart flisk up. The article on Compose hot reload covers your options.

The importer needs a recent core: version 1.3.104 is enforced, and 1.4.24 or later is recommended for container commands, extra ports, sidecars and volumes. On Windows, run the whole thing inside WSL2 Ubuntu with the project in the Linux home directory.

When not to import

If the project is two containers that work and nobody complains, the import adds a layer without removing work. It also does not turn your images into generated services: they stay bring-your-own, so you get the gateway, ordering and one command, not the code-sync features. The Compose file stays valid either way, so you can try the import on a branch and delete the new files if you do not like them.

After flisk up is green, run flisk status to see the routes, then look at depends_on and healthchecks to tidy the ordering. If the stack ever needs to leave Flisk, exporting a standalone Compose file is the way back.

Questions people ask

Does flisk import change my docker-compose.yml?

No. It only reads docker-compose.yml and writes new service.json files under services/<stack>/<service>/ plus .flisk/project.json if it does not exist.

Why was my compose.yaml not found?

The importer reads only docker-compose.yml. Files named compose.yaml or docker-compose.yaml, and override files, are not read, so rename or copy the file first.

Do I need Node to run flisk import?

Yes. The CLI runs the pinned flisk-import package through npx, so Node and npx must be on your PATH.
