How to design a team invitation flow for a SaaS app

Inviting a colleague looks like one button. Behind it are tokens, expiry, duplicates, existing accounts and seat limits that all need a decision.

An invitation is a row with a random token (stored hashed), the invited email, a role, an expiry and a state. Accepting it adds the signed-in user to the tenant in one transaction and marks the invite used. Decide up front what happens when the email already has an account, when the invite is sent twice and when the seat limit is reached.

The table

create table invitations (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references tenants(id),
  email text not null,
  role text not null,
  token_hash bytea not null unique,
  invited_by uuid not null,
  expires_at timestamptz not null,
  accepted_at timestamptz,
  revoked_at timestamptz,
  created_at timestamptz not null default now()
);

create unique index one_pending_invite
  on invitations (tenant_id, lower(email))
  where accepted_at is null and revoked_at is null;

The partial unique index means a tenant can have only one pending invite per email, however many times someone clicks "invite". Resending reuses the row and issues a new token, so the old link stops working.

Token handling

Treat the invite token like a password reset token. It is a credential for a short time:

  • Generate 32 random bytes, encode them for the URL, and store only a SHA-256 hash of the token. A database leak then does not hand out working links.
  • Make it single use. Set accepted_at in the same statement that checks it is still null.
  • Expire it, seven days is common, and check expiry on the server at acceptance time.
  • Do not put anything private in the link beyond the token. Look up the tenant name server-side to show on the accept page.

Accepting

Bind the invite to an email. The simplest safe rule: the user must be signed in with a verified email address equal to the invited one, otherwise acceptance fails with a clear message. If they have no account, send them to sign-up with the email prefilled and return to the invite afterwards. Without binding, anyone who gets the link, from a forwarded email or a shared chat, joins the tenant with the invited role.

begin;
  update invitations
     set accepted_at = now()
   where token_hash = $1
     and accepted_at is null and revoked_at is null
     and expires_at > now()
   returning tenant_id, role, email;
  -- if no row returned: rollback and show "invalid or expired"
  insert into memberships (tenant_id, user_id, role)
  values ($tenant, $user, $role)
  on conflict (tenant_id, user_id) do nothing;
commit;

Running both statements in one transaction means a crash between them cannot burn the invite without adding the member. The on conflict clause makes a second click harmless.

Seat limits and the race

If the plan allows ten seats, counting members and then inserting is a race: two invites accepted at the same moment can both see nine. Take a lock on the tenant row (select ... from tenants where id = $1 for update) before counting, or keep a counter with a check constraint. Decide whether pending invites count toward the limit. Counting them at creation time gives the sender feedback early, counting at acceptance is the only moment the limit is truly enforced, and most products check at both. Where the limit comes from is covered in plans and entitlements.

Reading invite links in local development

You do not need a mail server to build this. In development, have the API log the accept link instead of sending mail, switched by an environment variable such as MAIL_MODE=log that you define. With the services under Flisk, read the link from the service log:

flisk logs --service api --tail 50

The command returns recent output of that service, merged across services when you leave out the name. Set the variable in the manifest's env block so the whole team gets the same behavior. See the local stack layout for what else to run next to the API.

Pitfalls

  • Case in emails. Compare lower(email) consistently, or Ana@x.com and ana@x.com become two invites.
  • Role escalation. Check that the inviter may grant the role they chose. An editor must not invite an admin.
  • Link previews. Chat apps and mail scanners fetch links. Do not consume the invite on a GET. Show a page and accept on a POST.
  • Leaking existence. Responses to "is this email already a member" can reveal who uses your product. Keep them neutral outside the tenant's own admins.

Every accepted invite and role change is worth recording. The next article shows how: an audit log table.

Questions people ask

Should I store invitation tokens in plain text?

No. Store a hash, as you would for a password reset token, so a database leak does not expose usable links.

Why should accepting an invite be a POST?

Mail scanners and chat apps fetch links automatically. A GET that consumes the token would burn the invite before the person clicks.

How do I stop two invites exceeding the seat limit?

Lock the tenant row or use a counter with a check constraint, and do the count and the insert in the same transaction.
