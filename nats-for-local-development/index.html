How to run NATS with JetStream for local development

One NATS container, JetStream turned on, and a connection string every service can read. Here is the plain way and the Flisk way.

To run NATS locally, start one nats container with the -js flag so JetStream (the persistent part) is on, publish port 4222 to your machine, and give your services a single NATS_URL. With Flisk, flisk resource bus --type queue --stack shop writes that container definition for you and hands the URL to every service that lists it in dependsOn.

Core NATS or JetStream

NATS has two layers, and picking the wrong one is the most common local surprise.

  • Core NATS is fire-and-forget pub/sub. If nobody is subscribed when you publish, the message is gone. That is fine for presence pings and cache invalidation, and wrong for jobs.
  • JetStream stores messages in a stream on disk and tracks which consumer has acknowledged what. That is what you want for background jobs: a worker that restarts picks up where it stopped.

JetStream is off unless you start the server with -js. If your first publish works but nothing is stored, check that flag first.

The plain Docker way

You do not need any tool for this. One command gives you a server with JetStream, a data directory that survives restarts, and the monitoring endpoint on port 8222:

docker run --rm --name nats \
  -p 127.0.0.1:4222:4222 -p 127.0.0.1:8222:8222 \
  -v nats-data:/data \
  nats:2.11.8-alpine -js -sd /data -m 8222

-sd sets the JetStream storage directory and -m turns on the HTTP monitoring port. Binding to 127.0.0.1 keeps the server off your Wi-Fi, which matters because a default NATS server has no authentication.

In Docker Compose the same thing is a service with the same command and a named volume. Services in the same Compose project reach it at nats://nats:4222, and your host machine reaches it at nats://127.0.0.1:4222. Those are two different addresses, and mixing them up causes most "connection refused" reports.

The Flisk way

Install the CLI with npm install -g @flisk-sh/flisk, then in a Flisk project run:

flisk resource bus --type queue --stack shop --yes

NATS is the default queue framework, so no --framework is needed. The command writes services/shop/bus/service.json. This is the file I got from CLI 1.4.57:

{
  "schemaVersion": 1,
  "appName": "bus",
  "appType": "bring-your-own",
  "framework": "nats",
  "stack": "shop",
  "port": 4222,
  "image": "nats:2.11.8-alpine",
  "exposeViaProxy": false,
  "healthCheck": { "port": 4222 },
  "container": { "command": ["-js", "-sd", "/data", "-m", "8222"] },
  "volumes": [{ "source": "bus-data", "target": "/data" }],
  "provides": { "NATS_URL": "nats://bus:4222" }
}

It is the same container as the plain command: JetStream on, data in a named volume that flisk down keeps, and a readiness check on the port. Two fields are Flisk's own. exposeViaProxy: false keeps NATS off the HTTP gateway, because it does not speak HTTP. provides means every service that names bus in its dependsOn gets NATS_URL=nats://bus:4222 in its environment, so no URL is copied between files.

Wire a service to it:

"dependsOn": ["bus"]

Run flisk config verify afterwards. Then flisk up shop starts the queue first and the dependent service after it.

To use the nats command line tool or a GUI from your own machine, publish the client and monitoring ports with extraPorts. Flisk binds them to 127.0.0.1 only:

"extraPorts": [{ "port": 4222 }, { "port": 8222 }]

flisk config verify accepts this. I did not start the container to test the published ports, so after flisk up, check that the ports answer before you rely on them.

Do not add the nats feature to a worker's featuresEnabled to get a queue. In the 1.4.x CLI I checked, flisk doctor reports that no NATS server will start for such a worker. A queue resource is the way to get one.

Create a stream and publish from Node

This uses the nats npm package (version 2). The stream definition is idempotent: running it again with the same settings succeeds.

import { connect, StringCodec } from "nats";

const sc = StringCodec();
const nc = await connect({ servers: process.env.NATS_URL });

const jsm = await nc.jetstreamManager();
await jsm.streams.add({ name: "JOBS", subjects: ["jobs.>"] });

const js = nc.jetstream();
const ack = await js.publish(
  "jobs.email",
  sc.encode(JSON.stringify({ to: "ana@example.com" }))
);
console.log("stored as sequence", ack.seq);

await nc.drain();

The jobs.> subject means "everything under jobs.". A publish that matches no stream gets a "no responders" error, which is a useful signal that the stream is missing. The consumer side, with acknowledgements and retries, is in the retries article.

Pitfalls

  • Old messages come back. The data volume outlives flisk down, so a stream keeps its messages between runs. Purge one stream with nats stream purge JOBS, or remove the volume (find its full name with docker volume ls) when you want a clean slate.
  • The hostname bus only works inside the stack. From your host shell use nats://127.0.0.1:4222, and only if you published the port.
  • Keep it local. A default NATS server has no authentication, which is acceptable only while the port is bound to 127.0.0.1.
  • Need strict ordering or complex routing? Look at RabbitMQ. For most local job queues NATS is the lighter choice.

Questions people ask

Does NATS need JetStream for background jobs?

Yes, if you cannot lose a message. Core NATS drops a message when no subscriber is connected. JetStream stores it in a stream until a consumer acknowledges it. Start the server with the -js flag to turn it on.

How do I connect to NATS from my host machine when it runs in Docker?

Publish port 4222 to 127.0.0.1 and connect to nats://127.0.0.1:4222. The container hostname, such as bus, only resolves for other containers in the same network.

Does flisk down delete my NATS messages?

No. The queue resource stores JetStream data in a named volume, and flisk down keeps named volumes. Purge a stream with the nats CLI or remove the volume to start clean.
