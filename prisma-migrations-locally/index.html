Databases in local development

Prisma migrations in local development, step by step

Prisma has three commands you will use against a local database, and each one has a different job. Mixing them up is the usual source of drift.

Use prisma migrate dev on your machine to create a migration from a schema change and apply it. Use prisma migrate deploy to apply the migrations that already exist, which is what a container or CI should run. Use prisma migrate reset to drop the local database and replay everything from scratch.

The three commands

CommandWhat it doesWhere to run it
prisma migrate dev --name add_ordersDiffs your schema against the migration history, writes a new SQL file under prisma/migrations, applies it, regenerates the clientYour terminal, local database only
prisma migrate deployApplies pending migration files in order, never creates new ones, never resetsA migrator container, CI, production
prisma migrate resetDrops the database and applies every migration againYour terminal, local database only

migrate dev also needs permission to create a temporary shadow database, which a local superuser has and a managed production user usually does not. That is the practical reason it is a local command. Commit the generated prisma/migrations folder: it is the history other developers and CI replay.

Prisma and the connection string

Prisma reads the URL from your config. In a recent scaffold that is prisma.config.ts with datasource.url set from process.env.DATABASE_URL. A Prisma URL often ends with ?schema=public, which is a Prisma-specific parameter. Other tools such as psql reject it, so strip it when you use the same URL elsewhere.

The Flisk way

Flisk scaffolds the API and a migrator together:

flisk resource orders-api --type backend --stack shop --feature prisma --yes

Then install the dependencies in the new service folder with your package manager.

Both folders get a prisma/schema.prisma with a postgresql datasource and a prisma.config.ts. The schema has no models yet. The migrator's start script is prisma migrate deploy, and the API lists the migrator in dependsOn, so migrations apply before the API starts. The general pattern is in database migrations in local dev.

A good daily loop looks like this:

  1. Start the stack with flisk up shop so Postgres is running.
  2. Edit schema.prisma, adding a model.
  3. From the host, create the migration against the shared Postgres. The database is published on 127.0.0.1:15432; the user, database name and password come from your project (see connecting from your machine): 
    DATABASE_URL="postgresql://USER:PASSWORD@127.0.0.1:15432/DBNAME" \
  bunx prisma migrate dev --name add_orders
  4. Commit the new folder under prisma/migrations.
  5. Restart the migrator resource with flisk restart orders-api-migrator. It runs migrate deploy inside the container, which finds the migration you just committed.

The migrator can only apply migration files it can see, so make sure prisma/migrations exists in the migrator's folder. The scaffold creates a schema in both the API and the migrator folder. Choose one to edit and keep the other identical.

Why the shadow database matters

When migrate dev runs, Prisma creates a temporary database, replays every migration into it, and compares the result with your schema file. That is how it knows exactly what SQL to write, and how it detects that someone edited an old migration. It also means the database user needs the right to create databases. The local superuser has it. If you point migrate dev at a restricted user, you will see a permission error that has nothing to do with your schema.

Reset, seed and status

  • prisma migrate status tells you which migrations the database has applied and which are pending. Run it first when something looks off.
  • prisma migrate reset asks for confirmation, drops the database and replays all migrations. Prisma 7 does not run the seed automatically, so run prisma db seed as a separate step. See seed a local database.
  • prisma db push syncs the schema without writing a migration file. It is fine for a prototype and a mistake once other people share the schema, because there is no history to replay.

Pitfalls

  • Drift. If you edit the database by hand, migrate dev offers to reset it. On a local database that is acceptable. Never say yes against a shared one.
  • Editing an applied migration. Prisma stores a checksum. Changing a file after it was applied makes migrate dev report drift and migrate deploy fail. Add a new migration instead.
  • Generated client out of date. After pulling someone else's migration, run prisma generate, or TypeScript will not know the new fields.
  • Wrong host in the URL. Inside a container the database is not on localhost. Use the DATABASE_URL that Flisk passes to the container, and use 127.0.0.1 with the published port only from your own terminal.

If you use Drizzle instead, the model is a little different: read Drizzle migrations locally. If the migrator will not start, read service will not start. To start over cleanly, see how to reset a local database.

Questions people ask

What is the difference between prisma migrate dev and deploy?

migrate dev creates new migration files from schema changes and applies them, and is for local use. migrate deploy only applies existing migration files and is safe for containers, CI and production.

Should I commit the prisma/migrations folder?

Yes. It is the history that teammates, CI and production replay. Never edit a migration after it has been applied; add a new one.

Does Flisk run prisma migrate deploy for me?

The Prisma scaffold creates a migrator resource whose start script is prisma migrate deploy, and the API depends on it. Creating new migration files is still done by you with prisma migrate dev.
