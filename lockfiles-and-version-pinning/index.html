Lockfiles and Version Pinning: Ranges, Pins and npm ci

Decide when to use version ranges, exact pins and lockfiles, why CI should install from the lockfile, and what an updater bot needs from you.

Commit your lockfile, install from it in CI with npm ci (or your package manager's equivalent), and let a bot change it through pull requests. The lockfile records exact versions so builds are repeatable. Ranges in the manifest say what you accept, and the lockfile says what you got.

Ranges, pins and lockfiles

A range such as ^4.17.0 accepts compatible newer versions. An exact version such as 4.17.21 accepts only that one. A lockfile (package-lock.json, pnpm-lock.yaml, yarn.lock, poetry.lock, go.sum and others) pins the full resolved tree, including transitive dependencies. Without a committed lockfile, two installs a week apart can produce different code from the same commit, which is a classic source of CI failures with no related change.

Applications and libraries differ

For an application, commit the lockfile and install from it. You control what runs. For a library, commit the lockfile for your own CI, but keep the manifest ranges wide enough that your users can resolve a shared version with other packages. Tight pins in a library cause duplicate copies and conflicts for the people who depend on you. Test the library against the lowest and the newest versions you claim to support if you can.

Install from the lockfile in CI

npm ci          # npm
pnpm install --frozen-lockfile
yarn install --immutable
pip install -r requirements.txt   # with pinned versions
go build -mod=readonly ./...

npm ci deletes node_modules and installs exactly from the lockfile, and it fails when the lockfile and package.json disagree. That failure is useful: it catches a manifest edit without a lockfile update. Use the frozen variant of your tool for the same effect.

Pin what floats outside the manifest

Not everything is in a lockfile. Pin the language version (a .nvmrc, engines or a toolchain file), global CLI tools you install in CI, container base image tags (ideally by digest for important images) and GitHub Actions (by commit SHA for sensitive jobs). Each unpinned item can change without a commit. Pinning does not remove updates, it moves them into pull requests where CI can judge them, see keeping Actions up to date.

Reproducible builds beyond the lockfile

For stricter reproducibility, build in a container with a pinned base image digest, cache the downloaded packages and record the versions in the build output. When a bug report says 'it broke on Tuesday', the recorded versions answer what changed. Apply the same idea to Python with a hash-pinned requirements file, and to Go with the checked-in go.sum. Check your package manager docs for the exact commands.

Lockfile merge conflicts and drift

When two branches both change the lockfile, do not hand-merge it. Resolve the manifest, then regenerate the lockfile with the package manager and commit the result. Add a CI check that fails when running the install changes the lockfile:

npm install --package-lock-only
git diff --exit-code package-lock.json

The choice of a bot to produce these changes is covered in Dependabot vs Renovate.

Questions people ask

Should a library commit its lockfile?

Yes, for reproducible CI, but the lockfile is not shipped to users. Keep manifest ranges reasonably wide so consumers can resolve shared dependencies.

What is the difference between npm install and npm ci?

npm install can update the lockfile. npm ci installs exactly what the lockfile says and fails if it does not match the manifest, which is what CI needs.
