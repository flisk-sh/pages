How to stop and clean up a local stack and free disk space

Stopping a stack and cleaning it up are two different jobs. One is cheap and safe. The other deletes data.

To stop a local stack, run one stop command from the project folder. To clean up, decide what to delete: the stopped containers, the network, the images, the volumes that hold your database data, or the build cache. Stopping is safe and repeatable. Anything that touches volumes loses data, so look at what a command will do before you run it.

What a stack leaves behind

A stack of local processes leaves little: when the processes stop, they are gone. A container stack leaves more:

  • Containers, running or stopped.
  • Networks, one per project. Docker has a limited pool of address ranges, so many unused networks eventually cause errors.
  • Images, with a tag for every build.
  • Volumes, which hold database data.
  • Build cache, shared by every project on the machine, which grows quickly.

The plain approach is docker compose down, which removes containers and networks, and docker compose down -v, which also removes the volumes. For the rest you use docker image prune and docker builder prune, which act on the whole machine, not on one project.

The Flisk way: stop, then choose

Preview first:

flisk down --dry-run

Then stop. flisk down stops every running service of the project, whether they are local processes or Docker and Tilt. By default it also removes the project's Docker networks that no container uses, so Docker does not run out of address pools. To keep them, pass --no-prune-networks. Your data is not touched. After stopping a container project, it prints how much disk its images and the shared build cache still hold, and the command that frees it.

Then go further only if you need to:

flisk down --prune-cache           # also prune build cache older than 24h
flisk down --prune-cache --cache-until 7d
flisk down --purge                 # also delete volumes, networks and images of this project

Know what each does:

  • --prune-cache acts on the Docker build cache, which is shared across all projects. With the default of 24 hours, recent layers stay warm, so the next build is still fast.
  • --purge deletes this project's volumes, which means your local database is gone. The next flisk up starts from an empty database and runs migrations again. Use it when you want a clean slate, not as a routine.

Run flisk down --project <path> to stop a project in another folder, and --json for output a script can read.

Projects whose folder is gone

If you delete a project folder without stopping it, the Docker resources stay. List them, then remove them:

flisk projects --stale
flisk projects --stale --prune

The second command deletes the containers, volumes, networks and images those projects left. Read the list before you prune, because volumes hold data.

Watch the disk before it fills

flisk doctor warns when the Docker build cache is over 10 GB, and points to flisk down --prune-cache. A good habit: stop with --prune-cache at the end of the week, and purge only the projects you are done with. When the disk is full, Docker itself can fail in odd ways, and fixing it takes longer than avoiding it. Docker disk full covers the recovery.

Pitfalls

  • Purging by reflex. You lose seed data and test records. Keep a seed step so a purge is cheap.
  • Stopping the wrong project. With several running, pass --project so the command targets the folder you mean.
  • Expecting the cache to be per project. It is shared, so pruning it slows other projects' next build.

A routine that works: at the end of the day, run flisk down. At the end of the week, run flisk down --prune-cache. When you finish a feature branch that left odd database state, run flisk down --purge before you switch. Before any of these, flisk down --dry-run shows what would be stopped. If you only have local processes, there is nothing to prune, so a plain flisk down is the whole routine. The same command stops a stack started with flisk up --wait, and --json gives a result your script can check.

To keep data between runs on purpose, read keep volumes between runs. To run less in the first place, see start only the services you need.

Questions people ask

Does flisk down delete my database data?

No. flisk down stops services and removes the unused project networks. Database volumes stay until you pass --purge.

How do I free the most disk space?

The Docker build cache is usually the biggest part and is shared across projects. flisk down --prune-cache removes cache older than 24 hours by default. Images and volumes of one project go with --purge.

What about projects whose folder I deleted?

Their containers, volumes and images may still be in Docker. flisk projects --stale lists them, and adding --prune deletes what they left.
