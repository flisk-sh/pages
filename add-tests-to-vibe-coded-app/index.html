Vibe coding without the mess

How to add tests to a vibe-coded app without slowing down

Tests are what let you keep prompting without breaking old features. Start with a handful of checks on the behaviour that matters, and let the agent write them from your spec.

Write tests for the behaviour your spec promises, not for every function: sign in works, data is saved, one user cannot see another's data. Ask the agent to write them from the spec, run them after every prompt, and treat a failing test as the signal to stop and look.

Why tests matter more with an agent

When you type code yourself, you remember what you changed. When an agent edits six files per prompt, you do not. A test suite is the memory of what used to work. Without one, each prompt is a coin flip on old features.

Tests also change how you prompt. Instead of describing a bug in words, you can say "this test fails, make it pass without changing the test". That is a precise, checkable instruction, and agents are good at it because the failing output tells them exactly where to look.

Start with the "done means" list

If you wrote a spec (see the template), each "done means" line is a test. Ask: "Read SPEC.md. For each line under Done means, write one automated test. Do not change application code."

The last sentence matters. If the agent can edit both the code and the test, it may make the test pass by weakening it.

A small example with pytest

def test_checkin_twice_same_day_creates_one_row(client, user):
    habit = client.post("/habits", json={"name": "read"}, user=user).json()
    client.post(f"/habits/{habit['id']}/checkin", user=user)
    client.post(f"/habits/{habit['id']}/checkin", user=user)
    rows = client.get(f"/habits/{habit['id']}/checkins", user=user).json()
    assert len(rows) == 1

def test_user_cannot_read_other_users_habits(client, alice, bob):
    habit = client.post("/habits", json={"name": "read"}, user=alice).json()
    resp = client.get(f"/habits/{habit['id']}", user=bob)
    assert resp.status_code in (403, 404)

The fixtures (client, user) depend on your framework. Ask the agent to write them once and reuse them.

Notice what these tests do not check: how the code is written. They check outcomes. That is deliberate, so you can let the agent rewrite the insides freely while the tests keep the behaviour fixed.

Run them every time

Put the command in the spec and in a short instruction file the agent reads, for example "after every change, run pytest -q and fix failures before reporting done". A one-line check in a pre-commit hook or CI also works. See CI for multi-service apps.

Pitfalls

  • Tests that assert nothing. Open one and check it has a real assertion.
  • Mocking everything. A test that mocks the database proves little about the database. Prefer a real SQLite or test database.
  • Deleting a failing test. Check the diff for removed test files before you commit.

Tests find what you thought of. For what you did not, read the risky code yourself (when to read it).

Questions people ask

How many tests are enough to start?

Five to ten covering your main flow and your access rules is a good start. Add one test for every bug you fix.

Can the AI grade its own tests?

It can write them, but a human should confirm they assert something real. Run the suite against deliberately broken code once to see that it fails.
