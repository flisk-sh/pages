How to Split Slow GitHub Actions Jobs and Use needs and Artifacts

Break one long job into parallel jobs, share build output with artifacts, and order cheap checks first so failures stop the pipeline early.

Split a slow job when its steps do not depend on each other: lint, unit tests and a type check can run in parallel on separate runners. Use needs to order the ones that do depend on each other, and artifacts to pass files between them.

Parallel by default

Jobs in one workflow run in parallel unless you add needs. So one 15-minute job with three independent parts can become three 5-minute jobs.

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run lint
  types:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npx tsc --noEmit
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

Order with needs

Put slow, expensive jobs after cheap ones. If lint fails in 30 seconds, do not start a 20-minute end-to-end job.

  e2e:
    needs: [lint, types, unit]
    runs-on: ubuntu-latest
    steps:
      - run: echo run slow tests

The trade-off: needs adds waiting time on green runs. Use it for jobs that are costly or that need the output of another job.

Build once, test many times

If several jobs need the same build output, build once and share it as an artifact.

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist

Uploads and downloads take time. If the build is quick, rebuilding in each job can be faster than moving files around.

Avoid over-splitting

Every job pays for startup, checkout and setup, often 30 to 90 seconds. Ten tiny jobs can cost more than one medium job. A rule: split when each part runs longer than a couple of minutes, or when you want separate pass and fail signals. Check the real run in the Actions UI, where each job shows its setup time separately.

Fail fast on cheap checks

Order jobs so that the cheapest signal arrives first. A typical chain is lint and type check, then unit tests, then integration tests, then end-to-end tests. Only the first stage needs to be fast to give early feedback. If the earlier stages pass most of the time, needs adds only a small delay. If they fail often, you save a lot of runner time by not starting the later ones. Review the order every few months, since the cost of each stage changes as the code grows.

Reuse with workflows

When several jobs repeat the same setup, move it into a reusable workflow or a composite action so you maintain it once. Then watch the numbers over time with the steps in measuring speedups. For multiple repositories, see CI for multi-service apps.

Questions people ask

Do parallel jobs share files?

No. Each job runs on a fresh machine. Pass files between jobs with artifacts or caches.

How many jobs can run at once?

The limit depends on your plan. Check GitHub's documentation for the current concurrency limits.

Measure before you tune

See which workflows are slow before you change anything.
