GitHub Codespaces vs local development: how to decide

A remote workspace moves the machine, not the problem. Here is what changes and what stays the same.

Choose Codespaces or a similar cloud workspace when onboarding speed, a bigger machine or keeping code off laptops matters more than offline work and zero hourly cost. Stay local when your laptop is strong enough, you work offline, or you already have a one-command setup that new people finish in minutes. Either way, you still have to decide how the services of your app start together.

What a cloud workspace gives you

GitHub Codespaces runs a development container on a managed virtual machine and connects your browser or VS Code to it. The environment is defined by the repo's dev container configuration, so everyone gets the same tools. Practical advantages:

  • Fast onboarding. A new person opens the repo and gets a working environment, with no local installs.
  • Bigger machines. You can pick a larger VM for a heavy build or a stack that does not fit in 16 GB of laptop RAM. Available sizes and limits are on GitHub's pricing and plan pages, so check the current ones.
  • Prebuilds. The repo can prebuild the environment so opening it is quick.
  • Code stays remote. Useful for contractors and strict security policies.
  • Port forwarding. Forwarded ports can be shared with a teammate for a quick look.

What local still does better

  • No meter. Codespaces bills by compute time and storage after the included monthly quota for your plan. A laptop you already own has no hourly cost.
  • Offline and latency. Typing in a remote editor over a bad connection is painful, and offline is impossible.
  • Your own tools. Your editor setup, shell and GPU access are simply there.
  • Hardware access. Devices, local GPUs and special network setups are hard or impossible to reach from a cloud VM.

The part that does not change: starting the stack

A workspace gives you a shell on a machine. It does not start your API, your database and your worker. In both worlds you need a repeatable way to do that. In a Codespace that usually means one of these:

  1. A Compose file, started by a postStartCommand or by hand. The dev container can use Compose directly, as described in Dev Containers vs Docker Compose.
  2. A script or task runner. See Make vs just vs Task.
  3. A stack tool such as Flisk, run inside the workspace the same way you run it on a laptop.

If you use Flisk, flisk doctor detects Codespaces and reports it as the host kind (visible in flisk doctor --json as data.host.kind), along with whether a container runtime is reachable. Services that each have a command in service.json run as plain processes, so they do not need Docker in the workspace. Services on the container path do need a container runtime, which for a dev container means adding a Docker feature to its configuration.

A decision rule

If this is trueLean toward
Onboarding takes days and laptops vary a lotCloud workspace
The stack needs more RAM than developers' laptops haveCloud workspace
Developers often work offline or on a bad connectionLocal
Budget for hourly compute is tightLocal
You want bothDefine everything in a dev container and one start command, so either works

The last row is the safest bet. If the setup is one dev container plus one command, you are not locked to either side.

Pitfalls

  • Idle cost. A running workspace bills until it stops. Set an idle timeout and delete old ones.
  • Secrets. Use the platform's secret store rather than committing .env. See env var names, not values, in config.
  • URLs. Services do not live at localhost in your browser. Forwarded ports get their own URLs, so absolute localhost links in config can break callbacks.
  • Cold starts. A stopped workspace still needs to restart, and your stack inside it needs starting again.

To keep the choice open, next read how to choose a local dev tool.

Questions people ask

Is GitHub Codespaces free?

Personal accounts get an included monthly quota of compute and storage, then usage is billed. Check GitHub's current plan and pricing pages for the numbers.

Can I run docker compose in Codespaces?

Yes, if the dev container has Docker available, for example through a Docker feature in devcontainer.json.

Does Flisk work in Codespaces?

Flisk can run inside a workspace and flisk doctor detects Codespaces. Services run as plain processes, or as containers if a container runtime is reachable.
