Test the real stack, then hand it off

How to run a multi-service stack in GitHub Actions

Two jobs: a cheap one that catches config drift on every pull request, and a heavier one that actually starts your services.

To run a multi-service stack in GitHub Actions, check out the repository, install the tools the stack needs, start it in the background and wait for every health check, run your tests, upload the logs when something fails, and always stop the stack at the end. Splitting this into a cheap verification job and a heavier boot job gives you fast feedback on most mistakes and keeps runner minutes down.

What a CI stack is for

CI is a throwaway machine. You are not deploying anything, you are proving that a clean checkout can start and pass its tests. Everything that works only because of something on your laptop (a populated .env, a cached image, a running database) will fail here, which is the point. Plain Docker Compose works well for this: docker compose up -d --wait, run the tests, docker compose down -v.

If your stack is managed with Flisk, the same pattern applies with flisk commands. Flisk's own CI runs flisk up on hosted runners, and its documentation includes a copy-paste workflow adapted from those files. The version below is a shortened one.

A workflow

name: stack
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: stack-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

env:
  FLISK_VERSION: "1.4.57"   # use the version your team runs

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
        with: { persist-credentials: false }
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - name: Install Tilt
        run: |
          curl -fsSL -o tilt.tar.gz https://github.com/tilt-dev/tilt/releases/download/v0.37.8/tilt.0.37.8.linux.x86_64.tar.gz
          echo "e39513f958705d30524d55f68b1d46fbef2b46a0da568efd00e6383dee6be44f  tilt.tar.gz" | sha256sum -c -
          sudo tar -xzf tilt.tar.gz -C /usr/local/bin tilt
      - name: Install flisk
        run: npm install --global "@flisk-sh/flisk@${FLISK_VERSION}"
      # A fresh clone has no git-ignored .env and no generated folders
      - run: flisk project --yes
      - run: flisk doctor --no-ping
      - run: flisk config verify

  boot:
    needs: verify
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with: { persist-credentials: false }
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - name: Install Tilt
        run: |
          curl -fsSL -o tilt.tar.gz https://github.com/tilt-dev/tilt/releases/download/v0.37.8/tilt.0.37.8.linux.x86_64.tar.gz
          echo "e39513f958705d30524d55f68b1d46fbef2b46a0da568efd00e6383dee6be44f  tilt.tar.gz" | sha256sum -c -
          sudo tar -xzf tilt.tar.gz -C /usr/local/bin tilt
      - name: Install flisk
        run: npm install --global "@flisk-sh/flisk@${FLISK_VERSION}"
      - run: flisk project --yes
      - name: Start and wait for health
        run: flisk up --wait --wait-timeout 1200
      - name: Run the tests
        run: npm test --prefix tests/integration
      - name: Collect diagnostics
        if: always()
        run: |
          mkdir -p "$RUNNER_TEMP/logs"
          docker ps -a --format 'table {{.Names}}\t{{.Status}}' > "$RUNNER_TEMP/logs/docker-ps.txt" 2>&1 || true
          flisk status > "$RUNNER_TEMP/logs/status.txt" 2>&1 || true
          flisk logs --tail 300 > "$RUNNER_TEMP/logs/flisk.txt" 2>&1 || true
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: stack-logs
          path: ${{ runner.temp }}/logs/
          retention-days: 7
      - name: Stop the stack
        if: always()
        run: flisk down || true

Why each part is there

  • flisk project --yes. A fresh clone lacks the git-ignored .env (with the generated database password and JWT secret) and the generated .flisk/ output. Without this step, flisk config verify reports them as missing. It writes files only and does not need Docker.
  • flisk config verify. Exits non-zero when a generated file differs from what .flisk/project.json and the service.json files produce. It catches the classic "I edited the manifest and forgot to regenerate" mistake in seconds. More on that in check config drift in CI.
  • flisk up --wait. Starts the stack in the background and returns when every service is healthy, or exits with an error on failure or after --wait-timeout seconds (default 1800).
  • Diagnostics with if: always(). When a health check fails, "timed out" tells you nothing. Container states and service logs do.
  • The stop step. On a hosted runner the machine disappears anyway, but a stop step keeps the workflow valid on self-hosted runners, where a leftover stack would break the next job.
  • concurrency. Cancels the older run for the same pull request so you are not paying for results nobody will read.

Pitfalls

  • Port 5432 is taken. The Ubuntu runner image can have Postgres installed and listening. If your stack publishes 5432, stop and mask the runner's Postgres service first, or publish the stack's database on another port.
  • Check the workflow on a throwaway branch. Flisk's documentation says plainly that its example boot job's exact script was not run on GitHub when it was written. Treat any copied workflow, including this one, as a starting point and run it once before you rely on it. The --wait flag in particular replaces a longer polling script in older examples.
  • Pin versions. A moving latest in CI is how a green build turns red with no code change. Pin the CLI version, and raise minFliskVersion in .flisk/project.json when you raise it.
  • Cost. The boot job builds images on every run. Run it on pull requests that touch services, or nightly, if minutes matter.
  • Secrets. Use repository secrets for real credentials, and test values for everything else. Never print .env.

When not to boot the stack in CI

If your tests are unit tests with no network, a real stack adds minutes and gains nothing. Boot it when the thing you are testing is the wiring: services talking to each other, migrations, and browser journeys.

Questions people ask

Do GitHub-hosted runners have Docker?

Yes, ubuntu-latest runners include Docker and the Compose plugin. They do not include Tilt, which Flisk's container stacks use, so install it in the workflow. The runner image can also have its own Postgres listening on port 5432, which clashes with a stack that publishes that port.

Why split the workflow into a verify job and a boot job?

Verification needs no containers and finishes quickly, so it can run on every push and fail early on config drift. Booting the stack is slow and uses more minutes, so it runs only when the cheap job passes.

Is it safe to publish from the CI stack?

A CI stack is a throwaway test environment. It is not a deployment path. Build and publish images in a separate release workflow.
