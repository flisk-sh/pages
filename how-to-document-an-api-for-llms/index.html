How to document an API so LLMs can use it

Give a model what it needs to call your API correctly: an OpenAPI file, one real request and response per endpoint, error shapes and stated limits.

Publish a machine-readable spec such as an OpenAPI file, and back it with one complete, working example per endpoint. A model that sees real requests and responses calls an API far more reliably than one that reads descriptive prose.

Start with an OpenAPI file

An OpenAPI document is structured, widely supported and easy for tools to turn into client code or tool definitions. Keep it in the repository, version it with the code and link to it from the README. Write real descriptions on each operation and each parameter. An empty description gives a model nothing to work with.

paths:
  /orders/{id}:
    get:
      summary: Get one order by id
      description: Returns 404 if the order does not exist.
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }

One complete example per endpoint

Show the full request including headers, and the full response. Use a curl line that a reader can run.

curl -sS https://api.example.com/orders/ord_123 \
  -H "Authorization: Bearer $API_KEY"
{
  "id": "ord_123",
  "status": "paid",
  "total_cents": 4200
}

Use realistic values and say what units they are in. "total_cents" with an integer is clearer than "total" with 42.00.

Document errors as carefully as success

Agents spend much of their time recovering from errors. For each endpoint list the status codes it can return, the error body shape and what to do next.

StatusMeaningWhat to do
401Missing or bad keyCheck the Authorization header
404No such orderDo not retry
429Rate limitedWait for the Retry-After seconds, then retry

State limits and rules in text

  • Rate limits, in requests per time window, if you have them.
  • Pagination: how to ask for the next page and when to stop.
  • Idempotency: which calls are safe to repeat.
  • Required order of calls, for example create before confirm.

These are the facts a model otherwise guesses. Put them next to the endpoint they affect, not on a separate page.

Naming and consistency

Models generalise from patterns. If one endpoint uses customer_id and another uses customerId, expect mistakes. Pick one naming style for fields, one date format (ISO 8601 is a safe default) and one way to express money, and use them everywhere.

Say plainly when a field can be null or missing. "Optional" and "nullable" are different, and models confuse them when the docs do not.

  • List allowed values for every enum field.
  • Give the maximum length of strings that have one.
  • Mark deprecated fields and name their replacement.

Serve it in a model-friendly form

Publish the docs as plain Markdown pages as well as HTML, and list them in an llms.txt file. If you expose the API to agents through tools, the same descriptions become the tool descriptions, so write them once and well. See How to write docs for an MCP server for that case.

Questions people ask

Is OpenAPI enough on its own?

It is a strong base, but add real examples and error guidance. Descriptions and samples are what help a model choose correct values.

Should I include my API keys in examples?

Never. Use a placeholder such as an environment variable and explain how to get a key.
