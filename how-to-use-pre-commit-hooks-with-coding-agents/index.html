How to Use Pre-Commit Hooks With Coding Agents

Hooks catch formatting, secrets and bad commits before they leave the agent's machine. Here is a setup that does not slow everyone down.

Use pre-commit hooks for fast, deterministic checks like formatting, secret scanning and file-size limits, and leave slow tests to CI. When an agent commits, a failing hook gives it immediate feedback it can act on.

Why hooks suit agents

An agent that commits gets the hook output right away and can fix the problem in the same session. That is cheaper than a CI failure ten minutes later. Hooks also keep the diff clean: formatted code means reviewers see only the real change.

Set up the pre-commit framework

The pre-commit tool keeps hooks in a versioned config file, so everyone gets the same ones.

pip install pre-commit
pre-commit install
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: end-of-file-fixer
      - id: check-added-large-files
      - id: check-merge-conflict

Pin rev to a release you have checked. Husky and lint-staged are common alternatives in JavaScript projects.

Keep hooks fast

A hook that takes 40 seconds teaches people, and agents, to bypass it. Run only on staged files, and keep the total under about ten seconds. Move type checking of the whole project and test runs to CI or to the explicit check command described in one fast check command.

Do not trust hooks alone

Hooks live on the developer's machine and can be skipped with --no-verify. Run the same checks in CI so skipping them locally changes nothing. Add a line to AGENTS.md saying that bypassing hooks is not allowed, and consider a CI check that fails when the formatting step would change files.

Agent tool hooks are a different thing

Some agent tools have their own hooks that run before or after a tool call. These are configured in the tool's settings and can block risky commands. They complement git hooks and do not replace them. Check your tool's documentation for the events it supports.

A practical starter set

A good first set is small and fast: trailing whitespace and end-of-file fixes, a large-file check, a merge-conflict marker check, a secret scanner and your formatter in check mode. Add the linter for staged files only, using a tool such as lint-staged so it does not scan the whole project.

npx husky init
echo 'npx lint-staged' > .husky/pre-commit

Configure lint-staged in package.json to map file globs to commands, for example formatting TypeScript files and running ESLint on them. In Python projects the same role is played by the pre-commit framework shown above with ruff or black.

When a hook fails, make sure the message says how to fix it. An agent reads the output and acts on it, so "run npm run fix" is far better than a bare error code. Review the hook list yearly and remove anything nobody would miss.

Questions people ask

Can an agent skip hooks?

Yes, with git flags like --no-verify, unless a rule or tool setting blocks it. That is why CI must repeat the checks.

What belongs in a hook versus CI?

Fast checks on staged files belong in hooks. Slow suites, builds and anything needing services belong in CI.
