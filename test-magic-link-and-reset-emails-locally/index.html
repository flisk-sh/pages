Authentication in local development

How to test magic-link and password-reset emails locally

Passwordless login and reset flows send mail. Catch it on your own machine, where nothing reaches a real person.

Run Mailpit, a mail catcher. It listens for SMTP on port 1025 and shows every message in a web inbox on port 8025. Point your app's SMTP host at localhost:1025, trigger a sign-in link or a password reset, open http://localhost:8025, and click the link in the message. Nothing leaves your machine, so you can send to any address, real-looking or not.

Start Mailpit

Plain Docker, with the version tag pinned so every teammate gets the same behaviour:

docker run --rm \
  -p 127.0.0.1:8025:8025 \
  -p 127.0.0.1:1025:1025 \
  axllent/mailpit:v1.33.1

Port 8025 is the web inbox, 1025 is SMTP. Binding both to 127.0.0.1 keeps the catcher reachable from your computer only. With --rm and no volume, removing the container empties the inbox, which is usually what you want between test runs.

Point the app at it

Most mail libraries read a host, a port, and optional credentials. For a catcher you set the first two, turn TLS off, and leave the username and password empty. Names differ per framework; these are common ones:

SMTP_HOST=localhost
SMTP_PORT=1025
SMTP_SECURE=false
MAIL_FROM="Local App <no-reply@example.test>"

Use an address on a domain you do not own, such as example.test (the .test top-level domain is reserved and never resolves). Do not use a real company domain as the sender in tests: that is how a misconfigured setup ends up emailing real people. If sending fails with a TLS or STARTTLS error, the library is trying to upgrade a connection that this server accepts in plain text; set its secure or require-TLS option to false.

Run it with Flisk

Give Mailpit a service.json with an image and no command. The inbox is the main port; the SMTP listener goes in extraPorts, which publishes it on 127.0.0.1 too:

{
  "schemaVersion": 1,
  "appName": "mail",
  "appType": "bring-your-own",
  "stack": "auth",
  "image": "axllent/mailpit:v1.33.1",
  "port": 8025,
  "extraPorts": [{ "port": 1025 }]
}

Then make the app depend on it and hand it the SMTP address:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "backend",
  "stack": "auth",
  "command": "node server.js",
  "port": 4000,
  "dependsOn": ["mail"],
  "env": {
    "SMTP_HOST": "localhost",
    "SMTP_PORT": "1025"
  }
}

Run flisk config verify to check the files. flisk up prints the inbox address, and flisk status shows it next to the service. Docker is needed for the Mailpit container only.

What to check in the message

  • The link host. The link must point at http://localhost:3000/... or whatever your dev URL is, not the production site. If it holds the wrong host, your app builds it from a base URL setting that you forgot to override locally.
  • One use only. Click the link, then click it again. A magic link that signs you in twice is a bug.
  • Expiry. Wait past the token lifetime, or shorten it in a test, and confirm the old link is rejected with a clear page.
  • The cookie. After the click, the session cookie must stick. If you land back on the login page, see secure cookies on localhost.
  • Unknown addresses. A reset request for an address with no account should show the same page as one for a real account, so the form does not reveal who is registered.

If no mail shows up

  • Wrong host from a container. A containerised app cannot reach Mailpit at localhost. Use the address that container network provides, or run the app as a local process.
  • Port taken. If another catcher or a system mail daemon already holds 1025, the container fails to start. Change the published host port and update SMTP_PORT to match.
  • Errors swallowed. Many apps send mail in a background job and only log a failure. Read the app's log, with flisk logs --service web if Flisk runs it, before blaming the catcher.
  • Link rewriting. Some mail libraries wrap links for click tracking. Turn that off in development so the link in the inbox is the real one.

Using it in automated tests

Mailpit has an HTTP API next to the web inbox, so a test can fetch the latest message and extract the link instead of a person reading it. Check the API documentation of the version you pin for the exact paths. Clear the inbox at the start of each test so an old message cannot satisfy the next one.

Questions people ask

Which port does Mailpit use for SMTP?

Port 1025 for SMTP and 8025 for the web inbox and its API. These are its defaults.

Can I send to real addresses while testing with Mailpit?

By default Mailpit only catches messages and does not relay them, so nothing reaches the recipient. Still use reserved domains like example.test in test data.

Why do my magic links point at the wrong host?

The app builds the link from a base URL setting. Override it locally with your dev URL, for example http://localhost:3000.
