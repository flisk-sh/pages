Monorepos with several services

Monorepo or separate repos for backend services?

The honest answer depends on team boundaries more than on tools. Here is what each choice costs, including for local development.

Choose a monorepo when the services change together and one team owns most of them. Choose separate repos when teams ship independently and you want hard ownership and access boundaries. Neither is faster by itself: a monorepo moves the cost into tooling and CI, separate repos move it into versioning and local setup.

What a monorepo gives you

  • Atomic changes. One pull request can change an API and every caller. Nobody has to coordinate three merges and a release order.
  • One place to search and refactor. Renaming a shared type is a single change.
  • Shared tooling. One lint config, one TypeScript base config, one lockfile.
  • Easy local setup. One clone, one install, all code present.

What it costs

  • CI has to be selective. Running every test on every change gets slow. You need affected-only builds and caching. See running only the changed services.
  • Access is coarse. Anyone who can read the repo can read every service, unless you add path-based review rules such as CODEOWNERS.
  • Tooling is mandatory at scale. Workspaces, a task runner and a clear folder layout stop being optional.
  • Coupling creeps in. It is easy to import across service boundaries because the code is right there. Enforce boundaries with lint rules.

What separate repos give you, and cost

One repo per service gives a clean history, per-repo permissions, independent release cadence, and CI that only knows about one service. The price is paid elsewhere: a breaking API change needs coordinated pull requests and a deploy order, shared code must be published as a versioned package, and a new developer has to clone several repos and learn how to run them together.

A quick rule

SituationLean toward
One team, services released togetherMonorepo
Several teams, independent releasesSeparate repos
Frontend and its own backend, same teamMonorepo
Strict access control between servicesSeparate repos
Heavy shared libraries changing oftenMonorepo

You can also change your mind. Moving from many repos to one is mostly a history-preserving import. Splitting one out later is a path filter. Do not let this decision block building.

Running it locally with Flisk

Flisk's layout guide describes three ways to arrange a project when code spans repositories. One Flisk project is one repository tree: Flisk finds services by walking the project folder for service.json files.

  • A platform repo. One repo holds .flisk/project.json and a service.json for every service. Services whose code lives elsewhere are wrapped as bring-your-own resources, either from a registry image or from a source checkout via buildContext.
  • One project per service repo. Each repo is its own Flisk project with its own project name. Give each a different name; projects with the same name share network and database names. Services in different projects cannot reach each other by name.
  • A hub that clones the others. List repositories under repos in .flisk/project.json, each with a url, dir and branch. flisk up clones the missing ones before it discovers services, and flisk repos clone does it on demand. It never overwrites, pulls or checks out an existing directory.
{
  "repos": [
    {
      "url": "git@github.com:acme/orders-api.git",
      "dir": "services/shop/orders-api",
      "branch": "main"
    }
  ]
}

That is a fragment to merge into your existing .flisk/project.json. One thing does not work: pointing discovery.paths at service.json files in a sibling repo outside the project root. The CLI and Tilt disagree about such a service, so keep every service.json inside the project tree. The layout guide notes that it was tested by generating files and reading Tilt's resource list; a full flisk up could not be completed there, so treat these layouts as designs to try, not as proven workflows.

Pitfalls

  • Choosing separate repos but sharing code by copy and paste is the worst of both.
  • Choosing a monorepo without CI filters means every pull request runs everything.
  • Either way, write down how to run the whole system locally. See onboarding a developer on day one.

If you stay in one repo, the pnpm workspace article is the next step.

Questions people ask

Is a monorepo better for microservices?

Not by default. It helps when services change together and share code. Separate repos fit independent teams and release cycles. Pick by team boundaries.

Can Flisk run services from several repositories?

Yes, through a hub project that lists repos in .flisk/project.json and clones them, or a platform repo with bring-your-own services. A service.json outside the project root is not supported.

Does a monorepo make CI slower?

It can, if every change runs every test. Affected-only builds and caching keep it manageable.
