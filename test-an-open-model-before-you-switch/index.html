Open models and self-hosted inference

How to test an open model against your current one before switching

Build a small test set from real prompts, run both models, and compare with checks that do not depend on a model grading itself. A practical process with code.

Collect 30 to 100 real prompts, run them through both models, and score the answers with deterministic checks where you can and human review where you cannot. Switch only if the new model passes on your tasks, at a latency and cost you accept.

Build the test set

Take real inputs from your logs or your own use, with personal data removed. Cover the common cases, the hard cases and a few that should be refused. Store each as a line in a file:

{"id": "inv-01", "prompt": "Extract the total from: ...", "expect": "142.50"}
{"id": "inv-02", "prompt": "Extract the total from: ...", "expect": "89.00"}

Keep the set in version control next to your prompts. It becomes the regression suite for every future change, and it is the most valuable artifact in this whole exercise.

Run both models with the same client

If both serve an OpenAI-compatible API (how to serve one), one script covers both:

import json, time
from openai import OpenAI

models = {
  "current": (OpenAI(), "<current-model>"),
  "candidate": (OpenAI(base_url="http://localhost:11434/v1", api_key="x"), "llama3.2"),
}
rows = [json.loads(l) for l in open("cases.jsonl")]
for name, (client, model) in models.items():
    ok, secs = 0, 0.0
    for c in rows:
        t = time.time()
        out = client.chat.completions.create(
            model=model, temperature=0,
            messages=[{"role": "user", "content": c["prompt"]}],
        ).choices[0].message.content
        secs += time.time() - t
        ok += c["expect"] in out
    print(name, f"{ok}/{len(rows)} passed, {secs/len(rows):.2f}s avg")

Score without a judge model where possible

Exact match, contains, valid JSON against a schema, code that compiles and passes tests: these are cheap and repeatable. For open-ended answers, read a sample yourself. Using one model to grade another can work as a screen but has its own biases. See testing and evaluating AI agents.

When two models tie on accuracy, look at the failures. A model that fails by saying "I do not know" is safer than one that fails by inventing an answer, even if the pass rates match.

Compare more than accuracy

  • Latency at your real prompt sizes and concurrency.
  • Cost, including idle GPU time.
  • Failure modes: how often is output malformed, cut off, or off-topic?
  • Tool use and JSON if you depend on them.

Roll out safely

Send a small share of traffic to the new model first, keep the old one as a fallback, and watch the metrics (monitoring). Rerun the test set whenever you change the model, quantization or prompt, and add each production failure as a new case.

Record the results of each run in a small table with the date, model, quantization, prompt version and score. After a few runs you can see which changes helped and which only felt like they did.

Questions people ask

How many test cases do I need?

Thirty to a hundred real cases is enough to show large differences. More cases help you see smaller ones.

Why set temperature to 0?

It makes outputs as repeatable as the server allows, which helps comparisons. Some servers still vary slightly, so run important cases more than once.
