How to add a gRPC health check so a local stack waits for it

A gRPC server has no /health URL. You need another way to say 'ready', or the service that calls it will start too early and fail.

A gRPC server has no HTTP health path, so you check readiness in one of three ways: an open TCP port, the standard grpc.health.v1.Health service queried with grpc_health_probe, or a probe of your own. In a local stack, use the port check while you are starting out and the health protocol when "port open" is not the same as "ready to serve".

The standard health service

The gRPC project defines a health protocol in grpc.health.v1. A server registers a Health service with one unary method, Check, that returns SERVING or NOT_SERVING, plus a streaming Watch. Most language libraries ship an implementation. In Go:

import (
  "google.golang.org/grpc/health"
  healthpb "google.golang.org/grpc/health/grpc_health_v1"
)

hs := health.NewServer()
healthpb.RegisterHealthServer(s, hs)
// once the database connection works:
hs.SetServingStatus("", healthpb.HealthCheckResponse_SERVING)

The empty string is the whole server; you can also register a status per service name. Set NOT_SERVING at startup and flip it only after your dependencies (database, cache) answer. That is the difference between "the process is listening" and "it can handle a request".

Check it from the shell

With grpcurl:

grpcurl -plaintext -d '{"service": ""}' localhost:50051 grpc.health.v1.Health/Check

With grpc_health_probe, a small binary from the gRPC ecosystem made for exactly this, which exits 0 when the status is SERVING and non-zero otherwise:

grpc_health_probe -addr=localhost:50051

Kubernetes can call the health protocol natively through a grpc probe, and Docker Compose healthchecks usually run grpc_health_probe inside the image, which means the binary must be in the image. Locally you do not need either.

Readiness in a Flisk stack

Flisk can gate dependsOn on a TCP port or on a command, not only an HTTP path. The healthCheck field takes exactly one probe: path, port or command. For a gRPC server as a local process, a port probe:

{
  "schemaVersion": 1,
  "appName": "orders-grpc",
  "appType": "backend",
  "command": "go run ./cmd/orders",
  "port": 50051,
  "healthCheck": { "port": 50051 }
}

If you want the real protocol, make the command the probe. For a local process it runs on your host from the service folder and counts as ready when it exits 0:

"healthCheck": { "command": ["grpc_health_probe", "-addr=localhost:50051"] }

Services that list "dependsOn": ["orders-grpc"] start only after the probe passes. For a service that runs in a container (a bring-your-own image), the command runs inside the container, so the probe binary has to be in that image and the address is the container's own. With port or command Flisk gives the gateway no HTTP health path for the service. Check what you wrote with flisk config verify, and flisk status shows whether each service is ready.

How long does Flisk wait? In local-process mode it waits up to 60 seconds per service. If your server needs a slow migration first, run that migration as its own earlier step instead of making the server's start slower; see how to control service startup order.

Which probe to pick

ProbeWhat it provesUse when
TCP portThe process accepted a connectionEarly development, simple servers
grpc_health_probeThe server reports SERVINGThe server checks its own dependencies
Your own callA real method worksA cheap read-only method exists

What to test after you add it

Start the server with its database stopped and call the health method: it should answer NOT_SERVING or fail, not SERVING. Then start the database and check that it flips. The streaming Watch method lets a client see the change without polling; grpcurl can call it too and prints each status change. This takes five minutes and finds the common bug where a service reports healthy while its connection pool is empty.

You can also report status per logical service. Registering shop.v1.Orders with its own status lets a caller ask about one part of a server that hosts several. Keep the names equal to the full service name from your proto file.

Pitfalls

  • Always SERVING. A health service that returns SERVING from the first millisecond is a port check with extra steps.
  • Probe not installed. A command probe on the host needs the binary on PATH; install it before blaming the service.
  • TLS mismatch. grpc_health_probe needs TLS flags if the server uses TLS. Local servers usually do not.

Questions people ask

Does gRPC have a /health endpoint?

Not by default. The standard way is the grpc.health.v1.Health service, which you register in your server and query with a gRPC client such as grpc_health_probe or grpcurl.

Can Flisk wait for a gRPC service to be ready?

Yes. In service.json, healthCheck accepts a TCP port or a command such as grpc_health_probe, and services that depend on it start after the probe passes.

Is an open port enough to call a gRPC service ready?

Only for simple cases. An open port means the process is listening, not that its database is connected. Use the health service when that difference matters.
