Multi-agent system patterns

How to run and test a multi-agent system on your laptop

Run the agents, the queue, the database and the tools together locally, with fake models in tests and real ones when you want to see behaviour.

Run every part of the system locally with one command, and put a fake model behind the agents for tests so runs are fast, free and repeatable. Switch to a real model only for a small set of end-to-end checks.

Run the whole stack together

A multi-agent system is several processes: agents, a queue or database, tool servers. Starting them by hand in many terminals is fragile. Use one tool to start everything and show status. With Docker Compose that is docker compose up. With Flisk, each part is a service described by a service.json, and you create and start them like this:

flisk resource planner --type agent
flisk resource researcher --type agent
flisk resource tools --type mcp
flisk up
flisk status --json

flisk doctor checks your environment if something does not start. Flisk is a local development tool, not a production orchestrator. The flisk project agent-stack command scaffolds a starter with tools, a database and messaging, and the Flisk Agent Stack repo shows the result.

Use a fake model in unit tests

Make the model client an argument, so tests pass in a stub that returns canned replies.

class FakeLLM:
    def __init__(self, replies):
        self.replies = list(replies)
    async def __call__(self, prompt):
        return self.replies.pop(0)

async def test_orchestrator_runs_two_tasks():
    llm = FakeLLM(['[{"id":"1","instruction":"a"},{"id":"2","instruction":"b"}]', 'final'])
    out = await orchestrate('goal', llm, fake_worker)
    assert out == 'final'

These tests check your plumbing: parsing, queues, retries, limits. They do not check model quality.

Test the failure paths

Most value is in the unhappy paths, and a fake model makes them easy to trigger. Write tests for:

  • A worker that returns invalid JSON.
  • A worker that raises, then succeeds on retry.
  • A worker that never returns, to confirm the timeout fires.
  • The step budget being hit, to confirm a partial result is returned.

Name the failure you expect before you trigger it, then check the system reacts the way you wrote down. This turns a pile of ad hoc experiments into a regression suite you can run before every change to a prompt, a tool or a limit.

A few real-model runs

Keep a small set of end-to-end tasks that call a real model, run them on demand or nightly, and score the outputs with checks you can compute: a schema is valid, a test passes, a required fact is present. Local open models through Ollama are good for cheap runs, see local LLM models. For building a proper task set, read testing and evaluating AI agents.

Pitfalls

Do not point tests at production tools or real email. Use throwaway databases and fake tool servers. Pin model names in config so a provider change does not alter your results unnoticed, and record the model used in each run log. Check tracing and debugging for what to log.

Questions people ask

Can I test agents without calling a real model?

Yes. Inject a fake model client that returns canned replies. It tests your code paths, not the model's quality.

Does Flisk run agents in production?

No. Flisk is a local development tool. Production orchestration stays with your own platform.
