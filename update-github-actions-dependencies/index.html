Dependency Updates Without Chaos

How to Keep GitHub Actions Up to Date and Pinned

Actions in your workflows are dependencies too. Pin them by commit SHA and let Dependabot or Renovate propose updates so versions are reviewed, not floating.

Add the github-actions ecosystem to dependabot.yml and the updater will open pull requests when an action in your workflows has a newer version. Pin sensitive actions by full commit SHA, so a moved tag cannot change what runs, and let the bot keep the SHA current.

Why actions need updates

Every uses: line is third-party code that runs in your pipeline, often with a token. Old actions stop working when the platform changes (for example a runtime version being retired) and miss security fixes. At the same time, a tag like v4 is a moving pointer that the action owner can change. You want updates, but as reviewed pull requests, not silently.

Enable updates for actions

version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    groups:
      actions:
        patterns: ['*']

Grouping puts all action bumps in one pull request per week. Renovate handles workflows by default with its GitHub Actions manager, and can pin digests with a preset. Check the Renovate docs for the preset name before relying on it.

Pin by commit SHA

Replace the tag with the full 40 character commit SHA and keep the version as a comment:

- uses: actions/checkout@SHA_OF_THE_COMMIT # v4.x.y

The bot reads the comment and updates both. Pinning matters most in jobs with publish rights, deploy credentials or write tokens. For actions maintained by GitHub itself, many teams accept tags and pin only third-party ones. That is a judgement call: pin more where the blast radius is bigger. See GitHub Actions Security.

Other things that float in a workflow

  • runs-on: ubuntu-latest changes when GitHub moves the label to a newer image. Pin to a specific image label if you need stability, and update on purpose.
  • Tool versions installed by setup-* actions, such as node-version: 20. A major pinned is fine, a bare latest is not.
  • Docker images used in container: or services:.
  • Scripts fetched with curl from a branch URL.

Dependabot has a docker ecosystem for Dockerfiles. For images in workflow files, check what your updater supports.

Handle a breaking action update

Read the release notes for inputs that were renamed or removed, and for runtime changes. If CI fails on the bot pull request, fix the workflow in the same PR rather than merging red. If an action is abandoned, look for a maintained alternative or replace it with a few lines of shell, which removes a dependency completely. Fewer third-party actions also means a smaller attack surface for your pipeline.

Review those pull requests

An action update runs in your CI immediately, so a bad one is felt at once. Skim the release notes in the PR, look at the diff of the tag if the action is small, and let CI run on the pull request before merging. Since a broken action breaks every workflow, make sure the failing PR is visible, see CI checks for dependency pull requests.

Questions people ask

Does pinning by SHA stop updates?

No. The bot proposes new SHAs in pull requests. You choose when to merge them.

Do I need to pin actions published by GitHub?

It is a judgement call. Many teams pin third-party actions and accept official tags for low-risk jobs, but pin everything in jobs that publish or deploy.
