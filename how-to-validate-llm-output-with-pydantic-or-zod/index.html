How to validate LLM output with Pydantic or Zod

Define the shape once as a typed model, parse the reply, and turn failures into clear error messages. Working examples for Python and TypeScript.

Define the expected output as a Pydantic model (Python) or a Zod schema (TypeScript), parse the model's reply with it, and treat a parse failure as a normal, handled case. You get types, constraints and readable errors from one definition.

Python with Pydantic

from pydantic import BaseModel, Field, ValidationError
from typing import Literal

class Ticket(BaseModel):
    category: Literal["bug", "billing", "other"]
    priority: int = Field(ge=1, le=3)
    summary: str = Field(max_length=200)

try:
    t = Ticket.model_validate_json(reply)
except ValidationError as e:
    errors = e.errors()   # list of dicts: field, message

The same class can produce a JSON Schema with Ticket.model_json_schema(), which you can pass to a provider's structured output option. One source of truth.

TypeScript with Zod

import { z } from "zod";

const Ticket = z.object({
  category: z.enum(["bug", "billing", "other"]),
  priority: z.number().int().min(1).max(3),
  summary: z.string().max(200),
});

const result = Ticket.safeParse(JSON.parse(reply));
if (!result.success) {
  console.error(result.error.issues);
}

Remember JSON.parse can throw, so wrap it. Zod can also convert to JSON Schema through add-on libraries; check the docs for the current one.

Constraints that catch real mistakes

  • Enums instead of free strings for categories.
  • Numeric ranges for scores and priorities.
  • Max lengths for text going into a UI or database column.
  • Required versus optional fields that match your real rules.

Add a nullable or "unknown" option so the model has an honest way to say it could not tell.

Beyond shape: business checks

A type check cannot tell you that an order ID does not exist. Add a second stage that checks values against reality: look up the ID, check the date is not in the future, make sure the URL is on an allowed domain. Reject or flag, never silently fix.

What to do on failure

Return the validation errors to the model for a retry, as in retrying invalid JSON, and after the cap fail clearly. Log the raw reply and the errors, since that data tells you which fields the model gets wrong most. Do not guess missing fields to make the object pass. And never pass validated output into a shell or SQL string without the usual escaping or parameterization. See AI security for builders.

Keep the schema next to the prompt

Store the model class or Zod schema in the same module as the prompt that produces it, and name them together: ticket_prompt.md and ticket_schema.py. When one changes, the other shows up in the same diff. A mismatch, such as the prompt asking for priority from 1 to 5 while the schema allows 1 to 3, is one of the most common silent bugs, and a shared test that feeds the example output in the prompt through the schema catches it.

Questions people ask

Should I validate even when the API enforces a schema?

Yes. Enforcement covers the shape, but your own rules, such as existing IDs and allowed values, still need checking.

Which is better, Pydantic or Zod?

Use the one that matches your language. They solve the same problem: one typed definition for parsing, validation and schema generation.
