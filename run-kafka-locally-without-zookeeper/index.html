Kafka and streaming locally

How to run Kafka locally without ZooKeeper (KRaft mode)

ZooKeeper is gone from Kafka 4.0. Here is a single-node broker that your containers and your own tools can both reach.

Run the official apache/kafka image. Since Kafka 4.0 there is no ZooKeeper: a broker runs in KRaft mode and keeps its cluster metadata in an internal Raft log. For local development that means one container, one process role pair (broker and controller) and no second service to start first.

What changed with ZooKeeper

Older tutorials start a zookeeper container, then a kafka container that points at it with KAFKA_ZOOKEEPER_CONNECT. That setup is obsolete. Kafka 4.0 removed ZooKeeper support, and KRaft is the only mode. If a Compose file you found still lists ZooKeeper, it is pinned to an old Kafka version, and its settings will not carry over to a current image.

In KRaft mode each node has a process.roles value. A production cluster usually runs dedicated controller nodes and separate brokers. On a laptop one node can hold both roles: broker,controller. That is what the config below does.

The fastest way: one docker run

If you only want a broker for a quick experiment from your own machine, the image ships a default config that listens on port 9092 and advertises localhost:9092:

docker run --rm --name kafka -p 127.0.0.1:9092:9092 apache/kafka:4.2.2

Any client on your machine can now use localhost:9092 as its bootstrap server. This stops working the moment another container needs to reach the broker, because the broker still tells every client to connect to localhost, which inside a different container is that container itself. The next section fixes that. The cause is explained in full in Kafka advertised listeners.

A broker that containers and your laptop can both reach

Define two listeners: one named for the address other containers use (broker:9092) and one for your machine (127.0.0.1:29092), plus the controller listener that KRaft needs. Here is the same broker as a Flisk resource. Create it with the CLI, then edit the file:

npm install -g @flisk-sh/flisk
flisk resource broker --type bring-your-own --image apache/kafka:4.2.2 \
  --stack streaming --no-proxy --yes

Kafka is not one of Flisk's built-in queue frameworks (those are NATS and RabbitMQ), so this is a bring-your-own container: you supply the image and the settings, Flisk supplies start order, health checks, a named volume and logs. The command writes a basic service.json under services/streaming/broker/. Replace its contents with:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "broker",
  "appType": "bring-your-own",
  "stack": "streaming",
  "port": 9092,
  "exposeViaProxy": false,
  "image": "apache/kafka:4.2.2",
  "env": {
    "KAFKA_NODE_ID": "1",
    "KAFKA_PROCESS_ROLES": "broker,controller",
    "KAFKA_LISTENERS": "INTERNAL://:9092,EXTERNAL://:29092,CONTROLLER://:9093",
    "KAFKA_ADVERTISED_LISTENERS": "INTERNAL://broker:9092,EXTERNAL://127.0.0.1:29092",
    "KAFKA_LISTENER_SECURITY_PROTOCOL_MAP": "INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT",
    "KAFKA_INTER_BROKER_LISTENER_NAME": "INTERNAL",
    "KAFKA_CONTROLLER_LISTENER_NAMES": "CONTROLLER",
    "KAFKA_CONTROLLER_QUORUM_VOTERS": "1@localhost:9093",
    "KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR": "1",
    "KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR": "1",
    "KAFKA_TRANSACTION_STATE_LOG_MIN_ISR": "1",
    "KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS": "0"
  },
  "healthCheck": {
    "command": ["/opt/kafka/bin/kafka-broker-api-versions.sh", "--bootstrap-server", "localhost:9092"],
    "startPeriod": 30
  },
  "extraPorts": [{ "port": 29092 }],
  "volumes": [{ "source": "broker-data", "target": "/var/lib/kafka/data" }],
  "provides": { "KAFKA_BROKERS": "broker:9092" }
}

What the fields do:

  • env holds the Kafka settings. The official image turns each KAFKA_* variable into a broker property, so KAFKA_NODE_ID becomes node.id.
  • healthCheck.command runs inside the container and exits 0 once the broker answers. Services that list broker in dependsOn wait for it.
  • extraPorts publishes 29092 on 127.0.0.1 only, so your editor and CLI tools can connect and your network cannot.
  • volumes keeps the log directory in a named volume that survives flisk down.
  • provides gives every service that depends on the broker a KAFKA_BROKERS variable set to broker:9092. It is a connection setting, never a secret.

The --port flag of flisk resource only accepts 4000 to 5999 for this resource type, so set "port": 9092 by editing the file. In CLI 1.4.57, flisk config verify accepts it. Then:

flisk config verify
flisk up streaming
flisk status

Check that it works

flisk run executes a command inside a running service, so you can use the Kafka scripts that ship in the image without installing anything:

flisk run broker -- /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic smoke --partitions 1 --replication-factor 1
flisk run broker -- /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
flisk logs --service broker --tail 50

I validated the manifest with flisk config verify but did not start this broker while writing this page. The Kafka environment variables are the ones documented for the official image. If the broker exits at startup, flisk logs --service broker shows why, and the usual cause is a mistyped listener name.

Pitfalls

  • Heap size. Kafka's start script gives the JVM a 1 GB heap by default. On a small machine add "KAFKA_HEAP_OPTS": "-Xmx512m -Xms512m" to env.
  • Replication factors. A single node cannot hold three replicas. The three KAFKA_*_REPLICATION_FACTOR and MIN_ISR settings above are set to 1 for that reason. Without them, consumer groups fail because the internal offsets topic cannot be created.
  • Stale volume. If you change the node id or the quorum voters after the first start, the old metadata in the volume no longer matches. Stop the stack and remove the volume (see keep volumes between runs, or reset them).
  • Not a production layout. One node with both roles has no fault tolerance. Do not copy it to a server.

With a broker running, the next thing you need is topics. Create Kafka topics automatically on startup shows how to do it with a one-shot job. If you are not sure Kafka is the right broker for a laptop, read Redpanda or Kafka for local development first.

Questions people ask

Does Kafka still need ZooKeeper?

No. Kafka 4.0 removed ZooKeeper support. Every cluster runs in KRaft mode, where the brokers and controllers keep metadata in an internal Raft log.

Can one container be both broker and controller?

Yes, for local development. Set process roles to broker,controller and give the controller its own listener. A production cluster usually separates the two roles.

Why do I need replication factor 1?

A one-node cluster cannot place three replicas. The internal offsets and transaction topics default to three, so consumers fail until you lower them to 1.
