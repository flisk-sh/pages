Debugging CI Failures

How to Read GitHub Actions Logs and Find the Real Error

The first red line in a CI log is rarely the cause. Here is how to find the step, the first real error and the context around it in a few minutes.

Open the failed job, find the first step with a red mark, and read upwards from the end of that step's output until you find the first error, not the last one. The last lines are usually the exit code and a summary. The cause is usually earlier.

Start at the failed step, not the top of the log

A GitHub Actions run has workflows, jobs and steps. Click the failed job in the left panel and look for the step with the red cross. Every step before it passed, so you can ignore them for now. Expand only the failed step.

If the job has a matrix, several jobs may be red. Compare them. If every cell fails the same way, the cause is in the code or the workflow. If only one cell fails, the cause is the difference: an operating system, a Node version, a database version.

Find the first error, not the last

Test runners and build tools print a lot after the first failure. A compiler error can cause fifty more errors. A failed setup can cause every test to fail. Scroll to where the output first turns bad. Use the search box in the log viewer for words like error, failed, ECONNREFUSED, Cannot find module.

You can also download the raw log from the run menu and search it in your editor, or use the GitHub CLI:

gh run list --limit 5
gh run view RUN_ID --log-failed | less

--log-failed prints only the logs of failed steps, which cuts most of the noise.

Read the annotations and the summary

The run summary page shows annotations: errors and warnings that tools wrote with the ::error:: syntax. Many linters and test reporters use them. They often point to a file and a line, so you can skip the log completely.

Also check the exit code line. Process completed with exit code 1 means the command failed normally. exit code 137 usually means the process was killed, often for memory. exit code 143 is a termination signal, often a timeout or a cancel.

Look at what changed

Once you know the failing step, ask what is different from the last green run. Compare the two runs side by side: the commit, the runner image, the versions printed in the setup steps. A dependency that floats (for example latest or an unpinned range) can change without any commit in your repo.

If you suspect the environment and not your code, see how to tell a regression from an environment problem. If you cannot see enough detail, turn on debug logging and re-run.

Make logs easier to read next time

Small changes to the workflow pay back quickly. Print tool versions at the start. Name steps clearly. Use ::group:: and ::endgroup:: to fold long output. Make test runners print the failing test name and the assertion, not only a dot per test.

- name: Show versions
  run: |
    node --version
    npm --version
    docker --version

Good logs turn a twenty minute hunt into a two minute read.

Questions people ask

How do I see only the failed steps of a run?

Run gh run view RUN_ID --log-failed with the GitHub CLI. It prints the logs of failed steps only.

Why does the log show the error but the step is green?

The command probably returned exit code 0, or the step uses continue-on-error. Check the step definition and add set -e or an explicit exit code check.
