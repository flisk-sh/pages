How to write docs for an MCP server

Document an MCP server for two readers: the developer who installs it and the model that picks its tools. Covers install, config, tool descriptions and auth.

An MCP server needs two kinds of documentation: install and configuration steps for the human, and clear tool names, descriptions and argument docs for the model. The second kind is read by the model at runtime and decides whether it picks the right tool.

The human page: install and connect

Show how to add the server to a client with an exact config block. Most clients take a JSON entry with a command and arguments for a local server, or a URL for a remote one. The shape differs between clients, so give one example per client you support and link to that client's docs.

{
  "mcpServers": {
    "acme": {
      "command": "npx",
      "args": ["-y", "acme-mcp"],
      "env": { "ACME_API_KEY": "your-key-here" }
    }
  }
}

State the transport (local process or remote URL), whether sign-in is needed and where to get a key.

Tool names and descriptions are documentation

The model sees only the tool name, the description and the argument schema. Write them for it.

  • Name tools with a verb and an object: search_orders, not query.
  • Say in the description when to use the tool and when not to.
  • Describe each argument, with its format and an example value.
  • Say what the tool returns and what it does not.
search_orders: Find orders by customer email or date range.
Use when the user asks about past orders. Does not change anything.
Args: email (string, e.g. "ana@example.com"), since (ISO date, optional)

Mark side effects

Say which tools only read and which write, delete or spend money. A model weighs a tool differently when the description says "permanently deletes". Many clients also support annotations for read-only or destructive tools. Check the current MCP spec before you rely on a particular field.

Document auth, limits and errors

  • How authentication works and what scopes a key needs.
  • Rate limits and what the server returns when they are hit.
  • Error messages: write them so a model can act on them, such as "date must be ISO 8601, for example 2026-01-31".

A clear error is documentation delivered at the moment it is needed.

Test it with a real client

Follow your own install steps on a clean machine, then ask a model a question that should trigger each tool. If it picks the wrong tool, rewrite the description, not the prompt. For deeper design guidance, see MCP servers in production and Build an MCP server. For a similar treatment of an HTTP API, see How to document an API so LLMs can use it.

Questions people ask

Do tool descriptions count as documentation?

Yes. They are the only documentation the model reads when choosing a tool, so they deserve the most care.

Should I list example prompts?

Yes, a few in the human docs. They show readers what the server is for and help you test the tool descriptions.
