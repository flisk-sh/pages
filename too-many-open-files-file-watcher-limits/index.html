Fix EMFILE and ENOSPC "too many open files" in dev watchers

Two different limits produce similar errors. Which one you hit depends on the operating system and the watcher.

EMFILE means a process ran out of file descriptors; ENOSPC from a watcher means Linux ran out of inotify watches. Raise ulimit -n for EMFILE, raise fs.inotify.max_user_watches for ENOSPC, and in both cases make the watcher watch fewer files, because a limit raised to hide a huge watch set only moves the problem.

Tell the two errors apart

Error textMeaningUsual platform
EMFILE: too many open files, watchThe process hit its limit of open file descriptors.macOS, also Linux
ENOSPC: System limit for number of file watchers reachedThe per-user inotify watch limit is exhausted. It is not about disk space despite the name.Linux

Fix EMFILE (file descriptors)

Check the limit of the current shell:

ulimit -n

On macOS the default for a shell is often 256, which a large project exceeds quickly. Raise it for the shell where you start the dev server:

ulimit -n 10240

That applies to this shell and the programs it starts. To keep it, put the line in your shell profile. If the system refuses, the hard limit is lower: check with ulimit -Hn and, on macOS, launchctl limit maxfiles.

The better fix is a watcher that does not open one descriptor per file. On macOS, Node tools normally use the native file events API and need few descriptors; if you see EMFILE anyway, a polling watcher or a tool that cannot load its native module is the likely cause. Reinstalling dependencies can restore the native module. For very large trees, Watchman, which Jest and Metro can use, keeps one process watching on behalf of many tools.

Fix ENOSPC (inotify watches)

Linux limits how many files one user can watch. Look at the current value:

cat /proc/sys/fs/inotify/max_user_watches

Older kernels default to 8192, which a single node_modules can use up. Raise it persistently:

echo "fs.inotify.max_user_watches=524288" | sudo tee /etc/sysctl.d/99-watches.conf
sudo sysctl --system

Each watch costs a small amount of kernel memory, about a kilobyte on a 64-bit system according to the VS Code documentation, so 524288 watches is acceptable on a normal laptop. The related max_user_instances limit also exists; raise it if you run many separate watchers.

Inside a container the limits belong to the host kernel, so raise them on the host, or on the Linux VM that runs your containers. On a Mac with Docker, the VM is the machine that matters.

Make the watcher watch less

Raising limits is a patch. Reduce what is watched:

  • Ignore node_modules, .git, build output and caches in the tool's watch configuration (watchOptions.ignored in webpack, server.watch.ignored in Vite, --ignore or --watch-path style flags in runners).
  • Run one watcher per service, not one at the repo root that watches ten services.
  • Do not start the same project twice. Two dev servers, or an old one left in the background, double the usage.
  • In a monorepo, start only the services you are working on.

Where Flisk fits

Flisk does not change your OS limits. What it can do is keep the number of watchers down. A project of services with a command in service.json starts each as a local process, and flisk up --only web starts just web and what it depends on, so you do not run a watcher for every service in the repo. When a watcher fails, flisk logs --service web --since 5m shows the error with the service name in front of it, and flisk status shows whether the process is restarting. Flisk restarts a crashed process with growing delays and gives up after five quick exits, so an EMFILE crash will not loop forever.

Pitfalls

  • ulimit -n set in one terminal does not affect a dev server started from your IDE or a launcher. Start it from the shell where you set it.
  • An error that appears only after several hours can mean a watcher leaks descriptors. Restart it and watch lsof -p <pid> | wc -l over time.
  • Do not set limits to unlimited. A bug that opens files in a loop will then take the whole machine down instead of failing fast.

If reload does not trigger at all, rather than crashing, read hot reload not working. For the CPU side of watchers, see dev server at 100% CPU.

Questions people ask

Does ENOSPC mean my disk is full?

Not in a file watcher error. It means the Linux inotify watch limit is exhausted. Raise fs.inotify.max_user_watches.

How do I raise the open file limit on macOS?

Run ulimit -n 10240 in the shell where you start the dev server, and add it to your shell profile to keep it. The hard limit may need launchctl to change.

Is 524288 inotify watches safe?

On a normal laptop yes. Each watch uses a small amount of kernel memory, and this is the value VS Code documentation suggests.
