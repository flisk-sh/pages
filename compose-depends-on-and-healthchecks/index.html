Compose depends_on and healthchecks: wait for the database

Your API crashes because the database is not ready yet. This is how to order startup properly in Compose and in service.json.

In Compose, depends_on by itself only waits for a container to start, not for the service inside it to be ready. To wait for a database, give it a healthcheck and use depends_on with condition: service_healthy. Flisk has the same three conditions under dependsOn in service.json.

Why depends_on alone is not enough

A database container is "started" within a moment, but Postgres needs several more seconds before it accepts connections. If your API connects in that gap, it crashes with "connection refused", and Compose does not know it should have waited. The short form of depends_on only orders container creation.

The fix has two parts. The dependency declares how to tell that it is ready, and the dependent declares which state it needs.

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: example
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
  migrate:
    build: ./api
    command: npm run migrate
    depends_on:
      db:
        condition: service_healthy
  api:
    build: ./api
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully

Compose supports three conditions: service_started (the default), service_healthy and service_completed_successfully. The last one is for one-shot jobs such as a migration: the API waits until the job exits with code 0.

The same idea in service.json

In Flisk, dependsOn takes either plain names or objects with a condition:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "dependsOn": [
    "postgres",
    { "name": "migrator", "condition": "service_completed_successfully" }
  ]
}

The conditions are service_started, service_healthy and service_completed_successfully, the same names as Compose. The generated Tiltfile turns them into resource_deps. For service_healthy Flisk adds a separate <svc>-healthy resource, and for completion a <job>-done resource. The names postgres and database-management refer to the shared platform Postgres.

Two combinations are errors in the manifest: service_healthy on a one-shot job, and service_completed_successfully on a service that keeps running. A dependsOn name that matches no service is also an error, which catches typos early.

Define what healthy means

For HTTP APIs, healthCheckPath defaults to /health, so your service should answer there. You can change it, turn the check off with "healthCheck": false, or use an object that sets exactly one of path, port or command, plus timing. Intervals and timeouts are numbers of seconds, and command can be an array:

"healthCheck": {
  "command": ["pg_isready", "-U", "postgres"],
  "interval": 5,
  "timeout": 3,
  "retries": 10,
  "startPeriod": 10
}

Use command or port for things without an HTTP route, like a database or a gRPC server. For a bring-your-own container, startPeriod gives a slow-booting app time before failed probes start to count. Keep the check cheap: it runs repeatedly.

For a container, the check runs inside it. For a service that runs as a local process, a command check runs on the host from the service folder. With "healthCheck": false, a local process counts as ready while it runs, and a container gets no health check at all, so turn the check off only for things that cannot be probed.

Run migrations as their own resource

Do not run migrations from an API start script. A separate migrator resource makes the order explicit: database, then migrator, then API. If the migration fails, the API never starts, and you see the failure in the migrator's log instead of a half-started API. Flisk's own rule for new services is an explicit migrator resource with appType: migrator. Creating a backend with Prisma sets up the pair:

flisk resource orders-api --type backend --stack shop --feature prisma

Migrations in more detail are in database migrations in local dev.

Limits you should know

  • Startup ordering only. dependsOn does not make a service retry later. If the database restarts at minute ten, your API still needs its own reconnect logic. Both Compose and Flisk behave this way.
  • Dependencies come along. flisk up --only api starts the API and what it depends on, not only the API.
  • Healthcheck must be real. A check that always passes gives you the same race you had before. Test against something the service needs, such as an actual query.
  • Cycles. A dependency loop cannot be ordered. Break it by moving shared startup work into a third service.

If a service starts but behaves badly because its dependency was not ready, read service startup order for the wider picture. To start only part of a stack, profiles and stacks are the next topic.

Questions people ask

Does depends_on wait for the database to be ready?

Not by itself. It waits for the container to start. Add a healthcheck on the database and use condition: service_healthy to wait until it is ready.

How do I run a migration before the API starts?

Run it as a one-shot service and make the API depend on it with condition: service_completed_successfully. In Flisk, use a migrator resource and the same condition in dependsOn.

Will dependsOn restart my service if the database goes down later?

No. It controls startup order only, so your service still needs its own reconnect logic.
