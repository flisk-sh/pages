Frontend dev servers and APIs

How to proxy API requests in the Vite dev server

The Vite dev server can forward some URLs to your backend, so the browser only ever talks to one origin. Here is the config, the options that matter, and the traps.

Add a server.proxy entry to vite.config.ts that maps a path prefix such as /api to your backend URL. The browser then calls /api/items on the Vite origin, Vite forwards the request to the backend, and no CORS check applies because the page and the request share one origin.

What the proxy does and does not do

The Vite dev server is a Node HTTP server. When a request path matches a proxy key, Vite hands it to an HTTP proxy (http-proxy) instead of looking for a file. The request leaves from the dev server process, not from the browser, which is why the backend never sees a cross-origin browser request.

This only exists while the dev server runs. vite build produces static files and has no proxy, so a deployed frontend needs its own answer: a reverse proxy, a gateway or the API's own CORS rules. The same applies to the page you open with vite preview: it uses preview.proxy, which defaults to the value of server.proxy.

The basic config

import { defineConfig } from 'vite';

export default defineConfig({
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:3001',
        changeOrigin: true,
      },
    },
  },
});

In the frontend code, call relative URLs and never write the backend port:

const path = '/api/items';
const res = await fetch(path);

A fast way to test the rule without the browser is curl http://localhost:5173/api/items. If that returns the backend's JSON, the proxy works. If it returns your index.html, the path did not match a key and Vite fell back to the single page app.

Options you will actually use

  • changeOrigin rewrites the Host header to the target's host. Turn it on when the backend routes by host name. It is harmless for a plain localhost target.
  • rewrite changes the path before forwarding. Use it to strip a prefix: rewrite: (path) => path.replace(/^\/api/, '') sends /api/items to the backend as /items.
  • ws: true also proxies WebSocket upgrades on that prefix, which you need for a socket server that lives on the backend.
  • secure: false accepts a self-signed certificate when the target is https.
  • configure gives you the underlying proxy object, handy for logging a failed target: proxy.on('error', (err) => console.log(err.message)).

A key that starts with ^ is treated as a regular expression, so '^/(api|auth)/.*' covers two prefixes in one rule.

The Flisk way

If you start the backend and the frontend with Flisk as local processes, the scaffold writes this proxy for you. This is the verified route:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource api --framework express --local --stack app --yes
flisk resource web --type frontend --local --stack app --yes

The frontend gets a plain vite.config.ts with server.host set to localhost, strictPort: true, and a proxy that forwards /health and /api to the API's local port (the port from the API's service.json). The frontend's manifest lists the API in dependsOn and has "command": "npm run dev", so flisk up starts the API first and waits for its health check before it starts Vite. The starter page calls a relative /health, which goes through the proxy.

The config is a normal file in your repo. If your API lives under another prefix, such as /v1 or /graphql, add it to the same proxy object. Flisk does not rewrite the file again afterwards. If you change the API's port in its service.json, update the proxy target by hand.

Pitfalls

  • Hard-coded absolute URLs skip the proxy. a call to http://localhost:3001/api/items goes straight from the browser to the API and brings CORS back. Search the code for the backend port.
  • A trailing path matters. The key /api also matches /apiary. Use /api/ if you have routes that share the start of the word.
  • The proxy hides cookie domain problems, not all of them. A cookie the backend sets arrives on the Vite origin, which is usually what you want. See cookies not sent from a frontend to a local API for the cases where it is not.
  • Do not use a proxy as the production plan. It only helps in development. Decide early how the deployed frontend reaches the API.

Questions people ask

Does the Vite proxy work in production?

No. server.proxy only applies to the dev server, and to vite preview through preview.proxy. A production build is static files, so the deployed site needs a reverse proxy or an API with CORS rules.

Why does my proxied request return index.html?

The path did not match a proxy key, so Vite served the single page app fallback. Check the prefix, a missing leading slash, or a trailing slash in the key.

Do I still need CORS with the Vite proxy?

Not for requests that go through the proxy, because the browser only talks to the Vite origin. You need CORS again if any code calls the API origin directly.
