Build your own MCP server

How to debug an MCP server with the MCP Inspector

The Inspector is a plain MCP client with a UI. It shows what your server really returns, with no model in between.

Run npx @modelcontextprotocol/inspector, open the URL it prints, point it at your server, and use the Tools tab to list tools and call them with arguments you type in. The Inspector is the official debugging UI for MCP: it shows each request and response, so you can see exactly what a client would see, without involving an AI model.

Why not debug through an assistant

When you test a server through a chat window, three things can be wrong at once: your server, the client's configuration, and the model's choice of tool. A model can also hide an error by apologizing and carrying on. A plain client that does what you tell it, and prints the raw messages, takes two of those out of the picture.

Start the Inspector

You need Node.js. For a server you launch as a command (stdio), pass the command after the Inspector:

npx @modelcontextprotocol/inspector node build/index.js
npx @modelcontextprotocol/inspector uv run python server.py

The Inspector starts a small proxy and a web UI, and prints a local URL. The UI is normally at http://localhost:6274. Recent versions also print a session token in the URL, and the proxy refuses connections without it, so open the printed link rather than typing the address. For a Python project using the SDK's CLI extra, uv run mcp dev server.py does the same thing in one step.

For an HTTP server that is already running, start the Inspector with no command, choose Streamable HTTP as the transport in the sidebar, and paste the endpoint, for example http://127.0.0.1:8000/mcp. Press Connect.

What to check, in order

  1. Connect. If it fails, read the Inspector's notifications and the server's standard error. For stdio servers, stray output on stdout is the most likely cause.
  2. Tools tab, List Tools. Read names, descriptions and schemas as a model would. Are they clear? Are required fields marked?
  3. Call a tool. Fill in the form and run it. Look at the content that comes back, and at whether isError is set.
  4. Call it wrong. Leave out a required field, send a negative number, use an unknown id. Confirm you get a useful message and not a crash.
  5. Resources and Prompts tabs. If you registered those, list and read them too.
  6. History and notifications. Review the raw JSON-RPC messages for each action, which is helpful when a result looks odd.

When a scripted check is better

The Inspector is interactive, so it suits exploration and does not repeat itself the same way twice. For a quick, repeatable pass, flisk mcp check sends a fixed list of requests to an HTTP server and prints one pass or fail line per check. It works on a Flisk resource name or an https URL (plain http only for localhost and loopback addresses):

flisk mcp check notes-mcp
flisk mcp check http://127.0.0.1:8000/mcp --json

It checks initialize, tools/list, prompts, the refusal of an unknown method, bad JSON and a GET request, the handling of an Accept: application/json header, and that icon-512.png next to the endpoint is a PNG (--no-icon skips the last one). It is read-only unless you add --call, and the exit code is 1 when something fails, so it can gate a script. It does not send an Authorization header, so it cannot check a server that requires a token, and its tool check expects every tool to carry readOnlyHint: true. Use both tools: the Inspector to look around, the command to make sure you did not break the basics.

Pitfalls

  • The Inspector runs a local proxy. Keep it on your machine and do not expose its ports. Treat the session token as a secret.
  • Servers that check the Origin header. A server that validates Origin may refuse a connection that comes from a browser page. If the Inspector cannot connect to an HTTP server that works with curl, look at that check first.
  • Stale code. If you edit the server and nothing changes, you are probably talking to an old process. Restart it, or use a watch mode.
  • Not a load test. The Inspector sends one request at a time.

When what you do by hand in the Inspector is stable, turn it into tests. Automated tests for an MCP server shows how.

Questions people ask

What port does the MCP Inspector use?

The web UI is normally at http://localhost:6274 and its proxy listens on 6277. Open the URL printed in the terminal, which includes a session token in recent versions.

Can the MCP Inspector test an HTTP server?

Yes. Start it without a command, choose Streamable HTTP as the transport and enter the server's endpoint, such as http://127.0.0.1:8000/mcp.
