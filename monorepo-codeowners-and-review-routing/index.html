CODEOWNERS in a Monorepo: Route Reviews to the Right Team

Use a CODEOWNERS file so every directory in a monorepo has owners who are asked to review changes, and learn the pattern rules, the traps and how to enforce it with branch protection.

A CODEOWNERS file maps paths to people or teams, and GitHub automatically requests their review on pull requests that touch those paths. In a monorepo it is the simplest way to give every package an owner and to protect sensitive paths such as workflows and infrastructure.

The file and where it lives

Put it at .github/CODEOWNERS, in the repository root or in docs/. Each line is a path pattern followed by one or more owners, which can be users or teams in the form @org/team.

# default owner for everything
*                      @acme/platform

/services/api/         @acme/backend
/services/web/         @acme/frontend
/libs/shared/          @acme/platform @acme/backend
/.github/workflows/    @acme/platform
/infra/                @acme/sre

Pattern rules that bite

  • The last matching pattern wins, not the most specific one. Put general rules first and specific ones after.
  • A pattern like /services/api/ with a leading slash is anchored to the repo root. Without it, the pattern matches at any depth.
  • Teams must have write access to the repository, or the line is ignored.
  • Syntax errors do not break pushes. GitHub shows them in the file view, so check there after editing.

Make it a rule, not a suggestion

By default CODEOWNERS only requests reviews. To require them, turn on 'Require review from Code Owners' in the branch protection rule or ruleset for your default branch, see branch protection and rulesets. Then a pull request that touches /infra/ cannot merge without an approval from @acme/sre.

Protect the workflow directory especially, since a change to .github/workflows/ changes what code runs with your secrets, see GitHub Actions security.

Keep the load manageable

If every pull request needs five approvals, people route around the rule. Use teams rather than individuals so that anyone on the team can approve, and keep shared library owners small but not single-person. For generated files or lockfiles, either leave them without owners or give them to a team that approves in bulk. Review the file when people change teams, because stale owners are the most common failure.

Connect it to CI

Ownership also helps routing of failures. When a workflow is red, you want to know which team to ask. Reuse the same team names in your alerting and in your list of red workflows, as discussed in org-wide CI visibility. In a monorepo with a changed-files plan, see running only what changed, you can post the owners of the affected packages in the job summary. When coding agents open pull requests, CODEOWNERS makes sure a human from the right team still approves, which matters for agent-written pull requests.

Audit once a quarter: list top-level directories, check each has an owner line and that the named teams still exist.

Questions people ask

Does CODEOWNERS block merging by itself?

No. It requests reviews. To require them, enable the code owner review requirement in branch protection or a ruleset for the branch.

Can I use CODEOWNERS with a monorepo that has many teams?

Yes, that is a main use case. Give each directory a team owner, keep a default owner for everything else, and keep the file under review like any other config.
