How to stop AI from editing generated files in your repo

Assistants edit whatever file they find. A generated file edited by hand is overwritten on the next build, so the fix has to live somewhere else.

To stop an AI assistant from editing generated files, use three layers: tell it in AGENTS.md which paths are generated and where the real source is, keep the paths out of version control so they look like output, and deny edits to them in the assistant's own permission settings. Then check for drift with a command that compares output to source.

Why it keeps happening

A generated file looks like any other file. An assistant that is asked to fix a failing container will find the Dockerfile in a build folder, see the bug and patch it. The patch works until the next generation step overwrites it, and the bug is back with no commit that explains why. The same happens with compiled output, lock files edited by hand, and code generated from a schema.

The answer is not to hope the assistant notices a header comment. Give it the rule, remove the temptation, and make the mistake visible.

Layer 1: say it, with the source named

A rule that only says "do not edit X" leaves the assistant stuck. Say what to change instead:

- Do not edit anything under `services/**/.autogenerated/` or `.flisk/.flisk-out/`.
  Change the service's `service.json`, then run `flisk up`.

Put this in AGENTS.md (see writing an AGENTS.md file). Flisk writes a similar line into the file it generates for a new project.

Layer 2: make generated paths look like output

Add generated folders to .gitignore. A project created with flisk project ignores .flisk/.flisk-out/ and services/**/.autogenerated/, along with .env, node_modules/ and build folders. Many assistants respect ignore files when they search, so ignored paths show up less often in their results. This is a convenience, not a guarantee: an assistant that is pointed at a path can still open it.

Layer 3: deny the edit

Your assistant's permission settings are the strongest layer because they do not depend on the model obeying a sentence. In Claude Code you can add deny rules for edits to .claude/settings.json, for example:

{
  "permissions": {
    "deny": [
      "Edit(./.flisk/**)",
      "Edit(./services/**/.autogenerated/**)"
    ]
  }
}

Check the pattern syntax in the Claude Code permissions documentation for your version, because it has changed over time, and test it: ask the assistant to change a generated file and confirm it is refused. Cursor and Codex have their own ignore and approval settings. Where a tool has no deny rule, keep its approval prompts on for edits and read the file name before you accept.

Know what is generated

Do not guess from the file name. In a Flisk project, ask:

flisk config explain .flisk/.flisk-out/Tiltfile
flisk config explain services/main/api/service.json

The first answers that the file is generated from .flisk/project.json, says whether it was edited, and suggests editing the source and running flisk config regenerate, which discards hand edits. The second reports the file as user-owned, to be edited and followed by flisk up. A file Flisk does not write, such as .env or AGENTS.md, is reported as user-owned too. The same check is a tool for assistants (config_explain), so the assistant can ask before it edits.

Catch the mistake that got through

flisk config verify

It checks that the generated files match .flisk/project.json and that every service.json is valid, and reports "All files are in sync" when they are. Run it after an assistant session, and in CI to catch drift before merge. For the general version of this idea, your build step plus git diff --exit-code on committed generated files does the same job. If it fails, read generated config out of date.

When a generated file really is wrong

Sometimes the output is wrong because the generator has a bug or lacks an option. The fix is still not in the output. Change the source if the option exists, or report the generator, and work around it in a file you own, not in the generated one. A hand edit that survives only until the next run is a trap for the next person.

With the rules in place, your assistant can start and check the stack without touching the files that matter. See letting your coding assistant start the stack.

A last tip: when an assistant proposes a change to a generated file, ask it which source file produces it. If it cannot say, that is a sign the change belongs somewhere else, and asking costs one message.

Questions people ask

How do I know which files in a Flisk project are generated?

Run flisk config explain <file>. It says whether the file is generated or user-owned, whether it was edited, and what to edit instead.

Is a .gitignore entry enough to keep an assistant out of generated files?

No. It makes the paths look like output and shows up in search filters, but an assistant can still open a path it is pointed at. Add an AGENTS.md rule and an edit deny rule too.

What does flisk config regenerate do to hand edits?

It rewrites the generated master files from .flisk/project.json and discards edits in them. The MCP tool is a dry run unless dryRun is set to false.
