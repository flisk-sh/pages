Why Vite changes its port and breaks CORS, and how to pin it

One morning the API rejects a request that worked yesterday, and the only change is a number in the address bar. Here is why, and how to make it stop.

Vite starts on port 5173. If something already holds it, for example a second Vite project you forgot to stop, Vite quietly picks 5174 and prints the new address. Your API's CORS allow list still names http://localhost:5173, so every request from the new origin is rejected. Pin the port with server.strictPort: true so Vite fails instead of moving, and keep the allowed origin in one place.

Why a port is part of the problem

A browser origin is the scheme, host and port together. http://localhost:5173 and http://localhost:5174 are different origins, so an API that allows one blocks the other with the usual No 'Access-Control-Allow-Origin' header error. The same applies to anything else that stored the old address: an OAuth redirect URI registered with a provider, a cookie-related allow list, a webhook tester, a bookmarked URL.

The fault is the silent move. Nothing in the browser tells you the dev server changed. The terminal line did, but it scrolled away.

Fix 1: refuse to move

// vite.config.ts
export default defineConfig({
  server: {
    port: 5173,
    strictPort: true,
  },
});

With strictPort, Vite exits with Error: Port 5173 is already in use instead of choosing another. That error is the better outcome, because you now know a stale server is running. Find it and stop it:

lsof -nP -iTCP:5173 -sTCP:LISTEN

The output names the process and its id. Stop it, then start Vite again.

Fix 2: give each project its own port

Two projects that each want 5173 will collide whenever you work on both. Give every project a fixed port of its own and write it down in the config, not in your head. Ports from 5173 up in steps of one per project are easy to remember. Read the port from the environment so a script or a teammate can override it:

server: { port: Number(process.env.PORT ?? 5173), strictPort: true }

Fix 3: do not hard-code the origin in several places

If the API checks the origin with an allow list, read it from an environment variable that the frontend and the API both come from, or allow a pattern for local origins during development only:

const allowed = (process.env.CORS_ORIGINS ?? 'http://localhost:5173').split(',');
app.use(cors({ origin: (origin, cb) => cb(null, !origin || allowed.includes(origin)) }));

A pattern such as "any localhost port" is convenient in development. Do not ship it: in production the allow list should be exact. See how to fix a CORS error when a frontend calls a local API for the full set of headers.

Better: remove the cross-origin request

If the dev server proxies /api to the backend, the browser only ever talks to one origin, and the port of the frontend stops mattering to the API. The proxy request comes from Vite's server, not from the browser. See how to proxy API requests in the Vite dev server.

What Flisk does here

A frontend created with flisk resource web --type frontend --local gets a Vite config with host: 'localhost', port: Number(process.env.PORT ?? <port>) and strictPort: true, with a comment that Flisk checks and opens that exact port. The port is the one stored in the service's service.json, and Flisk passes it to the process as PORT. Before it starts anything, flisk up checks that the ports are free and reports a taken one together with the name of the process that holds it, and it refuses two services that claim the same port. So a stale Vite server shows up as a message before the browser, and the origin your API allows is the one that is actually running.

The scaffolded Express and Hono backends allow any localhost or *.localhost origin on any port, so in a Flisk project the port is not what breaks CORS. If you write your own allow list, the advice above still applies.

Pitfalls

  • 127.0.0.1 versus localhost. They are different origins even on the same port. Use one name everywhere.
  • OAuth redirect URIs. A provider that has only http://localhost:5173/callback registered rejects a login that started on 5174. Pin the port before you register the URI.
  • Preview server. vite preview defaults to port 4173, a separate origin from the dev server. Allow it too if you test the production build against the same API.

Questions people ask

Why does Vite use port 5174 instead of 5173?

Port 5173 was already taken, usually by another Vite server. Vite picks the next free port unless server.strictPort is true.

What does strictPort do in Vite?

It makes Vite exit with an error when the chosen port is in use, instead of moving to the next one.

How do I find what is using port 5173?

Run lsof -nP -iTCP:5173 -sTCP:LISTEN on macOS or Linux. It prints the process name and id.
