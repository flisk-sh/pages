CI Cache Problems: Stale Caches and How to Bust Them

Why a cached dependency or build output makes CI fail or pass wrongly, how to design cache keys, and how to clear a bad cache.

If CI fails in a way you cannot reproduce, a stale cache is a good suspect. Change the cache key, or delete the cache entry, and re-run. If the failure disappears, the key was wrong: it did not change when its inputs changed. Fix the key, not just the symptom.

How the cache action decides

The actions/cache action restores a saved directory when the key matches exactly, or when a restore key matches by prefix. If nothing matches, the step runs without cache and saves a new entry at the end of a successful job. The key should be built from everything that decides the content, most often a hash of the lockfile.

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      npm-${{ runner.os }}-

Signs of a stale or poisoned cache

  • The failure appears only when the cache hit line says it restored an entry.
  • A build passes on a fresh clone locally and fails on CI with old output files still present.
  • Native modules compiled for another Node version or operating system fail to load.
  • A deleted file still exists in the cache and tests pass that should fail.

The last one is the dangerous direction: a cache that makes a broken build look green.

Design keys that change when inputs change

Include the operating system and architecture, the language version, and the lockfile hash. Cache downloads (the package manager cache), not node_modules or build output, unless you have a reason. Downloads are safe to reuse, installed trees tied to a runtime are not. For build caches, include the compiler version and a hash of the config that changes output.

Restore keys give partial hits. They speed things up but can restore an older, mismatched tree. Use them for download caches only.

Bust a bad cache

Fast options: add a version prefix to the key (v2-npm-...) and commit, or delete entries in the repository's Actions caches page. With the GitHub CLI:

gh cache list
gh cache delete CACHE_ID

The version prefix is easy to review and leaves a record in git. Keep the prefix in an environment variable or a single place so you change it once.

A debugging routine

When you suspect a cache, test it in three runs. Run once with the cache step disabled. If it passes, the cache is involved. Run again with a new key prefix. If that passes and the old key fails, the old entry is bad. Then work out why the key did not change, for example a file that affects output but is not in the hash. Add that file to hashFiles and remove the temporary prefix change only when you are sure.

Cache scope and limits

Caches are scoped by branch. A pull request can read the default branch's caches but not those of sibling branches, and branches that never ran on the default branch start cold. Total cache size per repository is limited and old entries are evicted, so check the current limits in the GitHub docs. Many large caches can push out the useful ones. For more speed advice, see Faster GitHub Actions, and for the general approach to reading failures start with how to read the logs.

Questions people ask

Should I cache node_modules?

Usually cache the package manager download cache instead, then run a clean install. Caching the installed tree can carry stale or mismatched native modules.

How do I clear one cache entry?

Use the Actions caches page in repository settings, or gh cache delete with the cache ID from gh cache list.
