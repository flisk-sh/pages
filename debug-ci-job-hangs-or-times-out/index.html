Debugging CI Failures

How to Debug a GitHub Actions Job That Hangs or Times Out

Find which step stalls, set timeouts that fail fast, and track down the usual causes: open handles, waiting for input, deadlocks and slow network calls.

A job that hangs is stuck inside one step. Set timeout-minutes on the job and on suspect steps so it fails in minutes instead of hours, then find the step whose output stops. The common causes are a process waiting for input, an open handle that keeps the process alive, a deadlock and a network call without a timeout.

Fail fast with timeouts

The default job timeout on GitHub-hosted runners is long, and a hung job burns minutes and blocks the queue. Set a limit close to the normal run time plus margin.

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - run: npm test
        timeout-minutes: 10

A short timeout turns a hang into a clear failure with logs. It also makes the problem visible, which a ninety minute silent job is not.

Find the step that stalls

Open the running job and look at the last line of output. Then ask what the process should do next. If tests print a line per test, the hang is in the test after the last printed one. Run that test alone locally with a time limit:

timeout 60 npm test -- path/to/test.js

If it hangs locally too, you can attach a debugger or print a stack dump. If it only hangs in CI, compare resources and services.

Common causes

  • Waiting for input. A command asks a question (a confirmation, a prompt). CI has no terminal. Use non-interactive flags such as -y or --yes, or set CI=true.
  • Open handles. A test finishes but the process stays alive because of a server, timer or connection that was not closed. Many runners have an option to report open handles or force exit. Prefer fixing the leak over forcing exit.
  • Watch mode. A test command that starts in watch mode never ends. Check that the command used in CI is the single-run one.
  • Network calls without timeouts. A request to a service that never answers blocks forever. Set client timeouts everywhere.
  • Service not ready. Tests start before the database accepts connections and wait or retry forever. Add a health check and a bounded wait.

Wait for services with a bounded loop

A wait loop must have a limit, or it becomes the hang.

for i in $(seq 1 30); do
  pg_isready -h localhost -p 5432 && exit 0
  sleep 2
done
echo 'database did not start' >&2
exit 1

For service containers, declare health options so the job waits until the container is healthy before it runs steps.

Capture evidence before the timeout kills it

When the job is killed, you lose the state. Add a step with if: always() or if: cancelled() that prints process lists and open ports, and upload logs as artifacts. Also look at resources: running out of memory causes swapping and apparent hangs, and exit code 137 is a hint. Reduce parallel workers if memory is the limit. For repeated hangs on one test, treat it as flaky and follow the flaky test guide.

Questions people ask

What timeout should I set?

Roughly two to three times the normal duration of the job. It should be long enough for slow days and short enough to stop a hang quickly.

Can I stop a stuck run from the command line?

Yes, use gh run cancel RUN_ID with the GitHub CLI.
