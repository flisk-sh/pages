How to set up a Python virtual environment for each project

One virtual environment per project keeps dependencies from colliding. The commands are short. The part people trip on is making every tool use the same one.

Create one virtual environment inside each project folder with python3 -m venv .venv, activate it, and install the project's dependencies into it. Each project then gets its own packages and its own pip, so upgrading a library for one project cannot break another. Keep the .venv folder out of git and rebuild it from a requirements file whenever you need a fresh copy.

Create and activate the environment

From the project root:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt

On Windows PowerShell the activation line is .venv\Scripts\Activate.ps1. After activation, python and pip point at the copies inside .venv. Check it with:

python -c "import sys; print(sys.executable)"

The path should end in .venv/bin/python. If it does not, you are still using the system interpreter, and that is the cause of most "I installed it but it is not found" reports. Calling python -m pip instead of bare pip is a habit worth keeping, because it guarantees the package lands in the interpreter you just ran.

You do not have to activate the environment to use it. .venv/bin/python script.py and .venv/bin/pytest work from any shell, which is how editors, cron jobs and other tools usually run it.

Record and rebuild dependencies

A virtual environment is disposable. The files that describe it are not. Pick one of these and commit it:

  • requirements.txt: write it by hand with the top-level packages, or generate it with python -m pip freeze > requirements.txt. Freezing pins every transitive package too, which is reproducible but noisy.
  • pyproject.toml with a dependencies list, installed with python -m pip install -e . for a package or by a tool such as uv.

Then add .venv/ to .gitignore. To start over, delete the folder and run the three commands again. If rebuilding the environment feels expensive, your dependency list is not complete enough, which is worth knowing early.

Where to put the folder

The common choice is .venv at the repository root. Editors such as VS Code and PyCharm look for it there and offer it as the interpreter. In a repository with several Python services, you have two reasonable layouts:

  • One shared .venv at the root, when all services use compatible versions of the same libraries.
  • One .venv per service folder, when they differ. It costs disk space and gives clean isolation.

Do not copy a venv to another machine or folder. The scripts inside contain absolute paths, so a moved environment breaks in confusing ways. Recreate it instead.

Making a process manager use the venv

Any tool that starts your service has to find the right interpreter. There are two ways, and both are plain shell behaviour.

  1. Activate the environment in the shell that starts the tool. Child processes inherit the changed PATH.
  2. Name the interpreter in the command, for example .venv/bin/uvicorn.

Flisk runs a service whose service.json has a command as a local process, from the service's own folder, and the process inherits your shell's environment. So the first way works: activate, then run flisk up. Flisk does not create or activate a virtualenv itself. Here is a manifest that names the interpreter explicitly, which does not depend on the shell:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": ".venv/bin/uvicorn main:app --reload --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}

The path is relative to the service folder, so put the venv there or adjust the path. On native Windows each command runs through cmd.exe, where the folder is .venv\Scripts, so a team on mixed systems is better off activating the environment than hard-coding the path. The Flisk setup is described in running services without Docker.

Pitfalls

  • Two environments, one project. An editor using .venv while a terminal uses a global Python gives you different results from the same code. Print sys.executable in both.
  • Installing as root with sudo. It writes into the system Python. Activate the venv and install without sudo.
  • Committing the folder. It is large and not portable.
  • Using venv when you need system libraries. A venv isolates Python packages only. A package that needs a C library still needs it installed on the machine, or a container image that has it.

Next step

Once the environment is stable, decide how you will install into it quickly: uv or pip. And if the interpreter version itself keeps drifting between machines, see how to pin the Python version.

Questions people ask

Do I need to activate a virtual environment every time?

Only if you want python and pip to resolve to it. You can always run .venv/bin/python directly, and editors and process managers can be pointed at that path.

Should the venv folder be committed to git?

No. Commit requirements.txt or pyproject.toml and add .venv/ to .gitignore. The environment can be rebuilt from those files.

Can I move or rename a virtual environment?

Not safely. Its scripts contain absolute paths. Delete it and create a new one with python3 -m venv .venv.
