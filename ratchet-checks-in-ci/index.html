Ratchet checks in CI: improve a metric without a big-bang fix

A ratchet fails the build only when a number gets worse. Use it to pay down lint warnings, missing types or untested files one pull request at a time.

A ratchet is a CI check that stores a baseline number and fails when a pull request makes it worse. It lets a messy codebase improve without one giant cleanup, because the rule is only "do not go backwards".

When a ratchet beats a strict rule

You turn on a strict lint rule and 1,400 files break. You cannot fix them in one PR, and you cannot leave the rule off. A ratchet fixes this: record today's count, fail if the count rises, and let the number fall as people touch files.

Good ratchet metrics are countable by a script: lint warnings, any types, TODO comments, files without tests, bytes in a bundle, slow tests.

A simple ratchet in shell

Store the baseline in a file in the repo, so changes to it show up in review:

#!/usr/bin/env bash
set -euo pipefail
current=$(grep -rn ': any' src --include='*.ts' | wc -l | tr -d ' ')
baseline=$(cat ratchets/any-count.txt)
echo "any types: $current (baseline $baseline)"
if [ "$current" -gt "$baseline" ]; then
  echo "Count went up. Remove the new any, or justify it in the PR."
  exit 1
fi
if [ "$current" -lt "$baseline" ]; then
  echo "Improved. Run: echo $current > ratchets/any-count.txt"
fi

Lower the baseline in the same PR

When the number drops, the author should commit the new baseline. Otherwise the next PR can spend the improvement by adding the same number back. You can make this automatic: have the check fail when the current value is below the baseline too, with the message "update the baseline". That is stricter, but it locks every gain in.

Pitfalls

  • Moving the metric, not the problem. Renaming any to unknown as any passes the grep. Pick a metric that is hard to game, or review the diff of the baseline file.
  • A baseline nobody owns. Name a person or team for each ratchet, so a stuck number has someone to ask.
  • Merge conflicts on the baseline file. Keep one file per metric, so two PRs rarely touch the same one. When a conflict happens, take the lower of the two numbers.
  • Noisy numbers. Coverage and timing move without code changes. Give them a tolerance, for example fail only if coverage drops more than 0.5 points.

Show ratchets on a scoreboard

Ratchets are most useful when everyone sees the numbers. Print them in one place and track them over time, as described in a CI scoreboard for repo health. A ratchet nobody can see tends to be forgotten, and then somebody raises the baseline to get a PR through.

Questions people ask

Should a ratchet ever be allowed to go up?

Rarely, and on purpose. If you raise the baseline, do it in its own commit with a reason in the message so reviewers see it.

Is a ratchet the same as a threshold?

A threshold is a fixed limit everyone must meet. A ratchet uses the current value as the limit, so it works for repos that do not meet the ideal yet.
