Testing and evaluating AI agents

LLM-as-judge pitfalls and how to avoid them

Using a model to grade a model is useful and risky. Learn the common biases, how to write a grading prompt, and how to check the judge against human labels.

A model can grade fuzzy qualities such as tone or helpfulness, but it has biases: it favours longer answers, favours its own style, and can be swayed by the answer's confidence. Use a judge only for things code cannot check, give it a narrow rubric, and measure it against human labels before you trust it.

Use a judge last, not first

If a rule can be checked by code, check it by code. Did the agent call the right tool? Is the JSON valid? Does the answer contain the order number? Those are cheaper, faster and never disagree with themselves. Keep the judge for open questions like "is this explanation clear for a beginner?". More on the code side in deterministic graders.

Know the usual biases

  • Length bias: longer answers get higher scores even when they are padded.
  • Position bias: in side-by-side comparisons, the first or second answer wins more than it should.
  • Self-preference: a model tends to rate text that sounds like its own output higher.
  • Leniency: judges often pass answers a careful human would fail.

Do not take these on faith for your case. Test for them with a small experiment, such as swapping answer order and seeing whether scores flip.

Write a narrow rubric

Ask one question per judge call, with explicit pass and fail conditions, and ask for the reasoning before the verdict. Return a structured result so code can read it.

You are grading one answer. Question: did the answer tell the user
how to cancel their plan, with the exact menu path?

Answer to grade:
{answer}

Reply as JSON: {"reason": "one sentence", "pass": true or false}
Fail the answer if the menu path is missing or invented.

Use binary pass or fail where you can. A 1 to 10 scale produces noisy numbers that hide changes.

Check the judge against humans

Label 30 to 50 outputs yourself, then run the judge on the same outputs and compare. Count agreement, and read every disagreement. If the judge agrees with you 90 percent of the time and its mistakes are harmless, use it. If not, rewrite the rubric or drop the judge. Redo this check when you change the judge model or the rubric.

Reduce the risk further

  • Use a different model family as judge than the one being tested, where practical.
  • Run the judge at temperature 0 and pin the model version.
  • For comparisons, run both orders and count a win only if it holds in both.
  • Never let the agent see the rubric or the judge's output during the run.

The last point is the heart of the matter: a model that grades its own homework will learn to please the grader. Keep the final decision in a score that code computes, as in baselines and ratchets.

Questions people ask

Can I use the same model as agent and judge?

You can, but expect self-preference. A different model family is safer, and a human-labelled check tells you how much it matters.

Is a 1 to 10 score useful?

Usually not. Models cluster scores around a few values. Binary pass or fail on a narrow rule is more stable and easier to act on.
