How to generate a wrangler.toml from service.json

A Worker needs a name, an entry file, a compatibility date and a list of secrets. Most of that already sits in your manifest.

To create a Cloudflare Workers config from a Flisk project, run flisk export wrangler --resource <name>. It writes a wrangler.toml next to that resource, with the Worker name, the entry file, a compatibility date and, if you ask for one, a custom domain route. Secret values are never written. You set them in Cloudflare with wrangler secret put, then deploy with the wrangler command.

The general approach

A Worker is configured by wrangler.toml (or wrangler.jsonc). The minimum is a name, a main entry file and a compatibility_date that pins the runtime behaviour. Routes, bindings and variables are added as you need them. You can write this file by hand in a minute; the cost shows up later when the local manifest and the deploy file disagree about the entry file or which variables exist.

The Flisk way

The exporter needs to know which resource is the Worker, so --resource is required:

flisk export wrangler --resource edge --dry-run
flisk export wrangler --resource edge --route api.example.com

With --dry-run it prints the file and writes nothing. A real run for a Hono service produces:

# Written by `flisk export wrangler` from service.json. Nothing was deployed and no DNS record was created.
name = "edge"
main = "src/index.ts"
compatibility_date = "2026-11-14"

routes = [{ pattern = "api.example.com", custom_domain = true }]

# Environment from service.json, by name only. Set each one with `wrangler secret put <NAME>`:
#   API_TOKEN
#   ORIGIN_URL

How each line is decided:

  • name comes from the resource name.
  • main comes from main in the resource's package.json, or else the first file that exists from src/index.ts, src/index.js, src/worker.ts, src/worker.js, index.ts and index.js.
  • compatibility_date is the day you run the export. That pins the runtime to today's behaviour, so re-running the export later changes it. Review the date in the diff.
  • routes appears only when you pass --route. It writes a custom domain route. Wildcard patterns are refused.
  • Environment names appear as a comment, one per variable. Names only.

The file is written in the resource's folder, for example services/shop/edge/wrangler.toml, so run wrangler from there.

The Worker check

Not every service can run on Workers. The exporter looks at the resource and refuses one that has a Dockerfile, or that has no wrangler, @cloudflare/workers-types or hono dependency. In that case the message points you to flisk export render for Docker or Node services. If you know what you are doing, --allow-non-worker overrides the check. That is the flag you need for a service that Flisk scaffolded with a Dockerfile for local use but whose code is Worker-compatible.

An important detail for Hono: the local server and the Worker use different entry shapes. The scaffolded Hono service ends with export default { port, fetch: app.fetch }, which is a fetch handler and also what a Worker expects. Anything that touches Node-only APIs (the file system, native modules, long-lived sockets) will still fail on the Workers runtime. Test with wrangler dev before you deploy.

Secrets and deploy

  1. Install wrangler and log in: npx wrangler login.
  2. For each name in the comment run npx wrangler secret put API_TOKEN. Wrangler asks for the value on the terminal, and it is stored in Cloudflare, not in a file.
  3. Check locally with npx wrangler dev.
  4. Deploy with npx wrangler deploy.

The listed names are all keys under env in service.json, including harmless ones such as a URL or a log level. Plain, non-secret values can instead go in a [vars] block in wrangler.toml, which you write yourself. Use wrangler secret put for anything sensitive.

Pitfalls

  • The custom domain needs a Cloudflare zone. The exporter does not create DNS records. Add the domain to your Cloudflare account first.
  • Bindings are not exported. KV, D1, R2 and queues need entries you write by hand, and the local database is not a D1 database.
  • Re-running overwrites. Use --force only when you have nothing hand-edited in the file, or copy your additions back from the diff.
  • Not every service belongs on Workers. A service with a long-running connection to Postgres, or one that needs a full Node runtime, is usually simpler on a container host. See from local to Render.

Before you ship, apply the same naming rule to every environment variable: env var names, not values.

Questions people ask

Does flisk export wrangler deploy my Worker?

No. It writes wrangler.toml next to the resource and stops. It does not run wrangler deploy, create DNS records or call the Cloudflare API. You deploy with the wrangler command yourself.

Why does the exporter refuse my service?

It checks that the resource looks like a Worker. A resource with a Dockerfile, or one without a wrangler, @cloudflare/workers-types or hono dependency, is refused unless you pass --allow-non-worker. For Docker or Node services the error suggests flisk export render.

Where do secret values go?

Into Cloudflare, with wrangler secret put NAME. The generated file lists the variable names in a comment and never contains values.
