DevSpace vs Garden for Kubernetes development

Two Kubernetes dev tools with different centers of gravity: the developer's session versus the dependency graph.

DevSpace is built around the developer session: you run devspace dev and your code syncs into a pod, with ports forwarded and a terminal available. Garden is built around a graph of actions (build, deploy, run, test) with caching, aimed at a whole team or a CI pipeline. If you mainly want fast edits in a cluster, start with DevSpace. If you want repeatable builds and tests across many services, look at Garden.

What they share

Both assume your app runs on Kubernetes and that developing against a real cluster, local or remote, is worth the extra weight. Both read a config file at the repo root, build images, deploy with Helm or manifests, and support file sync so interpreted code does not need an image rebuild. Both can target a shared cluster, which is the case where they earn their place.

DevSpace in practice

DevSpace is a client-only CLI configured with devspace.yaml. The center of the workflow is dev mode. You declare which workload to replace or attach to, which folders to sync, which ports to forward and optionally a terminal to open. Then devspace dev does the rest. devspace deploy is the non-interactive counterpart, and pipelines in the config let you script the sequence. It works with a namespace in a shared cluster, which suits "my own namespace on the team cluster" workflows.

Strengths: the interactive loop feels direct, and the config can stay small for a single service. Costs: the model is per-developer, so shared test and build logic across many services is less central.

Garden in practice

Garden is configured with garden.yml files, usually one per module or service, plus a project file. Each file declares actions such as a container Build, a Deploy, a Run for tasks like migrations and a Test. Garden links them into a graph from their references and runs only what is needed. It tracks versions of the inputs, so it can skip an unchanged build or test. garden deploy and garden test work from the same graph, and garden dev gives an interactive session.

Strengths: dependency awareness across services, caching, and one definition for local, CI and shared environments. Costs: more concepts to learn, and the graph is something you maintain.

Run a one-service trial of each before you commit. The first hour shows whether the config model matches how your team thinks.

When the cluster is the problem

Both tools inherit the cost of Kubernetes: slow image pulls, cluster cost, network latency to a remote cluster and RBAC to sort out. If your daily work is application code that only becomes Kubernetes at deploy time, a laptop-only loop is simpler. One such option is Flisk, which runs services as local processes or on Docker and Tilt and does not use a cluster. It is for the inner loop only and leaves deploys to your Helm or Argo setup.

See local development without Kubernetes for how to decide.

Pitfalls

  • Shared clusters. Namespaces isolate names, not resources. One developer's runaway pod can still use up the node's memory.
  • Sync is not parity. A synced file runs in a container that is already running, so build-time steps are skipped. Rebuild before you trust a result.
  • Cost. A remote dev cluster per developer adds up. Set auto-shutdown or namespace cleanup.
  • Version drift. Config schemas change between major versions of both tools. Pin the tool version in your repo docs.

If the cluster is remote and you need to reach real services from your laptop, the next article covers Telepresence and mirrord.

Questions people ask

What is the difference between DevSpace and Skaffold?

Skaffold centers on a build and deploy pipeline you can reuse in CI. DevSpace centers on an interactive dev mode with sync, port forwarding and a terminal.

Does Garden cache test results?

Garden tracks the versions of an action's inputs and can skip work that has not changed, including builds and tests.

Do I need a remote cluster for DevSpace or Garden?

No. Both work with a local cluster such as kind or minikube, as well as a shared remote one.
