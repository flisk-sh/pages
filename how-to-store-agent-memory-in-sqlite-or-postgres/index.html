Agent memory and context engineering

How to store agent memory in SQLite or Postgres

A plain table of small notes, scoped by user and project, gets most agents further than a vector database. Schema, queries and the upgrade path to embeddings.

Use one table of small notes with a scope, a text body, a timestamp and a source. SQLite is enough for a single-process agent, Postgres when several services or users share the store. Add embeddings later, only if keyword search stops being enough.

A schema to start with

create table memory (
  id         integer primary key,
  scope      text not null,      -- "user:42", "project:shop", "global"
  kind       text not null,      -- "preference", "decision", "fact"
  body       text not null,      -- one self-contained sentence
  source     text,               -- session id or url
  created_at text default (datetime('now')),
  expires_at text,
  deleted    integer default 0
);
create index memory_scope on memory(scope, deleted);

The deleted flag and expires_at matter. You will need to remove bad notes, and some facts should lapse.

Writing notes

Have the agent propose a note, then validate it in code before inserting: non-empty, under 300 characters, no secrets pattern, and not a duplicate of an existing body in the same scope. Let the model write the sentence, but let your code decide whether it is stored.

Reading notes

Start with scope filtering and recency, which is fast and predictable.

select body from memory
where scope in ('global', 'user:42', 'project:shop')
  and deleted = 0
  and (expires_at is null or expires_at > datetime('now'))
order by created_at desc
limit 20;

For more relevance, add full-text search: SQLite has FTS5, and Postgres has tsvector and to_tsquery. Rank by match, then load the top 5 into the window.

When to add embeddings

Add a vector column or index when users write memories in many different phrasings and keyword search misses them. Postgres with the pgvector extension keeps notes and vectors in one place. Measure first: take 30 real questions and check how often the right note appears in the top 5, with and without vectors. The retrieval details are in RAG and vector databases locally.

Pitfalls

  • Per-user scope must be enforced in code, not left to the prompt.
  • Do not store secrets or raw personal data in notes. Notes get loaded into prompts and logs.
  • Cap how many notes enter a call. Twenty good ones beat two hundred mixed ones.

Run Postgres or SQLite beside your agent with checkpointed sessions so both live in the same local stack.

A forgetting policy

Decide up front how memory shrinks. A simple policy: preferences never expire, project facts expire after 90 days unless used, one-off decisions expire after 30. Update last_used_at when a note is loaded into a call, and delete notes unused for a long time. Show users a list of what is stored about them with a delete button. This keeps the store small and the agent honest, and it makes privacy requests easy to honour.

Questions people ask

SQLite or Postgres?

SQLite for one process and a local tool. Postgres when several services, workers or users write to the store at once.

Should the agent write to memory directly?

Let it propose notes, then validate and insert them in your own code so the rules for what gets stored are enforced.
