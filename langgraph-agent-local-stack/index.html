Running AI agents locally

Run a LangGraph agent locally with tools and resumable runs

LangGraph supplies checkpoints and replay. The rest of a local stack is a tool server, a start order and an HTTP wrapper. This is a working setup you can break on purpose.

To run a LangGraph agent locally with durable runs, give the graph a checkpointer, give every run a thread_id, and resume unfinished threads when the process starts. Flisk has a langgraph starter that does this with a JavaScript StateGraph, an MCP tool server and a file checkpointer, all as local processes.

What LangGraph gives you and what it leaves to you

LangGraph models an agent as a graph of nodes that read and write shared state. After each node it can save a checkpoint under a thread_id. If the process dies, calling the graph again on the same thread with no new input continues from the last checkpoint, and nodes that finished do not run again. That is the durability story.

It does not decide where the checkpoint lives (you pick a saver), how your HTTP API starts and resumes runs, or how the graph reaches its tools and database. Those are the parts of a local stack, and they are what a starter has to settle.

The plain approach

Write a small server around the graph. A POST /runs creates a thread id, stores the run in a file or table, and starts graph.invoke(input, { configurable: { thread_id } }) without waiting for it. On startup, read the stored runs and resume the ones still marked running by invoking with null input. For Python, the shape is the same with thread_id in the config and a saver such as the SQLite or Postgres one.

Then add the surroundings: install dependencies before the first start, start the tool server before the agent, and keep three logs readable. That glue is what a project file replaces.

The Flisk langgraph starter

Install Flisk with npm install -g @flisk-sh/flisk and create the project:

flisk project langgraph --path langgraph-demo --yes
cd langgraph-demo
flisk up
curl -X POST localhost:4400/runs -H 'content-type: application/json' \
  -d '{"goal":"Explain flisk and mcp and retries"}'
curl localhost:4400/runs

The graph plans a goal into topics, researches each topic with the lookup tool on the MCP tool server, writes an answer and checks it. If the checker finds a topic with no note, the graph goes back to research. The project has three services:

setup/service.json   one-shot job: npm install in ../agent, restart "no"
tools/service.json   appType "mcp", port 4401
agent/service.json   appType "backend", port 4400, dependsOn ["setup", "tools"],
                     env TOOLS_URL=http://localhost:4401

Because agent depends on setup, the packages are installed (with pinned versions in agent/package.json) before the agent starts. Nothing needs Docker.

Prove that a run survives a crash

Every node's result is a LangGraph checkpoint written to agent/.data/checkpoints.json by a small file saver. The run list is in agent/.data/runs.json. On start, the agent resumes every run that had not finished, from its last checkpoint. To see it, slow the nodes down, start a run and kill the process:

STEP_DELAY_MS=2000 flisk up
curl -X POST localhost:4400/runs -H 'content-type: application/json' \
  -d '{"goal":"Explain flisk and mcp and retries"}'
# find the agent's process id, then:
kill -9 <pid>
curl localhost:4400/runs

Flisk restarts the agent. The run shows a resumed count of 1 and finishes without repeating the nodes that were done. If it fails to resume, read the agent's log first (see reading logs from every service).

Retries and planning

A node that throws, for example because the tool server is restarting, is retried by LangGraph's retryPolicy: up to 5 attempts (MAX_ATTEMPTS), starting 1 second apart (RETRY_BACKOFF_MS) and doubling. Without an API key the planning node splits the goal with simple rules, so the whole thing works offline. Set ANTHROPIC_API_KEY and it asks a Claude model for the topics instead, falling back to the rules if the call fails. GET /runs says which planner ran.

Pitfalls

  • A file saver is for one process. It rewrites one JSON file, which is fine on a laptop and wrong for several writers. The starter's own advice is to swap in @langchain/langgraph-checkpoint-postgres for production.
  • Resume repeats a half-run node. A node that was running when the process died runs again. Make nodes that write to the outside world idempotent.
  • Python graphs. The starter is JavaScript. A Python LangGraph service runs fine as a bring-your-own container or as a local process with a command, using the same dependsOn and env fields; only the language changes. See bring your own Dockerfile.
  • Not a LangGraph replacement. Flisk starts and wires the processes. Step logic, retries and checkpoint format stay in your framework.

To add a database to this stack, continue with an agent with a database and a queue.

Questions people ask

Does the Flisk langgraph starter use Python?

No. It is JavaScript (LangGraph.js) with a file-based checkpointer. A Python LangGraph service can run next to the same tool server as a local process or a container.

Do I need an API key for the langgraph starter?

No. Without ANTHROPIC_API_KEY the plan node uses simple rules, so the starter runs offline. With a key it asks a Claude model to plan and falls back to the rules if the call fails.

What happens to a run when the agent process is killed?

On start, the agent resumes every run that had not finished from its last LangGraph checkpoint, and nodes that already finished do not run again.
