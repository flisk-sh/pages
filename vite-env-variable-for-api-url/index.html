Frontend dev servers and APIs

How to set the API URL in Vite with env variables

The frontend needs to know where the API is, and that address changes per machine and per environment. Here is how Vite reads it, and what bites people.

In Vite, put the API address in a variable that starts with VITE_, such as VITE_API_URL, and read it with import.meta.env.VITE_API_URL. Vite loads .env files at start-up, exposes only the prefixed names to the browser code, and replaces them with their values in the bundle. A variable without the prefix is undefined in the client.

Where the value comes from

Vite reads these files from the project root, in this order of increasing priority:

  • .env, always loaded
  • .env.local, loaded and ignored by git in the default Vite template
  • .env.development or .env.production, chosen by the mode (vite runs in development, vite build in production)
  • .env.development.local and .env.production.local

A variable that already exists in the shell when Vite starts beats all of the files. That is useful: VITE_API_URL=http://localhost:4010 npm run dev overrides the file for one run.

# .env
VITE_API_URL=http://localhost:4000

// src/api.ts
const API_URL = import.meta.env.VITE_API_URL ?? '';

export async function getItems() {
  const res = await fetch(API_URL + '/api/items');
  if (!res.ok) throw new Error('API returned ' + res.status);
  return res.json();
}

For TypeScript, declare the name in src/vite-env.d.ts by extending ImportMetaEnv, so a typo becomes a compile error instead of an undefined at run time.

Why the value feels frozen

Vite does not ship a way for the browser to ask the server for env values. The text import.meta.env.VITE_API_URL is replaced by the string. In development that happens when the dev server starts, so if you change a shell variable or an env file and the page still shows the old value, restart the dev server and hard reload. In a production build the value is fixed forever in the output files: you build once per environment, or you load a small config.json at start-up instead.

Leave the variable empty and call relative URLs when you use a dev server proxy. The code above then sends /api/items to the Vite origin, which forwards it. See how to proxy API requests in the Vite dev server.

The Flisk way, local processes

When a frontend has a command, Flisk runs it as a normal process and passes the manifest's env to it, plus PORT. Vite reads the process environment, so a VITE_ name in env is visible in the code:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "VITE_API_URL": "${VITE_API_URL:-http://localhost:4000}" }
}

Values in env may use ${VAR} or ${VAR:-default}. For a local process Flisk resolves them from your shell first, then the project .env, then the service's own .env next to its service.json, then the default. So a teammate can point the frontend at a different API with a one-line .env change, and the committed manifest does not move. Without Docker there is no generated frontend env file: you pass the address yourself, as above.

The Flisk way, Docker

In Docker mode Flisk writes .autogenerated/.env.frontend.autogenerated for each frontend and Compose passes it to the container. VITE_API_URL (and NEXT_PUBLIC_API_URL for Next.js) is the backend's gateway route, http://api.<project>.localhost/api/<backend name without -api>, or the backend's apiPath if it sets one, with the port added when the gateway is not on 80. Each backend, mcp or agent resource listed in the frontend's dependsOn also gets a VITE_<NAME>_API_URL line.

The file is generated, so do not edit it. After you change dependsOn, backendName or apiPath, run flisk restart <frontend>: the container reads the file when it starts and the value ends up in the browser bundle. If you are unsure what the frontend received, open that file. If a frontend has no backend at all, VITE_API_URL falls back to a route that serves Flisk's own API, not yours.

Pitfalls

  • Missing prefix. API_URL=... in .env is invisible to client code. Rename it, or change envPrefix in the config.
  • Quotes and spaces. Keep values simple. VITE_API_URL = "http://..." with spaces around the equals sign is a common cause of an empty value.
  • Not a secret store. Everything with the prefix goes to every visitor. See secrets in Vite and Next.js public variables.
  • Wrong directory. Vite reads .env next to vite.config.ts, not the monorepo root, unless you set envDir.

Questions people ask

Why is import.meta.env.VITE_API_URL undefined?

The name probably lacks the VITE_ prefix, the .env file is not next to vite.config.ts, or the dev server was started before you added it. Fix the name or location and restart the dev server.

Can I change a VITE_ variable without rebuilding?

In development, restart the dev server. In a production build the value is fixed in the output, so build again or load a runtime config file instead.

What overrides what in Vite env files?

A variable set in the shell wins. Then mode-specific local files, mode-specific files, .env.local and finally .env.
