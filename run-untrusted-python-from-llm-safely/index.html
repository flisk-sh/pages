How to run untrusted Python from an LLM safely

Why exec() and restricted Python are not safe, and a layered way to run model-written Python with resource limits, a clean environment and output caps.

Do not use exec() or eval() in your own process for model-written code, and do not trust "restricted Python" tricks. Run the code in a separate process inside a container or microVM, with limits on time, memory and network, and read only its captured output.

Why in-process sandboxes fail

Python can reach almost anything from almost anywhere. Stripping __builtins__ or blocking import os has been bypassed again and again through object attributes and introspection. If the code runs in your process, it can read your variables, including secrets. Treat the process boundary as the minimum.

Layer 1: a separate process with limits

Even before containers, you can cap a child process on Linux with resource. This is a safety net for accidents, not a security wall.

import resource, subprocess, sys

def limit():
    resource.setrlimit(resource.RLIMIT_CPU, (5, 5))
    resource.setrlimit(resource.RLIMIT_AS, (256 * 2**20, 256 * 2**20))
    resource.setrlimit(resource.RLIMIT_NPROC, (32, 32))

p = subprocess.run(
    [sys.executable, "-I", "job.py"],
    capture_output=True, text=True, timeout=10,
    preexec_fn=limit, env={},
)
print(p.stdout[:4000])

-I runs Python in isolated mode, and env={} hands the child an empty environment so it cannot read your tokens.

Layer 2: a container or microVM

Put that child process inside a sandbox. The recipe is in running AI code in Docker. The container gives you the file and network walls that rlimit cannot.

Control what goes in and out

  • Input: pass data as files in a read-only mount, not by interpolating it into a command string.
  • Output: cap bytes, strip control characters, and treat the text as untrusted when you show it to the user or feed it back to the model.
  • Dependencies: pre-install an allowed set. Do not let the agent install arbitrary packages at run time without a network policy.

Handle the result carefully

The output of sandboxed code is data from an untrusted source. If you feed it back into the model, it can contain instructions. Keep tool results clearly separated from your system prompt, and do not let one tool result trigger high-impact actions without a check. Also log every run with its input hash, exit code and duration so you can investigate odd behaviour.

Pitfalls

A common mistake is to run the code in a sandbox but then pickle.load or eval its output on the host. Return plain text or JSON and parse it with a strict parser. Another is sharing one long-lived sandbox between users: files and processes from one session leak into the next. Create a fresh sandbox per user session, and destroy it afterwards.

Questions people ask

Is RestrictedPython safe for this?

It reduces some risks for trusted-ish scripts, but it is not a security boundary for hostile code. Use OS-level isolation instead.

What about a Jupyter kernel?

A kernel is just a process with your user permissions. Run the kernel itself inside a container or microVM, not on your host.
