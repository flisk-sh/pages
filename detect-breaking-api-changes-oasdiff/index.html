How to detect breaking API changes before you merge

Most API outages from a deploy are a field someone renamed. A diff of the spec catches that in the pull request, not in production.

To detect breaking API changes, keep the OpenAPI spec in git and compare the version on your branch with the version on the main branch using a diff tool such as oasdiff. oasdiff breaking base.yaml revision.yaml lists removed paths, new required parameters and changed types, and exits non-zero when you ask it to, so the pull request fails before a client does.

What counts as breaking

A change is breaking when a client that worked yesterday can fail today without changing its own code. Rules of thumb for JSON over HTTP:

  • Breaking: removing or renaming a path, method, field or enum value that clients read; making an optional request field required; adding a required query parameter; changing a field's type; narrowing what you accept (a shorter maximum length); changing a status code that clients branch on.
  • Usually safe: adding an optional request field; adding a new response field (if clients ignore unknown fields, which you must tell them to do); adding a new endpoint; widening what you accept.
  • Depends on the client: adding a new value to a response enum. A client with an exhaustive switch may crash. Many diff tools flag this one for that reason.

Decide your policy once and write it down. For public APIs the safe default is: anything in the first list needs a new version (see running two API versions side by side) and a deprecation period (deprecating an endpoint).

Compare two specs

oasdiff is a free command line tool for OpenAPI files. Install it with brew install oasdiff or from its GitHub releases, or run it from its container image. Get the spec from your main branch and compare:

git show origin/main:openapi.yaml > /tmp/openapi.base.yaml
oasdiff breaking /tmp/openapi.base.yaml openapi.yaml --fail-on ERR

Each finding has a severity. --fail-on ERR makes the exit code non-zero when there is an error-level change, so you can use the command as a CI step. For a human-readable list of everything that changed, breaking or not, use the changelog form:

oasdiff changelog /tmp/openapi.base.yaml openapi.yaml

Paste that into the pull request description and reviewers see the API change without reading the YAML. If you generate the spec from code, the generated file is the input, as explained in spec first or from code.

Check against the spec the running service really serves

A committed file can be stale. The strongest check compares the base spec with what the new code actually serves. With a Flisk project of local processes, wrap it in a script:

#!/usr/bin/env bash
set -euo pipefail

cleanup() { flisk down || true; }
trap cleanup EXIT

flisk up --wait --wait-timeout 300
curl -fsS http://localhost:4000/openapi.json -o /tmp/openapi.current.json

git show origin/main:openapi.json > /tmp/openapi.base.json
oasdiff breaking /tmp/openapi.base.json /tmp/openapi.current.json --fail-on ERR

flisk up --wait starts the project in the background and returns once every service is healthy, or exits 1 on failure or timeout (--wait-timeout is in seconds). flisk down in the trap stops everything even when the diff fails. Replace the URL and port with your service's, as written in its service.json. This catches the case where someone forgot to regenerate the committed file.

Deal with an intended break

Sometimes you mean it. Do not turn the check off. Options, in order of preference:

  1. Add the change under a new version path, keep the old one, and mark it deprecated.
  2. If no external client exists (an internal API consumed by one repo you control), change both sides in one pull request and note it. Some teams use a label such as breaking-change-ok that CI reads to skip the failure.
  3. Use the tool's ignore file for a single known item, with a comment that says why.

Pitfalls

  • The spec is not the behavior. A diff of two specs cannot see that a server now returns null where it used to omit a field, if the spec says nothing about it. Pair this with request-level tests (API tests as files).
  • Nothing about consumers. The diff says what changed, not who uses it. If you have many clients, consumer-driven contract tests (Pact) tell you who would break.
  • Base branch drift. Compare against the target branch of the pull request, not a fixed old tag, or you will report changes that were already merged.
  • Tool version. Pin the oasdiff version in CI. Rules for what counts as breaking can change between releases.

Next, make the spec itself consistent with a linter (Spectral) so the diff has clean input.

Questions people ask

Is adding a field to a response a breaking change?

Usually not, as long as clients ignore fields they do not know. Say so in your API guidelines. Adding a value to a response enum can still break strict clients.

How do I make oasdiff fail a CI job?

Run oasdiff breaking base.yaml revision.yaml --fail-on ERR. The exit code is non-zero when an error-level change is found.

Does Flisk detect breaking API changes?

No. Flisk starts your services so you can fetch the live spec. The comparison is done by a tool such as oasdiff.
