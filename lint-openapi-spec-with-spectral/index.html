How to lint an OpenAPI spec with Spectral and fail CI on mistakes

A linter turns your API style guide from a document nobody reads into a check that runs on every pull request.

Spectral is a linter for OpenAPI and other JSON or YAML files. Run npx @stoplight/spectral-cli lint openapi.yaml with a ruleset file that extends spectral:oas, and it reports missing operation IDs, broken references, unused components and any custom rule you add. Put the same command in CI and the style guide enforces itself.

Why lint a spec at all

An OpenAPI file is code that other people generate clients from. Duplicate operationId values produce clashing function names in a generated SDK. A missing response schema turns into any in the client. A path called /getOrders next to /orders tells readers nobody was in charge. None of that breaks a build today and all of it costs time later. A linter catches it while the change is small.

Run it once

echo 'extends: ["spectral:oas"]' > .spectral.yaml
npx @stoplight/spectral-cli lint openapi.yaml

The spectral:oas ruleset ships with the tool. Each finding has a rule name, a severity (error, warn, info or hint), and a path into the document, for example paths./orders.get. Start by running it on an existing spec and reading the output before you change anything. The first run on an old file usually shows a long list. Do not fix everything at once: decide which rules you agree with, and turn the others off.

Tune the rules

Rules are switched on, off or re-rated in .spectral.yaml:

extends: ["spectral:oas"]
rules:
  operation-description: off
  operation-tags: warn
  info-contact: off
  paths-kebab-case:
    description: Path segments use lowercase kebab-case
    severity: error
    given: $.paths[*]~
    then:
      function: pattern
      functionOptions:
        match: "^(/([a-z0-9-]+|\\{[a-zA-Z]+\\}))+$"

The custom rule has three parts. given is a JSONPath query for the nodes to check; the trailing ~ selects the property name, here each path string. then names a function (pattern is built in) and its options. This one accepts /orders/{orderId} and rejects /getOrders and /Order_Items.

Other useful custom checks use the same shape: every operation has an operationId, every 4xx response uses your error schema, every list endpoint documents a limit parameter. Keep the list short. Ten rules the team respects beat sixty that people disable.

Decide what fails the build

By default Spectral exits with a non-zero code when it finds errors. To also fail on warnings, pass the failure severity:

npx @stoplight/spectral-cli lint openapi.yaml --fail-severity warn

A practical rollout: leave new strict rules at warn for a few weeks, fix what they find, then raise them to error. The command above is the whole CI step, and it works the same in any system that can run Node.

Pin the version in package.json (npm install --save-dev @stoplight/spectral-cli, then npx spectral lint ...) so a new release of the ruleset does not turn your build red on a Monday.

Read the output

A finding looks like a compiler message: a line and column in the file, the severity, the rule name and a sentence. Fix the oldest and most common rule first, because one root cause (for example a missing operationId pattern) often explains dozens of lines. When a rule is wrong for one place only, add an override for that path instead of switching the rule off for the whole file. Keep a short note next to the override saying why, so the next reader does not remove it by accident or copy it everywhere.

Rules also work on examples. A rule that requires every response schema to have an example pays back twice: documentation reads better, and a mock server such as the one in the Prism guide returns realistic data instead of placeholders.

Lint the spec you generate, too

If the spec comes from code, lint the exported file, not the source. Generated specs often fail rules about descriptions and examples, and that is useful feedback: it tells you which models and routes need documentation. The export step is described in spec first or from code.

Pitfalls

  • Linting is not validating behavior. A clean report says the document is well formed and follows your style. It does not say the server matches it. Test that separately with a contract test or a tool that sends requests from the spec.
  • Huge specs are slow to read. Split with $ref into several files, and lint the entry file. Spectral resolves references.
  • Do not lint with an editor plugin only. Editors differ. CI is the place that everyone shares.
  • Style rules need an owner. Someone has to say yes or no to a new rule, or the ruleset grows into noise.

After style, the next question is compatibility: which edits to the spec would break existing clients. That is covered in detecting breaking changes with oasdiff.

Questions people ask

How do I make Spectral fail on warnings?

Add --fail-severity warn to the lint command. By default only errors produce a non-zero exit code.

Does Spectral lint only OpenAPI?

No. It also lints AsyncAPI and any JSON or YAML document for which you write rules, but the built-in spectral:oas ruleset targets OpenAPI.

Can a clean Spectral run prove my API matches its spec?

No. It checks the document, not the running server. Use contract tests or a spec-driven request tool for behavior.
