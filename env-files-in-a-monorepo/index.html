Env files in a monorepo: root .env or one per app?

Tools look for .env in different folders. The result is an app that works from one terminal and not from another.

Use one root .env.example that lists every variable, keep real values in per-app .env files for what is app-specific, and put only truly shared values in a root file that you load explicitly. The reason is that most tools read .env from the app folder, not from the repo root, so a single root file often goes unread.

Who reads which file

  • Vite loads .env files from its project root, the folder it runs in, and exposes only variables that start with VITE_ to browser code. The envDir option points it at another folder, such as the repo root.
  • Next.js loads .env files from the app folder. A file in the workspace root is not read unless you load it yourself in next.config or start the process with the variables set.
  • Node reads no .env by default. From Node 20.6 you can pass node --env-file=../../.env. Older setups use the dotenv package or dotenv-cli.
  • Turborepo runs tasks with a filtered environment. In version 2 a task sees only the variables listed under env or globalEnv in turbo.json (plus a short built-in list). It also hashes those values into the cache key. Root .env files should be listed in globalDependencies, so a change invalidates the cache.

That is why "works with pnpm dev in the app folder, fails with turbo dev from the root" happens: the working directory and the filtered environment both changed.

A layout that stays predictable

shop/
  .env.example          every variable, no real values (committed)
  .env                  shared local values (git-ignored)
  apps/
    api/.env            API-only values (git-ignored)
    web/.env            web-only values (git-ignored)

Rules that keep it sane:

  1. Commit .env.example with names and harmless placeholders. Never commit .env.
  2. Put a value in the root file only if two or more apps need it, such as the database URL or the public API address.
  3. Give each variable one owner. If DATABASE_URL is in the root and an app file, nobody knows which wins.
  4. Prefix browser-exposed variables as your framework requires (VITE_, NEXT_PUBLIC_), and keep secrets out of those.

How Flisk resolves values

For a service that runs as a local process, Flisk reads env from its service.json, and each value may use ${VAR} or ${VAR:-default}. Those resolve in this order, first match wins: your shell, the project .env, the service's own .env next to its service.json, then the default.

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "pnpm dev",
  "port": 4000,
  "env": {
    "DATABASE_URL": "${DATABASE_URL}",
    "LOG_LEVEL": "${LOG_LEVEL:-info}"
  }
}

That gives you the root-plus-app layout above without a loader in your code: put shared names in the root .env and app-specific ones in apps/api/.env. Run flisk up --env-file .env.integration to use a different project env file for one run. For a development secret such as an auth key, secrets.generate in service.json makes Flisk append a random value to the project .env once, with mode 0600 on a new file, and keep it across restarts. Flisk prints the names it generated, never the values. flisk config verify and flisk doctor check the manifests, and flisk doctor warns about secret-looking values in public environment variables.

Flisk adds .env to .gitignore when it creates a project. If you set up the repo before, check the ignore file yourself.

Pitfalls

  • Quotes and spaces. Dotenv parsers differ on quotes, export prefixes and inline comments. Keep values simple and compare in two tools.
  • Stale values. Most dev servers read .env at start. Restart after editing.
  • Build-time versus run-time. A Vite or Next.js public variable is baked in at build or start; changing it later has no effect in a running page.
  • Copying the root file into images. See the .dockerignore advice in the Docker build context article.

For debugging a variable that never arrives, see environment variable not loaded in a local service. Then read port assignment in a monorepo, since ports are the other value every app reads.

Questions people ask

Can several apps share one .env file at the repo root?

Yes, but most tools read .env from the app folder, so you must load the root file explicitly, for example with Vite's envDir, node --env-file, or a runner that injects it.

Why does turbo not see my .env values?

Turborepo 2 passes only variables listed in env or globalEnv to a task. Add the names there, and list the .env files in globalDependencies.

Should I commit .env.example?

Yes. It documents every variable with placeholder values. Keep real values in git-ignored .env files.
