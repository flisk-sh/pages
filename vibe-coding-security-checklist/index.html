Vibe coding without the mess

Vibe coding security checklist before you ship

A short, concrete checklist for apps built mostly by an AI: secrets, access control, input handling, dependencies and logging. Run it before anyone else uses your app.

Before you ship an AI-built app, check six things: no secrets in the repo, every route checks who is asking, all input is validated, dependencies are real and pinned, errors do not leak details, and you can see what happened in the logs.

1. Secrets

Search the repo and its history for keys.

git grep -nEi "(api[_-]?key|secret|token|password)\s*[:=]"
git log -p -S"sk-" --all | head

Keys belong in environment variables, with .env in .gitignore. If a key was ever committed, rotate it. Deleting the line is not enough. More in env and secrets for local dev.

2. Access control

The most common bug in generated apps is a route that returns a record by id without checking the owner. For every route that takes an id, confirm the query includes the current user. Test it with two accounts: user B requests user A's record and must get a 403 or 404.

Also check the opposite direction: does the page hide a button for non-admins while the endpoint behind it still works for anyone? Hiding a control in the UI is not access control. The server must enforce it.

3. Input and output

  • Validate type and length on the server, not only in the form.
  • Use parameterised queries, never string-built SQL.
  • Escape user content when rendering HTML.
  • Never pass user input to a shell command or a file path unchecked.

4. Dependencies

Open the dependency file and read every package name. Remove what you did not ask for. Make sure each one exists on the registry and is the package you expect. Commit the lock file so installs are repeatable. Run npm audit or pip-audit if you use those ecosystems.

Prefer fewer, well known packages. Each extra dependency is code you did not read, running with the same permissions as your own.

5. Errors and logs

Turn debug mode off in production. A stack trace shown to a user can reveal paths, queries and keys. Log who did what and when for sign-in, deletes and payments, but never log passwords or tokens.

6. Limits

Add rate limits to sign-in and any endpoint that costs money, such as one that calls a paid model API. Without a limit, one script can run up your bill.

If the app gives a model tools, such as reading files or running code, read AI security for builders. And if something fails the checklist, fix it with a small, committed step (see small steps).

Print this list or keep it in the repo as SHIP.md. Tick each line with the command or file that proves it, not from memory. A checklist you run the same way every time finds more than a clever review you do once.

Questions people ask

Is this checklist enough for a production app with payments?

No. It catches the common mistakes. For payments or sensitive data, get a human security review and use your payment provider's hosted checkout.

Can an AI do the security review for me?

It can find many issues and is worth running as a second pair of eyes, but it misses things and can be wrong. Use it in addition to the checklist, not instead.
