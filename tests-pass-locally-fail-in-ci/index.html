Tests Pass Locally but Fail in CI: What to Check

A checklist of the usual causes when a test passes on your laptop and fails on the runner: versions, time, order, files, network, resources and secrets.

When a test passes locally and fails in CI, something differs between the two environments. The usual suspects are tool versions, timezone and locale, file system case, test order, parallelism, missing services and secrets. Work through them in that order and you will find most causes within minutes.

Versions and installs

Print the versions in CI and compare them with yours. Check the language version, the package manager version and the operating system. Then check the install step. If CI uses npm ci and you use npm install, you may run different dependency versions. A lockfile that is not committed or not in sync is a common cause.

Also look for tools that are installed globally on your machine and not in the project. A test that calls jq, git with a specific config or a system library works for you because you have it.

Time, locale and randomness

The runner's timezone is usually UTC. Tests that format dates, compare 'today' or run near midnight can fail only there. Locale affects sorting and number formatting. Set the timezone explicitly in the failing test run to reproduce:

TZ=UTC npm test
TZ=Pacific/Auckland npm test

Random data and unseeded generators fail rarely and look like flakes. Print the seed on failure and let the test accept it as input.

Files, case and line endings

macOS and Windows file systems are usually case insensitive. Linux is case sensitive. An import of ./Utils for a file called utils.js works locally and fails on Linux. CI also starts without ignored files: your .env, generated code, build output and fixtures that are in .gitignore. If a test needs them, the repo must create them.

Check git status --ignored to see what exists on your machine only.

Order, parallelism and resources

Tests that pass alone and fail together share state: a database row, a port, a temp file, a global. CI may run files in a different order or in parallel. Run the suite in random order and with the same worker count as CI. Hosted runners have limited CPU and memory, so tests with tight timeouts fail there first. Raise the timeout to confirm the cause, then fix the slow test. See debugging hangs and timeouts for more.

Make the gap smaller for good

After you fix the cause, remove the class of problem. Run tests in a container or with pinned tool versions locally. Set the timezone and locale in the test setup. Add a CI job step that runs the suite in random order now and then. Keep a script that does what CI does, so developers can run the same thing before they push. Every difference you remove is one less 'works for me' conversation.

Services, network and secrets

Your laptop has a running database and open network. CI has what the workflow defines. Check that service containers are declared and healthy before tests start, that tests do not call real external APIs, and that secrets are present. Secrets are not passed to workflows from forks, so a pull request from a fork can fail while the same code passes on a branch. See permission and secret errors.

If the failure seems random and passes on re-run, you have a flaky test, which needs a different approach: Flaky Tests and Flaky CI.

Questions people ask

Should I just re-run the job until it passes?

A re-run can confirm that a failure is intermittent, but it does not fix it. Record the failure and fix the cause, or the pipeline loses trust.

What is the fastest way to compare local and CI?

Print versions, environment variable names and the working directory in CI, then run the same install and test commands in a clean clone locally.
