Presigned upload URLs against a local MinIO: the host name trap

A presigned URL signed for the container name cannot be used by a browser. Sign it for the address the browser will call.

A presigned upload URL fails against a local MinIO when it was signed for one host name and used with another. The signature covers the Host header, so a URL created with the Docker-internal endpoint http://store:9000 returns SignatureDoesNotMatch or does not resolve at all in a browser. Sign it with a second S3 client whose endpoint is the address the browser actually calls, usually http://127.0.0.1:9000.

How presigned URLs work

A presigned URL lets a client upload one object without holding your credentials. Your backend signs a request (method, bucket, key, expiry, and optionally headers such as Content-Type) and hands back a URL with the signature in the query string. The browser then sends a plain PUT to that URL with the file as the body.

Because the host is part of what is signed, the server rebuilds the signature from the request it receives. Change the host after signing and the two no longer match. In production this is invisible, since your backend and the browser both use bucket.s3.amazonaws.com. Locally they see the same server under two names: your API container knows it as store, your browser as 127.0.0.1.

The fix: two endpoints

Use the internal endpoint for server-side calls and a separate client, configured with the public endpoint, only for signing. Signing does not contact the server, so the signing client does not need to reach 127.0.0.1:9000 from inside the container.

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const common = { region: "us-east-1", forcePathStyle: true };

// server-side reads and writes: inside the stack
export const s3 = new S3Client({ ...common, endpoint: process.env.AWS_ENDPOINT_URL_S3 });

// signing only: the address the browser will use
const signer = new S3Client({ ...common, endpoint: process.env.S3_PUBLIC_ENDPOINT });

export function uploadUrl(key, contentType) {
  return getSignedUrl(
    signer,
    new PutObjectCommand({ Bucket: "uploads", Key: key, ContentType: contentType }),
    { expiresIn: 300 },
  );
}

In boto3 the same idea is a second client created with endpoint_url set to the public address, then signer.generate_presigned_url("put_object", Params={"Bucket": "uploads", "Key": key, "ContentType": ct}, ExpiresIn=300).

In production S3_PUBLIC_ENDPOINT is unset and both clients point at real S3, so the code collapses to one behaviour.

The Flisk way

With Flisk's MinIO resource (see how to run MinIO locally), two things are needed. First, the S3 port must be published to your machine, because by default only the console on 9001 is. In the store's service.json:

"extraPorts": [{ "port": 9001 }, { "port": 9000 }]

Flisk publishes each extraPorts entry on 127.0.0.1 only, so the S3 port is still not exposed to your network. Second, give the API the public address as plain configuration in its service.json, next to the dependency that supplies the internal one:

"dependsOn": ["store"],
"env": { "S3_PUBLIC_ENDPOINT": "http://127.0.0.1:9000" }

Run flisk config verify after editing. If the host port 9000 is already taken on your machine, set hostPort in that extraPorts entry and use that port in the URL.

Upload from the browser

const { url } = await fetch("/api/upload-url", { method: "POST", body: JSON.stringify({ name: file.name, type: file.type }) }).then(r => r.json());

const res = await fetch(url, {
  method: "PUT",
  headers: { "Content-Type": file.type },   // must match what was signed
  body: file,
});
if (!res.ok) throw new Error(await res.text());

If you signed ContentType, the browser must send exactly that header. A mismatch gives SignatureDoesNotMatch.

Debug it from the command line

Take the URL your API returned and try it without a browser:

curl -i -X PUT -H "Content-Type: text/plain" --data-binary "hello" "PASTE_THE_URL_HERE"

A 200 means the signature and host are right and the problem is in browser code. An error body with SignatureDoesNotMatch points to the host, the headers or the clock. AccessDenied with an expiry message means the URL is older than expiresIn.

Pitfalls

  • CORS. A browser upload from a page on another origin sends a preflight OPTIONS. If the console shows a CORS error, check the OPTIONS response with curl -i -X OPTIONS and the Origin header before touching your code. MinIO configures CORS for the whole server rather than per bucket, so bucket CORS rules from your AWS setup do not apply to it.
  • Clock skew. Signatures carry a timestamp. A container with a wrong clock produces expired or not-yet-valid URLs.
  • The browser cannot resolve a container name. If a URL contains store or another Docker name, it was signed with the wrong client.
  • Checksum headers. Newer SDK versions can sign checksum headers into the URL. If the browser does not send them, the upload fails. Use requestChecksumCalculation: "WHEN_REQUIRED" on the signing client.

When not to use presigned URLs

For small files that your backend already receives, streaming them through the API is simpler and gives you validation before anything reaches storage. Presigned URLs earn their place with large files, or when you want uploads to bypass your servers.

See the SDK settings in pointing the AWS SDK at a local S3 endpoint, and test the full flow with integration tests against the real stack.

Questions people ask

Why does my presigned URL say SignatureDoesNotMatch?

The signature covers the host and any signed headers. The usual causes are a URL signed for the Docker-internal host name but used from a browser, a Content-Type header that differs from the signed one, or a wrong clock.

Can the signing client be separate from the normal client?

Yes. Signing is computed locally and does not contact the server, so a second client with the public endpoint can sign URLs even when the API container cannot reach that address.

Is a presigned URL a secret?

Treat it like one until it expires. Anyone holding the URL can perform that one request. Keep expiry short.
