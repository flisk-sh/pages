How to run an MCP server next to your local database

An MCP server that can query your development data is useful and risky. Wire it up so it starts after the database and can only do what you meant.

To run an MCP server next to a local database, start the database first, hand the server its connection string through an environment variable such as DATABASE_URL, and expose narrow, read-only tools instead of a free-form SQL runner. In Flisk you add a database resource and list it in the MCP resource's dependsOn.

Why put them side by side

An assistant that can look at real tables answers better questions: which rows are broken, what a migration did, what shape the data has. Running the MCP server in the same local stack as the database keeps the connection on your machine, and makes the setup reproducible for a teammate.

Plain scripting works. Start Postgres with Docker or a local install, export DATABASE_URL, start your server. The things you then have to own yourself are the start order (the server must not accept calls before Postgres does), the credentials, and who creates the schema.

Decide what the tools may do

This is the part that matters most, and it has nothing to do with Flisk. A tool called run_sql that takes any string will, sooner or later, run a DELETE or DROP TABLE that a model wrote with confidence. Prefer:

  • Named, narrow tools. list_tables, describe_table, count_rows, find_order_by_id. Each one has a fixed query and typed arguments.
  • A read-only database role. Create a Postgres role with SELECT only and give the MCP server that role's URL. Even a bug in a tool cannot write.
  • Parameters, never string building. Pass values as query parameters. Never paste a model-written value into SQL text.
  • Honest hints. Mark read-only tools with readOnlyHint: true. Clients can use it to skip a confirmation, and flisk mcp check expects it.

Keep this to development data. Do not point such a server at production, and do not load real customer data into a development database.

The Flisk way

Create the database and the MCP server as resources in one stack:

flisk resource db --type database --stack main --yes
flisk resource docs-mcp --type mcp --stack main --yes

The database resource's service.json is short ("appType": "database", "framework": "postgres", the shared Flisk Postgres by default). Then open services/main/docs-mcp/service.json and list the database in dependsOn, as the CLI's own hint says ("Add db to dependsOn in the services that use the database"):

{
  "appName": "docs-mcp",
  "appType": "mcp",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["db"]
}

Flisk runs one Postgres container for the project, and a service's generated DATABASE_URL points at a database named after the project and the stack, so the services of one stack share it. An mcp resource goes through the same path as a backend, and backend services read the database from the DATABASE_URL variable. Do not assume, check: with the stack running, print what the server really receives.

flisk run docs-mcp -- printenv DATABASE_URL

The container resource must be running for that command. Use the same output to confirm the host, user and database name before you write any query code.

Use it in a tool

With the pg package, a read-only tool is a few lines inside buildServer() in src/index.ts:

import pg from 'pg';
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

server.registerTool(
  'count_rows',
  {
    description: 'Count the rows in one table of the public schema',
    inputSchema: { table: z.enum(['orders', 'customers']) },
    annotations: { readOnlyHint: true },
  },
  async ({ table }) => {
    const r = await pool.query('select count(*)::int as n from ' + table);
    return { content: [{ type: 'text', text: String(r.rows[0].n) }] };
  }
);

The z.enum is the point: the table name comes from a fixed list, so nothing a model sends can reach the SQL text. Add pg to the service's package.json, and create the pool once, outside the per-request server, so each request does not open a new connection.

Who creates the tables

Not the MCP server. Schema changes belong in a migration job that runs once and exits, and Flisk's contributor rules require migrations to run in an explicit migrator resource, not from a server's start script. See database migrations in local dev for that setup. The MCP server then only needs to start after the schema exists.

Pitfalls

  • Reaching the database from your machine. Inside the stack a service uses the generated DATABASE_URL. From your laptop the host port is 15432 unless FLISK_POSTGRES_PORT says otherwise, and the password is DB_PASSWORD in the project .env.
  • Stateless server, stateful data. The MCP process may restart at any time. The data survives flisk down, because it lives in a named volume. flisk down --purge deletes it.
  • A shared database per stack. Every service in the stack sees the same tables. If the assistant should see only some data, use a role with limited grants.

Once the server works, connect an assistant and ask it a real question about your data. Testing with Claude Code shows how.

Questions people ask

Should an MCP server be allowed to write to my database?

Only through narrow tools you wrote on purpose. Start read-only, with a Postgres role that has SELECT only, and mark those tools readOnlyHint true.

How do I make the MCP server start after Postgres in Flisk?

Create a database resource and add its name to dependsOn in the MCP resource's service.json. Then check the environment with flisk run <name> -- printenv DATABASE_URL.

Where should the MCP server get the database connection string?

From the DATABASE_URL environment variable, never from a value written into the source. Under Flisk the stack generates it for services that depend on the database.
