How to test agent tool calls and trajectories

Record every tool call, then assert on which tools ran, in what order, with what arguments, and how many steps it took. Catch wrong paths that still produce a fine answer.

Record each tool call the agent makes as a list of tool names and arguments, called a trajectory, then write assertions on it: required calls, forbidden calls, argument values and a step limit. A final answer can look right while the agent took a risky or wasteful path, and only trajectory checks reveal that.

Capture a trace

Wrap your tool executor so every call is appended to a list with its name, arguments, result status and time. Do this in the test harness, not in the model prompt.

class Trace:
    def __init__(self): self.calls = []
    def wrap(self, name, fn):
        def inner(**args):
            try:
                out = fn(**args)
                self.calls.append({"tool": name, "args": args, "ok": True})
                return out
            except Exception as e:
                self.calls.append({"tool": name, "args": args, "ok": False, "err": str(e)})
                raise
        return inner

Assert on what must and must not happen

Three kinds of assertion cover most needs.

  • Required: the refund tool was called with the right order ID.
  • Forbidden: the delete tool was never called.
  • Bounded: the run used at most 8 steps and no tool failed more than twice in a row.
def test_refund_path(trace):
    names = [c["tool"] for c in trace.calls]
    assert "find_order" in names
    assert names.index("find_order") < names.index("refund_order")
    assert "delete_customer" not in names
    assert len(names) <= 8

Check order only where it matters

Do not demand an exact sequence. Agents find several valid routes, and exact-match tests break on harmless changes. Assert on ordering only for real dependencies, such as "look up before you modify", and leave the rest free. This keeps tests stable across model upgrades.

Look at failures as a group

One failed trace is an anecdote. Run the suite, then group failures by the first wrong step: wrong tool picked, right tool with wrong arguments, tool error ignored, or the final answer ignoring a good result. The group with the most cases is your next fix. Often the cause sits in a tool description rather than in the model, and rewriting one sentence fixes five cases.

Mock the tools

Replace real tools with fakes that return fixed data. Then a test depends only on the agent's choices, not on the state of the world. Include fakes that fail on purpose: a timeout, an empty result, a permission error. See mocking the model and tools for how to structure this.

Watch for loops and waste

Count repeated identical calls. An agent that calls search with the same query five times is stuck. Add a check for repeats and a step budget, and record the average number of steps per case over time, since a rise often means a prompt or tool description got worse. When a trajectory test fails, read the whole trace before changing anything. Often the fix is a clearer tool description, as in MCP servers in production.

Questions people ask

Should I assert on the exact sequence of calls?

Only for true dependencies. Exact-sequence tests are brittle because many correct agents choose different but valid paths.

How do I catch an agent stuck in a loop?

Set a maximum step count and flag repeated identical tool calls in the trace. Fail the case when either limit is passed.
