Email and notifications in local dev

How to stop your dev environment from emailing real users

It takes one restored production dump and one real API key to email ten thousand customers from a laptop. A few cheap layers make that impossible.

To stop a dev environment from emailing real users, use several independent layers: point SMTP at a local catcher by default, keep real provider keys out of dev entirely, check recipients against an allowlist in code, and never load real customer addresses into a dev database. One layer can fail. All four failing in the same week is unlikely.

How it usually goes wrong

These incidents share a pattern. Someone restores a production database dump to debug a problem. The dump has real addresses. A developer runs a script or a cron job that sends "your order shipped" or "we miss you", and the mail library has a live API key in its config because the .env was copied from a teammate. Nothing was malicious, and every step was normal.

Layer 1: default to a catcher

Make "send to the local catcher" the default configuration, so a developer has to do extra work to send real mail, not extra work to avoid it. Your code reads SMTP_HOST and SMTP_PORT, and the example env file ships with localhost and 1025. Setup steps are in the Mailpit article.

Layer 2: no live keys in dev

If the dev environment has no live key, a mistake has nothing to send with. Practical rules:

  • Keep real credentials out of files that are committed and out of any file you copy between machines. Commit an example file with names only; see env var names, not values, in committed config.
  • Give each environment its own key with its own limits, and prefer your provider's sandbox or test mode where one exists.
  • Store production keys in your host's secret store, not in a developer's shell history.

Layer 3: an allowlist at the sending boundary

Add one function that every email send goes through, and make it refuse addresses outside an allowed set when the environment is not production:

const ALLOWED = (process.env.MAIL_ALLOWED_DOMAINS ?? "example.test,example.com")
  .split(",")
  .map((d) => d.trim().toLowerCase());

export function assertSafeRecipient(address: string) {
  if (process.env.APP_ENV === "production") return;
  const domain = address.split("@").pop()?.toLowerCase() ?? "";
  if (ALLOWED.includes(domain) === false) {
    throw new Error(`Refusing to send to ${address} outside production`);
  }
}

Call it inside your sendEmail wrapper, not in every caller. If a bug slips through, the send throws and logs, and no mail leaves. Another option is to rewrite every recipient to a single team address in non-production, with the original address kept in a header, but a refusal is simpler to reason about.

Layer 4: scrub the data

A dev database should not hold real people's addresses. When you need production-shaped data, run a script after the restore that replaces every email with a fake one, for example user-123@example.test, and clears phone numbers and any stored tokens. Better, seed development data from scratch; the seeding guide shows one way. Do this in the same step as the restore, so no one can start the app between the two.

With Flisk

Flisk helps with layer 1 and a little with layer 2, nothing more. A Mailpit resource in the stack, listed in the app's dependsOn, gives the app SMTP_HOST and SMTP_PORT from the mail resource's provides, so a fresh flisk up sends to the catcher without anyone editing a file. Service manifests declare secret names in secrets.required and read values from the project .env, which stays out of git, so the manifest you commit holds names only. Flisk does not scan for live keys or block sends, so layers 3 and 4 are code and process, not tooling. Anything in the provides block is plain configuration, never a place for a key.

A quick audit for an existing project

Ask four questions of your current setup, and fix the first one that gets a "no" or a shrug:

  1. If I run the app after a fresh clone with no edits, where does its mail go?
  2. Which files on a developer's laptop contain a live provider key, and who gave it to them?
  3. If a script loops over every user and sends mail, what stops it in a non-production environment?
  4. When was the last time a dev database held real addresses, and how would I know?

Pitfalls

  • Other channels. SMS, push and Slack messages need the same layers. See testing SMS locally.
  • Background jobs already in a queue. A restored queue table may hold pending sends. Empty it as part of the restore.
  • "It is only staging." Staging with real customer data and a live key is production for the person who gets the email.

Next step

Add a test that proves the guard works: try to send to a non-allowlisted address and assert it throws. Then read how to assert emails in end-to-end tests for the positive case.

Questions people ask

What is the safest default for email in development?

Send everything to a local catcher such as Mailpit and keep no live provider key in the dev environment, so a mistake has nothing to send with.

Can I use a production database copy locally?

Only after scrubbing it: replace every email address with a fake one, clear phone numbers and tokens, and empty queues of pending sends, in the same step as the restore.

Does Flisk prevent sending real email?

No. It can run a local mail catcher and pass its SMTP settings to dependent services, which makes the safe default easy, but it does not block sends or scan for keys.
