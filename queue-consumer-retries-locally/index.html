How to test queue consumer retries and dead letters locally

A retry path that you have never run is a retry path that does not work. Here is how to force failures on your laptop and watch what the queue does.

To test retries locally, publish a message your consumer is guaranteed to fail on, then watch the queue redeliver it. You need to see three things: the message comes back after a failure, it stops coming back after a set number of attempts, and the final failure lands somewhere you can inspect instead of disappearing.

How retries work in a queue

A consumer takes a message, does the work and acknowledges it. If it never acknowledges, because it crashed or took too long, the queue assumes the work was lost and delivers the message again. That is called at-least-once delivery, and it has two consequences for your code.

  • Handlers must be safe to run twice. A retry after a half-finished job repeats the first half. Use an idempotency key, or make the work a single database transaction.
  • Retries need a limit. A message that can never succeed (a poison message) would otherwise loop forever. After a set number of attempts, move it aside.

RabbitMQ does this with a dead-letter exchange plus a message TTL or a reject. JetStream does it with consumer settings, and a few lines in your handler.

A consumer with a delivery limit

This uses Python and the nats-py package against the NATS server from the NATS article. The consumer gets at most four deliveries, waits ten seconds for an acknowledgement, and sends the last failure to a dead subject.

import asyncio, os, json
import nats
from nats.js.api import ConsumerConfig
from nats.errors import TimeoutError as FetchTimeout

MAX = 4

async def main():
    nc = await nats.connect(os.environ["NATS_URL"])
    js = nc.jetstream()
    await js.add_stream(name="JOBS", subjects=["jobs.>"])
    sub = await js.pull_subscribe(
        "jobs.email", durable="mailer",
        config=ConsumerConfig(max_deliver=MAX, ack_wait=10),
    )
    while True:
        try:
            msgs = await sub.fetch(1, timeout=5)
        except FetchTimeout:
            continue
        for msg in msgs:
            attempt = msg.metadata.num_delivered
            try:
                handle(json.loads(msg.data))
                await msg.ack()
            except Exception as err:
                print(f"attempt {attempt} failed: {err}", flush=True)
                if attempt >= MAX:
                    await js.publish("jobs.dead.email", msg.data)
                    await msg.term()      # stop redelivery
                else:
                    await msg.nak(delay=2)  # retry in 2 seconds

asyncio.run(main())

The dead subject jobs.dead.email is inside the jobs.> stream, so the stored message stays visible, and the consumer's filter on jobs.email keeps it from being picked up again.

The Flisk way

Create the queue and make the worker depend on it:

flisk resource bus --type queue --stack shop --yes
{
  "schemaVersion": 1,
  "appName": "mailer",
  "appType": "worker",
  "command": "python3 worker.py",
  "dependsOn": ["bus"]
}

The worker needs the client library, so run pip install nats-py in the environment that python3 uses. Check the config with flisk config verify, then start the stack with flisk up shop. The bus service provides NATS_URL to services that depend on it, as described in the Flisk BYO docs. I wrote the worker mode above from the documentation and have not run this exact stack, so if NATS_URL is missing in your worker, print the environment and compare it with the docs.

Now run three experiments:

  1. A normal failure. Publish a message that makes handle() raise. Watch flisk logs --service mailer --since 2m. You should see attempts one to four, spaced by the delay, then a dead message.
  2. A crash mid-job. Publish a slow job, and run flisk restart mailer while it works. The message was not acknowledged, so it returns after the acknowledgement wait. This is the redelivery that handlers must survive.
  3. Inspect the leftovers. With the nats CLI, nats consumer info JOBS mailer shows how many messages are pending and how many are waiting for acknowledgement, and nats stream ls shows the stream sizes.

The CLI needs the server port on your host. Publish it with extraPorts as shown in the NATS article, or run the CLI from another container.

Pitfalls

  • A short acknowledgement wait causes duplicates. If a job normally takes 20 seconds and ack_wait is 10, the queue redelivers while the first attempt is still running. Set the wait longer than your slowest honest job.
  • Retries without a delay hammer your dependency. Use a delay, and make it grow for real services.
  • Leftover state. The stream data lives in a volume, so old failed messages come back in the next run. Purge the stream between experiments.
  • The scaffolded worker does not retry for you. The Flisk worker template reads a retry count into its config but logs a failed job and moves on, so retry logic is yours to write.
  • When not to bother. If a lost job costs nothing, core NATS without JetStream is simpler, and so is a plain function call.

When a job is not failing but simply never finishes, the checks are different. Debugging a stuck job walks through them.

Questions people ask

How do I make a queue consumer fail on purpose?

Publish a message that your handler rejects, such as a payload with a missing field, and have the handler raise. Then watch the logs for repeated attempts and check the consumer's pending counts.

What is a dead letter queue?

It is a place where a message goes after it fails too many times, so it stops looping and you can inspect it. In RabbitMQ it is a dead-letter exchange. In JetStream you cap deliveries and publish the last failure to a separate subject.

Why is my message delivered twice when nothing failed?

The acknowledgement did not arrive before the wait time ended, usually because the job is slower than the ack wait. Raise the wait or acknowledge sooner, and keep the handler safe to repeat.
