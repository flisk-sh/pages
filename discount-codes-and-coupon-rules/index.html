How to build discount codes and coupon rules without double use

A coupon is a bundle of rules: when it is valid, who can use it, how often, and what it takes off. Put the limits in the database so concurrent checkouts cannot break them.

Model a discount code as one row of rules (type, amount, dates, limits) plus a redemptions table that records every use. Enforce the usage limit with a single guarded UPDATE, and a unique key for the per-customer limit, so two simultaneous checkouts cannot both use the last redemption. Calculate the discount with integer money and test each rule with a table of cases.

The data

CREATE TABLE coupons (
  id            bigserial PRIMARY KEY,
  code          text NOT NULL UNIQUE,         -- store upper-case
  kind          text NOT NULL CHECK (kind IN ('percent', 'fixed')),
  amount        bigint NOT NULL CHECK (amount > 0), -- basis points or minor units
  currency      char(3),                      -- required for fixed
  min_subtotal  bigint NOT NULL DEFAULT 0,
  starts_at     timestamptz,
  ends_at       timestamptz,
  max_uses      int,                          -- null means unlimited
  used_count    int NOT NULL DEFAULT 0,
  active        boolean NOT NULL DEFAULT true
);

CREATE TABLE coupon_redemptions (
  coupon_id   bigint NOT NULL REFERENCES coupons(id),
  customer_id bigint NOT NULL,
  order_id    bigint NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (coupon_id, order_id)
);

Store percentages as basis points (1500 for 15 percent) so everything stays an integer, and fixed amounts in minor units, as described in storing prices as integers. Normalise codes to upper case on input and on write, so summer10 and SUMMER10 are the same code.

Validate, then redeem atomically

Checking rules in code and incrementing later is the same race as the one that oversells stock. Combine the validity checks and the counter in one statement:

UPDATE coupons
SET used_count = used_count + 1
WHERE code = $1
  AND active
  AND (starts_at IS NULL OR starts_at <= now())
  AND (ends_at   IS NULL OR ends_at   >  now())
  AND (max_uses  IS NULL OR used_count < max_uses)
RETURNING id, kind, amount, currency, min_subtotal;

No row back means the code is invalid, expired or used up, and you can run a second query to tell the customer which one. Run this in the same transaction that creates the order, and insert the redemption row there too. If the order later fails or expires, decrement used_count and delete the redemption in the same place where you release stock.

For a per-customer limit of one use, add a unique index on a view of the data that matters, or check SELECT 1 FROM coupon_redemptions WHERE coupon_id = $1 AND customer_id = $2 inside the transaction after taking a lock on the coupon row. The lock matters: without it, two requests from the same customer can both pass the check.

Calculate the discount

function discount(subtotal: number, c: { kind: string; amount: number }) {
  if (c.kind === "percent") return Math.round((subtotal * c.amount) / 10000);
  return Math.min(c.amount, subtotal); // a fixed discount never goes below zero
}

Then check min_subtotal against the subtotal before shipping and tax, not after. State the order of operations (discount, then tax, then shipping) in a comment and keep it the same in the invoice.

Decide the stacking rules up front

The questions that cause arguments later: can two codes combine, does a code apply to items already on sale, does free shipping count as a code? The simplest rule is one code per order, and your schema above supports it. If you need several, add a priority and a combinable flag, apply them in a fixed order, and write tests for each pair. Another trap is a percentage code on a cart with a fixed code: the result depends on order, so the order must be defined.

Test the rules as a table

A list of cases, each with a cart, a code and an expected total, covers more than prose does. Include: just before and just after ends_at, exactly min_subtotal, the last allowed use, a lowercase code, a fixed discount larger than the cart, and the same customer twice. Run the redemption concurrently with 10 parallel requests against max_uses = 3 and assert exactly three succeed. If you run the stack with Flisk, a test like that can run inside the API service with flisk run orders-api -- bun test, so it uses the same database as the API.

Pitfalls

  • Guessable codes. Short, sequential codes get brute-forced. For codes that are worth money, generate long random ones and rate-limit the endpoint.
  • Counting at validation time. A customer who types a code in the cart has not used it. Count at order creation.
  • Percent of a rounded value. Apply the percentage to the exact subtotal in integer minor units, then round once.
  • Refunds. Decide whether a refunded order gives the use back. Most shops say no.

Questions people ask

Should coupon codes be case sensitive?

Usually not. Store and compare them in upper case so customers do not fail on capitalisation.

Where do I enforce a usage limit?

In the database, in one UPDATE that checks and increments the counter. Checking in application code first leaves a race.

Can a coupon apply to specific products only?

Yes. Add a coupon_products table, and calculate the discount over the matching order lines only.
