Cut LLM cost and latency

How to reduce LLM API costs without hurting quality

A ranked list of the changes that cut an LLM bill the most: measure first, then trim tokens, cache, route to smaller models and batch what can wait.

Measure cost per request and per feature first, then apply the cheap wins in order: shorter prompts, caching, a smaller model for easy work, and batching for anything that can wait. Most bills are dominated by input tokens that repeat on every call, so that is where to look first.

Measure before you change anything

Log the model name, input tokens, output tokens, latency and a feature label for every call. Every provider returns token usage in the response, so this costs you nothing extra.

log({ feature: 'support-reply', model, input_tokens: usage.input_tokens, output_tokens: usage.output_tokens, ms })

Group by feature. You will usually find that one or two features cause most of the spend. Optimise those and ignore the rest.

Send fewer tokens

Output tokens usually cost more than input tokens, and both add up. Cap max_tokens to what the feature needs. Remove instructions the model already follows. Do not paste a whole document when ten relevant paragraphs answer the question.

See how to shorten prompts without losing quality for concrete tactics.

Cache the part that repeats

A long system prompt, a tool list or a fixed document that is the same on every call is the best caching target. Providers offer prompt caching that charges less for a repeated prefix. Read prompt caching explained for the rules that make a cache hit.

Use the smallest model that passes your tests

Classification, extraction and short rewrites rarely need a top model. Keep a small test set, run it against a cheaper model, and switch if the score holds. Routing lets you keep the strong model for the hard requests only.

While you tune, a free open-beta API such as Flisk Inference (beta, daily request limit) can take the development traffic, so test runs do not hit a paid bill. It is a different model, so confirm quality on your production model before you ship.

Batch what can wait

Nightly summaries, bulk tagging and evaluations do not need an instant answer. Most large providers offer an asynchronous batch interface at a lower price. The trade-off is that results arrive later, so it suits background jobs, not chat. See batch API vs real-time requests.

Pitfalls

  • Cutting cost without a test set. You will not notice quality drops until users do.
  • Retries that resend a huge prompt. Cap retries and add backoff.
  • Agent loops with no step limit. One runaway loop can cost more than a week of normal traffic.

Re-measure after each change, one at a time. If you change the prompt, the model and the cache setting in one release, you will not know which one saved money or which one hurt quality. A weekly cost report per feature, sent to the team, keeps the habit alive.

Questions people ask

What is the fastest way to cut my LLM bill?

Find the feature with the most input tokens, then shorten its prompt and cache the repeated prefix. That usually beats any model switch.

Will a smaller model hurt quality?

Only for hard tasks. Run your own test set against the smaller model and switch the tasks where the score stays the same.
