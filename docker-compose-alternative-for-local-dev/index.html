Docker Compose for local development

Docker Compose alternative for local development

Docker Compose is a good default. This article shows where it runs out of road for local development and what a generated setup looks like.

Stay on Docker Compose if you run two or three services that are already containerized. Look for an alternative when most of your time goes into wiring around Compose: a reverse proxy, startup order, hot reload, a shared database and the same setup repeated in every repo. One option is Flisk, which generates the Compose, Traefik and Tilt files from one service.json per service.

When Compose is the right tool

Compose is on almost every developer machine, it needs no extra runtime, and everyone on the team can read a docker-compose.yml. For a small project it is the simplest honest answer.

  • You have two or three services and each one already has a Dockerfile.
  • You do not need pretty URLs. localhost:3000 and localhost:8080 are fine.
  • Your services start in any order, or you can add depends_on with a healthcheck once and forget it.
  • You rebuild the image when code changes, or you use docker compose watch for live sync.

Compose also has profiles for optional services, and docker init to scaffold a first Dockerfile and Compose file. If this list describes your project, you do not need another tool.

Where Compose starts to cost you time

The pain shows up as a project grows. None of these are bugs in Compose. They are things Compose leaves to you.

  • Routing. Every service publishes a host port, and you keep a mental table of which port is which. A gateway such as Traefik fixes that, but you write and maintain its labels yourself.
  • Ordering. depends_on with condition: service_healthy works, but every service needs a healthcheck written by hand.
  • Databases and migrations. A Postgres container, a volume, a migration job and the connection string are copied from the last project.
  • Repetition. The Dockerfile, the Compose entry and the proxy rules for a new service are three places to edit.

A fair way to judge this is to count the files you touch to add one service. If the answer is one file and one command, Compose is doing its job. If the answer is a Dockerfile, a Compose entry, proxy labels, a healthcheck and an env file, you are paying a tax on every new service, and that is the tax a generator removes.

What Flisk does differently

Flisk is a local development tool. You describe each service in a small service.json, and Flisk generates the Dockerfile, the Compose file, the Traefik gateway config and the Tilt file under .flisk/.flisk-out/. Container services run on Docker and Tilt, behind a gateway on *.localhost, so an API is reachable at a URL shaped like http://api.<project>.localhost/api/<name> instead of a port number.

Install it and scaffold a service with the CLI instead of writing the files by hand:

npm install -g @flisk-sh/flisk
flisk resource orders-api --type backend --stack shop
flisk up shop

Resources can declare dependsOn, a stack groups services so you can start one group with flisk up shop, and Postgres is included as a shared platform service. If you want to see it before you commit to anything, run the demo:

npx @flisk-sh/flisk demo

Because Flisk generates a Compose file and a Tiltfile, it does not replace Compose so much as write it for you. flisk config explain shows where each generated file comes from, so you can read what it produced. Generated files are not meant for hand edits: Flisk refuses to start when it detects them, and you change service.json instead.

Pitfalls and when not to switch

  • More moving parts. The container path needs Docker, Tilt, Node and Bun on the machine. Plain Compose needs only Docker. Check flisk doctor before you decide.
  • Local only. Flisk does not emit Kubernetes manifests and does not replace Helm, Kustomize, Flux or Argo. It is for the inner loop on your laptop.
  • Small projects. For two or three containers that already work, the extra layer does not pay for itself.
  • Existing Compose files. You do not have to rewrite anything. Flisk can read a docker-compose.yml and write the service.json files for you.
Rule of thumb: if adding a service takes you under a minute in Compose, stay. If you dread adding the fifth one, try a tool that generates the wiring.

The next step is the low-risk one. Follow how to import a docker-compose.yml with --dry-run and see what Flisk would write, without changing your Compose file. If Docker is the part you want to avoid, read about running services without Docker, or see local development without Kubernetes.

Questions people ask

Is Docker Compose enough for local development?

Yes for two or three services that already have Dockerfiles. Problems appear with many services, a gateway, startup order and shared databases, because Compose leaves that wiring to you.

Does Flisk replace Docker Compose?

No. For container stacks Flisk generates a Compose file and a Tiltfile from service.json and runs them on Docker and Tilt. You can read the generated files with flisk config explain.

Can I try Flisk without changing my Compose file?

Yes. flisk import reads docker-compose.yml, writes new service.json files and never changes the Compose file. Use --dry-run first to see the plan.
