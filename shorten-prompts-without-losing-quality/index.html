How to shorten prompts without losing quality

Cut tokens from a prompt safely: remove repeats, retrieve instead of pasting, compress history and prove with a test set that the answers did not get worse.

Shorten a prompt by deleting repeated instructions, sending only the context that is relevant to this request and summarising old conversation turns. Then rerun a fixed test set to prove that quality held. Never trim by feel alone.

Set a baseline first

Collect 30 to 100 real inputs with outputs you accept. Run the current prompt over them and save the results and token counts. Every change below is tested against this baseline. Without it you cannot tell a saving from a regression.

Delete what the model already does

Prompts collect lines added after every past bug. Remove one line at a time and rerun the tests. Common candidates are polite filler, rules repeated in two places, and long lists of things not to do that the model never does anyway.

  • Merge duplicate rules.
  • Replace long prose with a short list.
  • Use one or two good examples instead of six.

Send only relevant context

Do not paste the whole manual. Retrieve the few passages that match the question. A search step that returns the top five chunks often beats stuffing fifty pages into the prompt, in both cost and accuracy. See RAG and vector databases locally for a setup.

Compress the history

In a long chat, keep the last few turns verbatim and replace older turns with a short summary. Summarise with a cheap model, and store the summary rather than re-creating it on each call.

history = [summary_of_old_turns] + last_turns[-6:]

Keep facts the user stated, such as names and constraints, in the summary. Drop pleasantries.

Keep the stable part first

Shortening and caching work together: put the fixed instructions at the top so they can be cached, as described in prompt caching explained. A cached long prefix can cost less than a rewritten short one that breaks the cache, so measure both.

Watch for the quality traps

Some lines look removable but carry weight. Format rules, edge-case instructions and a line that says what to do when the answer is not in the context all prevent bad output. When a test fails after a cut, put the line back and move on. Also check the tail of your distribution: an average score can hold while the hardest ten percent of cases get worse.

Keep the old prompt in version control so you can compare and roll back.

Do this as a recurring chore, not a one-off. Prompts grow again as features are added, so review the longest ones every month and rerun the baseline. A short note in the repo with the token count of each prompt makes growth visible in code review.

Questions people ask

Can a shorter prompt be better?

Yes. Fewer conflicting or repeated instructions often make a model more consistent, as long as the test set confirms it.

How much can I cut?

It depends on the prompt. Many production prompts shrink by a third or more once duplicated rules are removed, but only your tests can tell you for yours.
