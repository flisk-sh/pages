Cut LLM cost and latency

How to set budgets and rate limits for an LLM feature

Stop a bug or a heavy user from running up your bill: per-user limits, step caps for agents, spend alerts and a kill switch you can test locally.

Put a cap in three places: per user and per request in your own code, per provider key in the provider dashboard, and a hard stop on agent loops. Test the caps locally before you rely on them, because a limit you never tested usually fails the day you need it.

Cap each request

Set max_tokens on every call and a maximum prompt size on your side. Reject oversized input before it reaches the model.

if (countTokens(input) > 8000) throw new Error('input too large');

Limit per user

Keep a counter per user and per day in your database or a key-value store. Block or degrade when the counter passes the limit, and say so in the UI.

const used = await store.incr('tokens:' + userId + ':' + today, tokensUsed);
if (used > DAILY_LIMIT) return res.status(429).json({ error: 'daily limit reached' });

Count real usage from the response, not an estimate. See how to count tokens.

Stop runaway agent loops

An agent that calls tools in a loop needs a maximum number of steps and a maximum total token count per task. When either is reached, return a partial result and an error, do not keep going.

for (let step = 0; step < MAX_STEPS; step++) {
  if (spent > TASK_BUDGET) break;
  // call model, run tool
}

Use the provider's own controls

Most providers let you set a monthly spend limit, a usage alert and separate keys per project. Use one key per environment and per feature. When a key leaks or a feature misbehaves you can revoke only that one. Rate limits at the provider return a 429, so add backoff with jitter on the client.

Test the limits locally

Run your stack on your laptop with a stub or a small local model and force the limit to a tiny number. With the open-source Flisk CLI you can run the API, the database and a worker together from one service.json per service, then hit the endpoint until it returns 429. Flisk is a local development tool, so the production limits still live in your app and your provider dashboard.

More on spending less overall in how to reduce LLM API costs.

Alert before you block

A hard block surprises users, so send a warning first. A common setup is a soft alert at 50 and 80 percent of the daily or monthly budget, sent to a channel the team reads, and a hard stop at 100 percent. Keep a manual kill switch, such as a feature flag, that turns the AI feature off without a deploy. Practise using it once, so the first time is not during an incident.

Questions people ask

What should happen when a user hits the limit?

Return a clear message with the reset time, or switch them to a cheaper model. Do not fail silently.

Is a provider spend limit enough?

No. It protects your total bill but not fairness between users. Add per-user limits in your own code.
