How to Quarantine Flaky Tests Without Losing Coverage

Move a flaky test out of the blocking suite, keep running it, and put a deadline on it. A practical pattern with markers, tags and a separate non-blocking job.

Quarantining means taking a flaky test out of the set that blocks merges while still running it and recording the result. The test is not deleted and not ignored. It moves to a non-blocking lane with an owner and a deadline.

Tag the test

Use a marker your runner understands, and put the reason and ticket in the tag.

# pytest.ini
[pytest]
markers =
    quarantine: known flaky, tracked in an issue

# test file
import pytest

@pytest.mark.quarantine
def test_job_finishes():
    ...

In Jest or Playwright, a title tag such as @quarantine works with the grep option. In Go, use a build tag or an environment check with t.Skip in the quarantine lane.

Split the jobs

Run the main suite without quarantined tests and a second job for them that is allowed to fail.

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pytest -m 'not quarantine'
  quarantine:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - uses: actions/checkout@v4
      - run: pytest -m quarantine

Only test should be a required check. The quarantine job gives you data: if it goes green fifty times in a row, the test may be fixed.

Rules that keep it honest

  • Every quarantined test has an issue and an owner.
  • Every quarantined test has a deadline, such as 14 days. After that it is fixed or deleted.
  • The list has a size cap. If it hits the cap, new quarantines are not allowed until someone fixes one.
  • A pull request that adds a quarantine marker needs a reviewer to approve it.

Without a cap and a deadline, quarantine becomes a graveyard where coverage quietly disappears.

Know what you give up

A quarantined test no longer protects merges. If it covers important behavior, that behavior is now unguarded. For critical paths, fix first and quarantine only as a last resort. For low-value tests, deleting is often better than quarantining.

A test that cannot be made reliable is usually testing too much. Consider a smaller unit test for the same logic.

Un-quarantine on evidence

Moving a test back should need proof, not a feeling. A simple rule: the test must pass in the quarantine job for a set number of consecutive runs, such as 30, after a fix merged. Then a pull request removes the marker. If the test fails again in that window, the counter resets. This gives you a clear exit that is not a debate.

If the quarantine job is allowed to fail, add a step that prints the pass count to the run summary so the number is visible to everyone.

Track the list

Print the quarantine count in the run summary, so it is always visible. Then review it weekly with the team flaky test policy.

Questions people ask

Is quarantine the same as skipping a test?

No. A skipped test does not run. A quarantined test still runs in a non-blocking job so you keep collecting results.

How long should a test stay quarantined?

Set a fixed limit, commonly one to two weeks. After that, fix it or delete it.
