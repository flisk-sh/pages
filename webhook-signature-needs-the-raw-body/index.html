Payments and webhooks locally

Webhook signature verification fails: use the raw request body

The signature covers the exact bytes the provider sent. Once a framework has parsed and re-serialized them, no key can make the check pass.

A webhook signature is computed over the exact bytes of the request body, so verification fails when your framework parses the JSON first and you verify the re-serialized object. Read the raw body, verify the signature against it, and only then parse it. The fix is a few lines in every framework, but the line is different in each.

Why parsing breaks the check

The provider builds a signature from a timestamp, the raw body and a shared secret. Stripe uses an HMAC-SHA256 over the timestamp, a dot and the body. If your server turns the body into an object and back into text, small things change: key order, spacing, number formatting, escaped characters. A single different byte gives a different HMAC, so the check fails with an error such as "No signatures found matching the expected signature for payload".

The error text points at the signature, so people often chase the secret. Before you change the secret, rule out the body. Log the length of the raw body and compare it with the Content-Length header the provider sent. If they differ, something altered the body before you saw it.

The fix in each framework

Express

Register the webhook route with the raw parser before the global JSON parser, or the global one consumes the stream first:

app.post("/webhooks/stripe",
  express.raw({ type: "application/json" }),
  (req, res) => {
    // req.body is a Buffer here
    const event = stripe.webhooks.constructEvent(
      req.body, req.get("stripe-signature"), secret);
    res.sendStatus(200);
  });

app.use(express.json());   // after the webhook route

Next.js App Router

A route handler can read the body as text. Do not call req.json():

export async function POST(req) {
  const raw = await req.text();
  const sig = req.headers.get("stripe-signature");
  const event = stripe.webhooks.constructEvent(raw, sig, process.env.STRIPE_WEBHOOK_SECRET);
  return new Response(null, { status: 200 });
}

In the older Pages Router, the handler needs export const config = { api: { bodyParser: false } } and the raw bytes read from the stream.

FastAPI

Take the Request object instead of a Pydantic model. A model parameter makes FastAPI parse the body for you:

@app.post("/webhooks/stripe")
async def stripe_webhook(request: Request):
    raw = await request.body()
    sig = request.headers.get("stripe-signature")
    event = stripe.Webhook.construct_event(raw, sig, WEBHOOK_SECRET)
    return {"ok": True}

Flask

raw = request.get_data()   # call this before request.get_json()
event = stripe.Webhook.construct_event(
    raw, request.headers.get("Stripe-Signature"), WEBHOOK_SECRET)

Go

payload, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 65536))
if err != nil { http.Error(w, "read error", 400); return }
event, err := webhook.ConstructEvent(payload, r.Header.Get("Stripe-Signature"), secret)

If you verify the signature yourself

Some providers have no SDK helper, and a hand-written check is short. Compare in constant time, and compare byte lengths first, because timingSafeEqual throws on buffers of different length:

import { createHmac, timingSafeEqual } from "node:crypto";

function verify(raw, header, secret) {
  const want = createHmac("sha256", secret).update(raw).digest();
  const given = Buffer.from(header ?? "", "hex");
  return given.length === want.length && timingSafeEqual(given, want);
}

This is the shape for a simple scheme where the header is a hex HMAC of the body. Stripe's header carries a timestamp and several signatures, so use its SDK for Stripe. The raw-bytes rule is the same.

A local test that catches this early

Add a test that signs a fixture and posts it as raw bytes to your running service. If a later change puts a parser in front of the route, the test fails the same way production would. With Flisk, the service runs as a local process, and you can run the test inside the service's environment:

flisk run api -- node test/webhook-signature.test.js

flisk run runs the command with the environment the service has in the stack and returns its exit code. Put the dummy signing key in the service's env block, loaded from .env, and keep real keys out of the fixtures. Testing webhooks locally covers duplicates and retries on top of this.

Pitfalls

  • A global middleware you forgot. Logging, compression or a "parse everything as JSON" middleware registered above your route can read or change the body.
  • Wrong secret that looks like a wrong body. If the raw body is intact and the check still fails, compare the secret. A secret from stripe listen differs from a Dashboard endpoint secret. See testing Stripe payments locally.
  • Body size limits. A limit that truncates a large event gives a signature error, not a size error.
  • Stale timestamps. Stripe's SDK rejects events whose timestamp is older than a tolerance, five minutes by default. A saved fixture that you replay next week fails for that reason, not the body.

Questions people ask

Why does Stripe webhook signature verification fail in Express?

Usually because express.json() parsed the body before your webhook route. Register the route with express.raw({ type: 'application/json' }) above the global JSON parser and pass the Buffer to constructEvent.

Can I verify a webhook after parsing the JSON?

No. The signature covers the exact bytes. Re-serializing the parsed object changes bytes such as key order and spacing, so the check fails. Verify first, then parse.

Why does a saved webhook payload fail verification a week later?

Many providers sign a timestamp and reject old ones. Stripe's SDK uses a five minute tolerance by default, so replay a freshly signed fixture instead.
