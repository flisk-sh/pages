Email and notifications in local dev

How to test web push notifications on localhost

Web push works on localhost without HTTPS, but it has more moving parts than email: keys, a service worker, a permission prompt and a browser vendor's push service.

You can test web push on http://localhost without HTTPS, because browsers treat localhost as a secure context. Generate a VAPID key pair, register a service worker that handles the push event, subscribe from a page after a user click, and send to the saved subscription from a small Node script. For the service worker alone, Chrome DevTools can fire a fake push event with no server.

The pieces

Web push has four parts, and bugs hide in the seams between them:

  1. VAPID keys. A public and private key pair that identifies your server to the push service.
  2. A service worker. A script that wakes up on a push event and shows the notification.
  3. A subscription. Created in the page. It contains an endpoint URL at the browser vendor's push service, plus encryption keys. Your server stores it.
  4. A sender. Your server, which posts an encrypted payload to the subscription's endpoint.

Step 1: generate keys

npm install web-push
npx web-push generate-vapid-keys

Keep the private key in an environment variable. The public key goes to the page. Never commit the private key; for local use, a dev-only pair in your git-ignored .env is fine, and production gets a different pair.

Step 2: service worker and subscription

The service worker, served from your site's root as /sw.js:

self.addEventListener("push", (event) => {
  const data = event.data ? event.data.json() : { title: "Hello", body: "" };
  event.waitUntil(self.registration.showNotification(data.title, { body: data.body }));
});

In the page, ask permission from a click handler (browsers ignore requests that are not caused by a user gesture) and subscribe:

const reg = await navigator.serviceWorker.register("/sw.js");
const permission = await Notification.requestPermission();
if (permission === "granted") {
  const sub = await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: PUBLIC_VAPID_KEY,
  });
  await fetch("/api/push/subscribe", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(sub),
  });
}

Step 3: send from Node

import webpush from "web-push";

webpush.setVapidDetails(
  "mailto:dev@example.test",
  process.env.VAPID_PUBLIC_KEY,
  process.env.VAPID_PRIVATE_KEY,
);

await webpush.sendNotification(
  savedSubscription,
  JSON.stringify({ title: "Order shipped", body: "Order 1042 is on its way" }),
);

This call goes to the push service of the browser vendor, for example Google's for Chrome and Mozilla's for Firefox. That means an internet connection is required for a real end-to-end send, so web push is the one notification channel that cannot run fully offline. Treat a 404 or 410 response as "this subscription is gone" and delete it from your store.

Test the worker without any server

In Chrome, open DevTools, go to the Application panel, choose Service Workers and use the Push button, which dispatches a push event with text you type. That tests your push handler and the notification display with no keys and no network. Use JSON text if your handler calls event.data.json(). It does not test subscription or delivery, so do the full send once as well.

With Flisk

Flisk runs the pieces that surround this: a frontend, an API that stores subscriptions and a worker that sends notifications, and it prints their URLs with flisk networks. It does not emulate a push service, and there is no local substitute for one. One thing to verify when you test through a routed *.localhost address instead of a plain localhost:port: open the browser console and check that window.isSecureContext is true. If it is false on your URL, service workers and push will not register there, and you should use the plain localhost address that Flisk's frontend also exposes. See local URLs instead of port numbers for how the hostnames work. Send from a worker, as described in the email worker article; the outbox and retry design applies to push as well.

Pitfalls

  • Permission blocked. After a user clicks "Block" the prompt never returns. Reset the site's permission in browser settings, or use a fresh profile.
  • Service worker caching. An old worker can keep running. In DevTools, tick "Update on reload" while developing.
  • Safari and iOS. Push on iPhone works only for web apps added to the home screen, and the details change between versions. Read Apple's current guidance before promising support.
  • Stale subscriptions. Users clear data and subscriptions die. Handle 404 and 410 by removing them.

Next step

If a user also has email and SMS, keep one place that decides which channel to use; test the email side with Mailpit and the text side with a fake SMS service.

Questions people ask

Does web push work on localhost without HTTPS?

Yes. Browsers treat localhost as a secure context, so service workers and push work over plain http there.

Can I test a push notification without a server?

Partly. Chrome DevTools has a Push button under Application, Service Workers that fires a push event into your worker. It does not test subscribing or delivery.

Why does a real web push need the internet?

The notification goes through the browser vendor's push service, which your server contacts over the network, so there is no fully offline path.
