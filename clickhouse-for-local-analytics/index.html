How to run ClickHouse locally for analytics development

ClickHouse is a column store for aggregating many rows fast. Running one locally is easy. Picking the sort key and keeping the data takes a little more care.

To run ClickHouse locally, start the official server image, publish its HTTP port (8123) on loopback, and keep /var/lib/clickhouse on a volume so the data survives a restart. Then create a MergeTree table whose ORDER BY matches how you filter, and query it over HTTP, in the built-in /play page, or from Python.

Plain Docker

docker run -d --name ch \
  -p 127.0.0.1:8123:8123 \
  -e CLICKHOUSE_USER=default \
  -e CLICKHOUSE_PASSWORD=flisk \
  -e CLICKHOUSE_DB=app \
  -v ch-data:/var/lib/clickhouse \
  clickhouse/clickhouse-server:25.8-alpine

Check it with one request:

curl 'http://127.0.0.1:8123/?user=default&password=flisk' --data-binary 'SELECT 1'

Port 8123 is HTTP, 9000 is the native protocol used by clickhouse-client. For application code HTTP is enough and passes through every proxy. Pin the image tag to a version you tested, because the default latest moves.

A table that fits your queries

A ClickHouse table has no row-by-row updates and no primary key in the relational sense. Its ORDER BY clause decides how data is sorted on disk, and queries that filter on the leading columns of that sort key read a small part of the data. Choose it from your most common WHERE clause:

CREATE TABLE app.events
(
    ts      DateTime,
    user_id UInt64,
    name    LowCardinality(String),
    amount  Float64
)
ENGINE = MergeTree
ORDER BY (name, ts);

INSERT INTO app.events
SELECT now() - number * 60, number % 50, ['view','click','buy'][number % 3 + 1], rand() % 100
FROM numbers(100000);

SELECT name, count() AS n, round(avg(amount), 1) AS avg_amount
FROM app.events
GROUP BY name ORDER BY n DESC;

Insert in batches of thousands of rows, never one row at a time. Each insert creates a data part on disk, and many tiny parts slow everything down. The built-in query page at http://127.0.0.1:8123/play is enough to try statements: enter the user and password in its fields, paste the query and run it.

The Flisk way

Flisk ships ClickHouse as a database preset:

flisk resource events --type database --framework clickhouse --stack ml --yes

This writes a service.json with a pinned image (clickhouse/clickhouse-server:25.8-alpine), a health check, a named volume for /var/lib/clickhouse that flisk down does not delete, and the play page published on 127.0.0.1:8123 only. The login is user default, password flisk, database app. Any service that lists events in dependsOn receives these variables:

  • CLICKHOUSE_URL
  • CLICKHOUSE_USER
  • CLICKHOUSE_PASSWORD
  • CLICKHOUSE_DB
flisk config verify
flisk up ml
flisk status
flisk run events -- clickhouse-client --password flisk --query "SELECT version()"

flisk run executes a command inside the running container, here the bundled client. See running a one-off command in a service. In a Python service, clickhouse-connect reads the provided variables. A real service needs to parse the host and port out of CLICKHOUSE_URL:

import os
from urllib.parse import urlparse

import clickhouse_connect

u = urlparse(os.environ["CLICKHOUSE_URL"])
client = clickhouse_connect.get_client(
    host=u.hostname,
    port=u.port or 8123,
    username=os.environ["CLICKHOUSE_USER"],
    password=os.environ["CLICKHOUSE_PASSWORD"],
    database=os.environ["CLICKHOUSE_DB"],
)
rows = client.query("SELECT name, count() FROM events GROUP BY name").result_rows

Keep the table definition in a file in the repository and apply it from a one-shot job with "restart": "no", the same way you would run migrations, see running a one-shot job in a local stack. To start from scratch, remove the volume: with Compose-style tools that is docker volume rm on the data volume after the stack is down, and see keeping volumes between runs for how long-lived volumes behave.

Pitfalls

  • It is not your OLTP database. ClickHouse is good at scans and aggregates. It is bad at frequent updates and single-row lookups. Keep orders and accounts in Postgres and copy events into ClickHouse.
  • Memory. A large GROUP BY can use gigabytes. If the container is killed, raise its memory limit or add a LIMIT while developing.
  • Default credentials. The password flisk is for a laptop. The HTTP port stays on loopback, so keep it there.
  • Dataset size. For a few gigabytes of files you only query yourself, DuckDB on Parquet files needs no server at all.

To see the numbers on a page rather than in a console, put a small app on top, see a Streamlit dashboard next to your API.

Questions people ask

Which port does ClickHouse use for HTTP?

8123 for HTTP and 9000 for the native protocol. Application libraries such as clickhouse-connect use HTTP.

How do I keep ClickHouse data after docker stops?

Mount a volume at /var/lib/clickhouse. Without a volume the data is deleted when the container is removed.

Can I update rows in ClickHouse?

Not efficiently. It is built for appending rows and aggregating them. Use a relational database for data that changes row by row.
