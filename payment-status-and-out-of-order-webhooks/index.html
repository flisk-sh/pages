Payments and webhooks locally

How to handle out-of-order payment webhook events

The event that says a payment succeeded can arrive before the event that says it was created. Your handler has to give the same result either way.

Payment providers do not guarantee that webhook events arrive in the order they happened, so a handler that applies each event as it comes can move a payment backwards, for example from "succeeded" to "processing". The reliable fix is to store the payment as a state machine with a rank per state, update it only when the new state ranks higher, and fetch the object from the provider when you need to be sure.

Why order breaks

Webhook delivery is at least once, from many workers, with retries. Event A can fail on the first attempt and be retried after event B was delivered. Stripe says this plainly in its documentation: it does not guarantee delivery in the order events were created. Your own network adds delay too, so the order you log is not the order that happened.

The classic damage looks like this. A payment goes processing then succeeded. The two events arrive reversed. A naive handler sets succeeded, then overwrites it with processing, and the order never ships.

Model the states first

Write down the states and the allowed moves before writing a handler. A small set covers most payment flows:

StateRankCan move to
created10processing, failed, succeeded
processing20succeeded, failed
failed30succeeded (a retry with a new card)
succeeded40refunded, disputed
refunded50none

Ranks make the rule one comparison: apply an event only if it moves the payment to a higher rank. A late processing arriving after succeeded is dropped. The exact states are yours to choose. The point is that each one has a number and the number never goes down.

Apply events with a guarded update

Do the comparison in the database, in one statement, so two concurrent handlers cannot interleave a read and a write:

CREATE TABLE payments (
  id          text PRIMARY KEY,
  status      text NOT NULL,
  status_rank int  NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

UPDATE payments
   SET status = $2, status_rank = $3, updated_at = now()
 WHERE id = $1 AND status_rank < $3;

If the row count is zero, either the event was stale or the payment row does not exist yet. For the second case, insert the row with the state from the event, using ON CONFLICT DO NOTHING first so an early event creates the record that a late "created" event finds already there.

When the event is not enough: fetch the object

An event is a snapshot from when it was created. The simplest correct handler treats it as a hint: take the payment ID from the event, call the provider's API to get the current object, and write that. The current state cannot be stale in the way an old event can. It costs one API call per event, and it needs a retry policy for the case where the API call fails, so keep it in a worker, not in the request. With Stripe, that is stripe.paymentIntents.retrieve(id) followed by the guarded update.

Test it by reversing the events

This is the check that finds real bugs. Write a test that takes a list of events for one payment and applies them in every order, or at least in forward and reverse, and asserts the same final state. A dozen lines of test code replace a class of production incidents. It needs no provider and no network: the events are saved JSON files.

const events = [created, processing, succeeded];

for (const order of [events, [...events].reverse(), [events[1], events[2], events[0]]]) {
  await resetPayments();
  for (const e of order) await post("/webhooks/demo", sign(e));
  assert.equal((await getPayment("pay_1")).status, "succeeded");
}

With Flisk, flisk up starts the API and its database as one stack, and flisk logs --service api shows which events were applied and which were dropped as stale. Make the handler log the decision, with the event ID, the current rank and the incoming rank. That one log line answers most "why is this payment stuck" questions.

Pitfalls

  • Ordering by event timestamp. Two events can share a timestamp, and clocks at different workers differ. Prefer state rank, or the provider's own sequence if it gives one.
  • Ranks for states that can reopen. A failed payment can later succeed with a new card, so a failure must not freeze the record. The table above allows that by giving failed a lower rank than succeeded.
  • Side effects inside the handler. Sending a receipt when the status changes is fine once. Make it depend on the row count of the guarded update, so a dropped stale event sends nothing.
  • Handling each event type separately with no shared record. A charge.refunded that arrives before you have stored the charge needs somewhere to land. Create the row on first sight.

Duplicates are a separate problem with a separate fix, covered in testing webhooks locally. When even the guarded handler cannot recover because an event never came, see reconciling payments after missed webhooks.

Questions people ask

Does Stripe guarantee webhook event order?

No. Stripe's documentation says events may arrive in a different order than they were created, so your handler must not depend on arrival order.

How do I stop an old event overwriting a newer payment status?

Give each status a rank and update only when the new rank is higher, in a single SQL statement. A stale event then changes nothing.

Should I call the provider API from a webhook handler?

It is the safest way to get current state, but do it in a worker with retries. Keep the request itself fast and return success once the event is stored.
