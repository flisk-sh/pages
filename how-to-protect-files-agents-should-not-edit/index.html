How to Protect Files Coding Agents Should Not Edit

Use CODEOWNERS, branch protection and a path-based CI check so an agent cannot quietly change workflows, migrations or lockfiles.

Tell agents which files are off limits in AGENTS.md, then enforce it with CODEOWNERS and branch protection so a human must approve any change to those paths. A rule in a text file is a request; a required review is a control.

Decide what is sensitive

Start with a short list. Typical candidates:

  • .github/workflows/: a changed workflow can change what CI trusts.
  • Migration folders: old migrations must never be edited.
  • Lockfiles and dependency manifests, when you want a person to approve new dependencies.
  • Generated files, which should be rebuilt, not hand-edited.
  • Auth, billing and permission code.

Enforce with CODEOWNERS

A CODEOWNERS file names who must review changes to a path. Combined with the branch protection setting that requires review from code owners, the agent's pull request cannot merge until a human approves.

# .github/CODEOWNERS
/.github/workflows/  @your-org/platform
/migrations/         @your-org/backend
/src/billing/        @your-org/payments

Use teams, not single people, so reviews do not stall when someone is away.

Add a path check in CI

For rules CODEOWNERS cannot express, such as "never edit an existing migration", add a small check that compares the pull request with the base branch.

git fetch origin main
if git diff --name-status origin/main...HEAD | grep -E '^(M|D)\s+migrations/'; then
  echo 'Existing migrations must not be modified'
  exit 1
fi

This catches modified and deleted files while allowing new ones.

Protect the rules themselves

If an agent can edit the CI workflow, it can edit the check. Put workflows and CODEOWNERS under their own required review, and keep branch protection settings out of the repo's reach by managing them as an admin. For workflow hardening in general, see GitHub Actions security.

Using rulesets and rollout

Repository rulesets let you apply protections across many branches or repositories from one place, and are worth using if you manage more than a few repos. Start in evaluate or log-only mode where available, so you see which pull requests would have been blocked before you enforce the rule. That avoids a day of surprised developers.

Roll out in steps. First write the protected paths list and agree it with the owning teams. Second add CODEOWNERS entries without enforcing review. Third turn on the code-owner review requirement for one repository and watch for a week. Finally apply it everywhere. During the rollout, tell the teams what the agent-facing message will say when a check fails, so the agent can read it and stop rather than work around it.

Remember to review the protected list every quarter. New sensitive areas appear as a codebase grows, and old ones disappear.

Questions people ask

Does CODEOWNERS block an agent from pushing?

Not by itself. It requires review from owners only when branch protection has the code-owner review option turned on for the target branch.

Should agents ever edit workflows?

Rarely. If they do, require a human code-owner review and keep the change as a separate pull request.
