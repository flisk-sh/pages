ModuleNotFoundError when starting a Python service: fixes

The error says a module is missing. Usually the module is installed, just not for the Python that is running. Here is how to find which Python that is, and the usual fixes.

ModuleNotFoundError: No module named 'x' means the Python that is running right now cannot find x on its search path. First find out which interpreter that is and what its path contains, then fix one of three things: install the package into that interpreter, run from the folder that makes your own modules importable, or correct a name that shadows a real module.

Step 1: ask the running Python

Do not guess. Run this with the same command, in the same shell, that fails:

python -c "import sys; print(sys.executable); print(sys.path)"
python -m pip show fastapi

The first line names the interpreter and the folders it searches. The second tells you whether a package is installed for that interpreter. If pip show reports nothing, the package is missing from this environment, even if you installed it yesterday somewhere else. Using python -m pip matters here: a bare pip can belong to a different Python than the python next to it.

Cause 1: the package is installed in a different environment

This is the most common one. You installed into the system Python and run in a venv, or the reverse, or an editor uses another interpreter than your terminal. Activate the project's environment, install again, and confirm with sys.executable. A command such as uvicorn can also be the global one on your PATH while your packages live in .venv. which uvicorn shows which one runs. See one virtual environment per project for the setup.

Cause 2: your own module is not importable

For your own code, Python searches the folder of the script you ran, or the current folder with -m, plus installed packages. With a layout like this:

api/
  pyproject.toml
  src/
    main.py
    app/
      routes.py

uvicorn main:app run from api/ fails with "No module named 'main'", because main.py is inside src. Fix it by telling uvicorn where to look, or by running from the right folder:

uvicorn main:app --app-dir src --reload

For pytest, pythonpath = ["src"] under [tool.pytest.ini_options] does the same. For a proper long-term answer, make the project installable with python -m pip install -e . so imports work from anywhere. Also check relative imports: from .routes import x only works when the file is imported as part of a package, not when you run the file directly with python routes.py. Use python -m app.routes from the right folder instead.

Cause 3: a file shadows a real module

A local file named random.py, email.py, types.py or the name of the library you are importing wins over the real module, because the current folder comes first on the search path. The error then says an attribute is missing, or an import fails with a confusing trace. Rename the file, and delete stale __pycache__ folders if the error persists.

What a process manager changes

When a tool starts your service, it may use a different shell, working directory and PATH than your terminal. That is why "it works when I run it by hand" happens. With Flisk, a service that has a command in its service.json runs from the service's own folder, in a process that inherits the environment of the shell where you ran flisk up. Two consequences:

  • If you activated your virtualenv in another terminal, flisk up does not see it. Activate it in the shell that starts Flisk, or put the interpreter in the command, for example .venv/bin/uvicorn main:app --port $PORT.
  • Paths in the command are relative to the service folder, not the repository root. --app-dir src then points at src inside that service.

To see exactly what the service sees, run a one-off command with its environment:

flisk run api -- python -c "import sys; print(sys.executable)"
flisk run api -- python -m pip show fastapi

flisk run works on the host, from the service folder, with the project .env, your shell and the service's env. If those commands print what you expect and the service still fails, compare them with the failing command. If the interpreter version is the issue, the toolchain field in service.json makes flisk up stop with the wanted and found versions, which is a clearer message than an import error. Flisk does not install packages or create virtualenvs, so installing remains your step. The general method for a service that will not start is in how to debug a service that will not start.

The container route is different again. A Python service scaffolded by Flisk is built from its pyproject.toml, so a dependency missing from that file is missing in the container, whatever you installed on your host.

Pitfalls

  • Installing with sudo. It puts the package in the system Python, not in the venv you run.
  • A stale venv. After upgrading Python, the old .venv still points at the previous interpreter. Delete it and rebuild.
  • Typos in install names. The import name and the package name can differ, such as import yaml from the package PyYAML, or import PIL from Pillow.
  • Editor and terminal disagree. Select the interpreter in the editor to match sys.executable in the terminal.

Next step

Once the import works, make the version choice permanent with pinning the Python version. For install speed and lock files, see uv vs pip.

Questions people ask

Why does pip say a package is installed but Python cannot import it?

The pip you ran belongs to a different interpreter than the python that is running. Use python -m pip, and check sys.executable and pip show in the same shell.

How do I make imports work with a src folder?

Pass --app-dir src to uvicorn, set pythonpath = ['src'] for pytest, or install the project in editable mode with python -m pip install -e .

Why does the service fail only when started by a tool?

The tool may use a different working directory, shell or PATH. Activate your virtualenv in the shell that starts it or name the interpreter in the command.
