Local development for a Go API with live reload

Go has no built-in watch mode, so live reload is a choice you make. Here are the options and what Flisk scaffolds for each runtime.

The Go toolchain has no file watcher: go run . compiles and runs once. For live reload you add a watcher such as air, or you let your dev tool rebuild on change. Flisk scaffolds a Go net/http API in two modes, a plain process with go run . and a Docker mode where live reload is opt-in.

Why Go dev loops feel slow

A Go build is fast, but a manual loop of stop, build, start adds up over a day. The simple fix is a watcher that restarts the binary on a file change. Air is the popular one, and watchexec -r -e go -- go run . works as well. In containers a second cost appears: if every change rebuilds the whole image, you wait for Docker layers instead of the compiler.

The plain approach

go install github.com/air-verse/air@latest
air

Keep each service in its own module (go.mod per folder) so a change in one API does not rebuild another. Test with go test ./.... Read configuration from the environment and listen on PORT, so the same binary runs in any tool.

The Flisk way, as a local process

With --local the scaffold needs no Docker. It writes go.mod, main.go and main_test.go, and a command of go run ..

npm install -g @flisk-sh/flisk
flisk resource orders --language go --local --stack app --yes
flisk up --only orders

The service has a /health route, so Flisk can wait for it before it starts anything that depends on it. A local go run . does not reload by itself. If you want reload there, write your own command in service.json, for example air, and keep the other fields.

Local mode has no live reload for Go by default. Change command to a watcher, or restart the service with flisk restart orders after a change.

The Flisk way, in Docker

Without --local, the same command creates a Go service that runs in a container behind Traefik:

flisk resource orders --language go --stack app --yes
flisk up

By default there is no live update in this mode: when you change a file, Tilt rebuilds the image. That is correct but slower than a watcher. To turn the live loop on, add one field to the service's service.json:

{
  "appName": "orders",
  "appType": "backend",
  "language": "go",
  "dev": { "liveReload": true }
}

With liveReload on, a watcher (flisk-go-watch) rebuilds the program when a .go file changes, without a new image build. If the code does not compile, the last good build keeps running, so one typo does not take the service down. Changes to go.mod or go.sum still rebuild the image, because new dependencies must be installed.

The image is based on golang:1.23 with GOTOOLCHAIN=auto, so a newer Go version in your go.mod can be fetched by the toolchain. The API is served at http://api.<project>.localhost/api/orders, with /api/orders stripped before it reaches your handler, so register routes at /health and /items, not under the prefix. If you need a CORS rule for a frontend, the scaffold already allows *.localhost origins.

Test the handler before you run the stack

A Go HTTP handler is easy to test without a server. The scaffold ships a main_test.go that exercises the router, and you can follow the same pattern for new routes: build a request with httptest.NewRequest, send it to the handler with httptest.NewRecorder, and check the status and body. Running go test ./... takes a moment, and it catches a broken route before you wait for a container to restart. Keep the router in a function that returns an http.Handler so tests and main use the same code.

Pitfalls

  • One module per service folder. The scaffold expects a go.mod in each service directory. A shared parent module will confuse the image build.
  • Listen on PORT. Flisk passes the port in the environment. Do not hard-code 8080.
  • Bind all interfaces in a container. Traefik reaches the container over the Docker network, so listening on localhost only is not enough in Docker mode.
  • Slow first build. The first image build downloads modules and takes longer than the ones after it.

Questions people ask

Does go run reload on file changes?

No. go run compiles and runs once. For live reload use a watcher such as air or watchexec, or set dev.liveReload to true in a Flisk Docker service.

What happens if my Go code does not compile with liveReload on?

The watcher keeps the last good build running and shows the compile error, so the service stays up until you fix the code.

Can I run a Go API with Flisk without Docker?

Yes. flisk resource with --language go and --local writes a service with command go run . that runs as a plain process, with no Docker or Tilt.
