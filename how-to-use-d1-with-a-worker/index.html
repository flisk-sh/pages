How to use D1 with a Cloudflare Worker

Create a D1 database, bind it to a Worker, write migrations, and run safe parameterised queries from your handler, with local and remote steps.

Create a database with npx wrangler d1 create app, add the printed binding to wrangler.toml, apply SQL migrations, and query with env.DB.prepare(...).bind(...). D1 is SQLite on Cloudflare's network.

Create and bind

npx wrangler d1 create app

The command prints a block to paste into your config.

[[d1_databases]]
binding = "DB"
database_name = "app"
database_id = "PASTE-THE-ID-HERE"

Write a migration

npx wrangler d1 migrations create app init

This creates a numbered SQL file in migrations/. Edit it.

CREATE TABLE notes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  body TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
npx wrangler d1 migrations apply app --local
npx wrangler d1 migrations apply app --remote

Apply locally first, then remote. Never edit a migration that has already been applied. Add a new one.

Query from the Worker

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (request.method === "POST" && url.pathname === "/notes") {
      const { body } = await request.json();
      await env.DB.prepare("INSERT INTO notes (body) VALUES (?)")
        .bind(body).run();
      return new Response(null, { status: 201 });
    }
    const { results } = await env.DB
      .prepare("SELECT id, body FROM notes ORDER BY id DESC LIMIT 50")
      .all();
    return Response.json(results);
  },
};

Always use ? placeholders with bind. Building SQL by string concatenation invites injection.

Batching

Use env.DB.batch([...]) to send several statements in one round trip. A batch runs as a transaction, so it also keeps related writes consistent.

Inspect and back up data

Query the remote database from your terminal to check what is actually stored.

npx wrangler d1 execute app --remote --command "SELECT count(*) AS n FROM notes"
npx wrangler d1 export app --remote --output backup.sql

Take an export before any risky migration, such as dropping a column. Treat the backup file as sensitive, since it contains your data, and keep it out of Git.

Add indexes for columns you filter on, for example CREATE INDEX idx_notes_created ON notes (created_at);. Without them, queries scan the whole table, which costs more reads and gets slower as data grows. Check query plans with EXPLAIN QUERY PLAN before shipping a new query.

Know the limits

  • Each database has a size cap and row and query limits that depend on your plan. Check the D1 limits page.
  • It is SQLite, so it suits small and medium read-heavy apps, not heavy write workloads.
  • For simple key lookups KV may be enough, see KV vs D1.

Questions people ask

Can I export a D1 database?

Yes, Wrangler has an export command for D1. Check wrangler d1 export in the current docs for options.

Can I use an ORM?

Yes, several work with D1, such as Drizzle. Check each tool's D1 guide for setup.
