Local URLs, routing and HTTPS

Fix "Invalid Host header" and blocked hosts in local dev

Your proxy works. The framework behind it refuses the name in the Host header, on purpose.

"Invalid Host header", "Blocked request. This host is not allowed" and Django's DisallowedHost mean the same thing: the server saw a Host header it was not told to accept. Add that host name to the framework's allowed list (server.allowedHosts in Vite, allowedHosts in webpack dev server, ALLOWED_HOSTS in Django, config.hosts in Rails), then restart the server.

Why frameworks check the Host header

A dev server that listens on your machine can be attacked through DNS rebinding: a malicious site points its own name at 127.0.0.1 and reads responses from your local server. Checking that the Host header is a name you expect blocks that. So the checks exist for a reason, and the fix is an allowed list, not turning the check off for good.

You meet the error the first time something other than localhost:port reaches the server: a reverse proxy, a gateway such as Traefik, a tunnel, or a custom name like app.shop.localhost or myapp.test. A proxy forwards the original Host header by default, so the framework sees the public name, not the port it listens on.

The fix for each framework

ToolSetting
Viteserver.allowedHosts: [".localhost", "myapp.test"] (a leading dot allows subdomains; true allows everything)
webpack dev serverdevServer.allowedHosts: ["auto"] or a list such as [".localhost"]
DjangoALLOWED_HOSTS = [".localhost", "myapp.test"]
Railsconfig.hosts << "myapp.test" in config/environments/development.rb
Next.js, Express, FlaskNo Host check by default, so this error does not come from them

Vite documents a default that already lets localhost names and IP addresses through, so a *.localhost name often works untouched while a .test or tunnel name does not. Keep the list in an environment variable if several developers use different names.

Option: rewrite the Host header in the proxy

If you cannot change the app, make the proxy send a Host the app accepts:

# nginx
proxy_set_header Host localhost:3000;

This works but hides the real name from the app, so absolute URLs it generates will be wrong. Prefer the allowed list.

Flisk and the Host header

In the Docker path, Traefik forwards the request to your container with the original host, api.<project>.localhost. Flisk's bring-your-own guide records the effect: a Rails example was blocked by Rails' host check until it allowed any host in its development setup, while most other examples (Angular, Flask, Gin, Symfony, Quarkus, Micronaut, Echo, chi, Sinatra, Docusaurus, SolidStart, Phoenix) accepted the name with no change. That list covers only the examples Flisk tested through flisk up, so test yours.

A good first check is to ask the service directly with the same header:

curl -i -H "Host: api.shop.localhost" http://127.0.0.1:4000/health

If this returns 400 or 403 while a plain request to localhost:4000 works, you have the host check. Run flisk logs to read the service's own message, and flisk networks to see the exact name the route uses (replace shop with your project name; the port in the printed URL is part of what a client sends, but the Host check usually looks at the name).

For services that run as local processes, Flisk prints http://localhost:<port>, so the Host header is localhost:<port> and this error rarely appears, unless you add your own proxy or domain in front.

Pitfalls

  • Allowing everything permanently. allowedHosts: true or ALLOWED_HOSTS = ["*"] is fine for a throwaway session. Do not copy it into production settings. Use separate settings per environment.
  • Forgetting to restart. Most of these settings are read at start.
  • Port in the list. Hosts in these lists are names without ports (Django strips the port before comparing; do not put it in).
  • Tunnels. A public tunnel name changes on every run. Allow the tunnel domain with a leading dot, such as .ngrok-free.app, not each name.

If the error appears only for one name, check how that name reaches the app: using a custom local domain explains how names and hosts files work. For a name that does not resolve at all, see why a *.localhost subdomain does not resolve.

Questions people ask

What causes Invalid Host header?

The server received a Host header that is not in its allowed list. It happens when a proxy, tunnel or custom domain sends a name the framework does not expect.

Is it safe to disable the host check locally?

Only briefly. The check protects against DNS rebinding, so prefer a list of the names you actually use.

How do I see which Host header my service gets?

Send a request with the header you expect, for example curl -H "Host: api.shop.localhost" against the service port, or log request.headers.host in the app.
