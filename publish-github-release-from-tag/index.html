How to Publish a GitHub Release from a Tag with Actions

A small workflow that runs on a version tag, tests the code, builds the artifacts and creates the GitHub release, with the permissions it needs and nothing more.

Trigger a workflow on tags that match v*, run the tests and the build, then create the release with the GitHub CLI. Give the job contents: write and nothing else. This turns a release into one action: push a tag.

The workflow

name: Release
on:
  push:
    tags: ['v*']

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
      - run: npm run build
      - run: npm pack
      - name: Create release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create "$GITHUB_REF_NAME" *.tgz --generate-notes

GITHUB_REF_NAME is the tag name. The *.tgz attaches the packed artifact to the release.

Cut the tag

Bump the version in the project file, commit, tag and push. Use an annotated tag so the tag has an author and a date.

npm version minor -m 'release %s'
git push --follow-tags

npm version edits package.json, commits and creates the tag. For other ecosystems, edit the version file by hand and run git tag -a v1.5.0 -m 'v1.5.0'. Check that the tag matches the version in the file inside the workflow, so a typo cannot publish the wrong thing:

test "v$(node -p "require('./package.json').version")" = "$GITHUB_REF_NAME"

Run the same checks as on main

Do not assume the tagged commit was green. Run the tests in the release workflow, or require that the commit already has a passing run. A release from a red commit is the most common avoidable mistake. Keep the workflow idempotent: if it fails halfway and you re-run it, it should not break because the release already exists. Use gh release view to check first, or edit instead of create.

Permissions and protection

Set permissions at the top and keep it small. Only people you trust should be able to push tags, so use tag protection rules or rulesets for v*. If the release publishes to a registry, move that to a separate job with an environment that requires approval, see secure a release workflow. Pin third-party actions by commit SHA when the job holds publish rights, as covered in GitHub Actions Security.

Test the workflow without a real release

Run the workflow once from a fork or a throwaway repository with a tag such as v0.0.1-test. Check that the release page, the attached files and the notes look right, then delete the test release and tag. You can also add a workflow_dispatch trigger with an input that makes the last step a dry run and prints what it would create. A rehearsal costs minutes and avoids a public mistake.

Pitfalls

  • A tag pushed with GITHUB_TOKEN from another workflow does not start new workflow runs. Push tags with a person's credentials or a dedicated token if a workflow creates them.
  • Checking out with a shallow clone hides history. If your notes or version logic need history, set fetch-depth: 0.
  • Do not move a published tag. Consumers may already have used it. Make a new patch release instead.

Questions people ask

Should the release workflow run on release creation or on tag push?

Tag push is simpler: the tag is the trigger and the workflow creates the release. Triggering on release creation fits teams that draft releases by hand first.

Can I mark a release as a pre-release?

Yes, add the --prerelease flag to gh release create, for example when the tag contains rc or beta.
