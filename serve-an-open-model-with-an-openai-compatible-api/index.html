Open models and self-hosted inference

How to serve an open model with an OpenAI-compatible API

Run a model behind a standard chat completions endpoint so existing code works unchanged. Commands for vLLM, llama.cpp and Ollama, plus auth and testing.

Start a server that speaks the OpenAI chat completions format, then point your client's base URL at it. With vLLM that is vllm serve <model>, with llama.cpp it is llama-server, and Ollama already serves /v1.

vLLM

pip install vllm
vllm serve <huggingface-model-id> --max-model-len 8192 --api-key my-secret
# listens on http://localhost:8000/v1 by default

The --api-key option makes the server require that key. Use it whenever the port is reachable by anyone else. The model must fit on your GPU, see VRAM.

The model id you pass in requests must match what the server loaded. For vLLM that is the Hugging Face id you served. Ask the server what it has with curl http://localhost:8000/v1/models if you are unsure.

Gated models on Hugging Face need you to accept their terms and provide a token before the download works. Set it as the HF_TOKEN environment variable.

llama.cpp

llama-server -m ./model-q4_k_m.gguf --port 8080 -c 4096
# endpoint: http://localhost:8080/v1/chat/completions

Flags differ between llama.cpp builds. Run llama-server --help to see options for GPU layers, parallel slots and context size. A larger context uses more memory, so raise it only as far as your inputs need.

Ollama

ollama serve
# endpoint: http://localhost:11434/v1/chat/completions

On most installs the service already runs in the background.

Test it with curl, then a client

curl http://localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer my-secret" \
  -H "Content-Type: application/json" \
  -d '{"model": "<huggingface-model-id>", "messages": [{"role": "user", "content": "ping"}]}'
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="my-secret")
r = client.chat.completions.create(
    model="<huggingface-model-id>",
    messages=[{"role": "user", "content": "ping"}])
print(r.choices[0].message.content)

If the first request works with curl but your app fails, compare headers and the model name. Wrong model names and missing keys account for most first-day errors. Add a streaming test too, because some proxies buffer streamed responses and break the live output.

Pitfalls

  • Not all parameters are supported. Tool calling, JSON mode and logprobs vary by server and model. Test the ones you rely on.
  • Chat templates. The server applies the model's template. A wrong template gives odd output.
  • Public exposure. Put TLS and a key in front of anything reachable from the internet.

If your app uses structured output, read prompts and structured outputs. To compare servers, see Ollama vs vLLM vs llama.cpp.

Finally, put the base URL and key in environment variables, not in code, so the same app can run against a local server in development and a different endpoint in production without edits.

Questions people ask

Why use the OpenAI-compatible format for my own model?

Most libraries and tools already speak it, so you can switch between a hosted model and your own by changing the base URL and model name.

What API key do I pass if I set none?

Most local servers ignore the key, but client libraries require a non-empty string, so any placeholder works.
