How to use Postgres row level security for tenant isolation

A forgotten WHERE clause is the classic tenant leak. Row level security moves the filter into the database, so one missed query cannot expose another customer.

Enable row level security on each tenant table, add a policy that compares tenant_id to a setting your app sets at the start of every transaction, and connect as a role that is neither a superuser nor the table owner. Then a query without a tenant filter returns nothing instead of leaking rows.

What RLS does and does not do

Row level security adds an invisible condition to every query on a table, based on policies you define. It protects against bugs in your queries, not against a stolen database password or an attacker who can run arbitrary SQL as your app role, because that role can also change the setting. Treat it as a second lock, with correct application code as the first.

Step by step

Start from a table that already has a tenant_id column, as described in multi-tenant database design.

alter table projects enable row level security;
alter table projects force row level security;

create policy tenant_isolation on projects
  using (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  with check (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);

Three details matter. current_setting('app.tenant_id', true) returns null instead of raising an error when the setting is missing, so an unscoped query sees no rows. using filters reads, updates and deletes, and with check rejects inserts and updates that would write a row for another tenant. force row level security applies the policy to the table owner as well.

Now create the role your app uses. It must not own the tables:

create role app_user login password 'change-me-locally' nosuperuser nobypassrls;
grant select, insert, update, delete on all tables in schema public to app_user;
grant usage on schema public to app_user;

Run migrations as an owner role, and run the API as app_user. Use two separate connection strings.

Setting the tenant per request

Set the value inside a transaction with set_config and its third argument true, which makes it local to that transaction:

await db.transaction(async (tx) => {
  await tx.query("select set_config('app.tenant_id', $1, true)", [tenantId]);
  return tx.query("select * from projects");
});

The local flag is essential with a connection pool. A plain session-level set stays on the connection after the request ends, and the next request that borrows the connection inherits the previous tenant. That is a leak that RLS was meant to prevent. With set_config(..., true) the value disappears at commit or rollback. If you use a pooler in transaction mode, session settings are also unreliable, which is another reason to stay with the local form.

Prove it works locally

The most common surprise is that RLS appears to do nothing. The Postgres container's default user, the one you create with POSTGRES_USER, is a superuser, and superusers bypass every policy. Roles with BYPASSRLS do too. If your local API connects as that user, your cross-tenant test passes for the wrong reason.

Check from the same connection your app uses:

select current_user, rolsuper, rolbypassrls
from pg_roles where rolname = current_user;

Both flags must be false. Then write a test that seeds two tenants, sets tenant A, and asserts that selecting from projects returns only A's rows, that an insert with B's tenant_id fails with an RLS error, and that a query with no setting returns zero rows.

With Flisk

Flisk does not create database roles for you, so put the role creation in your own migration or init SQL. What it helps with is running the check against the live stack. With a service named api, run a command in that service's environment:

flisk run api -- npm run test:tenant-isolation

The command gets the same environment the service has, including its database URL. If the stack uses a separate migrator resource, give the migrator the owner URL and the API the app_user URL through each service's env, with passwords coming from the project .env and not written into service.json.

When not to use it

  • Queries that must read across tenants, such as admin reports or background jobs, need a separate role with bypassrls or a policy for it. Keep that role out of the request path.
  • Policies that call functions or subqueries on every row can slow big tables. Keep the policy a plain column comparison and index tenant_id first.
  • If you run a schema or database per tenant, you already have stronger isolation and this adds little.

Next, decide how the tenant is identified on each request. Resolving the tenant from a subdomain is the usual start.

Questions people ask

Why does Postgres row level security not apply to my local user?

Superusers and roles with BYPASSRLS skip all policies, and the default user of the Postgres Docker image is a superuser. Connect the app as a plain role that does not own the tables.

Is SET LOCAL safe with connection pooling?

Yes, when used inside a transaction. set_config with the local flag set to true is cleared at the end of the transaction, so the next borrower of the connection starts clean.

Does row level security replace WHERE tenant_id in queries?

No. Keep filtering in your code for clarity and index use. RLS is the backstop for the query you forget.
