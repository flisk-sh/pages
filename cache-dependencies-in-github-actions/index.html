How to Cache Dependencies in GitHub Actions (npm, pip, Go)

Use setup actions' built-in cache or actions/cache with a lockfile hash key. Includes restore keys, cache size limits to watch and when caching makes things worse.

The simplest way to cache dependencies is to turn on the cache option of the setup action you already use. For anything else, use actions/cache with a key built from the hash of your lockfile, so the cache refreshes only when dependencies change.

Built-in caching in setup actions

Setup actions for Node, Python and Go can manage the cache for you.

- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm
- run: npm ci

- uses: actions/setup-python@v5
  with:
    python-version: '3.12'
    cache: pip
- run: pip install -r requirements.txt

- uses: actions/setup-go@v5
  with:
    go-version: stable

The key comes from the lockfile, such as package-lock.json or requirements.txt. Recent setup-go versions cache modules by default. Check the action's README for the current behavior.

Manual caching with actions/cache

- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('**/requirements.txt') }}
    restore-keys: |
      pip-${{ runner.os }}-

The key is an exact match. If no exact match exists, GitHub tries restore-keys prefixes and restores the newest cache that matches. That gives you a warm start even after a dependency bump, and the new cache is saved at the end.

Cache the download, not the install

Cache the package manager's download cache, such as ~/.npm or ~/.cache/pip, rather than node_modules. Then run npm ci as usual. It is safer, since a restored node_modules can be stale or built for another Node version, and npm ci deletes it anyway.

Limits and gotchas

  • Caches are scoped to branches. A pull request can read the default branch cache, but not the other way around.
  • GitHub keeps a limited amount of cache per repo and removes the least recently used entries. Check the docs for the current limit.
  • Do not cache secrets or anything you would not want another job in the repo to read.
  • Include runner.os in the key. Native modules differ between operating systems.

Check that the cache works

Open a run and look at the cache step. A hit prints a line like Cache restored from key and a miss prints that no cache was found. Run the workflow twice on the same lockfile. The second run should hit. If it does not, print the computed key and compare it between runs. Common causes are a path that differs per runner, a key with a changing value, or a lockfile that is generated during the run. Fix the key first, then compare step durations to confirm the install step got shorter.

When caching does not help

Restoring and saving a cache takes time too. If your install takes 10 seconds and the cache is 800 MB, you may lose time. Compare the step times before and after. Heavy gains come from compiled languages and large dependency trees. For container builds, see Docker build caching.

Questions people ask

Why is my cache never hit?

Usually the key changes every run, for example because it includes a timestamp or the run id. Build the key from the lockfile hash only.

Is a cache shared between pull requests?

A pull request can restore caches from its base branch, but caches saved by one pull request are not available to other pull requests.
