How to Archive or Hand Over an Open-Source Project

What to do when you can no longer maintain a repository: update the README, say it plainly, find a successor or archive it, and protect users who still depend on it.

  2. Tell people first

If you cannot maintain a project, say so in the README, then either hand it to someone trustworthy or archive the repository. Silence is the worst option, because users keep depending on code that nobody will fix.

Decide which path fits

  • Hand over when the project is used and there are active contributors who want it.
  • Archive when the project is finished or you see no successor. Archiving makes it read-only and shows a banner.
  • Keep with reduced scope when you only fix security issues and merge small pull requests. Say so explicitly.

Tell people first

Add a clear notice at the top of the README. Say the status, the date, the reason if you wish and where users should go next.

> **Status: no longer maintained.** I archived this repository on
> 2026-01-15. Security fixes will not be released. A maintained fork:
> https://github.com/other/fork

Pin a closing issue with the same text, and publish a final release so package pages show the notice too. For package registries, use their deprecation feature so installers see a warning, for example npm deprecate pkg@"*" "Unmaintained, use other-pkg".

Handing over safely

Choose people with a record in the project, not a stranger who emails asking for ownership. Several well-known supply chain attacks began with a newcomer who gained maintainer rights. Add them gradually: first triage, then write access, then admin. Move the repository to an organisation if you can, enable two-factor authentication requirements there, and make sure release credentials and registry ownership move too. Rotate any tokens you held. See secrets best practices.

Archive correctly

  1. Close or label open issues and pull requests, or at least pin an explanation.
  2. Publish the final release and deprecate packages.
  3. Update the description and homepage to say archived.
  4. In Settings, under Danger Zone, choose Archive this repository.
  5. Keep the license file as it is, so forks stay legal.

Archiving is reversible: you can unarchive later if you return. Nothing is deleted, so links and history keep working.

Help downstream users

Suggest alternatives you have checked, and describe migration steps if you know them. If you maintain related projects, update their dependency lists. Users will find the project through old blog posts for years, so the notice in the README is what saves them. Consider how you would have wanted to see a dependency end, and do that. Then review how to judge whether a project is maintained from the other side.

Write the notice before you feel finished. Many maintainers wait until they have the energy for a perfect handover, and the project sits silent for years. A two-line notice today is better than a thorough plan next year. You can improve the notice later, add a migration guide when you have time, and still change your mind if circumstances change, since both the notice and the archive state can be reverted.

Questions people ask

Can I unarchive a repository?

Yes. Archiving is reversible in the repository settings, and history, issues and stars are kept. Unarchive it if you resume work.

Should I delete the repository instead?

Usually no. Deleting breaks links and removes code that others depend on, though forks may survive. Archiving with a clear notice is kinder and keeps the license and history.
