How to run scheduled jobs with Cron Triggers

Add a scheduled handler to a Worker, set a cron expression, test it locally and handle failures so a nightly job does not silently stop.

Add a scheduled handler to your Worker and a [triggers] block with a cron expression in wrangler.toml. Deploy, and Cloudflare calls the handler on that schedule.

The handler and the schedule

export default {
  async scheduled(event, env, ctx) {
    ctx.waitUntil(cleanup(env));
  },
};

async function cleanup(env) {
  await env.DB
    .prepare("DELETE FROM sessions WHERE expires_at < datetime('now')")
    .run();
}
[triggers]
crons = ["0 3 * * *"]

The expression has five fields: minute, hour, day of month, month, day of week. This one runs at 03:00 UTC every day. Cron triggers run on UTC time.

Test locally

npx wrangler dev --test-scheduled
curl "http://localhost:8787/__scheduled"

The curl call invokes your scheduled handler once, so you can check the logic without waiting.

Combine with fetch

One Worker can have both a fetch and a scheduled handler. A typical small-app pattern: the cron fetches data from an API and stores it in D1 or KV, and the HTTP handler serves it from storage. This keeps the public endpoint fast and avoids calling the upstream on every request.

Make jobs idempotent

A job may run twice or be retried after a failure. Write it so a second run does no harm: use INSERT OR REPLACE, or check a marker row first. Record the last success time in storage so you can see when it stops.

await env.DB.prepare(
  "INSERT OR REPLACE INTO job_state (name, last_ok) VALUES ('cleanup', datetime('now'))"
).run();

Common job ideas

  • Delete expired sessions or old rows.
  • Refresh a cached API response into KV so reads are instant.
  • Send a daily digest by calling an email API.
  • Check an external page and post to a chat webhook if it changed.

Keep each job small and observable. If a job needs more than the CPU limit, move it to a queue or split it across several runs. Do not embed long-running work in one invocation.

Write down what each cron does and who owns it, in the README. Scheduled jobs are invisible until they fail, and a short note about the schedule, the data it touches and how to run it by hand will save the next person a lot of time.

Monitor it

  • Check the dashboard for trigger invocations and errors.
  • Call an uptime check on a /status route that reports last_ok and alerts if it is too old.
  • Stay within CPU time limits. If a job is large, split it into pages and process a batch per run. See the free plan limits.

Questions people ask

What timezone do cron triggers use?

UTC. Convert your local time when writing the expression.

How often can a cron run?

As often as every minute. Check the current limits for the number of triggers allowed per Worker.
