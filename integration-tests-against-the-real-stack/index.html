Test the real stack, then hand it off

How to run integration tests against a real local stack

An integration test that talks to a fake database proves little. Here is how to run the same tests against the services you actually ship, locally and in CI.

To run integration tests against a real stack, start every service the test needs, wait until each one reports healthy, run the tests with the service URLs in environment variables, and tear the stack down afterwards. The two steps people get wrong are the waiting (a fixed sleep is a flaky test waiting to happen) and the data (a test that leaves rows behind makes the next run fail for no visible reason).

What an integration test should cover

A unit test checks one function. An integration test checks that two or more pieces you own actually work together: your API and its database, a worker and its queue, a frontend and the API it calls. Mocks hide exactly the bugs you are looking for here: a column that does not exist, a header the gateway strips, a migration that was never applied.

So run the real thing for everything you own, and decide separately what to fake. That second question is covered in mock or run the real service.

The shape of a reliable run

  1. Start the stack from a clean state, or from a state you can describe.
  2. Wait for health checks, not for time.
  3. Prepare data: apply migrations, then load the fixtures your tests expect.
  4. Run the tests against the real URLs.
  5. Collect logs if anything failed, then stop the stack even when the tests failed.

Plain Docker Compose can do all of this. docker compose up -d --wait blocks until services with a healthcheck are healthy, and a trap in your shell script makes sure docker compose down -v runs on the way out. If that is enough for your project, keep it. The rest of this article shows the same flow with Flisk, which helps when you have more than a couple of services or when some of them run as plain local processes.

The same flow with Flisk

Flisk's flisk up --wait starts the stack in the background and returns once every service is healthy (exit 0), or when a service fails or --wait-timeout passes (exit 1). The stack keeps running until you call flisk down. The timeout is in seconds, from 1 to 21600, and defaults to 1800.

#!/usr/bin/env bash
set -euo pipefail

cleanup() { flisk down || true; }
trap cleanup EXIT

flisk up --wait --wait-timeout 900

# Run a one-off command with the environment of the api service
flisk run orders-api -- bun run seed

# Where do the services answer?
flisk networks --raw

API_URL="http://api.my-shop.localhost/api/orders" bun test tests/integration

flisk run <service> -- <command> runs the command with the environment the service has inside the stack (a docker exec into its running container, or on the host for a local process). Its exit code is the command's, so a failing seed stops the script because of set -e. Put -- before any command that has flags of its own.

flisk networks --raw prints the gateway URLs, one per line. Treat the printed URLs as the source of truth instead of hard-coding them: if port 80 is taken, Flisk moves to another port and the URLs change.

Keep test config separate from development config

Tests often need different settings: another database name, a fake payment endpoint, a feature flag. Flisk can start the stack with another project env file for one run:

cp .env .env.integration
printf '\nFEATURE_FLAGS=beta\n' >> .env.integration
flisk up --env-file .env.integration --wait

Copy the project .env first. The selected file replaces .env for that run, it is not merged, and Flisk refuses a file that lacks TILT_ENV, DB_PASSWORD or JWT_SECRET. A stack that is already running keeps the env file it started with, so flisk up --env-file is refused until you run flisk down (or pass --force). Also note that changing DB_PASSWORD does not change an existing Postgres volume: the database keeps the password it was created with.

Clean data between runs

You have three options, from cheapest to most thorough:

  • Isolate inside the test. Create unique records per test (a random email, a new tenant) and never assert on counts of shared tables. This is the fastest and works against a long-running stack.
  • Reset with a command. Truncate and re-seed with flisk run before each suite.
  • Delete the volumes. flisk down --purge removes the project's Docker volumes, networks and images. It is the right reset for CI, and the wrong one on your laptop if you have data you care about.

Migrations belong in their own one-shot step so the test run does not depend on an API start script. See database migrations in local dev.

Pitfalls

  • Health is not readiness for your test. A service can answer /health before its migrations have run. Make the health endpoint check what the tests need, or order the work with dependsOn.
  • Port clashes. A stale stack from the last run holds the ports. Always stop in a trap. If it still happens, see fix port already in use.
  • Do not run this on every save. A real stack takes longer than a unit test. Run unit tests in the watch loop and the integration suite before you push and in CI.
  • Slow first run. The first flisk up builds images. Do not set a tight timeout for it.

Once the script works on your machine, move it into CI: run the stack in GitHub Actions shows the same steps in a workflow.

Questions people ask

How do I make the test run wait until every service is ready?

Do not sleep for a fixed time. Use a command that returns only when all health checks pass. With Flisk, flisk up --wait starts the stack in the background and exits 0 once every service is healthy, or exits 1 if one fails or --wait-timeout passes. With Compose, docker compose up --wait does the same for services that have a healthcheck.

How do I get a clean database for each test run?

Either create a throwaway database name per run, or stop the stack and delete its volumes. With Flisk, flisk down --purge deletes the project's Docker volumes, networks and images, so use it only when you want everything gone. For a lighter reset, run a truncate or seed command with flisk run.

Should integration tests run in the same process as the services?

Usually not. Run the services as they run in development, and let the test runner call them over HTTP. That keeps the test honest about ports, headers, serialization and startup order.
