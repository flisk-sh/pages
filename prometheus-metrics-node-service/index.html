Logs, traces and metrics locally

Expose Prometheus metrics from a Node.js service

A few lines give you process metrics and request timings in the format Prometheus reads.

Install prom-client, call collectDefaultMetrics(), add a histogram for request duration, and serve await register.metrics() on a GET /metrics route. That gives you process metrics (memory, CPU, event loop lag) and request timings in the plain text format Prometheus reads. You can check the result with curl before any Prometheus exists.

Metrics, logs and traces answer different questions

A log line tells you what happened once. A trace follows one request. A metric is a number that is cheap to keep and to graph over time: requests per second, the 95th percentile of latency, the size of a queue. You reach for metrics when the question is "is it getting slower" or "how often does this fail", rather than "what happened to request 42". Prometheus works by pulling: it requests /metrics from each service every few seconds and stores the numbers.

Add the endpoint

npm install prom-client
// metrics.js
const client = require("prom-client");

client.collectDefaultMetrics();   // process_*, nodejs_* metrics

const httpDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "Duration of HTTP requests in seconds",
  labelNames: ["method", "route", "status"],
  buckets: [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

function metricsMiddleware(req, res, next) {
  const end = httpDuration.startTimer();
  res.on("finish", () => {
    end({
      method: req.method,
      route: req.route ? req.route.path : "unmatched",
      status: res.statusCode,
    });
  });
  next();
}

async function metricsHandler(_req, res) {
  res.set("Content-Type", client.register.contentType);
  res.end(await client.register.metrics());
}

module.exports = { metricsMiddleware, metricsHandler };

Mount the middleware before your routes and the handler on its own path:

const { metricsMiddleware, metricsHandler } = require("./metrics");

app.use(metricsMiddleware);
app.get("/metrics", metricsHandler);

Note that register.metrics() returns a promise in current versions of prom-client, so the handler must await it. Forgetting that prints [object Promise] instead of metrics.

Read the output

curl -s http://localhost:4000/metrics | grep http_request_duration

You will see lines such as http_request_duration_seconds_bucket{le="0.1",method="GET",route="/orders/:id",status="200"} 12. A histogram exports one counter per bucket, plus _sum and _count. Prometheus turns those into percentiles at query time:

histogram_quantile(0.95, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))

For a count of things that only go up, such as failed payments, use a Counter. For a value that moves both ways, such as jobs waiting, use a Gauge.

Run it with Flisk

Nothing special is needed. The /metrics route is part of your app, and Flisk runs the app. Keep healthCheckPath on a cheap route such as /health, not on /metrics, so readiness does not depend on how long metric collection takes:

{
  "schemaVersion": 1,
  "appName": "orders",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

After flisk up, curl http://localhost:4000/metrics works from the host, and so does a Prometheus container that scrapes the host. Scraping local services with Prometheus shows that second half. Flisk itself does not collect or graph metrics, and it does not read your /metrics endpoint: it only starts, waits for and stops the processes.

If you run several services, give each metrics a consistent prefix or label for the service, and use the same histogram name everywhere. Then one dashboard works for all of them. The guide on running microservices locally covers the wider setup.

Pitfalls

  • High-cardinality labels. Every distinct label value creates a new time series. Using the raw URL (/orders/9171) or a user ID as a label can create millions. Use the route pattern, as above, and send per-user detail to logs or traces.
  • Unmatched routes. A scanner hitting random paths would create a series per path if you used req.path. The "unmatched" fallback prevents that.
  • Exposing /metrics publicly. It reveals internals. Locally that is fine; before you deploy, serve it on an internal port or behind the network boundary.
  • Cluster or worker mode. With the Node cluster module each worker has its own registry. Use prom-client's cluster support, or scrape each process.
  • Default histogram buckets. The defaults suit web requests, but if your calls take minutes, set your own buckets, otherwise every observation lands in the last one and percentiles are useless.

With the endpoint in place, the next step is a Prometheus that finds it. See scraping local services with Prometheus.

Once the endpoint works, make a habit of looking at it after each change. Hit a route a few times, read the raw text again, and confirm that the labels are the ones you intended and that the counts moved. Raw output is easy to read after a little practice, and it catches a wrong label or a missing observation long before a graph does. When the numbers look right, point Prometheus at the service and let it do the remembering.

Questions people ask

Why does /metrics print [object Promise]?

In current prom-client versions register.metrics() returns a promise, so the handler must await it.

What should I avoid as a label?

Raw URLs and user IDs. Every distinct value creates a new time series. Use the route pattern instead.

Does Flisk read my metrics endpoint?

No. Flisk starts and stops your process. Prometheus does the scraping.
