Local dev tools compared

concurrently vs mprocs vs process-compose for dev commands

Each fits a different size of problem, from two npm scripts to a dozen services with startup order.

Use concurrently when you have two or three npm scripts and want them in one terminal. Use mprocs when you want a terminal UI where you can switch between processes and restart one. Use process-compose when you need startup order, health checks and restart policies. Beyond that, you are describing a stack, and a stack tool fits better.

concurrently

concurrently is an npm package. It runs several shell commands at once, prefixes each output line with a name and color, and can stop everything when one process ends.

{
  "scripts": {
    "dev": "concurrently -n api,web -c blue,green \"npm:dev:api\" \"npm:dev:web\"",
    "dev:api": "node --watch api/server.js",
    "dev:web": "vite"
  }
}

It is the lowest-friction option in a JavaScript repo because it is one dev dependency. Related tools such as npm-run-all2 (run-p) cover similar ground. Limits: there is no notion of readiness, so if the web app needs the API to be listening first, you add a wait-on step yourself. Output is a single merged stream, which gets noisy with more than a few processes.

mprocs

mprocs is a single binary with a terminal UI. You list processes in an mprocs.yaml file or on the command line. The UI shows a list of processes on the left and the selected process's output on the right. You can start, stop and restart one process without touching the others. It is a good fit when you often need to look at one service's output at a time, or restart one process after a crash.

procs:
  api:
    shell: "node --watch api/server.js"
  web:
    shell: "npm run dev"

It is about viewing and controlling processes. It does not model dependencies between them.

process-compose

process-compose is a scheduler for non-container processes, with a Compose-like YAML file and a terminal UI. It adds the pieces the other two lack: depends_on with conditions, readiness and liveness probes, restart policies and per-process environment.

version: "0.5"
processes:
  api:
    command: node server.js
    readiness_probe:
      http_get:
        host: 127.0.0.1
        port: 4000
        path: /health
  web:
    command: npm run dev
    depends_on:
      api:
        condition: process_healthy

Check the project's docs for the exact field names in your version, since the schema has evolved. If you want Compose's mental model for host processes, this is the closest match.

Where Flisk fits

Flisk's local-process mode covers the same ground as process-compose. Each service has a service.json with a command, and flisk up starts the services in dependsOn order, waits for health, prefixes logs, restarts crashed processes with backoff and prints the http://localhost:<port> URLs. flisk logs --service api --tail 50 reads recent output and flisk up --only web starts one service and what it depends on.

The difference is the road ahead. If you later need Postgres, one gateway URL or container parity, you remove command and move to Flisk's Docker and Tilt path, or run a database image next to local processes. The honest limit: Flisk's own comparison notes that process-compose has a richer terminal UI and more process options today. If the live TUI is what you want, choose process-compose or mprocs. A project cannot mix local processes with services built from Dockerfiles yet.

See run local services without Docker for the full field list.

Pitfalls

  • Zombie processes. If a runner is killed hard, child processes can stay alive and hold ports. Check with lsof -i :PORT before blaming the next run.
  • Watch mode doubles up. A tool that restarts the runner when files change, plus a dev server that restarts itself, can fight. Let one layer own reloads.
  • Windows. Quoting and process-tree cleanup differ. Test your script on the platforms your team uses.

Questions people ask

What is the simplest way to run two npm scripts at once?

Add concurrently as a dev dependency and call it from a dev script with both commands. npm-run-all2 with run-p is a similar option.

Does concurrently wait for one service before starting another?

No. It starts every command at once. Use a wait-on step, or a tool with dependency conditions such as process-compose.

Is process-compose a Docker Compose replacement?

It uses a similar file shape but runs host processes, not containers. It is for processes that should not be containerized.
