MCP servers in production

How to add authentication to a remote MCP server

Protect an HTTP MCP server with bearer tokens or OAuth, return the right 401 response, and keep tokens out of logs and tool arguments.

Put the MCP endpoint behind an HTTP check that requires an Authorization: Bearer token, and return 401 with a WWW-Authenticate header when it is missing or invalid. For a server only you or your team use, a static token is enough. For a server other people connect to, use OAuth so each user gets their own revocable token.

Pick the simplest scheme that fits

There are three realistic options. Choose by who your users are, not by what sounds most secure.

  • Static API key: one secret per client, stored in an environment variable. Fine for internal servers and early testing.
  • Per-user API keys: you issue and store hashed keys. Good when you have an account system already.
  • OAuth: the client sends the user to a login page and gets a short-lived token. The MCP specification's authorization section is built on OAuth, so MCP clients that support it can run the flow for you.

Do not invent your own login flow. If you need user sign-in, use OAuth or a provider that supplies it.

Check the token on every request

MCP over HTTP is a normal HTTP endpoint. Authenticate before you parse the JSON-RPC body. Here is a minimal Node check:

import { timingSafeEqual } from "node:crypto";

export function checkAuth(req) {
  const header = req.headers["authorization"] ?? "";
  const token = header.startsWith("Bearer ") ? header.slice(7) : "";
  const expected = process.env.MCP_TOKEN ?? "";
  if (!token || token.length !== expected.length) return false;
  return timingSafeEqual(Buffer.from(token), Buffer.from(expected));
}

Use a constant-time comparison so response timing does not leak the token. Reject early, before any tool code runs.

Return a proper 401

A client can only start an OAuth flow if the server tells it where to go. Respond with status 401 and a WWW-Authenticate: Bearer header. The MCP authorization spec points clients at protected resource metadata, served from a /.well-known/ path, which names the authorization server. Check the current spec text for the exact fields, because this part has changed between protocol revisions.

Use 403 when the token is valid but lacks permission for the tool being called, so clients can tell the difference.

Scope tokens to what a tool needs

A token that can call every tool is a risk. Give each token a list of allowed tools or scopes and check it inside the tool handler, not only at the door. A read-only token must not be able to call delete_record, even if a model asks nicely.

Keep token lifetime short where you can, and support revocation. A leaked key you cannot revoke is an incident.

Keep secrets out of places they leak

  • Never log the Authorization header. Log a token ID or the last four characters.
  • Never accept secrets as tool arguments. Arguments end up in model context and in transcripts.
  • Store upstream credentials (for example a database password) on the server, never return them from a tool.
  • Serve over HTTPS only. A bearer token over plain HTTP is a password in the clear.

More on this in the MCP security checklist, and on environment handling in env and secrets for local development.

Questions people ask

Do I need OAuth for an MCP server?

Not for a private or internal server, where a bearer token is enough. Use OAuth when many different users connect and each needs their own revocable access.

Can stdio MCP servers use bearer tokens?

No, a stdio server runs as a child process of the client, so access is controlled by who can start it. Pass any needed credentials through environment variables.
