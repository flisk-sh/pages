Testing and evaluating AI agents

Mocking the LLM and tool calls in agent unit tests

Test the code around your agent without calling a model: scripted responses, fake tools, recorded replies and a clear line between unit tests and evals.

Put the model behind a small interface, then in unit tests replace it with a fake that returns scripted replies. Do the same for tools. This tests your loop, parsing, retries and error handling in milliseconds, with no API key. Real-model checks belong in a separate eval suite.

Separate unit tests from evals

A unit test checks your code: does the loop stop, does it parse a tool call, does it handle a failed tool? It must be fast and deterministic. An eval checks the model's behaviour on your task and can be noisy. Mixing them gives slow tests that fail for reasons your code did not cause.

Hide the model behind an interface

Give your agent a single function or class for model calls. Then you can swap it.

class ScriptedModel:
    def __init__(self, replies): self.replies = list(replies)
    def complete(self, messages, tools):
        return self.replies.pop(0)

def test_agent_calls_tool_then_answers():
    model = ScriptedModel([
        {"tool_call": {"name": "find_order", "args": {"id": "4821"}}},
        {"text": "Order 4821 shipped yesterday."},
    ])
    tools = {"find_order": lambda id: {"status": "shipped"}}
    out = Agent(model, tools).run("Where is order 4821?")
    assert "shipped" in out

Test the failure paths

These are the cases real models trigger and happy-path tests miss. Script them on purpose.

  • The model returns malformed JSON for a tool call.
  • It asks for a tool that does not exist.
  • A tool raises an error or times out.
  • The model never stops calling tools, so the step limit must trigger.
def test_stops_after_step_limit():
    model = ScriptedModel([{"tool_call": {"name": "search", "args": {}}}] * 50)
    out = Agent(model, {"search": lambda: []}, max_steps=5).run("loop")
    assert out.stopped_reason == "max_steps"

Record and replay carefully

You can record real model replies once and replay them in tests. This is quick to set up, but recorded replies go stale when you change the prompt or tools, and the test then proves nothing. Re-record when prompts change, and keep a few hand-written scripts for the failure cases above.

What mocks cannot tell you

A scripted model proves that your loop handles the replies you imagined. It cannot prove that a real model produces them. Keep a handful of end-to-end checks with the real model, run less often, and label them clearly as evals. When one fails, copy the failing reply into a scripted test so the code path is covered forever, even if the model changes.

Run the whole stack locally

For integration tests with real services but no real model, start a local stack with a database and your tool servers. The Flisk CLI is built for that: flisk resource <name> --type agent adds an agent service, flisk up starts the stack and flisk status --json shows what is running. See the Flisk docs and AI agents local. Pair this with trajectory assertions for checks on the tool path.

Questions people ask

Is it worth mocking if I also run evals?

Yes. Unit tests are fast and cheap, and they find bugs in your own code. Evals find problems in the model's behaviour. You need both.

Can I use a small local model instead of a mock?

For integration checks, yes, but its output varies. Use a scripted mock for unit tests where you need exact control.
