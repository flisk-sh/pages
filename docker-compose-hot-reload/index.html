Docker Compose hot reload: bind mounts, watch and alternatives

Reloading code in a container is easy to get almost right. Here is what each approach does, what breaks, and where Flisk has no live reload.

With Docker Compose, mount your source into the container and run a watcher inside it, or use docker compose watch to sync files on change. With Flisk, services it generates get live sync through Tilt. Services you imported or brought yourself get no live reload, so for those you rebuild or use the runtime's own watcher.

Option 1: bind mount and an in-container watcher

This is the oldest approach and still the most common. You mount the project folder into the container and run a tool that restarts the process when files change, such as nodemon, node --watch, uvicorn --reload or air for Go.

services:
  api:
    build: ./api
    command: node --watch server.js
    volumes:
      - ./api:/app
      - /app/node_modules
    ports:
      - "4000:4000"

The second volume, /app/node_modules, stops the bind mount from hiding the dependencies installed in the image. Without it you often get "module not found" on the first start.

Known problems: on macOS and Windows, file change events cross a virtual machine boundary and can be slow or missing, so some watchers need polling mode (for example CHOKIDAR_USEPOLLING=true for chokidar-based tools). Bind mounts can also be slow for projects with huge dependency folders.

Option 2: docker compose watch

Recent Compose 2 versions add a develop.watch section. Compose watches paths on the host and applies an action for each change: sync copies the file into the container, rebuild rebuilds the image, and sync+restart copies and restarts the service.

services:
  web:
    build: ./web
    develop:
      watch:
        - action: sync
          path: ./web/src
          target: /app/src
        - action: rebuild
          path: ./web/package.json

Start it with docker compose up --watch or docker compose watch. It avoids the bind mount, which helps on macOS, and it handles the "dependencies changed, rebuild" case that a bind mount cannot. It still needs a watcher or a framework dev server inside the container if the process must reload code.

How Flisk handles it

For services that Flisk generates, Tilt live_update syncs directories into the running container. The directories come from the syncs field in service.json. When you leave it out, backends sync src and prisma, and frontends sync src and public. You edit a file and Tilt copies it, without rebuilding the image for each change.

Reload behaviour depends on the language:

  • Bun backends, workers, agents and MCP servers reload by default under bun --watch or --hot. Set dev.liveReload to false to turn that off.
  • Go services opt in with dev.liveReload: true, which compiles and reloads in the container through flisk-go-watch.
  • Python services can opt in to dev.testOnSave, which runs pytest when you save.
{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "billing",
  "appType": "backend",
  "dev": { "liveReload": true }
}

Treat the snippet as the shape of the dev block, not a complete Go service. Scaffold real services with flisk resource <name> --type backend and edit the generated service.json.

What does not reload

  • Bring-your-own containers, including everything created by flisk import. Flisk watches the manifest only. After a code change, rebuild from the Tilt UI or restart flisk up.
  • Local processes. A service with a command runs without Docker, so there is no sync step: the process reads your files directly. Use the runtime's own watcher in the command, such as node --watch server.js, bun --watch server.ts or uvicorn app:app --reload.

If you only have bring-your-own services but still want live reload, the honest answer is to keep a develop.watch block in your own Compose file or to run that service as a local process.

Choosing between them

If you already have a working Compose file and the code is in one or two services, compose watch is usually the least change. If the whole stack is generated by Flisk, the Tilt sync is already on and you only choose the reload behaviour per language. If you want zero container overhead for the code you edit all day, run that one service as a local process and keep the database in a container. Flisk supports that mix when the container is a database image declared as bring-your-own, as long as the project does not also contain services built from a Dockerfile.

Pitfalls

  • A new dependency needs a rebuild, not a sync. Changing a lockfile or package.json should trigger a rebuild.
  • Syncing generated or ignored folders (dist, .next) can loop. Sync source, not output.
  • If saves do nothing, check that the file is inside a synced directory first. The troubleshooting article on hot reload not working goes through the checks in order.

For a frontend and an API that must both reload, see hot reload across services. If your services are plain processes, running without Docker is the simplest way to get instant reload.

Questions people ask

Does docker compose watch replace bind mounts?

It can. It syncs, rebuilds or restarts on file changes without a bind mount. Your process still needs a watcher or dev server to pick up changed code.

Does Flisk reload imported Compose services?

No. Services created with flisk import are bring-your-own containers. Flisk watches the manifest only, so rebuild from the Tilt UI or restart flisk up.

How do I get live reload without Docker?

Run the service as a local process and use the runtime's watcher in its command, for example node --watch, bun --watch or uvicorn --reload.
