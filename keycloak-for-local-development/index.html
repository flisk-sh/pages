Authentication in local development

How to run Keycloak for local development with a realm import

A real identity provider on your laptop, seeded the same way every time, so nobody clicks through the admin console to get a test user.

Run the official image with the start-dev command, give it an admin user through environment variables, and mount a realm JSON file so Keycloak imports a client and test users on first start. The provider then lives at http://localhost:8080, and your API trusts the issuer http://localhost:8080/realms/dev.

The plain Docker way

This is the whole recipe without any other tool. It uses Keycloak 26, where the bootstrap admin variables are KC_BOOTSTRAP_ADMIN_USERNAME and KC_BOOTSTRAP_ADMIN_PASSWORD (older versions use KEYCLOAK_ADMIN and KEYCLOAK_ADMIN_PASSWORD):

docker run --rm -p 127.0.0.1:8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  -v "$PWD/import:/opt/keycloak/data/import" \
  quay.io/keycloak/keycloak:26.0.7 start-dev --import-realm

start-dev turns on development defaults: HTTP is allowed, strict host name checks are off and it uses an embedded database kept under /opt/keycloak/data. It is not for production. --import-realm reads every JSON file in /opt/keycloak/data/import at startup and creates those realms. It skips a realm that already exists, so editing the file later does nothing until you delete the stored data. The first start takes a while; wait for the log to say that Keycloak is listening.

A realm file with a client and a user

Save this as import/dev-realm.json. It creates a realm called dev, a public client for a browser app that uses the authorization code flow with PKCE, and one user:

{
  "realm": "dev",
  "enabled": true,
  "clients": [
    {
      "clientId": "web",
      "publicClient": true,
      "standardFlowEnabled": true,
      "redirectUris": ["http://localhost:3000/*"],
      "webOrigins": ["http://localhost:3000"],
      "attributes": { "pkce.code.challenge.method": "S256" }
    }
  ],
  "users": [
    {
      "username": "alice",
      "enabled": true,
      "email": "alice@example.test",
      "emailVerified": true,
      "credentials": [{ "type": "password", "value": "alice", "temporary": false }]
    }
  ]
}

Open http://localhost:8080/realms/dev/.well-known/openid-configuration to see the discovery document. The issuer in it is http://localhost:8080/realms/dev; any OIDC library takes that single URL and finds the rest. The admin console is at http://localhost:8080/admin. If you set up users by hand in the console and want them in the file, export the realm from the console or use Keycloak's export command, and trim it.

Run it with Flisk

Flisk can start the container next to your own code. Give Keycloak a service.json with an image and no command, and every other service a command. flisk up then starts the local processes, and the image with docker run, in dependsOn order. Docker must be running for the image; your own services need nothing but their runtime. The container's port is published on 127.0.0.1 at the same number.

{
  "schemaVersion": 1,
  "appName": "keycloak",
  "appType": "bring-your-own",
  "stack": "auth",
  "image": "quay.io/keycloak/keycloak:26.0.7",
  "port": 8080,
  "env": {
    "KC_BOOTSTRAP_ADMIN_USERNAME": "admin",
    "KC_BOOTSTRAP_ADMIN_PASSWORD": "${KEYCLOAK_ADMIN_PASSWORD:-admin}"
  },
  "container": { "command": ["start-dev", "--import-realm"] },
  "volumes": [
    { "source": "./import", "target": "/opt/keycloak/data/import" },
    { "source": "keycloak", "target": "/opt/keycloak/data", "name": "auth_keycloak" }
  ]
}

A ./ source is a bind mount inside the project, and a named volume keeps Keycloak's data across restarts; Flisk keeps named volumes on flisk down. container.command is the argument list of the container's process, which is what Docker calls the command. Then the API depends on it and reads the issuer from env:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "stack": "auth",
  "command": "node server.js",
  "port": 4000,
  "dependsOn": ["keycloak"],
  "env": { "OIDC_ISSUER": "http://localhost:8080/realms/dev" }
}

Run flisk config verify to check both files, and flisk up --dry-run to see the start order before anything starts. flisk logs --service keycloak shows the container's output. Without a health check Flisk treats the container as ready when its port accepts connections, which Docker does before Keycloak has finished booting, so make your API retry its first discovery request instead of failing at startup. To start fresh, run flisk down and remove the auth_keycloak volume with docker volume rm.

Pitfalls

  • Issuer mismatch. The iss claim holds the URL the browser used. If your API runs in a container and reaches Keycloak at http://keycloak:8080, it will see tokens whose issuer says localhost and reject them. Keep one name for both: run the API as a local process, or set Keycloak's hostname option to the browser-visible URL.
  • Redirect URI patterns. The wildcard in http://localhost:3000/* is fine for a laptop. List exact URIs in any shared environment. A mismatch shows Keycloak's "Invalid parameter: redirect_uri" page; the redirect URI article shows how to compare.
  • Re-import does nothing. Remove the data volume to re-run an import.
  • Weak passwords are for local only. Do not commit a realm file with real users, and never point a production app at it.

When you only need a fake provider for automated tests, Keycloak is heavier than necessary. The next article shows a mock OIDC server.

Questions people ask

How do I create a test user in Keycloak automatically?

Put the user in a realm JSON file under /opt/keycloak/data/import and start with --import-realm. Keycloak creates it on first start.

What is the Keycloak issuer URL for local development?

http://localhost:8080/realms/<realm>, for example http://localhost:8080/realms/dev. The discovery document is at /.well-known/openid-configuration under it.

Why does Keycloak ignore my changed realm file?

Import skips a realm that already exists. Delete the stored data volume and start again.
