Email and notifications in local dev

How to test SMS notifications locally without sending texts

Every real text costs money and can reach a real phone. Put the provider behind a small interface and give development a fake that you can read.

To test SMS locally, hide the provider behind a small send(to, body) interface and use a fake implementation in development that stores each message where you and your tests can read it. Nothing is sent, nothing is billed, and a verification code is one HTTP call away. Test the real provider separately, with its test credentials, in a few targeted checks.

Why you cannot just point at a catcher

Email has a standard protocol, so one catcher works for every library. SMS does not. Each provider has its own HTTP API, and there is no common local server that speaks all of them. Some providers publish test credentials that accept requests without sending a message, and a few tools emulate a particular API, but you cannot count on either. The dependable approach is to own the seam in your code.

Step 1: a sender interface

export interface SmsSender {
  send(to: string, body: string): Promise<void>;
}

class TwilioSender implements SmsSender {
  constructor(private client: any, private from: string) {}
  async send(to: string, body: string) {
    await this.client.messages.create({ to, from: this.from, body });
  }
}

class FakeSender implements SmsSender {
  async send(to: string, body: string) {
    await fetch(`${process.env.FAKE_SMS_URL}/messages`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ to, body, at: new Date().toISOString() }),
    });
  }
}

export const sms: SmsSender =
  process.env.SMS_MODE === "fake" ? new FakeSender() : new TwilioSender(realClient(), process.env.SMS_FROM ?? "");

The rest of the app imports sms and never mentions a provider. Switching provider later means one new class. Default SMS_MODE to fake in your example env file, so a fresh checkout cannot text anyone.

Step 2: a fake SMS service you can read

The fake needs two routes: POST /messages to record a message and GET /messages to list them, optionally filtered by number. An in-memory array is enough. Add a tiny page or just use curl:

curl "$FAKE_SMS_URL/messages?to=%2B15555550100"

A test then does the same thing the email tests do: trigger the login, poll the fake for a message to that number, read the six-digit code with a regular expression and submit it. Use fictional numbers; in North America the range 555-0100 to 555-0199 is reserved for fiction.

With Flisk

The fake is an ordinary backend resource:

flisk resource fake-sms --type backend --stack main --yes

Implement the two routes in the generated service. In the service that sends texts, add "dependsOn": ["fake-sms"] and set SMS_MODE to fake and FAKE_SMS_URL to the fake's address in its env block. Containers in a stack reach each other by resource name; run flisk resources --ports to see the port Flisk assigned (backends use the 4000 range), then use http://fake-sms:<port>. For a quick look from your host, flisk networks prints the routed URL of backend services. A non-secret setting like this belongs in the manifest; a real provider's credentials do not. Keep those in the project .env, git-ignored, and out of dev entirely unless you are running the provider checks. The general pattern is the one in mock or run the real service: run a fake that behaves like the thing, not a mock buried inside each test.

Step 3: check the real provider, separately

A fake cannot tell you that your provider rejects a number format, or that your message exceeds the length limit and is split into several segments. Cover those with a small number of tests against the provider's test credentials or sandbox, where one is offered. Read the provider's current documentation for what its test mode does, since behaviour and magic values differ and change. Run those tests on demand or in CI on a schedule, not on every save.

Pitfalls

  • Real numbers in a dev database. A real send costs money and can break consent rules. The same scrubbing rules as email apply: see stop your dev environment from emailing real users.
  • Format differences. Store numbers in E.164 form (+15555550100) and validate in one place; most provider errors in practice are number formatting.
  • One-time codes in logs. Printing codes to logs is handy in dev and a leak in production. Gate it on SMS_MODE=fake.
  • When this is too much. If your only SMS feature is one verification step, a code printed to the console in fake mode may be enough.

Questions people ask

Is there a local server for Twilio?

There is no standard one. Some providers offer test credentials and a few community tools emulate parts of an API, so the dependable way is a sender interface with a fake implementation in development.

How do I get the verification code in a test?

Have the fake SMS service record each message, then read the latest one for that number over HTTP in the test and extract the code with a regular expression.

Can I use real phone numbers in development?

Avoid it. Real texts cost money and can reach people who did not agree to them. Use fictional numbers and a fake sender.
