Email and notifications in local dev

How to preview HTML email templates before you send them

Browsers are forgiving and email clients are not. A local loop of render, send, look catches most layout bugs before a real inbox does.

To preview an HTML email before sending it to anyone, render the template to a file, open it in a browser for a first look, then send it to a local inbox such as Mailpit and view it there with the plain text tab and the HTML source. That loop takes seconds and catches broken links, missing text parts and most layout problems. Final checks across real clients still need a testing service or a few real accounts.

Why email HTML is different

An email client is not a web browser. Many clients strip <style> blocks or ignore parts of them, some ignore flexbox and grid, and desktop Outlook renders with the engine of a word processor. The practical rules have been stable for years:

  • Build the layout with nested tables, not flexbox or grid.
  • Put CSS inline on the elements, usually with a build step that inlines it for you.
  • Use absolute URLs for images and links. A relative path points nowhere in someone's inbox.
  • Give every image an alt attribute and a fixed width, since many clients block images by default.
  • Always include a plain text part. Spam filters score a message with no text version worse.

You rarely write that markup by hand. Tools such as MJML (which compiles a small tag language to table-based HTML) and React Email (components rendered to HTML) exist to generate it. Both can produce a file you can open locally, so the preview loop works with either.

Step 1: render to a file and open it

With MJML, compile and open the result:

npx mjml welcome.mjml -o welcome.html
open welcome.html

This shows structure and styling in a browser. It tells you nothing about how a mail client treats it, so treat it as the cheapest, fastest check, not the last one. Many of these tools also have a watch mode or a preview server that rebuilds when you save, which is worth using while you design.

Step 2: send it to a local inbox

Use the same code path your app uses to send real mail, aimed at a catcher (see the Mailpit setup). In the inbox, check these tabs for each template:

  1. HTML. Does it look right, including with images off in your browser?
  2. Text. Is the plain text version present and readable, not a dump of tags?
  3. Source. Are the headers correct: From, Reply-To, Subject, and a sensible Message-ID?
  4. Links. Does every button point to the right host? Mailpit has a link check feature that requests each URL and reports the ones that fail, which finds typos and links that still point at localhost in places where they should not.

Mailpit also has an HTML check that compares the markup and CSS you use against what common clients support and lists the problem spots. Treat it as a guide, not as proof.

Step 3: preview with realistic data

A template with "Hello Ada" looks fine. The real world has names like "Maximilian Alexander von Hohenzollern-Sigmaringen", amounts in other currencies, right-to-left text and a subject line with an emoji. Keep a few fixtures and send each one through the template:

  • a very long name and a very short one,
  • an empty optional field (does it leave a blank line or a stray comma?),
  • a long product list that wraps across several rows,
  • a non-Latin name.

With Flisk

Flisk does not render or preview email, and I would not pretend it does. What it gives you is the surrounding stack: the app that renders the template, the database that supplies the data, and a Mailpit resource that catches the result, all started with one flisk up. A handy pattern is a small route or script in your API that sends one sample of every template to a fixed address. Run it inside the stack's environment with flisk run api -- <your command>, then open the inbox at http://127.0.0.1:8025. If you change a template with a file watcher in a container, see why hot reload sometimes does not trigger.

What to check on real clients

A local inbox cannot tell you how Outlook, Gmail's clipping rules or dark mode treat your message. Before a launch, send the final templates through a testing service or to real test accounts at the clients your users have. Use your real email provider on a staging domain for this, never your production list.

Next step

Once templates look right, add a test that sends each one and fails on broken links: assert emails in end-to-end tests.

Questions people ask

Can I preview an email just by opening the HTML in a browser?

For a first look yes, but browsers support CSS that many email clients ignore. Send it to a local inbox and check on real clients before launch.

Why must email CSS be inline?

Several email clients remove or limit style blocks in the head. Inline styles on each element are the most widely supported, and build tools can inline them for you.

Does Mailpit check email client compatibility?

It has an HTML check that flags markup and CSS with weak client support, and a link check. It is a useful guide but does not replace testing on real clients.
