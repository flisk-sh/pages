How to Write an AGENTS.md That Coding Agents Follow

A short AGENTS.md with exact commands, boundaries and traps beats a long essay. Here is what to put in, what to leave out and how to keep it true.

An AGENTS.md is a plain Markdown file in the repo root that tells a coding agent how to build, test and change your project. Keep it short, put exact commands first, and list the traps that a newcomer would hit on day one.

Start with commands, not philosophy

An agent wastes the most time guessing how to run things. Open the file with the commands you actually use, copied from your terminal, not from memory.

## Commands
- Install: npm ci
- Typecheck: npm run typecheck
- Lint: npm run lint
- Unit tests: npm test
- One file: npm test -- path/to/file.test.ts

Add the one-file command. Agents run tests many times per task, and running the whole suite each time is slow and noisy.

Add a map of the repository

Five to ten lines is enough: which folder holds what, and which folder the agent should not touch. A map lets the agent open the right file first instead of searching the whole tree.

  • src/api/: HTTP handlers, one file per route.
  • src/jobs/: background workers.
  • migrations/: add new files only, never edit old ones.
  • dist/: generated, do not edit by hand.

List the traps and the hard rules

This is the part that earns the file its keep. Write down what has burned you before: a generated file that must be rebuilt, a test that needs a running database, a lint rule that fails CI but not your editor.

  • Say what must never happen: no secrets in commits, no edits to generated files, no skipped tests to get green.
  • Say what must always happen: run typecheck and tests before declaring a task done.
  • Keep each rule to one line. A rule you need a paragraph to explain is usually a missing lint check.

Keep it small and keep it true

Long instruction files get skimmed by humans and diluted for models. If a section only matters in one folder, put a second AGENTS.md in that folder. Many agents read the closest file to the code they are editing, but check your tool's docs before relying on it.

A stale file is worse than none, because the agent trusts it. Treat it like code: change it in the same pull request that changes the command. See AGENTS.md vs CLAUDE.md for how it fits with tool-specific files.

Test the file with a cold start

Open a fresh agent session with no history and give it a small task: add a log line, fix a typo, add a test. Watch where it stumbles. Each stumble is a missing line in the file. Two or three rounds of this teaches you more than any template.

Mistakes that make the file worse

Four mistakes show up again and again. First, copying a generic template full of advice such as "write clean code". The agent already knows that, and the noise hides your real rules. Second, describing the project's history instead of its current state. Third, listing commands you have never run in a clean checkout, so they fail on the first try. Fourth, writing rules in the negative only. "Do not edit dist" is useful, but add the positive version too: "run npm run build to regenerate dist".

Also avoid duplicating what the code already says. If your lint config enforces single quotes, do not repeat it in the file; the agent will find out the moment it runs lint. Spend the words on things a tool cannot tell it, such as why a folder is off limits, which service must be running for the integration tests, or which of two similar modules is the one to extend. When in doubt, ask whether a new teammate would need the line on their first day. If not, cut it.

Questions people ask

How long should an AGENTS.md be?

Aim for a page or less. Commands, a short repo map and a list of hard rules cover most of the value; move the rest into docs and link to them.

Should the file be written by an AI?

An agent can draft it, but you must check every command by running it. A generated file with a wrong command does real damage.

Try it

Give your agent a repo it can run on the first try.

Flisk is an open-source CLI that starts a project's services, databases and queues locally from one service.json per service, so an agent gets one command to bring the stack up.
