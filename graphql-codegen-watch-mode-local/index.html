GraphQL Codegen in watch mode: typed queries while you code

Typed queries only help while they match the schema. Watch mode regenerates them on every save, so TypeScript flags a bad field before the browser does.

GraphQL Code Generator reads your schema and your query documents and writes TypeScript types for them. Run graphql-codegen --watch in a terminal next to your dev server, point schema at a file or the running endpoint, and the generated types update when your .graphql or .ts documents change. The trick is deciding where the schema comes from and making sure the generator starts after the thing that produces it.

Install and configure

npm install --save-dev @graphql-codegen/cli @graphql-codegen/client-preset

Create codegen.ts in the frontend folder:

import type { CodegenConfig } from '@graphql-codegen/cli'

const config: CodegenConfig = {
  schema: 'http://localhost:4000/graphql',
  documents: ['src/**/*.{ts,tsx,graphql}'],
  generates: {
    './src/gql/': { preset: 'client' },
  },
}
export default config

The client preset generates a typed graphql() function: write the query in a template string, and the result type is inferred. Run once with npx graphql-codegen, or continuously with npx graphql-codegen --watch. Add both as scripts so teammates do not need to remember them.

Where the schema comes from

You have three options, with different trade-offs:

  • The running endpoint (URL). Always current, but the server must be up when codegen starts, and the schema is fetched once at start, so after a schema change re-run the command. Introspection must be enabled.
  • A schema file in the repo (schema.graphql or a glob). Works offline and with the server off, and watch mode sees edits to it. The server has to write or share that file, which some code-first libraries can do on startup.
  • The server's code. Code-first setups such as Pothos or Nexus can print the schema to a file; make codegen read that file.

For a single repo, a committed schema.graphql is the most reliable. It also shows schema changes in pull request diffs, which is the point of having a contract. The article on keeping a frontend and backend contract in sync covers that side.

Run it next to the dev server with Flisk

Treat the generator as one more long-running service. With Flisk, local processes are declared with a command; a process with no port counts as ready when it is still running after a second. The generator depends on the API so the schema URL exists:

{
  "schemaVersion": 1,
  "appName": "codegen",
  "appType": "backend",
  "command": "npx graphql-codegen --watch",
  "dependsOn": ["graphql-api"]
}

Install Flisk with npm install -g @flisk-sh/flisk, then flisk up starts the API, waits for it to be ready (give it a port in its own service.json), then starts codegen and the frontend in order. Check the order first with flisk up --dry-run. The output of each service is prefixed with its name, so a schema error from codegen is easy to tell apart from a Vite error; flisk logs --service codegen shows only it.

If you run codegen once instead of watching (for example npx graphql-codegen, which exits), set "restart": "no" in that service. Without it Flisk treats an exit as a crash and starts the command again, with growing delays.

There is no GraphQL-specific generator in Flisk, so keep codegen as shown here.

Using the generated types

With the client preset, import the generated graphql function and write the document in place:

import { graphql } from './gql'

const ProductsQuery = graphql(`
  query Products { products { id name priceCents } }
`)

Pass ProductsQuery to your client (Apollo Client, urql or graphql-request) and the result is typed. Rename priceCents on the server, let codegen run, and TypeScript marks every component that still reads the old field. That feedback loop, within a second or two of saving, is the reason to run it in watch mode instead of once in CI.

Pitfalls

  • Introspection disabled. A URL schema fails with an error about introspection. Enable it in development, or switch to a schema file.
  • Stale types after a schema change. With a URL schema, restart codegen. With a file schema, watch mode picks it up.
  • Documents not found. "Unable to find any GraphQL type definitions" or an empty output usually means the documents glob matches no files. Run from the folder that holds codegen.ts.
  • Generated folder committed or not. Decide, and add it to .gitignore or keep it. Do not hand-edit it.
  • Editor lag. Large schemas make watch mode slow; limit documents to the folders you use.

With types in place, a browser still needs permission to call the API: see CORS and CSRF errors with GraphQL.

Questions people ask

How do I run GraphQL Code Generator in watch mode?

Run graphql-codegen --watch (or add --watch to your codegen script). It regenerates when files matched by documents, and local schema files, change.

Should codegen read the schema from a URL or a file?

A committed schema file is the most reliable and shows changes in diffs. A URL is convenient but needs the server running and introspection on.

Why does codegen keep restarting under a process runner?

A command that runs once and exits looks like a crash to a runner that restarts exited processes. Use watch mode, or turn restart off for that service.
