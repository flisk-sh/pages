How to write a smoke test that runs after every deploy

A green deploy only means the container started. A smoke test asks whether the app does its one job.

A smoke test is a small script that runs right after a deploy and fails loudly if the app is not working. Make it call the health endpoint, one real read path that touches the database, and one page or API route users depend on, with retries for the start-up window and a non-zero exit code on failure. Five requests and a few lines of shell are enough to catch most bad releases.

What a smoke test is for

Hosts report a deploy as healthy when the process starts and the health check passes. That tells you very little. A missing environment variable can leave /health green while every login fails. A smoke test checks the paths a user would take, shallowly and quickly. It is not a full test suite. Keep it under a minute, make it safe to run against production (read-only requests, or a clearly marked test account), and make it the same script everywhere.

Make the health endpoint honest first

There are two useful endpoints. A liveness check answers "is the process up" and should not touch dependencies. A readiness check answers "can it serve requests now", and may check the database with a cheap query. Use the readiness style for the post-deploy check, and keep it fast and free of side effects. For the pattern in an agent service, see health vs readiness endpoints.

A script you can start with

#!/usr/bin/env bash
set -euo pipefail
BASE_URL="${1:?usage: smoke.sh https://app.example.com}"

check() {
  local name="$1" path="$2"
  curl --fail --silent --show-error --max-time 10 \
       --retry 10 --retry-delay 3 --retry-connrefused \
       "$BASE_URL$path" > /dev/null
  echo "ok   $name"
}

check "health"       /health
check "home page"    /
check "products api" /api/products?limit=1   # reads from the database
echo "smoke test passed"
  • --fail turns HTTP 4xx and 5xx into a non-zero exit code, which is what CI and deploy hooks read.
  • --retry with --retry-connrefused covers the seconds between a new instance starting and its port opening. Retries are for start-up. If the check keeps failing after 30 seconds, it is a real failure.
  • --max-time stops a hung request from hanging the pipeline.
  • set -euo pipefail makes the script stop on the first error.

Add checks for what your app is about: log in with a test user, create and delete one record, or load a page that renders data. Check the content too, not only the status code, for example with grep -q on a known string, because an error page can return 200.

Run the same script locally and in the pipeline

The value of a smoke test grows when you can run it against your laptop first. With Flisk, a service that sets healthCheckPath in service.json is waited on at that path before dependent services start, and flisk up prints the URL it found. Run the script against the printed address and fix the script on your laptop before it guards production:

bash smoke.sh http://localhost:4000

flisk doctor also pings the /health endpoint of running services, which is a quick sanity check, but it is a check of your local stack, not of production. The host gets the same health path from the exported config. flisk export render writes healthCheckPath (or /health when you did not set one) into the Blueprint, so make sure the production app really answers there. How to wire this into a pipeline is covered in waiting for services to be healthy in CI.

Where to run it

  1. In CI after the deploy step when your pipeline triggers the deploy. Fail the job so the team sees it.
  2. As a deploy hook on platforms that support a post-deploy command. Check your host's documentation for the name.
  3. On a schedule, every few minutes, as a cheap uptime check. This becomes monitoring, which is a separate topic.

Pitfalls

  • Testing the old version. During a rolling deploy, a request may hit the previous instance. Include a version in the health response, such as a commit SHA, and have the script wait until it matches the one you deployed.
  • Side effects on production. Sending real emails or charging a card from a smoke test is a bug. Use read-only calls or test mode.
  • Flaky checks. A test that fails randomly gets ignored. Retry only the start-up window and fix or delete the rest.
  • Secrets in the script. Pass tokens from the CI secret store, not the file.

When the smoke test fails, you need a fast way back. That is the subject of how to roll back a bad deploy.

Questions people ask

What is the difference between a smoke test and an end-to-end test?

A smoke test is a few shallow checks that prove the deploy is alive. An end-to-end test walks through full user flows and is slower and broader. Run smoke tests after every deploy and the larger suite before it.

Should a smoke test run against production?

Yes, with read-only requests or a dedicated test account. The point is to check the live environment, so avoid actions with real side effects.

How long should a smoke test take?

Under a minute. If it needs more, it is turning into a full test suite and will get skipped.
