How to secure an MCP server and the tools it exposes

An MCP server hands a model real capabilities. Authenticate callers, scope every tool, treat tool text as untrusted and review third-party servers before you connect them.

Secure an MCP server by authenticating every caller, giving each tool the narrowest permissions, validating all arguments in code, and treating anything the server returns as untrusted input to the model. When you connect a server you did not write, read its tools first.

Authenticate and authorize

A local server over stdio runs as your user and trusts its parent process. A server over HTTP is reachable by whoever can reach the URL, so it needs authentication. Require a token or use the authorization flow your MCP client supports, and check it on every request. Then authorize per tool: a valid caller is not automatically allowed to call every tool. The guide on MCP servers in production goes deeper on auth and transports.

Scope each tool

Apply the same rules as for any agent tool. A tool named query that takes raw SQL is a risk. A tool named get_invoice with an id is not. Use scoped database roles and check ownership: the invoice must belong to the caller's account, not just exist. See least-privilege tool permissions.

Validate arguments

The model fills in arguments, and it may be manipulated. Validate them like web request input.

from pydantic import BaseModel, Field

class GetInvoice(BaseModel):
    invoice_id: str = Field(pattern=r"^inv_[0-9]{6}$")

def get_invoice(args: dict, caller):
    a = GetInvoice(**args)
    inv = db.find_invoice(a.invoice_id)
    if inv is None or inv.account_id != caller.account_id:
        return {"error": "not found"}
    return inv.public_fields()

Note that a missing invoice and someone else's invoice give the same answer, so the tool does not reveal what exists.

Tool text is a prompt channel

Tool names, descriptions and results all go into the model's context. A malicious or compromised server can hide instructions in a description, or change a description after you approved it. Practical steps:

  • Read the tool descriptions of any third-party server before connecting it.
  • Pin the version you reviewed and re-review on updates.
  • Keep third-party servers away from agents that hold private data and can send data out.
  • Return only the fields the model needs, not whole records.

Log and limit

Rate-limit by caller and by tool, set timeouts, and cap the size of results. Log each call with caller, tool, arguments and outcome, as covered in the audit log guide. If you are building a server from scratch, the guide build an MCP server shows the basics before you add these controls.

Plan for the day a token leaks. Keep tokens short-lived or revocable per client, record which client made each call, and make rotation a routine you have tried. A server with one shared static token for every user cannot tell a legitimate caller from an attacker, and you cannot revoke one without breaking all.

Questions people ask

Is a local stdio MCP server safe without authentication?

It trusts the process that launched it, so the main risk is what that user can do. Still scope tools and validate arguments.

How do I vet a third-party MCP server?

Read its source or at least its tool list and descriptions, pin a version, run it with minimal permissions, and keep it away from sensitive data.
