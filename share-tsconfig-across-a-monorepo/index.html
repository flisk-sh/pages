How to share one tsconfig across a monorepo

Ten copies of a tsconfig drift apart within a month. A base file and a few small per-package files keep strictness and module settings aligned.

Put shared compiler options in tsconfig.base.json at the repo root, and have every package's tsconfig.json extends it and add only what is different. For packages that import each other, add project references so tsc --build compiles them in dependency order.

A base config and thin per-package files

The root file holds what every package agrees on:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "declaration": true,
    "sourceMap": true
  }
}

Each package keeps a small file:

// apps/api/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "types": ["node"]
  },
  "include": ["src"]
}

Remember two rules of extends. Paths in the base file such as outDir are resolved relative to the file that declares them, which is why outDir and rootDir belong in the package file. And include and exclude in the child replace the base's, they do not merge.

If you want several flavours, make small presets: tsconfig.node.json for services and tsconfig.react.json for websites, both extending the base. In recent TypeScript versions extends accepts an array, so a package can combine two.

Project references for shared packages

When apps/api imports packages/shared, TypeScript has to know about its types. Project references make that explicit. The shared package must set composite:

// packages/shared/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "composite": true, "outDir": "dist", "rootDir": "src" },
  "include": ["src"]
}

// apps/api/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "outDir": "dist", "rootDir": "src" },
  "include": ["src"],
  "references": [{ "path": "../../packages/shared" }]
}

Then tsc --build apps/api builds shared first and caches the result with an incremental build file, and tsc --build --watch keeps both fresh. A root tsconfig.json with "files": [] and a list of references lets you run one tsc --build for everything. For how the package is linked and exported, see sharing a package between services.

Path aliases

It is tempting to avoid references with paths such as "@shop/shared": ["../../packages/shared/src"]. That makes the editor happy, but TypeScript does not rewrite those paths in emitted JavaScript. The runtime or bundler must resolve them too: Vite needs vite-tsconfig-paths or an alias, tsx and Bun read them, plain Node does not. If the workspace link already resolves @shop/shared through node_modules, you need no alias at all.

Flisk and tsconfig

The Flisk part is small. When you scaffold a service with flisk resource, it writes a tsconfig.json in the service folder with its own options, so change it to extends your base. A service that runs as a local process through a command in service.json gets no generated TypeScript, Vite or Docker files: Flisk runs your command and nothing else, so your tsconfig stays exactly as you wrote it. Flisk does not read or manage the base config.

Type checking as a script

Give every package a typecheck script so checks are uniform and can be run by the workspace tool:

"scripts": { "typecheck": "tsc --noEmit" }

Then pnpm -r run typecheck checks everything, and pnpm --filter @shop/api typecheck checks one package. With project references, tsc --build is the command that checks referenced packages in order. Keep typecheck separate from the dev server: most dev servers transpile without checking types, so errors only appear when you run it.

Pitfalls

  • Everything in one config. A single root tsconfig.json that includes every app makes the editor slow and mixes DOM and Node types. Keep one config per package.
  • Wrong types. A website needs DOM types, a service does not. Set lib and types per package.
  • Missing composite. A referenced project without it gives the error "Referenced project must have setting composite: true".
  • Stale build info. If errors look wrong, run tsc --build --clean and rebuild.
  • Linting versus type checking. A shared ESLint or Biome config follows the same pattern: one base, thin package files.

To see the whole workspace set up around this, read running several services from a pnpm workspace.

Questions people ask

Do include and exclude merge when a tsconfig extends another?

No. In the child they replace the base values. Compiler options merge, with the child winning.

Do I need project references?

Not always. Linked workspace packages that resolve through node_modules work without them. References add ordered builds and faster incremental checks for packages that import each other.

Why do my paths aliases fail at runtime?

TypeScript does not rewrite path aliases in emitted JavaScript. Your runtime or bundler must resolve them as well.
