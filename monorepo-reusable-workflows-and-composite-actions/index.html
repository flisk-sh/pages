Reusable Workflows vs Composite Actions in a Monorepo

How to stop copy-pasting the same steps across package workflows: when to use a reusable workflow, when a composite action, and how inputs, secrets and permissions pass through.

Use a composite action to share a few steps inside a job, such as setup and install. Use a reusable workflow to share a whole job or several jobs, including their runner and permissions. Both live in your repo, so changes ship with the code.

Composite action: shared steps

Put it in .github/actions/setup/action.yml:

name: setup
inputs:
  node-version:
    default: '20'
runs:
  using: composite
  steps:
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: npm
    - run: npm ci
      shell: bash

Call it with uses: ./.github/actions/setup after a checkout step. Every run step in a composite action needs an explicit shell.

Reusable workflow: shared jobs

# .github/workflows/package-ci.yml
on:
  workflow_call:
    inputs:
      package:
        required: true
        type: string
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup
      - run: npm test --workspace ${{ inputs.package }}

A caller then declares one job per package:

jobs:
  api:
    uses: ./.github/workflows/package-ci.yml
    with:
      package: api

How to choose

NeedUse
Share setup stepsComposite action
Share a full job with its own runnerReusable workflow
Different permissions per jobReusable workflow
Show each step in the caller's logComposite action

Reusable workflows appear as one job per called job in the UI, while composite action steps are collapsed under a single step.

Secrets, permissions and limits

  • Secrets are not passed automatically. Use secrets: inherit for the same organisation or list them. Pass only what the called workflow needs.
  • A called workflow can keep or reduce the caller's token permissions, never raise them. See least privilege.
  • Reusable workflows can be nested, but only to a limited depth. Check the current limit in GitHub's docs.
  • Reference reusable workflows in other repositories by a pinned SHA.

Keep it readable

Do not abstract too early. Copy once, abstract at the third copy. Give inputs clear names and defaults, document them in a comment at the top of the file, and keep the number of layers small, since a failure three calls deep is slow to trace. When a job fails, debugging routine is easier if names in the logs map to files you can find.

Version the shared pieces like code. When you change a reusable workflow that many packages call, change one package first, watch the run, then roll the change to the rest. If the workflow lives in another repository, tag releases and pin callers to a tag or SHA, so a bad change does not break every pipeline at once. Document each input in a comment at the top of the file, with an example call, so people do not copy a stale caller.

Questions people ask

Can a composite action call another action?

Yes, it can use other actions and run shell steps. It cannot define its own jobs, runner or permissions, which belong to the calling job.

Do local reusable workflows need a pinned version?

A reference with ./ in the same repository uses the code at the same commit as the caller, so no pin is needed. Pin references to other repositories.
