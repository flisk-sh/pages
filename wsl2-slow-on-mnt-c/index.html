Windows and WSL local development

Why WSL2 is slow on /mnt/c and where to keep your project

WSL2 is fast inside its own Linux filesystem and slow across the bridge to your Windows drive. Where the repo lives decides which one you get.

A project under /mnt/c is read through a file-sharing layer between Linux and Windows, which makes installs, builds and file watching much slower than on the Linux filesystem. Keep the repository in your Linux home folder, for example ~/work/myapp, and open it from Windows tools through WSL, not the other way round.

Why the Windows drive is slow from Linux

WSL 2 runs a real Linux kernel in a lightweight VM. Its own files live in a virtual disk with an ext4 filesystem, and access there is native. Your Windows drives show up as /mnt/c, /mnt/d and so on, but every read and write crosses from the VM to Windows over a network-like file protocol. Two kinds of work suffer most:

  • Many small files. npm install, git status in a big repo and compilers touch thousands of files. Each one pays the crossing cost.
  • File watching. Linux file watchers rely on inotify events. Changes made from Windows tools to files on /mnt/c do not always raise those events inside Linux, so dev servers miss edits. Tools then fall back to polling, which burns CPU, or they simply do not reload.

If hot reload "works on my machine" but not on a colleague's Windows laptop, the project path is the first thing to compare. The general causes are in hot reload not working.

Move the project

From Ubuntu, clone fresh into the Linux home rather than copying across the bridge:

mkdir -p ~/work
cd ~/work
git clone https://github.com/your-org/your-repo.git
cd your-repo

If you already have uncommitted work on the Windows side, commit or stash it, push to a branch, and clone that. Copying a node_modules folder across is the slowest way to do it, and it is also wrong, because native modules built for Windows do not run on Linux. Reinstall dependencies inside Ubuntu.

Still use Windows editors

You do not have to give up your Windows tools.

  • VS Code: run code . inside the project folder in Ubuntu. It opens a window connected to WSL, so the editor, terminal and extensions run on the Linux side.
  • File Explorer: type \\wsl.localhost\Ubuntu\home\yourname\work in the address bar, or run explorer.exe . from the project folder in Ubuntu.

Reading Linux files from Windows through that path is fine for opening, copying out or dragging a file. It is the heavy, repeated work from Linux onto /mnt/c that hurts.

How Flisk reports it

When you run flisk doctor inside WSL2, a check named "WSL project location" looks at where the project root is. If it is under /mnt/c, it warns that hot reload may be broken and suggests moving the repository into the WSL filesystem, such as ~/projects. Add --strict and that warning becomes a failure:

flisk doctor --strict

The strict form is handy in a team script or a README step, because it turns "it feels slow" into a red line someone can act on. The check only looks for /mnt/c; a project on another Windows drive such as /mnt/d has the same slowness but is not flagged by this check, so apply the rule to every /mnt/* path yourself.

Pitfalls

  • Symlinks and permissions. Files on /mnt/c do not carry normal Linux permissions by default, so executable bits and symlinks can behave oddly. Another reason to stay on ext4.
  • Backups. The Linux filesystem is inside a virtual disk file. Push your work to a remote regularly, and see how that disk file grows and shrinks.
  • Docker bind mounts. A bind mount from ~/work into a container is fast. A bind mount from /mnt/c has the same slowness as everything else on that path.
  • Antivirus scans. Corporate security tools sometimes scan the Linux virtual disk too. If installs stay slow on ext4, ask IT whether the WSL distro folder is excluded.

When it does not matter

A tiny script or a docs folder on /mnt/c is fine. The rule is about repositories with thousands of files and watchers. If you only run Windows-native tools on a Windows checkout, leave it where it is.

Questions people ask

Is /mnt/c always slow?

It is slow for workloads with many small files and for file watching. Opening a single file or copying a small folder is fine.

How do I open a WSL project in VS Code?

Run code . from the project folder in the Ubuntu terminal. VS Code opens connected to WSL and runs its tools on the Linux side.

Does flisk doctor check other drives like /mnt/d?

The WSL project location check looks for /mnt/c only. Treat any /mnt/* path the same way and keep the repo in the Linux home.
