How to trace and debug a multi-agent run

Give every run an id, log each model call and handoff as a structured event, and you can replay what happened when the final answer is wrong.

To debug a multi-agent run, give it a run id, give each task a span id, and write one structured event per model call, tool call and handoff. With those events you can read the run as a timeline and find the first step where things went wrong.

Log events, not prose

Plain log lines are hard to query across agents. Write one JSON object per event, with the same keys each time.

{
  "run_id": "r_8f3a",
  "task_id": "t_2",
  "parent_task_id": "t_0",
  "agent": "researcher",
  "event": "model_call",
  "model": "your-model-name",
  "input_tokens": 1820,
  "output_tokens": 240,
  "ms": 3100,
  "status": "ok"
}

Add similar events for tool_call, handoff, retry and limit_hit. Write them as JSON lines to a file or a database table.

Keep the full prompts somewhere

Metadata tells you where to look. The prompt and the reply tell you why. Store them, with the same ids, in a separate table or object store so you can read the exact text a worker saw. Mind privacy: prompts can contain user data, so apply the same retention and access rules as for the data itself, and redact secrets before logging.

Read a run from the first wrong step

When the final answer is wrong, do not start at the end. Walk back along the task tree to the first step whose output was wrong. Usually it is one of:

  1. A plan that missed a task.
  2. A handoff that dropped a constraint.
  3. A tool result the worker misread.
  4. A worker that hit a limit and returned a partial result as if complete.

Each of these maps to a fix, described in why multi-agent systems fail.

Build one small viewer early: a script that takes a run id, prints the task tree with status, tokens and time for each node, and marks the first failed or partial task. Ten minutes of work here saves hours of scrolling raw logs, and it makes bug reports from teammates specific.

Replay and turn bugs into tests

Because you stored the prompts and tool results, you can replay a failing task against a changed prompt and compare. Better, turn each real failure into a test case. Save the inputs and the check that would have caught the failure, and add it to your suite. Over time the suite becomes a record of every mistake you have already fixed. The testing guide, testing and evaluating AI agents, shows how to score such cases.

Pitfalls

Do not log secrets or full user documents without a retention plan. Do not rely on timestamps alone to order events from different processes, since clocks differ; use a sequence number per run. And keep logging cheap, so it never becomes the reason a run is slow. For local setups, observability for local development covers logs and metrics.

Questions people ask

Do I need a tracing product to debug agents?

No. JSON lines with run, task and parent ids in a file or table are enough to start. Add a tool when the volume grows.

Should I log full prompts?

Store them for debugging, but redact secrets and apply the same retention and access rules as the underlying user data.
