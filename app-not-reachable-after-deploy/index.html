App runs but is not reachable after deploy: bind and PORT

The logs say the server started, and the host says nothing is listening. Both are true.

Updated

If your app starts but the host shows a timeout, a 502, or "no open ports detected", the server is almost always bound to 127.0.0.1 or listening on a port the host does not expect. Bind to 0.0.0.0 and read the port from the PORT environment variable. Those two changes fix most cases.

What is happening

A server listens on an address and a port. The address decides who can connect. 127.0.0.1 accepts connections only from the same network namespace. Inside a container, that is the container itself, so the host's proxy, which connects from outside, is refused. 0.0.0.0 means all interfaces, which is what you want for a service behind a proxy.

The port is the second half. Platforms such as Render, Heroku-style hosts and Google Cloud Run tell your app which port to use through a PORT variable, and their router sends traffic there. If your code listens on a fixed 3000 and the platform expects the value of PORT, the app runs and nothing receives traffic.

Fix it per runtime

Defaults differ, so check yours rather than assuming:

RuntimeListen on all interfaces, on PORT
Node http or Expressapp.listen(process.env.PORT || 3000, "0.0.0.0")
Python with uvicornuvicorn main:app --host 0.0.0.0 --port ${PORT:-8000} (the default host is 127.0.0.1)
Flaskflask run --host 0.0.0.0 --port ${PORT:-5000}
Gohttp.ListenAndServe(":"+port, handler), where an empty host means all interfaces
Vite previewvite preview --host 0.0.0.0 --port $PORT

Do not put a development server in production if you can avoid it. A Vite dev server or flask run is for your laptop. Build a static bundle or use a production server such as gunicorn.

Prove it on your laptop

You can reproduce the failure without deploying. Run the production image, publish the port, and call it from the host:

docker run --rm -p 8080:8080 -e PORT=8080 myapp:test
curl -i http://localhost:8080/health

If the app is bound to 127.0.0.1, docker run starts fine and the curl hangs or resets the connection, even though the log says the server is listening. That is the exact symptom the host shows. Fixing the bind address makes the same curl succeed.

The Flisk way

For a service that declares a command, Flisk runs it as a local process and passes the port from service.json as PORT, then waits until the port answers. So an app that reads PORT locally already has the right habit:

{
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health"
}

When you export a Render Blueprint with flisk export render, that port becomes a PORT entry with the same value, and healthCheckPath becomes the Blueprint's health check path (it falls back to /health if you did not set one). The app only has to read PORT and bind to 0.0.0.0. The exporter does not change your code, so the bind address is still yours to fix. If flisk up complains that a port is already in use locally, that is a different problem, covered in how to fix "port already in use".

Other causes to rule out

  • The health check path is wrong. The host probes /health, your app serves /healthz, so the deploy is marked failed. Align the two.
  • The app is slow to start. The platform gives up before it opens the port. Check the startup time in the logs and the host's timeout setting.
  • The app crashes after the first log line. A missing environment variable is common. Read the logs from the start.
  • A firewall or security group blocks the port on a plain VPS. This does not apply to managed platforms.
  • Only IPv6 or only IPv4. Some hosts connect over IPv6 internally. Binding to :: or to 0.0.0.0 depends on your runtime, so read the host's documentation on the address to use.

Once the port answers, add a check that proves it after every deploy, as in smoke test after deploy.

Questions people ask

Is 0.0.0.0 safe to bind to?

Inside a container behind a platform router, yes. On a plain server it accepts connections from every network interface, so combine it with a firewall or publish the port only to 127.0.0.1 behind a reverse proxy.

Why does it work in docker compose on my laptop?

Often you test through a published port and the framework default happens to bind all interfaces, or a dev server flag was set. Run the exact production image and command to compare.

Which port should my app use if the host does not set PORT?

Pick one, document it, and tell the host. Reading PORT with a fallback, such as 8080, covers both cases.
