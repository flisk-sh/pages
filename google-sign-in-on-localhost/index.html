Authentication in local development

Google sign-in on localhost: origins, redirect URIs, test users

Google is stricter than most providers about host names, and its consent screen has a testing mode that surprises people on day eight.

In Google Cloud Console create an OAuth client of type Web application, add http://localhost:3000 as an authorized JavaScript origin and your callback as an authorized redirect URI, and put your own Google account on the consent screen's test users list. Use localhost as the host. Custom names such as myapp.test are rejected for web clients.

Create the client

  1. Create or pick a Google Cloud project just for development. A separate project keeps test clients and test users away from anything real.
  2. Open APIs and Services, then the OAuth consent screen (Google's console now calls the area Google Auth Platform). Choose External unless every user belongs to your Google Workspace organisation. Fill in the app name and a support email.
  3. Open Credentials, Create credentials, OAuth client ID, and pick Web application.
  4. Add the origin and redirect URI described below, save, and copy the client ID and secret.

Origins and redirect URIs are two lists

People paste one value into the wrong box. They do different jobs:

  • Authorized JavaScript origins are for sign-in that runs in the browser, such as the Google Identity Services button. An origin has no path: http://localhost:3000.
  • Authorized redirect URIs are for the server-side authorization code flow. They carry the full path: http://localhost:3000/api/auth/callback/google. The match is exact, as in the redirect_uri_mismatch article.

Add both if your app uses both. Google also documents that changes to these lists can take a few minutes to apply, so a failure right after saving is not always your mistake.

Host name limits

Google validates hosts. A raw IP address is not allowed, with the exception of the loopback addresses, and other hosts must end in a public top-level domain. That is why http://localhost:3000 works and http://myapp.test:3000 does not. A subdomain of localhost, such as app.shop.localhost, is a grey area, so test it before you build a setup around it, and fall back to plain localhost if the console rejects it. For HTTPS on localhost see mkcert, but you do not need it for Google: plain http is accepted for localhost.

Test users and the testing status

A new External app starts in Testing status. In that state only accounts on the test users list can sign in, and everyone else sees "Access blocked: this app has not completed the Google verification process" or a similar message. Add your own address and your teammates' addresses under Test users.

Two limits to know about:

  • The list is capped (Google documents up to 100 test users).
  • For an app in Testing status that asks for non-basic scopes, a refresh token expires after seven days. If login works for a week and then your stored refresh token stops working, re-run the consent flow and store the new token. Requests for only the basic openid, email and profile scopes are not affected.

Do not publish the app just to get past the testing limits. Publishing a sensitive scope triggers verification. For local development, the testing status is the right place to stay.

The server side

Whatever library you use, the setting names are the same: client ID, client secret, and a redirect URI. Keep the secret in an ignored env file, as the GitHub article describes. With Flisk services that run as local processes, read them through the env map and fix the port so the registered URI never changes:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "env": {
    "GOOGLE_CLIENT_ID": "${GOOGLE_CLIENT_ID}",
    "GOOGLE_CLIENT_SECRET": "${GOOGLE_CLIENT_SECRET}"
  }
}

In a Docker stack the frontend lives on app.<project>.localhost, which is the grey-area host above. If Google rejects it, the simplest route is to run the web service as a local process on http://localhost:3000 and keep only your database and other infrastructure in containers. Flisk supports that mixed setup: a service with an image and no command is started with docker run next to the local processes.

Common failures

  • Error 400: redirect_uri_mismatch. Compare the value in the address bar with the console, including the port and the trailing slash.
  • Error 400: origin_mismatch. The browser flow runs from an origin that is not in the JavaScript origins list. Add the origin without a path.
  • Access blocked. The signed-in Google account is not a test user.
  • Works for you, fails for a teammate. Add their account to test users.
  • Wrong client. The client ID in the failing request is a different client from the one you edited. Look at the client_id parameter.

When the Google flow works, you can move on to running your own identity provider locally, which removes the console from the loop entirely. See the Keycloak article in this space.

Questions people ask

Can I use myapp.test as a Google redirect URI?

Not for a web client. Google requires a public top-level domain for hosts, with localhost as the exception.

Do I need HTTPS for Google sign-in on localhost?

No. Google accepts http for localhost redirect URIs and origins.

Why does Google say access blocked for my own app?

The app is in Testing status and the account is not on the test users list. Add it on the consent screen.
