Free hosting for a small backend: what to expect

Free tiers for APIs and bots come with sleeping processes, request caps and no persistent disk. Learn the trade-offs before you build on one.

Free backend hosting usually means your app sleeps when idle, has a small memory and CPU budget, and has no durable local disk. That is fine for a demo, a webhook or a hobby bot, and a poor fit for anything users depend on.

The usual limits

  • Sleeping: an idle process is stopped and the next request waits for a cold start.
  • Ephemeral disk: files you write can vanish on restart. Use a database or object storage.
  • Hours or request caps: a monthly allowance can run out mid-month.
  • Small memory: a large dependency or an in-process model may not fit.
  • Policy changes: free plans get cut or changed. Keep a way out.

Design for a stateless app

Keep no state in the process. Store data in a managed database, read configuration from environment variables, and make startup fast. These rules also make the app easy to move.

const port = process.env.PORT || 3000;
const db = process.env.DATABASE_URL;
app.listen(port);

Respect the PORT variable the platform gives you, and bind to 0.0.0.0 in containers.

Containers or a runtime platform

Platforms that run containers give you freedom of language but pay for it in cold starts. Edge runtimes such as Cloudflare Workers start fast and fit APIs and bots, but limit the runtime and execution time. Match the platform to the shape of the app.

Where to read more

The Host guide from Flisk is an early free hosting guide and service for small apps. Treat it like any free tier: read what it promises, keep backups, and do not host anything critical on it.

Plan an exit

Assume the free plan will change. Keep a one-page runbook: how the app is built, where the data lives, which environment variables it needs, and how to deploy it elsewhere. Containerise it if you can, since a Dockerfile moves between providers. Export your data on a schedule. A free host is a good place to start, as long as moving off it takes an afternoon rather than a rewrite. If your app needs several services at once, the local development guides cover running the full stack on your own machine first.

Keep it awake, or do not

Pinging a sleeping app every few minutes is a common trick, but it can burn through a monthly allowance and some providers forbid it. A better approach is to accept the cold start, return a fast loading state, or move the endpoint to a platform without cold starts.

Before putting anything online, read what not to publish.

Questions people ask

Can I run a database on a free host?

Use a managed database with its own free tier rather than a file on the app's disk, which may disappear on restart.

Is free hosting fine for a production app?

Only for tiny or non-critical ones. If people depend on it, pay for a plan with support and a clear service level.
