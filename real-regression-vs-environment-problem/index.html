Debugging CI Failures

CI Regression or Environment Problem? How to Tell

Decide in a few checks whether a red build is caused by your commit, by a changed dependency or runner, or by an outside service, and who should fix it.

A red build is a regression when re-running the same commit fails the same way and the previous commit passes. It is an environment problem when the same commit passes and fails, or when nothing in the repository changed but the result did. Two re-runs and one comparison with the last green run usually answer the question.

Step 1: re-run once

Re-run the failed job. If it passes, the failure is intermittent: a flaky test, a network blip, a runner problem. Note it and move on to the flaky path. If it fails the same way, continue. Do not re-run five times in a row. One re-run gives you the signal and the rest wastes minutes.

Step 2: compare with the last green run

Open the last green run of the same workflow on the same branch. Compare:

  • The commit range between the two runs.
  • The runner image version shown at the top of the setup log.
  • Resolved dependency versions printed by the install step.
  • Tool versions, for example Node or Python.

If the commit range touches code related to the error, suspect a regression. If the commits are unrelated (docs only) and the failure is in an install or network step, suspect the environment.

Step 3: check the usual outside causes

Floating versions move without a commit. A dependency with a range, an action pinned to a branch or tag that moved, a base image tag like latest, or an unpinned global tool can all change under you. Outside services fail too: the package registry, a container registry, GitHub itself, a third-party API. Check the provider's status page before you spend an hour in your code.

Rate limits are a quiet cause. Anonymous pulls from a container registry or unauthenticated API calls fail when many jobs share an address. Authenticate where the provider allows it.

Step 4: bisect if it is a regression

If the failure is deterministic and the code changed, find the commit rather than reading diffs. git bisect does this in a handful of steps. See how to find the commit that broke CI.

A quick decision table

ObservationLikely cause
Fails every time, related files changedRegression
Passes on re-runFlaky test or transient problem
Fails in install step, no related commitRegistry or floating dependency
Fails on one OS onlyPlatform difference or runner image change
Many repos fail at onceOutside outage or shared tooling change

The last row is a useful tell. If unrelated repositories turn red together, look at what they share, not at each commit.

Decide and record who owns it

Name the cause in the pull request or issue in one sentence: regression in commit X, dependency Y changed from A to B, registry outage. Then act. For a regression, revert first and fix after, so the main branch is green again. For a moved dependency, pin it and open a task to upgrade deliberately (see Dependency Updates Without Chaos). For an outside outage, wait and re-run later.

A red default branch blocks everybody, so restoring green has priority over finding the perfect fix.

Questions people ask

How many re-runs are reasonable?

One. If it passes, treat it as flaky and record it. If it fails again the same way, investigate as a real failure.

Should I revert or fix forward?

Revert when the cause is clear and the fix is not quick. A green main branch matters more than a clean history.
