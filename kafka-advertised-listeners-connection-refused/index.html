Kafka advertised listeners: fix "broker may not be available"

The broker tells clients where to connect, and that address is wrong for where the client runs. Two listeners solve it.

The client reached the broker, asked for metadata, and the broker answered with an address the client cannot reach. That is what "Connection refused", "Broker may not be available" and "getaddrinfo ENOTFOUND" almost always mean with Kafka. The fix is to give the broker one advertised listener per network the clients live on, and to make each client use the matching bootstrap address.

Why the first connection works and the second fails

A Kafka client connects to a bootstrap address you give it. The broker replies with cluster metadata: a list of brokers and the host and port of each one, taken from advertised.listeners. From then on the client connects to those advertised addresses, not to the bootstrap one. If the advertised address is localhost:9092 and the client is in another container, localhost is that container. If the advertised address is broker:9092 and the client is on your laptop, broker does not resolve.

Typical messages you will see:

  • Java clients: Connection to node 1 (localhost/127.0.0.1:9092) could not be established. Broker may not be available.
  • Node (kafkajs): KafkaJSConnectionError: Connection error: connect ECONNREFUSED or getaddrinfo ENOTFOUND broker
  • Python and others via librdkafka: Connect to ipv4#127.0.0.1:9092 failed: Connection refused

This is also why a single-listener Compose file found online works for one setup and breaks for another. It was written for clients in one place only. A tutorial that runs the app on the host advertises localhost. A tutorial that runs the app in Compose advertises the service name. Your project probably has both kinds of client, a service in the stack and a test run from your terminal, so one listener is not enough.

The general fix: two listeners

Declare two (or more) named listeners, each with its own port and advertised address, and map each name to a security protocol:

KAFKA_LISTENERS=INTERNAL://:9092,EXTERNAL://:29092,CONTROLLER://:9093
KAFKA_ADVERTISED_LISTENERS=INTERNAL://broker:9092,EXTERNAL://127.0.0.1:29092
KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT
KAFKA_INTER_BROKER_LISTENER_NAME=INTERNAL

Containers on the same Docker network connect to broker:9092. Anything running on your machine connects to 127.0.0.1:29092, which Docker publishes. The names INTERNAL and EXTERNAL are arbitrary. What matters is that each client uses the port whose advertised address works from where the client runs. The listener names also need an entry in the protocol map, or the broker refuses to start.

Do not "fix" this by advertising 0.0.0.0. Clients cannot connect to that address.

How the Flisk stack lines up

The broker resource from the KRaft article sets these listeners, and three Flisk fields make the two addresses easy to use:

  • "provides": { "KAFKA_BROKERS": "broker:9092" } gives every service that lists broker in dependsOn a KAFKA_BROKERS environment variable. Services read it and never hard-code a host.
  • "extraPorts": [{ "port": 29092 }] publishes 29092 on 127.0.0.1 only. Flisk binds extra ports to loopback unless an entry opts in to "bind": "0.0.0.0".
  • flisk status prints the addresses of the services, so you can confirm the published port.

In a service that runs inside the stack, read the variable:

const brokers = (process.env.KAFKA_BROKERS ?? "127.0.0.1:29092").split(",");

On your laptop, a tool or test runner uses the external address:

KAFKA_BROKERS=127.0.0.1:29092 npm test

The fallback in the code above is the external address, so the same file works inside and outside the stack. Only the environment differs.

If the consumer is a local process, not a container

A Flisk service with a command runs as a process on your machine, next to a broker that Flisk starts with docker run. The Flisk docs say these containers share no Docker network, and a local process reaches them at localhost, not by service name. In that layout the broker needs only one listener, advertising localhost:9092, and the consumer uses localhost:9092. Do not mix the two layouts in one file: a container that is built from a Dockerfile cannot run next to command services. Details are in Run local services without Docker.

Checklist when it still fails

  1. Run a client from the same place as your failing code. A tool in the broker container works while your app does not, which points at the advertised address.
  2. Look at the metadata the broker returns. With kcat from your laptop: kcat -b 127.0.0.1:29092 -L lists brokers with their host and port.
  3. Check that the port is published: the extraPorts entry exists and flisk status shows it.
  4. Make sure no old container is still holding the port. See how to fix "port already in use".
  5. With TLS or SASL later, the listener protocol map must say SSL or SASL_PLAINTEXT for that listener. Plain local work uses PLAINTEXT.

Once clients connect from both sides, you can look inside the broker. Read Kafka messages from the command line shows how.

Questions people ask

What does advertised.listeners do?

It is the address the broker hands to clients in metadata responses. Clients connect to it after the first bootstrap connection, so it must be reachable from where the client runs.

Why does localhost work for me but not from another container?

In another container, localhost is that container itself. Use a second listener that advertises the broker's service name for container clients.

Can I advertise 0.0.0.0?

No. 0.0.0.0 is a bind address, not a destination. Advertise a real host name or 127.0.0.1 for your own machine.
