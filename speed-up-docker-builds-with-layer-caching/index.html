Dockerfiles for development

How to speed up Docker builds with layer caching

Every code edit triggers a full npm install or pip install. The fix is the order of five lines in your Dockerfile, not a faster machine.

Docker caches the result of each Dockerfile instruction as a layer, and when one instruction changes, every instruction after it runs again. To keep rebuilds fast, put the lines that change rarely (base image, system packages, dependency install) first, and the lines that change on every edit (your source code) last. In practice that means copying only your dependency manifest, installing, and then copying the rest.

Why the install step runs on every edit

This is the Dockerfile most people start with:

FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]

Docker decides whether a COPY layer is still valid by checking the files it copies. COPY . . includes your source, so any edited file changes the layer. Everything after it, including RUN npm ci, is thrown away and rebuilt. You wait for a full install although package-lock.json did not change.

Order the layers by how often they change

Split the copy in two. The manifest and lockfile go first, the install runs against them, and only then does the source arrive:

FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["node", "server.js"]

Now an edit to server.js only invalidates the last COPY. The npm ci layer is reused until the lockfile changes. The same shape works in every ecosystem:

  • Python: COPY requirements.txt ., then RUN pip install -r requirements.txt, then COPY . ..
  • Go: COPY go.mod go.sum ./, then RUN go mod download, then COPY . ..
  • Rust: copy Cargo.toml and Cargo.lock with a stub src/main.rs, build to warm the dependencies, then copy the real source.

For system packages, put apt-get update and apt-get install in the same RUN line. If they are separate, Docker can reuse an old, cached update layer and the install then fails against a stale package index.

See what is cached and what is not

Run the build with plain progress output and read the step list:

docker build --progress=plain -t myapp .

Steps that were reused are marked CACHED. The first step that is not marked is where your cache broke. Common causes are a COPY . . placed too early, a changing ARG before the install (build arguments take part in the cache key, so keep rarely used ones late), and files you did not mean to copy, such as logs or a build output folder. A .dockerignore file removes those.

Where Flisk fits

If you let Flisk generate a service (a backend or frontend from flisk resource), you do not write this Dockerfile. Flisk builds a set of shared base images (it calls them golden images) once per machine, pulls prebuilt copies from ghcr.io/flisk-sh when it can, and each service's generated Dockerfile starts from them. The dependency layers are therefore shared across services instead of rebuilt per service.

If you bring your own Dockerfile with a bring-your-own resource, Flisk builds it as written, so layer order stays your job and everything above applies unchanged. The Dockerfile is referenced from service.json:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile"
}

The build context is the resource directory unless you set buildContext, so a COPY path is relative to that folder. See running an existing Dockerfile in a local dev stack for the full setup.

A worked example in Python

The same idea with a Python web app. Before, a one-line change to app.py reinstalls every package:

FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["python", "app.py"]

After, the install layer depends only on requirements.txt:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Edit app.py and rebuild: the first four steps report CACHED and only the final copy runs. Add a package to requirements.txt and the install runs again, which is correct. That is the whole trick, and it is worth checking in every Dockerfile you inherit.

Pitfalls

  • Cache is per machine. A fresh CI runner or a new laptop starts cold. In CI you can export and import the cache with docker buildx build --cache-to and --cache-from.
  • Pruning clears it. docker builder prune and docker system prune remove build cache, so the next build is slow. That is the price of freeing disk, see Docker disk full.
  • Do not chain unrelated work into one RUN. One giant line caches as one unit and any change reruns all of it.
  • Too many layers is not the problem. Cache hits matter more than layer count for a development loop.

Next step

Once layer order is right, the next saving is the package download itself. BuildKit cache mounts keep the npm, pip or Go cache between builds, even when the lockfile changes.

Questions people ask

Why does Docker reinstall my dependencies on every build?

Because an earlier instruction changed. Usually COPY . . comes before the install, so any source edit invalidates the install layer. Copy only the manifest and lockfile first, install, then copy the rest.

How do I know which layer broke the cache?

Build with docker build --progress=plain. Reused steps show CACHED. The first step without that mark, or the one right after the last CACHED line, is where the cache was invalidated.

Does Flisk change how my own Dockerfile is cached?

No. A bring-your-own resource is built with the Dockerfile you provide, so layer order is up to you. Flisk's shared base images only apply to services it generates.
