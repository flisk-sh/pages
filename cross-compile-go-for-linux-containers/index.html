How to cross-compile a Go service for Linux containers

Go cross-compiles with two environment variables. The real questions are cgo, which architecture your servers use, and how to keep the image small.

Set GOOS=linux and GOARCH to the target architecture, turn cgo off with CGO_ENABLED=0, and run go build. You get a static Linux binary from your Mac with no extra toolchain. Then copy that binary into a small image, or build it inside the image with a multi-stage Dockerfile so that nobody depends on a developer's laptop.

The one-line cross build

CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o bin/app .
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o bin/app-amd64 .
file bin/app

-trimpath removes local paths from the binary, and -s -w drops the symbol table and debug data, which shrinks the file and also stops a debugger from reading it (see debugging Go with Delve). Do not use those flags for a binary you want to debug.

Which GOARCH? On an Apple Silicon Mac, Docker runs linux/arm64 containers natively, so arm64 runs fast for local work. Many servers and CI runners are amd64. If you build for one and run on the other, the container fails with an "exec format error" or runs through slow emulation.

Why cgo is the catch

Cross-compilation only stays this simple while the program is pure Go. With CGO_ENABLED=1 the build needs a C compiler for the target. Common triggers are the mattn/go-sqlite3 driver, some image libraries, and the net or os/user packages when they fall back to the system resolver. For SQLite there is a pure Go alternative, modernc.org/sqlite. Setting CGO_ENABLED=0 makes the build fail loudly if something needs cgo, which is better than discovering it at runtime.

A multi-stage Dockerfile that cross-compiles

Run the compiler on the build machine's own architecture, and only target the other one. That avoids emulation during the build.

FROM --platform=$BUILDPLATFORM golang:1.23-bookworm AS build
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/app .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot
ENTRYPOINT ["/app"]

Copying go.mod and go.sum before the source means a code change does not download modules again. The final image has no shell and no package manager, which is a small, safe base for a static binary. If your program makes TLS calls you need CA certificates; the distroless static image includes them, and a bare scratch image does not.

Build for both architectures in one command with Buildx:

docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/orders:dev --push .

Pushing is needed because the local image store only holds one platform unless the containerd image store is enabled. For a local test, build one platform and use --load.

Where Flisk fits

For a Go service created by flisk resource orders --language go, Flisk generates the image itself. According to the Flisk docs it is a golang:1.23 build stage using CGO_ENABLED=0 go build, a test stage that runs go test ./..., and a small debian:bookworm-slim production stage with a health check. It builds for the machine you run on, which is what you want for local development, and it does not target other platforms. If you need a specific platform or a distroless final image, write your own Dockerfile and register it:

flisk resource orders --type bring-your-own --stack app --dockerfile ./Dockerfile --yes

That route is the one in run an existing Dockerfile in a local dev stack. A bring-your-own container has no live reload, because Flisk does not generate its image. Use the Go provider for the edit loop and your own Dockerfile for checking the image you will ship.

Pitfalls

  • Exec format error. The binary and the container architecture disagree. Check with docker image inspect --format '{{.Architecture}}' <image>.
  • Time zone data. A static image may lack tzdata. Import time/tzdata in your program if you load time zones by name.
  • Different Go versions. The Go in your Dockerfile and the one in go.mod can disagree. Recent Go versions can download a matching toolchain when GOTOOLCHAIN allows it.
  • Debug flags in the image. Keep the stripped build for the production image and a debuggable build for development.

Questions people ask

What GOARCH should I use on an Apple Silicon Mac?

Use arm64 for containers you run locally, since Docker runs linux/arm64 natively there. Use amd64 for servers or runners that are x86-64.

Why does my Go cross build fail with a cgo error?

Something in your dependencies needs cgo, and there is no C compiler for the target. Switch to a pure Go package, or build inside a container for the target.

Does Flisk cross-compile Go for other platforms?

No. The image it generates builds for the machine you run on. For another platform use your own Dockerfile as a bring-your-own resource.
