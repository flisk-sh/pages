Next.js rewrites: proxy API calls to a local backend

Next.js can forward browser requests to a separate API during development. Here is the rewrite, what runs where, and how it fits with Flisk's Next.js scaffold.

Add an async rewrites() function to next.config.mjs that maps /api/:path* to your backend's URL. The browser keeps calling the Next.js origin with a relative path, Next.js forwards the request on the server side, and you avoid CORS while you develop against a backend that runs on another port.

The rewrite

// next.config.mjs
const API_ORIGIN = process.env.API_ORIGIN ?? 'http://localhost:4000';

/** @type {import('next').NextConfig} */
const nextConfig = {
  async rewrites() {
    return [
      { source: '/api/:path*', destination: API_ORIGIN + '/api/:path*' },
    ];
  },
};

export default nextConfig;

Now fetch('/api/orders') in a client component reaches http://localhost:4000/api/orders. The destination is read when Next.js starts, so restart next dev after you change it. Keep the backend origin in an environment variable that is not prefixed with NEXT_PUBLIC_: it is only needed on the server, and a public variable would be copied into the browser bundle.

Three different places a request can come from

Developers often mix these up, so check which one you are in:

  • Browser code (a client component, an event handler): a relative URL goes through the rewrite. An absolute URL to the backend goes straight to it and needs CORS.
  • Server code (a server component, a route handler, getServerSideProps): there is no browser and no rewrite. A relative fetch('/api/orders') fails because there is no origin to resolve it against. Use the backend's full URL, which can be a private one.
  • Next.js route handlers in app/api: if a file there matches the same path, the file system route wins over a rewrites() entry that returns a plain array, so do not keep two owners for one path.

The Flisk way

Flisk can scaffold a Next.js App Router frontend as a local process, with no Docker:

npm install -g @flisk-sh/flisk
flisk project --yes
flisk resource api --framework express --local --stack app --yes
flisk resource web --type frontend --framework next --local --stack app --yes

The Next.js scaffold gets "command": "npm run dev", whose script is next dev -H localhost, a /health route that answers ok, "healthCheckPath": "/", and the API in dependsOn. Flisk passes the manifest's port as the PORT variable, which Next.js reads, and flisk up starts the API first.

The scaffolded next.config.mjs sets basePath from FLISK_BASE_PATH (unset on the host, so it serves from the root), turns on trailingSlash, and uses output: 'standalone'. It has no rewrites(). On the host the starter's health card calls the same origin, so you add the rewrite above yourself to reach the API. Put the API's port in env in the frontend's service.json, for example "env": { "API_ORIGIN": "http://localhost:4003" }, so the port is written once next to the service. Use the port from your own API manifest.

In Docker mode the same scaffold is routed by Traefik under /<name>/ on <project>.localhost, and Flisk writes NEXT_PUBLIC_API_URL into a generated env file: the backend's gateway route, which the browser calls directly. That route is cross-origin, and a backend scaffolded by Flisk allows *.localhost origins. Next.js is registered but not yet in Flisk's verified frontend list, so test the route with flisk networks before you rely on it.

Pitfalls

  • trailingSlash. With trailingSlash: true (the Flisk scaffold sets it), Next.js can answer /api/orders with a redirect to /api/orders/ before the rewrite runs. If a POST turns into a GET, or your API treats the two paths differently, change the setting or call the slash form.
  • basePath. When basePath is set, rewrites are prefixed with it unless you add basePath: false to the rule. Under a Flisk Docker route the base path is /<name>, so check the final URL in the network tab.
  • Rewrites are not a production proxy. They run inside the Next.js server. That can be fine, but decide on purpose, and check your host's limits on proxied request time and size.
  • Streaming and WebSockets. A rewrite is a plain HTTP forward. For a socket server, connect to it directly, with CORS or an origin check set up.

Questions people ask

Do Next.js rewrites run in the browser?

No. The browser requests a path on the Next.js origin, and the Next.js server forwards it to the destination. Server components and route handlers do not use rewrites at all.

Why does my relative fetch fail in a server component?

On the server there is no browser origin to resolve a relative URL against, and rewrites only apply to incoming requests. Use the backend's full URL there.

Should I put the backend URL in NEXT_PUBLIC_API_URL?

Only if the browser must call it directly. NEXT_PUBLIC_ values are copied into the client bundle at build time, so keep a server-only variable for a rewrite destination.
