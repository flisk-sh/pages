How to design MCP tools that agents use correctly

Fewer tools, clearer names, tight input schemas and useful errors: the design choices that decide whether a model calls your MCP tool correctly.

  2. Write descriptions for a reader who has no context
  3. Make the schema do the validation
  4. Return small, useful results
  5. Make errors recoverable

Design MCP tools around tasks the user wants done, not around your API endpoints. Give each tool a clear verb name, a one-paragraph description that says when to use it, a strict input schema, and an error message the model can act on. Most failed tool calls come from vague descriptions and loose schemas, not from the model.

Model tasks, not endpoints

If your REST API has twelve endpoints, do not expose twelve tools. A model has to read every tool description on every turn, and more tools means more wrong picks. Combine steps that always go together.

Instead of get_user, get_orders and get_order_items, offer find_order that takes an email or order number and returns what a person would want to see. Keep a tool list short enough that you can read it aloud in under a minute.

Write descriptions for a reader who has no context

The description is the only documentation the model sees. Say what the tool does, when to use it, and when not to.

{
  "name": "search_invoices",
  "description": "Find invoices by customer email or date range. Use this to answer questions about past billing. Do not use it to create or change invoices; use create_invoice for that.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "email": { "type": "string", "description": "Customer email, exact match" },
      "from": { "type": "string", "description": "Start date, YYYY-MM-DD" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 50, "default": 10 }
    },
    "required": ["email"]
  }
}

Make the schema do the validation

Use enums for fixed choices, min and max for numbers, and a format note for dates. Then validate again on the server, because a client may not enforce the schema. Reject unknown fields rather than guessing.

Avoid free-form arguments such as a raw SQL string or a shell command. They are hard to describe and dangerous to run. If you must offer one, see the security checklist.

Return small, useful results

Tool output goes into the model's context window. A 200 KB JSON dump wastes tokens and hides the answer. Return the fields that matter, a count, and a hint when results were cut, such as "truncated": true, "total": 312. Add pagination with a cursor for large lists.

Prefer readable names over internal IDs where you can, or return both.

Make errors recoverable

When a tool fails because of the input, return a normal result with isError: true and a message that says how to fix it. A protocol-level error tells the client the call was malformed. A tool-level error lets the model read the message and try again.

{ "isError": true,
  "content": [{ "type": "text",
    "text": "No customer with that email. Check the spelling or search by name with find_customer." }] }

Also set tool annotations such as readOnlyHint and destructiveHint where the SDK supports them, since clients can use them to decide when to ask for confirmation. Test the result with real prompts, as covered in testing an MCP server.

Questions people ask

How many tools is too many?

There is no fixed number, but quality drops as the list grows. If a model regularly picks the wrong tool, merge or remove tools before you rewrite descriptions.

Should tool names be long and descriptive?

Use short verb-first names such as search_invoices. Put the detail in the description, not the name.

Try it

Run an MCP server locally before you put it in front of users.

Flisk can scaffold an mcp service next to your database and agents, so you test the whole stack on your own machine first. It is a local development tool, not a production orchestrator.
