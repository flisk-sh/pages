Turborepo dev task: run many services with turbo dev

turbo dev can start every app in a repo with one command. The catch is a few settings that decide whether it works at all.

Define a dev task in turbo.json with "persistent": true and "cache": false, then run turbo run dev. Turborepo starts the dev script of every package that has one and keeps them running. Use --filter to start only some of them.

The turbo.json for dev servers

In Turborepo 2.x tasks live under the tasks key (older versions called it pipeline). A minimal file for a repo with build and dev tasks:

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

Two settings on dev matter:

  • "cache": false. A dev server has no output worth replaying, so caching it only adds confusion.
  • "persistent": true. It tells Turborepo the task never exits. Turborepo then refuses to make another task depend on it, which prevents a build from waiting forever on a server.

The ^ in "dependsOn": ["^build"] means "build the packages I depend on first". If your apps import a workspace package that compiles to dist, put "dependsOn": ["^build"] on dev too, or run a watch script for that package. See sharing a package between services.

Start all or some

turbo run dev
turbo run dev --filter=@shop/api
turbo run dev --filter=@shop/web...

The first starts every package with a dev script. The second starts one. The third starts @shop/web plus the packages it depends on. Turborepo 2 shows a terminal UI by default when several tasks run. If you want plain streamed output, for example in a script or a log file, add --ui=stream.

What turbo dev does not do

Turborepo is a task runner, and a good one. Its strengths are caching and the task graph for build, test and lint. For long-running servers, the gaps are practical:

  • It does not wait for a service to be healthy. Two persistent tasks start side by side; neither waits for the other to answer requests.
  • It does not restart a server that crashes.
  • It does not start a database or a message queue.
  • It does not pick ports. Each app chooses its own, and two can collide. See avoiding port clashes.

None of this is a flaw; it is outside what a build cache is for.

Using Turborepo with Flisk

Flisk's own comparison page says to keep Turborepo or Nx for builds and tests, and to point a service's command at the dev task. For one app, that looks like this in apps/api/service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "pnpm turbo run dev --ui=stream",
  "port": 4000,
  "healthCheckPath": "/health"
}

Because the command runs from the service folder, turbo scopes the task to that package. Add dependsOn on the other services, and flisk up starts them in order, waits for each health URL, prefixes the logs, and restarts crashes. A simpler option is "command": "pnpm dev" and leave turbo out of the dev loop entirely, keeping it for build, test and lint.

I did not run turbo inside a Flisk service for this article, so test the exact command once on your repo. Keep the command in one place so that flisk doctor can tell you when pnpm or turbo is not on the PATH.

Pitfalls

  • A dev script that is not marked persistent will make turbo report the task as finished when the process is still running, or make the next task wait. Always set both flags.
  • Environment variables: Turborepo 2 passes only variables you list in env or globalEnv to a task by default. If an app cannot see its .env values under turbo, that is the first thing to check. See env files in a monorepo.
  • A very large repo with fifty dev scripts should not start all of them. Filter, or start by team.

Questions people ask

What does persistent: true do in turbo.json?

It marks a task as one that never exits, such as a dev server. Turborepo keeps it running and does not let another task depend on it.

Why is my turbo dev task not using the cache?

It should not. A dev server has no output to replay, so set cache to false on the dev task.

Does turbo wait for the API before starting the website?

No. Persistent tasks start together and turbo does not check health. Use a service runner or retry logic in the client for that.
