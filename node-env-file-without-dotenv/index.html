Load a .env file in Node.js without the dotenv package

You may not need dotenv any more. Node reads env files itself, and the rules for which value wins are worth knowing.

Start your program with node --env-file=.env server.js. Node reads the file, adds each KEY=value line to process.env before your code runs, and you no longer need the dotenv package. The flag exists since Node 20.6.

The built-in options

There are three ways to do it, and they differ in when the load happens.

# 1. On the command line, before any of your code runs
node --env-file=.env server.js

# 2. Several files; a later file overrides an earlier one
node --env-file=.env --env-file=.env.local server.js

# 3. Inside the program
node -e "process.loadEnvFile('.env'); console.log(process.env.DATABASE_URL)"

process.loadEnvFile(path) is the same loader as a function. It is useful in a script where you choose the file at runtime. With the flag form, a missing file is an error and Node exits. Newer Node 22 releases (22.9 and later) add --env-file-if-exists, which skips a file that is not there. That is handy for an optional .env.local.

The file format is the usual one: one KEY=value per line, # comments, and quotes for values with spaces. Node supports multi-line values in double quotes. It does not expand ${OTHER} references inside the file the way Docker Compose does, so write the final value or build it in code.

Which value wins

A variable that is already set in the environment keeps its value. The file fills in only what is missing. This surprises people who expect the file to win:

echo 'PORT=3000' > .env
PORT=4000 node --env-file=.env -p "process.env.PORT"
# prints 4000

That is the right default for local work: a one-off PORT=4000 in the shell overrides the file without editing it. It also explains the common bug where a stale value exported in your shell profile beats the one in .env. If a variable "does not change" when you edit the file, run printenv NAME first. More on that in environment variable not loaded.

When dotenv or another loader is still useful

  • You support Node versions older than 20.6.
  • You need variable expansion in the file (dotenv-expand) or schema validation of the values (libraries such as zod or envalid are good for that, on top of any loader).
  • Your framework already loads .env files itself, as Vite and Next.js do. Do not load them twice with different rules.

How Flisk treats env files for local services

For a service with a command, the env map in service.json is what the process receives, and values can reference variables with ${VAR} or ${VAR:-default}. Flisk resolves them in this order, first match wins: your shell, the project .env next to .flisk/project.json, the service's own .env next to its service.json, then the default. A missing service .env is ignored.

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node --watch server.js",
  "port": 4000,
  "env": {
    "DATABASE_URL": "${DATABASE_URL}",
    "LOG_LEVEL": "${LOG_LEVEL:-info}"
  }
}

This keeps the committed manifest free of values: it holds names, and each developer's .env holds the secrets. Note the direction: the project .env feeds the ${...} expansion, it is not handed wholesale to the process. Name what the service needs in env, or load a file yourself in the command with node --env-file=.env server.js, which Node reads from the service directory because that is where the command runs.

To use a different project env file for one run, flisk up --env-file .env.integration does that. For keys you do not want to share, secrets.generate in service.json can create random development secrets and append them to .env once. See env var names, not values, in committed config.

Pitfalls

  • Never commit .env. Commit a .env.example with names and safe placeholder values and add .env to .gitignore.
  • Everything is a string. DEBUG=false is the truthy string "false". Parse booleans and numbers explicitly.
  • Relative path. --env-file=.env is relative to the directory where you start Node, not to the script.
  • Watch mode. Editing .env does not restart node --watch unless you add the file with --watch-path.

Next step

Questions people ask

Which Node version supports --env-file?

Node 20.6 and later. --env-file-if-exists, which ignores a missing file, arrived in later Node 22 releases (22.9 and up).

Does the .env file override variables already set in my shell?

No. A variable that is already in the environment keeps its value, and the file only fills in the missing ones.

Does Flisk pass my whole .env to a local service?

No. The service gets its env map from service.json, where ${VAR} references are filled from your shell, the project .env, the service .env or a default.
