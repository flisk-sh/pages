Kafka UI for local development: browse topics and messages

A browser view of your topics saves a lot of terminal commands. Kafbat UI is one container and two environment variables.

Run a Kafka web UI next to the broker. Kafbat UI (the maintained fork of the Provectus Kafka UI) lists topics, partitions, consumer groups and messages, and can publish a test message, all from a browser. You point it at the broker's internal address with two environment variables.

Why a UI at all

Command-line tools show everything, but they are slow when the question is "what is in that topic and where is my consumer group?" A UI answers that in two clicks:

  • See which topics exist, their partition counts and configs.
  • Browse messages by partition and offset, with key, value and headers decoded.
  • Watch consumer group lag next to the topic.
  • Publish a hand-written message to trigger a consumer.

Choices are plentiful. Redpanda Console works with any Kafka-compatible broker. AKHQ is another open-source option. Kafbat UI is a single container with a short configuration, which is why it is used here. The same pattern applies to the others: image, broker address, a web port.

The plain Docker way

If your broker already publishes a port to your machine, one command is enough on Linux, macOS and Windows. The UI container needs to reach the broker's published address, not 127.0.0.1, which would point back at the UI itself:

docker run --rm -p 127.0.0.1:8080:8080 \
  -e KAFKA_CLUSTERS_0_NAME=local \
  -e KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS=host.docker.internal:29092 \
  kafbat/kafka-ui:v1.5.0

The broker must advertise an address the UI can reach. host.docker.internal only works if the broker advertises it, which is a good reason to put the UI on the same Docker network as the broker and use its service name. That is what the next section does. See Kafka advertised listeners for why.

The Flisk way

With the broker from the KRaft article already in the streaming stack, add the UI as a bring-your-own web UI:

flisk resource ui --type bring-your-own --image kafbat/kafka-ui:v1.5.0 \
  --stack streaming --yes

Then set services/streaming/ui/service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "ui",
  "appType": "bring-your-own",
  "stack": "streaming",
  "port": 8080,
  "image": "kafbat/kafka-ui:v1.5.0",
  "webUi": true,
  "healthCheckPath": "/actuator/health",
  "env": {
    "KAFKA_CLUSTERS_0_NAME": "local",
    "KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS": "broker:9092"
  },
  "dependsOn": [{ "name": "broker", "condition": "service_healthy" }]
}

The pieces that matter:

  • "webUi": true tells Flisk the container serves pages from /. It then gets its own host name, ui.<project>.localhost, with no path prefix stripped. Without it, Flisk would route the container as an API at /api/ui, and the UI's assets would 404. flisk up prints the real address, and *.localhost names resolve to your machine in browsers without an /etc/hosts entry.
  • broker:9092 is the internal listener. The UI runs on the same Docker network as the broker, so the service name resolves.
  • The health path /actuator/health is the Spring Boot health endpoint that the image exposes.
flisk config verify
flisk up streaming

flisk config verify accepted this manifest in CLI 1.4.57. I did not start the UI container while writing this page, so the environment variable names come from the Kafbat documentation. If the page loads but shows no cluster, check flisk logs --service ui for a connection error and compare the address with the broker's internal listener.

Keep it read-only if you share the stack

A UI that can create topics and delete messages is a handy tool and a way to break a shared test setup. Kafbat reads a KAFKA_CLUSTERS_0_READONLY setting for that case. Add it to env with the value "true" when other people use the same broker. Flisk publishes the UI on a *.localhost host, so it is reachable from your own machine only unless you opt in to something wider.

Pitfalls

  • Empty message view. The UI browses a topic from an offset. Choose "from beginning" if you do not see anything, and check you are looking at the right partition.
  • Serde. Messages are shown as strings by default. JSON is readable. Avro or Protobuf need a schema registry configured, which this setup does not include.
  • Memory. The UI is a JVM application, so it adds to the broker's footprint. Start it only when you need it, or use profiles to keep it out of the default run. See start only the services you need.

A UI is the quickest way to look. For scripts and tests you want the terminal tools instead: read Kafka messages from the command line.

Questions people ask

Which Kafka UI should I use locally?

Any of Kafbat UI, Redpanda Console or AKHQ works with a Kafka-compatible broker. Pick one with a single container and a short config. Kafbat UI needs only a cluster name and a bootstrap address.

Why is webUi true needed in the Flisk manifest?

A routed bring-your-own container is served under /api/NAME with that prefix removed. A web app that serves pages and assets from / breaks there, so webUi true gives it its own host name instead.

Can the UI delete or change data?

It can create topics and delete messages unless you configure it as read-only. Turn read-only on when several developers share one broker.
