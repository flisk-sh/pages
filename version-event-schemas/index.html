Event-driven systems locally

How to version event schemas without breaking consumers

A producer can ship on Tuesday. A consumer might ship next month, or be replaying events from last year. The schema has to survive both.

Treat an event as a public contract. Keep changes additive (new optional fields only), put an event type and a schema version in an envelope around every payload, and when you must break the shape, publish a new version alongside the old one until every consumer has moved. Consumers should ignore fields they do not know.

Why events are harder than APIs

With an HTTP API you can deploy server and client together, and the server answers only current requests. Events differ in two ways. Producers and consumers deploy on different schedules, so for some time both old and new code are live. And events are stored: a consumer that replays last month's stream, or a new consumer reading history, meets every shape you ever published. A breaking change is not fixed by a redeploy.

Put the metadata in an envelope

Keep the business data separate from the fields every event needs. The CloudEvents specification names a similar set (id, type, source, time), and you can use it directly or write a smaller version of your own:

{
  "id": "6f1c0a6e-8d0a-4f5e-9d1e-2b7a4c1f9a10",
  "type": "order.created",
  "version": 2,
  "occurredAt": "2026-11-14T09:30:00Z",
  "producer": "orders-api",
  "data": {
    "orderId": "ord_123",
    "total": 4200,
    "currency": "EUR"
  }
}
  • id is unique per event and is what consumers deduplicate on.
  • type says what happened, in the past tense: order.created, not create.order.
  • version is the version of the data schema for that type, an integer that only goes up.
  • occurredAt is when it happened, not when it was published.

Changes that are safe

  • Adding an optional field. Old consumers ignore it, new consumers read it with a default when it is missing.
  • Adding a new event type. Consumers that do not know it must skip it, not crash.
  • Loosening a constraint, for example allowing a longer string.

Changes that break consumers

  • Removing or renaming a field.
  • Changing a type, such as an integer amount in cents to a decimal string.
  • Changing the meaning of a field without changing its name. This is the worst one, because nothing fails: the numbers are simply wrong.
  • Making an optional field required.

For a breaking change, publish a new version. Two ways to do it: emit both order.created version 1 and version 2 for a transition period, or publish version 2 only and have each consumer upgrade old events on read.

Upcast old events in the consumer

An upcaster is a pure function that turns an old shape into the current one before the handler sees it. The handler then only knows the latest version:

const upcasters = {
  "order.created": {
    1: (d) => ({ ...d, currency: "EUR" }),   // v1 had no currency
  },
};

function toLatest(event, latest) {
  let { version, data } = event;
  const steps = upcasters[event.type] ?? {};
  while (version < latest) {
    data = steps[version](data);
    version += 1;
  }
  return data;
}

Unit-test each upcaster with a saved real example of the old event. When you can answer "what did version 1 look like" from a fixture file in the repo, you can change the code with confidence. Fixtures are also the cheapest contract test: the producer's tests validate that its output matches a JSON Schema file, and each consumer's tests run its handler against the fixtures for every version it claims to support. Keep schema and fixtures in a shared folder, which is easy in a monorepo, see monorepo local dev setup.

Check before you ship

Add a step to CI that compares the new schema with the previous one and fails when a field disappears or a type changes. A simple version diffs the JSON Schema files in git. Dedicated tools exist, such as schema registries with compatibility modes, but a diff in a script catches most mistakes. With Flisk you run your services as usual with flisk up, and the schema checks stay ordinary tests in your repo, there is nothing Flisk-specific to configure.

Pitfalls

  • Strict validation in consumers. A consumer that rejects unknown fields turns every additive change into an outage. Validate the fields you use, ignore the rest.
  • Reusing a field. Never give an old field a new meaning. Add a new field and deprecate the old one.
  • Version in the topic name only. A subject like orders.v2 splits history across two streams and makes replay harder. Prefer the version in the envelope, unless you want a clean break.
  • No removal plan. Decide when version 1 stops being published, and check consumer logs for it before you stop.

Once events are versioned, the next risk is order: keeping events in order per entity.

Questions people ask

Do I need a schema registry for event versioning?

Not to start. A JSON Schema file per event type in your repo, fixtures for each version and a CI check for breaking changes cover most small systems. A registry becomes useful when many teams publish to shared topics.

Should the version be an integer or semantic version?

An integer is enough for payload schemas. You only need to know which shape to expect and the order of versions, so major and minor numbers add little.

Can I change an event that is already stored?

Avoid it. Stored events are history. Upcast them when reading, so the stored data stays as it was and your code handles every version.
