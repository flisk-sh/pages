How to store and rotate customer API keys safely

If your SaaS has an API, your customers will paste its keys into scripts and chat. Design them so a leaked database does not leak working keys.

Generate each key from a secure random source, show it to the customer once, and store only a hash of it plus a short non-secret prefix for lookup. Keep keys revocable and give each an owner, scopes and a last-used time. To rotate, allow two active keys at once so customers can switch without downtime.

What a good key looks like

A key is a password for a machine, so it needs to be long and random, not a user-chosen string. Include a readable prefix and a public identifier:

sk_live_k3j9x2ab_Qm8vN0yT4r5UeH7pXw2LcZb1DfGaJiKs9oR3tYn6A
  • sk_live tells humans and secret scanners what it is and which environment it belongs to.
  • k3j9x2ab is a public id. You store it in the clear and use it to find the row.
  • The long tail is at least 32 random bytes, encoded as base64url or hex.

A recognizable prefix helps with leaks. Services that scan public repositories for secrets can match your format, and customers can tell at a glance which of their keys they are looking at.

Store a hash, not the key

Unlike a user password, an API key has high entropy, so a fast hash is enough. You do not need bcrypt or Argon2, which exist to slow down guessing of short human passwords. Use SHA-256, or better, HMAC-SHA-256 with a server-side secret so that a copy of the database alone cannot be used to check guesses.

import { randomBytes, createHmac, timingSafeEqual } from "node:crypto";

const PEPPER = process.env.API_KEY_PEPPER;

export function createKey(env = "live") {
  const id = randomBytes(5).toString("hex");
  const secret = randomBytes(32).toString("base64url");
  const key = `sk_${env}_${id}_${secret}`;
  return { key, id, hash: digest(key) };   // show key once, store id and hash
}

const digest = (key) => createHmac("sha256", PEPPER).update(key).digest();

export async function verify(presented) {
  const id = presented.split("_")[2];
  const row = await db.oneOrNone(
    "select * from api_keys where key_id = $1 and revoked_at is null", [id]);
  if (!row) return null;
  const ok = timingSafeEqual(digest(presented), row.key_hash);
  return ok ? row : null;
}

The table needs the tenant, so a verified key also tells you which tenant is calling:

create table api_keys (
  key_id text primary key,
  tenant_id uuid not null references tenants(id),
  name text not null,
  key_hash bytea not null,
  scopes text[] not null default '{}',
  created_at timestamptz not null default now(),
  last_used_at timestamptz,
  expires_at timestamptz,
  revoked_at timestamptz
);

timingSafeEqual compares in constant time and throws if the two buffers differ in length. Both digests are 32 bytes here, so it is safe. Update last_used_at at most once a minute per key, not on every request, or you turn each API call into a write.

Rotation without downtime

Rotation fails when the old key stops working before customers have deployed the new one. Let a tenant hold several active keys. The flow is: create a new key, deploy it, check last_used_at on the old key to confirm nothing still uses it, then revoke it. For compromised keys, revoke immediately and tell the customer which request patterns used it, which your audit log should contain.

The pepper in local development

The server-side secret must not be committed, and every developer needs one. Flisk can generate it for you on flisk up. Declare the name in the service manifest and read it from env:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "secrets": { "generate": { "API_KEY_PEPPER": "hex:32" } },
  "env": { "API_KEY_PEPPER": "${API_KEY_PEPPER}" }
}

On flisk up Flisk appends the name to the project .env once, with 32 random bytes as hex, and never prints the value or overwrites an existing one. A manifest that also writes a fixed value for that name is rejected by flisk config verify. The catch: if you delete .env, the next run generates a new pepper and every hashed key made with the old one stops verifying. In development that is a nuisance. In production, store the pepper in your real secret manager and never rotate it casually. For the broader approach, see service.json as a team contract.

Pitfalls

  • Logging the key. Request logs and error trackers capture Authorization headers. Redact them.
  • Keys in URLs. Query strings end up in logs and browser history. Accept keys in a header only.
  • Showing the key twice. You cannot, because you do not have it. Say so in the UI and offer to create a new one.
  • One key for everything. Give keys scopes, such as read-only, and enforce them on the server.

Keys identify a tenant for machines. People join a tenant a different way, which is the next article: designing team invitations.

Questions people ask

Do API keys need bcrypt?

No. Keys are long random values, so a fast hash such as SHA-256 or HMAC-SHA-256 is enough. Slow hashes protect short human-chosen passwords.

Why store a key prefix or id in plain text?

It lets you find the one row to check without scanning every hash, and lets customers identify which key is which in a list.

How do I rotate an API key without breaking customers?

Allow two active keys at once. Create the new one, let the customer switch, check the last-used time of the old key, then revoke it.
