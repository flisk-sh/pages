Dependency Updates Without Chaos

What CI Should Prove Before You Merge a Dependency Update

A bot opens the pull request, but CI decides if it is safe. Define the checks that matter, keep them reliable, and watch the default branch for the damage that slips through.

A dependency update pull request should pass the same required checks as any change: install from the lockfile, build, type check, lint, tests and, where relevant, an integration run. If those checks cannot catch a broken update, the problem is the coverage, not the bot. Make the checks fast and trustworthy, then let them decide.

The minimum set of checks

  • Clean install from the lockfile, which fails when the manifest and lockfile disagree.
  • Build and type check, which catch removed or renamed APIs.
  • Unit and integration tests, which catch behaviour changes.
  • Lint, since new rules and plugin versions change results.
  • Package check for libraries: dry-run the pack and test the install, see Release Automation.

Make them required status checks on the default branch so neither a bot nor a person can merge around them.

Make bot pull requests behave like normal ones

Bot PRs often fail for reasons that have nothing to do with the dependency. Dependabot runs use their own secrets store, and read-only tokens by default, so a workflow that needs a secret fails on every bot PR. Either give Dependabot the secrets it needs (separately, under its own settings), or make the job skip steps that need secrets and run the rest. Do not let people merge bot PRs with red checks because 'it is always red'. That habit hides real failures.

Add checks specific to dependencies

Some checks pay off especially for updates. A lockfile drift check, an audit run for new advisories, a license check if your policy limits licenses, and a bundle size or startup time check for apps where it matters. Add a smoke test that runs the built app or CLI, because many dependency breaks only show at runtime. For multi-service apps, see CI for multi-service apps.

Keep the checks quick and not flaky

Dependency updates arrive in bursts. Slow or flaky CI turns a Monday batch into a queue and teaches people to click re-run. Cache package downloads, run only the jobs a change needs, and fix flaky tests when they appear. Faster pipelines also make small, frequent updates cheaper than big, rare ones. See Faster GitHub Actions and Flaky Tests and Flaky CI.

A small example job

- run: npm ci
- run: npm run build
- run: npm test
- run: npm install --package-lock-only && git diff --exit-code package-lock.json
- run: npm audit --omit=dev --audit-level=high

These five lines cover install, build, tests, lockfile drift and new serious advisories. Adjust the audit level to your policy and run the audit on a schedule too.

Watch the default branch afterwards

Even good checks miss things. After a batch of merges, look at whether the default branch stayed green and whether new flaky or slow workflows appeared. Cilytics (cilytics.flisk.si) is a public CI health dashboard that shows red, flaky and slow workflows for an org, or for any public repo with ?repo=owner/name. It uses default-branch runs from the last 100 runs, as an hourly snapshot, and skips repos inactive for 90 days, so use it as a trend view and not a live alarm. If a merged update broke the branch, revert first, then add the missing test.

Questions people ask

Why do Dependabot pull requests fail on secrets?

Dependabot runs use a separate secrets store and a read-only token by default. Add the needed secrets to the Dependabot secrets settings or skip secret-dependent steps for bot pull requests.

Should a bot pull request need human review?

For major updates and critical runtime packages, yes. For patch updates with strong required checks, automerge can be reasonable.
