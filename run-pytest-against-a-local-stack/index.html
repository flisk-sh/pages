How to run pytest against a local API and database

Unit tests tell you a function works. Integration tests tell you the service, its database and its queue work together. In Python this is mostly an organizational problem, and a few habits make it manageable.

Keep fast unit tests and slow integration tests apart with a pytest marker, point the integration tests at a running service through a BASE_URL environment variable, and give them a separate test database so they never touch your development data. Start the stack, wait until it is ready, run pytest -m integration, and stop the stack.

Two kinds of tests, two commands

A unit test calls code in the same process, for example through FastAPI's TestClient. It needs no server and no database, and it runs in milliseconds. An integration test sends real HTTP requests to a running service that uses a real database. Mixing them makes the whole suite slow and flaky, so mark the second kind. In pyproject.toml:

[tool.pytest.ini_options]
markers = ["integration: needs the stack to be running"]
addopts = "-m 'not integration'"

Now plain pytest skips them, and pytest -m integration runs them. (The -m given on the command line replaces the default in addopts.) A test then reads the address from the environment and falls back to a local default:

import os
import httpx
import pytest

BASE_URL = os.environ.get("BASE_URL", "http://localhost:4000")

@pytest.mark.integration
def test_create_and_read_item():
    created = httpx.post(f"{BASE_URL}/items", json={"name": "pen"}, timeout=5)
    assert created.status_code == 201
    item_id = created.json()["id"]
    fetched = httpx.get(f"{BASE_URL}/items/{item_id}", timeout=5)
    assert fetched.json()["name"] == "pen"

Always set a timeout. A test with no timeout that hits a hung service waits forever, which looks like a stuck CI job.

Use a separate database

Tests create and delete rows. Run them against the same database you click around in and you will lose data, or get failures that depend on what you left behind. Two simple options:

  • Create a second database on the same Postgres server, such as app_test, and give the service under test that DATABASE_URL.
  • Let a test framework do it. pytest-django creates a throwaway test_ database for you on its own.

In either case, make each test clean up after itself or run inside a transaction that is rolled back, so the order of tests does not matter. More background in integration tests against the real stack.

Waiting for readiness

The classic flake is a test that fires before the service has finished starting. Wait for a health endpoint, not for a fixed sleep:

import time, httpx, pytest

@pytest.fixture(scope="session", autouse=True)
def wait_for_service():
    for _ in range(60):
        try:
            if httpx.get(f"{BASE_URL}/health", timeout=1).status_code == 200:
                return
        except httpx.HTTPError:
            pass
        time.sleep(1)
    pytest.fail("service did not become healthy within 60 seconds")

The Flisk way

Flisk starts the stack and waits for each service's health path, so the fixture above becomes a safety net rather than the main mechanism. In a project where services run as local processes:

flisk up --json
BASE_URL=http://localhost:4000 pytest -m integration
flisk down

With local processes, flisk up --json prints one JSON line once every service is ready. That line includes each service's URL, so a script can read the address instead of hard-coding it. Run in the foreground, flisk up keeps running in its terminal, so in a script you start it in the background or in a second terminal first. Then flisk down stops the stack and frees the ports.

To run the tests with the service's own environment, so you do not copy DATABASE_URL by hand, use flisk run:

flisk run api -- pytest -m integration

For a service with a command, this runs on your machine from the service folder with the project .env, your shell and the service's own env and PORT. For a container service it uses docker exec in the running container, so the service must already be up. Add --json if an agent or script needs the exit code and output as one JSON object.

On the container route there is also an opt-in for fast feedback while coding. A Python service can set "dev": { "testOnSave": true } in its service.json, and Flisk registers a separate Tilt resource that runs pytest in the container when files under src/ or the test folder change. A failing test turns that resource red while the service keeps running. It runs the tests in your tests folder, so keep integration tests out of that path or behind the marker.

Pitfalls

  • Shared state between tests. If test B needs test A to have run, you have a hidden dependency. Create the data each test needs.
  • Testing against production URLs. A BASE_URL that someone changed in a shell profile can send writes to a real system. Default to localhost in the code.
  • Mocking everything. Mocks are fine for the edges you do not own. See mock or run the real service for a rule of thumb.
  • Slow suites. Run the integration tests in CI and on demand, and keep the default pytest for fast checks.

Questions people ask

How do I skip integration tests by default in pytest?

Register a marker such as integration and set addopts to -m 'not integration'. Run pytest -m integration to include them.

Should integration tests use my development database?

No. Use a separate test database so test data and cleanup never touch your development data.

How do I run pytest with a service's environment in Flisk?

Use flisk run <service> -- pytest. For a local-process service it runs on the host from the service folder with that service's environment.
