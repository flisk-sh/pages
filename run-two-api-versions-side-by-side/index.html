How to run two API versions side by side locally

Before you retire v1 you need to prove it still works while v2 exists. Running both on your laptop is the cheapest way to do that.

The simplest way to serve two API versions is one service that mounts both under different path prefixes, /v1/orders and /v2/orders, sharing the same database. When v1 must stay frozen at an older release, run that release as a second service on another port and send clients to the one they were built for.

Where the version goes

Three styles are common:

  • Path prefix (/v2/orders): visible in logs, easy to cache, easy to try with a browser or curl. Most public APIs choose it.
  • Header or media type (Accept: application/vnd.shop.v2+json): the URL stays stable, but the version is hidden from logs, links and casual testing.
  • Date-based header (a header with a date such as 2026-01-15): each client pins to the API as of a date. It needs good internal tooling to keep many behaviors alive.

For a team that owns its clients, a path prefix is the least surprising. Also decide what a new version means: bump it only for breaking changes (how to detect them). A new optional field does not need v2.

Option 1: two routers in one service

Keep one codebase, one database, two sets of handlers. Share the business logic, and change only the request and response shapes per version:

// Express
app.use('/v1/orders', ordersV1);   // returns { id, total }
app.use('/v2/orders', ordersV2);   // returns { id, total: { amount, currency } }

Both routers call the same OrderService. The version-specific part is a thin mapping layer, and each version can have its own OpenAPI file (openapi.v1.yaml, openapi.v2.yaml) so a mock or a diff can target one. Delete a version by deleting its router and mapper. This is the cheapest approach and the right default.

Option 2: the old release as a separate service

Sometimes v1 must not change at all, for example when it serves a mobile app that you cannot update, and the new code has moved on. Then run the old release next to the new one. Check out the tagged release into its own folder (a git worktree works well):

git worktree add services/orders-v1 v1.8.0
echo "services/orders-v1/" >> .gitignore

Add a service.json in that folder. The name and port must differ from the current service:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "orders-v1",
  "appType": "backend",
  "command": "node server.js",
  "port": 4001,
  "healthCheckPath": "/health"
}

The current service stays as it is, say orders on port 4000. flisk up starts both as local processes, in dependsOn order, and prints one URL for each: http://localhost:4000 and http://localhost:4001. Flisk checks that the ports are free and refuses to start when two services share one. Both can use the same Postgres if the old release is compatible with the current schema, which is the real constraint (see below).

A frontend or script then chooses its target with an env var, for example "env": { "API_URL": "http://localhost:4001" } in a service.json for an old client build. Without Docker there is no gateway that routes by hostname, so the choice happens through ports. If you need hostnames, that is a case for the container path with Traefik instead.

Prove both versions still work

A second version is only useful if it stays correct. Write the same request checks once and run them against both targets by changing a base URL variable (see API requests as test files):

hurl --test --variable base=http://localhost:4001 tests/v1/*.hurl
hurl --test --variable base=http://localhost:4000 tests/v2/*.hurl

Run this in CI as well as on your laptop. If v1 is frozen, its tests should never need edits, so a change to them is a red flag in review.

Pitfalls

  • The database is shared state. Migrations that drop or rename a column break the older version. Use expand-and-contract: add the new column, write both, migrate readers, then remove the old column after the old version is gone.
  • Do not copy and paste the whole service. Two diverging copies double every bug fix. Prefer shared logic with separate mappers, and use a separate old release only for a frozen version.
  • Old versions need a retirement date. Announce it in headers and docs: deprecation and Sunset headers.
  • Two runtimes, two dependency sets. A worktree has its own node_modules or virtualenv. Install dependencies in it before the first run.

For the general problem of starting several services and ordering them, see how to control service startup order.

Questions people ask

Should I version an API in the URL or in a header?

A URL path prefix such as /v2 is the easiest to see in logs, cache and test. Headers keep URLs stable but hide the version. Most teams pick the path.

When does an API need a new version?

Only for breaking changes: removed or renamed fields, new required inputs, changed types or status codes. Adding optional fields or new endpoints does not.

Can Flisk run two versions of one service?

Yes, as two services with different appName and port values, each with its own command. In local-process mode you reach them by port, not by hostname.
