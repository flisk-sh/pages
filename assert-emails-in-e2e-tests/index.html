Email and notifications in local dev

How to test password reset and signup emails in end-to-end tests

A test that clicks Forgot password has to read the email to finish. A local inbox with an HTTP API turns that into a few lines of code.

To test an email flow end to end, send the app's mail to a local catcher such as Mailpit, then have the test poll the catcher's HTTP API for a message to the address it used, read the link out of the body and open it. Use a fresh, unique address in every test so tests do not see each other's mail, and wait with a retry loop instead of a fixed sleep.

Why a real inbox beats a mock

You can mock your mail library in a unit test and assert that sendMail was called. That proves your code asked for an email. It does not prove the SMTP settings work, the template renders, the link has the right host, or the token in the link actually logs a user in. An end-to-end test with a real catcher covers all of that. The flow is the same in every stack:

  1. The test submits the form with a unique address.
  2. The app sends a message to the catcher.
  3. The test asks the catcher for messages to that address, retrying until one shows up.
  4. The test pulls the link out of the message and continues in the browser.

Mailpit's API in four calls

These are the endpoints you need, all under /api/v1 on the web port (8025 by default):

  • GET /search?query=to:ada@example.test lists messages that match. Queries can combine terms such as to:, subject: and from:.
  • GET /message/{ID} returns one message with its Text and HTML bodies.
  • GET /messages lists the newest messages.
  • DELETE /messages empties the inbox.

A Playwright example

import { test, expect, type APIRequestContext } from "@playwright/test";

const MAIL = process.env.MAIL_API ?? "http://127.0.0.1:8025";

async function waitForMail(request: APIRequestContext, to: string) {
  let id: string | undefined;
  await expect
    .poll(
      async () => {
        const res = await request.get(`${MAIL}/api/v1/search`, {
          params: { query: `to:${to}` },
        });
        const body = await res.json();
        id = body.messages?.[0]?.ID;
        return id;
      },
      { timeout: 15_000, message: `no mail for ${to}` },
    )
    .toBeTruthy();
  const res = await request.get(`${MAIL}/api/v1/message/${id}`);
  return res.json();
}

test("password reset link works", async ({ page, request }) => {
  const email = `user-${Date.now()}@example.test`;
  // ...create the user, then:
  await page.goto("/forgot-password");
  await page.getByLabel("Email").fill(email);
  await page.getByRole("button", { name: "Send link" }).click();

  const msg = await waitForMail(request, email);
  const link = msg.Text.match(/https?:\/\/\S+\/reset\?token=\S+/)?.[0];
  expect(link).toBeTruthy();

  await page.goto(String(link));
  await page.getByLabel("New password").fill("a-new-password-1");
  await page.getByRole("button", { name: "Save" }).click();
  await expect(page.getByText("Password updated")).toBeVisible();
});

Run one test and print msg once, because the exact field names matter and your Mailpit version is the authority. Everything else is ordinary Playwright. The pattern works the same in Cypress, pytest or any runner that can make an HTTP request.

Keeping tests independent

  • Unique addresses. Search by recipient, so parallel tests never read each other's messages. This is better than clearing the inbox before each test, which breaks as soon as two tests run at once.
  • Poll, do not sleep. A fixed sleep(2000) is either too slow or too short. A poll with a timeout is as fast as the system allows and fails with a clear message.
  • Check the link host. Assert that the link starts with the URL your tests expect. A reset link that points at a production host is a real bug that only an end-to-end test sees.
  • Clean up once. Call DELETE /messages in a global setup step, not per test.

With Flisk

The setup is the Mailpit resource from the Mailpit article next to your app. The test runs on your host, so it uses the published inbox port, 127.0.0.1:8025, as in the code above; the app inside the stack uses mail:1025 to send. Start the stack with flisk up main (add --wait if you want the command to return only when services are ready), then run Playwright. The general shape of running browser tests against a running stack is in Playwright against a local stack, and the same idea for non-browser tests is in integration tests against the real stack.

Pitfalls

  • Mail sent by a background worker arrives late. The poll absorbs this. If it still times out, check the worker's logs first; see the worker article.
  • Tokens in plain text mail but not HTML. Parse the part you assert on, and test both parts exist.
  • Using this against staging. A catcher only works where you control the SMTP host. In staging, use your provider's sandbox or a dedicated test domain.

Next step

Make sure those test addresses and local settings can never leak into a real send: stop your dev environment from emailing real users.

Questions people ask

How do I get the confirmation link out of an email in a test?

Fetch the message from the catcher's API, take its text or HTML body, and match the link with a regular expression. Then open that URL in the browser.

Should tests clear the inbox before each run?

Prefer unique recipient addresses per test, because clearing breaks parallel tests. Clear once in a global setup step if you want a clean start.

Why not just mock the email library?

A mock shows the code asked to send mail. It cannot show that the SMTP settings, the template and the link in the message work.
