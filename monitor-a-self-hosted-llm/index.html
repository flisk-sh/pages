Open models and self-hosted inference

How to monitor a self-hosted LLM: latency, throughput and errors

The metrics that tell you a model server is healthy: time to first token, tokens per second, queue depth, GPU memory and error rate, and how to collect them.

Watch five things on a self-hosted model: time to first token, tokens per second, queue or waiting requests, GPU memory, and error rate. Most serving engines expose metrics you can scrape, and a simple health check and request log cover the rest.

The metrics that matter

  • Time to first token (TTFT). How long a user waits before output starts. Affected by prompt length and queueing.
  • Tokens per second. Generation speed per request and in total.
  • Queue depth. Requests waiting. Growth means you are out of capacity.
  • GPU memory and utilisation. Memory near the limit risks out-of-memory failures.
  • Error rate and timeouts. By status code.

Record percentiles, not only averages. The median can look fine while the slowest five percent of users wait many seconds. Track the 95th percentile of time to first token and of total time.

Where to get them

vLLM exposes Prometheus-style metrics on its HTTP server at /metrics:

curl -s http://localhost:8000/metrics | head -40

llama.cpp's server can expose metrics when started with a metrics flag; see llama-server --help. For the GPU itself:

nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 5

Metric names differ between versions, so read the output of your own server instead of copying a dashboard blindly.

Measure from the client too

Server metrics miss network and proxy time. Log in your app: model, prompt tokens, output tokens, total duration, and error. A few lines go a long way:

import time
t0 = time.time()
r = client.chat.completions.create(model=m, messages=msgs)
log.info("llm model=%s in=%s out=%s sec=%.2f", m,
         r.usage.prompt_tokens, r.usage.completion_tokens, time.time() - t0)

Do not log full prompts if they may contain personal data. See observability for local development.

Health checks and alerts

Check the server answers a tiny real request, not only that the port is open. Alert on: no successful response for a few minutes, queue growing for a sustained period, GPU memory over a high threshold, and error rate above a normal baseline. Start with these four and tune from real traffic.

Keep a runbook of three lines for each alert: what it means, the first command to run, and who decides to restart. At small scale this is a note in your repo, and it saves time at the worst moment.

Set limits to stay healthy

Cap context length and output tokens, set request timeouts, and rate limit per user. One huge prompt can stall everyone's responses on a shared GPU. If latency is the problem, see cut LLM cost and latency. If memory is the problem, see VRAM.

Questions people ask

What is a good tokens per second?

It depends on the use. For chat, anything faster than reading speed feels fine. Measure your own baseline and watch for drops.

Do I need Prometheus and Grafana?

Not at the start. Logging duration and token counts from your app and looking at nvidia-smi is enough for a small setup. Add Prometheus when you have several servers or users.
