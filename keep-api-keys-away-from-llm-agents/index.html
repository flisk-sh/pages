How to keep API keys and secrets away from LLM agents

A model that can see a secret can be tricked into leaking it. Keep keys in your code and your tools, not in prompts, files or tool output the model reads.

Never put an API key in a prompt, and do not let a tool return one to the model. Keep secrets in environment variables or a secret store used by your own code, and let tools call the service on the agent's behalf so the model only sees the result.

Where leaks happen

Secrets reach a model by accident more often than by attack:

  • A key pasted into the system prompt "so the agent can call the API".
  • A tool that dumps the whole environment or a config file as its result.
  • A .env file the agent can read through a file tool.
  • A stack trace or debug log with a token in a header, returned as an error.

Once the key is in the context, an injection or a simple request can make the model repeat it, and it will also sit in your logs and provider records.

Let the tool hold the key

Write tools so the model asks for an action and your code adds the credential.

import os, requests

def create_issue(title: str, body: str) -> dict:
    token = os.environ["GITHUB_TOKEN"]  # never shown to the model
    r = requests.post(
        "https://api.github.com/repos/OWNER/REPO/issues",
        headers={"Authorization": f"Bearer {token}"},
        json={"title": title, "body": body},
        timeout=20,
    )
    r.raise_for_status()
    return {"number": r.json()["number"], "url": r.json()["html_url"]}

The model sees title and body in, number and url out. It never sees the token. Return only what the model needs.

Scope and shorten credentials

Assume a key will leak someday and make that cheap.

  • Use a token limited to one repository or one API route, with read-only access where possible.
  • Prefer short-lived tokens over permanent ones.
  • Use a separate key for the agent so you can revoke it without breaking everything else.
  • Set spending limits where the provider allows it.

Keep secrets out of files and logs

Add .env to .gitignore, commit a .env.example with fake values, and run a secret scanner in CI. A tool such as gitleaks can scan a repository for committed keys. Redact secrets from logs and from error messages before they reach the model. The older guide on environment variables and secrets in local development covers the practical setup.

Check the agent's tools for accidental exposure too. List every tool that reads files or runs commands and ask what it could return. A tool that can run env or cat .env defeats every other precaution, so remove it or run it in a sandbox with no secrets present at all.

Publishing agent output

Agents that generate pages or reports can paste a secret into the output without meaning to. Search the output for key patterns before you publish it. For example, Flisk Pages publishes a page to a free public link, so anything in the file is public by design. Scan first, then publish.

Questions people ask

What if the agent needs to call an API that needs a key?

Wrap the call in a tool that reads the key from the environment. The model asks for the action and never sees the key.

What should I do if a key reached a model prompt?

Treat it as leaked. Revoke it, create a new one, and check provider and application logs for where the old key was stored.

Run it in a sandbox

Test risky agent code away from your real machine.
