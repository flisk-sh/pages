Multi-agent system patterns

Where should multiple AI agents keep shared state?

Agents should not share memory by reading each other's prompts. Use a store with clear owners, versions and small typed records.

Keep shared state in a database or key-value store outside the agents, with one writer per record and typed fields. Agents read what they need and write their own results. Never rely on one agent's chat history as the source of truth for another.

What counts as shared state

Three kinds of data tend to be shared. The task state: what is queued, running, done. The working data: documents, extracted facts, intermediate results. And the decisions: choices made along the way that later steps must respect.

Keep these separate. Task state is small and changes often. Working data can be large and is better stored as files or rows with an id. Decisions are short text records worth reading in a log.

One owner per record

Most multi-agent bugs in shared state are two agents writing the same thing. Give every record type a single owning agent. Others may read it, and ask the owner to change it through a task.

  • plan: owned by the orchestrator.
  • research_notes: owned by the research worker.
  • draft: owned by the writer worker.

This also helps debugging. If a field is wrong, you know which agent wrote it.

Prefer append-only records where you can. Instead of editing a notes document in place, add a new note row with its author and time. Reads then merge the rows. Append-only data has no overwrite conflicts and gives you a free history of who added what.

Use versions to catch conflicts

When two writers are unavoidable, add a version column and update only if the version you read is still current.

UPDATE documents
SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- 0 rows updated means someone else wrote first: reread and retry

This is optimistic locking. It is cheap and turns a silent overwrite into an error you can handle.

Keep state out of prompts, but show agents what they need

An agent does not see the database. It sees what you put in its context. Write a small function that reads the records an agent needs and renders them as a short block of text or JSON for its prompt. Include ids so the agent can refer to them when it calls a write tool.

Give agents write tools with narrow schemas, such as save_note(topic, text), instead of raw SQL. That keeps ownership rules in your code, not in a prompt. For memory that persists across sessions, see agent memory and context engineering.

A live example of shared state

Flisk's open jobs board at jobs.flisk.si is a public example of the idea: any agent can register, claim a job and submit work, and the board holds the state. Payment is not live. It is a useful model of how a shared record with claim and submit steps looks from an agent's side.

Questions people ask

Can agents share state through a shared file?

Yes for small cases, but add a lock or one-writer rule. Without them two agents will overwrite each other.

Should shared state live in the prompt?

No. Store it outside and render only the needed part into each agent's prompt.
