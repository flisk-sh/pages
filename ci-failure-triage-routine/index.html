Debugging CI Failures

A 10-Minute CI Failure Triage Routine for Teams

A fixed routine for the morning red list: classify each failure, assign an owner, restore green first and track the repeat offenders.

5 min

  3. Assign exactly one owner

Triage means giving every red workflow a class and an owner within ten minutes, not fixing everything. Classify each failure as regression, flaky, environment or infrastructure, assign one person, and restore the default branch to green before anything else. A routine you repeat daily beats a heroic investigation once a month.

Start with the red list

List workflows where the latest run on the default branch failed. You can do it from the Actions tab filtered by branch and status, or with the CLI:

gh run list --branch main --status failure --limit 20

For a whole organisation, a dashboard saves time. Cilytics at cilytics.flisk.si is a public CI health dashboard for GitHub that shows red workflows (the newest default-branch run failed), per-repo pass rate and median run time, and flaky workflows. Try it on one public repo with ?repo=owner/name. Know its limits: it looks at default-branch runs, the last 100 runs, from an hourly snapshot, so it is not live.

Classify each failure

ClassSignalFirst action
RegressionFails on re-run, last green commit passesRevert or fix, bisect if unclear
FlakyPasses on re-run, fails and passes over timeQuarantine and file a task
EnvironmentNo related commit, a dependency or image changedPin, then upgrade deliberately
InfrastructureRegistry, runner or provider outageWait, re-run, note it

The checks for each class are in regression or environment problem.

Assign exactly one owner

A failure with two owners has none. Use the author of the suspect commit, the code owner of the failing area (a CODEOWNERS file helps) or a rotating triage person. Write the owner and class in the issue title or a comment, so the next person sees it without asking. A short template is enough:

Workflow: test (main)
Class: flaky
First seen: run 1234
Owner: @name
Next step: quarantine test, fix by Friday

Restore green first

A red default branch hides new failures, because nobody notices a second red job. Revert the breaking change, or disable a flaky test with a tracked issue, then fix properly. Keep the quarantine list short and visible, with a date to remove each item. The flaky workflow itself should be handled by the steps in Flaky Tests and Flaky CI.

Keep a visible log

Write down each triage result in one place, even a simple issue label such as ci-red. After a month you can count how many failures were regressions, flaky tests or outages, and where the time went. That count tells you what to invest in: better tests, pinned dependencies, or a different runner setup. Without a record, every red build feels new, and the same causes return again and again.

Review repeat offenders weekly

Once a week, look at which workflows failed most, which are slowest and which flipped between pass and fail. Those are your investments: a fix there removes the most noise. Track two numbers over time, the pass rate of the default branch and the time to get back to green after a failure. See CI Metrics That Matter for how to compute them. If you run this across many repositories, Org-Wide CI Visibility covers the weekly review.

Questions people ask

Who should do the triage?

A rotating person per week works well. The rotation spreads the knowledge and stops one engineer from becoming the CI janitor.

Should I disable a failing test?

Only with a tracked issue, an owner and a date to remove the quarantine. An untracked disabled test is lost coverage.
