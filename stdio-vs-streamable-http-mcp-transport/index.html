stdio vs Streamable HTTP for MCP servers: which to use

Choose the right MCP transport. stdio is simple and local, Streamable HTTP is for shared remote servers. Here is how they differ and how to move from one to the other.

Use stdio when the server runs on the same machine as one client, and Streamable HTTP when many clients or users connect over a network. stdio is easier to build and needs no authentication of its own. Streamable HTTP lets you deploy once and serve everyone, at the cost of auth, scaling and monitoring.

How each transport works

With stdio, the client starts your server as a child process and exchanges JSON-RPC messages over stdin and stdout. With Streamable HTTP, the server exposes one HTTP endpoint. The client sends JSON-RPC messages with POST, and the server answers with either a JSON body or a Server-Sent Events stream when it needs to send several messages.

Streamable HTTP replaced the older HTTP+SSE transport in the protocol. If you find a tutorial using two endpoints (one for SSE, one for POST), it describes the older design.

When stdio is the right choice

  • A tool that touches local files or local programs.
  • A server for one developer, started by their editor or agent.
  • Quick prototypes, where setup time matters most.

The main pitfall: stdout is the protocol channel. Any stray print or console.log corrupts the stream. Write logs to stderr.

console.error("tool called", name); // stderr, safe
console.log("debug");              // stdout, breaks the protocol

When Streamable HTTP is the right choice

  • A hosted service that many people use.
  • A server that needs shared state, such as a database connection pool or cache.
  • Anything you want to monitor, rate limit and update without asking users to reinstall.

You now own the usual web concerns: authentication, TLS, rate limits and deployment. Session handling is also yours. A server may issue an Mcp-Session-Id header at initialization, and the client sends it back on later requests. If you run several instances, either keep the server stateless or store session data somewhere shared.

Support both from one codebase

Tool definitions should not know which transport carries them. Build the server object once, then attach a transport at the entry point. With the official SDKs this is a few lines in a main file that picks a transport from an environment variable or flag.

const mode = process.env.MCP_TRANSPORT ?? "stdio";
if (mode === "http") startHttp(server, Number(process.env.PORT ?? 8080));
else startStdio(server);

Here startHttp and startStdio are your own small wrappers around the SDK transports. Check the SDK docs for the current class names.

Start with stdio. Move to HTTP the day a second person needs the server.

Questions people ask

Is SSE still supported for MCP?

Server-Sent Events are still used inside Streamable HTTP for streaming responses. The older standalone HTTP+SSE transport was replaced, though some clients still support it for compatibility.

Can I run a stdio server remotely?

Only through a proxy or bridge that wraps the process in an HTTP endpoint. It is usually cleaner to build the server with Streamable HTTP from the start.
