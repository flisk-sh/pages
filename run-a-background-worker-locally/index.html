Background jobs and queues locally

How to run a background worker locally next to your API

A worker has no URL to click and no page to reload, so it is easy to lose track of. Here is how to keep it running, visible and restartable.

A background worker is just a second process that starts with your API, shares its configuration and never answers HTTP. Run it as its own service with its own logs and restart policy, not as a thread inside the API, so a crash or a slow job never takes the web process down. Flisk scaffolds that service with flisk resource jobs-worker --type worker.

What a local worker needs

Whatever tool you use, a worker needs the same five things:

  • A start command separate from the API's.
  • The queue or database address, passed as an environment variable.
  • A start order: the queue must be up before the worker connects.
  • Logs you can read on their own, labelled by service.
  • A graceful stop. Docker sends SIGTERM, waits ten seconds by default, then sends SIGKILL. A worker that ignores SIGTERM loses the job it was holding.

Without Flisk

The low-tech version is a second terminal tab running npm run worker. It works until you forget it, or restart the API and not the worker, and then you debug jobs that were never processed. A step up is one command that runs both, such as concurrently in a package.json script, or a Procfile runner.

Docker Compose is the next step. The worker is a service with no ports, a depends_on on the queue, and restart: unless-stopped. That gives you ordering and restarts. What it does not give you is a way to start only the worker and its dependencies, or readable logs across services without piping docker compose logs yourself.

The Flisk way

Create the queue and the worker:

flisk resource bus --type queue --stack shop --yes
flisk resource jobs-worker --type worker --stack shop --yes

The worker scaffold is a Bun project with a src/index.ts. Its service.json runs bun run worker and a port in the worker range 6000 to 6999. Because a worker has no HTTP server, Flisk gives it no proxy route and no HTTP health check.

Open services/shop/jobs-worker/service.json and add the queue to dependsOn:

"dependsOn": ["bus"]

Now the worker starts after NATS and receives NATS_URL in its environment. Check the result and start it:

flisk config verify
flisk up shop

Be aware of what the scaffold is. The generated src/index.ts is a polling loop with a placeholder fetchJobs() that hands out one demo job and then waits. It reads WORKER_POLL_INTERVAL, WORKER_MAX_RETRIES and WORKER_BATCH_SIZE into a config object, handles SIGTERM and SIGINT by exiting, and logs a failed job and moves on. It does not connect to any queue and does not retry a failed job. Replacing fetchJobs() with a real subscription is your part, and the NATS article has the connection code.

See and restart it

flisk status
flisk logs --service jobs-worker --since 5m
flisk restart jobs-worker

flisk logs prints a bounded snapshot, so it is safe to paste into a bug report or hand to a coding assistant. flisk restart restarts one resource, which is a quick way to see how your worker handles being stopped in the middle of a job.

Run the worker as a plain process

If your worker is a Node, Python or Go script and you do not want a Docker build in the loop, give it a command. Flisk then runs it as a local process on your machine:

{
  "schemaVersion": 1,
  "appName": "mailer",
  "appType": "worker",
  "command": "node worker.js",
  "dependsOn": ["api"],
  "env": { "API_URL": "http://localhost:4000" }
}

I checked this file with flisk doctor, which accepted it. In this mode flisk up starts services in dependsOn order, prefixes each log line with the service name, and restarts a process that exits after 1 second, then 2, 4 and 8. After five quick exits in a row it stops restarting it. Set "restart": "no" for a job that should run once. A ready-made image, such as a database or the NATS container, can run beside local processes. The details are in run services without Docker.

Pitfalls

  • A crash loop looks like a healthy worker. With no HTTP health check, "running" only means the process is alive. Read the logs after every change.
  • Make handlers safe to run twice. A restart during a job means redelivery, so a duplicate must not charge a card twice.
  • Do not run migrations in the worker. Use a migrator resource, as in database migrations in local dev.
  • Do not use a worker for scheduled work. That needs a scheduler, covered in cron jobs in local dev.

Once the worker runs, the next question is what happens when a job fails. Testing consumer retries locally covers acknowledgements, redelivery and dead letters.

Questions people ask

Does Flisk give a worker a URL?

No. A worker has no HTTP server, so Flisk creates no proxy route and no HTTP health check for it. You read its output with flisk logs --service <name>.

Does the generated worker connect to a queue?

No. The scaffold is a polling loop with a placeholder fetchJobs() function and one demo job. You replace it with a real subscription, for example to the NATS queue resource.

How do I restart only the worker?

Run flisk restart <worker-name>. It restarts that one resource, or triggers its rebuild, and leaves the rest of the stack running.
