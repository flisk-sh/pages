Database migrations for Go and Rust: goose and sqlx locally

Go and Rust each have a good migration tool. The part that goes wrong is when the migrations run, and who runs them.

For Go, use goose: SQL files with up and down sections, run by the goose command. For Rust, use sqlx: numbered SQL files, run by sqlx migrate run or embedded in the binary with the sqlx::migrate macro. In both cases run migrations as a separate step before the API starts, not from the API's own start script, so a failed migration stops the start and a slow one does not look like a hung server.

Goose for Go

go install github.com/pressly/goose/v3/cmd/goose@latest
mkdir migrations
goose -dir migrations create create_orders sql

That writes a file such as migrations/20261114120000_create_orders.sql. Fill in both directions:

-- +goose Up
CREATE TABLE orders (
  id bigserial PRIMARY KEY,
  total_cents integer NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- +goose Down
DROP TABLE orders;

Run it against the local database:

export DATABASE_URL='postgres://app:app@localhost:5432/app?sslmode=disable'
goose -dir migrations postgres "$DATABASE_URL" up
goose -dir migrations postgres "$DATABASE_URL" status
goose -dir migrations postgres "$DATABASE_URL" down   # reverts one

Recent goose versions also read GOOSE_DRIVER, GOOSE_DBSTRING and GOOSE_MIGRATION_DIR from the environment, so the command can shrink to goose up. You can also embed the SQL files with go:embed and call goose as a library at startup. That is handy for tests, and for production you still want a separate job.

sqlx for Rust

cargo install sqlx-cli --no-default-features --features rustls,postgres
export DATABASE_URL='postgres://app:app@localhost:5432/app'
sqlx database create
sqlx migrate add -r create_orders   # -r makes an up and a down file
sqlx migrate run
sqlx migrate info

Edit the generated .up.sql and .down.sql files, then run them. sqlx records applied migrations in a _sqlx_migrations table, along with a checksum, so editing a file that has already run is an error. Write a new migration instead.

The query macros check your SQL against a live database at compile time, which means the build needs DATABASE_URL. For builds without a database, such as a Docker build or CI, run cargo sqlx prepare while the database is up, commit the .sqlx folder it writes, and build with SQLX_OFFLINE=true. Forgetting this is the usual reason a Rust image build fails with a connection error.

Run migrations as their own step with Flisk

Flisk's own rule for new examples is that migrations run in an explicit one-shot resource, not from an API start script. Its documented migrator type covers Prisma, Drizzle, Atlas and dbmate. goose and sqlx are not on that list, so the honest way to run them on the Docker route is a bring-your-own job with the restart policy turned off:

flisk resource migrate --type bring-your-own --stack app --dockerfile ./Dockerfile --restart no --yes

The Flisk docs state that a service listing such a job in dependsOn starts only after the job exited 0, and that a failed job stops the services after it. They show it working with a dbmate image; the repository's examples/byo-jobs folder is the runnable version. For goose, the Dockerfile is a small image that has the goose binary and your migrations folder:

FROM golang:1.23-bookworm AS tool
RUN CGO_ENABLED=0 go install github.com/pressly/goose/v3/cmd/goose@latest

FROM debian:bookworm-slim
COPY --from=tool /go/bin/goose /usr/local/bin/goose
COPY migrations /migrations
ENTRYPOINT ["/bin/sh", "-c", "goose -dir /migrations postgres \"$DATABASE_URL\" up"]

Give the job the database address in its env block, for example "env": { "DATABASE_URL": "${DATABASE_URL}" }, which Flisk expands from the project .env, and add "dependsOn": ["postgres"] so Postgres is up first. The .env that flisk project writes has a DATABASE_URL that points at the host postgres on the Docker network. Then make the API wait with "dependsOn": ["migrate"]. A sqlx job has the same shape, with sqlx-cli in the image and sqlx migrate run as the command. This is the pattern in run database migrations in local dev with a migrator, adapted to the Go and Rust tools.

If you run your services as local processes and only Postgres in Docker, a local process reaches the database at localhost, not by service name, and you run goose or sqlx from your own shell against that address.

Pitfalls

  • Migrating from the API start. Two replicas race, and a failure looks like a crash loop. Use a job and a dependency.
  • Editing an applied migration. sqlx rejects it by checksum, and goose will not rerun it. Add a new one.
  • A job that restarts forever. A container that exits 0 with an unless-stopped policy starts again. Set the restart policy to no.
  • Different databases. Check that the migrate step and the API read the same DATABASE_URL. See DATABASE_URL and env vars locally.

Questions people ask

Should migrations run when the API starts?

Prefer a separate step that finishes before the API starts. It fails fast, it does not race between replicas, and it is easy to rerun by itself.

Why does my sqlx build fail in Docker?

The query macros need a database at compile time. Run cargo sqlx prepare, commit the .sqlx folder, and build with SQLX_OFFLINE=true.

Does Flisk have a goose or sqlx migrator type?

The documented migrator type names Prisma, Drizzle, Atlas and dbmate. For goose or sqlx use a bring-your-own job with the restart policy set to no.
