How to generate realistic shop data for local development

Ten rows will not show you a slow query or a broken pagination. Generate thousands of rows that look like a real store, and make the data the same on every run.

Generate store data with a script that uses a fixed random seed, so every run produces the same rows. Make the data realistic in three ways that uniform random data is not: a few products sell far more than the rest, orders spread over months, and the awkward cases are included on purpose (a cancelled order, an empty description, a very long name). Insert in batches, so 50,000 rows take seconds.

Why uniform random data misleads you

If every product has the same chance of being ordered, every query looks equally fast and every page looks equally full. Real shops are lopsided: a handful of products make most of the sales, most customers order once, and a few order often. Queries that group by product or customer behave differently on lopsided data, and so do caches. Seeding to match that shape catches problems that a flat table hides.

Make it repeatable

@faker-js/faker (JavaScript) and Faker (Python) both accept a seed. With the same seed and the same call order, you get the same names and numbers:

import { faker } from "@faker-js/faker";
faker.seed(42);
faker.setDefaultRefDate("2026-01-01T00:00:00Z"); // fixed reference for relative dates

const email = faker.internet.email({ provider: "example.test" });

Using a .test address keeps any email your stack sends from reaching a real person. A repeatable seed lets a teammate say "order 1,204 fails" and you see the same order. If you change the script, the data changes, so keep the seed script in version control, and treat it as code.

Shape the data

Three small pieces of logic give most of the realism:

  • Skewed popularity. Pick the product for each order line with a weight such as 1 / (rank + 1), so rank 0 is chosen far more than rank 100.
  • Spread dates. Use faker.date.between over the last 12 months, and sort so ids and dates move together. Add a busier period if you want to test a sale.
  • Status mix. For example 70 percent delivered, 10 percent shipped, 8 percent cancelled, 7 percent pending, 5 percent refunded. This is what makes admin filters and reports worth testing.
function pickWeighted(n: number) {
  const weights = Array.from({ length: n }, (_, i) => 1 / (i + 1));
  let r = faker.number.float() * weights.reduce((a, b) => a + b, 0);
  for (let i = 0; i < n; i++) { r -= weights[i]; if (r <= 0) return i; }
  return n - 1;
}

Add the awkward rows on purpose

Random data rarely produces the cases that break code. Add them by hand at the top of the script, with fixed ids:

  • A product with a 200-character name and one with an emoji.
  • A customer with no name, and one with an apostrophe in it (O'Brien).
  • An order with a single line of quantity 99, and one with 40 lines.
  • A variant with zero stock and one that is inactive.
  • A refunded order and a cancelled order, to test the history and reports.

Insert fast

One INSERT per row is slow because of the round trip each time. Build batches of 500 to 1000 rows and insert each batch with a multi-row statement or, in Postgres, COPY through a library such as pg-copy-streams. Insert parents first (products, customers), then orders, then order lines, inside one transaction so a failure leaves nothing half done. After inserting rows with explicit ids, move the sequence forward so the next normal insert does not collide: SELECT setval(pg_get_serial_sequence('orders','id'), (SELECT max(id) FROM orders));.

Make the script safe to run twice. Either truncate the tables it owns at the start (TRUNCATE ... RESTART IDENTITY CASCADE) or skip when the data is already there. Never point it at production; read the database name from the environment and refuse to run unless it looks local.

Run it inside the Flisk stack

Add a script to the API's package.json, for example "seed": "bun run src/seed.ts", and run it with the environment the service has in the stack:

flisk run orders-api -- bun run seed

That form is the one shown in flisk run --help. The command runs in the running container with the service's own DATABASE_URL, so the script and the API talk to the same database, and the exit code is the script's, which makes it usable in a shell script or CI. The stack must be up first. If the tables are missing, the script fails on its first insert, so run the migrations before. The same pattern as a one-shot job inside flisk up is in seeding a local database, and resetting a local database shows how to wipe and start again.

Pitfalls

  • Copying production data. Do not. Names, addresses and emails are personal data; fake rows are enough.
  • Changing call order. Adding one faker call early shifts every value after it. That is fine, but regenerate expected values in tests that depend on them.
  • Too much data for the unit tests. Keep a small fixed dataset for tests and a large one for exploring performance.
  • Ignoring indexes. The point of a big seed is to run EXPLAIN ANALYZE on your slow pages. Try it on the order list, as in paginating order history.

Questions people ask

How many rows should a local seed have?

A few hundred products and a few tens of thousands of orders is enough to expose missing indexes on a laptop, without making the seed slow.

Should the seed be random or fixed?

Random values from a fixed seed. You get realistic variety and the same data on every run.

Can I use the same seed script in CI?

Yes. Seed with a smaller size in CI and a larger one locally, controlled by an environment variable.
