How to Fix Timing and Race Condition Flaky Tests

Replace fixed sleeps with waits on real conditions, inject the clock, and find races between your test and the code it checks. Examples in Python and JavaScript.

Fix timing flakes by never waiting for a fixed number of seconds. Wait for a condition, inject a fake clock, or make the code under test signal when it is done. A sleep(2) is a guess that fails on a slow runner.

Replace sleep with a wait on a condition

The bad version:

start_job()
time.sleep(2)
assert job.status == 'done'

The fix is a small polling helper with a timeout. It returns as soon as the condition is true, so it is fast on good days and patient on bad ones.

import time

def wait_for(cond, timeout=10, step=0.05):
    end = time.monotonic() + timeout
    while time.monotonic() < end:
        if cond():
            return
        time.sleep(step)
    raise AssertionError('condition not met in %ss' % timeout)

start_job()
wait_for(lambda: job.status == 'done')

Await the thing, not the time

In JavaScript, return and await the promise instead of timing it. A missing await is a very common flake: the test ends before the work does, and the failure lands in a later test.

test('saves', async () => {
  await save(item);          // await, do not setTimeout
  expect(await load(item.id)).toEqual(item);
});

For UI tests, use the framework's auto-waiting assertions rather than reading the page once.

Control the clock

Code that depends on now is nondeterministic. Pass the clock in, or use a fake timer.

// Jest
jest.useFakeTimers().setSystemTime(new Date('2025-01-31T23:59:59Z'));

# Python (pip install freezegun)
from freezegun import freeze_time

@freeze_time('2025-01-31 23:59:59')
def test_month_end(): ...

Test the edges on purpose: midnight, month end, leap day, daylight saving changes.

Find the real race

Sometimes the flake is a real race in your code, such as two threads updating one value. Run the Go race detector or a thread sanitizer.

go test -race -count=50 ./...

If the detector reports a race, fix the code with a lock, a channel or an atomic. Do not add a sleep to hide it. Also check for unawaited background tasks, leaked timers and open handles. Jest's --detectOpenHandles helps here.

Timeouts: set them with care

Waits need an upper bound, otherwise a real hang freezes the job. Pick a bound well above normal, such as ten times the typical duration, and set timeout-minutes on the job as a second guard. A generous timeout does not slow passing tests, because the wait returns as soon as the condition holds. The cost only appears when something is truly broken, which is when you want a clear failure message with the timeout value in it.

Include the last observed state in the message, for example the job status, so the log explains what the test was waiting for.

Check your fix

Loop the test again, as in reproducing it locally, under CPU limits. Run it a few hundred times. If it never fails, ship the fix.

Questions people ask

Is a longer sleep an acceptable fix?

Only as a stopgap. It makes tests slower and still fails when the machine is slower than your guess.

How do I test code that uses timeouts?

Use fake timers or inject a clock so the test advances time itself instead of waiting for it.
