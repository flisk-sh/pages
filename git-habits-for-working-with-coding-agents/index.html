Coding agents in practice

Git habits that make coding agents safe to use

Branch per task, commit often, review diffs, and know how to undo agent work. A short set of git habits that turn agent mistakes into cheap reversals.

Work on a branch for every task, commit after each green step, and read the diff before you merge. With those three habits an agent mistake costs you a git reset, not an afternoon. Git is your undo button, so make sure there is always something recent to go back to.

Start clean, on a branch

git status                # clean tree before you start
git switch -c agent/add-export

A clean tree means every change in the diff came from this task. Never let an agent work on main. For parallel work, use worktrees.

Commit small and often

Ask the agent to commit when a step is done and its tests pass, or do it yourself. Small commits give you checkpoints. If the next step goes wrong, you reset to the last good one. Use plain messages that say what and why. You can squash them before merging.

git add -p                       # stage hunks you have read
git commit -m "Add CSV export for reports"

Undo without panic

SituationCommand
Throw away uncommitted changes in one filegit restore path/to/file
Throw away all uncommitted changesgit restore . (tracked files only)
Keep changes aside to look latergit stash push -u -m "note"
Go back to the last commit, drop later onesgit reset --hard HEAD~1
Find a lost commitgit reflog

reset --hard and restore . destroy uncommitted work, so check git status first.

Read the diff, in order

Before merging, run git diff --stat main...HEAD to see the scope, then read the tests, then the code. Our review checklist covers what to look for. Watch for files that should never change: lockfiles, generated output, CI config, and anything with secrets.

Guardrails on the server

  • Protect main so pushes require a pull request and passing checks.
  • Forbid force-push on shared branches.
  • Add a secret scanner to CI so a leaked key fails the build.
  • Sign off or sign commits if your project requires it, and check the agent's commits follow the rule.

These protect you when an agent, or you, make a mistake at the wrong moment. For checks in CI, see CI guards and AI code review.

A short routine

Before the task: clean tree, new branch. During: commit after each green step. After: read the diff, run the full checks, squash if needed, open a pull request. Put the routine in your instructions file so the agent follows it too, and remember that you remain the person who merges.

Questions people ask

Should the agent be allowed to push?

Pushing a feature branch is usually fine. Pushing to main, force-pushing or deploying should stay with a human or a protected pipeline.

Do I need to squash agent commits?

Not required. Squash if the history is noisy, as you would for any branch.
