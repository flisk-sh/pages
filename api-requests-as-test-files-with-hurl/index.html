How to keep API requests as test files in git with Hurl

A pile of curl commands in a wiki goes stale. A folder of request files in git can run in CI and doubles as living documentation.

Hurl is a command line tool that runs HTTP requests written in plain text files and checks the responses. Put .hurl files in your repository, run hurl --test tests/*.hurl, and the same files serve as documentation, a smoke test on your laptop and a CI check. There is no GUI and no account.

Why requests belong in the repo

API collections that live in a desktop app or a wiki have three problems: they are not reviewed with the change that made them stale, they cannot run in CI without extra tooling, and teammates have their own copies. Text files in git fix all three. Alternatives with the same idea exist: Bruno stores collections as files in a folder, and VS Code or JetBrains editors run .http files. Pick the one your team will actually keep up to date. Hurl suits command line and CI use best.

A first file

Install with brew install hurl or a release package. Save this as tests/orders.hurl:

POST {{base}}/orders
Content-Type: application/json
{
  "sku": "A-1",
  "quantity": 2
}
HTTP 201
[Captures]
order_id: jsonpath "$.id"
[Asserts]
jsonpath "$.status" == "pending"

GET {{base}}/orders/{{order_id}}
HTTP 200
[Asserts]
header "Content-Type" contains "application/json"
jsonpath "$.quantity" == 2

Each entry is a request, then the expected status after HTTP. [Captures] saves a value from the response into a variable, and the second request uses it, so one file can walk a whole flow: create, read, update, delete. [Asserts] checks headers and body with JSONPath. A file with several entries stops at the first failure, with a message that shows the request and what was different.

Run it with the base URL as a variable, not hard-coded:

hurl --test --variable base=http://localhost:4000 tests/*.hurl

--test prints a pass or fail line per file and exits non-zero when anything fails. Because the base URL is a variable, the same files run against your laptop, a staging host, or an older version of the API (two versions side by side).

Run them against your local stack

The files need a running API. Start it, wait, run the tests, stop it. With Flisk and services declared as local processes:

#!/usr/bin/env bash
set -euo pipefail

cleanup() { flisk down || true; }
trap cleanup EXIT

flisk up --wait --wait-timeout 300
hurl --test --variable base=http://localhost:4000 tests/*.hurl

flisk up --wait returns when every service is healthy and exits 1 on failure or timeout, so the script does not start requests against a service that is still booting. Take the real port from the service's service.json or from the URLs flisk up prints. If the API needs data, create it in the test itself (the first request above does) or run a seed command first (seeding a local database). The same script works in CI; see running a stack in GitHub Actions.

What to put in these files

  • Smoke tests: every endpoint returns the right status and content type. Cheap and catches most breakage.
  • Flows: the three or four sequences users really do (sign up, create, pay), chained with captures.
  • Error cases: an invalid body gets 422, a missing item gets 404, and the body matches your error format (problem details).
  • Headers that are contract: pagination cursors, deprecation and sunset headers (deprecation).

Keep secrets out of the files. Pass tokens with --variable token=$TOKEN or an environment variable that starts with HURL_, and reference {{token}} in a header.

Organize the files

A layout that stays readable as the suite grows: one folder per area (tests/orders/, tests/auth/), one file per flow, and a name that says what the flow proves, such as create-and-cancel-order.hurl. Keep the smoke tests in their own folder so you can run them alone with a single glob before a push, and run the slower flows in CI. Hurl also has options for retrying a request and for waiting until a condition holds, which helps with endpoints that become correct a moment after a write, for example a search index or a queue consumer. Check the documentation of your installed version for the exact option names.

Review the files like code. A pull request that adds an endpoint should add or change a .hurl file in the same diff, and a reviewer can read the new expectations in plain text without opening an app.

Pitfalls

  • Not a load tester. Hurl runs sequentially and checks correctness. Use a dedicated tool for performance.
  • Tests that depend on leftover data. Create what you read. A file that assumes order 1 exists passes once and fails on a fresh database.
  • Brittle assertions. Do not assert a whole body with timestamps or generated IDs. Assert the fields that matter.
  • Syntax across versions. Older Hurl releases wrote the status as HTTP/1.1 200. Check the documentation of the version you install.

When you also need to prove a consumer's expectations rather than your own, add a contract test: Pact walkthrough.

Questions people ask

How is Hurl different from curl?

Curl sends one request. Hurl runs a sequence of requests from a file, captures values between them and asserts on the responses, with a pass or fail exit code.

Can Hurl share variables across requests?

Yes. Use [Captures] to save a value from a response and reference it with {{name}} in later requests of the same file.

Can I run the same Hurl files against different environments?

Yes. Put the base URL in a variable and pass --variable base=... on the command line.
