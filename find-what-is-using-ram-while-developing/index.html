How to find what is using your RAM while developing

Free memory is a misleading number. Memory pressure, resident size per process and swap tell you what is really going on.

To find what is using your RAM, sort processes by resident memory, then check memory pressure and swap to see whether the total is actually a problem. On a Mac use Activity Monitor or top -o mem; on Linux use ps sorted by RSS; for containers use docker stats. A full memory bar alone means little, because the system uses spare RAM for caches on purpose.

Read the numbers before you hunt

Operating systems fill unused RAM with file caches. That memory is handed back the moment a program asks for it, so "used" looks high on a healthy machine. Three signals matter more:

  • Memory pressure on macOS. The graph in Activity Monitor stays green when the system copes, turns yellow when it works hard to free pages and red when it cannot keep up.
  • Swap used. A few hundred MB of swap is normal. Several GB that keeps growing while you work means programs are being pushed out to disk and everything gets slower.
  • Compressed memory on macOS. A large compressed figure means the system is already squeezing pages to avoid swapping.

On the command line, macOS gives you these:

memory_pressure
vm_stat
sysctl hw.memsize

memory_pressure prints the free percentage and the current pressure level, vm_stat shows page counts and hw.memsize is your installed RAM in bytes. On Linux, free -h shows the same idea: look at the "available" column, not "free".

List the biggest processes

Sort by resident set size (RSS), the physical memory a process holds right now. On macOS:

top -o mem -l 1 -n 15 -stats pid,command,mem
ps -A -o pid,rss,command -m | head -15

On Linux:

ps aux --sort=-rss | head -15

The RSS column is in kilobytes. Expect these usual suspects on a developer laptop: browsers with many tabs, the editor and its language servers, one Node or Python process per service, the Docker or Colima virtual machine, and database servers.

Two traps. First, several processes can share pages, so adding up RSS overstates the total a little. Second, one program often shows up as many rows (a browser has one process per tab, an editor has several helpers). Group by program name when you read the list, or use the grouped view in Activity Monitor.

Containers are one big process from the outside

With Docker Desktop, Colima or Podman on a Mac, every container lives inside one virtual machine, and the host sees a single large process for all of them. The VM has a fixed memory size you chose in its settings. To see which container uses what inside it, ask the engine:

docker stats --no-stream

This prints one row per running container with its current memory use and limit. A container with no limit can grow until the VM is full. If the VM itself is too big for your machine, the settings pages of your runtime are where you shrink it. The Colima side is covered in Docker on a Mac with Colima.

Cut the list down

Once you know the top five, the usual fixes are:

  1. Quit what you do not use. A second browser profile or a forgotten IDE window can hold gigabytes.
  2. Stop services you are not working on. A service that is not running costs nothing.
  3. Run code you edit all day as a plain process, and keep only the awkward parts in containers, so the VM can be small.
  4. Put a memory limit on containers so a leak stops at a known size instead of eating the VM.

For the third point, Flisk runs any service that has a command in its service.json as a local process, with no Docker involved. A project of such services starts with flisk up and flisk status lists each one as ready, restarting or not running, so you can tell what is alive before you reach for top. For the second point, a service with "profiles": ["admin"] is left out of flisk up unless you ask for it with flisk up --profile admin, which keeps heavy extras off by default.

Pitfalls

  • Do not kill a process because its number looks big. Check that memory pressure is actually yellow or red and swap is growing first.
  • A Node process that hits its heap limit crashes with an out of memory error; that is a different problem from the machine running low, and the fix is not more RAM.
  • Measure while the machine is slow, not afterwards. Memory often looks fine once the stuck program has been killed.

Next, decide which of the heavy items you can drop for good. The article on running many services on one laptop shows a way to budget memory per service, and setting memory and CPU limits on a container covers the cap.

Questions people ask

Is it bad if my Mac shows almost no free memory?

Not by itself. macOS uses spare RAM as a file cache and releases it on demand. Look at the memory pressure graph and at swap used instead.

Which command shows the biggest memory users on macOS?

Run top -o mem -l 1 -n 15 -stats pid,command,mem, or sort the Memory tab of Activity Monitor.

Why does one container not show up in Activity Monitor?

Containers run inside one virtual machine, so the host sees the VM as a single process. Use docker stats to see each container.
