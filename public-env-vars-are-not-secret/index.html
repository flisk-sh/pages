Env vars and secrets in local dev

VITE_ and NEXT_PUBLIC_ env vars are public: keep secrets out

The prefix is a promise to the bundler that the value may be shown to everyone. Anything else belongs on the server.

Any variable with the VITE_ or NEXT_PUBLIC_ prefix is written into the JavaScript that every visitor downloads. It is public by design, so only put values in it that you are happy to publish, such as a public API URL or a publishable key. A secret key must stay on a server and be reached through your own backend.

How the leak happens

Frontend tools protect you by default: Vite only exposes variables that start with VITE_, and Next.js only exposes those that start with NEXT_PUBLIC_. The prefix is the opt-in. The mistake is adding it to make something "work" in the browser, such as VITE_OPENAI_API_KEY or NEXT_PUBLIC_STRIPE_SECRET. At build time the bundler replaces import.meta.env.VITE_OPENAI_API_KEY with the literal string. The key is now in the JavaScript, and anyone can read it from the browser's network tab or by searching the built files. Minification does not hide it.

What is safe to expose:

  • A public base URL for your API.
  • Publishable keys meant for browsers, such as a Stripe publishable key (pk_), a map tile token with a domain restriction, or an analytics site ID.
  • Feature flags that are not sensitive.

What is not safe: secret or restricted API keys, database URLs, signing secrets, service account files, and anything that starts with sk_ or carries a password in a URL.

The fix: move the call to the server

When the browser needs something that requires a secret, it should call your own backend, and the backend adds the secret:

  1. The frontend calls POST /api/summarize on your backend.
  2. The backend reads OPENAI_API_KEY from its own environment, with no prefix.
  3. The backend calls the provider and returns only the result.

In Next.js you can do this in a route handler or server action. In a Vite single-page app you need a separate backend, which is also the place to add rate limits and per-user checks. A "backend for frontend" is usually a few dozen lines.

If a secret already shipped in a bundle, rotate it. Redeploying without the key does not help, because old bundles may be cached or saved. The steps are in what to do after leaking a secret.

How Flisk helps

Flisk's flisk doctor includes a warning-only check for this. It reads the project's env files (.env, .env.local, .env.*) and warns when a NEXT_PUBLIC_* or VITE_* value looks like a credential. It recognises Stripe secret keys (sk_live_, sk_test_), AWS keys (AKIA), GitHub tokens (ghp_), Slack tokens (xoxb-), OpenAI keys (sk-proj-), Google API keys (AIza), private keys, JWTs and URLs with embedded credentials. Publishable keys (pk_live_, pk_test_, publishable_, pubkey_) and documentation placeholders such as sk_test_x do not trigger it. The output names the variable and the file, never the value:

flisk doctor

It is a pattern check, not a proof. A secret in a format it does not know passes silently, so use it as a net, not a guarantee.

The safer layout in a Flisk project keeps the secret in the backend's service.json, by name, with the value in the gitignored .env:

{
  "appName": "summarizer-api",
  "appType": "backend",
  "secrets": { "required": ["OPENAI_API_KEY"] }
}

The frontend gets only what Flisk generates for it, such as VITE_API_URL pointing at the backend route, plus a VITE_<NAME>_API_URL for each backend in its dependsOn. After changing a frontend variable, run flisk restart <frontend>, because the value is read when the dev server or build starts.

Pitfalls

  • Test keys are still keys. A sk_test_ key is limited to test mode, but it allows actions on your test account, and Flisk's check flags it for that reason.
  • Source maps and server logs. Check that a secret does not reach the browser through an error message or a source map.
  • Restricting a key helps. A browser key limited by HTTP referrer or origin is far safer than an unrestricted one, but anyone can still copy the header, so do not rely on it for anything costly.
  • Do not rename to hide it. Dropping the prefix makes the variable undefined in the browser. That is the protection working, not a bug to patch.

To keep the rest of your configuration safe, read keeping env var names, not values, in config.

Questions people ask

Is it safe to put an API key in a NEXT_PUBLIC_ variable?

Only if the key is meant to be public, such as a publishable key. Anything with secret power is copied into the browser bundle and visible to every visitor.

How do I call an API that needs a secret from a Vite app?

Call your own backend and keep the key there in an unprefixed environment variable. The backend calls the provider and returns the result.

Does flisk doctor catch secrets in VITE_ variables?

It warns when a VITE_ or NEXT_PUBLIC_ value matches known credential formats such as Stripe secret keys or AWS keys. It reports the name and file, not the value, and cannot catch unknown formats.
