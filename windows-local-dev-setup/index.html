Local development on Windows with WSL2: setup that works

Windows can run a full container stack, but only through Ubuntu on WSL2. Native Windows runs local-process projects.

On Windows, run container-based local development inside Ubuntu on WSL2, with Docker Desktop's WSL integration turned on. Native Windows works too, but only for projects whose services declare a command and run as local processes. That split is the main thing to decide before you install anything.

Pick the mode

  • Native Windows. Runs local-process projects, flisk demo, the flisk doctor inspection and flisk up --dry-run. A Docker stack is refused with the message Landscape startup needs Ubuntu on WSL2. Native Windows runs only services that declare a command, as local processes.
  • WSL2 with Ubuntu and Docker Desktop. Runs the full Docker and Tilt stack. This is the path for most teams.

If your services are plain Node or Python processes, the native path is the lighter one. For containers, continue below.

Step by step

  1. Install Ubuntu on WSL2. In an administrator PowerShell run wsl --install -d Ubuntu, then restart if asked and create your Linux user.
  2. Install Docker Desktop and open Settings, Resources, WSL Integration. Enable your Ubuntu distribution. Without this, docker inside Ubuntu is missing or points nowhere.
  3. Install Tilt inside Ubuntu with the project's script: curl -fsSL https://raw.githubusercontent.com/tilt-dev/tilt/master/scripts/install.sh | bash. Piping a script into a shell is a trust decision, so read it first if your policy requires that.
  4. Install Node 22.12 or newer in Ubuntu, with your usual version manager.
  5. Install Flisk in Ubuntu: curl -fsSL https://flisk.sh/install.sh | sh, or the npm package @flisk-sh/flisk.
  6. Set line endings: git config --global core.autocrlf input. Run it in Ubuntu and, if you also use Git for Windows, there as well.
  7. Clone under your Linux home, for example ~/work, not under /mnt/c.
  8. Check the machine: flisk doctor --strict.

A PowerShell helper, setup-wsl.ps1, exists in the project for the WSL part of this. Read it before running it, as with any script.

Why the two traps matter

Files on /mnt/c. The Windows drive is mounted into Linux through a translation layer. File watching and file access are slow there, and live reload suffers. Flisk's doctor warns about a project under /mnt/c, and --strict turns that warning into a failure. Keep the clone in the Linux filesystem and open it from Windows editors through the WSL integration of your editor.

Line endings. A shell script checked out with Windows line endings fails inside a Linux container with an error that mentions a missing file or an odd character. The cause is the carriage return at the end of the first line. core.autocrlf input keeps files as they are in the repository. Doctor checks this setting and warns if it is wrong.

Ports and URLs

A non-root user on Linux cannot bind ports 80 and 443 here, so Flisk falls back to the 8080 to 8180 range. URLs carry the port. A health check looks like http://api.myproject.localhost:8080/api/orders/health, where the port is the one printed by flisk up or flisk networks. Always copy the URL from that output instead of assuming a port, because the numbers can differ between projects and machines.

Check that it works

After flisk doctor --strict passes, start the project with flisk up and open one URL from its output. Then run flisk status to see every resource and its health. If a service is red, flisk logs --service name shows its output. Do this once on a new machine before you declare the setup done, and write the result in the project README so the next person can compare. If the first start fails, fix the cause and run flisk doctor again instead of retrying blindly, since doctor names the failing check and often the fix.

Pitfalls

  • Docker command not found in Ubuntu. The WSL integration toggle for that distribution is off.
  • Everything is slow. The project sits on /mnt/c. Move it.
  • Two Docker setups. If you also installed Docker Engine inside Ubuntu, you now have two daemons. Use one.
  • Corporate laptops. Virtualization may be disabled, and a proxy or private registry is not documented as supported. Ask IT before you plan on it.

When not to use this path

If your team has no containers and your services run as plain processes, skip WSL2 and use the native mode. If your policy forbids Docker Desktop, the Windows container path above is not available to you, and you should look at what your team can run instead of forcing it.

Next step: run flisk doctor --strict in Ubuntu and fix what it reports. Then share the result with the team as part of day-one onboarding, and compare container runtimes in Docker Desktop vs Colima vs Podman.

Questions people ask

Can I run a Docker stack on native Windows?

No. Native Windows runs services that declare a command as local processes. Docker stacks need Ubuntu on WSL2 with Docker Desktop.

Where should the repository live?

In the Linux home inside WSL2, for example ~/work. Projects under /mnt/c are slow and doctor warns about them.

Which git setting should I change?

Run git config --global core.autocrlf input so shell scripts keep Linux line endings.
