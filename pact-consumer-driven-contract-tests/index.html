Consumer-driven contract testing with Pact: a walkthrough

Contract tests let the service that calls an API say what it needs, and let the API team check that before they ship.

With Pact, the consumer (the service or frontend that calls an API) writes a test that records the requests it makes and the responses it needs. That produces a JSON file, the pact. The provider (the API) then replays the file against its real code and fails its own build if it can no longer satisfy a consumer. Neither side needs the other running during its own tests.

When Pact is worth the effort

Pact fits when you cannot easily test the two sides together: several consumers owned by different teams, a mobile app that cannot be updated in lockstep, or services in separate repositories. It answers one question exactly: "will this change break anyone who calls me, and who?" For one frontend and one backend in a single repository, a shared OpenAPI file with a diff check is cheaper (see keeping a contract in sync and breaking-change detection). Pact checks only what consumers actually use, so it will not flag an unused field you remove, which is both its strength and its limit.

Step 1: the consumer test

Using @pact-foundation/pact in the consumer's test suite, you describe an interaction and run your real client code against a mock provider that Pact starts for you:

import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import { getOrder } from '../src/orders-client';

const provider = new PactV3({ consumer: 'web', provider: 'orders-api', dir: './pacts' });

test('fetches an order', async () => {
  provider
    .given('order o_1 exists')
    .uponReceiving('a request for order o_1')
    .withRequest({ method: 'GET', path: '/orders/o_1' })
    .willRespondWith({
      status: 200,
      headers: { 'Content-Type': 'application/json' },
      body: { id: MatchersV3.string('o_1'), status: MatchersV3.string('paid') },
    });

  await provider.executeTest(async (mock) => {
    const order = await getOrder(mock.url, 'o_1');
    expect(order.status).toBe('paid');
  });
});

Two things matter here. The test calls your real client function, so the pact records what the client really sends. And MatchersV3.string asserts the type, not the exact value, so the provider is free to return any string. Match loosely: assert only the fields your code reads. Running the test writes pacts/web-orders-api.json.

Step 2: verify against the provider

The provider's team runs the pact against the real service. Start the service, then run a verifier from the provider's test code:

import { Verifier } from '@pact-foundation/pact';

await new Verifier({
  provider: 'orders-api',
  providerBaseUrl: 'http://localhost:4000',
  pactUrls: ['./pacts/web-orders-api.json'],
  stateHandlers: {
    'order o_1 exists': async () => { await insertOrder({ id: 'o_1', status: 'paid' }); },
  },
}).verifyProvider();

The given(...) text from the consumer test is the provider state. Each one needs a handler that puts the data in place, usually by inserting rows into the provider's test database. State handlers run in the verifier process, so they need access to the same database the service uses, or a test-only endpoint in the service.

With Flisk, the provider is an ordinary service with a command and a port in its service.json, and a script starts it and waits:

flisk up --wait --wait-timeout 300
npx jest provider-verify
flisk down

flisk up --wait returns once the services are healthy (or exits 1 on failure or timeout), and flisk down stops them. Use a trap so the stack is stopped when the test fails, as in integration tests against the real stack. If the provider needs a database, keep it in the same project, and seed it from the state handlers.

Step 3: share the pact

A file on one laptop is not a workflow. Consumers must publish pacts somewhere the provider's CI can fetch them. Options are a Pact Broker (open source, or the hosted PactFlow) or, for a small setup, a shared repository folder. A broker adds the key tool, can-i-deploy, which answers whether a given version of a service is compatible with the versions in production. Without a broker you still get the safety net, but the version bookkeeping is on you.

Pitfalls

  • Over-specifying. If the consumer asserts every field with an exact value, the provider cannot change anything. Use matchers and include only fields the client reads.
  • Provider states that lie. A handler that does not create the data the interaction names makes the verification pass or fail for the wrong reason. Keep states small and named in plain language.
  • Treating it as end-to-end testing. Pact verifies shapes and basic behavior of one interaction. It does not test business flows across services (Playwright against the stack does).
  • Library versions. Pact's JavaScript API changed across major versions. Follow the documentation for the version you install, and pin it.

If a contract test fails because the response really needs to change, do not edit the pact by hand. Version the endpoint instead (two versions side by side).

Questions people ask

What is the difference between a contract test and an integration test?

An integration test runs real services together. A contract test checks each side separately against a recorded agreement, so it is faster and does not need both services running at once.

Do I need a Pact Broker?

Not to start. You can pass pact files directly. A broker adds version tracking and can-i-deploy, which matter once several teams publish pacts.

Does Pact replace OpenAPI?

No. OpenAPI describes the whole API. Pact records what specific consumers use. Many teams use both.
