Fix 'Resource not accessible by integration' and Missing Secrets in CI

Why a workflow fails with permission errors or empty secrets, and how to fix GITHUB_TOKEN permissions, fork pull requests and environment secrets.

The error 'Resource not accessible by integration' means the GITHUB_TOKEN of that run lacks the permission the step needs. Add the minimum permission under permissions: in the workflow, for example pull-requests: write to comment on a PR. Empty secrets usually mean the run came from a fork or the secret lives in a different scope.

Give the token only what the job needs

Each run gets a temporary token. Its default permissions depend on repository and organisation settings, and many are read-only. Declare permissions in the workflow so the job does not depend on the default.

permissions:
  contents: read
  pull-requests: write

jobs:
  comment:
    runs-on: ubuntu-latest
    steps:
      - run: gh pr comment ${{ github.event.pull_request.number }} --body 'Checked'
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

When you set permissions, every permission you do not list becomes none. That is good for security, and it is also why a step that worked before suddenly fails after you add the block. Read the error, find which API call failed and add that one permission.

Pull requests from forks

For the pull_request event on a fork, the token is read-only and repository secrets are not available. That protects you from code you have not reviewed. So a comment bot or a deploy preview fails with a permission error only on fork PRs.

The pull_request_target event runs with write access and secrets, in the context of the base branch. It is dangerous if it checks out and runs the fork's code. Do not do that. Safer patterns split the work: run untrusted code in a pull_request workflow with no secrets, upload the result as an artifact, and let a second workflow with the workflow_run trigger read the artifact and post it. See GitHub Actions Security.

Empty or missing secrets

A secret that expands to an empty string does not raise an error by itself. Check for these causes:

  • The name has a typo. Names are case insensitive but must match.
  • The secret is set at the organisation level and not shared with this repository.
  • The secret belongs to an environment, and the job does not declare environment: name.
  • Dependabot runs use their own secrets store, separate from Actions secrets.
  • The run is a fork PR.

Fail early with a clear message:

- name: Require token
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}
  run: test -n "$API_TOKEN" || { echo 'API_TOKEN is empty'; exit 1; }

Other permission errors

A 403 on package publish usually means the token needs packages: write. OIDC login to a cloud provider needs id-token: write. A push from a workflow needs contents: write, and a protected branch may still reject it. A rejected push with a valid token points to branch protection, not the token. Pushes made with GITHUB_TOKEN also do not trigger new workflow runs, which surprises people who expect a chain. Check the GitHub documentation for the exact behaviour of your case.

Debug it step by step

Find the failing API call in the log, look up the permission it needs, add it, and re-run. Do not widen to write-all to make the error go away. If you cannot tell which call failed, enable debug logging and read the request lines.

Questions people ask

Why do secrets work on my branch but not on a fork pull request?

GitHub does not pass repository secrets to workflows triggered by pull requests from forks, to protect against untrusted code.

Is permissions: write-all a good fix?

No. It grants every write permission to the token. Add only the specific permission the failing call needs.
