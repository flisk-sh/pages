How to stop overselling stock when two customers check out

Overselling is a race condition, not a business rule. Make the database refuse the second sale and prove it with a test that fires two requests at once.

Updated

Stop overselling by letting the database decide who gets the last unit. Use one atomic statement, UPDATE ... SET on_hand = on_hand - 1 WHERE sku = $1 AND on_hand >= 1, and treat "zero rows updated" as "out of stock". Reading the stock count in your code and writing it back later is the pattern that oversells, because two requests can both read 1.

Why the read-then-write version fails

The broken version looks harmless:

const { on_hand } = await db.one("SELECT on_hand FROM inventory WHERE sku = $1", [sku]);
if (on_hand >= qty) {
  await db.none("UPDATE inventory SET on_hand = $2 WHERE sku = $1", [sku, on_hand - qty]);
}

Two requests arrive within a few milliseconds. Both read on_hand = 1, both pass the check, both write 0. You sold two items and have one. It never fails in a demo with one user, and it fails the first day of a real sale. The fix is to move the check into the write.

One guarded statement

Put the condition in the WHERE clause. Postgres locks the row for the duration of the update, so the second request waits, re-checks the condition against the new value and matches no row:

UPDATE inventory
SET on_hand = on_hand - $2
WHERE sku = $1 AND on_hand >= $2;

Check the affected row count in your driver. One means you got the stock, zero means you did not. Add a second line of defence in the schema, so a bug elsewhere cannot push the count below zero:

ALTER TABLE inventory ADD CONSTRAINT on_hand_not_negative CHECK (on_hand >= 0);

An order has several lines, so do all the decrements in one transaction and roll back if any line fails. Update the rows in a fixed order, for example sorted by SKU. Two carts that touch the same SKUs in different orders can otherwise deadlock; Postgres will abort one of them, and your code should be ready to retry once.

Reserve first, commit later

Decrementing at the moment the customer clicks "Place order" is fine when payment happens in the same request. When the customer has to pay on another page, you need a hold: the stock is taken but the order is not final. A small table does it:

CREATE TABLE reservations (
  id          bigserial PRIMARY KEY,
  order_id    bigint NOT NULL,
  sku         text   NOT NULL,
  qty         int    NOT NULL CHECK (qty > 0),
  expires_at  timestamptz NOT NULL,
  released_at timestamptz
);

Available stock is on_hand minus the sum of active reservations. To keep that race-free, take the reservation inside a transaction that first locks the inventory row with SELECT ... FOR UPDATE, computes availability, and inserts only if enough is free. Alternatively keep a second counter, reserved, on the inventory row and update it with the same guarded pattern: SET reserved = reserved + $2 WHERE sku = $1 AND on_hand - reserved >= $2. The counter is simpler to read, the table is simpler to audit. Pick one and do not mix them. Releasing expired holds is its own job, covered in expiring unpaid orders.

Run it on your laptop with Flisk

You only need an API and a Postgres database. Install with npm install -g @flisk-sh/flisk, then in a project folder:

flisk project --yes
flisk resource shop-db --type database --stack shop --yes
flisk resource orders-api --type backend --stack shop --feature drizzle --yes

The database resource names the shared Postgres that Flisk runs for the project. Edit services/shop/orders-api/service.json and add "dependsOn": ["shop-db"], so the database starts first and the API gets a DATABASE_URL. The Drizzle scaffold already contains a src/db.ts that reads that variable. Start the stack with flisk up shop. If you are not sure the variable arrived, print it from inside the service:

flisk run orders-api -- printenv DATABASE_URL

Put the table definitions in your migrations (see migrations in local dev), not in the API's start script.

Prove it with a race test

A fix you have not tested is a guess. Seed one SKU with on_hand = 1, then fire many purchase requests at the same moment and count the winners. Save this as race-test.ts:

const url = process.env.API_URL ?? "http://localhost:4000";
const results = await Promise.all(
  Array.from({ length: 20 }, () =>
    fetch(`${url}/orders`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ sku: "MUG-01", qty: 1 }),
    }).then((r) => r.status)
  )
);
const ok = results.filter((s) => s === 201).length;
console.log({ ok, rejected: results.length - ok });
if (ok !== 1) process.exit(1);

Run it from your machine against the API address that flisk networks --stack shop prints, for example API_URL=http://api.myproject.localhost:8081/api/orders-api bun race-test.ts (use your own project name and port, and adapt the route to your handler). A passing run prints ok: 1. Run it against the broken version once, to see it fail, and you will trust the test.

Pitfalls

  • Connection pool of one. If your local pool allows a single connection, requests queue up and the race never happens. Use a pool of at least 5 in the test, or you test nothing.
  • Cached stock on the product page. Showing "3 left" is a hint, not a promise. Always enforce on write.
  • Stock in two places. If a search index also holds counts, treat it as display data only.
  • Do not lock the whole table. Row-level locking on the SKU is enough and keeps unrelated orders moving.

When the stock logic is solid, the next question is how an order moves from "reserved" to "paid" to "shipped without a mistake"; see modelling order statuses as a state machine.

Questions people ask

Do I need a message queue to avoid overselling?

No. A guarded UPDATE or a row lock in one Postgres transaction is enough for most shops. A queue helps with throughput at very high volume, but it does not replace the check.

Is SELECT FOR UPDATE better than the guarded UPDATE?

The guarded UPDATE is shorter and holds the lock for less time. Use SELECT FOR UPDATE when you must read several rows and decide in code before writing.

How do I test this locally?

Seed one item with a stock of one, send twenty purchase requests at the same instant, and assert that exactly one succeeds.
