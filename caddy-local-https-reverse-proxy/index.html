Local URLs, routing and HTTPS

How to run Caddy as a local HTTPS reverse proxy

Caddy issues and renews local certificates by itself. You write the routes, it does the TLS.

To run Caddy as a local HTTPS reverse proxy, write a Caddyfile with one site block per host name, add tls internal, and point reverse_proxy at your service's port. Caddy creates a local certificate authority, issues certificates for the names you list, and serves them over HTTPS. Run caddy trust once so your system trusts that authority.

A minimal Caddyfile

Install Caddy (brew install caddy on macOS, or your package manager). Then create a Caddyfile:

app.shop.localhost {
  tls internal
  reverse_proxy localhost:3000
}

api.shop.localhost {
  tls internal
  reverse_proxy localhost:4000
}

Run it and trust the local authority:

caddy trust
caddy run --config Caddyfile

caddy trust installs Caddy's root certificate in the system store (it may ask for your password). After that, https://app.shop.localhost and https://api.shop.localhost show a padlock. Caddy listens on ports 80 and 443, redirects HTTP to HTTPS, and sets the X-Forwarded-* headers for your upstream.

Caddy picks an internal certificate on its own for localhost and IP addresses, but writing tls internal makes the intent clear for any other name.

One host, several services

You can also put everything behind a single name and split by path, which keeps cookies first-party and avoids CORS:

shop.localhost {
  tls internal
  handle_path /api/* {
    reverse_proxy localhost:4000
  }
  handle {
    reverse_proxy localhost:3000
  }
}

handle_path removes the matched prefix before proxying, so the API sees /orders, not /api/orders. Use plain handle if your API expects the prefix. WebSocket upgrades pass through reverse_proxy without extra settings.

Using Caddy with Flisk

Flisk does not configure TLS itself (its printed URLs are http://), so Caddy sits in front of what Flisk starts. Which port you proxy to depends on how the project runs:

  • Local processes (every service has a command). Flisk prints http://localhost:<port> for each service. Point reverse_proxy at those ports, as in the Caddyfile above.
  • Docker and Tilt. Flisk starts Traefik and tries to publish it on host ports 80 and 443. If you also want Caddy on 80 and 443 you will hit a conflict, which is the usual "port already in use". Run Caddy on other ports, for example app.shop.localhost:9443 as the site address, and proxy to the HTTP ingress port that flisk networks prints. Caddy passes the original Host header upstream by default, which Traefik needs to pick the right route.
app.shop.localhost:9443 {
  tls internal
  reverse_proxy localhost:80
}

Replace localhost:80 with the ingress port from flisk networks if Flisk fell back to 8080 or another port. If Flisk had to fall back to ports above 1024, nothing stops Caddy from using 443.

Run it every day without friction

Keep the Caddyfile in your repository root, or in a folder of developer tooling, and start it with caddy run --config Caddyfile in a spare terminal. Use caddy start to run it in the background and caddy stop to end it. After you edit the file, caddy reload --config Caddyfile applies the change without dropping connections, and caddy validate --config Caddyfile catches typos before you reload.

Format the file with caddy fmt --overwrite Caddyfile, because Caddy is strict about indentation and braces. If a site does not answer, run Caddy in the foreground and read its log: it prints one line per request with the upstream, the status and the duration, and a failed connection to your service shows as a dial tcp error that names the port it could not reach. That error nearly always means your service is not running yet, or it listens on a different port than the one in the file.

Every developer on the team can run the same Caddyfile, because the certificates are created per machine and the file contains only names and ports. Commit the file, and let each person run caddy trust once.

Pitfalls

  • The upstream still sees HTTP. Your app may build absolute links or redirects with http://. Read the X-Forwarded-Proto header, or configure the framework's trusted proxy setting. See the forwarded headers article.
  • Containers calling the HTTPS name. They do not trust Caddy's root, and localhost inside a container is the container itself. Call the service over the internal network instead.
  • Trust only on your machine. Caddy's root key lives in its data directory. Do not copy it to other computers.
  • Another process holds 443. Caddy will fail to start. Find the owner with lsof -iTCP:443 -sTCP:LISTEN.
  • Prefer mkcert plus nginx? That works too. Caddy is simply less work because it handles certificates itself.

For the certificate side by itself, read trusted HTTPS on localhost with mkcert. For the header details your upstream needs, see forwarded headers behind a local proxy.

Questions people ask

What does tls internal do in Caddy?

It tells Caddy to issue the certificate from its own local certificate authority instead of asking a public CA such as Let's Encrypt. Run caddy trust so your system accepts that authority.

Can Caddy and Flisk run at the same time?

Yes, if they do not fight over ports. In the Docker path Flisk's Traefik prefers host ports 80 and 443, so run Caddy on different ports, or proxy to the ports of local-process services.

Do I need to change my app to use Caddy?

Usually not. Your app keeps serving plain HTTP. Check that it respects X-Forwarded-Proto if it builds absolute URLs or redirects.
