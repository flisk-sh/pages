npm, pnpm, Yarn or Bun for local development: which to pick

Package managers differ less than their pages suggest. What hurts teams is using two at once.

Pick one package manager per repository and enforce it. npm is the safe default because it ships with Node. pnpm is a good choice for monorepos and for laptops with many projects, because it stores each package once on disk. Yarn and Bun are fine when the team already uses them. The choice matters less than having exactly one lockfile.

What actually differs

ToolLockfileWhere it is strongWhat to watch
npmpackage-lock.jsonComes with Node, works everywhere, workspaces supportedA full copy of each package in every project
pnpmpnpm-lock.yamlShared content store, strict node_modules, good workspace filtersStrictness exposes code that imports packages it never declared
Yarnyarn.lockMature workspaces, plugin system in current versionsClassic (1.x) and the current line behave differently, so check which one you have
Bunbun.lockInstaller, runner and test tool in one binaryNot every package works the same under the Bun runtime, so confirm your stack

Speed differs, but it depends on your cache state, network and project. Run each tool on your own repository before you believe a number from a benchmark page, including this one. A warm cache changes the result more than the tool does.

Pin the choice in the repo

The danger is a teammate who runs npm install in a pnpm project and commits a second lockfile. Corepack helps. It is a small tool that reads the packageManager field and runs that exact version:

{
  "packageManager": "pnpm@9.15.0"
}
corepack enable
pnpm install

Corepack came bundled with Node for a long time, but newer Node lines no longer bundle it, so you may need npm install -g corepack first. Check with corepack --version. You can also block the wrong tool with a preinstall script that runs npx only-allow pnpm. Add a CI step that fails when more than one lockfile exists.

Workspaces and several services

If the repo holds a web app, an API and a shared package, all four tools support workspaces. pnpm's --filter and -r options, and npm's -w flag, let you run one script in one package: pnpm --filter api dev or npm run dev -w api. For layouts with many services, see local development setup for a monorepo.

Where Flisk fits

Flisk does not care which tool you use. A local-process service runs whatever you put in command, such as pnpm dev or bun run dev, and it refuses to start when that program is not installed. It does not install dependencies for you, so run your install command first.

How to decide for your team

Ask four questions. Is it a monorepo with several packages? Then pnpm or Yarn workspaces give you filters and a single install at the root. Do people work on many Node projects on one laptop? Then pnpm's shared store saves disk. Does your CI or hosting platform assume one tool, for example a build image that only has npm? Then that tool wins, because you would otherwise fight the platform. Does the team already know one of them well? Keep it. A switch costs a day or two of confusion, and the gain is rarely large enough to pay for that on a small project.

Whatever you choose, write it down in the README and in packageManager, and keep the commands you run (install, dev, test, build) as scripts in package.json, so they have the same names under every tool.

Pitfalls

  • Two lockfiles. If package-lock.json and pnpm-lock.yaml both exist, installs will drift. Delete the extra one and add the rule to CI.
  • Phantom dependencies under pnpm. Code that works on npm because a package was hoisted may fail on pnpm with "Cannot find module". The fix is to add the missing package to package.json, which was a bug anyway.
  • Docker images. Copy the right lockfile and use the matching frozen install command. See npm ci vs npm install.
  • Switching tools late. Migrating is usually an afternoon, but plan it for a quiet week and move the CI cache at the same time.

Next step

Whichever you choose, write the exact install and start commands in the README so a new teammate needs no guesswork. Onboarding on day one has a checklist for that.

Questions people ask

Should I use pnpm instead of npm?

If you have a monorepo or many projects on one laptop, pnpm's shared store and workspace filters are worth it. For one small app npm is fine.

What is the packageManager field for?

It names the package manager and version for the repo. Corepack reads it and runs that exact tool, which keeps the team consistent.

Does Flisk work with pnpm, Yarn or Bun?

Flisk runs the command you write, so it works with any of them as long as the program is installed. It does not install dependencies.
