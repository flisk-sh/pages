How to check a dev tool for lock-in before you adopt it

Lock-in is rarely about the code. It is about which files you would have to rewrite on the day you leave, so test that day first.

To check a dev tool for lock-in, split your repository into what you wrote and what the tool wrote, then ask what a standalone version looks like. With Flisk, your source code and your own Dockerfiles stay yours. The exit is flisk export compose, which writes a standalone docker-compose.yml. You lose the conveniences the tool added, and you should know which ones before you start.

What lock-in means for a local dev tool

A local dev tool has three layers. Your application code and Dockerfiles are the first layer, and they belong to you. The manifests that describe your services are the second layer, and they are tool-specific. The behavior the tool provides while it runs (ordering, routing, reloading) is the third layer, and it exists only while the tool does. Lock-in is the cost of replacing layers two and three.

Ask three questions. Can I run the app without the tool? Can I get a standard file out of it? How long would the replacement take? A tool that answers the first two well and is honest about the third is safe to try.

Why eject is not the exit

The word suggests a clean exit, so be precise. In Flisk, flisk eject writes a single file, EJECTED.md. It copies nothing and generates nothing, and it does not produce a plain Compose setup. Do not plan your exit around it.

The real exit: export compose

The documented exit is flisk export compose. According to the project's contributor guide, it writes a standalone docker-compose.yml from your service.json files. The file uses bring-your-own resources and runs without Flisk. The export only writes files: it never deploys, never creates DNS records and never calls a cloud API. It writes environment variable names, never values.

flisk export compose . --dry-run
flisk export compose . --out ./exported

The options include --out, --force and --dry-run, and the same command family has render and wrangler targets for Render and Cloudflare Workers config. The command runs a separate package through npx, so the first run needs network access.

I could not run the export on the machine where I wrote this, so I cannot show you its output. Treat the file as a starting point: read it, start it on a clean machine, and compare the behavior with what you have today before you rely on it. A guide on what to check is in export a standalone Compose file.

What you keep and what you lose

Stays with youGoes away
Source codeLive update on file change
Your own DockerfilesStart order from dependsOn
A standalone Compose file from exportGenerated routes and *.localhost URLs
Environment variable namesService discovery and port picking
Your database data, if you keep the volumesflisk doctor and flisk config verify

Be careful with the last row on the left. flisk down --purge deletes the project's Docker volumes, including database data. Never run it as part of an exit unless you have a dump.

Run an exit rehearsal

  1. Create a branch and run the export with --dry-run. Save the list of files it plans to write.
  2. Run it for real into a separate folder, not over your existing Compose file.
  3. On a machine that does not have the tool installed, start the exported stack. Note what breaks.
  4. Write down the manual steps that replace each item in the Goes away column, and how long they took.

This takes an afternoon. It is the cheapest insurance you can buy, and it also tells you whether your own Compose files were good enough to begin with.

When lock-in is acceptable

Some lock-in is fine. If the tool saves each developer an hour a week and the exit costs two days, the arithmetic is simple. What is not fine is not knowing. A tool that cannot show you its exit should not hold your team's setup, and that applies to any tool, not only this one. Also remember what is out of scope: Kubernetes manifests are not generated, so production deployment stays with your own workflow.

Next step: do the rehearsal before the pilot ends, and put the written result next to your adoption notes from adopting a tool gradually.

Questions people ask

Does flisk eject give me a plain Compose file?

No. It writes only EJECTED.md. To get a standalone docker-compose.yml, use flisk export compose.

Does the export put secrets in the file?

No. It writes environment variable names, never values, and it never deploys anything.

What about my database data after leaving?

It lives in Docker volumes. Keep the volumes or dump the data first, and avoid flisk down --purge, which deletes them.
