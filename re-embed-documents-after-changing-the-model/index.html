How to re-embed documents after changing the embedding model

A new embedding model means a new index. Done in the wrong order you get silently bad search, so build beside the old one and switch when it is proven.

When you change the embedding model, every stored vector is out of date, even when the new model has the same number of dimensions. Build a second collection with the new model, run your questions against both, switch the application to the new one when it is at least as good, and only then delete the old one.

Why you cannot mix models

An embedding model defines its own coordinate system. The vector for a sentence from model A and the vector for the same sentence from model B are unrelated numbers. If the dimensions differ, the database rejects the insert with a size error, which is the lucky case. If they match, for example two 768-dimension models, the insert works and search returns confident, wrong results. The same holds for a model version bump, a change of query prefix, or a different normalization setting. Treat all of these as a model change.

A safe procedure

  1. Record the model in the index. Put the model name and dimension in the collection or table name, for example docs_nomic768, or in a metadata record. Future you will need it.
  2. Create a new collection with the new size and distance, for example docs_mxbai1024. Do not touch the old one.
  3. Run ingestion into the new collection. It needs the source documents, which is why they must live in version control or a known folder, not only in the index. See ingesting documents repeatably.
  4. Run your eval set against both collections. Compare hit rate and MRR with the method in testing retrieval quality. A bigger model is not always better on your data.
  5. Switch the application by changing one setting that names the collection and the model together. Both must change at the same moment, or questions get embedded with one model and searched in another model's space.
  6. Keep the old collection for a few days, then delete it.

In pgvector

The column type carries the dimension, so a new model usually means a new column or a new table:

ALTER TABLE chunks ADD COLUMN embedding_v2 vector(1024);
CREATE INDEX ON chunks USING hnsw (embedding_v2 vector_cosine_ops);
-- fill embedding_v2 with the ingestion job, compare, then:
ALTER TABLE chunks DROP COLUMN embedding;
ALTER TABLE chunks RENAME COLUMN embedding_v2 TO embedding;

Keeping the text in the same row means you re-embed from the table itself, without re-reading files. Setup of the database is in running pgvector locally.

With Flisk

Flisk does not manage embeddings or collections, it runs the containers around them. What it helps with is the model server and the storage. Pull the new model into the running Ollama container with flisk run embed -- ollama pull mxbai-embed-large, and if you keep models on a volume, both models stay available while you compare. If you want a completely clean vector store instead of a second collection, stop the stack with flisk down, then remove just that service's volume, found with docker volume ls --filter label=com.docker.compose.volume=vectors-data, and start again. Avoid flisk down --purge for this, since it deletes every volume of the project, including the Postgres data. More on that in keeping vector data between restarts.

Pitfalls

  • Changing only the query side. Updating the model name in the API but not re-indexing gives wrong results without an error.
  • Prefix drift. If your model expects search_document: and search_query: prefixes, changing them is a model change.
  • Cost and time. Re-embedding a big corpus takes real time on a laptop CPU. Do it in batches, keep the job restartable, and test on a sample first.
  • Losing the source. If your only copy of the text is in the index payload, export it before deleting anything.

Build the habit once: a model change is a normal, scripted event, not an incident.

Questions people ask

Can I keep old vectors when I change the embedding model?

No. Vectors from different models are not comparable, even with the same dimension. Re-embed all documents with the new model in a new collection.

What happens if the new model has a different dimension?

The database rejects inserts and queries with the wrong vector size. If the dimension is the same, it will not complain but results will be wrong.

How do I switch without downtime?

Build the new collection beside the old one, test it, then change the collection name and model together in one config setting, and delete the old collection later.
