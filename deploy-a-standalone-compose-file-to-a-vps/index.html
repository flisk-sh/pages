How to deploy a standalone Compose file to a VPS

A small server with Docker is enough for many apps. The export gives you a Compose file with no dependency on your development tool.

To deploy to a single server, export a standalone Compose file with flisk export compose, publish your images to a registry, copy the file and an .env to the server, and run docker compose up -d. Put a reverse proxy such as Caddy in front for HTTPS, and bind application ports to 127.0.0.1 so only the proxy is reachable from outside. The file works without Flisk, so the server never needs it.

The general approach

A VPS with Docker and the Compose plugin is a legitimate production target for small apps and internal tools. The pattern is old and plain: images come from a registry, one Compose file describes the services, an .env holds the values, and a proxy terminates TLS. What goes wrong is the file. A development Compose file uses bind mounts, local build contexts and networks that only exist on your machine. You need a file that refers to pushed images and nothing local.

The Flisk way: export it

The exporter reads service.json files and writes .autogenerated/docker-compose.yml. It covers bring-your-own resources only: services with an image or a Dockerfile, plus their env, secrets.required, volumes, health checks, dependsOn and extraPorts.

flisk export compose --dry-run   # print, write nothing
flisk export compose             # write .autogenerated/docker-compose.yml
flisk export compose --check     # exit 1 if the file is out of date

A trimmed result for an API, a Postgres database and a one-shot migration job looks like this:

name: "shop"

services:
  api:
    image: "ghcr.io/example/api:1.0.0"
    init: true
    restart: "unless-stopped"
    environment:
      DATABASE_URL: "${DATABASE_URL}"
      LOG_LEVEL: "info"
      SESSION_SECRET: "${SESSION_SECRET}"
    ports:
      - "0.0.0.0:4000:4000/tcp"
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully

  db:
    image: "postgres:17-alpine"
    environment:
      POSTGRES_DB: "shop"
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}"
    volumes:
      - "pgdata:/var/lib/postgresql/data"
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "postgres"]
      start_period: "10s"

  migrate:
    image: "ghcr.io/example/api:1.0.0"
    restart: "no"
    command: ["node", "migrate.js"]
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:

Points worth knowing:

  • Each required secret becomes a ${NAME} reference, so a name missing from the server's .env reaches the container as an empty value, with only a warning from Compose. Check that every name appears in the server's .env.
  • A dependency with a health check becomes service_healthy. A job with restart: "no" becomes service_completed_successfully, so migrations finish before the API starts.
  • No ports are published unless you list extraPorts. When a port is published it defaults to 127.0.0.1. A bind: "0.0.0.0" setting opens it to the world, as the api entry above shows, so set it only deliberately.
  • Services need images that exist. Build and push them in CI first, and pin a version tag instead of latest.

Run it on the server

  1. Install Docker Engine and the Compose plugin from Docker's documentation.
  2. Copy the file and your env: scp .autogenerated/docker-compose.yml .env deploy@server:/srv/shop/. Set chmod 600 .env, and use production values, never your laptop's.
  3. Log in to the registry if the images are private, then start: docker compose --env-file .env -f docker-compose.yml up -d.
  4. Check docker compose ps and the logs of the migration job.

To update, change the image tag, run docker compose pull, then repeat the up -d command. Take a database backup before a migration that changes data.

Put HTTPS in front

Caddy gets certificates automatically. A short Caddyfile is enough:

shop.example.com {
  reverse_proxy 127.0.0.1:4000
}

Point the DNS record at the server and run Caddy on the host or as another service. Now the API only needs to listen on 127.0.0.1:4000, so change bind back to the default in service.json.

Pitfalls

  • Docker bypasses ufw. A port published as 0.0.0.0:4000 can be reachable even if your firewall says otherwise, because Docker writes its own iptables rules. Binding to 127.0.0.1 is the dependable fix.
  • Back up the volume. pgdata is the only copy of your data. Schedule a dump and test a restore.
  • Keep the export honest. Run flisk export compose --check in CI so the committed file matches the manifests. See export a standalone Compose file.
  • One server is one failure domain. If you need rolling deploys or several machines, a managed platform is a better fit than more scripts. See from local to Render.
  • Leaving later. The point of a plain file is that nothing locks you in. Leave a tool without lock-in covers it.

Questions people ask

Does the exported Compose file need Flisk on the server?

No. It has no external networks and no Flisk-specific variables. The server needs Docker with the Compose plugin, the file and an .env with the values for the variables the file references.

Which services does flisk export compose include?

Bring-your-own resources, meaning services defined by an image or a Dockerfile. Native services that run as local processes with a command, and other resource types, are not exported.

How do I stop the exported file going stale?

Run flisk export compose --check in CI. It exits 1 when the committed file differs from what the service.json files would produce.
