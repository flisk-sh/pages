Payments and webhooks locally

How to run stripe-mock for offline payment tests

Sometimes you want to know that your code builds a valid Stripe request, not that Stripe charges a card. A local fake answers that in milliseconds.

stripe-mock is a small server from Stripe that answers Stripe API calls from Stripe's own OpenAPI spec. Run its Docker image, point your SDK at localhost:12111, and your code gets valid-shaped responses with no account, no network and no rate limits. It checks that your requests are well formed. It does not remember anything between calls and it does not send webhooks.

What it is good for, and what it is not

The mock validates each request against the spec and returns an example response for that endpoint. That makes it good for three jobs:

  • Catching bad requests. A misspelled parameter or a wrong type returns an error, the same as Stripe would.
  • Fast, offline CI. No secret in the pipeline, no flaky network, no test-account state to clean up.
  • Unit-level tests of your wrapper code that builds line items, handles error shapes or maps statuses.

It is the wrong tool for behaviour. It is stateless, so creating a customer and then fetching that customer does not return the customer you created. It does not run a card network, so there are no declines and no 3D Secure. And it sends no events, so your webhook handler never gets called by it. For those, use Stripe's test mode with the CLI: testing Stripe payments locally.

Running it

docker run --rm -p 12111:12111 stripe/stripe-mock:v0.206.0

Pin a version tag instead of latest, so a spec update does not change your test results on a day you did not touch the code. The server listens for HTTP on 12111 and HTTPS on 12112. A request needs an Authorization header with a test key. The mock accepts sk_test_ followed by letters or digits, and an underscore after that prefix is rejected with a 401, so sk_test_flisklocal works and sk_test_my_key does not. Check it:

curl -s http://localhost:12111/v1/customers \
  -H "Authorization: Bearer sk_test_flisklocal" -d email=a@example.com

Pointing the SDK at it

With the Node SDK, set the host, port and protocol when you build the client:

import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY, process.env.STRIPE_API_BASE
  ? { host: "localhost", port: 12111, protocol: "http" }
  : {});

Reading the base from an environment variable lets the same code talk to the mock in tests and to Stripe elsewhere. Other official SDKs have an equivalent setting for the API base URL. Look for it by name in the SDK's README, because the option differs per language.

Running it with Flisk

Flisk can start the mock next to your API in one command. A ready-made image with no command runs with docker run beside local processes, so Docker must be running, but your own code needs only Node. Install with npm install -g @flisk-sh/flisk. In stripe-mock/service.json:

{
  "schemaVersion": 1,
  "appName": "stripe-mock",
  "appType": "bring-your-own",
  "image": "stripe/stripe-mock:v0.206.0",
  "port": 12111
}

And in api/service.json:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["stripe-mock"],
  "env": {
    "STRIPE_API_BASE": "http://localhost:12111",
    "STRIPE_SECRET_KEY": "${STRIPE_SECRET_KEY:-sk_test_flisklocal}"
  }
}

The :- form gives a default when the variable is unset, so a fresh checkout works without a real key. Check the plan first:

flisk up --dry-run

It prints that it would start two services, with stripe-mock through docker run and api after it. Then flisk up starts both. In this mode the container publishes its port on 127.0.0.1 at the same number, so a local process reaches it at localhost:12111, not by the service name. flisk logs --service stripe-mock shows the mock's request log, which is handy for seeing exactly what your code sent.

If you run your API in a container instead, the Docker network gives the mock a hostname equal to its resource name, http://stripe-mock:12111. Do not mix the two: use localhost for local processes and the resource name for containers.

Pitfalls

  • Trusting a green test. The mock returns example data, so it passes any logic that does not look at the response closely. Assert on what you send, and test business behaviour against test mode.
  • Stale spec. A new Stripe field is unknown to an old mock version. If a new parameter returns an error, bump the pinned tag.
  • Silent fallback. If the base URL variable is empty, the SDK goes to Stripe's real API. Fail the test run when a mock was expected and the variable is missing.
  • Expecting webhooks. There are none. Send your own signed fixtures, as in testing webhooks locally.

The decision of when a fake is enough is covered more generally in mock or run the real service.

Questions people ask

What is stripe-mock?

A server from Stripe that validates requests against the Stripe OpenAPI spec and returns example responses. It runs locally, usually through the stripe/stripe-mock Docker image.

Does stripe-mock send webhooks?

No. It is stateless and only answers API calls. To test a webhook handler, send signed fixture events yourself or use the Stripe CLI in test mode.

Which port does stripe-mock use?

It serves HTTP on port 12111 and HTTPS on port 12112 by default.
