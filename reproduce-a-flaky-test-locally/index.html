Flaky Tests and Flaky CI

How to Reproduce a Flaky Test Locally

Run the suspect test in a loop, in random order, under CPU load and with the CI seed, until it fails on your machine. Commands for pytest, Jest, Go and Playwright.

To reproduce a flaky test, run it many times in a loop, then change one condition at a time: order, parallelism, CPU load, seed and clock. A failure you can trigger on demand is a failure you can fix.

Run it alone, many times

First answer one question: does it fail by itself? Loop the single test.

# Go
go test -run TestJobFinishes -count=200 ./...

# pytest (pip install pytest-repeat)
pytest tests/test_jobs.py::test_job_finishes --count=200

# Playwright
npx playwright test jobs.spec.ts --repeat-each=50

# anything else
for i in $(seq 1 200); do npm test -- -t 'job finishes' || break; done

If it fails alone, you have a timing or nondeterminism problem inside the test. If it never fails alone, suspect order or shared state.

Run it with the rest of the suite

If it only fails in the full run, another test is leaking state. Randomize order and note the seed so you can replay it.

# pytest with pytest-randomly prints a seed
pytest
pytest -p randomly --randomly-seed=12345

# Go
go test -shuffle=on ./...

The runner prints the seed when it shuffles. Copy it from the CI log and run with the same one. Check your runner's docs for the exact flag, since names differ.

Make your machine behave like CI

CI runners are slower and have fewer cores than your laptop. Many flakes only appear under load. Limit CPUs in a container to get closer.

docker run --rm --cpus=1 -v "$PWD":/app -w /app node:20 npm test

You can also run something heavy in another terminal while the loop runs. Run with parallel workers at the same count as CI, and with the same Node, Python or Go version.

Control the inputs

  • Time zone and clock. Set TZ=UTC and also try another zone. Tests near midnight or month ends fail on certain days.
  • Locale and sort order. Different OSes sort strings differently.
  • Random seed. Log the seed on failure so the next run can reuse it.
  • Environment variables. Diff env between CI and local.

A short checklist

  1. Loop the test alone, 100 to 200 times.
  2. Loop it with the whole suite, shuffled, with the CI seed.
  3. Limit CPU and run with the same worker count as CI.
  4. Match runtime versions and the time zone.
  5. Capture logs of the failing run and compare with a passing one.

Stop at the first step that produces a failure and work from there. Each step takes a few minutes and most flakes fall at step one or two.

When you cannot reproduce it

Add logging in the test, upload it as an artifact, and let CI catch the next failure with more data. Run the job with debug output for a week. If the failure only happens on runners, treat it as an environment problem: see flaky workflows versus flaky tests.

Questions people ask

How many loops are enough?

If a test fails one run in 20, 200 loops will almost certainly show it. For rarer flakes, run overnight or in parallel.

Why does it pass on my machine?

Your machine is usually faster, has more cores and a different clock or locale. Limit CPU, match versions and shuffle order to get closer to CI.
