How to generate gRPC and Protobuf code with buf locally

protoc works, but its flags grow fast. buf keeps the plugins, inputs and output paths in two small files you can commit and run the same way everywhere.

With buf, you describe your proto module in buf.yaml, list the code generators in buf.gen.yaml, and run buf generate to write the Go, TypeScript or Python code for your gRPC service. buf lint checks style and buf breaking compares against an older version so you do not break clients by accident. The same three commands work on every machine.

Why buf instead of raw protoc

protoc is the reference compiler and still works. A realistic invocation has an include path, a plugin binary per language, plugin options and an output directory for each, and nobody remembers it. buf wraps the compiler (it ships its own) and moves all of that into configuration. It also gives you linting and breaking-change detection that protoc does not have. Install with brew install bufbuild/buf/buf or npm install --save-dev @bufbuild/buf.

Lay out the module

proto/
  shop/v1/orders.proto
buf.yaml
buf.gen.yaml
gen/            # generated, output of buf generate

A small proto file:

syntax = "proto3";
package shop.v1;
option go_package = "example.com/shop/gen/go/shop/v1;shopv1";

service Orders {
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
}
message GetOrderRequest { string id = 1; }
message GetOrderResponse { string id = 1; string status = 2; }

buf.yaml (the v2 format) says where the module lives and which lint rules apply:

version: v2
modules:
  - path: proto
lint:
  use:
    - STANDARD
breaking:
  use:
    - FILE

Configure generation

buf.gen.yaml lists one entry per plugin. Local plugins are binaries on your PATH, so they run offline and are pinned by the version you install:

version: v2
plugins:
  - local: protoc-gen-go
    out: gen/go
    opt: paths=source_relative
  - local: protoc-gen-go-grpc
    out: gen/go
    opt: paths=source_relative
  - local: protoc-gen-es
    out: gen/ts
    opt: target=ts

Install the Go plugins with go install google.golang.org/protobuf/cmd/protoc-gen-go@latest and go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest, and the TypeScript one with npm install --save-dev @bufbuild/protoc-gen-es (put node_modules/.bin on PATH, or run through npx). Pin versions in your project; "latest" is fine for a first try but not for a team. buf also supports remote plugins hosted on the Buf Schema Registry, which need no local install but need network access.

buf lint
buf generate
buf breaking --against '.git#branch=main'

buf breaking builds the module from the main branch and reports changes that would break existing clients, such as removing a field or changing its type. Run it before you open a pull request.

Keep generated code in sync while you work

Two common policies: commit gen/ (clients that do not have buf can still build, but diffs get noisy) or ignore it and generate on every checkout (clean history, one more step to run). Pick one and write it in your README. In either case, regenerate before the service starts so code and proto cannot disagree.

If you start your services with Flisk, the command in service.json is a shell command, so you can put generation in front of the server:

{
  "schemaVersion": 1,
  "appName": "orders-grpc",
  "appType": "backend",
  "command": "buf generate && go run ./cmd/orders",
  "port": 50051,
  "healthCheck": { "port": 50051 }
}

Flisk restarts a crashed process after a delay, so a failing buf generate will show up in flisk logs --service orders-grpc and stop the start. Flisk does not know about Protobuf and does not run buf by itself; this is just a shell command. Install Flisk with npm install -g @flisk-sh/flisk. For live reload after an edit, add your language's file watcher (for Go, a tool such as air) rather than expecting Flisk to watch the files.

Run it in CI

The same three commands work in a pipeline: buf lint and buf breaking as checks, and buf generate followed by git diff --exit-code if you commit generated code, so the job fails when someone forgot to regenerate. For the breaking check the job needs the full history or the target branch fetched, or --against has nothing to compare with. Run these checks on pull requests only; they cost seconds on a normal module.

Pitfalls

  • Plugin not found. "protoc-gen-go: program not found" means the plugin is not on PATH. go install puts it in $(go env GOPATH)/bin.
  • Wrong go_package. Generated imports are wrong when it does not match your module path.
  • Renumbering fields. Never reuse a field number; mark old ones reserved. buf breaking catches the common cases.
  • Generated files edited by hand. They are overwritten on the next run. Fix the proto instead.

Once the code generates cleanly, test the running service with grpcurl, and for the contract between frontend and backend in general read how to keep an API contract in sync.

Questions people ask

What is the difference between buf and protoc?

protoc is the Protobuf compiler. buf is a CLI that wraps a compiler and adds a config-file workflow, linting and breaking-change detection.

Should I commit generated Protobuf code?

Both work. Committing lets people build without buf; ignoring it keeps diffs clean but requires a generate step after checkout. Choose one and document it.

Does buf generate need internet access?

Not with local plugins. Remote plugins from the Buf Schema Registry need network access.
