How to run an MLflow tracking server locally for experiments

Experiment tracking is only useful if the server is there when you run the training code. Here is how to keep one running next to your app, with its data on a volume.

To run MLflow locally, start a tracking server (mlflow server) with a backend store for run metadata and a place for artifacts, then point your code at it with the MLFLOW_TRACKING_URI environment variable. A SQLite file is enough for one developer. The part people get wrong is keeping the data: if the server lives in a container without a volume, every restart empties your experiment history.

The plain way: a server on your machine

With Python installed, one virtual environment and two commands give you a working server:

pip install mlflow
mlflow server --host 127.0.0.1 --port 5000 \
  --backend-store-uri sqlite:///mlflow.db \
  --artifacts-destination ./mlartifacts --serve-artifacts

The UI is at http://127.0.0.1:5000. --serve-artifacts makes the server the only thing a client needs to reach: artifacts such as model files are uploaded through the server instead of written to a path on the client's disk. Without it, a training job inside a container would try to write to its own filesystem and your files would vanish with the container.

Then in your training code:

import mlflow

mlflow.set_experiment("churn")
with mlflow.start_run():
    mlflow.log_param("C", 1.0)
    mlflow.log_metric("auc", 0.87)

The client reads MLFLOW_TRACKING_URI from the environment, so the code never hardcodes an address. That is the property to keep: the same script should run on your host, in a container and in CI by changing one variable.

Where this breaks down

A server on your host is fine until the code that logs runs somewhere else. A container cannot reach 127.0.0.1 of your machine, so the URI has to change, and you have to remember to start the server first. With Docker Compose you can add an MLflow service with a volume and a health check, see Compose depends_on and healthchecks for the waiting part. That is a good answer if you already live in Compose.

The Flisk way

Flisk has an MLflow preset. In a Flisk project (see the repository for install steps, or npm install -g @flisk-sh/flisk):

flisk resource tracking --type database --framework mlflow --stack ml --yes
flisk up ml

This writes a plain service.json for a container. What it contains, as generated:

  • the image ghcr.io/mlflow/mlflow:v3.17.2, port 5000;
  • a named volume tracking-data mounted at /data, which holds the SQLite database and the artifacts, and which flisk down keeps;
  • a start command that runs mlflow server with --serve-artifacts, one worker, and an allowed-hosts list that includes the resource name;
  • a memory limit of 3g;
  • provides with MLFLOW_TRACKING_URI=http://tracking:5000.

Any other service in the stack that lists tracking in its dependsOn gets that variable in its environment, so a training service needs no URL in its code:

{
  "appName": "trainer",
  "appType": "bring-your-own",
  "stack": "ml",
  "dockerfile": "./Dockerfile",
  "dependsOn": ["tracking"]
}

The UI is published on 127.0.0.1:5000 only, so nothing else on your network can open it. From a script on your host, set the variable yourself:

export MLFLOW_TRACKING_URI=http://127.0.0.1:5000
python train.py

Keep the data, or reset it

Because the data is on a named volume, runs survive flisk down and flisk up. To start from an empty tracking server, stop the stack and remove that volume with Docker, as described in keeping Compose volumes between runs, or resetting them. Do this on purpose: it deletes every run and every logged model.

Pitfalls

  • Port 5000 on macOS. The AirPlay Receiver listens on 5000. Docker still publishes MLflow on 127.0.0.1:5000, but a browser may reach AirPlay instead. Set hostPort in the extraPorts entry (for example { "port": 5000, "hostPort": 5001 }), or turn AirPlay Receiver off. Other containers still use tracking:5000.
  • 403 from the server. MLflow 3 rejects a request whose Host header it does not know. The preset allows the resource name, loopback and private address ranges. If you reach it through another name, add that name to the allowed hosts in the start command.
  • Client and server versions. Pin the client to the server's version. The server image tag is v3.17.2, so install mlflow==3.17.2 in your training image.
  • Memory. The preset reserves up to 3 GB. On a small Docker VM, a crashing tracking server is usually a memory problem, see why a container keeps restarting.

When not to use this

A SQLite backend and a single worker are for one developer. Do not point a team at it, and do not treat it as a model registry you depend on in production. For shared use, MLflow runs against Postgres and an object store, which is a different setup.

Next, send the model files somewhere that is not a Docker volume: storing MLflow artifacts in MinIO shows the one-line change.

Questions people ask

Does MLflow need a database to run locally?

No. A SQLite file is enough for one developer, and MLflow can also use a plain file store. A server such as Postgres matters when several people share the server.

Why do my runs disappear when the container restarts?

The tracking data was written to the container's own filesystem. Mount a named volume at the path the server uses for its database and artifacts.

How does my training code find the tracking server?

The MLflow client reads the MLFLOW_TRACKING_URI environment variable. Set it to the server address, and the same code works on the host and in a container.
