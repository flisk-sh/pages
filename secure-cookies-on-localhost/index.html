Local URLs, routing and HTTPS

Do you need HTTPS to test Secure cookies on localhost?

Mostly no, with two exceptions that waste an afternoon if you do not know them.

You usually do not need HTTPS to test a Secure cookie on localhost. Chrome and Firefox treat http://localhost as a secure context and accept and send Secure cookies there. Safari does not, and a custom host name such as myapp.test is not exempt in any browser, so those two cases need real HTTPS.

What the Secure flag asks for

A cookie with Secure is only sent over HTTPS. Browsers make a narrow exception for loopback, so that developers can keep the same cookie settings in development and production. The exception is a browser decision, not part of the cookie standard everywhere, so check the browser your team actually uses.

Two other attributes cause most "my cookie disappeared" reports, and they have nothing to do with TLS:

  • SameSite. SameSite=None requires Secure. Lax cookies are not sent on cross-site fetch or XHR calls. If your frontend and API are on different sites, a Lax session cookie never reaches the API.
  • Domain. A cookie without a Domain attribute belongs to the exact host that set it, and the port is ignored. A cookie set by api.shop.localhost is not visible to app.shop.localhost unless you set a shared Domain, and browsers can be strict about names that end in localhost. Test the exact names you use.

The simplest fix: one origin

The most reliable way to avoid cookie trouble is to make the browser see a single origin. Serve the frontend on / and the API under a prefix such as /api on the same host, through a reverse proxy. The cookie is then first-party, needs no Domain, no CORS, and no SameSite=None. The nginx article in this space shows the proxy configuration.

A dev server can do the same job with a proxy rule. In Vite, for example:

// vite.config.ts
export default {
  server: {
    proxy: { "/api": "http://localhost:4000" },
  },
};

Your page and its API calls both go to the Vite origin, and Vite forwards /api to the backend.

Where Flisk fits

Flisk's Docker path puts a frontend and a backend on different host names: app.<project>.localhost and api.<project>.localhost, so every call from the page is cross-origin, and Flisk's own documentation points at CORS as the first suspect. For cookie auth that means your session cookie crosses origins. Either use the one-origin approach above, or set cookies and CORS deliberately: credentials: "include" on the fetch, Access-Control-Allow-Credentials: true and an exact allowed origin on the API.

When services run without Docker, Flisk prints http://localhost:<port> for each, so a frontend on port 3000 and an API on 4000 share the host localhost. Cookies ignore ports, which means the API's cookie is visible to the frontend host, but the browser still treats the two as different origins for CORS. Use flisk networks and flisk status to confirm the real URLs before you debug cookie attributes.

When you do need HTTPS

  • You test in Safari and your cookie is Secure.
  • You use a custom domain such as myapp.test and want to keep Secure.
  • You depend on __Host- or __Secure- cookie prefixes, which require Secure.
  • You test from a phone on your network, where the address is not loopback.

Then follow the mkcert guide and terminate TLS in a proxy.

How to debug a missing cookie

  1. In devtools, open Network, select the response, and read Set-Cookie. Chrome marks rejected cookies with a warning icon and gives the reason.
  2. In Application, then Cookies, check the host, path and attributes of what was stored.
  3. On the next request, check whether the Cookie header is present. If it is not, the cause is host, path, SameSite or Secure.

If you decide you need HTTPS, get trusted HTTPS on localhost with mkcert. If the problem is a cross-origin call, read CORS between localhost subdomains.

Questions people ask

Does Secure work on http://localhost?

In Chrome and Firefox, yes: they treat localhost as a secure context. Safari does not, so a Secure cookie fails there over plain http.

Why is my cookie not sent to the API?

Usual causes are SameSite=Lax on a cross-site request, a different host than the one that set it, a missing credentials: include on fetch, or an API that does not allow credentials in CORS.

Do cookies care about the port number?

No. Cookies are scoped by host and path, not port, so localhost:3000 and localhost:4000 share cookies, though they are different origins for CORS.
