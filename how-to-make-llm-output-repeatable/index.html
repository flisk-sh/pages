Prompts and structured outputs

How to make LLM output more repeatable

Lower temperature, pin the model version, fix the prompt and constrain the format. What you can control, what you cannot, and how to test around the rest.

Set temperature low or to zero, pin an exact model version, keep the prompt text identical, and constrain the output format. That gets you much closer to repeatable, but not guaranteed identical, output from hosted models.

What you can control

  • Temperature and sampling: lower temperature, and lower top-p, make the output more stable. Zero picks the most likely token at each step.
  • Seed: some APIs and local servers accept a seed. Check whether yours does and what it promises.
  • Model version: use a dated or pinned model name where one exists, not an alias that moves.
  • Prompt text: any change, even whitespace, can change the result.
  • Output format: enforced schemas remove a lot of variation.

What you cannot fully control

Even at temperature zero, hosted models can return slightly different text on different runs. Batching, hardware and provider-side changes can all play a part. Do not build logic that needs byte-identical output from a hosted model. Compare parsed fields, not strings.

With a local server such as llama.cpp or Ollama on fixed hardware, a fixed seed and settings give much better repeatability, but a different build or GPU can still change results.

Design for stable decisions

Make the model produce small, discrete answers: a label from an enum, a number in a range, a yes or no with a reason. Variation in wording then does not matter. Where you need prose, accept that it varies, and test properties of it (length, required facts, no banned claims) instead of exact text.

An example call

curl http://localhost:11434/api/chat -d '{
  "model": "llama3.1",
  "messages": [{"role": "user", "content": "Label: refund request or not. Text: ..."}],
  "options": {"temperature": 0, "seed": 42},
  "stream": false
}'

The option names above are those of Ollama's native API. Other servers and hosted APIs use different names, so check yours. Substitute any model you have pulled.

Test for flakiness

Run each test case five times and record how often the answer changes. Cases that flip are your risky ones: give them better instructions or examples, or route them to a human. Track the flip rate after each prompt or model change, as part of your prompt tests. Pin the model in version-controlled config so upgrades are a deliberate change, not a surprise.

When repeatability is the wrong goal

Do not chase identical output for creative or conversational features. Variety is part of the experience there. Aim for repeatable decisions (labels, routes, extracted fields) and acceptable variation in wording. Spend your effort where a flipped answer causes real harm, such as approvals, refunds or data written to a system of record, and put a deterministic check or a human in front of those.

Questions people ask

Is temperature zero always the best setting?

It is best for extraction, classification and decisions. For brainstorming or varied writing, a higher temperature is the point.

Why do I still get different outputs at temperature zero?

Hosted systems can differ across runs because of batching, hardware and backend changes. Compare structured fields, not exact text.
