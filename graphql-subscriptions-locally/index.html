How to test GraphQL subscriptions locally: SSE and WebSocket

A subscription is a query that keeps the connection open. Test it from the terminal first, then from the browser, and fix the proxy that eats it.

A GraphQL subscription keeps one connection open and pushes results as events happen. Locally you can test it with curl if the server supports Server-Sent Events (GraphQL Yoga does by default), or from the browser through the graphql-ws WebSocket protocol. Most failures come from a proxy in the middle that buffers or does not upgrade the connection.

Two transports

  • Server-Sent Events (SSE). A normal HTTP request whose response stays open. It works with curl, passes through most HTTP proxies and needs no extra port.
  • WebSocket with graphql-ws. The graphql-transport-ws protocol, implemented by the graphql-ws library. It is what Apollo Client's GraphQLWsLink expects. The older subscriptions-transport-ws library is unmaintained; do not start new work on it.

Check which one your client and server pair uses. A client for one cannot talk to a server that offers only the other.

A subscription in GraphQL Yoga

Add a Subscription type with an async generator. Compared with the server in run a GraphQL server locally, only the schema and resolvers change:

typeDefs: /* GraphQL */ `
  type Query { hello: String! }
  type Subscription { countdown(from: Int!): Int! }
`,
resolvers: {
  Query: { hello: () => 'hi' },
  Subscription: {
    countdown: {
      subscribe: async function* (_, { from }) {
        for (let i = from; i >= 0; i--) {
          await new Promise((r) => setTimeout(r, 1000))
          yield { countdown: i }
        }
      },
      resolve: (payload) => payload.countdown,
    },
  },
},

Now call it from the terminal. -N turns off curl's output buffering so events print as they arrive:

curl -N http://localhost:4000/graphql \
  -H 'accept: text/event-stream' \
  -H 'content-type: application/json' \
  -d '{"query":"subscription { countdown(from: 3) }"}'

You see a few event: next lines with data, one per second, then event: complete. If the whole reply arrives at once at the end, something between curl and the server is buffering.

The WebSocket route

For a client that needs WebSocket, attach graphql-ws to your server. In a Node server with the ws package:

import { WebSocketServer } from 'ws'
import { useServer } from 'graphql-ws/lib/use/ws'

const wss = new WebSocketServer({ server: httpServer, path: '/graphql' })
useServer({ schema }, wss)

On the client, Apollo Client combines an HTTP link for queries and mutations with a WebSocket link for subscriptions, using split:

import { createClient } from 'graphql-ws'
import { GraphQLWsLink } from '@apollo/client/link/subscriptions'

const wsLink = new GraphQLWsLink(createClient({ url: 'ws://localhost:4000/graphql' }))

The URL scheme is ws:// for plain HTTP and wss:// for HTTPS. For a quick command-line check, websocat or wscat can connect to the endpoint with the graphql-transport-ws subprotocol and send a connection_init message first.

Running it with the rest of the app

A subscription server is still one process. In Flisk local-process mode it is a service.json with a command and a port, exactly like a plain GraphQL API, and WebSocket upgrades on that port work because nothing sits in between. Install with npm install -g @flisk-sh/flisk. The flisk logs --service graphql-api command is a handy way to watch connection and disconnect messages while you test. If you route traffic through Flisk's container gateway, Flisk lists a websocket feature for services, but I have not verified an end-to-end GraphQL subscription through that gateway, so test yours and fall back to the direct port. See local URLs instead of ports for how gateway URLs work.

Through a Vite dev proxy

A proxy entry for /graphql forwards HTTP only. Add ws: true so upgrade requests are forwarded:

server: { proxy: { '/graphql': { target: 'http://localhost:4000', ws: true } } }

Then use ws://localhost:3000/graphql in the client (the page's own origin). If you call the API origin directly, you need CORS for HTTP and an origin check on the WebSocket; see GraphQL CORS errors.

Pitfalls

  • Buffering proxies. Compression or buffering in a proxy delays SSE. Test without the proxy first.
  • Connection limits. Browsers allow a limited number of simultaneous HTTP/1.1 connections per origin (6 is the common limit), and each SSE stream uses one. HTTP/2 lifts this.
  • Leaks. Clean up listeners when a client disconnects, or restarts leave timers behind. An async generator's finally block runs on disconnect.
  • Auth. The WebSocket handshake cannot set arbitrary headers from a browser; pass credentials in connectionParams and check them in the server's onConnect.

A server-push feature is easier to trust when events come from a real queue; the next step in that direction is NATS for local development.

Questions people ask

Can I test a GraphQL subscription with curl?

Yes, if the server supports Server-Sent Events, as GraphQL Yoga does. Send the query with accept: text/event-stream and use curl -N.

Which library should I use for GraphQL subscriptions over WebSocket?

graphql-ws, which implements the graphql-transport-ws protocol. The older subscriptions-transport-ws is unmaintained.

Why do my subscription events arrive all at once?

A proxy or compression layer between client and server is buffering the response. Remove it for the test and then add it back with buffering off.
