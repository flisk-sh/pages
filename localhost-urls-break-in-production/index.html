Why hardcoded localhost URLs break in production

A URL that says localhost means this machine. On a host, that machine is the wrong one.

Reading time

Updated

A hardcoded http://localhost:4000 breaks in production because localhost always means the machine that runs the code. In a container it is the container itself. In a visitor's browser it is the visitor's own computer. The fix is to move every address into configuration, set per environment, and to know which side of the build each value is read on.

Three places localhost is wrong

  1. Server to server, in containers. Your API calls http://localhost:5432 for Postgres. Inside the API container, nothing listens there, because the database is a different container or a managed service. You get connection refused.
  2. Browser to API. Your frontend bundle calls http://localhost:4000/api. On your laptop that works. For a visitor, localhost is their own machine, so the request goes nowhere, or hits something unrelated that they run.
  3. Redirects and callbacks. OAuth redirect URIs, webhook URLs, email links and CORS allow-lists often contain localhost and are easy to forget. They fail only when a real user goes through the flow.

Find them

Search the repository, including config, tests fixtures and docs you copy from:

grep -rnE "localhost|127\.0\.0\.1|0\.0\.0\.0" --exclude-dir=node_modules --exclude-dir=.git .

Not every hit is a bug. A health check that curls its own port from inside the container is fine. Anything that names another service, a database, or a public address is not.

Move them into environment variables

For server code, read the address from the environment and fail loudly when it is missing:

const databaseUrl = process.env.DATABASE_URL;
if (!databaseUrl) throw new Error("DATABASE_URL is not set");

Use a different value in each place. For example, DATABASE_URL points to localhost on your laptop, to a service name inside a Compose network, and to the provider's internal host in production. Your code does not change, only the value does.

Frontends are different. A browser app cannot read a server's environment. Tools such as Vite replace import.meta.env.VITE_* values at build time, so the value is baked into the bundle. That means you must set the API URL when you build the production bundle, not when you start a server. If the production build still says localhost, the build ran without the variable. The details are in using a Vite env variable for the API URL. A simpler option is a relative URL such as /api with a reverse proxy that forwards it, so the frontend needs no absolute address at all.

The Flisk way

In service.json, the env field lists the variables a service needs, and values can refer to the shell or the project .env with ${VAR} or ${VAR:-default} syntax:

{
  "appName": "web",
  "appType": "frontend",
  "command": "node server.js",
  "port": 3000,
  "dependsOn": ["api"],
  "env": { "API_URL": "${API_URL:-http://localhost:4000}" }
}

The default keeps the laptop working, and the real value comes from outside. When you export a deploy file with flisk export render, each key under env is written as a name only, with sync: false, so Render asks you for the production value and nothing is stored in git. That includes keys that already have a default, so check the prompt for each one. For Docker-based projects, Flisk also serves services on *.localhost addresses, which keeps local URLs consistent. See local URLs instead of port numbers.

Pitfalls

  • Defaults that hide a missing variable. A fallback of http://localhost:4000 in production code silently works until it does not. Use defaults only in local config, and make production fail on a missing value.
  • Public variables are public. Anything baked into a browser bundle is visible to every visitor. Put no secrets there. See secrets in Vite and Next.js public variables.
  • CORS and cookies. When the frontend and API move to real domains, the allowed origin and cookie domain change too. Set them from the environment as well.
  • Not a bug. Binding a server to localhost for a local-only admin tool is a valid choice. It is just not reachable from outside, which is the point.

Next, check that the server itself is reachable once the addresses are right. That is the most common second failure, covered in app not reachable after deploy.

Questions people ask

Can I just replace localhost with my server IP?

You can, but it hardcodes another value. Put the address in an environment variable so each environment sets its own, and use a domain name rather than an IP when you can.

Why does my frontend still call localhost after I set the variable?

Build-time tools such as Vite read the variable when they build the bundle. Set it in the build step of the production build, then rebuild.

Is localhost ever correct in production?

Yes, for things on the same machine or in the same container, such as a sidecar or a health check that calls its own port.
