What to put in .dockerignore (and why builds get slow without it)

If docker build starts with a long 'transferring context' step, the fix is usually a ten-line file.

A .dockerignore file lists paths that are not sent to Docker as part of the build context. Put it in the root of the context (next to the Dockerfile in the usual layout) and list .git, dependency folders such as node_modules, build output, logs and every .env file. Builds start faster, COPY . . stops invalidating the cache for irrelevant files, and secrets stay out of the image.

What the build context is

When you run docker build ., the folder . is the build context. The client packs it up and hands it to the builder, and COPY can only read from inside it. Without an ignore file, that is everything: your .git history, a 600 MB node_modules built for your host OS, test videos, local databases. BuildKit transfers only what the Dockerfile actually uses in many cases, but COPY . . uses everything, so the full folder is hashed and copied.

A starting file

# version control and editor files
.git
.gitignore
.idea
.vscode

# dependencies and build output (rebuilt inside the image)
**/node_modules
**/dist
**/__pycache__
**/.venv
target

# secrets and local config
.env
.env.*
!.env.example

# logs and OS junk
*.log
.DS_Store

# the Docker files themselves
Dockerfile*
docker-compose*.yml
.dockerignore

Do not copy this blindly. If your Dockerfile copies dist from the host instead of building it, ignoring dist breaks the build. Ignoring Dockerfile is safe for COPY, because the builder still reads the Dockerfile itself.

How the patterns differ from .gitignore

  • Patterns are anchored at the context root. node_modules matches only a top-level folder. Use **/node_modules to match it in every subfolder of a monorepo.
  • Later lines win. !.env.example after .env.* puts that one file back.
  • There is no per-folder ignore file. Only the one in the context root is read, not nested ones.
  • BuildKit supports a per-Dockerfile file. Dockerfile.dev.dockerignore next to Dockerfile.dev applies only to that Dockerfile, so a dev build and a production build can ignore different things.

Check what a build actually sends

You do not have to guess. Build with plain progress output and look at the context line near the top, which reports how many bytes were transferred. Add a pattern, build again, and watch the number fall. If it stays large after you ignored the obvious folders, look for a stray database dump, a .venv in a subfolder, or a build cache folder such as .next or .turbo. These are easy to forget because your editor hides them.

Where it goes with Flisk

For a bring-your-own resource, Flisk uses the resource folder (the one holding service.json) as the build context. Put the .dockerignore there. If you set buildContext to a folder higher up, for example to build from a repository root, the ignore file belongs in that folder instead:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "buildContext": "../../..",
  "dockerfile": "services/app/api/Dockerfile"
}

With buildContext set, dockerfile is relative to that context. Flisk itself keeps .env out of version control by design, and your ignore file should keep it out of images for the same reason: a copied .env is readable by anyone who can pull the image.

A monorepo example

In a monorepo you often build from the repository root so a service can copy a shared package. That makes the context huge: every other service is in it. A root .dockerignore that excludes whole services keeps each build small:

**/node_modules
**/dist
.git
services/*
!services/api
!packages/shared

The wildcard drops every service folder, and the two negations put back the one being built and the shared package it needs. Order matters here: the exclusion line comes before the exceptions. If you build several services from one root with one ignore file, use the per-Dockerfile form, services/api/Dockerfile.dockerignore, so each build keeps only its own folders.

Pitfalls

  • A COPY of an ignored path fails. The error is "not found", which looks like a typo. Check the ignore file first.
  • Ignoring host node_modules is not optional for cross-OS work. Native modules built on macOS do not run in a Linux container.
  • Bind mounts ignore it. .dockerignore only affects the build context. A volumes mount at run time shows the full host folder.
  • Check the size. The first lines of docker build --progress=plain . show how much was transferred. A few megabytes is normal for most apps.

Next step

With a small context, the next cost is order inside the Dockerfile. Layer caching covers which lines to put first.

Questions people ask

Where does the .dockerignore file go?

In the root of the build context, the folder you pass to docker build. With a Flisk bring-your-own resource that is the service folder, or the buildContext folder if you set one.

Does .dockerignore apply to bind mounts?

No. It only filters the build context. A volume or bind mount at run time exposes the host folder as it is.

Why is node_modules still copied after I ignored it?

The pattern node_modules only matches the context root. Use **/node_modules to match it in subfolders.
