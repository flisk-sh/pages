Team dev environments and onboarding

How to onboard a developer to a multi-service app on day one

A new hire should see the whole app running before lunch, not after a week of wiki pages. Here is a short plan that gets there, with or without Flisk.

To onboard a developer on day one, cut the setup down to four steps that you can run in order: install the tools, check the machine, start everything with one command, and make one visible change. Anything that needs a human to explain it is a gap in the repository, not in the new hire.

Why setup takes days

Most slow onboarding comes from the same three things. The setup lives in a wiki that nobody updated after the last migration. Services need to start in a certain order, and only two people remember it. Failures are silent: a port is taken, a Docker daemon is off, a Node version is wrong, and the new developer cannot tell which one.

The fix does not need a specific tool. A Makefile with make doctor and make up, plus a Docker Compose file with health checks, already removes most of the pain. What matters is that the checks and the start command are code in the repository, so they cannot drift away from the truth.

The four-step day-one plan

  1. Install prerequisites. A short list with versions, in the README. Anything you can detect by script, detect by script.
  2. Check the machine. One command that says what is missing and prints the fix, instead of a stack trace three minutes into a build.
  3. Start everything. One command, in the right order, with health checks and URLs printed at the end.
  4. Make one change and see it. Edit a string in the frontend or an API response and watch it update. This proves hot reload works on this machine.

Pair this with a first ticket that is small and real, such as changing a label or adding a field to one endpoint. A first ticket that touches two services teaches the shape of the system better than any diagram.

The Flisk way

Flisk is a CLI that reads a service.json per service and starts the whole app locally. If you have not set it up in the repository yet, see the service.json contract article first. Once the files are committed, the new developer does this:

npm install -g @flisk-sh/flisk
git clone git@github.com:your-org/your-app.git
cd your-app
flisk project --yes
flisk doctor
flisk up

flisk project --yes writes the files that are git-ignored and machine specific: the project .env with generated defaults and the output under .flisk/.flisk-out/. Running it a second time changes nothing, so it is safe to put in the README as step one after cloning.

flisk doctor checks only what this project uses. For a project whose services all declare a command, it checks that each program is on the PATH and says Docker, Compose and Tilt are not needed. For a container project it checks the Docker daemon, Compose, Tilt and more, and prints a fix under each failed check. You re-run it until it ends clean.

flisk up starts the services in dependsOn order, waits for health, and prints the URLs. Two follow-up commands help a new person find their way around:

flisk resources      # every service with its stack, type and port
flisk networks       # the URL of every frontend and API service
flisk status         # what is running and healthy
flisk logs           # recent logs from the running stack

There is also a shortcut for a first look at someone else's repository: flisk up <git-url> clones a repository that has a Flisk project into ./<repo name> and starts it.

Make the version a team decision

Day-one problems often come from a CLI that is older than the repository expects. Put a floor in .flisk/project.json:

{ "minFliskVersion": "1.4.50" }

With that set, flisk doctor and flisk up refuse to run on an older CLI and print Run: flisk upgrade. The value must be a plain MAJOR.MINOR.PATCH string. If you need an exact version rather than a floor, there is also a pinnedFliskVersion field in the same file, and a mismatch is reported with the npm install command that fixes it. Use the version your team actually runs, not the example above.

Services that live in other repositories

If the app is spread over several repositories, a platform repository can declare them in .flisk/project.json under repos, each with a url, a dir and a branch. flisk up clones missing ones before discovery, and flisk repos clone does the same on demand. It never overwrites or pulls a directory that already exists, so a developer's local branches are safe. The trade-offs between layouts are covered in the Flisk layout guide, and the doctor output includes read-only checks for these directories.

What to check on the first day

  • Does flisk doctor end clean on a machine that has never run the project? Test this on a clean laptop or a fresh VM at least once per quarter, because your own machine hides missing steps.
  • Does the database come up with usable data? Migrations belong in a separate one-shot resource, covered in database migrations in local dev.
  • Is the Windows path documented? Windows developers need Ubuntu on WSL2 for a Docker stack, see the Windows setup article.
  • Does each failure message name the fix? If a failure needs a Slack thread, add a check or a README line.

When this plan does not fit

If your app is two services and a database, a Compose file and a three-line README are enough, and adding a CLI is more to learn than it saves. The plan above is about the number of steps, not the tool: count the manual steps in your current setup page and remove them one at a time. Flisk helps once the count is high enough that nobody remembers the order.

Questions people ask

How long should day-one setup take?

Set your own target and measure it on a clean machine. Flisk does not publish an onboarding time; the docs say onboarding time has not been measured on a hiring cohort.

What if the new developer is on Windows?

Use Ubuntu on WSL2 with Docker Desktop for a Docker stack. Native Windows runs projects whose services declare a command, and the small demo.

Does flisk project --yes overwrite my files?

In a repository that already had a package.json, Tiltfile, .tiltignore and docker-compose.yml it left them unchanged and only appended lines to .gitignore.
