RAG and vector databases locally

How to ingest documents into a vector database, repeatably

Ingestion is a build step. If you can run it twice and get the same index, you can change chunking or models without fear.

Write ingestion as a script you can run any number of times: read files, split them into chunks, embed the chunks in batches, and upsert them with ids derived from their content. Because the ids are stable, a second run overwrites the same points instead of adding duplicates, and unchanged text can be skipped.

What a repeatable ingestion does

  1. Lists the source files, never a hand-picked set.
  2. Splits each file into chunks, see chunking documents for RAG.
  3. Gives each chunk an id computed from the file path and chunk text, for example a hash.
  4. Embeds chunks in batches, so you make a few hundred requests, not a few thousand.
  5. Upserts the vectors with a payload: source, heading, chunk number and the text itself.
  6. Optionally deletes points whose source file no longer exists.

Storing the text in the payload means a search result can show its source without a second lookup. The stable id is what makes the job safe to repeat: upsert means insert or replace.

A working example for Qdrant and Ollama

This TypeScript script, runnable with Bun, embeds Markdown files from a docs folder using the chunker from the chunking article. The collection must already exist with the right size, for example 768 for nomic-embed-text.

import { createHash } from "node:crypto";
import { readdirSync, readFileSync } from "node:fs";
import { chunk } from "./chunk";

const QDRANT = process.env.QDRANT_URL ?? "http://localhost:6333";
const OLLAMA = process.env.OLLAMA_URL ?? "http://localhost:11434";
const COLLECTION = "docs";

const uuid = (s: string) => {
  const h = createHash("sha256").update(s).digest("hex");
  return `${h.slice(0, 8)}-${h.slice(8, 12)}-${h.slice(12, 16)}-${h.slice(16, 20)}-${h.slice(20, 32)}`;
};

async function embed(texts: string[]): Promise<number[][]> {
  const r = await fetch(`${OLLAMA}/api/embed`, {
    method: "POST",
    body: JSON.stringify({ model: "nomic-embed-text", input: texts.map((t) => "search_document: " + t) }),
  });
  if (!r.ok) throw new Error(`embed failed: ${r.status} ${await r.text()}`);
  return (await r.json()).embeddings;
}

for (const file of readdirSync("docs").filter((f) => f.endsWith(".md"))) {
  const chunks = chunk(readFileSync(`docs/${file}`, "utf8"));
  for (let i = 0; i < chunks.length; i += 32) {
    const batch = chunks.slice(i, i + 32);
    const vectors = await embed(batch);
    const points = batch.map((text, j) => ({
      id: uuid(`${file}:${text}`),
      vector: vectors[j],
      payload: { source: file, chunk: i + j, text },
    }));
    const r = await fetch(`${QDRANT}/collections/${COLLECTION}/points?wait=true`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ points }),
    });
    if (!r.ok) throw new Error(`upsert failed: ${r.status} ${await r.text()}`);
  }
  console.log(`${file}: ${chunks.length} chunks`);
}

Because the id comes from the text, an edited paragraph gets a new id and the old point stays behind. For a clean index, either delete points by source before re-adding a file (a filtered delete in Qdrant), or recreate the collection at the start of a full run.

The Flisk way

Create the job as a worker next to the vector store, and make it depend on both services:

flisk resource ingest --type worker --stack rag --yes

Set "dependsOn": ["vectors", "embed"] in its service.json. The vectors resource (the Qdrant preset) gives dependents QDRANT_URL. The Ollama server is reachable at http://embed:11434, the resource name being its host name on the Docker network. The script above falls back to localhost for use outside the stack, so inside the stack set its two addresses in your code or configuration (for Ollama, http://embed:11434). Put the script in the worker's src folder, then run it on demand inside the running service instead of at startup:

flisk run ingest -- bun run src/ingest.ts

flisk run runs a command with the environment the service has in the stack and returns the command's exit code, so it also works in a CI step. Check that your source files are visible in the container first, for example with flisk run ingest -- ls src. If a worker that runs at startup is not what you want, you can instead run the same script on your host against the published Qdrant port, which also works without any Flisk setup.

Pitfalls

  • Stale points. Deleted or edited documents leave old chunks behind unless you remove them. Test with a question about text you deleted.
  • Partial runs. A crash halfway leaves a half-built index. Idempotent upserts mean you simply run it again.
  • Rate limits on hosted embedding APIs. Batch, and retry with backoff. A local model has no rate limit but is slower per batch.
  • Secrets in documents. Whatever you ingest can be retrieved and shown. Filter out files that contain credentials.

Questions people ask

How do I avoid duplicate vectors when I re-run ingestion?

Derive each point id from the source path and chunk text, and use upsert. The same content then maps to the same id and is replaced, not added.

How big should an embedding batch be?

Tens of chunks per request is a common range, for example 16 to 64. Larger batches reduce overhead until memory or the input limit becomes the problem.

Should ingestion run at startup of the app?

Usually no. Run it as a separate on-demand job so a slow or failing ingest does not block your API from starting.
