Run an OpenTelemetry Collector locally with Flisk

A local collector lets services send telemetry to one place while you change where it goes.

Run the OpenTelemetry Collector contrib image, mount a small YAML file over its config path, listen for OTLP on 0.0.0.0:4317 and 0.0.0.0:4318, and add a debug exporter so every span, metric and log your services send is printed. Point your services at the collector instead of at a backend, and you can inspect, filter and fan out data without touching application code.

What a collector is for

You can send telemetry straight from a service to Jaeger or Grafana, and for one service that is the simpler choice. A collector earns its place when you want one stable address for every service, to see raw data while debugging instrumentation, to drop noisy spans (health checks, for example) in one place, or to send the same data to two backends. It is a separate process with three stages: receivers take data in, processors change it, exporters send it on.

A minimal configuration

Save this as otel-collector.yaml:

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch: {}
  filter/health:
    error_mode: ignore
    traces:
      span:
        - 'attributes["http.route"] == "/health"'

exporters:
  debug:
    verbosity: detailed
  otlphttp/jaeger:
    endpoint: http://jaeger:4318

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [filter/health, batch]
      exporters: [debug, otlphttp/jaeger]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]

Two details matter. First, the endpoints say 0.0.0.0 on purpose. Recent collector versions bind to localhost by default, which inside a container means nothing outside the container can connect, and the symptom is "connection refused" even though the container is up. Second, the debug exporter replaces the older logging exporter. Use verbosity: basic once you are done reading everything, because detailed is very chatty. The filter/health processor shows how to drop health-check spans in one place; the attribute name depends on your instrumentation, so check what your spans carry before relying on it. The otlphttp exporter adds /v1/traces to the endpoint itself.

Run it with Flisk

The collector is an image with a config file, so it is a bring-your-own resource with one bind mount. Put the YAML next to the service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "otel-collector",
  "appType": "bring-your-own",
  "stack": "obs",
  "port": 13133,
  "exposeViaProxy": false,
  "image": "otel/opentelemetry-collector-contrib:0.120.0",
  "extraPorts": [{ "port": 4317 }, { "port": 4318 }],
  "volumes": [
    { "source": "./otel-collector.yaml", "target": "/etc/otelcol-contrib/config.yaml", "readOnly": true }
  ],
  "dependsOn": ["jaeger"]
}

What each field does: image names the contrib build (pin a current tag; 0.120.0 is only an example). volumes with a path starting ./ is a bind mount relative to the folder of the service.json, and readOnly stops the container from writing to it. extraPorts publishes the OTLP ports on 127.0.0.1. exposeViaProxy: false gives it no Traefik route, because a collector has no web page. flisk config verify accepts this file. The collector image has no shell, so a health probe that runs a command inside it cannot work; rely on the logs and on the debug exporter output instead.

The jaeger resource is the one from sending OpenTelemetry traces from Node.js to Jaeger, except that it no longer needs to publish 4317 and 4318: the collector owns those host ports, and Jaeger keeps only its UI on 16686. Reaching Jaeger by the name jaeger works when both are containers on the Flisk Docker and Tilt path, since they share a Docker network there. In the mixed run, where your code is local processes and images start with docker run, containers do not share a network, so the collector cannot reach Jaeger by name. Keep the debug exporter only in that case.

Services then use one endpoint, http://localhost:4318 from a local process, or http://otel-collector:4318 from another container. See what arrives with:

flisk logs --service otel-collector --since 2m

Check that it is receiving

  1. Send one request through a traced service and run the command above. You should see a block per span, with its name, attributes and trace ID.
  2. If nothing appears, check the service first: OTEL_EXPORTER_OTLP_ENDPOINT must match the protocol, HTTP on 4318 or gRPC on 4317.
  3. If the service reports a connection error, check the bind address in the YAML and that the ports are published.

Pitfalls

  • Invalid config. The collector refuses to start on a YAML mistake and prints the reason in its log. A component named in a pipeline but not defined above it is the usual cause.
  • Core versus contrib. The core image has only a few components. Processors such as filter and many exporters live in the contrib image, whose config path is /etc/otelcol-contrib/config.yaml. The core image reads /etc/otelcol/config.yaml.
  • Port clashes. Only one thing can publish 4318 on your machine. Two backends that both publish it will fight, and the second container fails to start.
  • Extra hop. A collector adds a process and a place for data to be dropped silently, for example by a filter that matches more than you meant. Do not add one until you need it.

For metrics from the same collector, see running Grafana, Loki, Tempo and Prometheus in one container, which accepts OTLP for all three signal types.

Questions people ask

Do I need a collector for local development?

No. Services can export straight to Jaeger. A collector helps when you want one stable endpoint, filtering or several backends.

Why does the collector reject connections?

Check that the receivers bind to 0.0.0.0 rather than localhost, or a container-published port will not reach it.

What is the debug exporter for?

It prints the telemetry the collector receives, so you can confirm data arrives before looking at a backend.
