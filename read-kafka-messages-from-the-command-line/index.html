Kafka and streaming locally

How to read Kafka messages from the command line

You do not need application code to see what is in a topic. Three small tools print it, keys and offsets included.

Read messages with the console consumer that ships inside the Kafka image, or with kcat from your machine. Both print what is in a topic, and both can start from the oldest message, so you can check what a producer really sent without writing any code.

Option 1: the console consumer in the broker

Nothing to install. The tools live in the broker container, so run them there. Inside it the broker is at localhost:9092 (the internal listener from the KRaft article):

flisk run broker -- /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic orders --from-beginning \
  --property print.key=true --property print.partition=true \
  --property print.offset=true --timeout-ms 5000

Without Flisk, put docker exec -it and the container name in front of the same command. What the flags do:

  • --from-beginning starts at the oldest retained message. Without it the consumer waits for new messages only.
  • print.key, print.partition and print.offset add those fields to each line, which is what you need to debug ordering.
  • --timeout-ms 5000 exits after five quiet seconds, so the command is safe in a script. Without it, it runs until you press Ctrl-C.
  • --max-messages 10 stops after ten messages.
  • --partition 2 --offset 40 reads one partition from one offset.

A console consumer with no --group gets a throwaway group, so it does not move the bookmark of your real consumer. Adding --group NAME would, so do not pass the application's group by accident.

Option 2: kcat from your machine

kcat (formerly kafkacat) is a small client you install once, for example with brew install kcat. It connects the way your own code does, so it uses the external listener:

# list topics, partitions and the broker's advertised address
kcat -b localhost:29092 -L

# read everything and exit at the end of the topic
kcat -b localhost:29092 -t orders -C -o beginning -e \
  -f '%t[%p]@%o key=%k value=%s\n'

# send two keyed messages
printf 'o-1:{"id":"o-1"}\no-2:{"id":"o-2"}\n' | kcat -b localhost:29092 -t orders -P -K:

-L is the most useful first check. If the broker list it prints shows an address your machine cannot reach, you have the problem described in Kafka advertised listeners, and kcat shows it in one line instead of a stack trace from your application. -C consumes, -P produces, -o beginning picks the start, -e exits at the end, -K: sets the key delimiter, and -f is a format string with %k key, %s value, %p partition and %o offset.

Option 3: rpk on Redpanda

With a Redpanda broker from the Kafka or Redpanda comparison, the rpk tool is in the image:

flisk run broker -- rpk topic consume orders --offset start --num 10 --format '%p %o %k %v\n'
echo '{"id":"o-3"}' | flisk run broker -- rpk topic produce orders --key o-3

The service is named broker here as in the other pages, so use whatever name your service.json has. I did not run these on a live broker, and the rpk format verbs are worth a quick look at rpk topic consume --help on your version.

Which one to use

For a one-off look, the console consumer is enough. For anything you will repeat in a script or a bug report, kcat with an explicit format string gives output that you can paste into an issue and compare line by line.

Pitfalls

  • Two addresses for two places. Inside the broker container use localhost:9092. From your machine use localhost:29092. Using the first one from your machine gives the connection error this series keeps coming back to.
  • Binary values. The console tools print values as text. Avro, Protobuf or compressed payloads look like noise. Use a UI with a schema registry for those.
  • Empty output on a topic that has messages. You forgot --from-beginning or -o beginning, or retention already deleted them.
  • The exit wait. Without a timeout or -e the command never returns, which hangs a script.
  • Flisk quoting. Everything after -- goes to the container, so a quote that the shell would eat on your machine may be needed again inside sh -c.

Once you can read a topic you can reason about keys, partitions and message order, and about moving a consumer back with an offset reset.

Questions people ask

How do I read a topic from the beginning?

Pass --from-beginning to kafka-console-consumer.sh, -o beginning to kcat, or --offset start to rpk topic consume.

Why does kcat -L show an address I cannot reach?

That is the broker's advertised listener. The broker tells clients where to connect, and an address that only works inside Docker fails from your machine. Add a second listener for the host.

Does reading with the console consumer affect my application?

Not unless you pass its group id. Without --group the tool uses a throwaway group and leaves your committed offsets alone.
