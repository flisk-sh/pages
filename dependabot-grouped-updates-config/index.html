Dependabot Grouped Updates: A dependabot.yml That Works

Configure Dependabot to open a few grouped pull requests instead of dozens, with a weekly schedule, separate groups for dev tools and a limit on open PRs.

Create .github/dependabot.yml, set a schedule, and add groups so related updates arrive in one pull request. A weekly schedule with one group for patch and minor updates and a separate pull request for majors keeps the review load small. Security updates are handled on their own path.

A starting file

version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
      day: monday
    open-pull-requests-limit: 5
    groups:
      minor-and-patch:
        update-types:
          - minor
          - patch
    labels:
      - dependencies

  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly

With this, minor and patch updates for npm come as one pull request each week. A major update is not in the group, so it gets its own pull request, which is what you want for something that may break.

Groups by name or pattern

You can group by package names with patterns, for example all your linting tools or everything from one scope, and keep other updates separate.

    groups:
      lint:
        patterns:
          - 'eslint*'
          - 'prettier'
      types:
        patterns:
          - '@types/*'
      production:
        dependency-type: production
        update-types: [minor, patch]

A package that matches more than one group goes to the first match, so order matters. Check the Dependabot configuration reference for the exact option names in your case, because the file format is strict and an invalid key makes the whole file fail.

Keep it from flooding you

Use a weekly or monthly schedule, not daily. Use open-pull-requests-limit to cap how many version update PRs can be open. Add ignore entries for packages you cannot move yet, with a comment explaining why and a date to review.

    ignore:
      - dependency-name: 'typescript'
        update-types: ['version-update:semver-major']

An ignore without a reason becomes permanent by accident.

Several folders and ecosystems

Dependabot needs one entry per ecosystem and per directory that holds a manifest. A monorepo with packages in several folders needs an entry for each, or the directories list if your version supports it. Docker base images, GitHub Actions and Python requirement files are separate ecosystems. Forgetting one means those dependencies silently go stale.

Labels, reviewers and commit messages

Add labels so you can filter bot PRs, and set commit-message with a prefix such as chore(deps) if you use conventional commits, so release tooling does not count updates as features. Use reviewers or a CODEOWNERS entry to route the pull requests to a person or team. Small settings like these decide whether bot pull requests blend into your process or sit unnoticed.

Check that it works

After merging the file, open the Dependabot page under the repository's Insights, Dependency graph, to see the last run and any errors. If it reports a parse problem, fix the YAML. Run it once manually from there to see the first group PR. Then make sure CI actually runs on those pull requests and that required checks do not block them forever, see CI checks for dependency PRs. Remember that Dependabot pull requests get their own secrets store, not your Actions secrets, which explains many failures that only show up on bot PRs.

Questions people ask

Why did my group not include a package?

The package may not match any pattern or update type of the group, or an earlier group took it. Check the group rules and their order.

Does grouping apply to security updates?

Security updates follow separate settings. Check the current Dependabot documentation for how to group them, because the options differ from version updates.
