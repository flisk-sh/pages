Agent memory and context engineering

What is context engineering for AI agents?

Context engineering is deciding what goes into the model's window on each call. Here is what it covers, the four sources of context, and a simple checklist to apply.

Context engineering is the work of choosing exactly what the model sees on each call: instructions, tools, history, retrieved facts and the current task. The model has no memory of its own, so everything it "knows" in a turn was put there by your code.

Why it matters more than the prompt

A single prompt is a one-off string. An agent makes dozens of calls, and each call is built from parts that change: the latest tool result, the plan so far, a few files, a summary of older steps. If those parts are wrong, noisy or stale, a better wording of the instruction will not save you.

Most agent failures that look like "the model is dumb" are really "the model was shown the wrong things".

The four sources of context

  • Instructions: system prompt, rules, output format. Stable, so keep it short and put it first.
  • Tools: names, descriptions and schemas. Every tool costs tokens on every call.
  • History: earlier messages and tool results from this session.
  • Retrieved knowledge: files, search hits, database rows, memory notes pulled in for this step only.

Treat each one as a budget line, not a free resource.

Build the window on purpose

Write one function that assembles the messages for a call. Do not let the framework append everything by default.

def build_context(task, session, memory):
    return [
        {"role": "system", "content": RULES},
        {"role": "system", "content": "Notes:\n" + memory.top(task, k=5)},
        *session.summary_and_recent(max_tokens=6000),
        {"role": "user", "content": task},
    ]

Now you can log, test and change what the model sees in one place.

A checklist to apply

  1. Can you print the exact input of any call? If not, add that first.
  2. Is anything in the window that the next step does not need? Remove it.
  3. Is anything the next step needs missing? Fetch it by name or search, not by dumping everything.
  4. Are large tool results trimmed to the useful part before they enter history?
  5. Is stable text at the start and changing text at the end? This also helps provider-side caching.

Pitfalls

Do not equate a bigger window with a better agent. A long window lets you be lazy, and the cost is slower, more expensive calls and weaker attention to the parts that matter. See why long-context agents drift.

Do not hide context assembly inside a framework you cannot inspect. When behaviour is odd, you need to read the real input, as described in how to debug agent context problems.

A worked example

Take a support agent that answers questions about an order. A weak version dumps the full order history, the whole FAQ and 30 earlier messages into every call. A better version includes the one order being discussed, the two FAQ entries that match the question, a four-line summary of the chat so far, and the rules for refunds. The second input is a tenth of the size, costs less, answers faster and is easier to test, because you can say exactly what the model was shown when it got something wrong.

Questions people ask

Is context engineering the same as prompt engineering?

Prompt engineering is about the wording of instructions. Context engineering is wider: it also covers tools, history, retrieval and memory, and how they are assembled per call.

Do I need a framework for it?

No. A function that builds the message list, plus logging of its output, is enough to start. Add libraries only when you hit a clear need.
