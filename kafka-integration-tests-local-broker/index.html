Kafka and streaming locally

Kafka integration tests against a local broker

A shared local broker is faster than a container per test. Unique names and a join wait keep the tests from flaking.

Use one local broker that is already running and give every test its own topic and its own consumer group. Tests then run in parallel, never see each other's messages, and skip the slow part of starting a Kafka container for each test class. Wait for the consumer to join its group before you produce, and poll for the result with a deadline instead of sleeping.

Two ways to get a broker in tests

Container per test runOne shared local broker
IsolationPerfect, nothing is sharedBy unique topic and group names
Start costSeconds to tens of seconds each runPaid once, when the stack starts
Setup in the testA library such as TestcontainersAn address from an environment variable
Same broker as developmentNoYes

Testcontainers is a good fit when a test must control the broker itself, for example by killing it. For tests of your own producers and consumers a shared broker is faster and matches what you run by hand. Both work, and you can mix them.

Start the broker with the stack

Use the broker and the topics job from earlier in this series. Tests then read the address from the environment:

flisk up streaming
export KAFKA_BROKERS=localhost:29092
npm test

The tests run on your machine, so they use the external listener. In CI the same two lines work after the stack is up. See running a multi-service stack in GitHub Actions and integration tests against a real local stack for the surrounding pipeline.

A test helper with unique names

Create the topic and group inside the test with a random suffix. Here is a small helper for kafkajs:

// kafka-test.js
import { Kafka } from "kafkajs";
import { randomUUID } from "node:crypto";

export async function setup(partitions = 1) {
  const kafka = new Kafka({
    clientId: "test",
    brokers: (process.env.KAFKA_BROKERS || "localhost:29092").split(","),
  });
  const suffix = randomUUID().slice(0, 8);
  const topic = `test-orders-${suffix}`;
  const groupId = `test-group-${suffix}`;

  const admin = kafka.admin();
  await admin.connect();
  await admin.createTopics({ topics: [{ topic, numPartitions: partitions }] });

  return {
    kafka, topic, groupId,
    async cleanup() {
      await admin.deleteTopics({ topics: [topic] });
      await admin.disconnect();
    },
  };
}

The default replication factor works because the broker has one node. Creating the topic explicitly avoids the auto-create delay and gives you the partition count you want to test.

Wait for the consumer to join before producing

The most common flaky Kafka test produces a message right after calling run and then waits for it. If the consumer has not yet been assigned its partitions, and the group starts from the latest offset, the message is sent before the consumer starts reading and is never seen. Wait for the join event first:

// order.test.js
import { test } from "node:test";
import assert from "node:assert";
import { setup } from "./kafka-test.js";

test("consumer handles an order", async () => {
  const t = await setup();
  const seen = [];
  const consumer = t.kafka.consumer({ groupId: t.groupId });
  const joined = new Promise((r) => consumer.on(consumer.events.GROUP_JOIN, r));

  await consumer.connect();
  await consumer.subscribe({ topic: t.topic, fromBeginning: true });
  await consumer.run({ eachMessage: async ({ message }) => seen.push(message.value.toString()) });
  await joined;

  const producer = t.kafka.producer();
  await producer.connect();
  await producer.send({ topic: t.topic, messages: [{ key: "o-1", value: '{"id":"o-1"}' }] });

  await waitFor(() => seen.length === 1, 10000);
  assert.deepEqual(JSON.parse(seen[0]), { id: "o-1" });

  await producer.disconnect();
  await consumer.disconnect();
  await t.cleanup();
});

async function waitFor(check, ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {
    if (check()) return;
    await new Promise((r) => setTimeout(r, 100));
  }
  throw new Error("timed out waiting for the condition");
}

Using fromBeginning: true is a second guard, so even a message that arrives before the assignment is read. Both together make the test stable. Replace node:test with Jest or Vitest as you like, the shape stays the same.

Test the handler without Kafka at all

Most of your logic needs no broker. If you split the handler out as in the local consumer article, a plain unit test calls it with a fake save. Keep the broker tests for the wiring: serialization, keys, headers and what happens on a failing message. A handful of those cover a lot.

Pitfalls

  • Fixed sleeps. sleep(2000) is too short on a busy laptop and too long everywhere else. Poll with a deadline.
  • Shared group ids. Two tests with the same group split the partitions between them and each misses messages. Unique group per test.
  • Leftover topics. A suite that crashes before cleanup leaves topics behind. The test- prefix lets you list and delete them with kafka-topics.sh --list and --delete, and a fresh volume clears everything.
  • Retention and size. Local test topics are tiny, but a loop that produces millions of messages fills the broker's volume. Delete topics at the end of each test.
  • Key order across partitions. A test that asserts order across several partitions will fail sometimes. Use one partition for such a test, or assert per key, as in keys, partitions and message order.

I did not run this test file against a broker while writing it, so treat the event name and the topic options as the kafkajs API as documented, and run it once on your machine before relying on it.

Questions people ask

Should I use Testcontainers or a shared local broker for Kafka tests?

Use Testcontainers when the test must control the broker, for example to stop it. For tests of your own producers and consumers, one shared broker with a unique topic and group per test is faster.

Why is my Kafka consumer test flaky?

Usually the message is produced before the consumer has joined its group, and the group starts from the latest offset. Wait for the group join event and use fromBeginning true.

How do I keep tests from seeing each other's messages?

Give every test its own topic and its own consumer group id, for example with a random suffix, and delete the topic at the end.
