A nightly loop where a model proposes and a score decides

Let a model suggest changes overnight, but accept one only if a deterministic score improves. This keeps the speed of AI and the trust of tests.

A nightly improvement loop works like this: a model proposes a change on a branch, a script computes a score, and the change is kept only if the score beats the baseline. The model has ideas. The score has the vote.

The shape of the loop

  1. Pick a target with a measurable score: test pass rate, lint count, bundle size, README score, latency of a benchmark.
  2. Record the baseline on the default branch.
  3. Ask a model for one small change aimed at the target.
  4. Apply it on a throwaway branch and run the score again.
  5. If the score improved and all guards pass, open a PR. If not, discard it.

The important property: the decision in step 5 is made by code, not by the model's opinion of its own work.

A minimal script

#!/usr/bin/env bash
set -euo pipefail
base=$(./scripts/score.sh)
git switch -c nightly/$(date +%F)
./scripts/ask-model-for-patch.sh   # writes a patch, applies it
new=$(./scripts/score.sh)
if [ "$new" -gt "$base" ] && npm test; then
  git commit -am "nightly: score $base -> $new"
  gh pr create --fill --label nightly
else
  git switch - && git branch -D nightly/$(date +%F)
fi

The model call is a black box here. Whatever you use, keep it behind one script so you can swap it.

Choose the score carefully

The loop optimises whatever you give it. If the score is "number of tests", it will add useless tests. Use a score that is hard to game and that you trust: a pass rate on tests the model cannot edit, a benchmark of real tasks, or a count of real lint errors. Keep the scoring code and the test fixtures outside the area the model may change. See testing and evaluating AI agents for building such a score.

Limits and safety

  • Run it in a sandbox with no production secrets.
  • Limit the change to a small diff, and the loop to a fixed budget of tries.
  • Always open a PR. Do not push to main. A person reads it, with the score in the description.
  • Stop the loop when it has found nothing for several nights.

Where this idea is used

Flisk uses this guard, eval and loop pattern across its own repositories. The approach and tooling are described in GEL (Guard, Eval, Loop) at gel.flisk.si, with the repo at github.com/flisk-sh/gel. Adopt the pattern even if you do not use the tooling: a score you trust, a loop that proposes, a gate that decides. Pair it with the checks in what is a CI guard.

Questions people ask

Does the model need to be strong for this?

Not necessarily. Since the score filters bad ideas, a modest model with many cheap tries can work, but each try costs time and money, so set a budget.

Can the loop run on my laptop?

Yes. A cron job or a scheduled CI workflow both work. CI is easier to audit.
