How to run a Docker container as a non-root user

Containers run as root unless you say otherwise. Changing that takes four lines, plus a plan for the files the app writes.

To run a container as a non-root user, create a user in the Dockerfile, copy your files with --chown, and switch with USER before the final CMD. The part that trips people up is not the instruction but file ownership: the new user must be able to read your code and write wherever the app writes.

Why bother in development

Root in a container is root on the files you share with it. If a bind mount exposes your project folder and the container runs as root, anything it writes (a build folder, a lockfile, a cache) is owned by root on your machine and your editor cannot delete it. Running as an ordinary user also matches what most production platforms enforce, so a permission problem shows up on your laptop instead of in a deploy.

The Dockerfile

Official Node images already include a user named node (uid 1000), so the shortest version is:

FROM node:22-alpine
WORKDIR /app
COPY --chown=node:node package.json package-lock.json ./
RUN npm ci
COPY --chown=node:node . .
USER node
CMD ["node", "server.js"]

Python and most other images ship no such user, so you create one. On Debian-based images:

FROM python:3.12-slim
RUN groupadd --system app && useradd --system --gid app --create-home app
WORKDIR /app
COPY --chown=app:app requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY --chown=app:app . .
USER app
CMD ["python", "app.py"]

On Alpine the commands are addgroup -S app and adduser -S -G app app. Three details matter:

  • Install packages before USER. apt-get, apk and a global pip install need root.
  • WORKDIR creates the folder as root. If the app writes inside it, run chown on it or create the writable subfolder yourself with mkdir and chown.
  • Use ports above 1024. Binding 80 as a non-root user may be refused depending on the host, and nothing in development needs it.

Permission denied on a bind mount

On Linux, a bind mounted folder keeps the numeric owner from the host. If your host user is uid 1000 and the container user is uid 10001, the container cannot write to it. Two ways out: build the image with a user whose uid matches yours, or override the user at run time:

docker run --user "$(id -u):$(id -g)" -v "$PWD:/app" myimage

In Compose, set user: "${HOST_UID}:${HOST_GID}" and export those two variables from id -u and id -g (or put them in .env). On Docker Desktop for Mac and Windows the file sharing layer maps ownership for you, so this problem tends to appear only on Linux and in CI. That is a reason to test it on Linux at least once.

Named volumes behave differently. When Docker creates a named volume and mounts it at a path that exists in the image, it copies the image's content and ownership into the volume the first time. If you chown that folder in the Dockerfile, the volume starts out writable by your user.

Setting the user in Flisk

If you bring your own container to a Flisk stack and cannot or do not want to change its image, set the user in service.json instead. A container block turns into the matching Compose keys:

{
  "schemaVersion": 1,
  "appName": "web",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4000,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile",
  "container": {
    "user": "10001:10001",
    "readOnly": true,
    "tmpfs": ["/tmp"],
    "capDrop": ["ALL"],
    "securityOpt": ["no-new-privileges:true"]
  }
}

user becomes Compose's user, readOnly becomes read_only and tmpfs gives a writable in-memory /tmp to a read-only root. The block applies to bring-your-own resources only, and flisk config verify names any key it does not know. Flisk does not change the image itself, so a USER line in your Dockerfile and a user here are two separate settings, and the Compose value wins at run time.

Pitfalls

  • A read-only root breaks apps that write to their own folder. Give them a tmpfs or a volume for the places they write, such as /tmp and a cache folder.
  • Numeric users need an entry to have a home directory. Some tools read $HOME. With an arbitrary uid and no passwd entry, npm or pip may fail trying to write a cache. Set HOME to a writable path.
  • Dev tools that install at run time (an npm install in the entrypoint) need a writable node_modules. Install in the image instead.
  • Do not chmod 777 to make the error go away. Find which path the app writes and own that one.

Next step

If the container still exits at start-up after you switch user, read why a container keeps restarting and check the logs for a permission error. Then look at bind mounting source code for the development loop.

Questions people ask

Does USER in the Dockerfile affect RUN commands before it?

No. Instructions before USER run as root, instructions after it run as the new user. Install system packages before USER and switch as late as possible.

Why do I get permission denied on a bind mount only on Linux?

The mounted folder keeps its host uid and gid. If the container user has a different uid it cannot write. Run the container with your uid, or make the image user match. Docker Desktop on Mac and Windows hides this mismatch.

Can I set the user without editing the image in Flisk?

Yes, for a bring-your-own resource. Add a container block with user, for example 10001:10001, to service.json. It becomes the Compose user setting.
