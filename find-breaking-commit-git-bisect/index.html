How to Find the Commit That Broke CI with git bisect

Use git bisect with a script that exits non-zero on failure to find the first bad commit in a few steps instead of reading a long diff.

Run git bisect start, mark the current commit bad and an older passing commit good, and let git check out the commits between them. With a test script and git bisect run, git finds the first bad commit by itself, in about log2 of the number of commits.

Start the bisect

You need one commit that fails and one older commit that passes. The last green CI run gives you the good commit.

git bisect start
git bisect bad HEAD
git bisect good LAST_GREEN_SHA

Git checks out a commit in the middle. Run the failing check, then tell git the result with git bisect good or git bisect bad. Repeat until git prints the first bad commit.

Automate it with a script

Write a script that exits 0 when the commit is good and non-zero when it is bad. Exit code 125 tells bisect to skip a commit that cannot be tested, for example one that does not build for an unrelated reason.

#!/usr/bin/env bash
set -e
npm ci
npm test -- path/to/failing.test.js
git bisect run ./bisect.sh

Keep the script outside the repository, or untracked, so checking out other commits does not remove it. Run only the smallest check that shows the failure. A full suite on twenty commits is slow.

Handle merge commits and noisy history

If the history has many merge commits, a first-parent bisect can help find which pull request broke things, then you bisect inside that branch.

git bisect start --first-parent

With squash merges, each commit on main is a whole pull request, and bisect gets there faster. If broken intermediate commits exist (a commit that does not compile), mark them with git bisect skip.

Finish and clean up

When git names the first bad commit, read its diff. Then end the session so you return to your branch:

git bisect log
git bisect reset

git bisect log prints what you did, which you can paste into the issue. Confirm the finding by reverting that commit on a branch and running the test. If it turns green, you have your cause.

A worked example

Say the last green run was at commit a1b2c3 and 40 commits landed since. Bisect needs about six steps. Start the session, mark the endpoints and run the script. Git prints something like 'abc123 is the first bad commit' along with its message and files. Open that commit, look at the changed files that relate to the failing test, and you usually see the cause in a minute. Compared with reading 40 diffs, this saves a lot of time, and the written log is a good attachment for the revert pull request.

When bisect gives the wrong answer

Bisect assumes the failure is deterministic. A flaky test makes it point at a random commit. Run the check a few times per commit in your script if you suspect that, or confirm first with the regression or environment checks. A dependency that changed outside the repo also breaks the assumption, because old commits start failing too. In that case, bisect the lockfile or the dependency version instead of the code.

Questions people ask

How many steps does git bisect need?

About the base-2 logarithm of the number of commits in the range. For 1000 commits that is around 10 steps.

What does exit code 125 mean in bisect run?

It tells git to skip the current commit because it cannot be tested, for example because it does not build.
