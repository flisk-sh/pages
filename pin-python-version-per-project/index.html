Python local development setup

How to pin the Python version for a project (pyenv, uv, mise)

A project that works on 3.12 and fails on 3.9 is a project nobody pinned. Pinning takes three small files and saves hours of confusing bug reports.

Pin the Python version in three places: a .python-version file that version managers read, requires-python in pyproject.toml so installers refuse a wrong interpreter, and the version used by CI and your Dockerfile. When all three say 3.12, a teammate on 3.9 gets a clear error on day one instead of a strange one on day ten.

Why a pin matters

Python minor versions change behaviour in small ways: syntax such as match arrived in 3.10, typing features keep moving, and some packages ship wheels for only certain versions. Code that runs on your laptop under 3.12 can fail on another machine with a syntax error or a missing wheel. The symptom looks like a bug in your code. The cause is the interpreter.

Pick a version manager

You need something that can install and switch interpreters. Any of these is fine:

  • pyenv: pyenv install 3.12 then pyenv local 3.12, which writes .python-version in the current folder.
  • uv: uv python install 3.12 then uv python pin 3.12, which also writes .python-version.
  • mise (or asdf): mise use python@3.12 writes the pin to its own config file in the folder.
  • The system Python: fine if your whole team runs one OS image, which is rare.

Pick one for the team and say so in the README. The point is not the tool but that the pin lives in the repository.

The three places to say it

First, the version file:

3.12

Put that single line in .python-version. Writing 3.12 pins the minor version, and 3.12.4 pins the patch release. Most teams pin the minor version and let patch releases float.

Second, pyproject.toml:

[project]
name = "api"
version = "0.1.0"
requires-python = ">=3.12,<3.13"

This is a guard, not an installer. pip and uv refuse to install the project on an interpreter outside the range, with a message that names the problem.

Third, CI and Docker. In GitHub Actions, actions/setup-python can read the same file with python-version-file: .python-version. In a Dockerfile, use a matching tag such as python:3.12-slim. One number in three places will drift unless someone owns it, so update them in the same commit when you upgrade.

Checking the pin with Flisk

When a service in Flisk has a command, it runs on your host with whatever Python is on your PATH. You can state the version the command needs with the toolchain field:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "toolchain": "python@3.12",
  "command": "uvicorn main:app --reload --port $PORT",
  "port": 4000,
  "healthCheckPath": "/health"
}

flisk doctor and flisk up compare that with the python3 (or python) program on your PATH. Every part you give must match, so python@3.12 accepts 3.12.4 and rejects 3.9. On a mismatch, flisk up stops before it starts anything and names the service, the version it wants and the version it found, for example:

api: wants python@3.12 (service.json), python 3.9.6 is on PATH
Switch to that version with your version manager, or change "toolchain" in the service.json.

Flisk installs nothing, so the fix is to switch with pyenv, uv, mise or whichever you chose. If you leave toolchain out but have a .python-version in the service folder, Flisk reads it as a hint. A mismatch then produces a warning in flisk doctor and never stops flisk up. Use toolchain when you want the check to be binding. The format is python@3.12, and a value that does not look like tool@version is reported as an error.

These checks apply to local-process services. A container service gets its Python from its image, so the Dockerfile tag is its pin.

Pitfalls

  • A shell that ignores the pin. pyenv shims and mise hooks must be set up in your shell profile, or python still resolves to the system copy. Check with python --version inside the project folder.
  • A venv built on an old interpreter. After changing the pin, delete .venv and recreate it. A venv remembers the interpreter that made it.
  • Pinning too tightly. ==3.12.4 in requires-python blocks security patch updates for no benefit.

Next step

After pinning, rebuild the environment as described in one virtual environment per project. If you also run Node in the same repository, Python and Node in one repo shows both toolchains side by side.

Questions people ask

What is the difference between .python-version and requires-python?

.python-version tells version managers which interpreter to select. requires-python in pyproject.toml tells installers which interpreters the project supports, and they refuse others.

Does Flisk install the Python version I ask for?

No. The toolchain field in service.json only checks the python on your PATH and stops flisk up on a mismatch. Install and switch versions with your own version manager.

Should I pin the patch version too?

Usually not. Pinning the minor version, such as 3.12, keeps behaviour stable while allowing security patch releases.
