NestJS local development: watch mode and CORS

NestJS adds modules and decorators on top of Express. Here is how to run it in watch mode, expose a health check and allow a local frontend.

The standard way to run NestJS in development is nest start --watch, which recompiles and restarts on every change. For a local stack you also want a health route, a port from the environment, and CORS for the frontend origin. Flisk scaffolds a NestJS API with all three, running on Bun with bun run --watch.

What a local NestJS service needs

NestJS is built on decorators. Controllers, modules and injection all depend on TypeScript decorator support, so the compiler flags experimentalDecorators and emitDecoratorMetadata must stay on. Beyond that, a local service needs the same four things as any API: restart on save, a port from PORT, a route that says the service is alive, and a CORS rule so a browser app on another origin can call it.

The plain approach

npm i -g @nestjs/cli
nest new orders
cd orders
npm run start:dev

start:dev runs nest start --watch. Add a health controller and CORS in main.ts:

const app = await NestFactory.create(AppModule);
app.enableCors({ origin: 'http://localhost:5173' });
await app.listen(Number(process.env.PORT) || 3000);

For production-grade readiness checks the Nest project offers @nestjs/terminus, which can check a database or a downstream service. For local work a simple /health controller is often enough.

The Flisk way

npm install -g @flisk-sh/flisk
flisk resource orders --framework nestjs --stack app --yes
flisk up

The scaffold is a single src/index.ts with a controller, a module and a bootstrap() function. It depends on @nestjs/common, @nestjs/core and @nestjs/platform-express (version 11), plus reflect-metadata and rxjs. The controller answers GET /health, GET /health/live and GET /. Its dev script is bun run --watch src/index.ts, so an edit restarts the process, and the service's service.json lists src/**/* as the files to watch.

Two lines in bootstrap() matter for a local stack:

app.enableCors({ origin: LOCAL_FRONTEND_ORIGIN });
await app.listen(port, '0.0.0.0');

The first allows any *.localhost origin, which is the shape of Flisk's frontend URLs (http://app.<project>.localhost). The second binds all interfaces, because Traefik reaches the container over the Docker network. The URL of the API is http://api.<project>.localhost/api/orders, and Flisk strips /api/orders before the request reaches Nest, so declare your routes without the prefix, with @Get('items') and not @Get('orders/items'). Use flisk networks to see the exact addresses.

Add routes the normal way: new controllers go into the module's controllers array. As the app grows, split it into feature modules and files, as in any Nest project. Run the tests with the scaffold's test script, which uses Vitest.

Grow the app past one file

The scaffold keeps everything in src/index.ts so the first run is easy to read. A real service follows the usual Nest layout: one folder per feature with a module, a controller and a service, and the feature module imported by AppModule. Inject the service into the controller through its constructor, and keep database or HTTP calls inside the service so controllers stay thin. For request bodies, a ValidationPipe with class-validator rejects bad input before it reaches your code, which saves a lot of defensive checks. None of this depends on Flisk, and the watch mode picks up new files without any change to the setup. Because the scaffold watches everything under src/, a new feature folder needs no extra configuration, and a test for each service can sit beside it.

Pitfalls

  • Keep the decorator flags. The scaffold's tsconfig.json sets experimentalDecorators and emitDecoratorMetadata. Removing them breaks controllers. For class dependencies, an explicit @Inject() keeps injection from depending on emitted metadata.
  • A CORS rule for your own frontend. The scaffold allows *.localhost. A frontend on http://localhost:5173 is not covered, so add that origin or use a dev proxy.
  • Binding to 127.0.0.1 inside a container. The service looks healthy in its own logs and is unreachable from Traefik. Listen on 0.0.0.0.
  • A heavy framework for a tiny service. If the service has three routes, Hono or Express is less code. NestJS pays off when several people share a codebase and want enforced structure.
  • No readiness route in the scaffold. It has /health and /health/live. If your dependencies need a deeper check, add /health/ready yourself.

Questions people ask

How do I run NestJS in watch mode?

Use nest start --watch (the start:dev script in a Nest CLI project). The process recompiles and restarts when you save a file.

How do I allow a local frontend to call my NestJS API?

Call app.enableCors with the frontend origin, for example http://localhost:5173, in main.ts. Flisk scaffolds a rule that allows any *.localhost origin.

Why is my NestJS container unreachable although it logs that it started?

The server is probably listening on 127.0.0.1. In a container call app.listen(port, "0.0.0.0") so the proxy can reach it over the Docker network.
