How to restart an AI agent without losing conversation state

Restarting an agent should cost you a few seconds, not a conversation. This is how to make that true and how to prove it.

An agent survives a restart when its conversation is saved outside the process before each reply is sent, and when the storage outlives the container. The Flisk agent does both: it writes a checkpoint per session to a named Docker volume (or to Postgres) and saves before it answers. flisk restart assistant and flisk down keep the volume. Only flisk down --purge or removing the volume deletes sessions.

What a restart really destroys

When a container stops, everything in its writable layer and in process memory is gone. For an agent that includes the conversation history if you kept it in a variable, any cache of tool results, and any turn that was still running. So there are three places state can live, and only some of them survive:

  • Process memory. Lost on every restart. Fine for caches, wrong for conversations.
  • The container filesystem. Lost when the container is removed and recreated, which Compose does when the image or configuration changes.
  • A volume or a database. Kept. This is where checkpoints belong.

The same rule applies with plain Docker Compose: mount a named volume, or use a database service. The details of volume lifetimes are in keeping volumes between runs.

Where the Flisk agent keeps its state

An agent made with flisk resource assistant --type agent --stack shop --yes uses the files option by default. Each session is a JSON file at /var/lib/flisk-agent/<sessionId>.json (the path comes from AGENT_STATE_DIR), on a named volume called <project>-<stack>-autogenerated_<resource>-agent-state. Writes go to a temporary file first and are renamed over the old one, so a crash in the middle of a save does not leave a half-written checkpoint. With --durability postgres the same data is a row in flisk_agent_sessions.

The order inside a turn is what makes this safe. The agent loads the checkpoint, adds your message, runs the turn, adds the reply, saves, and only then responds. A reply you received has been stored.

Test it, do not assume it

With the stack up, create a conversation and restart the agent:

curl -s -X POST http://localhost:4000/turn \
  -H 'x-session-id: demo' -H 'content-type: application/json' \
  -d '{"input":"first"}'

flisk restart assistant

until curl -fs http://localhost:4000/ready > /dev/null; do sleep 1; done
curl -s -X POST http://localhost:4000/turn \
  -H 'x-session-id: demo' -H 'content-type: application/json' \
  -d '{"input":"second"}'

Use the URL that flisk status prints if your agent is behind the local router. The second reply should report "turns":2, not 1. You can also run flisk agent sessions assistant --session-id demo and see both messages, see inspect agent sessions. Put this check into a test that runs in CI, because it is the one that catches a missing volume.

What happens during the restart

On SIGTERM the agent drains: it refuses new turns with 503, lets running turns finish, and exits with code 0, by default within 10 seconds (DRAIN_TIMEOUT_MS). Wait for /ready to return 200 before sending the next turn, as in the loop above. A turn that is still running when the time limit passes is cut off. Its reply was never sent and never saved, so the client should treat a dropped connection as "not done" and send the turn again.

That retry is why turns should be safe to repeat. If a tool call has a side effect, such as sending an email, put an idempotency key on it, because a retried turn will call it again.

How to delete state when you want to

  • One session: DELETE /session with the x-session-id header. It answers 409 turn_in_flight if a turn is running.
  • Old sessions: an idle sweep removes sessions untouched for 24 hours, set by SESSION_IDLE_TIMEOUT_MS, checked every hour by default (SESSION_CLEANUP_INTERVAL_MS). It skips a session with a turn in flight.
  • Everything: flisk down --purge deletes the project's Docker volumes. To remove only the agent's volume, use docker volume rm with the volume name.

Pitfalls

  • A volume is not a backup. It lives on one machine, and a disk problem takes it with it.
  • Do not rename the volume casually. A different name is a different volume, and the old sessions stay behind.
  • Memory caches reset. If your runTurn keeps something in memory that the next turn needs, move it into the checkpoint.
  • Frameworks differ. If you wrap a framework such as a LangGraph or Mastra agent, its own storage setting decides what survives, not the generated one. See a LangGraph agent stack.

Questions people ask

Does flisk restart delete agent sessions?

No. The checkpoints are on a named volume or in Postgres, and both outlive the container. Only flisk down --purge or removing the volume deletes them.

What happens to a turn that is running when the agent restarts?

The agent drains for up to 10 seconds by default. A turn still running after that is cut off, its reply is never sent or saved, and the client should send it again.

How do I check that state really survived?

Send a turn, restart the agent, wait for /ready, send a second turn with the same x-session-id and check that the reply reports turns 2.
