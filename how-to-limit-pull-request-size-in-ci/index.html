How to Limit Pull Request Size in CI

Agents can write thousands of lines in one go. A small size check in CI keeps pull requests reviewable and easy to revert, with a labelled escape hatch.

Add a CI step that counts changed lines against the base branch and fails above a limit, with an explicit label to override. Small pull requests get reviewed properly; large ones get skimmed and approved.

Why size matters more with agents

People rarely write a 3,000-line change in an afternoon. An agent can. Reviewers then approve without reading, and the bugs show up in production. A hard limit changes the agent's behaviour: it splits the task, which is what you want.

A simple size check

Count added plus deleted lines, ignoring generated files and lockfiles.

git fetch origin main
CHANGED=$(git diff --numstat origin/main...HEAD -- . ':!*.lock' ':!package-lock.json' ':!dist' \
  | awk '{s+=$1+$2} END {print s+0}')
echo "changed lines: $CHANGED"
[ "$CHANGED" -le 600 ] || { echo 'PR too large, split it'; exit 1; }

Pick a limit from your own history. Look at the median size of pull requests that were reviewed well and set the limit a bit above it.

Wire it into a workflow

jobs:
  size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: bash scripts/pr-size.sh

The full history fetch is needed so the diff against the base works. Make this check required once you trust it.

Allow a labelled exception

Some changes are big and fine: a rename, a vendored file, a generated client. Let a maintainer add a label such as size-override and skip the check when the label is present. Only maintainers should be able to add labels, otherwise the agent can add it itself.

Ask the agent for stacked changes

In AGENTS.md, say that large tasks should be split into a sequence of small pull requests, each passing CI. Smaller changes also revert cleanly and make a merge queue more efficient; see setting up a merge queue.

Beyond line counts

Lines changed is a blunt measure. Files touched and directories touched are often better signals of review difficulty. A 200-line change across 25 files in six folders is harder to review than 400 lines in one file. Add a second limit on the number of top-level folders changed, and ask for a split when a pull request spans unrelated areas.

git diff --name-only origin/main...HEAD | cut -d/ -f1 | sort -u | wc -l

Report the numbers in the pull request as a comment rather than only failing, so the agent and the reviewer see them: files, lines, folders. Make the message actionable by telling the agent what to do, for example to split into one pull request per folder.

Review the limits twice a year against your real data. If everything passes easily, lower the limit. If people constantly use the override, raise it or fix the underlying reason, such as a large generated file that should be excluded.

Questions people ask

What limit should I use?

There is no universal number. Many teams start between 400 and 800 changed lines excluding generated files, then adjust from their review history.

Should tests count toward the limit?

You can count them, but many teams exclude test files so the check does not discourage writing tests.
