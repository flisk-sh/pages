Prompts and structured outputs

How to get reliable JSON from an LLM

Ask for a schema, use the provider's structured output feature where it exists, validate every reply in code, and retry with the error. The full recipe with code.

Describe the exact shape you want, use your provider's structured output or tool-call feature to enforce it, and validate the result in your own code before using it. Treat model output as untrusted input, even when it looks perfect.

Layer 1: say what you want

Even with enforcement, a clear instruction helps the content, not just the shape. State the fields, their types and what each means. Give one short example. Say what to do when information is missing, for instance "use null, never guess".

Extract the order from the email. Reply with JSON only:
{"order_id": string, "items": [{"sku": string, "qty": integer}],
 "ship_to_country": string or null}
If a value is not in the email, use null.

Layer 2: let the API enforce it

Most major providers offer a way to constrain output to a JSON Schema: a structured output or response-format option, or a forced tool call whose arguments are the schema. Local servers such as Ollama accept a schema too. Check your provider's docs for the exact parameter, because names and supported schema features differ. The next article compares the options: JSON mode vs structured outputs vs function calling.

Layer 3: validate in code

Enforcement guarantees syntax, not truth. A valid object can still hold a wrong date or an invented SKU. Parse and check it yourself.

import json
from pydantic import BaseModel

class Item(BaseModel):
    sku: str
    qty: int

class Order(BaseModel):
    order_id: str
    items: list[Item]
    ship_to_country: str | None

order = Order.model_validate_json(reply_text)

Then apply business rules: does the SKU exist, is qty positive, is the country code known?

Layer 4: retry with the error

If validation fails, send the error back once or twice and ask for a corrected reply. Cap the attempts. See how to retry when an LLM returns invalid JSON.

Pitfalls

  • Stripping code fences with a regex and hoping. Prefer enforcement to cleanup.
  • Deep, large schemas. Keep them flat and small; models fill simple shapes more accurately.
  • Free-text fields inside the JSON that you then parse again. Add real fields instead.
  • Trusting the result because it parsed. It is still model output, so validate it before it touches a database or a shell.

A test to run

Collect 50 real inputs, run the pipeline, and count: parsed, passed validation, passed business rules. Track the three numbers over time. A drop after a model or prompt change is your signal to look. For tooling that keeps these checks in CI, see how to test prompts before you ship changes.

Questions people ask

Is JSON the best format for model output?

It is the most widely supported, and parsers are everywhere. For simple answers, a single label or a short list of lines can be more reliable than JSON.

Can I rely on the model to never break the schema?

With enforced structured output the syntax is guaranteed by the provider, but you should still validate meaning. Without enforcement, expect occasional failures and handle them.
