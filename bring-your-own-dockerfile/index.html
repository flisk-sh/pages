Run an existing Dockerfile in a local dev stack

Not every service is written from a template. This is how to bring a container you already have into a local stack and what you give up.

Any service with a Dockerfile or a published image can join a local stack if it listens on the port you give it, binds 0.0.0.0, and answers 200 on a health path. With Flisk this is the bring-your-own resource type: you keep your Dockerfile, Flisk adds routing, health checks, start order and logs.

What a container must do to fit a stack

A local stack tool does not need to understand your language. It needs a contract: a port to reach, a way to ask if the service is healthy, and a way to configure it. The container contract is small:

  • Listen on the port from $PORT (or a fixed port you declare), and bind 0.0.0.0, not 127.0.0.1.
  • Answer a plain HTTP request with status 200 on a health path such as /health.
  • Read configuration from environment variables.
  • Provide a Dockerfile, or an image name to pull.

If a service already runs under Docker Compose, it almost certainly meets this. If it does not, a small change (a health route, a bind address) usually fixes it. See importing a Compose file if you have a whole docker-compose.yml to move.

Without Flisk

In Compose, you write a service block with build, ports, environment and a healthcheck. That is a good answer when you only have a handful of containers, and you keep full control. You choose host ports, avoid collisions yourself and write any reverse proxy rules by hand.

The Flisk way

npm install -g @flisk-sh/flisk
flisk resource legacy --type bring-your-own --stack app \
  --dockerfile ./Dockerfile --health-path /health \
  --path services/app/legacy --yes

If the folder already has a Dockerfile, Flisk keeps it and does not overwrite it. It writes a service.json like this:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "legacy",
  "appType": "bring-your-own",
  "stack": "app",
  "port": 4003,
  "healthCheckPath": "/health",
  "dockerfile": "./Dockerfile"
}

Set port to the port your container really listens on. flisk resource suggests the next free port in 4000 to 5999 when you do not pass one, and --port accepts an unused integer in that range. If you have a ready-made image, pass --image <name> instead of a Dockerfile. The build context is the resource directory unless you set buildContext to a path relative to it, which is useful when the Dockerfile lives in a larger source tree. When you do not provide a Dockerfile at all, Flisk writes a small Nginx one with a health endpoint, which is only a placeholder.

flisk up

Routing: an API or a web UI

A routed resource is reached at http://api.<project>.localhost/api/<name>, and Flisk strips /api/<name> before the request reaches your container. That suits an API. An app that serves its own pages and assets from / cannot work under a prefix, so set "webUi": true and it gets its own host, <name>.<project>.localhost, with nothing stripped. Use flisk networks to print the real addresses. To skip the route entirely, scaffold with --no-proxy.

Other fields you will need

  • One-shot jobs. A container restarts by default, so a job that exits cleanly starts again. Use --restart no for migrations or seeders. A service that depends on such a job starts only after the job exits with code 0.
  • Environment and secrets. Use env and secrets in service.json, and keep .env out of version control.
  • Volumes and runtime options. volumes, a container block (capabilities, read-only, user, shared memory) and extraPorts cover most special cases.

The repository has runnable examples under examples/byo/.

What you give up, and pitfalls

  • No live reload. A bring-your-own service is rebuilt as an image. After a code change, rebuild it from the Tilt UI or restart flisk up. For a fast loop, use a language provider that has a watcher (Go has one) or run the service as a local process.
  • Nothing is published on the host. You reach the service through its URL, not through localhost:<port>. Add extraPorts only if you need one.
  • A Postgres DATABASE_URL is set in every container. If your app reads that variable for something else, override it in env.
  • The Host header is api.<project>.localhost. Frameworks with host allow lists, such as Rails, reject it until you allow it.
  • A cold Docker cache is slow. The first build pulls every layer.
  • Names must be unique. Resource names have to be unique across Flisk projects on one Docker daemon.
  • CORS. A frontend served at http://app.<project>.localhost calling your container needs that origin allowed in your own code.

Next step

Check the result with flisk status and flisk config verify. If the service is a frontend in a framework Flisk does not scaffold, such as Nuxt or SvelteKit, this is the route to use, and Vue or Svelte with an API explains how it finds the backend.

Questions people ask

Can I use my own Dockerfile with Flisk?

Yes. Create the resource with --type bring-your-own and --dockerfile ./Dockerfile. Flisk keeps your Dockerfile and adds routing, health checks and start order around it.

Can I use a published image instead of a Dockerfile?

Yes. Pass --image with the image name when you create the resource, and Flisk runs that image with the same routing and health check.

Does a bring-your-own service reload when I edit code?

No. It is a container image, so rebuild it from the Tilt UI or restart flisk up.
