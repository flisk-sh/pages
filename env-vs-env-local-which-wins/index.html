Env vars and secrets in local dev

.env vs .env.local vs .env.development: which one wins?

A variable defined in three places has one effective value. Here is the order each common tool uses, and a way to check yours.

The shell wins over every file, and among files the more specific one wins: a mode file such as .env.development beats the generic .env, and a .local file beats its non-local twin. That is the rule in Vite and Next.js. Docker Compose and Flisk have their own orders, so a name defined in two places is worth checking, not guessing.

The order in the tools you probably use

ToolHighest to lowest
ViteVariables already in the environment, then .env.[mode].local, .env.[mode], .env.local, .env
Next.jsprocess.env, .env.$(NODE_ENV).local, .env.local (skipped when NODE_ENV is test), .env.$(NODE_ENV), .env
Node.js --env-fileThe existing environment, then the files, where a later --env-file overrides an earlier one
dotenv (npm package)Does not override a variable that is already set, unless you pass override: true

The common thread is that a value you export in the shell for one command is the strongest. That is useful for a quick test and a trap when you exported something last week and forgot.

The usual convention for .local files is that they hold one developer's overrides and are never committed, while .env and .env.development hold shared, non-secret defaults. Keep to that and the question "which one wins" mostly answers itself: your .local file wins, and teammates do not see it.

Docker Compose is different

Compose uses .env to fill in ${NAME} placeholders in the Compose file. That is a separate job from putting variables into a container. For a variable inside the container, the documented order is: docker compose run -e, then a value set with environment:, then env_file:, then ENV in the image. For interpolation, the shell beats the .env file. The next article, Compose env_file vs environment, goes through this in detail.

The order in Flisk

Flisk has a project .env (gitignored) and, per service, a few ways to add to it. These rules come from its environment documentation:

  • Local-process services (those with a command): ${VAR} and ${VAR:-default} inside env resolve in this order, first match wins: your shell, the project .env, the service's own .env next to its service.json, then the default. A missing service .env is ignored.
  • Container services: inside one container, the compose environment: entry beats the service env file generated from params. The secrets come from the env file of the run, and for keys that file defines, it wins over the value exported in your shell. A key the file does not define keeps the shell's value.
  • One run with other values: flisk up --env-file .env.integration replaces the project .env for that run. It is not merged. The file must be inside the project and carry TILT_ENV, DB_PASSWORD and JWT_SECRET, and a running stack refuses it until you flisk down or add --force.

A concrete example for a plain process, where a developer's port override sits in a service-level file:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "web",
  "appType": "frontend",
  "command": "npm run dev",
  "port": 3000,
  "env": { "API_URL": "http://localhost:${API_PORT:-4000}" }
}

With nothing set, API_URL is http://localhost:4000. A developer puts API_PORT=4100 in a .env next to the service, and it wins over the default, but loses to API_PORT exported in the shell. No edit to the committed manifest is needed.

How to see which one won

  1. Print the value in the process: flisk run web -- printenv API_URL, or printenv inside a container.
  2. If it is wrong, unset it in the shell first: env -u API_PORT flisk run web -- printenv API_URL. If the value changes, the shell was the culprit.
  3. Search the project for the name: grep -rn "API_PORT" . --include=".env*" --include="service.json".

Pitfalls

  • Flisk's generated .gitignore lines are .env, .env.* and !.env.example, so every variant except the example stays out of git. If your team wants to commit a shared .env.development, that pattern will ignore it. See gitignoring env files safely.
  • A name listed in secrets and also set in params or env uses the literal and ignores the secret from .env. flisk config verify warns about it.
  • Frontend variables are read when the dev server starts. Restart it after a change.

If a value still looks wrong after this, the checklist in environment variable not loaded picks up where this one ends.

Questions people ask

Does .env.local override .env?

In Vite and Next.js, yes: the .local file is read with higher priority than the generic .env. Variables already set in the shell beat both.

Does a shell variable beat a value in .env?

In Vite, Next.js, Node.js --env-file and the dotenv package, yes by default. In Flisk's local-process services the shell is also first. For container secrets, the env file of the run wins over the shell for keys it defines.

Can I merge two env files in Flisk?

Not with flisk up --env-file. The selected file replaces the project .env for that run and the two are not merged, so copy .env first and edit the copy.
