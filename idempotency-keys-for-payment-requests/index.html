How to add idempotency keys to a payment API endpoint

A client that times out will retry, and a customer who is impatient will click twice. An idempotency key turns both into the same single charge.

To make a payment endpoint safe to retry, require an Idempotency-Key header, store the key with a hash of the request in a table with a unique constraint, run the charge only for the request that inserted the key, and give every later request with that key the saved response. A retry after a timeout then repeats the answer instead of the charge.

What goes wrong without a key

A POST that creates a charge is not safe to repeat. Three ordinary events repeat it anyway:

  • The client sends the request, the server charges the card, and the response is lost. The client retries.
  • The customer double-clicks "Pay".
  • A mobile client resends a queued request after reconnecting.

In each case the server cannot tell a retry from a second purchase, because the two look identical. The client has to say which it is, and the key is how it says so: the same key means "this is the same attempt".

The rules your endpoint needs

  1. The client generates the key, usually a UUID, once per user intent, and reuses it for every retry of that intent.
  2. The same key with the same request returns the saved result, including a saved error, without doing the work again.
  3. The same key with a different request body is a client bug. Refuse it with a 422 rather than guessing.
  4. The same key while the first request is still running returns 409, so two parallel requests cannot both charge.
  5. Keys expire. Stripe keeps its keys for at least 24 hours. Pick a window that covers your longest realistic retry.

A table and a handler

CREATE TABLE idempotency_keys (
  key           text PRIMARY KEY,
  request_hash  text NOT NULL,
  status        text NOT NULL DEFAULT 'started',   -- started | done
  response_code int,
  response_body jsonb,
  created_at    timestamptz NOT NULL DEFAULT now()
);

The unique primary key does the real work. Two parallel requests race on the insert, and the database lets exactly one win:

import { createHash } from "node:crypto";

app.post("/payments", async (req, res) => {
  const key = req.get("idempotency-key");
  if (!key) return res.status(400).json({ error: "Idempotency-Key required" });

  const hash = createHash("sha256").update(JSON.stringify(req.body)).digest("hex");

  const ins = await db.query(
    `INSERT INTO idempotency_keys (key, request_hash)
     VALUES ($1, $2) ON CONFLICT (key) DO NOTHING RETURNING key`,
    [key, hash]);

  if (ins.rowCount === 0) {
    const { rows: [row] } = await db.query(
      "SELECT * FROM idempotency_keys WHERE key = $1", [key]);
    if (row.request_hash !== hash) return res.status(422).json({ error: "key reused with a different request" });
    if (row.status === "done") return res.status(row.response_code).json(row.response_body);
    return res.status(409).json({ error: "request in progress" });
  }

  // First request with this key: do the work, passing a stable key downstream
  const intent = await stripe.paymentIntents.create(
    { amount: req.body.amount, currency: "usd", payment_method: req.body.pm, confirm: true },
    { idempotencyKey: "order-" + req.body.orderId });

  const body = { id: intent.id, status: intent.status };
  await db.query(
    "UPDATE idempotency_keys SET status = 'done', response_code = 200, response_body = $2 WHERE key = $1",
    [key, body]);
  res.json(body);
});

Two details matter here. First, the downstream key is derived from your own order, not copied from the client, so even if your own table were lost the provider would still refuse a second charge for the same order. Second, a request that crashes between the insert and the update leaves a row stuck in started. Decide what that means for you: a sweeper that clears old started rows, or a timestamp check that lets a retry take over after a minute.

Testing it locally with Flisk

This needs a real Postgres, because the guarantee comes from the unique constraint and a mock would hide a missing one. Flisk can run your API as a local process and Postgres as a ready-made image beside it. Install with npm install -g @flisk-sh/flisk. The Postgres service, in postgres/service.json:

{
  "schemaVersion": 1,
  "appName": "postgres",
  "appType": "bring-your-own",
  "image": "postgres:17-alpine",
  "port": 5432,
  "env": { "POSTGRES_USER": "${POSTGRES_USER}", "POSTGRES_PASSWORD": "${POSTGRES_PASSWORD}", "POSTGRES_DB": "app" },
  "healthCheck": { "command": ["pg_isready", "-U", "${POSTGRES_USER}"] },
  "volumes": [{ "source": "postgres", "target": "/var/lib/postgresql/data", "name": "pay_postgres" }]
}

And the API, in api/service.json:

{
  "schemaVersion": 1,
  "appName": "api",
  "appType": "backend",
  "command": "node server.js",
  "port": 4000,
  "healthCheckPath": "/health",
  "dependsOn": ["postgres"],
  "env": {
    "DATABASE_URL": "postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@localhost:5432/app",
    "STRIPE_SECRET_KEY": "${STRIPE_SECRET_KEY}"
  }
}

Put POSTGRES_USER, POSTGRES_PASSWORD and the Stripe test key in the project .env. Docker must be running for the Postgres image, and the API needs only Node. flisk up starts the database first and the API once the database answers pg_isready. The mount path above is right for Postgres 17 and older; from Postgres 18 it must be /var/lib/postgresql.

Then fire the same request twice at once:

for i in 1 2; do
  curl -s -X POST http://localhost:4000/payments \
    -H "Idempotency-Key: demo-123" -H "Content-Type: application/json" \
    -d '{"amount":2000,"pm":"pm_card_visa","orderId":"o-1"}' &
done; wait

Expect one 200 and one 409, or two identical 200 responses if the first finished before the second arrived. Either way, the Stripe dashboard in test mode shows one payment. Run it again with a different amount and the same key to see the 422.

Pitfalls

  • Hashing the parsed body. Two equal requests with different key order hash differently. Canonicalize the JSON, or hash only the fields that define the intent.
  • Saving only successes. If you save nothing for a failed charge, a retry charges again after a decline that already happened. Save the outcome, then let the client choose a new key to try again.
  • Keys scoped globally. Scope the key to the authenticated account, or one customer can collide with another's key.
  • Applying it to GET. Reads are already safe to repeat. Stripe ignores the header on them.

The key stops duplicate requests. It does not stop duplicate events coming back the other way, which is a separate problem: handling out-of-order payment webhooks covers that side. Database setup details are in running Postgres locally.

Questions people ask

What is an Idempotency-Key header?

A unique value the client sends with a POST so the server can recognise a retry. The server runs the operation once for that key and returns the saved response for repeats.

Who should generate the idempotency key?

The client. It creates one key per user action, for example a UUID, and reuses it on every retry of that action. A server that makes up its own key cannot tell a retry from a new request.

How long should I keep idempotency keys?

Long enough to cover your longest realistic retry. Stripe keeps its keys for at least 24 hours. Delete older rows with a scheduled cleanup.
