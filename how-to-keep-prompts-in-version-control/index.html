How to keep LLM prompts in version control

Store prompts as files in your repo, load them by name, review changes like code and tie each change to a test run. A layout and loader you can copy.

Put each prompt in its own file in the repo, load it by name at runtime, change it through pull requests, and run a small test set on every change. Prompts are code that happens to be written in English, and they break in the same ways.

Why not keep them inline

Prompts pasted into code as long strings are hard to read, hard to diff and easy to edit by accident. A prompt in a dashboard with no history is worse: nobody knows which version produced Tuesday's bad answers. Files in git give you history, blame, review and rollback for free.

A simple layout

prompts/
  classify_ticket.v1.md
  classify_ticket.v2.md
  summarize_thread.md
tests/prompts/
  classify_ticket.cases.jsonl
  test_prompts.py

Use a version in the filename only if you need to run two versions side by side, for instance in an A/B test. Otherwise git history is the version.

A loader with variables

from pathlib import Path
from string import Template

def load_prompt(name, **vars):
    text = Path("prompts", name + ".md").read_text()
    return Template(text).substitute(**vars)

prompt = load_prompt("classify_ticket", text=ticket_text)

Template.substitute raises on a missing variable, which is what you want. Avoid f-strings on loaded text, since braces in JSON examples clash with them.

Review and test changes

In a pull request, show the prompt diff and the change in test results side by side. A reviewer should see "accuracy on 60 cases: 52 to 55, no regressions" and not just changed words. How to build that check is in testing prompts before you ship.

Log which version ran

Record the prompt file name and the git commit with each model call or trace. When a user reports a bad answer, you can find the exact prompt text that produced it. A short hash of the prompt content works even if files move.

A deterministic gate in CI

The pattern behind Flisk's GEL (gel.flisk.si) fits prompts well: the model proposes, a deterministic score decides. Treat the pass rate on your fixed cases as the score, and fail the build below a threshold. Start with a threshold equal to the current rate and only let it go up. See also CI guards and AI code review.

Pitfalls.

  • Editing a prompt in production by hand "just this once". Every change goes through the repo.
  • Secrets or customer data inside prompt files. Templates hold instructions only.
  • Changing the model and the prompt in one commit. If results move, you will not know which caused it.
  • No owner. Name who reviews prompt changes, the same as for any other code path.

Questions people ask

Should prompts live in a database instead?

Only if non-developers must edit them live. Then keep history and test gates there too. For most teams, files and pull requests are simpler and safer.

What about prompts that contain user data?

Keep templates in git, and fill in user data at runtime. Never commit real customer text into prompt files or test sets without clearing it first.
