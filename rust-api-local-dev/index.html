Rust API local dev: axum, cargo watch and Docker

Rust compiles slowly the first time and fast after that, if the cache survives. This is how to keep the loop short with and without containers.

The shortest Rust dev loop is a plain process with a watcher: cargo watch -x run rebuilds and restarts on every save, and incremental builds keep it quick. Inside Docker, the loop is only fast if the cargo registry and the target folder are cached between builds. Flisk scaffolds an axum API for both: a cargo run process, or a container whose image rebuilds with BuildKit cache mounts.

What makes Rust loops slow

The first cargo build compiles every dependency, and that is the slow part. Later builds only recompile your crate. Anything that throws the target folder away makes every build a cold build. In a container this happens whenever the Dockerfile copies the source before it fetches dependencies, or when the build runs without a cache for the registry and target.

The plain approach

cargo install cargo-watch
cargo watch -x run

cargo-watch is not part of Cargo, and it is in maintenance mode, so watchexec -r -e rs -- cargo run is a fair alternative. Run cargo check in a second terminal for faster feedback while you type, since it skips code generation. For Docker, mount caches in the build step:

RUN --mount=type=cache,target=/usr/local/cargo/registry \
    --mount=type=cache,target=/app/target \
    cargo build

Cache mounts need BuildKit, which current Docker versions use by default.

The Flisk way, as a local process

npm install -g @flisk-sh/flisk
flisk resource billing --language rust --local --stack app --yes
flisk up --only billing

The scaffold is axum 0.8 on tokio, with a Cargo.toml whose binary is named app and a src/main.rs with a /health route. In local mode the service command is cargo run, so it needs the Rust toolchain on your machine and no Docker. It does not reload on save. To get a watcher, change command in service.json:

{
  "$schema": "https://flisk.sh/schema.service.json",
  "schemaVersion": 1,
  "appName": "billing",
  "appType": "backend",
  "command": "cargo watch -x run",
  "port": 4000,
  "healthCheckPath": "/health"
}

Check the port: the scaffold reads PORT from the environment, which Flisk sets from the manifest.

The Flisk way, in Docker

flisk resource billing --language rust --stack app --yes
flisk up

In Docker mode there is no live update. When you change a file, Tilt rebuilds the image, and the Dockerfile uses BuildKit cache mounts for the cargo registry and the target folder, so a rebuild recompiles your crate and not every dependency. The dev.command in the manifest is cargo run. The API is available at http://api.<project>.localhost/api/billing, and Flisk strips /api/billing before the request reaches axum, so define routes as /health and /invoices.

The container must listen on 0.0.0.0 and on PORT. The local scaffold binds localhost, which is right for a process and wrong for a container, so do not copy the bind address from one mode into the other.

Make the compile itself faster

Whatever runs the build, a few Cargo habits shorten the loop. Use cargo check while you edit, and a full build only when you run the program. Do not use --release in development, because optimised builds take much longer. On Linux, a faster linker such as lld or mold cuts the link step, which dominates small incremental builds. In Cargo.toml, [profile.dev] debug = "line-tables-only" reduces the debug information the compiler writes, and you still get readable backtraces. Finally, keep the dependency list short: every crate you add is compiled on a cold build, and each feature flag you do not need is extra work.

Pitfalls

  • Cold start of the first image. The first Docker build compiles all dependencies. Expect it to be slow once, and quick after that as long as the cache mounts are kept.
  • Pruning the Docker cache. docker builder prune removes the cache mounts, and the next build is cold again.
  • Mixing a Rust service with a local-process service. A project cannot mix command services with Dockerfile-built services, and Flisk reports MIXED_RUNTIME. Pick one runtime for the project. Ready-made image services such as Postgres are fine next to command services.
  • Disk space. target folders and image layers grow quickly. See Docker disk full if builds start failing.

Questions people ask

How do I auto-reload a Rust API on save?

Use cargo watch -x run or watchexec -r -e rs -- cargo run. Both rebuild and restart the process when a source file changes.

Why is my Rust Docker build slow every time?

Usually the dependency layer or the target folder is not cached. Order the Dockerfile so dependencies are fetched before source is copied, and use BuildKit cache mounts for the cargo registry and target.

Does Flisk live reload Rust inside a container?

No. In Docker mode Tilt rebuilds the image on a change, helped by cargo cache mounts. For the fastest loop run the service as a local process with a watcher command.
