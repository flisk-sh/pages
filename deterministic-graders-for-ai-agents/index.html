Deterministic graders for AI agents: check the work, not the words

Grade agents with code: database state, files, tool-call logs, schemas and regex. Faster, cheaper and more stable than asking another model.

  1. Grade the state, not the story
  2. Grade the tool calls
  3. Validate output shape

The best grader for an agent is a function that inspects what the agent did and returns pass or fail. Check final state (database rows, files on disk), the sequence of tool calls, output schemas and a few key phrases. These checks are free to run, repeatable and cannot be talked into a pass.

Grade the state, not the story

An agent can say "done, I created the record" and be wrong. Look at the system the agent was meant to change. After a run, query the database or read the files, then assert on them.

def grade_refund(db, case):
    row = db.execute(
        "SELECT status FROM orders WHERE id = ?", (case["order_id"],)
    ).fetchone()
    return row is not None and row[0] == "refunded"

This also catches the reverse mistake: an agent that changed something it should not have. Add a check that unrelated rows are untouched.

Grade the tool calls

Record every tool call with its arguments during the run. Then assert on that list. See testing tool calls and trajectories for deeper patterns.

def called(trace, name, **args):
    return any(
        c["tool"] == name and all(c["args"].get(k) == v for k, v in args.items())
        for c in trace
    )

assert called(trace, "refund_order", order_id="4821")
assert not called(trace, "delete_customer")

Validate output shape

When an agent returns JSON, validate it against a schema. A JSON Schema library gives you a clear error list. Check required fields, types and allowed values. A well-formed answer with the wrong enum value is a real failure that no human would spot while skimming.

Use text checks carefully

Regex and substring checks are fine for facts that must appear: an order number, a date, a URL. They are brittle for wording. Normalize case and whitespace, and check for the fact, not the sentence. If you find yourself writing a long regex to catch "polite refusal", that is a sign you need a model-based grader for that one case.

Combine graders into one score

Give each case a list of checks and report the fraction that passed, plus a hard fail if any critical check fails. Keep the scoring code in the repo, versioned with the cases. Then the number means the same thing next month. A score that code computes can be used as a CI gate, as shown in running agent regression tests in GitHub Actions. When you do need a judge for a fuzzy check, apply the cautions in LLM-as-judge pitfalls.

Questions people ask

What if the right answer has many valid forms?

Grade the effect rather than the text. Check the state change or the key fact, and allow any phrasing around it.

Are deterministic graders enough on their own?

For many agents, yes. Use a model grader only for qualities like tone or clarity, and keep a human-checked sample to verify it.
