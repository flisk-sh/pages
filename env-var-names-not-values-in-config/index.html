How to keep env var names, not values, in committed config

The repository should say which settings exist. It should never say what the production password is.

Commit the names of your configuration, not the values. List every variable a service needs in a manifest or an example file, keep the real values in an untracked .env or a secret store, and make the start fail loudly when a required name is missing. That way a new developer sees what to fill in, CI can check the list, and a leaked repository does not leak production.

Why names belong in git

Values do not: they change per machine and per environment, and anything committed stays in history even after you delete it. Names do: they are part of how the service works. Without a list, the knowledge lives in someone's head, and the first sign of a missing variable is a runtime error in production. There are three kinds of setting, and they need different homes:

KindExampleWhere it lives
Plain configlog level, feature flag, public URLCommitted, in the manifest or a defaults file
Secretdatabase password, API key, signing secretName committed, value in .env or a secret store
Per-environment valuethe database host in productionSet by the platform or the deploy step

The general approach with Compose

Docker Compose substitutes ${NAME} from a .env file or the shell. Two forms make the list enforceable:

services:
  api:
    environment:
      LOG_LEVEL: "${LOG_LEVEL:-info}"      # default when unset
      SESSION_SECRET: "${SESSION_SECRET:?set SESSION_SECRET in .env}"

The :- form gives a default for plain config. The :? form makes Compose refuse to start, with your message, when the variable is unset or empty. Add a .env.example with the same names and placeholders, and put .env in .gitignore.

The Flisk way

Flisk gives each kind a field in service.json:

{
  "env": { "LOG_LEVEL": "info", "DATABASE_URL": "${DATABASE_URL}" },
  "params": { "FEATURE_X": "on" },
  "secrets": {
    "required": ["SESSION_SECRET"],
    "optional": ["SENTRY_DSN"]
  }
}
  • params are non-secret strings. They are committed and written to a generated env file for the resource.
  • secrets.required is injected as ${NAME:?...}. Compose refuses to start the resource and names the missing variable.
  • secrets.optional is injected as ${NAME:-}, so the resource starts with the variable empty.
  • The values live in the project .env, which Flisk gitignores. Generated files are checked by flisk config verify and are meant to be committed, and nothing secret is written into them.

For one-off runs, flisk up --env-file <path> uses another file in place of .env for that run. The file replaces the default one. It is not merged with it, and it must hold the keys Flisk needs, such as DB_PASSWORD and JWT_SECRET. Do not put a real credential in a file you plan to commit.

Names carry through to deploy files

The same rule runs through the exporters, which makes the habit worth keeping:

  • flisk export render writes each key under env as a sync: false entry, which Render prompts for. Names under secrets and params are not exported, so add those by hand. See from local to Render.
  • flisk export wrangler lists the names in a comment and tells you to run wrangler secret put <NAME>. See the wrangler config guide.
  • flisk export compose writes ${NAME} for every required secret, so the server needs an .env that defines it. See deploy a standalone Compose file.

Pitfalls

  • Public prefixes expose values. Next.js NEXT_PUBLIC_* and Vite VITE_* variables are inlined into the browser bundle at build time. flisk doctor warns when it finds a secret-looking value in them, for example a Stripe secret key. A publishable key is fine.
  • Do not set jwtSecret in service.json. It is ignored and flisk doctor warns about it. The signing secret comes from JWT_SECRET in .env.
  • A committed secret is a leaked secret. Deleting the file does not remove it from history. Rotate the credential, then clean the history if you need to.
  • Changing a password later. A new DB_PASSWORD does not change a Postgres volume that already exists. Reset the volume or alter the role. More in reset a local database.
  • Do not paste secrets into logs or tickets. Show names, not values, when asking for help.
  • A secret store is not always needed. For a solo project, a protected .env on the server may be enough. Move to a store when several people or systems need the values.

Questions people ask

Should I commit .env.example?

Yes, with names and harmless placeholder values. It documents what a new developer must set. The real .env stays out of git. A manifest that lists required names does the same job and can be checked by tools.

What is the difference between params and secrets in a service.json?

In Flisk, params are plain non-secret strings that are committed and written to a generated env file. secrets lists names only, and the values come from the project .env at run time. Required names stop the start when they are missing.

Is a NEXT_PUBLIC or VITE variable a safe place for a key?

Only for keys meant for browsers, such as a publishable key. These variables are inlined into the JavaScript bundle at build time, so anyone can read them. Keep real credentials in server-side variables.
