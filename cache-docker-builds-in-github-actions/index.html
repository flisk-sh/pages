How to cache Docker builds in GitHub Actions for many services

A fresh runner has no layers. Give BuildKit a cache, keep each service's cache separate, and build only what changed.

A GitHub-hosted runner starts empty, so every job rebuilds every image from scratch unless you hand BuildKit a cache. Export and import the layer cache with type=gha (or a registry), order your Dockerfile so the dependency layers rarely change, and build only the services whose files changed. Expect the first run to be slow and later runs to reuse layers.

Why CI rebuilds everything

On your laptop the Docker daemon keeps every layer it has built. A fresh runner has none, so each RUN npm ci or pip install runs again, for every service, on every push. With five services that is five dependency installs before a single test starts. Two things reduce this: make the layers cacheable, and give the runner somewhere to store and fetch them between runs.

Step 1: make the Dockerfile cache-friendly

Docker reuses a layer when the instruction and everything before it are unchanged. Put the slow, rarely changing steps first:

FROM node:22-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

Copying only the manifest and lockfile before npm ci means a source change does not invalidate the install layer. Add a .dockerignore with node_modules, .git and build output, otherwise a changed file you never use still changes the build context. Most of the CI speedup comes from this step, and it helps on your laptop too.

Step 2: store the cache between runs

BuildKit can export its cache to the GitHub Actions cache. With docker/build-push-action:

- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v6
  with:
    context: services/orders-api
    load: true
    tags: orders-api:ci
    cache-from: type=gha,scope=orders-api
    cache-to: type=gha,scope=orders-api,mode=max

mode=max exports the intermediate layers as well, which is what you want for a multi-stage Dockerfile. scope keeps each service's cache separate, so one service does not evict another's layers. If you build with a Compose file, docker/bake-action can read it and apply the same cache settings to every service in one step.

The alternative is a registry cache, type=registry,ref=ghcr.io/your-org/your-app:buildcache. It is not limited by the repository cache quota and is shared with other machines, but you must be able to push to the registry from the job.

Know the limits of the Actions cache

  • A repository gets 10 GB of cache in total. Entries not used for seven days are removed, and older ones are evicted when you go over the limit. A big multi-service build can fill it.
  • A workflow run can restore caches made on its own branch or on the default branch. A cache written by a pull request is not visible to other pull requests, so the default branch should run the build and write the cache.
  • A cache hit still has a cost: layers are downloaded to the runner. For a small image that is slower than rebuilding it.

Step 3: build less

The cheapest layer is the one you never build. If only the frontend changed, do not rebuild the worker. A change filter in the workflow does this, and the article on running CI only for changed services shows how. Also cache what is not a layer: actions/setup-node accepts cache: npm (or pnpm, yarn) to restore the package manager's download cache.

Where Flisk fits

On the container path, Flisk builds your service images on the machine that runs flisk up, through Tilt. Its own CI guide says plainly that it does not describe caching Docker layers or the images Flisk builds, and that the time a cold build takes for your stack was not measured. So treat the BuildKit settings above as your own tuning, and measure before and after on your project rather than assuming a result. Two behaviours are worth knowing on a long-lived self-hosted runner: flisk up checks free disk first (it stops under 5 GiB and warns under 15 GiB), and it trims the shared Docker build cache to 20 GiB. Both limits can be changed with environment variables, FLISK_DISK_MIN_GIB, FLISK_DISK_WARN_GIB and FLISK_BUILD_CACHE_MAX_GIB. A GitHub-hosted runner is discarded after the job, so neither matters there.

If a stack runs as local processes (a command in each service.json), there are no images to build, and the package manager cache is the only cache that matters. That is one reason some teams run the fast checks that way, covered in running integration tests in CI without Docker.

Pitfalls

  • A cache that never hits. A COPY . . before the install, a timestamp or build argument that changes each run, or a different scope per job all defeat it. Look for CACHED in the build output.
  • Secrets in layers. Cache exports include layers. Do not COPY a .env into an image, and use BuildKit secret mounts for tokens.
  • Stale base images. A pinned tag never updates. Rebuild without the cache on a schedule to pick up security fixes.

When not to bother

If a full build takes a minute or two and the job runs a few times a day, a cache adds moving parts for little gain. Add it when image builds are the largest part of your wall time, and keep the cold path working so a cache problem never blocks a merge.

For the other half of CI time, the start-up wait, read how to wait for every service to be healthy before CI tests.

Questions people ask

How big can the GitHub Actions cache be?

A repository gets 10 GB in total. Entries not accessed for seven days are removed, and the oldest are evicted when the limit is reached.

Should I use type=gha or a registry cache?

type=gha needs no registry and is easy to start with. A registry cache is not bound by the repository quota and can be shared with other machines, but the job needs push access to the registry.

Does Flisk cache Docker layers in CI?

Flisk builds images on the machine that runs flisk up. Its CI guide does not claim a CI cache recipe or a measured saving, so configure BuildKit caching yourself and measure it.
