How to keep a search index in sync with your database locally

A search index is a copy. Treat it as rebuildable, write to it idempotently and give yourself one command that makes it right again.

Keep a search index in sync by treating it as a disposable copy of the database: write to it with idempotent upserts keyed by the row id, run a full reindex command that rebuilds it from scratch, and add change-time updates on top for freshness. If the index is wrong, you run the rebuild instead of debugging it. That works the same for Meilisearch, Typesense, OpenSearch and a vector store.

Start with the rebuild

Write the reindex first, because every other approach depends on it. It reads rows in pages, converts each to a search document, and upserts them. Because the id is the key, you can run it twice and get the same result:

// scripts/reindex.mjs
import pg from "pg";

const db = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const MEILI = process.env.MEILI_URL;           // http://search:7700 inside the stack
const PAGE = 500;

let last = 0, total = 0;
for (;;) {
  const { rows } = await db.query(
    "SELECT id, title, body, updated_at FROM articles WHERE id > $1 ORDER BY id LIMIT $2",
    [last, PAGE],
  );
  if (rows.length === 0) break;
  const res = await fetch(`${MEILI}/indexes/articles/documents`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(rows),
  });
  if (!res.ok) throw new Error(await res.text());
  last = rows[rows.length - 1].id;
  total += rows.length;
}
console.log(`indexed ${total} rows`);
await db.end();

Paging by id > $1 (keyset paging) stays fast and does not skip rows when data changes during the run, unlike OFFSET. Deleted rows are the gap: a reindex that only upserts will leave deleted rows in the index. For a true rebuild, create a new index, fill it, then swap it in (Typesense aliases and OpenSearch aliases exist for this, and Meilisearch has an index swap). Writes in Meilisearch are asynchronous, so a script that must be sure of the result waits on the returned task.

Keeping it fresh

There are three patterns, in rising order of effort:

  • Write in the same code path. After the database commit, update the index. Simple, but if the second step fails the two disagree, and nothing notices.
  • An outbox. In the same transaction as the change, insert a row into an outbox table. A worker reads unprocessed rows, updates the index and marks them done. A crash between the two steps just means the row is retried, which is safe because upserts are idempotent. This is the pattern to use when the index must not silently drift.
  • Change data capture. Stream the database's change log into the index. Capable, and far more than a development setup needs.

For local work, the first pattern plus the rebuild command is usually enough. Add the outbox when you see drift you cannot explain.

The Flisk way

The index is a bring-your-own service (see run Meilisearch locally), and the reindex script is a one-off command, not a long-running service. Run it inside the stack with the environment its service has:

flisk run api -- node scripts/reindex.mjs

flisk run <service> -- <command> runs the command in that service's container, which needs the stack to be running. The container already has DATABASE_URL and MEILI_URL because the service depends on the database and the search resource. See run a one-off command in a service. I did not execute flisk run while writing this article, so check the output on your version.

If the index data is wrong beyond repair, or you want a clean start, stop the stack and remove the search volume with flisk down --purge, then bring it up and run the reindex. Remember that --purge removes all the project's volumes, the database included, so use it only when you also expect to reseed. For routine fixes, rebuild into a new index instead. For the seeding side, see seed a local database.

A migration that adds a searchable column should also trigger a reindex. Put the reindex after the migrator in your startup order, or document it in your README as the second command after seeding.

Detect drift

A cheap check compares counts. Add it to your test setup or run it by hand:

SELECT count(*) FROM articles;                       -- database
curl -s $MEILI_URL/indexes/articles/stats            # numberOfDocuments

Counts do not catch stale content, so also compare a checksum or the highest updated_at of each side for a sample. If a search result points at a row that no longer exists, that is the deleted-row gap above.

Pitfalls

  • Do not index secrets. Whatever you send is readable by anyone who can query the index. Build documents from an allow-list of fields.
  • Batch size. Very large batches hit request limits. A few hundred to a few thousand documents per call is a sensible start. Measure with your real data.
  • Asynchronous indexing. A test that writes and then searches immediately can fail. Wait for the task or poll until the document appears.
  • Schema drift. When a document shape changes, old documents keep the old shape until reindexed.

When not to use this

If the search lives in Postgres itself, there is nothing to sync. See Postgres full-text search.

Next, make sure your tests exercise the index with real data using integration tests against the real stack.

Questions people ask

Why not update the index and the database in one step?

They are separate systems, so no single transaction covers both. Use idempotent upserts and a rebuild command so any mismatch can be repaired, and add an outbox if drift matters.

How do I remove deleted rows from the index?

An upsert-only reindex cannot. Rebuild into a new index and swap it in, or send explicit delete calls from the same code path that deletes the row.

How often should I reindex?

Locally, whenever the document shape or the data changes in a way the live updates do not cover. In production, run it as a scheduled or on-demand job with monitoring.
