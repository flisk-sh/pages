Env vars and secrets in local dev

Docker Compose env_file vs environment vs .env: the difference

The .env file next to a Compose file does not put anything inside your container. That surprises many people, and it explains most of the confusion.

A .env file next to a Compose file fills in ${NAME} placeholders in the Compose file itself. It does not put variables into containers. environment: sets variables inside a container, and env_file: loads a file of variables inside a container. Mixing up the first with the other two is the root of most "my variable is not set" reports.

Three tools, three jobs

MechanismJobVisible in the container?
.env next to compose.yamlSupplies values for ${NAME} in the Compose file (interpolation)Only if the Compose file uses the placeholder somewhere that reaches the container
env_file:Loads a file of KEY=value lines into the containerYes
environment:Sets single variables for the container, a literal or an interpolated valueYes

Here is a file that uses all three:

services:
  api:
    image: my-api
    env_file:
      - ./api.env
    environment:
      LOG_LEVEL: debug
      DATABASE_URL: "postgres://app:${DB_PASSWORD}@db:5432/app"

Here DB_PASSWORD comes from the shell or from .env, is substituted into the Compose file, and arrives in the container as part of DATABASE_URL. DB_PASSWORD itself is not a variable inside the container unless you also list it. The variables in api.env arrive as they are, with no substitution.

Which one wins

For a variable inside the container, Compose documents this order, strongest first:

  1. A value passed with docker compose run -e.
  2. A value in environment: (after interpolation).
  3. A value from env_file:.
  4. An ENV instruction baked into the image.

For interpolation, a variable in your shell beats the same name in .env. You can pick another file with docker compose --env-file path, which replaces the default .env for that command.

Use docker compose config to see the result after interpolation and before anything starts. It prints the final file with every placeholder filled in, which is the fastest way to catch a typo or an empty value. Mind that it prints secrets in clear text, so do not paste its output into a ticket.

Make a missing variable stop the start

An unset placeholder becomes an empty string with only a warning. Two forms avoid that:

environment:
  LOG_LEVEL: "${LOG_LEVEL:-info}"           # default when unset or empty
  SESSION_SECRET: "${SESSION_SECRET:?set it in .env}"   # refuse to start

The :? form makes Compose stop with your message, which beats a container that boots with an empty secret.

What Flisk generates for you

Flisk's container path generates the Compose files, so you do not write these entries yourself, but the same three mechanisms are in use, and knowing them explains the behaviour:

  • The project .env (or the file passed to flisk up --env-file) is handed to Compose as its interpolation file.
  • params in a service.json are written to a generated .env.backend.autogenerated and loaded as the service env file. They are for non-secret values only.
  • Names under secrets become entries in environment:. A required name is written as ${NAME:?...} and an optional one as ${NAME:-}.
  • Because environment: beats the service env file inside the container, a generated value in environment such as DATABASE_URL beats anything from the params file.

A manifest that uses both fields:

{
  "appName": "orders-api",
  "appType": "backend",
  "params": { "LOG_LEVEL": "debug" },
  "secrets": { "required": ["STRIPE_KEY"], "optional": ["SENTRY_DSN"] }
}

Do not hand-edit the generated files. Edit service.json and run flisk config regenerate. Check what the container ends up with using flisk run orders-api -- printenv LOG_LEVEL. If you already have a Compose file you want to keep, exporting a standalone Compose file shows how the names carry across.

Pitfalls

  • Putting a secret in params. That file is generated plain text. Use secrets.
  • Expecting .env to reach the container. It only fills placeholders. List the variable under environment: or use env_file:.
  • A $ in a value. Compose expands it. Write $$ in Compose files, which Flisk does for you in params.
  • Changing a value and not recreating. A running container keeps its old environment. Recreate it.

The order across all sources, including the shell, is laid out in which .env file wins.

Questions people ask

Why is my variable in .env not visible inside the container?

Compose uses .env only to substitute ${NAME} in the Compose file. To put a variable in the container, reference it under environment: or load a file with env_file:.

Which wins, env_file or environment?

environment wins over env_file when both define the same name. A value passed with docker compose run -e wins over both.

How do I see the final values Compose will use?

Run docker compose config. It prints the file after interpolation. Treat the output as sensitive because it can contain secrets in clear text.
