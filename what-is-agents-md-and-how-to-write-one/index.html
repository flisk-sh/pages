What is AGENTS.md and how to write one

AGENTS.md is a plain Markdown file with instructions for coding agents. Learn what belongs in it, what to leave out and how to keep it short enough to be obeyed.

AGENTS.md is a Markdown file at the root of a repository that tells coding agents how to work in it: which commands to run, which rules to follow and which files to avoid. It has no required fields. Write it like a short briefing for a careful new contributor.

What goes in the file

Put in what an agent cannot learn by reading the code and what costs you time when it gets wrong. Typical sections are:

  • Commands for install, build, test and lint, exactly as you run them.
  • A short repository map.
  • Rules: coding conventions, naming, error handling.
  • Things never to do: edit generated files, commit secrets, touch a vendored folder.
  • How to prepare a pull request: commit format, required checks.

A minimal example

# AGENTS.md

## Commands
- Install: npm install
- Test: npm test
- Lint: npm run lint (fix with npm run lint:fix)

## Rules
- Do not edit files under dist/ or anything named *.generated.*.
- Every behaviour change needs a test in the same pull request.
- Never commit .env files or API keys.

## Pull requests
- One change per pull request.
- Sign off commits with git commit -s.

Notice that each line is a concrete instruction. "Write clean code" tells the agent nothing.

Keep it short

Agents load this file into their context on every task. A 600-line file crowds out the task and gets partly ignored. Aim for under 100 lines. If a rule applies to one folder, put a second AGENTS.md in that folder. Most tools that support the format use the file closest to the code being edited, but check your tool's docs for the exact lookup rule.

Link out instead of copying. "Read docs/architecture.md before changing src/engine" costs one line and the agent reads it only when needed.

Rules that work and rules that do not

WeakBetter
Follow best practicesUse the existing Result type, not thrown errors
Test your changesRun npm test and paste the summary line in the pull request
Be careful with the databaseMigrations live in db/migrations. Never edit an applied one.

A good rule names a command, a path or a type. If you have caught the same mistake twice in review, write the rule for it.

Keep it honest

Every command in the file must work. Run them after you write them, and again when the project changes. A wrong command is worse than none, because the agent trusts it. See How to keep docs from going stale for a way to test this in CI. For how this file relates to other instruction files, read AGENTS.md vs CLAUDE.md vs README.

Questions people ask

Is AGENTS.md an official standard?

It is a convention that several coding tools read, not a formal standard. It is plain Markdown, so nothing breaks if a tool ignores it.

Where do I put it?

At the repository root. Add more in subfolders for rules that only apply there.

Can I generate it with an agent?

You can draft it that way, but review every line and run every command yourself before you commit it.
