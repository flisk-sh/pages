How to test prompts before you ship a change

Build a small fixed set of real cases, run old and new prompts on it, score with code, and block regressions in CI. A minimal harness you can start with today.

Collect 30 to 100 real inputs with expected outputs, run your prompt on all of them, score with plain code, and compare against the current prompt before merging. A fixed set turns prompt editing from guesswork into a measured change.

Build the case file

One JSON object per line: the input, the expected output and a note. Take inputs from real traffic with personal data removed, and add every bug report as a new case. Cover the typical, the hard and the out-of-scope.

{"input": "I was charged twice in March", "expect": {"category": "billing"}}
{"input": "Do you have a podcast?", "expect": {"category": "other"}}

Run and score with code

import json

def run(prompt_fn, cases_path):
    ok = 0; rows = []
    for line in open(cases_path):
        c = json.loads(line)
        got = prompt_fn(c["input"])        # your model call, parsed
        good = got.get("category") == c["expect"]["category"]
        ok += good
        rows.append((c["input"], good))
    return ok / len(rows), rows

score, rows = run(classify, "tests/prompts/classify.cases.jsonl")
assert score >= 0.90, f"pass rate fell to {score:.2f}"

Exact-match scoring on labels and fields is cheap and unambiguous. Use it wherever you can.

When code cannot score it

For free text, test properties: valid JSON, length under a limit, contains required facts, does not contain banned phrases. If you still need a model to grade quality, keep it as a second signal, calibrate it against human judgements, and never let the same prompt grade its own output. The hub on testing and evaluating AI agents goes further.

Compare, do not just pass

Run the old prompt and the new prompt on the same cases and diff the results: what got fixed, what broke. A change that lifts the average but breaks three important cases may not be worth shipping. Print the failures, not just the score, so a reviewer can look at them.

Put it in CI

Run the suite on every pull request that touches a prompt or model setting. Model calls cost money and take time, so keep the set small, cache by prompt hash and input, and run the larger set nightly. Use a ratchet: the threshold equals the best pass rate so far and may only rise. This "model proposes, deterministic score decides" pattern is what Flisk's GEL approach is built on, and you can adapt the idea without any tool. See also repeatable output for reducing flakiness in these runs.

Common traps

  • Tuning the prompt on the same cases you score on. Hold back a third of the cases that you never look at while editing.
  • A set of only easy inputs, so every version scores 100 percent.
  • Ignoring cost and latency. Record tokens and time per run as well, since a prompt that doubles them has a price.

Questions people ask

How many test cases are enough?

Start with 30 to 50 that reflect real use and grow the set with each bug. Quality and coverage matter more than raw count.

Can I use an LLM to judge the outputs?

For subjective quality, sometimes. Calibrate it against human labels, use a different prompt from the one being tested, and keep deterministic checks as the main gate.
