How to test a Pydantic AI agent without calling a real model

Tests that call a real model are slow, cost money and give a different answer each run. Pydantic AI has test models built for this.

Pydantic AI lets you swap an agent's real model for a TestModel or a FunctionModel inside a test, so the agent runs, calls its tools and validates its output without any network call. You can then assert on tool arguments and on the final result with plain pytest, and block real requests globally so a forgotten override cannot spend money.

Why mock the model at all

A language model is the least testable part of your service: it is slow, its output varies, and every call costs something. What you actually want to test is your code around it: the tools you registered, the prompts you build, the way you parse and store the output. Those are deterministic, and they break when you refactor. So the model gets replaced and the rest runs for real.

Pydantic AI supports this directly. Do not confuse it with mocking an entire service in an integration test; the trade-off between the two is covered in mock or run the real service.

The agent under test

Define the agent in a module. Passing defer_model_check=True delays building the model client until the first run. Without it, a model string such as an OpenAI one can fail at import time when the API key is missing, which breaks test collection on a clean machine.

# src/support.py
import os

from pydantic_ai import Agent

agent = Agent(
    os.environ.get("MODEL", "openai:gpt-4o"),
    instructions="You answer order questions. Use the lookup tool.",
    defer_model_check=True,
)


@agent.tool_plain
def lookup_order(order_id: str) -> str:
    return f"order {order_id}: shipped"

Test with TestModel

TestModel calls every tool you registered once, with generated arguments, and then returns a text answer built from the tool results. It is the quickest way to check that the agent wires up and that your tool runs.

# tests/test_support.py
from pydantic_ai import models
from pydantic_ai.models.test import TestModel

from support import agent

models.ALLOW_MODEL_REQUESTS = False  # any real request now raises


def test_agent_runs_and_uses_the_tool():
    with agent.override(model=TestModel()):
        result = agent.run_sync("Where is order 7?")
    assert isinstance(result.output, str)
    assert "shipped" in result.output

The assignment to ALLOW_MODEL_REQUESTS is the safety net. Put it in conftest.py so every test file gets it. Result attribute names have changed between releases (older versions used .data), so check the version you have installed.

Script the model with FunctionModel

When you need a specific sequence, for example "call the tool with this id, then answer", use a FunctionModel. It receives the message history and returns what the model would have said, so you control every step and can assert on what your code sent.

from pydantic_ai.messages import ModelResponse, TextPart, ToolCallPart
from pydantic_ai.models.function import FunctionModel


def scripted(messages, info):
    if len(messages) == 1:
        return ModelResponse(parts=[ToolCallPart("lookup_order", {"order_id": "7"})])
    return ModelResponse(parts=[TextPart("Order 7 has shipped.")])


def test_scripted_flow():
    with agent.override(model=FunctionModel(scripted)):
        result = agent.run_sync("Where is order 7?")
    assert result.output == "Order 7 has shipped."

The first call sees one message (the user prompt) and answers with a tool call. The second call sees the tool result and answers with text. This also lets you test the unhappy paths that are hard to trigger on a real model: a tool call with a bad argument, or an empty reply.

Where Flisk fits

Flisk does not run your unit tests, and it has no Pydantic AI integration. It helps in two small ways. The Python service it scaffolds (flisk resource <name> --type backend --language python --local) already contains a tests folder, a pytest configuration with pythonpath = ["src"] and a dev extra that installs pytest, so the layout above works as it is. And once the unit tests pass, you can run the same service in the stack with a real key and check the full path, as described in integration tests against the real stack.

What these tests cannot tell you

  • Prompt quality. A scripted model proves your plumbing, not that a real model follows your instructions. Keep a small set of real-model checks that you run by hand or in a scheduled job.
  • Tool-call behaviour of a specific model. TestModel calls every tool, which a real model will not. Do not read a passing test as proof that the model picks the right tool.
  • Cost and latency. Only a real run measures those.

Questions people ask

Why does my agent fail on import with a missing API key?

Building a model client for a provider string can need the key right away. Create the agent with defer_model_check=True so the client is built on first run, and override the model in tests.

Is TestModel a good test of tool selection?

No. It calls every registered tool once, so it checks that tools are wired and run. Use FunctionModel to script a specific path, and a real model to judge tool choice.

Can I use the same approach for other frameworks?

The idea carries over: put the model behind an interface and replace it in tests. Other frameworks name the pieces differently, so check their own testing docs.
