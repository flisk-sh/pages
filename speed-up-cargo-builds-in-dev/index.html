How to speed up Cargo builds in local development

A cold Rust build is slow for good reasons. Most of the daily wait is avoidable if you stop rebuilding what has not changed.

The fastest wins are using cargo check while you type, keeping debug builds out of release mode, and caching compiled dependencies so that only your own crate is rebuilt. After that, a shared compiler cache and a faster linker help on larger projects. Start by finding out where the time goes, because the cure for slow compiling differs from the cure for slow linking.

Measure first

Run a clean build with timings and open the report it writes:

cargo clean
cargo build --timings

The report shows which crates took longest and how much ran in parallel. If one dependency dominates, look at its feature flags. If your own crate dominates, the steps below matter more. For a second build after a one-line change, the time is mostly your crate plus the link step, so that is the number to watch for the edit loop.

Change how you build while editing

  • Use cargo check. It type-checks without generating machine code, so it returns much sooner than cargo build. Run it in a second terminal, or let rust-analyzer do it. Build or run only when you need the program.
  • Stay in the dev profile. --release turns on optimisation and costs far more time per build. Use it for benchmarks, not for the edit loop.
  • Write less debug information. In Cargo.toml:
[profile.dev]
debug = "line-tables-only"   # keeps readable backtraces, drops variable info

[profile.dev.package."*"]
opt-level = 1                # optimise dependencies, keep your crate fast to build

The second block is a trade: it makes the first build of dependencies slower, and it can make a heavy dependency (a parser, an image decoder) run quicker while you test. Remove it if you do not need it. Note that line-tables-only removes the variable view in a debugger, so switch it back when you are stepping through code, as described in debugging Rust with LLDB.

Cache compiled work

sccache caches the output of rustc, so a dependency you compiled in another project or branch is reused.

cargo install sccache --locked
export RUSTC_WRAPPER=sccache
cargo build
sccache --show-stats

It does not cache the final link, and incremental compilation of your own crate is switched off while it wraps rustc, so it pays off for dependency-heavy projects and for CI, and less for a single crate that you edit all day.

Speed up the link step

For small edits the linker is often the longest part. On Linux, mold or lld is much quicker than the default GNU linker. With mold installed, a .cargo/config.toml in the project is enough:

[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=mold"]

On a Mac the system linker is already acceptable for most projects, so measure before you change it.

Share one target folder, with care

Each Cargo project builds into its own target folder. If you keep several services in one repo, put them in one Cargo workspace so that they share a target and a lock file, and a dependency compiles once. Separate projects can share a folder through CARGO_TARGET_DIR, but Cargo takes a lock on it, and a second build waits with the message "Blocking waiting for file lock". Two services building at once then queue instead of running in parallel.

Where Flisk fits

Flisk does not compile your code faster. It decides when and how the build runs. With the local scaffold the command is cargo run and there is no Docker:

flisk resource billing --language rust --local --stack app --yes
flisk up --only billing

Set environment variables for the process in the env field of service.json, for example "env": { "RUSTC_WRAPPER": "sccache" }, and make sure the tool is installed, because Flisk refuses to start a service whose program is missing from the machine. On the Docker route, the generated Dockerfile uses BuildKit cache mounts for the cargo registry and the target directory, so changing a source file recompiles the crate and not every dependency, as the Flisk Rust notes describe. That Docker route does not reload on save; Tilt rebuilds the image. The full comparison is in Rust API local dev.

Pitfalls

  • Changing RUSTFLAGS or the toolchain. Either one invalidates cached builds, and the next build is cold. Pin both in the repo.
  • Pruning Docker build cache. It also removes cache mounts. If builds suddenly turn cold, check Docker disk full for what you pruned.
  • A huge target folder. It grows with every toolchain and profile. cargo clean reclaims it, at the price of a cold build.

Questions people ask

Is cargo check faster than cargo build?

Yes. It skips code generation, so it finishes sooner. It still reports type and borrow errors, which is what you need while editing.

Does sccache speed up incremental builds?

Mostly not. It helps with dependencies and clean builds. Incremental compilation of your own crate is turned off while sccache wraps rustc.

Does Flisk cache Rust builds?

In Docker mode the generated Dockerfile uses BuildKit cache mounts for the cargo registry and target directory. In local mode it just runs your command, so Cargo's own cache applies.
